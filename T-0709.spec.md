# T-0709 [E16/P1] — /api/process-catalog: current step/role = REAL live Flowable node

Parent: capstone T-0691 / T-0349. Found live on the «Процессы» screen.

## Problem

`GET /api/process-catalog` returned each instance's `step`/`role` from the
`process.started` audit event — a SNAPSHOT written once at start time (the resolved
active user-task then, or, when the engine read came back empty, the config-primitive
fallback `resolveDefaultApproveStep`/`resolveDefaultApproverRole`). That snapshot is
NEVER re-derived as the engine token advances (or when a skip-submit auto-complete
moved the token AFTER the snapshot was written). Result: a running instance whose live
Flowable token sits on the initiator's submit step showed the NEXT approval step's
label/role on the catalog — e.g. «Согласование»/role-approver while the engine
(`/api/processes/:inst`, which reads the LIVE history via `getHistoricActivityInstances`,
`endedAt=null` on the current node) had the token on «Подача заявки»/role-initiator
(progress 0/2). The two surfaces disagreed: the «Процессы» screen said "waiting on the
approver" when it really waited on the initiator who had not yet submitted.

## Root cause

The catalog's step/role is a frozen start-time projection of `audit_event(process.started)`;
the instance-detail route reads the live engine. Same instance, two sources of truth →
divergence. No live-engine reconciliation existed on the catalog read path.

## Fix

Overlay each NON-DONE instance's displayed `step`/`role` with the engine's REAL active
user-task — the SAME live source `/api/processes/:inst` reads — before serializing the
catalog wire. Read via `flowable.getActiveUserTasks(instanceId)`
(`candidateGroups[0]` → role, `name` → step); reduce to the primary active node and
overlay. The audit track is NOT rewritten — this is a display-time correction of the
CURRENT-step label only.

- Pure core: `pickPrimaryLiveNode(tasks)` + `overlayLiveSteps(projections, liveByInst)`
  in `src/core/process-catalog-view.ts` (no engine dep, no case literals, no I/O).
- HTTP: `src/http/process-catalog.ts` gains an optional `flowable?: CatalogEnginePort`;
  the GET handler batch-resolves live nodes for the running instances and overlays.
- Wiring: `src/server.ts` passes the shared `flowableClient`.

## Acceptance

1. A running instance whose snapshot froze the NEXT step is reported on the LIVE first
   step/role by `/api/process-catalog` (overlay applied). Proven at the HTTP boundary
   (`process-catalog-live-step.test.ts` AC-1) and as pure logic
   (`process-catalog-view.test.ts` "ACCEPTANCE (родитель T-0349)").
2. A DONE instance is never overlaid — keeps its terminal projection.
3. Consistency catalog ↔ `/api/processes/:inst`: both derive the current node from the
   engine's live active user-task, so they no longer disagree.
4. Honest degrade: no flowable dep, engine unreachable per-instance, or no active
   user-task ⇒ the projection is returned UNCHANGED (the pre-T-0709 snapshot) — never
   worse than today, never a 500. Tenant-scope/PDP untouched (RLS + resolveActorTenant
   as before).
5. Anti-case: zero D-064 case literals added under `src/` (fixtures are neutral).

## Non-goals

- Not rewriting the audit projection or the `/api/processes` display plane.
- Not a full BPMN-count of unobserved future steps (ADR T-0278 §2.3 rejected a live
  engine query on the base read as disproportionate — this overlay is a bounded,
  best-effort fan-out over the already-capped running-instance page, off the critical
  path).
