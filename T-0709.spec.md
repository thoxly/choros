# T-0709 [E16/P1] — current step/role = REAL live Flowable node on BOTH read surfaces

Parent: capstone T-0691 / T-0349. Found live on the «Процессы» screen.

## Problem

Both process-read surfaces returned each instance's `step`/`role` (and the detail
route's `node`/`nodes`) from the `process.started` audit event — a SNAPSHOT written once
at start time (the resolved active user-task then, or, when the engine read came back
empty, the config-primitive fallback `resolveDefaultApproveStep`/`resolveDefaultApproverRole`).
That snapshot is NEVER re-derived as the engine token advances (or when a skip-submit
auto-complete moved the token AFTER the snapshot was written). Result: a running instance
whose live Flowable token sits on the initiator's submit step showed the NEXT approval
step's label/role — e.g. «Согласование»/role-approver while the engine really had the
token on «Подача заявки»/role-initiator (progress 0/2). The «Процессы» screen said
"waiting on the approver" when it really waited on the initiator who had not yet submitted.

## Root cause

The catalog (`GET /api/process-catalog`) AND the instance list/detail
(`GET /api/processes`, `GET /api/processes/:inst`) both derive the current step/role from
the SAME audit-snapshot projection (`listInstanceProjections`):

- catalog: `serializeInstance(projection).step/role`
- detail:  `projectionToInstance(projection).node/nodes`

`fetchInstanceHistoryDetail` (which DOES read the live engine via
`getHistoricActivityInstances`) only populated a separate `history[]` array — it never
overwrote `node`/`nodes`. So the "current step" was a frozen start-time projection on
BOTH surfaces; no live-engine reconciliation existed on either read path.

> Note (judge P0, corrected premise): the ORIGINAL spec incorrectly claimed
> `/api/processes/:inst` already read the live engine for its current step and that the
> catalog fix brought consistency with it. It did NOT — both surfaces read the same
> snapshot. Fixing only the catalog would have introduced a NEW divergence (catalog live,
> detail frozen). This revision applies the SAME live overlay to BOTH surfaces from ONE
> shared source, so they cannot disagree.

## Fix

Overlay each NON-DONE instance's displayed `step`/`role`/`concurrentSteps` (→ detail
`node`/`nodes`) with the engine's REAL active user-task set — read via
`flowable.getActiveUserTasks(instanceId)` (`candidateGroups[0]` → role, `name` → step) —
BEFORE serialization. The audit track is NOT rewritten: this is a display-time correction
of the CURRENT-step label only.

- **Single source of truth.** One pure core (`src/core/process-catalog-view.ts`) owns
  `pickPrimaryLiveNode` + `overlayLiveSteps` + `resolveLiveNodesByInstance` +
  `CatalogEnginePort`. BOTH HTTP surfaces feed their projections through it:
  - `src/http/process-catalog.ts` — GET /api/process-catalog (already, T-0709 v1).
  - `src/http/processes.ts` — GET /api/processes and /api/processes/:inst (this revision),
    via `overlayDetailLiveSteps` reusing the shared core. processes.ts stays pg-free and
    reaches the engine ONLY through the injected client's read method (FF-7-3 intact).
  `overlayLiveSteps` additionally overlays `concurrentSteps` for projections that carry
  the field (the detail plane's `InstanceProjection` → `nodes`); the catalog's
  `ProjectionLike` has no such field and stays byte-identical.

- **Deterministic primary on an AND-split (judge P1).** `getActiveUserTasks` appends no
  `sort=` — its response order is undocumented. So `pickPrimaryLiveNode` no longer takes
  `tasks[0]`; it orders tasks by an INTRINSIC stable key `(taskDefinitionKey, then id,
  then name)` and picks the first of that order. Two consecutive GETs for the same
  AND-split instance therefore report the SAME primary. When there is >1 active user-task
  the node is flagged `ambiguous: true` and ALL branches surface in `concurrentSteps` —
  mirroring the codebase's `AMBIGUOUS_ACTIVE_TASK` precedent (process-projection.ts:
  1719-1726) that treats >1 active task as a real structural fact to surface, not a
  silent array-index-0 collapse. (For a DISPLAY overlay, concurrent branches are
  legitimate, so we surface-not-refuse; the completion path keeps its hard refusal.)

- **Bounded critical-path cost (judge P2).** `resolveLiveNodesByInstance` takes an
  optional shared wall-clock `deadlineMs` budget (`LIVE_OVERLAY_DEADLINE_MS = 2000`).
  Once it elapses, in-flight per-instance calls are abandoned (results ignored) and no
  further instance is started — a uniformly-slow-but-alive engine can slow the read by at
  most ~2s, not ~30s × N. Abandoning a call only means "keep that instance's snapshot".

## Acceptance

1. A running instance whose snapshot froze the NEXT step is reported on the LIVE first
   step/role by `/api/process-catalog` (catalog overlay) AND by `/api/processes[/:inst]`
   (detail overlay). Proven at the HTTP boundary (process-catalog-live-step.test.ts AC-1;
   processes-live-instances.test.ts AC-D1) and as pure logic (process-catalog-view.test.ts).
2. A DONE instance is never overlaid on either surface — keeps its terminal projection.
3. **Consistency catalog ↔ list ↔ instance-detail**: all three derive the current node
   from the engine's live active user-task via the SAME core, so they cannot disagree.
   Proven: processes-live-instances.test.ts AC-D4 (list ↔ detail through the real
   handlers) + process-catalog-view.test.ts "catalog ↔ detail derive the SAME live node
   from ONE source" (shared-core invariant).
4. Honest degrade: no flowable dep / no getActiveUserTasks method, engine unreachable
   per-instance, no active user-task, or the shared deadline elapsing ⇒ the projection is
   returned UNCHANGED (the pre-T-0709 snapshot) on BOTH surfaces — never worse than today,
   never a 500. Tenant-scope/PDP untouched.
5. AND-split (P1): >1 active user-task → deterministic primary (by taskDefinitionKey/id,
   NOT response order) + `ambiguous:true` + all branches in `nodes`/concurrentSteps.
   Proven: process-catalog-view.test.ts (determinism across arrival orders) +
   processes-live-instances.test.ts AC-D3.
6. Anti-case: zero D-064 case literals added under `src/` (fixtures are neutral).

## Non-goals

- Not rewriting the audit projection.
- Not a full BPMN-count of unobserved future steps (ADR T-0278 §2.3 rejected a live
  engine query on the base read as disproportionate — this overlay is a bounded,
  best-effort, deadline-capped fan-out over the already-capped running-instance page).

## Follow-ups

- **T-0709-R-N-1 (observability, non-blocking):** engine-down vs no-active-task vs done
  are indistinguishable to operators in `resolveLiveNodesByInstance` (both omit the key).
  A debug-level log/counter on `!result.ok` specifically would make a real outage
  observable without changing the honest-degrade wire behaviour. Deferred.
- **`ambiguous` on the wire:** the flag is computed in the core and available to overlay
  consumers, but neither read surface currently serializes it to the client. Surfacing
  "N concurrent branches" in the UI is a small display follow-up (the data is honest today
  via `nodes`/`concurrentSteps`; the flag is the explicit signal).
