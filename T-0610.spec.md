## 1. Проблема

`src/http/invoke.ts::loadCallerInvokeGrants` — отдельный (не через
`getGrantsForSubject`) authority-путь для invoke-эффектов. Найдено security-ревью
T-0605 (`docs/review/T-0605.review.json`, находка **F-1**, severity info,
"security / out-of-scope" — предсуществующая дыра, НЕ регрессия T-0605, файл
диффом T-0605 не тронут):

> Отдельный (не через getGrantsForSubject) authority-путь для invoke-эффектов
> имеет ИНЛАЙН-запрос, который JOIN'ит role_assignment на employee_id БЕЗ
> КАКОГО-ЛИБО предиката активности назначения (нет confirmed_by IS NOT NULL, нет
> confirmed2/proposed-гейта, нет окна) и грузит гранты БЕЗ
> confirmed_by/confirmed2/критичного-гейта (только operation='invoke'). Это
> значит invoke-путь игнорирует дуал-контроль ГРАНТА полностью и даже
> proposal-статус НАЗНАЧЕНИЯ.

### 1.1. Наблюдаемое поведение (текущий код, `src/http/invoke.ts:261-307`)

```sql
SELECT g.id, g.role_id, g.resource_type, g.resource_facet,
       g.operation, g.scope, g."constraint", g.delegable,
       g.granted_by, g.valid_from, g.valid_until, g.created_at
   FROM choros."grant" g
   JOIN choros.role_assignment ra
     ON ra.tenant_id = g.tenant_id AND ra.role_id = g.role_id
  WHERE g.tenant_id = $1
    AND ra.employee_id = $2
    AND g.operation = 'invoke'
```

Отсутствует:
1. **Назначение-предикат** — нет `ra.confirmed_by IS NOT NULL`, нет
   `ra.valid_from/valid_until` окна, нет канонического
   `(ra.confirmed2_by IS NOT NULL OR ra.proposed_by IS NULL)` (T-0605 канон).
   Значит НЕПОДТВЕРЖЁННОЕ или ПРОСРОЧЕННОЕ назначение роли всё равно даёт
   invoke-грант.
2. **Грант-предикат** — нет `g.confirmed_by IS NOT NULL`, нет валидности-окна
   грант, и, что критично, нет `criticalGrantPredicate` + `confirmed2_by IS NOT
   NULL` гейта (T-0397 dual-control). Т.к. `resource_type = 'effect_resource' AND
   operation = 'invoke'` — это ROBOT axis-b критичности
   (`grants-dao.ts:143`), invoke-грант почти всегда критичен по построению — но
   инлайн-запрос это игнорирует полностью: **семи-подтверждённый (один
   аппрувер) invoke-грант PDP-активен**, дуал-контроль обойдён.

Итог: и назначение роли, и сам invoke-грант могут быть в ЛЮБОМ
неподтверждённом/просроченном/семи-подтверждённом состоянии — `loadCallerInvokeGrants`
всё равно вернёт их как активные, потому что единственный фильтр —
`g.operation = 'invoke'`.

### 1.2. Почему это баг, а не дизайн

Единственный резолвер прав в системе — `getGrantsForSubject`
(`src/db/grants-dao.ts:208`), уже реализующий:
- канонический assignment-active предикат (T-0605): `confirmed_by IS NOT NULL
  AND (confirmed2_by IS NOT NULL OR proposed_by IS NULL) AND in-window`;
- grant-level dual-control (T-0397): `confirmed_by IS NOT NULL AND in-window AND
  (NOT critical OR confirmed2_by IS NOT NULL)`, где critical покрывает и axis-b
  (`resource_type='effect_resource' AND operation='invoke'`).

Каждый другой consumer прав в кодовой базе (`records.ts`, `org.ts`, `inbox.ts`,
`capability-grants-dao.ts`, `sandbox-gate-dao.ts`, `registry-digest-dao.ts`,
`role-grant-dao.ts`) вызывает `getGrantsForSubject(pool, tenantId, actorSlug,
nowMs)` и затем фильтрует результат под свою потребность — НИКТО не пишет
собственный инлайн-JOIN на `role_assignment`/`grant`. `invoke.ts` — единственное
исключение: второй, более слабый путь принятия решения о правах.

## 2. Решение (одной фразой)

`loadCallerInvokeGrants` вызывает `getGrantsForSubject(pool, tenantId, callerId,
nowMs)` (тот же резолвер, что и весь остальной PDP) и фильтрует результат на
`operation === 'invoke'` — вместо собственного инлайн-SQL. Функция сохраняет
свою текущую сигнатуру возврата (`Grant[]`), только с ГОНОРАРНЫМ (не голым)
источником грантов.

## 3. Критерии приёмки (машинно-проверяемые)

- **AC-1** — `loadCallerInvokeGrants` (или его замена) вызывает
  `getGrantsForSubject` из `src/db/grants-dao.ts` — НЕ содержит собственного
  `JOIN choros.role_assignment` / `FROM choros."grant"` инлайн-запроса.
- **AC-2** — invoke-путь чтит канонический assignment-active предикат: caller с
  НЕПОДТВЕРЖЁННЫМ (`confirmed_by IS NULL`) или ПРОСРОЧЕННЫМ назначением роли
  НЕ получает invoke-грант этой роли (красный до фикса — единственная строка,
  которую raw SQL пропускал).
- **AC-3** — invoke-путь чтит grant-level дуал-контроль (T-0397): критичный
  invoke-грант (`resource_type='effect_resource'`, `operation='invoke'`) с
  ОДНИМ подтверждающим (`confirmed2_by IS NULL`) НЕ PDP-активен — caller НЕ
  может инициировать `POST /api/invoke/request|command` через этот грант.
  Тот же грант с ДВУМЯ подтверждающими (`confirmed2_by IS NOT NULL`) — активен.
- **AC-4** — существующие unit-тесty `src/__tests__/invoke-grant.test.ts` и
  `src/__tests__/invoke-caller-spoof.adversarial.test.ts` проходят без правок
  логики (`coversInvoke`, аудит, extractCallerId — не тронуты).
- **AC-5** — `ci/checks/invoke-grant-isolation.sh` зелёный (IG-5: единственный
  источник авторизации; IG-6: аудит через канонический seam) — новый код не
  вводит вторую систему авторизации.
- **AC-6** — новый additive fitness-чек (или усиление существующего) статически
  пинит: `invoke.ts` больше не содержит `JOIN choros.role_assignment` /
  свободный `FROM choros."grant"` рядом с `loadCallerInvokeGrants` — читает
  гранты ИСКЛЮЧИТЕЛЬНО через `getGrantsForSubject`.
- **AC-7** — `npx tsc --noEmit`, `npx eslint src`, `npx vitest run` — все
  зелёные (числа тестов не уменьшились).
- **AC-8** — `npm run fitness:db` зелёный на живом PG (:55432), включая НОВЫЙ
  DB-тест (`ci/checks/db/invoke-grant-resolver.db.test.ts` или аналог),
  доказывающий AC-2/AC-3 на реальной Postgres (не фейк-Pool).
- **AC-9** — анти-кейс гейт (`anti-case-lock.sh`) зелёный — никаких
  кейс-литералов (слаги ролей/бизнес-процессов) в `src/`.

## 4. Границы

- Grant-level дуал-контроль (`criticalGrantPredicate`, `confirmed2_by`) — НЕ
  переизобретается, берётся ИЗ `getGrantsForSubject` как есть (уже покрывает
  axis-b `effect_resource`+`invoke`).
- `coversInvoke` (scope/role-match предикат в invoke.ts) — не трогается, это
  отдельный, ортогональный предикат (агент-роль + org-scope), не про
  активацию назначения/гранта.
- `extractCallerId`, `resolveInvokeTenant`, `loadAgentCard`,
  `loadActiveRoleAssignment` (TARGET-сторона — резолюция агента-исполнителя, не
  authority caller-а) — вне рамок; F-1 касается ТОЛЬКО caller-side
  `loadCallerInvokeGrants`.
- Миграции не требуются (колонки/предикаты уже существуют, применяются к
  существующим таблицам).
