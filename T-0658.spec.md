# T-0658 — Спека: резолвер прав закрывает деактивированного сотрудника fail-closed

**Status:** ready
**Phase:** SPEC
**Task:** T-0658 [security/системный, столп 4 — агенты/сотрудники с правами]
**Date:** 2026-07-05
**База:** worktree `task/T-0658-resolver-deactivation-gate`, от `dev@de79ad5`

---

## 1. Проблема

`getGrantsForSubject` (`src/db/grants-dao.ts:208`) — единственный резолвер прав
(single-resolver constraint, см. T-0610/ADR-T0610), которым пользуются ВСЕ
consumers PDP: `invoke.ts`, `records.ts` (field-visibility + read-visibility),
`org.ts` (capability-token), `inbox.ts` (claim/approve роли), `sandbox-gate-dao.ts`,
`capability-grants-dao.ts`, `registry-digest-dao.ts`, `role-grant-dao.ts`.

Шаг 1 резолвера (`grants-dao.ts:216-220`):

```sql
SELECT id FROM choros.employee
 WHERE tenant_id = $1 AND slug = $2 LIMIT 1
```

резолвит subject slug → employee id БЕЗ предиката `deactivated_at IS NULL`.

### 1.1. Почему это дыра, а не безобидная деталь

`choros.employee.deactivated_at` (migration 125, T-0583) — маркер деактивации
УЧЁТНОЙ ЗАПИСИ, независимый от `role_assignment.valid_until` (ADR-T0583 §"Дыра
№2": "деактивированный = не держатель"). PATCH `/api/users/:employee_id`
(`user-mgmt.ts:489-556`) деактивирует KC-логин (`kc.setUserEnabled(id, false)`)
**KC-first**, затем ставит `deactivated_at`. Но KC `enabled:false` блокирует
только ВЫДАЧУ нового токена — уже выданный access-токен остаётся валидным до
истечения TTL (минуты). В этом окне уволенный/заблокированный сотрудник может
предъявить ещё-живой токен на ЛЮБОЙ PDP-путь (invoke, read/write записей,
report-pages, capability-token) — и `getGrantsForSubject` шаг 1 его РЕЗОЛЬВИТ
(находит employee-строку, деактивация никак не проверяется), после чего шаги
2-3 отдают его гранты как обычно.

Symptоm уже был замечен и залатан ЛОКАЛЬНО, не в резолвере: `inbox.ts` claim
(BLOCK-3, T-0588, `inbox.ts:1413-1417`) и approve (RE-VERIFY, T-0588,
`inbox.ts:1631-1643`) оба городят СВОЙ собственный `findEmployeeById` +
`deactivatedAt != null` гейт ПЕРЕД вызовом `resolveRolesForActor`
(`getGrantsForSubject`-путь), с явным комментарием "getRoleSlugsForActor does
not filter on employee.deactivated_at". Это asymmetric per-path defence:
каждый новый consumer PDP обязан САМ вспомнить про деактивацию и продублировать
такой же гейт — забыл один раз (а `invoke.ts`, `records.ts`, `org.ts`
capability-token, `sandbox-gate-dao.ts` этого НЕ делают) — дыра открыта на
этом пути.

### 1.2. Почему остальные функции этого файла УЖЕ фильтруют, а этот шаг — нет

`getHoldersForRole`, `findTenantOwnerSlug`, `getAuthoringDraftHolderEmployeeIds`,
`findTenantOwnerEmployeeId` (все — T-0588/T-0466, тот же файл) уже несут
`AND e.deactivated_at IS NULL`. `getGrantsForSubject` — единственная
PDP-критичная функция в файле, которая это пропустила: T-0588 закрыл
role-HOLDER-путь (кто держит роль), но не сам грант-резолвер (кто РЕЗОЛЬВИТСЯ
как subject для собственных прав).

## 2. Решение (одной фразой)

Добавить в шаг 1 `getGrantsForSubject` предикат `AND deactivated_at IS NULL`
(fail-closed): деактивированный subject резолвится в `[]` грантов СРАЗУ на
входе, закрывая дыру ОДНИМ местом для ВСЕХ текущих и будущих consumers PDP —
устраняя нужду в per-path гейтах (T-0588's inbox-локальные гейты становятся
избыточной, но безопасной defence-in-depth, не единственной линией защиты).

> **ПОПРАВКА (round 2, CHANGES_REQUESTED — адверс-скептик REAL_HOLE severity
> HIGH).** Грант-путь (`getGrantsForSubject`) — НЕ единственный live
> subject→authority резолвер. Владелец/админ авторизуются через ВТОРОЙ,
> параллельный резолвер `src/db/org.ts` (`isGenesisOwnerForTenant`,
> `loadAdminContext`), который ЗАКОРАЧИВАЕТ грант-PDP (owner-short-circuit в
> `capability-grants-dao.ts` отрабатывает ДО `getGrantsForSubject`). Тот же
> fail-closed предикат добавлен в ТРИ инлайн slug→employee подзапроса org.ts +
> в третий резолвер `report-page-render.ts` (delegated-reader ветка). Полный
> разбор всех трёх резолверов и триаж не-authority сайтов — ADR §3.1-3.4.
> Решение по каждому месту — тот же одиночный `AND deactivated_at IS NULL`.

### 2.1. Human vs agent — единый код-путь, гейт безопасен для обоих

`getGrantsForSubject` шаг 1 — ОДИН SQL против `choros.employee`, без ветвления
по `kind`. И human-, и agent-сотрудники (`kind='agent'`, напр. `assistant-agent`,
seed-агенты `a-recon`/`a-invoice`/`a-triage`/`s-ledger`/`s-ocr`) резолвятся
ЧЕРЕЗ ЭТОТ ЖЕ ЗАПРОС — нет отдельной агентской ветки резолюции subject→id
(разведка: `register.ts:364` комментарий "getGrantsForSubject returns [] for
the agent" подтверждает — assistant-agent employee резолвится ТЕМ ЖЕ шагом 1).

`deactivated_at` (migration 125) — колонка НА `employee`, общая для обоих
`kind`. НО **единственный write-путь**, ставящий её в non-NULL —
`PATCH /api/users/:employee_id` (`user-mgmt.ts:489-556`) — структурно
ограничен `kind === 'human'`:

```ts
if (!found || found.kind !== "human") {
  throw new HttpError(404, "NOT_FOUND", "user account not found in your tenant");
}
```

(`user-mgmt.ts:522`). `agent_card` (migration 032) НЕ имеет собственной
`deactivated_at`/enabled-колонки — агенты деактивируются (если вообще) ИНЫМ
механизмом (не через эту колонку). Значит для ЛЮБОГО `kind='agent'`
employee-row `deactivated_at` ВСЕГДА NULL в проде — гейт `AND deactivated_at
IS NULL` для агента **всегда true**, т.е. НИКОГДА не отфильтровывает
легитимного агента. Единый безусловный предикат в шаге 1 (без ветвления по
`kind`) безопасен для ОБЕИХ веток субъекта одновременно — ветвление не нужно.

## 3. Риппл-анализ потребителей (`getGrantsForSubject`)

Полный список вызывающих (`grep -rn getGrantsForSubject src/`):

| потребитель | путь | ожидание после фикса |
|---|---|---|
| `invoke.ts` | caller invoke-гранты (T-0610) | правильно: деактивированный caller не должен инициировать invoke |
| `records.ts` (`resolveFieldVisibility`) | field-visibility редакция записей | правильно: деактивированный не должен видеть classified-поля |
| `records.ts` (`resolveReadVisibility`) | read-PDP (T-0570) на записях | правильно: деактивированный не должен читать записи вообще |
| `org.ts` (capability-token) | `/api/org` capability-check | правильно: деактивированный теряет capability-token права |
| `inbox.ts` (`resolveRolesForActor`) | claim/approve роль-элигибилити | уже гейтится ЛОКАЛЬНО (T-0588 BLOCK-3/RE-VERIFY) — фикс делает этот локальный гейт избыточным, НЕ конфликтующим (both fail same direction: deny) |
| `sandbox-gate-dao.ts` | authoring_draft sandbox гейт | правильно: деактивированный конфигуратор теряет доступ к sandbox |
| `capability-grants-dao.ts` | LLM-connection capability-authz | правильно |
| `registry-digest-dao.ts` | registry-digest доступ | правильно |
| `role-grant-dao.ts` | НЕ вызывает `getGrantsForSubject` напрямую (комментарий "mirrors" — отдельная функция) — вне скоупа фикса | не задет |
| `server.ts` (composition root) | те же resolveFieldVisibility/resolveReadVisibility | правильно (композиция вызовов выше) |

**Не найдено ни одного потребителя, полагающегося на то, что деактивированный
субъект резолвится в НЕПУСТОЙ набор грантов** (напр. административный
аудит-путь, показывающий гранты уволенных). Все consumers — LIVE PDP-решения
(authorize-or-deny), где деактивированный ДОЛЖЕН получать `[]`. Не найдено ни
одного места, которое читало бы гранты уволенного сотрудника ради истории/аудита
через ЭТОТ резолвер — audit-события (`userMgmtAuditWriter`) хранятся отдельно
от grant-резолюции и не проходят через `getGrantsForSubject`.

**Вывод риппл-анализа: БЕЗОПАСНО** — фикс есть чистое СУЖЕНИЕ (никогда не
разрешает то, что было запрещено; может запретить то, что было ошибочно
разрешено — ровно то, что и требуется).

## 5. Критерии приёмки (машинно-проверяемые)

- **AC-1** — `getGrantsForSubject` шаг 1 несёт `AND deactivated_at IS NULL`
  (или эквивалент), применяясь И к human-, И к agent-веткам единым кодом (без
  ветвления по `kind`).
- **AC-2** — db-тест: деактивированный сотрудник с валидным (confirmed +
  in-window + dual-confirmed, если критичный) invoke-грантом →
  `getGrantsForSubject` возвращает `[]` (красный до фикса).
- **AC-3** — db-тест позитив-контроль: АКТИВНЫЙ сотрудник с тем же самым
  грантом → грант присутствует (happy-path не сломан).
- **AC-4** — db-тест: `kind='agent'` сотрудник (без `deactivated_at`, как и
  ВСЕ agent-строки в проде) резолвится НЕ ЗАТРОНУТЫМ гейтом деактивации —
  его гранты присутствуют как прежде.
- **AC-5** — риппл-анализ (§3) документирован в ADR: ни один потребитель не
  полагается на резолюцию деактивированного в непустой грант-набор.
- **AC-6** — существующие тесты (`src/__tests__/grants-dao.test.ts` и др.)
  проходят без перекраски (deactivated-незатронутые фикстуры не имеют
  `deactivated_at` — NULL по умолчанию).
- **AC-7** — `npx tsc --noEmit`, `npx eslint src`, `npx vitest run` — зелёные,
  число тестов НЕ уменьшилось.
- **AC-8** — `npm run fitness:db` зелёный на живом PG (:55432), включая НОВЫЙ
  db-тест, доказывающий AC-2/AC-3/AC-4 на реальной Postgres.
- **AC-9** — `grant-resolver-isolation.sh`, `dual-control-isolation.sh`,
  `single-resolver.sh` зелёные (SQL-предикат — additive `AND`, не трогает
  модульные границы/дуал-контрольный домен/резолвер object-handle).

## 6. Границы

- Дуал-контроль (`criticalGrantPredicate`, `confirmed2_by`, шаг 3) — НЕ
  переизобретается, гейт деактивации ортогонален и добавляется ТОЛЬКО в шаг 1
  (subject→id резолюция), не смешивается с шагом 3 предикатом.
- Локальные гейты `inbox.ts` (T-0588 BLOCK-3/RE-VERIFY) — НЕ удаляются в этом
  тspeace (defence-in-depth, избыточны но не вредны); дублирование отмечено в
  ADR как принятый residual (снятие — отдельный follow-up, не в скоупе).
- Миграции не требуются — колонка `deactivated_at` уже существует (migration
  125), меняется только READ-предикат.
- Агентская деактивация (если появится отдельный механизм на `agent_card`) —
  вне скоупа; текущий фикс безопасен для агентов ПОТОМУ ЧТО у них сейчас нет
  механизма ставить `deactivated_at` non-NULL, не потому что гейт explicit
  различает `kind`.

## 7. Вне рамок (follow-up, если найдётся)

- Удаление избыточных `inbox.ts` локальных deactivation-гейтов (T-0588
  BLOCK-3/RE-VERIFY) теперь, когда резолвер сам fail-closed — не делается
  здесь (defence-in-depth оставляем; удаление — отдельная задача, если
  когда-нибудь понадобится упростить).
- Отзыв уже ВЫДАННЫХ KC access-токенов при деактивации (сократить окно TTL до
  нуля через KC session-revocation API) — отдельная, более крупная задача;
  этот фикс закрывает ТОЛЬКО PDP-резолюцию в системе Choros, не сам KC-токен.
