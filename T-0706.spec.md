# T-0706 — Конструктор форм: пикер «Набор полей» согласован с target_registry_slug

Родитель: эпик T-0479. Найдено в LIVE_PROOF T-0669 (P0, слоем глубже). Столп
2/3 (интерфейс-из-блоков-на-данных + бесшовность). Спека контура:
`docs/design/ADR-T0665-forms-e2e-contour.md`.

## 1. Проблема (как есть, до задачи)

T-0669 согласовал пикер «Приложение» с `process_app_binding` — но НЕ пикер
«Набор полей» (`registryDefs`/`selectedDefId`, `web/src/forms/FormDesigner.jsx`).
Он до сих пор предлагает ВСЕ `registry_def` выбранного приложения
(`GET /api/registry-defs?application_id=…`), без учёта, что реальный
серверный гейт `classifyLayoutSave` → `resolveLiveRecordSchema`
(`src/db/live-form-schema.ts`) резолвит РОВНО ОДИН реестр — `registry_def`
с `slug = binding.target_registry_slug` (если задан на связке) ИЛИ
`slug = resolveDefaultStepResultSlug()` (серверный дефолт-слаг, если связка
несёт `target_registry_slug = NULL`).

Когда у приложения ≥ 2 `registry_def`, автор может выбрать легитимный-но-
неправильный набор полей — авторинг (драг-дроп/поля/превью) проходит чисто,
кнопка «Сохранить раскладку» активна, и падает только по клику непрозрачным
`Не удалось сохранить.` (`persistLayout`, `409 WRONG_FLOOR`).

Живой репро (LIVE_PROOF T-0669, кейс-фикстуры конкретного стенда — НЕ
переносятся в код/тесты этой задачи, см. anti-case-lock.sh): связка
процесс↔приложение с `target_registry_slug`, указывающим на ОДИН из двух
реестров приложения; выбор другого легитимного реестра приложения в пикере
«Набор полей» → `409`; выбор реестра, совпадающего со слагом связки → `201`.

## 2. Контекст (переиспользуется, не дублируется)

- T-0669 (в dev): `boundAppIdsForProcess` — фильтрует пикер «Приложение» по
  `GET /api/process-app-bindings`; `PROCESS_NOT_BOUND_HINT` — честный текст
  в потоке (не alert) для «нечего выбрать»; тот же файл, тот же паттерн
  эффектов/мемо.
- T-0681 (в dev): `GET /api/process-app-bindings` отдаёт `target_registry_slug`
  на каждой записи (`null` = дефолт, непустая строка = явный слаг связки).
- `src/db/live-form-schema.ts` `resolveLiveRecordSchema`: единственный
  источник истины для «какой реестр реально резолвится» —
  `appRow.target_registry_slug?.trim() || resolveDefaultStepResultSlug()`,
  затем `registry_def WHERE application_id = $app AND slug = $schemaSlug`.
  `resolveDefaultStepResultSlug()` читает `process.env` — СЕРВЕРНОЕ значение,
  клиенту недоступное напрямую ни через один существующий эндпоинт.

## 3. Решение

Природа данных (§2, migrations/075+119: `UNIQUE (tenant_id, process_key,
application_id)`) означает — для выбранной пары (процесс, приложение)
существует РОВНО ОДНА связка, несущая РОВНО ОДИН `target_registry_slug`
(явный или NULL→дефолт). Это НЕ «несколько легитимных таргетов на одну
связку» — сервер всегда резолвит один конкретный слаг. Поэтому применимый
вариант — **сужение (а)**, не подсказка (б): когда связка известна и несёт
явный `target_registry_slug`, пикер «Набор полей» ограничивается ЭТИМ одним
реестром (не показывает выбор вовсе — реестр уже задан связкой, показывается
как факт, не как открытый вопрос).

Для NULL-связки (дефолт-слаг) клиент НЕ знает точное серверное значение
(env-переменная, не отдаётся ни одним GET) — сужать до неизвестного значения
нечестно. Для этого случая — **честная подсказка ДО save**: пикер остаётся
открытым (все реестры приложения), но рядом — предупреждение, что связка не
фиксирует конкретный реестр явно и сервер применит реестр по умолчанию;
пользователю предлагается зафиксировать `target_registry_slug` на экране
«Процессы» (`BindProcessModal`, T-0669 §3.4/NB-2), а не гадать в конструкторе
форм.

### 3.1 Сужение — связка несёт явный `target_registry_slug`

- Когда `selectedProcessKey` + `selectedAppId` выбраны и в
  `processAppBindings` (уже загружены T-0669-эффектом, переиспользуется —
  НЕ второй fetch) находится запись `(process_key, application_id)` с
  непустым `target_registry_slug`:
  - пикер «Набор полей» (`<Select>`) СКРЫВАЕТСЯ;
  - вместо него — текст в потоке (не alert, честный русский, без жаргона):
    «Набор полей задан привязкой процесса: «{display_name реестра}».» —
    имя реестра (a) резолвится по `target_registry_slug` среди уже
    загруженных `registryDefs` (сопоставление по `slug`), (b) если совпадение
    не найдено (реестр со слагом связки отсутствует у приложения — сама по
    себе рассинхронизация данных, отдельный класс дефекта) — текст показывает
    честно «слаг «{target_registry_slug}» не найден среди наборов полей этого
    приложения» вместо тихого молчания;
  - `selectedDefId` при разрешённом совпадении АВТОМАТИЧЕСКИ выставляется на
    `id` найденного `registry_def` (эффект, аналог существующего
    "выбор reset при смене процесса") — автору не нужно вручную кликать
    единственно верный вариант; документ строится как раньше
    (`buildDefaultDocument`/schema-driven build effect не меняются).
  - Смена `selectedProcessKey`/`selectedAppId` на пару без такого совпадения
    возвращает пикер в открытое состояние (§3.2/старое поведение) —
    состояние не залипает.

### 3.2 Открытый пикер + подсказка — связка NULL (дефолт-слаг) или ещё не знаем

- Когда `processAppBindings` ещё `null` (не загружены) — поведение КАК ДО
  задачи (открытый пикер, без подсказки) — ждать лишний RTT не нужно для
  базового кейса (T-0669 §3.1 тот же принцип).
- Когда связка для пары найдена, но `target_registry_slug` пуст/NULL —
  пикер «Набор полей» остаётся ОТКРЫТЫМ (текущее поведение, все
  `registryDefs` приложения), плюс рядом — ненавязчивый (muted, `role="status"`,
  НЕ alert) текст: «Привязка процесса не фиксирует конкретный набор полей —
  сервер применит набор по умолчанию. Если у приложения несколько наборов
  полей, зафиксируйте нужный на экране «Процессы», иначе сохранение может
  не пройти.» Подсказка показывается ТОЛЬКО когда у приложения ≥ 2
  `registryDefs` (при ровно одном наборе — неоднозначности физически нет,
  подсказка была бы шумом).
- Когда для пары НЕТ записи в `processAppBindings` вовсе (не должно
  происходить при согласованном пикере «Приложение», T-0669 гарантирует это
  при штатном потоке, но остаётся возможным до загрузки/при
  `processAppBindings`-фетче с ошибкой=`null`) — поведение НЕ меняется
  (открытый пикер, без новой подсказки; T-0669's существующий
  `PROCESS_NOT_BOUND_HINT`/save-блокировка остаются единственной защитой на
  этом крае).

### 3.3 Defense-in-depth — save недостижим для несогласованного набора

- Save-кнопка дополнительно `disabled`, когда связка несёт явный
  `target_registry_slug`, среди `registryDefs` есть реестр с ЭТИМ слагом
  (совпадение разрешилось), и текущий `selectedDefId` указывает на ДРУГОЙ
  `registry_def` (не совпадающий по `slug`) — тот же честный текст-подсказка
  рядом с существующими save-блокировками (T-0665/T-0669 паттерн). В штатном
  потоке §3.1 (авто-выставление `selectedDefId`) это состояние недостижимо
  вручную — блокировка чинит гонку/устаревший `selectedDefId` (пользователь
  успел выбрать до того, как связка подгрузилась/изменилась).

### 3.4 Согласованная/однозначная пара — не регрессирует (NF)

- Приложение с РОВНО одним `registry_def` — пикер ведёт себя как раньше:
  либо остаётся открытым с одним вариантом (не скрывается, если связка НЕ
  несёт явный слаг — §3.2), либо сужается (§3.1, если связка несёт явный
  слаг, совпадающий с единственным набором) — обе ветки эквивалентны
  исходу, разница только в UI-представлении «выбор из одного» vs «факт».
- Без выбранного `selectedProcessKey` ИЛИ без `selectedAppId` — пикер как
  сейчас (обычный полный список набора полей выбранного приложения,
  §-логика неактивна — нечего сверять).

## 4. Acceptance criteria

- **AC-1 (сужение при явном target_registry_slug)**: для пары
  (`selectedProcessKey`, `selectedAppId`), чья связка несёт непустой
  `target_registry_slug`, совпадающий по `slug` с одним из `registryDefs`
  приложения, пикер «Набор полей» скрыт, вместо него — факт-текст с именем
  найденного реестра, и `selectedDefId` автоматически указывает на него.
- **AC-2 (честная подсказка при NULL/дефолт-слаге, ≥2 наборов)**: для пары,
  чья связка несёт `target_registry_slug = null` (или отсутствует), и у
  приложения ≥ 2 `registryDefs`, пикер остаётся открытым, но рядом появляется
  предупреждение (не alert) о незафиксированном наборе + отсылка на экран
  «Процессы».
- **AC-3 (несогласованный save недостижим или явно предупреждён)**: save
  «неправильного» набора для пары с явным `target_registry_slug` либо
  физически недостижим (AC-1 не даёт выбрать другой), либо (при гонке/ручном
  рассинхроне `selectedDefId`) кнопка «Сохранить раскладку» выключена с
  честным текстом — ни в одном штатном потоке пользователь не долетает до
  сырого `409` без предупреждения.
- **AC-4 (однозначный набор — NF)**: приложение с ровно одним `registry_def`
  не показывает подсказку AC-2 (нет неоднозначности); сохранение проходит как
  до задачи.
- **AC-5 (пара без известной связки/до загрузки — NF)**: без выбранного
  процесса/приложения, или пока `processAppBindings === null`, пикер «Набор
  полей» ведёт себя байт-в-байт как до задачи (открыт, полный список).
- **AC-6 (совпадение по слагу учитывает рассинхрон данных честно)**: если
  `target_registry_slug` связки не совпадает НИ С ОДНИМ `registryDefs.slug`
  приложения (сам реестр удалён/переименован), UI не молчит и не сужается в
  никуда — показывает честный текст с самим слагом, пикер остаётся открытым
  (деградация к §3.2-подобному предупреждению, не тихий сбой).
- **AC-7 (человеческий текст, без жаргона)**: тексты AC-1/AC-2/AC-6 не несут
  технических терминов (`target_registry_slug`, `registry_def`, `409`,
  `WRONG_FLOOR` и т.п.) — «набор полей», «привязка процесса», «на экране
  «Процессы»».
- **AC-8 (anti-case)**: реализация и тесты используют ТОЛЬКО generic-фикстуры
  (произвольные slug/display_name), не кейс-литералы конкретного стенда
  (`telLinear`/`purchases`/`soglasovanie`/`e-larina` и т.п. — anti-case-lock.sh).

## 5. Вне скоупа

- Изменение серверного `classifyLayoutSave`/`resolveLiveRecordSchema` —
  fail-closed судья не ослабляется (ADR §5, тот же принцип что T-0669).
- Экспозиция `resolveDefaultStepResultSlug()`/`CHOROS_DEFAULT_STEP_RESULT_SLUG`
  клиенту через новый эндпоинт — вне скоупа; §3.2 сознательно НЕ угадывает
  дефолт-слаг на клиенте, только честно предупреждает о его существовании.
- Редизайн `BindProcessModal` под явную фиксацию `target_registry_slug` на
  каждую связку — уже покрыт T-0669 §3.4 (префилл при ре-привязке); эта
  задача только ССЫЛАЕТСЯ на экран «Процессы» текстом, не меняет модалку.
