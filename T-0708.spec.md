# T-0708 — Карточка записи показывает связанные процессы (обратная связь E16 §6)

> E16/P1 из capstone T-0691, родитель эпик T-0349. Двусторонняя связь
> запись↔инстанс: карточка процесса уже несёт блок «ЗАПИСЬ-ИСТОЧНИК»
> (screen-process-instance.jsx, `RecordRef` по `instance.recordId`), а обратный
> путь запись→инстанс в UI МЁРТВ. Эта задача добавляет на карточку записи
> секцию «Процессы по этой записи».

## Дефект (что было)

`/apps/:appId/records/:id` (`web/src/screens/screen-record-detail.jsx`)
рендерит только поля записи + метаданные (Создано/Обновлено/Автор/Версия
схемы) + кросс-приложенческие связи (T-0352). Инстансов процессов,
стартованных из/связанных с этой записью, на карточке НЕТ — хотя E16 §6
требует двусторонней связи, а сервер УЖЕ знает `recordId` каждого инстанса
(`InstanceProjection.recordId`, читается из `process.started` payload
`record_id`; on_create-триггер T-0414/T-0356).

## Границы скоупа

- НЕ трогать `process-catalog` резолвер шага (T-0709 параллельно чинит
  `/api/process-catalog` step/role). «Текущий шаг» берётся из ТОГО ЖЕ источника
  истины, что и список процессов — `InstanceProjection.step` (Flowable-fold),
  не catalog.
- НЕ новый роут: фильтр по записи добавлен как query-параметр `?record=<id>`
  к СУЩЕСТВУЮЩЕМУ `GET /api/processes` (уже `withAuth`, tenant-scoped через
  `listInstanceProjections`) → auth-coverage гейт цел, PDP не обходится.
- Реюз человеко-имён: `StepRef` (текущий шаг), `StatusChip` (статус),
  `deriveInstanceTitle`+`RecordRef`-слой уже на карточке процесса — тот же
  человеческий слой (T-0648/T-0683/T-0687). Никаких голых UUID.
- Никакого кейс-контента в `src/`/`web/src`.

## Серверный контракт (дельта)

`GET /api/processes?record=<recordId>` — тот же роут, тот же tenant-scope,
тот же маппер `projectionToInstance`. Когда `record` присутствует и непуст,
ответ `{ instances }` содержит ТОЛЬКО инстансы, у которых
`recordId === <record>` (точное сравнение строк). Отсутствие/пустой `record`
⇒ поведение байт-идентично сегодня (полный tenant-список). Инстансы без
`recordId` в фильтрованном ответе не появляются никогда.

Tenant-скоуп унаследован: фильтр применяется ПОСЛЕ
`listInstanceProjections(pool, tenantId)` — по чужому тенанту запись не
подтянет чужие инстансы (проекции уже скоупнуты по `tenant_id`). No-DB
режим: сид-фолбэк отдаётся без фильтра только когда `record` отсутствует;
при заданном `record` без DB отдаём честный пустой список (сид не несёт
`recordId`, не масштабируем фикстуру на этот путь).

## Клиент (дельта к screen-record-detail.jsx)

Новая секция «Процессы по этой записи» на карточке записи (после полей,
рядом с кросс-приложенческими связями):
- Фетч `GET /api/processes?record=<record.id>` через auth-хелпер
  (`fetchWithAuthRetry`/`devHeaders`), без голого fetch.
- Каждый инстанс — строка: человеко-имя процесса
  (`deriveInstanceTitle(inst).title`, никогда голый ключ), текущий шаг через
  `StepRef` (или «Процесс завершён» для done), статус через `StatusChip`,
  ссылка на карточку процесса `/processes/:instanceId`.
- Пустое состояние: запись без процессов ⇒ секция СКРЫТА целиком (как
  `CrossAppLinksPanel` при пустом links). Никакого «процессов нет»-шума на
  карточках, где процессов и не ждут.
- Ошибка фетча ⇒ секция скрыта (не блокирует нативные поля, degrade как в
  `CrossAppLinksPanel`).

## Acceptance

1. Карточка записи с ≥1 связанным инстансом показывает секцию «Процессы по
   этой записи» с человеко-именем процесса, текущим шагом (`StepRef`),
   статусом (`StatusChip`) и рабочей ссылкой на `/processes/:instanceId`.
2. Запись без связанных инстансов ⇒ секция НЕ рендерится (скрыта).
3. Ни текущий шаг, ни имя процесса, ни id инстанса не рендерятся голым UUID —
   человеко-слой примитивов (`StepRef`/`deriveInstanceTitle`); id инстанса
   только в href/тултипе.
4. Сервер: `GET /api/processes?record=<id>` фильтрует до инстансов с этим
   `recordId`; инстанс с другим/без `recordId` не попадает; tenant-скоуп цел;
   без `record` — байт-совместимость с сегодняшним списком.
