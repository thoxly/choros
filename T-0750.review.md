## Findings

### F1 (non-blocking / nit, axis 2) — item.mine НЕ деактивационно-гейтнут

**Где:** `src/http/inbox.ts:1831` (ветка `item.mine`) + LIST `inTab("mine")`
`inbox.ts:1184`.

**Что:** мой live-probe **P1** — деактивированный актор, который ВЗЯЛ задачу
(claim) пока был активен, всё ещё читает её detail по живому остаточному JWT →
**HTTP 200**. Деактивация не снимает claim; `item.mine` — только identity-match.

**Почему non-blocking:**
1. self-scoped — только задача, которую актор лично взял и к которой уже имел
   полный доступ; time-bounded остаточным окном JWT (~300s).
2. **байт-симметрично LIST** `inTab("mine")` + бейдж «mine» — деактивированный
   claimant И ТАК видит эту задачу в LIST. Это **системное** свойство
   (deactivation ≠ claim release; видимость claim-state не ACTOR_ACTIVE-гейтнута
   НИГДЕ), не введённое T-0750.
3. ADR §3 **честно** ограничивает деактивационный cutoff ветками (2) role и (3)
   owner — НЕ переобещает, что mine отсекает деактивированного.
4. Finding под фиксом (role-addressee / произвольное чтение) ЗАКРЫТ (AC-3 + P4).
   Сужение только DETAIL сломало бы симметрию LIST/DETAIL, которую задача верно
   держит.

**Рекомендация (отдельная задача, НЕ в этом PR):** либо снимать активные claim'ы
при деактивации (claim-projection + миграция), либо ACTOR_ACTIVE-гейтнуть
видимость claim-state в ОБОИХ — LIST `inTab("mine")`/бейджах И DETAIL
`item.mine` — чтобы они остались симметричны.
