# T-0669 — Конструктор форм: пикер приложений согласован с process_app_binding

Родитель: эпик T-0479. Спека контура: `docs/design/ADR-T0665-forms-e2e-contour.md`.
Столп 2/3 (интерфейс-из-блоков-на-данных + бесшовность).

## 1. Проблема (как есть, до задачи)

`FormDesigner.jsx` («Привязка») несёт ДВА независимых пикера, которые ничего
друг о друге не знают:

- «Процесс» (`selectedProcessKey`) — из `/api/process-catalog`, только
  `published`.
- «Приложение» (`selectedAppId`) — из `/api/applications`, ВЕСЬ список
  приложений тенанта, без фильтра.

Оба пикера пишут в СВОЁ состояние; `selectedAppId` используется только чтобы
подгрузить `registry-defs` → набор полей → `buildDefaultDocument`. Реальная
проверка «этому процессу вообще разрешено сохраняться» происходит только на
сервере, внутри `classifyLayoutSave` → `resolveLiveRecordSchema`
(`src/db/live-form-schema.ts`): она резолвит `application_id` САМА, по
`process_app_binding WHERE process_key = $processKey` (без учёта, что выбрал
пользователь в пикере «Приложение») — и если пары `(process_key,
application_id)` нет в `process_app_binding`, `resolveLiveRecordSchema`
возвращает `null` → `classifyLayoutSave` бросает `409 WRONG_FLOOR`.

Итог: автор конструктора может свободно выбрать процесс A и приложение B, не
подозревая, что реальная привязка A↔B никогда не создавалась (или создана с
другим приложением C) — авторинг (drag/drop/поля/превью) проходит чисто,
кнопка «Сохранить раскладку» активна, и падает только по клику непрозрачным
`Не удалось сохранить.` (единственный текст ошибки в `persistLayout`,
`web/src/forms/FormDesigner.jsx`), без объяснения причины.

## 2. Контекст T-0681 (переиспользуется)

T-0681 (только что влит в dev) добавил:

- `GET /api/process-app-bindings` → `200 { bindings: [...] }`, каждая запись —
  `{ id, process_key, application_id, application_slug, application_name,
  form_key, trigger_type, start_form_key, field_mapping, target_registry_slug,
  created_at, updated_at }` (`src/http/process-catalog.ts`
  `serializeBinding`). Тот же список уже приходит инлайн и в
  `GET /api/process-catalog` (`{ definitions, instances, bindings }`), но
  ADR-T0665 и текущий `FormDesigner` этот канал не используют — новый
  отдельный вызов `/api/process-app-bindings` делает намерение «мне нужны
  ИМЕННО связи» явным и не зависит от смежных изменений `/api/process-catalog`.
- `BindProcessModal` (`web/src/screens/screen-processes.jsx`) — экран
  «Процессы», где реально создаются пары `(process_key, application_id)`.

NB-2 (судья T-0681, не блокирующая): `BindProcessModal` — всегда
create/upsert-форма, не подгружает текущий `target_registry_slug`
существующей связи при повторной привязке той же пары — апсерт на
`ON CONFLICT DO UPDATE` затирает колонку в NULL. Эта задача трогает именно
пикер приложений/модалку привязки → чинится в рамках той же зоны (см. §5).

## 3. Решение

### 3.1 FormDesigner — фильтрация + честная подсказка ДО save

- Новый эффект грузит `GET /api/process-app-bindings` один раз при монтировании
  (как `processCatalog`/`applications` — реальные данные тенанта, не
  константа; graceful-empty `{bindings: []}` — не ошибка).
- Когда выбран `selectedProcessKey`, пикер «Приложение» показывает ТОЛЬКО
  приложения, для которых существует запись `bindings` с этим
  `process_key` (сопоставление по `application_id` — тот же id, что
  `/api/applications` возвращает как `a.id`). Без выбранного процесса пикер
  ведёт себя как раньше (полный список) — фильтрация не имеет смысла, пока
  процесс не выбран (нечего сверять).
- Если для выбранного процесса `bindings` (после загрузки) даёт ПУСТОЙ список
  подходящих приложений — пикер «Приложение» не предлагает несогласованный
  выбор: показывается честная подсказка (не alert/toast, текст в потоке,
  человеческим русским, без жаргона): «Этот процесс не привязан ни к одному
  приложению — привяжите его на экране «Процессы».» Пикер в этом состоянии
  либо пуст (только placeholder «— выберите —»), либо скрыт — реализация
  предпочитает СКРЫТЬ `<Select>` и показать текст (нечего выбирать).
- Смена `selectedProcessKey` на процесс, где текущий `selectedAppId` более не
  входит в согласованный список, сбрасывает `selectedAppId`/`selectedDefId`/
  `registryDefs` (тот же сброс, что уже происходит при ручной смене
  приложения) — не оставляет невидимый несогласованный выбор в состоянии.
- Пока `/api/process-app-bindings` ещё грузится — пикер «Приложение» ведёт
  себя как ДО задачи (полный список, не блокируется), чтобы не заставлять
  пользователя ждать лишний RTT для базового кейса «привязок мало». Список
  сужается, как только ответ приходит (переоценка при каждой смене
  `selectedProcessKey`/загрузке `bindings`).
- Ошибка загрузки `/api/process-app-bindings` (не 200) — не блокирует
  конструктор: фильтр не применяется (тот же graceful-degrade, что у
  `catalogError` для процессов), полный список приложений остаётся видимым
  (пусть 409 на сохранении хуже, чем до задачи, ничего не сломано; сообщение
  об ошибке загрузки не обязательно, т.к. это НЕ основной путь).

### 3.2 Defense-in-depth: честная ошибка вместо непрозрачного 409

Даже с фильтрацией пикера возможен зазор (bindings ещё не загрузились,
race, устаревший кэш) — `persistLayout`/save-кнопка остаются финальным
рубежом:

- Save-кнопка дополнительно disabled, когда `selectedProcessKey` выбран,
  `bindings` уже загружены (не `null`), и среди них нет ни одной записи с
  этим `process_key` — тот же честный текст-подсказка, что и в §3.1, рядом с
  существующей подсказкой «Выберите процесс и шаг выше…».
- Существующий catch в `persistLayout` (`'Не удалось сохранить.'`) не
  трогается как общий фолбэк для прочих ошибок сохранения (сеть, 500 и т.п.)
  — вне скоупа этой задачи различать код ответа сервера подробнее; согласно
  ADR §5, `classifyLayoutSave` — fail-closed judge, который не ослабляется.

### 3.3 Согласованная пара — работает как раньше (NF, не регресс)

Когда выбранный `(selectedProcessKey, selectedAppId)` присутствует в
`bindings`, поведение конструктора байт-в-байт как до задачи: пикер набора
полей, драг-дроп, превью, save — ничего не меняется. Единственная разница —
пикер приложений СУЖЕН до согласованных вариантов (что для согласованной пары
не создаёт разницы в исходе, только убирает недостижимые варианты).

### 3.4 NB-2 — префилл target_registry_slug при ре-привязке (соседняя правка)

`BindProcessModal` (`web/src/screens/screen-processes.jsx`) — при выборе пары
`(processKey, applicationId)`, для которой в уже загруженном
`bindings` (проп `existingBindings`, новый, из `ProcessCatalogSection`, который
уже держит список) находится существующая запись — поля модалки
(`targetRegistrySlug`, `triggerType`, `startFormKey`/`formKey`,
`fieldMappingRaw`) префиллятся из неё, а не остаются на дефолте. Это чинит
ИМЕННО дыру NB-2 (затирание `target_registry_slug` в NULL при ре-привязке
через пустой пикер) заодно с остальными полями упсерта, раз модалка правится
в этой задаче. Ре-привязка НОВОЙ пары (нет существующей записи) ведёт себя как
раньше — пустая форма.

## 4. Acceptance criteria

- **AC-1 (фильтрация)**: при выбранном `selectedProcessKey`, для которого
  `bindings` содержит N ≥ 1 записей, пикер «Приложение» в FormDesigner
  предлагает РОВНО те N приложений (по `application_id`), а не полный список
  `/api/applications`.
- **AC-2 (пустой список — честная подсказка)**: при выбранном
  `selectedProcessKey`, для которого `bindings` не содержит ни одной записи
  (после успешной загрузки), FormDesigner показывает текст «Этот процесс не
  привязан ни к одному приложению — привяжите его на экране «Процессы».» и НЕ
  предлагает выбрать несогласованное приложение (Select скрыт/пуст).
- **AC-3 (несогласованная пара недостижима ИЛИ явно предупреждена до save)**:
  невозможно довести до нажатия «Сохранить раскладку» пару, которой нет в
  `bindings`, БЕЗ явного предупреждения — либо пикер её физически не предлагает
  (AC-1/AC-2), либо (при гонке загрузки) save-кнопка выключена с тем же
  текстом.
- **AC-4 (согласованная пара не регрессирует)**: пара, присутствующая в
  `bindings`, ведёт себя как до задачи — пикер набора полей появляется, save
  доступен при заполненном шаге (существующий гейт `doc?.step ||
  (selectedProcessKey && stepKey.trim())` не меняется).
- **AC-5 (пустой ответ `/api/process-app-bindings` в целом, до выбора
  процесса)**: без выбранного процесса пикер приложений — полный список
  (фильтрация неактивна), поведение НЕ регрессирует относительно текущего.
- **AC-6 (NB-2 — префилл при ре-привязке)**: открытие `BindProcessModal` для
  уже существующей пары `(process_key, application_id)` (выбраны оба, найдено
  совпадение в `existingBindings`) префиллит `target_registry_slug` (и прочие
  апсертящиеся поля) текущим значением связи, а НЕ дефолтом/пустой строкой;
  сабмит такой формы без изменений полей НЕ затирает `target_registry_slug` в
  NULL.
- **AC-7 (человеческий текст, без жаргона)**: подсказка из AC-2/AC-3 не несёт
  технических терминов (`process_app_binding`, `409`, `WRONG_FLOOR`,
  `application_id` и т.п.) — только «процесс», «приложение», «привяжите».

## 5. Вне скоупа

- Изменение серверного `classifyLayoutSave`/`resolveLiveRecordSchema` —
  fail-closed судья не ослабляется (ADR §5).
- Роль/доступ `process_designer` (T-0666).
- Полный редизайн `BindProcessModal` под редактирование существующих связей
  (список связей как отдельный edit-режим) — только точечный префилл полей
  при совпадении пары (AC-6), без смены общей формы "create/upsert".
