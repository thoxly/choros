# T-0681 — HTTP/UI-путь записи `process_app_binding.target_registry_slug`

**Эпик:** E-FORMS / P1 · **Источник:** live-proof T-0678/T-0680 (форма для НЕ-дефолт реестра не сохраняется)

## Проблема (что вскрыла приёмка)

`choros.process_app_binding.target_registry_slug` (миграция 119) — это per-(process, application)
конфигурация «в какой реестр этого приложения падает результат шага И против чьей схемы
валидируется форма». Значение НИКОГДА не выставляется ни через UI, ни через HTTP — только
сиды/`UPDATE` в миграциях (119 для ТЭЛ) или ручной SQL.

Оба существующих писателя строки биндинга —
`POST /api/process-app-bindings` (`src/http/process-catalog.ts`) и оператор ассистента
`author_binding` (`src/http/assistant.ts`) — вставляют строку БЕЗ `target_registry_slug`
(колонка остаётся `NULL`).

Следствие (серверный гейт T-0520 `classifyFloorBoundary` через
`resolveLiveRecordSchema`, `src/db/live-form-schema.ts`): когда `target_registry_slug IS NULL`,
живая схема резолвится по **дефолт-слагу** (`resolveDefaultStepResultSlug()`). Для процесса,
чей результат-реестр НЕ дефолтный, `registry_def` по дефолт-слагу под этим приложением
отсутствует → `resolveLiveRecordSchema` возвращает `null` → форма падает в Floor-2 →
первый же `save` формы даёт **409 WRONG_FLOOR**, хотя форма корректна. Реестр существует,
но связать процесс с ним негде.

## Корень

Дыра именно в СЛОЕ ЗАПИСИ биндинга: колонка 119 читается пятью резолверами
(`live-form-schema`, `step-applier`, `process-instance-resolver`, `process-defs` publish-gate,
`live-form-schema`), но НИ ОДИН writer её не пишет. Нужен честный HTTP/UI-путь.

## Решение (минимальный шов)

Протянуть `target_registry_slug` через существующий писатель `POST /api/process-app-bindings`
(и клиентский payload/форму) + оператор ассистента `author_binding`. Никакой новой таблицы,
новой миграции, нового RLS — колонка 119 уже есть; upsert уже есть.

Валидация (server-side, fail-closed): когда `target_registry_slug` непустой — реестр с этим
`slug` ДОЛЖЕН существовать под тем же `application_id` в тенанте caller'а (RLS-scoped SELECT);
иначе честная 400 `REGISTRY_NOT_FOUND` (не молчаливое сохранение висящего слага). `NULL`/пусто
= прежнее поведение (дефолт-слаг) — обратная совместимость.

## Acceptance (машинно-проверяемо)

- **AC-1** `POST /api/process-app-bindings` c телом, включающим валидный `target_registry_slug`
  (реестр существует под application_id), возвращает 201 и записывает колонку; повторный
  upsert той же пары обновляет `target_registry_slug`.
- **AC-2** `POST /api/process-app-bindings` c `target_registry_slug`, для которого нет
  `registry_def` под этим application_id → 400 `REGISTRY_NOT_FOUND` (строка НЕ записана /
  не изменена в этой части).
- **AC-3** Отсутствие `target_registry_slug` в теле (или `null`/пусто) → 201, колонка `NULL` —
  байт-в-байт прежнее поведение (обратная совместимость, дефолт-слаг).
- **AC-4** GET `/api/process-app-bindings` и `/api/process-catalog` отдают `target_registry_slug`
  в сериализованном биндинге (для отображения/предзаполнения формы).
- **AC-5 (интеграция шва с гейтом)** Свежий процесс, привязанный через
  `POST /api/process-app-bindings` к НЕ-дефолт реестру (`target_registry_slug` выставлен), даёт
  живую схему через `resolveLiveRecordSchema` → форма классифицируется Floor-1 → сохранение
  формы НЕ отбивается ложным 409 WRONG_FLOOR. (Прежде: `NULL` → дефолт-слаг → `null` схема →
  Floor-2 → 409.)
- **AC-6 (анти-кейс)** Ни одного case-литерала денилиста (`soglasovanie`, `role-approver`,
  персоны, `telLinear`, …) в `src/`/`web/src/`; слаг — данные из тела запроса, реестр —
  из тенанта. `anti-case-lock.sh` зелёный.

## Не входит

- Ассистентный `author_binding` получает пробрасывание `targetRegistrySlug` (симметрия), но
  UI-агента для него нет — покрывается той же серверной валидацией.
- Изменение семантики дефолт-слага, публикационного гейта T-0643, floor-boundary — не трогаем.
