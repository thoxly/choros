# T-0643 — Целевой набор результата шага из BINDING, не из хардкод-слага (BUG-017 остаток)

Столп: 1 (движок) / анти-кейс дисциплина D-064 §5. Кейс-доказательство: свежее
приложение+процесс, собранные из конструктора (без ТЭЛ-набора «Согласование»),
проходят через approve БЕЗ 422 — при условии что автор задал целевой набор в
binding (или создал набор с дефолтным именем); если автор ничего не настроил,
ошибка ловится ЧЕСТНО и РАНО (на publish), а не поздно (на первом approve).

## Контекст (что уже было, что осталось)

T-0575 (мерж c334d43, до этой задачи) уже сделал бо́льшую часть работы:
`src/db/step-applier.ts::applyStepResult` резолвит целевой registry для
результата шага из `process_app_binding.target_registry_slug` (миграция 119),
с фолбэком на `resolveDefaultStepResultSlug()` (env
`CHOROS_DEFAULT_STEP_RESULT_SLUG`, дефолт `"soglasovanie"` — ТЭЛ обратная
совместимость) — БОЛЬШЕ НЕ безусловный хардкод-слаг. Если ни явный, ни
дефолтный slug не резолвятся в реальный `registry_def`, `applyStepResult`
бросает типизированную `StepTargetUnresolvedError` (422, код
`STEP_TARGET_UNRESOLVED`) — структурная ошибка вместо голого 500 (старый
симптом BUG-017 «500 без лога»).

Карта примитивов (2026-07-02, §5) зафиксировала это как всё ещё нерешённое,
потому что на момент её написания T-0575 ещё не был смержен на dev-базу этой
ветки; после разведки в коде выяснилось: **логика резолва — сделана**,
остались два зазора:

1. **Анти-кейс остаток**: `SOGLASOVANIE_SLUG = "soglasovanie"` как реальный
   код-литерал остаётся в ДВУХ местах (`src/db/step-applier.ts:83` — сам
   config-primitive default; `src/http/form-record-persister.ts` —
   `resolveApprovalFormRegistrySlug()` держал СВОЮ, НЕЗАВИСИМУЮ копию того же
   литерала, несмотря на собственный комментарий, утверждавший, что она
   читает «тот же config-primitive»). anti-case-lock.sh (T-0576) считает это
   erosion-баром (`soglasovanie` было на 2 из baseline 2 — на потолке, не
   ниже).
2. **Поздняя честность**: unresolved target обнаруживается ТОЛЬКО на первом
   approve (422 при живом приближении реального человека), а не на publish —
   свежесобранное из конструктора приложение+процесс публикуется ЧИСТО и
   ломается только когда кто-то реально пытается согласовать первую заявку.
   Это и есть операционный симптом BUG-017 из карты примитивов
   («свежесобранное из конструктора приложение+процесс ломается
   STEP_TARGET_UNRESOLVED (422) при ПЕРВОМ approve (не при публикации —
   поздно)»).

## Функциональные требования

- FR-1: `resolveApprovalFormRegistrySlug()` (form-record-persister.ts) больше
  не держит собственный литерал `"soglasovanie"` — вызывает
  `resolveDefaultStepResultSlug()` из step-applier.ts напрямую (единая точка
  конфигурации на ВЕСЬ кодобазис, не две независимые копии).
- FR-2: publish (`POST /api/process-defs/:key/publish`, и её переиспользование
  в bundle-promote/solution-publish) получает НОВЫЙ шаг проверки (после
  T-0559 app-binding-draft гейта, до deploy): для КАЖДОЙ строки
  `process_app_binding` этого процесса резолвится целевой slug (явный
  `target_registry_slug` ИЛИ дефолт) и проверяется существование
  `registry_def` с этим slug под привязанным приложением. Если хотя бы одна
  строка не резолвится — publish отклоняется 422 (`STEP_TARGET_UNRESOLVED`,
  тот же код что approve-time ошибка), СПИСКОМ (по одной violation на
  offending binding), деплой в Flowable не происходит.
- FR-3: процесс БЕЗ строки `process_app_binding` вообще — это НЕ нарушение
  нового гейта (зеркалит step-applier.ts собственную «no_app_binding →
  санкционированный no-op» позицию: процесс, автор которого никогда не
  привязал приложение, никогда не ожидал писать сущность-результат шага —
  проверять на publish нечего).
- FR-4: bundle-promote путь (`solution-bundles.ts`) и `solution-publish.ts`
  (форма-едет-с-процессом) получают явную ветку на новый статус
  `step_target_unresolved` — не проваливаются в generic `default`.

## Нефункциональные / инварианты

- NF-1: НЕ трогать `src/runtime/agent-dispatch/**` (frozen, FF-15), assistant
  чат-диспетчер (кроме отсутствия импорта в новых местах), registry-digest-dao,
  inbox-мотор саму механику approve (только чтение уже существующего
  `applyStepResult` контракта — сигнатура не меняется).
- NF-2: миграция НЕ нужна — вся необходимая колонка (`target_registry_slug`)
  уже существует (119); резолв целиком читает существующие таблицы.
- NF-3: анти-кейс-лок (`ci/checks/anti-case-lock.sh`) должен остаться
  ЗЕЛЁНЫМ и СТАТЬ СТРОЖЕ: `soglasovanie` erode 2→1 в
  `ci/checks/data/anti-case-baseline.json` (потолок опущен, будущий рег
  ловится). Оставшийся 1 код-литерал (`step-applier.ts`'s
  `SOGLASOVANIE_SLUG`) — АРХИТЕКТУРНО обязателен как единственное значение
  config-primitive default (тот же паттерн, каким `detel-literal-baseline.sh`
  уже документирует `tel-approval`'s пол в 1) — устранять его означало бы
  менять дефолт-поведение для тенантов, никогда не задававших явный
  `target_registry_slug`, что вне скоупа этой задачи.
- NF-4: обратная совместимость — существующие процессы с уже засеянным
  «Согласование»-набором (ТЭЛ/демо, миграция 076/085/119-UPDATE) публикуются
  БЕЗ ИЗМЕНЕНИЙ (гейт видит slug резолвится → нет violation).

## Out of scope

- UI-поле для выбора `target_registry_slug` при настройке binding (сегодня
  нет вообще ни у одного поля этой колонки в web/src/) — не добавлялось;
  минимальный путь по заданию («если нет UI — понятная ошибка на publish»)
  реализован БЕЗ новой UI-поверхности. Follow-up для отдельной задачи, если
  продукту нужен UI-контрол вместо неявного дефолта/ошибки.
- Полное устранение `SOGLASOVANIE_SLUG`-литерала как значения (а не только
  дедупликация) — архитектурно требует либо (а) удаления дефолт-фоллбэка
  вовсе (ломает обратную совместимость для тенантов без явного slug —
  поведенческое изменение вне скоупа), либо (б) переноса дефолта из
  кода в БД-конфигурацию per-tenant (новый примитив, отдельная задача).
- `process-catalog.ts`/`assistant.ts`'s binding-creation routes НЕ получили
  новый параметр `target_registry_slug` во входном теле (нет UI, нет
  необходимости для честного publish-time гейта — оператор может задать его
  прямой SQL-строкой, как это уже делает миграция 119 для ТЭЛ-сида).
