# T-0611 — resolveIdBySlug: registry_def slug ambiguity across applications

Status: SPEC
Stems from: T-0607 review finding F4 (medium, non-blocking) — docs/review/T-0607.review.json

## Problem

`resolveIdBySlug` (src/http/assistant.ts:190-202) lets the assistant's configurator
tool-layer accept a SLUG (instead of a raw UUID) when the LLM references a
`registry_def` or `application` row, because the LLM has no id↔slug↔name
catalogue (T-0607 в1). The query is:

```sql
SELECT id FROM choros.${table} WHERE tenant_id = $1 AND slug = $2 LIMIT 1
```

For `application`, this is safe: the schema constraint is
`UNIQUE (tenant_id, slug)` (migrations/003_application.sql:15) — a slug is
unique within a tenant, so `LIMIT 1` can only ever return the one legitimate
row.

For `registry_def`, this is **unsafe**: the schema constraint is
`UNIQUE (tenant_id, application_id, slug)` (migrations/004_registry_def.sql:20)
— the SAME registry slug may legitimately exist in two (or more) different
applications belonging to the same tenant (e.g. two apps both have a section
slugged `items`). The query filters only by `tenant_id`, with **no
`application_id` filter and no `ORDER BY`**. On a cross-app slug collision it
returns an ARBITRARY, non-deterministic row (whichever Postgres happens to
scan first) via bare `LIMIT 1`.

Consequence: the configurator (`relate_application`, `edit_jsonschema_non_destructive`
call sites in src/http/assistant.ts) can then read/edit the WRONG registry's
`record_schema` — a different application's data model gets mutated instead of
the one the user meant. `buildHonestOpsReport` still reports this as a ✓
success (the op DID succeed — on the wrong target), so the user has no signal
anything went wrong. This is a столп-5 (settings-via-AI) correctness defect:
the assistant must never silently act on an unintended target.

Not a security hole (strictly within-tenant, within-rights, RLS-enforced — no
cross-tenant leak, no privilege escalation). It is a correctness/trust defect:
wrong-target mutation with a false-positive honest report.

## Root cause

1. No `application_id` (or any app-scoping context) is available at any of the
   `registry_def` call sites in the assistant tool-execution layer — the
   configurator's tool schemas (`relate_application`, `edit_jsonschema`) only
   ever pass a `registryDefId` / `sourceRegistryDefId` string (slug or UUID),
   never an accompanying `applicationId`. There is no "current application"
   scoped to the dialogue/thread today.
2. Even if an `application_id` were threaded through, the resolver itself has
   no path to honestly refuse when it CANNOT disambiguate — it always returns
   a single id or `null`, with no representation of "more than one candidate."

## Fix scope (this task)

`resolveIdBySlug` must never silently pick an arbitrary row when more than one
`registry_def` matches a slug within a tenant. Concretely:

1. The resolver detects the ambiguous case (>1 row matches `tenant_id + slug`
   for `registry_def`) and returns a distinct, typed signal — not just an id
   or `null` — so callers can distinguish "not found" from "ambiguous."
2. Every call site that resolves a `registry_def` slug must handle the
   ambiguous signal by refusing the write (no execution, no partial mutation)
   and returning a human-readable message that:
   - names the slug that was ambiguous,
   - enumerates the candidate applications (slug + display name) the slug
     exists under,
   - tells the user/LLM how to disambiguate (re-issue the op with the raw
     registry UUID, which IS unambiguous — `registry_def.id` is a tenant-wide
     primary key component).
3. `application` slug resolution keeps its existing behavior (still provably
   safe — `UNIQUE(tenant_id, slug)` — but the resolver's new return shape must
   accommodate both tables without weakening the `application` path).
4. Never a bare `LIMIT 1` with no `ORDER BY` masking non-determinism for the
   ambiguous table.

## Acceptance criteria

- AC-1: Given two registries with the SAME slug in two DIFFERENT applications
  of one tenant, resolving that slug for `registry_def` returns the ambiguous
  signal (not either candidate's id, not `null`).
- AC-2: The ambiguous signal, once surfaced through a configurator op
  (`edit_jsonschema_non_destructive`), produces an honest op-error string
  naming the slug and listing both candidate applications — the op performs
  NO database mutation (record_schema of neither registry changes).
- AC-3: The existing non-ambiguous paths remain green: resolving by raw UUID
  still passes through unchanged; resolving a unique slug (0 or 1 match)
  still resolves/reports "not found" exactly as before (T-0607 AC-6 db-test
  must stay green unmodified).
- AC-4: `application` slug resolution is unaffected (still resolves via
  `UNIQUE(tenant_id, slug)`; no new ambiguous path is introduced for it since
  none can occur under the schema constraint — but the shared return-shape
  change must not regress `author_binding` / `generate_process` grounding
  call sites).
- AC-5: No new NEEDS-DESIGN escalation — this is a bounded db-query +
  call-site fix, no schema migration required.

## Non-goals

- Threading a "current application" dialogue-scoped context through the
  configurator tool schemas (would require a broader tool-schema /
  dialogue-state change) — out of scope; the chosen fix (deterministic
  refusal + human disambiguation message) does not require it.
- Changing `UNIQUE(tenant_id, application_id, slug)` schema constraint.
