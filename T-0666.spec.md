# T-0666 — Спека: сохранение формы (POST /api/forms/binding) недоступно владельцу

**Status:** ready
**Task:** T-0666 [substrate/P0, столп 2 — интерфейс из блоков на данных]
**Date:** 2026-07-05
**База:** worktree `task/T-0666-forms-save-access`, от `dev@ba8dba4`

---

## 1. Проблема

`checkRole` (`src/http/binding.ts:153-180`) — единственная функция, гейтящая
запись форм-биндинга ролью `process_designer`, разделяемая ТРЕМЯ HTTP-путями:

- `POST /tenants/:tenantId/processes/:processKey/forms/:formKey/binding`
  (`binding.ts`)
- `POST /api/forms/binding` (`binding.ts`, actor-scoped)
- `PATCH .../edits` (`floor1-editor.ts` → `authorizeEditor` → `checkRole`)
- `POST /api/dmn-rule-tables[...]` (`dmn-rule-table.ts` → `authorizeDesigner` →
  `checkRole`)

В `keycloak`-режиме auth `checkRole` резолвит роль СТРОГО через

```sql
SELECT count(*) FROM choros.role_assignment ra
  JOIN choros.role r ON ...
  WHERE ra.tenant_id = $1 AND e.slug = $2 AND r.slug = 'process_designer'
```

Роль со slug `process_designer` **нигде не засеяна** — ни в дев-тенанте
(migrations 019/026), ни в `registerTenant` (`src/core/register.ts`, новые
самозарегистрированные тенанты), ни в бэкфилл-миграциях для существующих
тенантов (118/124). Итог: `count = 0` для ЛЮБОГО актора, включая владельца
тенанта — `checkRole` возвращает 403 FORBIDDEN ВСЕГДА в keycloak-режиме.

### 1.1. Почему это дыра, а не отсутствие фичи

Владелец тенанта (`tenant-owner`) уже имеет доступ ко всем остальным
mgmt-путям без ручной выдачи роли: оргструктура (`seed-write.ts`), LLM-connection
(`capability-grants-dao.ts::canConfigureLlmConnection`), системные агенты
(`canActorOperateSystemAgents`), делегирование прав (`loadAdminContext` /
`validateAdminDelegation`) — ВСЕ эти пути несут owner-short-circuit через
`isGenesisOwnerForTenant`/`loadAdminContext` (`src/db/org.ts`). Настройка форм —
такая же конфигурационная mgmt-операция (столп 2: интерфейс из блоков на
данных), но `checkRole` НЕ имеет этого шорт-circuit — единственный конвенциональный
(не PDP-грант) authz-путь во всей системе без owner bypass.

Обнаружено LIVE_PROOF T-0656: на живой приёмке пришлось выдавать
`process_designer` владельцу вручную в БД, чтобы сохранить форм-биндинг — это
обход, которого в продукте не существует (нет UI/API назначить роль, которой
нет ни у кого, и которую некому назначить, так как назначение ролей тоже
gated тем же mgmt-контуром, где владелец является единственным authority-root).

### 1.2. Root cause — два независимых дефекта

1. **Нет owner bypass** в `checkRole` — единственный конвенциональный authz-путь
   не следует уже установленному в `capability-grants-dao.ts` паттерну
   `if (await isGenesisOwnerForTenant(...)) return true;`.
2. **Роль `process_designer` не существует** ни в одном тенанте — даже если бы
   у владельца был отдельный грант-путь, назначить эту роль сотруднику-
   конструктору форм НЕВОЗМОЖНО (роль не существует как принципал).

## 2. Решение

### 2.1. Вариант A (обязательный) — owner bypass в `checkRole`

`checkRole` получает параметр `pool: pg.Pool` (помимо уже имеющихся `client`,
`tenantId`, `actorSlug`) и, в keycloak-режиме, ПЕРЕД role_assignment-запросом
проверяет:

```ts
if (await isGenesisOwnerForTenant(pool, tenantId, actorSlug, Date.now())) return;
```

`isGenesisOwnerForTenant` (`src/db/org.ts:721`) — уже гейченный T-0658
резолвер (`AND deactivated_at IS NULL` во внутреннем slug→employee подзапросе,
+ confirmed/in-window предикаты на `role_assignment`). Тот же резолвер, что
использует `capability-grants-dao.ts` (`canConfigureLlmConnection`,
`canActorOperateSystemAgents`) — ОДИН owner-authority путь, не второй.

Три вызывающих места обновляются, чтобб протащить `pool`:
- `binding.ts` — оба `POST`-хендлера (уже имеют `pool` в замыкании).
- `floor1-editor.ts::authorizeEditor` — уже принимает `pool: pg.Pool | null`.
- `dmn-rule-table.ts::authorizeDesigner` — уже принимает `pool: pg.Pool`.

Эффект: фикс `checkRole` закрывает дыру НА ВСЕХ ТРЁХ поверхностях одним местом
(single-resolver discipline — `checkRole` уже документирован как "single
source of truth for the process_designer authz convention").

### 2.2. Вариант B (доп.) — засев роли `process_designer`

`process_designer` — платформенный примитив (роль-конструктор форм, доступная
для делегирования сотруднику), не кейс-контент. Засевается КАК
`role-constructor-admin` (T-0469: seeded, но НЕ авто-назначена) — существует
как принцип, чтобы владелец мог назначить её штатному конструктору форм БЕЗ
доступа к БД напрямую:

- `src/core/register.ts` — новые тенанты получают роль `process_designer`
  (создаётся, не назначается) в той же транзакции, что и остальные
  tenant-zero роли (role-configurator, role-constructor-admin, role-reader).
- Миграция `128_process_designer_role_backfill.sql` — бэкфилл роли для
  СУЩЕСТВУЮЩИХ тенантов (мирроринг migration 118 паттерна:
  `INSERT ... SELECT ... FROM choros.tenant LEFT JOIN choros.role ... WHERE
  r.id IS NULL`, без хардкода tenant-UUID, идемпотентно).

Роль НЕ назначается никому автоматически (владелец получает доступ через
Вариант A bypass, не через эту роль) — семантика идентична
`role-constructor-admin`: существует для делегирования, назначение — акт
владельца через уже существующий rights-контур.

## 3. Критерии приёмки

- **AC-1** — `checkRole` принимает `pool` и в keycloak-режиме проверяет
  `isGenesisOwnerForTenant` ПЕРЕД role_assignment-запросом; owner → return
  (без 403), не-owner без роли → 403 (как раньше).
- **AC-2** — тест: владелец тенанта (без назначенной роли `process_designer`)
  → `POST /api/forms/binding` → 200/201 (было 403 до фикса).
- **AC-3** — тест: ДЕАКТИВИРОВАННЫЙ владелец → `isGenesisOwnerForTenant`
  возвращает false (T-0658 гейт) → падает на role_assignment-проверке (тоже
  0, роль не назначена) → 403 (владелец теряет доступ вместе с деактивацией,
  не в обход T-0658).
- **AC-4** — тест: рядовой сотрудник (не владелец, без роли `process_designer`)
  → 403 (доступ не разлит всем — owner bypass не ослабляет для остальных).
- **AC-5** — роль `process_designer` засевается в `register.ts` (новые
  тенанты) и в миграции-бэкфилле (существующие тенанты), НЕ авто-назначается
  никому.
- **AC-6** — `floor1-editor.ts` и `dmn-rule-table.ts` (оба вызывают
  `checkRole`) наследуют owner bypass без отдельного кода — риппл через общую
  функцию, не дублируется.
- **AC-7** — `npx tsc --noEmit`, `npx eslint src`, `npx vitest run` зелёные,
  число тестов не уменьшилось.
- **AC-8** — `npm run fitness:db` зелёный на живом PG (:55432), включая
  db-тест миграции 128 (роль появляется в существующем тенанте, идемпотентно).
- **AC-9** — `ci/checks/http-route-auth-coverage.sh`,
  `grant-resolver-isolation.sh`, `dual-control-isolation.sh`,
  `anti-case-lock.sh`, `role-migration-set.sh` — зелёные.
- **AC-10** — GET-путь биндинга (`getBinding`/layout, T-0665) НЕ тронут.

## 4. Границы

- НЕ трогается `getBinding`/`getBindingLayout`/`classifyLayoutSave` (T-0665
  parallel scope).
- НЕ вводится второй resolver — `checkRole` остаётся единственной функцией,
  `isGenesisOwnerForTenant` — единственный owner-резолвер (переиспользуется,
  не копируется).
- Роль `process_designer` — НЕ кейс-специфична, платформенный примитив (как
  `role-configurator`/`role-reader`/`role-constructor-admin`).
- Назначение роли `process_designer` реальному сотруднику — вне скоупа (уже
  существующий rights-контур делает это; данная задача только гарантирует, что
  роль СУЩЕСТВУЕТ и что владелец не заперт до момента, когда кому-то её
  назначат).
