## 1. Анти-UUID на узлах — доказано структурно, не только тестом

`NodeRef` (`web/src/components/components.jsx:385-398`) устроен СТРОЖЕ, чем `ActorChip`: у `ActorChip` есть путь
`(!idIsMachineKey && safeId)` — фоллбэк на сырой id, если имя демотировано, а id не является машинным ключом. У `NodeRef`
такого пути НЕТ ВООБЩЕ:

```js
const resolvedName = rawName && !nameIsMachineKey ? rawName : null;
const displayName = resolvedName || meta.deletedLabel;
```

Единственные два исхода — резолвленное человекочитаемое имя, либо `meta.deletedLabel` ("Отдел удалён"/"Должность
удалена"/"Узел удалён" для неизвестного kind). Raw id физически не может попасть в `displayName` ни при каком входе —
это НЕ «гейт поймал бы», это архитектурная невозможность. `isMachineActorLabel` (переиспользован, T-0685) якорится
regex'ом `^...$` (полная строка), матчит UUID v1-v5 case-insensitive — id узла всегда его пройдёт.

Проверил вручную краевые случаи, которых нет в тестах: `id` без `name` → tooltip = `meta.label` (без "undefined");
`name`, случайно похожее на UUID (гипотетически) — демотируется тем же путём, что честный фоллбэк резолвера. Пустой
`display_name`/`title` через API невозможен (`seed-write.ts:376,480,651,768` создание И `seed-write.ts:878-881` PATCH —
`display_name.length === 0` → `400 VALIDATION` на обоих путях), так что вырожденный кейс "резолвлен, но имя пустая
строка" не достижим через продукт.

`ci/checks/ux/anti-uuid-actor-render.sh` (0 находок + `--self-test` PASS) — гейт по замыслу целится в `.actor/
.claimedBy/.completedBy/.assignee/.recordId/.execSlug` (акторский слой), не в узловый `target`; для узлового слоя
анти-UUID закрыт напрямую `node-ref.test.jsx` (9/9) — честно, не притворяюсь, что bash-гейт покрывает этот класс.

## 2. Кросс-тенант — прогнал сам, live-PG

`batchResolveOrgNodes`'s `withTenant` — byte-identical копия `actor-resolver.ts`'s (сверил построчно): `assertUuid`
гвардит `tenantId` до интерполяции в `SET LOCAL choros.tenant_id = '${tenantId}'` (regex-anchored UUID, инъекция
закрыта на уровне формата, не на уровне escaping — тот же установленный паттерн, что уже адверсарно проверен на
T-0648/T-0685). ПЛЮС литеральный `WHERE tenant_id = $1` в самом запросе — двойной замок, как и заявлено.

RLS подтверждён в миграциях: `014_department.sql` и `015_position.sql` — `ENABLE ROW LEVEL SECURITY` +
`FORCE ROW LEVEL SECURITY` + policy `tenant_id = current_setting('choros.tenant_id', true)::uuid` на обеих таблицах.

Живой прогон (`DATABASE_URL=postgres://choros_migrator:...@localhost:55432/choros npx vitest run --dir ci/checks/db
org-move-api.db.test.ts --no-file-parallelism`) — **5/5 passed**, вкл. `AC-audit-read-node` через РЕАЛЬНЫЙ HTTP-роут
(`registerAuditRoutes` на том же роутере, что `registerSeedWriteRoutes`) — GET `/api/audit?action=department.moved`
резолвит `targetDisplay.name` в ЖИВОЕ значение (`'Переименовано'`), записанное этим же сьютом секундой раньше —
доказывает не фикстуру, а реальный Postgres-путь.

Прямого live-негативного кросс-тенантного кейса (создать узел под тенантом A, запросить audit под тенантом B, увидеть
честный miss) в `org-move-api.db.test.ts` нет — но это покрыто (а) unit-тестом `audit-log.test.ts`'s HTTP-уровневым
кейсом "CROSS-TENANT node id never resolves" (мок-pool, проверяет, что параметр запроса = TENANT_B, никогда TENANT_A)
и (б) `node-resolver.test.ts` case (g) (tenant-scope параметра). Сама RLS-политика — не новый код этой задачи (миграции
014/015 существуют с T-0017, уже покрыты `cross-tenant-fitness.sh` в общем fitness-наборе). Достаточно для approve —
не blocking, но фиксирую как наблюдение: полный e2e live-кросс-тенантный негатив специфично для node-resolver.ts
живьём не прогонялся ни строителем, ни мной (только его "половинки" — RLS живьём для смежных таблиц, tenant-scope
параметра юнит-тестом).

## 3. Батч не N+1

`SELECT ... FROM choros.department ... UNION ALL SELECT ... FROM choros.position ...` — один SQL-запрос, оба
`ANY($2::text[])`/`ANY($3::text[])` независимы, пустая сторона не роняет (`ANY('{}')` не матчит). Прогнал
`node-resolver.test.ts` сам — `queryCount()===1` для смешанной department+position страницы (10/10 тестов). В
`audit.ts` батч вызывается РОВНО ОДИН РАЗ на страницу (`handleGetAuditLog`), гвардится `if (distinctDeptIds.size > 0
|| distinctPosIds.size > 0)` — страница без `.moved`-эвентов node-резолвер не трогает вовсе (проверил тест на
`nodeSql === null`).

## 6. UX консистентность

`NodeRef` использует `--chs-text-sm` — ТОТ ЖЕ размер, что `.chs-exec` (базовый класс ExecutorBadge/ActorChip,
`components.css:14`), так что оба чипа в одной строке аудита визуально соразмерны. `--chs-color-text-faint` для
unresolved-состояния — существующий theme-paired токен (`tokens.css:160` light / `:230` dark), не новый хардкод;
`ux-g2-theme-pairing.sh` PASS, `ux-g6-no-new-hardcode.sh` — 0 новых хардкод-находок. NodeRef НЕ копирует
chip-визуал ActorChip (нет фона/бордера/глифа) — осознанное решение, задокументированное в ADR §2.1: узел — не актор,
глиф human/agent/service исказил бы отдел под системного актора. Согласен с решением: узел с чужим глифом был бы
худшим UX, чем простой текст.

Real-click браузером не гонял (стенд offline в этой сессии по заявлению строителя; сама задача — точечный текстовый/
read-only фикс без нового интерактивного поведения — hover/tooltip, без форм/модалок/навигации). Достаточность
покрытия для этого класса изменения: NodeRef — pure function component без хуков, юнит-тесты бьют РЕАЛЬНЫЙ рендер-дерево
(не снапшот верстки), структурная проверка через `findElementsByType` в `screen-audit.test.jsx` — этого достаточно для
approve текстового примитива без нового layout/interaction surface.

  T-0017), а `withTenant` — byte-identical проверенный паттерн. Рекомендация follow-up (не срочно): добавить в
  `org-move-api.db.test.ts` прямой live-негатив (второй тенант, department.moved от тенанта A, GET /api/audit тенантом
