# T-0712 — `/audit` человеко-summary + чип цели для `*.moved` (move-API)

> P3 из LIVE_PROOF T-0655 (эпик E-UX-HUMAN T-0647, spec `docs/design/ux-study-2026-07-05.md`).
> Родня: T-0648 (batch actor-resolver + ActorChip + anti-uuid-actor-render гейт),
> T-0500 (реальный `/api/audit`), T-0655 (move-API + `*.moved` writer).

## Дефект (что было)

`department.moved` / `position.moved` / `employee.moved` (записаны move-API
T-0655, `src/http/seed-write.ts`) на экране `/audit` рендерились БЕЗ
человеко-summary: `summaryFor()` (`src/db/audit-read-dao.ts`) не знает эти три
типа → падает на честный, но сырой fallback — **раздаётся сам `type`**
(«employee.moved») как единственный текст строки. Чипа цели тоже нет:
`safeTarget()` ищет запись только среди узкого `SAFE_TARGET_KEYS`
(`record_id`, `grant_id`, …) — move-diff-пейлоуд (`buildEmployeeMoveDiff` и
соседи, `src/core/org-move.ts`) не несёт НИ ОДНОГО из этих ключей (только
`from_position_id`/`to_position_id`/`renamed`/`from_name`/`to_name`), поэтому
`target` всегда `null` для всех трёх типов. Эталон — `record.create`: у него
ЕСТЬ `payload.record_id` (`SAFE_TARGET_KEYS`), поэтому строка уже несёт
чип-цель (`MonoId chip`) поверх канонической summary `"Событие записи"`.

## Диагноз: данных для чипа цели уже достаточно — БЕЗ writer-правки

`appendAuditEvent` (T-0655 seed-write.ts:924/1018/1113) уже пишет
`subject: deptId|posId|empId` — колонка `audit_event.subject` — в КАЖДОЕ
`*.moved` событие с САМОГО ПЕРВОГО коммита T-0655 (см.
`ci/checks/db/org-move-api.db.test.ts:171`, которая уже читает
`WHERE subject = $3`). Читающий DAO эту колонку просто никогда не
`SELECT`-ил. Значит: чип цели чинится ЧИСТО на чтении (доп. колонка в
SELECT), работает РЕТРОАКТИВНО на все существующие строки (не только новые) —
никакой деградации старых строк не возникает вовсе, т.к. `subject` был у них
всегда. **Writer НЕ трогаем** (append-only дисциплина — `audit_append_only`,
`audit_writer_isolation` — соблюдена тривиально: 0 диффа в
`src/db/audit-writer.ts` / `src/http/seed-write.ts` / `src/core/org-move.ts`).

Summary — тоже без новых данных: `renamed` (bool) и присутствие
`to_parent_id`/`to_department_id`/`to_position_id` (ключ, не его значение)
УЖЕ в текущем payload — этого достаточно, чтобы различить
переместили/переименовали/оба, не эхоя ни одного free-text значения
(`from_name`/`to_name` остаются НЕ читаемыми в summary — та же дисциплина
редакции, что и у остального `audit-read-dao.ts`: "summary — canned per
prefix, NEVER free-text from payload").

## Матрица (что показываем)

| type | payload-ключи moved-диффа | summary (варианты) | target / чип |
|---|---|---|---|
| `department.moved` | `to_parent_id` (moved), `renamed` (bool) | «Отдел перемещён» / «Отдел переименован» / «Отдел перемещён и переименован» / «Отдел изменён» (защитный fallback — на практике недостижим, `isEmptyPatch` гейтит пустой patch на 400 ДО audit-записи) | `subject` (id отдела) → `MonoId chip` — как у `record.create` (нет резолвера имени отдела; честная деградация до id-чипа, не имя) |
| `position.moved` | `to_department_id`, `renamed` | «Должность перемещена» / «Должность переименована» / «…перемещена и переименована» / «Должность изменена» | `subject` (id должности) → `MonoId chip` |
| `employee.moved` | `to_position_id`, `renamed` | «Сотрудник перемещён» / «Сотрудник переименован» / «…перемещён и переименован» / «Сотрудник изменён» | `subject` (id сотрудника) → **`ActorChip`** (сотрудник — та же таблица `choros.employee`, что и акторы; резолвится ТЕМ ЖЕ batch-резолвером T-0648, `batchResolveActors` матчит по `slug` ИЛИ `id`) |

`employee.moved` — единственный из трёх, где перемещаемая сущность сама
является «актором» (строка `choros.employee`), поэтому получает ПОЛНЫЙ
человеко-чип (имя + honest-деградация на деактивированный/неразрешённый id —
уже встроена в `ActorChip`/`resolveActorDisplay`, см. T-0648/T-0658). Для
department/position нет батч-резолвера имени (вне скоупа P3 — завёл
follow-up ниже) — id-чип остаётся честным, не хуже чем сейчас у
`record.create`.

## Не в скоупе (осознанно)

- Резолвинг человеческого ИМЕНИ отдела/должности (не id) в чип — отдельная
  задача (батч-резолвер по `choros.department`/`choros.position`, зеркало
  `actor-resolver.ts`). Follow-up ниже.
- «из X в Y» с двумя чипами (from/department-position) — задача просит
  «summary … ИЛИ по фактическим данным payload»: фактические данные не несут
  имён, только id; один чип цели (кто/что переместили) — тот же уровень
  детализации, что у `record.create` сегодня.
- Никаких изменений в `src/db/audit-writer.ts`, `src/http/seed-write.ts`,
  `src/core/org-move.ts` — read-only обогащение.

## Реализация

### `src/db/audit-read-dao.ts`
- `AuditRow` += `subject: string | null` (колонка уже существует, миграция
  006); SQL `SELECT` += `subject`.
- `summaryFor(type, payload)` (было `summaryFor(type)`): для трёх `.moved`
  типов делегирует в `summaryForMoved()` — читает ТОЛЬКО ключ-presence
  (`"to_..." in payload`) + `renamed === true`, никогда значение. Прочие типы
  — байт-идентичное поведение (`SUMMARY_BY_PREFIX`, без изменений).
- `safeTarget()` переименован в `safeTargetFromPayload()` (тело без
  изменений) + новая обёртка `safeTarget(type, payload, subject)`: сначала
  пробует `SAFE_TARGET_KEYS` payload (как раньше, для ВСЕХ типов), и ТОЛЬКО
  если тот вернул `null` И `type` — один из трёх `.moved` — падает на
  `subject`. Для любого другого типа поведение НЕ меняется (subject
  игнорируется).

### `src/http/audit.ts`
- `distinctActors`, помимо `item.actor`, теперь включает `item.target` для
  строк `action === "employee.moved"` (тот же единственный batch-запрос,
  просто более широкий IN-список — без нового round-trip).
- Ответ `events[]` += `targetDisplay` (та же форма `ResolvedActor`, что и
  `actorDisplay`) — заполнен ТОЛЬКО для `employee.moved`, иначе `null`.

### `web/src/screens/screen-audit.jsx`
- `AuditEventRow`: если `ev.targetDisplay` присутствует — рендерит
  `<ActorChip .../>` вместо старого `<MonoId chip>{ev.target}</MonoId>`
  (сотрудник получает ПОЛНЫЙ человеко-чип); иначе — прежний
  `<MonoId chip>{ev.target}</MonoId>` (id-чип, department/position/record/…
  без изменений).
- Никаких новых голых `{ev.xxx}`-рендеров — `anti-uuid-actor-render.sh`
  сканирует ТОЛЬКО `.actor/.claimedBy/.completedBy/.assignee/.recordId/
  .execSlug`; `.target`/`.targetDisplay` не в списке, но всё равно уходят
  через `MonoId`/`ActorChip` — без риска.

## Деградация старых строк

Т.к. `subject` уже был в КАЖДОМ `*.moved` событии с момента T-0655 — деградации
НЕТ: все существующие строки получают чип цели ретроактивно. Единственный
теоретический edge-case — `subject === null` (не должно случаться для этих
трёх типов, `seed-write.ts` всегда передаёт непустой id) — код defensively
не показывает чип, summary всё равно человеко-читаема (уже улучшение
относительно сырого `type`).
