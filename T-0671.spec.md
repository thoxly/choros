# T-0671 — Пикер процессов привязки включает движковые процессы (source=engine)

Родитель: эпик T-0479. Спека контура: `docs/design/ADR-T0665-forms-e2e-contour.md`.
Столп 2/3 (интерфейс-из-блоков-на-данных + бесшовность). forms/nit.

## 1. Проблема (как есть, до задачи)

`FormDesigner.jsx` («Привязка», T-0665) грузит `/api/process-catalog` и
фильтрует пикер «Процесс» предикатом `d.status === 'published'`
(`web/src/forms/FormDesigner.jsx:656`).

`/api/process-catalog` отдаёт определения из ДВУХ честных источников
(`src/core/process-catalog-view.ts buildCatalogDefinitions`):

- `source: 'modeler'` — строка `choros.process_definition` (074): `status`
  реально `'draft'` или `'published'`.
- `source: 'engine'` — процесс, задеплоенный НАПРЯМУЮ во Flowable (например
  эталонный `telLinear`, `config/flowable/processes/`), без строки в
  `process_definition`. У такого определения `status` ВСЕГДА `'deployed'`
  (см. `buildCatalogDefinitions`, ветка 2) — оно физически не может пройти
  `status === 'published'`.

Итог: движковые процессы (реально живые, с реальными запущенными
инстансами — например `telLinear`, 25 живых инстансов на стенде)
НИКОГДА не попадают в пикер привязки форм, хотя это ровно те процессы,
которые реально исполняются и которым форма нужнее всего.

## 2. Честный предикат

Привязываемый процесс = процесс, который реально можно исполнять:
- `source === 'engine'` (задеплоен напрямую в движок, живой по построению —
  `buildCatalogDefinitions` добавляет `engine`-запись ТОЛЬКО если есть хотя бы
  один реальный observed instance) **ИЛИ**
- `status === 'published'` (модельный процесс, осознанно опубликованный
  из UI-модельера).

Черновик модельера (`source==='modeler', status==='draft'`) остаётся
НЕ предлагаемым — его BPMN ещё может измениться/потерять шаг (см.
ADR-T0665 §5, риск сохраняется, этой задачей не ослабляется).

Новый предикат в `FormDesigner.jsx`:

```js
const defs = (data.definitions || []).filter(
  (d) => d.source === 'engine' || d.status === 'published',
);
```

## 3. Что НЕ меняется

- T-0669 (фильтрация пикера «Приложение» через `/api/process-app-bindings`,
  `boundAppIdsForProcess`) — работает по `process_key` строкового совпадения,
  не зависит от `source`/`status` процесса. Движковый процесс с реальной
  строкой в `process_app_binding` фильтруется точно так же, как модельный.
- `FormBuilder.jsx` — уже не фильтрует `/api/process-catalog` вообще (несёт
  весь список, включая `engine`/`draft`), вне скоупа этой задачи (nit только
  про `FormDesigner`).
- `/api/process-catalog`, `buildCatalogDefinitions`, серверная честность
  источников — не трогаются (чисто клиентский предикат).
- `classifyLayoutSave`/`resolveLiveRecordSchema` (fail-closed судья на save,
  ADR §5) — не ослабляется; реальная защита от неисполнимой связки остаётся
  на сервере.

## 4. Acceptance criteria

- **AC-1 (engine виден)**: процесс с `source==='engine'` (независимо от
  `status`) присутствует в списке опций пикера «Процесс».
- **AC-2 (draft по-прежнему скрыт)**: процесс с `source==='modeler',
  status==='draft'` НЕ присутствует в списке опций пикера «Процесс».
- **AC-3 (published по-прежнему виден, не регресс)**: процесс с
  `source==='modeler', status==='published'` присутствует (как до задачи).
- **AC-4 (T-0669 работает для engine-процесса)**: когда выбран
  `source==='engine'` процесс, пикер «Приложение» фильтруется через
  `boundAppIdsForProcess`/`process_app_binding` точно так же, как для
  модельного процесса — engine-процесс не получает особый путь.

## 5. Вне скоупа

- Правка `FormBuilder.jsx` (уже честен, ничего не фильтрует).
- Серверная сторона (`process-catalog.ts`, `process-catalog-view.ts`) —
  предикат `source`/`status` уже честный, меняется только клиентский фильтр.
- Анти-кейс: НЕ вносить литерал `telLinear` в код — предикат общий
  (`source === 'engine'`), не завязан на конкретный ключ процесса.
