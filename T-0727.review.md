## Критично — п.1: authz vs short-circuit (потенциальная дыра info-leak / ложного успеха)

**ЧИСТО. Authz стоит ДО short-circuit — дыры нет.**

Порядок в `registerUserMgmtRoutes` → PATCH `/api/users/:employee_id`:

| строка | шаг |
|--------|-----|
| 589 | `withAuth(...)` — аутентификация (route-level) |
| 596-597 | `extractActor` / `resolveActorTenant` — актор + ЕГО tenant |
| **601-605** | **`assertOrgObjectAuthority(admin, "mgmt_object:employee", "update", ...)` — АВТОРИЗАЦИЯ вызывающего (owner или mgmt_object:employee grant, иначе 403)** |
| 607-611 | чтение body, валидация `active` |
| 618-624 | target-lookup под RLS СВОЕГО tenant (`WHERE tenant_id=$1 AND id=$2`) |
| 625-627 | 404 если не найден / не human |
| **647-653** | **IDEMPOTENT NO-OP short-circuit** |

Authz-гейт (601) выполняется на КАЖДЫЙ запрос ДО того, как поток дойдёт до short-circuit (647). Не-уполномоченный вызывающий получает **403 ещё на строке 601** и НИКОГДА не достигает short-circuit — существующий тест FF-583-6 («non-privileged tenant member → 403 ADMIN_GATE_REJECTED на POST и PATCH») это фиксирует, он в тех же 36/36 зелёных. Значит:

- **не-уполномоченный не может «деактивировать» уже-деактивированного и получить ложный 200** — он не проходит 601;
- **info-leak состояния `deactivated_at` невозможен** — во-первых, чтобы дойти до short-circuit, нужно пройти authz; во-вторых, target-lookup RLS-ограничен tenant'ом актора (чужой employee_id → 404), а уполномоченный внутри своего tenant и так видит статус через `GET /accounts`. Short-circuit не раскрывает ничего сверх уже доступного.

Вывод по п.1: **short-circuit НЕ обходит authz** — он живёт ЗА authz-гейтом. Blocking-условие не сработало.

## п.2 — last-owner guard за short-circuit

**Безопасно.** Short-circuit срабатывает ТОЛЬКО при `alreadyInTargetState = (deactivated_at===null)===active` (текущее == запрошенному). Любая РЕАЛЬНАЯ деактивация активного владельца: current(active)≠requested(inactive) → `alreadyInTargetState=false` → НЕ короткозамыкается → проходит last-owner guard (668-711). Обойти guard реальной транзицией невозможно. No-op пропускает guard безвредно (цель уже деактивирована — защищать нечего). Порядок «до guard» дополнительно верен: избегает спурьёзного 409 LAST_OWNER на повторе из-за НЕСВЯЗАННОЙ поздней смены владельцев (ADR §3.1).

## п.3 — recovery честен + идемпотентность KC

**KC-вызовы идемпотентны по конструкции (проверено в коде порта):**
- `setUserEnabled(userId,false)` (admin-port.ts:493-512): PUT `{enabled}` → KC отдаёт 204/200 на повторную установку того же значения → не бросает. На уже-disabled — ок.
- `revokeUserSessions(userId)` (admin-port.ts:519-532): POST `/logout` → 204 даже на уже-разлогиненного; и обёрнут try/catch → любой сбой = `{revoked:false}`, НИКОГДА не бросает.

Recovery: `deactivated_at` сброшен в NULL (модель упавшей tx) → DB честно читает «active» → `alreadyInTargetState=false` → no-op НЕ срабатывает → полный re-run: guard → setUserEnabled (2-й раз, ок) → revoke (2-й раз, ок) → tx коммитится → `deactivated_at` проставлен. Тест FF-727-RECOVERY это доказывает живьём (setEnabledCallCount=2, revokeSessionsCallCount=2, deactivated_at not null).

Зафиксировано (R-1, nit): если tx падает СНОВА на recovery — оператор повторяет ещё раз (unbounded, но operator-visible; ADR §8 явно out-of-scope, согласуется с no-job-queue позицией T-0702). Приемлемо.

## п.4 — race-guard

**Корректно.** Два конкурентных `PATCH active=false`: оба проходят short-circuit (оба читают deactivated_at IS NULL), оба зовут KC (двойной disable+revoke — идемпотентно/безвредно), оба бьют в guarded `UPDATE ... WHERE deactivated_at IS NULL RETURNING id`. Под READ COMMITTED второй UPDATE блокируется на row-lock, после коммита первого пере-оценивает WHERE → 0 строк → пропускает audit (785-788 `return`), но всё равно доходит до 806 → честный 200 `{employee_id, active:false}`. Итог: оба 200 (конечное состояние верно), РОВНО один audit, KC вызван дважды (безвредно). Проигравший гонку НЕ пишет второй audit и НЕ врёт клиенту. Nit R-2: живого concurrency-теста нет (был бы флейки), но паттерн WHERE-guard+RETURNING верен по MVCC.

## п.5 — warn не шумит на норме, без утечки

`console.warn` внутри `if (!revoked)` (751) — только при ПРОВАЛЕ revoke, на успехе молчит. Контент: `employeeId` (UUID) + `kcUserId` (KC sub — не секрет); ни пароля, ни токена. Гейт `user-mgmt-no-secret-leak.sh` PASS. Конвенция `console.warn` `[<module> T-XXXX]` подтверждена: peers `inbox.ts:1476` / `timer-firing-loop.ts:132` используют bare `console.warn` БЕЗ eslint-disable; в `src/` ноль `eslint-disable no-console` — новый код консистентен, `no-console` warning (не error) — существующий принятый класс.

### Findings

- **R-1 (nit, ось 1):** recovery = ручной повтор PATCH; повторный провал tx → unbounded operator-retry. Operator-visible, ADR §8 out-of-scope. Action не требуется.
- **R-2 (nit, ось 3):** concurrency-race защищён конструкцией (WHERE-guard+RETURNING под READ COMMITTED), но нет живого concurrency-теста (был бы флейки). Приемлемо.
- **R-3 (nit, ось 5):** R-4 warn теперь эмитится и в stderr пре-существующего FF-702-DEGRADE теста — ожидаемо (тест намеренно валит revoke), безвредно.
