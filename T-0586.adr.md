# ADR · T-0586 — agentTask живьём: флип `liveEnabled` + per-job BYO LLM-порт

**Phase:** DESIGN · **Status:** ready (обе ND-развилки машинные, решены здесь; фаундера не зовём) · **Date:** 2026-07-04
**Task:** T-0586 [столп 4 — агенты как сотрудники] · **Spec:** `T-0586.spec.md` (status: ready)
**Seam:** T-0587 (аналитик в правах / READ-PDP) — общий LLM/secret-слой правим ТОЛЬКО аддитивно.

**Foundation (факты кода, проверено точечно):**
- `src/server/agent-dispatch-loop.ts:468` (`buildDegradedAgentDispatchDeps`) и `:521` (`buildAgentDispatchDeps`) — оба литералом пишут `runDeps: { llm: dormantLlmPort, liveEnabled: false }`. Это ЕДИНСТВЕННЫЙ разрыв. `buildAgentDispatchDeps` уже получает `env: NodeJS.ProcessEnv` и читает из него `AGENT_TOPICS` (:490) и `AGENT_WORKER_ID` (:523), а также имеет `production.pool` (:488).
- `src/runtime/agent-dispatch/run-agent-step.ts:175-176` — живой гейт написан правильно: `const port = deps.liveEnabled && llmConfigured(ctx.llm) ? deps.llm : dormantLlmPort;`. При флипе заработает без изменений мотора.
- `src/runtime/agent-dispatch/agent-step-context.ts:290-292,339-345` — `ctx.llm` УЖЕ собирается per-job через `readAgentCardLlmConfigById(tx, tenantId, agentEmployeeId)` (`src/db/agent-provision.ts:251`), который COALESCE-резолвит `llm_connection` (реестр 094) с фолбэком на легаси `agent_card.llm_*` и алиасит секрет в `secret_handle_ref`. Конфиг конкретного агента УЖЕ в контексте — переспрашивать БД не нужно.
- `src/adapters/openai-llm-port.ts:104` — `OpenAILlmPort` конструируется из `{endpoint, model, secretHandle, tenantId, secretResolver}`, при провале (невалидный ключ / HTTP≥400 / таймаут / сеть) бросает **типизированный `LlmUnavailableError`** (`src/core/llm-port.ts:217`). Применяет `assertSafeEndpoint` (SSRF) и `validateSecretHandleShape` (RL-3).
- `src/server.ts:154` `tenantSecretResolver` (экспорт, `SecretResolverPort`) — тот же резолвер, что использует assistant-путь; секрет резолвится в момент вызова, не логируется (redactHandle).
- `src/core/llm-port.ts:297` `canonicalizeLlmError(err)` — готовая чистая (без сети) функция: превращает пойманную LLM-ошибку в человекочитаемую русскую фразу без жаргона («Ключ LLM отклонён провайдером. Проверьте или замените ключ в LLM-соединениях.»).

---

## 1. Проблема

«Ни один агент никогда не исполнил ни одного шага» — не архитектурный пробел, а два
хардкод-литерала `liveEnabled: false` в композиционном корне. Вся BYO-цепочка
(`agent_card.llm_connection_id → llm_connection → secret_handle → OpenAILlmPort`), весь
мотор (`run-agent-step.ts` / `dispatch-outcome.ts` / `agent-precheck-motor.ts`), весь
defer→инбокс (`audit_event(agent.deferred)` → «Эскалации») — построены, юнит-тестированы и
живут в проде через assistant-путь. Не хватает одного: композиция agent-dispatch не читает
деплой-флаг и не строит живой порт из уже-собранного per-job конфига `ctx.llm`.

T-0378/T-0460 ADR прямо назвали это финальным флипом («LIVE proceed with a paid LLM — flip
`llm_*` after — follow-up flip, no code» / «FOUNDER-GATED live proof... Requires LLM key +
deploy GO»). Это не редизайн — это последний рубильник.

## 2. Решение (одним абзацем)

Заменить оба литерала `liveEnabled: false` на чтение деплой-флага `AGENT_LIVE_ENABLED` из
`env` (ровно как читается `AGENT_TOPICS`; дефолт/отсутствие/любое-не-`"true"` → `false`,
безопасный дормант). Когда флаг включён, `buildAgentDispatchDeps` дополнительно кладёт в
`runDeps` **новое аддитивное опциональное поле `llmPortFactory`** — per-job фабрику
`(cfg) => LlmPort`, которая строит реальный `OpenAILlmPort` из per-job конфига агента,
используя тот же `tenantSecretResolver`, что и assistant-путь. Мотор (`run-agent-step.ts`)
в живом гейте берёт `deps.llmPortFactory?.(ctx.llm) ?? deps.llm` — когда фабрика есть,
порт строится per-job из `ctx.llm` (свежий конфиг, без кэша в памяти процесса); когда
фабрики нет (юнит-тесты, degraded), поведение прежнее (`deps.llm` = стаб/дормант). Живой
провал вызова (`LlmUnavailableError`) классифицируется **в defer-to-human** с
человекочитаемой причиной (`canonicalizeLlmError`), а НЕ в fail-closed — так сломанный ключ
попадает в «Эскалации», процесс не зависает. Сигнатуры общих экспортов (`makeLlmPortFactory`,
`readAgentCardLlmConfigById`, `OpenAILlmPort`, `tenantSecretResolver`) не меняются — всё
аддитивно (шов с T-0587).

## 3. ND-развилки (решено машинно, фаундера не зовём)

### ND-1 — Форма флага `liveEnabled`: **ВАРИАНТ А (env-флаг деплой-уровня)**

**Решение:** `AGENT_LIVE_ENABLED` — булев env-флаг процесса, читаемый в
`buildAgentDispatchDeps` идентично `AGENT_TOPICS`. Дефолт при отсутствии/пустой строке/любом
значении кроме точного `"true"` = `false` (дормант).

**Обоснование (взвешено против per-tenant поля):**
1. Само намерение в коде и в T-0378/T-0460 ADR прямо называет это «config flip, no code
   change» — дизайн УЖЕ это предполагал.
2. Per-agent гранулярность УЖЕ существует на другом уровне: агент без `llm_connection_id`
   физически не может исполнить (`llmConfigured(ctx.llm)` → `false` → `dormantLlmPort`).
   Значит «кто именно живой» управляется из UI привязкой/отвязкой `llm_connection` к
   конкретному агенту. Глобальный флаг лишь открывает ворота тем агентам, у кого привязка
   уже есть.
3. **Stage-2 бюджеты/потолки агентов (T-0036+, T-0378-F3) ещё не построены** (gate C =
   `stubBudgetPort {exhausted:false}`). Без потолков расходов per-tenant рубильник дал бы
   ложное чувство управляемости («включил тенанту» ≠ «ограничил его траты»). Деплой-рубильник
   = честный минимум: один оператор, один стенд, один осознанный «включить». Per-tenant
   управляемость — следующая волна, ПОСЛЕ того как `proceed` доказан хоть для одного тенанта
   и построены бюджеты.
4. Не требует миграции (NF6), не расширяет объём за «флип+вызов».

**Отвергнуто — Вариант Б (per-tenant флаг в БД + UI-переключатель):** отдельный кусок работы
(миграция + гейт видимости + UI-экран), выходит за рамки «первый агент живьём»; и
преждевременен без Stage-2 бюджетов. Зафиксирован как явный follow-up.

### ND-2 — Момент конструирования LLM-порта: **ВАРИАНТ Б (shared фабрика в deps, вызов per-job)**

**Решение:** `RunAgentStepDeps` (тип ВНУТРИ зоны T-0586) получает НОВОЕ аддитивное
**опциональное** поле `llmPortFactory?: (cfg: LiveLlmConfig) => LlmPort`. Существующее поле
`llm: LlmPort` СОХРАНЯЕТСЯ как есть (frozen-контракт weld-тестов). В живом гейте мотор строит
порт per-job: `deps.llmPortFactory?.(liveCfgFromCtx(ctx.llm)) ?? deps.llm`. Фабрика читает
per-job `ctx.llm` (endpoint/model/secretHandle), уже зарезолвленный `readAgentCardLlmConfigById`
внутри tenant-tx — БЕЗ второго чтения БД, БЕЗ карты портов в памяти процесса, БЕЗ кэша ключа.

**Обоснование (взвешено: стоимость чтения-на-шаг vs правильность смены ключа):**
- **Правильность:** `ctx.llm` собирается заново на каждый job (`assembleAgentStepContext`
  вызывает `readAgentCardLlmConfigById` per-job). Значит смена ключа/коннекшна в UI
  подхватывается следующим шагом БЕЗ рестарта процесса — так же, как assistant-путь
  (`makeLlmPortFactory` вызывается per-request, «no caching» по PD-5). Секрет резолвится
  внутри `OpenAILlmPort.complete()` в момент вызова — не кэшируется в замыкании.
- **Стоимость:** нулевая дополнительная. Конфиг агента УЖЕ читается per-job (это делает
  `assembleAgentStepContext` независимо от нас). Фабрика лишь оборачивает уже-прочитанный
  `ctx.llm` в объект `OpenAILlmPort` (конструктор — чистая валидация формы хендла, без сети).
  Никакого «чтения конфига на шаг» СВЕРХ уже существующего.
- **Почему Б, а не «фабрика вместо порта» (замена типа `llm`):** заменить `RunAgentStepDeps.llm`
  с `LlmPort` на фабрику СЛОМАЛО БЫ frozen weld-тесты (AC-4/AC-5), которые передают
  `runDeps: { llm: stub, liveEnabled: ... }` — фиксированный порт, не фабрику. Аддитивное
  опциональное поле сохраняет DI-паттерн run-agent-step.ts (deps передаются один раз, фабрика
  зовётся per-job внутри) и все существующие тесты (фабрика `undefined` → фолбэк на `deps.llm`).

**Отвергнуто — Вариант А (порт строится внутри цикла диспетчера напрямую, без поля в deps):**
пришлось бы либо тянуть pool/резолвер в `runAgentDispatchOnce` (загрязняет чистый мотор), либо
строить порт в `agent-dispatch-loop.ts` до вызова мотора без знания `ctx.llm` (тогда порт не
per-agent). Вариант Б держит резолв per-job внутри мотора (где `ctx.llm` доступен) при чистой
инъекции фабрики из композиционного корня.

  Поле `llm: LlmPort` и `liveEnabled: boolean` — БЕЗ изменений.
- **Изменить** живой гейт (строка ~175-176):
  ```ts

  const port: LlmPort = liveConfigured
    ? (deps.llmPortFactory
        ? deps.llmPortFactory({
            tenantId: ctx.tenantId,
  ```

- **Изменить** classification (строки ~188-198): импортировать `LlmUnavailableError` и
  `canonicalizeLlmError` из `../../core/llm-port.js` (чистые, без сети) и **ДОБАВИТЬ ветку
  ПЕРЕД generic `else`**:
  ```ts

    // T-0586 F6(b): config exists but the live call failed (bad key / HTTP / net).
    // Route to defer-to-human (NOT fail-closed) so it lands in «Эскалации», with a
    // human-readable reason. The process does NOT hang; a human takes over.
    return {
      kind: "defer-to-human",
      signal: "model",

      inboxTaskRef: "pending",
    };
  } else if (err instanceof Error && err.message.toLowerCase().includes("timeout")) {
  ```

  `llm_error`. Стаб-порт бросает plain `Error` (не `LlmUnavailableError`), поэтому все
  существующие тесты (mode:"error"/"timeout"/"egress" → fail-closed) остаются зелёными.

  **Примечание по интеграции с `LlmOutcome`-формой (текущий catch, строки ~184-198):**
  catch не возвращает напрямую — он заполняет промежуточный `llmOutcome`, который
  потребляется сразу после (строки ~200-219). Coder волен реализовать defer одним из двух

  doubtReason: canonicalizeLlmError(err), inboxTaskRef:"pending" }` прямо в catch-ветке
  `LlmUnavailableError` (проще всего — исход детерминирован); ИЛИ (b) добавить флаг
  `deferUnavailable: true` + `doubtReason` в тип `LlmOutcome` (по образцу `dormant`) и в
  пост-catch блоке (~201) вернуть defer до fail-closed-ветки. Вариант (a) минимальнее и
  предпочтителен. Существующие `dormant`/`timeout`/`egress`/`llm_error` ветки не трогать.

## 5. Fail-safe семантика (политика ретраев + деградация)

| Условие | Путь | Исход | Инбокс? | Шаг закрыт? |
|---|---|---|---|---|
| Нет `llm_connection` (ctx.llm NULL) | `llmConfigured=false` → `dormantLlmPort` → `LlmDormantError` | defer-to-human (signal=dormant) | ✅ «Эскалации» | ✅ да |
| Ключ/коннекшн есть, вызов упал (401/сеть/таймаут) | `OpenAILlmPort` → `LlmUnavailableError` | **defer-to-human (signal=model)**, `doubtReason=canonicalizeLlmError` | ✅ «Эскалации» | ✅ да |
| Стаб/тест plain-Error (не типизирован) | generic `else` → `llm_error` | fail-closed (frozen контракт) | ✖ | ✖ (park) |
| Критичный шаг (gate B) | до вызова LLM | defer-to-human (signal=threshold) | ✅ | ✅ |
| `proceed` (confidence ≥ threshold) | живой порт | applyStepResult + agent.proceeded + close | — | ✅ |

**Ретраи:** **0 ретраев на уровне цикла для LLM-провала.** Мотор ловит `LlmUnavailableError`
ВНУТРИ и возвращает терминальный для этого шага `defer-to-human` (шаг закрывается, человек
берёт задачу) — НЕ пробрасывает исключение наверх, поэтому нет reclaim-на-lock-expiry
retry-шторма. Это ключевое отличие от fail-closed (который делает `jobStore.fail` + park и
НЕ закрывает шаг). Выбор defer-vs-fail-closed для живого провала — сознательное продуктовое
решение в пользу «человек продолжит из инбокса» (F6, AC-9), а не «процесс замер».

**Почему defer, а не fail-closed для `LlmUnavailableError`:** fail-closed (текущее поведение
generic-ветки) паркует job (`failRetries ?? 0` = терминальный park) и НЕ материализует
инбокс-задачу — процесс подвисает, человек не может продвинуть его из «Эскалаций». AC-9
явно требует defer-task в «Эскалациях» для сломанного ключа. Спека F6(b) это и подразумевает
(«уводит в defer-to-human»). Поэтому narrow типизированная ветка на `LlmUnavailableError`.
