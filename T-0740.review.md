## 1. Маркеры НЕ маскируют — оба РЕАЛЬНО несут гейт (главный вопрос)

**`getRoleSlugsForActor` (grants-dao.ts:431-494) — НЕСЁТ `${ACTOR_ACTIVE_SQL}` на ОБЕИХ выборках.** Hand-verified:
- первичная (grants-dao.ts:470): `SELECT id FROM choros.employee WHERE tenant_id=$1 AND slug=$2 AND ${ACTOR_ACTIVE_SQL} LIMIT 1`
- T-0366-фолбэк (grants-dao.ts:484): та же форма для `fallbackSlug`.
- `ACTOR_ACTIVE_SQL = "deactivated_at IS NULL"` (actor-authority-gate.ts:73). Добавлено T-0738 (inline-комментарий grants-dao.ts:444-467 цитирует находку T-0726).

**`resolveRolesForActor` (inbox.ts:428-439) — композирует `getRoleSlugsForActor` напрямую, без обхода.** DB-путь: `return await getRoleSlugsForActor(getOrgPool(), tenantId, actor, nowMs, fallbackActor)`. No-DB путь — фикстура `USER_ROLES` (тест-режим). Референс живой на **inbox.ts:1540** внутри блока `GET /api/inbox` (1435-1656): `const myRoles = await resolveRolesForActor(actor, inboxTenantId)`.

**Вывод:** маркеры легитимны — указывают на реальные резолверы, несущие предикат. НЕ evasion (маркер к незащищённому роуту). Ровно линия, которую стережёт self-test T-0662: если бы имя не несло предиката, FF-0662-1 упал бы.

## 2. `GET /api/inbox/:id` — честно оставлен, НАСТОЯЩАЯ дыра

Прочитан handler 1657-1789: вызывает `extractActorSlug` (резолюция актора, не authority), `findInboxItems(actor)` (tenant-scoped, БЕЗ ролевого фильтра), `findWaitingInstanceTask`/`listInstanceProjections` (проекции). **Ни `resolveRolesForActor`, ни `getRoleSlugsForActor`, ни любой другой authority-резолвер не вызывается нигде в достижимом графе.** Достигает НОЛЬ authority-резолверов → tenant-open by construction (любой аутентифицированный актор тенанта читает деталь любой задачи; для семьи ACTOR-ACTIVE — и держатель остаточного JWT деактивированного).

Строитель **НЕ добавил маркер** — правильно: это был бы ровно evasion-паттерн (маркер к незащищённому роуту), запрещённый self-test T-0662 case 3 и текстом задачи. Живой прогон подтверждает — это ЕДИНСТВЕННАЯ оставшаяся находка. Настоящий security-долг (отдельный follow-up, ШИРЕ деактивации — про отсутствие ролевой адресации DETAIL для ЛЮБОГО актора). Я завожу задачу.

## 4. Часть B корректно НЕ сделана (founder-gated)

Промоушен `getRoleSlugsForActor` из ALLOWLIST в AUTHORITY_RESOLVERS (deactivation-gate) требует **удаления** ALLOWLIST-строки (grants-dao.ts:getRoleSlugsForActor — подтверждён на строке 190) = мутация → `A-1` byte-preservation запрещает. Дубль-альтернатива (в обоих массивах) отвергается `A-4` (сущность уже в base_ents → «delta references existing entities» → R-1-ABSENT-AT-BASE, self-test это ловит — подтверждено прогоном). → founder-класс `FF-FCI12` через реальный `founder_decide`; самозапись `sanctioned_by:"founder"` = forgery. Coder-роль не эскалирует за registry-мейнтенанс (over-escalation тоже дефект). **Строитель прав, что не самовольничал.** Диф в ADR §5 точен. Замечание: часть B — гигиена реестра, НЕ живая дыра (резолвер уже несёт предикат, deactivation-gate зелён через ALLOWLIST).
