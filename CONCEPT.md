# Choros — концепция и архитектура

> Процессная платформа, где люди, ИИ-агенты и микросервисы работают в единой
> оргструктуре под одним control plane и одним аудит-логом.

Версия документа: 0.1 · Дата: 2026-06-06 · Статус: концепт

---

## 1. Идея в одном предложении

**Оркестратор бизнес-процессов для компаний на 150–300 человек, где ИИ-агент —
не чат-бот сбоку, а полноценный «сотрудник» в штатном расписании: с должностью,
ролью, правами, бюджетом и аудитом, работающий в одном процессе рядом с людьми и
микросервисами.**

Не «ещё одна BPM с low-code конструктором» и не «ещё одна автоматизация уровня
n8n». Ниша — на стыке: сильная процессная модель + оргструктура и ролевая модель
+ агенты как исполнители первого класса.

---

## 2. Проблема и наблюдение

Рынок 2026 года расколот на две половины, между которыми пусто:

- **Классические BPM (ELMA365, Comindware, BPMSoft, Directum).** Есть оргструктура,
  роли, объектная модель, исполняемые процессы. Но логика и формы собираются в
  low-code конструкторе, а агенты прикручены сбоку «ИИ-слоем», не встроены в
  процесс как исполнители.
- **Автоматизация и агентские движки (n8n, Zapier, Lindy, Camunda).** Умеют
  агентов и интеграции. Но не знают, что такое *компания*: нет оргструктуры,
  ролевой модели, замещений, человеческих задач как сущности предприятия.

При этом по данным Camunda (State of Agentic Orchestration 2026) 71% компаний уже
используют агентов, но лишь 11% кейсов дошли до прод — все упираются в
governance: права, границы автономии, аудит. Это и есть незанятое место.

**Тезис Choros:** процесс сегодня — это люди + агенты + сервисы вместе. Значит,
агентом нужно управлять теми же средствами, что и сотрудником: через оргструктуру,
роли и права. Это не делает сегодня никто в нише среднего бизнеса.

## 3. Ключевой дифференциатор

### Единая абстракция исполнителя

В BPMN-процессе есть три типа рабочего шага, и все три — равноправные исполнители
в одной модели:

| Тип шага | Исполнитель | Что несёт |
|---|---|---|
| **User Task** | Человек | Форма, инбокс, SLA, эскалация |
| **Agent Task** | ИИ-агент | Цель, набор инструментов (MCP), бюджет, граница автономии |
| **External Task** | Микросервис | Топик, retry-политика, идемпотентность |

### Агент = сотрудник

У агента есть карточка в оргструктуре: должность, роли, права. И из этого следует
всё остальное:

- **Права роли определяют доступные инструменты.** Агент в роли «закупщик» видит
  MCP-инструмент «запросить КП», но не «провести платёж». Least privilege, как у
  человека.
- **Бюджеты:** лимиты по токенам/деньгам/числу действий на инстанс процесса.
- **Граница автономии:** при уверенности ниже порога — эскалация на человека.
- **Полный аудит** каждого вызова инструмента в общем логе процесса.

Это паттерн guardrails, который Camunda продвигает как agentic orchestration, — но
у Choros он **привязан к оргструктуре компании**, чего нет ни у кого в сегменте.

### Позиционирование одной фразой

> «Не RPA и не чат-бот. Агент работает в должности — с правами и под аудитом — в
> одном процессе с людьми.»

## 4. Место на рынке

| Игрок | Что есть | Чего нет относительно Choros |
|---|---|---|
| ELMA365 / BPMSoft / Comindware | Оргструктура, роли, объектная модель | Агенты как исполнители первого класса; формы — через конструктор, не кодом |
| Camunda 8 (Agentic Orchestration) | Люди + агенты + системы в BPMN, MCP/A2A, guardrails | Enterprise-цена, ушли из РФ, нет коробочной оргструктуры под 200 человек |
| n8n / Zapier / Lindy | Дешёвая автоматизация + агенты | Нет понятия «компания»: ни оргструктуры, ни ролевой модели, ни человеческих задач |
| UiPath Maestro / Blue Prism | Agentic orchestration поверх RPA | Тяжёлый enterprise, не для среднего бизнеса |

**Вывод:** ниша «BPMN-движок + оргструктура + люди и агенты как равноправные
исполнители, формы кодом (AI-generated), а не конструктором» — пустая, особенно в
RU mid-market.

## 5. Архитектура

### Принцип: тонкое ядро, логика на границах

```
┌─────────────────────────────────────────────────────────┐
│  ЯДРО (монолитное, единый деплой)                        │
│  • Процессный движок (BPMN / DMN) — Flowable как инфра   │
│  • Оргструктура и ролевая модель                         │
│  • Объектная модель (JSONB + JSON Schema)                │
│  • Инбокс задач, SLA, эскалации, замещения               │
│  • Аудит-лог (люди + агенты + сервисы в одном потоке)    │
└───────────────┬───────────────────────┬──────────────────┘
                │ external worker API    │ (REST, long-poll, pull-модель)
                │                        │
        ┌───────▼────────┐    ┌──────────▼─────────────────┐
        │ Агентский      │    │ Микросервисы клиента        │
        │ рантайм        │    │ (любой язык):               │
        │ (Python):      │    │ • интеграция с 1С / ERP     │
        │ • MCP-tools    │    │ • скоринг, расчёты          │
        │ • A2A          │    │ • генерация документов      │
        │ • guardrails   │    │ • legacy-системы            │
        └────────────────┘    └─────────────────────────────┘
```

### Подключение микросервисов — pull-модель (external task pattern)

Это закрывает требование «сложную логику выводить на границы системы».

Когда процесс доходит до External Task, ядро **не вызывает** сервис напрямую, а
кладёт job в топик. Воркер клиента сам забирает (pull) задачу, лочит её,
исполняет и возвращает результат по REST.

Следствия:

- Воркер пишется на **любом языке** (есть официальные клиенты Flowable: Java,
  Python, JS, .NET).
- **Не нужен message bus** — pull-очередь заменяет его, сохраняя декаплинг.
- Воркеры **масштабируются и перезапускаются независимо**.
- **Падение воркера не валит процесс**: retry + таймаут лока + incident в ядре.
- Сложная/тяжёлая логика по определению живёт на границе — ядро только оркеструет.

Агентский рантайм подключается тем же механизмом: **агент архитектурно — это
просто external worker особого типа.**

## 6. Технологический стек

Контекст выбора: **код пишет ИИ, фаундер направляет и ревьюит.** Значит,
оптимизируем под (а) языки, где ИИ-кодогенерация надёжнее всего, и (б) минимум
языков/стыков, которые человеку придётся отлаживать вслепую.

| Слой | Технология | Обоснование |
|---|---|---|
| Процессный движок | **Flowable** (Apache 2.0) как **инфраструктура** — готовый контейнер, конфигурируется BPMN-файлами и REST | Зрелый BPMN 2.0 + DMN + CMMN, нативный external worker. Запасной вариант — Operaton / CIB seven (форки Camunda 7) |
| Ядро (API, оргмодель, UI) | **TypeScript** (Node) | Один связный репозиторий, который ИИ держит в голове целиком; топ для AI-кодогена; React-фронт всё равно на TS |
| Агентский рантайм | **Python** (Google ADK / LangGraph) | Сильнейшая агентская экосистема; подключается как external worker |
| БД | **PostgreSQL** | Таблицы движка + объектная модель в JSONB. Графовая БД на этом масштабе не нужна |
| Identity | **Keycloak** | Auth, SSO, группы; учётки и людям, и агентам |
| Моделирование процессов | **bpmn-js (bpmn.io)** | Бесплатный embeddable BPMN-редактор, индустриальный стандарт |
| Формы | **AI-codegen:** React-компонент + JSON Schema | Дифференциатор против low-code конструкторов |

### Почему движок — инфраструктура, а не embedded-код

Embedded-режим (движок внутри JVM-процесса) даёт транзакционную целостность
«процесс + данные в одном коммите», но требует писать ядро на JVM (Kotlin/Java) —
языке, где ИИ-кодогенерация слабее, чем в TS/Python. Размен невыгодный: embedded
страхует там, где ИИ и так силён (CRUD), ценой языка, где ИИ ошибается чаще.

Решение: движок — чёрный ящик уровня Postgres/Keycloak (его Java не считается
«языком стека»), а транзакционную целостность возвращаем **outbox-паттерном +
идемпотентными воркерами**. Это хорошо документированные шаблоны.

### Почему монолитное ядро

При нагрузке «десятки процессов, десятки тысяч инстансов» микросервисная
архитектура *ядра* добавляет распределённые транзакции и оверхед без пользы.
Архитектура — не «чистый монолит», а **модульное монолит-ядро + спутники
(агенты, микросервисы) на границе**. Решение обратимо: сервис выносится, когда
появляется реальная граница по нагрузке или команде, не раньше.

## 7. Бизнес-логика ядра

### Оргструктура и роли

- Подразделения → должности → сотрудники.
- Роли как сквозные срезы (например, «согласующий по бюджету», «юрист»).
- Замещения и отсутствия.
- Задача назначается на **роль/должность, а не на человека**: claim из пула,
  авто-переназначение при отпуске, эскалация по SLA.

### Агент как сотрудник

Карточка агента в оргструктуре: должность, роли, права → доступные MCP-инструменты,
бюджеты, правила эскалации, аудит каждого действия.

### Объектная модель

«Приложения» — справочники и реестры (контрагенты, договоры, заявки): JSON Schema
+ JSONB, права на уровне записей через роли. Процессы **ссылаются** на объекты, не
таскают данные в переменных.

### Формы кодом

Пользователь описывает форму текстом → LLM генерирует React-компонент + JSON
Schema → предпросмотр → версионирование вместе с процессом.

Безопасность: код формы исполняется в **sandbox-iframe**, все данные валидируются
на бэкенде по схеме (фронт не доверен). Fallback для тривиальных форм — form-js.

## 8. Стандарты ИИ-агентов

Сложившаяся де-факто триада стандартов, на которую опирается Choros:

- **MCP** — агент ↔ инструменты.
- **A2A (Agent2Agent, Google, апрель 2025, ныне под Linux Foundation, v0.3)** —
  агент ↔ агент. Agent Card (возможности, эндпоинт, аутентификация), OAuth 2.0 /
  mTLS, «непрозрачные» агенты.
- **BPMN** — control plane над всем: где и когда у агента есть автономия.
- **ADK** — каркас для сборки агентов с нативной поддержкой A2A.

Архитектурный паттерн (по Camunda): BPMN задаёт детерминированные границы, агент
получает автономию **внутри ad-hoc подпроцесса**, человек подключается на
hybrid-шагах (агент предлагает — человек подтверждает).

## 9. Сквозной пример: согласование закупки

1. Сотрудник заполняет форму заявки (AI-сгенерированную) → ядро стартует процесс.
2. **Agent Task:** агент-закупщик через MCP проверяет бюджет статьи, ищет
   поставщиков в реестре, запрашивает и сравнивает КП, формирует сводку.
   Уверенность ниже порога → эскалация.
3. **User Task:** руководитель (по оргструктуре — владелец бюджета, с учётом
   замещений) видит сводку агента, утверждает.
4. **External Task:** микросервис клиента в его контуре создаёт заказ в 1С.
5. Агент уведомляет заявителя.

Весь путь — **одна BPMN-диаграмма, один аудит-лог**: видно, что сделал человек,
что агент, что сервис.

## 10. Кейсы применения (компании 150–300 человек)

| Кейс | Человек | Агент | Микросервис |
|---|---|---|---|
| Согласование договоров | Юрист утверждает | Проверка по чек-листу рисков, сверка с типовой формой | Генерация PDF, отправка в ЭДО |
| Onboarding сотрудника | HR, руководитель | План адаптации, ответы новичку | Создание учёток (AD, почта, 1С) |
| Закупки | Владелец бюджета | Сбор и сравнение КП | Интеграция с 1С / ERP |
| Заявки клиентов / ITSM | Специалист — сложные случаи | Классификация, типовые ответы, маршрутизация | Внешние интеграции |
| Кадровые процессы (отпуска, КДП) | Сотрудник, HR | Проверка остатков, подготовка приказов | Выгрузка в 1С:ЗУП |
| Командировки, авансовые отчёты | Руководитель | Проверка чеков (vision), сверка с политикой | Бухгалтерская система |

## 11. Производительность и масштабирование

BPM-нагрузка по природе **ждущая, а не считающая**: задачи висят часами и днями.
Реальный поток операций движка — единицы, в пике десятки в секунду; Flowable
тянет тысячи/сек. Запас в 1–2 порядка. Zeebe (Camunda 8) ради миллионов/сек — не
нужен.

REST-хоп к движку добавляет ~1–5 мс — невидимо на фоне запроса к Postgres
(десятки мс) и человека.

**Узкие места по убыванию:**

1. **Postgres** — рост истории/аудита, тяжёлые запросы списков задач. Настоящий
   боттлнек на дистанции; лечится партиционированием и архивацией. Одинаков для
   embedded и REST.
2. **LLM-задержка агентов** — шаг агента это секунды (2–30 с) инференса. На порядки
   больше всего остального; врождённо для ИИ, от архитектуры не зависит.
3. Всё прочее (UI, формы, сетевой хоп) — шум.

Языки: нагрузка **I/O-bound** (ждём БД, сеть, LLM), а не CPU-bound — async-модель
Node и Python тут в своей стихии, GIL не мешает при ожидании сети.

**Вывод:** один скромный сервер (4–8 vCPU, 16–32 ГБ) + Postgres закрывают весь
целевой сегмент с запасом.

## 12. Поставка: self-hosted + SaaS

- Один артефакт: **docker-compose** (ядро + Postgres + Keycloak + агентский
  рантайм) для self-hosted; **Helm** для будущего pooled-SaaS.
- **Тенантность — отдельное архитектурное решение, см.
  [docs/design/tenancy-and-delivery.md](docs/design/tenancy-and-delivery.md).**
  Короткой версией: модель данных ядра **multi-tenant-aware с первого дня**
  (`tenant_id` сквозь схему), а физический дефолт развёртывания для целевого
  РФ-mid-market — **silo** (один клиент = один изолированный контур; on-prem по
  определению silo). Важно: нативная multi-tenancy Flowable покрывает только
  таблицы движка (`TENANT_ID_`) и **не фильтрует автоматически** — ценностный слой
  ядра (оргструктура, роли, инбокс, аудит, JSONB) изолируется средствами ядра, не
  движка. Всё — над одним артефактом; режим развёртывания = конфигурация.
- Критично для self-hosted в РФ: агентский рантайм работает с **любым
  LLM-эндпоинтом** (OpenAI-compatible API) — облако, прокси или локальная модель в
  контуре клиента. LLM-провайдер — **конфигурация, не зависимость**.

Среды развёртывания (prod/dev) и стратегия веток/интеграции вынесены в отдельные
доки: [docs/environments.md](docs/environments.md) и
[docs/branching.md](docs/branching.md).

## 13. Этапы (роадмап)

**MVP — ядро ценности**
Flowable как инфраструктура · оргструктура + роли + замещения · инбокс задач ·
bpmn-js модельер · формы на form-js · external worker API + документация.

**Этап 2 — агенты**
Агентский рантайм (Python, MCP, guardrails, аудит) · 2–3 готовых агента под кейсы
из таблицы.

**Этап 3 — ИИ-сборка и аналитика**
AI-генерация форм · DMN-правила · дашборды по процессам.

**Этап 4 — масштаб**
A2A для внешних агентов · миграция версий процессов · process mining-lite.

## 14. Риски и решения к принятию

**Риски:**

- **Безопасность AI-форм** — генерируемый код только в sandbox, вся валидация на
  бэке.
- **Граница OSS / Enterprise у Flowable** — external worker есть в open source, но
  лицензию фич проверять до коммита на движок (запас — Operaton / CIB seven).
- **Миграция инстансов** при изменении процесса — заложить в модель данных с
  первого дня, потом дорого.
- **Продуктовый риск** — не пытаться повторить ELMA целиком. Ядро ценности — агенты
  в оргструктуре, остальное минимально достаточное.
- **Зрелость форков Camunda 7** (Operaton, CIB seven) — им около года, проверять
  перед выбором.

**Открытые вопросы:**

- Название и домен (рабочее — Choros; проверить свободу домена и трейдмарк).
- Финальный выбор движка: Flowable vs Operaton/CIB seven.
- TS-only для ядра или TS + Python с первого дня.
