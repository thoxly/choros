## Сверка каждого обещания UI с сервером

Сервер: `registerSelfAbsence` (src/http/rights-intents.ts:1284-1393), тело ответа
1398-1413 — `tier: "tier1"|"tier2"`, `ttl_grant_id`, `valid_until`. Подтверждено
хендлером + серверными тестами s5/s6 (rights-intents.self-absence.authz.test.ts).
Строка `data?.tier === 'tier1'/'tier2'` в UI совпадает с типом сервера. ✓

### (а) tier1 — «если все остальные держатели станут недоступны, замещение вступит в силу автоматически» → БЛОКЕР (обещание без механизма)

Текст обещает АВТО-активацию замещения при опустошении пула. Сервер этого НЕ делает:

1. **Нет механизма авто-эскалации/ре-минта.** Поиск по `src/` — ни крона, ни
   ре-тиринга, ни ленивого минта гранта при исчезновении пула. `executor-resolver.ts`
   шаг 5 (SLA-escalation) прямо помечен «out of scope». tier вычисляется ОДИН раз при
   регистрации; в tier1 `ttl_grant_id = NULL` навсегда (s5 это фиксирует).
2. **Роутинг к замещающему при опустошении пула — да, происходит.** DAO
   (`substitution-dao.ts` SUBST_SELECT) НЕ фильтрует по `ttl_grant_id`, поэтому
   `executor-resolver` (шаг 3) добавляет tier1-замещающего в эффективный пул, когда
   держатель отсутствует.
3. **Но ДЕЙСТВОВАТЬ tier1-замещающий не может, если сам не держит роль.** Claim-гейт
   `inbox.ts:1856-1862` авторизует только (a) `myRoles.includes(taskRole)` ИЛИ
   (b) tier-2 правило. `resolveTier2SubstitutionClaim` (inbox.ts:1355) ЯВНО отсеивает
   tier1: `r.ttlGrantId !== null` с комментарием «Tier-1 substitutes already hold the
   role via role_assignment». Это ДОПУЩЕНИЕ, а не инвариант.
4. **Сервер НЕ проверяет, что замещающий держит роль** (registerSelfAbsence проверяет
   только что АКТОР держит роль, 1267-1282; substitute ≠ actor, 1219). UI-пикер
   замещающего = `dir.employees` (ВСЕ сотрудники, ra-intents.jsx:426), без ограничения
   на держателей роли.

Итог для **достижимого** нормального пути (tier1, замещающий НЕ держит роль → выбор
любого сотрудника пикером): когда пул опустеет, задача роутится замещающему, тот
получает **403 NOT_ELIGIBLE**, и, поскольку `executor-resolver` уже вернул
`kind:"substitution"` (единственный кандидат), задача НЕ падает на владельца —
**застревает** у того, кто не может её взять. «Замещение вступило в силу автоматически»
= ложь; исход хуже прежнего generic-сообщения.

Даже в лучшем случае (замещающий держит роль) он покрывал бы задачи КАК ДЕРЖАТЕЛЬ
всегда — правило-замещение инертно, «активация при опустошении пула» причинно не
существует; сообщение приписывает покрытие механизму, который его не даёт.

Прежнее (до T-0720) сообщение было ЧЕСТНЕЕ: «маршрутизатор перенаправит ваши задачи
замещающему» — только про роутинг (который реально есть), без обещания «вступит в силу».
T-0720 РЕГРЕССИРУЕТ честность tier1, добавив авторитет-обещание. А честность tier-ветки —
и есть заявленная цель задачи. Мандат судьи (a) явно: нет авто-эскалации → blocking.

### (б) tier2 — «он увидит ваши задачи в своём инбоксе» → ЧЕСТНО ✓

tier2 минтит subset-gated TTL-грант (1298-1372). Инбокс (`inbox.ts:636-676`) добавляет
замещающего в эффективный пул роли; claim авторизуется `resolveTier2SubstitutionClaim`
(ttlGrantId !== null, containment по орг-скоупу отсутствующего). Замещающий реально
видит и может взять задачи. «Не шире ваших прав» подтверждено `validateNarrowing`
(422 SUBSTITUTION_WIDENS на расширении). Точно. ✓

### (в) «до <дата>» valid_until → ЧЕСТНО, формат — наблюдение (nit)

`valid_until` в теле ответа = реально `validUntil` (конец окна отсутствия). `formatDate`
(web/src/lib/format.js:77, режим по умолчанию) даёт **«1 авг 2026, 13:00»** — день +
короткое имя месяца + год + ВРЕМЯ. Человеко-читаемо; для конца окна отсутствия показ
времени уместен. Это НЕ дд.мм.гггг (как предполагал хинт задачи) — для чисто-даты есть
`formatShortDate`. Не блокер.

## Findings

- **B1 (blocking, axis 1):** ra-intents.jsx:99-103 (`selfAbsenceResultMessage`, ветка
  tier1). Обещание «замещение вступит в силу автоматически» не подкреплено механизмом:
  для достижимого пути (tier1 + замещающий не держит роль) при опустошении пула задача
  роутится замещающему, но тот 403-ится (claim-гейт inbox.ts:1355 отсеивает tier1) →
  застревание. Авто-эскалации tier1→tier2 в системе нет (поиск по src/).
  Фикс (выбор строителя, не диктую код): либо смягчить текст до фактического — только
  про роутинг, без «вступит в силу» (как в fallback-ветке и как было до T-0720); либо
  обусловить обещание тем, что замещающий держит роль; либо (отдельная серверная задача)
  закрыть разрыв — валидировать, что tier1-замещающий держит роль, или минтить dormant
  standby-грант. Минимум честности: не заявлять авто-вступление в силу там, где сервер
  не авторизует не-держателя-замещающего.

- **N1 (nit, axis 5):** formatDate по умолчанию даёт «1 авг 2026, 13:00» (имя месяца +
  время), не дд.мм.гггг. Приемлемо; при желании чисто-даты — formatShortDate.

- **N2 (nit, axis 1, pre-existing, вне скоупа задачи):** даже ДО опустошения пула
  executor-resolver/inbox добавляют tier1-замещающего в эффективный пул
  (getActiveSubstitutionsByRole не фильтрует ttl_grant_id) — не-держатель-замещающий
  появляется кандидатом в инбоксе, но 403-ится на claim. Серверный квирк, не введён
  T-0720, но усиливает нечестность tier1. Follow-up.

- **N3 (nit, pre-existing):** интро-нота формы (ra-intents.jsx:419-421, не тронута
  задачей) «Задачи … будут автоматически перенаправлены замещающему» — та же
  оптимистичность для tier1-не-держателя (но про «перенаправлены»/роутинг, мягче). Follow-up.
