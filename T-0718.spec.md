# T-0718 — GET /api/inbox/:id: живой шаг из Flowable в projection (не фантомный снимок)

**Эпик:** E16 · **Приоритет:** P1 · **Родитель:** T-0349 · **Из re-proof:** T-0709
**Класс:** та же регрессия «замороженный снимок ↔ живой движок», что T-0709 закрыл в
каталоге/деталке, но в ИНБОКС-проекции — оверлей T-0709 туда не дотянулся.

## Дефект (найден живьём, T-0709 LIVE_PROOF)

`GET /api/inbox/:id` возвращает `{ item, projection }`. `projection` берётся напрямую из
`listInstanceProjections` (аудит-снимок `process.started`, зафиксированный на старте и НЕ
переработанный по мере продвижения токена — тот же снимок, что T-0709 перекрывал в каталоге
и деталке). Поэтому в drawer одновременно видно расхождение:

- «Задача» = `item.step` = 'Завершить проверку' (верно — из живого userTask)
- «Процесс → Текущий шаг» = `projection.step` = 'Согласование' (фантом — узел, на котором
  токена нет; никогда не был текущим для этого инстанса)

Репро на стенде: инстанс `99573238` → `item.step='Завершить проверку'`, но
`projection.step='Согласование'`.

## Корень

`projection` в детальном роуте /api/inbox/:id — это `InstanceProjection` из
`listInstanceProjections`, тот же аудит-снимок. Он НЕ проходит через живой-оверлей
`resolveLiveNodesByInstance` + `overlayLiveSteps` (src/core/process-catalog-view.ts, T-0709),
который каталог (/api/process-catalog) и деталка (/api/processes[/:id]) уже применяют. Инбокс —
третья read-поверхность того же снимка; она осталась замороженной.

## Решение (реюз ядра T-0709, без дублирования)

Применить ТОТ ЖЕ core-оверлей к единственной проекции детального роута ПЕРЕД сериализацией:

1. Резолвим живой активный узел движка для этого инстанса через
   `resolveLiveNodesByInstance(flowable, [inst], { deadlineMs })` — ТА ЖЕ функция, что
   в processes.ts (единый источник истины). Движок — только через инъецированный
   `writeDeps.flowableClient` (никакого bare fetch / нового транспорта).
2. Накладываем через `overlayLiveSteps([projection], liveByInst)` — берём `[0]`.
   `overlayLiveSteps<P extends ProjectionLike>` дженерик и сохраняет доп-поля
   `InstanceProjection` (в т.ч. `concurrentSteps`), перекрывая `step`/`role`/`concurrentSteps`
   на живые, если движок вернул активный userTask.
3. Реюз бюджета `LIVE_OVERLAY_DEADLINE_MS` (2000 ms), как в processes.ts.

Никаких кейс-литералов в src/ (D-064 анти-кейс): живые label/role — ДАННЫЕ из движка,
не хардкод. inbox.ts уже pg-carrying (импортирует pg, использует `writeDeps.pool`) — FF-7-3
display-plane isolation его НЕ покрывает (гейт скоупит только processes.ts / process-start.ts).

## Acceptance

- **AC-1.** `GET /api/inbox/:id` для waiting instance-backed задачи: `projection.step` =
  реальному имени активного узла Flowable (`getActiveUserTasks[primary].name`), НЕ замороженному
  снимку `process.started`. `projection.concurrentSteps` = живому набору веток.
- **AC-2.** `projection.step` больше НЕ расходится с `item.step` для одной и той же waiting
  задачи, когда движок доступен и активный узел = задача пользователя (репро дефекта закрыто).
- **AC-3.** Согласованность inbox ↔ catalog ↔ detail: все три read-поверхности берут текущий
  шаг из ОДНОГО живого источника (`resolveLiveNodesByInstance`), не могут разъехаться.
- **AC-4.** Инстанс на ПЕРВОМ шаге: инбокс-projection показывает первый шаг (не следующий/
  фантомный) — то же поведение, что каталог/деталка после T-0709.
- **AC-5.** Честный degrade: движок недоступен / нет активного userTask / клиент без метода
  `getActiveUserTasks` / дедлайн истёк / done-проекция ⇒ `projection` возвращается байт-в-байт
  на аудит-снимке (не хуже, чем до T-0718; никогда не 500). 200 сохраняется.
- **AC-6.** Дедлайн-бюджет: оверлей ограничен `LIVE_OVERLAY_DEADLINE_MS`; один инстанс — один
  вызов движка, best-effort.
- **AC-7.** Tenant-скоуп/PDP не тронуты: инстанс резолвится в тенанте актора, как и раньше;
  оверлей — display-only, аудит-трек не переписывается (`status`/`startedAt`/`inboxTaskId`
  неизменны).

## Тесты

- инстанс на первом шаге → инбокс-projection.step = первый шаг (живой), не следующий;
- согласованность: один и тот же live-резолв даёт inbox.step == detail.node == catalog.step;
- degrade: клиент без `getActiveUserTasks` / движок-миссы / done-проекция → projection неизменна;
- item.step и projection.step совпадают на живом активном узле (репро дефекта закрыто).

Фикстуры реюзаются; кейс-литералы (`telLinear`/`Согласование`) в src/ запрещены (anti-case).
