## Диагноз (из ux-study)

- **§6.3 несогласованность трёх островов**: `/users ↔ /org ↔ /rights ↔ /agents` — ни одного перехода в коде. Модель едина (`employee` = human|agent; учётка = логин-обвязка через KC; права = назначения на её `employee_id`), но UI — острова. «Права и доступ» из карточки исполнителя ведёт на `/rights` БЕЗ контекста (`onOpenRights(undefined)`, screen-org.jsx:537).
- **§6.4 / §1C move-API НЕТ**: seed-write.ts — только create+delete, «no edit/PATCH route» задокументирован (screen-org.jsx:40-45). Реорганизация = удалить+создать (рвёт историю+id). DnD вешать не на что.
- **/agents**: стена одинаковых деградаций («должность не назначена» + «НУЖНА LLM» ×N); нет действия «назначить должность»/«привязать LLM» на месте; нет перехода к правам.

## Слои (реализация инкрементально, коммит на каждый)

### Слой 1 — Move-API оргструктуры (бек, аддитивно; фундамент для DnD)

Новые эндпойнты в `src/http/seed-write.ts` (существующий org-write surface: `withAuth` + `authorizeOrgWrite` (cross-tenant guard) + `assertOrgObjectAuthority` (owner-OR-delegable-grant) + `withTenantTx` (RLS GUC) + canonical `appendAuditEvent`):

- **PATCH /api/departments/:id** — body `{ tenant_id, parent_id?, display_name? }`. Меняет родителя (реорг) и/или имя. Валидация циклов: отдел не может стать потомком самого себя ни транзитивно (реюз `loadTenantOrgAncestry` → проверить, что новый parent НЕ в поддереве перемещаемого отдела, и parent != self). Гейт `mgmt_object:department` / `update`.
- **PATCH /api/positions/:id** — body `{ tenant_id, department_id?, title? }`. Переносит должность в другой отдел и/или переименовывает. Гейт `mgmt_object:position` / `update`.
- **PATCH /api/employees/:id** — body `{ tenant_id, position_id?, display_name? }`. Переносит сотрудника на другую должность (null = снять с должности) и/или переименовывает. Гейт `mgmt_object:employee` / `update`.

Общие свойства:
- **AC-M1** каждый PATCH обновляет `updated_at` серверным временем.
- **AC-M2** аудит-событие `{department|position|employee}.moved` через canonical `appendAuditEvent` в ТОЙ ЖЕ транзакции (actor, subject=id, payload={from_parent/from_dept/from_position, to_…, renamed}). Что реально изменилось.
- **AC-M3** авторизация ОБЯЗАТЕЛЬНА: cross-tenant → 403 NOT_OWNER (тот же `authorizeOrgWrite`); не-owner без delegable grant → 403 (тот же `assertOrgObjectAuthority`). Owner-путь short-circuit. (Если T-0662 замержит `ACTOR_ACTIVE_SQL` — резолв актора уже идёт через `loadAdminContext`, который несёт T-0658 `deactivated_at IS NULL` fail-closed; отдельного резолвера актора move-API не заводит, паразитирует на существующем.)
- **AC-M4** цикл-детект для department: `parent_id == self` → 400 CYCLE; `parent_id` в поддереве self → 400 CYCLE. Проверка ДО UPDATE.
- **AC-M5** пустой patch (ни одного поля) → 400 VALIDATION.
- **AC-M6** несуществующий id в тенанте → 404 (rowCount 0).
- **AC-M7** FK-нарушение (напр. position_id/department_id/parent_id не в тенанте) → 409 FK_IN_USE или честный 400 (assertUuidShape + FK через 23503).
- **AC-M8** миграции НЕ требуется (все три таблицы уже имеют nullable parent/dept/position + updated_at; проверено на схеме).

Тесты: `src/__tests__/org-move-api.test.ts` — цикл-детект (unit на pure-функции), payload-builders, авторизация (403 cross-tenant), успешный move меняет parent/dept/position, пустой patch 400. Pure cycle-guard вынести в `src/core/org-move.ts` (unit-тестируемо, без DB) — mirrors sidebar-dnd.js split.

### Слой 2 — Identity hub исполнителя (фронт)

Единая карточка исполнителя, вызываемая из /org (карточка справа = уже хаб), с гранями и переходами:
- **AC-H1** карточка `ExecutorDetail` (screen-org.jsx) расширена гранями: оргместо (отдел/должность — уже есть), учётка (логин/статус из /users), роли и права (сводка назначений), для агента — LLM/инструкция/активность (переиспользовать блоки screen-agents.jsx honest-absent если API нет).
- **AC-H2** «Права и доступ» ведёт на `/rights` **С КОНТЕКСТОМ** исполнителя. `onOpenRights` в shell.jsx уже кладёт focus и navigate('/rights'); расширить: `openRights({ subject })` или отдельный `openRightsForSubject(employeeId, label)` → RightsScreen получает `initialSubject`. Кнопка передаёт `person` (employee slug/id + имя), НЕ `undefined`.
- **AC-H3** переходы-мосты между островами: с карточки — ссылки/кнопки «Учётка» (→/users с фокусом), «Оргместо» (уже /org), «Права» (→/rights subject), для агента «Открыть в /agents». Реализуемо навигацией; без мёртвых кнопок — только реально существующие маршруты.
- **AC-H4** сырой UUID в карточке (`<MonoId>{person.id}</MonoId>`) не как основной идентификатор — имя primary, id вторично (mirrors ActorChip; для human со slug=KC-sub id уже спрятан за именем). Использую ActorChip/MonoId как вторичное.
- **AC-H5** RightsScreen принимает `initialSubject` (employeeId) и фильтрует/скроллит к назначениям этого исполнителя (аддитивно к `initialRole`; если фильтра по субъекту нет — минимум подсветка/скролл + баннер «Права: <имя>»).

### Слой 3 — DnD оргдерева поверх move-API (фронт)

Паттерн T-0651: ▲/▼ + HTML5 DnD, с кнопочным fallback «Переместить в…» (доступность обязательна).
- **AC-D1** pure-логика в `web/src/screens/org-move-dnd.js` (mirrors sidebar-dnd.js): `computeEmployeeMove(person, targetPositionId)` → PATCH-payload; generic (никаких имён — anti-case).
- **AC-D2** перетащить сотрудника (leaf) на должность/отдел → PATCH /api/employees/:id { position_id }. drop на отдел → на «без должности» в отделе (или первую должность? — на «снять должность» безопаснее: position_id пустой недопустим для отдела; drop разрешаем только на должность-строку).
- **AC-D3** fallback-меню «Переместить в…» на строке узла (доступно с клавиатуры): открывает модалку выбора целевой должности (Select из tenant-state) → тот же PATCH. **ОБЯЗАТЕЛЬНО** (если DnD не влезает — DnD режется в followup, меню остаётся).
- **AC-D4** только `canWrite` (owner) видит DnD/меню; read-only не показывает.
- **AC-D5** после move — reload дерева (server-truth, как sidebar patchApplications).
- **AC-D6** переименование отдела/должности/сотрудника через тот же PATCH — кнопка «Переименовать» в меню узла (модалка с одним полем). (Move + rename — оба на move-API.)

### Слой 4 — Сворачивание /agents (фронт)

- **AC-A1** повторяющиеся деградации («должность не назначена» + «нет LLM») свернуть в ОДИН статус-бейдж на карточке: `⚠ вне оргструктуры · нет LLM` (StatusChip/Badge), убрать дублирующийся hint-текст ×N.
- **AC-A2** действия НА МЕСТЕ на бейдже: «Назначить должность» (открывает модалку выбора должности → PATCH /api/employees/:id { position_id } — тот же move-API! для org-attached агента) и «Привязать LLM» (уже есть кнопка — интегрировать в бейдж-группу).
- **AC-A3** ссылка «Права агента» с карточки → identity hub (или /rights subject) — переход к правам агента (сейчас нет).
- **AC-A4** honest: «Назначить должность» доступно только если есть UUID должностей (tenant-state загружен = owner). Для org-less (system) агента без employee_id move-API неприменим — честно скрыть «Назначить должность» (у него `has_org_place=false` и это архитектурно норм — показать «системный агент», без деградации-CTA).
