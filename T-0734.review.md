## 1. Фикс работает живьём (главное) — воспроизведён самостоятельно

Импортировал ТОЧНЫЙ коммиченный `config/keycloak/realm-choros.json` (переименован в throwaway-realm)
через `POST /admin/realms` — тот же десериализатор, что `--import-realm`/CI kc-job:

```
IMPORT committed realm -> HTTP 201
profile after import: declared=[username,email,firstName,lastName,actor_type]
                      actor_type edit=[admin], options=[human,agent]
registrar client_credentials (путь createHumanUser) -> token OK
POST /users {actor_type:[human]} -> HTTP 201
GET user back: attributes = {"actor_type": ["human"]}          <- ПЕРСИСТИТ
ROPC choros-api token: actor_type='human' | aud=['choros-api','account'] | iss=.../realms/<tr>
```

`verifyClaims` (`src/http/auth.ts:302`, AC-12): требует `actor_type ∈ {human,agent}` + iss/aud/exp/sub/preferred_username —
воспроизведённый токен удовлетворяет всем → **нет 401**. Корень (KC 25 declarative-profile молча дропает
unmanaged `actor_type`) подтверждён отдельно на «pre-fix» realm (components удалён): create no-names → `attributes={}` (дроп).
`createHumanUser` (`src/keycloak/admin-port.ts:380-407`) шлёт ровно тот payload, что я воспроизвёл (registrar POST /users,
`attributes.actor_type=["human"]`).

## 2. Анти-эскалация — ЗАБЛОКИРОВАНА (security-критично, доказано)

Живой юзер с валидным токеном (`actor_type='human'`) пытается сам себе поставить `agent` через Account REST:

```
POST /realms/<tr>/account {attributes:{actor_type:[agent]}} (bearer = токен самого юзера)
  -> HTTP 400 {"field":"actor_type","errorMessage":"error-user-attribute-read-only"}
stored actor_type после попытки = ["human"]     (не изменилось)
token actor_type после попытки  = 'human'       (не изменилось)
```

`permissions.edit=["admin"]` реально энфорсится KC — человек НЕ может стать агентом. Self-view (`view:[admin,user]`)
позволяет видеть свой тип — это безвредно. options-валидатор `[human,agent]` отвергает произвольное значение
на create (`superadmin -> 400 error-invalid-value`).

## 3. Seeded-регрессия — целы

На РЕАЛЬНОМ running realm `choros`: `e-kravtsova`, `e-orlov`, `e-larina` → токен `actor_type='human'`.
Через коммиченный-файл-import: seeded `e-kravtsova` тоже `'human'`. `setUserEnabled` PUT `{enabled:false}` → `204`,
`attributes={actor_type:[human]}` сохранён (профиль `not required`+`multivalued:false` не отвергает уже-записанное).

## Non-blocking findings

- **N1 (nit, ось 1 — верность доказательства).** `ci/checks/kc/ui-created-user-actor-type.sh:49` и live-proof
  ДОБАВЛЯЮТ `firstName`/`lastName` («so ROPC succeeds»), а РЕАЛЬНЫЙ `createHumanUser` (`admin-port.ts:392-407`) их НЕ шлёт.
  Проверил живьём: юзер БЕЗ имён (как реально) → `attributes` персистят + claim ставится (фикс работает), НО ROPC даёт
  `invalid_grant: Account is not fully set up`, а браузерный вход упрётся в интерактивный `VERIFY_PROFILE`
  («Update Account Information»). **Это ПРЕД-существующее** (KC-25 default-профиль тоже объявляет `firstName/lastName`
  `required:{roles:[user]}` — подтвердил на pre-fix realm: то же поведение), фикс его НЕ вносит и НЕ обязан чинить в своём
  скоупе (actor_type 401). Строитель честно вынес это в `followups_out_of_scope`. Следствие: авто-live-чек доказывает
  персистентность actor_type в ИЗОЛЯЦИИ, но НЕ доказывает сквозной продуктовый вход реального UI-аккаунта.
  Рекомендация follow-up (приоритезировать): форма «Создать учётку» собирает имя ИЛИ `createHumanUser` шлёт `firstName/lastName`,
  чтобы UI-аккаунт был login-complete без интерстишела.

- **N2 (nit, ось 3 — робастность recovery).** `scripts/kc-dev-setup.sh` шаг 5: при не-2xx от `PUT /users/profile`
  печатает только `[WARN]` и продолжает (exit 0). На persistent-стенде тихо-провалившийся реконсиль оставит `actor_type`
  unmanaged. Допустимо (DEV-only скрипт; CI/fresh идут через import, не через этот скрипт), но громкий fail на не-2xx был бы честнее.
