# T-0700 — судейский вердикт (REVIEW+TEST, backend)

**Вердикт: approved**

Задача: протянуть `targetRegistrySlug` в схему инструмента `TOOL_AUTHOR_BINDING`
конфигуратора-агента, чтобы бот мог направить результат шага в нестандартный
реестр — то, что человек уже мог через UI-форму «Реестр результата» (T-0681).
Инвариант «бот==человек», столп 5.

Все три блокирующих критерия чисты: параметр НЕ теряется по пути; бот НЕ шире
человека по правам; live-тест НЕ мокает суть исполнителя.

## 1. Схема (п.1) — OK

`src/core/assistant-configurator.ts:194-204`. `targetRegistrySlug` реально в
`TOOL_AUTHOR_BINDING.parameters.properties`, тип `string`, **НЕ** в `required`
(`required: ["processKey","applicationId","triggerType","humanReadableReason"]`,
строка 207). Описание русскоязычное, **общими словами** — «реестра внутри
приложения этой привязки», «реестра приложения по умолчанию», «конкретный реестр
этого приложения». Ни одного имени конкретного реестра/приложения (анти-кейс).
`anti-case-lock.sh` — PASS (aggregate 15, baseline 16, без роста) — прогнал сам.

Тип `string` без формата — валидация СУЩЕСТВОВАНИЯ на сервере, fail-closed:
`src/http/assistant.ts:784-793` — `SELECT 1 FROM registry_def WHERE tenant_id=$1
AND application_id=$2 AND slug=$3`; пусто → ROLLBACK + честная ошибка «реестр
«…» не найден в приложении этого пространства», строка НЕ пишется. Формат слага
как такового не проверяется, но это неважно: несуществующий/кривой слаг
отсекается existence-гейтом до записи.

## 3. ГЛАВНАЯ ДЫРА ПАРИТЕТА — право-гейт на реестр (п.3) — НЕТ ИНВЕРСИИ ✅

Проверил ОБА пути:

- **Человек**: `POST /api/process-app-bindings` (`process-catalog.ts:406`) —
  `withAuth` + `extractActor` (любой аутентифицированный актор тенанта), затем
  `registryExistsUnderApp(tenantId, applicationId, slug)` (строки 505-518),
  fail-closed 400 `REGISTRY_NOT_FOUND`. **Никакого per-registry PDP** и никакого
  authoring-capability гейта на уровне маршрута.
- **Бот**: `executeApprovedOpAsDraft` кейс `author_binding` — ТА ЖЕ
  existence-валидация (tenant + application + slug), fail-closed. И этот путь
  достижим ТОЛЬКО после `hasAuthoringDraftGrant` (owner ИЛИ authoring_draft/
  system_agent:operate в пересечении **агент∩пользователь**, никогда не шире
  пользователя).

Registry-reach envelope **идентичен** (tenant+application+slug existence,
RLS-scoped через `SET LOCAL choros.tenant_id`). Per-registry «право на реестр» в
Choros для привязки НЕ существует ни в одном из путей — авторитет живёт на уровне
tenant+authoring. Поэтому бот НЕ может дотянуться до реестра, до которого не мог
бы человек. Наоборот: бот СТРОЖЕ (доп. гейт authoring_draft + пересечение), т.е.
бот ≤ человек. **Инверсии инварианта нет.** Это самый важный итог review.

## Non-blocking (списком)

- **N1 (axis 2, discovery-паритет)** — человеческая форма показывает ПИКЕР
  реестров (список валидных слагов); у бота в тулсете нет affordance «перечисли
  реестры приложения», модель обязана уже ЗНАТЬ точный слаг. Инвариант «бот может
  ДОТЯНУТЬСЯ» выполнен (параметр объявлен, fail-closed на плохом слаге), но полный
  experiential-паритет (бот знает, КАКИЕ реестры есть) — отдельная capability
  (introspection-tool), follow-up. При невозможности смапить имя→слаг модель
  честно падает в отказ, а не создаёт вслепую — безопасно.
- **N2 (axis 3, тест-полнота)** — полный путь LLM→processToolCall→ApprovedOp→
  executor не покрыт одним автотестом (LLM-звено отложено, стенд offline). Шов
  покрыт двумя половинами (юнит: verbatim pass-through стаб-tool-call; live-PG:
  исполнитель), сходящимися на форме ApprovedOp.args, которую live-тест реплицирует
  точно. Приемлемо для offline-гейта; задача — PARTIAL до live-proof.
- **N3 (axis 4, nit)** — AC-T700-3 негативный assert `not.toMatch(/реестр
  результата/)` проходит лишь потому, что `humanReadableReason` теста в
  родительном падеже («реестрА результата») не содержит номинативной подстроки.
  Слегка хрупко; косметика.
