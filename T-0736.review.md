## 1. sod-check subjectID (самое опасное) — ТЕЧЬ НЕ ОБНАРУЖЕНА, доказано живьём

Гейт (`rights-sod.ts:418-427`): при `subjectId !== actorId` → `resolveActorPrivilege(...).isOwnerOrAdmin`, иначе 403 **ДО** `checkSodForSubject`. Прогнал живой PG (:55432) + СВОЙ адверсариальный пробник (не только тесты строителя):

| Пробник | Результат |
|---|---|
| unprivileged override на СУЩЕСТВУЮЩИЙ slug | `403` |
| unprivileged override на НЕсуществующий slug | `403` — **байт-в-байт идентично** существующему |
| self-view (implicit и explicit `?subjectId=<self>`) | `200` |
| owner override на чужого | `200` с реальными conflicts цели |
| DEACTIVATED owner override | `403` |
| пустой `?subjectId=` (`"" !== actor`) | `403` fail-closed |

**No-leak доказан:** тело 403 = `{"error":{"code":"FORBIDDEN","message":"viewing another subject's SoD conflicts requires admin/owner authority"}}` — статичное, БЕЗ `subjectId` / `conflicts` / `heldRoles`. Существующая и несуществующая цель дают идентичный ответ → **exists/absent-оракула нет**. Тайминг верен: privilege-check раньше резолва цели. (Уточнение по формулировке — см. nit R-1: тело НЕ буквально «пустое», это стандартный envelope; но security-свойство «нет утечки/оракула» выполнено полностью.)

## 2. change-requests «любой активный человек» — политика ВЕРНА, не утечка

LIST-гейт (`rights-change-requests.ts:598`) = `assertApproverIsHuman` — **тот же самый** резолвер, что несут write-роуты approve (`:620`) и reject (`:643`) на этом же файле. Значит read-eligibility == write-eligibility: любой, кто может действовать по заявке, может её и видеть. Согласуется с T-0044 §9 (второй approver = любой distinct активный человек, НЕ сужено до admin). Деактивированный отсекается (`ACTOR_ACTIVE_SQL` = `deactivated_at IS NULL` внутри WHERE → 0 строк → 403), агент → 403 `AGENT_NOT_ALLOWED`. Живьём подтверждено (AC-1/2/3). Экспозиция широкая (весь pending-queue тенанта виден любому активному человеку) — но это инвариант approver-pool модели и ровно уровень write-пути; эскалации нет. См. nit R-2 (не-blocking).

## 3. grant-trail admin/owner-only — деактивированный отсекается

`resolveActorPrivilege(...).isOwnerOrAdmin` композирует `loadAdminContext` (`org.ts:799`), где `ACTOR_ACTIVE_SQL` стоит **в обоих** субзапросах — owner-check (step 1) и assignment-check (step 2). Деактивированный actor → пустой employee-id subquery → `isGenesisOwner=false`, `adminGrants=[]` → `isOwnerOrAdmin=false` → 403. Живьём: owner→200 (AC-1), ordinary→403 (AC-2), **DEACTIVATED owner→403 (AC-3)**. `hasAuthoringDraftGrant` корректно ПРОИГНОРИРОВАН — код консультирует только `isOwnerOrAdmin` (authoring_draft = content-authoring ≠ mgmt_object, к rights-trail-read отношения не имеет). ✓

## 4. Collateral `r.name → r.display_name` — ЧЕСТНЫЙ фикс

Миграция 019 (`migrations/019_role.sql:27`) И живой PG (`information_schema.columns`) подтверждают: `choros.role` имеет `display_name`, колонки `name` НЕТ. `r.name` бросал бы `column does not exist` → 500 на любой pending-строке с ролью. Поведение сверх фикса 500 не меняется: `display_name` — ровно человекочитаемое имя роли, которое `role_name` и должен нести. **Тот же класс, что T-0698:** stub-pool (`rights-change-requests.test.ts`, 13 тестов) мокает результат query и никогда не бьёт реальную колонку — оттого прятал баг. Новые live-PG тесты его ловят. Sibling stub-сьют цел (13/13).
