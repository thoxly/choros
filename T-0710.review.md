## Итог по трём блокирующим вопросам

### 1. Параллельный шлюз НЕ схлопывается (ключевой вопрос)
Правило фикса `baseSuperseded = instancesWithAnyNextTask.has(inst)` — точный порт T-0608 из сиблинга `listInstanceInboxTasks` (сверил построчно: 1237–1244 vs 1047–1073, та же семантика «любой next_task ⇒ база вытеснена»).

Разобрал модель конкурентности: **честный AND-split ВСЕГДА представлен ОТДЕЛЬНЫМИ `process.next_task`-рядами**, по одному на каждый живой engine-task. Фан-аут `reconcileInstanceEngineDrive` (1958–2016) эмитит next_task на КАЖДЫЙ активный engine-task, дедуп по defKey; у базового ряда `taskDefKey=null`, поэтому база НИКОГДА не подавляет эмиссию конкурентной ветки. `concurrentSteps` собирается из pending next_task-рядов (`concurrentNextStepsByInst`) — все ветки сохраняются. База (`process.started`) — всегда ОДИН посеянный task, исключается только когда реально вытеснена.

Корнер «next_task на другой ветке выкинет легитимно-параллельную базу» **недостижим**: чтобы у движка было ≥2 конкурентных task, шаг ДО шлюза (база) должен был завершиться; а если база сама — живой конкурентный токен, фан-аут эмитит next_task и ДЛЯ НЕЁ (её defKey=null → не в alreadyProjectedDefKeys → эмитится), её ветка выживает как next_task.

**Собственный db-пробник (прошёл):** база + 2 pending next_task одного инстанса → `concurrentSteps=['step-B','step-C']`, база исключена. Схлопывания нет. Singular step/role следуют concurrentSteps[0] безопасно: для non-done concurrentSteps никогда не пуст (defensive push 1132), для done — step="Завершено". null/undefined наружу не течёт.

### 4. Пагинация — фикс 3 РЕШАЕТ исходную жалобу
Партиция `stableSortEscalatedLast(filtered)` применяется к ПОЛНОМУ tab-набору (строка 1588) **ДО** `paginateInMemory(filtered, page, limit)` (строка 1631). Значит старая approver-задача, ранее похороненная за страницей под defer-эскалациями, поднимается в начало и попадает на стр.1. Стабильность доказана unit-тестом (comparator `Number(isEscalated(a))-Number(isEscalated(b))`, sort стабилен с ES2019, no-mutation). db-тест подтверждает `plainIdx < escIdx` в ответе; `sort=sla` не тронут (эскалация первой при явной срочности).

**Остаток (nit F1):** переупорядочивание идёт ВНУТРИ окна DB-LIMIT, которое тянет findInboxItems (defer 100 DESC / instance 200 ASC). Если у тенанта >200 ждущих instance-задач, НОВЕЙШИЕ выпадают из ASC-200-окна и не видны ни на одной странице unscoped-списка — доперисущая усечёнка, ортогональна T-0710, смягчается фиксом 2 (scope по инстансу). Не блокер.
