**Date:** 2026-07-05
**База:** worktree `task/T-0663-email-format-record`, от `dev@d591610`

## 1. Проблема

Создание записи в реестре, где поле объявлено JSON-Schema `format:"email"`,
падает в UI с ошибкой `unknown format "email" ignored in schema` — **даже когда
email-поле оставлено ПУСТЫМ**. Запись не сохраняется через форму ни при каких
значениях. Вскрыто на LIVE_PROOF в системном реестре «Контрагенты»
(`kontragenty`, `migrations/083_core_system_registries_seed.sql`), поле
`contact_email`.

### 1.1. Корень (разведано, не гипотеза)

`src/core/record-schema-validator.ts` — единственный модуль, где создаётся AJV
для валидации записей. Две функции, каждая со своим `new Ajv()` без опций:

- `validateRecordAgainstSchema` (вызывается `src/http/records.ts::assertDataValid`,
  ДВА живых call-site — POST и PUT `/api/records`).
- `validateRecordSchemaDefinition` (вызывается `src/http/registry-defs.ts`,
  гейт при создании/правке `registry_def.record_schema`).

AJV v8 по умолчанию работает в `strict: true`. Строгий режим **бросает
исключение при `ajv.compile()`**, если схема содержит `format`, для которого не
зарегистрирован валидатор — это происходит **на этапе компиляции схемы**, ДО
того, как `validate(data)` вообще посмотрит на значение поля:

```
$ node -e "new (require('ajv').Ajv)().compile({type:'object',properties:{email:{type:'string',format:'email'}}})"
unknown format "email" ignored in schema at path "#/properties/email"
```

Это объясняет наблюдение «падает даже с пустым полем»: ошибка не зависит от
данных записи вообще — `assertDataValid` (records.ts:610-628) ловит исключение
`ajv.compile()` и заворачивает его в `400 VALIDATION` для ЛЮБОГО payload
(включая `{}` или email-ключ, отсутствующий в data), пока схема реестра несёт
`format:"email"`.

### 1.2. Почему бага не поймали раньше (T-0516 частично залатал, но не всё)

`web/src/screens/apps-schema.js` (T-0516) уже знает про это ограничение — **для
схем, которые СОЗДАЁТ конструктор реестров через UI**, email/url/date поля
эмитятся НЕ как `format:"email"`/`format:"uri"`/`format:"date"`, а как
`x-email`/`x-url`/`x-date` (x-*-расширения, которые `stripXExtensions` снимает
перед компиляцией). Комментарий в коде прямо называет причину: *«AJV strict
rejects format:"email" (unknown format) — use x-email as the round-trip
discriminator»*.

НО это workaround только для НОВЫХ схем, созданных через конструктор
реестров ПОСЛЕ T-0516. Два системных SEED-реестра, заведённых миграциями ДО
этого решения, всё ещё несут «сырой» `format`:

- `migrations/073_vendor_crm_seed.sql` — `customer-subscription`:
  `contact_email` (`format:"email"`, REQUIRED), `not_after`
  (`format:"date"`), `activation_key_issued_at` (`format:"date-time"`).
- `migrations/083_core_system_registries_seed.sql` — `kontragenty`
  («Контрагенты», is_system=true): `contact_email` (`format:"email"`,
  optional), `prod-kalendar` («Производственный календарь»): `date`
  (`format:"date"`, REQUIRED).

Любая запись в эти системные реестры (используемые ВСЕМИ процессами,
ссылающимися на контрагента) 400-ит безусловно. `kontragenty` — core-справочник
(is_system=true, "используется всеми процессами и реестрами, которые
ссылаются на юридическое лицо") — это блокирует не только "Контрагенты"
напрямую, но потенциально любой кейс, ссылающийся на юрлицо.

### 1.3. Второй, более тонкий баг: пустая строка против `format`

JSON Schema `format` — это ограничение НА ЗНАЧЕНИЕ, которое присутствует;
вопрос "может ли поле отсутствовать" решает отдельно `required`. Но библиотеки
формат-валидации (включая `ajv-formats`) применяют регэксп формата К ЛЮБОЙ
строке, включая `""` — RFC 5321 email-грамматика не матчит пустую строку.
Значит даже ПОСЛЕ регистрации `email`-формата: клиент, который явно шлёт
`contact_email: ""` (а не опускает ключ), всё ещё получил бы 400 на
НЕОБЯЗАТЕЛЬНОМ поле. Фронт (`web/src/screens/records-form.js
serializeRecordData`) уже ОПУСКАЕТ пустые необязательные строковые поля из
payload — но сервер (источник истины валидации) не должен полагаться на это
поведение клиента.

## 2. Решение (одной фразой)

Зарегистрировать стандартный словарь JSON-Schema `format` (`ajv-formats`) на
ОБОИХ AJV-инстансах `record-schema-validator.ts` через общую фабрику
`makeAjv()`, и обернуть каждый СТРОКОВЫЙ format-валидатор так, чтобы `""`
всегда проходил FORMAT-проверку (пропуская обязательность полю — единственный
судья присутствия — `required`, который не трогаем).

## 3. Критерии приёмки (машинно-проверяемые)

- **AC-1** — `validateRecordAgainstSchema` для схемы с `properties.<key> =
  {type:"string", format:"email"}` НЕ бросает `unknown format` при компиляции
  (ни для валидного, ни для пустого, ни для отсутствующего значения).
- **AC-2** — запись с ВАЛИДНЫМ email в email-поле (обязательном или
  необязательном) сохраняется (`valid:true` / HTTP 201).
- **AC-3** — запись с ПУСТЫМ НЕОБЯЗАТЕЛЬНЫМ email-полем (ключ отсутствует В
  data ИЛИ явно `""`) сохраняется (`valid:true` / HTTP 201) — это был
  репортнутый баг.
- **AC-4** — запись с НЕВАЛИДНЫМ (непустым, ломаным) email в ОБЯЗАТЕЛЬНОМ
  email-поле честно отклоняется (`valid:false` / HTTP 400) — валидация не
  ослаблена в обратную сторону; `required`+отсутствующий email тоже отклоняется
  (пустая строка — НЕ бэкдор вокруг `required`).
- **AC-5** — тот же паттерн (`format:"date"`, `format:"date-time"`, из
  migrations 073/083) компилируется и валидирует корректно (валидное значение
  проходит, пустое-необязательное проходит, битое — честно отклоняется).
- **AC-6** — `validateRecordSchemaDefinition` (T-0263 authoring guard) тоже
  принимает `format:"email"` как валидное определение схемы (тот же
  `makeAjv()`, одна и та же семантика на обоих путях).
- **AC-7** — единственный ajv-инстанс продакшн-кода — `record-schema-validator.ts`
  (`src/http/records.ts` и `src/http/registry-defs.ts` вызывают ЕГО функции, не
  создают свой AJV). Фронтовые `web/src/screens/*.test.js` используют `new
  Ajv()` ТОЛЬКО как test-mirror (зеркалируют бэкенд-поведение в юнит-тесте,
  не второй продакшн-валидатор) — не трогаются, но ремарка зафиксирована в
  ADR.
- **AC-8** — `npx tsc --noEmit`, `npx eslint src`, `npx vitest run` зелёные;
  числа тестов не уменьшились.
- **AC-9** — `npm run fitness:db` зелёный на живом PG (:55432), включая НОВЫЙ
  DB-тест (`ci/checks/db/records_crud.test.ts` — блок T-0663), доказывающий
  AC-2/AC-3/AC-4 через РЕАЛЬНЫЙ HTTP-путь `POST /api/records` на реальной
  Postgres (не только юнит на голом AJV).
- **AC-10** — `bash ci/checks/anti-case-lock.sh` зелёный — фикс не вводит
  кейс-литералов в `src/`.
- **AC-11** — красные-до-фикса тесты подтверждены мутационно: и юнит
  (`src/__tests__/record-schema-validator.test.ts`, блок T-0663), и DB-тест
  красные при откате `src/core/record-schema-validator.ts` к до-фиксовому
  состоянию (проверено вручную `git stash`).

## 4. Границы

- Миграции 073/083 (seed-схемы с `format:"email"/"date"/"date-time"`) — **НЕ
  переписываются** на `x-email`/`x-date` конвенцию: это отдельная, обратно
  несовместимая миграция схемы (потребовала бы registry_schema_history
  bump + переиндексацию существующих данных). Данный фикс делает СЕРВЕРНЫЙ
  валидатор корректным для ОБЕИХ конвенций (`format:` и `x-*`) — обе схемы
  теперь компилируются и валидируют правильно, без необходимости трогать
  seed-данные.
- Конструктор реестров (`web/src/screens/apps-schema.js`, T-0516) — эмитит
  `x-email`/`x-url`/`x-date` для НОВЫХ полей; это НЕ трогается фиксом (уже
  корректно работало, просто вторым путём — x-* расширение, а не `format`).
  После этого фикса ОБА пути валидны на сервере.
- `web/src/screens/apps-schema.test.js` / `records-form.test.js` — их
  `new Ajv()` тестовые mirror-инстансы НЕ регистрируют `ajv-formats` — они
  проверяют, что схемы, которые ЭМИТИТ конструктор (x-*-конвенция), компилируются
  на ГОЛОМ AJV (то есть УЖЕ не используют `format`). Это намеренно и не
  меняется — доказывает, что путь конструктора не зависит от нового пакета.
- Пакет `ajv-formats@^3.0.1` добавлен как root dependency (peer `ajv@^8.0.0`
  совпадает с уже используемым `ajv@8.20.0`). `package-lock.json` обновлён.
