# T-0679 — BYO-онбординг немого ассистента (столп 5, E-FORMS)

Спека: SPEC+DESIGN+BUILD. Продуктовая часть решения фаундера 2026-07-07 (строгий BYO-LLM).

## Проблема (наблюдение)

Свежий тенант получает НЕМОГО ассистента: без подключённого LLM-ключа экран
«Ассистент» приземляется на пустую панель «Выберите разговор», а над ней —
тонкая предупреждающая полоса (T-0599) «Ассистент пока не может отвечать / Не
подключён LLM-ключ». Это ЧЕСТНО, но подано как ОШИБКА, а не как приглашение.
Столп 5 «настройка через ИИ» из коробки выглядит сломанным, а не «требующим
одного шага настройки».

## Решение фаундера (2026-07-07): строгий BYO

Свежие тенанты НЕ наследуют глобальный LLM-ключ (фаундер не платит за юзеров).
По умолчанию ассистент немой — и это НОРМАЛЬНОЕ стартовое состояние, которое
требует ЯВНОГО онбординга «подключите свой LLM-ключ», а не выглядит как поломка.

## Что уже построено (НЕ трогаем — реюз)

BYO-плумбинг завершён предыдущими задачами:
- Хранилище: `app_secret` (миграция 106) — AES-256-GCM, мастер-ключ
  `APP_SECRET_MASTER_KEY`, случайный nonce на строку. Сырой ключ НЕ хранится,
  НЕ логируется, НЕ возвращается.
- Реестр профилей: `llm_connection` (миграция 094), tenant-isolated RLS.
- Маршруты: `GET/POST /api/llm-connections`, `POST /api/llm-connections/:id/key`
  (шифрует), `GET .../key/status` (только `secret_bound` + redacted scheme),
  `POST .../:id/test`, `PUT /api/agents/:id/llm-connection`.
- Экран `/llm-connections` (screen-llm-connections.jsx): полный путь
  создать профиль → «Вставить API-ключ» (провайдер + ключ + опц. endpoint/model)
  → «Проверить подключение» → «Назначить ассистенту». Ключ маскируется.
- Свежий тенант ПОЛУЧАЕТ строку assistant-agent + agent_card (register.ts
  3e-3j-bis, миграции 115/118) → `GET /api/agents` честно отдаёт
  `llm_bound=false` для него.

Итого: точка ввода ключа и шифрование — есть. НЕТ строгого BYO — вопрос
наследования глобального ключа (проверить, что свежий тенант пустой). И слабо:
немая заглушка подана как ошибка, а не онбординг.

## Acceptance (что делает эта задача)

- AC-1 (онбординг вместо немой заглушки): на экране «Ассистент», когда у
  ассистента тенанта доказанно НЕТ рабочего ключа (`llm_bound === false`),
  основная область показывает НЕ пустую панель «Выберите разговор» и НЕ просто
  предупреждающую полоску, а ЯВНУЮ онбординг-панель с ценностной рамкой:
  «Подключите свой LLM-ключ, чтобы ассистент собирал формы и настраивал
  приложения». Панель объясняет BYO («ключ — ваш, вы платите провайдеру
  напрямую») человеческим русским.
- AC-2 (админ → действие): для админа/владельца тенанта панель несёт первичную
  кнопку, ведущую на `/llm-connections` (существующий экран ввода ключа). Это
  та же клиентская навигация, что и в T-0599; серверный гейт не обходится.
- AC-3 (не-админ → честный тупик без мёртвой двери): рядовому сотруднику панель
  честно говорит обратиться к администратору организации; кнопки на admin-only
  экран НЕТ (её всё равно не видно в его навигации).
- AC-4 (honest-degrade, без жаргона): текст панели — человеческий русский, без
  dev-жаргона (без `LLM_NOT_CONFIGURED`, `endpoint`, `secret_handle`,
  `APP_SECRET_MASTER_KEY`, `app://`, `503`, T-id). Проходит
  ux-g5-jargon-denylist.
- AC-5 (loading-honesty): панель НЕ мигает до резолва статуса. Показывается
  только на ДОКАЗАННОМ `llm_bound === false`; на unknown/null (сеть/ошибка) —
  НЕ показывается (обычный экран), не фабрикуем «ключа точно нет».
- AC-6 (ключ оживляет ассистента, реюз): ввод ключа происходит на существующем
  `/llm-connections` (POST → шифрование app://). После привязки+назначения
  `llm_bound` становится true, панель исчезает при следующем резолве (re-read
  on focus, уже есть в useAssistantLlmStatus). НОВЫХ маршрутов ключа нет.
- AC-7 (секрет-хранение — регресс-страж): ключ шифруется мастер-ключом
  (app_secret AES-256-GCM), НЕ логируется, `GET /api/llm-connections` НЕ
  возвращает сырой ключ (только `secret_bound` + redacted). Эта задача НЕ
  ослабляет ни одно из этих свойств (проверяется существующими серверными
  тестами; не-регресс).
- AC-8 (BYO строгий — не наследовать глобальный ключ): свежий тенант стартует
  БЕЗ привязанного ключа у ассистента (`llm_connection_id IS NULL`), даже если
  оператор задал серверный env-ключ. Проверить в разведке register.ts + маршрут
  списка, что глобальный/env-ключ НЕ подставляется автоматически профилем
  тенанта. Если подставляется — это дефект строгого BYO (зафиксировать/починить
  или эскалировать как followup).

## Дизайн

- Компонент `AssistantByoOnboarding` в screen-assistant.jsx заменяет пару
  (тонкий баннер T-0599 + `NothingSelected`) на первичную онбординг-панель,
  когда `showLlmBanner` (llmBound===false, не loading). Пока есть активный тред —
  всё равно ассистент немой, но пользователь мог открыть тред: панель остаётся
  над тредом как и раньше (не ломаем существующее поведение отправки → honest
  503). Ключевое изменение: КОГДА тред НЕ выбран и ключа нет — вместо
  «Выберите разговор» показываем онбординг (это первый экран немого тенанта).
- Kit-only: `Notice`/`EmptyState`/`Button` + `--chs-*` токены, без хардкод-цвета
  и эмодзи (OBLIK G6).
- Текст держится в web-слое (web/ не импортит src/), но зеркалит стиль
  ASSISTANT_LLM_UNAVAILABLE_MESSAGE_* — ценностная рамка + BYO-объяснение.

## Тесты (web, node-env, source-presence — конвенция экрана)

- T1: онбординг-панель существует и рендерится вместо немой заглушки при
  llmBound===false.
- T2: ценностная рамка «собир…форм» + BYO-объяснение «ваш ключ»/«платите
  провайдеру» присутствуют в тексте.
- T3: админ-ветка несёт CTA на /llm-connections; не-админ — обращение к
  администратору без пути/кнопки.
- T4: loading/unknown → онбординг НЕ показывается (regression T-0599 AC-4/AC-8
  остаётся зелёным).
- T5 (jargon): текст панели без dev-жаргона (денилист-совместим).

## Не-цели

- Live-proof AI-сборки (браузером на Dev Silo) — отдельно, оркестратор.
- Новый серверный маршрут ключа — не нужен (реюз app:// binder).
- Ротация мастер-ключа — не-цель (миграция 106 §10).
