## 1. Обходы гейта — ИСКАЛ, НЕ НАШЁЛ (гейт стоит на единственном канале P1-датумы)

Гейт стоит только на DETAIL — проверил, нет ли второго канала `variables`/`history`/`completedBy*`.

- **(а) Единственный производитель P1-датумы.** `variables`/`history`/`completedBy*`
  рождаются ТОЛЬКО в `fetchInstanceHistoryDetail` (`processes.ts:340`), у которой
  РОВНО ОДИН HTTP-вызыватель — теперь-гейтнутый DETAIL-хендлер (`processes.ts:687`).
  `getHistoricVariableInstances`/`getHistoricActivityInstances` (`flowable-client.ts`)
  не имеют ДРУГИХ вызывателей (grep по всему `src/`). SSE/websocket/event-stream —
  отсутствуют в кодовой базе.
- **(б) LIST + `/api/process-catalog` НЕ отдают P1-датуму.** Оба сериализуют
  `InstanceProjection` (через `projectionToInstance` / `serializeInstance`), в котором
  полей `variables`/`history`/`completedBy*` физически НЕТ (проверил интерфейс
  `process-projection.ts:116`). Они отдают `recordId`+метаданные — это P2/Phase-2
  (T-0722), заявленный вне скоупа. Подтверждено.
- **(в) Агент/ассистент НЕ читают инстанс-деталку.** Все тулы `assistant.ts`
  (`create_application`, `relate_application`, `author_binding`,
  `edit_jsonschema_non_destructive`, `emit_form`, `author_dmn`, `generate_process`) —
  authoring/write. Ни один не импортирует `process-projection`/`getHistoric*`/
  `fetchInstance*` и не читает `variables`/`history` (grep чист). Столп-4 агент,
  дёргающий HTTP, попадёт под тот же гейт (тот же роут).
- **Инбокс** (`GET /api/inbox/:id`) отдаёт `{item, projection}`, projection =
  `InstanceProjection` без P1-полей. Держатель задачи работает целиком через
  инбокс-плоскость — расследование строителя (ADR §2.4) подтверждено по коду.

**Вывод п.1: второго канала P1-датумы нет. Гейт на DETAIL закрывает единственную дверь.**

## 2. Корректность гейта — верна во всех углах

- `recordId === undefined` → `true` (record-less, phase-1 не сужается) — unit + live-PG.
- Запись в ДРУГОМ тенанте: `loadRecordRowAncestry` идёт через `withTenant` (SET LOCAL
  `choros.tenant_id` + `assertUuid` + явный `WHERE r.tenant_id=$1 AND r.id=$2`),
  `recordId` берётся из тенант-скоупнутой проекции → двойная изоляция (RLS-GUC + WHERE).
- Удалённая/несуществующая запись (recordId есть, строки нет) → `null` → `false` → 404.
  Unit-тест «deleted → honest-deny даже с wide-грантом» ✓.
- Malformed instance id → нет совпадения в проекции → 404. До `loadRecordRowAncestry`
  доходит только `match.recordId` (валидный UUID/undefined из проекции) — никогда сырой
  `params.id`. **500 невозможен** (весь блок в `try/catch` → 404).
- Кросс-тенант инстанс: не резолвится в проекции актора → 404 (live-PG тест 6). ✓

## 3. Honest-404 — shape неотличим; тайминг-сайдченнел (non-blocking в phase-1)

Деней и not-found кидают БАЙТ-ИДЕНТИЧНЫЙ `HttpError(404,"NOT_FOUND","instance not found")`
(тот же код, то же тело). Неразличимо по shape. **Но** есть тайминг-класс-разница:
деней-путь делает +3 DB round-trip (`getGrantsForSubject`+`loadTenantOrgAncestry`+
`loadRecordRowAncestry`) до 404, а честный not-found (нет совпадения в проекции)
уходит в 404 сразу. Это раскрывает «существует ли инстанс в тенанте». В phase-1
БЕЗВРЕДНО: LIST уже раскрывает существование инстансов оптом (заявленный скоуп).
→ **nit R-3**, важно пере-проверить, когда T-0722 закроет LIST (иначе DETAIL-тайминг
подорвёт non-disclosure, который LIST-гейт установит).

## 4. Live-PG матрица (прогнал 6/6 сам) — что покрыто и чего НЕ хватает

Покрыто: no-grant→404 · reader(default-open)→200+vars/history · owner→200(без bespoke)
· record-less→200 · honest-degrade(без резолвера)→200 · кросс-тенант→404.

НЕ хватает (**nit R-4**, non-blocking — покрыто транзитивно реюзом `isRecordReadable`
и его собств. сьютом records-read-pdp, но НЕ доказано на инстанс-пути):
- **узкий record-scoped грант**: грант на запись X → инстанс-X видим, инстанс-Y → 404
  (в матрице только широкий RESOURCE_ROOT грант).
- **грант отозван/истёк** (`valid_until` в прошлом) → сразу 404.

## 5. FF синтетика — СЛОМАЛ реальное дерево, обе FF краснеют (восстановлено начисто)

  хендлера) → **FAIL [FF-INST-VIS-1b] exit 1** ✓.
  ⚠️ **nit R-2**: детектор FF-1b грепает подстроку `isInstanceDetailVisible(` — переименование
  в СУПЕРСТРОКУ (`BYPASSED_isInstanceDetailVisible(`) проскакивает FF-1 (проверил живьём:

- **FF-2**: сломал все три класса на реальном дереве —
  2a (локальный ре-предикат `isFooReadable`), 2b (прямой импорт `isNarrowerOrEqual`),
  2c (bespoke `SELECT … FROM choros."grant"`) — каждый → **FAIL exit 1** ✓.
- Дерево восстановлено (`git status --porcelain` пусто перед коммитом вердикта).

## 6. Fail-open / fail-closed — NON-BLOCKING (структурно недостижим в проде)

- **Отсутствие резолвера → fail-OPEN** (`detailVisible=true`, гейт пропущен, все члены
  тенанта видят). Это РАТИФИЦИРОВАННЫЙ honest-degrade паттерн T-0570 — `records.ts:2061`
  делает БАЙТ-В-БАЙТ то же (`if (resolveReadVisibility !== undefined)`).
- **Почему НЕ blocking:** в проде `resolveReadVisibility` со-врезан со `startDeps` в ОДНОМ
  объект-литерале (`server.ts:685-714`, оба под `grantsPool && flowableClient`).
  Единственная точка конструкции `StartInstanceDeps` в `src/` — эта. Значит НЕТ прод-пути,
  где `variables` отдаются, а гейт пропущен. Fail-open проявляется только в тест-фикстурах,
  намеренно опускающих резолвер.
- **Защита от регресса:** удаление резолвера из `server.ts` унесёт маркер-комментарий
  `T-0721 (D-064, P1 из T-0714`, на который якорится **FF-INST-VIS-2d** → FF краснеет.
  То есть «тихо уронить прод-wiring» невозможно — FF-2d ловит.
- **Ошибка в резолвере/lookup в рантайме → внешний `try/catch` → 404 = fail-CLOSED.** ✓

**Вывод п.6: деградация fail-open присутствует по букве, но недостижима в проде
(со-wiring + FF-2d-якорь) и идентична ратифицированному T-0570. Non-blocking.**
