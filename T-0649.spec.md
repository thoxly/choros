# T-0649 — Полевые контролы (P1) + честность целостности данных

**Столп:** 2 (интерфейс из блоков на данных) · **Волна:** W4-UX (stage4)
**Источник:** docs/design/ux-study-2026-07-05.md §2 (заказ фаундера: поле даты + проверка остальных полей)
**Рендерер:** `web/src/forms/field-renderer.jsx` — ЕДИН для записей и задач; контролы ложатся во все формы разом (анти-кейс: генерик по типу поля, без кейс-контента).

## Что чиним (по приоритету)

### P1-1 — MoneyInput: потеря копеек (целостность данных)

**Факт (проверено кодом, не только живьём):** деньги хранятся ЧЕСТНО — `web/src/screens/records-form.js:955-968` сериализует money как `Number(str)` без округления (JS number → JSONB, копейки не теряются на записи). Баг — ЧИСТО ДИСПЛЕЙНЫЙ: `formatCellValue` (`records-form.js:1167-1172`) вызывает
```js
value.toLocaleString("ru-RU", { style: "currency", currency: "RUB", maximumFractionDigits: 0 })
```
`maximumFractionDigits: 0` округляет копейки НА ПОКАЗЕ (150000.5 → «150 001 ₽»). Это единственная точка форматирования — используется списком (`screen-app-records.jsx:1382`), канбаном (`kanban-board.jsx:88`) и деталкой записи (`screen-record-detail.jsx:839,897`) — один фикс закрывает все три места.

**Фикс:** показывать копейки, когда они есть (дробная часть ≠ 0) — 2 знака после запятой; целые рубли — без копеек (не «150 000,00 ₽» для круглой суммы, чтобы не захламлять типичный список). `minimumFractionDigits: 0, maximumFractionDigits: 2`.

**Ввод-поле (field-renderer.jsx `money` presentation, строки 1409-1430):** сегодня голый `<input type="number">` с плавающим ₽ снаружи (правильно принимает дробную часть браузером — потери на вводе НЕТ, только на показе). Заменяем на `MoneyInput` — ₽ ВНУТРИ поля (не обрезается границей), разряды-разделители при вводе (маска "150 000,50"), внутреннее состояние хранит "сырую" строку для ввода и парсит в число при onChange (тот же контракт — `onChange(key, string)`, сериализация не меняется).

### P1-2 — PersonPicker: `GET /api/org` 401 при живой сессии

**Корень (доказано по коду, не транзиент):** `fetchEmployees()` (`field-renderer.jsx:92-118`, ДО фикса) делает `fetch('/api/org')` БЕЗ единого заголовка авторизации. Комментарий в коде ошибочно предполагал, что «браузер сам пришлёт cookie» — но keycloak-режим авторизации в Choros ЦЕЛИКОМ на `Authorization: Bearer <token>` (`src/http/auth.ts:398-414`, `authenticate()`): без заголовка `withAuth` бросает 401 «missing Authorization header» ДО того, как `resolveActorSlugFromAuth` вообще вызывается. Каждый ДРУГОЙ fetch в том же файле (RelationPickerField, FileField) уже прикладывает `devHeaders()` — `fetchEmployees` единственное исключение. Это ДЕТЕРМИНИРОВАННЫЙ баг (100% воспроизводится в keycloak-режиме на каждый вызов), не транзиентный сбой сети/JWKS — `resolveActorSlugFromAuth` (src/db/org.ts, T-0371/T-0633) в порядке и не является причиной.

**Фикс:** `fetchEmployees()` → использовать `fetchWithAuthRetry('/api/org', { headers: devHeaders() })` (тот же паттерн T-0608 self-heal, который уже есть в `dev-auth.js` — заодно закрывает «транзиентный 401 без retry» для НАСТОЯЩЕГО транзиентного случая: истёкший токен посреди сессии). PersonPicker: честная ошибка + кнопка «Повторить» (retry перезапускает fetch).

### P1-3 — DateInput + datetime-тип + x-date в collection

- **DateInput**: стилизованный триггер «05.07.2026 📅» вместо голого `<input type="date">`; хранение — ISO как раньше (без изменения контракта `onChange`); список/деталка форматируют ISO → дд.мм.гггг вместо сырого `2026-07-05`.
- **datetime** — новый скалярный тип в таксономии (рядом с `date`): хранится как ISO-8601 datetime-строка, показывается «дд.мм.гггг чч:мм».
- **x-date в collection**: сегодня схема-редактор УЖЕ позволяет создать колонку типа `date` в «Список строк» (`COLLECTION_SUB_FIELD_TYPES` включает `"date"`, `screen-app-schema.jsx` предлагает её в пикере типа колонки) — но на чтении схемы (`apps-schema.js` parseCollectionSubFields, ~L845-860) тип читается ТОЛЬКО из `sfDef.type` (голый JSON-Schema `type:"string"`, без дискриминатора — AJV strict не позволяет вложенный `x-date` в `items.properties`, задокументировано в `apps-schema.js:716-718`), поэтому дата-колонка ПОСЛЕ перезагрузки схемы читается назад как обычная строка — рендер ячейки навсегда голый текст. Фикс: `x-date` пишем НЕ как JSON-Schema keyword, а через параллельный
  `items['x-collection-date-fields']: string[]` (список ключей суб-полей, которые являются датами) — родной верхнеуровневый ключ на `items` (не внутри `properties[key]`), AJV strict это не видит (мы его стрипаем как и остальные x-*), но парсер читает его ПОСЛЕ построения subFields и восстанавливает `sfType: "date"` для перечисленных ключей. Рендер ячейки (`CollectionField`) уже правильно диспетчерит `sf.type === "date"` через `FieldControl` → просто нужно, чтобы sfType дошёл до рендера как `"date"`, и в списке/деталке форматирование дд.мм.гггг применяется и к collection-ячейкам (через тот же `formatCellValue`/`FieldControl`).

### P1-4 — Убрать дублирующую колонку «Создано»

`screen-app-records.jsx:1359-1405` — `columns` (из `buildFieldCatalog`/view-config) уже включает pseudo-колонку `created_at` с `label: 'Создано'` (`list-view-panel.js:138`), но таблица ДОПОЛНИТЕЛЬНО рендерит захардкоженный `<th>Создано</th>` + `<td>{fmtTs(rec.created_at)}</td>` (строки 1363, 1401-1405). Если `created_at` уже присутствует в `columns` (видимая колонка активного view), это дубль. Фикс: рендерить `created_at` ТОЛЬКО через `columns` (как штатную колонку с типом `created_at`), убрать захардкоженный `<th>`/`<td>` дубль — но fallback: если по какой-то причине активный view НЕ включает `created_at` в columns (скрыт пользователем), не рисовать вторую колонку насильно — «Создано» показывается, только если оно есть в columns (согласовано с view-primitive из §4 исследования).

### P1-5 — Авто-retry транзиентного 401

`fetchWithAuthRetry` (`dev-auth.js:150-179`) уже реализует ровно этот паттерн (refresh-once → retry-once → login-redirect) для T-0608 — просто НЕ применялся в `fetchEmployees`. Тот же фикс из P1-2 закрывает и этот пункт для person-поля. Общая формулировка "убрать ложное «Сессия не авторизована — войдите заново»" — там, где экран уже использует `fetchWithAuthRetry`, транзиентный 401 самолечится; там, где экран использует голый `fetch` + `devHeaders()` без `fetchWithAuthRetry`, ложное сообщение возможно, но это отдельный périмetr (много экранов) — вне узкого скоупа T-0649 (сфокусировано на field-renderer.jsx). FINDING заведён отдельно (см. ниже).

## Анти-кейс

Контролы генерик (по типу поля: money/date/person), без кейс-контента (не «сумма закупки», не «дата подписания» — только денежный/датовый/персональный ТИП). Тема — исключительно через `--chs-*` токены (`.chs-input`/`.chs-label`), локализация рус, честные состояния (loading/error/empty), без мёртвых кнопок.

## Не в скоупе (P1 fixes только там, где узко и целостно за 1 заход)

- RelationPicker autocomplete, MultiSelect chips — волна B (§2.4/2.5 исследования), не сюда.
- Слаг-ад (§7), сайдбар (§1), UUID-зачистка (§3) — отдельные задачи волны W4.
- `fetchWithAuthRetry` НЕ применяется ретроактивно ко ВСЕМ экранам с голым fetch — только к `fetchEmployees` (единственная точка входа PersonPicker). FINDING заведён на широкий periметр.

## Тесты (по срезам)

1. MoneyInput/formatCellValue: `150000.5` → хранится точно (сериализация не меняется, регресс-тест) + показывается как «150 000,50 ₽» (не «150 001 ₽»), красный до фикса.
2. DateInput: рендерит дд.мм.гггг в списке/деталке для ISO `2026-07-05`.
3. datetime-тип: `resolveFieldContract`/`schemaToFormFields` распознаёт `x-datetime`, рендерит и форматирует с временем.
4. PersonPicker: fetchEmployees с 401 → честная ошибка + кнопка «Повторить»; повтор без 401 → список.
5. x-date в collection: колонка типа date сохраняется/читается назад как `date` (не деградирует в `string`).
6. Дубль «Создано»: список показывает ОДНУ колонку «Создано».
