## Главный риск: OWNER-CLAIM НЕ ПЕРЕ-ВЫДАЁТ (4 под-проверки) — ✔ подтверждено ЖИВЬЁМ на PG

`isOwnerOrphanClaimEligible = isGenesisOwnerForTenant(actor) ∧ isRoleEffectivePoolEmpty(role)`
(`src/http/inbox.ts:1441-1453`), fail-closed (try/catch → false).

- **(а) точно genesis-owner, не любой admin/owner-like.** `isGenesisOwnerForTenant`
  (`src/db/org.ts:747`) фильтрует именно `r.slug = 'tenant-owner'` + confirmed + in-window
  role_assignment, резолвится ИЗ БД (не из JWT, NF-3). Не «owner-like». ✔
- **(б) ТОЛЬКО при пустом пуле — не обходит нормальный claim.** Три регресс-кейса живого PG
  доказывают owner-claim **403** когда пул НЕ пуст: (c1) Tier-1-со-держатель, (c2) живой
  держатель, (c3) Tier-2-замещающий. Пустота считается тем же `computeEffectivePool` над теми
  же DAO (`getHoldersForRole` + `getActiveSubstitutionsByRole`), что и роутинг-путь B —
  роутер и claim-гейт структурно не могут разойтись. Держатель без правила отсутствия НИКОГДА
  не удаляется из пула ⇒ живой пул ⇒ owner denied. ✔
- **(в) fail-closed на деактивированном владельце.** Двойная защита: (1) внутренний
  slug→employee подзапрос `isGenesisOwnerForTenant` несёт `ACTOR_ACTIVE_SQL =
  "deactivated_at IS NULL"` → деактивированный владелец резолвится в false; (2) отдельный
  account-deactivation гейт (`inbox.ts:1919-1924` claim / `:2338-2343` approve) кидает 403
  ЕЩЁ ДО owner-ветки. `actor-authority-deactivation-gate.sh` (+self-test) PASS. Любая
  DB-ошибка в предикате → catch → false → честный 403 (не 500, не wrong-allow). ✔
  *(nit R-1: прямого live-кейса «деактивированный владелец → 403» в новом DB-тесте нет —
  безопасность наследуется структурно и независимо загейчена; замечание не блокирующее.)*
- **(г) владелец действует КАК СЕБЯ, не on_behalf_of.** DB-тест читает payload `task.claimed`
  и утверждает `'on_behalf_of' in payload === false` для owner-claim (кейс b), тогда как для
  Tier-2 (c3) `on_behalf_of === absentSlug`. Не эскалация чужих прав. ✔

## Замечания (все non-blocking)

- **R-1 (nit, ось 3 — тесты).** Новый DB-тест не покрывает прямой кейс «деактивированный
  genesis-owner → 403» для НОВОЙ authority-ветки. Безопасность структурно airtight
  (ACTOR_ACTIVE_SQL + отдельный account-deactivation гейт до owner-ветки + gate PASS), но
  прямая live-проверка была бы belt-and-suspenders для этого нового пути. `inbox.ts:1441`.
- **R-2 (nit, ось 2 — security-линза).** approve owner-ветка (`inbox.ts:2378`) не имеет
  guard-а `task.role !== undefined`, который есть в claim (`:1964` `taskRole !== undefined`).
  Не эксплуатируемо (owner-гейт + empty-pool-гейт; и pre-existing Tier-2-ветка уже бежит без
  этого guard-а), но симметричный truthiness-guard закрыл бы гипотетический approve владельцем
  безадресной (role="") задачи через пустой пул.
- **R-3 (nit, ось 4 — простота).** Путь B всё ещё резолвит `ownerSlug` через
  `findTenantOwnerSlug` (`inbox.ts:678-681`) и `void ownerSlug` (`:694`, коммент «used
  structurally by the fallback path»). После T-0744 owner-eligibility считается независимо в
  claim-гейте → это резолвинг дважды-мёртв, а коммент неточен. Pre-existing, вне скоупа
  T-0744, но кандидат на уборку.
- **R-4 (nit, ось 5 — соразмерность/точность).** PR-хэндофф пишет «T-0710 4» регресс; сьют
  escalation-order = 2 теста (T-0710 размазан по 3 db-файлам). Косметика счёта, не дефект.

Ни одно замечание не блокирует. Blocking-условия (owner пере-выдаёт при непустом пуле /
не-genesis / деактивированный проходит / эскалация on_behalf_of / предикат ломает
Tier-2/активный / approve-дыра) — НИ ОДНО не сработало.
