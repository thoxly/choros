# T-0653 — View-примитив платформы + рабочий инбокс под сотни задач

> W5-UX / §4 ux-study-2026-07-05. Родитель: эпик T-0647 E-UX-HUMAN.
> Фундамент: обобщение `list_view` (T-0581) до view-примитива с `source` +
> личными видами (`owner_actor`) поверх user-prefs (T-0651, миграция 129).
> Живой инбокс: серверный поиск/фильтры/группировка, кликабельные строки,
> контекст записи, агентские сигналы, ссылки из деталки, «настроить под себя».

## Границы скоупа (из брифа)
- `records` — ЖИВЬЁМ. `processes` — заявлен в типе/контракте с минимальной
  реализацией (открытый `source`-дискриминатор + валидатор-диспетчер), без
  собственного read-пути; UI-грид процессов НЕ в объёме.
- **Личный вид ИНБОКСА (колонки+плотность) живёт в `user_pref`** (T-0651, ключ
  `inbox.view`) — тот же per-user стор, что и сворачивание сайдбара, НЕ в
  `list_view`. Ревью fix-forward (defect #5) нашло, что серверный inbox-dispatch
  (`INBOX_VIEW_COLUMNS`/`validateViewSourceConfig(source='inbox')`/
  `defaultInboxViewConfig`) был МЁРТВ — экран его никогда не звал (сохранял через
  `user_pref`). Мёртвый параллельный путь с валидацией-которая-ничего-не-защищает
  ВЫРЕЗАН: `inbox` больше НЕ source-вид (`validateViewSourceConfig('inbox',…)` →
  unknown source). Держим ОДИН честный стор личного инбокс-вида (`user_pref`).
  Source-view-путь `list_view` теперь доказывается на `processes` (заявленный
  минимальный источник) — открытость `source`-дискриминатора как контракт цела.
- Канбан/календарь — НЕ надо.
- Обратная совместимость `list_view` (T-0581) обязательна: `GET /api/records`
  без view-параметров — байт-идентичен (FF-VR-6 держится).
- НЕ трогать: screen-app-records.jsx, screen-users.jsx, shell.jsx-топбар,
  rights/* (соседние T-0673/T-0652). Зона: inbox/*, view/list_view слой,
  user-prefs, серверный inbox API.

## Объектная модель (дельта к T-0581)

Миграция 130 (следующий свободный; 129 занят T-0651) — АДДИТИВНАЯ ALTER на
`choros.list_view`:
- `source text NOT NULL DEFAULT 'records'` — ОТКРЫТЫЙ дискриминатор источника
  (records|inbox|processes; НЕ CHECK-enum — как `type`, чтобы новый источник
  не требовал DDL). Существующие строки → 'records' (байт-совместимость).
- `owner_actor text NULL` — личный вид актора (NULL = общий тенантный вид, как
  сегодня). ADR T-0581 §5/§2 явно предусмотрел «per-user поверх той же таблицы,
  nullable owner_actor».
- `registry_def_id`/`application_id` → NULLABLE (inbox/processes-виды не
  привязаны к набору полей). Составные FK остаются, но срабатывают только на
  не-NULL (records-виды). records-вид по-прежнему требует registry_def_id
  (валидатор в TS).
- Партиал-уникальный дефолт переосмыслен: ≤1 default на
  (tenant, source, coalesce(registry_def_id, source), coalesce(owner_actor,'')) —
  общий и личный дефолт не конфликтуют, разные источники не конфликтуют.
- Идемпотентна (ADD COLUMN IF NOT EXISTS; DO-guard на индекс). Файл НЕ
  называется `*_list_view_registry.sql` (тот 123, читается RLS-гейтом).

## Acceptance (машинно-проверяемые)

### Часть 1 — view-примитив (source + личные виды)
- AC-1.1: `POST /api/list-views` принимает `source: "records"|"processes"`
  (по умолчанию "records"); неизвестный source → 400 VIEW_SOURCE_INVALID.
  `source:"inbox"` тоже → 400 (не source-вид, живёт в user_pref — см. скоуп).
- AC-1.2: `POST /api/list-views` с `personal:true` (или owner_actor) создаёт
  ЛИЧНЫЙ вид (owner_actor = актор-создатель, из токена/slug, НЕ из тела).
- AC-1.3: `GET /api/list-views` возвращает ОБЩИЕ виды тенанта + ЛИЧНЫЕ виды
  ТОЛЬКО этого актора; чужой личный вид НЕ виден (owner_actor-скоуп поверх RLS).
  То же для `GET /api/records?view_id=` (defect #8): чужой личный view_id → 404.
- AC-1.4: records-вид (source='records') требует registry_def_id; валидатор
  config = validateViewConfig как в T-0581 (обратная совместимость).
- AC-1.5: processes-вид НЕ требует registry_def_id; config валидируется
  диспетчером по source (validateViewSourceConfig) против СТАТИЧЕСКОГО каталога
  колонок processes (не registry_def). Открытость source-дискриминатора как
  контракт (новый источник = новая ветка валидатора БЕЗ DDL).
- AC-1.8 (defect #9): уникальность имени вида скоупится по
  (tenant, source, registry_def, owner_actor) — два актора могут назвать личные
  виды одинаково; дубль ВНУТРИ одного владельца → 409.
- AC-1.6: `GET /api/records` без view-параметров — байт-идентичен (FF-VR-6
  держится: records-view-application.test.ts зелёный, без list_view-запроса).
- AC-1.7: PUT/DELETE личного вида другим актором → 404 (owner_actor-скоуп); RLS
  чужого тенанта → 404.

### Часть 2 — серверный поиск + фильтры инбокса
- AC-2.1: `GET /api/inbox?q=<текст>` фильтрует по name/step/processName/inst
  (регистронезависимо, серверно, ДО пагинации).
- AC-2.2: `?process=<procKey|имя|inst>` фильтрует по процессу.
- AC-2.3: `?status=running|waiting|failed|done|paused` фильтрует по статусу.
- AC-2.4: `?deadline_from=<ms>&deadline_to=<ms>` фильтрует по дедлайн-диапазону.
- AC-2.5: фильтры комбинируются с существующими tab/exec/sort (AND); per-tab
  counts УВАЖАЮТ активные q/exec/фильтры (defect #3) — бейдж вкладки = число
  строк этой вкладки под текущим поиском (бейдж ↔ видимый список сходятся), а не
  общий tenant-scoped счёт. Тенант-скоуп и role-addressing (inTab) неизменны.
- AC-2.6: `?q=` параметризован/чист — фильтрация инбокса идёт по in-memory
  материализованным строкам, БЕЗ SQL-интерполяции (в inbox нет SQL-пути для q).

### Часть 3 — группировка по процессу
- AC-3.1: `GET /api/inbox?group=process` возвращает `groups: [{ key, label,
  count, procKey?, inst? }]` — свёртки по процессу с каунтами, плюс items.
  **Честность каунтов (defect #1, вариант «б»):** в grouped-режиме сервер
  возвращает ВЕСЬ отфильтрованный набор (НЕ страницу), ограниченный потолком
  `INBOX_GROUP_ROW_CAP=500`; `groups[].count` и тела групп считаются от ОДНИХ
  строк → бейдж группы никогда не висит над пустым/недогруженным tbody.
  `page:1,totalPages:1` в grouped-режиме → клиент не показывает «Показать ещё»
  (defect #2). При превышении потолка ответ несёт `groupTruncated:true` +
  `groupRowCap` → клиент показывает честное «показаны первые N».
- AC-3.2: без `group` ответ БЕЗ изменений (groups отсутствует, FLAT-пагинация
  как в T-0401) — обратная совместимость ответа инбокса.

### Часть 4 — контекст записи в имени задачи (список)
- AC-4.1: строка списка несёт recordId (уже есть на wire, T-0683) → RecordRef
  в имени задачи (уже частично в T-0687-list; проверить, что применено к
  ГЛАВНОМУ списку, а не только деталке). recordId честно опущен для
  manually-started/legacy.

### Часть 5 — кликабельная строка + ссылки из деталки
- AC-5.1: вся строка инбокса кликабельна (открывает деталку), не только «Открыть»;
  клики по вложенным ссылкам/кнопкам (RecordRef, Взять, Согласовать) НЕ
  всплывают в открытие деталки (stopPropagation); клавиатурная доступность
  (role/ tabIndex/Enter).
- AC-5.2: деталка задачи даёт ссылку на ЗАПИСЬ (RecordRef, уже есть) и на
  ИНСТАНС процесса — «Связанные задачи этого процесса» ведут на инбокс,
  ОТФИЛЬТРОВАННЫЙ по инстансу (не общий инбокс).

### Часть 6 — агентские сигналы в инбоксе
- AC-6.1: `doubt_reason` (T-0221) → бейдж «Агент сомневается: <причина>».
- AC-6.2: `routed_to_fallback:"role_unfilled"` (T-0380) → бейдж «Роль не
  заполнена — направлено вам».
- AC-6.3: `messageCatch` (T-0459) → бейдж «Ожидает сообщения[: <messageName>]».
- AC-6.4: сигналы едут по wire уже (проверено в inbox.ts InboxItem) — задача
  их ПОКАЗЫВАЕТ в списке (сейчас выбрасываются UI).

### Часть 7 — «настроить под себя» (личный вид инбокса)
- AC-7.1: пользователь скрывает/показывает колонки инбокса + переключает
  плотность (compact|comfortable) — сохраняется per-user через user-prefs
  store (T-0651, ключ `inbox.view`), переживает reload.
- AC-7.2: панель настройки — kit-компоненты, honest Loading/Empty/Error, без
  дев-жаргона, клавиатурно-операбельный reorder/toggle (UX-гейт).
