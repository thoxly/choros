## BLOCKING

### B1 (ось 2) — третий flatten дропает поле: person-поля в ДЕТАЛКЕ записи не несут маркер

`web/src/screens/screen-record-detail.jsx:772`

```js
setAuthorNames(new Map(list.map((e) => [e.id, e.name])));  // ← flatten до name-строки
```

Это ровно «ещё один flatten, дропающий поле», о котором предупреждал заказчик
ревью. Деталка записи — **второй потребитель** `fetchEmployees()` (первый —
`screen-app-records.jsx`), и она строит СВОЮ карту `Map<id, name-строка>`,
теряя `deactivated` (и всё остальное). Эта карта питает `PersonFieldValue`
(`screen-record-detail.jsx:629-632`):

```js
export function PersonFieldValue({ personId, authorNames }) {
  const name = authorNames instanceof Map ? authorNames.get(personId) : undefined;
  return <ActorChip type="human" name={name || personId} id={personId} />;   // ← нет deactivated
}
```

`PersonFieldValue` рендерит **значения person-ТИПА полей** в деталке
(`screen-record-detail.jsx:1064-1070`, `f.type === 'person'`) через тот же
`ActorChip`, что и `PersonCell`, — но БЕЗ пропа `deactivated` (и не смог бы:
карта его не несёт).

**Почему blocking, а не «out of scope».** T-0698 не просто «оставляет пробел» —
он **вводит НОВУЮ рассогласованность между двумя соседними поверхностями одной
фичи**. До T-0698 и таблица, и деталка одинаково не показывали маркер
(единообразно-неверно). После T-0698: тот же деактивированный сотрудник в том же
person-поле показан **зачёркнуто-приглушённым в ТАБЛИЦЕ записей, но полностью
активным в ДЕТАЛКЕ** (один клик). Это в точности класс дефекта «сигнал теряется /
человеческий слой несогласован», ради устранения которого существует эпик
E-UX-HUMAN и прецедент T-0648. Спека строителя декларирует «любые другие места
кроме PersonCell — вне охвата», но нельзя убрать пользовательскую
рассогласованность, объявив рассогласованного близнеца «вне охвата» — тем более
что и `PersonCell`, и `PersonFieldValue` рождены ОДНОЙ задачей T-0673 и рендерят
через ОДИН `ActorChip`.

**Suggestion (не правлю сам, D-007):** протянуть `deactivated` через
`screen-record-detail.jsx` — заменить `authorNames` на `Map<id, {name, deactivated}>`
(или параллельную карту), и передать `deactivated` в `PersonFieldValue` →
`ActorChip`, тем же выражением, что и `employeesById` в `screen-app-records.jsx`.
Метадата-поле «Автор» (`record.created_by`, строка 1113) рендерится простым
`Mono`-текстом, не `ActorChip`, — маркер там не требуется; блокер только про
person-ТИПА поля (`PersonFieldValue`).

## Ответы на линзы заказчика ревью

1. **Полнота протяжки:** НЕТ, не единственный путь. Таблица записей (`PersonCell`
   через `employeesById`) — починена. Деталка записи (`PersonFieldValue` через
   `authorNames`) — **третий разрыв, B1**. Канбан — person-поля «—» (пре-сущ., N2).
2. **Приватность:** OK. `listOrgTree` маппит `deactivated: e.deactivated_at != null`
   — сырой timestamp запрашивается, но на `OrgPerson` кладётся ТОЛЬКО boolean.
   В ответе `/api/org` сырой даты нет (db-тест `AC-boolean` это утверждает:
   `expect(person["deactivated_at"]).toBeUndefined()`). Grep client-дифа: все
   упоминания `deactivated_at` — комментарии. Консистентно с T-0648. PASS.
3. **Mutation-proof:** воспроизведён (revert org.ts → 3 RED), восстановлено, дерево чистое.
4. **e2e честность:** реальный `fetchEmployees` + реальный `PersonCell`, но Map —
   рукотворная копия выражения (N1).
5. **UX-линза:** `PersonCell → ActorChip → ExecutorBadge` навешивает
   `chs-exec--deactivated` (`components.css:29-30`: `opacity: 0.55` +
   `text-decoration: line-through`) + «· деактивирован» в тултипе/AT — **тот же
   muted-сигнал, что ActorChip в аудите/инбоксе/трейле**. Консистентно. g2 PASS.
6. **Гейты:** tsc 0; web 2675/2675; db 3/3 + mutation-red; anti-case-lock PASS
   (15<16); ux-g2 PASS; anti-uuid-actor-render PASS.
7. **Сервер:** `deactivated_at` — аддитивная колонка ИЗ ТОЙ ЖЕ `choros.employee`,
   тот же `WHERE tenant_id=$1 AND position_id=$2`, БЕЗ нового JOIN. Ни RLS, ни
   индексов, ни плана не задевает. Диф скоуплен (org.ts + field-renderer +
   комментарий в records + тесты + ADR/spec + pr-handoff + db-тест).

Итог: столпы 4/2 (агенты-как-сотрудники / интерфейс-на-данных) требуют, чтобы
сигнал деактивации был согласован ВЕЗДЕ, где показан актор. Табличная ячейка
починена образцово, но соседняя деталка того же поля осталась рассогласованной —
возврат строителю на дотяжку `PersonFieldValue`.
