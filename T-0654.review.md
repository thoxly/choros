## П.1 — PDP-КОМПОЗИЦИЯ и total (критично)

**Факт состояния (сверено git, не по описанию задачи):**
- Текущий `dev` (tip `018d2ac8`) УЖЕ содержит ОБА гейта в `src/http/processes.ts`:
  - T-0721: DETAIL `GET /api/processes/:id` обёрнут в `if (detailVisible)` (isInstanceDetailVisible → isRecordReadable, honest-404 при отказе).
  - T-0722: LIST `GET /api/processes` сужает `projections` через `filterProjectionsByReadVisibility(...)` → `visibleProjections` ПЕРЕД overlay/маппингом.
- Ветка T-0654 (base `a9d95206`) ПРЕДШЕСТВУЕТ обоим. `git merge-tree dev HEAD` → **CONFLICT (content) в `src/http/processes.ts`** (git НЕ авто-резолвит; резолв ручной) — в LIST-блоке И в DETAIL-блоке.

**Что делает ветка как есть (уровень LIST):**
```
projections   = listInstanceProjections(pool, tenantId, {limit:500})   // tenant-scoped, БЕЗ PDP
allInstances  = projections.map(projectionToInstance)                  // маппит ВСЁ tenant-видимое
selected      = selectProcessPage(allInstances, query)                 // фильтр→сорт→пагинация
total         = selected.total                                          // ← счёт по tenant-набору, НЕ по PDP-видимому
```
На собственной базе это не НОВАЯ дыра (совпадает с до-T-0722 постурой). Но dev ушёл вперёд.

**Failure-mode при наивном мерже «взять T-0654»:**
- LIST: `filterProjectionsByReadVisibility` выпадает → enumeration-утечка T-0722 переоткрывается; `total` считает НЕвидимые инстансы → **счётчик течёт enumeration** (сколько всего инстансов в тенанте) — ровно «total течёт», обозначенный фаундером blocking.
- DETAIL: `detailVisible`-гейт выпадает → сырые variables/history/completedBy* снова текут любому члену тенанта — переоткрытие P1 T-0721.

**Хорошая новость — структура КОМПОНУЕМА.** `selectProcessPage` — чистая функция, потребляет любой поданный массив. Корректный резолв: вставить PDP-фильтр dev ПЕРЕД `.map`/`selectProcessPage`, тогда `total` естественно = |PDP-видимое ∩ query-match| = пост-PDP:
```
projections        = listInstanceProjections(pool, tenantId, {limit:500})
visibleProjections = projections
if (resolveReadVisibility) { visibleProjections = filterProjectionsByReadVisibility(pool, tenantId, projections, grants, ancestry, nowMs) }  // dev/T-0722, ПЕРЕД pipeline
allInstances       = visibleProjections.map(projectionToInstance)   // ← маппим ТОЛЬКО PDP-видимое
selected           = selectProcessPage(allInstances, query)
total              = selected.total                                  // ← пост-PDP ✓
// overlay ТОЛЬКО page (как сейчас), enrichStarterNames
```
DETAIL: сохранить `if (detailVisible)`-обёртку T-0721 ВОКРУГ нового стартер-fold (starter-резолв внутри разрешённой ветки).

**Итог п.1:** ветка как есть — `total` считает tenant-набор (НЕ PDP), LIST/DETAIL без гейтов → при мерже без аккуратного ре-компоуза течёт enumeration + variables/history. Компонуемо, но рекомпозиция секьюрити-критична и в ветке НЕ покрыта тестом (не могла — база раньше гейтов). **Blocking.**

## Findings

### F1 — blocking (axis 4, security/PDP) — LIST: PDP-композиция + total enumeration
`src/http/processes.ts` LIST-хендлер (DB-ветка). Ветка маппит/пагинирует по tenant-набору БЕЗ PDP-фильтра T-0722, и `total` считает tenant-набор. dev уже несёт `filterProjectionsByReadVisibility`. Мерж = CONFLICT; наивный резолв роняет фильтр → enumeration + `total` течёт число невидимых.
**Suggestion:** ребейз на текущий dev; вставить `filterProjectionsByReadVisibility(pool, tenantId, projections, grants, ancestry, nowMs)` ПЕРЕД `.map(projectionToInstance)`/`selectProcessPage`, чтобы `total` = пост-PDP. Добавить композиц-тест: читатель с узким грантом видит МЕНЬШИЙ `total`, чем читатель с полной видимостью над тем же тенантом.

### F2 — blocking (axis 4, security/PDP) — DETAIL: мерж роняет гейт T-0721
`src/http/processes.ts` DETAIL-хендлер. Ветка добавила стартер-резолв на до-T-0721 базе → её DETAIL БЕЗ `if (detailVisible)`. Мерж = CONFLICT; наивный резолв роняет гейт → сырые variables/history снова текут любому члену тенанта.
**Suggestion:** сохранить обёртку `if (detailVisible)` (T-0721) вокруг нового стартер-fold — starter-резолв только в разрешённой ветке; отказ → honest-404.

### F3 — nit (axis 4) — total ограничен fold-окном ≤500
`total` — размер отфильтрованного набора В ПРЕДЕЛАХ fold-окна `listInstanceProjections({limit:500})` (cap readEvents), не истинный total тенанта. Для тенанта с >500 инстансов недо-отчёт. Предсуществующее ограничение, не введено частью A.
**Suggestion:** документировать семантику `total` как «в пределах окна» либо follow-up на честный COUNT в проекции.

### F4 — nit (axis 3) — нет композиц-теста PDP×query в ветке
Инвариант «PDP сужает ДО query-фильтра, total пост-PDP» не покрыт тестом (база раньше гейтов). Складывается в suggestion F1 — добавить при рекомпозиции.
