## 1. Решение

Три независимых, узко-скоуплённых фикса в периметре анти-кейс замка:

**Фикс 1 (R-4, свой файл `ci/checks/anti-case-lock.sh`).** `count_literal()`'s первая grep-стадия
переходит с жёсткого двойно-кавычного паттерна `"\"${literal}\""` на quote-agnostic
`"[\"'\`]${literal}[\"'\`]"` — литерал, обёрнутый в ЛЮБУЮ из трёх кавычек (двойная/одинарная/
обратная), единообразно для всех 8 денилист-литералов, без per-литерал спецкейсов. `ci/checks/
data/anti-case-baseline.json` пересчитывается ФАКТОМ прогоном этого нового матчера на HEAD ветки
(не переносится текстовой оценкой из ревью-документа T-0576 — методология этой волны: baseline
обязан быть измерен, не предсказан).

**Фикс 2 (ECO-1, чужой файл `ci/checks/rights-ui-anti-case.sh`, владелец T-0572).** Однострочная
правка `PROJECT_ROOT="$(cd "${SCRIPT_DIR}/.." && pwd)"` → `PROJECT_ROOT="$(cd "${SCRIPT_DIR}/../.."
&& pwd)"` (строка 25) — приводит идиому резолва к тому же виду, что уже используют
`read-pdp-anti-case.sh:26` и `anti-case-lock.sh:70` (оба резолвят `${SCRIPT_DIR}` = `<repo>/ci/checks`
на два уровня вверх до repo root). Санкционируется founder-класс записью в
`ci/checks/data/frozen-sanctions.jsonl` (см. §7 governance note — почему founder, не auto_additive).

**Фикс 3 (R-5, свой файл `ci/checks/anti-case-lock.sh`).** `count_literal()`/`read_baseline()`'s
внешняя (первая) grep-стадия перестаёт слепо глушить весь nonzero rc через `|| true`. Явная
трёхветочная развилка на перехваченном `rc`:
- `rc=0` (match found) — данные, как раньше.
- `rc=1` (no match) — легитимный "eroded" исход, как раньше (R-1 zero-safety не регрессирует).
- `rc>=2` (реальная ошибка grep: несуществующий/нечитаемый root, permission denied, некорректный
  regex) — ФАТАЛЬНО: явное `FAIL`-сообщение с указанием какой root/литерал вызвал ошибку,
  ненулевой exit ВСЕГО скрипта (не молчаливый "0 OK (eroded)").

### Почему три отдельных фикса, а не единая переработка

Рассмотрен вариант объединить фикс 1 и фикс 3 в единый "переписать `count_literal()` с нуля"
патч — отклонён: R-4 (детекция) и R-5 (обработка ошибок) — ортогональные оси находки ревью
(`axis: "detection coverage boundary"` vs `axis: "rc>=2 masking"`), правка каждой по отдельности
даёт меньший, легче аудируемый диф на каждую находку (одна находка ревью = один логический
кусок диффа, отслеживаемый по ID находки в commit message — тот же принцип, что практикуют
предыдущие R-N раунды T-0570/T-0575/T-0576).

Фикс 2 (ECO-1) физически не может быть объединён с фиксами 1/3 — он в ДРУГОМ файле, чужом
(`rights-ui-anti-case.sh`, владелец T-0572), c собственной санкц-записью — смешивание его с
правками собственного файла `anti-case-lock.sh` в одном коммите усложнило бы аудит "что именно
здесь санкционировано" (санкция должна покрывать РОВНО дифф чужого файла, не более).

## 2. Отвергнутые альтернативы

| Вариант | Почему отвергнут |
|---|---|
| А1. Матчер на regex-alternation `"(\"${literal}\"|'${literal}')"` (явно двойная ИЛИ одинарная, без backtick) | Отклонён — репозиторий сегодня не использует template-literal-обёрнутые денилист-значения, но кавычка-класс `["'\`]` в character-class форме читается компактнее regex-alternation и покрывает третий стиль кавычек без дополнительного условия — если backtick-обёртка появится в будущем (template literal), гейт уже готов, вместо того чтобы потребовать ЕЩЁ один follow-up ревью той же природы, что R-4. |
| А2. Раздельные denylist-паттерны per-кавычка-стиль (двойные проверяются одним проходом, одинарные — вторым, агрегируются) | Отклонён — усложняет `count_literal()` без функциональной разницы: единый quote-agnostic паттерн в ОДНОМ grep-вызове даёт тот же подсчёт строк, что два прохода + суммирование, но без риска двойного счёта строки, содержащей И двойную, И одинарную кавычку одного литерала на одной строке (маловероятно, но единый проход исключает этот класс бага по конструкции). |
| Б1. Перезаписать baseline вручную числами из текста ревью (role-approver:3, approvalRequired:5, агрегат:24) без прогона | Отклонён явно мандатом задачи ("baseline=факт") — ревью использовало quote-agnostic контр-грeп для СВОЕЙ независимой проверки при round 2, но не запускало сам продакшн-скрипт с новым матчером (матчер тогда ещё не существовал); baseline этой волны обязан быть выводом РЕАЛЬНОГО прогона нового кода на реальном дереве, не транскрипцией предсказания ревью — иначе тот же класс риска, что R-2 находка T-0576 (spec-drift от факта). |
| В1. Не чинить `rights-ui-anti-case.sh` вовсе, только задокументировать ECO-1 как known-issue | Отклонён — задача явно мандирует фикс; кроме того, оставление гейта вечно-зелёным (структурно нефункциональным) означает, что D-064 §5 периметр `web/src/` эффективно НЕ защищён diff-scoped гейтом уже несколько волн (T-0572 создавался как "companion gate" именно для web/src/) — тихое согласие с нефункциональным required-CI-звеном хуже честного фикса. |
| В2. Переписать `rights-ui-anti-case.sh` целиком (не точечный фикс одной строки) | Отклонён — спека NF-3 требует диффовую честность: чем БОЛЬШЕ строк меняется в чужом файле, тем труднее аудитору (или будущему `auto-sanction-additive.sh`-подобному механизму) верифицировать, что правка не расширяет/не ослабляет предикат гейта за пределы заявленного основания (ECO-1 restoration). Один символ-уровня фикс (`..` → `../..`) — минимально возможный дифф, доказуемо тот же класс правки, что чисто арифметическая ошибка, а не архитектурное решение. |
| Г1. Классифицировать санкцию фикса 2 как `auto_additive` (FF-FCI13, не требует founder-диалога) | Отклонён после проверки `auto-sanction-additive.sh`'s правил A-1..A-4: A-1 требует, чтобы КАЖДАЯ непустая строка BASE_REF-версии файла присутствовала в HEAD-версии БАЙТ-ИДЕНТИЧНО (дифф — только "+"-строки). Фикс МЕНЯЕТ значение существующей строки (`PROJECT_ROOT=...` присвоение) — это модификация, не добавление; A-1 буквально нарушается по конструкции правки. `auto_additive`-канал структурно недоступен для value-fix на существующей строке; единственный доступный канал — `founder` (FF-FCI12), тот же класс, что санкция FF-0328-3 в T-0576 (см. §7). |
| Д1. Оставить `|| true` без изменений, задокументировать R-5 как permanent known-limitation | Отклонён — задача явно мандирует явную обработку; кроме того, R-5 сама называет узкий, но реальный материальный риск (missing/unreadable root маскируется в "OK (eroded)" вместо явной ошибки), который дёшево закрывается (несколько строк rc-перехвата), не требуя архитектурных изменений. |
| Д2. `[[ -d "${SRC_ROOT}" ]]`/`[[ -d "${WEB_ROOT}" ]]` asserts перед сканом (предложение самого ревью, R-5 suggestion) вместо rc-перехвата в `count_literal()` | Рассмотрен, НЕ выбран как единственная мера (дополняет, не заменяет) — `-d`-assert ловит ТОЛЬКО класс "директория отсутствует", но не остальные rc>=2 причины (permission denied на файл внутри дерева, corrupt regex переданный по ошибке будущей правкой). Явный rc-перехват в самой функции — более общая защита, покрывающая весь класс "grep вернул rc>=2 по любой причине", включая ту, что `-d`-assert не поймает. `-d`-assert остаётся ДОПОЛНИТЕЛЬНО дешёвым дальнейшим ужесточением (out-of-scope O5 этой волны, если анализ покажет вторичные grep-стадии структурно недостижимыми для rc>=2). |

## 7. Governance note (санкция фикса 2, ECO-1)

Правка `ci/checks/rights-ui-anti-case.sh` (владелец T-0572) — модификация ОДНОЙ существующей
строки (значение `PROJECT_ROOT`-присвоения), не добавление новой. Проверка `auto-sanction-
additive.sh`'s A-1 ("каждая непустая строка BASE_REF-версии присутствует в HEAD байт-идентично")
показывает: этот канал структурно недоступен для value-fix такого рода — A-1 буквально требует
byte-identical сохранение строки, а фикс её МЕНЯЕТ. Значит санкция идёт через `founder`-канал
(FF-FCI12), тот же governance-класс, что санкция FF-0328-3 в T-0576 (запись `task:"T-0576"` в
`frozen-sanctions.jsonl` — тоже классифицирована `founder`, не `auto_additive`, по аналогичной
причине: сужение allowlist-предиката — модификация существующего элемента массива, не чистое
добавление).

**Прецедент как основание.** Санкция T-0576 (`task:"T-0576"`, `file:"ci/checks/
http-route-auth-coverage.sh"`) уже установила рабочий прецедент в этом репозитории: **правка,
исправляющая структурную неточность/дефект чужого чека относительно его же задокументированного
контракта — валидное основание для founder-класс санкции**, если (а) диф скоупится РОВНО к
исправлению этого дефекта (не более), (б) обоснование прослеживается к конкретному документу
(там — ADR §4.2; здесь — `docs/test/T-0576.test-report.json` `notes.ECO-1_foreign_check_bug` +
`docs/review/T-0576.review.json` finding ECO-1/R-4), (в) правка ВОССТАНАВЛИВАЕТ enforcement
(строгость), не ослабляет его.

Для фикса 2 это основание даже СИЛЬНЕЕ, чем в прецеденте T-0576: там сужался предикат (уменьшение
enforcement-поверхности одного арма, компенсированное отдельным структурным гейтом); здесь
чинится чистый арифметический баг (`${SCRIPT_DIR}/..` вместо `${SCRIPT_DIR}/../..`), после
которого гейт идёт от "структурно всегда пуст" (`pathspec` резолвится в несуществующий путь) к
"работает по задокументированному design т-0572" (git-diff-scoped scan над `web/src/`) — фикс
СТРОГО увеличивает enforcement, не может дать false-positive относительно старого (нулевого)
поведения на любом входе, где старое поведение было PASS по причине бага. Санкц-запись фиксирует
это основание явно (`sanctioned_by:"founder"`, `decision` ссылается на этот ADR §7 + review/test
находки T-0576).
