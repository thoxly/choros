## 1. Судьба секрет-хэндл-поля: УДАЛЕНО из формы создания (не advanced-collapse)

### 1.1 Разведка: почему поле не «непонятное», а нерабочее

Задача давала два варианта: свернуть в advanced-блок «для оператора» ИЛИ
убрать вовсе — решение по факту, кто реально пользуется env-хэндлом после
T-0600. Разведка кода дала однозначный ответ: **никто не может им
воспользоваться, потому что резолюция невозможна структурно**, не только
«обычно недоступна».

Три факта, найденные в коде (не в спеке/памяти — читал реализацию):

1. **`env://` безусловно отклоняется в tenant-пути.**
   `src/server.ts:203-217` (`tenantSecretResolver`, T-0413):
   ```ts
   const decision = decideEnvHandle(handle);
   if (decision.kind !== "not_env") {
     throw new Error(
       `[T-0413] env:// handles are system-only and may not be used as tenant secret ` +
       `handles (handle: ${redactHandle(handle)}). Store tenant keys via the ` +
       `secret-handle custody store (POST /api/agents/:id/secret-handle).`,
     );
   }
   ```
   Это не «текущий баг, который могут исправить» — это НАМЕРЕННЫЙ security
   guard (allow-list существует ТОЛЬКО для system-internal путей,
   `env-secret-allowlist.ts`, T-0382 D5 BLOCKER-1: «arbitrary env exfil
   guard»). Ослаблять его нельзя — тенант, способный резолвить произвольный
   `env://ИМЯ`, мог бы прочитать секреты ДРУГИХ тенантов/системы.

2. **`vault://` объявлен, но резолвер никогда не реализован.**
   `src/http/secret-handle.ts:18`: «`resolveSecret` port is declared
   (SecretResolverPort), NEVER invoked here (FR-6 / Stage-2)». Grep
   подтверждает: ни один production call-site не резолвит `vault://` ни для
   какого тенанта. Указывать `vault://путь` в форме — это ввод данных в
   пустоту, которая никогда не активируется без отдельного будущего проекта.

3. **`llm_connection.secret_handle` — это ЖИВОЙ путь до реального вызова.**
   `src/db/agent-provision.ts:readConfiguredAgentLlmConfig` резолвит
   `COALESCE(lc.secret_handle, ac.llm_secret_handle)` — т.е. хэндл,
   введённый в ЭТУ форму (`llm_connection.secret_handle`), при привязке
   профиля к ассистенту (`AssistantBinder`, `PUT /api/agents/:id/llm-connection`)
   реально доходит до `makeLlmPortFactory` → `validateSecretHandleShape` →
   тот самый `[T-0413]`-reject. Это не мёртвая колонка для показухи — это
   именно то поле, которое владелец тенанта видел бы использованным, если
   бы оно работало. Оно не работает.

Итог: владелец тенанта, ввёдший `env://DEEPSEEK_API_KEY` по плейсхолдеру
формы, получает профиль, который **пройдёт валидацию создания** (shape-guard
проверяет только «похоже на ссылку», не резолвируемость), но **никогда не
заработает** — либо честная ошибка на «Проверить подключение»
(`llm-connection-test.ts:183-185`: «Эта ссылка-хэндл (env://) недоступна как
ключ тенанта.»), либо тихий dormant/503 у реального ассистента. Это
классическая UX-ловушка: форма предлагает путь, который выглядит валидным,
но структурно ведёт в тупик.

### 1.2 Решение — удалить, не сворачивать

Advanced-collapse («Дополнительно, для оператора сервера») был бы уместен,
если бы хэндл РАБОТАЛ для оператора через какой-то другой (не тенантский)
путь конфигурации — например, если бы существовал отдельный
admin/operator-экран, где `env://`/`vault://` резолвятся системным
контекстом. Такого экрана НЕТ: `llm_connection` — тенант-скоуп таблица
(RLS, `tenant_id` в каждой строке, T-0474), read/write всегда идёт через
`resolveActorTenant(actor)` — то есть **даже оператор, зашедший как
пользователь тенанта, попадает в тот же самый tenantSecretResolver reject**.
Единственный способ завести реально работающий `env://`-ключ — вручную
править БД / переменные окружения сервера в обход HTTP API вообще (за
пределами любого UI). Advanced-блок в ЭТОЙ форме не открыл бы легитимный
путь — он лишь красивее спрятал бы ту же ловушку под ярлыком «для
продвинутых», что хуже статус-кво (неявно повышает доверие пользователя к
опции, которая всё ещё нерабочая).

**Поле удаляется из формы создания целиком.** Серверный контракт
(`secret_handle` как опциональное поле API) НЕ меняется — это оставляет
дверь открытой для будущего легитимного admin-инструмента (например, скрипт
миграции существующих `env://`-based интеграций или будущий Stage-2
vault-резолвер), не проливая тенантский UI-жаргон на пользователя сегодня.

## 2. Провайдер-нейтральная/динамическая инструкция

Текущий блок «Откуда взять ключ» жёстко ведёт по Anthropic
(`console.anthropic.com`), независимо от выбранного в форме провайдера —
рассинхрон, аналогичный тому, что T-0597 уже чинило для ДЕФОЛТОВ формы (но
не для текста инструкции). Решение: `PROVIDER_PRESETS` получает поле
`consoleHint: { url: string, label: string } | null` — единственный источник
текста, читаемый и формой (уже читает `PROVIDER_PRESETS` для
endpoint/model/price), и инструкцией. Инструкция рендерит `consoleHint`
ТЕКУЩЕГО выбранного `provider` (реактивно — меняется при `onProviderChange`),
с нейтральным фолбэком текстом, когда `consoleHint === null`
(self-hosted/другой): «У вашего провайдера должен быть раздел с
API-ключами в личном кабинете.» — честно, не выдумывает несуществующий URL.

**Отклонённая альтернатива:** статический провайдер-agnostic текст без
конкретных URL вообще («зайдите в консоль вашего провайдера»). Отклонено —
конкретный URL (когда он есть) снижает трение сильнее, чем общая фраза;
T-0574 уже доказал ценность конкретики (`console.anthropic.com` + точный
путь «API Keys» → «Create Key»), нет причин откатывать эту конкретность для
провайдеров, для которых мы её знаем — только добавить её для остальных двух
(DeepSeek/OpenAI) и честно её убрать там, где не знаем (self-hosted/другой).

## 3. Карточки: человеческая подпись вместо сырого `app://…`

Сервер уже отдаёт `secret_handle_redacted` (редактированная строка с
сохранённым префиксом схемы, `redactHandle()` — не меняется, N1/O1). Клиент
парсит префикс (`app://`/`env://`/`vault://`) БЕЗ нового серверного поля и
рендерит человеческую строку вместо сырой. Это ЧИСТО клиентское форматирование
существующих данных — не новый API, не новая колонка.

**Отклонённая альтернатива:** добавить серверное поле `secret_handle_kind`
(enum) вместо клиентского парсинга префикса. Отклонено — избыточно: префикс
схемы уже механически детерминирован (`redactHandle` сохраняет его как
первые символы, по конвенции T-0474/T-0476/T-0413 — все три схемы
префиксные по построению), парсинг трёх строковых префиксов на клиенте не
требует нового серверного контракта ради решения чисто текстового вопроса
(SRP: сервер уже сказал «связан + какая схема», клиент решает, как это
показать по-человечески — ровно тот же принцип, что уже применён к
`secret_bound`/`chipStyle` в T-0597).

## 4. Object model

Не вводится ни одна новая серверная сущность/поле/таблица. Клиентское

локального массива, не персистентное).

## 8. Rejected alternatives (сводно)

1. **Advanced-collapse блока секрет-хэндла вместо удаления** — отклонено
   (§1.2): нет легитимного admin-пути, который бы этот блок открывал в
   ЭТОЙ форме (тенант-скоуп RLS одинаков для оператора и владельца); скрыть
   ловушку глубже — не то же самое, что убрать её.
2. **Провайдер-agnostic статичный текст инструкции без конкретных URL** —
   отклонено (§2): конкретика там, где она есть (3 из 5 провайдеров),
   снижает трение сильнее общей фразы; честный фолбэк остаётся только там,
   где URL реально неизвестен.
3. **Новое серверное поле `secret_handle_kind`** — отклонено (§3): избыточно,
   префикс схемы уже детерминирован существующим `redactHandle`, парсинг
   на клиенте — чисто текстовое форматирование.

## 9. Escalation

Нет. Изменение — чисто клиентское (форма/тексты/один helper), не меняет
серверный контракт, не расширяет права/данные/секреты. Решение убрать (а не
свернуть) секрет-хэндл-поле опирается на код-факт (env:// категорически
отклоняется T-0413, vault:// не реализован), не на догадку — задокументировано
выше с точными путями/строками.
