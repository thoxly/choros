# ADR-T0587 — Аналитик живьём в контуре READ-PDP спрашивающего (столп 6)

Статус: accepted (design). Спека: `T-0587.spec.md` (+ прозовый компаньон
`docs/specs/T-0587-analyst-pdp.spec.md`). Схема выхода: `schemas/adr.schema.json`
(`T-0587.adr.md`).

Принцип: любой факт/агрегат о данных компании, попадающий в ответ аналитика,
вычислен строго по подмножеству, видимому СПРАШИВАЮЩЕМУ через тот же READ-PDP
(T-0570), что человеческий REST-путь тех же данных — и доказан живьём двумя
пользователями разных грантов. Не вторая система прав, не более щедрая аналитик-
ветка, не подмена identity владельцем/сервисным аккаунтом.

Задача НЕ переписывает ассистента: T-0607 (`bb67bf4`, в dev) уже дал ядро —
реальный identity спрашивающего (`ctx.userSubject.subjectId`, `intersectionGrants`
агент∩юзер) + READ-PDP-дайджест реестров + honest-503. Остаток T-0587:
(а) минимальный агрегат по видимому числовому полю (кейс-вопрос «на какую сумму»),
(б) честная формулировка отказа по объёму видимости, (в) регресс-замки на identity
и порядок фильтрации, (г) chat-level и live доказательство.

## §1 — Развилка ND: агрегатный порт — BUILD (минимальный, внутри уже-безопасного цикла дайджеста)

**Решение: строить, но НЕ новым каналом и НЕ переиспользуя Floor-1.** Расширяю
существующий per-row цикл `loadReadableRegistryDigest` (`registry-digest-dao.ts`),
который УЖЕ фильтрует каждую строку через `isRecordReadable` и УЖЕ грузит `row.data`,
дополнительной bounded-аккумуляцией числового агрегата. Ни одного нового SELECT, ни
одного нового PDP-пути, ни одной строки, обходящей предикат.

### §1.1 Почему НЕ Floor-1 report-builder (T-0121/T-0492)

Разведка кода: `src/http/report-page-render.ts::buildAggSql` считает count/sum/avg/
min/max **сырым SQL с GROUP BY** (`SELECT SUM((data->>'field')::numeric) FROM
choros.record WHERE tenant_id=$1 AND registry_id=$2`). Этот путь проверяет
**application-level** read-грант (`checkReadGrant`), но **НЕ применяет
`isRecordReadable` построчно** — по архитектурному замыслу Floor-1 (ADR-T0121 §4/
§9.2, отчёт-страницы application-scoped, не record-scoped). Переиспользовать его
для аналитика значило бы **посчитать сумму по записям, которые спрашивающий читать
не вправе** — ровно та утечка, что FR-2/NF-1 запрещают. Отвергнуто.

### §1.2 Почему НЕ полный listRecords record-lister

`listRecords`-порт в `runAnalyst` не подключён (production = `[]`, §0.1 спеки).
Поднять полный постраничный ридер записей = O1 follow-up ADR-T0607, вне объёма
(out_of_scope §4). Он тянет пагинацию, произвольные поля, tool-use — несоразмерно
(рубрика ось 5). Кейс-вопрос «сколько и на какую сумму» отвечается точечным
агрегатом, не полным ридером.

### §1.3 Почему НЕ «только существующий count/samples»

Дайджест сегодня даёт «сколько» (`visibleCount`) и «какие» (`samples`), но НЕ «на
какую сумму». Кейс-вопрос в `business_summary` — «сколько сделок в работе и на какую
сумму?» — без агрегата по значениям поля отвечается наполовину, и LIVE_PROOF был бы
половинчатым (числа-суммы недоступны структурно). Минимальный sum-агрегат по одному
числовому полю закрывает кейс-вопрос при нулевой цене риска (тот же цикл, тот же
предикат, тот же лимит).

### §1.4 Что именно строится

`loadReadableRegistryDigest` уже проходит bounded окно (`scanLimit`, default 200)
записей каждого реестра, вызывая `isRecordReadable` на каждой и загружая `row.data`.
В ЭТОМ ЖЕ цикле, ПОСЛЕ прохождения предиката (строка уже разрешена), аккумулируем
per-registry числовые агрегаты по **автоматически определённым числовым полям**
записи:

- Новое поле в `ReadableRegistryEntry`: `numericAggregates?: readonly NumericFieldAggregate[]`.
- `NumericFieldAggregate = { fieldKey; fieldLabel; count; sum; avg; min; max }`.
- Числовое поле определяется **generic**, через существующий
  `field-type-dictionary.ts::deriveFieldType(prop) === "number"` по
  `registry_def.record_schema.properties` (D-064: имя поля НЕ хардкодится — берётся
  из схемы реестра, только тип «number»). Cap: не более `numericFieldLimit` (default
  5) числовых полей на реестр — bounded (NF-5).
- Аккумуляция — **чистая** (`+=` по уже загруженной `row.data[fieldKey]` после
  `Number()`-коэрса и `Number.isFinite`-проверки; нечисловые/пустые значения
  пропускаются, не роняют аккумулятор). Никакого нового SQL, никакого GROUP BY в БД.
- Чистая функция-аккумулятор выносится в новый pure-модуль
  `src/core/visible-aggregate.ts` (IO-free, тестируется без БД), которую цикл DAO
  вызывает: `accumulateNumeric(acc, row.data, numericFieldKeys)` →
  `finalizeNumeric(acc)`. Это даёт AC-4-уровневый unit-тест агрегата в отрыве от pg.

**Инвариант порядка (FR-2):** агрегат обновляется ТОЛЬКО внутри ветки, где
`isRecordReadable(...) === true` — та же строка, что инкрементит `visibleCount`.
Строка, не прошедшая предикат, не входит ни в count, ни в sum/avg/min/max.

`buildDraftContext` (`assistant-analyst.ts`) рендерит новую под-строку агрегатов
под каждым реестром: `«поле X»: сумма N, среднее M, мин…макс` — генерически, из
`numericAggregates`, только когда они непусты. LLM видит суммы уже-в-правах; не
имеет отдельного доступа к БД.

## §2 — Семантика честности отказа (FR-3/FR-5): формулировка = часть приёмки

Проблема утечки: формулировка отказа не должна отличать «нет записей» (реестр пуст
для всех) от «нет прав» (записи есть, но не видны спрашивающему) — иначе агрегат/
текст палит существование скрытой записи (FR-3).

### §2.1 Новая платформенная константа отказа

Новая user-facing строка в `src/core/assistant-messages.ts`:

```
ASSISTANT_ANALYST_NO_VISIBLE_DATA_MESSAGE =
  "В вашей зоне видимости данных по этому вопросу нет. " +
  "Если данные должны быть вам доступны — обратитесь к администратору вашей " +
  "организации, чтобы он выдал доступ.";
```

Свойства (проходит `assistant-llm-message-jargon.sh`, NF-6):
- НЕ утверждает «данных в системе нет» (это была бы ложь о СОСТОЯНИИ системы, не о
  видимости спрашивающего — FR-5);
- НЕ различает «пусто» и «нет прав» — единая формулировка «в вашей зоне видимости
  нет», применимая к обоим (FR-3: неразличимость = анти-утечка);
- генерическая, платформенная — без кейс-литерала (D-064), без имени реестра/
  записи, без кода ошибки/жаргона.

### §2.2 Где применяется — в `buildDraftContext`, детерминированно, ДО LLM

Ключ: отказ FR-5 — это **серверно-построенная строка контекста**, а не «надежда,
что LLM откажет». `buildDraftContext` получает новую ветку:

- **Zero-visibility-условие**: дайджест НЕ `null`, НЕ `degraded`, И
  `totalVisible === 0` по ВСЕМ реестрам (сумма `visibleCount` = 0), И ни у одного
  реестра нет ненулевых агрегатов. Тогда секция реестров заменяется единой строкой,
  инструктирующей LLM: пользователю не видно ни одной записи → ответить формулировкой
  `ASSISTANT_ANALYST_NO_VISIBLE_DATA_MESSAGE`, не приводить числа, не утверждать
  существование конкретных записей.
- Существующая ветка «дайджест известен и пуст» (§0: registries.length===0) и ветка
  totalVisible===0 сливаются в эту семантику. Разница с сегодняшним кодом: сегодня
  при `totalVisible===0` контекст говорит «в доступных разделах пока нет записей —
  это достоверный факт»; это верно, только когда реестры действительно пусты для
  ВСЕХ. Когда реестры существуют и НЕ пусты глобально, но спрашивающий не видит ни
  одной — сегодняшняя строка «нет записей — достоверный факт» была бы ложью о
  состоянии системы. Новая ветка не утверждает факт о системе — только о зоне
  видимости спрашивающего.

**Важно про FR-3-неразличимость:** дайджест по построению перечисляет только
`published`-реестры (метаданные реестра-как-раздела открыты — это не утечка записи).
Существование КОНКРЕТНОЙ невидимой ЗАПИСИ никогда не упоминается: агрегаты и samples
считаются только по видимым строкам, `visibleCount` невидимых = 0. Reader без грантов
видит `visibleCount:0` по каждому реестру (как в `registry-digest.test.ts` AC-3b) →
zero-visibility-ветка → FR-5-формулировка.

## §4 — Fitness-функции (машинно-проверяемые границы для CI)

См. `fitness_functions` в `T-0587.adr.md`. Ключевые:

- **FF-1 (identity анти-регресс, AC-1):** ни один путь построения `draftContext` не
  резолвит видимость иначе как через `ctx.userSubject.subjectId`. Grep-guard +
  unit-тест: `runAnalyst` вызывает `loadRegistryDigest(ctx.tenantId,
  ctx.userSubject.subjectId)` (не `agentSubject`, не литерал-владелец, не «все гранты»).
- **FF-2 (порядок фильтрации, AC-4):** агрегат/count вычислен ПОСЛЕ `isRecordReadable`.
  Unit над `visible-aggregate.ts` + DAO-стаб-строки: строки, не прошедшие предикат, не
  входят ни в count, ни в sum/avg/min/max.
- **FF-3 (два юзера → разные ответы, AC-2):** live-DB (`fitness:db`): User A (полный
  грант) и User B (суженный) → `visibleCount`/агрегат/`draftContext` строго различны,
  B ⊆ A; chat-level: два identity через реальные routes → разные тексты.
- **FF-4 (honest refusal, AC-3/AC-5/FR-3):** zero-visibility → `draftContext` содержит
  `ASSISTANT_ANALYST_NO_VISIBLE_DATA_MESSAGE`-семантику, НЕ числовые факты о невидимых
  записях, НЕ утверждение о существовании записи, НЕ «данных в системе нет».
- **FF-5 (honest-503 регресс, AC-6):** нет LLM-ключа → 503 `LLM_UNAVAILABLE` +
  `ASSISTANT_LLM_UNAVAILABLE_MESSAGE_*`, НЕ `INTERNAL`/сырой exception (регресс
  существующего T-0573/T-0607 пути — переиспользует `assistant-llm-unavailable.test.ts`
  harness).
- **FF-6 (bounded, NF-5):** новый агрегат остаётся в пределах `scanLimit`/
  `numericFieldLimit`; grep-guard: нет нового безлимитного SELECT/скана в
  `registry-digest-dao.ts`.
- **FF-7 (анти-кейс, AC-8):** `anti-case-lock.sh` зелёный, baseline не растёт — новый
  код не вносит кейс-литералов (числовое поле берётся из схемы, не хардкодится).
- **FF-8 (жаргон, AC-9):** `assistant-llm-message-jargon.sh` (+ `--self-test`) зелёный
  для FR-5-константы — расширить self-test планка новой константой.
- **FF-9 (аддитивность сигнатур, AC-11):** grep/typecheck по diff — существующие
  экспорты `HandlerResult/AnalystPorts/LlmPort/HandlerContext` не изменены.
- **FF-10 (шов T-0586, AC-12):** diff не трогает `src/runtime/agent-dispatch/**`.
- **FF-11 (сборка/тесты, AC-10):** `npm test`, `npm run build`, `npm run fitness:db`
  зелёные.

## §5 — План LIVE_PROOF (D-064, tester после мержа)

Стенд `100.121.76.86:3000`, DeepSeek подключён (приёмка W1). Браузером, не curl
(шаги 2-4). Учесть P0-баг учёток (T-0583): **логин строго email-вида** до мержа
T-0628 — при создании юзеров через UI использовать email как логин.

1. **Подготовка (API или UI — не предмет доказательства):** тенант с ≥1 реестром,
   ≥2 записями, у записей — **числовое поле** (сумма/amount-подобное, заведённое как
   тип «Число» в конструкторе). User A — грант, покрывающий весь реестр (или
   default-open). User B — грант, суженный так, что видит **строго подмножество**
   (например 1 из 2 записей). User C — без единого READ-гранта.
2. **User A** в чате браузером: «сколько записей в разделе X и на какую сумму» →
   ответ показывает число = ПОЛНОЕ множество A и сумму по видимому A-подмножеству.
3. **User B** тот же дословный вопрос, новый тред → число/сумма = ТОЛЬКО суженное
   B-подмножество, строго меньше A; примеры/суммы не содержат данных из записи без
   гранта.
4. **User C** любой вопрос о данных → FR-5-формулировка «в вашей зоне видимости данных
   по этому вопросу нет», НЕ числа, НЕ техошибка, НЕ тот же ответ, что A/B.
5. (Если стенд позволяет — временно испортить LLM-ключ) любой юзер → FR-4-текст «не
   подключён рабочий LLM-ключ…», НЕ INTERNAL/500 без текста в треде. Восстановить ключ.
6. Скриншоты/консоль браузера обоих тредов приложить (не пересказ).

**Обход UI (curl/API-напрямую для шагов 2-4) = P0-находка.** Настройка гранта в
шаге 1 — через API/UI как удобнее.

## §7 — Runtime / deploy-таргет

Сервер (GT-4): live-DB fitness (`fitness:db`) и LIVE_PROOF идут на стенде
`100.121.76.86:3000` с подключённым DeepSeek. Внешний ресурс (стенд + LLM-ключ) уже
