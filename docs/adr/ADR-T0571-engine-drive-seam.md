# ADR T-0571 — Шов approve→Flowable (BUG-014): базовый шаг завершает движковый user-task по ИДЕНТИЧНОСТИ инстанса, не по ТЭЛ-литералу ключа

- **Date:** 2026-07-02
- **Task:** T-0571 [W1/шов] BUG-014 — «Действие в инбоксе РЕАЛЬНО завершает Flowable user-task для GENERIC-процесса».
- **Предшественники:** T-0440/T-0443/T-0456 (engine-drive построен), T-0442 (redesign, abandoned), T-0522 (idempotent reconcile — landed, живьём НЕ закрывает BUG-014).

## 1. Контекст — код есть, правды нет (C↔L)

Живая приёмка «Закупки» 2026-07-01/02: пользователь жмёт «Согласовать» для GENERIC-процесса → продукт отвечает **200-ok** → user-task в Flowable **не завершается** → кейс докручен обходом через admin-REST (= P0 по D-064: обход = приёмка не пройдена).

Код-грунтованная причина (проверено построчно в worktree 2026-07-02, все три звена подтверждены):

1. **Корень (process-projection.ts:865).** `listInstanceInboxTasks` при фолде БАЗОВОЙ (`process.started`) задачи ЛЮБОГО процесса безусловно проставляет `taskDefKey: "task-approve"` — ТЭЛ-литерал (комментарий рядом это признаёт: «base process.started rows always map to the primary approve BPMN task»), без чтения из движка/BPMN, без привязки к `procKey`. Задачи `process.next_task` (строка 898) УЖЕ читают истинный `task_def_key` из payload — хардкод только на базовом шаге.
2. **Проводник (inbox.ts:1660).** `const approvedTaskDefKey = task.taskDefKey;` тянет этот литерал в reconcile.
3. **Отказ (process-projection.ts:1198–1209).** `reconcileInstanceEngineDrive` в post-approve режиме ищет активную задачу движка по `t.taskDefinitionKey === args.approvedTaskDefKey`. Для generic-процесса первый узел назван автором иначе (не `"task-approve"`) → `.find()` НИКОГДА не матчит. Поскольку `tasksResult.tasks.length > 0` (задача РЕАЛЬНО есть, просто с другим ключом), ранний выход `length === 0` не срабатывает → поллинг крутится до `pollTimeoutMs` (10с) → `engineTaskId === null` → **`completeUserTask` не вызван ни разу** → возврат `{ ok:true, ended:false, completed:false }` — тихо, без исключения, неотличимо от «завершать было нечего».
4. **Проглатывание (inbox.ts:1662, 1688).** reconcile запущен как `void (async…)()`; результат не влияет на HTTP-ответ — approve всегда 200. Это и есть ложный 200 (AC-7 — главное зло).

**Второй канал (inbox.ts:1654 / server.ts:481–494):** весь engine-drive обёрнут в `if (writeDepsFlowable)`, а клиент собирается только при наличии БД-пула И `FLOWABLE_REST_APP_ADMIN_PASSWORD`. Отсутствие клиента = approve работает чисто-аудитно, тоже 200-без-эффекта, но это ЛЕГИТИМНАЯ конфигурация (демо/офлайн), а не сбой — её нельзя схлопывать в тот же тихий 200, что и сбой (NF-3).

**T-0522 reconcile-on-read** (inbox.ts:1013–1034) страхует ПОТЕРЮ ГОНКИ, но не СТРУКТУРНОЕ несовпадение ключа: повтор с тем же обречённым `approvedTaskDefKey` так же не матчит. Он тоже завязан на ключ и потому тоже требует фикса (см. §3.2).

## 2. Решение

### 2.1 Источник истины для базового шага — идентичность инстанса, не литерал ключа

**Принцип: у базового `process.started`-шага целевой движковый user-task определяется НЕ по совпадению строкового ключа, а по тому, что это АКТИВНЫЙ user-task ДАННОГО инстанса.** Движок — источник правды о том, какая задача сейчас ждёт (Option A: inbox мирроит движок, а не диктует ему ключ).

Механически (за BUILD, здесь — контракт поведения): в `reconcileInstanceEngineDrive`, когда шаг помечен как БАЗОВЫЙ (см. §2.2 — сигнал «resolve-by-instance», а не буквальный ключ), матчинг активной задачи движка перестаёт быть `find(t => t.taskDefinitionKey === literal)` и становится «взять активный user-task инстанса» — тот же `getActiveUserTasks(instanceId)`, что уже вызывается, но без фильтра по обречённому литералу. `engineTaskId` и (для последующего reconcile/дедупа) РЕАЛЬНЫЙ `taskDefinitionKey` берутся из найденной задачи движка. Поллинг сохраняется — но выходит по «появилась активная задача инстанса», а не по «появилась задача С ЭТИМ ключом».

**Контракт при >1 активной user-task на момент базового действия (обязателен, D-064 честность):** базовый `process.started` в модели событий представляет РОВНО ОДИН ожидающий человеческий шаг (проекция эмитит один waiting-task на `process.started`; развилки/AND-split приходят как `process.next_task` с уже истинным ключом — это НЕ базовый шаг). Значит на момент базового approve движок нормально имеет РОВНО одну активную user-task. Контракт:
- **0 активных user-tasks** после поллинга → это НЕ «нечего завершать молча», а один из двух наблюдаемых исходов: (а) инстанс уже завершён (idempotent-повтор — легитимно, `ok:true, completed:false, alreadyEnded`), проверяется `isInstanceEnded`; (б) движок недоступен/пуст по ошибке → `ok:false` (NF-1). Различение — по `isInstanceEnded`/коду порта, не по «length===0 ⇒ тихо».
- **ровно 1** → это целевая задача (типовой путь).
- **>1** активных user-tasks у базового шага → **структурная аномалия** (базовый шаг не должен видеть параллельную вилку до своего завершения). Контракт: НЕ угадывать «первую», а вернуть explicit `ok:false, code:"AMBIGUOUS_ACTIVE_TASK", stage:"poll"` → пользователь видит ошибку (NF-1), а не молчаливо-неверное завершение произвольного токена. Это редчайший край; честный отказ дешевле неверного завершения чужого шага.

Итог: базовый шаг завершает ТУ задачу, что реально ждёт в движке у этого инстанса — воспроизводимо для процесса с любыми именами узлов (FR-3, AC-1/AC-4).

### 2.2 Судьба ТЭЛ-литерала `task-approve` — снять с НЕСУЩЕГО пути, не деТЭЛизировать роли (граница с T-0575)

- В `listInstanceInboxTasks` базовый шаг перестаёт нести `taskDefKey: "task-approve"` как ПРЕДИКАТ МАТЧИНГА. Вместо литерала базовая строка несёт **сигнал «резолвить задачу по инстансу»** (напр. `taskDefKey: null`/отдельный флаг `resolveByInstance: true` — точная форма за BUILD, критерий: reconcile для базового шага НЕ сравнивает движковые задачи с литералом `"task-approve"`). `InstanceInboxTask.taskDefKey` — public-поверхность (см. §5): менять на `string | null` можно только additive-совместимо.
- **Что ОСТАЁТСЯ (граница с T-0575, стартует после мержа T-0571):** `APPROVER_ROLE="role-approver"`, `APPROVE_STEP`, `APPROVE_TASK_NAME`, `SOGLASOVANIE_SLUG`, чтение `candidateGroups` (BUG-015/016/017) — НЕ трогаются. T-0571 снимает литерал ТОЛЬКО с пути завершения движковой задачи (несущий путь BUG-014). Отображаемые дефолты роли/имени для UI могут оставаться дефолтами — они не участвуют в матчинге движка. **Шов зафиксирован: T-0571 = «правильную задачу завершить»; T-0575 = «правильную роль/набор/переменные».**
- **NF-4 (анти-кейс):** фикс НЕ вводит новых кейс-строк — он УБИРАЕТ литерал с несущего пути. Наоборот: `resolveByInstance` — процесс-агностичный сигнал, не строка кейса.

### 2.3 Ошибка/недоступность движка НЕ глотается — синхронный честный статус на несущем пути

**Решение: post-approve завершение движковой задачи для базового шага становится СИНХРОННЫМ по отношению к HTTP-ответу — approve отвечает 200 ТОЛЬКО когда движковый шаг реально завершён (или легитимный idempotent-повтор), иначе — не-2xx с типизированным кодом.** Обоснование выбора «синхронно vs async-с-видимым-состоянием»:

- Сегодняшнее зло (AC-7) — ЛОЖНЫЙ 200 из fire-and-forget `void`. Соразмерное лечение — снять fire-and-forget с ПУТИ ЗАВЕРШЕНИЯ (completeUserTask базового шага), а не строить очередь состояний (это O6, вне скоупа). Завершение задачи детерминировано и быстрое (poll до появления активной задачи инстанса + один `completeUserTask`); ждать его в запросе дёшево и даёт честный статус.
- **Async оставляем ТОЛЬКО для последующего reconcile-fan-out** (§3, surface next_task после завершения) — эта часть может быть eventually-consistent (ADR-T0432 §4 уже это приняла: следующая задача появляется async, страхуется reconcile-on-read). Разделяем: ЗАВЕРШЕНИЕ базового шага (несущее, синхронно, честный статус) ≠ ПОЯВЛЕНИЕ следующего шага (async, самоисцеляется на read).

**Контракт ответа approve (движок сконфигурирован — `writeDepsFlowable` присутствует):**

| Ситуация | HTTP | тело |
|---|---|---|
| Базовая задача найдена в движке и завершена | 200 | `{ instanceId, status:"done", action:"approve", outcome, engine:"completed" }` |
| Idempotent-повтор: инстанс уже завершён этим шагом (задача уже не активна, `isInstanceEnded` или NOT_FOUND на complete) | 200 | `{ …, engine:"already" }` (NF-2: легитимное завершённое состояние) |
| Движок недоступен / HTTP-ошибка (`getActiveUserTasks`/`completeUserTask`/`isInstanceEnded` → `ok:false`) | **502** | `{ code:"ENGINE_DRIVE_FAILED", stage, engineCode }` |
| Активная задача инстанса не найдена, при этом инстанс НЕ завершён (структурный сбой BUG-014) | **502** | `{ code:"ENGINE_TASK_NOT_FOUND", stage:"poll" }` |
| >1 активной user-task у базового шага (§2.1) | **502** | `{ code:"AMBIGUOUS_ACTIVE_TASK", stage:"poll" }` |

**Контракт при движке НЕ сконфигурированном (`writeDepsFlowable` отсутствует, NF-3):** approve отвечает 200 с `{ …, engine:"not_configured" }` — существующий audit-only режим СОХРАНЯЕТСЯ, но становится ЯВНЫМ полем ответа (наблюдаемо ≠ тихий 200 сбоя). Различение «не настроен» vs «настроен-но-упал» = разные значения поля `engine` + разный HTTP-код (200 vs 502). На живом стенде движок настроен → путь §2.1 обязан работать (AC-1..AC-5).

`applyStepResult` (запись результата шага в сущность, `task.approved`-событие) выполняется в СВОЕЙ tx ДО завершения движка и НЕ откатывается при 502 — продуктовое решение зафиксировано (человек решил «согласовать»), но продвижение движка не удалось: ответ 502 честно говорит «ваше решение записано, но шаг в движке не завершён — повторите/эскалируйте». (Альтернатива — откатывать `task.approved` при engine-fail — отвергнута в §6: решение человека не должно теряться из-за движкового сбоя; reconcile-on-read + повтор approve дожмут завершение идемпотентно.)

### 2.4 Идемпотентность (AC-8, не регрессировать T-0522)

Свойства T-0522 сохраняются дословно:
- Повтор завершения уже завершённой задачи: `completeUserTask` → NOT_FOUND трактуется как idempotent-success (текущая логика 1213–1214), путь §2.3 → `engine:"already"`, 200. Дублей событий нет.
- Reconcile-on-read (`completeEngineTask:false`) остаётся ЧИСТЫМ зеркалом — НИКОГДА не завершает задачу; синхронный путь §2.3 живёт только на post-approve (`completeEngineTask:true`). On-read fan-out next_task дедуплится по defKey (существующий `alreadyProjectedDefKeys`, 1259–1276) — не трогаем.
- `instance.ended` эмитится один раз (`isInstanceEndedProjected` guard 1232) — не трогаем.

### 2.5 Совместимость: ТЭЛ-процесс продолжает работать

Для канонического ТЭЛ реальный `taskDefinitionKey` базового узла В ДВИЖКЕ и есть `"task-approve"` — резолв-по-инстансу вернёт РОВНО его же `engineTaskId`. Поведение эквивалентно старому для ТЭЛ (тот же токен завершён), но БЕЗ зависимости от совпадения строки. Frozen ТЭЛ-джорнеи (`e2e/tel-linear.e2e.ts`, `e2e/journeys/tel-linear.journey.ts`, `tel-gateway-routing.journey.ts`) обязаны остаться зелёными — это FF-4.

## 3. Отвергнутые альтернативы

| Опция | Почему нет |
|---|---|
| **B1. «Переименовать литерал» / параметризовать `task-approve` по procKey** | Лечит симптом «Закупок», но остаётся матчинг-по-строке: любой следующий процесс с иным именем узла снова упадёт. Не устраняет класс дефекта (structural key-mismatch), лишь сдвигает границу. |
| **B2. Читать `taskDefinitionKey` базового узла из BPMN-модели при старте и класть в `process.started` payload** | Дублирует парсинг BPMN в проекцию (второй источник правды о ключе → тот же дрейф «две машины», что Option B в ADR-T0432 отвергла). Движок УЖЕ знает активную задачу — читать её из движка проще и не может разойтись с токеном. Соразмерность: лишний парсер vs один уже-делаемый вызов `getActiveUserTasks`. |
| **B3. Оставить fire-and-forget, лечить только матчинг** | Матчинг починится, но ложный 200 при недоступности/сбое движка останется (AC-7 не закрыт). Главное зло — не несовпадение ключа само по себе, а то, что сбой невидим. |
| **B4. Полностью синхронный весь reconcile (ждать и появления next_task в ответе)** | Связывает latency approve с появлением следующей задачи (до 10с поллинга + доступность движка на fan-out). ADR-T0432 §4 уже приняла eventual-consistency следующего шага. Синхронизируем ТОЛЬКО завершение (несущее), не fan-out. |
| **B5. Durable outbox-очередь для post-approve reconcile** | Это O6 (вне скоупа спеки §6). Не требуется для детерминизма §2.3: завершение синхронно, fan-out самоисцеляется reconcile-on-read. Очередь — отдельный рефактор, если BUILD докажет гоночную деградацию отдельно от структурной. |
| **B6. Откатывать `task.approved` при engine-fail (атомарно решение+движок)** | Теряет решение человека при транзиентном сбое движка; следующий повтор approve не найдёт waiting-task (он «done» в проекции) → тупик. Idempotent-повтор поверх сохранённого `task.approved` + честный 502 надёжнее (§2.3). |

## 5. Совместимость public-поверхности

Меняется `InstanceInboxTask.taskDefKey` (экспортируемый тип, `process-projection.ts`). Импортёры (Grep `task.taskDefKey` / `.taskDefKey`):
- `src/http/inbox.ts:1660` — `approvedTaskDefKey = task.taskDefKey` (несущий; адаптируется к сигналу resolveByInstance — это и есть фикс).
- `src/http/process-projection.ts` — `listInstanceInboxTasks` (write), `reconcileInstanceEngineDrive`/`reconcileInboxEngineDriveOnRead` дедуп по `.taskDefKey` (1265), `reconcileInstanceTimers` (1005).
- Тесты: `src/__tests__/inbox-engine-drive.test.ts` (мокает форму задачи).

**Контракт совместимости:** `taskDefKey` расширяется до `string | null` (или добавляется `resolveByInstance?: boolean` при сохранении `taskDefKey?`). Изменение ADDITIVE: `process.next_task`-строки и все дедуп-читатели (`.taskDefKey` в Set) продолжают получать строку для не-базовых шагов; базовый шаг несёт сигнал-резолва. НИ ОДИН существующий консюмер не должен получить behavior-change для не-базовых задач. Frozen/regression покрытие — FF-4/FF-5.

Модель событий (`process.started`, `task.approved`, `process.next_task`, `instance.ended`) НЕ меняется — миграции БД нет (ADR-T0432 §4.1 п.1: additive-only сохранён).
