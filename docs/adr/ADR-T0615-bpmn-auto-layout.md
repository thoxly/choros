## 1. Решение

### 1.1. Где генерить раскладку — вариант A (клиент), первичный

Раскладку (diagram-interchange, DI) генерим НА КЛИЕНТЕ, при открытии определения в модельере,
ДО `importXML`. Обоснование выбора A над B:

- **A чинит ВСЕ существующие определения без миграции данных.** Проблема — не в новых
  определениях, а в уже лежащих в `choros.process_definition.bpmn_xml` без DI (seed / API /
  emit ИИ). Клиентский фикс на пути открытия покрывает их ВСЕ сразу, включая боевой процесс
  закупок волны 1, без единого UPDATE в БД.
- **B (серверная генерация DI при сохранении) НЕ чинит уже сохранённые** — нужен ещё
  одноразовый бэкфилл, а сам бэкенд сейчас не умеет раскладку: `src/core/bpmn-deploy-normalizer.ts`
  — чистые строковые трансформы, bpmn-moddle на сервере НЕТ. Добавить его = новая рантайм-
  зависимость в бэкенд + миграция данных. Непропорционально для гейта «показать диаграмму».
- A локализован в единственной точке рендера (`bpmn-modeler-wrapper.jsx`), зависимость —
  клиентская, риск ограничен модельером.

B оставлен follow-up'ом O1 (консистентность хранимого XML), но НЕ блокирует T-0615.

### 1.2. Чистый модуль `web/src/canvas/bpmn-ensure-layout.js`

Два экспорта, оба тестируемы в node-окружении (не требуют DOM):

```
hasDiagramInterchange(xml) → boolean
  // структурный детектор: есть ли в XML открывающий тег элемента BPMNDiagram
  // (локальное имя, ЛЮБОЙ/без namespace-префикс — префикс произволен по правилам
  // XML namespaces), за которым следует пробел, '>' или '/'. Регэксп якорён на '<',
  // так что не ловит подстроку внутри значения атрибута или текста узла.
  //   /<(?:[A-Za-z_][\w.-]*:)?BPMNDiagram(?=[\s/>])/
  // Пустой/не-строковый ввод → false.

ensureLayout(xml) → Promise<{ xml, layoutApplied }>
  // DI есть  → { xml, layoutApplied:false }  (исходный XML верно, авторская раскладка)
  // DI нет   → laidOut = await layoutProcess(xml); { xml:laidOut, layoutApplied:true }
  // провал layoutProcess       → throw Error('auto-layout failed: <cause>')
  // layoutProcess дал НЕ-DI XML → throw Error('auto-layout produced no diagram interchange')
  // не-строка/пусто            → throw Error('ensureLayout: xml must be a non-empty string')
```

`layoutProcess` — экспорт `bpmn-auto-layout@1.3.0` (bpmn-io), чистый bpmn-moddle-трансформ:
парсит BPMN, вычисляет координаты, сериализует обратно с `<bpmndi:BPMNDiagram>`. Async, без DOM
(проверено живьём в node: DI-less вход → выход с `BPMNDiagram`/`BPMNShape`/`Bounds`).

### 1.3. Вклинивание в `bpmn-modeler-wrapper.jsx`

`useEffect` (mount-once) заменяет `modeler.importXML(xmlToLoad).then(...)` на:

```
ensureLayout(xmlToLoad)
  .then((prepared) => modeler.importXML(prepared.xml))
  .then(() => { /* существующий post-import: zoom fit, exec-markers, keyboard, onReady */ })
  .catch((err) => {
    console.error(...);
    if (typeof onError === 'function') {
      const isLayoutFailure = /auto-layout/i.test(err?.message || '');
      onError(isLayoutFailure
        ? `Не удалось построить схему автоматически: ${…}`   // F4 честная деградация
        : `Не удалось открыть диаграмму: ${…}`);             // прежний реджект importXML (T-0484)
    }
  });
```

Единая промис-цепочка: провал `ensureLayout` (авто-раскладка) И реджект `importXML` попадают
в ОДИН `.catch`, различаются по тексту ошибки, оба поверхностны пользователю через `onError`.
Пустой канвас без объяснения невозможен. Существующий контракт T-0484 (`.catch`→`onError`)
сохранён дословно.

### 1.4. Закон границы D-064

Детект DI — структурный (наличие элемента `BPMNDiagram`), НЕ по имени процесса/тенанта/роли.
Ни одного кейс-литерала (`purchaseApproval`, `acceptance-demo`, `role-approver`, `telLinear` …)
в `src`/`web/src`. `anti-case-lock.sh` остаётся на baseline (aggregate 24=24). Механизм —
универсальный примитив: «любое определение без раскладки рисуется», а не «конкретный процесс чинится».

## 2. Отвергнутые альтернативы

1. **Вариант B (серверная генерация DI при сохранении/публикации) как первичный** — отвергнут:
   не чинит уже сохранённые определения без бэкфилла; требует bpmn-moddle в бэкенде (сейчас
   чистые строковые трансформы) — новая рантайм-зависимость + миграция данных ради «показать схему».
   Оставлен follow-up O1.
2. **Всегда прогонять авто-раскладку (и для XML с DI)** — отвергнут: перетёр бы авторскую
   раскладку (координаты, которые пользователь расставил осознанно) на автоматическую сетку.
   `ensureLayout` НЕ трогает XML с DI (layoutApplied=false, байт-в-байт).
3. **Ловить реджект importXML и только тогда раскладывать (retry-after-fail)** — отвергнут в
   пользу проактивного детекта: retry-путь мутнее (нужно точно распознать именно «no diagram»
   среди прочих ошибок парсинга), дважды инициализирует импорт, и не даёт чистого места для
   честной деградации. Структурный предикат `hasDiagramInterchange` до импорта — детерминирован.
4. **Правка встроенного bpmnlint / bpmn-js для отрисовки без DI** — отвергнут: bpmn-js по
   архитектуре рендерит DI; «нарисовать без координат» = переписать рендерер. Авто-раскладка —
   штатный инструмент bpmn-io ровно для этого.

## 3. Follow-up

- **O1** — серверная генерация DI при сохранении/публикации (вариант B) + одноразовый бэкфилл
  уже сохранённых определений без DI (консистентность хранимого XML).
- **O2** — под-процессы/группы/аннотации/message flow/2-й участник коллаборации авто-раскладкой
  bpmn-io не раскрываются (свёрнуто/пропущены) — при таких определениях раскладка частичная,
  канвас рисуется, но не идеален; отдельная задача при появлении таких определений.

## 4. Fitness-функции

Полный список FF-1..FF-6 + traceability AC↔FF — в контракте `docs/adr/T-0615.adr.contract.json`.
Ключевые: FF-1/FF-2 (unit ensure-layout: DI-less→layoutApplied+DI на выходе / DI→байт-в-байт),

.catch→onError), FF-6 (anti-case-lock.sh на baseline — D-064).

## 5. Эскалация

Не требуется. Изменение локально (клиентский модельер), не трогает деньги/секреты/необратимое/
границу фаундера. Новая зависимость — client-only, от bpmn-io (тот же вендор, что bpmn-js),
совместимые транзитивные версии (bpmn-moddle@^10, min-dash@^5 — как у bpmn-js@17). Поведение
определений с DI не меняется. Риск ограничен: провал авто-раскладки деградирует честным баннером,
а не пустым канвасом.
