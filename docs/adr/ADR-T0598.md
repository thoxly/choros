# ADR-T0598 — «Первые шаги» на Обзоре + честный пустой инбокс

Статус: ready. Источник: `docs/ux-loop-report-2026-07-02.md` находки №1/№7.

## Контекст

Отчёт design-steward установил, что «Обзор» приземляет нового владельца на
4 плитки старой ИА, ни одна из которых не ведёт к тому, ради чего он пришёл:
вставить LLM-ключ и запустить ассистента. Отдельно — пустой инбокс честно
объясняет пустоту, но не даёт следующего шага. Оба фикса объединены в один T
(петля №1+№7), потому что оба про один и тот же критический путь «владелец
сам поднял ассистента и увидел первую задачу».

## Решение 1 — полоса «Первые шаги» (находка №1)

### Паттерн

Сверено через `ToolSearch`→`mcp__ux-patterns__get_pattern`:
- `patterns/advanced/wizard` — «Use for onboarding... with dependencies».
  Каноничная анатомия («Step indicator», «Step panel», «Back/Next»,
  «Review step», «Save and resume») ПОЛНОСТЬЮ не подходит буквально — у нас
  нет последовательного gate (шаг 2 не требует прохождения шага 1), нет
  Review-экрана, нет отдельного save/resume state (состояние целиком
  производно от живых данных тенанта). Берём из паттерна только применимую
  часть: «Step indicator» (визуальный чек done/not-done на каждом шаге) +
  «is most useful for onboarding» use-case. Это чек-лист-вариант паттерна —
  шаги независимы, каждый — прямая ссылка, не форма с внутренней навигацией.
- `patterns/user-feedback/empty-states` (first-use variant: «message +
  primary action + secondary recovery path») — информирует тон каждого шага
  как мини-empty-state («здесь ничего нет, вот что сделать»).

**Отклонённая альтернатива:** полноценный `Wizard`-компонент с
back/next/review (буквальная реализация паттерна). Отклонено — рамки задачи
явно требуют «non-blocking stepper (не модал, не туториал-оверлей)», а
владелец должен иметь возможность пропустить/выполнить шаги в любом порядке
через обычную навигацию приложения (перейти в /apps напрямую, не через
полосу) — жёсткий wizard-gate противоречил бы этому и создал бы
пользователя-в-тюрьме-визарда, которого явно не хочет рамка задачи.

### Источники сигналов — почему НЕ новый API

Три обязательных шага кормятся строго существующими READ-эндпоинтами:

1. **Приложение** — `GET /api/applications`. Экран УЖЕ вызывает этот эндпоинт
   для счётчика плитки «Конструктор» (`apps` state, `load()` в
   `screen-overview.jsx:156`). Шаг переиспользует ТО ЖЕ значение — не второй
   фетч, просто вторая точка чтения того же `apps` state.
2. **LLM-ключ** — `GET /api/agents` + `resolveAssistantBinding(agents)`.
   Эта чистая функция уже существует и экспортирована в
   `screen-llm-connections.jsx:176-184` именно для того, чтобы найти
   агента-ассистента тенанта (`agent_type==='assistant'`) и достать его
   текущую `llm_connection_id`. Переиспользуем ИМПОРТОМ — не копируем логику
   во второй раз (единственный источник истины про то, как выглядит
   «ассистент подключён»). Существенное открытие в ходе разведки: `GET
   /api/agents` защищён только `withAuth` (`src/http/agents-list.ts:277`),
   БЕЗ капабилити `llm_connection:configure`, которую требует `GET
   /api/llm-connections` (`src/http/llm-connections.ts:186` — 403 для
   рядового сотрудника). Значит шаг «Подключите ключ» может честно
   показать свой статус (done/not-done) ЛЮБОМУ авторизованному пользователю
   тенанта, не только админу — READ дешевле, чем WRITE-капабилити,
   специфичная про конфигурацию.
3. **Ассистент** — `GET /api/assistant/threads`. Тот же список, что рендерит
   `screen-assistant.jsx`; `ThreadRow`/проекция `fetchThreads` уже включает
   `message_count` на каждый тред (используется списком тредов в самом
   ассистенте для сортировки/бейджей) — шаг просто ищет `threads.some(t =>
   t.message_count > 0)`, без дополнительного парсинга.
4. **[опционально] Права** — `GET /api/rights/tenant-state` (T-0572,
   READ-эндпоинт, уже отдаёт `can_manage` по авторитету вызывающего).

Ни один из четырёх не требует нового эндпоинта или изменения существующего —
рамка задачи «кормить шаги живыми состояниями из УЖЕ существующих API»
соблюдена буквально, включая явное указание рамки для шага (б) («статус из
/api/llm-connections ИЛИ /api/agents») — выбран `/api/agents`, так как он не
гейтится capability и уже несёт готовую чистую функцию резолюции.

### Деградация и скрытие

Каждый чек — best-effort, зеркалит существующий `fetchCount()` в этом же
файле (тот же паттерн деградации, что три текущих счётчика плиток): любой
сбой → `null`/`false` без падения экрана, шаг остаётся «без чека», ссылка
рабочая. Полоса скрывается целиком ТОЛЬКО когда все три обязательных сигнала
подтверждённо `true` — не по ошибке, не по dismiss-клику. Отклонена
localStorage-альтернатива (черновик отчёта её допускал) — авто-скрытие по
факту готовности данных проще, не создаёт «закрыл и забыл, где искать» риска,
и честно реагирует, если состояние тенанта регрессирует (например,
единственное приложение было удалено — тогда шаг 1 внезапно `false`, полоса
корректно появляется снова, отражая реальность, а не кэшированное
«когда-то было готово»).

### Опциональный 4-й шаг — почему не входит в критерий скрытия

Шаг «Настроить права» показывается только когда `can_manage:true` реально
пришло (иначе структурно отсутствует — паттерн T-0572 ADR §2.5: «формы
рендерятся ТОЛЬКО при can_manage:true», тот же принцип переносится на
видимость шага чек-листа). Раз он опционален и не всем видим, он НЕ входит в
условие «все шаги true → скрыть полосу» — иначе тенант без прав на
управление ролями никогда не увидел бы полосу скрытой (шаг 4 у него навсегда
отсутствует, но не «false» — юридически не участвует).

## Решение 2 — честный CTA на пустом инбоксе (находка №7)

**Решение:** `EmptyState` на вкладке «Все» без активного `exec`-фильтра при
реальном `counts.all === 0` получает `action` — кнопку «Открыть процессы» →
`navigate('/processes')`. Путь подтверждён существующим `<Route
path="/processes" element={<ProcessesScreen />} />` (`shell.jsx:1161`) — не
изобретается.

**Различение контекстов:** вкладки `mine`/`pool`/`esc` или активный
`exec`-фильтр на вкладке «Все» получают ДРУГОЙ (уточняющий) текст без
`action` — иначе «Открыть процессы» на пустой вкладке «Мне» (при том что
задачи ЕСТЬ на других вкладках) было бы вводящим в заблуждение обещанием
«вот откуда взять задачи», хотя реальная причина пустоты — просто фильтр.
Рамка задачи явно требует этого различения (принцип honest degradation,
приложенный к empty-state семантике — тот же дух, что и деградация сигналов
в Решении 1).

**Отклонённая альтернатива:** одна и та же CTA-кнопка на ЛЮБОЙ пустой
вкладке/фильтре. Отклонено — противоречит honest-messaging принципу
проекта (принципы §6: явные состояния, не обманывающие пользователя о
причине пустоты) и самому тексту отчёта, который явно предостерегает от
«CTA-обмана» на нефильтрованных пустых вкладках.

## Границы

Никаких изменений в `src/http/**` (сервер), `components.jsx` (kit-контракты),
`screen-llm-connections.jsx` (кроме использования его существующего экспорта
`resolveAssistantBinding` — импорт, не правка файла).

## FF-UX гейты (проверены вручную при написании)

- **g4** (state-primitives): новые async-ветки шагов используют
  `LoadingState`/условный рендер, не hand-rolled `<div>Загрузка…</div>` без
  role.
- **g5** (jargon denylist): весь новый видимый текст — чистый продуктовый
  русский («Создайте приложение», «Подключите ключ LLM», «Спросите
  ассистента», «Открыть процессы»), без T-id/dev-терминов.
- **g6** (no-new-hardcode): все новые стили — исключительно `--chs-*` токены,
  переиспользуются существующие паттерны инлайн-стилей этого же файла
  (`tileStyle`-соседние константы).

## Эскалация

Нет. Оба решения используют существующие эндпоинты/паттерны/токены проекта;
ни одно не требует founder-решения (не деньги/секреты/необратимое — оба
фикса reversible git revert).
