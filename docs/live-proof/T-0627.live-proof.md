## Ход приёмки

### 1. Баннер виден сразу при заходе на draft-приложение
Создал приложение «LP T0627 Баннер» (`POST /api/applications` → 201,
`tier:"draft"`). Перешёл на `/app-records/:id` (экран записей) — баннер
виден СРАЗУ, без дополнительных действий:

> «Приложение в черновике: пока видны только ваши записи. Опубликуйте, чтобы
> команда работала на общей доске.» + кнопка **«Опубликовать»**

Баннер — реальный `role="status"` элемент (проверено программно, не только
визуально). Скрин: `01-banner-before-publish.png`.

### 2. Клик «Опубликовать» → диалог подтверждения → факт публикации
Клик на кнопку «Опубликовать» открыл диалог **«Опубликовать решение · LP
T0627 Баннер»** — явно показывает границу («приложение… будет
опубликовано», «Затронуто: 1 элемент решения», обратимость поясняется
текстом). Это переиспользованный `PublishSolutionDialog`
(тот же компонент, что и в `/apps`, как и описано в pr-handoff). Скрин:
`02-publish-confirm-dialog.png`.

Клик «Опубликовать (1)» → `POST /api/applications/:id/publish-solution` →
**200**, тело: `{"all_ok":true,"results":[{"kind":"application","ok":true,...}]}`.
Диалог сменился на «Результат публикации: Все части решения опубликованы» с
зелёной галочкой.

### 3. Баннер исчезает ЖИВЬЁМ — без перезагрузки страницы
Закрыл диалог результата («Готово») — **НИКАКОГО `page.reload()` не было**,
весь сценарий (создание → баннер → клик «Опубликовать» → подтверждение →
закрытие результата → проверка) выполнен в ОДНОЙ навигации браузерной
вкладки. Проверил `document.querySelectorAll('[role="status"]')` СРАЗУ
после закрытия диалога результата — draft-баннер **отсутствует** (остались
только: честный empty-state «У приложения пока нет полей» — не относится к
draft-статусу, и всплывающий toast «Решение опубликовано. Опубликовано 1 из
1.» — тоже не draft-баннер). Явная проверка текста:
`document.body.innerText.includes('Приложение в черновике')` → **false**.
Кнопка «Опубликовать» — 0 штук (пропала вместе с баннером). Скрин:
`03-banner-gone-after-publish-no-reload.png` — визуально видно: та же
страница, тот же URL, синяя кнопка «Опубликовать» пропала из toolbar,
жёлтой полосы баннера нет вообще, только зелёный toast снизу справа.

**До/после — идентичный кадр той же страницы**, разница только в отсутствии
жёлтой полосы и кнопки — прямое визуальное доказательство «живого» исчезновения.

## Обходы (P0-проверка)
**Обходов не было.** Создание приложения, просмотр баннера, клик
«Опубликовать», подтверждение в диалоге, закрытие результата — всё сделано
кликами через реальный UI. Сетевой перехват использовался только для чтения
статус-кода/тела уже отправленного публикационного запроса (подтверждение
факта, не подмена действия). Проверка «баннер пропал» сделана programmatic
DOM-запросом к УЖЕ ОТРЕНДЕРЕННОЙ разметке той же страницы после реального
клика — не через отдельный API-запрос к серверу.

## FINDINGS
Отклонений от заявленного поведения не найдено. Диалог подтверждения
публикации (`PublishSolutionDialog`) даёт дополнительную, не заявленную в
задании, но полезную честность («Затронуто: 1 элемент решения», явная
формулировка необратимости) — качественный побочный эффект переиспользования
существующего компонента, не самостоятельная находка T-0627.

## FRICTION (для будущих приёмок)
- `role="status"` на странице может быть НЕ ЕДИНСТВЕННЫМ (empty-state
  «У приложения пока нет полей» тоже использует эту роль) — при проверке
  «баннер пропал» нельзя полагаться на простой `count() === 0`, нужно точно
  фильтровать по ТЕКСТУ баннера (`includes('Приложение в черновике')`), иначе
  можно спутать с другими honest-state элементами на той же роли.
- Диалог публикации имеет два последовательных шага (подтверждение → «Готово»
  на результате) — тест должен явно закрыть оба, иначе первый скриншот
  «после» на самом деле снят поверх ещё открытого диалога результата (не
  баг, а двухшаговый UX-паттерн, знать для будущих тестов).
