## Детали доказательств

### #1 — Авто-ключ из «Название» (GREEN)
В редакторе набора полей (`/app-schema/...`) поле-строка ведёт столбцом **НАЗВАНИЕ** (не КЛЮЧ), под строкой — подпись «ключ сгенерируется из названия · изменить».
Ввёл в НАЗВАНИЕ только «Сумма аванса» (ключ не трогал). Живой DOM-превью: **`ключ: summa_avansa`** — snake_case транслит (Сумма→summa, аванса→avansa, `_` разделитель). Название обязательно, ключ ручного ввода не требует.
Сохранил набор (кнопка «Создать набор») — успех БЕЗ единого ручного ключа. Набор: «Основной набор» · `osnovnoy-nabor` · 2 поля · V1.
**БД (ground truth):**
```json
"summa_avansa": {"type": "string", "title": "Сумма аванса"}
```

### #2 — Коллизия (GREEN)
Второе поле с идентичным «Сумма аванса». БД после сохранения:
```json
{"properties": {
   "summa_avansa":   {"type":"string","title":"Сумма аванса"},
   "summa_avansa_2": {"type":"string","title":"Сумма аванса"}},
 "x-field-order": ["summa_avansa","summa_avansa_2"]}
```
Ключи уникальны в наборе (`summa_avansa` / `summa_avansa_2`); titles-дубликаты разрешены (уникальность требуется только для ключей = property names).
**Нюанс UI (косметика):** живой превью ДО сохранения показывал `summa_avansa_2` на ОБЕИХ строках (резолвер уникальности в превью суффиксует обе). Но сохранённые ключи корректны (`summa_avansa` + `_2`), и edit-view после reload показывает их правильно. Данные верны; расходится только превью незасохранённого состояния.

### #3 — Правимость + snake_case валидация (GREEN)
«изменить» у ключа раскрывает ручной ввод «КЛЮЧ ПОЛЯ» со значением `summa_avansa` + подсказка «Латинские буквы/цифры/подчёркивание. **Стабилен после сохранения — записи ссылаются на него.**»
Ввёл невалидный `Invalid Key 123` → save → поле красное + инлайн-ошибка **«Ключ: латинская буква/подчёркивание, затем буквы/цифры/_ (1–64)»**. Save заблокирован. (грамматика `FIELD_KEY_RE = /^[A-Za-z_][A-Za-z0-9_]{0,63}$/`.)

### #4 — ИНВАРИАНТ переименования (GREEN — критический пункт)
Существующий сохранённый набор (V1, ключи `summa_avansa`/`summa_avansa_2`). Переименовал поле-1 «Сумма аванса» → «Авансовый платёж итого», сохранил (PUT /api/registry-defs/... → 200).
**БД после переименования+save (record_schema_version=2):**
```json
"summa_avansa":   {"type":"string","title":"Авансовый платёж итого"},   ← КЛЮЧ СТАБИЛЕН, сменился title
"summa_avansa_2": {"type":"string","title":"Сумма аванса"}
```
Ключ `summa_avansa` НЕ пере-derived — записи, ссылающиеся на него, не осиротеют. Подтверждено кодом: `withAutoFieldKeys` заполняет ТОЛЬКО пустые ключи; загруженное из БД поле несёт `key` (parseRecordSchema), поэтому не пере-генерится.
**Robust-проверка:** повторно открыл V2 и нажал save БЕЗ изменений (несмотря на вводящий-в-заблуждение превью — см. нюанс ниже) → БД остался `summa_avansa` (версия не сдвинулась). Инвариант держится даже под «опасным» re-save.

**Нюанс UI (косметика, follow-up):** при загрузке существующего набора `parseRecordSchema` НЕ ставит `keyTouched:true` на строку. Из-за этого превью-подпись показывает ключ как «живой из названия»: после reload поле-1 отображает `ключ: avansovyy_platezh_itogo`, ХОТЯ реальный persisted-ключ = `summa_avansa`. Это ВИЗУАЛЬНАЯ рассинхронизация — на save ключ НЕ перезаписывается (доказано двумя запросами БД). Рекомендация follow-up: parseRecordSchema должен ставить `keyTouched:true` для загруженных полей, чтобы превью показывал настоящий ключ.

### #5 — Пустое «Название» (GREEN для основного create-flow)
Добавил НОВОЕ пустое поле (ключ пуст + название пусто) → save → БЛОК: поле красное + инлайн **«Название: Укажите название поля»** (validateField: при пустом ключе и пустом title требует имя).
**Граничный нюанс:** у СУЩЕСТВУЮЩЕГО поля (ключ уже есть) очистка названия НЕ блокируется — сохранилось как `{"type":"string"}` без `title` (V3). Причина в коде: гард `errors.title` срабатывает только при пустом ключе (`key.length===0`). Для поля с уже-ключом название не обязательно (ключ — идентичность, уже существует). Основной кейс фикса («добавь поле, введя только название») закрыт: новое поле без имени заблокировано.
