### Может ли UI собрать дефектную модель мышью?

`web/src/canvas/timer-deadline-panel.jsx` (панель свойств таймера) и `web/src/canvas/bpmn-palette-provider.js`
проверены (`grep cancelActivity|interrupting` — **0 совпадений** в обоих файлах). Панель даёт настроить
`deadlineKind`/`deadline`/`escalateTo`, но **нигде не даёт установить `cancelActivity`/прерывающий-непрерывающий
режим**. Палитра создаёт `IntermediateCatchEvent` с `TimerEventDefinition`, который bpmn-js авто-конвертирует

задавая его (де-факто BPMN-дефолт = **interrupting=true**). Ручная попытка через canvas (палитра + drag) в
браузере это подтвердила: нет affordance ни в палитре, ни в context-pad, ни в панели свойств для явного
non-interrupting таймера.

**НАХОДКА (P0, дизайн-ограничение, зафиксировано в спеке T-0612 заранее, не новое): дефектный паттерн
физически нельзя собрать мышью в этом продукте — он мог возникнуть ТОЛЬКО через hand-authored/imported XML.**

реально пользуется сам продукт — не обход, а штатная функция модельера), как и предусматривала инструкция
задачи для этого случая.

### P1-находка (UX, не блокирует вердикт Уровня 1): текст `message` обрезается до нечитаемости

Список violations рендерится через `formatJsonReadable(v)` (`web/src/lib/format.js:279-291`) —
это ОБЩИЙ fallback-форматтер для "любого объекта": `JSON.stringify(value).slice(0, 120) + '…'`. Функция НЕ
знает, что у `LintViolation` есть предназначенное для человека поле `.message` — вместо показа этого текста
она сериализует весь объект и обрезает после первых 120 символов. Проверено численно:
`JSON.stringify({type,elementId,elementKind,message:'…'})` — префикс ДО ключа `"message"` уже занимает
**108 символов** при лимите 120 → из настоящего человекочитаемого текста (который специально написан подробным,
actionable, с конкретным fix hint) выживает **максимум ~12 символов**, независимо от того, какой конкретно
lint-check сработал. Это системный баг рендеринга баннера нарушений (используется КАЖДЫМ проверочным гейтом
публикации — не специфично для T-0612), не специфичный дефект самого нового чека. Пользователь видит факт
блокировки и `elementId`, но не видит ни причину, ни fix hint, пока не откроет DevTools/Network.

### Сценарий B (дополнительный, живьём обнаруженный нюанс — таймер УЖЕ сработал, обе ветки открыты)

Использован инстанс `29bb45ad-7858-11f1-abdf-aaa9cc4b0546` (запущен раньше, таймер успел сработать —
одновременно открыты и `task-fin`, и `task-esc`). Дозавершил **только `task-fin`** (`level2c-late-approval.mjs`):

```
activityId gw-fin-converge  10:02:58.261Z → 10:02:58.261Z   (сработал)
activityId sf-converge-end  10:02:58.261Z → 10:02:58.261Z   (сработал)
```

Токен от `task-fin` дошёл до `gw-fin-converge` и дальше — НО historic-process-instance после этого:
`endTime: null`, `runtime GET → 200` (инстанс всё ещё жив), `runtime/tasks?processInstanceId=...` показывает
**1 активную задачу**: `task-esc` (`Эскалация: финдир молчит`), исполнение — отдельный (`parentId` = корневой),
конкурентный execution, не связанный с завершившейся веткой `task-fin`.

Дозавершил и `task-esc` (`level2d-complete-escalation-too.mjs`) — **только после этого**:
```
endTime: 2026-07-05T10:04:53.865Z, endActivityId: end-order-placed
runtime GET → 404
```

**Интерпретация (важно, не регрессия фикса):** ADR-T0612 §2 D2 явно описывает сценарий «таймер сработал →
task-esc завершается пулом владельцев → gw-fin-converge срабатывает → 'Заказ размещён'. task-fin остаётся
открытой задачей в инбоксе независимо (out of scope, продуктовый вопрос на будущее)» — т.е. ADR предполагает,
что именно ЗАВЕРШЕНИЕ ПОСЛЕДНЕЙ ветки закрывает ИНСТАНС, а недозавершённая (или уже неактуальная) ветка может
остаться как отдельная, безвредная висящая ЗАДАЧА в инбоксе — но НЕ как незавершённый ИНСТАНС. Живой прогон
подтверждает это буквально: `exclusiveGateway` в Flowable корректно не ждёт синхронизации (сработал сразу на
первом пришедшем токене — ЛОГИКА сходимости верна и работает), НО экземпляр процесса как таковой (Flowable
`ProcessInstance`) не помечается завершённым, пока ВСЕ параллельные execution-и (включая `task-esc`,
порождённый non-interrupting boundary-таймером как отдельная конкурентная ветвь) не завершатся или не будут
отменены — независимо от того, что один из двух токенов уже достиг `endEvent`. Итог: если approve приходит
ПОСЛЕ срабатывания таймера, инстанс требует завершения ОБЕИХ пользовательских задач (в любом порядке), не
только одной, чтобы перестать быть "живым" в Flowable (хотя каждая по отдельности НЕ является зомби в смысле
исходного бага — обе задачи видны, доступны, не потеряны, и `act_hi_procinst.end_time` в итоге корректно
проставляется, когда обе завершены).

**Это НЕ регрессия дефекта T-0612 (зомби навсегда, end_time НИКОГДА не проставляется) — оба сценария живьём
довели `end_time_` до НЕ-NULL значения.** Но это уточнение к гарантии ADR: «эскалация — просто напоминание,
исходный процесс не блокируется» верно для СЛУЧАЯ, когда финдир согласовывает ДО срабатывания таймера
(sub-8-секундное завершение). Если он согласовывает ПОСЛЕ (когда эскалация уже открыта), инстанс остаётся
технически «в работе» до тех пор, пока владелец/менеджер тоже не обработает эскалационную задачу — что ADR
называет открытым продуктовым вопросом («out of scope for this fix to adjudicate»), но живой прогон показывает,
что это не просто «task-fin виснет в инбоксе», а что САМ ИНСТАНС остаётся неоконченным до этого момента.
Рекомендация: пометить как FOLLOW-UP находку (не P0 — не воспроизводит исходный баг; скорее P2/уточнение
документации ADR §2 D2, чтобы явно предупреждать «инстанс закрывается только когда закрыты ОБЕ пользовательские
задачи, если обе оказались одновременно открыты»).

## Обходы, использованные в самом доказательстве (=находки, не маскирую)

- **Старт инстанса шёл через `POST /api/processes/start`, вызванный `fetch()` внутри аутентифицированной
  страницы (`page.evaluate`), а не через кнопку в UI.** Причина: T-0374 сознательно убрал generic-лаунчер
  «Запустить процесс» — по продуктовому решению процессы стартуют только из бизнес-триггеров
  (on_create/record_action/launcher/auto), которых для голого тестового процесса нет и не может быть без
  собранного приложения. Это ТОЧНО тот же вызов, что сделал бы триггер приложения — не curl-обход в обычном
  смысле (тот же браузер, тот же Bearer-токен сессии, тот же реальный HTTP-роут продукта), но это НЕ клик по
  реальной кнопке продукта, поэтому фиксирую как обход. Соответствует явной оговорке задачи: «если старт
  закупки требует собранного приложения — минимально докажи хотя бы деплой+старт+завершение исправленной
  модели голым инстансом, если продукт это даёт» — продукт это дал через POST /api/processes/start.
- Пароль e-owner на стенде был сброшен через Keycloak admin REST (`reset-password`, `temporary:false`) —
  предыдущий пароль из памяти (`LiveProof-0583-owner!`) больше не валиден (ротация в одной из последующих
  сессий). Новый пароль: `LiveProof-T0612-owner!` (residue, см. ниже).
- `flowable:candidateGroups` в тестовых XML-артефактах (`T-0612-liveproof-defect.bpmn20.xml`,
  `T-0612-liveproof-fixed.bpmn20.xml`) использует `tenant-owner` вместо официальных `role-manager`/`role-owner`
  (из `docs/design/T-0612-purchaseApproval-fixed.bpmn20.xml.txt`) — эти роли не существуют в Dev Silo, только в
  тенанте ООО Аксон, где живёт реальный зомби-кейс (e-owner туда доступа не имеет, отдельный tenant_id). Это
  чисто LIVE_PROOF-инфраструктурная адаптация тестового артефакта под доступный тенант, не изменение самого
  фикса (структура графа идентична официальному артефакту).

  подтверждён живьём как КОРРЕКТНОЕ поведение authz, не связанное с фиксом T-0612). Безвредный, но незакрытый
  тестовый инстанс — можно оставить как живую иллюстрацию authz-гейта или закрыть вручную при следующей уборке.
