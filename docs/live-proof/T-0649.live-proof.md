### 1. MoneyInput — «150000.5» → «150 000,50 ₽»
В форме создания записи ввёл в поле «СУММА» значение `150000.5`. Отправил
форму → `POST /api/records` → **201**, тело ответа: `"data":{"amount":150000.5,...}`
— **точное значение сохранено без округления** (не 150000, не 150001).

В списке записей колонка «СУММА» отображает **«150 000,50 ₽»** — тысячи
разделены пробелом, копейки показаны как `,50` (НЕ `,00`, НЕ округлено до
«150 001 ₽»). Открыл «Детали записи» — то же самое: «150 000,50 ₽».
Открыл «Редактировать» — поле СУММА пере-заполнилось как «150 000,5»
(сгруппированное, точное значение сохранилось при повторном открытии формы).
Скрины: `01-create-record-form-fields.png` (форма создания),
`03-list-money-kopecks-date-format.png` (список), `04-record-detail-view.png`
(детали), `05-edit-form-repopulated-correctly.png` (повторное открытие для
редактирования — видно «150 000,5» в самом инпуте).

Это подтверждает P1-фикс, явно описанный в коде
(`web/src/screens/records-form.js` `formatCellValue`, комментарий
«P1 FIX (T-0649, data-integrity bug caught live 2026-07-05): the previous
maximumFractionDigits:0 SILENTLY ROUNDED AWAY kopecks on display») —
**фикс подтверждён живьём, не только по коду.**

Ввёл в поле поиска «Ларина» → список отфильтровался до ОДНОЙ строки

записалось. `POST /api/records` тело: `"assignee":"e-larina"` (slug сотрудника,

### 3. DateInput — дд.мм.гггг в форме И в списке
В форме создания поле «СРОК» — нативный `<input type="date">` с текстовым
оверлеем дд.мм.гггг (по ADR: «keeps full native keyboard/a11y/picker semantics
… locale-independent numeric display via overlay»). Заполнил `2026-08-15`
через Playwright `fill()` (эквивалент ввода через сам date-picker) — поле
сразу показало **«15.08.2026»** (не сырой ISO `2026-08-15`).

`POST /api/records` тело: `"due_date":"2026-08-15"` (хранится в ISO, как и
задумано — только ДИСПЛЕЙ форматируется). В списке записей колонка «СРОК»
показывает **«15.08.2026»** (тот же формат). В деталях записи — тоже
«15.08.2026». В форме редактирования — пере-заполнилось как «15.08.2026»
корректно. Формат dд.мм.гггг подтверждён на ВСЕХ 3 поверхностях (форма
создания / список / детали / форма редактирования) — не только на одной.

## FINDINGS

### [P1, не в исходных 3 пунктах задания] Список и детали записи показывают person как сырой slug, не имя
И «Список записей», и «Детали записи» показывают колонку/поле «СОТРУДНИК»
как **`e-larina`** (сырой slug), а не «Е. Ларина — Финансовый директор»
(человеко-читаемое имя, которое сам PersonPicker показывает при выборе/
редактировании). Это прямо признано в коде-комментарии самой функции
(`web/src/screens/records-form.js:1270-1278`, `formatCellValue`):

> «person value is an employee id string... formatCellValue itself cannot
> resolve the id async... The display component in the list/card SHOULD
> pre-resolve the id to a name via the employees list from GET /api/org and
> pass the name in `value` if possible; otherwise the id is shown as
> fallback.»

Проверил `web/src/screens/screen-app-records.jsx` — там НЕТ вызова
`GET /api/org` и никакого pre-resolve для `type==='person'` (в отличие от
`relation`/`file`, для которых есть явные асинхронные ячейки
`RELATION_CELL_ASYNC`/`FILE_CELL_ASYNC` с реальным резолвом). Person — единственный
из трёх «резолвящихся по id» типов (relation/file/person), для которого
асинхронный резолв в списке/деталях НЕ реализован — только сырой fallback.

**Не блокер этой приёмки** (все 3 явно заказанных пункта — GREEN), но
реальный UX-долг: любой реестр с полем «Сотрудник» будет показывать
непонятные slug'и вместо имён в списке и в деталях записи, что нарушает
общий принцип «человеко-читаемо, не UUID/slug» (тот же принцип, что уже
защищён для relation/file). Стоит завести отдельную задачу на резолв person
в списке/деталях по аналогии с RELATION_CELL_ASYNC/FILE_CELL_ASYNC.

## FRICTION (для будущих приёмок)
- Модальные кнопки с одинаковым текстом («Создать», «Создать запись») часто
  дублируются на странице (фоновая кнопка-триггер + кнопка отправки формы) —
  нужно скоуп-ить локатор к `[role="dialog"]`, иначе Playwright ловит
  strict-mode violation или кликает не туда.
- `page.getByRole('button', {name pattern})` без явного `.first()`/scope может
  попасть на элемент, скрытый за оверлеем модалки — тайм-аут «intercepts
  pointer events» без явной ошибки логики.
- Дата, введённая через Playwright `fill('2026-08-15')` в `<input type="date">`
  с оверлеем — надёжный способ проверить сам оверлей, эквивалентен вводу
  через нативный picker.
