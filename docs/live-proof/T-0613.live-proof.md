задеплоены, per задание). Тенант: Dev Silo (`a0000000-0000-0000-0000-000000000001`). Вход:
уже залогинен в браузерной сессии как `t0586-admin` (владелец/админ-роль, судя по видимым
разделам «Конструктор»/«Работа»/«Наблюдаемость» и доступу к созданию приложений). Браузер:

## Вердикт: **GREEN**

Ассистент называет записи реестра, где первое поле схемы — код (ИНН), по их **имени**
(«АО Василёк», «ООО Ромашка»), НЕ по коду. Дословный ответ ассистента приведён ниже.

## Живость LLM-контура

Ответ пришёл содержательным, на русском, структурированным (нумерованный список +
предложение сохранить как отчёт) — LLM-контур живой, не заглушка и не provider-error.
Не потребовалось отдельно проверять карточки LLM-соединений — сам факт содержательного
ответа ассистента на явно data-specific вопрос это доказывает.

## Подготовка кейса (реестр с кодом ПЕРЕД именем)

На стенде НЕ нашлось уже готового популярного реестра с этой формой схемы и заполненными
записями одновременно:
- `Контрагенты` (a8000000-0000-0000-0000-000000000002, схема `{inn, kpp, name, ogrn,
  phone, contact_email, legal_address}` — inn ПЕРЕД name) — 0 записей, и создание записи
  через UI падало на не связанном с этой задачей баге валидации схемы (см. FINDINGS/P0
  ниже) — не смог использовать.
- `Внешние участники` (a5000000-0000-0000-0000-000000000002, схема `{inn, kind, note,
  display_name, contact_email}`) — создал 2 записи через UI успешно, НО это приложение
  (`Внешние справочники`, tier=draft) не публиковалось → по дизайну (FF-10, D-064
  sandbox-gate, ADR-T0607 §1.1) НЕ входит в digest ассистента ни для одной роли, включая
  владельца. Ассистент честно ответил, что раздела «Внешние участники» нет в его контексте
  данных (см. `docs/live-proof/T-0613-evidence/response-external-participants-absent.txt`
  ниже) — это НЕ дефект, это подтверждение существующего sandbox-гейта, работающего как
  спроектировано.

Создал новое приложение и реестр через UI Конструктора (позволено заданием: «найди/создай
реестр»):
- Приложение «T0613 LP Поставщики» (slug `t0613-lp-postavshiki`), Конструктор → Приложения
  → Создать приложение.
- Набор полей «Поставщики» (slug `postavshiki`), Конструктор → Приложения → «T0613 LP
  Поставщики» → Настроить поля → Новый набор полей, поля **в этом порядке**: `inn`
  (Текст, «ИНН»), `name` (Текст, «Наименование»). Порядок полей в форме и в схеме — именно
  код ПЕРЕД именем, воспроизводит форму дефекта T-0607.
- Опубликовал решение целиком (Действия → «Опубликовать решение», один клик,
  подтверждение — черновики публикуются вместе, включая набор полей V1).
- Создал 2 записи через UI («Создать запись» → заполнить форму → сабмит):
  - ИНН `7712345678`, Наименование `ООО Ромашка`
  - ИНН `7798765432`, Наименование `АО Василёк`

Перекрёстная проверка через SQL (диагностика, НЕ путь доказательства — сам вопрос
ассистенту и его ответ идут только через UI):

```
SELECT rd.display_name, rd.record_schema->'properties' AS props, r.data
FROM choros.registry_def rd
JOIN choros.record r ON r.tenant_id=rd.tenant_id AND r.registry_id=rd.id
WHERE rd.slug='postavshiki' AND rd.tenant_id='a0000000-0000-0000-0000-000000000001';

 display_name |                          props                           |                data
--------------+-----------------------------------------------------------+-----------------------------------------------
 Поставщики   | {"inn":{"type":"string","title":"ИНН"},                    | {"inn":"7712345678","name":"ООО Ромашка"}
              |  "name":{"type":"string","title":"Наименование"}}          |
 Поставщики   | (то же)                                                     | {"inn":"7798765432","name":"АО Василёк"}
```

Подтверждает: схема имеет `inn` ПЕРВЫМ ключом, `name` ВТОРЫМ — ровно форма анти-кейса,
которую фикс T-0613 должен обработать (было бы: сэмпл = ИНН; стало: сэмпл = имя).

**Обе записи названы по ИМЕНИ («АО Василёк», «ООО Ромашка»), НЕ по коду (7798765432 /
7712345678).** ИНН упомянут только как опция для дальнейшего запроса («например,
контакты, ИНН или статус») — не как замена имени в списке. Это ровно ожидаемое поведение
после фикса pickTitleFieldKey/pickSampleValue (src/core/registry-title-field.ts,
src/db/registry-digest-dao.ts): цикл прошёл по схеме, нашёл `name` (title-shaped key,
шаг 2 эвристики) и использовал его значение как сэмпл, а не первый scalar по
data-key-order (которым в этом случае была бы `inn`).

## Соответствие критериям приёмки

- **FR-1/FR-2/FR-3 (эвристика резолвит title-field и pickSampleValue пробует его
  первым)**: подтверждено живьём — ответ называет записи по `name`, не по `inn`,
  несмотря на то что `inn` идёт первым в порядке ключей схемы и данных.
- Задание («примеры записей названы по имени, НЕ голым ИНН/кодом»): **выполнено
  дословно** — конкретно проверенный сценарий с явной формой «код-перед-именем».

## FINDINGS (не относится к T-0613/T-0616, зафиксировано для честности LIVE_PROOF)

- **P0-находка, не в скоупе этой задачи**: создание записи в реестре «Контрагенты»
  (a8000000-0000-0000-0000-000000000002, схема содержит `contact_email` с
  `format: "email"`) через UI («Создать запись» → «Создать запись» в модале) стабильно
  возвращает ошибку `data does not conform to registry_def schema: schema validation
  error: unknown format "email" ignored in schema at path "#/properties/contact_email"`
  — воспроизведено дважды подряд, ДАЖЕ когда поле email оставлено пустым в форме. Это
  блокирует создание любых записей в этом системном реестре через UI. Не чинил (вне
  скоупа LIVE_PROOF T-0613/T-0616), но фиксирую как находку для отдельной задачи —
  вероятно связано с JSON-Schema `format` keyword validation (ajv strict-mode?) не
  учитывающим/не поддерживающим `email` формат как non-fatal warning на бэкенде, но
  фактически превращающим его в hard-reject при СОЗДАНИИ записи.
- Реестр «Внешние участники» (та же форма схемы, `inn` перед `display_name`) не мог быть
  использован для основного доказательства, т.к. его приложение «Внешние справочники»
  осталось tier=draft (система/genesis-seed приложение) — ассистент корректно НЕ видит
  черновые реестры (D-064 sandbox-gate), так что это не альтернативный путь для этого
  теста, а отдельное (правильно работающее) поведение.

## Обходы (для протокола LIVE_PROOF)

- Ни одного обхода в самом доказательстве (создание приложения/реестра/записей и вопрос
  ассистенту — всё через UI кликами/формами). SQL использован ИСКЛЮЧИТЕЛЬНО как
  перекрёстная сверка порядка полей схемы, не как замена UI-наблюдения.
- Скриншоты сделаны в ходе сессии инструментом `computer` (`save_to_disk: true`,
  claude-in-chrome MCP), но их бинарные файлы оказались недоступны для копирования в этот
  worktree (внутреннее хранилище MCP-инструмента не адресуется локальным `find` в разумных
  директориях — проверено `/private/tmp`, `~/Library`, репо-относительные пути). Ключевые
  текстовые доказательства (дословные ответы ассистента, SQL cross-check) приведены выше
  дословно вместо скриншотов; это FRICTION инструментария LIVE_PROOF-тулинга, а не пробел
  в самом доказательстве факта.
