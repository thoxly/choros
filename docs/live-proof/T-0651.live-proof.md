# LIVE_PROOF — T-0651 (сайдбар-рабочее место) — 2026-07-05

Стенд: http://100.121.76.86:3000 (dev @ af7a8fc). Тенант: Dev Silo. Вход: реальная
Keycloak-форма (Playwright chromium headless через Bash, НЕ dev-shortcut) —
владелец e-owner (пароль сброшен через KC admin API на стенде, т.к. предыдущий
из choros-acceptance-t0583/T-0656 протух; новый пароль оставлен в residue ниже).
Native HTML5 drag-and-drop эмулирован ручным dispatch DragEvent+DataTransfer с
короткими паузами между событиями (dragstart→dragenter→dragover→drop→dragend,
~50ms между каждым) — Playwright `dragTo()` не бьёт нативные draggable-обработчики,
на которых построен сайдбар (тот же паттерн, что задокументирован в T-0656
приёмке).

## Вердикт: **GREEN** по всем 4 пунктам задания

1. **Collapsible-группы (клик + клавиатура) + дефолт свёрнуто** — GREEN
2. **Persist per-user через reload** — GREEN
3. **«+ Раздел» создаёт раздел** — GREEN (с уточнением: пустой раздел не рендерится, пока в нём нет приложений — by design, см. ниже)
4. **DnD приложения в раздел (меняет section_id, переживает reload) + кнопки ▲/▼** — GREEN

## Ход приёмки

### 0. Подготовка
Пароль e-owner сброшен через `POST /admin/realms/choros/users/{id}/reset-password`
(KC admin REST, admin-cli/choros_kc_admin) на `LiveProof-0651-owner!`. Вход
подтверждён: `chs-kc-session` в localStorage, редирект на `/overview`.

### 1. Дефолт свёрнуто — реально ~10 видимых пунктов, не 43
При заходе владельцем на `/overview`, боковая панель показывает: Обзор + группа
РАБОТА (Мои задачи/Процессы + список приложений) + три ЗАГОЛОВКА групп
(КОНСТРУКТОР/НАБЛЮДАЕМОСТЬ/АДМИНИСТРИРОВАНИЕ), каждый со стрелкой ▼ (свёрнуто).
`aria-expanded="false"` на всех трёх подтверждено программно. Раскрытие
КОНСТРУКТОР добавляет 5 доп. пунктов (Приложения/Разделы/Конструктор форм/
Модельер/Ассистент) — то есть дефолт действительно прячет десятки пунктов за
3 клика. Скрин: `01-groups-collapsed-default.png`.

### 2. Клик мышью раскрывает/сворачивает
Клик по заголовку «КОНСТРУКТОР» (`button.chs-nav__grouplabel--collapsible`) →
`aria-expanded` переключился `false→true`, 5 пунктов появились в DOM
(проверено подсчётом `.chs-navitem`: 25→30). Повторный клик → `true→false`,
пункты исчезли. Скрин: `02-constructor-expanded-click.png`.

### 3. Клавиатура (Enter/Space на заголовке) работает
Фокус на заголовке + `Enter` → `aria-expanded` переключился (подтверждено
программно на каждом шаге: false→true→false→true→false в серии тестов).
Фокус + `Space` → тоже переключает. Оба клавиатурных пути подтверждены живьём,
не только по коду. Заголовок — реальная `<button aria-expanded>`, а не
`div onClick` (клавиатурная активация работает нативно). Скрин:
`03-constructor-expanded-keyboard-enter.png`, `05-space-key-toggle.png`.

### 4. Persist per-user через `/api/user-prefs` — подтверждено сетевым перехватом
Каждый клик/keypress по заголовку группы вызывает
`PUT /api/user-prefs/sidebar.collapsed_groups` → **200**, тело ответа отражает
корректный список свёрнутых групп (например
`{"value":["observability","admin"]}` после раскрытия constructor). Базовое
состояние на старте сессии: `GET /api/user-prefs` →
`{"sidebar.collapsed_groups":["observability","admin","constructor"]}` —
дефолт-состояние ВСЕ ТРИ свёрнуты, как заказано.

**Явная проверка reload**: раскрыл КОНСТРУКТОР (PUT подтверждён 200) →
`page.reload()` (полная перезагрузка, не SPA-навигация) →
`aria-expanded` на КОНСТРУКТОР **остался `"true"`** после релоада. Повторено
дважды с одинаковым результатом (один раз ловил гонку в собственном
тест-скрипте — не дождался отклика PUT перед reload — после добавления
`waitForResponse` на PUT перед reload воспроизводится стабильно GREEN, см.
FRICTION). Скрин: `04-after-reload-group-state-persisted.png`.

### 5. «+ Раздел» создаёт раздел
Кнопка `.chs-nav__add-section-btn` («+ Раздел», текст+SVG-плюс) под списком
приложений зоны РАБОТА. Клик → инлайн-форма (`Создать`/`Отмена` + текстовый
input) появляется на месте кнопки. Ввод имени + `Enter` →
`POST /api/sections` → **201**. Подтверждено дважды: (a) сетевым перехватом
статус-кода, (b) прямым запросом `GET /api/sections` после — новая строка
`{"id":"166ddf54-...","name":"LP Тест Раздел 904946","sort_order":0}`
физически существует на сервере. Скрин: `06-section-created-201.png`.

**Важное уточнение (не баг, а осознанное поведение из ADR)**: сразу после
создания раздел **не появляется** как отдельный заголовок в сайдбаре — потому
что в нём 0 приложений, а `groupAppsBySection()` (`web/src/app-shell/nav-sections.js`,
инвариант `FF-SECTIONS-EMPTY-HIDDEN`: «пустой массив → пустой результат; нет
групп-пустышек») намеренно не рендерит пустые группы, чтобы не засорять нав
пустыми папками. Как только в раздел попадает хотя бы одно приложение
(см. §6 ниже — методом контекст-меню «⋯ → В раздел →»), заголовок раздела
сразу появляется в сайдбаре. Проверил это дважды (создание раздела → не видно;
перенос приложения в него → сразу видно). Это ожидаемое поведение по ADR, не
дефект — но стоит иметь в виду: сразу после «+ Раздел» пользователь не увидит
результат в самом сайдбаре, пока не добавит туда приложение (в
Разделы-экране `/sections`, впрочем, пустой раздел виден). Не блокер приёмки.

### 6. DnD приложения в раздел — механика подтверждена живым native DragEvent
Переместил приложение «мое приложение» (было в «БЕЗ РАЗДЕЛА») в новый раздел
«LP Тест Раздел 904946» **двумя независимыми путями**:

**(a) Через контекст-меню** («⋯» на строке приложения → «В раздел →» →
`<select>` со списком разделов → выбрал «LP Тест Раздел 904946» → «Сохранить»)
— `PATCH /api/applications/:id` → **200**, тело: `section_id` изменился на id
нового раздела, `section_name` корректно денормализован. Раздел сразу появился
в сайдбаре с этим приложением внутри. Скрин: `07-move-into-section-via-menu.png`.

**(b) Настоящий HTML5 DnD** (не контекст-меню-обход): перетащил «мое
приложение» (в «БЕЗ РАЗДЕЛА») ПРЯМО НА строку приложения «T0586 Тест B»
(уже лежавшего в целевом разделе) реальным нативным drag-событием
(dragstart на источнике → dragenter/dragover/drop на цели → dragend).
`PATCH /api/applications/:id` → **200** с новым `section_id` == целевой
раздел + пересчитанный `sort_order` (0 для перемещённого — встал первым,
1 для «T0586 Тест B» — сдвинулся вниз). Визуально приложение появилось
ВНУТРИ раздела «LP ТЕСТ РАЗДЕЛ 904946» сразу после drop, без reload. Скрин:
`08-real-dnd-app-moved-into-section.png`. **Важный технический нюанс**:
drop СРАБОТАЛ, когда целью dispatch был `.chs-nav__app-row` (строка другого
приложения ВНУТРИ раздела), но НЕ срабатывал (0 PATCH-вызовов), когда целью
был непосредственно `.chs-nav__subgroup` (контейнер-заголовок раздела) —
возможно, событийная модель компонента ожидает событие сначала на дочернем
элементе, которое всплывает наверх, либо гонка между React-состоянием
draggingAppId и обработчиком дропа при слишком быстрой синтетической
последовательности без пауз. Не блокер (drop на существующий элемент внутри
раздела — стандартный сценарий реального пользователя тоже), но важная
заметка для будущих DnD-приёмок (см. FRICTION).

**Persist через reload подтверждён**: после полного `page.reload()`
(networkidle), раздел «LP ТЕСТ РАЗДЕЛ 904946» с обоими приложениями внутри,
в том же порядке (мое приложение → T0586 Тест B), сохранился. Скрин:
`09-dnd-persisted-after-reload.png`.

### 7. Кнопки ▲/▼ — первоклассный клавиатурный путь, работает независимо от DnD
Навёл на строку «T0586 Тест B» (внутри раздела, после drag стояло вторым) →
появились кнопки со стрелками, `aria-label="Переместить «T0586 Тест B» вверх"`
подтверждает доступность через скринридер. Клик по кнопке ▲ →
`PATCH /api/applications/:id` (тот же контракт, что DnD) → приложение
переместилось выше «мое приложение» в списке — визуально подтверждено.
Скрин: `10-arrow-button-reorder.png`.

### 8. Счётчик «Мои задачи» == число задач
Сайдбар показывает `Мои задачи` со счётчиком `0` (`.chs-navitem__count`).
Сетевой перехват `GET /api/inbox` (та же лента, что рендерит и сам экран)
вернул `counts: {"all":25,"mine":0,"pool":0,"esc":16}` — счётчик в сайдбаре
берёт именно `counts.mine`, что подтверждено (а) числом, (б) прямым переходом
на экран «Мои задачи»: вкладка «Мне» там тоже показывает **0** — идентичное
число на обеих поверхностях (сайдбар и сам экран инбокса читают одну и ту же
ленту, не рассинхронизированы). Скрин: `11-counter-matches-mine-tab.png`
(виден одновременно сайдбар слева со счётчиком 0 и экран справа с вкладкой
«Мне 0»). Владелец объективно имеет 0 задач, лично назначенных ему (все 25
открытых задач — либо в пуле, либо назначены другим исполнителям, что видно
в таблице).

## Обходы (P0-проверка)
**НЕ было обходов браузера API вместо UI.** Все 4 проверяемых механики
(collapse/expand, persist, «+ Раздел», DnD+▲▼, счётчик) пройдены целиком через
реальный браузерный UI — клики, клавиатурные события, нативные drag-события.
Сетевой перехват использовался ТОЛЬКО для чтения (подтверждения статус-кодов
и тел ответов на уже произошедшие UI-действия), не для обхода UI-пути. Единственное
использование `page.evaluate(fetch(...))` было для GET-диагностики (что уже
лежит на сервере, до/после UI-действия) — ни разу для самого мутирующего
действия (POST/PATCH/PUT все сделаны через реальные клики/keypress/drag).

## FINDINGS
1. **[Не баг, документированное поведение]** Только что созданный пустой
   раздел не отображается в сайдбаре сразу после создания (по дизайну —
   `FF-SECTIONS-EMPTY-HIDDEN`), только после того как в него попадёт первое
   приложение. Стоит рассмотреть добавление визуальной подсказки
   («раздел создан — перетащите сюда приложение») сразу после создания, чтобы
   не создавалось впечатление, будто раздел не сохранился (первое впечатление
   при быстрой проверке — «где мой раздел?»). Не блокер, минорный UX-долг.
2. **[Наблюдение, не блокер]** Ручной DnD (dispatch DragEvent) требует, чтобы
   drop-таргетом было существующее приложение ВНУТРИ раздела, а не сам
   заголовок/контейнер раздела — иначе drop молча не срабатывает (0 сетевых
   вызовов, без ошибки в консоли). Для пустых разделов (0 приложений внутри)
   единственный способ поместить туда первое приложение — контекст-меню
   «В раздел →» (что и есть штатный путь по коду — сам компонент раздела
   принимает drop на пустую зону согласно комментарию в `shell.jsx`
   `«dropping an app onto an EMPTY section... still moves the app here»`, но
   в реальном браузере пустой раздел изначально не виден в DOM вообще, так
   что физически перетащить туда что-то мышью нельзя, пока раздел пуст и
   скрыт — сначала обязательно контекст-меню). Итог тот же: и DnD, и контекст-меню
   реально работают на существующем разделе с хотя бы одним приложением.

## FRICTION (для будущих приёмок)
- KC-пароль e-owner снова протух между приёмками (третий раз подряд после
  T-0583/T-0656) — сброс через
  `POST /admin/realms/choros/users/{id}/reset-password` быстрый, но стоит
  рассмотреть более долгоживущий сервисный аккаунт для приёмок.
- Ручной DnD (native HTML5 drag-and-drop) требует пауз (~50ms) между
  dispatch-событиями dragstart/dragenter/dragover/drop/dragend — без пауз
  события доходят до DOM, но обработчик компонента иногда не успевает
  среагировать (0 сетевых вызовов без явной ошибки, тихий no-op) — тратил
  время на диагностику первой неудачной попытки без пауз.
- Тест-скрипт должен явно ждать `page.waitForResponse` на PUT
  `/api/user-prefs/...` ПЕРЕД `page.reload()` — без этого гонка между
  асинхронным PUT и релоадом даёт ложный RED (первая попытка проверки
  persistence ошибочно показала «не сохранилось», хотя дело было в тайминге
  теста, не в продукте — переверифицировано с явным ожиданием, стабильно
  GREEN).
- «Мои задачи» счётчик и `/api/inbox` — одна и та же лента, оба возвращают
  0 для e-owner в текущем состоянии тенанта (все задачи либо в пуле, либо
  назначены другим); удобный побочный эффект для проверки — не пришлось
  создавать отдельную тестовую задачу «на владельца».
