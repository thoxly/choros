# LIVE_PROOF — T-0656 (DnD-конструктор форм) — 2026-07-05

Стенд: http://100.121.76.86:3000 (dev @ d591610). Тенант: Dev Silo. Вход: реальная
Keycloak-форма (Playwright, НЕ dev-shortcut) — владелец e-owner (пароль сброшен
через KC admin API на стенде, т.к. предыдущий из choros-acceptance-t0583 протух;
новый пароль оставлен в residue ниже). Браузер: Playwright chromium headless
через Node-скрипты (Bash), HTML5 native drag-and-drop эмулировался ручным
dispatch DragEvent+DataTransfer (стандартный приём — Playwright `dragTo` не бьёт
нативные `draggable`/`onDragStart`/`onDragOver`/`onDrop`, на которых построен
канвас).

## Вердикт

- **Человеко-канвас (механика DnD/fullscreen/клавиатура): GREEN** — сама механика
  реально удобна и работает так, как заказал фаундер.
- **Человеко-канвас (СОХРАНЕНИЕ и цельный контур «собрал→увидел в проде»): RED (P0)**
  — собранную раскладку невозможно сохранить ни на один реальный процесс из
  самого конструктора, и даже если она сохранена (в обход, ниже), ни сам
  конструктор при переоткрытии, ни реальный экран задачи инбокса её не
  показывают. Контур не замкнут.
- **Машинный шов (эндпоинт `POST /api/forms/document-ops`): GREEN** механически
  (200/version+1/409/400 все корректны, доказано на реальном тенанте) —
  **но замкнут на тот же разорванный контур**, так что результат агента тоже
  никому не виден в проде.

Итог по заказу фаундера «удобно и человеку, и машине»: **машина и человек оба
получили качественно построенный инструмент, но ни один из них не может
довести результат до реального экрана исполнителя**. Это P0 не T-0656-фичи
как таковой (сама DnD-механика — качественный, кропотливо доведённый UX), а
структурного шва данных, который T-0656 унаследовал, не проверив предположение
«путь сохранения существует и на что-то реальное указывает».

### 5. P0 — Сохранение из DnD-конструктора структурно не работает
`FormDesigner.jsx` не имеет НИ ОДНОГО UI-поля для ввода `processKey`/`stepKey`.
`doc.step` нигде не устанавливается кодом компонента (grep подтвердил — только
AI-draft путь из ассистента передаёт `step`, обычный человеческий путь
приложение→набор-полей — никогда). Значит `persistLayout()` ВСЕГДА шлёт
`process_key: doc.step?.processKey || 'record'` → **захардкоженный fallback
`process_key="record", form_key="record-form"`**, к которому не привязано НИ
ОДНОГО реального процесса ни в одном тенанте (проверено в БД: `form_binding`
для Dev Silo — 0 строк вообще на момент начала приёмки). Сохранение падает
`409 WRONG_FLOOR` («Form layout cannot be validated against a live record_schema
for process "record" (no registry binding)») — **при ЛЮБОМ выборе
приложения/набора-полей**, потому что тело сохранения игнорирует этот выбор.

Это воспроизведено дословно (см. `54` — нет, там уже обходной путь; прямой
POST body из перехвата сети приложен в FINDINGS ниже).

### 6. Обход: сохранение через «Привязка полей (запасное)» (FormBuilder)
Чтобы всё же проверить сохранение+рендер+машинный шов, сохранил форму через
вторую вкладку («запасное» — degenerate fallback по своему собственному
комментарию в коде), указав РЕАЛЬНЫЙ processKey `telLinear` (единственный в
Dev Silo с explicit `target_registry_slug='soglasovanie'` в
`process_app_binding`, иначе схема не резолвится и правки тоже 409). Результат:
`POST /api/forms/binding` → **201, version:1** (`11-formbuilder-fallback-save-201.png`).

**Это уже обход человеко-пути** (не сама DnD-фича) — FormBuilder не пишет
`layout`, только `fields[]`. Т.е. эта форма и DnD-конструктор — **два разных,
несовместимых формата хранения одной и той же строки `form_binding`.**

### 7. Ещё один разрыв: FormDesigner не читает существующий layout
Даже когда в БД уже лежит `form_binding.layout` (наполнил вручную UPDATE через
`choros_migrator` — секция с 2 полями `decision`+`comment`, как честная
реконструкция «что сохранил бы DnD-конструктор, если бы мог достать до
реального processKey»), переоткрытие `/forms` с тем же приложение+набор-полей
показывает **все 5 полей плоским списком, без секции** — `buildDefaultDocument`
в `useEffect` (строка 613-623 `FormDesigner.jsx`) **безусловно перестраивает
документ с нуля** из схемы набора полей при каждом выборе, никогда не
запрашивая существующий `layout` с сервера (нет ни одного `GET
/api/forms/binding` вызова из `FormDesigner.jsx` — grep подтвердил, только
`fetch('/api/forms/binding', {method:'POST'...})` для сохранения). **Любая
ручная раскладка (секции/колонки/порядок/удаление лишних полей) теряется
безвозвратно при следующем открытии формы.**

### 8. Машинный шов — `POST /api/forms/document-ops` (реальный тенант, реальная строка)
На той же строке (`telLinear`/`liveproof-t0656-step`, после ручного наполнения
`layout`), через тот же Bearer-токен залогиненной сессии владельца (не обход
UI — это ровно машинный путь, который и есть фича):

| Тест | Op | Результат |
|---|---|---|
| Валидная вставка | `insert` поля `approved_by` в root | **200**, `version: 1→2`, новый узел в `layout.root.children` |
| Неизвестный kind | `{kind:'teleport'}` | **400 VALIDATION** — `"unknown op kind «teleport» (allowed: insert, remove, reorder, update, move)"` |
| Висящий fieldKey | `insert` поля `totally_not_a_real_field` | **409 WRONG_FLOOR** — `"R-4: ключ ... отсутствует в живой record_schema — висящий биндинг → Floor-2"` |

Все три — честные, ожидаемые коды (не 500, не тихий no-op). БД подтверждает
`version=2` и новый узел `f-approved-machine` физически персистирован
(`SELECT ... FROM choros.form_binding` — attached below). **Механика шва
доказана живьём: GREEN.**

### 9. «Видно в UI при переоткрытии»? — НЕТ (структурный, не машинный, разрыв)
Задание требовало: «переоткрой форму в UI — новое поле видно». Проверил ОБЕ
поверхности:
- **Конструктор форм** (`/forms`, тот же экран) — не покажет (см. §7: игнорирует
  сохранённый `layout` целиком, всегда rebuild с нуля).
- **Реальный экран задачи инбокса** (`InboxTaskForm` в `screen-inbox.jsx`) —
  дергает тот же `GET /api/forms/binding?processKey=...&stepKey=...`, но
  сервер (`src/http/binding.ts` строка ~460) **возвращает только `{fields,
  version, processKey, stepKey}` — БЕЗ поля `layout` вообще**. Проверил живьём:
  GET той самой строки (у которой `fields` — от FormBuilder, `layout` — от
  ручного наполнения+machine-op) вернул `fields` (5 старых scalar-полей от
  FormBuilder), `layout` в ответе просто нет как ключа.

**Итог: ни человек через DnD-конструктор, ни агент через machine seam не могут
на этом стенде довести изменение формы до экрана, где сотрудник реально
заполняет задачу.** `layout` (общий контракт человека и агента, на котором и
строится вся история T-0656) **нигде не читается production-рендерером
задачи.** Только `FormDocumentRenderer.jsx` (live-preview ВНУТРИ самого
конструктора, для просмотра «как будет выглядеть») знает про `layout` — но и
она видит только in-memory `doc`, не персистированный сервером результат.

## FINDINGS (по значимости)

1. **[P0] FormDesigner никогда не привязывает раскладку к реальному
   processKey/stepKey.** Нет UI-поля для этого; `persistLayout()` жёстко шлёт
   `process_key:'record', form_key:'record-form'` (`web/src/forms/
   FormDesigner.jsx:1128-1129`), которых нет ни в одном тенанте → сохранение
   всегда 409 WRONG_FLOOR, при любом выбранном приложении/наборе-полей.
   Затрагивает: `web/src/forms/FormDesigner.jsx`.

2. **[P0] FormDesigner не загружает существующий `form_binding.layout` при
   открытии.** `useEffect` на `selectedDefId` (строка 613-623) безусловно
   вызывает `buildDefaultDocument(...)`, никогда не делая
   `GET /api/forms/binding`. Любая ранее сохранённая раскладка (секции,
   порядок, удалённые поля) теряется при каждом повторном открытии формы.
   Затрагивает: `web/src/forms/FormDesigner.jsx` (нет GET-эффекта вообще).

3. **[P0] Production-рендерер задачи (`InboxTaskForm`) никогда не читает
   `layout`.** `GET /api/forms/binding` (актор-путь, `src/http/binding.ts`
   ~строка 460) отдаёт только `{fields, version, processKey, stepKey}` —
   `layout` не входит в ответ. Значит ни DnD-раскладка человека, ни
   machine-seam правка агента НЕ ВИДНЫ на реальном экране, где сотрудник
   заполняет задачу — только `fields[]` (плоский FormBuilder-контракт)
   рендерится по-настоящему. Весь машинный шов T-0656 технически исправен, но
   упирается в нерабочий konturr далее по цепочке. Затрагивает:
   `src/http/binding.ts`, `web/src/screens/screen-inbox.jsx`.

4. **[P0, предсуществующий, не T-0656] `process_designer` роль не засеяна ни в
   одном тенанте, а `checkRole` в keycloak-режиме не имеет owner
   short-circuit.** Результат — сохранение формы (`POST /api/forms/binding`,
   и транзитивно весь machine seam, который делит `checkRole`) недоступно
   ВООБЩЕ НИКОМУ на стенде, включая владельца, до ручного грант́а роли.
   Код-комментарий в `src/http/binding.ts:146` признаёт это как известный
   пробел («not yet seeded in dev DB»), но датирован до перехода стенда на
   `keycloak`-режим, где смягчение до "authenticated" (только `dev`-режим)
   больше не действует. Затрагивает: `src/http/binding.ts` (`checkRole`).

5. **[Minor] FormDesigner и FormBuilder пишут несовместимые половины одной
   строки `form_binding`.** FormBuilder пишет только `fields` (оставляя
   `layout=NULL`); FormDesigner пишет только `layout` (отправляя `fields:
   undefined`, что бэкенд трактует как «нет `fields`, но раз есть `layout` —
   сохраняем `fields:[]`», см. `binding.ts:528-530`). Нет пути, где обе формы
   заполнены согласованно одним человеком через один UI без ручного вмешательства.

## Обходы (что было обходом, не самой фичей)
- Обход P0 №4 (роль `process_designer`): вручную завёл роль+role_assignment в
  БД (`choros_migrator`), см. Residue — без этого приёмка не могла бы
  проверить save/seam вообще.
- Обход P0 №1 (нет processKey в DnD): сохранение реальной формы сделано через
  «Привязка полей (запасное)» — ВТОРУЮ вкладку, другой UI-путь, не
  DnD-конструктор.
- Обход P0 №2/№5 (layout не персистится согласованно): `layout` для
  machine-seam теста наполнен вручную UPDATE через `choros_migrator`
  (реконструкция «что сохранил бы конструктор, если бы мог») — это ПРОВЕРКА
  контракта эндпоинта document-ops, не обход самого эндпоинта (эндпоинт
  вызывался честно через реальный HTTP + реальный Bearer-токен реальной
  сессии).

Все обходы документированы явно; ни один результат раздела 2-4 (человеко-DnD
механика: drop-preview/подсветка/fullscreen/клавиатура) обхода не потребовал —
это чистые наблюдения через реальные события браузера.

## FRICTION (для будущих приёмок)
- HTML5 native drag-and-drop (`draggable`+`onDragStart`/`onDragOver`/`onDrop`)
  не бьётся Playwright `dragTo()` — нужен ручной `page.evaluate` с
  dispatch(`dragstart`→`dragenter`→`dragover`→`drop`→`dragend`) и общим
  `DataTransfer`. Клик по `.chs-canvas-node` через `.first()` может попасть на
  дочернюю кнопку (▲▼⧉×) вместо самого узла — кликать по `strong`-метке текста.
- KC-пароли, заведённые в прошлых приёмках (choros-acceptance-t0583,
  poehali-w2/w3), протухают/забываются между сессиями — сброс через
  `POST /admin/realms/choros/users/{id}/reset-password` с admin-cli токеном
  работает быстро и надёжно, не требует помнить старый пароль.
- `process_designer` роль — постоянная яма для будущих form-related приёмок,
  пока FINDING #4 не закрыт: любая новая приёмка сохранения форм упрётся в
  403 первым делом.
