# T-0663 — LIVE_PROOF (реестр с полем email принимает записи)

**Дата:** 2026-07-05
**Стенд:** http://100.121.76.86:3000 (dev@ba8dba4, Dev Silo, LLM=deepseek жив)
**Метод:** реальный браузер (Chrome extension MCP), глазами пользователя, форма создания записи через UI; SQL — только перекрёстная сверка (не вместо UI).
**Вход:** сессия уже была залогинена как `t0586-admin` (owner-level).
**Блокер по пути:** контейнер приложения был не запущен в начале сессии (см. T-0648.live-proof.md §блокер) — устранено `docker compose up -d choros`, не относится к продукту.

## Вердикт: **GREEN**

Запись с email создаётся и пустой, и валидной; невалидный email честно отклоняется — валидация НЕ сломана.

---

## Важное уточнение маршрута (P0-находка методики, не бага)

Первая попытка была на приложении **«Внешние справочники»** (`external-directory`, реестр «Внешние участники», id `a5000000-0000-0000-0000-000000000002`) — оно похоже по названию на «Контрагенты», но это **другой** реестр: SQL-сверка его `record_schema` показала, что поле `contact_email` объявлено просто `{"type":"string"}` **без `format:"email"`** — там в принципе не было бага (валидатор ничего не проверяет), поэтому три сценария там прошли тривиально (пустой/валидный/НЕВАЛИДНЫЙ email — все три сохранились без ошибки, включая невалидный `not-an-email`, что для ЭТОГО реестра ожидаемо и не является дефектом — там просто нет format-ограничения).

Настоящий системный реестр из спеки T-0663 — **«Контрагенты» (`kontragenty`, is_system=true, seed-миграция `083_core_system_registries_seed.sql`)**, application_id `a8000000-0000-0000-0000-000000000001` → приложение «Системные справочники» → набор полей «Контрагенты». SQL подтвердил `record_schema.properties.contact_email = {"type":"string","title":"Email контакта","format":"email"}` — это именно то поле, где раньше падало `unknown format "email"` при ЛЮБОМ значении (даже пустом). Все три сценария ниже повторно проверены НА ЭТОМ реестре.

Это не блокер задачи, но фиксирую как находку методики: приложение навигации/имён достаточно похоже («Внешние справочники» vs «Контрагенты»), что легко протестировать не тот реестр и получить ложно-позитивный результат. Тестировщику будущих LIVE_PROOF стоит явно сверять `record_schema` через SQL/API перед тем, как считать сценарий воспроизведённым.

## Сценарии (на реестре «Контрагенты», kontragenty)

Форма создания записи: поля ИНН, КПП, Наименование*, ОГРН, Телефон, Email контакта, Юридический адрес.

### (а) Пустой email → сохраняется — **PASS**
Заполнено только обязательное «Наименование» = «ИП Пустая Почта Контрагент (T-0663 empty)», «Email контакта» оставлено пустым. Клик «Создать запись» → запись сохранена, появилась в списке с `EMAIL КОНТАКТА: —`. Раньше это падало `unknown format "email"` → 503/400 при ЛЮБОМ payload, включая пустой email — сейчас нет ошибки вообще.
SQL-сверка: `choros.record` (registry_id=`a8000000-...002`) → `{"kind":"counterparty","display_name":"ИП Пустая Почта Контрагент (T-0663 empty)"}` — поле `contact_email` в data отсутствует (не был отправлен как пустая строка либо явно опущен), запись существует.

### (б) Валидный email → сохраняется — **PASS**
Наименование = «ООО Валидный Контрагент (T-0663 valid)», Email = `valid-kontragent-t0663@example.com`. Клик «Создать запись» → сохранено, в списке `EMAIL КОНТАКТА: valid-kontragent-t0663@example.com`.
SQL-сверка: запись есть, `contact_email: "valid-kontragent-t0663@example.com"` — совпадает.

### (в) Невалидный email → честно отклоняется — **PASS**
Наименование = «ЗАО Невалидный Контрагент (T-0663 invalid)», Email = `not-an-email-kontragent` (без `@`, без домена). Клик «Создать запись» →
- Инлайн-ошибка ПОД полем: **«must match format "email"»**.
- Общая ошибка формы: **«data does not conform to registry_def schema: #/properties/contact_email/format: must match format "email"»**.
- Запись НЕ создана — счётчик записей остался 2 (не увеличился до 3), диалог не закрылся.

SQL-сверка (после закрытия диалога без сохранения): `select ... from choros.record where registry_id='a8000000-...002'` вернул РОВНО 2 строки (пустой-email + валидный-email из (а)/(б)) — невалидная запись отсутствует в БД. Валидация реально серверная, не только косметика формы.

## Обходы (=P0)
Не было. Все три сценария проверены исключительно через UI-форму создания записи (клик «Создать запись» → заполнение полей → клик «Создать запись» в диалоге). SQL использовался только ПОСЛЕ UI-действия, для перекрёстной сверки сохранённого/несохранённого состояния — никогда как замена клика.

## Residue на стенде
- В реестре «Контрагенты» (`kontragenty`) остались 2 тестовые записи: «ИП Пустая Почта Контрагент (T-0663 empty)» (пустой email) и «ООО Валидный Контрагент (T-0663 valid)» (`valid-kontragent-t0663@example.com`) — оставлены намеренно как живое доказательство фикса (безобидные демо-данные, соответствуют паттерну прошлых LIVE_PROOF-сессий). Невалидная тестовая запись НЕ была создана (отклонена валидацией) — residue нет.
- В реестре «Внешние справочники» (`external-directory`, ошибочно протестированном первым) 3 тестовые записи созданы и затем **удалены** через UI (кнопка «Удалить» + подтверждение) — реестр возвращён к исходным 2 записям («АО Василёк», «ООО Ромашка»).

## FINDINGS
1. **Не блокер, но важно для дальнейших LIVE_PROOF:** название приложения «Внешние справочники» (реестр «Внешние участники») легко перепутать с системным «Контрагенты» — оба про контрагентов/визитёров, но только «Контрагенты» несёт настоящий `format:"email"` в схеме. Возможно стоит переименовать/пометить чтобы это различие было очевиднее в навигации (вне скоупа T-0663).
2. Сообщение об ошибке при невалидном email технически честное и информативное (`must match format "email"` + путь схемы), не «503 сервис недоступен» — хороший паттерн, соответствует урокам из прошлых P0 (T-0583 email-логин 503).
