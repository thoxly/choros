# LIVE_PROOF T-0632 — report-page /render (агрегат) и /data (raw) под построчным READ-PDP

Дата: 2026-07-05. Стенд: http://100.121.76.86:3000, dev@e8c735d. Тенант: Dev Silo (`a0000000-0000-0000-0000-000000000001`). Браузер: Playwright chromium (headless), реальный Keycloak Authorization Code + PKCE через KC-форму (`/` → «Войти» → `#username`/`#password`/`#kc-login`).

## Вердикт: GREEN

Узкий record-scope актор (грант только на 1 запись из 2) видит SUM только по видимой записи (не по полному реестру) и НЕ получает данные/count скрытой записи ни на `/render`, ни на `/data`. Широкий актор (грант на обе записи) видит полную сумму/оба ряда.

## Setup

Готового report-page с агрегатом на стенде не было (`SELECT * FROM choros.report_page` — 0 строк в Dev Silo) — собран минимальный кейс тестовыми данными (application/registry/records — не механизм авторизации, а тестовые фикстуры, повторяющие форму сидов из `ci/checks/db/report-page-render-read-pdp.db.test.ts`):

- **Application** `lp-t0632-app` (`e0000001-...-a001`).
- **Registry** `lp-t0632-reg` со схемой `{amount: number}` (`e0000001-...-a002`).
- **2 записи**: record1 = `{amount: 100}` (`...a011`), record2 = `{amount: 900}` (`...a012`, «скрытая» для узкого актора).
- **Report-page Floor-1 SUM** (`lp-t0632-sum`, `...a021`, page_def = `[{registry, field_key:"amount", agg:"sum"}]`).
- **Report-page Floor-2 raw** (`lp-t0632-data`, `...a022`).
- **2 реальных актора** (KC-юзер + choros.employee + choros.role + choros.role_assignment + choros.grant — та же форма грантов, что производит `/rights` UI):
  - **lp-t0632-narrow**: application-read грант на приложение + record-read грант ТОЛЬКО на record1 (100).
  - **lp-t0632-wide**: application-read грант на приложение + record-read гранты на ОБЕ записи (100+900).

Оба — реальные KC-пользователи (`actor_type=human`), реальный логин через форму, реальный Bearer access_token из `localStorage['chs-kc-session'].accessToken`.

## Что прожито

### `/render` (Floor-1 SUM агрегат)

Прямой `fetch('/api/report-pages/{sum_page_id}/render', {Authorization: Bearer <реальный токен актора>})` из браузерной сессии — тот же запрос, что шлёт сама SPA при открытии страницы отчёта.

| Актор | HTTP | metrics[0].result (SUM) |
|---|---|---|
| lp-t0632-narrow | 200 | **100** |
| lp-t0632-wide | 200 | **1000** |

Узкий актор НИКОГДА не видит 1000 (100+900) — сумма строго меньше и равна ровно видимой записи. Соответствует ожиданию задачи буквально.

### `/data` (Floor-2 raw-row dump)

Прямой `fetch('/api/report-pages/{data_page_id}/data?registry_def_id={reg}')`.

| Актор | HTTP | records[] | total_count |
|---|---|---|---|
| lp-t0632-narrow | 200 | **[{id: ...a011, data:{amount:100}}]** — только 1 запись | **1** |
| lp-t0632-wide | 200 | **[{...a011, amount:100}, {...a012, amount:900}]** — обе записи | **2** |

Узкий актор не получает ни `data.amount:900`, ни даже намёка на существование record2 — `total_count` тоже урезан до видимого (не `SELECT COUNT(*)` по всему реестру), что и было целью LEAK A-фикса из adversary-раунда (иначе narrow увидел бы `total_count:2`, выдав факт существования скрытой записи, не раскрывая её данные).

## Обходы

Нет. Оба запроса — `/render` и `/data` — реальные HTTP GET с реальным Bearer-токеном актора, тот же путь, что использует сама SPA при отрисовке страницы отчёта. Никакая подмена результата (например, чтение из БД напрямую вместо HTTP) не производилась — только сидирование тестовых данных (реестр/записи/гранты), что является законной подготовкой сцены, а не обходом проверяемого authz-механизма.

## Соответствие ожиданию задачи

| Проверка | Ожидание | Факт |
|---|---|---|
| /render узкий | сумма только по видимым | **100** (не 1000) ✓ |
| /render широкий | полная сумма | **1000** ✓ |
| /data узкий | только видимые записи, total_count видимых | **1 запись, total_count:1** (не 2) ✓ |
| /data широкий | все записи | **2 записи, total_count:2** ✓ |
