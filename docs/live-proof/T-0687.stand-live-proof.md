## A. Task-detail дровер («Мои задачи» → задача)

### A(3) StepRef — человеко-имя шага primary, node-id demoted — GREEN
Дровер задачи без recordId («Проверить: агенту не назначена инструкция…»), DOM:
```html
<span class="chs-stepref">
  <span class="chs-stepref__name" title="legal_precheck">Шаг процесса</span>
  <span class="chs-monoid chs-monoid--chip" data-testid="technical-id">legal_precheck</span>
</span>
```
- primary = «Шаг процесса» (человеко-generic), сырой BPMN-id `legal_precheck` — DEMOTED mono-чип (не primary), доступен в `title=` и как серый бейдж.
- В строке списка сабтайтл шага тоже гуманизирован через `deriveStepLabel`: 9 строк «Проверить…» показывают «Шаг процесса», а не `legal_precheck`.

### A(2) «Запись» = отдельная строка (RecordRef), не сырой recordId primary — GREEN
- Задача БЕЗ recordId: строка «Запись» ОТСУТСТВУЕТ (`hasZapisRow:false`) — документированный OK-кейс. ✔
- Задача С recordId («Подача заявки», recordId `3f67cb0b-…`, заклеймлена из пула для открытия дровера): строка «Запись» ПРИСУТСТВУЕТ отдельно от блока идентификаторов. RecordRef отрендерил honest-sentinel `MonoId chip` (серый UUID), НЕ `chs-recordref--link`, потому что `GET /api/records/3f67cb0b-…` вернул **404** (см. корневую причину). Сырой UUID НИГДЕ не является primary-текстом.

### «Идентификаторы» (сырой inst-UUID + procKey) — DEMOTED — GREEN
Секция «ПРОЦЕСС» дровера (задача с проекцией):
```
Процесс        telLinear                (человеко primary)
Текущий шаг    Подача заявки            (StepRef, человеко)
Состояние      ОЖИДАНИЕ РЕШЕНИЯ
Запущен        04.07.2026, 22:09:14
Идентификаторы d89dcfa4-77db-11f1-abdf-aaa9cc4b0546   ← inst UUID (muted/demoted)
               telLinear                              ← procKey (muted/demoted)
```
Zoom подтвердил: «Запись» и «Процесс»-record-дизамбигуатор — серые mono-чипы; сырой instance-UUID собран в demoted «Идентификаторы», НЕ primary.

### A(4) имя задачи списка несёт контекст записи — GREEN
Строка списка (DOM `.chs-task__name` + `.chs-task__record`):
`Подача заявки — 3f67cb0b-200b-4286-ae6f-c773f12c85de`
— имя + record-дизамбигуатор (RecordRef, fallback-чип), отличает её от 15+ одноимённых «Подача заявки». Колонка ПРОЦЕСС: `telLinear` (primary) + demoted UUID-чип.

### Корневая причина RecordRef-fallback (почему не «title+ссылка») — НЕ регресс фикса
Сверка БД (`docker exec choros-postgres-1 psql -d choros`):
- `choros.record` `3f67cb0b-…`: tenant `a0000000-…-0001` = **Dev Silo** (тот же тенант, что у e-orlov), `data.title = "T-0588 Tier-2 retest заявка"` — title ЕСТЬ.
- Владеющий registry `a7000000-…-0002` → application `a7000000-…-0001` = `tel-approval` «Согласование заявок (ТЭЛ)», **tier = `draft`**.
- Сеть браузера: `GET /api/records/3f67cb0b-…` → **404** (×4, аутентифицированные вызовы приложения).
- Хендлер `src/http/records.ts` GET `/api/records/:id`: 404 честно неразличим для {не-в-тенанте | DRAFT-скрыт (T-0558 sandbox-gate) | нет READ-грант (T-0570 READ-PDP)}. Приложение — DRAFT, e-orlov не sandbox-privileged → честный 404.

Вывод: RecordRef ведёт себя ровно по контракту D2 (никогда не рендерит сырой id как primary; на 404/denied — honest demoted mono-чип; «Запись» — отдельная строка). Позитивный «title+link» не наблюдаем ЖИВЬЁМ только потому, что единственная record-несущая задача в инбоксе e-orlov указывает на запись под DRAFT-приложением. Это средовое, не дефект T-0687 (фикс client-only).

## FRICTION
1. **Позитивный RecordRef «title+ссылка» не наблюдаем на этом стенде.** Единственная record-несущая задача в инбоксе e-orlov (`Подача заявки`, recordId `3f67cb0b-…`) указывает на запись под DRAFT-приложением `tel-approval` → `GET /api/records/:id` честно 404 → RecordRef fallback на demoted UUID-чип. Чтобы отрендерить title+link ЖИВЬЁМ, нужна record-несущая задача, чья запись под ОПУБЛИКОВАННЫМ приложением ЛИБО приёмка под sandbox-privileged/владельцем (e-owner) для того же draft-app. Рекомендация: добавить в тест-данные задачу поверх опубликованного app, либо повторить дровер под e-owner.
2. **Голый fetch без auth → 401** (подтвердил DURABLE-грабли памяти): мой ручной `fetch('/api/records/…')` без `authHeaders()` вернул 401 — не показатель; реальные вызовы приложения (Bearer) вернули 404. Смотреть сеть браузера, а не ручной fetch.
3. **Тест-данные:** 15+ одноимённых «Подача заявки» без recordId в пуле; только одна несёт recordId — узкая выборка для проверки A(2)/A(4) позитива.
