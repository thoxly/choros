# T-0680 — LIVE_PROOF (D-064): форма с полем-ТАБЛИЦЕЙ сохраняется (был 409 WRONG_FLOOR)

**Вердикт: GREEN.**
Форма CRM «Сделка» С ТАБЛИЦЕЙ «Позиции» (collection, колонки qty/product) собирается
на человеческом канвасе, кнопка «Сохранить раскладку» активна без «висящего биндинга»,
POST /api/forms/binding возвращает **не-409** (200), строка `choros.form_binding`
персистит table-ноду с суб-ключами колонок, round-trip грузит и рендерит таблицу.
Негатив-страховка: настоящий висящий биндинг (top-level и суб-ключ) ВСЁ ЕЩЁ ловится (409).

- Актор: `final-demo@example.com` (human), тенант `final-demo` (`f120cb3f-5445-4d75-9835-2c26f0ff8667`).
- Сцена: набор «Сделка» (`sdelka`, registryDefId `93715fef-38c6-4d03-ba60-8d6d2b5548ea`)
  приложения «crm» (`18e8ddd9-3bcd-4937-80a7-fe63576a640b`) — уже имел residue-форму

## Что доказано (браузером claude-in-chrome, без обходов)

### 1. Сцена, где капстоун был вынужден УДАЛИТЬ таблицу
FormDesigner (`/forms`, Конструктор drag-n-drop). Процесс = «LP T-0678 форма сделки»,
шаг = «Проверка сделки», приложение = crm, набор = «Сделка».
Палитра surfaced все 5 полей включая **«Позиции collection»**. Канвас собрал форму:
title / amount(money) / close_date(date) / stage(select) / **Таблица «Позиции» → positions**.

Замечание по UI-контуру (не блокер T-0680, зафиксировано): при УЖЕ загруженном биндинге
(`setFields(data.fields)` кладёт только 4 скаляра) выбор набора полей единожды пропускается
`skipNextSchemaRebuildRef` → collection-поле НЕ появлялось в палитре. Повторный выбор набора
(consume skip-flag) вызвал `parseRecordSchema` → `positions` появилось как «collection», канвас
пересобрался с table-нодой через `nodeForField` (columns из subFields). Кнопка «Сохранить
раскладку» — активна, блок «Ошибки авторинга» отсутствует, «висящего биндинга» нет.

### 2. КЛЮЧЕВОЕ: сохранение table-формы → НЕ 409, а успех
Клик «Сохранить раскладку» (перехват fetch зафиксировал запрос+ответ):

```
POST /api/forms/binding → 200        (НЕ 409 WRONG_FLOOR)
request.layout содержит table-ноду:
  { type:"table", fieldKey:"positions", label:"Позиции", id:"t14",
    columns:[ {subKey:"qty", widget:"number", label:"Количество"},
              {subKey:"product", widget:"text", label:"Товар"} ] }
response: { id:"0703eb88-de14-4bef-8ff1-43fc9cd6af57", version:2 }
```

UI показал зелёное «Сохранено.» под кнопкой.

БД-подтверждение (`ssh homeserver-vm`, только для верификации, не для сборки):
```
SELECT id, version, jsonb_pretty(layout) FROM choros.form_binding
 WHERE tenant_id='f120cb3f-…' AND process_key='lp-t-0678-forma-sdelki';
→ 0703eb88-… | 2 | root.children[4] = table-нода «Позиции» (fieldKey:positions),
     columns: [{subKey:qty,widget:number}, {subKey:product,widget:text}]
```
Именно эта раскладка ранее давала 409 WRONG_FLOOR (R-4 сваливал subKey коллекции
в плоский top-level keySet → колонка=висящей → Floor-2). Фикс T-0680:
`classifyLayoutSave` резолвит `subKeysByCollection` (resolveLiveCollectionSubKeys),
scanDocument выносит subKey в `scan.collectionSubKeys`, R-4 канал 2 сверяет с
sub-schema коллекции, а не с top-level.

### 3. Round-trip
F5 (reload, beforeunload-гард снят). Канвас восстановил процесс/шаг/набор и
загрузил сохранённый биндинг:
- дерево канваса: treeitem «Таблица: Позиции» присутствует.
- GET /api/forms/binding?processKey=lp-t-0678-forma-sdelki&stepKey=Проверка сделки
  → **version 2**, layout содержит table-ноду с columns qty/product (subKeys).
- превью/исполнитель рендерит таблицу «ПОЗИЦИИ» с колонками «КОЛИЧЕСТВО»/«ТОВАР»
  (пустое состояние «Нет позиций»).

### 4. Негатив-страховка (R-4 жив, фикс хирургический)
Через тот же POST /api/forms/binding (тот же гейт):
- **Top-level фантом-поле** `ghost_field_not_in_schema` (канал 1 dangling):
  → **409 WRONG_FLOOR** «ключ "ghost_field_not_in_schema" … отсутствует в живой
    record_schema — висящий биндинг → Floor-2».
- **Битый суб-ключ** `bogus_col_not_in_subschema` в коллекции `positions` (канал 2 dangling):
  → **409 WRONG_FLOOR** «колонка "bogus_col_not_in_subschema" отсутствует в sub-schema
    коллекции "positions" — висящий биндинг → Floor-2».
Оба НЕ сохранились молча.

БД после негативов: `version=2`, `has_ghost=f`, `has_bogus=f`, `has_positions=t` —
валидная table-форма персистит, обе фантом-раскладки отвергнуты и не записаны.

## Итог
Валидные суб-ключи коллекции (qty/product) проходят (был 409 → теперь 200/201, персист,
round-trip, рендер). Настоящий висящий биндинг — top-level поле ИЛИ битый суб-ключ
коллекции — по-прежнему ловится (409), не сохраняется молча. Дискриминация R-4 точная.
**GREEN.**

RED-точек нет. Follow-up (не блокер T-0680): FormDesigner на УЖЕ загруженном биндинге
не показывает collection-поле в палитре при первом выборе набора — нужен повторный
выбор набора (skip-flag), чтобы `parseRecordSchema` пересобрал fields с коллекцией.
Стоит surfaced-ить collection в палитре сразу и/или не глушить rebuild навсегда.
