## Вердикт: **GREEN**

Фикс T-0611 подтверждён живьём глазами пользователя через браузер: (а) коллизия
слагов `registry_def` между двумя приложениями честно отклоняется ассистентом
по-русски со списком кандидатов, БЕЗ мутации ни одного из двух реестров;

реестру, второй остаётся нетронутым. LLM-контур живой (не блокер, в отличие от
w3). Проверено и через UI (визуально), и перекрёстно через БД (диагностика, не
основной путь доказательства).

## Шаг 1: коллизия слагов registry_def — использована ЕСТЕСТВЕННАЯ (не создавал новую)

Проверил через БД (`SELECT ... GROUP BY slug`), что в тенанте Dev Silo уже

| registry_def.id | slug | application.slug | application.display_name |
|---|---|---|---|
| `5bcbf15f-e8ff-4f98-9571-bc95c6ab50b5` | soglasovanie | `t0588-tier2-trigger` | T0588 Tier2 Trigger |

## Шаг 2: ассистент — попытка отредактировать по слагу (неоднозначность)

Открыл «Конструктор → Ассистент» (nav), создал новый разговор кнопкой
«+ Новый». **Живая находка по пути**: первая фраза-запрос («Добавь текстовое
поле "Комментарий доп." в раздел с слагом soglasovanie») была классифицирована
верно в configurator-режим (ключевое слово «добавь»), но LLM САМ решил не
вызывать инструмент и вместо этого спросил UUID заранее («у меня нет
инструмента для поиска по слагу… подскажете?») — это разумное консервативное
поведение LLM, не баг резолвера (см. FRICTION ниже). Второй заход с фразой
«просто попробуй» свалился в analyst-режим (ключевые слова не совпали).

**Третий, директивный заход** («Настрой раздел: добавь текстовое поле с
ключом "extra_comment" и подписью "Комментарий доп." в registry_def,
используя как идентификатор сам слаг "soglasovanie" … Выполни это действие
сейчас.») заставил LLM реально вызвать `edit_jsonschema_non_destructive` с
`registryDefId="soglasovanie"`. Ответ ассистента (дословно):

> Ни одна из 1 операций не была выполнена. Ниже — фактические исходы.
>
> ✗ Обновление поля «extra_comment» (add_field) в схеме реестра «soglasovanie»:
> Добавлено текстовое поле для дополнительного комментария в раздел
> согласования — edit_jsonschema_non_destructive: слаг «soglasovanie»
> неоднозначен — существует в нескольких приложениях этого пространства
> (T0588 Tier2 Trigger [t0588-tier2-trigger], Согласование заявок (ТЭЛ)
> [tel-approval]). Уточните: укажите raw UUID нужного реестра (registryDefId).
>
> Часть операций не удалась — исправьте причину и повторите. Ничего лишнего
> не создано и не перезаписано (все изменения — в черновике).

Отказ **на русском**, **честный** (явно "не выполнено", не ложный ✓), **со
списком кандидатов** (слаг приложения в скобках + человекочитаемое имя), **с
инструкцией уточнить UUID**. Соответствует AC-2 дословно.

Скрины: `07-new-conversation.png`, `11-typed-directive.png`,
`12-response-directive.png`.

## Обходы / отклонения от чистого UI-пути (FINDINGS для честности LIVE_PROOF)

1. **Сброс пароля e-owner через Keycloak Admin REST** (не через продуктовый
   UI) — потребовался, потому что пароль с прошлого прогона (T-0583,
   2026-07-04) не сохранён/неизвестен в этой сессии. Это административная
   подготовка входа, а не часть проверяемого сценария — сам вход и весь
   тестируемый путь (шаги 2-3) идут через настоящую KC-форму в браузере.
2. **Не создавал новую пару приложение+раздел с коллизией слага через
   конструктор** — переиспользовал уже существующую естественную коллизию
   `soglasovanie` (t0588-tier2-trigger × tel-approval), накопленную прошлыми
   прогонами. Задание разрешает это explicit («Если такие уже есть от прошлых
   прогонов — переиспользуй»). Не обход: коллизия — состояние данных тенанта,
   не механизм проверки.
3. **Снятие baseline / verification схем через прямой SQL** (`psql` к
   registry_def.record_schema/updated_at) — использовано КАК ПЕРЕКРЁСТНАЯ
   диагностика в дополнение к UI-проверке (не вместо неё). Основное
   доказательство нуль-мутации/точного таргетинга получено визуально через
   Конструктор → Приложения → Данные (столбцы полей), SQL лишь подтверждает
   на уровне персистентности. Это осознанный выбор для дополнительной
   строгости, а не необходимость (UI-проверка была бы достаточна сама по
   себе).

Ни один из этих пунктов не является «продукт этого не даёт» — весь
пользовательский путь ассистент-взаимодействия и весь путь верификации через
Конструктор пройден в браузере без обхода API.

## FRICTION (не блокеры, но живые наблюдения о взаимодействии с ассистентом)

- **classifyIntent (src/core/assistant-intent.ts) хрупок к формулировке**:
  ключевые слова простые (`добавь`, `настрой`, `собери` → configurator;
  `отчёт`, `анализ` → analyst; per-message, не per-thread). Фраза «Просто
  попробуй выполнить операцию…» не содержала ни одного configurator-триггера
  → ушла в analyst-режим, ассистент отказался действовать по роли
  («моя роль — только читать и анализировать»), а не из-за резолвера. Для
  пользователя это выглядит как два разных отказа по разным причинам —
  разница между «не понял intent» и «нашёл коллизию слага» не всегда очевидна
  без явного директивного фразирования.
- **Первый (корректно классифицированный configurator) заход тоже не дошёл до
  вызова инструмента** — LLM решил заранее уточнить UUID вместо попытки с
  тем, что дал пользователь (слагом), хотя система ЧЕСТНО поддерживает slug
  passthrough. Это консервативное поведение самой LLM (не системный баг), но
  означает, что типичный пользователь, не проинструктированный явно
  «выполни сейчас, передай слаг как есть», может никогда не увидеть тестируемый
  путь резолвера — ассистент сам подстрахуется вопросом раньше. Хорошо для UX
  (меньше шанс промаха), но означает: живой E2E-обход дефекта T-0611
  («молча редактирует не тот») в практике был бы ещё РЕЖЕ, чем казалось из
  спеки — LLM сам не любит гадать с неполной информацией.
- Профиль `T0586 DeepSeek` имеет provider=`anthropic`, но model=`deepseek-chat`
  и работает через deepseek endpoint — несостыковка ярлыка/провайдера в
  данных из прошлого прогона (не проверялось, не блокер этого LIVE_PROOF,
  возможная находка для отдельной задачи).

## Соответствие критериям приёмки (AC из T-0611.spec.md)

- **AC-1** (ambiguous signal вместо id/null): подтверждён косвенно через
  наблюдаемое поведение (честный отказ вместо мутации) — резолвер вернул

- **AC-2** (честный op-error, оба кандидата, НЕ мутирует ни один): **GREEN**,
  подтверждено дважды через UI + БД.
- **AC-3** (raw UUID проходит и мутирует ровно один, старый non-ambiguous путь
  не сломан): **GREEN**, подтверждено дважды через UI + БД; попутно косвенно
  подтверждён и «application» путь — вся навигация по приложениям (клики по
  display_name в сайдбаре/списке) работала без сюрпризов на всём протяжении
  сценария.
- **AC-4/AC-5**: не в скоупе живого сценария (db-test / no-migration
  критерии, уже покрыты в pr-handoff CI-разделе; не переисполнялись здесь).
