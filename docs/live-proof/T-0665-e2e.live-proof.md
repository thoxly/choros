## P0 (доказанный код-анализом на реальном исходнике, не гипотеза)

**`InboxTaskForm` никогда не отрисует layout-путь (F5) для ЛЮБОЙ формы, собранной человеком через FormDesigner.**

Причина — гонка двух инвариантов в разных слоях:

1. `src/http/binding.ts` (~строка 543-545), обработчик `POST /api/forms/binding`:
   ```ts
   } else if (layout !== null) {
     // FormDesigner sends layout but not fields; store an empty array (column is NOT NULL).
     fields = [];
   }
   ```
   `web/src/forms/FormDesigner.jsx`'s `persistLayout()` шлёт `{process_key, form_key, layout}` — **без ключа `fields`** (подтверждено чтением функции, строки 1333-1355). Значит КАЖДАЯ форма, сохранённая через флагманский drag-n-drop конструктор, кладёт `form_binding.fields = []` в БД. Подтверждено живьём: GET после save вернул `"fields":[]` в теле ответа (шаг 7 выше).

2. `web/src/screens/screen-inbox.jsx`, `InboxTaskForm`, строки 188-210:
   ```js
   const fields = binding.fields || [];
   if (fields.length === 0) return null;   // ← строка 189, выполняется ПЕРВОЙ
   ...
   const hasLayout = binding.layout && typeof binding.layout === 'object' && binding.layout.root;  // ← строка 210
   ```
   Проверка «пустые ли fields» стоит **раньше** проверки `hasLayout` и возвращает `null` (компонент не рендерит вообще ничего) прежде, чем код успевает посмотреть на `binding.layout`.

Комбинация 1+2: любая карточка задачи для шага с формой, собранной человеком в FormDesigner, отрисуется как «нет формы» (`return null` на строке 189) — ветка `hasLayout` (T-0665 F5, заявленная в pr-handoff как готовая) **физически недостижима** в проде. Единственный способ прорваться — вручную отправить непустой `fields[]` вместе с `layout` через сырой API-запрос в обход UI FormDesigner — то есть ровно тот обход, которого просило избегать задание.

**Тесты не ловят это**: `screen-inbox.test.jsx`'s блок «T-0665 F5» (строки 249-277) — чисто source-presence assertions (`expect(src).toContain(...)`), не поведенческие; они проверяют, что строка `hasLayout ? (` существует в файле, но НЕ проверяют порядок веток относительно guard `fields.length === 0`. Гейты зелёные, контур мёртв — ровно паттерн D-064, который приёмка ищет специально.

**Фикс (не делал — вне мандата LIVE_PROOF, только диагноз):** либо `persistLayout` должен слать актуальный `fields` (live schema snapshot) вместе с `layout`, либо `POST` не должен писать `fields=[]` для layout-пути (снапшотить схему на сервере от `application_id`/`registryDefId` источника), либо (минимально) `InboxTaskForm`'s empty-fields guard должен идти ПОСЛЕ `hasLayout` check (a layout с непустым деревом — не то же самое, что «нечего показывать»).

## Средние находки (не P0, но релевантны T-0665)

1. **Приложение в конструкторе форм не синхронизировано с `process_app_binding`.** Секция «Привязка» позволяет свободно выбрать ЛЮБОЙ процесс + ЛЮБОЕ приложение независимо друг от друга — нет UI-подсказки/фильтра, что для процесса `X` реально привязано только приложение `Y` (через `process_app_binding`, отдельный API `/api/process-app-bindings`, не используемый FormDesigner-ом вообще). Несогласованный выбор проходит всю сборку без предупреждения и падает только на Save с непрозрачным 409 «(no registry binding)» — сообщение верно технически, но не подсказывает пользователю, ЧТО приложение выбрано неверно. Обнаружил только эмпирически (перебором всех 10 `novyy-protsess-*` через пустой layout-пробник).
2. **`telLinear` (эталонный ТЭЛ-процесс, source=engine, 25 живых инстансов) недоступен в пикере «Процесс»** секции «Привязка» — фильтр `status === 'published'` (FormDesigner.jsx строка 642) исключает процессы со `status==='deployed'` (те, что задеплоены напрямую в Flowable, не через модельер). Единственный процесс с гарантированно рабочей live-schema резолюцией (по факту, `resolveDefaultStepResultSlug()` заточен именно под ТЭЛ-кейс `slug='soglasovanie'`) недостижим из UI флагманского конструктора.
3. **Money-поле ломает дефолтную сборку формы.** `web/src/forms/widget-registry.js`'s `WIDGET_COMPAT_TABLE` не содержит ключа `money` (только `number`/`integer` допускают виджет `money`). Поле схемы с `field.type === 'money'` напрямую (не `number`+widget) через `nodeTypeForFieldType()` попадает в `default: 'field'`, а `field-contract.js`'s `resolveFieldContract({type:'money'})` резолвит в `contractKind:'money'`, не входящий в допустимые `scalar`/`enum` для `type==='field'` — валидатор авторинга (`form-document.js` V-CONTRACT) немедленно рапортует «Узел «Поле» нельзя привязать к полю «amount»» для ЛЮБОЙ формы, где в наборе полей есть money-поле и сборка не удаляет его вручную. Воспроизведено дважды на реальной схеме «Заявки» (поле «Сумма», money).
4. **Datalist-подсказка шага в FormDesigner отдаёт BPMN `id`, а не человекочитаемое `name`, хотя подсказка под полем гласит «Совпадает со значением поля «Шаг» в карточке задачи инбокса».** `bpmn-user-tasks.js`'s `extractUserTasks()` возвращает `{id, name}`, но `<option value={t.id}>{t.name}</option>` (FormDesigner.jsx ~строка 1077) кладёт в `value` именно `id` — а реальное значение `item.step` в `/api/inbox` для этого же шага оказалось человекочитаемым именем («Согласование»), не BPMN id (`Activity_0dsh0ls`). Первая привязка (по id) не совпала бы ни с одной инбокс-задачей молча (GET/POST прошли бы 200/201, просто НИКОГДА не резолвились бы для реальной задачи) — воспроизведено: обе привязки (по id и по name) сохранились по отдельности как две разные строки `form_binding`, что также означает лишний дубль без явного предупреждения пользователю.

## Не обход

Все финальные сохранения (201) выполнены ЧЕРЕЗ РЕАЛЬНЫЙ UI FormDesigner (клик по палитре/select/Save-кнопке), не прямым API-вызовом. Прямые `fetch()`-пробники использовались ТОЛЬКО для разведки (проверка `/api/process-catalog`, `/api/process-app-bindings`, поиск согласованной пары процесс+приложение, эмпирическая проверка резолва live-schema по 9 ключам пустым layout) — ни один из них не является заявленным доказательством "форма собрана и сохранена", это было сделано отдельно и полноценно через клики. Единственное отступление от чистого UI-пути — сборка формы №1 (несогласованная пара novyy-protsess-2 + T0587 Заявки) была намеренно оставлена как зафиксированная находка (409), а не удалена/скрыта.
