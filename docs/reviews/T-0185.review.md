## 1. Migration 049 vs 050 regression diff

049 function body (`migrations/049_tier.sql`):

```sql
BEGIN
  IF OLD.tier = 'published'
     AND current_setting('choros.promoting', true) IS DISTINCT FROM '1' THEN
    RAISE EXCEPTION
      'tier published rows are managed/locked (T-0087 FR-4): direct write forbidden';
  END IF;
  RETURN NEW;  -- all paths
END
```

050 function body (`migrations/050_tier_delete_fix.sql`):

```sql
BEGIN
  IF OLD.tier = 'published'
     AND current_setting('choros.promoting', true) IS DISTINCT FROM '1' THEN
    RAISE EXCEPTION
      'tier published rows are managed/locked (T-0087 FR-4): direct write forbidden';
  END IF;

  IF TG_OP = 'DELETE' THEN
    RETURN OLD;
  END IF;
  RETURN NEW;
END
```

The RAISE path, the GUC check, and the UPDATE RETURN NEW are byte-identical to
049. The only difference is the added `IF TG_OP = 'DELETE' THEN RETURN OLD`
branch before the final `RETURN NEW`. This is exactly the correct fix for
Postgres's semantics where BEFORE DELETE NEW is NULL.

Trigger attachment in 050 is identical to 049 (same three tables:
`choros.application`, `choros.registry_def`, `choros."grant"`).

049 is untouched (`git diff … -- migrations/049_tier.sql` is empty).

Idempotency: uses `CREATE OR REPLACE` + `DROP TRIGGER IF EXISTS` / `CREATE
TRIGGER` — re-running is safe.

**Run 2:** identical result — 5/5 pass.

**Cleanup leak (nit):** DEL-2 and DEL-4 leave published `del-app-*` rows in
`choros.application` after each run (ROLLBACK in DEL-2 is intentional; DEL-4
also rolls back; the row from `insertDraftApp + promoteApp` persists). After two
test runs, 20 such rows accumulate. The test is correct — it does not leave
duplicate IDs (each run uses `crypto.randomUUID()`). But the DB is not cleaned
up, and repeated CI runs will slowly grow this table. This is a nit: correctness
is not affected, but a test `afterEach` cleanup would be proper hygiene.

## 3. Pre-existing failing tests (externalWorker.e2e.test.ts, health.test.ts)

**Confirmed pre-existing, NOT caused by this diff.**

Both files at HEAD are **byte-identical** to their merge-base counterparts
(`diff /tmp/health_base.test.ts …/health.test.ts` → empty;
`diff /tmp/externalWorker_base.test.ts …` → empty).

**Cause (ambient DATABASE_URL pollution):**

- `health.test.ts` failures (AC-1, AC-4): The `/health` handler is async. The
  test calls `handleRequest(req, res)` synchronously and immediately reads
  `capture.body`. When `DATABASE_URL` is **not** set, `createJobStore()`
  returns an `InMemoryJobStore` and the handler writes the body synchronously
  (no real await). When `DATABASE_URL` **is** set, `createJobStore()` creates a
  `PostgresJobStore` and the handler is fully async — by the time the test
  reads `capture.body`, the body is still empty (`""`), causing
  `JSON.parse("")` → `SyntaxError: Unexpected end of JSON input`.

- `externalWorker.e2e.test.ts` failures: `createServer()` with no args calls
  `createJobStore()`. With `DATABASE_URL` exported (as in the `fitness:db`
  run), it creates a `PostgresJobStore` that immediately errors on
  `unrecognized configuration parameter "choros.tenant_id"` because the test
  doesn't set up the choros schema GUC environment.

**Verified:** running both files **without** `DATABASE_URL` → 22/22 pass. The
failures only appear when `DATABASE_URL` is in the process environment (ambient
Postgres from a combined `fitness:db` run). This is a pre-existing design gap:
these unit/e2e tests rely on `createJobStore()` returning an in-memory store but
are not defensively guarded against an ambient `DATABASE_URL`.

This is **not blocking** for T-0185 — the diff does not touch the failing files
or their code paths.
