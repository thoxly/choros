## 2. Axis findings

### Axis 1 — Behavioural correctness

**R-0 (nit):** `src/core/flowable-client.ts` literal defaults for `baseUrl` and
`adminUser` survive in core. The ADR §3 explicitly ratifies this (rejected
alternative "Make baseUrl a required parameter" documented). `"admin"` and the
container URL are non-secret, stable Flowable defaults — a literal there is
semantically more precise than an env fallback. Not a violation of NF-1 per ADR.
No issue.

**Call-site audit — all `makeFlowableClient` invocations:**

| Call-site | Pattern | Post-patch |
|-----------|---------|------------|
| `src/bridge-runner.ts:49` | `makeFlowableClient({ baseUrl, adminUser, adminPassword })` — explicit config built from local env reads at L39–42 | Correct |
| `src/bridge-smoke-runner.ts:80` | `makeFlowableClient({ baseUrl, adminUser, adminPassword: adminPass })` — explicit config built from local env reads at L71–74 | Correct |

No call-site is broken by the change.

**Integration tests (skipped suite):** `flowable-client.integration.test.ts` passes
explicit config including `adminPassword: process.env["FLOWABLE_REST_APP_ADMIN_PASSWORD"] ?? "choros_flowable_dev_pw"`.
When `FLOWABLE_INTEGRATION=1` is set (as in the `flowable` CI job), the suite will
run against a live Flowable with the correct password. The env read has been moved
from `src/core/` to `src/__tests__/` — the tests never depended on the factory's
internal env fallback. **No regression.**

### Axis 5 — CI env alignment (bridge-e2e-smoke / GitHub Actions)

The GitHub Actions `flowable` job sets only `FLOWABLE_REST_APP_ADMIN_PASSWORD:
choros_flowable_dev_pw` explicitly in the step's `env:` block.

`bridge-e2e-smoke.sh` (which invokes `bridge-smoke-runner.js`) does:
```
FLOWABLE_PORT="${FLOWABLE_PORT:-8082}"
ADMIN_USER="${FLOWABLE_REST_APP_ADMIN_USER_ID:-admin}"   # default "admin" if unset
ADMIN_PASS="${FLOWABLE_REST_APP_ADMIN_PASSWORD:-choros_flowable_dev_pw}"
export FLOWABLE_BASE_URL="${BASE_URL}"   # ← sets FLOWABLE_BASE_URL for bridge-smoke-runner
```

`bridge-smoke-runner.ts` post-patch reads:
- `FLOWABLE_BASE_URL` — exported by `bridge-e2e-smoke.sh`; **name matches.**
- `FLOWABLE_REST_APP_ADMIN_USER_ID` — not set by CI job; `bridge-smoke-runner.ts`
  defaults to `"admin"` which is identical to `bridge-e2e-smoke.sh`'s own default;
  **behavior consistent.**
- `FLOWABLE_REST_APP_ADMIN_PASSWORD` — set by CI job as `choros_flowable_dev_pw`;
  **name matches.**

**Conclusion: env names are consistent between the CI job, the smoke shell script,
and `bridge-smoke-runner.ts`. No misalignment introduced.**

`FLOWABLE_REST_APP_ADMIN_USER_ID` is never passed explicitly by the CI job; both
`bridge-e2e-smoke.sh` and `bridge-smoke-runner.ts` independently default to
`"admin"`. This is a pre-existing design (not introduced by T-0163) and is
consistent.

### Axis 6 — Fitness function integrity / duplicate key

**Pre-existing defect (out of T-0163 scope):** `package.json` contains two
`"fitness"` keys in `scripts` (lines 13 and 14). JSON parsers use the **last**
value for duplicate keys; `npm run fitness` executes **KEY2** (line 14), which
includes `no-env-in-core.sh`. KEY1 (line 13, T-0163's intended target line) also
contains `no-env-in-core.sh`, so the invariant is enforced regardless of which key
wins. The duplicate is pre-existing (introduced before T-0163, visible in
`git diff $(git merge-base HEAD dev)..HEAD -- package.json` which shows only 2
lines changed — both `"fitness"` lines — confirming the duplicate existed on dev
before this task).

KEY1 has `named-binding-isolation.sh` + `npm run build` but lacks `sim-adr-*`,
`demo/*`, `bundle-coherence`, `grant-trail-bypassrls-predicate` checks. KEY2 is
superset in those dimensions but lacks `named-binding-isolation`. This asymmetry
is a pre-existing gap, not introduced by T-0163. **Nit (axis 6) flagged for
separate cleanup; does not block T-0163.**
