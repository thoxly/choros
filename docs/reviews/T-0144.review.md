## 3. Механика afterAll cleanup

Паттерн правильный: `let id: string | undefined` на уровне `describe`, присваивается
до первого `expect()`, `afterAll` по `id`. Все 5 векторов реализуют схему из ADR §3.

FF-10 (vector 3.5): `freeformGrantId = json.id` присваивается **до** первого
`expect(res.status)` (строки 644–650). AC-4 выполнен.

ADV-3 не тронут (FR-4). Assertions не удалены (FR-5).

### 3.1 Проблема: DB-окружение — trigger блокирует все DELETE

Обнаружена при двойном прогоне. Счётчик растёт: каждый прогон добавляет ≈4+1+1
строк (`test`/`d0…ff`/`e-owner`). Диагностика через `psql`:

```
SELECT xmin, xmax FROM choros."grant" WHERE id='...';
-- xmax != 0 && txid_status(xmax) = 'committed' → строка помечена как удалённая
-- но остаётся видимой при COUNT(*)
```

Причина: триггер `tier_published_locked` (BEFORE DELETE, для таблицы `choros."grant"`)
введён задачей T-0087, смерженной в `dev` **после** точки ветвления T-0144.
Функция триггера для non-published строк выполняет:
```plpgsql
RETURN NEW;  -- bug: for BEFORE DELETE, RETURN NEW = NULL = suppress delete
```
В PostgreSQL `RETURN NULL` из BEFORE ROW DELETE триггера **подавляет удаление**.
В результате `DELETE ... WHERE id=$2` всегда возвращает `rowCount=0`,
afterAll cleanup кода T-0144 молча завершается без ошибки, строки остаются.

**Это bug в T-0087, не в T-0144.** T-0144 не может контролировать DB-состояние
чужой миграции. Однако это означает что приёмочный критерий AC-1/AC-2
(двойной прогон, count=17 после каждого) **не верифицируем** на текущем dev-DB.

### Безопасность РАЗОВОЙ санации dev-БД: SQL-предикат и риски

**Контекст:** в dev-БД накоплено 240 строк `granted_by='e-owner'`, из них 15 строк соответствуют паттерну ADV-3 (role_id=DEV_ROLE_OWNER, resource_type='mgmt_object:role'). Эти 15 строк ломают genesis-owner-seed AC-12 (ожидает ровно 17 строк на DEV_ROLE_OWNER, фактически 32).

**Точный SQL-предикат безопасного DELETE для оркестратора:**

```sql
DELETE FROM choros."grant"
WHERE tenant_id = 'a0000000-0000-0000-0000-000000000001'
  AND role_id   = 'e0000000-0000-0000-0000-000000000001'  -- DEV_ROLE_OWNER
  AND resource_type LIKE 'mgmt_object:%'
  AND granted_by = 'e-owner';
-- Ожидаемый rowCount: 15
```

**Почему безопасно:**
1. `granted_by='seed'` — genesis-гранты (migration 026) — не попадают под предикат.
2. 7 seed-строк с `resource_type='authoring_draft'` — не попадают (`LIKE 'mgmt_object:%'`).
3. `role_id=DEV_ROLE_OWNER` — не затрагивает role_budget (e0000000-…-002) и record-гранты.
4. В prod `granted_by` содержит UUID сотрудника, никогда строку `'e-owner'` — cross-env безопасен.

**Что НЕ должно попасть под этот предикат:**
- `granted_by='seed'` — genesis data, иное значение.
- `resource_type='authoring_draft'` или `resource_type='record'` — иные типы.
- `role_id != 'e0000000-0000-0000-0000-000000000001'` — бюджет-апрувер и другие роли.
- Любая строка с реальным UUID в `granted_by` (prod-операция).

**Риск ADV-3 race:** ADV-3.beforeAll вставляет строку с `granted_by='e-owner'` и `role_id=DEV_ROLE_OWNER` — попадёт под предикат. Если оркестратор запустит санацию **во время** ADV-3 теста (между beforeAll и afterAll), жертвенная строка будет удалена и ADV-3a/b упадут. Санация безопасна только **когда тест-сюит не запущен** одновременно. Для dev-БД (запускается вручную) это приемлемо.

**Дополнительные 225 строк `granted_by='e-owner'` с иными role_id/resource_type:** предикат выше их не затрагивает. Для полной очистки всего e-owner мусора потребуется отдельный расширенный предикат вне FR-6 — это выходит за скоуп T-0144 и требует RFC.
