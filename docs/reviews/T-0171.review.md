## 2. Axis 1 — Correctness (соответствие ADR/спеке)

### 2.1 pgPrefStore: порт NotificationPrefStore (FR-1, AC-1)

`PostgresPrefStore implements NotificationPrefStore` — сигнатура
`getPreferences(tenantId: string, eventKind: string): Promise<NotificationPreference[]>` точно
совпадает с портом в `notification-router.ts:209`. `NotificationPreference` импортируется, не
переобъявляется. `tsc --noEmit` проверяет структурную совместимость. **Соответствует.**

### 2.2 Dead wiring: PostgresPrefStore не подключён к publishNotificationEvent

`publishNotificationEvent` принимает `deps.prefStore: NotificationPrefStore`. В `server.ts` и
всём HTTP-слое нет ни одного места, где `PostgresPrefStore` передаётся как `deps.prefStore`
для `publishNotificationEvent`. Grep: `grep -rn "publishNotificationEvent" src/` (исключая тесты и
router) — **0 результатов**. Это **known-acceptable** для E-N.4 scope: E-N.4 поставляет DAO +
REST; полный wiring `publishNotificationEvent → PostgresPrefStore` ложится на E-N.6/E-N.7 или
отдельную интеграционную задачу. Спека не требует production-wiring fanout в рамках T-0171.
**Замечания нет.**

### 2.3 DEFAULT_PREFERENCES vs ADR §2.4 (FR-3, AC-5)

ADR §2.4 (строки 165–168):
```
task.assigned → [in_app]
approval.requested → [in_app]
sla.warning → [in_app, email-if-configured]
sla.breach / escalation.raised → [in_app, email-if-configured]
```

Реализация (`pgPrefStore.ts:207–211`):
```
task.assigned      → actor:assignee  → [in_app]           ✓
approval.requested → actor:approver  → [in_app]           ✓
sla.warning        → object_owner    → [in_app, email]    ✓
sla.breach         → object_owner    → [in_app, email]    ✓
escalation.raised  → escalation_chain → [in_app, email]   ✓
```

ADR говорит «email-if-configured» (т.е. только если email-канал настроен), реализация кладёт
`email` в channels безусловно. Это семантически верно: routing-слой (T-0169) применяет
`EmailChannelDriver` только если email настроен; preference-строка с `email` — лишь подписка,
не гарантия доставки. **Соответствует ADR.**

### 2.4 BLOCKING: AC-6/AC-7 — PDP-авторизация admin-эндпоинтов не реализована

**AC-6** требует: `GET /api/notification-preferences` возвращает 403 без grant
`mgmt_object:notification_config/read`.
**AC-7** требует: `PUT /api/notification-preferences` возвращает 403 без grant
`mgmt_object:notification_config/update`.

Реализация (`notification-prefs.ts:157, 186`) содержит только `// TODO: PDP resolveFor…` — без
реального вызова. Gate = наличие заголовка `x-dev-user`: любой аутентифицированный пользователь
может читать/писать preferences любого тенанта.

**AC-10** в `spec.contract.json` формулирует: «вызов resolveFor присутствует (FF-PREF-AUTHZ)».
`resolveFor` не вызывается вообще. Fitness-check FF-NP1 проверяет лишь **отсутствие** новых ACL-
механизмов, но **не проверяет присутствие** вызова `resolveFor`. Таким образом:
- AC-6 не покрыт (нет ни кода 403, ни теста для него).
- AC-7 не покрыт (см. выше).
- AC-10 частично не покрыт (второй критерий «resolveFor присутствует» не выполнен).

Замечание: **R-1 (blocking)**.

### 2.5 BLOCKING: AC-8 — self-guard не отклоняет actor:foreign-id

**AC-8** требует: `PUT /api/notification-preferences/self` с `recipient_scope: 'role:manager'` →
400. Это реализовано в `assertSelfScopeValid` (`notification-prefs.ts:111–118`).

Но AC-8 также требует: «с валидным event_kind → 200, сохранён `actor:<self>`». Сервер
конструирует `recipientScope = 'actor:${actorId}'` — это верно.

**Проблема:** `assertSelfScopeValid` проверяет только `role:` prefix. Если тело содержит
`recipientScope: 'actor:другой-uuid'`, функция **не бросает 400** (комментарий «server overrides»).
Это семантически корректно (сервер всё равно override-ит), но комментарий к функции заявляет
«Reject explicitly to return a clear error» — ожидание клиента и реализация расходятся. Более
важно: спека (FR-7) требует, чтобы `role:x` → 400. Это выполнено. `actor:other` → тихое
переопределение допустимо по спеке (FR-7 не требует 400 для actor:). **Это nit, не blocking.**

Пересматриваю: AC-8 выполнен в части `role: → 400`. Часть `actor:other` → сервер молча заменяет
— допустимо по spec. **Снижаю до nit.** Замечание **R-2 (nit)**.

### 2.6 Аудит (FR-8, NF-5)

Admin PUT и self PUT вызывают `appendPrefAudit` с типом `notif.preference.changed` внутри той же
транзакции `withTenantTx`. GET-маршруты не аудитируются — корректно (FF-NO-ISREAD-AUDIT). Payload
не содержит секретов. **Соответствует.**

## 4. Axis 3 — Security

### 4.1 SQL-injection риск SET LOCAL (nit, codebase-wide pattern)

`pgPrefStore.ts:103` и `notification-prefs.ts:61`:
```ts
await client.query(`SET LOCAL choros.tenant_id = '${tenantId}'`);
```
В `notification-prefs.ts` вызов через `withTenantTx`, где на строке 57 стоит `assertUuidShape(tenantId)` — UUID-валидация перед интерполяцией. В `pgPrefStore.ts:103` (`getPreferences`) UUID-валидации нет, но `tenantId` приходит из `publishNotificationEvent` (trusted routing-layer) — не из user input. Этот паттерн — **codebase-wide** (grep: 14 мест, включая `pgOutboxStore.ts:202`, `pgTimerStore.ts:137`). Не вводится новый риск. **Nit уровня codebase, не специфичный для T-0171.** Замечание **R-3 (nit)**.

### 4.2 Структурный барьер self-scope

`recipient_scope` для self-эндпоинта конструируется на сервере (`actor:${actorId}`), body-значение
полностью перезаписывается. Клиент не может установить `role:` или чужой `actor:` — верно. **OK.**
