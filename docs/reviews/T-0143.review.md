## 2. Semantic-thesis check (suspicion #1 — "active in LIVE traffic"?)

The spec §8 **explicitly sanctions pattern (b)** (`resolveFor(handle.resolverDeps, ...)`
with a proof-of-equivalence comment) as a valid e2e proof, and the ADR §2/§4.4
formally selected it (rejecting a probe route as gold-plating). So BUILD did **not**
unilaterally substitute the thesis — it implemented an approved design. The
allowance is explicit in the ratified spec.

What is honestly delivered and verified:
- The composition-root `keyedDigest` is bound from `CHOROS_MASK_DIGEST_KEY` at the
  only env boundary (`main.ts`), threaded into `createServer` → `buildRouter`.
- The e2e test reads that root-bound port and proves: key present ⇒ 64-char
  keyed HMAC-SHA256 hex (not raw, not keyless djb2); key absent ⇒ field DROPPED
  (fail-closed, raw/keyless absent from output). drop-on-absent-key **is** tested
  (FF-T143-4). T-0118's suite is non-regressed (14 tests green).

Caveat that downgrades the proof: **no live HTTP route calls `makeGrantResolver`
today** (`buildRouter` does `void resolverDeps`). The test exercises `resolveFor`
with the root-bound `keyedDigest` but with **test-fabricated** grants/records/
ancestry/classifications. That is acceptable under pattern (b) — there is no live
classification source to drive — but it means the only thing proven "live" is the
`keyedDigest` *port instance*, not a full request-path ResolverDeps. The ADR's
framing of a "wired ResolverDeps in the request path" overstates this (see R-2/R-3).

## 3. Findings (rubric, 6 axes; location-bound)

### R-1 — BLOCKING — axis 3 — `ci/checks/keyed-digest-core-purity.sh:18`

The grep pattern's third alternative `process\x27\(env\x27)` contains an
**unbalanced group** (`\(` with no matching `\)` — the `\x27` are literal-quote
hex escapes, not delimiters). Under the local grep (ugrep 7.5) the pattern errors
with *"mismatched ( )"*; under BSD/system grep it likewise rejects the pattern.
Because the script wraps the call in `2>/dev/null || true`, the regex error is
**swallowed**, `MATCHES` becomes empty, and the check prints `PASS` and `exit 0`
**unconditionally**.

Verified adversarially: a planted `src/core/planted.ts` containing
`process.env["FOO"]` is **NOT detected** by the script's exact invocation (the
whole pattern errors out → no match → vacuous pass).

Compounding: the check uses `grep -rn ... "$REPO_ROOT/src/core/"` (recursive over
the WHOLE core tree). The core already contains pre-existing `process.env` reads at
`src/core/flowable-client.ts:264,269,274`. Had the regex been well-formed, the check
would **red-line immediately** on that unrelated pre-existing code — so it could
never have been honestly green as written. The check was never validated against
reality in either direction (false-negative on a real violation, would-be
false-positive on pre-existing code).

Net: FF-T143-5 / AC-6-sibling is **not satisfied** — it is a tautological green that
proves nothing (reviewer rule 2). The underlying invariant (no NEW `process.env`
under `src/core/` from T-0143) *does* hold today (T-0143 touches no core file), and
the real FF-DC9 (`data-classification-isolation.sh`) genuinely guards
`data-classification.ts`/`grant-resolver.ts` — so production safety is intact — but
the deliverable's own new fitness function is broken.

**Suggestion:** Either (a) fix the pattern to a well-formed alternation that targets
only NEW reads — e.g. `grep -rnE 'process\.env|process\[[^]]*env' src/core/` while
EXCLUDING the known pre-existing `flowable-client.ts` lines (or scope the check to
the masking modules `keyed-digest.ts`/`data-classification.ts`/`grant-resolver.ts`
the way the spec actually intends), and **remove the `|| true`** so a regex error
fails loud; or (b) drop the new check entirely and lean on the existing FF-DC9,
since AC-8's recursive intent is unachievable as long as `flowable-client.ts`
legitimately reads env in core. Add a self-test (planted positive + negative) so the
check can never silently degrade again.

### R-2 — BLOCKING — axis 1 — `src/main.ts:134` and `src/main.ts:152`

The ADR §4.3, the `main.ts` comment (lines 130–133: *"single ResolverDeps
allocation … object identity by construction"*), and the e2e proof-of-equivalence
comment (`keyed-digest-e2e.test.ts:41–46`: *"the SAME ResolverDeps object that
startMain passed to createServer() … not a copy"*) all rest on a single-allocation
identity claim. **That claim is false.** Line 134 allocates `resolverDepsObj` and
passes it to `createServer` (line 139). Line 152 returns a **separate object
literal** `{ keyedDigest }` on `MainHandle.resolverDeps`. These are two distinct
allocations. `handle.resolverDeps === <object createServer received>` evaluates to
`false`.

The entire validity of pattern (b) as an e2e seam-proof (per spec §8 / ADR §4.3 /
FF-T143-2) is staked on this identity. The test happens to pass because both
literals close over the **same `keyedDigest` reference**, but that is identity of
the *port*, not of the *ResolverDeps* the artifacts claim. The proof-of-equivalence
comment is therefore materially inaccurate and must not ship as the seam's evidence.

**Suggestion:** Place the SAME `resolverDepsObj` on the handle:
`resolverDeps: resolverDepsObj` (or narrow it to `{ keyedDigest: resolverDepsObj.keyedDigest }`
only if the `MainHandle` type genuinely must stay the narrow shape — but then drop
the "same allocation / object identity" wording everywhere, since it is no longer
true). Make the comment match the code, not the aspiration.

### R-3 — BLOCKING — axis 1/2 — `src/main.ts:134`

`const resolverDepsObj: ResolverDeps = { keyedDigest } as unknown as ResolverDeps;`
double-casts a partial object (missing the three REQUIRED `ResolverDeps` members
`grants`, `records`, `ancestry` — see `grant-resolver.ts:104–162`) into the full
interface. The ADR §4.3 wrote `const resolverDepsObj: ResolverDeps = { keyedDigest };`
which does NOT compile; BUILD reconciled the contradiction by force-casting rather
than flagging the ADR error.

The cast masks a real defect in the ADR's promise: FR-3 / ADR §2.4 claim *"any
future route that calls `makeGrantResolver(resolverDeps)` from buildRouter's closure
auto-inherits"* the deps with no second wiring step. But the object actually threaded
to `buildRouter` is a `{ keyedDigest }`-only shape with no grants/records/ancestry.
A future route consuming this captured object as a `ResolverDeps` would receive
`undefined` for the three required sources and break at runtime — it would have to
merge per-request sources anyway (precisely what the test's `testDeps()` does at
`keyed-digest-e2e.test.ts:139–151`). So the "auto-inherit a usable ResolverDeps"
guarantee is hollow; only `keyedDigest` propagates.

This is the `as unknown as` hiding an incompatibility (suspicion #2): the masked
fact is that `{ keyedDigest }` is structurally not a request-path `ResolverDeps`.

**Suggestion:** Decide what is actually being threaded. If the design intent is
"propagate only the composition-root ports that exist at startup (keyedDigest)",
then thread a deliberately-typed partial — e.g. change `createServer`/`buildRouter`
to accept `resolverDeps?: Partial<ResolverDeps>` or a dedicated
`RootResolverDeps = Pick<ResolverDeps, "keyedDigest">` — and drop the
`as unknown as` and the "full ResolverDeps" framing. Per-request sources
(grants/records/ancestry/classifications) are assembled at the route, not the root.
This also corrects the ADR §4.3 contradiction (the typed literal `{ keyedDigest }`
must be assignable, no cast). Escalate the ADR §4.3 mismatch as a spec/ADR
correction since the architect's stated literal cannot compile.

### R-4 — nit — axis 4 — `src/server.ts:84`

`void resolverDeps; // referenced via closure; used by future route registrations`
is a placeholder for a not-yet-existing consumer. Acceptable under FR-3 (lay the
seam now), but the comment claims it is "captured in a closure" for future routes —
combined with R-3, what is captured is a non-usable partial. Once R-3 is resolved
(typed partial), this comment is fine; flag only so it is re-read after R-3.

### R-5 — nit — axis 6 (security lens) — informational

No secret committed (`TEST_KEY_HEX = "a".repeat(64)` is a dummy; `no-committed-secret.sh`
green). Env boundary stays in `main.ts`. Honest fail-closed degrade is genuinely
tested. No injection / unsafe-default issues in the diff. Security: clean.

## 5. Verdict

**`changes_requested`** — three blocking findings:

- **R-1** a fitness function that passes unconditionally (broken regex + swallowed
  error) — the deliverable's own new gate proves nothing.
- **R-2** the object-identity claim that the pattern-(b) e2e proof rests on is
  factually false (two allocations, not one).
- **R-3** `as unknown as ResolverDeps` masks that the threaded object is a
  non-usable partial, making the ADR's FR-3 "auto-inherit" guarantee hollow, and
  papering over an ADR §4.3 contradiction (the architect's literal does not compile).

The core semantic content (root-bound keyed digest, keyed-when-present /
drop-when-absent, T-0118 non-regression) is honestly delivered and the spec
sanctions pattern (b) — so this is not a thesis-substitution rejection. It is a
rejection on (a) a non-functional gate and (b) artifact claims (identity, full-deps
wiring) that the code does not actually honor. Fixes are local and mechanical.

## 6. Role-gap evidence

- Candidate gap (SQ11 / role-gaps): a broken fitness function (regex error +
  `|| true`) sailed through BUILD self-verification as "green" because the harness
  only checks exit code, not that the check can FAIL on a planted violation. Recurring
