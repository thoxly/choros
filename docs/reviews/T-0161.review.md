## Key Facts Verified (самостоятельная проверка)

### Факт 1: 3 строки невидимы resolveAgentToolset

`resolveAgentToolset` (`src/core/mcp-tool-registry.ts:178`) вызывает `McpToolSource.listTools(tenantId)`, где `tenantId` передаётся из вызывающего кода. При RLS (`FORCE ROW LEVEL SECURITY`) `choros_app`-сессия фильтрует по `choros.tenant_id`. Канонический dev-тенант — `a0000000-0000-0000-0000-000000000001` (используется migration 044, migration 053, всеми CI-тестами с `DEV_TENANT`). Строки 040-seed под `00000000-0000-0000-0000-000000000001` (genesis/bootstrap тенант) никогда не возвращались бы при вызове с dev-тенантом. Утверждение обосновано.

### Факт 2: ни тест/UI/фитнес-чек не ссылается на 3 UUID или имена

`grep` по всему репо:
- UUID `10000000-...-0001`, `10000000-...-0002`, `10000000-...-0003` → только `migrations/040_mcp_tool.sql` и `migrations/055_fix_mcp_tool_demo_tenant.sql`
- Имена `http-integration-tool`, `slack-notify-tool`, `json-transform-tool` → только те же два файла

Утверждение верно: никаких внешних ссылок нет.

### Факт 3: genesis-тенант 00000000-...-001 — что там живёт, не затронет ли DELETE

Тенант `00000000-0000-0000-0000-000000000001` используется в:
- `migrations/040_mcp_tool.sql` — 3 demo mcp_tool строки (те самые, что удаляются)
- `migrations/045_form_binding.sql` — одна строка form_binding (purchase-approval)
- `ci/checks/db/form_binding.test.ts` — тест формы
- `ci/checks/db/schema_change_api.test.ts` — registry-defs API тест

DELETE ограничен двойным предикатом: `tenant_id = '00000000-...-001' AND id IN (...)`. Три UUID уникальны — они появляются только в 040. Форма и другие строки genesis-тенанта не затронуты. Предикат точен.

Живая проверка: после применения 055 — `SELECT ... WHERE id IN (3 UUID)` → 0 строк; `SELECT tenant_id, count(*) FROM choros.mcp_tool GROUP BY tenant_id` → `a0000000-...-001: 8`, `00000000-...-001: 0 rows` (genesis тенант исчезает из результата, как и ожидается).

## Review by 6 Axes

### Axis 1 — Correctness (семантика, ADR-фidelity)

**PASS**

Решение DELETE (не MOVE) обосновано в комментарии миграции и подтверждено независимо:

1. ADR T-0077 §4.2 (docs/design/T-0077.adr.contract.json) прямо отверг опцию «seed mcp_tool строк в тенант `00000000-...-001` (как существующий seed 040)» — тем самым зафиксировав, что правильный тенант для authoring-инструментов это `a0000000-...-001`.
2. Три строки 040 имеют `resource_ops = effect_resource/invoke`; инструменты config-агента (migration 044) имеют `resource_ops = authoring_draft`. Семантика несовместима — MOVE создал бы мусор в dev-тенанте и нарушил бы AC-02 (8 authoring_draft rows).
3. Сам migration 040 не изменяется (freeze invariant FF-10 соблюдён).

Идемпотентность: `DELETE ... WHERE` — no-op при повторном прогоне. Подтверждено: второй ручной DELETE вернул `DELETE 0`.

### Axis 2 — Tenant isolation / scope

**PASS**

Предикат `WHERE tenant_id = '00000000-...' AND id IN (...)` строго ограничен тремя UUID. RLS не влияет на DELETE через choros_migrator (BYPASSRLS), что корректно для миграционного контекста (тот же паттерн, что в 040/044/053). Никакие строки других тенантов не затронуты.

### Axis 3 — Idempotency

**PASS**

`DELETE ... WHERE` — идемпотентный: если строк нет, операция возвращает `DELETE 0`. Подтверждено живой проверкой.

### Axis 4 — Migration slot coordination

**PASS (с нотой)**

Slot 054 зарезервирован ADR T-0128 (`migrations/054_connector.sql` запланирован, но ещё не приземлился). Slot 055 — следующий свободный. Миграционный runner (`run.mjs`) сортирует лексикографически и пропускает уже применённые версии: когда T-0128 приземлит 054, runner прогонит её на чистой БД до 055 (054 < 055), а на dev-БД где 055 уже применена — просто применит 054. Порядок операций не конфликтует: 054 создаёт `connector`-таблицу, 055 удаляет строки из `mcp_tool` — независимые операции.

**Нота (nit):** комментарий в строке 22 миграции говорит «max on-disk slot at time of writing is 053», но на dev-БД `schema_migrations` содержит 055 как применённую. Это не дефект (055 и есть эта миграция), но потенциально вводит в заблуждение будущего читателя. Поскольку комментарий описывает момент написания — некритично.

### Axis 5 — Proportionality / no over-engineering

**PASS**

Минимальный diff: 46 строк SQL + 1 строка excludes. Ноль изменений в src/, тестах, DDL. Пропорционально задаче (data-mutation cleanup). Документация в комментарии миграции полная — объясняет context, decision, coordination.

### Axis 6 — Security

**PASS**

- Нет секретов в миграции
- Нет CREATE/ALTER/DROP — data-mutation only
- DELETE не открывает никаких новых путей доступа
- choros_migrator BYPASSRLS используется только в рамках стандартного migration runner (не новый bypass-путь)
