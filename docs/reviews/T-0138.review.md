## 3. Анализ оси 2 — Authz / Безопасность (ключевой вопрос ревью)

### 3a. Гейт GET /api/audit/export vs GET /api/audit

`GET /api/audit/export` (T-0138) требует заголовок `x-dev-user` → 401 при отсутствии.
`GET /api/audit` (pre-existing) **не имеет auth-гейта** — возвращает 200 без любой аутентификации.
`GET /api/audit/:instanceId` (pre-existing) — аналогично, без гейта.

Это **консистентно-слабая** картина: весь audit-раздел в dev-режиме открыт без аутентификации.
Export добавляет x-dev-user гейт сверх existing pattern, что чуть строже, но асимметрично:
пользователь может прочитать `GET /api/audit/INS-7731` без auth, но не может скачать тот же файл
через `/api/audit/export?instance=INS-7731` без заголовка.

**Вывод по п.1 ревью-промпта:**
- Нет PDP-гейта ни на export, ни на screen-read. Оба пути = dev-slice (T-0053 seed).
- Export защищён x-dev-user (401); screen-endpoint — нет. Это **не blocking** для dev-слайса:
  PDP forward-obligation явно аннотирован inline в коде (`FORWARD-OBLIGATION` комментарий).
- Данные в AUDIT_SEED — hardcoded fixture, не реальные classified данные T-0033.
  Payload-поля (call/out) содержат имитационные суммы/договоры, а не живые PII/финансы.
  Маскинг T-0033 не применим к seed-данным — это корректно для dev-слайса.
- Риск: нит (задокументированный dev-режим), не blocking.

### 3b. FORWARD-OBLIGATION аннотация

В `src/http/audit.ts:290–292`:
```
// FORWARD-OBLIGATION: production route MUST check PDP for
// operation=read on resource=audit_trace before returning data.
```

Комментарий корректен, но не упоминает, что **базовый GET /api/audit также потребует гейта**.
Это потенциальная ловушка при production-хардентинге: разработчик видит только export,
не замечает, что screen-read тоже открытый.

### 3c. Маскинг classified-полей

T-0033 (data-classification) управляет полями через `data_classification` таблицу и
`maskFields` gate в `grant-resolver.ts`. Эта механика применяется к object-handle facets
(T-0021 projection flow). `AuditData` в `AUDIT_SEED` — полностью in-memory fixture,
не проходит через grant-resolver/maskFields. Поэтому вопрос маскинга к export релевантен
только в production (PDP forward-obligation path), не в dev-слайсе. Это нит-уровень,
не blocking.

## 5. Ось 1 — Корректность

### 5a. claim — порядок проверок

В `src/http/inbox.ts:150–175` порядок: сначала проверка `CLAIMED.get(taskId)` (идемпотентность/conflict),
затем `task.pool`. Это корректно: если задача уже заклеймлена тем же пользователем — идемпотентный 200;
если другим — 409 ALREADY_CLAIMED; только потом проверяется `pool`. Логический порядок правильный:
конфликт идентифицируется до проверки pool-статуса.

### 5b. Content-Disposition filename

`audit-${data.instance.id}-${Date.now()}.json` — имя файла включает instance.id из seed (без
пользовательского ввода), не содержит внедряемых символов. Корректно.

### 5c. Route ordering — "export" vs ":instanceId"

Маршрут `/api/audit/export` зарегистрирован явно **до** `/api/audit/:instanceId` (строки 280 и 329
в audit.ts) с комментарием о причине. AC-6 теста (`GET /api/audit/INS-7731` возвращает 200 без
Content-Disposition) верифицирует отсутствие shadowing. Корректно.

### 5d. In-memory CLAIMED — thread safety

Node.js single-threaded event loop: конкурентный доступ к `CLAIMED` в одном процессе невозможен
между двумя обработчиками без явного `await`. Обращения к `CLAIMED.get/set` в handler синхронны —
race condition невозможна. Верно документировано: «process-lifetime only».

### 5e. `_resetClaimStateForTests`

Экспортируется только для тестов, не вызывается из production-кода. Паттерн консистентен с
`_resetJwksCache` из `auth.ts`. Корректно.

## Findings

### R-N1 (nit, ось 2 — безопасность / документация)

**Файл:** `src/http/audit.ts:289–292`

FORWARD-OBLIGATION комментарий аннотирует только export-маршрут. Не упоминает, что
`GET /api/audit` и `GET /api/audit/:instanceId` (pre-existing routes, строки 272–277 и 330–338)
также открыты без auth-гейта в dev-режиме. При production-хардентинге нужно гейтить все три.

**Suggestion:** Добавить в `registerAuditRoutes` docstring или в FORWARD-OBLIGATION:
«ПРИМЕЧАНИЕ: GET /api/audit и GET /api/audit/:instanceId также не имеют auth-гейта в dev-режиме
и ДОЛЖНЫ получить PDP-гейт при production hardening вместе с export».

### R-N2 (nit, ось 2 — безопасность / документация)

**Файл:** `src/http/audit.ts:12–17` (модульный docstring)

Модульный docstring: «PDP gate: same principal as GET /api/audit» — это сравнение вводит в заблуждение:
GET /api/audit не имеет principal-проверки вообще (не требует x-dev-user).
Фраза подразумевает, что export и screen-read имеют одинаковый authz-уровень, но export
**строже** (требует x-dev-user, screen-read — нет).

**Suggestion:** Перефразировать: «В dev-режиме: экспорт требует x-dev-user (401 иначе);
screen-read [GET /api/audit] открыт без гейта — оба маршрута получат PDP-гейт при production hardening».
