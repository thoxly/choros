## Summary

Two test suites (`externalWorker.e2e.test.ts` and `health.test.ts`) failed under
ambient `DATABASE_URL` (pre-existing gap from T-0185 review §3). The fix is an
additive `storeMode?: 'auto' | 'memory'` parameter threaded through `createJobStore`,
`createTimerStore`, `createOutboxStore`, `createServer`, and `handleRequest`. The
production path (`'auto'` / undefined) is byte-for-byte preserved. Both test
scenarios (no env, with `DATABASE_URL=postgres://choros_migrator:…`) are confirmed
green. CI, tsc, and fitness are all green.

## 3. Router cache per mode — state leakage check

`handleRequest` now uses `_routerCache: Partial<Record<StoreMode, Router>>` keyed by
`'auto' | 'memory'`. Each mode gets its own lazily-constructed `Router` instance.
Only `health.test.ts` imports `handleRequest` directly, and all four calls in that file
use `TEST_STORE_MODE = 'memory'` consistently — the `'auto'` slot in the cache is
never populated by that test module. No cross-mode contamination possible in the current
test suite.

**Design note (nit — not blocking):** `_routerCache` is module-level state. In a
hypothetical future test that mixes `handleRequest(req, res, 'memory')` and
`handleRequest(req, res)` (auto) within the same vitest worker, routers from both
calls are cached independently. This is correct behaviour (no leakage), but future
test authors should be aware that the cached 'auto'-mode router captures whatever
`DATABASE_URL` was set at the time of the first auto-mode call. The spec documents
this (FR-3 / NF-4). No action required for this diff.

## 4. Health/externalWorker Postgres blind-spot assessment

The spec out-of-scope declares: "Fixing the async/synchronous health.test.ts pattern
beyond pinning the store mode (the synchronous test pattern is intentional and correct
for in-memory stores)." The question is whether these tests skipping Postgres leaves a
real blind spot.

**Finding: NOT a blind spot — Postgres path is already covered by ci/checks/db.**

- `ci/checks/db/pgJobStore.integration.test.ts` covers `getQueueHealth` (AC-13/AC-14)
  with a real Postgres pool including `workerIncidents` metrics (T-0063 AC-9/AC-10).
- `ci/checks/db/pgTimerStore.integration.test.ts` covers `getTimerHealth` (AC-9/AC-10/AC-11)
  with overdue timer scenarios against real Postgres.
- `health.test.ts` is explicitly an HTTP-contract test (status code, Content-Type,
  synchronous body pattern) — its purpose is to verify the HTTP layer and router
  dispatch, not the Postgres query logic. In-memory mode is the correct seam for this.

**Assessment:** The current test architecture is sound. `health.test.ts` + store pinning
is a contract test; `ci/checks/db/pg*.integration.test.ts` are the Postgres-variant
tests. There is no blind spot. Classification: nit (informational) — no action needed.
