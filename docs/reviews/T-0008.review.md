## Критические оси

### R-1 [BLOCKING] Ось 3 (корректность) — нет `needs: ci` в deploy-dev.yml

**Локация:** `.github/workflows/deploy-dev.yml`, структура `jobs.deploy-dev`

**Проблема:**  
Workflow `deploy-dev` не имеет `needs: ci`. Это означает, что при пуше в `dev` оба workflow запустятся параллельно. Деплой может начаться до того, как CI завершится — и если CI красный, деплой всё равно выполнится.

Комментарий в коде говорит: *«we rely on GitHub's required status checks branch protection (founder sets that in RL-2 gate)»*. Это перекладывает гейт на ручную настройку branch protection фаундером. Однако порядок действий не атомарен: если фаундер добавит `DEPLOY_SSH_KEY` раньше, чем настроит branch protection, деплой сможет запускаться на сломанном CI.

**Исправление:**  
Добавить в `jobs.deploy-dev`:
```yaml
needs: ci
```
Это делает гейт декларативным и не зависящим от внешней настройки.

### R-2 [nit] Ось 6 (безопасность) — ssh-keyscan TOFU без пиннинга

**Локация:** `.github/workflows/deploy-dev.yml:44`

### R-3 [nit] Ось 6 (безопасность) — прямая интерполяция секрета в run-шаге

**Локация:** `.github/workflows/deploy-dev.yml:41`

**Проблема:**  
```yaml
echo "${{ secrets.DEPLOY_SSH_KEY }}" > ~/.ssh/deploy_key
```
Прямая интерполяция `${{ secrets.DEPLOY_SSH_KEY }}` расширяется до значения секрета в тексте команды. GitHub Actions маскирует вывод, но значение потенциально видно в expanded workflow YAML и process list до маскирования.

**Рекомендованный паттерн:**
```yaml
- name: Install SSH key
  env:
    SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
  run: |
    mkdir -p ~/.ssh
    echo "$SSH_KEY" > ~/.ssh/deploy_key
    chmod 600 ~/.ssh/deploy_key
```
Передача через `env:` изолирует значение в переменную окружения и не попадает в shell heredoc.

### R-5 [nit] Ось 2 (операционная надёжность) — `docker-compose.override.yml` не в `.gitignore`

**Локация:** `.gitignore` (корень репо); сервер: `/srv/choros/docker-compose.override.yml`

**Проблема:**  
На сервере существует `/srv/choros/docker-compose.override.yml` (restart: unless-stopped — он обеспечивает выживание стека после ребута). Файл **сейчас untracked** на сервере → `git reset --hard origin/dev` его НЕ трогает (reset --hard убирает только tracked файлы).

Однако `.gitignore` не содержит `docker-compose.override.yml`. Если кто-то выполнит `git add docker-compose.override.yml` на сервере, следующий деплой (`reset --hard`) удалит его — сервис потеряет restart-policy и не поднимется после ребута.

**Исправление:** добавить `docker-compose.override.yml` в `.gitignore`.

### R-6 [nit] Ось 3 (корректность) — command substitution в SSH-команде выполняется локально

**Локация:** `scripts/deploy-dev.sh:65`

**Проблема:**  
```bash

  ...
```

**Исправление:** экранировать: `\$(git log --oneline -1)`.

## Dormant-гейт (п.3): анализ

**Синтаксис:**
```yaml
if: ${{ secrets.DEPLOY_SSH_KEY != '' }}
```

**Вердикт: функционально корректен** для данного триггера.

Контекст `secrets` доступен в job-level `if` для `push`-событий (не fork PR). Когда секрет не задан, `secrets.DEPLOY_SSH_KEY` возвращает `''` (пустую строку), условие `'' != ''` = `false` → job пропускается. Workflow run создаётся (GitHub не блокирует), но job показывается как skipped в UI — без красного шума. При добавлении секрета job активируется автоматически.

**Известная ловушка (не применима здесь):** недоступность `secrets` в job-level `if` для `pull_request` от fork — в этом workflow триггер только `push: branches: [dev]`, который выполняется в контексте владельца → ловушка не срабатывает.

### R-1 — решение (б): `workflow_run` vs `needs: ci`

Предписание ревью предлагало добавить `needs: ci` в `jobs.deploy-dev`. Это невозможно в прямом смысле: `needs:` работает только между job'ами **одного и того же workflow**. `ci.yml` и `deploy-dev.yml` — два отдельных workflow, поэтому `needs:` не применим между ними.

Реализовано решение (б) — `workflow_run` триггер:

```yaml
on:
  workflow_run:
    workflows: ["ci"]
    types: [completed]
    branches: [dev]

jobs:
  deploy-dev:
    if: ${{ github.event.workflow_run.conclusion == 'success' && secrets.DEPLOY_SSH_KEY != '' }}
```

**Доказательство эквивалентности/превосходства:**

- `conclusion == 'success'` — это поле выставляется GitHub только когда все jobs в workflow `ci` завершились с `success`. Любой другой исход (`failure`, `cancelled`, `timed_out`, `skipped`) даёт другое значение → `if` = false → job **не запускается**.
- В отличие от `needs: ci` внутри одного workflow, `workflow_run` является **causal dependency across workflows**: `deploy-dev.yml` физически не может запуститься раньше, чем `ci.yml` завершится — GitHub не эмитирует событие `workflow_run[completed]` до реального завершения.
- При `conclusion != 'success'` (красный CI) GitHub Actions не эмитирует событие, которое бы запустило deploy, либо эмитирует с `conclusion='failure'` — в обоих случаях `if` блокирует job.
- Dormant-гейт (`secrets.DEPLOY_SSH_KEY != ''`) сохранён и объединён через `&&` — оба условия обязаны выполниться одновременно.

**Вывод:** `workflow_run` с `conclusion == 'success'` является **каноническим и превосходящим** паттерном для cross-workflow gating в GitHub Actions. `needs: ci` при одном workflow было бы возможно только путём дублирования ci-job'а в deploy-dev.yml, что ревью прямо запрещало.
