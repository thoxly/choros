### Ось 1 — Корректность (семантическое поведение)

Все ключевые точки спеки реализованы правильно:

**Promote-гейт:**
- `checkReportPageDepFields` вызывается через `validateAndLoadDeps` **внутри транзакции** (`withTenantTx`) со свежим `record_schema` (SELECT `registry_def` по `registry_def_id` в той же транзакции). Кеш/устаревшая схема исключены. `report-pages.ts:341–373`.
- SET LOCAL `choros.promoting='1'` вызывается **до** `UPDATE tier` в той же транзакции (T-0087 семантика, `report-pages.ts:902→909`). Порядок операций корректен.
- Negative-проба: unit-тест AC-14 (stale dep → 409 `STALE_DEPENDENCIES`) с `fakeDraftPage` + stale dep row в row-set; live-DB тест AC-14 с прямой вставкой `stale=true` dep — оба верифицируют, что `tier` остаётся `'draft'`.
- Страница NOT_IN_DRAFT (уже `published`) гейтируется до stale-check (шаг 4 перед шагом 5 в `promoteReportPage`). Правильный порядок.

**PDP — `mgmt_object:report_page` (ADR §6):**
- Правильный `resource_type = 'mgmt_object:report_page'` (`report-pages.ts:142`).
- `loadAdminContext` использует `LIKE 'mgmt_object:%'` (`org.ts:456`) — покрывает новый resource_type без правки frozen union.
- Genesis-owner short-circuit (`isGenesisOwner` → `{ok: true}`) — соответствует ADR §6 и T-0029.
- Операция `'promote'` сравнивается string-based (`g.operation as string`) === `operation` — не правит frozen `Operation` union (ADR T-0121 §6 / T-0077 §2.2).

**classifyReportPageFloor:**
- Вызывается при `create` (шаг 3, `report-pages.ts:447–455`) для Floor-2 + не-null `page_def`.
- Вызывается при `update` (шаг PATCH, `report-pages.ts:644–651`) при изменении `page_def` на Floor-2 странице.
- Правильно: Floor-1 страница (`isFloor1=true`) не проверяется на FLOOR_MISMATCH при PATCH — проверка нужна только для Floor-2.

**Аудит (ADR §7, T-0016):**
- Единственный sink `_auditWriter.appendAuditEvent` (modulе-level singleton `makePgAuditWriter`).
- Все обязательные события присутствуют: `report_page.authored`, `report_page.promoted`, `report_page.deleted`, `report_page_dep.registered`, `report_page_dep.updated`, `report_page_dep.deleted`.
- `report_page.deleted` записывается **до** `DELETE FROM choros.report_page` (NF-7, `report-pages.ts:814→828`). Аудит-след переживает удаление.
- Все вызовы атомарны с основной операцией в `withTenantTx`.

**T-0144 (BEGIN до SET LOCAL):**
- `withTenantTx` корректно: `BEGIN` → `SET LOCAL choros.tenant_id` → `SET LOCAL search_path` (`report-pages.ts:178–180`).
- Cleanup: `client.release()` в finally-блоке.

**server.ts аддитивен:** 4-строчный diff — только import + один `registerReportPageRoutes(router)` вызов. Нет изменений в существующей логике.

### R-1 (blocking) — AC-12: unit-тест `FORBIDDEN_AGENT_SELF_PROMOTE` деградирован до no-op

**Ось 1 / Ось 4 (Coverage) — blocking**  
**Локация:** `src/__tests__/report-pages.test.ts:708`

Спека AC-12: «`POST /api/report-pages/:id/promote` для agent-actor → 403 `FORBIDDEN_AGENT_SELF_PROMOTE`» — verifiable: **test**.

Фактическое утверждение в unit-тесте:
```ts
expect([200, 403, 404, 409, 503]).toContain(status);
```

Это принимает **любой** из пяти статусов — фактически ничего не проверяет. Тест дефектен: `e-agent` отсутствует в `ORG_SEED` (только `a-recon`, `a-invoice`, `a-triage`, `s-ledger`, `s-ocr` существуют как агенты), и тест сам документирует, что без DB `findEmployee` возвращает `null` → `actorType` defaults to `'human'` → агент-гейт не срабатывает.

В live-DB тестах (`ci/checks/db/report_page_crud.test.ts`) AC-12 отсутствует полностью (grep confirms: no `AC-12`, no `FORBIDDEN_AGENT_SELF_PROMOTE`).

**Итог:** AC-12 не покрыт ни одним реально работающим тестом, несмотря на декларацию `verifiable: test` в спеке. Код гейта (`report-pages.ts:851–857`) корректен, но не верифицирован.

**Требование к coder:** добавить live-DB тест в `report_page_crud.test.ts` использующий ORG_SEED-агента (например `a-recon`) через `x-dev-user`-header → проверить 403 `FORBIDDEN_AGENT_SELF_PROMOTE`; OR добавить `e-agent` в ORG_SEED с `type: 'agent'` + укрепить unit-тест до `expect(status).toBe(403)`.
