## Верификация R-2 (RESOLVED)

**R-2: `defaultCheckReadGrant` использовал неверный grant-pool (`mgmt_object:*` гранты).**

Фикс полностью переписывает `defaultCheckReadGrant`:

1. **Genesis short-circuit**: `loadAdminContext` → `admin.isGenesisOwner` → `{ok:true}` без лишних запросов.
2. **Non-genesis path**: прямой JOIN `grant × role_assignment` с фильтрами:
   - `g.resource_type = 'application'` ✓
   - `g.operation = 'read'` ✓
   - `ra.confirmed_by IS NOT NULL` ✓ (не-«предложенные» role_assignment)
   - Validity window на `role_assignment`: `(valid_from IS NULL OR valid_from <= $3) AND (valid_until IS NULL OR valid_until > $3)` ✓
   - Validity window на `grant`: аналогично ✓
   - `LIMIT 1` — достаточно одного покрывающего гранта

**Анализ JOIN-запроса:**

- `confirmed_by IS NOT NULL` — корректно: ADR §4.1 T-0018 упоминает `confirmed_by` как признак подтверждённого assignment. Неподтверждённые (proposed) assignments не должны давать права.
- `valid_from/until` на `role_assignment` — корректно: T-0018 §4.5 `isEffective` применяется к граντу, а T-0022 определяет валидность assignment. Оба окна проверяются.
- `valid_from/until` на `grant` — корректно: T-0018 §4.5.
- `delegable` — **не требуется для использования**: `delegable=true` означает, что грант МОЖЕТ быть родителем делегированного гранта. Использование (read-path) не требует `delegable=true` — актор может использовать `delegable=false` грант для чтения. Пример: genesis owner мог выдать `delegable=false application/read` grant; RLS-only scope. Проверять `delegable` при read — ошибка (over-deny). **Запрос корректен — `delegable` не фильтруется.**
- `scope` — **не проверяется**: см. R-6 (нит) ниже.

**Паттерн соответствует `invoke.ts:loadCallerInvokeGrants` (строки 239-244)**, с дополнением validity-window и `confirmed_by` фильтров, которых в `invoke.ts` нет (invoke.ts упрощён — не фильтрует validity, т.к. строка 244 содержит только `g.operation = 'invoke'`). Render-path строже — это корректно.

**Статус: RESOLVED.**

## Новая находка (iter-2)

### R-6 (NIT) — Scope-containment: grant на App-A даёт доступ ко всем страницам тенанта, включая App-B

**Ось 6 (security)**
**Локация:** `src/http/report-page-render.ts:161-178` (`defaultCheckReadGrant`, JOIN-запрос)

**Анализ:**

ADR T-0121 §6 (таблица прав):
> Просмотр страницы | `read` на `application` | любой с grant **на app**

ADR T-0121 §6 (описание гранулярности):
> Гранулярность просмотра — на уровне `application` (страница наследует видимость app)

Это формулировка per-app: `application read` grant с scope `{nodeId: app-A-uuid}` должен давать доступ только к страницам App-A.

Текущий JOIN-запрос в `defaultCheckReadGrant` не фильтрует `g.scope` относительно конкретного `app_id` запрошенной страницы — он ищет **любой** `application/read` грант в тенанте:

```sql
SELECT g.id FROM choros."grant" g
  JOIN choros.role_assignment ra ON ...
 WHERE g.resource_type = 'application'
   AND g.operation = 'read'
   -- НЕТ: AND g.scope @> jsonb_app_id(page.app_id)
```

Это значит: актор с грантом на App-A получает доступ ко всем страницам тенанта (App-B, App-C и т.д.).

**Для сравнения**: PDP T-0021 `resolveFor` делает:
```ts
const handleScope = refToScope(handle.ref);  // {kind:'node', nodeId: page.app_id}
isNarrowerOrEqual(handleScope, g.scope, ancestry);  // проверяет, что g.scope содержит page.app_id
```

**Почему это нит, а не blocking:**

1. **ADR T-0121 §6 явно указывает «через PDP T-0021»** — `checkReadGrant` является промежуточным day-1 суррогатом, а не полным PDP. Полный `resolveFor`-путь добавит scope-containment при интеграции T-0021 в render-path.
2. **Интерфейс `checkReadGrant` не принимает `app_id`** — чтобы добавить per-app scope-containment, потребуется либо передавать `app_id` в `checkReadGrant`, либо переделывать gate на `resolveFor`. Это выходит за scope T-0181.
3. **Реальный риск ограничен**: условие нарушения — multi-app тенант, где у актора есть грант на одно приложение, но не на другое. Day-1 тенанты, как правило, либо одно-приложенческие, либо имеют tenant-wide гранты.
4. **Исходная T-0181 задача** — Floor-1 рендерер + Floor-2 data API; PDP-полнота для multi-app scope была вне scope задачи.

**Рекомендация:** при интеграции T-0021 в render-path заменить `checkReadGrant` на `resolveFor(deps, {tenantId, ref:{kind:'application', applicationId: page.app_id}}, subject, 'read')` — тогда scope-containment будет корректным через уже существующий lattice. Или расширить `checkReadGrant` сигнатуру на `(pool, tenantId, actor, nowMs, appId)` и добавить scope-join.
