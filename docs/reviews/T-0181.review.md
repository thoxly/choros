## Findings

### R-1 (BLOCKING) — Floor-1 `/render` не имеет PDP-gate; actor воидится

**Ось 2 (ADR/spec соответствие)**
**Локация:** `src/http/report-page-render.ts:743-756`

```ts
const actor = extractActor(req);
void actor; // floor-1 render gate is application-read — checked by PDP inside renderFloor1 via withTenantTx
const result = await renderFloor1({ pool: _poolHint ?? getPool(), tenantId: DEV_TENANT_ID, pageId });
```

`renderFloor1` не принимает `actor` и не вызывает `authzDeps.checkReadGrant`. Коментарий «checked by PDP inside renderFloor1 via withTenantTx» — неверен: `withTenantTx` обеспечивает только RLS tenant-изоляцию, но не PDP.

ADR §6, таблица прав:
> Просмотр страницы | `read` на `application` | любой с grant на app

Это требование распространяется на **оба эндпоинта** — Floor-1 `/render` и Floor-2 `/data`. Сейчас Floor-1 доступен любому аутентифицированному пользователю без проверки `application read` grant. Floor-2 проверяет, Floor-1 — нет.

**Исправление:** передать `actor`, `nowMs` и `authzDeps` в `renderFloor1`; вызвать `authzDeps.checkReadGrant` перед `withTenantTx` (по аналогии с `dataFloor2`, строки 634-637). Добавить `AC-10-FLOOR1` тест, проверяющий 403 для non-genesis без гранта.

### R-2 (BLOCKING) — `defaultCheckReadGrant` использует неправильный grant-pool; проверяет ANY delegable mgmt_object grant вместо `application read`

**Ось 6 (security)**
**Локация:** `src/http/report-page-render.ts:136-138`

```ts
const hasRead = admin.adminGrants.some(
  (g) => g.delegable && (g.operation as string) === "read",
);
```

`loadAdminContext` (org.ts:456) загружает ТОЛЬКО гранты с `resource_type LIKE 'mgmt_object:%'`. В системе `operation='read'` на `mgmt_object:*` ресурсах не существует — операции там `author`, `promote`, `apply`, и т.д. Таким образом это условие ВСЕГДА вернёт `false` для non-genesis пользователей, независимо от наличия у них `application read` гранта.

ADR §6 требует: grant `read` на resource_type `application` (не `mgmt_object:*`). `loadAdminContext` не загружает `application` grants — это load-путь из другой ветки PDP.

**Два последствия:**
1. Non-genesis пользователь с валидным `application read` грантом получит 403 (over-deny, функциональный баг).
2. Проверка де-факто сводится к genesis-owner шорт-сёркиту (everyone else denied) — скрытая регрессия прав.

**Исправление:** изменить `defaultCheckReadGrant` чтобы использовать PDP T-0021 `resolveFor` (или другой правильный путь к `application read` grant), а не `loadAdminContext.adminGrants`. Добавить живой тест: non-genesis с `application read` грантом получает 200.

**Дополнительно:** отсутствует `resource_type` фильтр в условии (нет `g.resourceType === "application"`). Даже если бы `adminGrants` содержал смешанные типы, условие не различает ресурсы.

## Анализ SQL-инъекций (п.1 проверка) — все пути

### field_key (строки 1745, 1916, 2049, 2062)
- FIELD_KEY_SAFE_RE `/^[a-zA-Z0-9_-]+$/` применяется в `assertFieldKeySafe`.
- Вызывается **дважды**: в `parseMetrics` (при чтении page_def, до любых DB-запросов) и в `buildAggSql` (перед SQL-строительством).
- Charset `[a-zA-Z0-9_-]` исключает `'`, `"`, `;`, пробел, `--` и т.д. Кавычка исключена → невозможно вырваться из `data->>'field_key'`.
- **jsonb-путь:** `data->>'${field_key}'` — field_key является строковым литералом внутри jsonb-оператора. После валидации charset-гарда инъекция невозможна (нет метасимволов SQL).
- **Вывод:** field_key защищён корректно.

### group_by (строки 1994-1996, 2051-2053, 2101-2120)
- Применяется `assertFieldKeySafe` в `parseMetrics` и в `buildAggSql`.
- Используется в `data->>'${group_by}'` (SELECT) и ` GROUP BY data->>'${group_by}'`.
- Та же защита что и field_key. **Защищён корректно.**

### filter.op (строки 1327-1329, 1415)
- Проверяется через whitelist: `validOps = ["=", "!=", "<", ">", "in"]` — закрытое множество.
- Интерполируется напрямую: ` AND (...) ${filter.op} ${ph}` — но op из закрытого whitelist, все допустимые значения безопасны для SQL.
- **Защищён корректно.**

### filter.value (строки 1410-1416, 1071-1082)
- Скалярное значение: `params.push(filter.value); ... $${paramIdx}` — полностью параметризировано.
- `in`-значение: каждый элемент массива `params.push(v); ... $${paramIdx}` — полностью параметризировано.
- **Защищён корректно.**

### source_registry_def_id (строки 2199-2205)
- Проверяется `UUID_RE.test(registryDefId)` (UUID regex) перед передачей в параметр `$2`.
- UUID не содержит SQL-метасимволов; передаётся как параметр `$N` в запросы.
- **Защищён корректно.**

### agg → sqlAgg (строки 2112, 1984)
- `agg` проходит whitelist `["count", "sum", "avg", "min", "max", "list"]` в `parseMetrics`.
- `agg.toUpperCase()` только преобразует регистр замкнутого множества → `SUM`, `AVG`, etc.
- Интерполируется как `${sqlAgg}(...)` в SELECT — безопасно.
- **Защищён корректно.**

### withTenantTx tenantId (строка 1837)
- `SET LOCAL choros.tenant_id = '${tenantId}'` — tenantId проверяется UUID_RE на входе в `withTenantTx`.
- UUID не содержит кавычек или SQL-метасимволов.
- **Корректно, но нит: паттерн идентичен report-pages.ts — приемлем.**

### Итог по п.1
Все пути в SQL-текст через поля page_def (field_key, group_by) защищены двойным гардом (charset + whitelist). filter.op — закрытый whitelist. filter.value — параметр. agg — закрытый enum. registry_def_id — UUID regex + параметр. **Инъекция через page_def невозможна.** Найден только один edge-case (нит R-4).

## Анализ RLS/PDP и data-classification (п.2)

### Floor-2 data API
- RLS: `withTenantTx` устанавливает `SET LOCAL choros.tenant_id`, FORCE RLS на таблицах активна → cross-tenant невозможен.
- PDP: `checkReadGrant` вызывается **до** `withTenantTx` (строки 634-637) — fail-early.
- Но `defaultCheckReadGrant` сломан (R-2) — использует неправильный grant-pool.

### data-classification (T-0033 / ADR §7)
ADR §7 для T-0121g (`FF-FLOOR2-RLS`, NF-4) НЕ упоминает T-0033 masking для Floor-2 raw data endpoint. Таблица fitness §8 не указывает `FF-DATA-CLASSIF` для T-0121g. Задача T-0181 = Floor-2 RLS-gated data API; классификация полей record.data — вне scope (data-classification применяется на уровне object-handles и grant-resolver, не на уровне прямого record SELECT).

**Вывод:** Отсутствие maskFields для Floor-2 record.data **не является** blocking-нарушением scope T-0181. ADR §6/§7 для T-0121g требует только: RLS tenant-изоляция + `application read` PDP — не field-level masking.

## Нит-замечания

### R-4 (NIT) — charset `[a-zA-Z0-9_-]` включает `-` (дефис); нестандартный JSONB ключ

**Ось 5 (соразмерность/полнота)**
**Локация:** `src/http/report-page-render.ts:1745`

Дефис в field_key (например `unit-cost`) технически допустим в jsonb и проходит charset-гард. В PostgreSQL `data->>'unit-cost'` работает корректно. Проблем с инъекцией нет. Нит: в practice большинство registry_def schemas не содержат дефисов в field_key (Python/JS конвенция — underscore). Можно рассмотреть `/^[a-zA-Z0-9_]+$/` для единообразия, но это продуктовое решение, не security.

### R-5 (NIT) — Floor-2 AC-6 ожидает `denyDeps` с пустым pool (FakePool `[]`)

**Ось 1 (correctness)**
**Локация:** `src/__tests__/report-page-render.test.ts:1546`

```ts
const { server: s, baseUrl: b } = buildTestServer(denyDeps, makeFakePool([]));
```

Тест передаёт `makeFakePool([])` — пустой fake pool. При `denyDeps`, `checkReadGrant` возвращает `{ok:false}` **до** попытки подключиться к пулу, поэтому 403 всегда вернётся. Если когда-либо будет добавлена логика, требующая пул до auth-гейта, тест сломается незаметно. Нит: добавить комментарий «denyDeps fires before pool touch».

- **R-1**: Floor-1 `/render` без PDP-gate (actor воидится, ADR §6 нарушен).
