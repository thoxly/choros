## Findings

### R-1 · BLOCKING · Axis 4 (ADR-соответствие) — `lossy live-migration` не покрыта operation table

**Location:** `docs/specs/T-0078-authoring-redlines.spec.md:22-33`, `src/core/authoring-redlines.ts:56-65`

**Issue:**  
ADR §4 (RED-LINES, строка 154-155) явно перечисляет следующие категорически-gate операции:

> «drop/rename поля, lossy type-change, **lossy live-migration**, delete/rename core/system-directory-поля.»

Операция `lossy live-migration` (Camunda-grade `fromActivity→toActivity` перенос инстансов при деструктивном изменении schema; rollback при живых инстансах — ADR §7, строки 246-248) в `AuthoringOpKind` отсутствует. Спека (таблица охвата, строки 22-33) её тоже не включает, и в `Out of Scope` (§5 спеки) она не упомянута явно.

**Оценка серьёзности:**  
Формально T-0078 заявлен как guard для "форм и объектных схем" (`form_def`, `object_schema`). Однако ADR §4 перечисляет `lossy live-migration` в одном ряду с остальными red-lines без разделения по домену. Отсутствие операции в вокабуляре = gap в coverage гарда. Spec должен либо (а) явно поместить `live_migration` в Out of Scope с указанием задачи, которая покрывает её (T-0084, T-0085 или иная), либо (б) добавить `live_migration` в `AuthoringOpKind` и накрыть тестом.

**Suggestion:**  
В `docs/specs/T-0078-authoring-redlines.spec.md` §5 (Out of Scope) добавить:
```
- Lossy live-migration операции (Camunda-grade instance rerouting) — отдельная задача (TODO: вписать номер)
```
Либо добавить `live_migration` в `AuthoringOpKind` с классификацией `destructive` (non-core) / `core_pinned` (core) и один тест AC-19.

**Location:** `docs/specs/T-0078-authoring-redlines.spec.md:61-62`, `src/core/authoring-redlines.ts:265-273` (`isValidConfirm`)

**Suggestion:**

Вариант Б (full): добавить константу `FORBIDDEN_STATEMENTS` (напр. `["yes", "ok", "да", "нет"]`), реализовать проверку, добавить AC-19 + тест.

## Анализ семантического confirm (п.2 из задания ревью)

**Вопрос:** `consequenceStatement ≥ 10` — это «семантический» confirm или length-чек?

**Вывод: length-чек с двумя оговорками.**

ADR §4 формулирует цель: «Подтверждение — семантическое («поле X удаляется, данные теряются»), не техническое.» Цель — чтобы человек НАПИСАЛ последствие словами, а не нажал кнопку. Реализация:

```ts
const MIN_CONSEQUENCE_LENGTH = 10;
return confirm.force === true &&
       typeof confirm.consequenceStatement === "string" &&
       confirm.consequenceStatement.trim().length >= MIN_CONSEQUENCE_LENGTH;
```

Строка "1234567890" (10 цифр) проходит проверку. "удалить ок" (10 символов) проходит. Это НЕ семантика — это length floor.

**Почему это тем не менее честный floor:**

1. ADR §4 не формализует алгоритм semantic-check — он описывает UX-ЦЕЛЬ. Машинная проверка семантики строки требует LLM-судьи, который spec явно исключает из scope (comment в impl: «пустой шаблон» — отдельная проверка, которую spec обещает, но impl не делает).

2. Length-floor = минимальный ненулевой барьер против кнопки-OK (boolean флага). HTTP-слой (T-0073) и UI-форма несут ответственность за то, чтобы поле consequenceStatement заполнялось осмысленно (placeholder, server-side prompt, label). Гард — последняя линия, а не первая.

3. Граница 10 символов = содержательный выбор: в русском «да удалить» = 9 символов с пробелом (deny), «да, удалить» = 11 (allow). ADR §4 говорит «не техническое» — 10 char обеспечивает минимум нескольких слов. Это не "один символ" и не "один слог".

**Однако:**  
ADR говорит «семантическое» — реализация даёт length. Это ЧЕСТНЫЙ пол, но НЕ семантика в полном смысле. Задача назвала этот guard «semantic human-confirm», но реализовала «length-floor human-confirm». Это нужно зафиксировать в комментарии: "length-floor = минимальный барьер против OK-флага; истинная семантическая валидация = UX-слой (T-0073)."

**Итог по п.2:** length=10 — не выродившийся floor (он несёт реальный барьер), но и не семантический чек (машинно семантику не проверить без LLM-судьи). Честный вывод: **нит/честный floor**, не blocking при условии, что комментарий в коде явно признаёт ограничение. Blocking из R-2 — про пропущенную forbidden-template проверку, которую spec обещает.

## Архитектурные наблюдения (non-blocking)

1. **core_pinned = корректно строже T-0177.** T-0177 разрешает `force` escape-hatch для registry_def.record_schema. T-0078 для core-pinned полей escape-hatch запрещает. Это точно соответствует ADR §5 «БЛОКИРУЕТ delete/rename/overwrite» — без исключений. Архитектурно верно.

2. **isLossyFieldChange vs isLossyNarrowing (T-0177).** Функция не скопирована механически — она выведена из тех же ADR §4-критериев с явной ссылкой на прецедент в комментарии. `FieldSchemaEntry` правильно импортируется из `schema-change-classifier.js`. Дублирование типа отсутствует.

3. **conservative default для missing schemas.** `op.oldSchema ?? {}` → `op.newSchema ?? {}` для `change_type` без схем → `non_destructive`. Это документировано в комментарии как «HTTP-слой обязан передавать схемы». Консервативный дефолт корректен: лучше пропустить операцию и поймать на HTTP-слое, чем ложно заблокировать.

4. **FieldSchemaEntry re-export.** `export type { FieldSchemaEntry }` из модуля — удобство для вызывающего кода (T-0073). Не нарушает purity.

5. **Симметрия с ADR §9 гард 7.** default-DENY реализован корректно: non_destructive → allow, destructive без confirm → deny, core_pinned → deny всегда. Это строже enumerated-allowlist (T-0078 требует позитивного подтверждения, не absence of blocklist).
