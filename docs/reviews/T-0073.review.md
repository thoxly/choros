## 2. Ось 1 — Корректность (ADR/спека)

### 2.1 Classifier-гейт: WRONG_FLOOR

Классификатор T-0074 вызывается корректно: `validateFloor1Request` первым делом
вызывает `classifyAuthoringFloor({kind: request.kind as FormEditKind})` и при
`requiredFloor === '2'` возвращает `WRONG_FLOOR` с fail-fast. Все 8 Floor-2 kinds
(AC-14 в тестах) блокируются на уровне core.

**Оговорка по HTTP-тесту AC-22.** Тест `HTTP AC-22 — Floor-2 kind in body.edit → 409
WRONG_FLOOR` фактически проверяет 400, а не 409 — потому что `parseEditRequest`
перехватывает unknown kind через `default: case → HttpError(400)` ДО того, как
запрос доходит до `applyFloor1Edit`. Это задокументировано в самом тесте комментарием,
но названо вводящим в заблуждение: заголовок AC-22 заявляет 409, а тело ожидает 400.
Путь 409 тестируется только на уровне core (AC-14), не на HTTP-уровне.
Классифицирую как **нит** (нет false-pass, путь покрыт, документация честная).

### 2.2 6 Floor-1 kinds поддержаны

Все 6 kinds из `FLOOR1_EDIT_KINDS` реализованы в `applyFloor1Edit`: relabel_field,
toggle_required, hide_field, show_field, reorder_fields, set_help_text. Switch-ветки
полны, соответствуют типам T-0074. Нарушений нет.

## 3. Ось 1 — Binding-инвариант (п.2)

### 3.1 Неизменность key (checkBindingCompat)

Floor-1 операции не добавляют и не удаляют поля из binding: key-множество
`Set(fields[].key)` остаётся идентичным до и после любой Floor-1 трансформации.
`checkBindingCompat` (T-0072) проверяет именно ключевое множество
(`Set(fields[].key) === bpmnVarNames`). Таким образом, после Floor-1 правки
`checkBindingCompat` тривиально вернёт ok:true — вызов в HTTP-слое ничего
не защищает, но и не вреден.

Однако **HTTP-докстринг в строке 21–24 `floor1-editor.ts` утверждает:**
> `checkBindingCompat() is called after transformation to assert fields ↔ bpmnVars`

Фактически в коде `checkBindingCompat` **НЕ вызывается**. Из `binding-compat.ts`
импортируется только `validateBindingFields`. Это мислидящий CONTRACT-комментарий —
нит (функционально безопасно, т.к. вызов был бы no-op; docstring вводит в заблуждение).

### 3.2 toggle_required и required-ужесточение

`toggle_required` изменяет `BindingField.required` — контракт-поле binding.
ADR §9.1 признаёт `toggle_required` Floor-1 операцией без human-gate. Это верно:
`required` — UI/validation-флаг, не schema-структура в смысле BPMN-variables.
`checkBindingCompat` не проверяет `required` (смотрит только на ключи).
required-ужесточение (`false → true`) может сломать form-code, ожидающий optional,
но это клиентская логика, вне scope binding-compat-контракта T-0072.

**Blocking гарда нет, и это соответствует ADR.** Проблемы нет в рамках этой задачи.
Если в будущем потребуется required-compat-check — это задача T-0078 (red-lines).

## 4. Ось 3 — Безопасность / Authz (BLOCKING)

### 4.1 Только аутентификация, нет авторизации

`floor1-editor.ts:335`: роут вызывает `extractActor(req)` — проверяет наличие
`x-dev-user` заголовка и выбрасывает 401 при отсутствии. Это аутентификация.

Сосед `binding.ts` (POST/GET `/tenants/.../binding` — та же `form_binding` таблица)
имеет явный `checkRole(client, tenantId, actorId)` → 403 FORBIDDEN при отсутствии
роли `process_designer`. Авторинг формы — management-операция (ADR §4: «Системный
config-агент = сотрудник в оргструктуре, роль→MCP-tools»).

Floor-1 редактор позволяет любому аутентифицированному пользователю (x-dev-user)
редактировать форму любого тенанта (UUID из URL), не проверяя наличие
`process_designer` или какой-либо другой авторизующей роли.

**Риск:** любой знающий tenantId и format URL может изменить форму, не имея
соответствующих прав. Это несоответствие классу операции (management/authoring)
и паттерну соседей.

**Нюанс Mode A (stateless):** роут не пишет в БД (клиент сам должен персистировать
через PATCH /binding). Это частично смягчает немедленный риск, но не устраняет:
(а) уже сейчас существуют планы перехода на Mode B (DB-read-through); (б) форма
авторинга требует authz по принципу least-privilege независимо от storage-механики.

**Фикс:** добавить `checkRole`-паттерн из `binding.ts` с аналогичным dev-mode
смягчением (не blocker для тестов без KC), либо явно задокументировать ADR-решение
об отложенном authz с конкретным тикетом (если статeless Mode A признаётся dev-only
surface). В любом случае 403-путь должен быть тестируемым.

`checkRole`. В dev auth mode (`getAuthMode()` = dev) — смягчить до «authenticated»
(аналогично binding.ts строка 98). В keycloak mode — проверять наличие
`process_designer` в `role_assignment` для данного тенанта и актора. Добавить
тест AC на 403 FORBIDDEN (analogous to AC-23 для 401).

**R-N1 (nit):** Убрать из docstring строку 21–24 упоминание `checkBindingCompat() is called`
или заменить на честный комментарий: `checkBindingCompat not needed: Floor-1 ops
preserve key-set (no add/drop) → always ok:true`.

`HTTP AC-22 — Floor-2 kind → 400 VALIDATION (WRONG_FLOOR 409 path covered at core in AC-14)`.
