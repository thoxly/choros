## Сводка

Изменение добавляет диагностический explain-эндпоинт через trace-режим в `resolveFor`
(опциональный 7-й параметр `traceOut?: TraceCollector`, 9 trace-точек) + роут
`POST /api/pdp/explain`. Идея «единой логики» (вердикт explain == вердикт резолвера
структурно, не копией) — архитектурно верная. Но реализация имеет **красный CI (lint)**
и две содержательные дыры в анти-oracle/верности трассы.

**Вердикт = `changes_requested`** по двум независимым основаниям:
1. CI-lint красный (роль-правило 2: красный CI → авто-changes_requested).
2. Blocking-findings по осям 2/3/4 (анти-oracle авторизация не покрыта тестами;
   stub RecordSource + неподключённые effects/sod делают трассу неверной и расходящейся
   с боевым вердиктом для не-read операций — нарушение центрального AC-1).

## Ось 1 — Поведенческая неизменность резолвера (ГЛАВНАЯ, max-риск) — ЧИСТО

Прочитан diff `src/core/grant-resolver.ts` построчно против merge-base.

- **Control-flow без изменений.** Все `traceOut?.push(...)` стоят ПЕРЕД соответствующим
  `return`/после установления факта. Ни один ранний return не добавлен/убран/переставлен.
  При `traceOut === undefined` `?.` делает все push no-op — байт-в-байт прежнее поведение.
- **Рефактор шага 3 эквивалентен.** Оригинал — один `.filter()` с цепочкой `return false`
  (tenant→op→isEffective→isLatticeScope→isNarrowerOrEqual). Новый код разбит на
  `effective` (tenant+op+isEffective) и `scopePassed = effective.filter(isLatticeScope &&
  isNarrowerOrEqual)`, `covering = scopePassed`. Итоговое множество **идентично** (та же
  конъюнкция предикатов). Порядок вычисления `isLatticeScope` перед `isNarrowerOrEqual`
  сохранён (short-circuit во втором фильтре) → `isNarrowerOrEqual` по-прежнему не вызывается
  для не-lattice scope. Никаких побочных эффектов у предикатов нет.
- **Тесты не правлены.** `git diff` по `src/**/*resolver*` показывает изменён только
  `grant-resolver.ts`; добавлен лишь новый `src/__tests__/pdp-explain.test.ts`. 48
  grant-resolver тестов зелёные БЕЗ модификации.
- **FF-гейты зелёные:** `single-resolver.sh` PASS, `grant-resolver-isolation.sh` PASS
  (frozen-модули не тронуты, нет второй authority, порты не обойдены).
- `tsc --noEmit` чисто. Полный test-suite: 1407 passed / 6 skipped.

**Вывод оси 1: правка ядра безопасна. Поведенческая неизменность подтверждена.**

## Ось 2 — Trace не ослабляет fail-closed — ЧАСТИЧНО (см. R-3)

- `collector.push` — чистый append в массив, бросить не может; `maskedFields`-цикл
  (vis × fields/raw) — чистая итерация, без IO/throw. Изоляция trace от вердикта корректна:
  push стоит ДО return, не влияет на возвращаемое значение. Утечки trace в обычный ответ нет.
- НО: trace в explain-роуте бежит на **stub RecordSource + неподключённых effects/sod**.
  Сам fail-closed `resolveFor` не нарушен, но **трасса не отражает боевые fail-closed
  ворота** (record/effect/sod) — см. R-3, R-4.

## Ось 3 — Anti-oracle — BLOCKING (R-1)

- Маскинг-анти-oracle структурно есть: для `self` HTTP-слой срезает `maskedFields`
  (строки 430-436), оставляя только `governed`. Соответствует инв-4/AC-8.
- **НО вся authz-поверхность (`checkExplainAuthz`, 403 EXPLAIN_FORBIDDEN, self/admin,
  срез maskedFields) не покрыта НИ ОДНИМ тестом.** Комментарий-матрица в тесте (стр.18)
  обещает «authz: 403 for non-admin caller (HTTP layer)», но соответствующего теста нет
  (grep по `EXPLAIN_FORBIDDEN|checkExplainAuthz|403` в тест-файле — пусто). AC-9/AC-10
  заявлены покрытыми, фактически не верифицированы. Это самый чувствительный (анти-oracle)
  контур правки ядра — оставлять его без теста недопустимо.

## Ось 4 — Верность трассы / stub RecordSource — BLOCKING (R-2, R-3)

- **stub RecordSource всегда non-null** (`__explain_sentinel__`, стр.395/401). Значит шаг
  `record_fetch` в боевом эндпоинте **никогда не покажет `not_found`** — трасса ВРЁТ о
  record-этапе (всегда зелёный), даже если реальная запись отсутствует. AC-6 в ADR заявлен
  покрытым, но HTTP-путь его произвести не может (покрыт лишь юнит-тестом через прямой
  `nullRecord()`, не через эндпоинт). Ограничение нигде в ответе не задекларировано — клиент
  explain не отличит «запись есть» от «record-этап подделан».
- **effects/sod не подключены** в `explainDeps` (стр.404-406). Для `op ∈ {invoke}` боевой
  `resolveFor` проверяет effect-гранты (может вернуть `no_effect_grant`), а explain — нет
  (блок пропущен, шаг `effect_grants` не эмитится). Для `op ∈ {approve, transition}` боевой
  путь гоняет SoD, explain — нет. → **explain.verdict РАСХОДИТСЯ с боевым вердиктом для
  не-read операций** — прямое нарушение центрального AC-1 («verdict совпадает для матрицы
  кейсов»). Эндпоинт принимает все 7 операций (VALID_OPS, стр.255), но честен только для read.

## Ось 5 — Property-тест AC-1 — ЧАСТИЧНО (R-5, nit)

- Property-тест есть (`property: explain verdict matches resolveFor verdict`, 9 кейсов).
  Но он сравнивает `resolveFor`-без-trace против `resolveFor`-с-trace на ОДНИХ И ТЕХ ЖЕ
  deps. Это валидирует NF-1 (trace не мутирует вердикт) — ценно и корректно. **Но не**
  валидирует заявленный AC-1: «вердикт ЭНДПОИНТА == боевой вердикт PDP». Эндпоинт использует
  stub-record и урезанные deps; для read-без-маскинга совпадает, для invoke/approve/transition
  — нет (R-2). Матрица кейсов содержит только `read`; ни одного invoke/approve/transition.

## Ось 6 — Гейт-дисциплина — ЧАСТИЧНО (R-6 blocking: lint красный)

- Резолвер-правка легальна: `single-resolver.sh` + `grant-resolver-isolation.sh` зелёные.
- tsc чисто, 1407 тестов зелёные.
