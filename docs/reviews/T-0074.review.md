## 2. Словарный audit: §9.2 / §4 ADR против FLOOR1/FLOOR2

### Floor-1 — согласно ADR §9.1 и T-0073

ADR §9.1 (extensibility-and-authoring.md строка 287–289):
> «Все field-level правки (relabel / hide / toggle-required / порядок / **help-text**),
> не токен-подмножество — кнопочные, zero-LLM, переживают агента-офлайн.»

T-0073 в task DB (title):
> «E11.2 · Floor-1 — декларативный JSON-Schema+UI-schema, кнопочный zero-LLM редактор
> (relabel/hide/required/order/**help**), бэкенд-валидация [ADR §4/§9.1]»

Пять операций по ADR/T-0073:

| ADR / T-0073 операция | Kind в FLOOR1_EDIT_KINDS | Статус |
|---|---|---|
| relabel | `relabel_field` | ЕСТЬ |
| hide | `hide_field` + `show_field` | ЕСТЬ |
| toggle-required | `toggle_required` | ЕСТЬ |
| order / порядок | `reorder_fields` | ЕСТЬ |
| **help-text / help** | _(отсутствует)_ | **MISSING** |

Кодер сложил `help-text` в docstring `relabel_field`: «изменить label / placeholder /
help-text поля». Но T-0073 трактует `help` как **отдельную кнопку** — если T-0073
эмитит change с kind `set_help_text` (или аналогичным), классификатор отправит его
в unknown → Floor-2. Это нарушает §9.2: тривиальная Zero-LLM операция wrongly
escalated to Floor-2. Blocking.

источник истины — без этого контракт между T-0073 и T-0074 неформален и уязвим.

Расхождение — нит, не blocking.

тавтологично (если бы set был пуст, тест всё равно проходил бы). Однако:

Тавтология AC-1/AC-2 (meta-loop) — мягкая: защищает от неожиданных изменений в
sets между test-runs, но не верифицирует _содержание_ sets. AC-9/AC-10 — реальное
покрытие. Нет false-pass рисков за исключением пропущенного kind (blocking R-1).
