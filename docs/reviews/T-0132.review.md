## Blocking findings

### R-1 [blocking · axis 4 (соответствие ADR/эталону) · `T-0132-pilot-rollout.adr.md:122-138` (§3.3), таблица §0 строка `meet`, §10/§13]

**`meet(node, interval)` НЕ даёт `set([node, interval])` в живом коде — формула компиляции
§3.3 фактически неверна против `grant-lattice.ts`.**

ADR §3.3 (строки 127-135) и таблица §0 (`meet (⊓) для interval … [ЖИВОЙ grant-lattice.ts:367-372]`)
утверждают, что `derivedScope` пилота получается **живым** `meet`:
```
meet({kind:"node",…}, {kind:"interval",…}, ancestryOracle)  // ⇒ {kind:"set", members:[node, interval]}
```
Сверено по исходнику (`sed -n` подтверждён):
- `meet` (`grant-lattice.ts:298-334`) для двух **различных НЕ-set атомов** падает в
  `atomMeet` (`:333`), а `atomMeet` для node⊓interval возвращает **`BOTTOM`** (`:376`,
  комментарий `// Distinct non-set kinds: ⊥`). НЕ `set`.
- Ветка, строящая `set`, в `meet` есть **только если один из операндов УЖЕ `set`** (`:307-330`).
  `node ⊓ interval` сюда не попадает.
- `meet` — это **⊓ (greatest-lower-bound / пересечение)**, а не конъюнкция-в-set. Чтобы
  получить `set([node, interval])` нужно `normalize({kind:"set", members:[node, interval]})`
  напрямую (живой `normalize` `:124-168`), а НЕ `meet`.

Цитата `grant-lattice.ts:367-372` указывает на ветку **interval ⊓ interval** (`:367`), которая
к комбинации узла и интервала отношения не имеет — это **мис-цитата, маскирующая семантический
разрыв**. Несущая [ЖИВОЙ]-опора «комбинация через `meet`/⊓» (§1 стр.55, §3.2 стр.116, §3.3
стр.131-135) ложна.

**Почему blocking, а не nit:** это центральный механизм ADR («понятие материализуется
существующими грант-кортежами через живой `meet`»). Если `meet` здесь не работает, тезис
«ноль нового scope-примитива, всё живо» теряет одну из двух опор. T-0129 §10.1 называет scope
пилота как `set([node,interval])` — то есть конструкция-цель верна, но **способ её получения в
ADR назван неправильным живым символом**.

**Suggestion:** заменить в §3.3/§0/§1/§3.2 `meet(node, interval)` на прямое построение
`normalize({kind:"set", members:[node, interval]})` (живой `normalize` `grant-lattice.ts:124`),
и переписать клейм строки §0 с «`meet (⊓) для interval [ЖИВОЙ :367-372]`» на честное
«`set`-конструктор + `normalize` [ЖИВОЙ :124]; `meet` НЕ применим к node⊓interval (даёт ⊥)».
Либо, если архитектор настаивает на `meet`-пути, показать, что один операнд приходит уже как
`set` — но в §3.3 оба операнда атомарны, так что это не спасает.

### R-2 [blocking · axis 4 + axis 6 (security-линза: необеспеченная граница авторизации) · `T-0132-pilot-rollout.adr.md:55-60` (§1), §3.3 стр.142-146, §5 стр.191-196]

**«Сумма кейса проверяется интервалом на живом `resolveFor`» — НЕ обеспечено живым read-path:
значение axis (сумма) в `handle.ref` НЕ кладётся, и узел пилота на `hierarchy:"org"`
структурно несравним с resource-handle.**

Адверсариальный вопрос «откуда БЕРЁТСЯ сумма кейса при resolve» — проверен по коду:
- Живой `resolveFor` (`grant-resolver.ts:489`) выводит проверяемый scope так:
  `const handleScope = refToScope(handle.ref)` (`:507`).
- `refToScope` (`:178-200`) возвращает **исключительно `{kind:"node", hierarchy:"resource", …}`**
  (application / registry / record). Комментарий `:169` прямо: «map a handle's **identity-only**
  ResourceRef». **Никакого `interval` с суммой кейса handle не несёт.**
- В `grant-resolver.ts` **ноль** упоминаний `axis`/`amount`/`interval` (grep пуст). Сумма кейса
  на read-path в scope не попадает — её некому туда положить.
- Двойная несравнимость: пилотный `set([org-node, interval])` против resource-`node`:
  `isNarrowerOrEqual` (set-parent ветка `:250`) требует, чтобы handle ⊑ **хотя бы одного**
  члена. org-`node` имеет `hierarchy:"org"`, handle — `hierarchy:"resource"` ⇒
  `atomIsNarrowerOrEqual` вернёт false (разные иерархии, `:269`); interval-член против
  resource-node — cross-kind ⇒ false. Итог: пилотный грант **никогда не покрывает кейс** на
  текущем живом резолвере, либо (если игнорировать org-узел) граница по сумме **не
  проверяется вовсе**.

То есть утверждение §5 (стр.191-196) «кейс с суммой выше интервала по `isNarrowerOrEqual`
(`:279`)/`isEffective` не применим — `resolveFor` вернёт `no_grant`» **НЕ выполняется живым
кодом**: чтобы interval-предикат связался с суммой кейса, нужна НЕ-существующая проводка
«поле записи (amount) → `handle.ref` → `refToScope` → interval-элемент scope». Это **НОВАЯ
работа** (расширение `ResourceRef`/`refToScope` axis-проекцией + источник значения axis из
поля кейса + кто его кладёт), а ADR помечает её как **[ЖИВОЙ]** (§0 строки resolveFor :489 /
isNarrowerOrEqual :279) и заявляет «прошлый класс blocking снят».

**Security-линза:** это «необеспеченная решёткой граница» — ровно тот класс, который сам ADR
объявляет катастрофой в Rejected-alt (§14 строка про if-фильтр). На живом коде граница по
сумме сейчас **либо не существует, либо отдаёт `no_grant` на ВСЁ** (drain по полному процессу
маскирует это: вне-срезовый и в-срезовый кейс одинаково уходят в полный процесс). То есть AC-2
(«интервал = grant-предикат в той же ⊑-проверке») и AC-5 («граница = следствие резолюции»)
текстуально присутствуют, но **не реализуемы на заявленной живой основе без новой проводки**.

**Suggestion:** добавить в §0/§3.3/§5 честный клейм **[НОВАЯ B-N]** «проекция axis-значения
кейса (напр. `amount` из поля записи) в resolve-scope: расширение `ResourceRef`/`refToScope`
(или передача axis-контекста в `resolveFor`), плюс источник значения axis и кто его кладёт в
handle». Указать, что interval-axis на read-path сегодня **не вычисляется** (resolver
identity-only, `:169`) и это часть build-задачи, а не живой механизм. Снять формулировку
«прошлый класс blocking снят» в части интервала-по-сумме — он снят для node-оси, но НЕ для
amount-оси. Опционально вынести в SEAM/role-gap: реестр осей (SEAM-3) + проводка значения оси —
связанные открытые куски.

## role_gap_evidence

Класс «doc-foundations-линтер (FF-1) проверяет присутствие символа, но не корректность его
применения» — рецидив FE-W23-0008-семейства (ADR ссылается на живой символ, делающий НЕ то,
что заявлено). Кандидат в `ledgers/role-gaps.md`: foundations-check должен уметь негатив-ассерт
на мис-применение (напр. «§ не утверждает `meet(A,B)⇒set` если A,B атомы разных kind»).
Систематический риск: «зелёный FF при ложном [ЖИВОЙ]».
