## 3. Adversarial probes (all survive)

1. **FF-RENDER-VIA-PDP executable / no renderer bypasses resolveFor?**
   ✓ Designed enforceable. §2.1 zone table + §2.3 mandate per-record `resolveFor`+`projectFields`;
   FF-RENDER-VIA-PDP greps `from .*record` in `document-render*` ⇒ must route via PDP-port, plus an
   AST/import rule. §10 step 3 wires `render` to take `deps.resolver`, not a raw record repo. The
   batch-read is "batch of per-record `resolveFor`" (§2.3 "per-запись"), NOT a bulk SELECT bypassing
   PDP — the invariant is explicit and grep+import-lint can hold it. Executable.

2. **Omission vs masking — honest split vs T-0118/T-0033 maskFields semantics?**
   ✓ ADR is precise. T-0033 `maskFields` produces FOUR transforms (reveal/partial/redact/hash) for
   *visible-but-classified* fields, AND `drop`=omission for fields outside clearance/visibility. The
   ADR uses ONLY the `drop`/omission path for *invisible* records/fields (§2.3 step 3, rej-7), and
   inherits the full mask-transform set for *visible* fields via `projectFields`→`maskFields` (it
   says "проходит тот же транс­форм, что обычное чтение", §0 last bullet / §2.3). So: invisible ⇒
   drop (omit, anti-oracle); visible-classified ⇒ T-0033 mask transform. No conflict — the ADR does
   not claim "everything is dropped"; it claims "invisible is dropped, visible goes through the same
   masking as a normal read." Honest.

3. **Snapshot reproducibility / render-vs-fix race?**
   ✓ Adequately closed by design. `renderAndFix` (§2.5) is `render()` → `addVersion(bytes)` — the
   bytes are captured at render time and frozen as an immutable `file_version`; a later `record`
   mutation cannot retro-alter the stored bytes (FF-V immutability, T-0119). `sourceDigest` is over
   the *projected rows already in hand*, not a re-read. There IS a benign live-window between read
   and addVersion, but that is inherent to any point-in-time snapshot and is exactly what
   `renderedAt`+`sourceDigest` in RenderMeta record. NF-2/FF-REPRODUCIBLE test (AC-13) pins it:
   fix → mutate → re-download = byte-identical. No reproducibility hole.

4. **live-no-cache vs anti-DoS (render per QR-scan)?**
   ✓ Correctly deferred, not silently dropped. §4 + §5 rej-8 explicitly: anti-DoS/rate-limit/TTL is
   *inherited as a T-0122 deploy-time parameter* (T-0122 §8/§10), NOT re-invented here (NF-5). The
   external channel (where the DoS surface lives) is wholly T-0122's; T-0124 only supplies bytes.
   This is the right boundary — T-0124 introducing its own rate-limiter would violate
   FF-NO-DUP-SUBSYSTEM. The deferral has an owner (T-0122) and is not hand-waved.

5. **template_dep mirrors report_page_dep — does FF-NO-DUP-SUBSYSTEM self-violate?**
   ✓ No. The ADR is careful: `template_dep` is "расширение T-0121 `report_page_dep`-модели, не
   четвёртый механизм" (§2.9) — it adds a TSV row to the *existing* `bundle_members.txt` and
   *extends* the *existing* `bundle-coherence.sh` with one check, mirroring how T-0121 extended
   T-0072. The "one control plane (NF-1)" claim holds: T-0072 (form→schema) / T-0121 (page→schema) /
   T-0124 (template→schema) are three consumers of ONE named-binding coherence discipline, each a
   pure `check*Compat` function, one shared CI guard. Not a new subsystem. (Caveat: this depends on
   the impl actually extending `bundle-coherence.sh` rather than forking a script — FF-NO-DUP-SUBSYSTEM
   + the `bundle_members.txt` membership requirement enforce it.)

6. **T-0121 boundary — report_page vs template_def, two paths to "document from data"?**
   ✓ Boundary is sharp (§2.8 FF-NOT-T0121, spec FR-6). T-0121 = *UI page* to a manager (React over
   aggregation, interactive surface). T-0124 = *file artifact* (csv/html bytes for download / external
   party / snapshot). Different surfaces, different outputs (rendered React vs downloadable bytes),
   different consumers (internal manager vs external/file). The ONLY shared layer is template↔schema
   coherence (§2.9), explicitly reused not duplicated. Not competing mechanisms.

7. **FF self-tests executable now?**
   ✓ FF-NO-RENDER-ACL grep returns ∅ on-branch (no render_acl/document_visibility yet — correct
   pre-impl state). FF-NO-DUP `render_log` grep returns ∅. `bundle_members.txt`+`known_tenant_tables.txt`
   present for the registry-extension FFs. All grep-based FFs are concrete and runnable; test-based
   FFs (FF-REPRODUCIBLE/AUDIT/LIVE-NO-CACHE) bind to AC-11..14.
