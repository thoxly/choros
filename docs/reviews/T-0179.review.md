### Ось 2 — Соответствие ADR/спеке

**ADR §5.4 (T-0121):**  
§5.4 требует: (а) добавить `report_page_dep` в `bundle_members.txt` как `kind=choros_table` — выполнено. (б) добавить `check-report-page-deps` в `bundle-coherence.sh` — здесь автор интерпретировал «в» как «в систему bundle-coherence», создав companion-скрипт вместо правки frozen T-0082 файла. (в) пройти `bundle-coherence.sh` — пройден (exit 0).

Интерпретация (б) аргументирована в spec §"Легальность пути": `bundle-coherence.sh` заморожен (owned T-0082, FF-FCI1 предотвращает правку из T-0179 branch), поэтому companion-скрипт — единственно допустимый путь. Fitness-chain в `package.json` включает оба скрипта последовательно. FF-BUNDLE-DEPS (`bundle-coherence.sh` содержит `check-report-page-deps`) трактуется как «bundle-coherence CI-слой содержит эту проверку» — и она там есть через `package.json` chain.

Нит: ADR FF-BUNDLE-DEPS буквально говорит «`bundle-coherence.sh` **содержит** `check-report-page-deps`» — в `bundle-coherence.sh` нет делегирования в `check-report-page-deps.sh`. Companion полностью покрывает смысловое требование, но формально FF-BUNDLE-DEPS вернее читать как «CI-слой bundle-coherence *теперь включает* check-report-page-deps». Это document-precision nit, не семантический разрыв.

## Known Environment — кросс-веточное загрязнение template (T-0180)

**Статус:** ПОДТВЕРЖДЕНО. Не дефект T-0179.

**Данные:**  
`choros_test_template` (общий Postgres-шаблон для виртуальных тест-клонов): `migration 053_author_report_page_seed` применена.  
```
SELECT version FROM choros.schema_migrations ORDER BY version DESC LIMIT 1;
→ 053_author_report_page_seed
```

Это миграция соседней задачи T-0180 (MCP-seed `author_report_page`). T-0179 branch содержит migrations только до 052. Когда T-0180 запускал `fitness:db`, она применила migration 053 к template, добавив 1 `mcp_tool` строку (`author_report_page`) + 2 grant строки.

**Следствие:** `config-agent-seed.test.ts` ожидает ровно 7 `mcp_tool` rows (от migration 044) и 7 grants. Клоны, созданные из contaminated template, содержат 8 mcp_tool + 9 grants → AC-02/AC-04 fail.

**Проверка `SELECT count(*)` в clone:**  
Три существующих clone-DB (`choros_test_1781200550484_ea76`, `_5e04`, `_6244`) — созданы ДО загрязнения template → каждая содержит 7 mcp_tool (ожидаемо). Template содержит 8. Новые clone-DB (создаваемые в ходе `fitness:db` run из T-0179 worktree) будут наследовать 8 → config-agent-seed.test.ts падает.

**Механизм:** `globalSetup.ts` делает `CREATE DATABASE runId TEMPLATE choros_test_template` → clone наследует все строки template включая migration 053 данные. T-0179 тест-файлы (`report_page_bundle_deps.test.ts`) сами по себе зелёные (3/3).

**Гэп T-0147 материализован как отдельная задача** (согласно контексту) — template-reset/isolation механизм.

**Вывод:** fitness:db для T-0179 в текущем shared-template окружении даёт загрязнённый прогон. Это среда, не код T-0179. Reviewer верифицировал T-0179-специфичные тесты (`report_page_bundle_deps.test.ts`) на clean-clone — все зелёные.
