### Корневая причина обоих blocking
Ownership доказывается **двумя атакуемыми строками**, обе полностью под контролем нарушителя:
1. **строка 2 файла** (`# T-XXXX ·`) — нарушитель её переписывает (PROBE 2, 3);
2. **имя ветки** (`task/T-XXXX-*`) — нарушитель её называет как хочет (PROBE 5).

Чек сверяет строку 2 файла С именем ветки — но обе подделываются самим агентом, между ними нет независимого якоря (нет сверки `header_tid` с заголовком в **BASE_REF**-версии того же файла; нет сверки TASK_ID-ветки с реальным claim в control-plane). В результате гейт, который должен делать ослабление чужого инварианта **CI-видимым до PR** (спека §2), пропускает его зелёным: достаточно одной лишней строки правки (переписать заголовок) или правильно назвать ветку. Это ровно retro-класс T-0035/T-0118 с минимальным «обходным манёвром».

### Почему это blocking, а не accepted-risk
Орк-контекст упоминал границу «порог — ошибающийся агент, не адверсарий», **но в спеке и ADR этой формулировки НЕТ** (grep по обоим документам: совпадений по «адверсар/ошибающ/порог/захват/ownership-rewrite» — нет). Спека §7 «Out of scope» перечисляет: контроль содержимого собственного чека, non-task ветки, переименование (=D+A), семантику bash, .ts/migrations, GitHub Actions. **Захват ownership через переписывание заголовка и спуфинг через имя ветки в Out-of-scope НЕ перечислены.** По правилу ревью: неупомянутая дыра в защитном инварианте = blocking, не «approved с оговоркой».

PROBE 4 и 7 — **accepted**: .txt-реестр (FR-6.2, AC-9) и package.json явно вне glob `ci/checks/*.sh` по дизайну (спека §7). Отмечены как nit/остаточный риск.

## 5. Findings

- **R-1 (blocking, ось 4 — соответствие назначению):** ownership-capture обход. Правка чужого `ci/checks/*.sh` + переписывание строки 2 на свой `# T-XXXX ·` → PASS. Репро: PROBE 2/3 выше. TASK_ID из имени ветки не верифицируется против реального claim. Минимум: задокументировать как явный accepted-risk в ADR §7 с обоснованием (полагаемся на review diff заголовка) — тогда станет minor; иначе закрыть (напр. для существующих файлов требовать совпадения заголовка в BASE_REF).
- **R-3 (nit / accepted, ось 5):** урезание `known_tenant_tables.txt` (не только аддитив) проходит. Соответствует FR-6.2 (txt вне области), но спека обещает «аддитивные правки» — деструктивные тоже проходят. Остаточный риск, принят дизайном.

### Новый пробой fallback `git show HEAD:path` (HEAD под контролем атакующего)
Fallback срабатывает ТОЛЬКО когда `BASE_REF:path` пуст. Прогнаны два сценария:
- **FALLBACK-B** (имя ЕСТЬ в BASE с чужим заголовком T-0044; ветка коммитит свою-заголовок версию `# T-0999 ·`, так что `HEAD:path`=T-0999, затем правит): результат — `BASE_REF:path` непуст (возвращает T-0044), fallback НЕ срабатывает, **exit 1**. BASE-проверка существования выигрывает, как и требовалось в задании. Захват чужого ИМЕНИ через последовательность коммитов невозможен.
- **FALLBACK-FIRE** (имя НЕТ в BASE; файл добавлен веткой, правлен в рабочем дереве → попадает в CDMRT через `diff HEAD`): `BASE_REF:path` пуст, fallback читает `HEAD:path` = собственный T-ID ветки → **exit 0**. Корректно: для имени не-из-BASE `HEAD:path` всегда написан самой веткой, поэтому fallback физически не может вернуть чужой T-ID. Дыры нет.

Вывод по fallback: BASE-якорь — несущая проверка; fallback не переоткрывает R-1.
