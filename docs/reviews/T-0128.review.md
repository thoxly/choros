## 5. Адверсариальные зонды

**(a) `backs_effect_resource_id` без FK — orphan-риск.** Зонд: effect_resource удалён →
connector ссылается на труп; кто чистит/валидирует? **Разбор §5 ADR удовлетворителен:** поле
явно «логическая ссылка, НЕ FK, НЕ участвует в авторизации». Авторизация вызова целиком на
T-0034 `verifyEffectGrants` (живой, :194) по самому effect_resource — висячая ссылка **не может**
открыть доступ (грант проверяется на стороне effect_resource, не по connector-полю). Day-1
драйверов нет → orphan безвреден (никто по ссылке не ходит). Это **корректная заглушечная
семантика**, не дыра. → **nit R-2**: ADR стоило бы одной строкой зафиксировать «висячий
`backs_effect_resource_id` = no-op (драйвер day-2 валидирует существование при резолве; до того
поле информативно)», чтобы impl/tester не предположил FK-целостность. Не blocking.

**(b) `http_generic` — «произвольный вызов наружу» в обход effect-грантов?** Зонд: не обещает ли
модель generic-HTTP без effect-гейта? **Нет.** `http_generic` — лишь значение `kind` (тип системы)
в конфигурационной записи; §5/§8/FR-6 жёстко держат инвариант «вызов = invoke-грант на
effect_resource», `ConnectorDriverPort.invoke` — **только тип, ни одного implements day-1**
(FF-CONN-4), NF-2/AC-14 банят реальный вызов. Модель НЕ обещает generic-вызов без effect-гейта:
любой будущий http-драйвер всё равно пройдёт `verifyEffectGrants`. → **nit R-4**: явно
проговорить в §3.1/§5, что `http_generic`-коннектор без backing effect_resource + invoke-гранта
невызываем (драйвер обязан резолвить через T-0034), чтобы closed-`kind` не читался как «открытый
egress». Инвариант уже соблюдён механически; это документирующий nit.

**(c) Handle-mint — кто выпускает секрет?** Зонд: secret_handle в connector + custody T-0025 —
описана ли связка выпуска? **Разрешено сверкой T-0170:** handle — **caller-supplied opaque**
(`EmailChannelConfigInput.smtpHandle: string`, shape-guarded, **платформа НЕ минтит**). Connector
повторяет: `SetConnectorInput.secretHandle?` валидируется `validateSecretHandleShape`, не
выпускается. «Кто минтит» — вне скоупа by design (client-hosted credential, RL-3); это **не
пробел**, а явный инвариант custody (сырой секрет/выпуск никогда не на платформе). Соответствует
T-0025/T-0170. Замечаний нет.

**(d) FF-CONN-9 (T-0170 нетронут via git diff) — вечный ли это инвариант?** Зонд: после мержа в
dev diff пуст → FF тривиально-зелёный навсегда; это одноразовая проверка ветки, не инвариант.
**Зонд валиден.** `git diff dev -- <T-0170-paths>` действительно ловит регресс только пока ветка
отстоит от dev; после мержа diff пуст всегда → как «вечный» FF чек становится no-op (всегда
зелёный, ничего не охраняет). Сравни: AC-10 (T-0170-суит зелёный после мержа) — *вот* настоящий
вечный инвариант, и он уже есть (`npm test` + notification-email.sh). → **nit R-5**: переформулировать
FF-CONN-9 как **pre-merge ветко-гейт** (diff против merge-base, не вечный fitness), а защиту
поведения T-0170 навсегда повесить на AC-10 (живой суит). Не blocking: защита поведения уже
покрыта AC-10; FF-CONN-9 просто переоценён по сроку годности.

**(e) Согласованность `mgmt_object:connector` с T-0171/T-0191/scoped-admin.** Сверено:
`mgmt_object:${string}` (grant-lattice строка 37) уже принимает произвольный `<entity>`;
`MGMT_OBJECT_KINDS` (scoped-admin:54-57) и живые `mgmt_object:agent` (agent-hire:179),
`mgmt_object:role` (seed-write:405/416) — прецедент `mgmt_object:<entity>` напрямую, **без нового
БД-enum**. `mgmt_object:connector` укладывается ровно так же. Согласовано. (Замечу для tester:
`MGMT_OBJECT_KINDS`-массив в scoped-admin.ts перечисляет role/agent/process/grant — если какой-то
путь валидирует kind по этому замкнутому массиву, `connector` придётся туда дописать; ADR §4.1
полагается на открытый template-тип. Это уточняет impl, не меняет дизайн — см. R-2/информативно.)

## 6. Security-линза

  Чисто. ✓
- Fail-closed: unknown `kind` → reject (total-predicate, не string-cast); unknown gate → deny. ✓
- Инъекции: §8/D4 DAO — параметризованный SQL по `pgEmailConfigStore.ts`; `config jsonb` opaque,

- Второй авторизатор: запрещён (FF-CONN-1 ACL-бан) — один механизм прав. ✓
- Egress: NF-2/FF-CONN-2 — нет `fetch`/`net`/`http`; ни одного implements драйвера. ✓

Систематического security-класса для `ledgers/role-gaps.md` нет.
