## 1. Главная проба: конструируем ли apply-грант? Что говорит ADR?

### 1a. CHECK-ограничение на grant.operation

Миграция `008_grant.sql` — поле `operation text NOT NULL` без CHECK-ограничения на словарь.
Проверено в живой БД:

```sql
-- нет CHECK constraint на operation
-- прямой INSERT с operation='apply' успешно проходит (откат выполнен):
INSERT INTO choros."grant" (..., operation, ...) VALUES (..., 'apply', ...) → SUCCESS (ROLLBACK)
```

Вывод: DB не блокирует `operation='apply'` структурно.

### 1b. Grant API — пропустит ли 'apply'?

`src/http/grants.ts:506-509` — валидация только `typeof operation === "string"`.
`DICT_OPERATIONS` (строки 382-390) — список `["read","create","update","delete","approve","transition","invoke"]`.
Этот список используется ТОЛЬКО для словаря UI (`GET /api/rights/dictionaries`), не как allowlist при INSERT.

Функция `validateAdminDelegation` — в `scoped-admin.ts:181-183`:
```
if (admin.isGenesisOwner) return { ok: true };  // шаг 3 — genesis short-circuit
```

Итог: genesis-owner может вставить грант с `operation='apply'` через `POST /api/rights/roles/:id/grants`. Путь существует и рабочий.

### 1c. Genesis-сид — есть ли строка с 'apply'?

`migrations/026_genesis_owner_seed.sql` — 17 грантов на роль `tenant-owner`:
`mgmt_object:{role,agent,process,grant}` × `{create,read,update,delete}` + `mgmt_object:agent`/`invoke`.
Гранта `mgmt_object:schema_destructive`/`apply` в сиде **нет**.

В живой БД (`SELECT ... WHERE resource_type LIKE 'mgmt_object:schema%'`) — 0 строк.

### 1d. Что говорит ADR T-0121 §6 (цитата)

Из `docs/design/T-0121-reports-pages.adr.md`:

> **Права — единый PDP T-0021, ноль новых permission-механизмов (FF-R6).** ... деструктив-force = `mgmt_object:schema_destructive`/`apply` (admin-only). Все `resource_type`-строки живут как TEXT (паттерн T-0077 §2.2 widening-cast), не правят frozen `ResourceType`-union.

И далее в таблице §6:

> | Деструктив-force схемы | `mgmt_object:schema_destructive` / `apply` | admin-only |

И в замечании §6.2:

> `Operation` = `"read"|"create"|"update"|"delete"|"approve"|"transition"|"invoke"`. `"apply"` не входит. ... В production-коде `g.operation === "apply"` — строковое сравнение, не type-guard. Frozen union `Operation` в `grant-lattice.ts` не меняется.

### 1e. Итог главной пробы

**Ситуация: apply-грант конструируем, но НЕ сидирован.**

- Genesis-owner (actor с ролью `tenant-owner`) может создать `mgmt_object:schema_destructive`/`apply` через grant API.
- Другие акторы не могут (genesis-owner short-circuit + `validateAdminDelegation` шаг 5 требует покрывающего гранта с той же operation; у genesis-owner такого гранта нет, но он проходит через short-circuit на шаге 3).
- По умолчанию (fresh DB + seed 026) гейт = owner-only: только genesis-owner проходит через `isGenesisOwner` short-circuit.
- ADR T-0121 §6 явно называет это "admin-only" и задаёт именно этот паттерн. Никакого противоречия нет.
- Реализация точно следует ADR. Поведение owner-only по умолчанию — **осознанный day-1 дизайн**, явно описанный в ADR.

**Не blocking.**

### 1f. Одно нит: spec contract AC-7 и coverage несоответствие

Spec contract `T-0191.spec.contract.json` AC-7 ("live: force=true + сидированный grant → 200") — живой тест на non-owner путь с реальным сидированным грантом отсутствует. Реализованный AC-10 (fitness:db) использует genesis-owner short-circuit, а не сидированный грант. Путь с настоящим делегированным `apply`-грантом не покрыт live-тестом. ADR это не запрещает (spec §8 допускала "Опцию B"), но AC-7 формально не выполнен.

Severity: **nit** (для day-1 не критично — genesis-short-circuit покрывает рабочий сценарий; сидирование гранта = задача T-0121f или отдельный seed).
