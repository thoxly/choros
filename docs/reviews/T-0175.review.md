## 3. RLS — T-0013 pattern verbatim (axis 2)

Reference pattern from `046_notification.sql` and `038_egress_policy.sql`:

```sql
ALTER TABLE choros.<table> ENABLE  ROW LEVEL SECURITY;
ALTER TABLE choros.<table> FORCE   ROW LEVEL SECURITY;

DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_policies WHERE schemaname='choros'
    AND tablename='<table>' AND policyname='<table>_tenant_isolation') THEN
    CREATE POLICY <table>_tenant_isolation ON choros.<table>
      USING     (tenant_id = current_setting('choros.tenant_id', true)::uuid)
      WITH CHECK (tenant_id = current_setting('choros.tenant_id', true)::uuid);
  END IF;
END $$;

GRANT SELECT, INSERT, UPDATE, DELETE ON choros.<table> TO choros_app;
```

Both migrations 051 and 052 replicate this pattern verbatim:
- ENABLE + FORCE with two-space alignment — ✓
- DO-guard for idempotent policy creation — ✓
- USING + WITH CHECK symmetric on `current_setting('choros.tenant_id', true)::uuid` — ✓
- Policy names: `report_page_tenant_isolation` / `report_page_dep_tenant_isolation` — ✓
- GRANT to `choros_app` (NOBYPASSRLS role) — ✓

**RLS: verbatim T-0013 pattern confirmed.**

## 4. FK CASCADE semantics (axis 1)

ADR §2.2 explicitly mandates `ON DELETE CASCADE` on the `page_id` FK in `report_page_dep`:
> "ON DELETE CASCADE on page_id FK: deleting a report_page removes its deps"
> "audit_event is append-only and survives deletion (ADR §7 NF-7)"

Migration 052 implements this correctly:
```sql
CONSTRAINT report_page_dep_page_fk
  FOREIGN KEY (tenant_id, page_id)
  REFERENCES choros.report_page(tenant_id, id)
  ON DELETE CASCADE
```

The `registry_def_id` FK has **no** CASCADE, which is correct — deleting a registry_def does not automatically remove page deps (that would be destructive-force territory). The ADR does not mandate CASCADE there, and none is present.

**FK CASCADE semantics: correct per ADR.**
