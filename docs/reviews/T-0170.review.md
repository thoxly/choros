### 2.2 Структурный анализ: может ли raw secret попасть в лог/audit/exception?

**Путь resolve → SMTP:**

`deliver()` (`notification-email.ts:367-414`) получает `resolvedSecret` из `secretResolver.resolveSecret()`. Секрет передаётся ТОЛЬКО в `smtpSender.sendEmail({ ..., authPass: resolvedSecret, ... })`. В catch-ветке SmtpSendError секрет не захватывается в `reason` (строки 403-408: `"smtp_transient_error"` / `"smtp_permanent_error"`). В catch неизвестной ошибки — `"smtp_send_exception"` (строка 411). Проверено:

- Нет `console.*` с `smtpHandle` или `resolvedSecret` (FF-E1a: PASS)
- Нет `smtp_handle:` как ключа объекта в audit payload (FF-E1b: PASS)
- `redactHandle()` вызывается в `getEmailChannelConfigStatus` (FF-E1c: PASS)

**Planted-проверка: путь config_load_error:**

`notification-email.ts:350-351`:
```typescript
const msg = err instanceof Error ? err.message : String(err);
return { ok: false, retryable: true, reason: `config_load_error: ${msg}` };
```
Это ошибка чтения конфига из БД — ПЕРЕД resolve SMTP-секрета. `smtpHandle` является данными в БД, теоретически PostgreSQL constraint-ошибка может включить часть данных в `err.message` (например, если уникальный индекс нарушен и сообщение содержит значение). Однако это `configStore.get()` (SELECT), не INSERT/UPDATE — constraint-ошибки в SELECT невозможны. Поэтому путь `config_load_error: ${msg}` БЕЗОПАСЕН: `smtpHandle` не может попасть в сообщение об ошибке SELECT.

**Итог по секретам:** чистый. Raw secret структурно не достигает ни лога, ни аудита, ни exception.reason.

### 3.4 BLOCKING — R-1: maxAttempts=5 противоречит требованию immediate-dead

Комментарий в lifecycle-bridge.ts, строки 261-262:
```
// maxAttempts=1 for the notification path: immediate-dead semantics (ADR §2.6,
// IMMEDIATE_DEAD_ERROR_PREFIX rows die on first attempt without back-off cycle).
```

Но реальный код, строка 280:
```typescript
const dispatchLoop = startOutboxDispatcherLoop(deps.outboxStore, deliver, {
  batchLimit: 10,
  maxAttempts: 5,   // <-- ПЯТЬ, не 1
  ...
});
```

`IMMEDIATE_DEAD_ERROR_PREFIX` НЕ обрабатывается в `runOutboxOnce` как per-row `maxAttempts=0` — это явно задокументировано в `notification-router.ts:481-494`:
> «`runOutboxOnce` does NOT parse this prefix. A row whose deliver() returns `{ok:false, error: "IMMEDIATE_DEAD:…"}` enters the normal back-off cycle and is retried until `opts.maxAttempts` is exhausted»

`pgOutboxStore.markRetry` логика: `CASE WHEN attempts + 1 >= 5 THEN 'dead' ELSE 'pending'`. При `attempts=0` и `maxAttempts=5` → `0+1=1 < 5` → `state='pending'`. Строка НЕ умирает немедленно — она повторяется ещё 4 раза.

Spec AC-13: «wiring lifecycle-bridge использует `maxAttempts=1` для notification dispatcher (or equivalent row dies on attempt 1)» — **НЕ выполнен**.

Spec FR-8: «immediate-dead семантика: ... wiring использует `maxAttempts=1` для notification rows» — **НЕ выполнен**.

Также: spec contract summary говорит «Immediate-dead = maxAttempts=1 для notification dispatcher-instance» — это не реализовано.

**Вариант исправления (spec FR-8/AC-13):** Либо (a) создать отдельный `startOutboxDispatcherLoop` для notification rows с `maxAttempts=1`, либо (b) расширить `runOutboxOnce` с per-row override при `IMMEDIATE_DEAD_ERROR_PREFIX`. Вариант (a) проще и не меняет T-0062.

### 3.5 BLOCKING — R-2: EmailChannelDriver не инстанциируется в production

FR-9: «Registry включает `inAppNoOpDriver` и `emailChannelDriver`». Но `main.ts` не передаёт `notificationRegistry` в `startLifecycleBridge`, поэтому используется дефолт `new Map([[inAppNoOpDriver.key, inAppNoOpDriver]])`.

`EmailChannelDriver` ни разу не инстанциируется в `main.ts`, `index.ts`, `server.ts`. В production `email` channel не достижим через registry — `makeNotificationDeliver` вернёт `{ok:false, error: "IMMEDIATE_DEAD:no ChannelDriver registered for channel 'email'"}` для любого email outbox-ряда.

Lifecycle-bridge jsdoc строка 84: «Production: Map with inAppNoOpDriver + EmailChannelDriver» — это описание намерения, которое в production-коде не реализовано.

Wired-entry тест (AC-12) **ПРОХОДИТ**, потому что он инжектирует stub registry самостоятельно — он не тестирует production-default path в main.ts. Тест честный, но не доказывает production-wiring.

**Вариант исправления:** В `main.ts` при `startLifecycleBridge()` создать `notificationRegistry` с `new EmailChannelDriver(pgEmailConfigStore, makeDirectStringSmtpResolver(), new NodemailerSmtpSender())` и передать его как `deps.notificationRegistry`. (Либо создать `PgEmailConfigStore` DAO как порт-реализацию для production path.)

2. **R-2** (`main.ts` — отсутствие): `EmailChannelDriver` не инстанциируется в production. `main.ts` не передаёт `notificationRegistry`. В production email channel недостижим. FR-9 не выполнен.
