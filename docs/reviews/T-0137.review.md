### 3a. Двухзапросный положительный сценарий (escalating → semi-confirmed → confirmed)

**Шаг 0:** Создан свежий test-role без существующих грантов:
```
POST /api/roles (x-dev-user: e-owner) → {id: "24405a78-..."}
```

**Шаг 1:** Предложен `effect_resource:invoke` (ось b `external_invoke` = false→true → escalates):
```
POST /api/grants (x-dev-user: e-owner)
{role_id: "24405a78...", resource_type: "effect_resource", operation: "invoke", ...}
→ {id: "76ebe4e7-...", state: "semi-confirmed", second_approver_required: true,
   reason: "escalates_criticality"}
```
Состояние `semi-confirmed` и `second_approver_required` корректны.

**Шаг 2a (негатив — same-actor):**
```
POST /api/grants (x-dev-user: e-owner) {phase: "confirm2", change_ref: "76ebe4e7..."}
→ HTTP 409 {"error":{"code":"DUAL_CONTROL_UNSATISFIED","message":"self_confirm"}}
```
Бэкенд отвергает самоподтверждение на уровне `handleSecondConfirm` — загружает из БД
`proposed_by`/`confirmed_by` строки и проверяет `actor === row.proposed_by || actor === row.confirmed_by`.
Проходит.

**Шаг 2b (позитив — другой актор):**
```
POST /api/grants (x-dev-user: e-owner2) {phase: "confirm2", change_ref: "76ebe4e7..."}
→ HTTP 200 {"id": "76ebe4e7-...", "state": "confirmed"}
```
Грант переведён в confirmed. Проходит.

### 3b. Честность UI против бэкенда

UI (`ra-role-editor.jsx`) в `postSecondConfirm` передаёт `confirmActor` в заголовок
`x-dev-user` (строка 203: `"x-dev-user": actorId`). Бэкенд (`handleSecondConfirm`) берёт
актора ТОЛЬКО из `extractActor(req)` — из header `x-dev-user`, не из тела (R-AUTH §9.2/§9.5).
Поле тела `confirmActor` не ложится в body — только в header. Механика корректна.

**Самоподтверждение через UI:** пользователь может ввести тот же `ACTOR_ID` ("e-owner")
в поле `confirmActor`. Бэкенд вернёт `{"code":"DUAL_CONTROL_UNSATISFIED","message":"self_confirm"}`.
UI показывает это как `✕ {reason}` в `confirmResult`. Это корректно — бэкенд режет,
UI отображает ошибку. Самоподтверждение невозможно даже через UI dev-стенда.

## 4. Ось 1 — Корректность

### 4a. Маршруты shell.jsx

`RightsSubTabs` компонент использует `useLocation` + `useNavigate` из react-router-dom.
Детект активной вкладки: `t.path === location.pathname || (t.path !== "/rights" && location.pathname.startsWith(t.path))`.
Логика корректна — `/rights/editor` не подхватит `/rights` (guard `t.path !== "/rights"`).
`/rights` и `/rights/editor` не конфликтуют с роутами — `<Routes>` первый совпадающий маршрут.

### 4b. `postSecondConfirm` — HTTP body vs header

`postSecondConfirm(changeRef, actorId)` (строка 203):
```js
headers: { "Content-Type": "application/json", "x-dev-user": actorId },
body: JSON.stringify({ phase: "confirm2", change_ref: changeRef }),
```
`actorId` идёт в header — это confirmActor state, вводимый пользователем.
Бэкенд читает `x-dev-user` как `actor` (R-AUTH). Верно.

### 4c. `pendingConfirms` после handleSubmit

В `handleSubmit` и `confirmProposed` накапливаются только гранты с `state === "semi-confirmed"`.
При повторном сабмите `setPendingConfirms([])` сбрасывается перед циклом — нет утечки
старых pending.

### 4d. Тип `confirmResult` — `"loading" | {ok, reason?} | null`

`confirmResult === "loading"` используется как строка и как проверка через `confirmResult !== "loading"`.
Это корректно — строка не равна объекту.

## 5. Ось 2 — Безопасность

### 5a. Автор second-confirm через UI

Поле `confirmActor` — это UX dev-стенда, имитирующий смену пользователя. В production это
будет JWT/session актор. Самоподтверждение режется БЭКЕНДОМ (AC-6 T-0044), не UI.
Никакого security-регресса: поле не bypass.

### 5b. Нет новых авторити в теле

`postGrant` убрал `confirmed_by` из тела (rev-2 R-AUTH, строка 296-297: `confirmed_by` не
передаётся). `postSecondConfirm` тоже не передаёт `confirmed_by` — только `phase` и
`change_ref`. Закрытие pre-existing body-assertion hole сохранено.

## Findings

### R-N1 (nit, ось 6 — тестируемость)

**Файл:** `web/src/screens/rights/ra-shell.jsx`
**Строки:** 1–127

`ra-shell.jsx` — standalone preview shell (дублирует nav + subtabs + tab-switch),
больше не используется как entry-point: все 4 экрана теперь смонтированы в `AppShell`
через роутер (`shell.jsx`). `ra-shell.jsx` не импортируется нигде в main.jsx или shell.jsx.

Файл является мёртвым кодом (dead preview artifact) ИЛИ сознательным preview-компонентом
для standalone разработки (легальный паттерн для dev-стенда). Commit message и diff не
упоминают удаление или оставление `ra-shell.jsx` как намеренный выбор.

**Suggestion:** Либо добавить комментарий `// standalone preview — intentionally kept for local dev`
в начало файла, либо удалить. Не blocking — functional regression невозможен.

### R-N2 (nit, ось 1 — корректность UI)

**Файл:** `web/src/screens/rights/ra-role-editor.jsx`
**Строка:** 237

`const [confirmActor, setConfirmActor] = useState("e-owner2");`

Дефолт `"e-owner2"` — другой актор (не `ACTOR_ID = "e-owner"`), поэтому при стандартном
использовании UI автоматически предлагает правильного второго актора. Однако:
- Если пользователь вводит `"e-owner"` (идентичный ACTOR_ID) и нажимает confirm2, бэкенд
  вернёт 409 `self_confirm`, UI покажет `✕ self_confirm` — это верно.
- При default `"e-owner2"`, если этот slug не имеет admin прав, бэкенд вернёт
  `ADMIN_GATE_REJECTED`. UI покажет ошибку. Dev-стенд: `e-owner2` не является сидированным
  пользователем с полными правами, но `handleSecondConfirm` обходит `validateAdminDelegation`
  (только проверяет distinctness + confirmed2_by IS NULL). Значит `e-owner2` пройдёт confirm2
  без проверки admin authority второго актора.

  **Это ограничение дизайна T-0044 rev-2, не регрессия T-0137:** `handleSecondConfirm`
  намеренно не повторяет admin-gate (второй актор уже аутентифицирован и distinct).
  Нит без runtime-риска в рамках dev dev-стенда.

**Suggestion:** В banner добавить hint-текст «второй актор должен иметь права администратора»,
либо документировать это в комментарии к `handleSecondConfirm`.
