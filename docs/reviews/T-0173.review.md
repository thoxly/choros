## Review Axes

### Axis 1 — Correctness

**Keyset pagination (equal created_at tie-break):**
SQL uses `(created_at, id) < ($N, $M)` — a proper SQL ROW VALUE comparison. When two rows
share the same `created_at`, Postgres evaluates the `id` component as the tie-break, yielding
strict ordering. AC-3 DB test inserts 5 rows with distinct `createdAt` values and verifies
no duplicates/gaps across two pages — passes. Adversarial: forged cursor shifts the pagination
window only; it cannot expose another tenant's rows (RLS enforces `tenant_id`) or another
user's rows (`recipient_id = actorId` is always server-constructed from the header).

**Parameter index off-by-one audit:**
Traced `args` array construction for all three cases (no isRead + cursor; isRead + cursor;
no cursor). The computation `caIdx = args.length - 1; idIdx = args.length` after
`args.push(createdAt, id)` is correct in all paths. Verified by simulation.

**countUnread — partial index:**
SQL: `WHERE recipient_id = $1 AND is_read = false`. Confirmed via live EXPLAIN:
`Index Only Scan using idx_notification_unread`. The `tenant_id` column is implicitly
filtered by RLS (`current_setting('choros.tenant_id')::uuid`), so the index is fully
utilized even without explicit `tenant_id` in the SQL WHERE clause.

**markRead / batchMarkRead own-only:**
`UPDATE WHERE id = $1 AND recipient_id = $2` — foreign row cannot match → `rowCount = 0`
→ returns `false` → HTTP 404. DB test (AC-6) confirms no mutation on the row for the
wrong-recipient case. `batchMarkRead` uses `id = ANY($1) AND recipient_id = $2` — foreign
ids are skipped, not errored; updated count = only own rows. Per spec FR-9.

**server.ts integration:**
Additive 5-line change. `registerNotificationRoutes` gated by `grantsPool` (same guard as
`registerNotificationPrefRoutes`). No side effects on existing routes.

### Axis 4 — Security

**Cursor injection:** Base64url-decoded, then parsed as JSON, then individual fields used
as parameterized SQL args. No interpolation. Cannot inject SQL.

**Cursor cross-tenant/cross-user:** Cursor carries only `(createdAt, id)` position. Even
a forged cursor with valid-looking values cannot access other tenants' data (RLS on GUC)
or other users' rows (`WHERE recipient_id = actorId` is server-only). Safe.

**UUID validation:** `notifId` (from path params) and all `ids` (from PATCH body) are
validated against `UUID_RE` before use. `actorId` from X-Dev-User header is used as a
parameterized SQL argument — no injection path. In dev auth mode, any string is accepted;
Keycloak mode enforces real identity. This is consistent with the rest of the codebase
(same pattern as `notification-prefs.ts`). Nit only.

**GUC interpolation:** `withTenantTx` uses string interpolation for `SET LOCAL choros.tenant_id = '${tenantId}'`.
This is preceded by `assertUuidShape(tenantId, "tenantId")` which rejects non-UUID values.
`tenantId` is the hardcoded `DEV_TENANT_ID` env var. Same pattern as `notification-prefs.ts`.
No external input flows through here unguarded.

No security-class evidence for `role-gaps.md`.
