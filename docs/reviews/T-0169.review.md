## 2. Axis 1 — Correctness (ADR соответствие, fanout-пайплайн §4.5)

### 2.1 Fanout-пайплайн по ADR §4.5 (шаг-в-шаг)

ADR §4.5 задаёт последовательность из 6 шагов:
1. tenant-gate fail-closed
2. читает `notification_preference` для `(tenant_id, event_kind)`
3. разворачивает `recipient_scope` → `recipient_id[]`
4. рендерит `title`/`body` (≤ `internal`)
5. per (получатель × канал): in_app → INSERT notification + outbox; email → outbox-ряд (if is_enabled)
6. не пишет `audit_event`

**Реализация:** `publishNotificationEvent` (строки 285-407 `notification-router.ts`) точно следует этой последовательности. Рендер (шаг 4) вынесен ДО внутреннего цикла — правильно, один вызов на событие. Шаги 5а/5б разведены через `driver.requiresInAppRow` и `driver.requiresEmailConfig` флаги.

**Тонкость по шагу 5:** ADR §2.1 пишет «если канал `in_app`» — условие по имени. Реализация заменяет это условие флагом `driver.requiresInAppRow`. Это не нарушение FF-NO-SWITCH-CHANNEL — флаг проверяется у driver-объекта, не сравнивается строка-ключ. Нит-ниже (R-1).

### 2.2 ChannelDriver contract vs ADR §2.5/§4.4

ADR §2.5 определяет `ChannelDriver` с полями `key` и `deliver`. Реализация добавляет два опциональных поля `requiresInAppRow?` и `requiresEmailConfig?`. Оба опциональны, тип совместим структурно. **Не breaking.** Добавленные поля не нарушают ни ADR, ни FF-NO-SWITCH-CHANNEL — они переносят поведенческие различия в driver-объект без switch по ключу. Отмечаю как нит (R-1).

### 2.3 Идемпотентность outbox-ряда

`idempotencyKey = 'notif:' + notifId + ':' + channel` — точно по ADR §2.6. Для in_app `notifId` = UUID нотификации (AC-14 покрыт тестом). Для email используется `deliveryId` = `randomUUID()`, НЕ notification.id — это соответствует ADR (email-ряд не привязан к in_app-строке; для email нет строки `notification`).

## 3. Axis 2 — Интеграция с runOutboxOnce (КРИТИЧЕСКИЙ ВОПРОС)

**Вопрос:** кто РЕАЛЬНО вызывает `makeNotificationDeliver` из outbox-цикла? Если соединительный шов не сделан — это «зелёные юниты поверх мёртвой проводки» (FE-W24-0045).

**Результат исследования:**

`src/server/lifecycle-bridge.ts:236` — единственный `deliver` в production-пути:
```typescript
const deliver = makeExternalTaskDeliver(flowableClient, deps.jobStore);
const dispatchLoop = startOutboxDispatcherLoop(deps.outboxStore, deliver, {...});
```

`makeNotificationDeliver` **нигде не вызывается** вне тестов. Строка `lifecycle-bridge.ts` передаёт только `makeExternalTaskDeliver` в `startOutboxDispatcherLoop`.

**Blocking или нет?** Разбираем по ADR §5 таблице E-N.2:

Scope E-N.2: _«`src/core/notification-router.ts` (`publishNotificationEvent`, fanout, scope-разворот), `ChannelDriver`/`DeliveryJob`/`DeliveryResult`-типы, `makeNotificationDeliver` (Map, не switch), in_app-no-op-driver»_.

E-N.2 отвечает за **создание** `makeNotificationDeliver` как готового `Deliver`-сима под T-0062. Про **регистрацию** в composition root ADR §5 E-N.2 явно не пишет (в отличие от E-N.3, который создаёт email-драйвер). Фраза ADR §2.6: «deliver(row) (notification-вариант, **инжектируется** в `runOutboxOnce`)» — это описание намерения, а не инструкция E-N.2.

**Вывод:** wiring-шов в composition root (lifecycle-bridge) НЕ является обязательным deliverable E-N.2. E-N.2 производит модуль и тип-совместимый `Deliver`. Регистрация `makeNotificationDeliver` в lifecycle-bridge — это задача следующей E-N-задачи (E-N.3 или отдельная wiring-задача), когда email-драйвер и полный registry будут доступны для сборки.

Однако: **отсутствие wiring нужно зафиксировать явно** как технический долг, чтобы следующий разработчик не упустил. Это нит уровня документации (R-2).

**Итог по п.2: НЕ blocking.** ADR E-N.2 не требует composition-root wiring. Зелёные юниты — честные: `makeNotificationDeliver` производит корректный `Deliver` для `runOutboxOnce` (тесты AC-3/AC-10 это доказывают). Проводка — следующий шаг.

## 4. Axis 3 — Fail-closed семантика

### 4.1 tenantId пустой / отсутствует

`src/core/notification-router.ts:291-296`:
```typescript
if (!ev.tenantId || !ctx.tenantId) {
  throw new Error("publishNotificationEvent: tenantId required (fail-closed)");
}
if (ev.tenantId !== ctx.tenantId) {
  throw new Error("publishNotificationEvent: tenantId mismatch (cross-tenant denied)");
}
```
FF-FANOUT-FAILCLOSED реализован верно. Три теста в AC-5 покрывают: пустой ev.tenantId, cross-tenant mismatch, пустой ctx.tenantId.

### 4.2 Preferences default (нет строк)

Если `prefStore.getPreferences` вернул пустой массив — возврат `{inAppCreated: 0, outboxEnqueued: 0}` немедленно (строки 301-303). Fail-closed корректно: нет подписок → нет доставки.

### 4.3 IMMEDIATE_DEAD_ERROR_PREFIX семантика

`notification-router.ts` экспортирует `IMMEDIATE_DEAD_ERROR_PREFIX = "IMMEDIATE_DEAD:"` и документирует, что dispatcher должен перехватить этот префикс и вызвать `markRetry(…, 0)`. НО: `runOutboxOnce` (T-0062) не читает error-строку и не переопределяет `maxAttempts` динамически — он использует глобальный `opts.maxAttempts`. Следовательно, `retryable:false` отправится в back-off цикл вместо немедленного `dead`, пока `attempts` не достигнет `opts.maxAttempts`.

Это семантический gap между намерением (immediate-dead) и реальностью (задержанный dead через N попыток). Сам E-N.2 AC-10 spec formulation честен: «вызывающий dispatcher **установит** dead» — это обещание о будущем caller, а не E-N.2 deliverable. Единица поставки E-N.2 — `DispatchResult` с правильным префиксом — выполнена. **Но gap требует фиксации**: либо T-0062 будет доработан для per-row maxAttempts override, либо E-N.3/wiring-задача установит собственный dispatcher с `maxAttempts=1` для нотификаций. Нит R-3.

## 10. Вердикт

**`approved`**

Код соответствует ADR T-0120 §2/§4.4–4.5 E-N.2. Fanout-пайплайн реализован точно по §4.5. FF-NO-SWITCH-CHANNEL честно выполнен через флаги в driver-объекте. Чистый pure-core модуль (нет IO-импортов). Fail-closed корректен. 31 тест не тавтологичен.

Отсутствие composition-root wiring (`makeNotificationDeliver` в lifecycle-bridge) — **не blocking**: ADR E-N.2 scope создаёт модуль, не регистрирует его в production dispatcher. Регистрация — следующая E-N-задача.

4 nit-замечания (R-1..R-4) не требуют возврата кодеру; могут быть адресованы в E-N.3 или wiring-задаче.
