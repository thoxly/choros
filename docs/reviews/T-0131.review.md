## 2. Key experiment reproduction

All experiments reproduced against a fresh `flowable/flowable-rest:7.1.0` container (`spike_flowable_t131_review`, port 18080).

### 2.1 Q1 — Global Clock API does not exist

Probed GET / POST / PUT `/management/clock`:

```
GET  → HTTP 500 {"message":"Internal server error","exception":"No endpoint GET /flowable-rest/service/management/clock."}
POST → HTTP 500 {"message":"Internal server error","exception":"No endpoint POST /flowable-rest/service/management/clock."}
PUT  → HTTP 500 {"message":"Internal server error","exception":"No endpoint PUT /flowable-rest/service/management/clock."}
```

**Reproduced exactly. Global clock API is absent from Flowable 7.1.0 OSS REST.**

### 2.2 Q2(a) — action=move fires timer per-instance (positive probe)

Deployed `timerBoundaryReview` BPMN (non-interrupting boundary, PT5M). Started instances A and B. Posted `{"action":"move"}` on instance A's timer job only.

```
HTTP response for action=move: 204  ← expected 204
```

After async executor lag (~12s):

```
Tasks on Instance A: ['Wait for approval', 'Escalation task']  ← escalation fired ✓
Tasks on Instance B: ['Wait for approval']                     ← timer untouched ✓
```

Timer A job gone from `act_ru_timer_job`; timer B still present with original dueDate. **Per-instance isolation confirmed. Reproduced exactly.**

### 2.3 Q2(b) — action=reschedule returns 400 (negative probe)

Posted `{"action":"reschedule","newDueDate":"..."}` on instance B timer job with three date formats:
- ISO 8601 with Z: `→ HTTP 400 "Invalid reschedule timer action. Reschedule timer actions must have a valid due date."`
- ISO 8601 with +0000: `→ HTTP 400` (identical exception)
- no timezone: `→ HTTP 400` (identical exception)

Timer B dueDate unchanged after all three attempts. **Negative probe reproduced exactly — reschedule is broken in Flowable 7.1.0 for duration-type timers.**
