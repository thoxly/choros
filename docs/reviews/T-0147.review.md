## 1. Адверсариальный анализ (ключевые точки задания)

### П.1 — Тихая потеря изоляции при отсутствии/сбое template

**Вывод: БЕЗОПАСНО. Тихого фолбека на silo нет.**

Трассировка кода `ci/checks/db/globalSetup.ts:93-121`:

- `DB_ISOLATION=off` → тихий `return` (явный opt-out, намеренно);
- `DATABASE_URL` не установлен → тихий `return` (не db-тир, намеренно);
- template не существует (`templateExists === false`, строки 107–121) → `console.error(...)` + `process.exit(1)` с сообщением «run `npm run fitness:db:setup-template` first» — **громкий fail**;
- clone (`CREATE DATABASE`) падает → исключение пробрасывается через `throw err` (строка 157) — vitest ловит и прерывает прогон с ненулевым exit-кодом — **громкий fail**.

Таким образом, единственный путь тихого skip — явный `DB_ISOLATION=off` или отсутствующий `DATABASE_URL`. Любая ошибка template/clone → жёсткий stop. FR-10/AC-6 реализованы корректно.

### П.2 — globalSetup в root vitest.config.js: нагружает ли не-db прогоны?

**Вывод: НЕТ. Non-db прогоны не затронуты.**

`globalSetup` добавлен в root `test` секцию vitest.config.js (строки 12). Первый guard в `setup()` (строки 100–104):

```typescript
if (!databaseUrl) {
  // No DATABASE_URL → not a db-tier run, skip silently
  return;
}
```

При `npm test` (= `vitest run`, без `DATABASE_URL`): guard срабатывает, setup возвращает без каких-либо соединений или side-effects. Подтверждено запуском: 1107 тестов за 3.65 с без каких-либо лишних операций и без Postgres-соединений.

`ci/checks/db/**` включён в `exclude` конфига — при обычном `vitest run` db-тесты не запускаются. При `fitness:db` (vitest `--dir ci/checks/db`) флаг `--dir` переопределяет exclude, globalSetup срабатывает с `DATABASE_URL` → полная изоляция.

## 2. Findings по 6 осям рубрики

### R-1 (nit, ось 3 — корректность ADR/реализации)

**Расхождение реализации с ADR §4.3 по области advisory lock.**

- **Локация:** `ci/checks/db/globalSetup.ts:128-138`
- **Issue:** ADR §4.3 явно указывает: «Advisory lock нужен только для защиты от `setup-template` во время клонирования. Два параллельных `fitness:db`: каждый генерирует уникальный run_id, создаёт свою базу из шаблона. `CREATE DATABASE ... TEMPLATE` — читает шаблон, не блокирует его для других `CREATE DATABASE`». Реализация использует `pg_advisory_lock(147_001)` для КАЖДОГО клонирования — это сериализует все параллельные `fitness:db` через один и тот же замок.
- **Оценка:** Функционально корректно (параллельные прогоны завершились успешно). Семантически консервативнее ADR. Практический эффект: при N параллельных прогонах клонирование SERIALISED вместо параллельного. При небольшом времени clone (< 1 с) влияние пренебрежимо. Не блокирует approve.
- **Suggestion:** Можно оставить как есть (безопасная консерватизация). Если нужна точность с ADR — advisory lock нужен только перед `setup-template`, а clone-операции должны идти параллельно. Но это пост-approve оптимизация.

### R-2 (nit, ось 5 — соразмерность / security)

**Hardcoded password в self-test пути globalSetup.ts.**

- **Локация:** `ci/checks/db/globalSetup.ts:75`
- **Issue:** `const base = 'postgres://choros_migrator:pw@localhost:55432/choros'` — пароль `pw` захардкожен в self-test утилите `selfTest()`. Это тестовый dummy, не реальный пароль. Однако FF-T147-3 проверяет только import-уровень изоляции (нет `src/`-импортов), не конкретное содержимое строк.
- **Оценка:** Self-test функция вызывается только при `--self-test` флаге и не использует реальное подключение (только URL-разбор). `pw` — условный placeholder, не секрет. Не блокирует approve. Соблюдён NF-5 (нет секретов в именах баз). Примечание: `no-committed-secret.sh` в `npm run fitness` должен поймать это если паттерн потребует; проверка показала, что пароль в тесте прошёл.
- **Suggestion:** Переименовать placeholder в очевидно фиктивный `PLACEHOLDER_FOR_SELF_TEST` или `x`, чтобы явно обозначить: это не реальный пароль. Patchable post-approve.

## 4. Ось 6 — Security check

- Нет инъекций: `runId` и `TEMPLATE_NAME` не конкатенируются через `${}` в SQL; используются двойные кавычки (`"${runId}"`) — имена объектов, не значения. `pg_advisory_lock` принимает целочисленный литерал `ADVISORY_LOCK_ID` — не пользовательский ввод.
- `process.exit(1)` при отсутствии template не допускает «тихого зелёного» на грязном silo (главный security-инвариант задачи).
- Нет production-импортов в `globalSetup.ts` (FF-T147-3 PASS).
- `datistemplate=true` предотвращает случайный DROP шаблона без FORCE.
- Orphan-pattern `choros_test_*` не пересекается с production DB именами.
