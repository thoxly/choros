## 2. Adversarial findings (all NIT — none blocking)

### R-1 (nit · axis 6 security) — residual BYPASSRLS-class read in grant-trail (OUT OF SCOPE)
The same latent class the BUILD fixed in `org.ts` still exists in `src/db/audit-grant-trail.ts:10-11`: `queryGrantTrail` reads `choros.audit_event` relying **only** on the `SET LOCAL choros.tenant_id` GUC + RLS, executed on `getOrgPool()` = `choros_migrator` (**BYPASSRLS**, which ignores RLS). **Not exploitable** via the showcase persona path — `grant-trail.ts:222-228` hardcodes `tenantId = DEV_TENANT_ID` regardless of `X-Dev-User`. Untouched file, out of T-0141 scope → logged as role_gap_evidence, not blocking. Fix in a follow-up (explicit `WHERE tenant_id=$1`, or migrate read pool to `choros_app`).

### R-2 (nit · axis 4 spec-fidelity) — e-owner persona is not a showcase member
Spec FR-4 names `e-owner` as the "Владелец тенанта" demo persona, but live + pack inspection shows `e-owner` exists **only in the dev-silo tenant** (migration 026), is absent from `seed/showcase/pack.json`, and holds no `tenant-owner` assignment in showcase. `resolveActorTenant('e-owner')` therefore correctly falls back to `DEV_TENANT_ID`. **Mitigated:** `e-owner` is not in the login picker (`/api/users` returns the 7 showcase humans only), and the spec's own §6 walkthrough uses `e-larina`/`e-kravtsova`/`e-orlov`. This is an internal spec inconsistency (FR-4 table vs §6), not an impl defect; AC-4 is satisfied. Surface to founder: the showcase owner-archetype is `e-larina`, not `e-owner`.

### R-3 (nit · axis 5 proportion) — two no-DB FF not in the default fitness gate
`FF-PACK-2` and `FF-FALLBACK-6` are self-contained (no live DB needed; FF-PACK-2 uses a non-connectable sentinel `DATABASE_URL`) and pass, but neither is wired into `npm run fitness` — only the 4 pure-static demo checks are. ADR §9 claims they run "always"; in practice the always-gate omits them. Either add them to the `fitness` chain or correct ADR §9.

### R-4 (nit · axis 2 correctness of the test) — FF-SCOPE-3 leak proxy is count, not identity
`no-cross-tenant-org.sh` proves isolation via `dept count === 3` (dev-silo and showcase share fin/cs/plat slugs, so slug identity can't distinguish them). The count catches the realistic failure modes (BYPASSRLS merge → 6; missing WHERE → all tenants). Acceptable for the gate; the true guarantee is the explicit `WHERE tenant_id=$1` (now present), which this review verified directly via live code probe.

## 3. BUILD point-by-point conclusions

**1a — are ALL BYPASSRLS reads on this pool closed?** In `src/db/org.ts`: **yes**. Every tenant-scoped read now carries an explicit `WHERE … tenant_id = $1` (listOrgTree dept/pos/emp; findEmployeeById; listHumanEmployees; isGenesisOwnerForTenant & loadAdminContext already had it). `resolveActorTenant`/`resolveTenantBySlug` are intentionally unscoped (they *resolve* the tenant) and tie-break demo-first. The only residual GUC-only BYPASSRLS read in the whole runtime read path is `audit-grant-trail.ts` (R-1) — out of scope, not exploitable here.

**1b — additive, non-breaking for the non-BYPASSRLS path?** Yes. The explicit `WHERE tenant_id=$1` is redundant-but-correct for a future `choros_app` (NOBYPASSRLS) connection where RLS would also filter — no behaviour change. Confirmed by the frozen `org.e2e` suite staying green.

**1c — why did no existing fitness catch it? (role_gap)** Test-apparatus role-mismatch: `ci/checks/db/cross_tenant.test.ts` proves RLS through `appUrl()` = `choros_app` (NOBYPASSRLS), but the runtime read endpoints connect via `DATABASE_URL` = `choros_migrator` (BYPASSRLS). The fitness exercises RLS via the app role yet never exercises the actual runtime pool role for the read endpoints, so a missing WHERE on a migrator-pool read is structurally invisible to it. Recorded as role_gap_evidence.

**2 — resolveActorTenant / X-Dev-User cross-tenant?** Slug is **global, not per-tenant** — `e-kravtsova` collides across **11 tenants** on the live dev DB. `resolveActorTenant` handles this with `ORDER BY (CASE demo-tenant THEN 0 ELSE 1), created_at DESC` → verified live to resolve to `showcase`. Unknown slug → `DEV_TENANT_ID` fallback. The header is a dev-only mechanic (T-0106) and the picker only offers in-tenant slugs, so there is no cross-tenant *escalation* — at worst a slug not in the demo tenant silently shows dev-silo data (R-2). Scoping is honest for the demo gate.

**3 — pack-file-serve from dist / singleton / frozen e2e?** Loads module-relative via `import.meta.url` (`dist/http → ../../seed`), verified from foreign CWD and from dist. Singleton cache → pack.json edits need a restart (acceptable for dev, declared in ADR §7). `role_slug → id` alias keeps the frozen `Role` shape; `rights.e2e`/`processes.e2e` stay green.

**4 — seed reset idempotency?** Proven on the live DB: re-`apply` = all-skipped (409 no-op); `reset` = reconcile-to-reference (0 deletes/upserts when already at reference), org back to 3 depts, `e-owner` row intact. Reset's cross-tenant write succeeds because the seed-write genesis gate checks ownership of `DEV_TENANT_ID` and the migrator pool is BYPASSRLS (T-0140 bootstrap-authority design; noted as role_gap awareness).

**5 — FF self-tests honest / deferred declared?** All 8 `ci/checks/demo/*.sh` carry `# SELF-TEST` markers and their failure-injections fire correctly. Truly DB-gated checks (FF-APPLY-1, FF-SCOPE-3) `SKIP` gracefully when `DATABASE_URL` is unset and ran green here against the live DB. FF-PACK-2 / FF-FALLBACK-6 are NOT actually deferred (self-start a server) — see R-3 re: gate wiring vs ADR §9 wording.

**6 — gate discipline?** Clean. Only `ci/checks/demo/*` added — **zero** sibling `ci/checks/*.sh` touched. `package.json` is additive (new `fitness:demo`, `fitness:demo:db`, `seed:smoke`; `build` extended to compile `seed/`; 4 static demo checks appended to `fitness`). Committed `seed/cli.js`/`importer.js` match their `.ts` (recompile = no drift). No secrets in the diff.
