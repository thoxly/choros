## R-1 (iter-1 blocking) — re-verdict: **READ-путь решён; WRITE-путь = новый nit R-6**

### Read-путь — РЕШЁН по существу ✓

iter-1 R-1 = «как tenant-B-сессия читает `scope='system'`-доку под FORCE RLS, не вводя второй read/authz-путь».
Fix решает это **проекцией** (§2.4): system-доки физически живут в каждом тенанте как обычные `tenant_id=<его>`
строки (`scope='system'`, `authored_by='system'`, `catalog_version`), поэтому **все три потребителя (lint/MCP/UI)
читают ОДИН класс данных ОДНИМ путём** — `tenant_id = current_setting('choros.tenant_id')`, без второго
USING-предиката и без context-switch. Master-копия (`a0…001`) физически недостижима из чужой сессии (FORCE RLS
режет до `scope`). Проверено:

- **Прецедент RLS-политики верен:** `migrations/051_report_page.sql:79` — единственный USING `tenant_id =
  current_setting('choros.tenant_id', true)::uuid`, без `scope`. Проекция остаётся в этом паттерне (ноль
  второго предиката).
- **System-тенант реален:** `a0000000-…-001` — живой dev-тенант (`migrations/044_config_agent_seed.sql:32`).
- **Отвергнутые ветви (§7) обоснованы честно:** (б) выделенная RLS-политика `USING (scope='system')` = именно
  второй authorization-предикат не по `tenant_id` (правильно назван «второй read/authz-путь»); (в) глобальная
  таблица без RLS раскалывает «один слой» (NF-3) на две ветки чтения — оба отвергнуты в пользу проекции с
  корректным аргументом.
- **FF-DOCS-SYSTEM-PROJECTION** покрывает read-путь обеими гранями: static (`grep` политик `doc_page` ⇒
  единственный USING `tenant_id`; `grep` MCP/UI-слоя ⇒ нет `SET choros.tenant_id`/context-switch) + live-impl
  (B-сессия читает свою проекцию; `SELECT scope='system' AND tenant_id=a0…001` ⇒ 0 строк под FORCE RLS).

**Самый опасный угол (внешняя harness read-поверхность) закрыт структурно**, без второго механизма. R-1
blocking **снимается**.

### Write-путь проекции — честный шов, ADR его не называет (→ R-6 nit)

Fix **переместил** cross-tenant-операцию с read на write, но не назвал и не ограничил её. Чтобы записать
`scope='system'`-строки в `tenant_id = B` (где B ≠ сессия-источник и ≠ system-тенант), агент-поставщик
(§2.4 «реплицирует», T-0134i) ОБЯЗАН под FORCE RLS + `WITH CHECK (tenant_id = current_setting(...))` либо
(а) выставить `choros.tenant_id = B` для каждого целевого тенанта (тот самый tenant-context-switch, который
отвергнут на read-пути — теперь на write-пути), либо (б) писать привилегированной ролью мимо RLS. **Это
write-путь vendor→tenant, PDP/RLS-context-обходной по определению** — то есть **системная provision-операция**.

Это **защитимо**: провижн по природе кросс-тенантный (он *создаёт* тенант), и любой per-tenant seed уже это
делает — `044_config_agent_seed` (seed в `a0…001`), mcp_tool-seed T-0077 §2.3, инстанцирование каталога
T-0133. Это легитимный provision-time write, который **предшествует** любому внешнему/harness-доступу
(read-only). Поэтому — **не blocking**.

НО ADR не доводит честность read-разбора (§2.1-инвариант — образцовый) до write-стороны:
- **не назван под какой ролью** пишет проекция (provision/migrator-класс?),
- **не назван честно** PDP/RLS-context-обходной системной операцией (как read-ветви (а)/(б) названы «вторым
  путём» — write-ветвь заслуживает той же прямоты),
- **не ограничен**: только `scope='system'`-строки, только проекция (не произвольный cross-tenant write),
  с аудитом (`docs.system_projected` упомянут — хорошо, но не как граница write-полномочия),
- **нет FF на write-сторону.** Все FF (DOCS-TENANT, DOCS-SYSTEM-PROJECTION, T13-DOCS) ограничивают **чтение**;
  write-bypass проекции просто вне их периметра (FF грепает MCP/UI read-слой, провижн-writer — вне его), а DoD
  T-0134i лишь повторяет read-свойство. То есть «нет второго пути» доказано **только для read**; для write
  bypass не пойман, а вынесен из-под FF.

Корректный ход (R-6, nit): §2.4/T-0134i явно сказать — «проекция = provision-time системная операция,
context-обходная по определению; ограничена `scope='system'`-строками, projection-only, аудируется; не
открывает произвольный cross-tenant write» + FF, ограничивающая write-сторону (provision-writer пишет только
`scope='system'`, не `scope='tenant'`, и эта роль недоступна harness-поверхности).

**Итог R-1:** **снят** (read решён по существу, NF-1 на самой опасной поверхности удержан). Остаточная
write-честность — **R-6 nit**, не возврат.

## Verdict

**approved.** Fix `fc6e899` решает iter-1 R-1 blocking **по существу на самой опасной поверхности**: проекция
делает `scope='system'`-доки обычными per-tenant строками → один RLS-путь по `tenant_id` для всех трёх
потребителей, master-копия структурно недостижима из чужой сессии, FF-DOCS-SYSTEM-PROJECTION доказывает
read-инвариант (static + live). Отвергнутые ветви (б)/(в) обоснованы честно (§7). R-2..R-5 закрыты и
перепроверены против живой базы (report-page-compat.ts в base, 054=T-0128 смержен, T-0126 отсутствует,
build/CI-граница `code_symbol` зафиксирована). Контракт schema-валиден. 20/20 AC покрыты для day-1-рамки.

Остаётся **R-6 (nit, не возврат):** write-путь проекции (vendor→tenant) — честный provision-time
context-обходной шов, ADR довёл честность до read, но не до write (роль/границы/FF write-стороны не названы).
Это легитимная системная provision-операция (прецедент = `044`-seed / T-0077 / T-0133), предшествующая
внешнему read-доступу — потому не блокирует, но стоит назвать прямо в §2.4/T-0134i + добавить write-FF.
R-7 (nit) — T-0133 ещё не в base: импл-координация порядка T-0133 → T-0134i.

Дизайн крепкий, единый механизм прав/аудита/lint удержан, blocking снят. **approved.**
