## 2. Классификатор vs ADR §5.2 — построчно (ось 1)

| Правило ADR §5.2 | Реализация | Статус |
|-----------------|------------|--------|
| drop `field_key` (ключ в old, нет в new) → destructive для всех deps | `classifySchemaChange` строки 138-141: `if (!(field_key in newProps)) → destructiveDeps.push(dep)` | OK |
| rename = drop старого → destructive | Эквивалентен drop: dep на старый ключ → destructive (drop). Тест AC-3: "rename = drop old + add new → destructive for old dep" | OK |
| lossy type-narrowing при `dep_kind='aggregate'` → destructive | `isLossyNarrowing` + check `dep_kind === 'aggregate'`, строки 155-162 | OK |
| lossy type-narrowing при `dep_kind='read'` → soft | `dep_kind !== 'aggregate'` → `softWarnings.push(dep)`, строки 163-167 | OK |
| add field, enum widening, relabel, toggle required → no-op (нет нарушения для dep) | Нет явного ветвления: все эти случаи не дают `isLossyNarrowing=true` и не попадают в case 1 | OK |
| `number → integer` = lossy narrowing | `isLossyNarrowing`: `oldType === 'number' && newType === 'integer' → true` | OK |
| `string → enum` с меньшим vocab = lossy narrowing | `isLossyNarrowing`: old не-enum + new.enum присутствует при `oldType ∈ {string,number,integer}` → true | OK |
| enum → enum с меньшим набором = lossy narrowing | `isLossyNarrowing`: `newEnumSize < oldEntry.enum.length → true` | OK |

**Вывод:** классификатор полностью зеркалит ADR §5.2.

### Тонкость: `number → enum` с большим набором

Если old-field `{type:'number'}` (без enum) → new `{type:'number', enum:[1,2,3]}`, то `isLossyNarrowing` возвращает `true` (ветка "Was an open type, now constrained to enum"). Это корректно — сужение открытого числового типа до 3 значений деструктивно для aggregate-dep. ADR §5.2 это покрывает как "string→enum с меньшим vocab".

## 4. 409 default-DENY — force=false и отсутствие force идентичны? (ось 2)

```ts
const force = body["force"] === true;   // строка 385
```

- `force=true` → `true` (force path)
- `force=false` → `false === true` → `false` → deny
- `force` отсутствует → `undefined === true` → `false` → deny

Обе формы ("absent" и "false") дают `!force === true` → 409. **Spec FR-4 / ADR §5.2 "default-DENY" выполнен.**

## 7. Findings (6 осей рубрики)

### R-1 — **BLOCKING** | Ось 6 (gate discipline) | `ci/checks/db/schema_change_api.test.ts:431-457`

**Issue:** Тест "Route registration (no-DB)" падает при запуске в полном наборе (`1 failed | 533 passed`) с результатом `expected 404 to be 503`. Причина — **утечка module-level синглтона `_pool`** из `src/http/registry-defs.ts`: при запуске после live-DB тестов `_pool` уже установлен (кэш ESM-модуля), поэтому `getPool()` не бросает `HttpError(503)`, а возвращает существующий пул. Конкретная последовательность: live-тесты устанавливают `_pool` → тест удаляет `DATABASE_URL` и создаёт новый `createServer()` → `getPool()` возвращает старый пул → запрос проходит в handler → пул пытается подключиться к уже удалённой test-DB → ошибка не `HttpError` → роутер отдаёт 500 INTERNAL... или статик-хэндлер отдаёт 404 (PUT → `throw new HttpError(404, 'NOT_FOUND', ...)`). Тест видит 404.

**Воспроизводится:** `DATABASE_URL=... npx vitest run --dir ci/checks/db --no-file-parallelism` → провал последнего теста.

**Не воспроизводится в изоляции:** `--testNamePattern="Route registration"` → pass.

**Suggestion:** Экспортировать `resetPoolForTesting()` из `registry-defs.ts` (аналог паттерна из `artifacts.ts` / `binding.ts` если они имеют его) или переписать тест так, чтобы он создавал сервер с явным `_poolHint=null` или запускался первым в своём файле. Простейший fix: переместить тест "Route registration" в НАЧАЛО файла (до live-DB тестов), чтобы `_pool` был ещё не установлен.

---

### R-2 — **Nit** | Ось 1 (correctness) | `src/http/registry-defs.ts:186-402`

**Issue:** `kind: "noop"` определён в union `UpdateSchemaResult` (строка 188) и обрабатывается в response-logic (строки 399-404), но `updateSchemaInTx` **никогда его не возвращает**. Ветка "unchanged schema" в handler-е не реализована — идентичный `record_schema` всё равно триггерит DB UPDATE и возвращает `{updated:true}`. Spec-comment ("If record_schema is absent or unchanged → 200 { updated: false }") содержит "unchanged" как no-op, но реализация его не детектирует.

**Suggestion:** Либо убрать `noop` из union и удалить мёртвый branch (`result.kind === "noop"`), либо добавить сравнение `JSON.stringify(oldSchema) === JSON.stringify(newSchema)` перед применением UPDATE.

### R-3 — **Nit** | Ось 4 (test coverage) | `ci/checks/db/schema_change_api.test.ts:12`

**Issue:** AC-13 ("Partial failure → ROLLBACK: record_schema не изменена, stale=false, tier='published'") указана в заголовке файла как покрытая, но живого теста нет — только comment. Rollback-корректность force-пути при ошибке `appendAuditEvent` не верифицирована live-пробой.

**Suggestion:** Добавить тест с mock/spy на `makePgAuditWriter` который бросает исключение внутри транзакции; затем проверить, что `record_schema`, `stale` и `tier` остались неизменными.

### R-4 — **Nit** | Ось 2 (design clarity) | `src/http/registry-defs.ts:244`

**Issue:** `SET LOCAL choros.promoting = '1'` (строка 244) выставляется до ветки `if (destructiveDeps.length === 0) return {kind:'soft'}` (строка 247). В soft-пути GUC бесполезен (нет UPDATE report_page), код вводит читателя в заблуждение.

**Suggestion:** Переместить `SET LOCAL choros.promoting = '1'` ниже — в начало блока "7b. Force path" (после проверки `destructiveDeps.length === 0`).

### R-5 — **Nit** | Ось 3 (efficiency) | `src/http/registry-defs.ts:277-288, 293-301`

**Issue:** Депромоут deps и pages выполняется цикломи по одному UPDATE на dep/page вместо batch. При большом числе затронутых deps (тысячи) — N+1 roundtrips.

**Suggestion:** Заменить на `UPDATE ... WHERE (page_id, field_key) IN (SELECT * FROM unnest($1::uuid[], $2::text[]))` или аналогичный batch-запрос. Для MVP объёмов не критично.
