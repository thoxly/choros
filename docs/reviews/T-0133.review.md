## Адверсариальные проверки (по пунктам задания)

### 1. «Лишняя секция `process_templates` не ломает существующий seed apply/reset» — ВЕРНО, но обоснование в ADR неточно
- `importer.ts::validatePackShape` проверяет только **наличие** `required`-полей; неизвестные
  ключи **игнорируются**, а apply-loop итерирует закрытый `LIVE_ENTITY_ORDER` →
  `process_templates` не итерируется и не ломает apply/reset. **Аддитивность безопасна — TRUE.**
- НО ADR (§1/§2.1, claim «лишняя секция **отвергнется живым импортёром**») утверждает
  обратное направление и оно **неточно**: (а) importer extras **не отвергает**, а игнорирует;
  (б) живой гейт `ci/checks/seed/pack-schema-valid.sh` использует **собственный Node-валидатор,
  который НЕ соблюдает `additionalProperties:false`** (нет обработки `additionalProperties` —
  только required/properties/items/enum/pattern/minLength) — то есть неизвестная секция
  **пройдёт** гейт даже без правки схемы. Схема имеет `additionalProperties:false`, но
  единственный гейт над ней этого не применяет. → **R-2 (nit).** Сам вывод ADR (аддитивно =
  безопасно) от этого не страдает.

### 2. «process_templates в pack.json как у seed-pack, ноль изменений существующих гардов» — внутреннее напряжение
- §5 заявляет «ноль изменений существующих гардов», §7 BUILD-A «расширить
  `seed/pack.schema.json` секцией `process_templates[]`». Схема **является** гардом FF-1
  (`pack-schema-valid.sh`) и **будет изменена**. Честное секвенирование есть в §7, но строка
  §5 буквально противоречит. → **R-3 (nit, ось 1/4).**

### 3. Инстанцирование «через публичные authoring-API (T-0129/T-0077)» — живые ли?
- Живые write-API: org/roles/grants/role-assignments/report-pages. **Process/BPMN authoring
  API и forms authoring API — НЕ существуют** (`/api/processes` = display-plane GET; POST на
  bpmn-def/form-def нет). Это **[НОВАЯ]/deferred**, не живой путь.
- ADR **честен** об этом по сути: §1 «form-def/bpmn-def-таблиц нет», наследует T-0082
  deferral-контракт, инстанциатор вынесен в BUILD-B. НО контракт §4 формулирует
  `instantiateTemplate ... поверх ПУБЛИЧНЫХ authoring-API` без маркера [deferred] — читается
  как живой. → **R-4 (nit, ось 4):** пометить authoring-API инстанцирования как
  deferred/[НОВАЯ] явно, как сделано для form/bpmn в §1.

### 4. `parameters[].target` резолвимость при ИМПОРТЕ vs оргструктура клиента — РАЗВЕДЕНО ЧЕСТНО
- §3.4 + FF-2: `target` для `role-binding` = **абстрактная роль/узел самого бандла**,
  `default: null`; резолвится при загрузке каталога **против бандла**, НЕ против оргструктуры
  клиента (она неизвестна на импорте). Маппинг роль→**живой узел оргструктуры** — момент
  интервью (T-0129 FR-4), `default null`. FF-2 проверяет только «target резолвится в узел/роль
  **бандла**» — не против клиента. **Граница проведена корректно, без подмены.** Замечаний нет.

### 5. FF-self «создан файлом или [обещан]?» — ОБЕЩАН, при этом заявлен исполнимым СЕЙЧАС
- `ci/checks/T-0133-adr-shape.sh` **не существует** (DESIGN-коммит db913d6 добавил только
  2 doc-файла). ADR §5 называет FF-self **«DESIGN-гард, исполним сейчас»**,
  **«исполним на этой фазе DESIGN»**, «Покрывает AC-2/AC-5/AC-13/AC-14 fitness».
- **Калибровка:** прецедентные DESIGN-ADR (T-0082/T-0129/T-0130/T-0128) **тоже не везут**
  self-shape CI-файл — конвенция «DESIGN везёт контракт-гарда, не файл». То есть отсутствие
  файла — норма; проблема узкая: **только T-0133 уникально заявляет present-tense
  исполнимость**, которой нет, и именно на ней висит `fitness`-верифицируемость
  AC-2/AC-5/AC-13/AC-14 (спека помечает их `verifiable_as: fitness`). → **R-1 (nit, ось 4):**
  либо материализовать `T-0133-adr-shape.sh` в этой DESIGN-поставке (тогда заявление
  правдиво), либо переклассифицировать FF-self в build-наследуемую (как FF-1..FF-5) и убрать
  «исполним сейчас». Контент ADR покрывает эти AC и проверяем вручную — поэтому **nit, не
  blocking**.

### 6. Непротиворечие T-0129/T-0130/§11 — ДЕРЖИТСЯ
- Граница T-0133↔T-0129 (что параметризуемо / как заполняется) проведена явно (§2.4, AC-5),
  интервью не дублируется. Инстанс не минует прогон T-0130/human-gate (§2.4, NF-2). §11
  managed-solution применён как уже зафиксированный durable-риск (notify-only day-1,
  three-way-merge → Stage-2 deferral), не переоткрыт. Противоречий нет.

### 7. Контракт-валидность
- `T-0133.adr.contract.json` структурно валиден против `adr.schema.json` (task_id/pattern,
  status enum, decision, fitness_functions minItems≥1 — 6 FF, traceability 14 AC). Соответствует
  телу ADR (object_model/contracts/rejected_alternatives зеркалят §2–§4). Замечаний нет.

## Резюме

ADR **архитектурно состоятелен, полон (14/14 AC по существу), опирается на ЖИВЫЕ механизмы**
(seed-pack importer-over-HTTP, bundle-coherence+deferral, appendAuditEvent, тиры §8,
managed-solution §11, T-0129 FR-4, T-0130) и **честно секвенирует** недоматериализованное
(form/bpmn authoring, three-way-merge) через deferral-контракт T-0082. Ключевое разведение
`target`-резолвимости (бандл при импорте vs живая оргструктура при интервью) проведено
корректно. Четыре нита — про **точность формулировок** (FF-self present-tense overclaim,
«отвержение» импортёром, «ноль изменений гардов», authoring-API без [deferred]-маркера), не
про существо решения. Ни одного blocking. **Verdict: approved.**
