# T-0581 — SPEC · Список как настраиваемый блок + фундамент реестра представлений (view registry)

> Фаза SPEC (analyst). Столп 2 («интерфейс из блоков на данных»). Кейс-доказательство:
> **CRM — «список сделок под себя»** (референс-кейс К1). Сегодня список записей приложения
> **автогенерируется и не настраивается** — это первый шаг «интерфейса из блоков»: список
> перестаёт быть жёстким автогеном и становится **сохраняемым представлением**, а его
> хранилище — **реестром представлений**, поверх которого T-0582 строит канбан.
>
> spec_ref: `docs/choros-primitives-map-2026-07-02.md` §B2 (список — «есть, но это не блок»),
> §B7 (страницы из блоков — ядро столпа 2 не начато). Анти-кейс (D-064): примитив
> **generic** — никаких «сделок/стадий» в платформенном коде; CRM — только тест-материал.

## 0. Контекст: что есть сегодня (разведка кода)

- **Список** рендерит `web/src/screens/screen-app-records.jsx` (`AppRecordsScreen`): таблица
  `<table class="chs-itable">`, колонки выводятся из схемы набора полей на КАЖДОЙ загрузке
  через `schemaToColumns(record_schema)` (`web/src/screens/records-form.js:933`). **Сортировка и
  фильтры отсутствуют**; порядок фиксирован `ORDER BY created_at DESC, id ASC`; настройка
  колонок нигде не сохраняется.
- **Список-эндпоинт** `GET /api/records` (`src/http/records.ts:1617`,
  `listRecordsPaginated:1127`) принимает `application_id`, `registry_def_id`, `limit`, `after`
  (keyset-курсор). Данных-фильтров/сортировки нет. Тенант-изоляция — RLS
  (`withTenantTx` + `SET LOCAL choros.tenant_id`), поверх неё sandbox-gate (T-0558),
  field-visibility redaction (T-0419) и **READ-PDP** (T-0570): страница грузится, затем
  **фильтруется в памяти** `isRecordReadable` (`src/core/read-visibility.ts:130`) —
  единственный источник видимости-чтения (`grant`-латтис T-0018, без второго ACL).
- **Типы полей** (`web/src/screens/apps-schema.js:107` `FIELD_TYPES`): `string, number,
  integer, boolean, select, multi-select, date, url, email, money, relation, person,
  collection, computed`. В `record_schema` (JSONB) хранится JSON-Schema `type`
  (`string`/`number`/`boolean`/`array`) + семантические аннотации `x-relation`, `x-money`,
  `x-multi-select`, `x-rollup`, `x-person`, `x-field-order`. `computed` и `collection` **не
  хранятся** в `record.data` (computed считается на чтении).
- **Похожей «view/saved-view» сущности нет.** Ближайший аналог хранения per-tenant/per-app
  JSONB-конфига — `report_page` (migration 051): tenant-scoped, `slug`/`title`/`tier`, RLS.

## 1. Что строим (summary)

**Сохраняемое представление (view)** = именованная, tenant-scoped конфигурация показа записей
одного приложения(набора полей): `{ columns (видимость+порядок+ширина), filters, sort }`.
Представления живут в **реестре представлений** — новой tenant-сущности `list_view` с полем
`type` (`list` сейчас; `kanban` и др. — расширение, T-0582) и JSONB-конфигом с **рантайм-
валидацией схемы конфига**. Текущий автоген-список становится **default-представлением** (когда
у набора полей нет ни одного сохранённого view — рендерится синтетический default из
`record_schema`). Сервер применяет фильтры/сортировку (не клиент), **через существующий
data-слой с READ-PDP** — новый прямой SQL-путь мимо PDP запрещён.

## 2. Функциональные требования

- **FR-1 — Сущность представления.** Существует tenant-scoped сущность «представление»
  (`list_view`) с полями: владелец-набор (registry_def) и/или приложение, `type` (v1 = `list`),
  `name`, JSONB-`config`, `is_default`, тайм-штампы. Уникальность имени в разрезе
  (tenant, набор полей). Реестр расширяем под другие `type` без изменения контракта (T-0582
  добавляет `kanban`).
- **FR-2 — Конфиг представления (v1, тип list).** `config` описывает:
  - **columns**: упорядоченный список `{ field_key, visible, width? }`. Порядок массива = порядок
    колонок. `visible=false` скрывает колонку. `width` — опциональная ширина (px или доля).
    Каждый `field_key` — либо ключ поля из `record_schema`, либо системная псевдо-колонка
    `created_at` (та же, что «Создано» сегодня).
  - **filters**: массив условий `{ field_key, op, value }`, соединённых **AND** (v1). Набор
    операторов **зависит от типа поля** (см. FR-5).
  - **sort**: массив `{ field_key, dir }` (`dir ∈ asc|desc`); v1 допускает ≥0 ключей, применяется
    как многоключевой ORDER BY по полям, **допустимым для серверной сортировки** (FR-6).
- **FR-3 — Default-представление.** Для набора полей без сохранённых представлений
  список отдаёт **синтетический default** (все поля видимы в порядке `x-field-order`, без
  фильтров, сортировка `created_at desc` — байт-эквивалент сегодняшнему поведению). Как
  только у набора появляется ≥1 сохранённое представление, одно из них может быть помечено
  `is_default=true` и открывается по умолчанию; максимум одно default на (tenant, набор полей).
- **FR-4 — CRUD представлений.** Пользователь создаёт/читает/обновляет/удаляет представления
  из UI **без кода**: панель настройки колонок (видимость/порядок/ширина), конструктор
  фильтров (по полю + оператор по типу), конструктор сортировки. Изменения сохраняются в
  реестр и переживают перезагрузку/сессию/устройство (server-persisted, не localStorage).
- **FR-5 — Фильтры v1: операторы по типу поля.** Сервер фильтрует по полям записи операторами,
  соответствующими типу поля (тип берётся из `record_schema`, не угадывается):
  - текст (`string`/`url`/`email`): `eq`, `neq`, `contains`, `starts_with`, `is_empty`, `is_not_empty`;
  - число/`integer`/`money`: `eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `between`, `is_empty`, `is_not_empty`;
  - `date`: `eq`, `before`, `after`, `between`, `is_empty`, `is_not_empty` (диапазон дат);
  - `boolean`: `is_true`, `is_false`, `is_empty`;
  - `select`: `eq`, `neq`, `in`, `is_empty`, `is_not_empty`;
  - `multi-select`: `contains_any`, `contains_all`, `is_empty`, `is_not_empty`;
  - `person`, `relation`: `eq`, `neq`, `is_empty`, `is_not_empty` (сравнение по хранимому id).
  - `computed`, `collection`: **не фильтруются на сервере v1** (computed не хранится; collection —
    вложенный массив) — попытка задать фильтр по такому полю отклоняется валидатором конфига.
- **FR-6 — Серверная сортировка по хранимым скалярам.** Сортировка применяется на сервере по
  полям, физически хранимым как скаляр в `record.data` (`string`/`number`/`integer`/`money`/
  `date`/`boolean`/`select`) + псевдо-поле `created_at`. Поля `computed`/`collection`/
  `multi-select`/`relation`/`person` **не сортируются на сервере v1** (валидатор конфига
  отклоняет их в `sort`). Сортировка стабилизируется вторичным ключом `id` (детерминизм страниц).
- **FR-7 — Применение через data-слой с READ-PDP (без обхода PDP).** Фильтры/сортировка
  реализуются в том же tenant-scoped пути `GET /api/records`, что уже несёт RLS + sandbox-gate +
  READ-PDP (`isRecordReadable`) + field-visibility. **Запрещён** новый прямой SQL-путь к
  `choros.record`, обходящий эти гейты. Фильтр по полю, скрытому field-visibility-грантом
  актора, **не раскрывает** его значение (см. FR-8).
- **FR-8 — Фильтр не обходит field-visibility.** Условие фильтра по полю, которое актор не
  вправе видеть (redacted его грантом), не должно превращаться в оракул значений: такое
  условие либо игнорируется (поле для актора отсутствует → строка не матчится/матчится по
  тем же правилам, что и отсутствие значения), либо отклоняется. Точную семантику фиксирует
  DESIGN; требование — **фильтр не даёт увидеть значение скрытого поля косвенно**.
- **FR-9 — Tenant-изоляция реестра.** Представление тенанта A невидимо и неизменяемо из тенанта
  B (RLS-паттерн продукта: `tenant_id`-leading PK, ENABLE+FORCE RLS, default-DENY policy).
- **FR-10 — Модель видимости представлений (v1): общие для тенанта.** Представления —
  **конфигурация приложения, общая в пределах тенанта** (не per-user): любой актор тенанта,
  имеющий доступ к набору полей, видит и применяет сохранённые представления. Создание/
  редактирование/удаление представления — привилегия конфигуратора (owner/admin ИЛИ
  `authoring_draft`-грант — тот же уровень, что правка записей/схемы: `resolveActorPrivilege`,
  как в DELETE /api/records). Обоснование решения — §6.
- **FR-11 — Расширяемость под канбан (фундамент, не реализация).** Контракт сущности и конфига
  спроектирован так, что T-0582 добавляет `type='kanban'` и `kanban`-ветку конфига (группировка
  по select-полю) **без изменения** таблицы, CRUD-контракта и валидатора-диспетчера — только
  добавлением нового вида конфига. Канбан в этой задаче **НЕ реализуется**.

## 3. Нефункциональные требования

- **NF-1 — Не N+1.** Применение представления не добавляет пер-строчных запросов PDP/грантов:
  резолюция грантов актора остаётся O(1) на HTTP-запрос (как в T-0570), фильтр/сортировка —
  в одном SQL-запросе.
- **NF-2 — Обратная совместимость.** `GET /api/records` без параметров представления ведёт себя
  **байт-идентично** сегодняшнему (default-представление = текущий автоген). Существующий
  фронт и frozen-контракт ответа `{ records, nextCursor, limit }` не ломаются (новые поля —
  аддитивны/опциональны).
- **NF-3 — Tenant isolation не ослабляется.** RLS + явный tenant-фильтр остаются ПЕРВЫМ и
  обязательным фильтром; фильтры/сортировка представления — поверх, никогда вместо.
- **NF-4 — Анти-кейс (D-064 §5).** Ни одной кейс-строки (`role-approver`, `soglasovanie`,
  `tel-`, `Согласование`-как-константа, `telLinear`, `e-larina`/`e-orlov`, `approvalRequired`,
  «сделка»/«стадия»/«deal»/«stage» как платформенная константа) в коде, добавленном этой
  задачей. Реестр — generic-примитив; агрегат anti-case-lock не растёт.
- **NF-5 — Пропорциональность.** Переиспользует существующий data-слой (`records.ts`,
  `data-access-port.ts`, `read-visibility.ts`), AJV-валидатор (`record-schema-validator.ts`
  как образец), RLS-шаблон (`report_page`/`section`); не переизобретает латтис-математику,
  курсор-пагинацию и PDP.
- **NF-6 — Инъекционная безопасность динамического ORDER BY/WHERE.** `field_key` в sort/filter
  никогда не подставляется в SQL как текст: он валидируется против ключей `record_schema` и
  сопоставляется с параметризованным JSONB-путём; значения — только через bind-параметры.
- **NF-7 — UX-гейт (D-062/OBLIK).** Панель настройки колонок/фильтров/сортировки проходит
  UX honest-gate G1–G7 (контраст ≥ WCAG AA в обеих темах, нет мёртвых enabled-аффордансов,
  Empty/Loading/Error-состояния, без дев-жаргона «view/registry/JSONB», потребление слоя без
  хардкода цвета).

## 4. Явные не-цели (out of scope)

- **Канбан** (`type='kanban'`, группировка по select) — T-0582 поверх этого реестра.
- **Календарь/гант/произвольные страницы из блоков** (B4/B7 карты) — отдельная стройка.
- **Per-user приватные представления** («моё представление») — v1 общие для тенанта (§6);
  per-user — возможное расширение поверх той же таблицы (добавлением owner-колонки), не сейчас.
- **OR/вложенные группы условий фильтра** — v1 только плоский AND.
- **Настройка представлений ассистентом** (столп 5) — реестр должен быть механически
  доступен ассистенту позже, но AI-emit представлений — не эта задача.
- **Сохранение ширины/порядка колонок как per-user-эфемерного состояния** (drag-resize без
  явного сохранения) — v1 ширина/порядок живут только внутри именованного представления.
- **Экспорт представления в bundle/шаблон** (J3 карты) — не сейчас.
- **Полнотекстовый поиск / релевантность** — фильтры v1 = точные операторы по полю.
- **Агрегаты/группировки-в-списке** (кроме существующего computed on-read) — не сейчас.

## 6. Решение по модели видимости представлений (зафиксировано, не BLOCKING)

Задача разрешает выбор «общие для тенанта vs per-user» **по существующей модели прав**, не
эскалируя. Решение: **v1 — представления общие для тенанта** (FR-10). Обоснование:

1. **Соответствие существующей модели.** Сегодня конфигурация приложения (набор полей, форма,
   разделы, привязки процессов) — **общая для тенанта**, правится конфигуратором (owner/admin |
   `authoring_draft`), а не приватна per-user. Представление — это конфигурация показа
   приложения, того же класса; делать его per-user значило бы вводить новую ось прав, которой в
   продукте нет.
2. **Кейс-доказательство К1** («список сделок под себя») читается как «настроить список
   приложения под рабочий процесс команды», а не «у каждого свой приватный список» — общий
   настроенный список закрывает кейс.
3. **Меньше поверхность прав.** READ-видимость строк уже гейтится READ-PDP (T-0570): даже при
   общем представлении каждый актор видит в нём только доступные ему строки — приватность
   данных обеспечена слоем ниже, представлению не нужно её дублировать.
4. **Расширяемость.** Per-user приватные представления добавляются поверх той же таблицы
   (nullable `owner_actor` + правило видимости) — не переделкой, а расширением. Зафиксировано
   как явная не-цель, чтобы v1 не разросся.

Это решение — в компетенции analyst по существующей модели прав (директива задачи), поэтому
**статус спеки `ready`**, blocking-вопросов нет.

## 7. Трассировка кейса (столп 2, К1)

- Сегодня: список «сделок» = автоген всех полей, фикс-порядок, без фильтра/сортировки → «не
  блок» (§B2 карты).
