# Spec: Формат форма-документа (фундамент F1, эпик E-FORMS T-0479)

Статус: DRAFT · 2026-06-25. Реализует фундамент F1 (T-0480).
Опирается на [forms-data-contract-foundation.spec.md](forms-data-contract-foundation.spec.md)
(§3.1 каталог контрактов, §3.2 валидация, **§6 направление: drag-n-drop как основной авторинг**)
и ADR [extensibility-and-authoring.md](../design/extensibility-and-authoring.md) (named-binding, Floor-1/2).

## 1. Зачем
Нужен ОДИН сериализуемый артефакт «как выглядит форма», который:
- правит **человек** (drag-n-drop, основная среда — F2),
- эмитит **бот** (ИИ выдаёт тот же документ — уточнение PD-9 «форма→документ», не сырой React),
- рисует **один рендерер** детерминированно,
- валидируется против ЖИВОЙ схемы данных (PD-9: только существующие поля).

Это убирает корни тонкого D3: 4 рассинхрон-рендерера, снимок-вместо-вида (enum→текст), запись без
валидации (JSONB-дрейф). См. D7 §2.

## 2. Модель документа (верхний уровень)

```jsonc
{
  "schemaVersion": 1,
  "source": {                      // откуда поля — обязательно
    "applicationId": "<uuid>",
    "registryDefId": "<uuid>"      // набор полей; типы/options тянутся из ЖИВОЙ record_schema
  },
  "step": {                        // опционально — только для формы ШАГА процесса
    "processKey": "purchase-approval",
    "step": "Согласование"         // == значение поля «Шаг» в карточке инбокса (named-binding)
  },
  "root": { "type": "section", "children": [ /* дерево узлов */ ] }
}
```

- **Нет `step`** → форма ЗАПИСИ (создать/править запись приложения).
- **Есть `step`** → форма ШАГА (что человек заполняет в инбоксе на этом шаге).
- Формат ОДИН для обоих (различие только в `step` + режимах §5).

## 3. Типы узлов (дерево `root.children`)

Два класса узлов. **Порядок = порядок в массиве `children`** (отдельного `display_order` нет — дерево и есть раскладка).

### 3.1 Презентационные (НЕ привязаны к полю)
| type | назначение | свойства |
|---|---|---|
| `section` | озаглавленная группа | `title?`, `collapsible?`, `children[]` |
| `columns` | n колонок в ряд | `count` (2..4), `children[]` (по колонкам) |
| `tabs` | вкладки | `tabs: [{title, children[]}]` |
| `divider` | разделитель | — |
| `text` | статичный текст/подсказка | `content` (markdown-lite) |

### 3.2 Привязанные к данным
| type | привязка | свойства |
|---|---|---|
| `field` | скалярное поле | `fieldKey`, `widget`, `label?`, `mode?`, `placeholder?` |
| `table` | поле-`collection` (Позиции) | `fieldKey`, `columns: [{subKey, widget, label?}]`, `mode?` |
| `readout` | поле-`computed` (Итого) | `fieldKey`, `label?` (всегда read-only) |
| `relation` | поле-`relation` (Контрагент) | `fieldKey`, `widget:"record-picker"`, `displayField?`, `mode?` |
| `custom` | escape (Floor-2 кл-б) | `componentId`, `bindings:[fieldKey...]` — sandbox-iframe, редкий, флагованный |

`custom` — ВНЕ основного пути (рисуется в sandbox, трогает состояние только через перечисленные
`bindings`, не мутирует процесс напрямую — инвариант ADR §9). В drag-n-drop палитре помечен «код».

## 4. Привязка к полю (named-binding) — анти-дрейф

- `fieldKey` (и `subKey` для table) == ключ поля в `registry_def.record_schema` == имя процесс-переменной
  (named-binding инвариант). Документ хранит ТОЛЬКО ключ + презентацию.
- **Тип и `options` поля НЕ хранятся в документе** — резолвятся из ЖИВОЙ `record_schema` на рендере.
  Это чинит снимок-дрейф D7 §2 (раньше options терялись → enum рисовался текстом).
- Снятое из схемы поле → узел становится «битым» и подсвечивается на авторинге (а не молча пропадает).

## 5. Режимы поля по шагу (D7-9)
`mode` на field/table/relation узле: `editable` (дефолт) · `readonly` · `hidden` · `required`.
Для формы ШАГА режим может отличаться от формы записи (на «Согласовании» Сумма=`readonly`, кнопка
решения — действие шага, не поле). Реализация: режим в самом узле документа шага (документ шага —
свой, не overlay; так проще и для drag-n-drop, и для ИИ).

## 6. Каталог виджетов по типу поля (контракты D7 §3.1)
Авторинг-валидатор разрешает только совместимые пары «тип поля → widget»:

| Тип поля (record_schema) | допустимые `widget` |
|---|---|
| string | `text` (дефолт) · `textarea` · `select` (если в схеме enum/options) |
| number / integer | `number` (дефолт) · `money` |
| boolean | `switch` (дефолт) · `checkbox` |
| select | `select` (дефолт) · `radio` |
| date | `date` (дефолт) · `date-range` |
| relation | `record-picker` (только) |
| collection | `table` (только; через узел `table`) |
| computed | `readout` (только; read-only) |

Несовместимая пара (напр. `money` на string) → ошибка авторинга. Палитра drag-n-drop показывает для
выбранного поля только допустимые виджеты.

## 7. Сериализация и хранение
- Документ = JSON, поле `layout jsonb` в `form_binding` (эволюция таблицы; старый снимок `fields`
  депрекейтится, миграция переносит его в минимальный документ: плоский список `field`-узлов).
- Ключ хранения: `(tenant_id, process_key, step)` для формы шага; `(tenant_id, registry_def_id, kind='record')`
  для формы записи (одна на набор по умолчанию).
- Tenant-isolated (RLS как всё), правка — за грантом авторинга (`authoring_draft` / owner).

## 8. Три драйвера — один документ + валидация
- **Человек (F2):** drag-n-drop правит дерево; палитра ограничена каталогом §6; битые привязки видны.
- **Бот:** ИИ эмитит документ этого же формата; перед сохранением — тот же авторинг-валидатор.
- **Рендерер (F1):** обходит дерево, по `fieldKey` берёт тип/options из живой схемы, рисует widget.
- **Валидация двухфазная:** (а) авторинг — каждый `fieldKey` существует в схеме + пара тип→widget
  допустима; (б) сабмит (D7-2) — значения против живой `record_schema`, неизвестные ключи отклоняются.

## 9. Пример: форма шага «Согласование» (кейс Заявка)

```jsonc
{
  "schemaVersion": 1,
  "source": { "applicationId": "588fa343-…", "registryDefId": "52bd9fdc-…" },
  "step": { "processKey": "purchase-approval", "step": "Согласование" },
  "root": { "type": "section", "children": [
    { "type": "section", "title": "Заявка", "children": [
      { "type": "columns", "count": 2, "children": [
        { "type": "field",    "fieldKey": "amount",       "widget": "money",        "label": "Сумма",      "mode": "readonly" },
        { "type": "relation", "fieldKey": "counterparty", "widget": "record-picker","label": "Контрагент", "mode": "readonly" }
      ]},
      { "type": "table", "fieldKey": "items", "label": "Позиции", "mode": "readonly", "columns": [
        { "subKey": "product",  "widget": "text",   "label": "Товар" },
        { "subKey": "quantity", "widget": "number", "label": "Кол-во" },
        { "subKey": "price",    "widget": "money",  "label": "Цена" }
      ]},
      { "type": "readout", "fieldKey": "total", "label": "Итого" }
    ]}
  ]}
}
```
Согласующий видит данные read-only + действие шага «Согласовать» (действие процесса, не поле формы).

## 10. Границы / не входит
- **Правило границы Floor-1↔Floor-2** (§9.2/D7-5) — отдельно (обсуждается). Здесь зафиксировано лишь,
  что 99% = узлы документа (drag-n-drop ИЛИ ИИ), `custom`-узел = редкий код-escape.
- **Виджеты-представления** Гант/канбан/календарь (Floor-2 поверх контрактов) — не форма-документ, отдельно.
- **Посредник данных + лимиты** (D7-3) — отдельная задача.

## 11. Что реализует F1 vs F2
- **F1 (T-0480):** §2–§8 — схема документа + авторинг-валидатор + ОДИН рендерер (резолв типов из живой
  схемы) + сабмит-валидация. Без визуального редактора — документ можно создать программно/ИИ.
- **F2 (T-0481):** drag-n-drop поверх §3 палитры + ИИ-эмиттер документа. Основная среда авторинга.
- **F3 (T-0482):** снести ТЭЛ-предпросмотр, форму записи рендерить из схемы дефолтным документом,
  форму шага — в панели userTask модельера (D8 §3.7).

## 12. Acceptance (F1)
- Программно/ИИ создан документ §9 → рендерер рисует 2 колонки + таблицу позиций + readout «Итого»,
  типы/options взяты из живой схемы (enum рисуется select, не текстом).
- `fieldKey`, которого нет в схеме → авторинг-ошибка (не молчит); пара `money`+string → авторинг-ошибка.
- Сабмит с лишним ключом → отклонён (не пишется в JSONB).
- Один и тот же документ-формат используется и формой записи (без `step`), и формой шага (со `step`).
