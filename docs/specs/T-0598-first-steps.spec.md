находки №1 и №7. Рамки заданы в задаче T-0598 (UX-петля №1+№7).

Отчёт уже установил: «Обзор» (`screen-overview.jsx`) молчит про критический

## FR-1 (= находка №1) — полоса «Первые шаги» на Обзоре

**Файл:** `web/src/screens/screen-overview.jsx`.

**Паттерн (uxpatterns MCP, сверено через `get_pattern`):**
`patterns/advanced/wizard` («Wizard / Stepper» — "Use for onboarding... with
dependencies", non-blocking-вариант — шаги не блокируют друг друга, каждый
достижим независимо через прямую навигацию) — некоторые шаги в нашем случае
одноходовые ссылки, а не последовательный gate; это НЕ multi-step form с
back/next, а checklist-презентация того же паттерна (Step indicator + прямое
действие на каждый шаг, без Review-шага и без save/resume state — состояние
целиком производно от живых данных, не персистится отдельно). Дополнительно
`patterns/user-feedback/empty-states` (first-use variant: message + primary
action) информирует тон отдельных шагов, у которых чек ещё не пройден.

**Должно быть:**
- Тонкая горизонтальная полоса над сеткой плиток (`gridStyle`), рендерится
  ТОЛЬКО пока хотя бы один шаг не выполнен (см. FR-1.5 — скрытие).
- Три обязательных шага + один опциональный:
  1. **«Создайте приложение»** — done, когда `GET /api/applications` вернул
     `applications.length > 0`. CTA «Создать приложение» → `navigate('/apps')`.
  2. **«Подключите LLM-ключ»** — done, когда у ассистента тенанта есть
     привязанный LLM-коннекшн. Источник сигнала: `GET /api/agents` (уже
     грузится этим же экраном не будет — экран сегодня его не фетчит,
     добавляем как ЧЕТВЁРТЫЙ best-effort фетч, симметричный трём существующим)
     → находим `agents.find(a => a.agent_type === 'assistant')` (та же чистая
     функция `resolveAssistantBinding`, что уже существует и экспортирована в
     `screen-llm-connections.jsx:176-184` — переиспользуем импортом, НЕ
     дублируем логику) → done = `assistant.llm_connection_id != null` (что
     ровно то же самое условие, что `serializeAgent` в
     `src/http/agents-list.ts:189` уже проецирует как
     `status: 'configured'`/`llm_bound: true` для того же агента). Это работает
     БЕЗ капабилити `llm_connection:configure` (в отличие от
     `GET /api/llm-connections`, который требует owner/grant и вернул бы 403
     рядовому сотруднику) — `GET /api/agents` защищён только `withAuth`, так
     что шаг честно виден и не-админу (хотя CTA «Подключить» ведёт на
     `/llm-connections`, где форма сама скрыта/недоступна не-админу — это
     существующее поведение экрана назначения, не меняется этим T). CTA
     «Подключить ключ LLM» → `navigate('/llm-connections')`.
  3. **«Спросите ассистента»** — done, когда есть хотя бы один тред с
     `message_count > 0`. Источник: `GET /api/assistant/threads` (тот же
     список, что грузит `screen-assistant.jsx`) — дёшево (один HTTP-вызов,
     JSON уже содержит `message_count` в каждом элементе по контракту
     `fetchThreads`/`ThreadRow`, лишний парсинг не нужен). CTA «Спросить
     ассистента» → `navigate('/assistant')`. Если фетч треда упал/недоступен —
     шаг остаётся «без чека» (см. деградацию FR-1.4), ссылка всё равно рабочая
     (ссылка не зависит от успеха фетча).
  4. **[опционально] «Настройте права»** — done, когда `can_manage===true`
     в проекции `GET /api/rights/tenant-state` ИЛИ шаг не показывается вовсе,
     если сигнал недоступен (см. FR-1.4). Обычный пользователь без прав на
     управление ролями не видит этот шаг как «то, что нужно сделать» —
     рендерится только когда есть реальный сигнал что делать (`can_manage`
     true И `roles` пуст — иначе шаг не несёт действия). CTA «Настроить права»
     → `navigate('/rights')`.
- Каждый шаг — это строка/чип: иконка-состояние (галка `KitIcon
  name="check"` для done / нейтральный маркер для not-done) + текст шага +
  Button-CTA (variant="ghost", size="sm") ведущая в соответствующий экран.
  Выполненные шаги остаются видны (не исчезают по одному) — вся полоса
  целиком скрывается только когда ВСЕ обязательные шаги (1–3) done (FR-1.5).
- Не модал, не оверлей, не блокирует остальной контент Обзора — обычный
  `<section>` в потоке документа, встроенные плитки ИА под ним не двигаются
  логически (полоса — дополнительный блок сверху, не замена).

### FR-1.1 — состояния загрузки

Пока сигналы шагов ещё грузятся (`loading===true` для соответствующего
источника), шаг рендерится с компактным `LoadingState` (проп `compact`,
как уже делает `Stat` в этом же файле для счётчиков плиток) ВМЕСТО
галки/нейтрального маркера — no flicker: сначала не показываем ни true ни
false, ждём ответа. CTA-кнопка остаётся кликабельной даже во время загрузки
чека (шаг всегда актуален как ссылка, только визуальный чек ждёт данных).

### FR-1.2 — почему НЕ строим новые API

Все три обязательных сигнала уже дёшево доступны из существующих READ-эндпоинтов,
которые экран либо уже вызывает (`/api/applications`), либо использует тот же
паттерн, что уже эксплуатирует другой экран этого же тенантского приложения
(`resolveAssistantBinding` в `screen-llm-connections.jsx`, `fetchThreads`-контракт
в `assistant.ts`). Задача прямо запрещает строить новый API для этого — рамки
соблюдены без единого нового эндпоинта.

### FR-1.3 — паттерн деградации (обязателен по рамкам задачи)

Каждый фетч — best-effort, по образцу существующего `fetchCount()` в этом же
файле: любая ошибка (сеть/HTTP/парсинг) → шаг просто не получает чек (не
падает в error state, не красный экран). Явно: HTTP-ошибка или сетевой сбой
на любом из четырёх сигналов деградирует ЭТОТ шаг до состояния «шаг без
чека» — сама ссылка/CTA остаётся рабочей (навигация не зависит от статуса
чека), полоса как целое не скрывается ошибочно (потому что критерий скрытия
requires ВСЕ обязательные шаги === true — если сигнал недоступен, шаг не
true, значит полоса не скрывается, что и есть безопасное поведение по
умолчанию: лучше показать лишний раз, чем скрыть ошибочно).

### FR-1.4 — шаг «Настроить права» — опциональность

Шаг 4 рендерится только если его сигнал (`GET /api/rights/tenant-state`)
успешно вернул `can_manage: true` — при 403/сетевой ошибке/`can_manage:false`
шаг СТРУКТУРНО отсутствует из списка (не «шаг без чека», а не рендерится
вовсе), поскольку для обычного сотрудника «настроить права» — не его
задача, показывать её как непройденный шаг было бы честно неверно
(соответствует ADR T-0572 паттерну «can_manage:false ⇒ форма отсутствует в
DOM, не disabled» — тот же принцип переносится сюда). Так как шаг 4
опционален, он НЕ участвует в критерии скрытия полосы (FR-1.5 считает только
шаги 1–3).

### FR-1.5 — скрытие полосы у опытных пользователей

Полоса целиком не рендерится (`return null` для всего блока), когда все ТРИ
обязательных сигнала (шаги 1–3) вернули `true` УСПЕШНО (не «сигнал
недоступен», а именно подтверждённое `true`). Это чистое производное
состояние от уже загруженных данных — БЕЗ localStorage/dismiss-кнопки:
как только тенант реально прошёл путь (есть приложение, ключ, разговор),
полоса перестаёт занимать место при каждом заходе на Обзор. Ручного
«закрыть» не вводим (упрощение против черновика отчёта, который допускал
localStorage-скрытие как альтернативу) — авто-скрытие по факту готовности
самодостаточно и не создаёт риска «случайно закрыл и забыл, где искать»
(FR-6 отчёта, closed-vs-shown, не относится к этому T напрямую, но
тот же принцип «не прятать безвозвратно» соблюдён естественно: если тенант
позже создаст ситуацию, где сигнал снова false — например, единственное
приложение удалено — полоса появится снова, что честно отражает состояние).

## FR-2 (= находка №7) — пустой инбокс с честным CTA

**Файл:** `web/src/screens/screen-inbox.jsx:789-794` (`EmptyState` в ветке
`items.length === 0`).

**Сейчас:** `EmptyState` показывает `title="Задач нет"` +
`description="Новые задачи появятся здесь, как только процессы их создадут."`
БЕЗ `action` — тупик без выхода, независимо от вкладки/фильтра.

**Должно быть:** различать «нет задач вообще на вкладке Все, без фильтра» от
«нет задач по текущему фильтру/вкладке»:
- Вкладка `tab === 'all'` И нет активного фильтра исполнителя (`exec === null`)
  И нет активной сортировки-фильтра, влияющей на набор (`sortSla` не меняет
  СОСТАВ набора, только порядок — не считается фильтром для этой цели) И
  `counts.all === 0` (реальный ноль по тенанту, не по текущей серверной
  выборке с фильтром) → **first-use EmptyState**: тот же честный `description`
  («Задачи появляются, когда запускаются процессы») + новый `action`:
  `<Button variant="secondary" size="sm" onClick={() => navigate('/processes')}>Открыть процессы</Button>`
  (текст кнопки — рамки задачи говорят «Открыть Процессы»; используем
  Sentence-case «Открыть процессы» — консистентно с остальными CTA-лейблами
  проекта, которые не капитализируют второе слово, ср. «Создать приложение»,
  «Мои задачи» в `screen-overview.jsx`).
- Любая другая комбинация (вкладка `mine`/`pool`/`esc`, ЛИБО `tab==='all'` но
  `exec` активен) → EmptyState БЕЗ action, текст уточняется под контекст:
  «Нет задач в этой вкладке» / «Нет задач по этому фильтру» — не через
  выдуманный «сделайте X», раз выхода из фильтра одним кликом на самом
  EmptyState не предусмотрено рамками (кнопка сброса фильтра — за периметром
  этого T, отчёт её не требовал).
- `useNavigate()` уже не импортирован в `screen-inbox.jsx` — добавляется тем
  же паттерном, что и в `ra-overview-forms.jsx` (T-0597 FR-3): вызов легален,
  компонент монтируется внутри Router-дерева.
- Путь `/processes` подтверждён существующим `<Route path="/processes"
  element={<ProcessesScreen />} />` (`shell.jsx:1161`) — не изобретается.

  решение фаундера).

- OOS-5: не меняется `EmptyState`/`Button`/`LoadingState` контракт в
  `components.jsx` — оба FR используют существующие пропы как есть.

## Acceptance criteria

- AC-1: `screen-overview.jsx` рендерит полосу «Первые шаги» с тремя
  обязательными шагами (приложение/LLM-ключ/ассистент) + опциональным
  четвёртым (права), каждый — ссылка в соответствующий раздел.
- AC-2: шаг «Создайте приложение» помечен done, когда
  `GET /api/applications` возвращает `applications.length > 0`
  (переиспользует существующий `apps`-счётчик экрана — не второй фетч).
- AC-3: шаг «Подключите LLM-ключ» использует `GET /api/agents` +
  переиспользованный `resolveAssistantBinding` из
  `screen-llm-connections.jsx` (импорт, не копия логики) — done, когда
  `assistantConnectionId != null`.
- AC-4: шаг «Спросите ассистента» использует `GET /api/assistant/threads` —
  done, когда хотя бы один тред имеет `message_count > 0`.
- AC-5: опциональный шаг «Настройте права» рендерится ТОЛЬКО при успешном
  `can_manage: true` от `/api/rights/tenant-state`; при ошибке/403/false —
  структурно отсутствует (не «без чека», а не в списке).
- AC-6: любой сбой сигнала (сеть/HTTP/парсинг) на шагах 1–3 не рушит экран —
  шаг остаётся видимым без чека, ссылка кликабельна; полоса не скрывается
  ошибочно.
- AC-7: полоса целиком не рендерится, когда шаги 1–3 все подтверждённо true.
- AC-8: во время загрузки сигнала шаг показывает compact `LoadingState`, не
  мигает между «не выполнено»→«выполнено» после ответа.
- AC-9: `screen-inbox.jsx` EmptyState на вкладке «Все» без активного фильтра
  исполнителя при реальном `counts.all === 0` получает `action` —
  кнопку/ссылку, вызывающую `navigate('/processes')`.
- AC-10: EmptyState на вкладках `mine`/`pool`/`esc` или при активном
  фильтре исполнителя НЕ получает вводящий в заблуждение `action` — текст
  явно различает «эта вкладка/фильтр пуста» от «вообще пусто».
- AC-11: путь `/processes` подтверждён существующим Route в `shell.jsx` —
  не изобретён.
- AC-12: ни один из фиксов не вводит новый хардкод-цвет вне `--chs-*`
  токенов (ux-g6).
- AC-13: ни один из фиксов не вводит dev-жаргон в видимый текст (ux-g5).
- AC-14: полный web vitest прогон зелёный, включая расширенные/новые тесты
  `screen-overview.test.jsx` (новый) и `screen-inbox.test.jsx` (расширение).
- AC-15: существующие тесты `screen-inbox.test.jsx` (T-0597, alert→toast)
  продолжают проходить без модификации их утверждений (только добавление
  новых describe-блоков).
