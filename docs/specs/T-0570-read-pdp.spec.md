## 0. Проблема (LIMITATION-018, доказано живьём 2026-07-01/02)

`src/http/records.ts` (`GET /api/records`, `GET /api/records/:id`) читает записи через
`listRecordsPaginated` / `getRecordDetail` — обе функции фильтруют **только**:
1. tenant RLS (`r.tenant_id = $1` + Postgres RLS policy `record_tenant_isolation`);
2. sandbox/draft-tier gate (`sandboxReadPredicate`, T-0558 — прячет черновики от
   непривилегированных, не зависит от гранта на конкретную запись).

**Ни одна из них не резолвит гранты на чтение конкретной записи.** Field-уровень частично
закрыт (T-0081 `roleFieldVisibility` / `applyFieldVisibilityRedaction`, вызывается через
опциональный `resolveFieldVisibility`) — но это only-narrows поверх поля, не строку; и
поле-политика сама пуста, пока никто её не заполнил. Record-уровень (какая СТРОКА видна)
не гейтится вообще: внутри тенанта запись видят все аутентифицированные акторы, у которых
есть доступ к тенанту. Действия (`card-action.ts` → `resolveFor`, гейт D2) уже проходят
через PDP и fail-closed — только чтение списков/деталей — нет.

Это блокирует К1 «менеджер видит только своих клиентов» (см. карта примитивов A/D3) и
делает пустым фундамент столпов 4 (агент=сотрудник, чтение агента должно быть УЖЕ
ограничено его грантами) и 6 (ассистент-в-контуре-прав, отвечал бы «всё всем»).

## 1. Summary

Провести чтение записей (`GET /api/records`, `GET /api/records/:id`) через тот же
grant-resolver PDP, что уже гейтит действия (`card-action.ts` → `resolveFor` →
`grantResolver`/`resolveFor` в `src/core/grant-resolver.ts`), при этом:

- КАЖДОМУ тенанту (существующему и новому) сидируется грант **"read всё внутри
  тенанта"** — единственная точка входа default-open, не埋 in-code исключение;
- поведение существующих тенантов НЕ меняется в день выката (все записи остаются
  видны всем, кто видел их раньше) — обеспечивается backfill-миграцией default-грантов
  ДО того, как чтение начинает их требовать;
- сужение видимости (запись видна только автору/владельцу/своему отделу и т.п.) —
  это настройка (создание более узкого гранта поверх/вместо default-гранта), а не
  код-путь платформы; сам механизм ОБЯЗАН поддерживать запись- и поле-уровневое сужение,
  настройка конкретно под кейс «менеджер видит своих» — за периметром этой задачи
  (референс на будущую задачу конфигурации, если заведена);
- никакой new authority subsystem (FR-7 T-0021) — только READ-путь начинает СПРАШИВАТЬ
  тот же PDP, который уже отвечает на действия.

## 2. Проверенное состояние кода (разведка 2026-07-02, живой worktree T-0570)

- `src/http/records.ts` `listRecordsPaginated` (SQL, строки ~929–1012) и
  `getRecordDetail` (~1020–1045): условия WHERE — `r.tenant_id = $1` +
  `sandboxReadPredicate(...)`. Нет JOIN/условия на `choros."grant"`.
- `applyFieldVisibilityRedaction` / `resolveFieldVisibility` (T-0419/T-0421) уже вызываются
  на LIST и DETAIL, но: (а) OPTIONAL-деп — honest-degrade в no-op, если composition root
  его не подключил; (б) даже подключённый, сегодня работает только НАД полями через
  `roleFieldVisibility` (most-restrictive intersection полей), не решает «показать ли
  строку вообще».
- `src/core/grant-resolver.ts` `resolveFor` (строка ~567) — существующий чокпоинт для
  handle→fields, уже используется на записи ЧЕРЕЗ `card-action.ts` (approve/transition/
  update/create/invoke путь, D2, живьём доказан 403 fail-closed 2026-07-01/02). Тот же
  проекционный слой (`projectFields`/`visibleFields`) — единственная функция и для
  человека, и для агента (AC-5 T-0021).
- `refToScope` (`grant-resolver.ts:197`) мапит `ResourceRef{kind:"record"}` в
  `ScopeElement{kind:"node", hierarchy:"resource", nodeLevel:"record", nodeId:recordId}`.
  Containment грант⊒запись проверяется через инжектируемый `AncestryOracle.
  isDescendantOrSelf("resource", recordId, grant.scope.nodeId)`.
- **Ключевая находка**: ancestry-oracle, реально подключённый в проде для
  `hierarchy:"resource"`-скоупов (`pdp-explain.ts:484` `loadTenantOrgAncestry`,
  `card-action.ts` через `deps.resolverDeps.ancestry`), сегодня строится ТОЛЬКО из
  ORG-дерева (`src/db/org-ancestry.ts`, департаменты). Для `hierarchy:"resource"`
  (application→registry→record) НЕТ живого resource-ancestry-оракула — `_hierarchy`
  параметр молча игнорируется существующей реализацией `makeOrgAncestryOracle`. Грант
  со scope `{kind:"node", hierarchy:"resource", nodeLevel:"application", nodeId:X}`
  сегодня НЕ покрыл бы запись `nodeLevel:"record"` этого приложения — оракул не умеет
  подниматься record→registry→application. **Это архитектурный разрыв, который READ-PDP
  обязан закрыть (зона architect), но должен быть явно назван здесь, т.к. он определяет,
  реализуем ли "один грант = вся запись тенанта" буквально через существующий
  `nodeLevel`-скоуп, или требует нового scope-примитива (например `nodeLevel:"tenant"`
  либо scope `{kind:"tags"}`/`{kind:"set", members:[…]}` тенант-ширины, либо новый
  resource-ancestry-оракул).** Спека фиксирует ЧТО (default-open через грант, тенант-
  широкий охват, запись-и-поле сужаемость), не КАК резолвится containment — это выбор
  architect в пределах T-0018 латтиса, не второй авторитетный путь (FR-7).
- Существующий сид `migrations/088_configurator_authoring_draft_grant_seed.sql` —
  анти-паттерн для этой задачи (хардкод `DEV_TENANT_ID` = один конкретный tenant).
  Default-read-грант ДОЛЖЕН сидироваться (а) для КАЖДОГО существующего тенанта через
  backfill-миграцию, читающую `choros.tenant` (без хардкода конкретного UUID), и
  (б) для каждого НОВОГО тенанта из `registerTenant` (`src/core/register.ts`), рядом с
  уже существующим tenant-zero seeding блоком (T-0373, PD-7 — configurator role/grants,
  строка ~308+).
- `field-visibility.ts` (T-0081) — готовый, чистый, уже сужает поля через intersection
  covering-грантов; повторно используется, НЕ переизобретается (FR-7-подобная дисциплина).

## 3. Функциональные требования

- **FR-1 — READ-путь спрашивает PDP.** `GET /api/records` и `GET /api/records/:id`
  резолвят видимость КАЖДОЙ строки через тот же grant-resolver PDP (`resolveFor` /
  `grantResolver`, `src/core/grant-resolver.ts`), а не только через tenant-RLS +
  sandbox-gate. Запись, для которой у актора нет покрывающего READ-гранта, НЕ появляется
  в ответе (list — строка отсутствует; detail — 404, симметрично существующему
  cross-tenant/not-found контракту, без утечки факта существования записи).
- **FR-2 — Default-open грант сидируется в КАЖДЫЙ тенант.** Существует ровно один класс
  сидированного READ-гранта на уровне "все записи тенанта" (роль/scope — решает
  architect в пределах T-0018 латтиса), который:
  - сидируется в КАЖДЫЙ существующий тенант backfill-миграцией (без хардкода
    конкретного tenant UUID — обход по `choros.tenant`, зеркалит анти-паттерн-урок
    из migrations/088, которого здесь быть не должно);
  - сидируется в КАЖДЫЙ новый тенант из `registerTenant` (рядом с существующим
    tenant-zero блоком T-0373).
- **FR-3 — Сужение = настройка гранта, не правка платформы.** Сузить видимость записей
  (record-level: «видит только свои»; field-level: «видит запись, но не все поля») —
  это создание/редактирование грантов через существующий грант-механизм
  (`src/http/grants.ts`, `src/db/grants-dao.ts`), НЕ новый код-путь, НЕ новая ветка в
  `records.ts`. Механизм ОБЯЗАН поддерживать оба уровня сужения технически; настройка
  конкретно под сценарий «менеджер видит только своих клиентов» (создание узких грантов
  под роль/сотрудника) остаётся отдельной задачей конфигурации, ЕСЛИ заведена отдельно —
  эта спека НЕ утверждает такую задачу, только требует, чтобы READ-PDP делал сужение
  технически достижимым.
- **FR-4 — Field-уровень переиспользуется, не дублируется.** Field-visibility redaction
  (T-0081/T-0419/T-0421, `field-visibility.ts` + `applyFieldVisibilityRedaction`) остаётся
  ЕДИНСТВЕННЫМ полe-проекционным слоем; READ-PDP record-уровня НЕ вводит второй способ
  прятать поля. `resolveFieldVisibility` перестаёт быть honest-degrade-в-no-op по
  умолчанию для тенантов, где default-грант сидирован (т.к. сидированный грант — это
  covering-грант, из которого выводится visible field set).
- **FR-5 — Fail-closed при отсутствии гранта.** Актор без ЛЮБОГО покрывающего READ-гранта
  на запись (ни default-open, ни более узкого) НЕ видит запись — ни в списке, ни в
  detail-эндпоинте. Отсутствие гранта — это не ошибка 500/403 на списочном эндпоинте
  (список просто короче), а на detail — 404 (тот же контракт, что cross-tenant/not-found
  сегодня, symmetric-с-D2-семантикой `no_grant`).
- **FR-6 — Человек и агент — один путь.** READ-путь записи, будь то UI-список/деталь
  (человек) или чтение агентом/ассистентом (столпы 4/6), резолвится ОДНИМ и тем же PDP-
  вызовом с ОДНИМ и тем же вычислением visible-set (AC-5-подобная дисциплина T-0021) —
  агент не получает отдельный, более щедрый или более узкий, путь чтения записей.
- **FR-7 — Один резолвер, не вторая система прав.** READ-путь не вводит параллельный
  ACL/whitelist/store для record-видимости — решение выводится ТОЛЬКО из строк
  `choros."grant"` (тот же T-0018-латтис, тот же `resolveFor`), зеркалит FR-7 T-0021.

## 4. Нефункциональные требования

- **NF-1 — Без деградации в N+1.** Чтение СПИСКА записей не должно порождать один
  PDP/DB-запрос грантов НА КАЖДУЮ строку результата. Резолюция грантов актора выполняется
  один раз на запрос (актор+тенант+операция), контэйнмент по каждой строке — либо через
  SQL-предикат (join/exists на `choros."grant"`, аналогично `sandboxReadPredicate`-
  паттерну — доп. `AND`, не меняющий индексацию параметров), либо через уже загруженный
  в память per-request grant-set + чистую функцию per-row (не по одному сетевому вызову
  на строку). Конкретный механизм — зона architect; NF фиксирует бюджет (без деградации
  до N+1), не реализацию.
- **NF-2 — Обратная совместимость на день выката.** До/во время выката ни один
  существующий тенант не теряет видимость ни одной записи, которая была видна раньше
  (backfill default-гранта — предусловие смены поведения чтения, не следствие).
- **NF-3 — Tenant isolation не ослабляется.** RLS tenant-гейт остаётся первым и
  обязательным фильтром (как сегодня); PDP-гейт — ДОПОЛНИТЕЛЬНЫЙ поверх, никогда не
  единственный.
- **NF-4 — Анти-кейс (D-064).** Ни в одной строке `src/`, добавленной/изменённой этой
  задачей, не появляется имя конкретной роли/слага живого кейса (например
  `role-approver`, `soglasovanie`, `tel-`, «Согласование» как строковая константа,
  персоны `e-larina`/`e-orlov`/`e-configurator`). Default-грант — платформенный
  примитив, не кейсовый факт.
- **NF-5 — Пропорциональность.** READ-PDP переиспользует существующий
  `resolveFor`/`grant-resolver.ts`/`field-visibility.ts`; не переизобретает латтис-
  математику T-0018 (зеркалит NF-5 T-0021).

## 5. Out of scope (явно НЕ в этой задаче)

- Настройка конкретного сужения «менеджер видит только своих клиентов» (создание узких
  грантов под роль CRM-менеджера) — это применение механизма к кейсу К1, не сам механизм;
  отдельная задача, если заведена.
- Resource-hierarchy ancestry-оракул (application→registry→record containment) как
  универсальный примитив, если architect решит, что он нужен сверх текущего
  `nodeLevel`-скоупа — конкретная реализация оракула вне спеки (зона design/architect,
  см. находку в §2).
- UI/экран управления грантами («Доступ» показывает «Нет ролей» — известный баг,
  карта примитивов D4/D5) — не эта задача.
- Дальнейшее расширение маскинг-грамматики (T-0033/E4.3) сверх существующего
  facet-narrowing и `roleFieldVisibility`.
- Изменение семантики действий (D2, `card-action.ts` PDP уже работает, не трогается).
- Cross-app / cross-solution relation-видимость (H1 карты примитивов) — отдельный
  примитив.
- Производительность сверх NF-1 бюджета (нет требования к конкретной latency-цифре —
  только «не N+1»).

## 6. LIVE_PROOF-путь (D-064)

Обязательный путь, который на живом стенде докажет задачу ГЛАЗАМИ (не CI, не unit-test):

1. На живом тенанте (любом, не привязанном к конкретному бизнес-кейсу — например
   существующий self-reg тенант, НЕ демо-ТЭЛ) есть ≥2 записи одного приложения и ≥2
   пользователя (User A, User B), у обоих есть роль с default-open READ-грантом
   (сидирован автоматически).
2. **Шаг "было/осталось" (backfill, NF-2):** ДО настройки сужения оба пользователя
   открывают список записей приложения → оба видят ОБЕ записи (как было до этой задачи).
3. **Шаг "сужение — это настройка":** владелец/админ создаёт (через существующий
   грант-механизм, `POST /api/grants` или эквивалент UI) более узкий READ-грант для
   User B, покрывающий ТОЛЬКО одну из двух записей (например по создателю/владельцу
   записи, любой реализуемый на T-0018-латтисе способ сузить scope) — БЕЗ правки кода,
   БЕЗ редеплоя.
4. **Проверка на глаз:** User B перезагружает список записей → видит ТОЛЬКО ту запись,
   на которую у него теперь есть грант; вторая запись физически отсутствует в ответе
   (не показана как «нет доступа» — просто отсутствует, list короче). User B открывает
   detail-URL второй (недоступной) записи напрямую по id → получает 404, не 200 и не 403
   с утечкой данных.
5. User A (у которого грант НЕ сужали) по-прежнему видит ОБЕ записи — сужение одного
   актора не задело другого.
6. (Если field-сужение реализовано в рамках этой же задачи как часть механизма) — тот же
   User B с грантом, дающим read самой записи, но facet, узким по полям, видит запись
   в списке/detail, но некоторые JSONB-ключи `data` физически отсутствуют в ответе
   (не `null` — отсутствуют), проверяется через сырой JSON-ответ API (Network-вкладка
   или curl с токеном), не только визуально в UI.

Обход (просмотр API напрямую/curl вместо UI, если UI для настройки грантов ещё не готов)
— допустим для шага 3 (грант можно завести через уже существующий `POST /api/grants`);
шаги 2/4/5/6 — обязаны быть прожиты через тот же путь, каким реально читает продукт
(UI-список/detail, либо тот же HTTP API, каким пользуется UI) — не через прямой SQL/DAO
в обход роутов.

## 7. Критерии приёмки

| id | text | verifiable_as |
|---|---|---|
| AC-1 | `GET /api/records` не возвращает ни одной строки, для которой у актора нет ни одного покрывающего READ-гранта (default-open или более узкого) на эту запись — при пустом grant-множестве актора (гипотетически, если default-грант отсутствует) список пуст, а не полон. | fitness |
| AC-2 | `GET /api/records/:id` возвращает 404 (не 200, не 403 с утечкой данных) для записи, на которую у актора нет покрывающего READ-гранта — неотличимо по коду/форме ответа от «запись не существует» / «чужой тенант». | fitness |
| AC-3 | **Backfill не ломает существующих:** для тенанта, существовавшего ДО применения миграции default-грантов, после применения миграции КАЖДЫЙ актор, ранее видевший запись через старый (только-RLS) путь, продолжает видеть её через новый (PDP) путь — сравнение до/после на фиксированном наборе записей даёт одинаковый видимый набор. | fitness |
| AC-4 | **Tenant-zero:** `registerTenant` для НОВОГО тенанта сидирует default-open READ-грант атомарно в той же транзакции, что и остальной tenant-zero seed (T-0373) — сразу после регистрации владелец видит записи своего (изначально пустого) тенанта без ручной настройки. | fitness |
| AC-5 | **Сужение достижимо без правки платформы (record-level):** создание более узкого READ-гранта (через существующий грант-эндпоинт/DAO, без изменения кода `records.ts`) для одного актора приводит к тому, что этот актор перестаёт видеть записи вне нового узкого scope, а ДРУГОЙ актор (с default-грантом нетронутым) продолжает видеть их все. | fitness |
