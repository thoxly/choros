## 1. Summary

Choros получает первоклассную модель **файлов-вложений к записям** реестров поверх **S3-совместимого объектного хранилища**: бинарный контент живёт в S3, метаданные файла (имя, тип, размер, хэш, версия, привязка к записи, ретенция) — в tenant-таблице ядра. Право прочитать/скачать/заменить/удалить файл **выводится из права на запись-владельца** через существующий PDP (T-0021) — отдельного ACL у файла нет. При циклах доработки процесса (референс ТЭЛ: «внести правки» → сброс виз → маршрут заново) файл версионируется: старые версии сохраняются, актуальной считается последняя. Завершённые записи уходят «в архив» — для их файлов действует политика ретенции. Tenant-изоляция распространяется и на S3: ключ объекта префиксован `tenant_id`, доступ к bucket идёт только через серверный слой ядра (никаких прямых клиентских URL мимо PDP).

Это **дизайн-задача**: выход фазы — спека требований, которые обязан покрыть будущий ADR (модель данных, производность прав, версии, ретенция, S3-изоляция, граница MVP). Acceptance-критерии сформулированы как **проверяемые свойства будущего ADR/реализации** (fitness-линт ADR-текста или test после имплементации), не как готовое решение.

## 2. Функциональные требования к дизайну (ADR обязан покрыть)

### FR-1 — Модель файл↔запись (вложение к записи)
ADR обязан определить сущность файла (`file` / `attachment`) как **вложение к записи реестра** (`record`, T-0014). Привязка:
- Файл принадлежит ровно одному tenant и ссылается на запись-владельца в рамках того же tenant (`tenant_id`-leading, composite FK на `record(tenant_id, id)` либо логическая ссылка по дисциплине T-0017, если FK к ещё-не-существующей таблице).
- Запись может иметь 0…N файлов (проект договора, протокол разногласий, скан оригинала — референс ТЭЛ §1).
- ADR обязан зафиксировать, является ли «вложение к процессу» отдельной поверхностью или сводится к вложению к записи-карточке процесса (референс ТЭЛ: файлы живут на карточке договора, не на инстансе движка). Рекомендация спеки: одна точка истины — запись; процесс несёт handle (T-0015), не файл.

### FR-2 — Бинарь в S3, метаданные в ядре
ADR обязан развести: **контент** файла → S3-совместимый объект; **метаданные** → tenant-таблица ядра (минимум: `tenant_id`, `id`, ссылка на запись-владельца, `object_key`, исходное имя, MIME-тип, размер, контент-хэш, версия, кто/когда загрузил, статус ретенции). Ядро никогда не хранит бинарь в Postgres.

### FR-3 — Производность прав (НЕ второй механизм авторизации)
Право на файл **выводится из права на запись-владельца** через существующий PDP (T-0021):
- Чтобы прочитать/скачать файл — субъект обязан иметь grant `read` на запись-владельца (по grant-алгебре T-0018, action-time, fail-closed).
- Чтобы заменить/добавить/удалить файл — соответствующее право (`update`/`create`/`delete`) на запись-владельца.
- ADR **не вводит** отдельную таблицу `file_acl` / `attachment_rights` / поле видимости файла — это нарушило бы единый источник истины (T-0018 §2, T-0021 §3 «no second authority subsystem», FF-R6). Решение «кто видит файл» = решение «кто видит запись», вычисленное тем же резолвером.
- ADR обязан зафиксировать, как это выражается в существующей grant-модели: либо файл-операция переводится в операцию над записью-владельцем перед PDP, либо вводится производный resource-маппинг файла на scope записи. Второй permission-путь запрещён.

### FR-4 — Доступ к S3 только через серверный слой за PDP
Никакого клиентского доступа к bucket мимо PDP. ADR обязан определить путь выдачи контента: либо стриминг через ядро после allow-решения PDP, либо **краткоживущий presigned-URL, выпускаемый ТОЛЬКО после allow-решения PDP** (TOCTOU-граница: presign выдаётся в момент проверки права, срок жизни короткий). Прямые постоянные публичные URL объектов запрещены. Bucket-политика — deny-by-default, доступ только серверной ролью ядра.

### FR-5 — Версии при циклах доработки
ADR обязан определить версионирование файла, согласованное с циклами доработки процесса (референс ТЭЛ §1: «внести правки» → задача менеджеру → сброс флагов → маршрут заново):
- Замена контента файла создаёт **новую версию**, не затирает предыдущую; история версий сохраняется и доступна (кто/когда/хэш каждой версии).
- Понятие «актуальная версия» определено однозначно (последняя по порядку версий).
- Версии одного файла лежат под разными S3-ключами (контент иммутабелен per-версия; перезаписи существующего объекта нет).
- ADR обязан зафиксировать связь версии с событием процесса/цикла доработки (трассируемость «эта версия — после такого-то возврата на доработку»), но НЕ обязан дублировать механизм версионирования: если документ-источник версионируется отдельной подсистемой, ADR ссылается на неё. Для вложений-файлов версия — атрибут файла.

### FR-6 — Ретенция в архиве
ADR обязан определить политику ретенции для файлов записей, ушедших «в архив» (терминальные статусы референс-процесса: «В архиве», «Отказано», «Отменён»):
- Статус ретенции файла (активный / архивный / помеченный к удалению) и кто/что его меняет.
- Ретенция выражена декларативно (срок/класс), а не хардкодом; deny-by-default к удалению до истечения (нельзя случайно стереть архивный артефакт).
- Удаление контента (физическое стирание объекта в S3) и удаление метаданных-строки разведены: ADR фиксирует, что аудит-след о существовании файла переживает удаление контента (T-0016 append-only).
- ADR обязан зафиксировать границу: реализуем ли авто-применение ретенции (фоновый sweeper) сейчас или это Stage-2; схема статуса ретенции — day-1.

### FR-7 — Tenant-изоляция в S3-ключах
ADR обязан определить S3-ключевую схему так, что объекты разных тенантов структурно неслияемы:
- `object_key` префиксован `tenant_id` (например `<tenant_id>/<...>`); cross-tenant ключ структурно невозможен.
- Метаданные-таблица — tenant-таблица с полным контрактом T-0013: `tenant_id`-leading PK, ENABLE+FORCE RLS, default-DENY политика на `current_setting('choros.tenant_id', true)`, DML только `choros_app`, занесена в `ci/checks/known_tenant_tables.txt`.
- Выпуск presigned-URL / стриминг fail-closed по tenant-контексту в async/фоновых исполнителях (tenancy §9 п.7): нет tenant-контекста → операция падает, не выполняется глобально.
- ADR обязан зафиксировать модель развёртывания хранилища для silo (gap-map: silo — дефолт): один bucket с tenant-префиксами vs bucket-на-тенант — выбор обоснован против tenancy-инвариантов (изоляция не должна зависеть только от дисциплины кода).

### FR-8 — Целостность и аудит
ADR обязан определить:
- Контент-хэш файла при загрузке (целостность; обнаружение повреждения/подмены); согласование с hash-oracle (T-0118), если применимо.
- Аудит-события (T-0016) на загрузку/замену/скачивание/удаление файла: что записывается (актор, запись-владелец, версия, хэш), tenant-scoped.
- Лимиты загрузки (макс. размер, допустимые MIME-типы) — declared, не unbounded; ADR фиксирует, где порог и как он tenant-конфигурируем (или фиксирован day-1).

### FR-9 — Снапшот для document-on-demand (инвариант T-0124)
ADR обязан гарантировать, что файловое хранилище способно принять **снапшот сгенерированного-на-лету документа** (gap-map §4б инвариант 1): document-on-demand (T-0124) фиксирует живой рендер как иммутабельный файл-версию в этом хранилище, на который указывает QR/внешняя ссылка. Спека T-0119 фиксирует только **наличие приёмной поверхности** (создать файл из байтов рендера, пометить иммутабельным/снапшот), не сам рендер (T-0124).

## 3. Нефункциональные требования

### NF-1 — Единый механизм прав (несущий)
Никакого второго механизма авторизации файлов. Решение видимости/доступа файла = производная решения по записи-владельцу через PDP T-0021. Это аудит-инвариант (один источник истины), не оптимизация.

### NF-2 — Tenant-изоляция (инвариант tenancy, non-negotiable)
S3-ключи tenant-префиксованы; метаданные-таблица под FORCE RLS; cross-tenant доступ к контенту структурно невозможен (не на дисциплине кода). Один cross-tenant leak файла = смерть GTM на РФ-рынке (tenancy §5).

### NF-3 — Иммутабельность контента per-версия
S3-объект версии не перезаписывается; новая версия = новый ключ. Это обеспечивает воспроизводимость (вчерашний артефакт восстановим) и целостность аудит-следа.

### NF-4 — Контент мимо PDP не утекает
Ни один путь не отдаёт байты файла без предшествующего allow-решения PDP по записи-владельцу (включая presigned-URL: presign только после allow, короткий TTL). Прямых публичных постоянных URL нет.

### NF-5 — Аудит переживает удаление контента
Удаление бинаря из S3 (по ретенции) не стирает аудит-след о факте существования/жизненном цикле файла (T-0016 append-only).

### NF-6 — Egress-согласование для агентов
Если контент файла (или извлечённый текст) уходит в LLM-агента, это попадает под egress-политику по DataClass (T-0041) — ADR обязан отметить эту границу (классификация контента/вложения), даже если runtime-гейт egress = Stage-2.

## 4. Out of Scope (явные не-цели T-0119)

1. **Реализация (DDL/код/S3-клиент):** T-0119 — дизайн-задача; сам ADR + реализация (миграция метаданных-таблицы, S3-адаптер, presign-сервис) — последующие фазы/задачи. Следующая миграция — после `040_mcp_tool.sql` (свободный номер ≥ 041, по run-seam дисциплине).
2. **Document-on-demand рендер (T-0124):** генерация документа из живых справочников — T-0124; здесь только приёмная поверхность снапшота (FR-9).
3. **Внешняя поверхность / headless скачивание (T-0122/T-0126):** механизм внешнего принципала и токенизированного доступа — те задачи; T-0119 лишь гарантирует, что путь прав файла — производный грант, не второй механизм.
4. **Docgen из шаблона в архив:** генерация документа по шаблону — отдельный модуль (gap-map §2, 🔵); поглощается document-on-demand.
5. **ЭДО / подписание / штамп ЭП:** интеграция с электронной подписью оригинала — нишевой модуль.
6. **Полнотекстовый поиск/превью/антивирус-скан контента:** не MVP; ADR может отметить как точку расширения, не проектировать.
7. **Версионирование документа-источника как отдельной подсистемы:** если источник версионируется механизмом T-0082 (единица версионирования) — T-0119 ссылается, не дублирует (gap-map §4б).
8. **UI вложений:** компоненты загрузки/просмотра в слайсе — задачи зоны 7 (T-0137/T-0138), не здесь.
9. **Pooled-режим S3:** дефолт — silo (tenancy §5); ADR закладывает tenant-префикс так, чтобы pooled не требовал ретрофита, но не достраивает pooled.

## 5. Acceptance Criteria

Критерии — **проверяемые свойства будущего ADR** (fitness-линт текста ADR на присутствие решения / трассируемость) либо **test после реализации**. Для дизайн-задачи `verifiable_as=fitness` означает машинно-проверяемое требование к артефакту ADR (раздел/решение присутствует и не противоречит инвариантам); `test` — проверяемо кодом после имплементации; `manual` — ревью-гейт.

## 6. Снятые неоднозначности (резолюции без эскалации)

Развилки, **уже закрытые фаундером** в gap-map — не поднимаются заново:
- **Хранилище = S3-совместимое** (gap-map §3а) — данность.
- **Права файла = производная прав записи** (gap-map §2) — данность; способ выражения в grant-модели — зона DESIGN (FR-3).
- **Версии при циклах доработки + ретенция в архиве** (gap-map §2) — обязательные требования (FR-5/FR-6).

Резолюции по существующей модели (не эскалация):
- **Вложение к записи, не к инстансу процесса:** референс ТЭЛ показывает файлы на карточке договора (записи); процесс несёт handle (T-0015). Принято как рекомендация спеки; финальное оформление — DESIGN (FR-1).
- **Один bucket + tenant-префикс vs bucket-на-тенант:** не блокер объёма — обе опции совместимы с silo-дефолтом и tenant-префиксной изоляцией; выбор — DESIGN (FR-7), tenancy-инварианты обязательны при любом.
- **Presign vs стриминг:** обе опции допустимы при условии «только после allow PDP» (FR-4/NF-4); выбор — DESIGN.

**Blocking questions:** нет. Решения фаундера по S3, производности прав, версиям и ретенции закрывают объём; остальные развилки — внутри зоны DESIGN и не меняют продуктовый объём. Статус спеки = `ready`.
