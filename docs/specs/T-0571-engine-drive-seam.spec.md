# T-0571 · Шов approve→Flowable (BUG-014): продуктовое действие реально завершает движковый user-task

**Status:** ready (no blocking questions)
**Phase:** SPEC
**Date:** 2026-07-02
**Task:** T-0571 [W1/шов] BUG-014 — «Действие в инбоксе РЕАЛЬНО завершает Flowable user-task (редизайн engine-drive, преемник abandoned T-0442)»
**Предшественники:** T-0440 (done, T-0443/T-0456/T-0458/T-0459 engine-drive построен), T-0442 (redesign, abandoned), T-0522 (durable idempotent reconcile — landed, но живьём НЕ закрывает BUG-014)
**ADR:** `docs/adr/ADR-T0432-engine-backed-inbox.md` — **Option A признана и построена** («inbox = projection живого Flowable», не своя ветвящаяся машина). Этот тask не пересматривает A/B; закрывает разрыв C↔L внутри уже выбранного направления A.
**Источник наблюдений:** живая приёмка 2026-07-01/02 «Закупки» (глубокий прогон), карта примитивов `demiurge/docs/choros-primitives-map-2026-07-02.md` §C3, §4 п.3.

## 1. Проблема (L-факт, не гипотеза)

На живом стенде (100.121.76.86:3000) в глубоком прогоне приёмки «Закупки» (generic-процесс, НЕ ТЭЛ): пользователь нажимает «Согласовать» в инбоксе → продукт отвечает **200-ok** → user-task в Flowable **не завершается** → процесс стоит на месте. Весь кейс приёмки был завершён **обходом через Flowable admin-REST** — что само по себе является P0-находкой по D-064 (обход = приёмка не считается пройденной, инструмент не может расписаться за свой обман).

Код (C-слой) при этом выглядит построенным: цепочка `POST /api/inbox/:id/action` → `reconcileInstanceEngineDrive` → `engine.completeUserTask` присутствует в `src/http/inbox.ts` и `src/http/process-projection.ts`, реализована как «честный», идемпотентный, error-explicit reconcile (T-0522, вслед за ADR-T0432 §3.1 hardening). Налицо противоречие C↔L: код есть, живьём для generic-процесса не работает.

## 2. Диагностическая разведка (наблюдения, не решение)

Ниже — что фактически найдено в коде worktree на 2026-07-02. Это фиксация ПОВЕДЕНИЯ системы для спеки, не проектирование фикса (аналитик не проектирует решение).

### 2.1 Основная находка: хардкод `taskDefKey` в фолде базовой задачи — процесс-агностичный код содержит ТЭЛ-специфичный литерал

`src/http/process-projection.ts`, функция `listInstanceInboxTasks` (строки ~840–905), при фолде БАЗОВОЙ (`process.started`) задачи **любого** процесса безусловно проставляет:

```
taskDefKey: "task-approve"
```

(строка 865, без чтения из BPMN/движка/`процесса`, без привязки к `procKey`). Комментарий над блоком (строки ~209–220) прямо называет источник: *«the canonical linear ТЭЛ U4 approval task (BPMN task-approve, candidateGroups="role-approver")»* — то есть блок дефолтов писан ПОД ТЭЛ и не параметризован по процессу.

`reconcileInstanceEngineDrive` (там же, строки ~1157–1219) в post-approve режиме (`completeEngineTask: true`) получает этот `taskDefKey` как `approvedTaskDefKey` (проброшен из `src/http/inbox.ts:1660` — `const approvedTaskDefKey: string = task.taskDefKey;`) и ищет среди активных задач движка совпадение:

```
tasksResult.tasks.find(t => t.taskDefinitionKey === args.approvedTaskDefKey)
```

**Наблюдаемый эффект для generic-процесса:** если первый user-task BPMN-модели процесса «Закупки» (или любого не-ТЭЛ процесса) имеет `taskDefinitionKey`, отличный от буквальной строки `"task-approve"` (что типично — имя узла в модельере задаёт автор процесса), поиск НИКОГДА не находит совпадение. Цикл поллинга (строки 1193–1209) не считает это ошибкой: раз `tasksResult.tasks.length > 0` (задача в движке реально есть, просто с другим ключом), условие `tasksResult.tasks.length === 0` (выход по «нет задач вовсе») не срабатывает — цикл крутится до `pollTimeoutMs` (10 000 мс по умолчанию), затем молча выходит с `engineTaskId === null`. `completeUserTask` **не вызывается ни разу**. Функция проваливается в шаг 2 (`isInstanceEnded`) и шаг 3 (surface next tasks), которые читают ТЕКУЩЕЕ (незавершённое) состояние движка и возвращают `{ ok: true, ended: false, emitted: 0, completed: false }` — **без единого исключения, без кода ошибки**. Ответ approve-хендлера (`src/http/inbox.ts:1688–1694`) в любом случае 200 (реконсайл запущен как `void (async () => {...})()`, строка 1662, результат не влияет на HTTP-ответ) — это и есть наблюдаемый BUG-014: 200-ok при нетронутом движковом токене.

**Важно:** это диагностика механизма, воспроизводимого КОДОМ безусловно для любого процесса, чей первый узел назван иначе, чем `"task-approve"` — она объясняет наблюдаемое поведение на «Закупках», но задача не требует, чтобы фикс был именно «переименовать литерал»: спека фиксирует целевое ПОВЕДЕНИЕ (§4), путь достижения — за BUILD.

### 2.2 Второй канал деградации: `writeDepsFlowable` (движковый клиент) опционален end-to-end

`src/http/inbox.ts:1654` — весь post-approve engine-drive блок обёрнут в `if (writeDepsFlowable)`. Этот клиент собирается в `src/server.ts:481–494` **только если** одновременно есть `grantsPool` (БД) И `process.env.FLOWABLE_REST_APP_ADMIN_PASSWORD`. Комментарий на строке 1637 прямо называет это «honest-degrade»: отсутствие клиента = approve работает по старому чисто-аудитному пути БЕЗ движка, без ошибки, без индикации пользователю. Это самостоятельный (второй) путь к тому же наблюдаемому симптому «200-ok без эффекта в движке» и должен быть учтён в целевом поведении: если движок настроен и доступен, деградация недопустима; если он в принципе не сконфигурирован — это отдельное явное состояние, не тихая деградация (см. AC-3).

### 2.3 Reconcile-on-read (T-0522) — самоисцеляющая сеть, но не работает, если сам матчинг обречён

`GET /api/inbox` (строки ~1013–1032) уже гоняет `reconcileInboxEngineDriveOnRead` для «зависших» инстансов (approved, но не ended, нет pending next_task) — задумано как страховка от потери гонки в fire-and-forget post-approve пути. Но при §2.1 (`taskDefKey` не матчится в принципе, не единожды из-за гонки) повторный прогон реконсайла с тем же обречённым `approvedTaskDefKey` **не самоисцеляет** — каждый повтор так же не находит совпадение. Наблюдение: сеть T-0522 закрывает класс «потеряна гонка/временная недоступность движка», но НЕ класс «структурное несовпадение ключа задачи», который и наблюдался на «Закупках».

### 2.4 Ошибка не глотается ТОЛЬКО частично

`reconcileInstanceEngineDrive` действительно не глотает ошибки ДВИЖКА (недоступность, HTTP-ошибка на `completeUserTask`/`getActiveUserTasks`/`isInstanceEnded` — возвращает `{ok:false, code, stage}`, залогировано в `inbox.ts:1679–1683` как `console.warn`). Но случай §2.1 (задача есть, просто не найдена по ключу) **не классифицируется как ошибка вообще** — это ok:true с `completed:false`, неотличимое от «завершать было нечего, всё уже в порядке». Наблюдение: сегодняшняя типизация `EngineDriveResult` не различает «не было что завершать (легитимно)» от «должны были завершить, но не нашли задачу (структурный сбой)» — оба случая складываются в один и тот же тихий путь.

## 3. Смежные баги той же приёмки (НЕ в этом скоупе)

Границы шва, отражены как `out_of_scope` — берёт **T-0575**:
- **BUG-015** — проекция хардкодит `role-approver` (`APPROVER_ROLE`, `process-projection.ts:216`) вместо чтения `candidateGroups` из движка/BPMN.
- **BUG-016** — `computed`-поля (rollup) не попадают в переменные процесса.
- **BUG-017** — `step-applier.ts` (`SOGLASOVANIE_SLUG = "soglasovanie"`, строка 78) требует, чтобы целевой набор результата шага назывался буквально `soglasovanie` — для generic-процесса без набора с этим слагом запись результата падает 500 без внятного лога.

Эти баги не блокируют T-0571 функционально (BUG-014 воспроизводится и без них — сам факт незавершения движковой задачи), но живут в тех же файлах/на том же шве и НЕ входят в этот тask.

## 4. Целевое поведение (что должно стать истиной на живом стенде)

### 4.1 Функциональное

**FR-1.** Когда пользователь нажимает действие (согласовать/отклонить и т.п.) на карточке инбокса для ЛЮБОГО процесса (не только ТЭЛ), реальный Flowable user-task, соответствующий этому шагу этого инстанса, переходит в завершённое состояние в движке (проверяемо через `GET {flowable}/runtime/tasks?processInstanceId=...` — задача с прежним `id` в списке активных отсутствует).

**FR-2.** После завершения шага процесс либо (а) продвигается к следующему узлу — новая задача становится видна в инбоксе адресату следующего шага, либо (б) если это был последний узел — инстанс переходит в завершённое состояние, наблюдаемое через UI (список processes/аудит).

**FR-3.** Поведение из FR-1/FR-2 верно для процесса, ЗАВЕДЁННОГО как generic (не являющегося каноническим линейным ТЭЛ) — в частности, воспроизводимо на процессе «Закупки» приёмки 2026-07-01/02 или эквивалентном ему по структуре (произвольно названные узлы BPMN, не совпадающие с строкой `"task-approve"`).

**FR-4.** Продуктовый пользовательский путь завершения движкового user-task НЕ включает обращения к Flowable admin-REST API напрямую (ни человеком через консоль/curl, ни продуктовым кодом как обходной путь мимо инбокс-экшна). Единственный вход — действие в UI инбокса продукта.

### 4.2 Нефункциональное — обработка ошибок

**NF-1.** Если продукт настроен на работу с движком (движковый клиент сконфигурирован — есть `FLOWABLE_REST_APP_ADMIN_PASSWORD` и БД-пул) и `completeUserTask`/матчинг задачи в движке завершается неуспехом (движок недоступен, HTTP-ошибка, либо — что является диагностированной причиной BUG-014 — ни одна активная задача движка не соответствует шагу, который approve пытается завершить), пользователь ОБЯЗАН увидеть эту ошибку в ответ на своё действие (не 200 без эффекта). Формат ошибки (код/сообщение) — на усмотрение BUILD, критерий — что она видна и отличима от успеха.

**NF-2.** Успешный ответ approve-действия (HTTP 200 / эквивалент «принято») допустим ТОЛЬКО когда движковый шаг реально завершён (или иное объяснимое легитимное состояние, например инстанс уже был завершён ранее той же задачей — идемпотентный повтор), но НЕ когда движковая задача, соответствующая этому шагу, осталась активной и незавершённой после обработки действия.

**NF-3.** Различие между «движок не настроен вовсе» (осознанный конфиг продукта, например демо/офлайн-режим) и «движок настроен, но завершение не удалось» ОБЯЗАНО быть наблюдаемым по-разному: первое — не является ошибкой approve (существующий audit-only режим может остаться, если явно так решено продуктом), второе — обязано отражаться как ошибка по NF-1. Спека не предписывает, существует ли режим «движок не настроен» на живом стенде сегодня — это диагностический факт для BUILD; критерий проверяет только то, что на СТЕНДЕ, где движок настроен (текущее состояние 100.121.76.86:3000), путь §4.1 работает без обходов.

### 4.3 Анти-кейс (D-064)

**NF-4.** Изменения, вносимые в рамках закрытия этого шва, НЕ вводят новых кейс-специфичных строковых констант (имена процессов, названия шагов, роли, slug'и конкретного демо-кейса — по образцу уже существующих `APPROVER_ROLE="role-approver"`, `SOGLASOVANIE_SLUG="soglasovanie"`) в `src/`. Существующие хардкоды вне прямой причины BUG-014 (§3) — не предмет этой задачи, деТЭЛизация — отдельно.

## 5. LIVE_PROOF-путь (D-064) — как это доказывается на живом стенде

Доказательство обязано быть глазами через UI на живом стенде (100.121.76.86:3000 или эквивалентном dev-стенде), не через тесты в изоляции и не через прямой опрос БД/движка в обход продукта:

1. Открыть/создать generic-процесс (НЕ канонический линейный ТЭЛ — процесс «Закупки» из приёмки 2026-07-01/02 или новый мини-процесс с произвольно названными узлами BPMN, залитый XML через API — DURABLE-факт стенда).
2. Создать запись, инициирующую процесс (on_create trigger либо явный старт) → инстанс стартует, первая задача появляется в инбоксе.
3. Зайти под пользователем-адресатом, нажать действие «Согласовать»/эквивалент на карточке инбокса — БЕЗ обращения к Flowable admin-REST.
4. Наблюдать глазами: (а) следующая задача процесса появляется в инбоксе следующего адресата — ИЛИ — (б) если шаг последний, статус инстанса в UI (экран processes/аудит) отображается как завершённый.
5. Параллельно (для доказательства, не для UI) допустимо подтвердить состояние движка через `GET /runtime/tasks?processInstanceId=...` (задача, которую пользователь только что завершил, отсутствует среди активных) — это проверка ДОКАЗАТЕЛЬСТВА, не элемент пользовательского пути (FR-4 не нарушается: чтение для верификации ≠ обход в пользовательском пути завершения).
6. Анти-кейс: повторить шаги 1–4 на ВТОРОМ, отличном от первого, generic-процессе (другие имена узлов/шагов) — убедиться, что поведение не завязано на конкретные строки конкретного BPMN-файла.

- **O2.** BUG-016 (computed-поля/rollup не пробрасываются в переменные процесса) — берёт **T-0575**.

- **O4.** Полная деТЭЛизация всех хардкодов карты примитивов §5 (порог 5 000 000, DMN-константы в миграции, персоны e-larina/e-orlov и т.д.) — отдельный объём, не входит в этот шов.
- **O5.** Анти-кейс CI-гейт (грep-список запрещённых строк в `src/`, механизированный, постоянно действующий) — это D-064 инфраструктурная задача уровня фабрики, не продуктовый код этого task; T-0571 обязан НЕ ухудшать ситуацию (NF-4), но не обязан строить сам гейт.
- **O6.** Надёжность доставки/очередь для post-approve reconcile (например замена fire-and-forget `void (async…)` на durable job/outbox-очередь, упомянутая в ADR-T0432 §3.1 п.1 как возможное направление hardening) — если диагностика BUILD подтвердит, что таймингово-гоночная деградация (не структурное несовпадение ключа) тоже актуальна на живом стенде, это отдельный по объёму under-the-hood рефактор; данный тask требует только чтобы НАБЛЮДАЕМОЕ поведение (§4) выполнялось детерминированно на LIVE_PROOF-прогоне, а не конкретной техники доставки.
- **O7.** Timer-воркер (C6 карты примитивов, «reconcile только on-read, фонового воркера нет») — отдельная известная дыра, не предмет approve→Flowable шва.

## 7. Открытые вопросы

Нет blocking-вопросов. Диагностическая неопределённость (почему именно живьём не срабатывает) — не blocking по правилу аналитика: это предмет задачи, разведка §2 даёт код-грунтованную гипотезу (taskDefKey-хардкод), а спека фиксирует целевое ПОВЕДЕНИЕ (§4), не обязывает BUILD к конкретному способу фикса.
