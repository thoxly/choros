# Spec · T-0124 — Document-on-demand: рендер документа из живых справочников

**Status:** ready
**Phase:** SPEC (для дизайн-задачи — выход фазы = требования к будущему ADR, не сам ADR)
**Date:** 2026-06-11
**Task:** T-0124 (product=choros, type=design, prio 50, deps: T-0122 DONE)
**spec_ref:** `playbooks/choros-product-gap-map.md` §2 (envelope: «Document-on-demand»; «Docgen»), §3а/§4б (инвариант снапшота); `playbooks/choros-reference-process-tel.md` §5 (QR-кейс) + §1 «Вспомогательное» (генерация реестра договоров по шаблону).

**Решение фаундера (данность, НЕ развилка):**
- **Document-on-demand** (gap-map §2) — новый примитив ядра: документ **рендерится из живых справочников в момент запроса** (НЕ файл, лежащий в архиве). Покрывает QR-кейс (валидация документа на сайте клиента) и генерацию реестров.
- QR-кейс (ТЭЛ §5): «вся логика заведения — в системе: люди/агенты правят справочники в ходе работы (данные живут), итоговый документ формируется **на лету** из живых справочников».
- Docgen из шаблона в архив (gap-map §2, 🔵) — **частично поглощается** document-on-demand.

**Опора (НЕ противоречить):**
- `docs/design/T-0122-external-participant.adr.md` — внешняя поверхность УЖЕ спроектирована и **ждёт** document-on-demand. Контракт делегирования: `external_surface.doc_mode text NOT NULL DEFAULT 'snapshot'` CHECK ∈ `{snapshot, live}` (T-0122 §4.1); `verify` = facet-срез записи-цели (`resolveFor` → `projectFields`, T-0122 §2.5); `download` = presign **снапшота** (T-0119) **либо** живого-документа-рендера — «T-0124 потребляет этот контракт, рендер — там» (T-0122 §4.4 step5, §2.9). T-0122 даёт **поверхность доступа**, T-0124 — **рендер**.
- `docs/design/T-0119-files-attachments.adr.md` — **приёмная поверхность снапшота**: `is_snapshot boolean NOT NULL DEFAULT false` (T-0119 §2.1, AC-12); `addVersion(...isSnapshot)` создаёт иммутабельный файл-версию из байтов; «здесь только приёмная поверхность снапшота, не рендер — T-0124» (T-0119 §263). Граница (gap-map §4б инвариант 1): live-рендер всегда может быть **зафиксирован снапшотом** в файловое хранилище; вчерашний реестр воспроизводим; QR/ссылка указывает на снапшот ЛИБО явно «живой документ».
- `docs/design/T-0014-registry-model.adr.md` — namespace Application→Registry→Record; «живые справочники» = tenant-записи реестра; рендер читает их как источник данных.
- `docs/design/T-0021-grant-resolver-pdp.adr.md` — единый PDP-чокпойнт; рендер = **чтение записей**, права рендера = производная прав чтения этих записей (action-time, fail-closed, `projectFields`). Никакого второго permission-механизма для рендера.
- `docs/design/T-0016-audit-floor.adr.md` — append-only per-tenant hash-chained `audit_event`; open-vocab `type` (новые события = строки, не таблицы); рендер аудируется этой механикой.
- `docs/design/T-0033-data-classification.adr.md` — `DataClass`; срез полей в рендере проходит тот же clearance-транс­форм, что и обычное чтение.

**Связанные задачи (инварианты, читать дизайнеру):**
- **Инвариант снапшота (gap-map §4б инвариант 1, non-negotiable):** document-on-demand **всегда может быть зафиксирован снапшотом** в файловое хранилище (T-0119). QR/внешняя ссылка указывает на снапшот **либо** явно помечена «живой документ» — недвусмысленно. Вчерашний реестр обязан быть воспроизводим. Это несущее ограничение.
- **T-0122 (внешний участник) — DONE, deps:** делегировал T-0124 ровно рендер: контракт `doc_mode ∈ {snapshot, live}` определяет, на что указывает ссылка; `download` живого документа = вызов рендера T-0124; `verify` («валидно/невалидно» + публичный срез) — facet-проекция, которую рендер обязан уметь отдать внешней поверхности. T-0124 НЕ переопределяет внешнюю поверхность/токены/анти-абьюз — потребляет их.
- **T-0119 (файлы) — приёмная поверхность снапшота:** T-0124 фиксирует рендер как иммутабельный `is_snapshot=true` файл-версию через `addVersion`; T-0124 НЕ достраивает файл-хранилище/presign/версии.
- **T-0121 (отчёты-как-UI) — НЕ дубль:** T-0121 = кастомные UI-страницы руководителю (floor-2 React над named-binding) + реестр зависимостей страниц от полей. T-0124 = **документ-артефакт** (PDF/CSV/HTML-файл) из живых данных по шаблону, потенциально для внешней стороны/снапшота. Разные поверхности; ADR обязан провести границу, не плодить второй механизм рендеринга агрегаций.
- **Шаблоны и версионирование (gap-map §4б):** шаблон документа — производный артефакт от полей схемы (`registry_def.record_schema`); версионируется и проверяется на согласованность **той же подсистемой**, что T-0072 (named-binding) / T-0082 (единица версионирования связки) / T-0121 (реестр зависимостей) — НЕ четвёртый механизм «производный артефакт ↔ источник». Изменение поля схемы, на которое ссылается шаблон → предупреждение/red-line по той же дисциплине.

## 1. Summary

Choros получает примитив **document-on-demand** — документ (реестр договоров, справка о валидности по QR, выписка) **рендерится из живых справочников (`record`, T-0014) в момент запроса**, а НЕ хранится как готовый файл в архиве. Шаблон + текущие данные → документ. Права рендера — **производная прав чтения** тех записей, которые рендер читает (тот же PDP, T-0021), без второго механизма. Каждый рендер аудируется (T-0016). Любой живой рендер может быть **зафиксирован снапшотом** в файловое хранилище (T-0119, `is_snapshot`) — для юридической воспроизводимости («вчерашний реестр»); внешняя ссылка/QR (через поверхность T-0122, контракт `doc_mode`) указывает либо на иммутабельный снапшот, либо явно на «живой документ». QR-кейс (внешний видит «валидно/невалидно» + публичный срез + может скачать) и генерация реестра (выгрузка из справочника по фильтру) собираются из этого одного примитива.

Это **дизайн-задача**: выход фазы — спека требований, которые обязан покрыть будущий ADR (модель шаблона, контракт рендера, форматы day-1, граница снапшот↔живой, права как производность чтения, аудит, версионирование шаблонов, MVP↔Stage-2). Acceptance-критерии — **проверяемые свойства будущего ADR** (fitness-линт текста/трассируемость) либо **test после имплементации**.

## 2. Функциональные требования к дизайну (ADR обязан покрыть)

### FR-1 — Рендер из живых данных в момент запроса
ADR обязан определить **document-on-demand** как операцию `(шаблон, параметры) → документ`, где источник данных — **актуальное состояние живых справочников** (`record`, T-0014) на момент запроса, а не предзаписанный файл:
- Документ НЕ материализуется заранее; запрос рендера читает записи и собирает артефакт «на лету».
- ADR обязан зафиксировать **вход рендера**: ссылка на шаблон + параметры выборки (конкретная запись для справки по QR; фильтр/выборка для реестра) + субъект (для прав, FR-5).
- ADR обязан зафиксировать **выход**: байты документа в объявленном формате + метаданные (формат, момент рендера, версия шаблона, источник-данных-снимок для трассировки).

### FR-2 — Форматы документа day-1 (ADR выбирает и обосновывает)
ADR обязан определить **закрытый набор форматов рендера day-1** и обосновать выбор; набор расширяется той же механикой, не новым примитивом. Ось выбора (зона дизайна, но решение обязательно): какие из {PDF, HTML, CSV/табличный реестр} day-1; QR-кейс требует человекочитаемого (PDF/HTML), генерация реестра — табличного (CSV/XLSX). ADR обязан зафиксировать, что формат — атрибут шаблона/запроса, а движок рендера един для всех форматов (не код per-кейс).

### FR-3 — Отличие от снапшота T-0119 (когда живой реестр, когда зафиксированный документ)
**Несущее требование (gap-map §4б инвариант 1):** ADR обязан недвусмысленно развести два режима и зафиксировать, **когда что**:
- **Живой документ** — рендер каждый раз из текущих данных (`doc_mode='live'` на поверхности T-0122); отражает справочник «сейчас»; НЕ воспроизводим задним числом.
- **Снапшот** — рендер зафиксирован как иммутабельный файл-версия в хранилище (T-0119 `is_snapshot=true`); воспроизводим (`вчерашний реестр`), юридически фиксируем; ссылка/QR указывает на него (`doc_mode='snapshot'`).
- ADR обязан определить **операцию фиксации**: «отрендерить + сохранить снапшотом» = рендер (FR-1) → `addVersion(..., isSnapshot=true)` (T-0119); document-on-demand является **производителем байтов** для приёмной поверхности T-0119, не достраивает хранилище.
- ADR обязан зафиксировать: документ согласования (юридический артефакт) фиксируется снапшотом; оперативный реестр/справка может быть живым; выбор режима — атрибут конфигурации, недвусмысленный (никакого «то ли живой, то ли архивный»).

### FR-4 — QR-валидация через поверхность T-0122 (что показывается внешнему)
ADR обязан зафиксировать, как document-on-demand питает QR-кейс (ТЭЛ §5) **через уже спроектированную внешнюю поверхность T-0122**, не вводя свой канал доступа:
- **verify** (внешний без учётки) → document-on-demand отдаёт **узкий публичный срез** = «валидно/невалидно» + опубликованные поля (facet поверхности ∩ facet гранта, T-0122 §2.5); скрытые поля физически отсутствуют, verify не раскрывает их существование.
- **download** (внешний) → либо presign снапшота (`doc_mode='snapshot'`), либо рендер живого документа (`doc_mode='live'`) — T-0124 предоставляет рендер, который T-0122 `download` вызывает.
- ADR обязан зафиксировать, что «валидно/невалидно» выводится **из живых данных** (запись существует/в нужном статусе), а не из факта наличия файла; токены/TTL/отзыв/анти-абьюз — целиком T-0122, T-0124 не дублирует.

### FR-5 — Права рендера = производная прав чтения записей (НЕ второй механизм)
**Несущее требование (один механизм прав):** ADR обязан зафиксировать, что **право отрендерить документ выводится из права читать записи**, которые рендер читает, через тот же PDP (T-0021):
- Рендер читает каждую запись-источник под субъектом запроса; недоступная субъекту запись/поле **физически не попадает** в документ (`projectFields`, fail-closed) — рендер не обходит маскинг.
- Document-on-demand **не вводит** отдельного права «рендерить» / `render_acl` / поля видимости документа в обход grant-таблицы. Шаблон не повышает привилегию: рендер под субъектом X не может показать больше, чем X видит при обычном чтении.
- Для реестра (множество записей): в документ попадают только записи, на которые у субъекта есть `read`-грант; остальные отсутствуют (не «строка с прочерком», раскрывающая существование).
- Внешний (через T-0122) рендерит под производным ограниченным грантом — тем же путём, что внутренний субъект.

### FR-6 — Генерация реестров (выгрузка из справочника по фильтру)
ADR обязан определить генерацию реестра как частный случай document-on-demand: `(шаблон-реестра, фильтр/выборка) → табличный документ`:
- Вход — фильтр по реестру (тип/период/статус, как «реестр договоров» ТЭЛ §1); выход — табличный артефакт (FR-2).
- Применяются права FR-5 (только видимые субъекту записи) и режимы FR-3 (живой реестр сейчас vs снапшот «Прошлые реестры» ТЭЛ §1 — воспроизводимый).
- ADR обязан зафиксировать границу с T-0121: реестр = **документ-артефакт** (файл по шаблону), отчётная UI-страница руководителю = T-0121; общий слой согласованности шаблон↔поля — FR-8.

### FR-7 — Аудит рендеров
ADR обязан зафиксировать, что **каждый рендер** (успех И отказ) пишется в `audit_event` (T-0016, open-vocab `type`, не новая таблица):
- `actor` (кто/токен-поверхность для внешнего), `subject` (шаблон + параметры/выборка), `via`, результат (rendered/denied + reason), формат, версия шаблона.
- Для снапшота — событие фиксации связывает рендер с созданной файл-версией (`is_snapshot`), чтобы «какой снапшот когда из каких данных» был восстановим из аудита.
- Секрет токена (для внешнего пути) не пишется (наследует T-0122 §2.8).

### FR-8 — Шаблоны: авторинг и версионирование (та же подсистема согласованности)
ADR обязан определить **шаблон документа** как производный артефакт и зафиксировать его связь с источником-схемой **в существующей подсистеме согласованности**, не плодя четвёртый механизм:
- Шаблон ссылается на поля схемы (`registry_def.record_schema`); зависимость регистрируется/проверяется **той же дисциплиной**, что T-0072 (named-binding), T-0082 (единица версионирования связки), T-0121 (`report_page_dep`). Изменение поля, на которое ссылается шаблон → предупреждение/red-line на деструктивное (как T-0121 FR-2).
- ADR обязан зафиксировать: **кто авторит** шаблон (администратор/config-агент T-0077 как DRAFT-артефакт; human-gated promote — ось governance) и **как версионируется** (внутри/совместимо с единицей версионирования T-0082, не вторым механизмом).
- Версия шаблона — часть метаданных рендера (FR-1) и снапшота (трассировка «каким шаблоном отрендерено»).

### FR-9 — MVP vs Stage 2 (граница объёма)
ADR обязан явно провести границу day-1 / Stage-2 и обосновать:
- **MVP day-1:** контракт рендера + ≥1 формат, режимы живой/снапшот (FR-3), питание verify/download поверхности T-0122 (QR-кейс), генерация реестра (FR-6), права-как-производность (FR-5), аудит (FR-7), шаблон + согласованность (FR-8).
- **Stage-2 (явно отложить с критерием разморозки):** агентная генерация/правка шаблона под рантайм-разморозку (E5.6–E5.10, gap-map §4б инвариант 3); сложные форматы/верстка сверх day-1-набора; docgen-модуль по первому клиенту (gap-map §2, 🔵) сверх поглощённого ядра.

## 3. Нефункциональные требования

- **NF-1 (один механизм прав, non-negotiable):** рендер не вводит отдельной authority-подсистемы; право = производная прав чтения записей через PDP T-0021 (gap-map §4б инвариант 2). Нет `render_acl`/document-visibility в обход grant-таблицы.
- **NF-2 (воспроизводимость снапшота):** зафиксированный снапшот иммутабелен и воспроизводим — «вчерашний реестр» отдаёт байт-идентичный документ; живой документ явно помечен и не претендует на воспроизводимость (gap-map §4б инвариант 1).
- **NF-3 (fail-closed проекция):** недоступные субъекту записи/поля физически отсутствуют в документе; рендер не обходит `projectFields`/маскинг (T-0021/T-0033); сбой прав ⇒ отказ, не частичный документ с утечкой.
- **NF-4 (tenant-изоляция):** рендер читает только записи своего tenant (RLS, T-0013); cross-tenant источник в шаблоне невозможен; внешний путь — tenant выводится из токена (T-0122), не из запроса.
- **NF-5 (потребление, не достройка):** T-0124 потребляет T-0119 (приёмная поверхность снапшота), T-0122 (внешняя поверхность/токены/анти-абьюз), T-0021 (PDP), T-0016 (аудит) — не переопределяет и не дублирует их.
- **NF-6 (соразмерность):** day-1 набор форматов и режимов закрыт и минимален; расширение — той же механикой, не новым примитивом.

## 4. Явные не-цели (out of scope)

1. **Реализация** (DDL/код/движок рендера/эндпоинт) — последующие фазы; миграция (если нужна) по run-seam дисциплине, номер выбирает coder.
2. **Файл-хранилище / presign / версии** (T-0119) — переиспользуется как приёмная поверхность снапшота, не достраивается.
3. **Внешняя поверхность / токены / TTL / отзыв / анти-абьюз / anti-oracle** (T-0122) — переиспользуется; T-0124 не вводит свой канал доступа.
4. **Отчётные UI-страницы руководителю** (T-0121) — кастомные React-страницы; T-0124 = документ-артефакт по шаблону. Граница проводится, не дублируется.
5. **Агентная генерация/правка шаблона как рантайм-ответ агента** — design-only до разморозки Stage-2 (gap-map §4б инвариант 3); day-1 шаблон авторится config-агентом в DRAFT + human-gated promote.
6. **ЭДО / электронная подпись отрендеренного документа** — нишевой модуль (gap-map §2, 🔵).
7. **Docgen-модуль сверх поглощённого ядра** (сложная верстка/брендирование под конкретного клиента) — модуль по первому клиенту (gap-map §2, 🔵).
8. **UI рендера** (кнопка «сформировать реестр», QR-лендинг посетителя, выбор шаблона в пульте) — задачи слайса/UI-эпиков.
9. **Pooled-режим** — дефолт silo; tenant-вывод закладывается без ретрофита.

## 6. BLOCKING-вопросы фаундеру

Нет. Объём задачи определён решениями фаундера (gap-map §2 примитив document-on-demand; §4б инварианты 1–3) и контрактом делегирования от T-0122 (`doc_mode`) / T-0119 (`is_snapshot`). Открытые оси (набор форматов day-1, способ наполнения реестра зависимостей шаблона, представление прав рендера) — **зона DESIGN** (ADR выбирает и обосновывает), не меняют объём/поведение продукта и потому не BLOCKING. Граница MVP/Stage-2 зафиксирована инвариантом 3 (рантайм-агентная генерация — за разморозкой E5.6–E5.10), не требует нового решения фаундера.
