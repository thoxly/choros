# Spec · T-0039 — LLM-proposes-grants / human-confirms (E3.5)

**Epic/Story:** E3.5 — *"Describe a role in words → an LLM proposes structural grants → an admin
confirms"* (`proposed_by=LLM`, `confirmed_by=human`). **The proposal LLM is a BYO connected agent,
not a platform LLM dependency** (kickoff §4.5 "platform governs, client hosts").

**Status:** `ready` (no blocking founder questions — GT-1 signed for E3.5 as day-1; all open points
below are implementation-scoped and resolved by the signed model).

**Phase:** SPEC. Machine-readable contract: `docs/specs/T-0039.spec.contract.json`
(schema `schemas/spec.schema.json`).

**Deps:**
- E3.4 (T-0030): `POST /api/grants` write-API with `proposed_by`/`confirmed_by` columns already in
  the DB (migration 030) and wired in `src/http/grants.ts`. The static "Предложить гранты" button
  and `LLM_PROPOSALS` constant already exist in `ra-role-editor.jsx`; T-0039 replaces the static
  mock with a live BYO-LLM call.

---

## 0. One-line summary

Wire the "Предложить гранты" UI panel in `ra-role-editor.jsx` to a **backend proposal endpoint**
(`POST /api/grants/propose`) that forwards the natural-language role description to a **BYO
connected agent** (registered in `agent_card` with its own `llm_endpoint` + `llm_secret_handle`),
receives back a structured grant-set, stores it as a **pending proposal** (active only after human
confirmation), and lets an admin confirm or reject each proposed grant via the existing
`POST /api/grants` write-path (with `proposed_by=<agent-employee-id>`, `confirmed_by=<admin-actor>`).
No grant takes effect without explicit human confirmation.

## 1. Context: what already exists (do not rebuild)

### 1.1 Grant write-API and proposal semantics (T-0030)

`src/http/grants.ts` already handles `POST /api/grants` with `proposed_by` / `confirmed_by`
nullable columns (migration 030). A grant INSERT with `confirmed_by=null` is already representable
in the schema (the column is nullable). T-0039 must NOT change the lattice, the narrowing gate, or
the `validateAdminDelegation` call — those are frozen (NF-7 of T-0029).

The `GrantAuditEvent` shape from `src/core/grant-lattice.ts` already carries `proposedBy?` and
`confirmedBy?` — T-0039 populates both on the confirm path.

### 1.2 Static mock already in the UI (T-0030 seam)

`ra-role-editor.jsx` already contains:
- A textarea for the natural-language description (`llmText` state).
- `LLM_PROPOSALS` — a static mock array (three hardcoded proposal objects).
- `propose()` — currently sets `proposed` state from `LLM_PROPOSALS` (static, no HTTP call).
- `confirmGrant(i)` — POSTs a single confirmed grant via `POST /api/grants` with
  `proposed_by: "llm"`, `confirmed_by: ACTOR_ID`.

T-0039 replaces the `propose()` function body with a real HTTP call to `POST /api/grants/propose`.
The confirm path (`confirmGrant`) is **unchanged** — it already does the right thing.

### 1.3 BYO-LLM posture (RL-3 / E5.5)

"Platform governs, client hosts" — the platform holds **no** LLM credential. The proposal LLM
is a registered agent-employee (`kind=agent`) with an `agent_card` row carrying `llm_endpoint`
and `llm_secret_handle` (an RL-3 opaque handle resolved at call time, never stored as a raw key).
There is **no fallback to any platform-hosted LLM**. If no BYO agent is configured, the endpoint
returns `503 NO_PROPOSAL_AGENT`.

## 2. Functional requirements

### FR-1 — Proposal endpoint
The platform exposes `POST /api/grants/propose` that accepts a natural-language role description
(`text: string`) and a target `role_id` (`string`, UUID) and returns a structured set of proposed
grants (list of `ProposedGrantAtom`).

### FR-2 — BYO connected agent as proposal LLM
The proposal is generated by calling a registered agent-employee whose `agent_card.llm_endpoint`
and `agent_card.llm_secret_handle` are used for the LLM call. The platform never holds an LLM
credential directly (RL-3). The agent is identified by a well-known tenant-scoped slug
`proposal-agent` (configurable per tenant; day-1 a seed row or env var).

### FR-3 — Pending state: no grant active without human confirmation
`POST /api/grants/propose` **does NOT insert** any `grant` row. It returns a proposal payload
only. Grant rows are created only after an admin explicitly calls `POST /api/grants` with
`confirmed_by=<admin-id>`. A proposal that is never confirmed has no effect on the DB.

### FR-4 — Provenance recording
When an admin confirms a proposed grant, the POST body carries `proposed_by=<agent-employee-id>`
and `confirmed_by=<admin-actor-id>`. Both values are recorded in the `grant` row and in the
`GrantAuditEvent`. The `proposed_by` value is the agent's employee UUID (not the string `"llm"`
— that was the static-mock placeholder; T-0039 replaces it with the real agent-employee id).

### FR-5 — Scope and operation within the closed lattice
The LLM proposal returns grant atoms expressed as the four admissible `ScopeElement` kinds
(node / tags / interval / set — the same closed lattice already used by the structural editor).
Freeform scope is **never admitted** from an LLM proposal, regardless of whether the
confirming admin is the genesis owner (only humans may submit freeform scope; LLM proposals
are structurally lattice-only).

### FR-6 — Admin delegation gate on confirmation path
No change to the existing gate: `confirmGrant` already posts through `POST /api/grants` which
calls `validateAdminDelegation` before INSERT (FF-9 of T-0030). An LLM-proposed grant is
rejected at confirmation time if the confirming admin does not hold covering `mgmt_object:grant`
authority.

### FR-7 — No platform LLM dependency
The feature works only when a BYO agent is configured. There is no fallback platform LLM.
The `POST /api/grants/propose` endpoint returns `503 NO_PROPOSAL_AGENT` when no proposal agent
is registered for the tenant. The platform ships no LLM API key or SDK dependency.

### FR-8 — Tenant isolation
`POST /api/grants/propose` is tenant-scoped: the proposal agent lookup, the LLM call, and any
intermediate state are all scoped to the acting principal's tenant. Cross-tenant proposal is
structurally impossible (same `withTenant` / RLS pattern as other routes).

### FR-9 — Audit of proposal call
The act of calling the BYO agent for a proposal (whether or not the admin confirms) is written
to the `audit_event` table as a `grant.proposal_requested` event (actor = admin who clicked
"Предложить гранты", subject = target `role_id`, via = `"grant-propose"`). This is an
informational audit row; it is not a `GrantAuditEvent` (no grant row exists yet).

## 3. Non-functional requirements

### NF-1 — No LLM in the platform dependency tree
No `import` from any LLM SDK, no platform-held API key, no `OPENAI_API_KEY` / `ANTHROPIC_API_KEY`
environment variable required. The HTTP call to the BYO endpoint is plain `fetch`/`node:http`.

### NF-2 — Lattice purity: proposal output structurally validated
`POST /api/grants/propose` validates every atom in the LLM's response through `parseScopeElement`
(already exported from `src/http/grants.ts`). Any atom with an invalid scope is rejected (dropped
from the proposal list, not silently admitted). The endpoint returns a sanitized list.

### NF-3 — Freeform scope never in proposal output
Even if the BYO LLM returns `scope: {kind: "freeform", ...}`, the backend strips it from the
proposal list (NF-2 + FR-5 combined: `parseScopeElement` returns `null` for freeform → atom dropped).

### NF-4 — Secret handle resolved at call time, never logged
The `llm_secret_handle` is passed through the RL-3 handle resolver. The resolved value (the
actual credential) must not appear in logs, audit rows, or HTTP response bodies.

### NF-5 — One active proposal agent per tenant (day-1)
Day-1: one `proposal-agent` slug per tenant. Multi-agent selection and agent-picker UI are
out of scope. The proposal agent is resolved by a well-known slug or an env-var override.

### NF-6 — validateAdminDelegation not modified
The narrowing gate (`src/core/scoped-admin.ts`) is not touched. T-0039 only adds the proposal
endpoint and wires the confirm path's `proposed_by` field.

---

## 4. Out of scope

- **Persisting proposals as draft objects** — proposals are ephemeral (returned in the HTTP
  response only; not stored in the DB). Storing them is a future feature.
- **Multi-agent proposal selection UI** — day-1 one BYO agent per tenant.
- **LLM confidence scores / reasoning explanation** — out of scope; not required by the spec.
- **Streaming proposal response** — the proposal endpoint is a synchronous request/response.
- **Reject/dismiss individual proposed atoms via a separate API call** — rejection is implicit
  (admin simply does not call `POST /api/grants` for that atom). No `POST /api/proposals/:id/reject`.
- **Freeform scope in proposals** — structurally excluded (FR-5 / NF-2 / NF-3).
- **Stage-2 autonomy enforcement** (E5.7) — this task is day-1 / human-confirms only.
- **A2A call-graph breakers** (E5.8) — Stage-2, out of scope.
- **Retry / fallback to another agent on proposal failure** — out of scope day-1.

## 5. Acceptance criteria

### AC-01 — Proposal endpoint exists and returns structured grant list
`POST /api/grants/propose` with a valid JSON body `{text: "...", role_id: "<uuid>"}` and a
configured BYO agent returns `200` with `{ proposed: ProposedGrantAtom[] }` where each atom
has `resource_type`, `operation`, `scope` (valid `ScopeElement`), and optional `reason` string.
**Verifiable as:** test (integration test with a stub BYO agent HTTP server returning a fixture
grant list; assert 200 + valid atom structure).

### AC-02 — No grant row created by the proposal endpoint
After `POST /api/grants/propose`, a `SELECT COUNT(*) FROM choros."grant"` inside the tenant
shows the same count as before the call.
**Verifiable as:** test (integration test asserting DB row count unchanged after propose call).

### AC-03 — Confirmed grant carries proposed_by = agent-employee-id
When an admin calls `POST /api/grants` with `proposed_by=<agent-uuid>` and `confirmed_by=<admin-uuid>`,
the inserted `grant` row has `proposed_by = <agent-uuid>` and `confirmed_by = <admin-uuid>` (not null,
not the static string `"llm"`).
**Verifiable as:** test (integration test: propose → confirm cycle; assert DB row columns).

### AC-04 — Confirmed grant emits GrantAuditEvent with both fields populated
The `audit_event` row for the confirmed grant has `proposed_by = <agent-uuid>` and
`confirmed_by = <admin-uuid>` (via the `encodeGrantAuditEvent` path from T-0031).
**Verifiable as:** test (integration test: assert audit_event row after confirm).

### AC-05 — No grant takes effect without confirmed_by populated
A `grant` row with `confirmed_by IS NULL` is NOT included in `grant_resolver`'s active-grant
read (the PDP query from T-0021 already filters on `confirmed_by IS NOT NULL` — or its absence
means inactive). A proposed-but-never-confirmed grant gives zero capability.
**Verifiable as:** fitness (grep / static analysis: `grant_resolver` must include a
`confirmed_by IS NOT NULL` predicate in its effective-grant query; integration test: unconfirmed
proposed grant → `grant_resolver` returns no matching grants for that role).

### AC-06 — Freeform scope stripped from proposal output
If the BYO agent response includes an atom with `scope: {kind: "freeform", ...}`, that atom is
absent from the `proposed` list in the endpoint response.
**Verifiable as:** test (unit test: stub BYO response with a freeform atom; assert it is absent
from the sanitized output).

### AC-07 — Platform holds no LLM key
`grep -rE "OPENAI_API_KEY|ANTHROPIC_API_KEY|sk-[a-zA-Z0-9]+" src/` returns zero matches in
production code paths (excluding test fixtures with placeholder values).
**Verifiable as:** fitness (CI grep — the command above must return empty on `src/`).

### AC-08 — 503 when no proposal agent configured
`POST /api/grants/propose` with no proposal agent registered in the tenant returns
`503` with error code `NO_PROPOSAL_AGENT`.
**Verifiable as:** test (integration test: no agent seeded → assert 503 + error code).

### AC-09 — Proposal call audited as grant.proposal_requested
After `POST /api/grants/propose` (whether or not admin confirms), `audit_event` contains a row
with `type = 'grant.proposal_requested'`, `actor = <admin-who-clicked>`, `subject = <role_id>`,
`via = 'grant-propose'`.
**Verifiable as:** test (integration test: assert audit_event row after propose call).

### AC-10 — Admin delegation gate fires on confirmation
Confirming a proposed grant via `POST /api/grants` with an actor who lacks `mgmt_object:grant`
authority returns `403 ADMIN_GATE_REJECTED` — identical to direct grant creation (T-0030 AC-02).
**Verifiable as:** test (integration test: actor without admin authority → assert 403).

### AC-11 — Proposal output atoms pass parseScopeElement
Every atom in the proposal response has a scope that parses successfully through
`parseScopeElement` (no null, no freeform). Atoms with invalid scope are dropped, not surfaced
as 500.
**Verifiable as:** test (unit test: stub response with mixed valid/invalid atoms; assert only
valid atoms in output, no 500 on invalid input).

### AC-12 — Tenant isolation: proposal agent resolved in acting tenant only
Two tenants with different proposal agents configured: a request from tenant A uses tenant A's
agent, not tenant B's. Cross-tenant agent lookup is impossible by construction (RLS + GUC).
**Verifiable as:** test (integration test with two tenants; assert each uses its own agent
via stub responses).

### AC-13 — Secret handle not in logs or HTTP responses
The resolved credential from `llm_secret_handle` does not appear in any HTTP response body,
any `console.log`/`console.error` output, or any `audit_event.payload` column during the
proposal flow.
**Verifiable as:** test (integration test: capture stdout + response body + audit row; assert
no credential string present).

### AC-14 — UI propose() replaces static mock with HTTP call
After T-0039, `ra-role-editor.jsx`'s `propose()` function makes a real `fetch('/api/grants/propose', ...)`
call instead of setting state from `LLM_PROPOSALS`. The `LLM_PROPOSALS` static constant is removed.
**Verifiable as:** fitness (grep: `grep -n "LLM_PROPOSALS" web/src/screens/rights/ra-role-editor.jsx`
must return zero matches).

### AC-15 — proposed_by value is agent employee UUID, not string "llm"
In the confirm POST body, `proposed_by` carries the UUID of the agent-employee row (from the
`agent_card` lookup), not the legacy string `"llm"`. The `confirmGrant` UI handler is updated
to use the UUID returned by the proposal endpoint response.
**Verifiable as:** test (integration test: propose → confirm; assert `proposed_by` in DB row
is a valid UUID matching the proposal agent's employee id).

## 7. Interfaces / seams with existing code (for architect phase)

The following seams exist; their implementation is **architect-phase** work:

1. **`POST /api/grants/propose`** — new route in `src/http/grants.ts` (or a new module
   `src/http/grant-propose.ts`). Input: `{text, role_id}`. Output: `{proposed: ProposedGrantAtom[]}`.
2. **Proposal agent lookup** — query `agent_card` (T-0020 table) by a well-known slug
   (`proposal-agent`) within the tenant, read `llm_endpoint` + `llm_secret_handle`.
3. **BYO LLM HTTP call** — plain HTTP POST to `llm_endpoint` with the natural-language description
   and a structured-output schema for grant atoms (architect decides the prompt template and
   schema format — not specified here).
4. **`parseScopeElement` reuse** — already exported from `src/http/grants.ts`; sanitization hook.
5. **`appendAuditEventInput` reuse** — already available via `makePgAuditWriter()` for the
   `grant.proposal_requested` event.
6. **UI `propose()` replacement** — `ra-role-editor.jsx` line ~291: replace `LLM_PROPOSALS` mock
   with `fetch('/api/grants/propose', ...)`.
7. **`confirmGrant` proposed_by update** — `ra-role-editor.jsx` line ~305: replace hardcoded
   `"llm"` with the agent employee UUID returned in the proposal response.

The `grant_resolver` (T-0021 / `src/core/grant-resolver.ts`) active-grant predicate must filter
`confirmed_by IS NOT NULL` (AC-05). If it already does this, no change needed. If it does not,
that is a coder-phase fix.
