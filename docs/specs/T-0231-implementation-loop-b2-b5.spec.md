## 0. Резюме (что строим)

Реализуем **детерминированное ядро внедренческой петли** — четыре build-инкремента поверх
уже сидированного governance-аппарата агента-внедренца (B-1/migration 059):

- **B-2** — машина фаз `implementation` + модель-проекция `bundle`
  (`components{process,forms,statuses,roles,grants}` + `coherence_hash` + `changelog`) +
  аудит переходов фаз. **Несущий инкремент: B-3/B-4 зависят от B-2.**
- **B-3** — валидатор грант-консистентности бандла (разрешимый-адресат + drain-десинк),
  поверх `isNarrowerOrEqual` (T-0018) **как READER**.
- **B-4** — протокол интервью (`interview_claim` + валидация против read-only оргструктуры;
  поднятие `ask_interview_question` на `missing_role`/`ambiguous_assignee`; БЕЗ фантомных оргузлов).
- **B-5** — симуляция режим 1 (детерминированный расчёт маршрутов, расширение `bpmn-linter.ts`; БЕЗ движка).

**Design-достаточность.** ADR T-0129 §14 (+§2/§5/§6/§7/§8/§11/§15) — **достаточен как DESIGN**:
он фиксирует декомпозицию B-2..B-5 с порядком сборки и зависимостями, объектные контракты
(`implementation`, `bundle`, `interview_claim`), три гарда и инвариант когерентности, контракт-шов
с T-0130. Эти инкременты — **механическая материализация контрактов, уже зафиксированных ADR**;
новых продуктовых решений (меняющих объём) не требуется. Дельта-DESIGN **не нужен** —
см. §8 (Design-sufficiency) для точечных design-owned уточнений, которые архитектор/coder
решают автономно в рамке ADR без эскалации фаундеру.

**Граница (FROZEN-CLEAR):** grant-lattice (`src/core/grant-lattice.ts`) и object-handle —
**только ЧТЕНИЕ** (B-3 импортирует `isNarrowerOrEqual` как pure reader). Сборка **НЕ
модифицирует** эти файлы — frozen-guard (как Check-6 в `implementation-agent-seed.sh`) машинно
это гарантирует.

**Runtime агента DORMANT:** day-1 = governance + детерминированные гарды (как T-0077). LLM-runtime
агента-внедренца (поля `llm_*` в `agent_card` = NULL из migration 059) **не активируется** в B-2..B-5.

## 1. B-2 — машина фаз + проекция бандла

### 1.1 Функциональные требования
- **FR-B2-1 (машина фаз):** сущность `implementation` с полем `phase` ∈
  `{org_ready, interview, draft_bundle, simulation, pilot, promote_pending, production}`
  (ADR §2). Переходы — детерминированная функция; легальные рёбра = таблица §2 + обратные рёбра
  `revise` (`simulation→interview|draft_bundle`) и `evolve` (`production→interview`).
  Нелегальный переход — **отклоняется fail-closed** (не молчаливый no-op).
- **FR-B2-2 (инвариант human-gate):** единственный переход, инициируемый человеком, —
  `promote_pending→production`; все прочие инициирует внедренец, но ни один не пересекает
  границу draft→published без human-gate (ADR §2 «инвариант фаз», §4). Машина **не способна**
  выразить self-promote.
- **FR-B2-3 (проекция бандла):** `bundle` = проекция (НЕ новый authority-store) c полями §5.1:
  `bundle_id, implementation_id, tier∈{draft,published}, version:int (монотонная),
  components{process:BPMN-XML, forms:FormSpec[], statuses:StatusModel, roles:RoleRef[], grants:GrantSpec[]},
  coherence_hash:string, changelog:SemanticChangelog`.
- **FR-B2-4 (coherence_hash):** `coherence_hash` — детерминированная функция от версий всех
  компонентов; рассинхрон версий компонентов внутри бандла → хэш не совпадает → **ошибка**
  (инвариант когерентности §5.1). Одинаковый набор компонентов → одинаковый хэш (детерминизм).
- **FR-B2-5 (changelog семантический):** `changelog` — **семантический** («добавлено поле X,
  мягкая миграция Y»), НЕ raw git-diff (§5.1, §5.3).
- **FR-B2-6 (аудит переходов):** каждый переход фазы пишется в единый аудит через
  `appendAuditEvent` (T-0031) c типом `impl.phase.transitioned`; сборка бандла → `impl.bundle.assembled`
  (вокабуляр §10.4). Новый аудит-лог НЕ вводится.
- **FR-B2-7 (частичный promote недостижим):** published-версия = ровно тот draft-бандл,
  что прошёл прогон; нельзя промоутнуть подмножество компонентов — `coherence_hash` связывает
  все компоненты в единую версию-связку (§10.1).

### 1.2 Acceptance (machine-checkable) — см. AC-1..AC-8.

## 2. B-3 — грант-консистентность бандла (READER над T-0018)

### 2.1 Функциональные требования
- **FR-B3-1 (разрешимый адресат):** для каждого `GrantSpec.scope` шага бандла валидатор проверяет,
  что существует узел оргдерева/роль тенанта, на который грант резолвится непусто (§6). Шаг без
  разрешимого адресата → **отказ валидации** (не молчаливый грант).
- **FR-B3-2 (narrowing через READER):** проверка «грант не шире скоупа роли-родителя» использует
  `isNarrowerOrEqual` (T-0018) **как импортируемый pure reader**; B-3 **НЕ** определяет новую решётку
  и **НЕ** модифицирует `grant-lattice.ts`.
- **FR-B3-3 (drain-десинк):** дренируемый старый инстанс **не получает** грант, которого не было
  в его версии бандла (§5.1 security-десинк, §10.3 drain-by-default). Десинк версий → **ошибка**.
- **FR-B3-4 (расхождение, не угадывание):** недостающая роль (напр. «Юротдел» для правила «≥5 млн →
  юротдел») — это **расхождение** (вход для B-4 `ask_interview_question`), а не молчаливый/фантомный грант (§6).

### 2.2 Acceptance — см. AC-9..AC-12.

## 3. B-4 — протокол интервью (read-only оргструктура)

### 3.1 Функциональные требования
- **FR-B4-1 (контракт claim):** `interview_claim{claim_id, text, org_refs:RoleRef[],
  resolution∈{resolved,discrepancy}, discrepancy?{kind∈{missing_role,ambiguous_assignee,scope_unrepresentable}, question}}` (§7).
- **FR-B4-2 (валидация против живой оргструктуры):** каждое утверждение валидируется против
  существующей **read-only** оргструктуры тенанта; интервью её **читает, но не создаёт узлов**.
- **FR-B4-3 (расхождение → вопрос, не фантом):** если утверждение ссылается на отсутствующую
  роль/узел ИЛИ адресат неоднозначен — внедренец **обязан** поднять явный вопрос человеку
  (`ask_interview_question`, аудит `impl.interview.question_asked`) и **НЕ** создавать фантомный
  оргузел, **НЕ** угадывать адресата (§7 жёсткий инвариант AC-4). `missing_role` и
  `ambiguous_assignee` — обязательные распознаваемые виды расхождения.
- **FR-B4-4 (резолв claim):** разрешённое утверждение → `resolution=resolved`, аудит
  `impl.interview.claim_resolved`.
- **FR-B4-5 (старт из шаблона — параметр, не блокер):** «старт из каталога шаблонов vs с нуля» —
  MVP-параметр фазы интервью; **наполнение каталога контентом — out-of-scope** (Stage-2, §12).

### 3.2 Acceptance — см. AC-13..AC-16.

## 4. B-5 — симуляция режим 1 (расчёт маршрутов, БЕЗ движка)

### 4.1 Функциональные требования
- **FR-B5-1 (детерминированный расчёт маршрутов):** расширение `src/core/bpmn-linter.ts` (T-0027):
  детерминированное протаскивание атрибутов синтетических кейсов через шлюзы/DMN; выход — таблица
  «кейс → маршрут → какой реальный человек/роль получил бы задачу» (§8.1 режим 1).
- **FR-B5-2 (БЕЗ движка, БЕЗ эффектов):** режим 1 — чистая функция: без Flowable, без БД-side-effect,
  без сети; пересчитываем при каждой правке черновика (§8.1, §18). Детерминизм: один и тот же бандл +
  кейсы → один и тот же маршрут-результат.
- **FR-B5-3 (включает линт):** прогон режим 1 консумирует `lintBpmn(xml)` (T-0027) как **единственный**
  BPMN-линтер; B-5 **НЕ** вводит новый/параллельный линтер/парсер (§6, §8.1, AC-6).
- **FR-B5-4 (адресат из живой оргструктуры):** «какой реальный человек получил бы задачу» резолвится
  из живой read-only оргструктуры по RoleRef бандла (связь с B-3 разрешимым-адресатом).

### 4.2 Acceptance — см. AC-17..AC-20.

## 5. Нефункциональные требования

- **NF-1 (опора, ноль переизобретения):** B-2..B-5 расширяют T-0077/T-0027/T-0018/T-0031/extensibility §7-§9;
  ноль нового authority-store, второго аудит-лога, новой модели сред, нового scope-механизма (ADR §1/§3/§15).
- **NF-2 (frozen-clear: grant-lattice/object-handle READ-only):** сборка **не модифицирует**
  `src/core/grant-lattice.ts`, `src/core/grant-resolver.ts`, object-handle и прочие frozen-файлы
  списка `implementation-agent-seed.sh` Check-6. B-3 импортирует `isNarrowerOrEqual` только как reader.
- **NF-3 (agent LLM runtime stays dormant):** LLM-runtime агента-внедренца не активируется;
  `agent_card.llm_*` остаются NULL (migration 059); day-1 = детерминированные гарды + governance (как T-0077).
- **NF-4 (детерминизм + fail-closed):** все гарды/расчёты детерминированы; невалидный вход
  (нелегальный переход, нерезолвимый адресат, десинк версий, нелинтуемый BPMN) → **отказ**, не молчаливый успех.
- **NF-5 (идемпотентность миграций):** любые миграции B-2..B-5 — `ON CONFLICT DO NOTHING`,
  без `CREATE TABLE` сверх необходимого; `known_tenant_tables.txt` обновляется при новой таблице
  (паттерн bundle-coherence/grant-trail).
- **NF-6 (каждый CI-чек умеет падать):** каждый новый fitness-чек поставляется с `--self-test`,
  краснеющим на намеренно-сломанной фикстуре (паттерн §16 ADR, T-0207 Check self-test).
- **NF-7 (порядок сборки):** B-2 → (B-3 ∥ B-4) → B-5; B-3/B-4 импортируют модель B-2, B-5 потребляет
  бандл B-2 и RoleRef-резолв B-3/B-4. PR-цепочка/мерж в этом порядке.
- **NF-8 (тенант-изоляция):** все новые сущности tenant-scoped; новые db-тесты, добавляющие аудит,
  минтят свежий случайный tenant UUID (НЕ переиспользуют TENANT_A/_B — урок T-0205/db-shared-db-gotcha).

## 8. Design-sufficiency (для оркестратора: нужен ли DESIGN перед BUILD?)

**Вывод: ADR T-0129 §14 (+§2/§5/§6/§7/§8/§11/§15) ДОСТАТОЧЕН как DESIGN — дельта-DESIGN НЕ нужен.**
BUILD может идти прямо против ADR. Обоснование:
- §14 даёт декомпозицию B-2..B-5 с тем же scope, что задача, + порядок и зависимости.
- §2/§5/§7 фиксируют объектные контракты (фазы, бандл, interview_claim) на уровне полей.
- §6 фиксирует три гарда; §8.1/§11 — контракт режима 1 и шов с T-0130.
- §15 явно помечает сущности как **проекции** (не authority-таблицы) — модель уже спроектирована.
- Эти инкременты — материализация уже-зафиксированных контрактов; продуктовых развилок нет.

**Точечные design-owned уточнения (архитектор/coder решают автономно в рамке ADR, НЕ эскалация):**
эти пункты — «КАК», а не «ЧТО»; ADR оставляет их реализатору и они **не** меняют объём продукта:
- **G-1** Физическая форма хранения проекций `implementation`/`bundle` (новые tenant-таблицы vs
  проекция-view поверх existing) — реализационный выбор; ADR §15 требует лишь «проекция, не новый
  authority-store». Если новая таблица — обновить `known_tenant_tables.txt` (NF-5).
- **G-2** Конкретная функция `coherence_hash` (алгоритм/канонизация компонентов) — реализационная,
  ADR требует лишь детерминизма и ловли десинка (§5.1).
- **G-3** Формат `StatusModel`/`FormSpec`/`RoleRef`/`GrantSpec` сериализации — переиспользует
  existing формы/статусы/grant-схемы; coder выравнивает по existing типам.
- **G-4** Точная сигнатура расширения `bpmn-linter.ts` под режим 1 (новая exported функция
  route-calc рядом с `lintBpmn`, импортирующая его) — реализационная.

Ни один G-* не меняет объём/поведение продукта и не требует фаундера → **status `ready`, design_sufficient=true**.

## 9. Blocking questions
