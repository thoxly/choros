# T-0688 — связка мелких UX-дефектов (E-UX-HUMAN/minor, капстоун T-0647)

## Контекст

Капстоун-приёмка T-0647 (2026-07-03, `docs/live-proof/T-0647.capstone-live-proof.md:21`)
зафиксировала 4 minor-находки одной строкой:

> «Выполнить шаг» после claim показал ложное «Эта задача уже недоступна» хотя шаг
> завершился (stale-drawer). Строки инбокса не кликабельны; ДЕДЛАЙН/ДЕЙСТВИЕ
> обрезаны вьюпортом. «Экспорт» в журнале прав — нет запроса/скачивания (мёртвая
> кнопка, §6).

Между этой находкой и T-0688 в dev влетели T-0652 (администрирование честное,
включая живой CSV-экспорт журнала прав) и T-0653 (view-примитив + рабочий инбокс:
поиск/фильтры/группировка/кликабельная строка). Сверщик волны 5 флагнул риск
дубля — T-0688 начался с разведки каждого из 4 пунктов на актуальном dev
(`git log dev` по T-0652/T-0653) ПЕРЕД реализацией.

## Разведка: что уже закрыто, что осталось

### Пункт 2 — «строки инбокса не кликабельны целиком» → ЗАКРЫТО T-0653

### Пункт 4 — «Экспорт» в журнале прав мёртвая → ЗАКРЫТО T-0652

`web/src/screens/rights/ra-grant-trail.jsx` — кнопка «Экспорт CSV» вызывает

### Пункт 1 — stale-drawer после claim/complete → ОТКРЫТ, основной объём задачи

Подтверждено разведкой кода (не только по формулировке находки): POST
`/api/inbox/:id/action` (`src/http/inbox.ts`, обработчик на `router.register("POST",
"/api/inbox/:id/action", ...)`) ищет задачу через `findWaitingInstanceTask` —
если задача **уже не waiting** (шаг реально завершился МЕЖДУ открытием дровера и
кликом «Выполнить шаг» — типичная причина: T-0522 engine-drive reconcile-on-read
net на КАЖДОМ `GET /api/inbox` самолечит пропущенный post-approve engine drive
фоном, либо дублирующий клик/вторая вкладка), обработчик БЕЗ ДОПОЛНИТЕЛЬНОЙ
проверки падал в общий `404 NOT_FOUND "задача не найдена — обновите страницу"`.
Фронт (`screen-inbox.jsx` `ACTION_ERROR_MESSAGE.NOT_FOUND`) маппит этот код в
ровно ту фразу из находки: «Эта задача уже недоступна — обновите страницу».
Технически честно (записи о waiting-задаче действительно больше нет), но вводит
в заблуждение: шаг ФАКТИЧЕСКИ завершился успешно — просто не в результате ЭТОГО
клика.

Симметричный случай уже был решён в другом маршруте: `GET /api/inbox/:id`
(деталь дровера, тот же файл, ветка `if (!item && writeDeps)`) при пустом
`findWaitingInstanceTask` дополнительно сверяется с `listInstanceProjections` —
запись со `status:"done"` и совпадающим `inboxTaskId` синтезирует честный
«Завершено» вместо провала. POST-обработчик этой сверки не делал.

## ADR

### D1 — «уже выполнено» сверяется той же проекцией, что и GET-деталь, до генерик-404

В `!task` ветке POST `/api/inbox/:id/action`, ПЕРЕД тем как провалиться в
defer-row путь (и его собственный честный 404), добавлена проверка:
`listInstanceProjections(pool, tenantId).find(p => p.inboxTaskId === taskId &&
p.status === "done")`. Совпадение → обычный `200 {instanceId, status:"done",
action:"approve", outcome, engine:"already"}` (тот же контракт, что и настоящий
успех/что и defer-ветка уже возвращает при `driveResult.alreadyEnded`) — НЕ
ошибка. Не совпало → падение в существующий defer-row/генерик-404 путь без
изменений (genuine 404 остаётся genuine 404 — юнит-тест на это есть).

Отклонённая альтернатива: чинить на фронте (не показывать ошибку после
успешного `approveTask`/`handleComplete`) — не покрывает случай, когда шаг
завершился ФОНОМ (reconcile-on-read между открытием дровера и кликом), т.е. НЕ
в результате действия этого конкретного клика — фронт не может знать «уже
выполнено» без ответа сервера. Серверная проверка — единственное место, где это
различимо от «задачи никогда не было».

Переиспользование: `listInstanceProjections` — тот же вызов, что GET-деталь уже
делает; новых запросов/таблиц/эндпойнтов нет.

### D2 — обновлённый тест

`src/__tests__/inbox-action.test.ts`: два новых теста —
(а) `200 + status:done (idempotent)` при повторном approve уже завершённой
задачи (первый approve реально завершает шаг, второй на тот же `taskId` раньше
падал 404, теперь 200 `engine:"already"`);
(б) регрессия на честность: `404 NOT_FOUND` для ДЕЙСТВИТЕЛЬНО неизвестного
`taskId` остаётся 404 — проверка «уже выполнено» не маскирует настоящее
отсутствие задачи.

### D3 — колонки ДЕДЛАЙН/ДЕЙСТВИЕ обрезаны вьюпортом: подтверждено ТОЛЬКО в плоском режиме

T-0653 (`fix-forward defect #12`) уже дал сгруппированному режиму
`table-layout: fixed` + `chs-r` (колонка «Действие») закреплённой в 140px
(`web/src/app-shell/app.css`, `.chs-inbox__group .chs-itable`). Плоский
(несгруппированный) режим сознательно остался на `auto` layout (комментарий:
«a lone table has nothing to misalign against, and auto layout gives the
«Задача» column its natural room») — но НЕ получил анти-обрезной механизм.

Живая проверка (Playwright, статический HTML-харнесс с реальными
`tokens.css`/`components.css`/`app.css` и разметкой `screen-inbox.jsx`/
`shell.jsx`): `.chs-inbox__scroll` действительно несёт `overflow:auto` и
технически прокручивается (`scrollLeft` реально сдвигает содержимое) — НО
горизонтальный скроллбар сидит в самом низу высокой, преимущественно
вертикально-скроллящейся таблицы и не является различимым аффордансом; на
1280px и 1024px вьюпортах колонка ДЕЙСТВИЕ полностью пропадала за правым краем
без единого визуального намёка на «прокрутите вправо» — ровно то, что находка
описывает как «обрезаны», хотя формально путь скролла существовал.

Причина переполнения — три столбца («Задача», «Процесс», «Исполнитель») росли
до полной длины контента без ограничения (в отличие от «SLA»/«Дедлайн»/
«Действие», у которых содержимое короткое по природе).

### D4 — фикс: ограничить три открытых столбца по КЛАССУ содержимого, не по позиции

`web/src/app-shell/app.css`, новый блок, scoped `.chs-inbox__scroll > .chs-itable`
(только плоский режим — правило T-0653 для `.chs-inbox__group` не тронуто,
общая база `.chs-table`/`.chs-itable` в `components.css` не тронута):

- `.chs-task` (столбец «Задача») → `max-width: 320px`
- `.chs-processref` (столбец «Процесс») → `max-width: 200px`
- `.chs-actorchip` (столбец «Исполнитель») → `max-width: 160px`
- `.chs-r` (столбец «Действие») → `width: 140px` (тот же паттерн, что T-0653
  уже применил в сгруппированном режиме)

Каждый контейнер получает `min-width: 0` (необходимо, т.к. и `.chs-task`, и
`.chs-actorchip`/`.chs-exec` — flex-контейнеры; без этого текст-потомок не
может сжаться для эллипсиса) + `overflow:hidden; text-overflow:ellipsis;
white-space:nowrap` на текстовом узле.

Селекторы адресуют СОДЕРЖИМОЕ (`.chs-task`, `.chs-processref`, `.chs-actorchip`),
а не позицию колонки (`:nth-child`) — панель «Настроить» (T-0653) позволяет
скрывать любую из name/process/executor независимо; позиционный селектор молча
ограничил бы не ту колонку после скрытия одной из них.

Живая Playwright-проверка ДО/ПОСЛЕ (реалистичный контент + одна намеренно
длинная «adversarial» строка на каждую колонку сразу):
- До фикса (1280px): ДЕЙСТВИЕ полностью за краем, без видимого скролла.
- После фикса (1280px, реалистичный контент): все 6 колонок видны, ДЕДЛАЙН
  читается целиком, ДЕЙСТВИЕ у самого края (минимальный остаточный скролл).
  При 1440px+ помещается целиком. Экстремальная (adversarial) строка
  корректно эллипсируется, не ломая ширину остальных строк сильнее разумного.
- `.chs-inbox__scroll`'s `overflow:auto` остаётся честным фолбэком для
  вьюпортов уже 1280px или контента ещё длиннее — не убран, а стал
  крайним случаем вместо основного пути.

Отклонённая альтернатива: `table-layout: fixed` на весь плоский режим (как в
группах) — переоценивает риск: T-0653 сознательно оставил `auto` для «Задачи»
именно в плоском режиме (единственная таблица, нечему рассинхронизироваться
между группами), и `fixed` потребовал бы жёстко зафиксировать ВСЕ колонки
(включая SLA/Дедлайн) через `<col>`/проценты — больше кода ради того же
результата, который таргетированные `max-width` дают точечно.

## Побочная находка (НЕ в этой задаче, follow-up)

`src/http/inbox.ts` содержит 2 сырых NUL-байта (`\x00`) внутри
`.join(" \x00 ")` — судя по контексту (соседний код собирает поисковый
haystack через `.join(" · ")` для T-0653's server-side search), это
искажённый разделитель «·» (U+00B7), а не намеренный NUL. Не относится к
данной задаче (обнаружено grep'ом, который тихо ломался об эти байты при
разведке); не тронуто. Кандидат отдельной задачи — заменить на буквальный `"·"`.

## Acceptance-критерии

- AC-1: повторный (или фоново-опередивший) клик «Выполнить шаг»/«Согласовать»
  на уже завершённом шаге возвращает 200 с `status:"done"`, не 404 —
  юнит-тест `inbox-action.test.ts`.
- AC-2: генуинно неизвестный `taskId` по-прежнему 404 `NOT_FOUND` — регрессия
  не маскирует настоящее отсутствие задачи — юнит-тест `inbox-action.test.ts`.
- AC-3: в плоском (несгруппированном) режиме инбокса колонки ДЕДЛАЙН/ДЕЙСТВИЕ
  остаются в пределах вьюпорта под реалистичным контентом на ≥1280px; при
  экстремальном контенте деградация — горизонтальный скролл
  (`.chs-inbox__scroll`), не необратимая обрезка.
- AC-4 (документационный): пункты 2 и 4 подтверждены закрытыми T-0653/T-0652
  соответственно — код не дублирован.
