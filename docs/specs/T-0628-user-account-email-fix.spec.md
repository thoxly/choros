# T-0628 — свободный login + обязательный email при создании учётки, гейт /users

Контракт-JSON: `docs/specs/T-0628.spec.contract.json` (schema `demiurge/spec`, валидирован).

## Контекст

Живая приёмка T-0583 (2026-07-04) нашла P0: `POST /api/users` передавал в Keycloak
`email: login` хардкодом. Не-email `login` → Keycloak 400 `error-invalid-email` →
у нас это маппилось в 503 `AUTH_UNAVAILABLE` — обычный happy-path из UI ломался.

Между обнаружением и этой задачей в main уже влетел **T-0625** (предок этой ветки —
`git merge-base --is-ancestor` подтверждает), который закрыл тот же 503-баг
**другим путём**: сделал `login` обязательно email-формата (валидация на клиенте и
сервере ДО похода в KC, честный 400 вместо 503) + добавил колонку
`employee.login` (миграция 126) так, что список учёток показывает настоящий логин,
а не KC UUID.

Т.е. из трёх пунктов исходного тикета T-0628:
- **BUG (список показывает UUID)** — уже полностью закрыт T-0625, не трогаем.
- **P0 (email хардкод → 503)** — 503 устранён, но контракт не совпадает с тем,
  что просит T-0628: там login должен остаться свободным (не обязан быть email),
  а email — отдельное обязательное поле. Это и есть основной объём этой задачи.
- **Минор (/users открывается не-владельцу по прямому URL)** — не тронут вообще.

## ADR

### D1 — email отдельная колонка, не переиспользование login

Добавляем `choros.employee.email text NULL` (миграция 127, аддитивная, стиль
125/126). `NULL` для существующих строк (сид-данные, учётки до фикса) —
легаси-паттерн идентичен `login`/`deactivated_at`. Отклонённая альтернатива:
писать email в `login` и выводить «настоящий» логин отдельно — усложняет схему
без пользы, т.к. это разные атрибуты одного человека.

### D2 — валидация: email обязателен+формат, login обязателен без формата

`validateCreateBody` (user-mgmt.ts): убрана проверка `EMAIL_RE.test(login)`,
добавлена проверка `EMAIL_RE.test(email)` на новом обязательном поле `email`.
Сервер — источник истины; клиент (`users-form.js`) зеркалит ту же валидацию
(существующий паттерн, mirrors register.ts).

### D3 — KC-порт без изменений сигнатуры

`KeycloakUserPort.createHumanUser(spec: KcHumanUserSpec)` уже принимает
`username` и `email` как два поля с T-0342 — интерфейс не менялся. Меняется
только вызывающий код: `kc.createHumanUser({ username: login, email, password,
actorType: 'human' })` вместо `{ username: login, email: login, ... }`.

`fake-user-port.ts` валидирует `spec.email` email-форматом (не трогаем — email
и так будет валиден к этому месту в реальном потоке) — но **больше не требует
email-формат от `spec.username`**: это единственная правка в фейк-порте. Причина:
реальный Keycloak realm (`config/keycloak/realm-choros.json` — проверено, не
выставляет `registrationEmailAsUsername`/иных email-only флагов) не требует
username быть email-подобным. Требование «login=email» было собственным
решением T-0625, не ограничением самого KC.

### D4 — гейт /users клиентский, по существующему паттерну (не redirect)

В кодовой базе нет route-guard/redirect компонента ни для одного admin-раздела
(`/agents`, `/org`, `/llm-connections` и т.д. — везде nav-hiding + честный 403 от
сервера на write, разведано агентом и лично). Паттерн `screen-org.jsx`:
`canWrite` вычисляется из статуса уже вызываемого экраном гейтованного GET
(`/api/org/tenant-state`: 200→`canWrite=true`, 403→`canWrite=false`), контролы
записи скрываются/заменяются пояснительным баннером. `screen-users.jsx` уже
дёргает ровно этот эндпоинт (для списка должностей) — переиспользуем его статус
вместо нового вызова.

Отклонённая альтернатива: redirect на `/overview` для не-владельца — не
соответствует ни одному существующему паттерну кодовой базы, добавил бы новый
архитектурный примитив ради одного экрана (несоразмерно объёму задачи).

### D5 — миграция 127

Максимальный существующий номер — 126 (`126_employee_login.sql`). Новая:
`127_employee_email.sql`, аддитивная (`ADD COLUMN IF NOT EXISTS email text
NULL`), без FK/RLS-изменений (наследует `employee`'s existing FORCE RLS policy).

## Что уже закрыто (не трогать)

- 503→400 фикс структуры (валидация ДО KC-вызова) — сохраняем сам факт
  «валидация раньше похода в KC», меняем только ЧТО валидируется.
- `GET /api/users/accounts` показывает `login`, не UUID (T-0625, migration 126).
- `ci/checks/user-mgmt-reuses-kc-port.sh` инвариант (нет своего HTTP к KC).
