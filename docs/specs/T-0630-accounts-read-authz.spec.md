# T-0630 — GET /api/users/accounts без authority-гейта (адверс-находка T-0628)

Task: T-0630 (security, столп 4 — агенты/сотрудники с правами)
Base: dev@aee684b, branch `task/T-0630-accounts-read-authz`

## Контекст

Живая приёмка/адверс-скептик T-0628 нашёл: `GET /api/users/accounts`
(`src/http/user-mgmt.ts`) отдаёт полный список учёток тенанта (login, ФИО,
должность, отдел, active) ЛЮБОМУ аутентифицированному сотруднику — маршрут
обёрнут в `withAuth` (аутентификация есть), но внутри обработчика нет
authority-проверки. `POST /api/users` и `PATCH /api/users/:employee_id` в
ЭТОМ ЖЕ ФАЙЛЕ гейтуются `authorizeOrgWrite` → `loadAdminContext` →
`assertOrgObjectAuthority(admin, "mgmt_object:employee", "create"|"update", …)`
— владелец ИЛИ держатель делегируемого `mgmt_object:employee` гранта. GET
пропускал этот шаг целиком: рядовой сотрудник без единого mgmt-гранта получал
200 со всем списком учёток тенанта прямым `fetch`.

Это гейт-паритетный баг того же класса, что T-0619/T-0620/T-0622 (волна 2):
write-гейт стоит, read-гейт отсутствует, живое проживание рядовым вскрывает
брешь, которую CI (green) не ловит, потому что тестировавшийся актор всегда
был владельцем/ассистентом.

## D-064 / T-0658 предупреждение

Спека фаундера прямо запрещает городить НОВЫЙ employee-lookup без
`deactivated_at` — это был бы 6-й authority-путь параллельно
`getGrantsForSubject` / `isGenesisOwnerForTenant` / `loadAdminContext` (см.
ADR-T0658-resolver-deactivation-gate.md: "единственный резолвер прав"
инвариант T-0610, оба текущих admin-резолвера уже несут
`AND deactivated_at IS NULL` fail-closed после T-0658). Фикс ОБЯЗАН
переиспользовать `loadAdminContext` (тот же вызов, что уже строкой выше в
POST/PATCH этого файла) — не изобретать параллельный SQL-запрос на
"сотрудник активен?".

## Functional

- F1. `GET /api/users/accounts` резолвит актора и его тенант (как раньше:
  `extractActor` + `resolveActorTenant`), затем строит `AdminContext` через
  `loadAdminContext(pool, tenantId, actorId, nowMs())` — ТУ ЖЕ функцию,
  которую POST/PATCH уже вызывают в этом файле.
- F2. Пускает запрос (200 + список), если ЛИБО `admin.isGenesisOwner`
  (владелец тенанта — резолвится из БД, несёт T-0658 `deactivated_at IS
  NULL`), ЛИБО актор держит любой делегируемый `mgmt_object:employee` грант
  (create/update/delete — не сужаем до конкретной операции: держатель ЛЮБОГО
  из этих грантов уже полномочен видеть организационную структуру, которую
  этот грант позволяет менять; это read-паритет с существующим
  `hasOrgObjectAuthority` в seed-write.ts, но специфично для
  `mgmt_object:employee`, а не "любой оргобъект" — задача просит именно этот
  ресурс-тайп).
- F3. Рядовой сотрудник без владения и без такого гранта получает честный
  403 `NOT_OWNER` (тот же код ошибки, что POST/PATCH уже возвращают на этом
  файле для несанкционированной записи — единообразие сообщения, не новая
  таксономия ошибок).
- F4. Тенант-изоляция не меняется: гейт проверяется ПОСЛЕ резолва
  собственного тенанта актора (`resolveActorTenant`) — актор никогда не
  видит чужой тенант независимо от исхода authority-проверки (это уже было
  верно и остаётся).
- F5 (заодно, из тикета). 409-текст на дубль email смягчается: было "an
  account with that email already exists" — вводит в заблуждение при
  коллизии по `login` (Keycloak возвращает недифференцируемый 409 при клэше
  username ИЛИ email в некоторых конфигурациях/версиях; наш `EMAIL_TAKEN` код
  — это наша интерпретация KC-ответа, см. `admin-port.ts` "DEFAULT to
  EMAIL_TAKEN when the body is absent/unparseable/ambiguous"). Новый текст:
  "логин или email уже заняты" — честно отражает неопределённость источника
  409 без обещания диагноза, которого код не может дать.

## Non-functional

- N1. Zero new authority path (D-064/T-0658 discipline): переиспользуем
  `loadAdminContext` (уже импортирован в user-mgmt.ts) — НЕ пишем свой
  `SELECT … FROM employee` для проверки активности/роли.
- N2. Фикс мутационно доказуем красным: тест должен ПАДАТЬ на до-фикс коде
  (рядовой сотрудник получал 200) и проходить после.
- N3. `assertOrgObjectAuthority`'s operation type расширяется додполнительно
  `"read"` (аддитивно — существующие 8 вызовов с create/update/delete не
  ломаются; `Operation` в `grant-lattice.ts` УЖЕ включает `"read"`, так что
  ни латтис, ни `validateAdminDelegation` не меняются, меняется только
  сигнатура тонкой обёртки в seed-write.ts).
- N4. Никакого ослабления POST/PATCH — их код не трогается, кроме текста
  409 (F5).
- N5. Анти-кейс (D-064): без бизнес-слагов/кейс-контента в src/.

## Out of scope

- UI-скрытие контрола (не тронуто — это чисто серверный authority-гейт;
  фронт `screen-users.jsx` уже деградирует по T-0628 D4 отдельным путём).
- Пересмотр самого определения `mgmt_object:employee` гранта / его выдачи —
  вне охвата, это только read-гейт на существующий примитив.

## Acceptance criteria

- AC-1: владелец тенанта → `GET /api/users/accounts` 200 со списком (не
  регрессирует существующий FF-583-1/2 сценарий).
- AC-2: сотрудник с делегируемым `mgmt_object:employee` грантом (не
  владелец) → 200 со списком.
- AC-3: рядовой сотрудник без гранта и не владелец → 403 `NOT_OWNER`,
  список НЕ возвращается (мутационно доказано: тест красный без фикса).
- AC-4: cross-tenant изоляция не регрессирует (FF-583-5 остаётся зелёным
  без изменений).
- AC-5: 409 на дубль email/login несёт текст "логин или email уже заняты"
  (или эквивалент), не утверждает конкретно "email занят".
