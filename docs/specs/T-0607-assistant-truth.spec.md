# T-0607 — Пять дефектов честности контура ассистента (столпы 5-6)

> Живой факт приёмки 2026-07-03, тенант с DeepSeek-live: ассистент лжёт владельцу пять
> разными способами. Все пять — дефекты ЧЕСТНОСТИ (не новая функциональность): ответ
> не должен утверждать того, чего сервер не проверил, и не должен показывать
> пользователю то, чего проверять нельзя. Минимально-инвазивные фиксы, не переписывание.

## Контекст / инварианты, которые НЕ меняем

- Разделение ролей: `src/http/assistant.ts` (роут, sealed-по-Wave2) → `intentDispatch`
  (`assistant-intent.ts`) → `handleAnalyst` (read-only) / `handleConfigurator` (draft-only).
- PDP: серверный резолвер грантов (`getGrantsForSubject` / `makeIntersectionGrantSource`),
  READ-PDP T-0570 (`isRecordReadable` + composite ancestry).
- D-064 закон границы: НИКАКИХ кейс-строк (имена сущностей/тенантов) в `src/` — всё
  генерически; кейс — только в тестовых фикстурах.
- Честный-503 путь T-0573/T-0595 (`respondLlmUnavailable`, canonical `_ADMIN`/`_NON_ADMIN`
  константы) — не ослабляем; расширяем ту же дисциплину на «любую» ошибку диспатча (г).

## Дефекты и корни

### (а) Слепота к данным сущностей — столп 6
`src/server.ts::setAnalystPorts` НЕ передаёт `listRecords` (явный комментарий:
«listRecords: not wired here … Defaults to []»). Аналитик поэтому НИКОГДА не читает
реестровые данные — только S3-журнал. При пустом наборе `assistant-analyst.ts::buildDraftContext`
пишет в контекст LLM «Записей нет (либо доступ ограничен правами)», и LLM уверенно
рапортует владельцу «записей нет», хотя тот ВИДИТ раздел в UI. Корень: read-порт реестров
в правах актёра не подключён.

### (б) Недетерминированный гейт прав
`assistant-configurator.ts::hasAuthoringDraftGrant` проверяет ТОЛЬКО
`canOperateSystemAgent(intersectionGrants)`, но НЕ применяет owner-short-circuit, который
сам `canOperateSystemAgent`-doc (`capability-authz.ts` :121-124) объявляет
обязанностью caller'а («The owner short-circuit (isGenesisOwner) is applied by the
caller»). Пересечение (agent ∩ user) может «мигать» в зависимости от scope грантов
seeded-агента; владелец, чья власть идёт ОТ владения, а не от явного пересекающегося
гранта, получает детерминированный ЛОЖНЫЙ отказ `AUTHORING_ACCESS_DENIED_MESSAGE` + «в
пространстве нет администратора». Корень: серверный PDP-гейт не считает владельца
владельцем.

### (в) Ложный рапорт при упавших ops
Двойной дефект:
- (в1) `assistant.ts::executeApprovedOpAsDraft` (kind `edit_jsonschema_non_destructive`,
  и родственные `relate_application`/`author_binding`/`emit_form`/`generate_process`)
  требует сырой UUID реестра/приложения, а LLM в аргументах передаёт SLUG (у него нет
  каталога id↔slug↔name) → `invalid input syntax for type uuid: "<slug>"`. Планировщик
  `processToolCall` не валидирует форму идентификатора и штампует `✓ [DRAFT]`.
- (в2) Итоговый текст = `finalText` (LLM: «Все поля добавлены ✅») + оптимистичный
  changelog `processToolCall` (штампуется ДО реального DB-исполнения). Реальные падения
  добавляются лишь отдельной пометкой «⚠ Ошибки…», но исходный «✅» и оптимистичный
  журнал остаются — рапорт лжёт.

### (г) Тихие без-ответы
`handleAnalyst`→`runAnalyst` вызывает `ctx.llm.chat()` БЕЗ try/catch (в отличие от
`runConfiguratorLoop`, у которого catch есть). Любая неклассифицируемая ошибка LLM
(таймаут/сеть/малформед) или исключение между шагами 3 и 6 роутера пробрасывается →
router шлёт 500-конверт, но НИ ОДНО assistant-сообщение в тред не пишется → в треде
остаётся user-сообщение без ответа и без ошибки. Корень: нет гаранта «каждому user-message
— либо ответ, либо честная ошибка В ТРЕДЕ».

### (д) Утечка внутренностей
`assistant-analyst.ts::buildDraftContext` безусловно вклеивает в контекст LLM «Цикловое
время по активностям (S3 журнал)» и «Разбивка по типу актора» — внутреннюю телеметрию —
которую LLM затем предлагает пользователю как объяснение. Корень: контекст, который
нельзя показывать, предлагается как объяснение.

## Функциональные требования

- **F-a1**. Аналитик получает read-порт реестров в правах актёра: по каждому читаемому
  реестру — display_name/slug, число видимых записей, и до N примеров значений. Чтение
  идёт через тот же грант-резолвер (`getGrantsForSubject`) + READ-PDP (`isRecordReadable`)
  — НЕ сырой SQL в обход прав, НЕ шире прав пользователя.
- **F-a2**. Когда read-порт РЕАЛЬНО отработал и вернул 0 читаемых реестров/записей, текст
  честен: «в доступных вам разделах записей нет». Когда порт деградировал (honest-degrade,
  не смог прочитать), текст НЕ утверждает отсутствие данных как факт.
- **F-b1**. Решение о праве конфигурировать принимает СЕРВЕРНЫЙ PDP ДО/ВНЕ LLM:
  `hasAuthoringDraftGrant` применяет owner-short-circuit (владелец тенанта → всегда
  разрешено) поверх `canOperateSystemAgent(userGrants)`. Право резолвится на грантах
  ПОЛЬЗОВАТЕЛЯ (не на «мигающем» пересечении для целей допуска), детерминированно.
- **F-b2**. При отсутствии права — детерминированный серверный отказ (честный, указывает,
  к кому обратиться), LLM не решает и не переопределяет.
- **F-v1**. Исполнитель ops принимает идентификацию реестра/приложения, которую LLM реально
  знает: slug ИЛИ UUID. Резолв slug→UUID выполняется на стороне исполнителя (в правах
  тенанта) перед DB-записью. Не-резолвящийся идентификатор → honest op-error, НЕ 500.
- **F-v2**. Итоговый рапорт отражает РЕАЛЬНЫЕ исходы ops. Строки changelog для УПАВШИХ ops
  не подаются как успех; когда все/часть ops упали, «✅ добавлено»-формулировка не
  используется. Дубль-op (поле уже есть) отличается от «поля нет».
- **F-g1**. Каждый user-message получает либо ответ, либо честную ошибку В ТРЕДЕ:
  (i) `runAnalyst` оборачивает `ctx.llm.chat()` и возвращает канонический
  `canonicalizeLlmError`-текст вместо проброса; (ii) роут гарантирует запись
  assistant-сообщения с честной ошибкой в тред при любом неперехваченном сбое диспатча
  (в дополнение к HTTP-конверту), без утечки сырого текста.
- **F-d1**. S3-телеметрия (цикловое время, разбивка по актору) НЕ вклеивается в
  user-facing контекст аналитика по умолчанию; включается только когда запрос явно про
  процессную аналитику. Никакая внутренняя телеметрия не предлагается пользователю как
  объяснение по общему запросу о данных.

## Нефункциональные

- **N1**. D-064: без кейс-литералов в `src/` — `ci/checks/anti-case-lock.sh` зелёный.
- **N2**. Жаргон-гейт `ci/checks/ux/assistant-llm-message-jargon.sh` (+ `--self-test`)
  зелёный; новые user-facing тексты без жаргона денилиста.
- **N3**. Read-порт (а) не расширяет права: возвращает только то, что покрыто READ-грантом
  актёра; agent∩user-инвариант сохраняется; RLS/тенант-изоляция не ослаблена.
- **N4**. Owner-short-circuit НЕ расширяет права не-владельцам; не-владелец без гранта
  по-прежнему детерминированно отказан + capture-as-request не ломается.
- **N5**. Публичные типы (`HandlerResult`, `ConfiguratorResult`, `AnalystPorts`, `LlmPort`)
  структурно не ломаются; существующие тесты T-0573/T-0595/T-0599/T-0600 проходят.
- **N6**. Пул/кост: read-порт аналитика — O(1) резолв грантов + один bounded SELECT на
  реестр (cap на число реестров и примеров), не N+1 на запись сверх page.

## Вне скоупа (follow-up ADR)

- **O1**. Полноценный tool-use аналитик (LLM сам решает, какие реестры читать, пагинация,
  агрегации) — MVP-шаг здесь: детерминированный дайджест читаемых реестров. Остальное — FU.
- **O2**. LLM-роутер интента (замена keyword-`classifyIntent`) — не в скоупе; гейт прав (б)
  чинится независимо от способа роутинга.
- **O3**. Единый транзакционный «plan→execute→report» с откатом всего бандла при частичном
  провале — здесь только честный рапорт частичного исхода; атомарный бандл-execute — FU.
- **O4**. Резолв slug→UUID для generate_process.applicationId делаем; более глубокая
  нормализация всех аргументов всех tools под единую схему — FU.

## Критерии приёмки

- **AC-1** (а): unit — аналитик со stub read-портом, вернувшим дайджест реестра с записями,
  строит контекст, где присутствуют имя реестра и число записей; LLM-текст не содержит
  «записей нет». `verifiable_as: test`.
- **AC-2** (а): unit — при read-порте, вернувшем 0 читаемых реестров (отработал), контекст
  говорит об отсутствии данных в доступных разделах; при деградации порта (throw→honest
  fallback) контекст НЕ утверждает отсутствие как факт. `verifiable_as: test`.
- **AC-3** (а): live DB — реальный тенант с реестром и записью + READ-грантом актёра →
  `loadReadableRegistryDigest` возвращает count≥1 и sample; тот же вызов под вторым
  юзером без READ-гранта → 0 (права соблюдены). `verifiable_as: fitness`.
- **AC-4** (б): unit — `hasAuthoringDraftGrant` для владельца (isGenesisOwner=true) без
  явного пересекающегося гранта → true (owner-short-circuit); для не-владельца без
  гранта → false. `verifiable_as: test`.
- **AC-5** (б): live DB — реальный владелец тенанта → configurator-путь допущен
  детерминированно (нет `AUTHORING_ACCESS_DENIED_MESSAGE`); не-владелец без гранта →
  детерминированный отказ. `verifiable_as: fitness`.
- **AC-6** (в1): live DB — `edit_jsonschema_non_destructive` с `registryDefId`=SLUG
  существующего реестра → исполнитель резолвит slug→UUID и запись проходит (поле в схеме);
  несуществующий slug → honest op-error, НЕ исключение. `verifiable_as: fitness`.
- **AC-7** (в2): unit — при исходах ops [1 ok, 1 fail] итоговый рапорт помечает упавшую как
  упавшую и НЕ содержит «✅»-подтверждения для неё; changelog упавшей не подаётся как
  успех. `verifiable_as: test`.
- **AC-8** (г): unit — `runAnalyst` с LLM-портом, бросающим ошибку, возвращает
  `HandlerResult` с каноническим текстом (без проброса, без сырого тела). `verifiable_as: test`.
- **AC-9** (г): unit — роут-уровневый обработчик: при неперехваченном сбое диспатча в тред
  пишется assistant-сообщение с честной ошибкой (проверяется на извлечённой чистой
  функции построения ошибочного ответа). `verifiable_as: test`.
- **AC-10** (д): unit — по общему запросу о данных контекст аналитика НЕ содержит
  «Цикловое время»/«Разбивка по типу актора»; по явному запросу процессной аналитики —
  содержит. `verifiable_as: test`.
- **AC-11**: `bash ci/checks/ux/assistant-llm-message-jargon.sh` и `--self-test` зелёные.
  `verifiable_as: fitness`.
- **AC-12**: `bash ci/checks/anti-case-lock.sh` зелёный, без новых кейс-литералов.
  `verifiable_as: fitness`.
- **AC-13**: `npm test`, `npm run build`, `npm run fitness:db` зелёные (флейки
  doc-*/seed-pack изолированно). `verifiable_as: fitness`.
