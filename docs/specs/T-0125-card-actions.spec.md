# SPEC · T-0125 — Card actions как примитив формы

**Status:** ready (no escalation)
**Phase:** SPEC
**Task:** T-0125 (design, prio 50) — «[design] Card actions как примитив формы:
кнопка на карточке = операция с грантом + аудит-событием + привязкой к процессу
(terminate/message через REST движка); дефолтная карточка из объектной модели +
процесса, кастом поверх»
**Источники ТЗ:** `playbooks/choros-product-gap-map.md` §3а + envelope-строка
«Действия на карточке»; `playbooks/choros-reference-process-tel.md` §1 (кейс
«Прервать согласование», «Переназначить»).
**Решение фаундера (gap-map §3а):** блокер снят (terminate/message = REST движка);
дефолтная карточка из объектной модели + процесса, кастом поверх; примитив
описать в E9.

---

## 0. Что строим (одно предложение)

Дизайн-требования к примитиву **card action**: декларативная кнопка на карточке
записи = именованная операция над записью/инстансом процесса, авторизуемая
**существующим грантом через PDP** (не UI-флажком), исполняемая через уже
спроектированные пути (guarded transition T-0019/T-0021, engine-bridge
terminate/message T-0058, invoke-effect T-0024), с **аудит-событием** на каждое
действие (T-0016), где дефолтный набор действий **выводится из объектной модели
записи (T-0014) + статусной модели процесса**, а кастомные действия лежат
**поверх** в той же декларативной форме-схеме (Floor-1 T-0073 / модуль T-0079,
named-binding T-0072), версионируемой как конфиг (единица версионирования T-0082).

Это **дизайн-задача**: выход фазы — ADR с card-action-контрактом, который потом
кодируется. SPEC фиксирует ЧТО и оси требований, не КАК (механизм/слои — зона
architect).

## 1. Контекст и границы примитива

«Действия на карточке» — инвариант всех процессных классов (gap-map §2, ТЭЛ §4):
без него не собирается ни один маршрутный процесс (кейс «Прервать согласование»
в ТЭЛ §1 не выразим). Архитектурного блокера нет: в Flowable terminate
(удаление/прерывание инстанса) и message correlation доступны через REST движка
из кастомного UI; Java не пишем (external-task контракт, stack-and-fleet-ops.md).

**Существующие примитивы, которые card action ПЕРЕИСПОЛЬЗУЕТ (не достраивает):**

- **Closed Operation enum** (`src/core/grant-lattice.ts`): `read, create, update,
  delete, approve, transition, invoke`. Card action **отображается на
  существующую операцию**, а не вводит новый тип права (gap-map §4б:
  «Прервать» использует существующую операцию transition T-0019, не новый тип).
- **PDP** `resolveFor` (T-0021): авторизация действия = резолв гранта субъекта на
  (op, ResourceRef); guarded ops (approve/transition) идут через mutation-gateway
  (T-0028) — единственный writer.
- **Actor-event ledger T-0019**: guarded transition пишет actor_event-строку
  (SoD-трейл); статусная модель + защищённые переходы — там.
- **Audit floor T-0016** (open-vocab type): каждое действие = audit_event.
- **Engine bridge T-0058/T-0064/T-0067**: terminate/message инстанса процесса =
  REST движка через bridge; mutation-guard контракт FF-G3.
- **Invoke-effect T-0024**: побочные эффекты (внешний вызов) = op `invoke`.
- **Форма-схема Floor-1 T-0073 / модуль T-0079 / named-binding T-0072**: card
  action — элемент декларативной формы-схемы (gap-map §4б).
- **Единица версионирования T-0082 (E12.1)**: кастомизация формы (и её действий)
  версионируется внутри bundle, не вторым механизмом.

**Что card action ЯВНО НЕ ЕСТЬ (границы, не-цели):**

- НЕ конструктор UI общего вида / произвольная отчётная страница — это T-0121
  (two-floor report pages). Card action — типизированная кнопка на карточке
  записи, питающая закрытый набор семантик действия, а не свободный React-холст.
- НЕ новый тип права/новая authority-подсистема (один механизм прав, gap-map
  §4б инвариант 2).
- НЕ новая audit-таблица (переиспользуется T-0016 open-vocab).
- НЕ свой канал к движку (переиспользуется engine-bridge; Java не пишем).

## 2. Оси требований (для будущего ADR)

### Ось A — card action = именованная операция (грант через PDP, не UI-флажок)

Card action — декларативная сущность с (id/имя, целевая семантика действия,
отображение на Operation+ResourceRef, видимость-предикат). Видимость и
исполнимость кнопки **выводятся из PDP** (грант субъекта), а не из UI-конфига:
нет гранта → действие недоступно/невидимо тем же fail-closed путём, что и PDP.
«Кнопка есть в форме» ≠ «кнопка доступна»; авторизация — всегда resolveFor.

### Ось B — привязка к процессу (terminate/message инстанса; набор day-1)

Card action может адресовать **инстанс процесса**, привязанный к записи: семантика
действия — над движком через bridge (terminate инстанса; message correlation для
сигнала в работающий процесс) либо guarded transition статуса карточки (T-0019).
Day-1 закрытый набор семантик действия (с обоснованием каждой):

- **transition** — смена статуса карточки через guarded-transition gateway
  (T-0019/T-0021); напр. «перевести в Отказано».
- **terminate** — прерывание привязанного инстанса процесса через engine-bridge
  REST (deleteProcessInstance-семантика); снимает активные задачи инстанса.
- **message** — message correlation: сигнал в работающий инстанс (boundary/
  intermediate catch) через engine-bridge REST; напр. «вернуть на доработку».
- **invoke** — побочный эффект (T-0024), если действие = внешний вызов.

«Переназначить» (ТЭЛ §1) — частный случай: смена исполнителя задачи; SPEC требует,
чтобы ADR явно разместил его (transition/message + право «кто может переназначить»,
понимая что право переназначения дожимается в E7 — gap-map §2 «Переназначить» 🟡).

### Ось C — дефолтная карточка из объектной модели + статуса процесса

Дефолтный набор card actions **генерится** (не задаётся вручную) из:
(а) объектной модели записи (T-0014 registry_def / record_schema) — какие
операции над записью вообще определены; (б) статусной модели процесса/карточки
(T-0019) — какие переходы доступны из текущего статуса. SPEC фиксирует, что
именно входит в дефолт day-1 (минимум: доступные guarded transitions из текущего
статуса + terminate привязанного инстанса при наличии гранта). Дефолт не требует
ручного авторинга, чтобы базовая карточка ТЭЛ работала «из коробки».

### Ось D — кастом поверх (как хранится кастомизация)

Кастомные действия лежат **поверх** дефолта в той же декларативной форме-схеме
(Floor-1 T-0073 / модуль T-0079). SPEC фиксирует: (а) кастом-действие переопределяет/
добавляет, но **не может расширить** Operation enum и **не может обойти PDP**
(кастом всё равно отображается на существующую op + резолвится грантом);
(б) кастомизация **хранится и версионируется как конфиг** внутри единицы
версионирования bundle (T-0082, E12), а не отдельным механизмом; (в) ссылки
действия на поля/переменные схемы согласуются той же подсистемой согласованности,
что named-binding (T-0072) и report-page-dep (T-0121) — не четвёртый механизм
(gap-map §4б: не плодить три механизма «производный артефакт ↔ источник»).

### Ось E — аудит каждого действия

Каждое срабатывание card action (успех И отказ по правам) = строка audit_event
(T-0016, open-vocab type, не новая таблица) с actor, subject (запись/инстанс +
имя действия + параметры), via (грант), результат (executed/denied + reason),
привязка к инстансу процесса при наличии. Guarded transition дополнительно пишет
actor_event-строку (T-0019) — две таблицы, как зафиксировано в T-0019 §2.

### Ось F — граница MVP day-1 / Stage-2

ADR обязан явно провести границу. Ожидаемый day-1: контракт card action +
отображение на Operation+PDP + закрытый набор семантик (transition/terminate/
message/invoke) + генерация дефолта из объектной модели+статуса + кастом-поверх
в форме-схеме + версионирование как конфиг + аудит + прогон кейса «Прервать
согласование». Ожидаемый Stage-2 (с критерием разморозки): действия,
зависящие от агент-рантайма (E5.6–E5.10); сложные UI-холсты действий (граница с
T-0121). Точное содержимое границы — решение ADR, не SPEC.

## 3. Приёмочный прогон — кейс «Прервать согласование» (ТЭЛ §1)

SPEC требует, чтобы ADR прогнал кейс ТЭЛ §1 целиком и показал сборку из
примитивов без нового механизма:

- Кнопка «Прервать согласование» на карточке договора = card action с семантикой
  **terminate** (снять активные задачи инстанса через engine-bridge) +
  **transition** карточки в статус «Отказано» (guarded T-0019).
- Право = грант субъекта на соответствующую op над ResourceRef записи (PDP T-0021);
  нет гранта → кнопки нет/она отклоняется fail-closed.
- «Фиксирует причину» = параметр действия (записывается в audit_event subject /
  актор-событие), не свободный новый механизм.
- «Переводит в Отказано» + «уведомления участникам» — переход аудируется здесь;
  доставка уведомления = T-0120 (card action только эмитит событие/переход,
  доставку не реализует — граница).
- «Переназначить» = card action со сменой исполнителя (message/transition + право
  E7); ADR размещает явно.

## 4. Out of scope

- Реализация (DDL/код/эндпоинт/React-кнопка/wiring в shell) — последующие фазы;
  миграция (если нужна) по run-seam дисциплине, номер выбирает coder.
- Новый тип права / расширение Operation enum — запрещено (один механизм прав).
- Новая audit-таблица — переиспользуется T-0016 open-vocab.
- Свой канал к движку / Java-код движка — переиспользуется engine-bridge
  (external-task контракт).
- Отчётные/произвольные UI-страницы (T-0121 two-floor) — card action ≠ конструктор
  UI; граница проводится, не дублируется.
- Доставка уведомлений (T-0120) — card action эмитит событие/переход, доставку не
  реализует.
- Право «кто может переназначить/прервать» как самостоятельная модель — дожимается
  в E7; card action потребляет грант, не определяет ролевую модель.
- Дизайн самой формы-схемы (Floor-1 T-0073 / модуль T-0079 / named-binding T-0072 /
  версионирование T-0082) — переиспользуется как носитель card action, не
  переопределяется.
- Pooled-режим — дефолт silo; tenant-вывод (RLS T-0013) закладывается без ретрофита.

## 5. Трассируемость

Каждое FR покрыто ≥1 AC (см. contract). ADR обязан: (а) дать таблицу AC→design;
(б) прогнать кейс «Прервать согласование» (ТЭЛ §1) через примитив; (в) показать
ревью-гейту архитектора, что ни одно решение не вводит дублирующей подсистемы
(право/аудит/канал-к-движку/механизм-согласованности).

## 6. BLOCKING-вопросы

Нет. Направление фаундера зафиксировано в gap-map §3а (блокер снят, дефолт из
модели+процесса, кастом поверх); набор day-1-семантик, граница MVP/Stage-2 и
размещение «Переназначить» — проектные решения фазы DESIGN в рамках
зафиксированных инвариантов, не вопросы, меняющие объём продукта. Статус `ready`.
