# T-0127 — Genesis-инсталлятор + активационный ключ (SPEC)

> Фаза: SPEC (analyst). Задача: [design] Genesis-инсталлятор: терминальная
> self-service установка (скрипт, docker/БД сами, один конфиг) + активационный
> ключ = identity + entitlement контура для control-plane; red-line: без
> kill-switch в ядре.
> Статус спеки: **needs_founder** (BLOCKING — развилки лицензирования, см. §7).
> Источник решения фаундера: `playbooks/choros-product-gap-map.md` §3а
> («Genesis тенанта») + рабочая гипотеза по лицензированию (там же, абзац
> «Рабочая гипотеза по лицензированию»).

---

## 1. Что строим (одно предложение)

Терминальный self-service инсталлятор on-prem контура Choros — один скрипт,
который из чистой машины (с Docker) поднимает весь dev/prod-стек
(`docker-compose.yml` + overlay), сам мигрирует БД, сам сеет genesis-owner и
выдаёт работающий вход, — плюс **активационный ключ вендора** как
offline-проверяемая identity + entitlement контура для связи с control-plane
вендора, причём ключ **никогда не может погасить инсталляцию** (red-line: без
kill-switch в ядре, offline-режим всегда рабочий).

## 2. Контекст и опора (что уже есть, на чём стоим)

Инсталлятор — **обёртка над уже существующими примитивами**, не новый стек:

- `docker-compose.yml` (T-0053/54/58/61) — silo-стек: Postgres 16, Keycloak 25,
  Flowable 7, choros-app. Bring-up unattended, healthcheck'и на каждый сервис.
- `docker-compose.prod.yml` + `.env.prod.example` (T-0061) — prod-overlay с
  required-form `${VAR:?}` (compose ABORT при отсутствии секрета).
- `ops/docker-entrypoint.sh` + `migrations/run.mjs` (T-0061/53) — миграции
  прогоняются ДО старта app, идемпотентно, fail-closed.
- `migrations/026_genesis_owner_seed.sql` (T-0029) — **genesis-owner уже
  существует как сид**: employee `e-owner` + 17 делегируемых mgmt-грантов +
  подтверждённое назначение роли `tenant-owner`. Аддитивно, идемпотентно.
- Tenancy ADR (`docs/design/tenancy-and-delivery.md`) — silo-only сейчас;
  on-prem = вырожденный 1 тенант той же scoped-схемы; «Tenant onboarding-контракт:
  провижининг silo-ячейки (docker-compose)» — открытый пункт §12, который эта
  задача закрывает с продуктовой стороны.
- Fleet-ops ADR (`docs/design/stack-and-fleet-ops.md` §2) — **control-plane
  вендора = отдельный контур («мозг»)**; контур клиента связывается с ним только
  задачами/телеметрией. Активационный ключ — то, чем контур себя предъявляет
  этому control-plane.

**Граница задачи:** SPEC описывает ЧТО инсталлятор делает и какими свойствами
обладает (включая red-line offline). Механизм (язык скрипта, формат ключа,
крипто-подпись, способ распространения) — зона `architect` (T-0127 DESIGN).

## 3. Решения фаундера, которые НЕ переоткрываем

Из gap-map §3а — приняты, спека их кодирует, не оспаривает:

1. **Genesis тенанта = self-service установка из терминала**: скрипт установки,
   docker/база подтягиваются сами, возможно один конфиг.
2. **Активация ключом вендора по запросу** (on-prem; для SaaS неактуально).
3. **Опора при установке — документация** (страница + MCP, T-0134) — не часть
   этой задачи, но инсталлятор на неё ссылается.
4. **RED-LINE (рабочая гипотеза лицензирования, явно зафиксирована фаундером):**
   «система клиента **никогда** не встаёт из-за биллинга — kill-switch не
   делаем». Ключ = identity + entitlement, **проверяется при обращении к
   вендорским сервисам, не таймер в ядре**, не DRM. Истечение ключа =
   автономный режим (всё работает, никто не обслуживает).

## 4. Требования

### 4.1 Функциональные — инсталлятор (терминальный self-service)

- **F-1.** Один входной артефакт запуска: единственная команда из терминала
  (`./install.sh` или эквивалент) на чистой целевой машине с предустановленным
  Docker + docker compose поднимает весь стек до состояния «есть рабочий вход».
- **F-2.** Один конфиг: установка управляется ОДНИМ файлом конфигурации (имя
  контура/тенанта, секреты БД/Keycloak/Flowable, порты, активационный ключ).
  Инсталлятор генерирует его из шаблона (по образцу `.env.prod.example`) и
  заполняет недостающие секреты безопасными случайными значениями там, где
  значение не задано человеком.
- **F-3.** Docker/БД «сами»: инсталлятор сам поднимает Postgres/Keycloak/
  Flowable/app через compose, дожидается healthcheck'ей, сам прогоняет миграции
  (`run.mjs`) — никакого ручного SQL, никакого ручного `docker compose up`.
- **F-4.** Genesis-owner создаётся при установке: по завершении в контуре
  существует employee `e-owner` с ролью `tenant-owner` и полным набором
  делегируемых mgmt-грантов (миграция 026), и инсталлятор печатает человеку,
  как войти первым владельцем.
- **F-5.** Идемпотентный повторный прогон: повторный запуск на уже установленном
  контуре не ломает данные, не дублирует genesis-сид, не пересоздаёт секреты;
  доводит до целевого состояния и сообщает «уже установлено / достроено».
- **F-6.** Чёткий результат и провал: при успехе — структурированный итог
  (эндпоинт, как войти, версия, статус активации); при провале любого шага —
  понятное сообщение с упавшим шагом и кодом возврата ≠ 0, без частично
  поднятого «зелёного» контура, выдаваемого за рабочий.
- **F-7.** Предполётная проверка: до изменения системы инсталлятор проверяет
  предусловия (наличие Docker/compose, свободные порты по умолчанию
  55432/8180/9000/8082/3000, место на диске) и при невыполнении останавливается
  с инструкцией, ничего не подняв.

### 4.2 Функциональные — активационный ключ (identity + entitlement)

- **F-8.** Ключ как identity: ключ однозначно идентифицирует контур для
  control-plane вендора (кто этот контур — тенант/клиент/инсталляция),
  проверяемо вне БД клиента.
- **F-9.** Ключ как entitlement: ключ несёт перечень включённого сервисного
  слоя (обновления / агентное сопровождение / поддержка / срок) — то, что
  control-plane вендора предоставляет/отказывает при обращении.
- **F-10.** Установка без обязательной онлайн-активации: контур ставится и
  работает (genesis-owner, процессы, аудит, RLS) даже если ключ не введён или
  не подтверждён вендором (см. red-line offline ниже). Ключ вводится «по
  запросу» (gap-map: «активация ключом по запросу»).
- **F-11.** Ключ проверяется на границе обращения к вендорским сервисам
  (control-plane / обновления / агентное сопровождение), а НЕ в горячем пути
  ядра (PDP/процессы/аудит). Отсутствие/истечение ключа отключает только
  вендорский сервисный слой, не функции контура.

### 4.3 Нефункциональные / red-lines

- **NF-1 (RED-LINE — без kill-switch в ядре).** Ни один путь исполнения ядра
  (вход, PDP, процессы, таймеры, аудит, RLS) не имеет ветки, которая
  останавливает/деградирует работу контура по причине состояния активационного
  ключа (отсутствует/истёк/отозван/нет связи с control-plane). Это
  проверяется статически: в `src/` нет чтения статуса ключа/срока лицензии в
  коде ядра.
- **NF-2 (RED-LINE — offline-friendly).** Контур, у которого нет сетевой связи с
  control-plane вендора (и/или ключ истёк), полностью функционален для конечных
  пользователей: вход, процессы, аудит, права работают без деградации.
  Истечение ключа = «автономный режим» (никто не обслуживает), НЕ «не работает».
- **NF-3.** Секреты не коммитятся и не печатаются в открытом виде: инсталлятор
  следует существующей RL-1/RL-3 дисциплине (`.env.prod` в `.gitignore`,
  prod-секреты required-form, dev-дефолты только для dev).
- **NF-4.** Один артефакт, режим = конфигурация (tenancy ADR §7): инсталлятор не
  форкает `src/`; он параметризует существующий compose/overlay/миграции.
- **NF-5.** Целевая ОС и предусловия объявлены явно (см. BLOCKING Q-2 — без
  ответа фаундера множество поддерживаемых ОС не фиксируется).

### 4.4 Не-цели (out of scope)

- **OS-1.** Не DRM, не лицензионный enforcement в рантайме, не удалённое гашение
  — прямое следствие red-line.
- **OS-2.** Не SaaS-провижининг (pooled-ячейки, биллинг, квоты) — tenancy ADR:
  pooled отложен; ключ-активация «для SaaS неактуальна».
- **OS-3.** Не выпуск/жизненный цикл самих ключей на стороне вендора (генерация,
  ротация, отзыв, привязка к договору) — это control-plane вендора, отдельная
  задача; здесь — только потребление ключа контуром.
- **OS-4.** Не импорт данных клиента (оргструктура из 1С/AD, справочники) — это
  внедренческая петля (T-0129) и отдельные genesis/импорт-задачи (gap-map зона 1).
- **OS-5.** Не fleet control-plane сам по себе (Sentinel/Diagnost/Operator) —
  отдельный контур вендора (fleet-ops ADR); здесь только предъявление контура
  ему через ключ.
- **OS-6.** Не TLS/обратный прокси/доменная настройка (E0.7) — но инсталлятор
  не должен этому противоречить.
- **OS-7.** Юридическая форма лицензии, цена, доля ценности в сервисном слое —
  исследование №1, не эта задача (см. BLOCKING).

## 5. Связи и инварианты (для дизайнера)

- **Genesis-owner не переизобретать:** F-4 реализуется существующей миграцией
  026 (`e-owner` + tenant-owner + mgmt-гранты), запускаемой штатным `run.mjs`.
  Дизайн не должен вводить второй путь создания владельца.
- **Активация ≠ ядро:** граница проверки ключа совпадает с границей
  «контур ↔ control-plane вендора» из fleet-ops ADR §2 (связь между плоскостями
  только задачами/телеметрией). Ключ предъявляется на ЭТОЙ границе.
- **Инсталлятор = и апгрейдер?** Семантика silo-upgrade уже есть
  (`docker-entrypoint.sh` гоняет миграции при старте новой версии образа). См.
  BLOCKING Q-3: разворачивает ли тот же скрипт обновления, или апгрейд —
  отдельная ответственность fleet-ops (rolling_upgrade в каталоге ops).
- **Идемпотентность бесплатна на сидах:** миграция 026 и `run.mjs` уже
  идемпотентны (ON CONFLICT DO NOTHING, schema_migrations); F-5 наследует это,
  не строит заново.

## 6. Критерии приёмки (машинно-проверяемые)

| ID | Критерий | verifiable_as |
|---|---|---|
| AC-1 | Из чистой машины с Docker одна задокументированная команда инсталлятора доводит стек до состояния, где `GET /health` choros-app возвращает 200, без ручных шагов между запуском и готовностью. | test |
| AC-2 | После успешной установки в БД контура существует ровно один genesis-owner: `SELECT count(*) FROM choros.role_assignment WHERE source='genesis'` = 1, и employee `e-owner` имеет роль `tenant-owner` с делегируемыми mgmt-грантами (≥17 строк grant на роль tenant-owner). | test |
| AC-3 | Установка управляется одним конфиг-файлом: запуск без него генерирует/запрашивает один файл (по образцу `.env.prod.example`); все параметры контура берутся только оттуда (нет второго обязательного источника конфигурации). | test |
| AC-4 | Повторный запуск инсталлятора на установленном контуре завершается успехом (код 0), не меняет число строк genesis-сида и не перегенерирует уже записанные секреты (диф конфига пуст). | test |
| AC-5 | При недоступности предусловия (занят дефолтный порт, нет docker compose) инсталлятор завершается кодом ≠ 0 ДО любого `compose up`, печатает упавшее предусловие, и стек не поднят. | test |
| AC-6 | RED-LINE: статическая проверка — ни один файл в `src/` (ядро: вход/PDP/процессы/таймеры/аудит/RLS) не читает статус/срок активационного ключа и не имеет ветки остановки по нему (grep-fitness: запрет паттернов чтения license/activation-state в core-путях). | fitness |
| AC-7 | RED-LINE offline: контур, запущенный без активационного ключа (или с истёкшим) и без сетевой связи с control-plane, проходит сценарий «вход genesis-owner → создать процесс/задачу → запись в аудит» полностью успешно. | test |
| AC-8 | Активационный ключ проверяется только на границе обращения к вендорским сервисам: при отсутствии/истечении ключа возвращается ошибка/отказ ИМЕННО на вызове вендорского сервиса (обновления/control-plane/сопровождение), а пользовательские эндпоинты контура — 200. | test |
| AC-9 | Ключ несёт identity + entitlement: предъявленный control-plane ключ парсится в (идентификатор контура, перечень включённого сервисного слоя, срок); невалидный/подделанный ключ control-plane отвергает (подпись), но это НЕ влияет на работу контура (см. AC-7). | test |
| AC-10 | При успехе инсталлятор печатает структурированный итог с: эндпоинтом, как войти первым владельцем, версией, статусом активации (активен/автономный режим). | manual |
| AC-11 | Секреты: после установки `.env.prod`-эквивалент не в git (в `.gitignore`), prod-секреты в required-form, дефолтные креды не остаются в prod-режиме. | test |
| AC-12 | Установленный стек — тот же артефакт: инсталлятор не создаёт форк `src/`; он использует существующие `docker-compose.yml` + overlay + `migrations/run.mjs` (нет дублирующего стека в дереве инсталлятора). | fitness |

## 7. BLOCKING-вопросы (GT-1 — остановка до ответа фаундера)

Эти развилки меняют ДЕНЬГИ / прод-модель / объём поддерживаемого; роль не
угадывает (red-lines «правило при сомнении»). Решения фаундера из gap-map §3а
НЕ переоткрываются — ниже только то, что в gap-map явно оставлено открытым
(«проверить в исследовании №1») либо не зафиксировано.

- **Q-1 — формат entitlement и что именно гейтит ключ.** Рабочая гипотеза
  (perpetual-fallback hybrid) фиксирует, что ключ оплачивает «сервисный слой:
  обновления + агентное сопровождение + поддержка», и явно отправлена «проверить
  в исследовании №1». Точный перечень entitlement-флагов (что включается/
  выключается истечением: только обновления? только агент-сопровождение? доступ
  к каталогу шаблонов T-0133? MCP-доки T-0134?) определяет, какие границы кода
  должны спрашивать ключ. Меняет объём задачи и прод-модель → BLOCKING.

- **Q-2 — целевая ОС и форма поставки инсталлятора.** Множество поддерживаемых
  целевых ОС (только Linux x86_64? + ARM? оффлайн-инсталляция с предзагруженными
  образами для air-gapped РФ-клиента?) и форма (bash-скрипт vs подписанный
  бинарь vs образ) не зафиксированы. Меняет объём (матрица тестирования, оффлайн-
  поставка образов критична для регулируемого РФ-сегмента) → BLOCKING.

- **Q-3 — инсталлятор = апгрейдер, или апгрейд отдаём fleet-ops?** Тот же скрипт
  обновляет версию контура (pull нового образа + миграции), или обновления —
  ответственность вендорского fleet-ops (`rolling_upgrade` из каталога ops,
  canary→fleet)? Граница «self-service установка» vs «вендор обслуживает
  обновления по ключу» определяет, входит ли upgrade-путь в эту задачу и как он
  соотносится с entitlement (Q-1). Меняет объём и сервисную модель → BLOCKING.

- **Q-4 — самоидентификация контура при выпуске ключа.** Ключ должен быть
  identity контура — но identity присваивается ДО или ВО ВРЕМЯ установки?
  (Клиент запрашивает ключ заранее по идентификатору договора и вводит при
  установке; ИЛИ контур генерирует свой identity при установке и регистрируется
  в control-plane post-hoc.) Это определяет порядок «активация по запросу» и
  bootstrap доверия (как control-plane верит, что предъявивший ключ контур — тот
  самый). Затрагивает прод-процесс продажи/онбординга → BLOCKING.

> Статус остаётся **needs_founder**, пока Q-1…Q-4 не получат ответ и фаундер не
> подпишет (`approve_task`). Без этого DESIGN не стартует: ответы меняют, какие
> границы кода спрашивают ключ (Q-1), матрицу поставки (Q-2), объём
> upgrade-пути (Q-3) и онбординг-процесс (Q-4).
