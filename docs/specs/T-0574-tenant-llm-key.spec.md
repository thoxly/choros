# Спека: T-0574 — LLM-ключ тенанта в UI (BYO, secret-handle, довести до места)

Статус: спека · 2026-07-02. Волна: W1/LLM-ключ (карта примитивов 2026-07-02, F2/G1/G4).

> Владелец тенанта открывает настройки → вставляет свой ключ Anthropic (или иного
> провайдера) → видит «подключение работает» → ассистент/аналитик тенанта начинают
> отвечать. Ключ вводит ЧЕЛОВЕК; машина ключи не переносит, не логирует, не
> показывает обратно.

Связанные спеки (прочитаны): [ai-assistant-byo.spec.md](ai-assistant-byo.spec.md) §3.1
(F1 BYO per-tenant LLM), [agent-registry-and-llm-keys.spec.md](agent-registry-and-llm-keys.spec.md)
§5–7 (`app://` стор, `llm_connection` реестр, авторизация). Карта примитивов:
`demiurge/docs/choros-primitives-map-2026-07-02.md` §G1/F2/G4.

## 1. Зачем

Живьём (2026-07-02, приёмка глазами владельца тенанта): ассистент отвечает
«У вас нет прав…» (G1, отдельная причина — грант authoring_draft, **out of scope**
здесь, см. T-0573), аналитик падает сырым `{"error":{"code":"INTERNAL"}}` вместо
честного «подключите LLM» (G4). Обе жалобы — по касательной к этой задаче: даже
если оба бага починить, ответить нечем, потому что **у тенанта физически нет
привязанного рабочего LLM-ключа**, а разведка кода показывает, что довести
существующий ключ до ассистента сегодня из UI НЕЛЬЗЯ (см. §2).

## 2. Разведанное состояние кода (2026-07-02, до этой задачи)

Инфраструктура «вставить ключ» **уже построена** (задачи T-0474…T-0498, слой
E-AGENTS L2/L3/L5) — это не новая стройка с нуля, а недостающее последнее звено
цепи. Разведка:

1. **`web/src/screens/screen-llm-connections.jsx`** (`/llm-connections`, nav-config
   `id: "llm-connections"`, `status: "live"`) — полноценный экран: форма создания
   именованного профиля подключения (провайдер/эндпойнт/модель/цены), компонент
   `ConnectionKeyBinder` — write-only вставка API-ключа (`POST /api/llm-connections/:id/key`,
   шифрует на сервере в `app_secret`, никогда не отдаёт обратно — только
   `secret_bound:bool`), компонент `ConnectionTester` — реальная проверка
   (`POST /api/llm-connections/:id/test`, живой вызов провайдера, честный
   ok/error без утечки ключа, санитайзер `sanitizeProviderError`).
2. **Резолвер уже умеет читать новый реестр**: `src/db/agent-provision.ts:
   readConfiguredAgentLlmConfig` делает `LEFT JOIN choros.llm_connection lc ON
   lc.id = ac.llm_connection_id` и `COALESCE(lc.*, ac.llm_*)` — если у агента
   проставлен `agent_card.llm_connection_id`, ассистентский LLM-порт (`server.ts:
   makeLlmPortFactory` → `loadTenantLlmConfig`) подхватит ключ из нового
   `app://`-стора автоматически, БЕЗ доработки резолвера.
3. **Разрыв — привязка отсутствует для ассистента конкретно.** Три факта вместе:
   - `assistant-agent` создаётся в `src/core/register.ts` (онбординг тенанта)
     как `employee(kind='agent', slug='assistant-agent')` — **без строки
     `agent_card`** (подтверждено комментарием в `migrations/093_agent_taxonomy_employee_nullable.sql`:
     «assistant-agent is created per-tenant as an EMPLOYEE only… and writes NO
     agent_card row today»).
   - Единственный писатель `agent_card` — `src/db/agent-provision.ts:insertAgentRows`
     (flow найма РАБОЧЕГО агента, `agent-hire.ts`), не онбординг тенанта.
   - `GET /api/agents` (`src/http/agents-list.ts`, питает `screen-agents.jsx`,
     единственный UI с селектором `PUT /api/agents/:id/llm-connection`) селектит
     `FROM choros.agent_card ac` — без строки `agent_card` для `assistant-agent`
     он **не появляется в списке агентов** и его нельзя выбрать для привязки
     LLM-соединения.
   - Итог: владелец может создать профиль подключения и вставить ключ на
     `/llm-connections`, но **неоткуда** привязать этот профиль к ассистенту
     тенанта — цепочка UI physically обрывается на последнем шаге.
4. Старый параллельный экран `screen-llm-config.jsx` (T-0382, `/llm-config`) пишет
   `llm_endpoint`/`llm_model` напрямую в `agent_card` и требует отдельно вызвать
   `POST /api/agents/:id/secret-handle` со ССЫЛКОЙ (`env://`/`vault://`) — не
   принимает сырой ключ вообще (значит человеку без доступа к серверным env-переменным
   нечего туда вставить). Тот же баг адресуемости: без `agent_card` строки для
   assistant-agent этот путь тоже недостижим для него.
5. Провайдер Anthropic уже в `PROVIDER_PRESETS` экрана `/llm-connections`
   (endpoint `https://api.anthropic.com/v1`, дефолтная модель `claude-3-5-sonnet`) —
   пресет есть, но НЕ проверено, совместим ли `OpenAILlmPort`-адаптер с
   Anthropic-совместимым (не OpenAI-совместимым) API форматом запроса/ответа
   (см. blocking-вопрос BQ-1 в §7 — снят ниже до "не blocking", см. решение).

## 3. Что делает эта задача (в объёме)

Замыкает цепь «UI создать/вставить ключ» → «ассистент/аналитик реально отвечают»,
переиспользуя существующую инфраструктуру (§2 п.1–2), не проектируя новую:

- Обеспечить, чтобы у `assistant-agent` тенанта существовал адресуемый
  `agent_card`-подобный якорь, к которому можно привязать `llm_connection_id`
  (то есть закрыть разрыв §2 п.3) — КАК именно (backfill `agent_card` строки при
  онбординге / at-read лениво / расширение адресации `PUT /api/agents/:id/llm-connection`
  на employee-slug без agent_card) — решение архитектора/имплементации, НЕ этой
  спеки (analyst не проектирует, правило 3). Спека фиксирует НАБЛЮДАЕМЫЙ
  результат: после связывания ключ реально резолвится ассистентским LLM-портом.
- Экран (существующий `/llm-connections`, либо его доработка) даёт владельцу/
  админу тенанта: создать/выбрать профиль → вставить ключ → увидеть «ключ
  привязан» → нажать «Проверить подключение» → увидеть человекочитаемый
  результат → (если этот профиль ещё не назначен ассистенту) назначить его
  профилем ассистента одним действием из этого же экрана.
- Инструкция «куда вставить» — короткий недев-текст на экране: где взять ключ
  Anthropic, что вставить, что произойдёт после.
- Финальный интеграционный критерий: после сохранения рабочего ключа ассистент/
  аналитик тенанта отвечают в чате (не 503 «подключите LLM», не INTERNAL) —
  проверяется на живом стенде глазами (LIVE_PROOF, D-064).

## 4. Явно out of scope

- O1. Полная разблокировка ассистента правами (грант `authoring_draft`
  владельцу существующего тенанта, G1 «нет прав настраивать систему») — T-0573,
  отдельная задача. Эта спека делает ассистента способным ОТВЕЧАТЬ на ключе;
  способность НАСТРАИВАТЬ (конфигуратор draft-write) — там.
- O2. Починка G4 (аналитик отдаёт сырой `INTERNAL` вместо честного 503
  «подключите LLM» при отсутствии ключа) — самостоятельный баг обработки
  ошибок, не создание ключевой инфраструктуры. Если чинится попутно в той же
  волне — не возбраняется, но не является AC этой спеки. (Пограничный случай:
  AC-6 этой спеки требует, чтобы ПОСЛЕ привязки ключа ассистент отвечал —
  это не требует починки G4-ошибки для случая «ключ ЕСТЬ»; G4 актуален только
  для случая «ключа ещё нет», который вне AC здесь.)
- O3. Расширяемость провайдеров сверх Anthropic + уже существующих пресетов
  (DeepSeek/OpenAI/self-hosted/other) — зона architect (UX-детали списка
  провайдеров не blocking по правилу 1).
- O4. Потолки/лимиты/отсечка бюджета по ключу (L6 из agent-registry спеки,
  «Stage-2, позже») — не в этой задаче.
- O5. Привязка LLM-ключа к РАБОЧИМ (workforce) агентам процессов (F3 карты
  примитивов, «agentTask исполняется агентом») — существующий путь
  `screen-agents.jsx` + `PUT /api/agents/:id/llm-connection` уже это покрывает
  для агентов С `agent_card`; не трогается.
- O6. UI редактирования системного промта ассистента/аналитика (F3 в
  ai-assistant-byo.spec.md §3.3) — отдельная задача, не эта.
- O7. Ротация мастер-ключа шифрования (`APP_SECRET_MASTER_KEY`), `vault://`
  резолвер — вне scope (agent-registry спека §10, non-goals).

## 5. Функциональные требования

- F1. На экране подключений LLM тенанта (`/llm-connections` или его прямой
  преемник) владелец/админ тенанта может создать профиль подключения с
  провайдером Anthropic (минимум; прочие провайдеры уже пресечены — не
  регресс) и вставить в него сырой API-ключ через существующий write-only
  механизм (`ConnectionKeyBinder` / `POST /api/llm-connections/:id/key`).
- F2. После вставки ключа экран показывает факт наличия ключа (маска/статус
  «ключ привязан»), НЕ сам ключ, с возможностью заменить или удалить —
  используя существующий контракт (`secret_bound:bool` + `secret_handle_redacted`).
- F3. На экране есть управляемая кнопка/автопроверка «Проверить подключение»,
  которая делает РЕАЛЬНЫЙ вызов провайдера и показывает один из трёх
  человекочитаемых исходов: подключение работает (модель/латентность) / ключ
  неверный / нет сети или эндпойнт недоступен — без раскрытия ключа в любом из
  трёх случаев.
- F4. Владелец/админ тенанта может назначить один из созданных профилей
  подключения РАБОЧИМ профилем ассистента тенанта (в терминах спеки —
  «профиль по умолчанию для ассистента»/явная привязка) прямо из потока этого
  экрана, без хождения по отдельным недокументированным API.
- F5. После назначения рабочего профиля ассистенту и успешной проверки
  подключения (F3 = «работает»), ассистентский LLM-порт тенанта (композиция —
  `server.ts:makeLlmPortFactory`) резолвит именно этот ключ на следующем чат-
  запросе — БЕЗ рестарта сервера (существующий контракт: «каждый вызов читает
  свежую конфигурацию из БД», `agent-card-llm.ts` doc-комментарий).
- F6. На экране присутствует короткий человекочитаемый (не dev-жаргон) текст:
  где владелец берёт ключ Anthropic (console.anthropic.com → API Keys → Create
  Key) и что именно вставить в поле «API-ключ» на этой странице.
- F7. Экран корректно обрабатывает состояния: Empty (нет ни одного профиля
  подключения — понятный призыв к действию, НЕ пустой белый экран), Loading
  (список профилей грузится — видимый индикатор, не замороженный UI), Error
  (сеть/сервер недоступны при загрузке списка ИЛИ при сохранении ключа —
  явное сообщение с возможностью повторить, а не тихий сбой/белый экран).

## 6. Нефункциональные / инвариантные требования

- N1. Сырой API-ключ НИКОГДА не возвращается ни в одном HTTP-ответе API,
  включая: список профилей, статус, ответ на «Проверить подключение»,
  ответ на привязку профиля ассистенту, ошибки. Ни при каком статусе.
- N2. Сырой API-ключ НИКОГДА не пишется в лог/аудит (ни полностью, ни
  частично/фрагментом) — включая текст ошибки провайдера при неудачной
  проверке подключения (провайдерская ошибка обязана проходить через
  санитайзер, не эхом).
- N3. Сырой ключ не хранится в БД в открытом виде — только шифртекст
  (`app_secret.ciphertext`); чтение колонки шифртекста напрямую (`SELECT`)
  не даёт читаемого ключа.
- N4. Расшифровка ключа происходит ТОЛЬКО в памяти сервера в момент вызова
  провайдера (resolveSecret) — не логируется, не кэшируется на диск, не
  передаётся ни в какой другой сервис.
- N5. Автозаполнение полей формы (браузер autocomplete) для поля ключа
  отключено (поле помечено `autoComplete="off"`, тип `password`) — уже
  реализовано в `ConnectionKeyBinder`, не регресс.
- N6. Действия сохранить/заменить/удалить ключ и назначить профиль ассистенту
  доступны ТОЛЬКО владельцу/админу тенанта (существующий гейт
  `canConfigureLlmConnection` / `holdsAgentMgmtUpdate`); не-админ получает 403,
  не тихий отказ.
- N7. UX_REVIEW-фаза ОБЯЗАТЕЛЬНА (D-062) — это задача, трогающая `web/`.
  Design-steward проверяет соответствие OBLIK (`--chs-*` токены), доступность
  формы (label/aria на поле ключа), контраст статусных чипов (успех/ошибка).

## 7. Открытые вопросы

Нет blocking-вопросов. Один вопрос был снят до статуса non-blocking по правилу 1
(зона architect/design-steward, не аналитика):

- Совместимость `OpenAILlmPort`-адаптера с форматом Anthropic Messages API
  (Anthropic использует `/v1/messages` + заголовок `x-api-key`, не OpenAI-
  совместимый `/v1/chat/completions` + `Authorization: Bearer`) — если текущий
  адаптер шлёт OpenAI-shaped запрос на `https://api.anthropic.com/v1`,
  «Проверить подключение» для пресета Anthropic будет ЧЕСТНО возвращать
  ok:false (санитайзер уже покрывает 404/401 случаи) — это не ломает
  требование F3 (проверка обязана быть честной, а не притворяться), но может
  означать, что для реального успеха AC-6 (ассистент отвечает) первым рабочим
  провайдером на живом стенде технически станет DeepSeek/OpenAI-совместимый,
  а Anthropic-путь потребует либо анthropic-совместимый адаптер, либо
  OpenAI-совместимый прокси перед Anthropic — это ДИЗАЙН/IMPL решение
  (какой адаптер использовать/добавлять), не блокирует спеку: критерии ниже
  сформулированы провайдер-агностично («провайдер, реально работающий на
  момент приёмки»), с Anthropic как явно требуемым минимумом по формулировке
  задачи (см. AC-1, AC-6) — если протокольная несовместимость подтвердится на
  импле, это станет отдельным блокером импла, а не спеки.

## 8. Acceptance criteria (машинно-проверяемые)

- **AC-1.** На экране LLM-подключений форма создания профиля предлагает
  провайдер Anthropic как один из вариантов выбора; создание профиля с
  `provider: "anthropic"` возвращает `HTTP 201` и профиль появляется в списке
  `GET /api/llm-connections`. *(test)*
- **AC-2.** `POST /api/llm-connections/:id/key` с валидным телом `{api_key}`
  возвращает `HTTP 200 {secret_bound:true}`; последующий `GET /api/llm-connections`
  для этого профиля показывает `secret_bound:true` и НЕ содержит поля с сырым
  ключом ни под каким именем в теле ответа (проверка сериализованного JSON на
  отсутствие подстроки введённого тестового ключа). *(test)*
- **AC-3.** `POST /api/llm-connections/:id/test` на профиле с валидным рабочим
  ключом делает реальный вызов провайдера и возвращает `HTTP 200 {ok:true, model, latency_ms}`;
  на профиле с заведомо неверным ключом возвращает `HTTP 200 {ok:false, error}`
  с человекочитаемым `error`, НЕ содержащим ни фрагмента введённого ключа, ни
  сырого текста ошибки провайдера (санитайзер отработал). *(test)*
- **AC-4.** Существует управляемое из UI действие «назначить профиль
  ассистенту тенанта» (эндпоинт может переиспользовать/расширять
  `PUT /api/agents/:id/llm-connection` или эквивалент), которое для тенанта
  без `agent_card`-строки у `assistant-agent` НЕ возвращает 404
  `AGENT_NOT_FOUND` — привязка проходит и делает профиль резолвируемым
  для ассистентского LLM-порта этого тенанта. *(test)*
- **AC-5.** После выполнения AC-4 на профиле с привязанным рабочим ключом,
  прямой вызов серверной композиции резолвинга LLM-конфига тенанта
  (`loadTenantLlmConfig`/`readConfiguredAgentLlmConfig` или их наблюдаемый
  HTTP-эквивалент) возвращает non-null конфиг с тем самым `llm_endpoint`/
  `llm_model` профиля — без перезапуска процесса сервера между привязкой и
  проверкой. *(test)*
- **AC-6 (LIVE_PROOF, D-064).** На задеплоенном dev-стенде: владелец тенанта
  открывает `/llm-connections` → создаёт профиль с реальным рабочим ключом
  провайдера (Anthropic либо иной реально работающий на момент приёмки
  OpenAI-совместимый провайдер, см. §7) → «Проверить подключение» показывает
  «работает» → назначает профиль ассистенту → открывает чат ассистента/
  аналитика тенанта → отправляет сообщение → получает содержательный ответ
  модели (НЕ `503`, НЕ `{"error":{"code":"INTERNAL"}}`, НЕ таймаут) — весь
  путь проходится глазами через UI без API/SSH-обходов. *(manual)*
- **AC-7.** Ни один HTTP-ответ ни одного маршрута из семейства `/api/llm-connections/*`,
  `/api/agents/:id/llm-connection`, `/api/agents/:id/secret-handle*` не
  содержит сырого значения введённого тестового ключа — фиксируется
  автоматизированным грепом тела ВСЕХ ответов в интеграционном прогоне на
  известную тестовую строку ключа (fail, если найдено совпадение хоть в
  одном ответе). *(fitness)*
- **AC-8.** Ни одна запись в серверных логах / `audit_event` (payload) за
  время прогона AC-2/AC-3/AC-6 не содержит подстроки тестового ключа —
  автоматизированный грep журнала/аудита на известную тестовую строку после
  прогона (fail, если найдено). *(fitness)*
- **AC-9.** Экран LLM-подключений в состоянии Empty (0 профилей) показывает
  видимый Empty-компонент с призывом к действию (не пустое пространство/
  не бесконечный спиннер); в состоянии Loading — видимый индикатор загрузки;
  при HTTP-ошибке загрузки списка (сеть недоступна/сервер вернул 5xx) —
  видимый Error-компонент с возможностью повторить запрос, а не тихий
  белый экран/uncaught exception в консоли. *(test)*
- **AC-10.** Действие сохранить/заменить/удалить ключ и действие «назначить
  профиль ассистенту» под непривилегированным членом тенанта (не владелец,
  без гранта `llm_connection:configure`/`mgmt_object:agent update`)
  возвращают `HTTP 403`, а не тихо проходят или падают 500. *(test)*
- **AC-11.** На экране присутствует статический человекочитаемый блок текста
  (без dev-жаргона вроде «endpoint»/«handle»/«resolve») с инструкцией: где
  получить ключ Anthropic и что вставить в поле ключа на этой странице —
  проверяется наличием текстового узла с ожидаемыми ключевыми фразами в
  снапшоте/DOM экрана. *(test)*
- **AC-12.** UX_REVIEW-фаза пройдена (D-062): design-steward подтвердил
  соответствие изменённых/новых частей экрана токенам OBLIK (`--chs-*`),
  наличие `label`/`aria-*` на поле ввода ключа, читаемый контраст статусных
  чипов «ключ привязан»/«ключ не привязан»/«работает»/«ошибка». *(manual)*

## 9. Definition of done (справочно, не AC-поле)

DoD этой задачи = зелёный AC-1..AC-5, AC-7..AC-11 в CI/тестах + AC-6 и AC-12
пройдены глазами на задеплоенном dev-стенде (LIVE_PROOF, D-064) — карточка
не закрывается по одной лишь арифметике дочерних PR, а по факту «владелец
тенанта вставил ключ и получил ответ ассистента» (D-064 анти-кейс-дисциплина).
