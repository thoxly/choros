# SPEC T-0582 — Канбан-представление (второй вид в реестре T-0581)

> Фаза SPEC (analyst). Машинно-проверяемый контракт: `docs/specs/T-0582.spec.contract.json` (status `ready`).
> Столп 2 (интерфейс из блоков на данных). Кейс-доказательство: CRM «воронка сделок» — **тест-материал**, generic-примитив «канбан по SELECT-полю».
> Стоит на реестре представлений T-0581 (уже на dev): `list_view` с открытым `type`, диспетчер-валидатор `validateViewConfig(type, config, recordSchema)`, применение через `GET /api/records?view_id=`.

## 1. Что строим (одно предложение)

Второй вид представления в реестре T-0581 — **канбан-доска**: `type='kanban'`, колонки = enum-варианты выбранного SELECT-поля (`group_by_field`), карточки = записи набора, разложенные по значению этого поля; перенос карточки между колонками меняет значение поля записи через **существующий** `PUT /api/records/:id` (с его авторизацией — паритет T-0620), доступный мышью **и** с клавиатуры.

## 2. Контекст: что даёт T-0581 (фундамент, который переиспользуем)

- **Сущность `list_view`** (миграция 123) с `type text NOT NULL DEFAULT 'list'` — **открытый** дискриминатор, БЕЗ `CHECK (type IN …)` (специально, под канбан; гейт `view-registry-type-open.sh`).
- **Диспетчер-валидатор** `validateViewConfig(type, config, recordSchema)` в `src/core/view-config.ts` — `switch(type)` с ветвью `case 'list'` и `default:` (отказ неизвестного). Kanban = **новая ветка** `case 'kanban'`.
- **CRUD** `src/http/list-views.ts` — POST/GET/PUT/DELETE `/api/list-views`, tenant-scoped, RLS, привилегия конфигуратора на запись; принимает `type` из тела (по умолчанию `'list'`). Валидирует config через диспетчер против record_schema набора. **Не меняется.**
- **Применение** — `GET /api/records?view_id=<uuid>` в `src/http/records.ts` (RLS + sandbox + READ-PDP `isRecordReadable` + field-visibility + курсор-пагинация). **Не меняется.**
- **Общие структуры** `filters[] {field_key, op, value}` (AND) и `sort[] {field_key, dir}` + таблица `operatorsForFieldType`/`isServerSortable` — переиспользуются канбаном как есть.
- **Фронт**: панель «Настроить список» (`web/src/screens/list-view-panel.jsx`/`.js`) + `ViewSwitcher` + интеграция `screen-app-records.jsx` (переключает **режим отображения** по активному view). Канбан = второй режим отображения по `activeView.type === 'kanban'`.

## 3. Функциональные требования

- **FR-1** — Расширение реестра `type='kanban'` без изменения таблицы/CRUD/формы диспетчера: только новая ветка `validateViewConfig('kanban', …)` + новый вид config. DDL-миграции нет.
- **FR-2** — `config` канбана: `group_by_field` (ключ одного SELECT-поля, обязателен), `card_fields[]` (ключи полей на карточке, порядок = визуальный порядок), `columns_order[]` (опц. порядок enum-колонок), `filters[]`/`sort[]` (те же структуры T-0581; sort = порядок карточек внутри колонки).
- **FR-3** — Колонки = enum-варианты `group_by`-поля (`record_schema.properties[group_by_field].enum`, **данные тенанта**) + псевдо-колонка «Без значения» для записей с пустым/несоответствующим значением.
- **FR-4** — Карточки читаются тем же `GET /api/records?view_id=` (RLS+READ-PDP+field-visibility); группировка по `group_by` детерминирована; **нового прямого SQL-пути мимо PDP нет**.
- **FR-5** — Перенос A→B ставит `group_by`-поле = enum-значению B через **существующий** `PUT /api/records/:id { data }`; прямой путь смены поля мимо валидации/авторизации/аудита запрещён.
- **FR-6** — Авторизация переноса = паритет record-write (T-0620): tenant-membership + field write-mask guard. Отказ → та же ошибка, что при редактировании, + визуальный откат карточки.
- **FR-7** — PUT re-валидирует **весь** `data` и заменяет его целиком → перенос шлёт **полный** текущий `data` записи с изменённым только `group_by`-полем (карточка несёт полный `data` из GET).
- **FR-8** — Перенос доступен **с клавиатуры** (не drag-only): фокусируемый механизм смены колонки; ARIA-роли/подписи/счётчики на доске/колонках/карточках.
- **FR-9** — Канбан — второе представление: создаётся через ту же панель (расширенную выбором вида), переключается тем же `ViewSwitcher`; server-persisted; общий для тенанта.
- **FR-10** — Валидатор отклоняет 400: `group_by_field` нет / не ключ / не select; `card_fields` с несуществующим ключом; недопустимый оператор фильтра.

## 4. Нефункциональные требования

- **NF-1** — Расширение без изменения контракта T-0581 (одна ветка диспетчера + вид config + UI; ни новой таблицы, ни эндпоинта).
- **NF-2** — Переиспользование, не дублирование: filters/sort/операторы, record-write, GET /api/records, резолюция типов полей — существующие.
- **NF-3** — Никакого пути записи/чтения мимо PDP (перенос = PUT; чтение = GET /api/records).
- **NF-4** — Tenant-изоляция (наследует RLS `list_view` и `record`).
- **NF-5** — Анти-кейс (D-064): без «сделка/стадия/воронка/deal/stage/pipeline/CRM» как констант; колонки/имена — данные тенанта.
- **NF-6** — Пропорциональность: нативный HTML5 DnD + клавиатура, kit-примитивы + токены, без drag-библиотек.
- **NF-7** — UX-гейт G1-G7 (контраст, клавиатурная альтернатива drag, honest Empty/Loading/Error, видимые пустые колонки, без жаргона, слой не хардкод, откат при ошибке).
- **NF-8** — Безопасность обратной записи: enum-значение уходит bind-параметром обычного PUT; AJV+kanban-валидатор гарантируют допустимый enum.

## 5. Явные не-цели (out of scope)

Календарь/гант/страницы-из-блоков; группировка по не-select полям; WIP-лимиты/agg-по-колонке/swimlanes; ручной per-record порядок внутри колонки; правка не-group_by полей перетаскиванием; новая процессная семантика поверх record.update; per-user приватные kanban-view; AI-emit канбана; массовый перенос; виртуализация тысяч карточек. ## 6. Критерии приёмки

Машинно-проверяемые критерии AC-1…AC-14 — в `T-0582.spec.contract.json`. Ключевые:
- **AC-1/AC-11** — kanban создаётся в реестре без изменения таблицы/CRUD/диспетчера (T-0581 FF-VR-4 зелёный).
- **AC-2** — валидатор канбана отклоняет невалидный group_by/card_fields/оператор.
- **AC-3** — колонки ровно из enum + «Без значения»; ничего не теряется.
- **AC-4** — карточки через GET /api/records с READ-PDP/field-visibility; нет нового SQL-пути.
- **AC-5/AC-6/AC-12** — перенос = PUT с полным data, паритет-авторизация T-0620, откат при отказе, bind-параметр.
- **AC-7** — клавиатурный перенос + ARIA.
- **AC-8** — «Без значения»: очистка если не required, отказ если required.
- **AC-13** — UX honest-gate.
- **AC-14** — LIVE_PROOF на живом стенде (мышь И клавиатура, второй актор, отказ записи, READ-невидимость).

Нет.
