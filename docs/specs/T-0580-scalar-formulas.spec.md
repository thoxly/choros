# T-0580 — Скаляр-формулы в computed (spec)

Фаза: SPEC. Столп 3 (данные). Кейс-доказательство: **К4 «проекты — сроки/суммы из
договоров»**, шаг «в записи договора считается сумма-с-НДС и дедлайн = дата+срок без
правки платформы». Ветка: `task/T-0580-scalar-formulas` (от dev@9e7d9f7).

Источник: `docs/choros-primitives-map-2026-07-02.md` §A8 (скаляр-формулы = ⛔ блокер К4)
+ `choros-field-type-taxonomy-rethink` (computed без скаляр-формул — крупный гэп).

---

## 1. Проблема (разведка кода на ветке)

`computed` («Итог») сегодня — ТОЛЬКО агрегат. Тип реализован как единственная семантика
rollup:

- **Авторинг (web):** `apps-schema.js` FIELD_TYPES содержит `{ value: "computed",
  label: "Итог" }` (строка 121); `buildRecordSchema` при `type==="computed"` эмитит
  `{ type: "number", "x-rollup": { source, op, value_field, factor_field? } }`
  (строки 452–463). Редактор — `RollupConfigEditor` (`screen-app-schema.jsx:278`),
  показывается в `FieldRow` при `field.type === 'computed'` (строка 697).
- **Контракт (core):** `rollup-contract.ts` — `DerivedFieldSpec` — размеченное
  объединение `kind: "rollup" | "rollup-embedded" | "matrix-lookup"`; `extractDerivedFields`
  сканирует `record_schema.properties[*]` на `x-rollup`/`x-matrix-lookup`.
- **Вычисление (server):** derived-значения НЕ хранятся в `record.data` (доктрина PD-20);
  считаются на READ (`records.ts:1762`) через `computeAllDerivedFields` (`derived-fields-dao.ts:239`)
  и оверлеятся в переменные процесса на старте (`records.ts:892`, BUG-016 фикс T-0575).
  `computeEmbeddedRollup` (`rollup-contract.ts:439`) — ПОКАЗАТЕЛЬНЫЙ прецедент: ЧИСТЫЙ
  in-memory расчёт над `record.data`, зеркало клиентского `records-form.js::computeRollup`.
- **Схема-контракт:** `x-*` — generic-extension; `stripXExtensions` (`record-schema-validator.ts:174`)
  срезает ЛЮБОЙ `x-`-ключ перед AJV-compile — новый `x-formula` не требует whitelist-правки.

Следствие: «сумма с НДС» (`base * (1 + rate)`), «маржа» (`revenue − cost`), «дедлайн =
дата подписания + срок в днях» — не выражаются ничем в продукте. Только rollup-агрегат по
табличной части. Это блокер К4 и половины «вычисляемых» из ТЗ таксономии.

## 2. Что строим (одно предложение)

Второй флейвор поля `computed` — **скаляр-формула**: read-only выражение над скаляр-полями
ЭТОЙ ЖЕ записи (числа/деньги, дата+срок→дата, проценты как обычная арифметика), рядом с
rollup (не вместо), считаемое БЕЗОПАСНЫМ evaluator'ом (парсер→AST→обход дерева, НЕ
`eval`/`Function`), с редактором формулы в конструкторе полей.

## 3. Функциональные требования

- **FR-1 (флейвор рядом с rollup).** `computed` получает второй режим — «формула» —
  наравне с «агрегат» (rollup). Автор выбирает режим в редакторе поля; выбор «формула»
  эмитит `x-formula`, выбор «агрегат» — прежний `x-rollup`. Оба под одним `type:"computed"`.
  Никакой третий тип поля не вводится; единый рендерер readout сохраняется.

- **FR-2 (операнды).** Операнды формулы — ссылки на скаляр-поля ТОЙ ЖЕ записи по ключу поля:
  числовые (`number`/`integer`), денежные (`money`), даты (`date`), И read-only derived-поля
  той же записи (результат rollup/matrix-lookup — число). Строковые/булевы/relation/collection/
  multi-select поля НЕ являются валидными операндами v1 (см. O-2). Числовые литералы
  (включая проценты как `0.2`) — операнды.

- **FR-3 (операции v1, арифметика чисел/денег).** Поддерживаются бинарные `+ − * /`,
  унарный минус, скобки `( )`, стандартный приоритет (`* /` выше `+ −`), лево-ассоциативность.
  Операнды-деньги трактуются как числовой скаляр (T-0509: money = число+валюта; для арифметики
  берётся числовая величина). Результат числовой арифметики — число. Процент/НДС выражается
  пользователем в ДАННЫХ формулы (`base * 0.2`, `base * (1 + rate)` где `rate` — поле записи) —
  константа-процент НЕ живёт в платформенном коде (анти-кейс D-064, см. NF-2).

- **FR-4 (дата-арифметика, дата+срок→дата).** Поддерживаются ровно два дата-паттерна v1:
  (a) `date_field + N` и `date_field − N`, где `date_field` — поле типа `date`, `N` —
  числовое выражение (поле/литерал), интерпретируемое как **целое число дней** → результат
  типа **дата** (ISO `YYYY-MM-DD`); (b) `date_field_a − date_field_b`, разность двух дат →
  **число дней** (целое). Любая иная комбинация с датой (дата*число, дата+дата, дата/…) —
  ошибка типизации на этапе авторинга (см. FR-7). N в (a) усекается к целому (floor к нулю)
  — сложение календарных дней, без учёта времени (тип `date` — без времени, §apps-schema x-date).

- **FR-5 (когда пересчитывается).** Формульное поле пересчитывается в ТЕХ ЖЕ точках, что и
  rollup — оно проходит через тот же `DerivedFieldSpec`-контур: (a) на READ записи
  (`GET /api/records/:id` → добавляется в `derived`-map ответа), (b) при проекции переменных
  процесса на старте (on_create / explicit start) — оверлей derived перед построением
  переменных движка. Значение НИКОГДА не хранится в `record.data` (доктрина PD-20, как rollup).
  Клиентское превью в форме (records-form.js) — опционально (NF-4), не блокирует расчёт: сервер
  — источник правды.

- **FR-6 (циклы полей).** Формула, ссылающаяся на другое формульное поле, разрешена, ПОКА граф
  зависимостей формул ацикличен. Цикл (`a=f(b)`, `b=f(a)`, самоссылка `a=f(a)`, любой более
  длинный цикл) — ошибка авторинга: сохранение схемы с циклом отклоняется. На расчёте цикл
  НЕ достижим (схема уже провалидирована), но evaluator обязан иметь defense-in-depth предел
  глубины разрешения ссылок, чтобы никакая порча схемы не дала бесконечную рекурсию.

- **FR-7 (валидация формулы на авторинге).** При сохранении схемы формула
  ПАРСИТСЯ и ТИПИЗИРУЕТСЯ: (a) синтаксис (сбалансированные скобки, известные токены);
  (b) каждая ссылка указывает на существующее сиблинг-поле допустимого типа (FR-2); (c) типизация
  операций (число±число→число, дата±дни→дата, дата−дата→число, запрет остальных дата-комбинаций);
  (d) отсутствие цикла (FR-6); (e) лимиты (NF-5). Невалидная формула → сохранение схемы
  отклоняется с человекочитаемой ошибкой, привязанной к полю. Пустая формула у поля-формулы —
  ошибка (как rollup без source).

- **FR-8 (ошибки времени расчёта — деление на 0, null).** На расчёте (данные, не схема):
  - **null-операнд** (поле пусто/отсутствует): результат всей формулы — `null` (не 0, не
    исключение). Честная null-семантика как у rollup без дочерних (T-0575 NF: `null`, не `0`).
    Распространение: любой null-операнд в подвыражении → всё выражение null.
  - **деление на 0** (делитель = 0 или стал 0): результат — `null` (не `Infinity`, не throw,
    не `NaN`). Тихая деградация в null — та же дисциплина, что `derived-fields-dao` (ошибка
    расчёта одного поля → `null`, не крэш записи).
  - **нечисловой операнд** (порча данных, поле содержит не-число там, где ждём число): →
    `null` для всего выражения.
  - Расчёт одного формульного поля НИКОГДА не роняет чтение записи или старт процесса
    (изоляция как у существующего derived-precompute SAVEPOINT, `records.ts:883`).

- **FR-9 (совместимость).** Существующие `computed`-поля (rollup) продолжают работать без
  изменений: их `x-rollup` парсится и считается как раньше; форма/список/переменные процесса
  видят те же значения. Формула — чисто аддитивное расширение (`x-formula`, новый `kind:"formula"`).

## 4. Нефункциональные требования

- **NF-1 (безопасный evaluator, инъекция = P0).** Вычисление формулы НЕ использует
  `eval`, `new Function`, `Function(...)`, шаблонные-строки-в-исполнение, `vm`, динамический
  `import()`, доступ к глобалам/прототипам. Только ПАРСЕР→AST→обход дерева над закрытым
  набором узлов (число, ссылка-на-поле, бинарная/унарная операция). Ни один путь данных
  пользователя не превращается в исполняемый код.

- **NF-2 (анти-кейс D-064, закон границы).** Диф задачи НЕ добавляет в `src/` (и `web/src/`)
  кейс-специфичных бизнес-констант: ставка НДС «0.2»/«20», имена полей демо-кейса,
  пороги. Платформа даёт ОПЕРАТОРЫ и грамматику; проценты/ставки/сроки живут в формуле
  пользователя (данные тенанта). Анти-кейс baseline (`anti-case-lock.sh`) не растёт.

- **NF-3 (чистота ядра).** Парсер+evaluator живут в `src/core/` и ЧИСТЫ: без `pg`, `node:*`,
  `process.env`, сети, БД — зеркало дисциплины `rollup-contract.ts` (`no-env-in-core.sh`,
  `pg-single-dep.sh`). Zero-dep: НЕ добавляется npm-зависимость (только `ajv`/`pg` — `package.json`).

- **NF-4 (сервер — источник правды; фронт-превью опционально).** Каноническое значение
  формулы считает сервер (тот же derived-контур). Клиентский расчёт в форме — превью для UX,
  считается ТЕМ ЖЕ алгоритмом (или отсутствует в v1 без потери корректности). При расхождении
  прав правды — сервер. (Урок BUG-016: UI-число ≠ движковое число — не допустить снова.)

- **NF-5 (лимиты evaluator — DoS).** Формула имеет жёсткие лимиты, проверяемые при авторинге
  И при расчёте (defense-in-depth): длина исходной строки ≤ 500 символов; глубина AST ≤ 32;
  число ссылок-на-поля ≤ 32 на формулу. Превышение при авторинге → отказ сохранения; при
  расчёте (порча) → `null`, не исполнение.

- **NF-6 (детерминизм/без побочек).** Evaluator детерминирован и без побочных эффектов: не
  читает часы (`today()`/`now()` НЕ в v1 — см. O-1), не пишет, не сети, чистая функция от
  (AST, record.data + derived). Один и тот же вход → один и тот же выход.

- **NF-7 (UX-гейт).** Редактор формулы в `web/` соблюдает G1–G7 (kit-токены, контраст обеих
  тем, честные Empty/Loading/Error, без dev-жаргона: «формула», «поле», не «AST/eval»),
  как соседний `RollupConfigEditor`.

## 5. Вне области (out of scope)

- **O-1.** Функции-встроенки в грамматике: `today()`, `now()`, `round()`, `min()/max()`,
  `if()`, конкатенация строк, агрегаты. v1 — только арифметика скаляров + два дата-паттерна.
  (Динамический `today()` нарушил бы детерминизм NF-6; агрегаты — это rollup.)
- **O-2.** Операнды-строки/булевы/relation/multi-select/collection; форматирование результата
  (валюта/локаль вывода). Формула v1 оперирует числами и датами.
- **O-3.** Кросс-записевые формулы (значения из связанных записей) — это rollup/relation-контур,
  не скаляр-формула. Формула ссылается ТОЛЬКО на поля своей записи.
- **O-4.** Формула, ПИШУЩАЯ в `record.data` (materialized/сохранённое вычисляемое). v1 — строго
  read-only derived, как rollup (доктрина PD-20).
- **O-5.** Автодополнение имён полей в редакторе — nice-to-have (не золотим): если недорого —
  выпадающий список сиблинг-полей для вставки; сама формула валидируется в любом случае.
- **O-6.** Единицы времени кроме дней в дата-арифметике (месяцы/годы/рабочие дни/часы) —
  v1 только целые календарные дни.
- **O-7.** Формула как условие шлюза / в DMN — отдельный контур (условия уже есть, T-0524);
  задача только про computed-поле записи.

## 7. Блокирующие вопросы фаундеру (GT-1)

Нет BLOCKING-вопросов. Границы v1 однозначны из карты примитивов §A8 и таксономии; спорные
расширения (функции, `today()`, кросс-записевость, materialization) вынесены в out-of-scope
как явные не-цели v1 и НЕ меняют объём поведения ядра задачи. Дата-семантика (дни, floor,
без времени) выведена из существующего хранения `date` (`x-date`, ISO без времени). Решение
«сервер — источник правды, фронт-превью опционально» следует из урока BUG-016 и доктрины PD-20,
не требует продуктового вердикта.
