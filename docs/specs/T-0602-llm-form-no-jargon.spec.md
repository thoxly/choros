# T-0602 — форма «Новый профиль» (LLM-соединения): убрать невозможное поле, честная инструкция, честные подписи карточек

Источник: живой фидбек владельца тенанта на приёмке — «нету никакого env для
пользователя» (он открыл форму «Новый профиль» на `/llm-connections`, увидел
поле «Секрет-хэндл (ссылка, не ключ)» с плейсхолдером `env://DEEPSEEK_API_KEY`
и не понял, что это и откуда это взять — на стенде тенанта такого понятия нет).

## Контекст: почему поле не просто «непонятное», а нерабочее

Разведка кода (`src/server.ts:203-217`, T-0413) подтверждает: `env://`-хэндл,
введённый через `POST /api/llm-connections` (`secret_handle`), **безусловно
отклоняется** при попытке реального резолва в тенантском пути —
`makeLlmPortFactory` бросает `[T-0413] env:// handles are system-only and may
not be used as tenant secret handles`. Единственное, что видит владелец —
либо честная ошибка теста подключения («Эта ссылка-хэндл (env://) недоступна
как ключ тенанта.», `src/http/llm-connection-test.ts:183-185`), либо тихий
dormant/503 в реальном вызове ассистента (T-0600 убрал env-fallback, замена
на честный 503, но профиль всё равно никогда не заработает).

`vault://` не отклоняется по shape, но резолвер для него **не существует**:
`src/http/secret-handle.ts` документирует `resolveSecret` порт как
объявленный, но НИКОГДА не вызываемый (Stage-2). Ни один production
call-site не резолвит `vault://` для тенанта.

Единственный ЖИВОЙ путь получения ключа — `app://`, через
«Вставить API-ключ» (`ConnectionKeyBinder`, `POST /api/llm-connections/:id/key`,
шифрование AES-256-GCM на сервере, T-0476). Он уже существует на карточке
профиля, но форма СОЗДАНИЯ профиля не указывает на него и вместо этого
выпячивает мёртвое для тенанта поле.

**Вывод (решается в DESIGN/ADR):** секрет-хэндл-поле в форме СОЗДАНИЯ профиля
не может быть «продвинутым, но легитимным» — единственные схемы, которые оно
принимает (`env://`, `vault://`), либо отклоняются, либо не резолвятся ни при
каких обстоятельствах на тенантском пути. Advanced-collapse не спасает
ситуацию — он лишь спрячет ловушку чуть глубже. Поле удаляется из формы
создания.

## FR-1 — форма «Новый профиль»: убрать секрет-хэндл-поле, поток = создать → вставить ключ

**Файл:** `web/src/screens/screen-llm-connections.jsx` (форма `onCreate`,
блок `~751-799` до правки).

**Сейчас:** форма содержит поле «Секрет-хэндл (ссылка, не ключ)»
(`secretHandle` state), плейсхолдер `env://DEEPSEEK_API_KEY`, hint
«ССЫЛКА на секрет (env:// / vault:// / app://)». `secretHandle` также
используется для honest-статуса после создания (`createOkNoKey`).

**Должно быть:**
- Поле «Секрет-хэндл» убирается из формы «Новый профиль» целиком (JSX +
  `secretHandle`/`setSecretHandle` state, `fieldErrors.secretHandle`
  client-валидация, `body.secret_handle` в `onCreate`).
- `createOkNoKey` логика упрощается: после успешного `POST` секрет-хэндл
  никогда не передаётся с формы → баннер успеха ВСЕГДА показывает следующий
  шаг («Теперь вставьте API-ключ, чтобы он заработал.») — эта ветка
  перестаёт быть условной (createOkNoKey всегда true после создания через
  эту форму), но state сохраняется как явный признак «этот профиль только
  что создан без ключа», чтобы не разрастаться в булеву закладку без имени.
- Описание формы (`descStyle` абзац) переписывается: «Именованное
  подключение к LLM (провайдер, эндпойнт, модель, цены). После создания
  профиля вставьте API-ключ на его карточке ниже.» — без упоминания
  секрет-хэндла/ссылки.
- Серверный контракт `POST /api/llm-connections` НЕ меняется:
  `secret_handle` остаётся опциональным полем API (обратная совместимость,
  скрипты/сиды/будущий admin-путь могут продолжать его слать) — эта задача
  убирает ТОЛЬКО клиентскую форму создания, не серверную валидацию/DAO/схему
  (OOS-1).

## FR-2 — инструкция сверху экрана: провайдер-нейтральный путь пользователя

**Файл:** `web/src/screens/screen-llm-connections.jsx:728-741` (блок
«Откуда взять ключ и что с ним сделать»).

**Сейчас:** текст жёстко привязан к Anthropic («Зайдите на
console.anthropic.com, откройте раздел «API Keys»…») — форма же предлагает
DeepSeek/OpenAI/Anthropic/self-hosted/другой на равных, дефолт (Anthropic)
задан только текущим `useState`, при смене провайдера инструкция не
меняется и вводит в заблуждение пользователей DeepSeek/OpenAI.

**Должно быть:** `PROVIDER_PRESETS` получает новое опциональное поле
`consoleHint: string | null` — короткая, человеческая подсказка «где взять
ключ» для каждого провайдера с реальным консольным URL (DeepSeek →
`platform.deepseek.com`, OpenAI → `platform.openai.com/api-keys`, Anthropic →
`console.anthropic.com`; self-hosted/другой → `consoleHint: null`, для них
подсказка не показывает конкретный домен). Инструкция становится
ДИНАМИЧЕСКОЙ: рендерит `consoleHint` ВЫБРАННОГО В ФОРМЕ провайдера (`provider`
state), с честным нейтральным фолбэком, когда `consoleHint` отсутствует
(self-hosted/другой) — «У вашего провайдера должен быть раздел с API-ключами
в личном кабинете.» Остаток инструкции (создать профиль → вставить ключ →
проверить подключение → назначить ассистенту) — провайдер-агностичный,
переписывается один раз без привязки к конкретному провайдеру.

## FR-3 — карточки профилей: человеческая подпись вместо сырого `app://…`

**Файл:** `web/src/screens/screen-llm-connections.jsx` (блок рендера карточки,
`secret_handle_redacted`, `~904-912` до правки).

**Сейчас:** карточка рендерит чип «ключ привязан»/«ключ не привязан»
(honest, из T-0597) плюс — если есть — вторую строку с сырым редактированным
хэндлом (`<span style={monoStyle}>{c.secret_handle_redacted}</span>`, т.е.
буквально текст вида `app://...` или `env://...`).

**Должно быть:** сырой `secret_handle_redacted` заменяется человеческой
подписью, определяемой по схеме префикса (сервер уже отдаёт редактированную
строку вида `"app://..."`/`"env://..."`/`"vault://..."` — схема остаётся
видна в первых символах, парсим её на клиенте БЕЗ нового серверного поля):
  - `app://` → «Ключ зашифрован и привязан»;
  - `env://` → «Ключ сервера (настроен оператором)»;
  - `vault://` → «Ключ из внешнего хранилища (настроено оператором)»;
  - иная/неизвестная схема или `null` → ничего не рендерим (чипа
    «ключ привязан»/«ключ не привязан» уже достаточно, лишняя строка не
    нужна).
Сырой `secret_handle_redacted` можно оставить ВТОРОЙ, мелкой строкой
(`--chs-text-xs`, `--chs-color-text-muted`) — не основной, только как
техническая деталь для тех, кому нужна точность (не жаргон в ПЕРВОЙ строке).

## FR-4 — дефолты провайдер↔модель↔эндпойнт: консистентность (без изменений, если уже верно)

**Файл:** `web/src/screens/screen-llm-connections.jsx:32-42`
(`PROVIDER_PRESETS`), `:614-629` (`onProviderChange`).

**Разведка:** `onProviderChange` уже переустанавливает `endpoint`+`model`+
цены+валюту ИЗ ТОГО ЖЕ найденного пресета при смене `provider` — единственный
источник данных один и тот же массив `PROVIDER_PRESETS`, нет расхождения
провайдер↔модель↔эндпойнт (T-0597 уже свело начальный state формы к
`ANTHROPIC_PRESET`, тот же массив). Плейсхолдер имени «DeepSeek (прод)»
(`Field label="Имя профиля" placeholder=...`) — это ТОЛЬКО placeholder text
поля имени (не зависит от провайдера, не подставляется как значение) — не
дефолт-рассинхрон, а иллюстративный пример синтаксиса имени; после смены
провайдера на Anthropic поле остаётся пустым (placeholder — не value),
пользователь вводит своё имя сам. **Вывод: изменений не требуется** (задача
явно допускает «если уже так — не трогай»); FR-4 в этой спеке фиксирует
разведку, а не правку.

## Границы (out of scope)

- OOS-1: серверный контракт `POST /api/llm-connections` (включая
  `secret_handle` как опциональное поле, shape-guard, DAO, миграция 094) —
  не меняется. Убирается только клиентская форма создания.
- OOS-2: `agent_card.llm_secret_handle` / `/api/agents/:id/secret-handle`
  (`screen-agents.jsx`, T-0025) — отдельный, самостоятельный контур
  (админ-путь привязки хэндла к employee-агенту напрямую, вне LLM-соединений),
  не трогается этой задачей.
- OOS-3: `screen-llm-config.jsx` (T-0382, отдельный устаревший экран
  BYO-настройки с собственным `PROVIDER_PRESETS`/`handleHint`) — вне периметра
  (задача называет конкретно `screen-llm-connections.jsx`).
- OOS-4: серверная классификация ошибок (`sanitizeProviderError`,
  `llm-connection-test.ts`) — не меняется; текст «Эта ссылка-хэндл (env://)
  недоступна как ключ тенанта.» остаётся (защита на случай, если хэндл
  всё же попал в БД любым другим путём, например через будущий admin-API).
- OOS-5: `ConnectionKeyBinder` (форма «Вставить API-ключ») — логика не
  меняется, она уже честная (T-0476/T-0597); эта задача только делает её
  ЕДИНСТВЕННЫМ путём, на который форма создания указывает.

## Acceptance criteria

- AC-1: форма «Новый профиль» не содержит поля с меткой «Секрет-хэндл» —
  ни JSX-узла, ни связанного `secretHandle`/`setSecretHandle` state в
  create-форме.
- AC-2: `onCreate` не отправляет `secret_handle` в теле запроса (поле
  исключено из тела POST).
- AC-3: успех-баннер после создания профиля через эту форму всегда включает
  честный next-step («Теперь вставьте API-ключ, чтобы он заработал.») —
  секрет-хэндл с формы прийти больше не может, веточное условие снимается.
- AC-4: описание формы не упоминает «секрет-хэндл»/«ссылку»/«env://»/
  «vault://».
- AC-5: инструкция «Откуда взять ключ» отображает подсказку, зависящую от
  ВЫБРАННОГО в форме провайдера (меняется при смене `provider`), с честным
  нейтральным текстом для self-hosted/другой (без утверждения конкретного
  домена).
- AC-6: `PROVIDER_PRESETS` расширен полем `consoleHint` для всех пяти
  провайдеров (null для self-hosted/other).
- AC-7: карточка профиля рендерит человеческую подпись
  (app→«Ключ зашифрован и привязан», env→«Ключ сервера (настроен
  оператором)», vault→«Ключ из внешнего хранилища (настроено оператором)»)
  вместо сырого `secret_handle_redacted` как ПЕРВОЙ строки; сырой хэндл
  (если оставлен) — только вторично, мелким текстом.
- AC-8: жаргон-гейт (`ux-g5-jargon-denylist.sh`) не даёт новых находок в
  видимом тексте (`env://`/`vault://`/`handle`/«хэндл» не должны появляться
  в пользовательском тексте формы/карточки/инструкции — только в комментариях
  и JS-идентификаторах, вне текста, который видит пользователь).
- AC-9: `bash ci/checks/ux/ux-g8-scroll-reachable.sh` зелёный (не
  затрагивается — уже проходит на уровне шелла, T-0601).
- AC-10: `bash ci/checks/anti-case-lock.sh` зелёный, без новых кейс-литералов.
- AC-11: существующие тесты `screen-llm-connections.test.jsx` /
  `screen-llm-connections.states.test.jsx` / `screen-llm-connections.a11y.test.jsx`,
  не относящиеся к убранному полю, проходят без регресса (AssistantBinder,
  ConnectionTester, ConnectionKeyBinder, Loading/Error/Empty states — не
  затрагиваются этой задачей). Тест AC-11 (T-0574) instruction-block
  обновляется под провайдер-нейтральный/динамический текст (ссылка на
  «console.anthropic.com» перестаёт быть безусловной).
- AC-12: `npm run build` (root) и `cd web && npm run build` зелёные.
- AC-13: `cd web && npx vitest run` зелёный, без новых упавших тестов.
