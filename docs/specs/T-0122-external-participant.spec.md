**Status:** ready
**Phase:** SPEC (для дизайн-задачи — выход фазы = требования к будущему ADR, не сам ADR)
**Date:** 2026-06-11
**Task:** T-0122 (product=choros, type=design, prio 55)
**spec_ref:** `playbooks/choros-product-gap-map.md` §2 (envelope: «Внешний участник»), §3а (решение фаундера); `playbooks/choros-reference-process-tel.md` §5 (QR-кейс) + §1/§2 (контрагент как внешняя сторона).
**Решение фаундера (данность, НЕ развилка):**
- **Внешний участник как ДАННЫЕ = запись в справочнике** (gap-map §3а): контрагент/посетитель моделируется записью реестра (`record`, T-0014), **НЕ учётной записью Keycloak**, не tenant-пользователем, не ролью.
- **Канал = примитив «внешняя поверхность»** (gap-map §2, §3а): **токенизированный доступ без учётки** к **узкому срезу** действий (скачать / проверить / загрузить), **с аудитом**.
- Фаундер отметил неуверенность в направлении — **проверять на QR-кейсе** (ТЭЛ §5). Это требование к ADR (см. AC-15), не открытая развилка объёма.

**Опора (НЕ противоречить):**

- `docs/design/T-0014-registry-model.adr.md` — namespace Application→Registry→Record; запись = grant-target; внешний участник = запись.
- `docs/design/T-0015-object-handles.adr.md` — непрозрачные ручки; внешняя ссылка несёт handle/токен, не данные.
- `docs/design/T-0018-grant-authority.adr.md` — единая grant-алгебра (closed scope-lattice); «нет второго permission-подсистемы»; грант **производен** и **сужается** монотонно (write-time subset gate); грант привязан к роли-принципалу, имеет окно валидности `valid_from/valid_until` (TTL = снятие capability), `delegable`.
- `docs/design/T-0021-grant-resolver-pdp.adr.md` — единый PDP-чокпойнт `grant-resolver`; права выводятся из grant-строк, **action-time** (revoke→deny между mint и resolve), **fail-closed**; reason-union `"no_grant" | "cross_tenant" | "not_found"`; человек≡агент — один путь проекции.
- `docs/design/T-0016-audit-floor.adr.md` — append-only per-tenant hash-chained `audit_event`; `actor`/`subject`/`via`/`scope`/`payload`; open-vocab `type` (новые события = строки, не таблицы), tenant-scoped.
- `docs/design/T-0119-files-attachments.adr.md` — **presign-after-allow**: контент файла отдаётся ТОЛЬКО после allow-решения PDP по записи-владельцу; путь прав файла = производный грант; внешний участник скачивает файл **тем же путём прав**, не вторым механизмом (T-0119 §2.5, §5 defers → T-0122).
- `docs/design/T-0033-data-classification.adr.md` — `DataClass = "public"|"internal"|"confidential"|"restricted"`; клиренс = максимальный DataClass из покрывающих грантов; внешний срез проектируется через тот же транс­форм-механизм.

**Связанные задачи (инварианты, читать дизайнеру):**
- **Один механизм прав (gap-map §4б инвариант 2, non-negotiable):** внешняя поверхность (T-0122) и headless API (T-0126) вводят **«внешнего принципала» ВНУТРИ grant-модели** (производный ограниченный грант), а **не второй механизм авторизации**. Это несущее ограничение всей задачи.
- **T-0124 (document-on-demand) зависит от T-0122** — QR-кейс (ТЭЛ §5): внешний посетитель видит «валидно/невалидно» + скачивает документ; live-рендер фиксируется снапшотом-файлом (T-0119), QR/ссылка указывает на снапшот либо явно помечена «живой документ» (gap-map §4б инвариант 1). T-0122 проектирует **поверхность доступа**, не сам рендер (T-0124).
- **T-0119 (файлы):** скачивание/загрузка файла внешним участником идёт через presign-after-allow по записи-владельцу; T-0122 даёт внешнему принципалу производный грант, T-0119 — путь контента.
- **T-0126 (headless API) — отдельная задача:** программная поверхность (запрос из чужого приложения → ответ агента) — там; **headless-ответы агента — design-only до разморозки Stage-2** (gap-map §4б инвариант 3). T-0122 — поверхность для **человека-внешнего-участника** (скачать/проверить/загрузить), не агентский ответ.

## 1. Summary

Choros получает примитив **«внешняя поверхность»** — способ дать стороне **без учётной записи** (контрагент по договору, посетитель сайта со сканированным QR) **токенизированный доступ к узкому, заранее определённому срезу действий** над конкретной записью: **скачать** артефакт, **проверить** статус/валидность, **загрузить** ответный файл — **с полным аудитом** каждого действия. Внешний участник как **данные** — это запись справочника (`record`, T-0014), не Keycloak-принципал. Внешний участник как **канал** — это **токен**, который PDP (T-0021) разрешает в **производный ограниченный грант** (T-0018) на узкий scope+операции, с TTL и отзывом, **строго внутри одной grant-модели** — никакого второго механизма авторизации (gap-map §4б инвариант 2). Скачивание/загрузка файлов идёт через **presign-after-allow** (T-0119). Действия внешнего пишутся в аудит (T-0016) с актором, производным от токена/внешней-поверхности (учётки нет). Токены tenant-изолированы и защищены от перебора.

Это **дизайн-задача**: выход фазы — спека требований, которые обязан покрыть будущий ADR (модель данных внешнего участника, модель токенизированной поверхности, производный грант, TTL/отзыв, аудит без учётки, tenant-изоляция токенов, анти-абьюз, граница MVP). Acceptance-критерии — **проверяемые свойства будущего ADR** (fitness-линт текста/трассируемость) либо **test после имплементации**.

## 2. Функциональные требования к дизайну (ADR обязан покрыть)

### FR-1 — Внешний участник как данные = запись справочника
ADR обязан зафиксировать, что внешний участник (контрагент, посетитель) моделируется как **запись реестра** (`record`, T-0014) того же tenant, а **НЕ** как Keycloak-учётка / tenant-пользователь / роль. Никакой второй identity-подсистемы для внешних не вводится:
- Запись внешнего участника — обычная tenant-запись (grant-target по T-0014); связь «договор ↔ контрагент» — кросс-реестровая ссылка, не новый тип сущности.
- ADR обязан явно отметить: внешняя поверхность **не создаёт** Keycloak-realm-пользователя и не выдаёт JWT-сессию ядра (tenancy §6 identity-модель не расширяется на внешних).

### FR-2 — Примитив «внешняя поверхность» (токенизированный доступ без учётки)
ADR обязан определить сущность **внешней поверхности** — конфигурацию доступа без учётки, минимум:
- **К чему** привязана: к конкретной записи-цели (`record`) того же tenant (узкий scope, не «весь реестр»).
- **Что разрешено**: узкий, закрытый набор операций из множества **{скачать, проверить, загрузить}** (download / verify-check / upload), а не произвольная операция grant-алгебры. ADR фиксирует, как эти три отображаются на операции T-0018 (`read`/`invoke`/`create`/`update`) и facet-сужение.
- **Носитель доступа** — **токен** (непрозрачный, высокоэнтропийный секрет), предъявляемый внешним без учётки; ссылка/QR несёт токен или handle (T-0015), не данные.
- ADR обязан зафиксировать: внешняя поверхность — **декларативная конфигурация** (кто/что/срок выдал), а не код per-кейс; QR-кейс и контрагент-кейс собираются из одного примитива (envelope-принцип gap-map §2).

### FR-3 — Токен разрешается в производный ОГРАНИЧЕННЫЙ грант (НЕ второй механизм)
**Несущее требование (gap-map §4б инвариант 2):** предъявление токена PDP (T-0021) разрешается в **производный ограниченный грант** в существующей grant-модели (T-0018):
- Грант внешней поверхности — **сужение** (write-time subset gate, T-0018 §4.3): его scope ⊑ scope записи-цели, его операции ⊆ {download/verify/upload}-отображение, facet — только опубликованный срез. Он **не может** быть шире, чем то, что выдавший принципал имел право делегировать.
- Грант внешней поверхности `delegable = false` (внешний не может переделегировать).
- Решение «что видит/может внешний» принимает **тот же PDP-резолвер** (T-0021), action-time, fail-closed — не отдельный код-путь. Внешний принципал предъявляется резолверу как субъект (его identity производна от токена — см. FR-6), и проекция полей (T-0021 `projectFields`) применяется к нему так же, как к внутреннему субъекту.
- ADR **запрещает** второй механизм авторизации для внешних: нет `external_acl`, `public_share_rights`, поля видимости «для внешних» в обход grant-таблицы (соответствует T-0018 §2 / T-0021 FF-R6).
- ADR обязан зафиксировать, КАК токен связан с грантом: токен — секрет, чья проверка даёт PDP идентичность внешнего принципала + scope; сам грант (или его производная) хранится grant-строкой/выводится из конфигурации поверхности — выбор представления = зона DESIGN, но «один механизм прав» обязателен.

### FR-4 — TTL и отзыв токена
ADR обязан определить жизненный цикл токена/поверхности:
- **TTL**: токен/грант имеет окно валидности (опирается на `valid_from`/`valid_until` T-0018 — out-of-window ⇒ ноль capability на read-path, action-time). Истёкший токен ⇒ `no_grant`/отказ, не «работает, но логируется».
- **Отзыв (revoke)**: выдавший (или уполномоченный) может отозвать токен/поверхность ДО истечения TTL; отзыв действует **немедленно на следующем resolve** (action-time, T-0021 — не кэш mint-time). ADR фиксирует, что отзыв = снятие/инвалидация гранта тем же путём, что обычный revoke гранта.
- ADR фиксирует: одноразовый vs многоразовый токен, и можно ли ограничить число использований — как декларативный атрибут поверхности (выбор day-1-объёма — зона DESIGN, но механизм отзыва+TTL обязателен).

### FR-5 — Узкий срез действий: скачать / проверить / загрузить
ADR обязан определить семантику трёх действий внешней поверхности так, чтобы каждое было **отдельной проверяемой операцией под PDP**:
- **Скачать (download):** выдача контента файла записи-цели — **через presign-after-allow** (T-0119): PDP разрешает производный грант на `read` записи-цели → presign короткого TTL → байты из S3. Ни байта без allow.
- **Проверить (verify/check):** внешний видит **узкий публичный срез** статуса/валидности записи (QR-кейс ТЭЛ §5: «валидно/невалидно»). Срез — facet-сужение (T-0021 `projectFields`); скрытые поля **физически отсутствуют** в ответе (capability-not-text, T-0021), не маскируются строкой. ADR фиксирует, что verify не раскрывает существование скрытых полей.
- **Загрузить (upload):** внешний кладёт ответный файл (протокол разногласий, подписанный скан — ТЭЛ §1), привязанный к записи-цели, **через путь T-0119** (`update`/`create` на запись-цель производным грантом). ADR фиксирует declared-лимиты загрузки (размер, MIME-allowlist) для внешнего пути — не unbounded (анти-абьюз, см. FR-8).
- ADR обязан зафиксировать, что набор действий **закрыт** для day-1 (только эти три); расширение — той же механикой (envelope), не новый примитив.

### FR-6 — Аудит действий внешнего участника (актор без учётки)
**Несущая развилка задачи, решаемая ADR (не эскалация):** у внешнего нет Keycloak-учётки — кто `actor` в `audit_event`? ADR обязан определить:
- Каждое действие внешнего (download/verify/upload, успех И отказ) пишет событие в `audit_event` (T-0016), tenant-scoped, open-vocab `type` (например `external.download`/`external.verify`/`external.upload`) — **строки, не новая таблица**.
- `actor` производен от **идентичности внешней поверхности/токена** (например `external-surface:<id>` или хэш/идентификатор токена-без-секрета), а не от tenant-пользователя; ADR фиксирует, что в аудите видно (а) какая поверхность, (б) на какую запись-цель (`subject`), (в) через какой канал (`via`), (г) результат (allow/deny + reason). Секрет токена в аудит НЕ пишется.
- ADR фиксирует трассируемость: по аудиту восстановимо «кто выдал поверхность» (granted_by гранта) ↔ «что сделал внешний по ней».

### FR-7 — Tenant-изоляция токенов и внешней поверхности
ADR обязан гарантировать tenant-изоляцию (tenancy §5/§9 — non-negotiable):
- Токен/поверхность принадлежат ровно одному tenant; предъявление токена резолвится **только** в контексте его tenant; cross-tenant предъявление ⇒ `cross_tenant`/отказ, ни байта (как T-0021 tenant-gate first).
- Метаданные поверхности/токена — tenant-таблица с полным T-0013-контрактом (FORCE RLS, default-DENY на `current_setting('choros.tenant_id', true)`, `tenant_id`-leading PK, занесение в `ci/checks/known_tenant_tables.txt`), либо производны от существующих tenant-таблиц грантов.
- **Fail-closed tenant-контекст** на внешнем пути (tenancy §9 п.7): входящий запрос с токеном устанавливает tenant-контекст ДО любого доступа к данным; отсутствие/неоднозначность tenant-контекста ⇒ отказ, не глобальное действие. ADR фиксирует, как tenant выводится из токена (токен сам несёт/детерминирует tenant — нельзя, чтобы внешний выбирал tenant).

### FR-8 — Анти-абьюз (перебор токенов, без учётки = без сессии)
ADR обязан определить защиту неаутентифицированной поверхности от злоупотребления:
- Токен — **высокоэнтропийный** секрет (перебор вычислительно неосуществим); ADR фиксирует требование к энтропии и к хранению (хэш токена, не plaintext — как пароль).
- **Rate-limiting / throttling** на внешнем эндпоинте (защита от brute-force перебора и от DoS-скачиваний); ADR фиксирует, где гейт (per-токен, per-IP, per-tenant) и что превышение лога́ется в аудит.
- **Fail-closed по умолчанию:** неверный/истёкший/отозванный токен ⇒ единообразный отказ без утечки информации (не «токен есть, но истёк» vs «токена нет» — чтобы не давать оракул перебора). ADR фиксирует, что отказ не раскрывает существование записи-цели.
- ADR фиксирует declared-лимиты загрузки (FR-5) как часть анти-абьюза (внешний не заливает unbounded).

### FR-9 — Поддержка QR-кейса (document-on-demand, инвариант T-0124)
ADR обязан зафиксировать, что внешняя поверхность **закрывает QR-кейс** (ТЭЛ §5): посетитель сканирует QR на сайте клиента → внешняя поверхность по токену/handle → «валидно/невалидно» (verify, FR-5) + скачивание документа (download, FR-5):
- Скачиваемый документ — либо **снапшот** в файловом хранилище (T-0119, иммутабельный — «вчерашний реестр воспроизводим»), либо **явно помеченный «живой документ»** (gap-map §4б инвариант 1). ADR фиксирует, что внешняя ссылка указывает на одно из двух недвусмысленно.
- T-0122 проектирует **поверхность доступа** (токен → verify/download); сам рендер документа из живых справочников — **T-0124** (deps на T-0122). ADR T-0122 фиксирует контракт, который T-0124 потребляет, не сам рендер.

## 3. Нефункциональные требования

### NF-1 — Единый механизм прав (несущий, gap-map §4б инвариант 2)
Внешний принципал вводится ВНУТРИ grant-модели как производный ограниченный грант (T-0018), резолвится тем же PDP (T-0021). Никакого второго механизма авторизации для внешних (`external_acl`/`public_share`/поле видимости). Это аудит-инвариант (один источник истины), не оптимизация.

### NF-2 — Tenant-изоляция (инвариант tenancy, non-negotiable)
Токены/поверхности tenant-изолированы; cross-tenant предъявление структурно отклоняется (не на дисциплине кода); tenant выводится из токена, не выбирается внешним. Один cross-tenant leak через публичную поверхность = смерть GTM (tenancy §5).

### NF-3 — Минимальная привилегия / узкий срез
Внешняя поверхность даёт **строго сужающий** грант (subset gate T-0018): только заявленные scope+операции+facet, `delegable=false`. Невозможно через внешний токен получить шире, чем опубликовано. Срез по умолчанию — пустой (deny-by-default): что не опубликовано — невидимо/недоступно.

### NF-4 — Action-time, fail-closed (как весь PDP)
Право внешнего проверяется в момент действия (T-0021): отзыв/истечение действуют на следующем resolve, нет mint-time снапшота capability. Любой неуспех (нет токена/истёк/отозван/cross-tenant/нет записи) ⇒ fail-closed отказ.

### NF-5 — Контент мимо PDP не утекает (presign-after-allow, T-0119)
Скачивание внешним идёт через presign-after-allow по записи-цели: ни байта без предшествующего allow PDP; presign короткого TTL; постоянных публичных URL объекта нет. Verify не отдаёт скрытые поля (физически отсутствуют, T-0021).

### NF-6 — Неразглашение при отказе (анти-оракул)
Отказы внешней поверхности единообразны и не служат оракулом перебора/разведки (не раскрывают существование записи-цели, не различают «истёк» vs «не существует» наружу). Энтропия токена + rate-limit + хэш-хранение токена обязательны.

### NF-7 — Аудит-полнота без учётки
Каждое действие внешнего (включая отказ) аудируется (T-0016) с производным актором и записью-целью как subject; секрет токена не пишется; аудит-след tenant-scoped и переживает истечение/отзыв поверхности.

## 4. Out of Scope (явные не-цели T-0122)

1. **Реализация (DDL/код/эндпоинт/токен-сервис):** T-0122 — дизайн-задача; сам ADR + реализация — последующие фазы. Следующая миграция (если нужна) — свободный номер по run-seam дисциплине (≥ свободного после T-0119-миграции), точный номер выбирает coder.
2. **Headless API / программная поверхность (T-0126):** запрос из чужого приложения → ответ агента (банк-кейс) — отдельная задача; **агентский headless-ответ — design-only до разморозки Stage-2** (gap-map §4б инвариант 3). T-0122 — поверхность для человека-внешнего (скачать/проверить/загрузить), не агентский ответ.
3. **Document-on-demand рендер (T-0124):** генерация документа из живых справочников — T-0124 (deps на T-0122); здесь только **поверхность доступа** (verify/download) + контракт, который T-0124 потребляет.
4. **Файл-хранилище / presign-сервис (T-0119):** механика S3/версий/ретенции — T-0119; T-0122 переиспользует presign-after-allow, не достраивает хранилище.
5. **Keycloak / федерация / внешние IdP:** внешний участник НЕ получает учётку (FR-1); интеграция с внешними IdP для внешних сторон — не цель (и противоречила бы «без учётки»).
6. **ЭДО / электронная подпись внешнего:** подписание загруженного внешним документа ЭП — нишевой модуль, не здесь.
7. **UI внешней поверхности (страница посетителя/QR-лендинг):** клиентская страница, которую видит внешний, и UI выдачи токена в пульте — задачи слайса/UI-эпиков; T-0122 проектирует поверхность и её контракт, не вёрстку.
8. **Двусторонний долгоживущий портал контрагента (личный кабинет с историей):** day-1 — узкий токенизированный срез (скачать/проверить/загрузить), не полноценный внешний портал с навигацией; расширение — потом той же механикой.
9. **Pooled-режим:** дефолт silo (tenancy §5); ADR закладывает tenant-вывод из токена так, чтобы pooled не требовал ретрофита, но не достраивает pooled.

## 5. Acceptance Criteria

Критерии — **проверяемые свойства будущего ADR** (fitness-линт текста ADR на присутствие решения / трассируемость) либо **test после реализации**. Для дизайн-задачи `verifiable_as=fitness` = машинно-проверяемое требование к артефакту ADR (раздел/решение присутствует и не противоречит инвариантам); `test` — проверяемо кодом после имплементации; `manual` — ревью-гейт.

| ID | Text | Verifiable as |
|---|---|---|
| **AC-1** | ADR фиксирует внешнего участника как **запись справочника** (`record`, T-0014) того же tenant, явно НЕ как Keycloak-учётку/tenant-пользователя/роль; identity-модель tenancy §6 не расширяется на внешних (внешняя поверхность не создаёт realm-пользователя). | fitness |
| **AC-2** | ADR определяет примитив «внешняя поверхность»: привязка к конкретной записи-цели, закрытый набор операций ⊆ {скачать, проверить, загрузить}, носитель = непрозрачный токен; поверхность — декларативная конфигурация (QR-кейс и контрагент собираются из одного примитива). | fitness |
| **AC-3** | ADR выражает доступ внешнего как **производный ОГРАНИЧЕННЫЙ грант** внутри grant-модели (T-0018): scope ⊑ записи-цели (subset gate), операции ⊆ {download/verify/upload}-отображение, facet = опубликованный срез, `delegable=false`; решение принимает тот же PDP (T-0021), action-time, fail-closed. | fitness |
| **AC-4** | ADR **явно запрещает** второй механизм авторизации для внешних (`external_acl`/`public_share_rights`/поле видимости «для внешних») — соответствует T-0018 §2 / T-0021 FF-R6 (gap-map §4б инвариант 2). | fitness |
| **AC-5** | ADR определяет TTL токена/гранта (через `valid_from`/`valid_until` T-0018; out-of-window ⇒ ноль capability) и **отзыв** до истечения, действующий немедленно на следующем resolve (action-time, не mint-time кэш). | fitness |
| **AC-6** | ADR определяет три действия как отдельные операции под PDP: **скачать** = presign-after-allow по записи-цели (T-0119, ни байта без allow); **проверить** = узкий facet-срез (скрытые поля физически отсутствуют, T-0021, verify не раскрывает их существование); **загрузить** = путь T-0119 с declared-лимитами; набор day-1 закрыт. | fitness |
| **AC-7** | ADR решает «актор без учётки»: каждое действие внешнего (успех И отказ) = строка `audit_event` (T-0016, open-vocab `type`, не новая таблица) с актором, производным от поверхности/токена (не tenant-пользователя), записью-целью в `subject`, каналом в `via`, результатом+reason; **секрет токена не пишется**; трассируемо «кто выдал ↔ что сделал внешний». | fitness |
| **AC-8** | ADR определяет tenant-изоляцию токенов: tenant выводится из токена (внешний его не выбирает); cross-tenant предъявление ⇒ отказ ни-байта; метаданные поверхности — полный T-0013-контракт (FORCE RLS, default-DENY, `tenant_id`-leading, known_tenant_tables) либо производны от tenant-таблиц грантов; fail-closed tenant-контекст на внешнем пути (tenancy §9 п.7). | fitness |
| **AC-9** | ADR определяет анти-абьюз: высокоэнтропийный токен (перебор неосуществим) + хэш-хранение (не plaintext), rate-limit/throttle на внешнем эндпоинте (per-токен/IP/tenant, превышение в аудит), единообразный fail-closed отказ-без-оракула (не различает наружу «истёк» vs «не существует», не раскрывает существование записи-цели), declared-лимиты загрузки. | fitness |

| **AC-13** | Post-impl: предъявление токена tenant B в контексте/эндпоинте tenant A ⇒ `cross_tenant`/отказ, ни байта контента; запись-цель tenant B недостижима из tenant A. | test |
| **AC-14** | Post-impl: каждое действие внешнего (download/verify/upload и отказ при неверном/истёкшем токене) порождает ожидаемое `audit_event` (актор=поверхность/токен-id, subject=запись-цель, tenant-scoped); секрет токена в событии отсутствует. | test |
| **AC-15** | Трассируемость + проверка на QR-кейсе (требование фаундера): каждое FR-1..FR-9 покрыто ≥1 решением ADR (таблица AC→design); ADR прогоняет QR-кейс (ТЭЛ §5) и контрагент-кейс (ТЭЛ §1/§2) через примитив и показывает, что оба собираются без второго механизма прав и без учётки; ни одно решение не вводит второй permission-подсистемы и не противоречит tenancy/grant/audit-инвариантам (ревью-гейт архитектора). | manual |

## 6. Снятые неоднозначности (резолюции без эскалации)

Развилки, **уже закрытые фаундером** в gap-map — не поднимаются заново:
- **Внешний участник = данные = запись справочника** (gap-map §3а) — данность; НЕ учётка Keycloak.
- **Канал = «внешняя поверхность» = токенизированный доступ без учётки к узкому срезу (скачать/проверить/загрузить), с аудитом** (gap-map §2, §3а) — данность объёма.
- **Один механизм прав** (gap-map §4б инвариант 2) — внешний принципал ВНУТРИ grant-модели как производный грант; второй механизм запрещён.
- **Снапшот vs живой документ** (gap-map §4б инвариант 1) — обязательное недвусмысленное различие в QR-кейсе.

Резолюции по существующей модели (не эскалация — зона DESIGN):
- **«Актор без учётки» в аудите** — НЕ blocking: модель T-0016 (`actor` — свободный `text`, open-vocab `type`) уже вмещает производный актор поверхности/токена; конкретное написание — DESIGN (FR-6/AC-7).
- **Представление токена↔грант** (grant-строка с производной идентичностью vs конфигурация поверхности, из которой грант выводится) — обе совместимы с «одним механизмом прав»; выбор — DESIGN (FR-3), subset gate обязателен при любом.
- **Одноразовый vs многоразовый токен, лимит использований** — декларативный атрибут поверхности; объём day-1 — DESIGN (FR-4), TTL+отзыв обязательны.
- **Скачивание/загрузка контента** — переиспользует presign-after-allow T-0119 (уже спроектировано); T-0122 не достраивает хранилище.
- **Неуверенность фаундера в направлении** — снимается требованием AC-15 (прогон QR-кейса и контрагент-кейса через примитив в ADR), не эскалацией: направление задано (запись + внешняя поверхность), проверка на кейсе — обязанность дизайнера.

**Blocking questions:** нет. Решения фаундера (внешний = запись; канал = токенизированная внешняя поверхность к узкому срезу с аудитом) + инварианты grant/PDP/audit/files закрывают продуктовый объём. Развилка «актор без учётки» и представление токена — внутри зоны DESIGN, продуктовый объём не меняют (модель T-0016/T-0018 их уже вмещает). Статус спеки = `ready`.
