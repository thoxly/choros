## 0. Проблема и текущее состояние (разведка кода, 2026-07-04, живой worktree T-0587)

Карта примитивов §G4 фиксирует диагноз на 2026-07-02: аналитик (`handleAnalyst`)
падал сырым `{"error":{"code":"INTERNAL"}}` при отсутствии LLM-ключа тенанта, и
концептуально «контур прав на чтении пуст — отвечал бы всё-всем». **Обе половины
диагноза частично устарели** — между картой примитивов и этой задачей смержен
T-0607 (`bb67bf4`), который закрыл существенную часть проблемы. Разведка кода на
момент написания этой спеки:

### 0.1 Идентити, которым аналитик ходит за данными — СЕГОДНЯ

Поток одного вызова аналитика:
1. `src/http/assistant.ts` (роут, шаг 4, ~:2085-2099) резолвит **реального
   аутентифицированного вызывающего** — `actorSlug` (не сервисный аккаунт, не
   владелец по умолчанию) — и строит `userSubject: ResolveSubject = { tenantId,
   subjectId: actorSlug }`.
2. Гранты, которыми ограничен ответ — `intersectionGrants =
   makeIntersectionGrantSource(baseGrantSource, agentSubject, userSubject,
   ancestry)` (`assistant.ts:2094-2099`) — **пересечение** гранта агента-ассистента
   И гранта спрашивающего пользователя. Ответ никогда не шире ни того, ни другого
   потолка — агент не даёт спрашивающему увидеть больше своих собственных прав,
   и не отвечает от лица владельца/сервисного аккаунта.
3. `src/core/assistant-intent.ts` строит `HandlerContext{userSubject, agentSubject,
   intersectionGrants, ancestry, ...}` и диспатчит на `handleAnalyst`
   (`assistant-intent.ts:172-173, 210`).
4. `handleAnalyst` (`src/core/assistant-analyst.ts:577-582`) делегирует в
   `runAnalyst` (`:400-530`), который:
   - вызывает `listRecords(ctx.tenantId, ctx.intersectionGrants, ctx.ancestry,
     ctx.userSubject)` (`:423-428`) — **порт НЕ подключён в `server.ts`**, поэтому
     production реально использует `defaultListRecords = async () => []`
     (`:183`) — этот канал сегодня structurally мёртв (не читает записи вообще,
     возвращает пустой список независимо от прав);
   - вызывает `loadRegistryDigest(ctx.tenantId, ctx.userSubject.subjectId)`
     (`:434-437`), подключённый в `server.ts:1067-1068` к
     `loadReadableRegistryDigest` (`src/db/registry-digest-dao.ts:123-232`,
     T-0607 дельта а) — **это единственный сегодня живой канал данных сущностей**
     в контуре аналитика. Резолвит `getGrantsForSubject` + `loadTenantOrgAncestry`
     + `makeResourceAncestryOracle` — **тот же READ-PDP-резолвер (T-0570)**, что
     `GET /api/records`, — и фильтрует КАЖДУЮ строку через `isRecordReadable`
     (тот же предикат, что LIST records) прежде чем посчитать её в
     `visibleCount`/включить в `samples`. Identity, которым идёт этот запрос —
     `ctx.userSubject.subjectId`, реальный слаг спрашивающего, НЕ владелец, НЕ
     сервисный аккаунт.
   - условно (только если вопрос про процессную аналитику,
     `isProcessAnalyticsQuery`) читает S3-журнал (cycle-time/actor-breakdown) —
     внутренняя телеметрия, не сущностные данные компании.
5. Единственный LLM-вызов — `ctx.llm.chat({system, messages:[{role:"user",
   content: draftContext + userText}]})` (`:507-517`), где `draftContext` =
   `buildDraftContext(draft)` — строковый рендер уже отфильтрованного
   READ-PDP'ом дайджеста. LLM не имеет отдельного доступа к БД и не видит ничего
   сверх того, что уже легло в `draftContext`.

**Вывод разведки**: канал `loadRegistryDigest` (счёт видимых записей + до N
примеров) уже честно ходит через READ-PDP спрашивающего — это не сервисный
аккаунт и не владелец по умолчанию. Но канал `listRecords` (полные записи —
предпосылка для содержательных ответов вида «на какую сумму» с реальными
значениями, не просто счётом) **не подключён вообще** — сегодня всегда `[]`.
Это значит: на вопрос «сколько записей в реестре X» аналитик сегодня может
ответить честно и в правах (через дайджест); на вопрос, требующий агрегата по
полю записи (сумма, среднее, разбивка) — аналитик **структурно не может**
ответить вообще (нет данных в контексте), НЕ что он отвечает шире прав.

### 0.2 READ-PDP: текущий публичный контракт

`src/core/read-visibility.ts`:
```ts
export function isRecordReadable(
  row: RowAncestry,               // {recordId, registryId, applicationId}
  grants: readonly Grant[],
  ancestry: AncestryOracle,
  nowMs: number,
): boolean
```
Чистый per-row предикат (allow/deny одной уже загруженной строки), не сам
запрос/агрегат. Множественные/агрегатные вопросы обслуживаются РУЧНЫМ циклом
вызывающего кода: `loadReadableRegistryDigest` (`registry-digest-dao.ts`) сам
проходит по строкам (bounded `scanLimit`, default 200) и вызывает
`isRecordReadable` на каждой, накапливая `visibleCount` и до `sampleLimit`
примеров — **общего PDP-примитива для count/sum по видимому подмножеству не
существует**; каждый вызывающий код (records.ts LIST/DETAIL, registry-digest-dao)
реализует свой цикл фильтрации над тем же предикатом. Эта задача не обязана
вводить новый общий примитив — обязана лишь применить существующий предикат
корректно для тех агрегатов, которые уже подаются в ответ аналитика.

### 0.3 Как READ-PDP применяется в обычных (не-аналитик) роутах — образец

`src/http/records.ts`:
- LIST (`GET /api/records`, ~:1901-2003): `resolveReadVisibility` резолвит
  `{grants, ancestry}` один раз на запрос (`:1964`), затем
  `page.items.filter(row => isRecordReadable(rowAncestry, readGrants, ancestry,
  nowMs))` (`:1965-1972`) — «до» = сырая tenant/sandbox-страница, «после» =
  ACL-отфильтрованный список; отсутствующая строка просто короче список, не
  замена на «нет доступа».
- DETAIL (`GET /api/records/:id`, ~:2016-2052): `if (!isRecordReadable(...))
  throw new HttpError(404, "NOT_FOUND", ...)` (`:2049-2051`) — отказ
  неотличим от «не существует»/чужой тенант.

Это эталонный паттерн «до/после фильтра», который эта задача обязана
воспроизводить для любых данных, которые аналитик подмешивает в LLM-контекст.

## 1. Summary

Довести существующий READ-PDP-контур аналитика (T-0570 резолвер + T-0607
дайджест-порт) до состояния, где **любой агрегат/факт, попадающий в ответ
аналитика о данных компании, вычислен строго по подмножеству, видимому
СПРАШИВАЮЩЕМУ пользователю** (не сервисному аккаунту, не владельцу-по-умолчанию,
не агенту-ассистенту в одиночку) — и доказать это ЖИВЬЁМ: два реальных
пользователя с разными READ-грантами в одном тенанте, один и тот же вопрос в
чате → разные ответы, соответствующие их правам.

## 2. Функциональные требования

- **FR-1 — Одна identity на всём пути.** Каждый DB/API-вызов, который
  подмешивает данные компании в LLM-контекст аналитика, резолвится с
  `ctx.userSubject.subjectId` (реальный спрашивающий) как минимум-потолком
  видимости — через `ctx.intersectionGrants` (агент ∩ пользователь). Ни один
  путь не должен подменять эту identity на владельца тенанта, системного агента
  или «все гранты тенанта» ни при какой ветке (в т.ч. когда спрашивающий сам
  владелец — тогда потолок совпадает с его собственными правами, не шире).
- **FR-2 — Агрегаты по видимому подмножеству.** Любой count/sum/перечисление,
  который аналитик подаёт в ответ (включая уже существующий `visibleCount` и
  `samples` в `ReadableRegistryDigest`), вычислен **после** применения
  `isRecordReadable` к каждой строке — не по всей таблице реестра с последующим
  текстовым дисклеймером. Это уже верно для `loadReadableRegistryDigest`
  (регресс-тестом закрепить, не переизобретать); для ЛЮБОГО нового
  агрегатного канала, который эта задача подключает или расширяет — тот же
  порядок операций обязателен.
- **FR-3 — Не палить существование через агрегат.** Когда у спрашивающего нет
  READ-гранта ни на одну запись реестра, ответ не должен содержать факт вида
  «реестр X существует, но записей вам не видно» — реестр либо не упоминается,
  либо (если в реестре 0 видимых записей, но реестр сам published и метаданные
  реестра открыты) явно сказано «в доступных вам разделах записей нет» —
  не более. Существование КОНКРЕТНОЙ невидимой ЗАПИСИ (не реестра-как-раздела)
  никогда не утверждается и не подразумевается формулировкой.
- **FR-4 — Честный отказ по LLM-ключу.** Отсутствие рабочего LLM-ключа тенанта
  → пользователь видит человечный текст «Ассистент пока не может ответить — не
  подключён рабочий LLM-ключ...» (уже существующие
  `ASSISTANT_LLM_UNAVAILABLE_MESSAGE_ADMIN`/`_NON_ADMIN`), НЕ
  `{"error":{"code":"INTERNAL"}}` и НЕ сырой текст исключения/провайдера.
  Регрессионный тест фиксирует существующее поведение (T-0573/T-0595/T-0607),
  не вводит новое.
- **FR-5 — Честный отказ по объёму видимости.** Когда спрашивающий не имеет ни
  одного READ-гранта, покрывающего предмет вопроса (весь тенант пуст для него
  READ-PDP-wise, либо конкретный реестр вне его грантов), ответ формулируется
  человеческим языком в духе «в вашей зоне видимости данных по этому вопросу
  нет» — не молчание, не `[]`, не техническая ошибка, не утверждение
  «данных в системе нет» (это была бы ложь о состоянии системы, не о видимости
  спрашивающего). Точная формулировка — не кейс-литерал, генерическая на уровне
  платформы.
- **FR-6 — Два пользователя, разные гранты → разные ответы.** На идентичный
  текст вопроса, заданный от имени двух разных пользователей одного тенанта с
  разными READ-грантами (в т.ч. пересекающимися частично), итоговый текст
  ответа аналитика (или как минимум используемые в нём числа/факты) детерминированно
  различается в соответствии с разницей их видимого подмножества. Пользователь
  без единого READ-гранта на предмет вопроса получает FR-5-отказ, а не тот же
  содержательный ответ, что и пользователь с грантом.

## 3. Нефункциональные требования

- **NF-1 — Один резолвер, не вторая система прав.** Аналитик не вводит
  параллельный ACL/whitelist для видимости данных — решение выводится
  исключительно через существующий `isRecordReadable` +
  `getGrantsForSubject`/`loadTenantOrgAncestry`/`makeResourceAncestryOracle`
  (тот же путь, что `GET /api/records`) — зеркалит FR-7 T-0570.
- **NF-2 — Человек и агент — один путь (зеркало FR-6 T-0570).** Видимость
  данных для аналитика вычисляется тем же PDP-вызовом с тем же
  grant-разрешением, что и человеческий REST-путь чтения тех же данных — не
  отдельная, более щедрая или более узкая, аналитик-ветка.
- **NF-3 — Sealed-роут не расширяется по сигнатуре.** `src/http/assistant.ts`
  (sealed по Wave2/ADR-T0607 §5) и публичные типы (`HandlerResult`,
  `AnalystPorts`, `LlmPort`, `HandlerContext`) — правки только аддитивные
  (новые опциональные порты/поля), существующие экспортируемые сигнатуры не
  ломаются (зеркалит N5 T-0607).
- **NF-4 — Анти-кейс (D-064).** Ни одна добавленная/изменённая строка `src/`
  не содержит кейс-специфичных литералов (имя роли/тенанта/сущности живого
  бизнес-кейса) — проверяется существующим зонтичным гейтом
  `ci/checks/anti-case-lock.sh` (который делегирует в
  `read-pdp-anti-case.sh`/`rights-ui-anti-case.sh`/`detel-literal-baseline.sh` и
  добавляет repo-wide baseline-скан) — гейт должен остаться зелёным, задача не
  ослабляет baseline.
- **NF-5 — Без N+1/безлимитного скана.** Любой новый или расширенный агрегатный
  канал (FR-2) остаётся bounded (registryLimit/sampleLimit/scanLimit-подобные
  ограничения, как уже сделано в `loadReadableRegistryDigest`) — не полный
  скан таблицы без лимита ради точного count.
- **NF-6 — Жаргон-гейт.** Новые/изменённые user-facing тексты (в т.ч. FR-5
  формулировка отказа) проходят `ci/checks/ux/assistant-llm-message-jargon.sh`
  (и его `--self-test`) — без кодов ошибок/имён внутренних сущностей/жаргона.

## 4. Out of scope (явно НЕ в этой задаче)

- **Новые виды отчётов/дашбордов.** Задача — вопрос-ответ поверх существующего
  read-контура (дайджест реестров +, при необходимости, точечное расширение
  агрегатов уже существующим предикатом), НЕ конструктор новых визуализаций/
  отчётных страниц. Существующий `report_page`/«Сохранить как отчёт» механизм
  (T-0121) не меняется.
- **Полноценный tool-use аналитик** (LLM сам решает, какие реестры читать,
  пагинация, произвольные агрегации по любому полю) — явный follow-up O1 в
  ADR-T0607 §2; эта задача остаётся в рамках детерминированного,
  сервер-построенного контекста (дайджест + при необходимости точечные
  read-ports), не отдаёт LLM свободный доступ к БД.
- **`src/runtime/agent-dispatch/**`** — зона T-0586, не трогается.
- **Общий resource-ancestry-оракул / новый scope-примитив T-0018-латтиса** — уже
  решено architect-уровнем в T-0570 §2/§5, не пересматривается здесь.
- **UI управления грантами** («Доступ» показывает «Нет ролей») — известный,
  отдельный дефект (карта примитивов D4/D5), не эта задача.
- **Изменение семантики действий (D2, card-action.ts)** — не трогается,
  задача только про READ/чтение вопросов-ответов.
- **Полный `listRecords` record-lister** (сегодня всегда `[]`, §0.1) — задача
  ФИКСИРУЕТ и ДОКАЗЫВАЕТ честность существующего дайджест-канала (счёт+примеры)
  и любых точечных агрегатов, которые она решит подключить в его рамках; не
  обязана поднимать полный постраничный ридер записей (это O1 ADR-T0607) —
  если в ходе DESIGN architect сочтёт, что вопрос «на какую сумму» требует
  минимального точечного агрегатного порта (например «сумма по числовому полю
  видимых записей реестра»), это ДОПУСТИМО реализовать в рамках FR-2 при
  условии NF-1/NF-5, но не обязательный объём — если не реализовано,
  LIVE_PROOF (§6) обязан использовать вопрос, отвечаемый уже существующим
  дайджест-каналом (счёт/примеры), не гипотетический полнообъёмный агрегат.

## 5. LIVE_PROOF-путь (D-064)

Обязательный путь, доказывающий задачу ГЛАЗАМИ на живом стенде — браузером, не
curl:

1. На живом тенанте (НЕ демо-ТЭЛ-кейс, любой рабочий/self-reg тенант с
   реальным LLM-ключом — на стенде DeepSeek уже подключён, приёмка W1) есть
   ≥1 реестр с ≥2 записями и ≥2 пользователя: User A с READ-грантом,
   покрывающим весь реестр (или тенант-широкий default-open, T-0570 FR-2),
   User B с READ-грантом, суженным так, что он видит **строго подмножество**
   записей этого реестра (например 1 из 2) — сужение заводится через
   существующий грант-механизм (`POST /api/grants`/UI), без правки кода.
2. От имени User A в чате задаётся вопрос вида «сколько записей в разделе X и
   какие они» (или содержательный эквивалент, отвечаемый существующим
   дайджест-каналом/агрегатом, реализованным в рамках этой задачи) —
   ответ ассистента показывает число, соответствующее ПОЛНОМУ множеству
   записей, видимых User A.
3. От имени User B — тот же дословный вопрос в новом треде — ответ показывает
   число, соответствующее ТОЛЬКО суженному подмножеству User B, меньшее, чем
   ответ User A; примеры/факты в ответе User B не содержат данных из записи,
   на которую у него нет гранта.
4. User C (третий пользователь тенанта, без единого READ-гранта ни на один
   реестр) задаёт любой вопрос о данных компании → получает FR-5-формулировку
   («в вашей зоне видимости данных по этому вопросу нет» или эквивалент), не
   числа, не техническую ошибку, не тот же ответ, что User A/B.
5. (Если стенд позволяет — временно отключить/испортить LLM-ключ тенанта)
   Любой из пользователей задаёт вопрос → видит FR-4-текст «не подключён
   рабочий LLM-ключ...», не INTERNAL/500 без текста в треде. Восстановить ключ
   после проверки.
6. Скриншоты/консоль браузера прикладываются как доказательство (не только
   текстовый пересказ) — оба треда (User A и User B) видны одновременно или
   последовательно с точным текстом вопроса и ответа.

Обход curl/API-напрямую **не допускается** для шагов 2-4 (сам чат — это
интерфейс, через который продукт заявляет способность отвечать честно; браузер
обязателен, зеркалит требование задачи). Настройка гранта в шаге 1 может быть
через API/UI как удобнее (сама настройка — не предмет доказательства).

## 7. Blocking questions

Нет. Направление задано картой примитивов §G4 и уже частично исполнено T-0607
(READ-PDP-дайджест в контуре аналитика, honest-503, honest-degrade — все три
смержены). Остаток — доказать сквозняком (LIVE_PROOF браузером, два живых
пользователя) и закрепить регрессией то, что уже реализовано, плюс честные
формулировки отказа по объёму видимости (FR-3/FR-5), которые не были явно
специфицированы в T-0607. Выбор — реализовывать ли точечный агрегатный порт
сверх существующего дайджеста (например «сумма по полю») — инженерное решение
в пределах уже описанного READ-PDP-предиката (см. §4 out-of-scope, последний
пункт), не разворот объёма/поведения, поэтому не блокирует SPEC.
