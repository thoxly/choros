## 1. Разведка: что реально работает, а что «спит»

### 1.1 Substitution-модель и запись правил — РАБОТАЕТ (не строим заново)

`substitution_rule` (migration 036) — живая таблица. Write-путь уже есть и
проверен статически:
- `POST /api/rights/intents/substitute` (админ назначает замещение любому
  сотруднику под свою орг-область, `src/http/rights-intents.ts`
  `registerSubstitute`).
- `POST /api/rights/intents/self-absence` (сотрудник объявляет СВОЁ отсутствие
  и замещающего, `registerSelfAbsence`).
- Оба пути: Tier-1 (пул уже имеет держателя роли → routing-only, грант не
  минтится) или Tier-2 (единственный держатель → минтится TTL'd грант,
  subset-gated `validateNarrowing`, `delegable=false`).
- UI: `SubstituteForm` + `SelfAbsenceForm` на `/rights/intents` — экран уже
  `status: "live"` в навигации, не черновик.

**Вывод: экран назначения замещения СУЩЕСТВУЕТ.** Задача T-0588 не строит
«с нуля», а чинит стык между уже созданным `substitution_rule` и реальной
маршрутизацией задачи + добавляет обработку деактивации/эскалации.

### 1.2 Два параллельных пути резолва исполнителя — расхождение

**Путь A — `resolveExecutor` (executor-resolver.ts), pure single-task resolver.**
Комментарий в коде честно фиксирует: `ResolverDeps.substitution` —
**опциональный порт**; если он не инжектирован вызывающим кодом, шаг 3
(substitution) — no-op, лестница проваливается сразу на шаг 4 (fallback-owner).
Нет ни одного прод-вызова `resolveExecutor(...)` с реально переданным
`deps.substitution` — единственный экспортируемый adapter
(`makeDbSubstitutionPort` в `substitution-dao.ts`) существует, но не
подключён нигде в composition root. **Это и есть «порт undefined (dormant)»
из карты примитивов** — конкретно про путь A.

**Путь B — `resolveExecutorFallbackBatch` (inbox.ts), батч-резолвер для
проекции инбокса.** Этот путь УЖЕ вызывает `getActiveSubstitutionsByRole` и
корректно подавляет отсутствующего держателя + добавляет заместителя в
эффективный пул (suppress-absent + add-substitute), используется на каждом
чтении инбокса (`findInboxItems` → `resolveExecutorFallbackBatch`). Он влияет
на то, помечается ли задача `routed_to_fallback: "role_unfilled"` в
JSON-ответе `/api/inbox`.

**Расхождение путей A и B — не предмет этой задачи** (оба уже существуют,
рефакторинг в единый резолвер — отдельная работа, не блокирует LIVE_PROOF).
Существенный практический разрыв — не в существовании путей, а в следующем:

### 1.3 Реальная дыра №1 — claim-eligibility не видит Tier-2 substitution

`POST /api/inbox/:id/claim` (inbox.ts) проверяет право забрать задачу из пула
строго через `myRoles.includes(taskRole)`, где `myRoles = resolveRolesForActor
→ getRoleSlugsForActor` (`grants-dao.ts`) — запрос по `role_assignment`, JOIN
`employee`+`role`. `substitution_rule` в этом запросе не участвует.

- **Tier-1** substitution по конструкции безопасен: заместитель по T-0035
  определению — сотрудник, УЖЕ держащий ту же роль (`role_assignment`
  существует независимо от правила подмены) → `myRoles.includes(taskRole)`
  и так проходит. Разрыва нет.
- **Tier-2** substitution минтит `grant` (не `role_assignment`) на
  `substitute_employee_id`. Заместитель, у которого НЕТ собственного
  `role_assignment` на эту роль, получает 403 `NOT_ELIGIBLE` при попытке
  забрать задачу из пула, несмотря на действующий TTL-грант. **Это реальный,
  узко-локализуемый баг**, не требующий новой модели данных — только
  дополнительная проверка в claim-eligibility, аналогичная логике
  `resolveExecutorFallbackBatch`.

### 1.4 Реальная дыра №2 — деактивация не фильтруется в резолве исполнителя

`employee.deactivated_at` (migration 125, T-0583/T-0628) используется
СЕГОДНЯ только в `src/http/user-mgmt.ts` (список учёток + PATCH деактивации)
и в Keycloak-связке (`setUserEnabled`). Проверено построчно:
- `getHoldersForRole` (`grants-dao.ts:461-482`) — JOIN `employee`+
  `role_assignment`+`role`, **без фильтра `deactivated_at IS NULL`**.
- `findTenantOwnerSlug` (`grants-dao.ts:497-518`) — тот же паттерн, тот же
  пробел; fallback-owner может резолвиться в деактивированного владельца.
- `getRoleSlugsForActor` (claim-eligibility) — тот же паттерн.

**Следствие:** деактивация (увольнение) сотрудника НЕ снимает его с пула
держателей роли. Новые задачи процесса продолжают литься деактивированному
исполнителю (который не может залогиниться в Keycloak) — задача физически
не виснет в БД, но виснет ПРОДУКТОВО: никто не может её увидеть/забрать,
пока владелец/админ не заметит вручную и не создаст `substitution_rule`
или не переназначит роль.

### 1.5 Иерархия подчинения людей (E2/E3) — честно НЕ в этом срезе

Проверено: `department` (migration 014) — только дерево подразделений
(`parent_id` на department, adjacency list). **У `employee` нет `manager_id`
/ `supervisor_id` / `reports_to`.** Единственный существующий «эскалация»
примитив в коде — плоский прыжок «роль пуста → tenant-owner» (F6/PD-10,
`findTenantOwnerSlug`), НЕ обход дерева подразделений и НЕ иерархия людей.
«Директор-вершина», «мой руководитель», эскалация по цепочке руководителей —
требует НОВОЙ модели данных (поле на `employee` + миграция + вся семантика
«кто чей руководитель», включая многоролевых сотрудников и конфликты при
смене оргструктуры). Это самостоятельная задача корневого объёма, вынесена в
§6 needs_design, в этот срез не включается.

## 2. Функциональные требования (МИНИМАЛЬНЫЙ вертикальный срез)

### FR-1 — Claim-eligibility учитывает Tier-2 substitution

`POST /api/inbox/:id/claim` (и, если применимо, эквивалентный write-путь для
инстанс-тасков) ДОПОЛНИТЕЛЬНО (additively) проверяет: если заявленный
`taskRole` не входит в `myRoles`, но существует эффективное
`substitution_rule` с `substitute_employee_id = актёр`, `role_id` =
роль задачи (по slug), в силе на `nowMs`, и покрывающее орг-область задачи —
claim РАЗРЕШЁН. Источник — уже существующий `getActiveSubstitutionsForEmployee`/
`getActiveSubstitutionsByRole` (substitution-dao.ts), без изменения их
контракта.

### FR-2 — Резолв держателей роли и fallback-owner исключает деактивированных

`getHoldersForRole` и `findTenantOwnerSlug` (`grants-dao.ts`) ДОПОЛНИТЕЛЬНО
фильтруют `e.deactivated_at IS NULL`. Деактивированный сотрудник никогда не
попадает в пул держателей роли и никогда не становится fallback-исполнителем,
даже если у него формально есть действующий `role_assignment`.

### FR-3 — Деактивация активного держателя роли, при наличии активного
`substitution_rule`, где он — `absent_employee_id`, немедленно перенаправляет
его задачи на `substitute_employee_id` (без ручного вмешательства). Это уже
частично покрыто путём B (`resolveExecutorFallbackBatch`) + FR-2 (деактивация
убирает его из raw-пула holders) — задача этого пункта: подтвердить и
закрыть тестом сквозной случай «деактивирован БЕЗ substitution_rule» → см. FR-4.

### FR-4 — Эскалация при пустой роли/деактивации без замещения

Если после применения FR-2/FR-3 эффективный пул исполнителей для роли пуст
(роль никогда не заполнялась ИЛИ единственный держатель деактивирован и не
имеет активного `substitution_rule`), задача маршрутизируется на fallback-
исполнителя (существующий F6/PD-10 путь: tenant owner, ЕСЛИ owner сам не
деактивирован — FR-2 покрывает это). Если и fallback-owner недоступен
(деактивирован/не существует) — результат `kind: "unresolvable"`
(`executor-resolver.ts` уже это возвращает); инбокс/проекция ОБЯЗАНА
показать это состояние явно (не молча проглотить задачу), например тем же
полем `routed_to_fallback`/явным индикатором «нет доступного исполнителя» —
без придумывания новой семантики сверх уже определённой `FallbackReason`.

### FR-5 — Порт активного пути B применяется single-task резолверу либо
задача явно ограничивается путём B

Так как прод сегодня реально работает через путь B
(`resolveExecutorFallbackBatch` в `inbox.ts`), а не через `resolveExecutor`
(путь A, порт `dormant`), эта задача НЕ обязана «подключать»
`ResolverDeps.substitution` в пути A, если путь A не используется ни одним
реальным write/read-путём в проде. Единственное обязательное условие:
FR-1..FR-4 реализуются в РЕАЛЬНО исполняемом коде (путь B и/или
claim-эндпоинт), а не только в pure-функциях пути A. Если по факту
проектирования (фаза DESIGN) окажется, что путь A всё-таки вызывается
где-то ещё (не обнаружено при разведке) — architect обязан это заметить и
подключить порт там тоже.

### FR-6 — UI замещения: подтверждение существующего пути, без новой стройки

`SubstituteForm`/`SelfAbsenceForm` (`/rights/intents`) уже позволяют
назначить замещение из UI. Эта задача НЕ обязана строить новый экран.
Единственное необходимое дополнение UI — если приёмка (см. §4 LIVE_PROOF)
обнаружит, что назначенное через существующую форму замещение не отражается
понятно в инбоксе заместителя (например, нет пометки «эта задача — по
замещению за X»), добавить минимальную индикацию в карточку задачи
(`inbox.ts`/frontend), используя уже существующее поле
`kind: "substitution"` из `ExecutorResolution`/аналогичный маркер из пути B
— без нового экрана, без новой модели.

## 3. Нефункциональные требования

- **NF-1 (D-064 анти-кейс).** Никаких кейс-литералов (слаги ролей/лиц/
  бизнес-порогов конкретного кейса) в `src/`. Правки в `grants-dao.ts`,
  `inbox.ts`, `substitution-dao.ts` — только структурные предикаты
  (`deactivated_at IS NULL`, join на `substitution_rule`), не привязанные к
  конкретным slug'ам ролей/сотрудников.
- **NF-2 (аддитивность).** Изменения в `getHoldersForRole`,
  `findTenantOwnerSlug`, `getRoleSlugsForActor`, claim-эндпоинте — добавление
  условия в существующий SQL/логику, БЕЗ смены сигнатур экспортируемых
  функций и БЕЗ удаления существующих полей ответа.
- **NF-3 (параллельная безопасность).** T-0586 (`src/runtime/agent-dispatch/**`)
  и T-0587 (assistant-analyst/registry-digest) выполняются параллельно.
  T-0588 не трогает эти пути. Общие модули (`grants-dao.ts`,
  `executor-resolver.ts`, `substitution.ts`, `substitution-dao.ts`,
  `inbox.ts`) — правки строго additive (мержатся без конфликта логики).
- **NF-4 (миграции).** Следующий свободный номер после `127` — уточняется
  architect'ом на момент DESIGN (на момент SPEC — 128; при коллизии с
  T-0586/T-0587 разрешается последним мержем согласно инструкции задачи).
  Эта задача, по факту разведки, **вероятно НЕ требует новой миграции**
  (FR-1..FR-4 — это SQL-предикаты и код, не новая структура данных); если
  architect найдёт необходимость в структурном изменении — обосновать
  отдельно.
- **NF-5.** `tsc --noEmit`, eslint, `npm run fitness`, `npm run fitness:db`
  зелёные после изменений.
- **NF-6.** Существующие тесты `executor-resolver.test.ts`,
  `substitution.test.ts`, инбокс-тесты (claim/fallback) остаются зелёными
  без модификации их существующих ожиданий (только дополняются новыми
  кейсами).

## 4. Out of scope (явно НЕ делаем в этой задаче)

- **O1.** Иерархия подчинения ЛЮДЕЙ (`manager_id`/«мой руководитель»,
  директор-вершина, многоролевой сотрудник с конфликтующими руководителями) —
  §1.5. Новая модель данных, отдельная задача (needs_design, см. §6).
  Существующая эскалация «пустая роль → tenant owner» остаётся ЕДИНСТВЕННЫМ
  эскалационным путём в этой задаче; обход дерева подразделений/
  руководителей НЕ вводится.
- **O2.** Унификация путей A (`resolveExecutor`) и B
  (`resolveExecutorFallbackBatch`) в единый резолвер — рефакторинг, не
  требуется для LIVE_PROOF этой задачи (см. FR-5).
- **O3.** UI для CRUD над `substitution_rule` (список активных замещений,
  редактирование, досрочная отмена) — форма СОЗДАНИЯ уже есть
  (`/rights/intents`); просмотр/отмена — future.
- **O4.** Chained substitutions (A→B→C) — T-0035/T-0429 явно фиксируют
  single-hop-only; не переоткрывается.
- **O5.** Автоматизация «увольнение (hard-delete) сотрудника» — эта задача
  работает с уже существующей мягкой деактивацией (`deactivated_at`,
  T-0583/T-0628); hard-delete — отдельный owner-only путь, не меняется.
- **O6.** SLA-эскалация (по таймауту) — явно отклонена ещё в
  executor-resolver.ts комментарии («phase 3, D rejected»), не переоткрывается.
- **O7.** Email/уведомления о том, что задача досталась заместителю — вне
  охвата (нет email-контура в проекте, по прежним директивам).

## 6. Needs-design / follow-up рекомендации (НЕ блокируют эту задачу)

- **ND-1 — Иерархия подчинения людей (E2).** Новая модель данных: вероятно
  `employee.manager_id` (self-FK) + правило «директор-вершина» (либо
  единственный узел с `manager_id IS NULL`, либо явная роль
  `tenant-director`). Открытые вопросы для фаундера/architect (уже
  зафиксированы в карте примитивов E2 как «вопрос фаундера без ответа»):
  может ли сотрудник быть многоролевым с разными руководителями по разным
  ролям; как задаётся «директор-вершина» (единственность, смена); что
  происходит при циклах/реорганизации. **Рекомендация: отдельная задача
  следующей волны**, НЕ в этом срезе.
- **ND-2 — Эскалация вверх по дереву подразделений (E3), НЕ к tenant-owner
  напрямую.** Сегодня единственный fallback — плоский прыжок к
  `tenant-owner`. Полноценная эскалация «к непосредственному руководителю,
  затем выше» требует ND-1 как предпосылку. Пока ND-1 не решено, F6/PD-10
  (tenant-owner fallback, уже покрыт FR-2/FR-4 этой задачи) — единственный
  практически достижимый эскалационный путь.
- **ND-3 — Унификация путей A/B резолвера.** `resolveExecutor` (path A) и
  `resolveExecutorFallbackBatch` (path B) решают одну задачу двумя
  независимыми кодовыми путями с разной степенью актуальности. Рекомендация:
  технический долг на рефакторинг-волну (не продуктовая задача, не
  блокирует эту).
- **ND-4 — Просмотр/управление активными substitution_rule из UI.** Сейчас
  можно только СОЗДАТЬ правило; нет экрана «мои активные замещения» /
  «кто сейчас меня замещает» / досрочная отмена. Рекомендация: future task
  (не в этом срезе, форма создания достаточна для LIVE_PROOF AC-8/AC-9).
