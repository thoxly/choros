# Спека: Исполняемый набор элементов процесса + настройка + бесшовность (D8 · Трек R)

> Реальный процесс собирается из **исполняемых** элементов, и каждый элемент
> настраивается **против полей приложения**. Это фундамент, на который садится
> текст-генерация (D8 · Трек G — `text-first-solution-builder.spec.md`).
>
> Решения: [../product-decisions.md](../product-decisions.md) PD-21, PD-22, PD-23.
> Связано: `process-execution-model.spec.md` (D4 — agentTask/диспетчер, НЕ дублируем),
> `forms-data-contract-foundation.spec.md` (D7 — каталог контрактов привязки),
> `honest-empty-no-hardcode.spec.md` (палитра). Статус: спека · 2026-06-25.

## 1. Зачем
Сегодня движок исполняет **тонкий** набор: start/end, userTask, exclusiveGateway+условие,
sequenceFlow. Хватает на линейное согласование, но не на «нормальный процесс»: нет
параллельности, нет таймеров/дедлайнов, нет ожидания внешних событий, привязка к роли не
выражается дорожкой, agentTask деплоится но не исполняется. Цель Трека R — довести
исполняемый набор до v1 (решение фаундера 2026-06-25: «без дорожек/шлюзов/таймеров нормальный
процесс не собрать») и сделать **каждый элемент настраиваемым против данных приложения** —
бесшовность процесс↔приложение — несущая зона ответственности продукта.

## 3. Дизайн

### 3.1 Исполняемый набор v1 (PD-22)
**Свободная топология** (не шаблоны) из набора: start/end · userTask · agentTask · serviceTask ·
exclusiveGateway · **parallelGateway** · sequenceFlow+условие · **timer/boundary** ·
**message/signal** (catch/throw). **НЕ в v1:** под-процесс, цикл/мульти-инстанс, инклюзивный
шлюз. Линтер расширяется ровно на этот набор; всё вне — отлетает на publish (гард честен).

### 3.2 Параллельный шлюз (R1)
Flowable исполняет AND-split/join нативно. Наша работа: **проекция/инбокс под несколько
одновременно активных задач одного инстанса** (engine-drive реконсиляция нескольких токенов —
расширение того, что для одного active-узла), линтер-coherence для parallelGateway (по аналогии
T-0436), карточка процесса показывает конкурентные ветки.

### 3.3 Дорожка → роль (R2)
Capability исполняется — нужен **визуал**. Завайрить `laneSet`/`lane` ↔ `candidateGroups` задач
внутри неё: положил userTask в дорожку «Бухгалтер» → `candidateGroups=role:бухгалтер`. Резолв
уже есть (`executor-resolver`). Палитра возвращает **lane как РАБОЧИЙ** элемент (pool остаётся
вне набора — нет cross-pool семантики в v1).

### 3.4 Таймер / дедлайн + эскалация (R3)
Boundary/intermediate timer на Flowable + проекция срабатывания. **Связать с T-0432:** таймаут
шага/ожидания → эскалация (руководитель/овнер, §4.5 process-execution-model) с предзаполненной
формой (F5 / `defer-inbox-producer.slaMinutes`). Конфиг элемента: срок (длительность/дата) +
действие при срабатывании (кому эскалация).

### 3.5 События сообщений/сигналов (R4) — PD-23
**Принцип: не второй транспорт.** Сообщение = конверт `{ tenant, messageName, correlationKey,
payload, source }`; **корреляция по бизнес-ключу из поля записи** (бесшовность встроена в
корреляцию). Tenant-fail-closed: корреляция **только внутри тенанта** (RLS + tenancy §9
«fail-closed в async/фоне»). Cross-tenant корреляция — никогда.

Источники **v1**: (a) **внешний человек** — токен-поверхность T-0122 (подписал/загрузил →
сообщение в коррелированный инстанс; токен уже привязан к записи→инстансу, авторизация не
дублируется); (b) **внутренний сигнал** — смена статуса записи / другой процесс (broadcast
внутри тенанта по signal-name). **Транспорт = Pull (PD-23): нового входящего эндпоинта нет.**
Коннектор-pull (опрос внешней системы, T-0128) — **шов закладываем в v1, polling-драйвер =
Stage-2**.

**Throw (отправка)** = `invoke`-грант на `effect_resource` (T-0034) через канал
(notifications/email) / коннектор; payload из полей записи. Отправка управляется той же
грант-моделью.

**BPMN:** message catch (`receiveTask`/`intermediateCatchEvent` — виды уже в
`inflight-migration.ts`) ждёт; signal catch/throw = broadcast по signal-name. Flowable
корреляцию умеет — наша работа: **подать сообщение + спроецировать ожидание в инбокс + загейтить
грантом**, не писать корреляционный движок.

**Сцепка:** message-catch **обязан** иметь таймаут (R3) — иначе вечное ожидание.

### 3.6 agentTask живой (R5) — НЕ дублируем
agentTask = **реализовать** `process-execution-model.spec.md` (D4): диспетчер берёт job → грузит
права+LLM агента → precheck-motor → в пределах `autonomy_threshold` закрывает шаг сам, иначе
defer→человек (эскалация-форма). Worker-auth = T-0328. Эта спека НЕ переписывает D4 — только
включает agentTask в исполняемый набор (3.1) и в настройку элемента (3.7).

### 3.7 Настройка каждого элемента = бесшовность (R6) — PD-22
Типизированная **панель свойств по типу элемента**; почти каждое свойство ссылается на поля
приложения (`registry_def`):

| Элемент | Что настраивается (тянется к данным приложения) |
|---|---|
| start | триггер: on_create / лаунчер / вручную |
| userTask | **роль** (дорожка), **форма**, видимые/редактируемые **поля**, **что пишет в запись** |
| agentTask | **агент**, порог автономии, системный промт, какие **поля** читает/пишет, fallback→человек |
| exclusiveGateway | **условие**: поле приложения + оператор + значение (E16) |
| parallelGateway | split/join — без параметров |
| timer/boundary | срок + действие при срабатывании → **эскалация кому** |
| message/signal | имя сообщения · корреляция = **какое поле записи** · throw: канал/коннектор + payload из полей |
| end | финал + что фиксируется в записи |

Один контракт настройки — **два драйвера** (человек в панели / бот D8). Привязки переиспользуют
каталог контрактов D7 (`forms-data-contract-foundation`) и `form_binding`.

### 3.8 Бесшовная публикация (зависимость сквозного прогона)
**B19:** автоген ключа процесса при первом save (slug из имени / uuid) ИЛИ publish =
save+assign-key+deploy одним кликом. **B16:** mode-aware резолвер актора на process-start (как
s39-роуты). Без них «запусти на записи» не закрывается — отметить зависимостями journey (G6).

## 4. Инвентарь работ → задачи
- **R1** параллельный шлюз (проекция конкурентных токенов + линтер-coherence).
- **R2** дорожка→роль (визуал `lane` ↔ `candidateGroups`).
- **R3** таймер/дедлайн + эскалация (с T-0432).
- **R4** события сообщений/сигналов (Pull; внешний человек T-0122 + внутренний сигнал;
  коннектор-pull шов; корреляция + receiveTask-вайринг + проекция ожидания в инбокс).
- **R5** agentTask живой = реализовать D4 (`process-execution-model`) + T-0328 worker-auth.
- **R6** настройка элементов + биндинг к полям (каталог D7).
- Зависимости сквозного прогона: **B19** бесшовный publish, **B16** process-start auth.

## 5. Открытое к уточнению на импле
- Хранение конфига элемента: `choros:*` extension в process-def XML vs боковая
  per-element-config таблица.
- Модель внутреннего сигнала: событие записи vs явный throw в другом процессе — выбрать на R4.
- Коннектор-pull: частота/идемпотентность опроса — на Stage-2 драйвере.

## 6. Последовательность
1) **R6** (настройка+биндинг) + **R2** (дорожка→роль) — фундамент, ссылки на данные.
2) **R1** (параллельный) + **R3** (таймер) + **R4** (сообщения, Pull) — расширение топологии.
3) **R5** (agentTask живой = D4).
Затем Трек G (текст-генерация) садится поверх исполняемого набора.
