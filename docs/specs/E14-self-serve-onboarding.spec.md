## 1. Бизнес-интент

Продать/раздать Choros нельзя, пока новый человек не может **сам** завести рабочее место без
участия фаундера. Сегодня вход в продукт — это dev-пикер персон демо-компании (showcase): он
доказывает движок, но НЕ является онбордингом. Эпик E14 замыкает петлю самообслуживания:

**аноним → «Создать организацию» (орг+email+пароль) → сразу вошёл → свой ЧИСТЫЙ тенант →
собрал первое приложение на конструкторе (E13) → данные в БД его тенанта.**

Это прямой вклад в столп «изолированное внедрение» и в бизнес-цель фаундера (соло-продукт,
который может расти без ручного заведения клиентов). Демо-стенд, отработав роль витрины
движка, теперь **мешает рулить** (заслоняет реальное состояние продукта mock-данными) —
поэтому его вывод входит в этот же эпик.

## 2. Проверенное состояние кода (разведка, не память)

Всё ниже прочитано в дереве на ветке `task/T-0694` (от dev), не выдумано.

### 2.1 Механизм регистрации — ПОСТРОЕН (покрывает T-0303)

- **Keycloak-режим vs self-registration.** Realm-фикстура `config/keycloak/realm-choros.json`
  держит `"registrationAllowed": false` (встроенная KC-страница регистрации ОТКЛЮЧЕНА) и
  вместо неё — конфиденциальный сервис-аккаунт-клиент **`choros-registrar`**
  (`serviceAccountsEnabled: true`, роли `manage-users`/`view-users`/`manage-clients` на
  realm-management). То есть выбран **кастомный signup через KC Admin API**, а НЕ встроенная
  self-registration KC. Это и есть решённая развилка T-0303 (§4 честно разбирает trade-offs).
- **Порт.** `src/keycloak/admin-port.ts::KeycloakUserPort` — `createHumanUser` (POST
  `/admin/realms/<realm>/users`, ставит `actor_type=["human"]` + пароль) и `deleteUser`
  (компенсация). Живая реализация `makeHttpKeycloakUserPort()`; при отсутствии
  `KC_REGISTRAR_CLIENT_SECRET` сервер подставляет honest-degrade-порт (всё → `AUTH_UNAVAILABLE`/503).
- **БЕЗ email-верификации.** `createHumanUser` не запрашивает verify-email; realm
  `resetPasswordAllowed: true`, но verify-email flow не включён — соответствует директиве.

### 2.2 Public signup API — ПОСТРОЕН (покрывает T-0304)

- **`POST /api/register`** — публичный (БЕЗ `withAuth`, pre-login), тонкий HTTP-адаптер
  `src/http/register.ts` над чистым ядром `src/core/register.ts::registerTenant`.
- **Один атомарный поток** (`registerTenant`, §3 ADR access-and-tenant-zero):
  KC-first (`createHumanUser`) → DB-транзакция в скоупе нового тенанта (`SET LOCAL
  choros.tenant_id`) → INSERT `tenant` (self-ref `tenant_id=id`) + роль `tenant-owner` +
  `employee(slug=kcSub, kind='human')` + confirmed `role_assignment` (source `registration`),
  плюс tenant-zero seeding (роль-конфигуратор, assistant-agent + agent_card,
  role-reader + tenant-wide READ-грант, role-constructor-admin, process_designer — все
  СЕМЕНА, часть auto-assigned владельцу, часть seeded-but-unassigned).
- **Идемпотентность / коллизии.** Слаг-коллизия (23505) ретраится до 5 раз со случайным
  суффиксом (две одноимённые орг-ы регистрируются обе). При исчерпании — компенсация
  (`kc.deleteUser`) + `409 ORG_TAKEN`. Компенсация KC-юзера при любом DB-сбое после
  KC-create (FF-2).
- **Лёгкая защита от абуза — НЕ реализована.** В `register.ts`/`server.ts` нет rate-limit,
  throttle или captcha (grep пуст). Стенд на Tailscale (не публичный интернет), поэтому это
  сегодня приемлемо — но T-0304 просит «лёгкую защиту от абуза», а её нет → **открытый
  вопрос фаундеру Q1 (§8)**, НЕ решается этой спекой.
- **Маппинг ошибок:** `400 VALIDATION` / `409 EMAIL_TAKEN` / `409 ORG_TAKEN` /
  `409 LOGIN_RESERVED` (T-0633 анти-коллизия с seeded-персонами) / `503 AUTH_UNAVAILABLE` /
  `500 INTERNAL`.
- **Server wiring** (`src/server.ts`): `registerRegisterRoutes` + `registerUserMgmtRoutes`
  используют ОДИН `kcUserPort` (self-reg И per-tenant «завести учётку», N5).

### 2.3 Signup UI — ПОСТРОЕН (покрывает T-0305)

- **Экран** `web/src/screens/screen-register.jsx` (T-0342): поля «Название организации ·
  Email · Пароль»; на 201 → `kc.login()` (PKCE-редирект) → пользователь входит в свой тенант.
- **Чистая логика формы** `web/src/screens/register-form.js`: `validateRegisterForm`
  (orgName 1..120, email RFC-lite, пароль ≥8), `mapRegisterError` (внятные RU-сообщения:
  «Пользователь с таким email уже зарегистрирован», «Организация с таким названием уже
  существует», «Сервис регистрации временно недоступен» и т.д.), `postRegister`.
- **Роутинг** `web/src/app-shell/shell.jsx`: `/register` — публичный pre-auth роут, отдаётся
  ДО login-гейта; ссылка «Войти» → `/`.
- **Юниты:** `web/src/screens/register-form.test.js`.

### 2.4 First-run пустого workspace — ЧАСТИЧНО (покрывает T-0306)

- Новый тенант стартует **функционально чистым**: `registerTenant` сидит только служебные
  роли/агента/READ-грант, НО **0 бизнес-данных** (0 departments, 0 positions человеко-
  сотрудников, 0 приложений/разделов, 0 записей, 0 процессов).
- **Empty-state конструктора существует, но не полон.** Есть, напр.,
  `web/src/screens/screen-sections.jsx` (`EmptyState` «Раздел — папка боковой панели
  "Работа". Создайте первый и положите в него приложения.») и `FormBuilder.jsx`. Но
  ЕДИНОГО, срежиссированного first-run onboarding-нарратива «ты только что создал орг —
  вот 3 шага» нет → остаточная работа §7.C.

### 2.5 Что такое «мок-демостенд» СЕГОДНЯ (объект вывода)

Демо-стенд — это НЕ один флаг, а **четыре механизма display-plane-моков** для seeded
dev-сило (`DEV_TENANT_ID = a0000000-0000-0000-0000-000000000001`):

1. **In-memory mock-массивы** в http-хендлерах, керенные на `DEV_TENANT_ID`/`OTHER_TENANT_ID`.
   Эталон — `src/http/inbox.ts::INBOX_SEED` (11+ хардкод-задач «Проверить реквизиты счёта
   №4471» и т.п. + `OTHER_TENANT_ID`-строка для доказательства изоляции). Аналогичные
   fallback-константы (`ORG_SEED`/`PROCESSES_SEED`/`RIGHTS_SEED`) в ряде экранов.
2. **`DEV_TENANT_ID` display-plane fallback** в ~25 хендлерах (`grep DEV_TENANT_ID src/http`).
   ВАЖНО: авторизационный резолвер `resolveActorTenant` (`src/db/org.ts`) уже НЕ падает на
   `DEV_TENANT_ID` (fail-closed, T-0366) — речь ТОЛЬКО о display-plane-моках, не о security.
3. **Seed-паки** `seed/showcase/pack.json` (showcase-компания, T-0140/T-0141) и
   `seed/demo/tel-scenario.*` (ТЭЛ-сценарий).
4. **«демо»-бейджи** в навигации (`shell.jsx`, напр. «Каталог ролей» status:`demo`,
   demoTooltip «данные иллюстративные»).

Вывод демостенда = сделать так, чтобы **новый self-reg тенант не видел НИ ОДНОГО** из этих
моков, при этом не сломав существующие приёмки, которые всё ещё опираются на dev-сило (§7.B).

### 2.6 Инфраструктура auth-режима

- `CHOROS_AUTH_MODE` читается лениво в `src/http/auth.ts` (default `dev`; единственная точка
  ветвления, AC-17). `docker-compose.yml` (app-сервис): `CHOROS_AUTH_MODE=${...:-dev}`, а
  `KC_REGISTRAR_CLIENT_ID`/`KC_REGISTRAR_CLIENT_SECRET`/`KEYCLOAK_BASE_URL`/`KEYCLOAK_REALM`
  **уже прокинуты с dev-дефолтами**. То есть флип на keycloak — это изменение ОКРУЖЕНИЯ
  (одна переменная) + realm уже импортируется on-start; кодовой доработки регистрации не
  требуется.
- T-0291 (обёртка SPA-роутов в `withAuth` для keycloak-режима) — **done**. Гейт снят.

## 4. Развилка T-0303: KC self-registration vs кастомный signup (решено + trade-offs честно)

Задача T-0303 явно ставит выбор: «Keycloak self-registration ЛИБО кастомный signup,
создающий KC-юзера». **Реализованное решение: кастомный signup через KC Admin API**
(`registrationAllowed:false` + `choros-registrar` сервис-аккаунт + `POST /api/register`).
Ниже — честный разбор, почему, и что мы этим теряем.

### Вариант A — встроенная KC self-registration (`registrationAllowed:true`)
- **Плюсы:** ноль кастомного signup-кода; KC сам держит форму, флуд-защиту, verify-email,
  password-policy, брутфорс-детектор; стандартный, аудируемый identity-путь.
- **Минусы (почему НЕ выбран):**
  - KC создаёт ТОЛЬКО identity-юзера — он НЕ создаёт **тенант Choros + оргструктуру + tenant-
    zero seeding**. Нужен пост-хук/first-login flow, который всё равно вызывает нашу
    provisioning-логику. Разрыв «KC создал юзера» ↔ «Choros создал тенант» — источник
    рассинхрона (юзер есть, тенанта нет).
  - Поле «Название организации» — не стандартное KC-registration-поле; нужен кастомный theme
    или user-attribute-хак.
  - Транзакционная атомарность (юзер+тенант+owner+seed за один поток с компенсацией)
    недостижима, когда создание юзера живёт в KC-редиректе, а не под нашим контролем.

### Вариант B — кастомный signup через Admin API (**ВЫБРАН, построен**)
- **Плюсы:** один атомарный поток `registerTenant` (KC-first → DB-tx → компенсация при сбое);
  «Название организации» — обычное поле нашей формы; полный контроль над tenant-zero seeding;
  единый `kcUserPort` переиспользуется для per-tenant «завести учётку» (N5).
- **Минусы (что теряем, честно):**
  - Мы САМИ отвечаем за то, что KC делал бы бесплатно: **rate-limit / anti-abuse / captcha**
    — сейчас ОТСУТСТВУЕТ (§2.2, Q1). На Tailscale-стенде терпимо; для публичного интернета —
    красная зона.
  - `choros-registrar` — конфиденциальный клиент с `manage-users`: его секрет — чувствительный
    актив (сейчас dev-дефолт `choros-registrar-dev-secret`, RL-1; для прода — реальный секрет,
    вне git).
  - Password-policy KC (длина/сложность/брутфорс) не применяется автоматически на нашем пути —
    мы валидируем только «≥8 символов» клиентски+серверно; KC-policy-enforcement на
    Admin-API-create надо проверять отдельно (открытый пункт §10).

**Trade-off по анти-абузу — ОТКРЫТЫЙ ВОПРОС ФАУНДЕРУ (Q1, §8), НЕ решается спекой.** Открытая
регистрация даже на Tailscale = потенциальные спам-тенанты; rate-limit/captcha — продуктовое
и операционное решение (влияет на UX и на порог входа), поэтому эскалируется, а не выбирается
здесь.

## 5. Тенант-изоляция нового workspace (0 мок-данных, genesis-владелец)

Инварианты, которые НОВЫЙ self-reg тенант обязан удовлетворять (не нарушая T-0013):

- **FR-ISO-1 — самореферентный tenant.** `registerTenant` пишет `tenant(tenant_id=id)`;
  вся вставка идёт под `SET LOCAL choros.tenant_id = '<новый>'`, RLS WITH CHECK проходит.
- **FR-ISO-2 — владелец = genesis-owner СВОЕГО тенанта.** `employee.slug == kcSub`,
  confirmed `role_assignment` на `tenant-owner`, `source='registration'`; `granted_by ==
  confirmed_by == сам` (self-bootstrap). Владельческий гейт org-write проверяется против
  тенанта ВЫЗЫВАЮЩЕГО (`isGenesisOwnerForTenant`), НЕ против `DEV_TENANT_ID`
  (access-and-tenant-zero §3.1, done).
- **FR-ISO-3 — 0 бизнес-данных.** Ни один seed-пак (showcase / tel-scenario) НЕ применяется к
  self-reg тенанту. In-memory mock-массивы (INBOX_SEED и родня) керены на `DEV_TENANT_ID` —
  их выборка для НОВОГО тенанта обязана вернуть пусто.
- **FR-ISO-4 — служебный tenant-zero seeding ≠ бизнес-данные.** role-configurator,
  assistant-agent (+agent_card), role-reader + tenant-wide READ-грант, role-constructor-admin,
  process_designer — это ПЛАТФОРМЕННЫЙ каркас прав (чтобы конфигуратор/ассистент/чтение
  работали в пустом тенанте), а не «мок-контент». Он остаётся (иначе конфигуратор недоступен —
  урок access-and-tenant-zero §1).
- **FR-ISO-5 — нет cross-tenant утечки.** Данные нового тенанта не видны из `DEV_TENANT_ID` и
  наоборот (T-0013 AC-6/AC-7). Адверс-тест уже существует:
  `src/__tests__/register-tenant-isolation.adversarial.test.ts` +
  `ci/checks/db/register-tenant-isolation.adversarial.test.ts` (T-0427).

## 6. Границы эпика (что НЕ делаем)

Явно out of scope для E14 (директива + соразмерность):

1. **Email-верификация** — «почту пока не прикручиваем» (директива). Нет verify-email flow,
   нет SMTP-зависимости. (Смежно: «Забыли пароль» через SMTP — тоже вне E14; см.
   память `choros-founder-cred-lockout-2026-07-06`.)
2. **Биллинг / тарифы / квоты** — Stage-2 (choros-customer-subscription-mgmt), не здесь.
3. **Публичный интернет-хостинг** — стенд на Tailscale; DNS/TLS-hardening/публичный go-live —
   отдельно.
4. **Anti-abuse механизм (rate-limit/captcha)** — сам механизм НЕ строим в этой спеке;
   решение о нём — открытый вопрос Q1 фаундеру. (Если фаундер скажет «нужен» — отдельная
   follow-up задача.)
5. **Конструктор E13** — это ЗАВИСИМОСТЬ (шаг J7), не поставка E14. E14 доводит человека ДО
   конструктора с пустым тенантом; сам конструктор — свой эпик.
6. **Полное удаление seed-паков/showcase из репозитория** — showcase остаётся как
   dev-инструмент/приёмочная фикстура (§7.B); «вывод» = новый тенант их не видит + они не
   всплывают в проде, а НЕ `rm -rf seed/`.
7. **Смена self-reg → Enterprise SSO / внешние IdP** — вне MVP.

## 7. Остаточная работа эпика (реальные щели поверх T-0342)

Три вертикали. Это ЕДИНСТВЕННОЕ, что осталось закрыть, чтобы journey §3 был зелёным на деплое.

### 7.A — Флип `CHOROS_AUTH_MODE=keycloak` на dev + live-proof journey (ядро приёмки)

- Установить `CHOROS_AUTH_MODE=keycloak` на dev-стенде (переменная уже проброшена в compose;
  KC realm импортируется on-start; registrar-секрет уже дефолтится). Проверить, что
  `POST /api/register` в keycloak-режиме реально создаёт KC-юзера (registrar-порт живой, не
  honest-degrade) и что PKCE-login после 201 доводит до входа.
- **Не менять** дефолт compose вслепую, если это уронит существующие dev-приёмки, которые
  живут в dev-режиме (x-dev-user). Решение о том, становится ли keycloak дефолтом dev-стенда
  ИЛИ включается точечно для приёмки E14 — часть Q2 фаундеру (§8), т.к. это трогает как рулят
  стендом.
- Live-proof: реальный браузер (Playwright, реальная KC-форма — паттерн из
  `choros-acceptance-t0583-users-2026-07-04`): аноним → `/register` → заполнил → 201 → вошёл →
  пустой workspace → собрал приложение (E13) → строка в БД его тенанта.

### 7.B — Вывод мок-демостенда (не сломав приёмки)

- **Цель:** новый self-reg тенант видит 0 моков (§2.5); демо-данные не всплывают в проде.
- **Механика (соразмерно, дизайн-свобода impl):**
  - In-memory mock-массивы (INBOX_SEED и родня, керенные на `DEV_TENANT_ID`) обязаны
    возвращать пусто для любого тенанта ≠ `DEV_TENANT_ID`. Проверить/убедиться для КАЖДОГО
    хендлера, что fallback-seed не «протекает» новому тенанту.
  - Демо-данные (showcase / tel-scenario / «демо»-бейджи) не должны появляться в
    keycloak/prod-режиме. Предпочтительный подход — **гейт демо-контента флагом окружения**
    (напр. новый тенант просто не имеет seed-данных; showcase остаётся только для явно
    seeded dev-сило `DEV_TENANT_ID`), а НЕ хирургическое удаление кода из репо.
- **Как не сломать существующие приёмки:** множество текущих dev-приёмок логинятся под
  showcase-персонами в `DEV_TENANT_ID` и опираются на эти моки. Поэтому «вывод» = **сделать
  моки видимыми ТОЛЬКО для явного dev-сило `DEV_TENANT_ID`**, а не глобально снести. Тогда:
  (а) self-reg тенант чист; (б) старые приёмки, работающие против `DEV_TENANT_ID` в dev-режиме,
  продолжают видеть showcase. Полное списание showcase-паков — отдельное решение позже.
- Открытый под-вопрос (в Q2): держим ли showcase-стенд как «песочницу-демо» параллельно или
  выводим совсем — это про то, как фаундер рулит стендом.

### 7.C — Полировка first-run пустого workspace (T-0306 residual)

- Срежиссированный empty-state для ТОЛЬКО-ЧТО созданного тенанта: внятная подсказка «Вы
  создали организацию — соберите первый раздел/приложение», ведущая в конструктор E13. Не
  голая пустая таблица (§2.4). Опереться на существующие kit-`EmptyState` (screen-sections,
  FormBuilder) — свести к единому onboarding-нарративу, не изобретать виджет.

## 8. Открытые вопросы фаундеру (НЕ решаются этой спекой)

- **Q1 — Anti-abuse на открытой регистрации.** Сейчас `POST /api/register` без rate-limit /
  throttle / captcha. На Tailscale-стенде терпимо, но T-0304 просит «лёгкую защиту от абуза», и
  открытая регистрация = риск спам-тенантов. Нужен ли anti-abuse сейчас (rate-limit по IP?
  captcha? invite-код?), или откладываем до публичного go-live? Это трогает UX-порог входа и
  операционку — продуктовое решение, эскалируется.
- **Q2 — Как рулим стендом при флипе на keycloak + вывод демо.** Становится ли
  `CHOROS_AUTH_MODE=keycloak` дефолтом dev-стенда (тогда dev-пикер персон исчезает, все
  приёмки идут через реальный KC-вход) ИЛИ keycloak включается точечно для приёмки E14, а
  showcase-демо остаётся параллельной песочницей? И: showcase-стенд выводим совсем или держим
  как демо-песочницу? Это про то, как фаундер наблюдает/демонстрирует продукт — граница
  «продукт/деньги», эскалируется.

> Оба вопроса НЕ блокируют написание кода остаточной работы (§7.A/B/C можно начинать при
> дефолтных допущениях: anti-abuse отложен, keycloak включается точечно для E14-приёмки,
> showcase гейтится на `DEV_TENANT_ID`). Они блокируют только финальную политику стенда.

### 10.2 Live-proof journey (обязателен на деплое — сердце приёмки эпика)

**AC-LP** — на dev-деплое в `CHOROS_AUTH_MODE=keycloak`, реальным браузером (Playwright +
реальная KC-форма):
```
аноним → /register → орг+email+пароль → «Создать организацию» → 201
       → PKCE-вход → попал в СВОЙ тенант → workspace пустой (0 мок-данных)
       → собрал первое приложение на конструкторе (E13)
       → GET/DB подтверждает: запись лежит в БД ЕГО тенанта (RLS-изолирована)
```
Зелёный AC-LP = эпик T-0299 закрыт (директива s33, acceptance дословно).
