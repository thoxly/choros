## 1. Контекст

Ревью T-0702 (отзыв KC-сессий при деактивации, `PATCH /api/users/:employee_id`,
`src/http/user-mgmt.ts`) оставило два открытых пункта операционной гигиены:

- **R-4**: провал `kc.revokeUserSessions` писался ТОЛЬКО в
  `payload.kc_sessions_revoked:false` на audit-событии
  `user_account.deactivate` — оператор, читающий логи (не диффящий audit
  trail построчно), не получал НИКАКОГО сигнала, что KC был недоступен в
  момент деактивации. Тихая деградация.
- **R-5**: порядок `setUserEnabled(false)` → `revokeUserSessions` →
  DB-транзакция (ставит `deactivated_at` + пишет audit). Падение
  DB-транзакции ПОСЛЕ успешных KC-вызовов оставляет рассинхрон
  «KC-disabled, но choros всё ещё active» (`deactivated_at IS NULL`) —
  pre-existing разрыв T-0583 (не новый, не введён T-0702). Кроме того, ДО
  этой задачи повторный `PATCH {active:false}` на УЖЕ деактивированной
  учётке безусловно писал ВТОРОЕ audit-событие `user_account.deactivate` и
  ПЕРЕЗАПИСЫВАЛ `deactivated_at` временем повтора — теряя исходное время
  деактивации и засоряя audit-trail дублями при любом ретрае/двойном клике.

## 2. Разведка

- `src/http/user-mgmt.ts:577-797` — единственный write-путь `deactivated_at`
  (см. ADR-T0658 §2.2 / T-0702 §2, подтверждено `grep -rn "SET deactivated_at"
  src/` — ровно одна строка).
- Логирование в этом кодовом слое — БЕЗ отдельной logger-абстракции:
  `console.warn`/`console.error` с префиксом `[<модуль> T-XXXX]`
  (`grep -rn "console\.\(warn\|error\)" src` — единый паттерн, см. например
  `src/http/inbox.ts:1476` `"[inbox T-0458] ... (non-fatal)"`,
  `src/server/timer-firing-loop.ts:132` `"[timer-firing] ... (non-fatal)"`).
  Эта задача НЕ вводит новую logger-абстракцию (соразмерность) — использует
  тот же `console.warn`.
- `kc.setUserEnabled` / `kc.revokeUserSessions`
  (`src/keycloak/admin-port.ts`) уже ИДЕМПОТЕНТНЫ по конструкции: PUT
  `{enabled}` безопасно повторить (KC просто устанавливает то же значение);
  `revokeUserSessions` НИКОГДА не бросает (ADR-T0702 §2.2) и безопасно
  повторяем (повторный logout — не ошибка). Эта задача НЕ меняет их
  реализацию — только опирается на существующее свойство.
- LAST-OWNER guard (T-0658 round 3, `user-mgmt.ts:643-699`) не учитывает
  ТЕКУЩЕЕ состояние деактивации цели — только роль-assignment. Повторный
  no-op PATCH на уже-деактивированной цели мог бы задеть этот guard по
  НЕСВЯЗАННОЙ более поздней смене владельцев (см. §4 ниже).

## 3. Объём (что строим)

1. **R-4 — лог при провале revoke.** Внутри существующего блока
   `if (active === false) { const {revoked} = await kc.revokeUserSessions(...) }`
   — если `!revoked`, `console.warn` с префиксом `[user-mgmt T-0727]`,
   содержащим `employee_id` и `kcUserId`. НЕ меняет поведение (деактивация
   по-прежнему завершается 200) — только добавляет видимость.
2. **R-5 — идемпотентный повтор.**
   - Читаем `deactivated_at` ВМЕСТЕ со `slug`/`kind` в существующем запросе,
     резолвящем целевого сотрудника (без второго round-trip).
   - Если запрошенный `active` УЖЕ совпадает с текущим состоянием
     (`(deactivated_at === null) === active`) — ранний no-op: 200
     `{employee_id, active}`, БЕЗ вызова LAST-OWNER guard, БЕЗ вызова KC, БЕЗ
     записи в DB/audit. Обоснование порядка см. §4в.
   - Если состояние ДЕЙСТВИТЕЛЬНО меняется — существующий поток
     (LAST-OWNER guard → `setUserEnabled` → `revokeUserSessions` (только на
     деактивации) → DB-транзакция) идёт как раньше, с ОДНИМ добавлением:
     финальный `UPDATE` внутри транзакции получает `WHERE ... AND
     deactivated_at IS [NOT] NULL` (симметрично требуемому переходу) +
     `RETURNING id`; audit-событие пишется, только если `UPDATE` реально
     затронул строку (`RETURNING` непустой) — защита от узкой гонки между
     ранним чтением и самой транзакцией (двойной конкурентный PATCH).
3. **Recovery-путь задокументирован в ADR** (см. §4б ниже и
   `docs/design/ADR-T0727-deactivation-hygiene.md` §3): рассинхрон
   «KC-disabled + choros-active» читается КАК РЕАЛЬНЫЙ переход (текущее
   состояние ≠ запрошенное), поэтому повторный `PATCH {active:false}`
   НЕ попадает под no-op-гейт и доводит транзакцию до конца при повторной
   попытке.

## 4. Вне объёма / решённые вопросы

- **(а) Логирование остаётся `console.warn`, не заводит logger-библиотеку.**
  Единственная существующая конвенция в кодовой базе — вводить зависимость
  ради одной строки лога было бы превышением объёма задачи.
- **(б) Recovery-путь остаётся РУЧНЫМ повтором PATCH, не автоматическим
  ретраем/job-queue.** В кодовой базе нет job-queue инфраструктуры (тот же
  вывод, что ADR-T0702 §2.1а для самого revoke-вызова) — заводить её ради
  редкого случая падения DB-tx ПОСЛЕ успешных KC-вызовов было бы
  несоразмерно. Повторный `PATCH {active:false}` (тот же запрос, что
  оператор/клиент уже посылал) — минимальный, уже-существующий интерфейс
  восстановления.
- **(в) No-op короткое замыкание идёт ДО LAST-OWNER guard и ДО KC-вызовов
  (не после).** Если бы guard/KC-вызовы выполнялись даже на уже-достигнутом
  состоянии, повторный PATCH на давно деактивированной цели мог бы получить
  409 `LAST_OWNER` из-за ПОЗДНЕЙ, не связанной с этим запросом смены
  владельцев (цель — единственный сохранившийся `role_assignment` на
  `tenant-owner`, при том что при ОРИГИНАЛЬНОЙ деактивации был другой
  активный владелец, который сам позже деактивирован). Настоящий
  идемпотентный no-op обязан быть БЕЗУСЛОВНО безопасным, независимо от
  несвязанных изменений, случившихся ПОСЛЕ достижения целевого состояния.
- **(г) KC-вызовы НЕ форсируются на no-op-повторе ради самопочинки дрейфа
  KC.** Рассматривался вариант «даже на no-op DB-состоянии всё равно звать
  `setUserEnabled`/`revokeUserSessions`, чтобы подтянуть KC, если кто-то
  вручную включил юзера обратно» — отклонён: это не тот сценарий, что
  называет ревью (recovery-путь — именно «choros ещё active», не «choros уже
  inactive, но KC разошёлся»), и раздувает объём инвариантом, который никто
  не просил. Единственный ИМЕННО ЗАПРОШЕННЫЙ recovery-путь (KC-disabled +
  choros-active) и БЕЗ этого решения проходит: DB там ещё «active», поэтому
  no-op-гейт не срабатывает, весь поток идёт заново.
