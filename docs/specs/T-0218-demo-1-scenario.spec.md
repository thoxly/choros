# T-0218 · DEMO-1 — Сценарий первой демо (исполнимый seed + проход)

> Тип: design (architecture) · spec_ref: `playbooks/v1-demo-and-trust-surface.md#A`
> depends_on: T-0140 (seed-pack «showcase», DONE) · T-0141 (демо-тенант на dev, DONE)
> Опора на эталон: `playbooks/choros-reference-process-tel.md` (ТЭЛ §1/§3/§4)
> Слоты-агенты: T-0219 (intake-agent) · T-0234 (legal-precheck motor, рантайм T-0233)

## 0. Что эта спека фиксирует

Машинно-проверяемые приёмочные критерии **первой демо** Choros: один
**линейный ТЭЛ** (без циклов и исключений — straight-through), который
незнакомый зритель проходит за ~5 экранов, и в который два более поздних
таска (T-0219 / T-0234) вписывают живые навыки агентов в **заранее
размеченные слоты**.

Несущее решение по домену и по «один поток или два» — в ADR
(`docs/design/T-0218-demo-1-scenario.adr.md`). Здесь — контракт приёмки.

**Граница задачи (важно):** это DESIGN-задача. Реализуемая часть — только
**исполнимый seed сценария + написанный проход (walkthrough)**. Сами навыки
агентов НЕ строятся здесь (T-0219 / T-0234) — проектируются их СЛОТЫ.

## 1. Домен (решение фабрики, делегировано фаундером G.1)

Выбран домен **(a) заявка на расход/закупку** — в редакции «упрощённый
линейный ТЭЛ»: заявка на закупку/расход = договорная заявка, проходящая
прямой путь ТЭЛ §1.1→§1.4 без веток. Обоснование яркости триажа — ADR §2.
ITSM-кандидат (b) отклонён (ADR §2.3): его триаж площе и «деньги → кто
обязан согласовать» не нативен, а таймеры/SLA выводят его из класса ТЭЛ
(reference-tel §4).

## 2. Функциональные требования

- **FR-1.** Сценарий = ОДИН линейный ТЭЛ-инстанс из 5 именованных экранов,
  проходимых строго по порядку (без ветвлений в демо-проходе): `S1 Подача` →
  `S2 Триаж` → `S3 Юр-предпроверка (условный гейт)` → `S4 Согласование
  человеком` → `S5 Аудит-floor`.
- **FR-2.** Сценарий реализуется как **расширение showcase-механизма через
  публичные API / importer** (НЕ прямой PG). Demo-seed для actor-плоскости
  (роли/назначения/гранты intake-agent) применяется через `applyPack`-путь
  (importer.ts). Demo-проход (наполнение инстанса) — через скрипт поверх
  публичного API.
- **FR-3.** **Display-плоскость showcase-пакета НЕ раздувается.** Счётчики
  `GET /api/rights → 8` и `GET /api/processes → 8` (FF-PACK-2) остаются
  ровно 8/8. Демо-инстанс ТЭЛ показывается через ПЕРЕИСПОЛЬЗОВАНИЕ
  существующей записи `process_instances` (репозиционирование INS-7731 на
  ТЭЛ-семантику), а не добавлением новой строки. (ADR §6.)
- **FR-4.** **Слот T-0219 (intake-agent)** размечен на экране **S2**: вход =
  поля поданной заявки (предмет, сумма, обоснование); выход = заполненная
  карточка (категория, бюджетная статья, направление, маршрут согласования)
  + reasoning-trace «почему». Контракт слота (имена полей вход/выход,
  reasoning-surface) зафиксирован в ADR §4.1 и в seed как
  `agent_slot.intake`.
- **FR-5.** **Слот T-0234 (legal-precheck)** размечен на экране **S3** как
  **условный гейт**: срабатывает тогда и только тогда, когда
  классифицированная сумма ≥ порога ТЭЛ (5 000 000 ₽). Вход слота =
  `dealContext { amount, kind, direction }` (точная сигнатура мотора
  `runLegalPrecheck`, T-0233); выход = `PrecheckOutcome`
  (proceed / defer-to-human / fail-closed). Контракт слота — ADR §4.2 и seed
  `agent_slot.legal_precheck`.
- **FR-6.** **Moat-момент виден** на S3→S4: агент доводит инстанс до
  согласующего шлюза, но структурно НЕ может сам перейти «Согласовано» —
  переход требует гранта `approve`, которого у роли агента нет (показывается
  на проходе). Это не новый механизм — существующий PDP-deny.
- **FR-7.** **reasoning-trace** агентских шагов (S2, S3) проявлен в проходе
  как отдельная поверхность «почему агент решил X» (D-139: наружу — только
  безопасный answer/метаданные, сырой reasoning — в audit). Демо опирается на
  то, что мотор уже пишет reasoning в audit (T-0233 FR-6), не вводит новый
  egress.
- **FR-8.** **Walkthrough** (`docs/demo/T-0218-walkthrough.md`) — письменный
  5-экранный скрипт прохода: для каждого экрана — кто действует (персона
  X-Dev-User), что видно, какое доказательство §0 v1-demo это закрывает, где
  стоит слот агента. Скрипт ссылается на персон из showcase-пакета (e-* / a-*)
  и на demo-seed-роль intake-agent.
- **FR-9.** **Idempotent / lint-clean.** Demo-seed применяется повторно как
  no-op (наследует idempotency importer-а, AC-8 T-0140). Demo-скрипт
  типизирован (tsc) и проходит eslint. Никаких новых платных вызовов, никакой
  сети к LLM (агенты здесь dormant — только слоты).

## 3. Нефункциональные требования

- **NF-1.** Ни один байт-frozen security-файл не тронут (`touched_frozen=false`).
  Все записи seed — через importer/публичный API (I-1 T-0140).
- **NF-2.** dev остаётся ЗЕЛЁНЫМ: `fitness:seed` и `fitness:demo` (статические)
  проходят; FF-PACK-2 (8/8) не ломается (FR-3).
- **NF-3.** Один источник правды (FF-4 single-source): demo-сценарий НЕ
  дублирует org/role/process-данные новой копией `*_SEED`-константы вне
  allow-list; demo actor-данные — внутри пакета или его overlay-пути через
  importer.
- **NF-4.** Слоты агентов — **только разметка** (контракт вход/выход + где в
  потоке). Никакого кода навыка, никакого live-провода в этой задаче.
- **NF-5.** Демо-сумма гейта ≥ 5 000 000 ₽ согласована с порогом T-0233
  (ТЭЛ §1.4), demo-deal-фикстура совместима с `runLegalPrecheck` dealContext.

## 5. Out of scope

- Реализация навыков агентов (T-0219 intake, T-0234 legal-precheck) — здесь
  только СЛОТЫ.
- Циклы доработки / исключения / отказ-ветки ТЭЛ — демо строго линейна
  (reference-tel §1 «внести правки»-цикл = вне первой демо).
- Публичный демостенд / деплой (T-0142, founder-gated).
- Сцены B (graceful degradation) и D (бытовые права) v1-demo §B/§D — отдельные
  таски (T-0220/0221/0222/0223); этот сценарий лишь оставляет им место.
- Новый UI-экран: демо переиспользует уже существующие 5 экранов слайса
  (inbox/org/processes/rights/audit + forms) — новых React-экранов не строим.
