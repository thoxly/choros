# SPEC T-0057 — ADR: TS-only ядро vs TS+Python с дня 1

**Задача (S-3):** «TS-only ядро vs TS+Python с дня 1». Гипотеза заголовка бэклога:
*MVP-ядро — TS; Python — только Stage 2.* **Refs:** CONCEPT §6, §14; backlog §S.

**Фаза:** SPEC для ADR-задачи. Деливерабл задачи — **ADR-черновик для решения
фаундера** (ратификация — его гейт, GT-1). Эта спека НЕ решает вопрос; она его
**проверяемо оформляет**: фиксирует решаемый вопрос, границы, критерии решения и
данные, которые архитектору нужны для честного сравнения. Сам выбор — фаза DESIGN
+ подпись фаундера.

---

## 1. Решаемый вопрос (что именно решаем)

**На каком языке/языках живёт исполняемый код Choros в MVP, и где проходит граница
«Python — Stage 2».**

Декомпозиция вопроса на три независимо-решаемых среза (ADR должен ответить по
каждому, не валить в один «да/нет»):

- **РВ-1 — язык ядра MVP.** Ядро = API, оргмодель/RBAC, объектная модель, мост к
  движку (external-task bridge / outbox), серверный рендер форм, fleet-ops-органы
  (ops-каталог), UI. Сейчас это 100% TypeScript (Node ≥20, `pg`), без единого
  Python-файла. Вопрос: остаётся ли ядро MVP **TS-only**, или с дня 1 в ядро
  (или в обязательный для MVP контур) входит Python-рантайм.
- **РВ-2 — где граница Stage 2.** По каждому классу кода зафиксировать: **TS day-1**
  / **Python day-1** / **Python Stage 2** / **не-цель MVP**. Классы:
  (а) агентский рантайм (LLM-агенты как external worker — CONCEPT §6 предлагает
  Python/ADK/LangGraph);
  (б) ML/инференс-воркеры;
  (в) ops/эксплуатационные скрипты (сейчас TS-каталог + bash CI-чеки);
  (г) модули расширения / authoring (config-as-code, кастомные обработчики —
  см. extensibility-and-authoring.md);
  (д) BYO-LLM интеграции / коннекторы к внешним моделям.
- **РВ-3 — статус «агентский рантайм = Python» из CONCEPT §6.** §6 называет Python
  агентским рантаймом по умолчанию. ADR должен подтвердить, **смягчить** (агентский
  воркер может быть TS day-1, Python — когда понадобится экосистема) или
  **отвергнуть** эту строку стека — с обоснованием, а не унаследовать по инерции.

**Что НЕ является вопросом** (вне T-0057):
- JVM Flowable как рантайм — **уже ратифицирован** (stack ADR §1: движок = чёрный
  ящик уровня Postgres, его Java «не считается языком стека»). T-0057 про
  *прикладной* язык, не про движок.
- Финальный выбор движка (S-1), имя/домен (S-2) — отдельные решения.
- Язык фронтенда — React/TS зафиксирован (CONCEPT §6), не пересматривается.

## 2. Контекст (факты на дату спеки, проверяемые)

- **Кодовая база MVP — 100% TypeScript.** `find . -name '*.py'` вне node_modules →
  пусто. `package.json`: `type: module`, Node ≥20, единственная рантайм-зависимость
  `pg`. Ops-каталог — TS (`ops/catalog/run_vacuum.ts`, `queue_stats.ts`). CI-fitness —
  bash-скрипты (`ci/checks/*.sh`), не Python. Тесты — vitest. Спайк Flowable — bash.
- **Гипотеза §6:** ядро (API/оргмодель/UI/формы) = TS; агентский рантайм = Python
  (Google ADK / LangGraph) **как external worker**, т.е. за границей ядра по тому же
  pull-паттерну, что и любой микросервис (§5 «тонкое ядро, логика на границах»).
- **Поставка — silo-per-tenant** (stack ADR §1, tenancy-and-delivery.md): на каждый
  контур едет полный набор контейнеров. Каждый дополнительный рантайм = +образ,
  +память, +поверхность обновления/CVE **× число контуров** (200–300 тенантов
  целевой флот).
- **JVM уже присутствует** как «второй рантайм» в контуре (Flowable) и помечен P1-риском
  (stack ADR §59: timer-lag/GC — метрики day-1). Python стал бы **третьим** рантаймом
  в silo-контуре.
- **Fleet-ops day-1 автономный** (stack ADR §2): диагностика/починка контуров —
  ИИ-агенты; каждый рантайм в контуре должен быть покрыт ops-каталогом (диагностика
  + починка). Третий рантайм = третий класс ops-органов на контур.
- **Контекст выбора (CONCEPT §6):** код пишет ИИ, фаундер ревьюит вслепую →
  оптимизация под (а) языки надёжной AI-кодогенерации и (б) **минимум
  языков/стыков**, которые человек отлаживает вслепую. Это и есть весовой принцип
  для критериев §4.

## 3. Варианты решения (ADR обязан сравнить эти три)

- **В-A — TS-only day-1.** Весь исполняемый код MVP (ядро + агентский воркер +
  ops + расширения) на TS. Python не входит в MVP-контур. Агентские интеграции —
  через TS-SDK провайдеров LLM. Python остаётся **возможным** Stage-2-расширением
  по external-task-паттерну, но не реализуется и не поставляется в MVP.
- **В-B — TS+Python day-1.** Ядро на TS; Python-агентский рантайм (ADK/LangGraph)
  входит в MVP-контур как обязательный external worker с дня 1 (буквальное чтение §6).
- **В-C — TS-ядро + Python-как-Stage-2-расширение (гипотеза заголовка).** Ядро и
  весь обязательный MVP-контур — TS-only; в архитектуре **зарезервирована граница**
  (external-task contract / worker-протокол), через которую Python-воркер
  подключается в Stage 2 **без переписывания ядра**. MVP не везёт Python, но и не
  закрывает дверь.

ADR должен для каждого варианта дать вердикт go/no-go-для-MVP и обоснование по
критериям §4, и **назвать рекомендованный** (рекомендация → фаундеру на ратификацию).

## 4. Критерии решения (по ним ADR сравнивает варианты)

Машинно-проверяемое — где возможно (фактом о кодовой базе/контуре); экспертно-
обоснованное — где речь о найме/экосистеме (тогда критерий требует **явного
письменного обоснования**, а не «очевидно»).

- **К-1 — стоимость рантаймов в silo-поставке.** Для каждого варианта: число
  рантаймов в одном контуре (TS-node, JVM-движок, [Python?]), и что каждый добавляет
  — образ (МБ), базовая память, поверхность обновлений/CVE — **× число контуров**.
  *Проверяемо:* счётный список рантаймов на контур; В-A/В-C = 2 (node+JVM),
  В-B = 3 (+Python).
- **К-2 — единый аудит / RLS-доступ к данным.** Любой код, читающий данные тенанта,
  проходит **единый** PDP/grant-resolver и tenant-RLS (T-0018/T-0021/T-0115). Критерий:
  показать, что в каждом варианте доступ к данным идёт через один путь авторизации.
  Python-воркер, ходящий в БД напрямую, **дублировал бы** RLS/PDP на втором языке —
  это red-line-риск (один резолвер — fitness-инвариант `single-resolver.sh`); либо
  Python ходит только через API ядра (тогда он не «второй путь к данным»). ADR
  обязан зафиксировать, каким путём ходит Python в каждом варианте, где он есть.
- **К-3 — найм / скорость доставки.** Контекст §6: основной кодген — ИИ; ревью —
  фаундер вслепую. Критерий: для каждого варианта — оценка стоимости второго языка
  для (а) надёжности AI-кодгена, (б) человеческого ревью стыка TS↔Python.
  *Обоснование письменное*, опирается на §6 («минимум языков/стыков»).
- **К-4 — экосистема агентов / BPMN-Flowable-клиентов.** Что в каждом варианте
  теряется по экосистеме: (а) агентские фреймворки — ADK/LangGraph сильнее в Python
  vs зрелость TS-агентских SDK на дату ADR; (б) Flowable external-task клиенты —
  есть ли пригодный TS-клиент или он есть только/лучше в Java/Python. *Проверяемо
  частично:* наличие/зрелость TS external-task клиента для выбранного движка —
  факт, который ADR фиксирует, а не предполагает.
- **К-5 — BYO-LLM / провайдерские интеграции.** Покрывают ли TS-SDK провайдеров
  (включая BYO-LLM, локальные/российские модели — контекст 152-ФЗ из tenancy-дока)
  потребности MVP-агентов, или критичная интеграция доступна только в Python.
  *Проверяемо:* список интеграций MVP × доступность TS-SDK.
- **К-6 — fleet-ops покрытие.** Каждый рантайм в контуре требует ops-органов
  (диагностика+починка) в каталоге (stack ADR §2 DoD). Критерий: число классов
  ops-органов на контур по варианту; В-B добавляет Python-класс на каждый из
  200–300 контуров.
- **К-7 — обратимость / стоимость отсрочки.** Для В-C: показать, что граница
  (external-task contract) позволяет добавить Python в Stage 2 **без переписывания
  ядра** (это и есть «решение обратимо» из §6). Для В-A: показать, что TS-only не
  создаёт необратимого запирания. Критерий обратимости — архитектурный, проверяется
  наличием стабильного контракта воркера, не реализацией.

## 5. Данные, нужные архитектору для честного сравнения (вход в DESIGN)

ADR не имеет права быть «по ощущениям». К моменту DESIGN собрать/зафиксировать:

- **Д-1.** Полный перечень рантаймов на один silo-контур по каждому варианту
  (node / JVM-движок / Python?) + образ/память/CVE-поверхность каждого. Источник:
  docker-compose контура, stack ADR §1.
- **Д-2.** Список агентских сценариев MVP (какие агенты нужны в MVP по CONCEPT §3/§8
  и backlog), и для каждого — реализуем ли он на TS-SDK или требует Python-фреймворка.
  Без этого К-3/К-4/К-5 — гадание.
- **Д-3.** Факт о Flowable/Operaton external-task клиенте: есть ли поддерживаемый
  **TS** клиент к выбранному движку (S-1), его зрелость. Источник: S-1/T-0117 спайк
  + апстрим движка.
- **Д-4.** Зрелость TS-агентских фреймворков на дату ADR vs Python ADK/LangGraph —
  что именно теряется (фичи оркестрации/инструментов/памяти), письменно.
- **Д-5.** Перечень BYO-LLM/провайдерских интеграций, требуемых MVP (с учётом
  152-ФЗ / on-prem-моделей из tenancy-дока), и покрытие их TS-SDK.
- **Д-6.** Путь доступа Python-воркера к данным тенанта в В-B (через API ядра vs
  прямой БД-доступ) и его совместимость с инвариантами «один резолвер» + tenant-RLS
  (T-0018/T-0021/T-0115, fitness `single-resolver.sh`/`cross-tenant-fitness.sh`).

## 6. Не-цели (out of scope T-0057)

- **Не решать** вопрос самим — выбор варианта и ратификация = DESIGN + фаундер (GT-1).
- Не пересматривать **JVM/движок** (ратифицирован, stack ADR) и **React/TS-фронт**
  (CONCEPT §6).
- Не выбирать конкретный **агентский фреймворк** (ADK vs LangGraph vs TS-аналог) —
  это следующий слой после выбора языка.
- Не писать код агентского воркера / Python-инфраструктуру.
- Не решать S-1 (движок), S-2 (домен) — смежные, но отдельные решения.
- Не делать юридический разбор лицензий/152-ФЗ (юрист, не инженерный гейт).

## 8. BLOCKING-вопросы

**Нет.** Направление-гипотеза (MVP-ядро TS, Python — Stage 2) уже стоит в заголовке
бэклога; спека оформляет вопрос проверяемо, не предрешая. Объём и поведение
ADR-задачи однозначны без ответа фаундера: фаундер отвечает **результатом**
(ратификацией ADR), а не входным BLOCKING. Поэтому статус — `ready`.
