# Spec · T-0134 — Документация: агентный слой (LLM-wiki без raw) + страница доков в UI + MCP-сервер документации

**Status:** ready
**Phase:** SPEC (для дизайн-задачи — выход фазы = требования к будущему ADR, не сам ADR)
**Date:** 2026-06-11
**Task:** T-0134 (product=choros, type=design, prio 40)
**spec_ref:** `playbooks/choros-product-gap-map.md` §2 (envelope: «Документация (агентная, MCP-доступ)»), §3а (решение фаундера «Документация», 2026-06-11); базис — gist Карпатого 442a6bf5 (LLM-wiki с index/log + lint-проход).

**Решение фаундера (данность, НЕ развилка):**
- **Доки пишут и поддерживают агенты** (не люди вручную, не разовый ручной текст).
- Принцип — **адаптированный LLM-wiki Карпатого**: wiki-слой с `index`/`log` и **lint-проходом**, но **БЕЗ папки `raw`** — источник истины = **живая система** (код / конфиги / схемы / процессы); lint сверяет доки с **актуальным состоянием** системы, а не с замороженным сырьём.
- **Три потребителя** одного и того же док-слоя:
  1. **Страница доков в UI** (человек-клиент/админ/внедренец читает в продукте);
  2. **Внутренний агент-интерфейс** (агенты Choros читают доки как контекст);
  3. **Внешние harness** (Claude Code / ChatGPT / ЯндексGPT) через **MCP-слой документации** — «продукт настраиваем чужими агентами», та же логика headless-поверхности.
- **Детализация пайплайна генерации/поддержки доков → исследование №3** (агентный docs-pipeline). Это **ОТЛОЖЕННАЯ ЧАСТЬ**, явно вынесенная из объёма SPEC (см. §4 Out of scope, SEAM-3).

---

## 1. Summary

Choros получает **агентный слой документации**: машинно-поддерживаемый wiki-слой, чей **источник истины — живая система** (символы кода, REST-эндпоинты, таблицы/схемы, BPMN/DMN-процессы, конфиги), без отдельной папки `raw`-сырья. Каждая ссылка дока на элемент системы (символ / эндпоинт / таблица / процесс) — **машинно-проверяема против живого состояния** проходом-**lint**: устаревшая ссылка (символ переименован, эндпоинт удалён, столбец исчез) детектируется автоматически, а не «замечается человеком». Один и тот же слой обслуживает **три потребителя**: **UI-страницу доков** (человек), **внутренний агент-интерфейс** (агенты Choros) и **внешние harness** через **read-only MCP-сервер документации** (чужие агенты настраивают/исследуют продукт). MCP-поверхность — **read-only** и авторизуется **внутри единой grant-модели** (T-0018/T-0021): внешний/harness-принципал = **производный ограниченный грант**, никакого второго механизма авторизации; каждое обращение — в аудит (T-0016).

Это **дизайн-задача**: выход фазы — спека требований, которые обязан покрыть будущий ADR (модель док-страницы и где она живёт; машина lint-устаревания; UI-страница; read-only MCP-сервер и его authz; граница MVP и трассировка). Acceptance-критерии — **проверяемые свойства будущего ADR** (fitness-линт структуры/трассируемости текста, как T-0132 FF-1) либо **test/manual после имплементации**. **Пайплайн генерации доков агентом — НЕ в этой спеке** (исследование №3); рамка проектируема сейчас, пайплайн — Stage-2 после исследования.

## 2. Функциональные требования к дизайну (ADR обязан покрыть)

**Ось A — Модель док-страницы (где живёт, версионирование).**

- **FR-1 — Источник истины = живая система, БЕЗ `raw`.** ADR фиксирует: доки — это wiki-слой поверх **живых артефактов** (код / схемы / эндпоинты / процессы / конфиги); **отдельной папки/таблицы `raw`-сырья НЕТ** (отличие от исходного gist Карпатого). Это несущий принцип — отсутствие явного утверждения «нет raw, источник = живая система» = брак.
- **FR-2 — Структура wiki = `index` + страницы + `log`.** ADR определяет минимальную структуру слоя: **индекс** (каталог страниц/тем), **страницы доков** (единица контента), **журнал** (`log`) изменений доков (что/когда/каким агентом обновлено) — в духе LLM-wiki, адаптированного под Choros.
- **FR-3 — Где живёт док-слой (развилка модели данных — ADR ОБЯЗАН выбрать).** ADR явно выбирает носитель: **таблица(ы) в Postgres** (tenant-scoped, FORCE RLS per T-0013) и/или **файлы в репозитории/хранилище**, и обосновывает выбор. Если страницы tenant-видимы в UI — носитель обязан быть **tenant-изолирован** (T-0013); общесистемные доки продукта (не per-tenant) — отдельный класс, ADR разграничивает.
- **FR-4 — Версионирование/история.** ADR специфицирует, как версионируются страницы (история правок: кто-агент, когда, diff/`log`-запись), чтобы устаревание и регресс доков были видимы и обратимы. **Не плодить новый механизм версионирования** — переиспользовать существующую подсистему согласованности артефактов там, где применимо (см. инварианты §5: T-0082 единица версионирования, T-0072 named-binding), а не вводить четвёртый «производный артефакт ↔ источник».

**Ось B — Lint устаревания (каждая ссылка машинно-проверяема против живой системы — паттерн T-0132 FF-1).**

- **FR-5 — Типизированная ссылка на элемент системы.** ADR вводит понятие **машинно-разрешимой ссылки** дока на конкретный элемент живой системы: **символ кода** (модуль/функция/тип), **REST-эндпоинт**, **таблица/столбец схемы**, **процесс** (BPMN/DMN ключ), **конфиг-ключ**. Ссылка несёт **проверяемый идентификатор** (не свободный текст), по которому lint находит элемент в живой системе.
- **FR-6 — Lint-проход = сверка ссылок с живым состоянием.** ADR специфицирует **lint** как проход, который для каждой типизированной ссылки (FR-5) проверяет: **референт существует в актуальной системе** (символ есть, эндпоинт зарегистрирован, столбец в схеме, процесс задеплоен, конфиг-ключ валиден). Устаревшая ссылка (референт исчез/переименован) → **детектируемый дефект** дока, а не «человек заметит». Это и есть «lint против устаревания» из решения фаундера.
- **FR-7 — Lint машинно-исполним (fitness-функция, как T-0132 FF-1).** ADR специфицирует lint так, чтобы он стал **CI-fitness-функцией / тестом**: вход = страница доков + снимок живой системы; выход = список битых ссылок (пусто = ок). Свойство «каждая ссылка проверяема против живой системы» — структурно-машинно-проверяемое, не «работает корректно».
- **FR-8 — Поведение lint при устаревании.** ADR определяет реакцию на битую ссылку: как минимум **сигнал устаревания** (страница помечена устаревшей / дефект в отчёте lint), и развилку «блокировать ли публикацию/CI» — design-owned (SEAM-2), но **факт детекции обязателен**.

**Ось C — UI-страница доков.**

- **FR-9 — Страница доков в продукте.** ADR специфицирует **UI-страницу**, на которой человек (клиент/админ/внедренец) **читает** документацию из того же слоя (FR-2): навигация по `index`, чтение страниц. Страница **читает тот же источник**, что и агенты/MCP — **не отдельная копия доков** (один слой, три потребителя).
- **FR-10 — Видимость устаревания в UI.** ADR специфицирует, что результат lint (FR-6/FR-8) **виден на UI-странице** (например, бейдж/предупреждение «раздел может быть устаревшим»), чтобы человек не доверял молча протухшему тексту. (UI-страница доков сама по себе — отчётно-навигационная; редактор доков людьми — НЕ в объёме, доки пишут агенты, FR решения фаундера.)
- **FR-11 — Видимость tenant-границы.** ADR фиксирует, что UI-страница показывает только доки, на которые у пользователя есть видимость (tenant-изоляция T-0013 + видимость по грантам, если страницы scoped); общесистемные доки продукта vs tenant-специфичные — разграничены (FR-3).

**Ось D — MCP-сервер документации (read-only поверхность для внешних harness — authz!).**

- **FR-12 — Read-only MCP-сервер доков.** ADR специфицирует **MCP-сервер документации** — поверхность, через которую **внешний harness** (Claude Code / ChatGPT / ЯндексGPT) **читает** док-слой (тот же `index`/страницы, FR-2). Поверхность **строго read-only**: список/чтение страниц/поиск; **никаких мутаций** системы или доков через неё (запись доков — зона агентов Choros по пайплайну исследования №3, не внешних harness).
- **FR-13 — Authz внутри единой grant-модели (non-negotiable инвариант).** ADR фиксирует: доступ к MCP-серверу доков авторизуется **внутри grant-модели T-0018/T-0021** — внешний/harness-принципал = **производный ограниченный грант** (read-only scope на док-ресурс), **а НЕ второй механизм авторизации** (gap-map §4б инвариант 2; та же логика, что T-0122 внешняя поверхность / T-0126 headless). PDP (T-0021) — единый чокпойнт, fail-closed.
- **FR-14 — Tenant-изоляция MCP-доступа.** ADR специфицирует, что MCP-сервер доков отдаёт только доки, на которые у предъявленного принципала/токена есть грант; **cross-tenant-утечка структурно невозможна** (T-0013 FORCE RLS + tenant-контекст fail-closed в external-пути, tenancy-and-delivery §9 п.7). Общесистемные доки продукта (не per-tenant) — отдельный read-класс, явно разграничен.
- **FR-15 — Аудит обращений MCP.** ADR специфицирует, что обращения к MCP-серверу доков (кто/какой harness-принципал, что прочитал) пишутся в **единый аудит** (T-0016, append-only hash-chained), без второго лога; актор — производный от harness-токена/внешней поверхности (учётки может не быть, как T-0122).
- **FR-16 — Согласованность с реестром mcp_tool (T-0043).** ADR фиксирует связь с существующим `mcp_tool`-реестром (T-0043, E5.3): docs-сервер — read-only MCP-поверхность; если он представлен как mcp-инструмент(ы), их `declares`/`resource_ops` типизированы и проверяемы тем же путём (T-0043), **не свободный текст**; docs-сервер **не вводит** новый authority-store поверх T-0043/T-0018.

**Ось E — Граница и трассировка.**

- **FR-17 — Пайплайн генерации доков агентом = ОТЛОЖЕН (исследование №3).** ADR явно фиксирует, что **как именно агент генерирует и поддерживает доки** (триггеры, обход живой системы, генерация/обновление страниц, дедуп, конфликт-резолюция, частота) — **вне объёма T-0134** и определяется **исследованием №3** (gap-map §3а). T-0134 проектирует **рамку** (модель страницы, lint, UI, MCP-authz), пайплайн — **Stage-2 после исследования**. Это **НЕ blocking** для T-0134 (рамка проектируема сейчас).
- **FR-18 — Трассировка.** ADR содержит раздел трассировки: каждое требование → к решению фаундера §3а «Документация» / envelope §2 / опорному ADR (T-0013/T-0016/T-0018/T-0021/T-0043). Раздел трассировки обязателен.

## 3. Нефункциональные требования к дизайну

- **NF-1 — Ноль второго механизма авторизации.** MCP-сервер доков и любой внешний/harness-доступ авторизуются ТОЛЬКО через grant-модель T-0018 + PDP T-0021; ADR не вводит новый authority-store, новый scope-алгоритм или второй аудит-лог (gap-map §4б инвариант 2).
- **NF-2 — Источник истины неустраним = живая система.** ADR не вводит дублирующее `raw`-сырьё как параллельный источник; устаревание детектируется сверкой с живой системой, не с замороженной копией (решение фаундера, FR-1/FR-6).
- **NF-3 — Один слой — три потребителя.** UI-страница (FR-9), внутренний агент-интерфейс и MCP-сервер (FR-12) читают **один** док-слой; ADR не проектирует три копии доков.
- **NF-4 — Lint машинно-проверяем (CI-готов).** Свойство устаревания формулируется как fitness/test (FR-7), не как ручная вычитка; «доки актуальны» без машинного критерия — недостаточно (паттерн T-0132 FF-1).
- **NF-5 — Tenant-изоляция везде.** Любой носитель/поверхность, отдающие tenant-видимые доки, наследуют FORCE RLS T-0013 и fail-closed tenant-контекст в external/async-пути (tenancy-and-delivery §6/§9).
- **NF-6 — Не плодить механизмы согласованности.** Версионирование/«производный артефакт ↔ источник» переиспользует существующую подсистему (T-0082 единица версионирования, T-0072 named-binding, T-0084 валидатор changelog↔diff) там, где применимо, а не вводит четвёртый параллельный механизм (gap-map §4б).
- **NF-7 — Трассируемость.** Каждое требование ADR трассируется к §3а/envelope/опорному ADR (FR-18).

## 4. Out of scope (явные не-цели)

- **Реализация** (миграции, объектная модель доков, код MCP-сервера, UI-компоненты, строки lint-правил) — design-only; производные DESIGN/BUILD-задачи.
- **Пайплайн генерации/поддержки доков агентом** (как агент обходит систему, генерирует/обновляет/дедуплицирует страницы, разрешает конфликты, как часто, по каким триггерам) — **исследование №3** (SEAM-3, FR-17). T-0134 даёт рамку, не пайплайн.
- **Редактор доков людьми / ручное авторство** — решение фаундера: доки **пишут агенты**; ручной WYSIWYG-редактор доков клиентом не проектируется.
- **Запись/мутация через MCP-сервер** — поверхность read-only (FR-12); внешние harness не пишут доки и не мутируют систему через docs-MCP.
- **Транспорт/протокол MCP, развёртывание сервера, аутентификация harness на уровне инфраструктуры** (как именно harness предъявляет токен, network-уровень) — механизм, зона architect/BUILD; SPEC фиксирует authz-модель (FR-13), не wire-протокол.
- **Headless-ответы агента внешнему приложению** (банк-кейс, агент отвечает на запрос) — это T-0126, design-only до Stage-2 (gap-map §4б инвариант 3); docs-MCP — read-only чтение доков, не агентский ответ.
- **Алгебра решётки грантов** (⊑/normalize/validateNarrowing) — построена в T-0018, не переоткрывается; docs-authz опирается.
- **Реестр `mcp_tool`** (declares/resource_ops/reachability) — построен в T-0043; docs-MCP опирается, не переоткрывает (FR-16).
- **Аудит-движок** (hash-chain, схема `audit_event`) — T-0016; docs-MCP пишет события в него, не строит новый.
- **Политика «блокировать ли CI/публикацию при битой ссылке»** — дефолт = детекция+сигнал (FR-8); жёсткий гейт — design-owned/Stage-2.

## 5. Связанные задачи и инварианты (читать дизайнеру)

- **Один механизм прав (gap-map §4б инвариант 2, non-negotiable):** docs-MCP вводит внешнего/harness-принципала **внутри** grant-модели (производный read-only грант), не второй authz. Та же логика, что T-0122 (внешняя поверхность) и T-0126 (headless API).
- **T-0043 (`mcp_tool` registry):** docs-MCP согласован с реестром MCP-инструментов; `declares`/`resource_ops` типизированы (FR-16), не свободный текст.
- **T-0013 (tenant isolation):** любой носитель tenant-видимых доков — FORCE RLS, leading `tenant_id`-PK; cross-tenant-утечка структурно невозможна (NF-5).
- **T-0016 (audit floor) / T-0021 (PDP):** обращения к docs-MCP — в единый аудит, авторизация — единый PDP-чокпойнт fail-closed.
- **T-0082 (единица версионирования) / T-0072 (named-binding) / T-0084 (валидатор changelog↔diff):** lint устаревания и версионирование доков — **та же подсистема согласованности** «производный артефакт ↔ источник», что реестр зависимостей отчётов T-0121; не плодить четвёртый механизм (NF-6). Lint доков структурно родственен FF-1-паттерну T-0132 (машинная сверка структуры/ссылок).
- **Исследование №3 (агентный docs-pipeline):** детальный пайплайн генерации — отдельная research-сессия по команде фаундера, НЕ задача бэклога; T-0134 — рамка, разблокирует №3 (FR-17, SEAM-3).
- **T-0127 (genesis-инсталлятор):** при self-service установке опора = документация (страница + MCP) — gap-map §3а; docs-слой обслуживает и онбординг.

## 6. Критерии приёмки

> Артефакт фазы — ADR (design-only). `fitness` = машинно-проверяемая структура (наличие именованного утверждения/раздела/трассировки в тексте ADR — паттерн T-0132 FF-1); `manual` = смысловое свойство ADR, проверяемое ревью; `test` = проверяемо после имплементации производной задачей.

| AC | Критерий | verifiable_as |
|---|---|---|
| AC-1 | ADR явно утверждает: источник истины доков = **живая система** (код/схемы/эндпоинты/процессы/конфиги), **папки/таблицы `raw`-сырья НЕТ** (отличие от gist Карпатого). Отсутствие этого утверждения — брак (FR-1, NF-2). | fitness |
| AC-2 | ADR определяет структуру wiki-слоя: `index` (каталог) + страницы (единица контента) + `log` (журнал изменений доков: что/когда/каким агентом) (FR-2). | fitness |
| AC-3 | ADR **выбирает** носитель док-слоя (Postgres-таблица tenant-scoped с FORCE RLS T-0013 и/или файлы/хранилище) и обосновывает выбор; tenant-видимые доки — tenant-изолированы; общесистемные доки продукта vs per-tenant — разграничены (FR-3, NF-5). | fitness |

## 7. BLOCKING-вопросы

**Нет.** Решение фаундера §3а «Документация» зафиксировало все продуктовые развилки: доки пишут агенты; LLM-wiki без `raw`, источник = живая система, lint против устаревания; три потребителя (UI / внутренний агент / внешние harness через MCP-слой); детальный пайплайн — отложен в исследование №3 (явно НЕ блокирует рамку). Развилки модели данных (носитель страницы FR-3, реакция lint FR-8, представление docs-MCP как mcp_tool FR-16) — **design-owned** (зона architect), не product-blocking: ADR обязан выбрать и обосновать, но любой из вариантов укладывается в рамку и инварианты. Статус — `ready`.
