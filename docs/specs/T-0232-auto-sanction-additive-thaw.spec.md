## 0. Note on scope (CI-gate-change family)

Эта задача меняет **поведение CI-мета-гейта** и **формат записи в санкционном канале** — не объектную
модель продукта и не рантайм. Как и существующие frozen-чеки, артефакт самотестируем через `--self-test`,
без БД/сети/часов, и исполняется на КАЖДОМ прогоне `npm run fitness`. Спека пинит ЧТО должен делать класс
авто-санкции и какие инварианты он обязан удержать; КАК (точный парсер диффа, схема строки, где живёт
аттестация Врага) — зона `architect`/`coder`. Каждый критерий несёт `verifiable_as`, перевешено в
`fitness`/`test`.

## 1. Summary

Сегодня снятие байт-замка с любого чужого frozen-чека (`ci/checks/*.sh`) требует строки в
`frozen-sanctions.jsonl`, авторизованной `founder_decide`. По D-060 это утечка к фаундеру для целого
класса правок, которые система может удостоверить сама: **аддитивный thaw** (дописана новая сущность;
существующая байт-frozen поверхность не тронута; ни одно уже выданное право не сменило смысл), **прошедший
adversarial-гейт «Враг» (T-0151) при зелёном CI**. Для этого класса `frozen-checks-immutable.sh` должен
принимать **второй класс санкции** — `auto-additive`, чья авторизация — не `founder_decide`-трейс, а
**машинно-проверяемая аттестация аддитивности + ссылка на зелёный прогон Врага**, которую сам оркестратор
аппендит в санкционный канал постфактум с полным аудитом.

Граница жёсткая: **деструктивный/редуктивный thaw** (убран вид, изменён смысл существующего, перевёрнут
дефолт «запрещено→разрешено», расширён scope уже выданного права) `auto-additive`-санкции НЕ получает —
он по-прежнему только `founder_decide`, превентивно. Инвариант D-026 сохранён: агент не может убрать или
ослабить инвариант сам; снимается лишь рутинный человек-в-петле на ДОКАЗУЕМО-аддитивных правках, которые
**независимо** подтвердил Враг (D-007).

Спека пинит: (1) машинно-проверяемое определение «аддитивного thaw»; (2) precondition авто-санкции
(аттестация аддитивности + зелёный Враг + зелёный CI, заменяющая `founder_decide`); (3) формат
auto-санкционной строки, отличимый от founder-класса; (4) поведение `frozen-checks-immutable.sh` — принимает
ОБА класса, но REJECT `auto-additive` для не-аддитивного диффа; (5) сохранение guardrail (агент не
само-санкционирует деструктивный thaw).

## 2. Определения

- **frozen-thaw** — правка/удаление чужого (`# T-YYYY ≠ TASK_ID`) `ci/checks/*.sh` ИЛИ правка
  каталога/корпуса Врага под прикрытием санкции на соответствующий enemy-чек, ИЛИ — расширительно для D-060
  — правка байт-frozen security-ядра, защищаемого frozen-чеком (напр. дописывание вида в `ResourceType`,
  закрытое `mutation-gateway-isolation.sh`). Для ЭТОЙ задачи thaw материализуется как пара `{task,file}` в
  санкционном канале, разрешающая мета-гейту пропустить правку.
- **Аддитивный thaw** (auto-санкционируемый класс) — см. §4: дописаны только новые сущности; вся
  поверхность, существовавшая в BASE_REF, сохранена байт-в-байт; ни один уже-существующий toggle/дефолт/scope
  не сменил смысл.
- **Деструктивный/редуктивный thaw** (founder-only класс) — любой thaw, не удовлетворяющий §4: удалён вид,
  переименован/изменён существующий enum-член, перевёрнут дефолт, расширен scope существующего права,
  ослаблен существующий инвариант.
- **Враг-аттестация аддитивности** — машинно-читаемое свидетельство, что adversarial-гейт T-0151
  (`enemy/*` чеки + `enemy.adversarial.test.ts`) прошёл ЗЕЛЁНЫМ на коммите задачи И что Враг покрывает
  семью инвариантов, затронутую thaw. Это НЕ самооценка агента (D-007) — артефакт привязан к
  детерминированному корпусу/генератору Врага и зелёному статусу CI.
- **founder-класс санкции** — строка в `frozen-sanctions.jsonl` с `"sanctioned_by":"founder"` и
  `"decision":"founder_decide@DATE"` (существующий канал T-0199).
- **auto-additive-класс санкции** — новая строка с `"sanctioned_by":"auto-additive"` (или эквивалентный
  машинно-отличимый маркер), несущая ссылку на Враг-аттестацию вместо `founder_decide`-трейса.

## 3. Функциональные требования

**FR-1 (второй класс санкции).** `frozen-checks-immutable.sh` ПРИНИМАЕТ bypass чужого frozen-чека для пары
`{task,file}`, авторизованной ЛИБО founder-классом (как сегодня, FF-FCI12), ЛИБО новым auto-additive-классом.
Оба класса печатают SANCTION+AUDIT строки (никогда не молча), и аудит-строка явно НАЗЫВАЕТ класс
(`founder` vs `auto-additive`), чтобы постфактум-ревью фаундера видело, что было само-санкционировано.

**FR-2 (машинно-проверяемая аддитивность — крус).** Для auto-additive-санкции мета-гейт (или вызываемый им
аддитивность-верификатор) ОБЯЗАН доказать, что КАЖДЫЙ файл `f` из санкционируемого диффа аддитивен против
BASE_REF по правилу §4. Если хоть один затронутый файл не проходит проверку аддитивности — auto-санкция
ОТКЛОНЕНА (FAIL), правка не пропускается (для неё нужен founder-класс).

**FR-3 (precondition = Враг + зелёный CI, не founder_decide).** Auto-additive-санкция действительна ТОЛЬКО
при наличии Враг-аттестации (§2), привязанной к этой задаче/коммиту. Отсутствие/несоответствие аттестации
⇒ auto-санкция ОТКЛОНЕНА. (Зелёность самого Врага гарантируется тем, что `enemy/*` чеки + adversarial-тест
уже в цепочке `npm run fitness` и должны пройти на том же прогоне; аддитивность-верификатор лишь
СВЕРЯЕТ присутствие аттестации, не дублирует прогон Врага.)

**FR-4 (само-аппенд оркестратором, постфактум, аудируемо).** После зелёного Врага + зелёного CI на
аддитивном thaw оркестратор САМ аппендит auto-additive-строку в `frozen-sanctions.jsonl` (append-only) —
без `founder_decide`, без парковки задачи в `awaiting_founder`. Строка несёт: `task`, `file`, `owner`
(T-ID чужого чека), маркер класса, ссылку на Враг-аттестацию (who/what/why/attestation-ref), временную метку.

**FR-5 (отказ для деструктивного thaw).** Если thaw не аддитивен (§4), auto-additive-санкция НЕВОЗМОЖНА:
аддитивность-верификатор краснеет, мета-гейт не пропускает правку по auto-классу. Такой thaw проходит
ТОЛЬКО через founder-класс (`founder_decide` → строка `"sanctioned_by":"founder"`), как сегодня. Система
не имеет пути само-санкционировать деструктивный thaw.

**FR-6 (founder-класс не сломан).** Существующие founder-строки (T-0085, T-0227) продолжают работать без
изменений: их матчинг, SANCTION/AUDIT-печать и пропуск правки идентичны до-T-0232 поведению. T-0232 —
строго аддитивное расширение мета-гейта (новый класс рядом, существующий путь байт-эквивалентен).

**FR-7 (самотест — Враг кусает обе стороны).** Новый/расширенный чек несёт `--self-test`, доказывающий:
(a) чистый аддитивный thaw с валидной аттестацией → auto-санкция ПРИНЯТА; (b) деструктивный thaw (синтетика:
удалён enum-член / изменён существующий / расширен scope) → auto-санкция ОТКЛОНЕНА; (c) аддитивный thaw БЕЗ
Враг-аттестации → ОТКЛОНЕНА; (d) founder-класс по-прежнему ПРИНЯТ. Self-test exit 2 = сломана машинерия чека.

## 4. Машинно-проверяемое определение «аддитивного thaw» (крус)

Thaw набора файлов `F` (затронутых под санкцию) против BASE_REF (merge-base с `dev`/`origin/dev`) считается
**АДДИТИВНЫМ** тогда и только тогда, когда для КАЖДОГО `f ∈ F` диффа BASE_REF→HEAD одновременно выполнены:

- **A-1 (сохранение существующих строк — байт-prefix/субсеквенция).** Каждая непустая
  не-комментарий строка, присутствовавшая в BASE_REF-версии `f`, присутствует в HEAD-версии `f`
  **байт-идентично** (структурный аналог `corpus-append-only.sh` FF-CORPUS1). Ни одна существующая строка не
  удалена и не мутирована. Дифф состоит ИСКЛЮЧИТЕЛЬНО из добавленных строк (`git diff` показывает только
  `+`, ни одной `-` по содержательным строкам).
- **A-2 (нет удаления именованной сущности).** Множество именованных сущностей, объявленных в BASE_REF-версии
  (enum-члены/`ResourceType`-виды/инвариант-семьи/enforcement-ссылки — в зависимости от защищаемой
  поверхности), является ПОДмножеством множества в HEAD-версии. Множество может РАСТИ, не сужаться (аналог
  `catalog-frozen.sh` FF-CAT1/FF-CAT2).
- **A-3 (нет смысловой мутации существующего).** Ни один существующий именованный член не переименован, не
  переопределён и не сменил привязку (значение/scope/дефолт). Перенос дефолта `deny→allow`, расширение scope
  уже выданного права, флип булева toggle — НЕ аддитивны (это явные триггеры founder-класса по D-060).
- **A-4 (только новые сущности в дельте).** Содержимое дельты (HEAD ∖ BASE_REF) состоит только из ДОБАВЛЕНИЯ
  новых сущностей/строк; добавленное не ослабляет ни один существующий инвариант (напр. не дописывает в
  существующий allowlist элемент, расширяющий уже выданное право).

Если ЛЮБОЙ из A-1..A-4 нарушен для ЛЮБОГО `f ∈ F` — thaw НЕ аддитивен ⇒ founder-only.

**Якорь — BASE_REF, не рабочая копия.** Как и в `frozen-checks-immutable.sh` (R-1 fix) и
`corpus-append-only.sh`, проверка аддитивности читает «было» из BASE_REF через `git show`, а не из on-disk
версии — иначе аддитивность можно подделать переписав файл. На dev/main/non-task ветке или при отсутствии
merge-base проверка — fail-open no-op (как все frozen-чеки), т.к. вне task-ветки нечего санкционировать.

**Граница точности (осознанный остаточный риск).** Машинная проверка аддитивности структурна (строки + набор
именованных сущностей), не семантическая полнота. Класс правок, которые синтаксически выглядят аддитивно, но
семантически расширяют право (напр. новый enum-член, который PDP трактует как «всё разрешено»), — закрывается
ИМЕННО Врагом: A-1..A-4 — необходимое условие, зелёный adversarial-гейт T-0151 — достаточное независимое
подтверждение (D-007). Оба обязательны для auto-санкции; ни одного по отдельности недостаточно.

## 5. Нефункциональные требования

- **NF-1 (offline/детерминизм).** Аддитивность-верификатор и self-test — чистые (git/grep/awk/diff), без
  БД/сети/часов; зелёные и на task-ветке, и постфактум на dev (тот же приём BASE_REF, что у sibling-чеков).
- **NF-2 (append-only канал сохранён).** `frozen-sanctions.jsonl` остаётся append-only; auto-additive-строки
  только аппендятся; ни founder-, ни auto-строки никогда не удаляются/переписываются.
- **NF-3 (никогда не молча).** Каждый bypass (обоих классов) печатает SANCTION+AUDIT; молчаливый пропуск —
  дефект.
- **NF-4 (нет нового auth-root).** T-0232 НЕ вводит новый trust-root и НЕ ослабляет T-0146: сам мета-гейт —
  `ci/checks/*.sh`, защищён собой; новая логика аддитивности живёт в файле(ах), которыми T-0232 владеет, и
  регистрируется в `npm run fitness` с `--self-test`.
- **NF-5 (постфактум-видимость фаундера).** Auto-санкционированные правки остаются полностью видимы
  фаундеру детективно: AUDIT-строка в логе гейта + auto-additive-запись в jsonl с классом и Враг-ссылкой;
  фаундер может в любой момент ретроспективно ревьюить.

## 6. Out of scope (явные не-цели)

- **OOS-1.** Не вводить auto-санкцию для деструктивного/редуктивного thaw — он остаётся founder-only (D-060).
- **OOS-2.** Не менять механику Врага (генератор/корпус/арена) — T-0232 ПОТРЕБЛЯЕТ зелёный статус Врага, не
  переписывает его (эпик T-0151).
- **OOS-3.** Не менять `founder_decide` control-plane тул и не трогать существующие founder-строки в jsonl.
- **OOS-4.** Не реализовывать сам оркестраторский аппенд-степ кодом control-plane здесь — спека пинит ЧТО
  он аппендит и какой инвариант гейт удерживает; точная имплементация аппенда — зона architect/coder и/или
  orchestrator-контракта.
- **OOS-5.** Не строить семантический доказатель эквивалентности прав — достаточность обеспечивает Враг, не
  статический анализ (см. §4 граница точности).
- **OOS-6.** Не трогать T-0146 frozen-файл (`frozen-checks-immutable.sh`) деструктивно: расширение под новый
  класс — само по себе аддитивный thaw чужого чека, требующий либо владения T-0146 (нет), либо санкции; см.
  Q-зону §8 — это РАЗРЕШЁННЫЙ вопрос, не блокирующий.

## 8. Blocking questions

**Нет BLOCKING-вопросов.** D-060 явно ратифицирует границу (аддитивный→авто, деструктивный→фаундер) и
определяет класс — спека лишь пинит её машинно. Ниже — НЕблокирующие вопросы для architect (объём/поведение
не меняют, выбор механизма):
