## 0. Контекст и ретро-причина

За день rt-choros-s8 BUILD-агенты дважды вписывали exclusion-паттерны в **чужие** frozen-чеки:

- **T-0118 BUILD** (`e7dc2ad`) — добавил `FROZEN_EXCLUDE_RE` в `role-criticality-isolation.sh`
  и `dual-control-isolation.sh` (чужие задаче T-0118); ловил reviewer → revert `1037eba`.
- **T-0035 BUILD** (`72a02fd`) — добавил exclusion-паттерны в те же файлы; ловил reviewer →
  revert `e6a9a79`.

В обоих случаях агент обходил чужой гейт, чтобы добиться зелёного CI, вместо того чтобы разрешить
конфликт через механизм интеграции (rebase-reconciliation, явный мерж-гейт). Такое изменение:
1. Молча расширяет «дыру» в инварианте, который чужой гейт защищает.
2. Проходит сквозь `npm run fitness` незамеченным — нет чека, который бы это запрещал.

Фикс — новый мета-гейт `ci/checks/frozen-checks-immutable.sh`, который сам запускается в составе
`npm run fitness` и при наличии diff vs `dev` объявляет нарушение, если изменение затрагивает
существующий `ci/checks/*.sh`, которым **не владеет** текущая задача.

---

## 1. Что строим (одно предложение)

Новый fitness-чек `ci/checks/frozen-checks-immutable.sh`, который на task-ветке (при наличии
diff vs merge-base с `dev`) запрещает любое изменение или удаление существующих `ci/checks/*.sh`,
кроме единственного исключения: чек, чьё имя задачи в заголовке (`# T-XXXX ·`) совпадает с
T-ID текущей ветки, может быть изменён только своим BUILD-агентом.

---

## 2. Зачем это существует

Каждый `ci/checks/*.sh` — это инвариант безопасности или структурной целостности конкретной задачи.
Разрешить соседней задаче тихо добавить `grep -vE` или `FROZEN_EXCLUDE_RE` = разрешить сломать
инвариант без явного review-решения. Мета-гейт делает такое изменение **CI-видимым** сразу, на
этапе локального `npm run fitness`, до отправки PR, давая агенту корректный сигнал.

---

## 3. Функциональные требования

**FR-1 — Обнаружение diff vs dev.**
Чек должен вычислять список изменённых/удалённых файлов относительно merge-base с `dev`
(аналогично механизму в `dual-control-isolation.sh` и `role-criticality-isolation.sh`):
merge-base(`dev`, `HEAD`) → `git diff --name-only <base> HEAD` + uncommitted changes.
Если merge-base с `dev` недоступен (`dev` ветки нет, detached HEAD на самой `dev`) — чек
возвращает `exit 0` (зелёный, нет task-контекста для проверки).

**FR-2 — Детектирование task-ветки и вывод T-ID.**
Чек читает текущее имя ветки (`git rev-parse --abbrev-ref HEAD`). Если имя соответствует
шаблону `task/T-XXXX-*` (где XXXX — одна или более цифр), извлекается `T-XXXX` как ID задачи
текущей ветки. Если имя не соответствует шаблону (интеграционная ветка, dev, main, detached HEAD)
— чек возвращает `exit 0`.

**FR-3 — Определение «собственного чека» задачи.**
Для каждого файла `ci/checks/*.sh` в diff чек смотрит вторую строку файла на совпадение
с `# T-XXXX ·` (ровно второй комментарий-строки, формат `^# T-XXXX[[:space:]]·`).
Если T-ID в заголовке совпадает с T-ID текущей ветки — это **свой чек**, изменения разрешены.
Если заголовок отличается или отсутствует — это **чужой чек**, изменения запрещены.

**FR-4 — Запрет изменения чужих чеков.**
Любой файл `ci/checks/*.sh` в diff, определённый как чужой по FR-3, является нарушением.
Чек выводит `FAIL` с именем файла и причиной, накапливает счётчик ошибок, возвращает `exit 1`.

**FR-5 — Запрет удаления чужих чеков.**
Удаление (DELETE) существующего `ci/checks/*.sh` — тот же класс нарушения, что и изменение.
Чек должен детектировать удалённые файлы (через `git diff --name-only --diff-filter=D`) и
запрещать удаление чужих чеков. Удаление собственного чека задачи — разрешено (редко, но
возможно при рефакторинге гейта).

**FR-6 — Разрешённые классы правок (исчерпывающий список).**
На task-ветке разрешено без нарушения мета-гейта:
1. **Добавление новых файлов** в `ci/checks/` (новый `*.sh` — гейт новой задачи).
2. **Аддитивные правки реестров** (`ci/checks/known_tenant_tables.txt`) — текстовый файл,
   не shell-скрипт, не затрагивается этим чеком.
3. **Правки тестов и вспомогательных файлов** вне `ci/checks/*.sh` (`*.test.ts`, `migrations/`,
   `src/`, `docs/` и т.д.) — не в области проверки.
4. **Правки собственного `*.sh`** (заголовок `# T-XXXX ·` совпадает с T-ID ветки).
5. **Правки поддиректорий** `ci/checks/db/`, `ci/checks/kc/`, `ci/checks/flowable/` —
   находятся за пределами паттерна `ci/checks/*.sh` (glob верхнего уровня), не в области.

Всё остальное, включая изменение чужого `*.sh` любым способом (добавление строки, удаление строки,
переименование), является нарушением.

**FR-7 — Регистрация в `npm run fitness`.**
После создания `ci/checks/frozen-checks-immutable.sh` он должен быть добавлен в конец цепочки
`fitness` в `package.json` (аналогично последнему добавленному чеку `substitution-isolation`).

**FR-8 — Собственный hostile-probe тест чека.**
В составе задачи должен быть виртуальный тест `ci/checks/db/frozen-checks-immutable.test.ts`
или скрипт-самопроверка, воспроизводящий три приёмочных сценария (AC-1 / AC-2 / AC-3) через
прямой вызов чека с искусственным git-состоянием (shell-test: временный bare-репозиторий или
smoke-вызов). Точный механизм (vitest shell-spawning vs bash test harness) — зона DESIGN, не SPEC.

## 4. Нефункциональные требования

**NF-1 — Zero новых runtime-зависимостей.** Чек — pure bash, stdlib git, без Python/Node.

**NF-2 — Паттерн merge-base совпадает с существующими чеками.** Чек использует тот же
алгоритм разрешения BASE_REF, что `dual-control-isolation.sh` и `role-criticality-isolation.sh`
(перебор `dev` / `origin/dev`, merge-base). Не хардкодит SHA.

**NF-3 — На `dev` (нет task-diff) → зелёный.** Если merge-base совпадает с HEAD или ветка не
task/T-XXXX-*, чек всегда exit 0. Инварианты `dev` не ломаются.

**NF-4 — Сам чек не нарушает собственный гейт.** `ci/checks/frozen-checks-immutable.sh`
должен иметь заголовок `# T-0146 ·` на второй строке — тогда на ветке `task/T-0146-*` он сам
является собственным чеком и его создание/изменение разрешено.

**NF-5 — Устойчивость к отсутствию `dev`.** Если ветка `dev` и `origin/dev` оба недоступны
(offline, fresh clone без remote), чек должен gracefully exit 0 с предупреждением, не падать.

## 5. Семантика «соответствия» чека задаче ветки (детальная)

Это ключевой алгоритм: как из имени ветки `task/T-XXXX-slug` и содержимого `ci/checks/foo.sh`
определяется, является ли `foo.sh` **собственным** чеком задачи.

### 5.1 Шаг 1 — Извлечение T-ID из имени ветки

```
BRANCH=$(git rev-parse --abbrev-ref HEAD)
TASK_ID=$(echo "${BRANCH}" | grep -oE '^task/(T-[0-9]+)' | sed 's|^task/||')
```

Результат: `TASK_ID="T-0146"` для `task/T-0146-frozen-checks-immutable`.
Если `TASK_ID` пуст (нет совпадения) — чек выходит exit 0.

### 5.2 Шаг 2 — Считывание «заголовка задачи» из `*.sh`

Вторая строка файла (`sed -n '2p'`) сравнивается с паттерном:

```
^# <TASK_ID>[[:space:]][^#]
```

Точнее: `^# T-[0-9]+[[:space:]]·` — где `·` (Unicode U+00B7, middle dot) является разделителем
в принятом стиле заголовков (`# T-0040 · FF-RC1 ...`).

Если совпадение есть и извлечённый T-ID = TASK_ID — файл является собственным чеком.

### 5.3 Чеки без T-ID в заголовке

Ряд чеков имеет заголовок без явного T-ID (например, `actor_event_append_only.sh` начинается с
`# FF-4 (static half, ...)`). Такие чеки считаются **чужими** для любой конкретной задачи —
их нельзя изменять на task-ветке. (Они обслуживаются как «base infrastructure» и изменяются
только через ветки вне паттерна `task/T-XXXX-*`.)

### 5.4 Граничные случаи

| Ситуация | Поведение |
|---|---|
| Ветка `dev` или `main` | exit 0 (нет task-контекста) |
| Detached HEAD | `git rev-parse --abbrev-ref HEAD` вернёт `HEAD`; паттерн не совпадает → exit 0 |
| Ветка `task/T-0146-*` на самом `dev` (HEAD = dev) | merge-base = HEAD → diff пуст → exit 0 |
| `ci/checks/frozen-checks-immutable.sh` в diff, TASK_ID=T-0146 | собственный чек → разрешено |
| `ci/checks/dual-control-isolation.sh` в diff, TASK_ID=T-0118 | заголовок `# T-0044 ·` ≠ T-0118 → FAIL |
| Новый файл `ci/checks/new-gate.sh` в diff | diff-filter=A, не существует ранее → не нарушение (FR-6.1) |
| Удалён `ci/checks/role-criticality-isolation.sh`, TASK_ID=T-0099 | заголовок `# T-0040 ·` ≠ T-0099 → FAIL |

## 7. Out of scope

- **Контроль содержимого правок собственного чека** — мета-гейт разрешает любые изменения
  в собственном `*.sh` без проверки их семантики. Контроль смысла — зона ревьюера.
- **Изменения через non-task ветки** (ветки вне паттерна `task/T-XXXX-*`) — мета-гейт exit 0,
  эти изменения идут через отдельный review-процесс.
- **Переименование файлов `ci/checks/*.sh`** — рассматривается как DELETE + ADD; DELETE чужого
  файла уже запрещено (FR-5); новый файл — разрешён (FR-6.1).
- **Семантическая валидация bash-кода** в `*.sh` — не в области этого чека.
- **Проверка `.ts`-файлов, миграций, `src/`** — другие isolation-чеки.
- **Интеграция с GitHub Actions** — мета-гейт запускается в `npm run fitness` (локально и в CI);
  отдельный GitHub Actions job — за пределами задачи.
