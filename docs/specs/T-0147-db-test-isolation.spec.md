# Spec · T-0147 — Изоляция db-тестов от общего silo

**Phase:** SPEC
**Status:** ready (no BLOCKING — архитектурная развилка зафиксирована, решение принято на уровне требований)
**Product:** Choros · CI / db fitness tier
**Base:** dev · branch `task/T-0147-db-test-isolation`
**Born from:** rt-choros-s8 observation + T-0144 post-mortem — общий silo 55432 при параллельных
BUILD даёт загрязнение (genesis 17→70 за волну), T-0144 — паллиатив с afterAll-cleanup;
ложные красные от чужих live-DDL (FF-FK-RESOLVE на недомерженных миграциях сестёр).

---

## 0. Контекст и корневые причины

### 0.1 Два независимых вектора загрязнения

| Вектор | Механизм | Проявление |
|--------|----------|------------|
| **V-1: данные** | Параллельные `npm run fitness:db` из разных worktree пишут строки в один silo; `afterAll` одной сессии удаляет строки до того, как другая сессия их прочитала — гонка | `genesis-owner-seed.test.ts` AC-12: count ≠ 17 |
| **V-2: schema** | Соседняя task-ветка применяет новые миграции к общему silo пока текущая сессия ещё не смержена; FK-ссылки на несуществующие таблицы ломают INSERT-тесты | Ложные красные `FF-FK-RESOLVE` |

T-0144 фиксирует только обеспечение идемпотентности afterAll в пределах **одной** сессии.
T-0147 фиксирует изоляцию между **разными** сессиями (разные worktree, параллельные прогоны).

### 0.2 Архитектурная развилка

Рассматривались два подхода:

#### Вариант A: BEGIN / SAVEPOINT + ROLLBACK вокруг каждого теста

Каждый тест оборачивается в транзакцию, `afterEach` делает ROLLBACK, данные теста никогда не
коммитятся в silo.

**Проблема:** ряд тестов в `ci/checks/db/` принципиально несовместим с этим подходом:
- `pgTimerStore.integration.test.ts` AC-8 — два **параллельных пула** (`pool1 = makeAppPool()`,
  `pool2 = makeAppPool()`) проверяют `FOR UPDATE SKIP LOCKED`; SKIP LOCKED видит только
  строки **не залоченные** другими транзакциями — если каждый тест в своей открытой транзакции,
  семантика SKIP LOCKED нарушается.
- `cross_tenant.test.ts` — попеременно использует `migratorUrl()` (BYPASSRLS) и `appUrl()`
  (choros_app, NOBYPASSRLS) на **разных** соединениях; строки, вставленные через одно соединение
  внутри открытой транзакции, не видны второму соединению до COMMIT.
- `seed-pack.test.ts` и `grant-editor.test.ts` FF-10 live — поднимают реальный HTTP-сервер,
  который открывает собственный пул соединений; строки вставленные сервером через его пул
  не попадут под ROLLBACK тестового соединения.

Итог: Вариант A **не применим как универсальный механизм** — он сломает тесты, которые
намеренно тестируют multi-connection семантику. Может использоваться как opt-in для
отдельных тестов, но не решает проблему изоляции между параллельными прогонами.

#### Вариант B: Postgres template database (клон per-run, дроп после)

Перед запуском `npm run fitness:db` создаётся новая база данных из шаблона
(`CREATE DATABASE choros_test_<run_id> TEMPLATE choros_test_template`), полностью
независимая от silo 55432. После прогона база дропается. Разные worktree работают с
разными БД — гонки данных исключены по конструкции.

**Ограничения:**
- `CREATE DATABASE ... TEMPLATE <tmpl>` требует отсутствия активных соединений к шаблонной БД.
- Именование per-run должно учитывать одновременный запуск нескольких прогонов.
- Дроп базы требует закрытия всех соединений и может потребовать `pg_terminate_backend`.
- Шаблонная база должна существовать и быть заранее мигрирована (не пересоздаётся каждый раз).

Итог: Вариант B решает оба вектора загрязнения (V-1 и V-2), совместим с multi-connection тестами,
и является **рекомендованным решением**.

**Выбор ARCHITECT-а:** архитектор должен принять решение о конкретной механике создания/дропа
базы (globalSetup/globalTeardown vitest или обёртка в npm-скрипт), именовании (`choros_test_<pid>`,
`choros_test_<timestamp>`, или `choros_test_<random>`), и схеме прав (роли choros_migrator/choros_app
должны существовать на новой БД). Эта спека фиксирует требования — не реализацию.

## 1. Функциональные требования

**FR-1 — Изоляция прогонов по базам данных.** Каждый запуск `npm run fitness:db` должен работать
с базой данных, не разделяемой с параллельными прогонами из других worktree. Разные прогоны
должны использовать разные базы данных Postgres.

**FR-2 — Шаблонная база данных.** Должна существовать база-шаблон `choros_test_template`,
содержащая полностью применённые миграции choros (все файлы `migrations/NNN_*.sql`). При старте
прогона из неё клонируется рабочая база с уникальным именем. Шаблонная база не изменяется
в ходе прогонов.

**FR-3 — Уникальное именование per-run.** Имя рабочей базы должно быть уникальным для каждого
прогона и не конфликтовать с другими параллельными прогонами. Именование не должно зависеть
от фиксированного порта или worktree-пути — только от run-unique идентификатора.

**FR-4 — Прозрачный сетап шаблонной базы.** Должен существовать скрипт/команда
`npm run fitness:db:setup-template` (или эквивалентный step), который:
1. Создаёт базу `choros_test_template` (если не существует).
2. Применяет все миграции из `migrations/run.mjs` к шаблонной базе.
3. Идемпотентен: повторный запуск только применяет новые миграции (уже-применённые пропускает).
4. Требует `DATABASE_URL` суперпользователя/migrator с правом `CREATEDB`.

**FR-5 — Lifecycle: создание и удаление рабочей базы.** Lifecycle изоляции выполняется
автоматически в рамках прогона `npm run fitness:db`:
1. До запуска тестов: `CREATE DATABASE choros_test_<run_id> TEMPLATE choros_test_template`.
2. После завершения тестов (pass или fail): `DROP DATABASE choros_test_<run_id>`.
3. `DATABASE_URL` и `APP_DATABASE_URL` переопределяются для тестов так, чтобы указывали
   на рабочую базу (не на silo 55432).

**FR-6 — Совместимость с существующими тестами.** Ни один из существующих файлов в
`ci/checks/db/*.test.ts` не должен быть изменён. Механизм изоляции реализуется через
vitest `globalSetup`/`globalTeardown` или npm-скрипт-обёртку — снаружи тестов.
`_helpers.ts` (`migratorUrl()`, `appUrl()`) читают `DATABASE_URL`/`APP_DATABASE_URL` из env —
они уже корректно параметризованы.

**FR-7 — Сохранение режима `--no-file-parallelism`.** Текущий флаг
`vitest run --dir ci/checks/db --no-file-parallelism` сохраняется: тестовые файлы внутри
одного прогона выполняются последовательно. Это предотвращает гонки внутри одного прогона.
T-0147 изолирует только разные прогоны (разные worktree/PID).

**FR-8 — Дроп при наличии активных соединений.** Команда дропа рабочей базы должна корректно
завершить/разорвать активные соединения перед `DROP DATABASE` (через `pg_terminate_backend` или
`WITH (FORCE)` в Postgres 13+).

**FR-9 — Сохранение T-0144 afterAll-паттерна.** Cleanup-паттерны T-0144 (afterAll DELETE by ID)
остаются на месте — они полезны как второй слой защиты внутри одного прогона. T-0147 не
отменяет T-0144.

**FR-10 — Обратная совместимость CLI.** `npm run fitness:db` продолжает работать без
дополнительных аргументов при наличии `DATABASE_URL` (migrator-уровень) с правом `CREATEDB`.
Прогон без шаблонной базы (шаблон не создан) должен завершаться понятной ошибкой с инструкцией
запустить `npm run fitness:db:setup-template`.

## 2. Нефункциональные требования

**NF-1 — Без новых production-зависимостей.** Все дополнительные инструменты — только
`devDependencies`. Механика клонирования — стандартный SQL (`CREATE DATABASE ... TEMPLATE`),
доступный в Postgres 13+. Версия в docker-compose: postgres:16 — совместима.

**NF-2 — Стоимость клонирования.** Время `CREATE DATABASE ... TEMPLATE choros_test_template`
должно быть ≤5 секунд на dev-машине. (Postgres template clone = копия файловой системы внутри
кластера, типично < 1 с для небольшой БД.)

**NF-3 — Генезис стабильно = 17.** После T-0147 два параллельных прогона из разных worktree,
стартующих одновременно, каждый должен завершить `genesis-owner-seed.test.ts` AC-12 с count = 17.

**NF-4 — Отказоустойчивость дропа.** Если прогон упал аварийно (SIGKILL, OOM) и `DROP DATABASE`
не выполнился, должна быть возможность очистки вручную. Именование баз должно позволять
идентифицировать осиротевшие тестовые базы (паттерн `choros_test_*`) и предоставить
скрипт/команду `npm run fitness:db:cleanup-orphans`.

**NF-5 — Нет секретов в именах.** Имя базы не содержит паролей, токенов или worktree-путей.
Допустимо: PID, timestamp, random hex.

## 3. Не в области видимости

- Вариант A (BEGIN/ROLLBACK per test) как универсальный механизм — несовместим с multi-connection
  тестами (AC-8 pgTimerStore, cross_tenant) и отклонён.
- Изоляция других CI-тиров (`fitness:kc`, `fitness:flowable`) — только `fitness:db`.
- Изменение структуры `migrations/run.mjs` — он уже работает с произвольной `DATABASE_URL`.
- Изменение `docker-compose.yml` или silo 55432 — изоляция реализуется поверх него.
- Изоляция на уровне Postgres-схем (не баз) — не даёт изоляции по ролям и миграционной таблице.
- Параллелизм внутри одного прогона (убрать `--no-file-parallelism`) — вне задачи.
- Изоляция `fitness:demo:db` — отдельный тир, отдельная задача.

## 4. Критерии приёмки

### AC-1 — Два параллельных прогона из разных worktree не конфликтуют

**Verifiable as:** test

Два одновременных прогона `npm run fitness:db` из разных worktree (разные каталоги,
разные `TMPDIR`/`PID`) должны оба завершиться зелёными. В частности:
- `genesis-owner-seed.test.ts` AC-12 зелёный в обоих прогонах (count = 17 в каждой БД).
- Ни один прогон не получает `ERROR: database "choros_test_*" is being accessed by other users`.

### AC-2 — Повторный прогон не меняет состояние шаблонной базы

**Verifiable as:** test

Запуск `npm run fitness:db` дважды подряд (последовательно):
1. После каждого прогона рабочая база задроплена.
2. Шаблонная база `choros_test_template` не изменена (row counts идентичны до и после).
3. `genesis-owner-seed.test.ts` AC-12: count = 17 в обоих прогонах.

### AC-3 — genesis стабильно = 17

**Verifiable as:** test

Запуск `npm run fitness:db` на чисто мигрированной шаблонной базе: `genesis-owner-seed.test.ts`
завершается зелёным с count = 17. Повторный запуск — то же самое. N-й запуск — то же самое.

### AC-4 — Существующие тесты не изменены

**Verifiable as:** fitness

`git diff HEAD -- ci/checks/db/*.test.ts` пустой (ни один тестовый файл не изменён).
Механизм изоляции реализован снаружи тестов.

### AC-5 — Рабочая база задропается даже при аварийном завершении тестов

**Verifiable as:** test / manual

При принудительном `kill -9` vitest-процесса в ходе прогона рабочая база
`choros_test_<run_id>` не остаётся в живом состоянии (либо дроп выполнен при следующем
старте, либо `npm run fitness:db:cleanup-orphans` удаляет все `choros_test_*` базы).

### AC-6 — Понятная ошибка при отсутствии шаблонной базы

**Verifiable as:** manual

При запуске `npm run fitness:db` без предварительного `npm run fitness:db:setup-template`
прогон завершается с exit code ≠ 0 и сообщением, явно указывающим: «run
`npm run fitness:db:setup-template` first» (или эквивалентным).

### AC-7 — setup-template идемпотентен

**Verifiable as:** test / manual

Двукратный запуск `npm run fitness:db:setup-template` не дублирует миграции и не
падает с ошибкой. Второй запуск выводит «nothing to apply» (паттерн `migrations/run.mjs`).

### AC-8 — Права rolemap на рабочей базе корректны

**Verifiable as:** test

После клонирования: `withClient(appUrl())` (choros_app) и `withClient(migratorUrl())` (choros_migrator)
успешно подключаются к рабочей базе. RLS-тесты (`cross_tenant.test.ts`) зелёные.

### AC-9 — Стоимость клона ≤ 5 с

**Verifiable as:** manual

`time CREATE DATABASE choros_test_perf_check TEMPLATE choros_test_template` на dev-машине
(homeserver-vm или локальный docker) занимает < 5 секунд.

## 5. Развилки для ARCHITECT

Следующие вопросы не меняют объём задачи, но меняют конкретную реализацию и должны
быть решены в фазе DESIGN:

**D-1 — Lifecycle-механизм: globalSetup vs npm-обёртка.**
`vitest.config.ts` поддерживает `globalSetup`/`globalTeardown` — lifecycle до и после
прогона; альтернатива — обёртка в npm-скрипт `scripts/run-db-tests.sh` (создать БД →
`vitest run` → дропнуть БД). `globalSetup` чище, но требует Typescript в конфиге.

**D-2 — Именование per-run базы: PID vs timestamp vs random hex.**
Требования: уникальность, < 63 символов (limit Postgres), паттерн `choros_test_*`.
Варианты: `choros_test_<pid>` (не уникален при перезапусках), `choros_test_<epoch_ms>`,
`choros_test_<random_8hex>`. Architect выбирает.

**D-3 — Механизм передачи URL в тесты.**
`vitest globalSetup` не может напрямую передать env-переменные в тест-файлы (они уже
форкнуты). Варианты: запись в `process.env` до spawn worker'ов (нативно в vitest 1.x+),
или файл `.env.test` (перезаписывается перед прогоном). Architect выбирает.

**D-4 — Права CREATE DATABASE.**
Стандартный `choros_migrator` (bootstrap owner) может не иметь `CREATEDB`. Architect
должен проверить и при необходимости задокументировать, нужно ли ALTER ROLE или
использовать суперпользователя только для CREATE/DROP DATABASE.
