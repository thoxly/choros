# Спека: Текст-первый конструктор сквозных решений (D8 · Трек G)

> Пользователь **описывает проблему словами** → система определяет, какие сущности есть /
> чего нет → собирает **сквозное** решение (приложение + связи + процесс) в песочнице →
> человек ревьюит и публикует. Садится **поверх** исполняемого набора
> (`process-element-runtime.spec.md`, D8 · Трек R).
>
> Решения: [../product-decisions.md](../product-decisions.md) PD-21, PD-22, PD-23.
> Расширяет PD-3/PD-5/PD-16 (был draft-only «правь существующее» → теперь генеративно «собери
> новое», включая создание приложений и каскад связей). Зависит: D1 tenant-zero (T-0373 —
> доступность бота), D5 BYO (T-0382), D7 forms-data-contract. Статус: спека · 2026-06-25.

## 1. Зачем
Цель — из **человеческого описания** («у нас бардак с закупками… хочу единую форму,
автоподсчёт суммы, и чтобы крупные заявки шли на доп. согласование») собрать сквозное решение:
приложение с полями (включая связь/позиции/итог) + процесс с ветвлением по сумме + прогон.
Эталон приёмки — детальный чек-лист закупок (Часть А данные + Часть Б процесс), но **вход —
обычная жалоба**, не пошаговая инструкция.

## 2. Проверенное состояние (2026-06-25)
- Конфигуратор `assistant-configurator.ts`: **5 инструментов** (edit_jsonschema / emit_form /
  author_binding / author_dmn / request_promote), все **DRAFT**, грант `authoring_draft`.
  **Инструмента создания приложения НЕТ** (правит только существующий `registry_def` по id).
- **Каскада «целевого приложения нет → создать» НЕТ.** `cross-app-ref.ts` обрабатывает
  несуществующую **ЗАПИСЬ на чтении** (`not_found`/`dangling_ref`), а не несуществующее
  **ПРИЛОЖЕНИЕ на авторинге**.
- Интент «построй/собери CRM» → `classifyIntent`→`handleAnalyst` (**read-only аналитик**), не
  конфигуратор.
- Доступность: самозарег-тенант без `assistant-agent`/гранта → 503/403 (D1 tenant-zero T-0373).
  Работает только в seeded-тенанте.
- Слой данных: `registry_def` + поля scalar/enum/**relation(cross_app_ref)**/**collection
  (line-items)**/**rollup** — F5-трио задеплоено.
- Процесс: публикация draft→lint→deploy готова; рантайм исполняет ветвление (E15). **Свободной
  генерации процесса ботом нет** (нет инструмента авторить граф).

## 3. Дизайн

### 3.1 Поток (PD-21)
1. **План в диалоге (лёгкий, текст).** Бот разобрал жалобу → определил, какие сущности есть /
   чего нет → предложил план человеческим языком («нужно приложение *Заявки на закупку* с
   полями …; приложения *Контрагенты* у вас **нет** — создам связанное; процесс: подача →
   согласование → если сумма большая → доп. согласование, иначе закрыть»). Пользователь правит
   текстом.
2. **Генерация в песочницу (DRAFT).** One-shot: бот собирает весь черновик **бандлом**.
3. **Ревью и публикация в разделах.** Deep-link в Приложения/Модельер; визуальная проверка там
   (экраны уже рендерят форму/диаграмму/карточку), **promote там**. **НЕ рендерим всё в
   диалоге** (это переписать конструктор в чате — слишком тяжело). Деструктив/публикация —
   human-gated.

### 3.2 Каскад связанных приложений (G2) — примитив в ядре
Relation-поле ссылается на приложение, которого нет → бот создаёт связанное приложение в **ТОМ
ЖЕ DRAFT-бандле** (один promote), показывает заметно в плане. **Дедуп:** сперва ищет похожее
среди существующих `registry_def` (PD-5 «валидировать против существующего») — нашёл →
ссылается, неоднозначно → спрашивает. **Глубина каскада** ограничена (HOP_CAP=3, как
`cross-app-ref`). Примитив живёт в **authoring-ядре**: бот и визуальный relation-picker — оба
драйверы (Развилка-5: один примитив, два входа).

### 3.3 Инструменты конфигуратора (G1)
Добавить **`create_application`** (создать раздел+приложение в DRAFT). Роутинг интента:
«построй / собери / настрой» → **конфигуратор** (не аналитик), при наличии гранта
`authoring_draft`.

### 3.4 Генерация свободного процесса (G3)
Над исполняемым набором (Трек R). Бот эмитит **BPMN-черновик свободной топологии** → цикл
**«сгенерил → `bpmn-linter` / гард мёртвой ветки → почини по тексту ошибки → повтор»**
(ограниченное число попыток). Условия шлюзов и роли **заземлены на реальные** поля/роли (создал
→ ссылается; нет → каскад). Ревью — в Модельере (диаграмма уже рисуется).

### 3.5 Доступ (G5) — PD-21
Песочница (DRAFT) = только держатель `authoring_draft` (админ/владелец). Остальным —
**человеческий** ответ «у вас нет прав настраивать, обратитесь к администратору» (не сырой 503).
Опция: **захватить описание не-админа и положить админу заявкой-на-настройку** (founder-решение,
п.5). Песочница → продуктив = `promote`.

## 4. Инвентарь работ → задачи
- **G1** `create_application` + интент-роутинг (построй→конфигуратор).
- **G2** каскад связанных приложений (примитив в ядре, дедуп против существующего, hop-cap).
- **G3** свободная генерация процесса (generate→lint→repair, заземление на реальные поля/роли).
- **G4** план-в-диалоге + ревью-в-разделах (deep-links) + бандл-promote.
- **G5** гейтинг доступа + не-админ-роутинг.
- **G6** deploy-acceptance journey: **сценарий закупок целиком** (Часть А данные +
  Часть Б процесс+прогон) зелёный на деплое.
- Зависимости: T-0373 (tenant-zero доступность), T-0382 (BYO), **Трек R целиком**.

## 5. Открытое к уточнению на импле
- Формат «плана»: структурированный JSON-превью vs чистый текст — на G4.
- Дедуп-матчинг приложений: точное имя vs эмбеддинг-похожесть — на G2.
- Заявка-на-настройку от не-админа: в v1 или опция — за фаундером.

## 6. Последовательность
Трек R (исполняемый набор) → **G1+G2** (данные+каскад) → **G3** (процесс) → **G4** (UX потока)
→ **G5** (доступ) → **G6** (сквозной journey). Доступность реальному юзеру = T-0373/T-0382
(параллельный гейт продакшна; способность доказываем в seeded-тенанте).
