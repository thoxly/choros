## 0. Проблема (доказано живьём 2026-07-01/02, карта примитивов D4/D5)

Экран «Доступ» (`/rights`) сегодня **лжёт**: `GET /api/rights` (`src/http/rights.ts`) не
читает tenant-состояние (реальные `choros.role`/`choros.role_assignment`/`choros."grant"`)
— он либо отдаёт `RIGHTS_SEED` (12 захардкоженных ролей, no-DB fallback), либо, при
`DATABASE_URL` установленном, читает **demo-showcase-pack** (`tryLoadShowcasePack()`,
`pack.rights_cards`) — статичный фикстур-файл, не строки БД. Ни один путь не делает
`SELECT ... FROM choros.role` / `choros.role_assignment` / `choros."grant"` для тенанта
вызывающего. На живом тенанте с реально созданными ролями (владелец видел это глазами
2026-07-02) экран показывает пустой список («Нет ролей») или демо-пакет — то и другое
неправда относительно того, что реально есть в БД.

Отдельно, вкладка «Каталог ролей» (`web/src/app-shell/shell.jsx:72`,
`id:"editor", path:"/rights/editor", status:"demo"`) рендерит `RoleEditorScreen`
(`ra-role-editor.jsx`), который **частично уже жив** (T-0039: `propose()`/POST к реальному
`/api/grants`, `/api/grants/propose`, динамический выбор роли устранил хардкод
`EDITOR_ROLE_ID` — комментарий в коде подтверждает: «EDITOR_ROLE_ID is now the
live-selected role UUID»). Бейдж «demo» на этой вкладке — устаревшая декорация, не
отражающая текущее состояние кода (нарушение G7 «бейдж≡контент»).

При этом бэкенд **богатый и живой**:
- `POST /api/grants`, `POST /api/grants/:id/revoke`, `POST /api/role-assignments`,
  `POST /api/role-assignments/:id/revoke` (`src/http/grants.ts`) — структурная запись
  грантов/назначений, gated `validateAdminDelegation`, атомарная запись+аудит.
- Two-phase dual-control **уже реализован end-to-end**: `POST /api/grants` /
  `POST /api/role-assignments` с `{phase:"confirm2", change_ref}` — второй
  аутентифицированный подтверждающий (различность enforced на трёх принципалах:
  proposer/confirmed_by/confirmed2_by).
- `GET /api/rights/change-requests` + `POST /api/rights/change-requests/:id/approve|reject`
  (`src/http/rights-change-requests.ts`, T-0390) — **уже готовый** UI-friendly слой
  над dual-control: список semi-confirmed (`confirmed_by IS NOT NULL AND confirmed2_by
  IS NULL`) grant/assignment строк + approve/reject. Уже потребляется вкладкой
  `/rights/criticality` (`ra-criticality.jsx`) честно (loading/error/empty/list).
- `GET /api/rights/dictionaries` (`src/http/grants.ts`) — 10+4 именованных пресета,
  словари ресурсов/операций/org-дерева/scope-тегов.
- `GET /api/org/tenant-state?tenant_id=X` (`src/http/seed-write.ts`) — читает реальные
  `department`/`position`/`employee`/`role` строки тенанта (`{id, slug}`), но: (а) gated
  `isGenesisOwner || hasOrgObjectAuthority` (admin-only, не для read-only-юзера), (б) не
  содержит грантов/назначений/holders — это importer/reset-diff инструмент, не «Обзор
  ролей».
- Нет НИ ОДНОГО GET-эндпоинта, который читает `choros.role` + `choros.role_assignment` +
  `choros."grant"` вместе для «честного обзора ролей тенанта» — это и есть корень лжи D4.

Замкнутый круг (карта примитивов §4 п.4): `authoring_draft`-грант ассистенту/владельцу
некому выдать — грант-UI нет. Эта задача размыкает круг, давая ручку выдачи/отзыва из
продукта; T-0573 (параллельно) даёт backfill старым тенантам.

## 1. Summary

1. **Честный «Обзор ролей»**: новый GET-эндпоинт читает tenant-состояние (`choros.role`
   LEFT JOIN `choros.role_assignment` LEFT JOIN `choros."grant"`) для тенанта
   вызывающего — не demo-пак, не in-memory seed. `screen-rights.jsx` переключается на
   него. Пустой тенант показывает честный `EmptyState`; тенант с ролями показывает их.
2. **Выдача/отзыв роли пользователю** и **выдача/отзыв гранта роли** — из UI, через
   существующие `POST /api/role-assignments`, `POST /api/role-assignments/:id/revoke`,
   `POST /api/grants`, `POST /api/grants/:id/revoke`. Никакого нового write-пути в обход
   dual-control: если ответ сервера `{state:"semi-confirmed", second_approver_required:
   true}`, UI показывает состояние «ждёт второго подтверждения» честно (не притворяется,
   что грант уже активен).
3. **«Кто что может»**: новая вкладка/секция — админ видит выданные права по роли/по
   пользователю (агрегация ролей+грантов+назначений); обычный пользователь видит только
   СВОИ права (PD-17 F1 — read-only человеческим языком).
4. **«Каталог ролей» декорация снята**: либо убрать `status:"demo"` (заменить на `"live"`,
   т.к. `ra-role-editor.jsx` уже пишет в реальный API), либо, если найдётся оставшийся
   мок-путь при разведке на DESIGN/BUILD, зафиксировать его явным `TODO` с номером
   следующей задачи — G7 не разрешает молчаливое несоответствие бейджа коду.
5. **READ уважает PDP**: сам экран «Доступ» не раскрывает грант-механику акторам без прав
   на неё (403 fail-closed на write-эндпоинтах уже есть через `validateAdminDelegation`;
   этот пункт фиксирует, что UI **скрывает** недоступные действия, а не просто ловит 403
   постфактум — деградация чтения, не только записи).

## 3. Функциональные требования

- **FR-1 — Честный источник «Обзора ролей».** Новый GET-эндпоинт (владелец решения —
  architect: новый файл `src/http/rights-overview.ts` или эквивалент) возвращает
  tenant-состояние: для тенанта вызывающего — ВСЕ строки `choros.role`, для каждой роли
  — её подтверждённые (`confirmed_by IS NOT NULL`, в окне валидности) `role_assignment`
  (→ employee display/type: human/agent/service) и её подтверждённые `grant` (→
  resource_type/operation/scope). Тенант с 0 ролей возвращает `{roles: []}` — честно,
  без demo-флага, без подмены сидом. `screen-rights.jsx` (или его преемник) читает ЭТОТ
  эндпоинт, не `/api/rights`.
- **FR-2 — Выдача/отзыв роли пользователю из UI.** Экран предоставляет форму «назначить
  роль сотруднику» (employee + role + org_scope), которая POSTит на существующий
  `POST /api/role-assignments` (не новый эндпоинт). Отзыв — кнопка на существующем
  назначении → `POST /api/role-assignments/:id/revoke`. UI показывает результат сервера
  без прикрас: `{state:"confirmed"}` → назначение активно; `{state:"semi-confirmed",
  second_approver_required:true}` → назначение показано как «ждёт подтверждения» (не
  «активно»), с явной ссылкой/переходом на существующий инбокс `/rights/criticality`
  (`GET /api/rights/change-requests`) для второго подтверждающего — НЕ дублирует его
  approve/reject логику в новом месте.
- **FR-3 — Выдача/отзыв гранта роли из UI.** Экран предоставляет форму «дать роли право»
  (resource_type + operation + scope [+ constraint]) на базе существующих словарей
  (`GET /api/rights/dictionaries`) и/или пресетов, которая POSTит на существующий
  `POST /api/grants`. Отзыв — `POST /api/grants/:id/revoke`. Тот же честный
  semi-confirmed/confirmed рендеринг, что и FR-2. Advanced-режим (сырой грант на
  resource_type/operation/scope) — только для владельца/админа (PD-17 F1); НЕ для
  обычного пользователя (у которого нет authority-гранта — сервер и так вернёт 403
  `ADMIN_GATE_REJECTED`, но UI обязан не предлагать форму, которую пользователь не может
  выполнить — деградация видимости, не только перехват ошибки).
- **FR-4 — Сужение скоупа гранта достижимо из UI.** Форма гранта (FR-3) поддерживает
  задание `scope` уже (T-0021/T-0018 латтис: `node`/`tags`/`interval`/`set`) — форма НЕ
  ограничивается «весь тенант / ничего»: пользователь может создать грант с более узким
  scope, чем существующий default/wide грант той же роли (сужение — настройка, не код,
  T-0570 FR-3). Если конкретный UX для record-level сужения (например «только свои
  записи») требует record-scope выбора, которого текущая `ScopeElement` палитра ещё не
  показывает в UI (только `org`/`resource` node-дерево видно в `ra-role-editor.jsx`
  сегодня) — DESIGN явно фиксирует, какой поднабор scope-примитивов выставлен в форме
  день-1, остальное — `out_of_scope` со ссылкой на будущую задачу. Эта спека НЕ требует
  полного UI на все ветки `ScopeElement`-объединения — только чтобы сужение было
  технически достижимо через уже существующий scope-parser (`parseScopeElement`,
  `src/http/grants.ts`), не через новый код-путь.
- **FR-5 — Dual-control честен, не обходится.** Ни один UI-путь эту задачу не создаёт
  грант/назначение в обход `POST /api/grants`/`POST /api/role-assignments` (никакого
  прямого DAO-вызова из HTTP-слоя в обход существующего write-API). Состояние
  «semi-confirmed» **не** показывается как активное право нигде на экране (ни в «Обзоре
  ролей», ни в «кто что может») — до `confirmed2_by IS NOT NULL` право не входит в
  «действующие права» этой роли/пользователя.
- **FR-6 — «Кто что может»: два взгляда.** Экран (новая вкладка ИЛИ секция существующей
  `overview`, решает DESIGN) предоставляет:
  - **Админ-взгляд**: список выданных прав, группируемый по роли ИЛИ по пользователю
    (сотруднику) — переиспользует данные FR-1 (роли+назначения+гранты), спроецированные
    в человеко-читаемый вид (аналогично существующей секции «Производное от грантов» в
    `screen-rights.jsx`, которая уже вычисляет `tools`/`fields` из `role.grants`).
  - **Юзер-взгляд**: обычный пользователь видит ТОЛЬКО свои права (роли, которыми он
    обладает, и что эти роли дают) человеческим языком (PD-17 F1 read-only) — новый или
    расширенный эндпоинт фильтрует по `employee_id = self`, не по всему тенанту, когда
    вызывающий не admin/owner (сервер решает по грантам вызывающего, не по клиентскому
    флагу — тот же принцип, что и `holdsObservabilityRead`/`isGenesisOwner`
    паттерн в `capability-authz.ts`/`org.ts`).
- **FR-7 — READ уважает PDP на самом экране.** Формы выдачи/отзыва (FR-2/FR-3) НЕ
  рендерятся (или рендерятся в disabled-состоянии с честным объяснением, аналогично уже
  существующей кнопке «Запросить изменение» в `screen-rights.jsx:143`, которая disabled
  с title, когда эндпоинт не существует) для актора, у которого нет authority-гранта
  (`mgmt_object:role`/`mgmt_object:grant`) — определяется тем же серверным сигналом, что
  уже используется в `GET /api/me/nav-capabilities` (`zones.includes('admin')` /
  `isGenesisOwner`). Обычный пользователь видит read-only «Обзор ролей» + «Мои права»;
  не видит форм записи вообще (не просто disabled-кнопки — как минимум формы не должны
  протекать данные о том, ЧТО можно было бы выдать, если у актора нет причины это знать
  — соответствует принципу «403 fail-closed», уже действующему на бэкенде).
- **FR-8 — «Каталог ролей» бейдж честен.** По итогам разведки DESIGN: если
  `ra-role-editor.jsx` действительно полностью пишет в реальный API (что подтверждено
  этой спекой на уровне кода, §2), бейдж `status:"demo"` в `shell.jsx:72` меняется на
  `"live"`. Если DESIGN находит остаточный мок-путь (например, что-то в
  `ra-data.jsx`/`INITIAL_GRANTS`, используемое НЕ только как placeholder до первого
  fetch), бейдж остаётся `"demo"`, но в тексте/тултипе указывается КОНКРЕТНО что именно
  мок — не общая формулировка. G7 (бейдж≡контент) применяется буквально: перед мержем
  DESIGN обязан явно решить, какой из двух случаев верен.

## 4. Нефункциональные требования

- **NF-1 — Переиспользование, не дублирование write-API.** Никакой новый POST-эндпоинт
  для создания/отзыва грантов или назначений — используются существующие
  `POST /api/grants(/:id/revoke)`, `POST /api/role-assignments(/:id/revoke)`,
  `POST /api/grants` `{phase:"confirm2"}`. Единственный новый эндпоинт по этой спеке —
  READ (FR-1/FR-6) — write-путь заморожен (зеркалит NF-5 T-0570/T-0044).
- **NF-2 — Dual-control не отключается из UI.** Ни один UI-флаг/параметр не позволяет
  обойти two-phase confirm для критичных изменений (PD-17 F2 — «не отключаемо» —
  буквально: в коде экрана нет пути, который бы звал `POST /api/grants` с телом, минующим
  существующий `dualControlDecision`-гейт на сервере; сервер и так это гарантирует, но
  спека фиксирует, что клиент не пытается сделать вид, что гейта нет).
- **NF-3 — Fail-closed видимость.** Экран деградирует к пустому/read-only состоянию при
  отсутствии прав или данных — никогда не показывает частично устаревшее/угаданное
  состояние вместо честной ошибки (Empty/Loading/Error — обязательны на каждой вкладке,
  зеркалит существующий паттерн `screen-rights.jsx`/`ra-criticality.jsx`).
- **NF-4 — Анти-кейс (D-064).** Ни одна добавленная/изменённая строка под `src/` или
  `web/src/` этой задачи не содержит `role-approver`, `soglasovanie`, `tel-`,
  `Согласование` (как строковая константа), `e-larina`, `e-orlov`, `e-configurator` —
  проверяется тем же git-diff-scoped гейтом `ci/checks/read-pdp-anti-case.sh` (D-064,
  применяется репо-широко, не только к T-0570).
- **NF-5 — Пропорциональность.** Новый серверный код переиспользует
  `resolveActorTenant`/`resolveActorSlugFromAuth`/`loadAdminContext`/`withAuth` (те же
  примитивы, что `grants.ts`/`rights-change-requests.ts`/`org.ts`) — не переизобретает
  actor/tenant resolution.
- **NF-6 — UX_REVIEW обязателен.** Эта задача трогает `web/` существенно (минимум 2 экрана
  переписываются на живые данные + минимум 1 новая форма/секция) — UX_REVIEW фаза
  обязательна перед TEST (зеркалит D-064 дисциплину «UX_REVIEW для всего, что трогает
  web/»).
- **NF-7 — Empty/Loading/Error — AC, не пожелание.** Каждая вкладка/секция, которую эта
  задача добавляет или переписывает («Обзор ролей», «кто что может» — оба взгляда, формы
  выдачи/отзыва) реализует все три состояния явно (проверяется по факту наличия
  соответствующих компонентов/веток рендера, не по ощущению).

## 5. Out of scope (явно НЕ в этой задаче)

- READ-PDP механизм record/field-видимости самого движка — T-0570 (уже в базе, эта задача
  строит UI НАД ним, не переделывает резолвер).
- Backfill default-грантов старым тенантам — T-0573 (параллельно в волне).
- SoD (`sod_constraint`) DAO/write-эндпоинты/UI — T-0032/T-0386 (`ra-sod.jsx` остаётся
  вне периметра; отдельный примитив от dual-control, FR-18 T-0044 фиксирует границу).
- Расширение маскинг-грамматики поверх существующего `roleFieldVisibility`/
  `applyFieldVisibilityRedaction` — не трогается.
- Полный UI на ВСЕ ветки `ScopeElement` (в частности `interval`/произвольный `tags`-набор
  для record-level «менеджер видит своих клиентов» К1-сценария) — день-1 достаточно, чтобы
  сужение было ДОСТИЖИМО через существующий scope-parser; полнота палитры — отдельная
  задача, если заведена (см. FR-4).
- Изменение `dual-control.ts`/`role-criticality.ts`/`grant-resolver.ts`/`grant-lattice.ts`
  — заморожены (NF-5).
- «Запросить изменение» для обычного пользователя (мёртвая disabled-кнопка в
  `screen-rights.jsx:143`) — остаётся disabled, если только не найден готовый бэкенд-путь
  на разведке DESIGN (не заявлено этой спекой как FR).
- Новый эндпоинт `/api/pdp/explain`-подобный «почему у меня нет доступа к X» вне
  существующего explain (T-0136) — не расширяется этой задачей.
- Управление пользователями-учётками (создание сотрудника из UI, а не из Keycloak-admin)
  — карта примитивов E5, отдельный примитив.

## 6. LIVE_PROOF-путь (D-064)

Обязательный путь на живом тенанте (владелец ООО Аксон, не демо-ТЭЛ), глазами, не CI:

1. Владелец открывает «Доступ» (`/rights`) → видит вкладку «Обзор ролей» с РЕАЛЬНЫМИ
   ролями тенанта (не «Нет ролей», если роли есть; если ролей действительно 0 — честный
   `EmptyState`, не demo-заглушка).
2. Владелец выбирает существующую роль (или создаёт назначение новому сотруднику) →
   выдаёт роль сотруднику через форму (FR-2) → видит либо немедленное подтверждение
   (`state:"confirmed"`, некритичное изменение), либо честное «ждёт второго
   подтверждения» (`state:"semi-confirmed"`) для критичного случая.
3. Владелец выдаёт грант роли — например `authoring_draft` (для разблокировки ассистента,
   карта примитивов §4 п.4) или сужение `role-reader` (READ-гранта, T-0570) — через форму
   (FR-3), с явным scope.
4. Владелец открывает «кто что может» → видит выданное право в списке (если
   `confirmed`) — по роли и/или по сотруднику.
5. **Dual-control честно прожит**: если шаг 2 или 3 эскалировал в `semi-confirmed`,
   владелец (или второй администратор) переходит в существующий инбокс
   (`/rights/criticality`, уже живой) и подтверждает через `POST
   /api/rights/change-requests/:id/approve` — ПОСЛЕ этого право появляется в «кто что
   может» как активное; ДО этого оно не появляется там как активное (может быть показано
   как «ожидает» в «Обзоре ролей», если DESIGN решает это отобразить).
6. Обычный сотрудник (не админ) открывает «Доступ» → видит ТОЛЬКО свои права
   человеческим языком (не грант-редактор, не список чужих ролей с формами записи).
7. **Круг размыкается**: владелец, у которого до этой задачи не было UI-пути выдать
   `authoring_draft` (карта примитивов §4 п.4 — «выдать его неоткуда»), теперь может это
   сделать сам себе или ассистенту через форму FR-3 — без прямого API/curl.
