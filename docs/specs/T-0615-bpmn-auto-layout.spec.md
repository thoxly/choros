## 1. Контекст (живой факт со стенда, 2026-07-03, подтверждён консолью)

Модельер процессов (`/processes/:id/edit`) падает с ошибкой bpmn-js `importXML error: no diagram to display`
для ЛЮБОГО определения, чей BPMN-XML НЕ содержит diagram-interchange (DI) — блока
`<bpmndi:BPMNDiagram>` с координатами узлов. Пользователь видит пустой канвас с палитрой,
но без диаграммы: процесс невозможно посмотреть или править.

Живые строки таблицы `choros.process_definition.bpmn_xml` (со стенда):
- определения, залитые голым BPMN через seed / API / emit ИИ-ассистента, — БЕЗ DI (`has_di=false`)
  → не рисуются вообще (в т.ч. боевой процесс закупок волны 1);
- определение, созданное в самом модельере, — С DI → рисуется нормально.

Причина техническая: bpmn-js — это рендерер diagram-interchange. Без `<bpmndi:BPMNDiagram>`
→ нет `BPMNPlane` → нет `BPMNShape`/`BPMNEdge` → нечего рисовать → `importXML` реджектит.
Голый BPMN (только `<process>` с узлами и потоками) исполним движком Flowable, но
не несёт КООРДИНАТ — их никто не вычислял, потому что модельер этот XML не трогал.

## 2. Разведка (карта кода)

- **Единственная точка рендера:** `web/src/canvas/bpmn-modeler-wrapper.jsx` — единственный
  файл, инстанцирующий `BpmnModeler` (`bpmn-js/lib/Modeler`) и зовущий `importXML`.
  - `xmlToLoad = initialXml || DEFAULT_DIAGRAM_XML` (строка 165): `initialXml` — XML с бэкенда
    (может быть без DI); `DEFAULT_DIAGRAM_XML` — встроенный шаблон для новых пустых определений
    (несёт DI).
  - `modeler.importXML(xmlToLoad).then(...).catch(...)` — цепочка с уже существующим (T-0484)
    честным `onError`-баннером в `.catch` (иначе пустой канвас без объяснения).
- **DMN-редактор** (`web/src/screens/screen-dmn-editor.jsx`) НЕ использует bpmn-js — это React-форма;
  вне рамок.
- **Бэкенд** (`src/http/process-defs.ts`, `src/core/bpmn-deploy-normalizer.ts`): хранит `bpmn_xml`
  как строку; при публикации нормализует (правит id/isExecutable, переписывает `BPMNPlane bpmnElement`
  ЕСЛИ DI уже есть), но НЕ генерит координаты. Никакой bpmn-moddle на сервере — чистые строковые
  трансформации. То есть определения без DI приходят с сервера без DI и остаются без DI.
- **bpmn-auto-layout** (`layoutProcess(xml) → Promise<string>`, пакет bpmn-io) — чистый
  bpmn-moddle-трансформ, генерит `<bpmndi:BPMNDiagram>` с координатами; НЕ требует DOM
  (проверено: работает в node-окружении тестов). Зависимости `bpmn-moddle@^10`, `min-dash@^5`
  совпадают с транзитивными зависимостями bpmn-js@17 — конфликта версий нет.

## 3. Решение

- (A, ПЕРВИЧНЫЙ) КЛИЕНТ: при загрузке XML в модельер детектить отсутствие DI структурно
  и прогонять XML через `bpmn-auto-layout` ДО `importXML`. Это чинит ВСЕ существующие
  определения при открытии (включая боевой процесс закупок) БЕЗ миграции данных.
- (B, FOLLOW-UP) СЕРВЕР: генерить DI при сохранении/публикации, чтобы хранимый XML всегда
  был с DI (консистентность хранения). Не входит в T-0615 — вынесено в O1 (см. ниже, требует
  bpmn-moddle на бэкенде + бэкфилл уже сохранённых определений).

Механизм ОБЩИЙ (закон границы D-064): отсутствие DI определяется структурно (есть ли элемент
`BPMNDiagram`), НЕ по имени процесса. Никаких кейс-литералов в src/web.

## 4. Функциональные требования

- **F1.** Новый чистый модуль `web/src/canvas/bpmn-ensure-layout.js` экспортирует
  `hasDiagramInterchange(xml) → boolean` — структурный, prefix-agnostic детектор наличия
  элемента `BPMNDiagram` (любой/без namespace-префикс; не ложно-срабатывает на подстроку
  внутри значения атрибута или текста; безопасен для пустого/не-строкового ввода).
- **F2.** `ensureLayout(xml) → Promise<{ xml, layoutApplied }>`: если DI отсутствует —
  прогоняет `layoutProcess(xml)` и возвращает XML с DI (`layoutApplied=true`); полученный XML
  несёт `BPMNShape`+`Bounds`, то есть канвас получает рисуемые узлы.
- **F3.** Если DI УЖЕ присутствует — `ensureLayout` возвращает исходный XML БАЙТ-В-БАЙТ
  (`layoutApplied=false`), авто-раскладка НЕ вызывается: раскладка автора важнее и не перетирается.
- **F4.** Честная деградация: если сам `layoutProcess` упал (или не породил DI) — `ensureLayout`
  бросает именованную ошибку `auto-layout failed: …`; `bpmn-modeler-wrapper.jsx` в `.catch`
  показывает пользователю понятное «Не удалось построить схему автоматически: …» через `onError`,
  а НЕ немой пустой канвас.
- **F5.** `bpmn-modeler-wrapper.jsx` вклинивает `ensureLayout(xmlToLoad)` перед `importXML`
  в ту же промис-цепочку `.then()/.catch()` (существующий `onError`-путь T-0484 сохранён).

## 5. Нефункциональные требования

- **N1.** Закон границы D-064: НИ ОДНОГО кейс-литерала (имени процесса/тенанта/роли) в
  `src`/`web/src`. Детект DI — структурный. `anti-case-lock.sh` остаётся на baseline (aggregate 24=24).
- **N2.** Новая зависимость `bpmn-auto-layout` — КЛИЕНТСКАЯ (`web/package.json`), не попадает
  в бэкенд `src` (`bpmn-linter-isolation.sh` сканирует рантайм-зону `src` — не затронут).
- **N3.** Тесты в node-окружении (vitest env=node): тестируется чистый модуль (не инстанцируется
  `BpmnModeler`, который требует DOM); `layoutProcess` — bpmn-moddle-трансформ, работает в node.
- **N4.** Существующее поведение определений С DI не меняется (их XML не трогается).

## 6. Вне рамок (follow-up)

- **O1.** Серверный бэкфилл/генерация DI при сохранении-публикации (вариант B): требует
  bpmn-moddle на бэкенде (сейчас чистые строковые трансформы) + одноразовый бэкфилл уже
  сохранённых определений без DI. Клиентский фикс T-0615 покрывает открытие всех определений
  без миграции — B нужен только для консистентности хранимого XML.
- **O2.** bpmn-auto-layout не раскладывает под-процессы (рисует свёрнутыми), группы, аннотации,
  message flow и второго+ участника коллаборации — это ограничение движка bpmn-io; при таких
  определениях раскладка получится частичной, но канвас нарисуется (не пустой). Отдельная задача,
  если встретятся такие определения на стенде.
