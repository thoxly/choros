# Спека: фундамент форм и данных (D7) — каталог контрактов привязки + посредник данных

> Под тонкий D3 (формы из UI — T-0376/0377/0396, на `dev`) надо подвести прочный фундамент:
> один каталог типизированных контрактов привязки, единый рендерер, посредник доступа к данным
> с правами и лимитами, явная граница «оперативная аналитика, не BI». Виджеты-представления
> (Гант / канбан / календарь) кодит агент — ПОВЕРХ этих контрактов, не мимо них.
>
> Решения: [../product-decisions.md](../product-decisions.md) PD-18 / PD-19 / PD-20; уточняет PD-9.
> Наследует ADR [../design/extensibility-and-authoring.md](../design/extensibility-and-authoring.md)
> (named-binding §4, ACL-на-каждом-hop §6, граница Floor §9.2).
> Статус: спека · 2026-06-22.

## 1. Зачем
D3 дал кликабельные формы, но на тонком фундаменте. Если расти на нём — получим: (а) утечки
между тенантами в агентских виджетах, (б) тяжёлые страницы, тянущие сырьё в браузер, (в)
расхождение формы со схемой данных, (г) размножение рендереров. Цель: один КОНЕЧНЫЙ набор
контрактов привязки + посредник, который всегда сужает данные по «кто спрашивает + чья фирма»
и по размеру. Тогда «агент соберёт любой виджет» — фича, а не риск.

## 2. Что построил D3 (проверенные очаги)
- **4-й рендерер.** `web/src/screens/screen-inbox.jsx` (`InboxTaskForm` / `FormField`) — инлайн-
  маппинг тип→контрол, помимо `form-defs.js` (iframe), `records-form.js`, Floor-2. Каждый — свой
  словарь типов.
- **Снимок вместо вида.** `web/src/forms/FormBuilder.jsx` выводит поля из `registry_def.record_schema`
  (PD-9 ок), но кладёт СНИМОК в `form_binding.fields` (`{key,type,required,label,display_order}`).
  `options` НЕ переносятся → enum в инбоксе рисуется как text-input (тихий баг).
- **Запись без валидации.** `src/http/inbox.ts` (T-0396) пишет `formValues` в сущность через
  `applyStepResult` — в коде явно «no runtime re-validation against form_binding.fields»: лишние
  ключи молча попадают в JSONB. Provenance-поля защищены, proto-ключи вырезаны, НО инвариант PD-9
  «только существующие переменные» в рантайме НЕ форсится.
- **Без лимитов.** Списки инбокса/записей материализуются целиком (нет пагинации/курсора).
- **Tenant-изоляция держится** (`withTenantTx` + FORCE RLS, actor-resolve) — здесь дыры нет.

## 3. Дизайн

### 3.1 Каталог контрактов привязки (PD-18)
Система владеет КОНЕЧНЫМ набором типизированных контрактов привязки, а не каталогом визуалов:
`scalar` · `enum` · `relation` (cross_app_ref) · `collection`/one-to-many · `date-range` · `money` ·
`file` · `rollup`/aggregate · `matrix-lookup`. Каждый контракт декларирует, к какому слоту схемы
он биндится и какие режимы поддерживает. `form_binding.fields` (BindingField) расширяется
до этого контракта (presentation + options). Один рендерер потребляет каталог; сегодняшние 4 пути
сводятся к нему. Визуалы (Гант, канбан, календарь) — агентский код Floor-2 ПОВЕРХ контрактов.

### 3.2 Инвариант PD-9 форсится в рантайме
На сабмите значения формы валидируются против привязки И живой `record_schema`: неизвестные ключи
отклоняются (не пишутся в JSONB), enum проверяется по options, удалённые из схемы поля ловятся
(дрейф). Авторинг-контракт + рантайм-гейт = «форма ссылается только на существующее» по-настоящему.

### 3.3 Посредник данных: права + лимиты (PD-19)
Единый порт доступа: виджет (в т.ч. агентский Floor-2) НЕ ходит за данными сам — просит у платформы.
Платформа: (1) сужает по actor + tenant и применяет field-visibility (редакция); (2) ограничивает
размер — страница/курсор/limit, бюджет запроса (max-rows / timeout / payload), hop-cap на обход
связей (ADR §6 уже); (3) запись — через тот же порт с валидацией write-mask. Floor-2 получает
готовый отфильтрованный датасет и API «прошу изменить» — не сырьё, не БД. Это закрывает И
tenant-leak агентских виджетов, И тяжёлые страницы. Списки инбокса/записей — на пагинацию.

### 3.4 Оперативная аналитика, не BI (PD-20)
Живое = оперативное, в рамках команды/периода/процесса, ограниченное. Агрегаты (суммы, загрузка
по периодам) считает БД (GROUP BY по индексу), браузер получает маленький результат. Произвольная
аналитика по всем срезам → выгрузка `.xlsx` / внешний BI, не живой браузер. Продукт осознанно НЕ
склад данных и НЕ ad-hoc BI-движок. (ТЗ «Управление инженерными ресурсами» уже провёл эту границу:
этап-1 таблица → этап-2 график → этап-4 Гант; глубокий анализ — выгрузка.)

### 3.5 Граница Floor-1 ↔ Floor-2
Формальное машинно-проверяемое правило, какая правка тривиальна (Floor-1) vs структурна (Floor-2),
+ гейт. Требуется ADR §9.2 ДО первого релиза Floor-2-кода.

## 4. Инвентарь работ → задачи
- Каталог контрактов + единый рендерер (свести 4 пути) → **D7-K** (keystone).
- Рантайм-валидация сабмита (закрыть JSONB-дрейф T-0396 + перенос `options`) → **D7-2**.
- Посредник данных (права + лимиты) + пагинация списков → **D7-3**.
- Оперативные агрегаты в БД + `.xlsx`, не BI → **D7-4**.
- Граница Floor-1 ↔ Floor-2 (ADR §9.2) → **D7-5**.
- Типы каталога: relation / date-range / file / currency / multi-select / person → **D7-6**.
- `collection` / line-items (one-to-many) → **D7-7**.
- `rollup`/lookup + `matrix-lookup` (суммарные показатели; правило норматива) → **D7-8**.
- Режим поля от шага процесса (read / required-to-advance / hidden) → **D7-9**.

## 5. Последовательность
1. **D7-K** (каталог + рендерер) — фундамент, всё остальное на нём.
2. Параллельно безопасность: **D7-2** (валидация сабмита) + **D7-3** (посредник + лимиты) —
   закрывают реальные дыры тонкого D3.
3. **D7-5** (граница Floor) до любого Floor-2-кода; **D7-6** (типы) расширяют каталог.
4. Структурное под кейсы вроде инж.ресурсов: **D7-7** (line-items) → **D7-8** (rollup) →
   **D7-9** (режимы полей).
