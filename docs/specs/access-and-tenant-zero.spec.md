# Спека: доступ и tenant-zero (D1)

> Реальный самозарегистрированный клиент = полноправный, без seed-привилегий. Закрыть
> auth-дыры, дать новому владельцу рабочий кабинет, ввести служебные учётки для
> агентов/воркеров.
>
> Решения: [../product-decisions.md](../product-decisions.md) PD-7, PD-8, PD-14 (F1–F3).
> Статус: спека · 2026-06-22.

## 1. Зачем
Сейчас фиксы делались под seeded-демо (DEV_TENANT_ID); реальный self-reg тенант пробивает
стены: 403 при заведении людей, «missing x-dev-user» при старте процесса, пустой тенант без
агента/грантов → конфигуратор недоступен. Цель: self-reg владелец может всё настроить.

## 2. Проверенное состояние кода
- `registerTenant` (`src/core/register.ts:178-301`) сидит ТОЛЬКО: tenant + роль tenant-owner
  (без грантов) + employee(slug==jwt.sub) + confirmed role_assignment. Ни агента, ни грантов.
- Genesis-owner гейт org-write (`src/http/seed-write.ts:360-365` → `isGenesisOwnerForTenant`
  `src/db/org.ts:451-516`) проверяет владение против **захардкоженного DEV_TENANT_ID** → у
  self-reg овнера роль в ЕГО тенанте → 0 строк → 403 (B6).
- `process-start.ts:56-63` (и invoke/binding/floor1-editor/…) `extractActor` = старая
  dev-only версия, не смотрит keycloak-токен → «missing x-dev-user» (B16). SPA-роуты уже
  чинены `resolveActorSlugFromAuth` (s39).
- `agent_card` (миграция 032): `llm_endpoint/llm_model/llm_secret_handle` есть. Миграция 088
  сидит assistant-agent + confirmed authoring_draft грант — но ТОЛЬКО в demo-тенант.
- Keycloak живой на dev.

## 3. Дизайн

### 3.1 Genesis-owner гейт против тенанта вызывающего (чинит B6)
Все org-write роуты (employees/departments/positions/roles/role-assignments) проверяют
владение против **тенанта вызывающего** (резолв из его identity), не DEV_TENANT_ID. После
фикса self-reg владелец заводит людей/оргструктуру в своём тенанте.

### 3.2 Служебные учётки для агентов/воркеров/сервисов (F1; чинит B16/T-0328)
Заменить x-dev-user заглушку на **worker-token модель** (отличную от человеческого SSO):
- у агента/воркера/сервиса — своя служебная учётка (агент = employee/agent_card; воркер/
  сервис = служебный принципал) с выдаваемым токеном;
- роут резолвит токен → принципал → его роль/гранты → least-privilege (как у человека);
- применить ко ВСЕМ bypass-поверхностям (process-start, invoke, binding, floor1-editor,
  email-channel-config, vendor-activation; secret-handle FROZEN — отдельная санкция).
Решение «какой именно токен/выдача» — на импле (архитектор), но модель = личность+токен.

### 3.3 tenant-zero: что сидится в новый тенант (F2; чинит B1)
`registerTenant` дополнительно сидит **в КАЖДЫЙ новый тенант**:
- assistant-agent employee + confirmed authoring_draft грант владельцу (класс миграции 088),
  чтобы конфигуратор/авторинг были доступны реальному овнеру;
- агент **«спит»**: без LLM (BYO не подключён) отвечает честным 503 «подключите LLM», не
  падает молча.
Оргструктура/роли — НЕ сидятся (PD-7, аддитивны). Кабинет пустой + лёгкие подсказки.

### 3.4 Приглашение по ссылке (F3)
Владелец генерит **одноразовый invite-токен** → ссылка; приглашённый открывает, заводит
пароль (KC-юзер), входит в тенант с назначенной ролью. Без email. Токен одноразовый, с TTL.
Email-инвайты + сброс пароля — позже (PD-8, нужен mail-сервер → founder_request).

## 4. Инвентарь работ → задачи
- **B6 genesis-гейт** (org-write владение по тенанту вызывающего) → НОВАЯ задача (Тир-0).
- **F1 worker-token** (закрыть bypass) → T-0328.
- **F2 tenant-zero seeding** → T-0373.
- **F3 invite-link** → часть онбординга (T-0299/T-0306) или отдельная подзадача.
- Empty-state + подсказки → T-0306.

## 5. Открытое к уточнению на импле
- Формат/выдача/хранение worker-token; маппинг принципал→гранты для не-человека.
- Какие поверхности «агент» vs «воркер» vs «человек».
- TTL и отзыв invite-токена.

## 6. Последовательность
1) B6 genesis-гейт + tenant-zero seeding (self-reg владелец сразу полноценен) →
2) worker-token (агенты/воркеры реально входят, предпосылка D4) →
3) invite-link (приглашение людей).
