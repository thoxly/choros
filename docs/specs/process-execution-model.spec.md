# Спека: исполнительная модель процесса

> Keystone тезиса «ИИ = участник процесса» (PD-2). Недостающий **слой исполнения**,
> который собирает уже построенные подсистемы в живой цикл: резолв исполнителя →
> исполнение (человек/агент) → запись результата как сущности → закрытие шага.
>
> Решения: [../product-decisions.md](../product-decisions.md) PD-2, PD-10, PD-13 (F1–F7).
> Видение: [../../CONCEPT.md](../../CONCEPT.md) §3, §7, §8.
> Статус: спека · 2026-06-22 · собрана штурманом из проверенного состояния кода.

---

## 1. Зачем

Сегодня **человеческие** шаги исполняются e2e (задача → инбокс → действие → процесс
идёт). **Агентские** шаги — нет: external-task мост приносит шаг в очередь, но
**диспетчера, который запускает агента, нет** → шаг висит, процесс стопорится. Эта
спека закрывает разрыв и заодно унифицирует резолв исполнителя (пул → замещение →
fallback-овнер).

## 3. Слой исполнения (целевой цикл)

Для **любого** шага:

```
шаг готов
  → РЕЗОЛВ ИСПОЛНИТЕЛЯ (§4)
      ├─ человек → ИНБОКС (§5)
      └─ агент   → ДИСПЕТЧЕР (§6)
  → результат как СУЩНОСТЬ + АУДИТ (§8)
  → закрыть шаг в движке (мост, существует)
```

## 4. Резолв исполнителя (единый, для всех шагов)

Один резолвер, порядок:

1. **Прямой назначенец** (если шаг называет человека) — редко.
2. **Пул роли** — подтверждённые держатели в окне (`getRoleSlugsForActor`).
3. **Замещение** — отсутствует держатель → заместитель (`resolveSubstitution`, завайрить).
4. **Fallback → овнер** — роль пуста. Исполнитель **настраиваемый на тенант/процесс,
   дефолт = овнер** (F6). Задача **помечается** «роль не заполнена, поэтому вам» (F7).
5. **SLA-эскалация** — не взяли в срок → руководитель/овнер (фаза 3).

**Авторинг:** публикация процесса с незаполненной ролью → **предупреждение, не блок**
(fallback покрывает) (F7).

## 6. Диспетчер агента

**Триггер:** мост кладёт job для шага `choros:executorType="agent"` в JobStore.

**Диспетчер (новый цикл) читает job → собирает `AgentStepContext`:**
- **objective** шага — структурно (поля) + опц. NL, скомпилированный конфигуратором (F1);
- **record ref** — сущность(и), над которой шаг (процесс ссылается, не таскает данные);
- **tools** = гранты роли агента → разрешённые MCP-инструменты (least privilege);
- **llm** = `agent_card.llm_*` (BYO, PD-5);
- **budget** = лимиты токенов/денег/действий на инстанс;
- **autonomy** = порог уверенности (тенант-дефолт + override агента, F4) + потолок
  критичности (агент не делает критичное сам, F3).

**Запуск обобщённого мотора → исход (контракт уже есть):**

**Двое ворот автономии (переиспользуют готовые движки):**
- **A — уверенность:** `confidence ≥ autonomy_threshold`.
- **B — полномочие/критичность:** операция в пределах потолка агента. По F3 любая
  «критичная» операция (approve/transition, внешний invoke, чтение чувствительного,
  классификация из `role-criticality.ts`) → **всегда к человеку**, агент сам — никогда.
- **C — бюджет** не исчерпан.

**Разложение исхода:**
- **`proceed`** (A∧B∧C) → записать **результат-сущность** (F2) + аудит каждого
  tool-call → закрыть шаг в движке.
- **`defer-to-human` / провал ворот** → создать человеческую задачу, **предзаполненную
  черновиком агента + обоснованием**, маршрут через §4, человек «принять/поправить/
  отклонить» (F5). При принятии → шаг закрывается. _(мотор уже создаёт ссылку на
  инбокс-задачу в исходе `defer-to-human` — переиспользуем.)_
- **`fail-closed`** → инцидент + аудит deny + fail шага (retry-политика моста).

**Идемпотентность:** истёк лок job → повторный fetch → повторный прогон; мотор
идемпотентен / побочные эффекты защищены (outbox + идемпотентность JobStore).

## 7. Модель автономии (сводно)

- `autonomy_threshold`: **дефолт на тенант + override на агента**, одно число (F4).
- **Потолок критичности:** агент **никогда** не выполняет сам критичные операции (F3)
  — переиспользует классификацию `role-criticality.ts`.
- **Связь с dual-control:** критичное grant-изменение по-прежнему требует двух людей
  (существующий двухфазный flow); агент **не может** быть одним из этих апруверов.

## 8. Результат и аудит

- Результат шага = **сущность** (F2): стандартная запись «исход агента»
  (решение, уверенность, краткое обоснование, ссылка на trail инструментов).
- **Каждый** вызов инструмента + финальное решение → единый аудит-лог (CONCEPT §3).

## 9. Инвентарь работ

**Новое (небольшое, склейка):**
1. Диспетчер-цикл (читает JobStore → мотор → разложение исхода).
2. Обобщение мотора с legal-precheck до доменно-нейтрального шага агента.
3. Ветка **fallback → овнер** в резолвере (§4.4) + настраиваемый исполнитель.
4. **Активация** порогов автономии (тенант-дефолт + override).
5. **Вайринг замещений** в роутинг задач.
6. UI эскалации = **предзаполненная форма** черновиком агента (F5).
7. Бюджет-энфорсмент на инстанс.

**Переиспользуем:** мост, логика мотора, гранты→инструменты, критичность/dual-control,
резолвер замещений, инбокс, step-applier.

## 11. Предлагаемая последовательность

- **Фаза 1 — человеческие шаги «железно».** Резолвер исполнителя + fallback-овнер +
  вайринг замещений + пометка fallback + авторинг-предупреждение. Без агентов.
- **Фаза 2 — диспетчер агента (рутина).** `proceed`/`fail-closed`, потолок критичности
  = «критичное всегда к человеку» → все критичные шаги эскалируют, агент делает рутину.
- **Фаза 3 — автономия + эскалация + бюджет.** Активные пороги, предзаполненная
  форма эскалации, бюджет-энфорсмент, SLA-эскалация.

Так сначала человеческий путь становится надёжным, затем агент берёт рутину и
предлагает на критичном — ровно паттерн PD-2/CONCEPT §8.
