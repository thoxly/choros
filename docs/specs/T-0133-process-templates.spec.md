## 0. Природа задачи (DESIGN-only, не build)

T-0133 — задача **типа design**. Её выход — **спецификация требований к будущему
ADR** «каталог шаблонных процессов», который проектирует архитектор (фаза DESIGN).
Спек НЕ проектирует механизм (таблицы, формат файла шаблона, MCP-tool строки,
миграции — зона `architect`) и НЕ пишет код. Он фиксирует, **какими проверяемыми
свойствами обязан обладать ADR** и продукт, чтобы реализовать §5 п.5 рамки без её
искажения и без переизобретения уже принятых основ (bundle T-0082, тиры
extensibility §8, seed-pack-механизм T-0140, петля T-0129).

Поскольку артефакт фазы — ADR (документ), большинство критериев приёмки
проверяются как **manual** (ревью ADR против пунктов рамки/основ) или **fitness**
(где структура ADR машинно-проверяема: наличие именованных секций, поимённые
ссылки на существующие основы, отсутствие запрещённых конструкций).

## 1. Summary

Спецификация требований к ADR «каталог шаблонных процессов»: продукт поставляет
**стартовые шаблоны процессов** (договоры / заявки в IT / командировки) как
**поставляемые когерентные бандлы** (процесс BPMN + формы + статусы + роли +
гранты — пятичленная связка T-0082) в формате **пакета-как-данные, применяемого
через публичные API** (механизм seed-pack T-0140, не SQL, не новая сущность-хранилище).
Инстанцирование шаблона = создание **draft-бандла** в тире клиента (extensibility
§8), который дальше адаптируется интервью внедренца (T-0129 FR-4) через явные
**точки параметризации** (роли→узлы оргструктуры клиента, пороги сумм, сроки) и
проверяется симуляцией (T-0130) до promote. Каталог **версионируется** как
вендорский артефакт; обновление вендорского шаблона vs локальные адаптации клиента
разрешается по модели managed-solution (extensibility §11 vendor-documented cliff),
**не стирая правки клиента молча**. ADR обязан опираться на T-0082 (bundle),
extensibility §8 (тиры), T-0140 (формат пакета), T-0129 (вход петли), T-0130
(симуляция), а не переизобретать их.

## 2. Функциональные требования (что ADR обязан специфицировать)

### FR-1 — Шаблон = поставляемый когерентный бандл (форма T-0082)

ADR определяет шаблон процесса как **bundle той же пятичленной формы, что
T-0082**: процесс (BPMN) + формы (form-код + form-JSON-Schema) + статусы +
роли + гранты, согласованные по версиям как **одна когерентная единица**. Шаблон
из каталога обязан проходить **bundle-coherence CI-гард** (T-0082) так же, как
бандл, рождённый интервью. ADR **не вводит** второй модели «что есть процесс» рядом
с бандлом: каталожный шаблон и draft-бандл интервью — один тип артефакта, отличаются
только происхождением (поставлен вендором vs сгенерирован внедренцем).

### FR-2 — Формат хранения каталога = пакет-как-данные через публичные API (T-0140)

ADR специфицирует формат хранения каталога как **версионируемый пакет-как-данные**
(декларативное описание бандла), применяемый к тенанту **через публичные API
продукта, НЕ прямым SQL и НЕ новой privileged-сущностью-хранилищем** — дословно
механизм seed-pack T-0140 (`apply`/`reset`, идемпотентность). ADR обязан явно
определить отношение к T-0140: каталог процессов и seed-pack `showcase`/`blank` —
**один механизм шаблонов тенанта** (стык E11/E12, прецедент зафиксирован), где
`showcase` = демо-наполнение, а каталог = поставляемые стартовые **процессы**.
ADR обязан утверждать, что инстанцирование идёт теми же публичными authoring-API,
которыми пользуется внедренец (T-0129/T-0077), а не привилегированным обходным путём.

### FR-3 — Состав day-1 каталога: договоры / заявки в IT / командировки

ADR фиксирует **минимальный состав каталога day-1** из рамки §5 п.5: три стартовых
шаблона — **«Согласование договоров», «Заявки в IT (ITSM)», «Командировки»**. Для
шаблона «договоры» ADR обязан опираться на **референс ТЭЛ**
(`choros-reference-process-tel.md`) как источник состава (роли, маршрут по
тип/сумма/направление, порог ≥5 млн ₽ → юротдел, циклы доработки, статусы/отказ).
ADR классифицирует, какие из трёх шаблонов входят в **MVP-каталог**, а какие —
**Stage-2 наполнение** (рамка §2.243 / T-0129 out-of-scope: «наполнение шаблонами =
контент, Stage-2»): механизм каталога — day-1, исчерпывающее наполнение — Stage-2.

### FR-4 — Точки параметризации шаблона — явные и машинно-описанные

ADR специфицирует, что каждый шаблон несёт **явный, машинно-читаемый перечень точек
параметризации** (а не свободный текст «настройте под себя»), минимум трёх классов:
- **роли → узлы оргструктуры клиента**: каждая абстрактная роль шаблона (напр.
  «юротдел», «Главбух») — параметр, который интервью внедренца (T-0129 FR-4)
  привязывает к **реальному узлу живой оргструктуры тенанта**; несоответствие
  «роль шаблона не имеет узла в оргдереве клиента» обязано подниматься как явный
  вопрос (T-0129 FR-4), а не молча подставляться;
- **пороги/суммы**: числовые параметры маршрутизации (напр. порог ≥5 млн ₽ →
  юротдел) — настраиваемые значения, не зашитые константы шаблона;
- **сроки/SLA**: временны́е параметры (где есть) — параметры, не константы.
Перечень точек параметризации — часть контракта шаблона, проверяемый при загрузке
каталога.

### FR-5 — Адаптация шаблона = вход интервью внедренца (граница с T-0129)

ADR специфицирует, что **адаптация** шаблона под оргструктуру клиента выполняется
**интервью внедренца (T-0129), а не отдельным механизмом каталога**: каталог
поставляет шаблон + перечень его точек параметризации; внедренец (T-0129 FR-4)
ведёт интервью, заполняет параметры против живой оргструктуры и порождает
адаптированный draft-бандл. ADR обязан явно провести границу: **T-0133 = каталог
и контракт шаблона (что параметризуемо); T-0129 = процесс заполнения параметров
(как)**. ADR не дублирует механику интервью.

### FR-6 — Инстанцирование шаблона = создание draft-бандла в тире клиента

ADR специфицирует, что **инстанцирование** шаблона (выбор шаблона из каталога →
старт внедрения) создаёт **draft-бандл в draft-тире клиента** (extensibility §8,
логические тиры), а НЕ сразу published-процесс. Инстанцированный draft дальше
проходит петлю T-0129 (адаптация → прогон T-0130 → human-gated promote). ADR обязан
сослаться на тиры extensibility §8 и на симуляцию T-0130 как обязательный шлюз до
promote; **не вводит новую модель сред** и не позволяет шаблону миновать прогон.

### FR-7 — Версионирование каталога: вендорский артефакт с версией

ADR специфицирует, что **каталог и каждый шаблон версионируются как вендорский
артефакт** (версия шаблона зафиксирована в пакете). Инстанцированный у клиента
draft-бандл **запоминает, из какой версии какого шаблона он порождён** (происхождение
/ provenance), чтобы будущее обновление каталога было адресуемым. Версионирование
шаблона когерентно версионированию бандла (extensibility §7: связка коммитится
атомарно) — рассинхрон версий внутри шаблона ловит тот же bundle-coherence гард
(T-0082).

### FR-8 — Обновление вендорского каталога vs локальные адаптации (managed-solution)

ADR специфицирует поведение при **обновлении вендорского шаблона**, когда клиент уже
адаптировал его инстанс: вендорское обновление **НЕ затирает локальные адаптации
клиента молча**. ADR разрешает это по модели **managed-solution** (extensibility §11
vendor-documented cliff / Power-Platform managed-solution): локальные правки клиента —
отдельный слой поверх вендорской базы; обновление базы предъявляется клиенту как
**предложение к промоушну под human-gate** (T-0129 FR-11: человек подтверждает
проверенные сценарии), а конфликт «вендор изменил то же, что клиент» — явный, не
тихий. ADR обязан явно сослаться на §11 как на уже зафиксированный durable-риск, а
не открывать его заново; полная git-под-капотом семантика three-way-merge может быть
**Stage-2** при условии явного deferral-контракта (паттерн T-0082).

### FR-9 — Загрузка/обновление каталога — governed-операция, fail-closed

ADR специфицирует, что **поставка/обновление каталога** (вендор кладёт новый
шаблон) — операция под governance (CONCEPT §3 / extensibility §8: «агент предлагает —
человек подтверждает»), а не молчаливая мутация: новый/обновлённый шаблон, прежде чем
стать доступным для инстанцирования, проходит **bundle-coherence гард (T-0082)** и
валидацию точек параметризации (FR-4); невалидный шаблон каталога **fail-closed**
(не попадает в каталог), как невалидный реестр-член у T-0082. Каждая поставка/
инстанцирование пишется в **единый аудит-лог** (T-0031 `appendAuditEvent`).

### FR-10 — Каталог не обязывает клиента смотреть на BPMN (two-floor)

ADR удерживает планку квалификации клиента (рамка §1, T-0129 NF-2): клиент выбирает
шаблон **по человеко-понятному описанию** («Согласование договоров») и отвечает на
вопросы интервью о параметрах — он **не обязан читать BPMN/DMN/form-JSON-Schema/
гранты** шаблона. Бандл (включая каталожный) остаётся машинным слоем под карточкой
внедрения (T-0129 FR-14). ADR явно утверждает этот инвариант для каталога.

## 3. Нефункциональные требования (свойства ADR)

### NF-1 — Опора на принятые основы, ноль переизобретения

ADR ссылается на и переиспользует: T-0082 (bundle как когерентная единица +
coherence-гард), extensibility §8 (логические тиры draft→published, config-only
promote), §7 (когерентная связка, drain), §11 (managed-solution / vendor cliff),
T-0140 (формат пакета-как-данные через публичные API, `apply`/`reset`,
идемпотентность), T-0129 (вход петли, интервью-адаптация, human-gate), T-0130
(симуляция как обязательный шлюз до promote), T-0031 (единый аудит). ADR **не
вводит**: новой сущности-хранилища шаблонов вместо seed-pack-механизма, второй
модели «что есть процесс» рядом с бандлом, новой модели сред, второго аудит-лога,
прямого SQL-пути инстанцирования.

### NF-2 — Каталог встроен в петлю, не параллелен ей

ADR удерживает, что каталог — **вход петли T-0129** (FR-4 петли: «старт из каталога
предпочтительнее, чем с нуля»), а не самостоятельный канал создания процессов в
обход интервью/прогона/гейта. Инстанс шаблона обязан пройти ту же петлю
(адаптация → симуляция T-0130 → human-gated promote), что бандл «с нуля».

### NF-3 — Происхождение (provenance) шаблона трассируемо

ADR обеспечивает, что любой инстанцированный у клиента процесс трассируется к
**версии шаблона и версии каталога**, из которых он порождён (FR-7), либо явно
помечен как «с нуля». Это предусловие адресного обновления (FR-8) и аудита.

### NF-4 — Каждый примитив трассируется к рамке/основам

Каждое требование ADR трассируется к конкретному пункту playbook (§5 п.5 / §1) или
к поимённой основе (T-0082 / T-0140 / T-0129 / T-0130 / extensibility §7/§8/§11).
Требований «из ниоткуда» нет; раздел трассировки присутствует.

## 5. Acceptance Criteria (проверяемые свойства будущего ADR)

> Артефакт фазы — ADR. Критерии — свойства, которые ревьюер/гейт проверяет против
> playbook и основ. `manual` = ревью текста ADR против пункта; `fitness` = машинно-
> проверяемая структура (наличие секции, поимённые ссылки, отсутствие запрещённой
> конструкции).

**AC-1** — ADR определяет шаблон каталога как **bundle той же пятичленной формы,
что T-0082** (BPMN + формы + статусы + роли + гранты, когерентная единица), и явно
утверждает, что каталожный шаблон обязан проходить bundle-coherence гард T-0082;
не вводит второй модели «что есть процесс» рядом с бандлом.
*verifiable_as: manual*

**AC-2** — ADR специфицирует формат хранения каталога как **пакет-как-данные,
применяемый через публичные API (не SQL, не новая privileged-сущность-хранилище)**,
поимённо ссылается на механизм seed-pack T-0140 и явно определяет каталог процессов
и `showcase`/`blank` как **один механизм шаблонов тенанта**.
*verifiable_as: fitness*

**AC-3** — ADR фиксирует состав day-1 каталога (договоры / заявки в IT /
командировки) из рамки §5 п.5; для шаблона «договоры» опирается на референс ТЭЛ
поимённо; разделяет «механизм каталога = day-1» vs «исчерпывающее наполнение
шаблонами = Stage-2».
*verifiable_as: manual*

**AC-4** — ADR специфицирует, что каждый шаблон несёт **явный машинно-читаемый
перечень точек параметризации** минимум трёх классов: роли→узлы оргструктуры,
пороги/суммы, сроки/SLA; перечень — часть контракта шаблона, проверяемый при

*verifiable_as: manual*

**AC-5** — ADR явно проводит границу T-0133 ↔ T-0129: каталог даёт шаблон +
контракт точек параметризации (что параметризуемо), интервью внедренца (T-0129 FR-4)
заполняет параметры против живой оргструктуры (как); ADR не дублирует механику
интервью и ссылается на T-0129 поимённо.
*verifiable_as: fitness*

**AC-6** — ADR специфицирует инстанцирование шаблона как **создание draft-бандла в
draft-тире клиента** (extensibility §8), обязанного пройти петлю (адаптация →
симуляция T-0130 → human-gated promote); ADR ссылается на тиры §8 и на T-0130
поимённо и НЕ позволяет шаблону миновать прогон/гейт.

**AC-7** — ADR специфицирует версионирование каталога и шаблона как вендорского

порождён draft-бандл); версионирование шаблона когерентно версии бандла (T-0082 /

*verifiable_as: manual*

**AC-8** — ADR специфицирует поведение **vendor-update vs local-edit** по модели

молча; обновление базы предъявляется как предложение под human-gate; ADR ссылается

*verifiable_as: manual*

**AC-9** — ADR специфицирует поставку/обновление каталога как **governed-операцию,

**AC-11** — ADR явно классифицирует границу MVP vs Stage-2: механизм каталога +

## 6. Blocking Questions

**Нет BLOCKING-вопросов к фаундеру.** Рамка `playbooks/choros-implementation-loop.md`
§5 п.5 подтверждена фаундером 2026-06-11; все несущие развилки уже разрешены принятыми
основами, не требующими нового решения фаундера:

- **Формат хранения** (in-repo seed-pack vs отдельная сущность) — **разрешён
  прецедентом T-0140** (решение фаундера 2026-06-11): «пакет-как-данные через
  публичные API, не SQL; `blank`/`showcase` = один механизм шаблонов тенанта». Каталог
  процессов — продуктовый сиблинг того же механизма; новой развилки нет.
- **Состав day-1** (договоры/заявки/командировки) — задан рамкой §5 п.5 буквально;
  состав шаблона «договоры» — референсом ТЭЛ (зафиксирован фаундером).
- **Адаптация = вход петли** — разрешено T-0129 FR-4 (done): старт из каталога =
  предпочтительный вход интервью; T-0133 лишь даёт контракт точек параметризации.
- **Версионирование vendor vs local** — разрешено по модели managed-solution,
  **уже зафиксированной** как vendor-documented cliff в extensibility §11 (принятый
  ADR); T-0133 применяет, а не открывает заново. Полный three-way-merge отложен в
  Stage-2 консервативно (паттерн deferral T-0082) — это design-owned секвенирование,
  не founder-решение.
- **Инстанцирование = draft-бандл** — следует из тиров extensibility §8 (принято) +
  обязательного шлюза симуляции T-0130 (в dev).

**Design-owned точки (архитектор разрешает в ADR автономно, не founder-input):**
точная схема пакета шаблона и поля контракта точек параметризации; глубина
managed-solution-слоя на MVP vs Stage-2; маппинг ролей шаблона на узлы при
неоднозначности (несколько кандидатов-узлов) — консервативный дефолт «поднять
вопрос человеку» (T-0129 FR-4) безопасен.

Если архитектор в ходе DESIGN обнаружит развилку, меняющую ОБЪЁМ продукта и не
покрытую рамкой/основами, он эскалирует её отдельным GT-1 — но на входе SPEC таких нет.
