# T-0087 · E12.6 — Среды клиента: 2 логических тира (draft→published)

**Title:** Два логических тира (draft→published) в одном silo — config-only promotion, prod managed/locked
**Status:** ready (нет blocking-вопросов)
**Authored:** 2026-06-11
**spec_ref:** `docs/design/extensibility-and-authoring.md` §8 (+§9.6)
**Parent:** T-0071 (E12 — extensibility/authoring foundation)
**task_type:** build

---

## 1. Summary

T-0087 вводит два логических тира конфигурации клиента — **draft** и **published** — внутри
одного silo-экземпляра Choros. Prod-тир управляем и заблокирован от прямых правок;
promotion переносит только конфигурацию (не данные), и всегда human-gated. Физические
контуры (отдельный экземпляр БД) — явная on-demand эскалация, не дефолт.

Область T-0087 — **модель данных тиров и контракт записи/чтения** (ЧТО и ОТКУДА
принадлежит какому тиру, как enforce-ится прямой доступ к prod, что несёт promote).
Полная версионность связки BPMN↔форма↔схема↔гранты — T-0082 (E12.1). Config-агент как
сотрудник (DRAFT-only авторинг) — T-0077 (E11.6). Simulate/прогон поверх draft-тира —
T-0130 (ссылается на T-0087 как на несущее).

## 3. Функциональные требования

### FR-1  Модель тиров: draft и published

Каждый конфигурационный артефакт (BPMN-процесс, форма, объектная схема, гранты, DMN-таблица,
nav-конфиг) — в контексте тенанта — имеет атрибут тира со значением `draft` или `published`.
Дополнительных тиров в рамках T-0087 нет. Физически оба тира живут в одной БД (одном silo).

### FR-2  Запись в draft-тир

Любой авторизованный субъект (человек или агент с соответствующим грантом) **может создавать
и изменять** артефакты в draft-тире. Прямая запись в published-тир **запрещена** — любая
операция записи, не проходящая через путь promote, должна быть отклонена с явной ошибкой.

### FR-3  Config-only promotion: draft → published

Операция `promote` переносит конфигурационный артефакт из draft в published в рамках одного
тенанта. Промоут всегда human-gated: он не может быть инициирован агентом самостоятельно.
Promote переносит только метаданные конфигурации. Пользовательские данные (записи реестров,
аудит-события, инстансы процессов) **не копируются** и не пересекают тир-границу.

### FR-4  Prod managed/locked

После promote артефакт переходит в published-тир. В published-тире допустимо только чтение
и promote следующей версии из draft. Прямое изменение published-артефактов — запрещено.
Это справедливо для обоих этажей (Floor-1 config и Floor-2 код).

### FR-5  Изоляция тестовых данных в draft

Экземпляры процессов и записи, созданные в draft-тире (прогон/симуляция по T-0130), физически
присутствуют в той же БД, но **помечены тиром `draft`** и исключены из prod-контекста:

- Запросы в prod-контексте не возвращают draft-строки.
- Promote тира не копирует draft-данные.

### FR-6  Ортогональность: среды клиента ≠ SDLC Choros

Тиры `draft`/`published` — атрибут конфигурации **клиента внутри продукта**. Они
не связаны и не смешиваются с dev/prod окружениями самого Choros (`docs/environments.md`,
`docs/branching.md`). Код продукта одинаково обслуживает оба тира клиента в любом
окружении Choros.

### FR-7  Физический контур — только on-demand

Предоставление отдельного физического экземпляра БД или отдельного silo для окружения
клиента (изоляция интеграционных кредов, нагрузочный контур и т.п.) — явная эскалация,
требующая human-gate. Продукт не инициирует её автоматически и не предлагает как дефолт.

## 4. Нефункциональные требования

### NF-1  Принудительный контроль тиров в БД

Невозможность прямой записи в published-тир должна обеспечиваться как минимум на уровне
приложения (явная проверка с понятной ошибкой). Тир-атрибут хранится рядом с артефактом,
доступен для запроса без дополнительных join-ов.

### NF-2  Promote — атомарная операция

Переход артефакта из draft в published выполняется транзакционно: нет промежуточного
состояния «частично published».

### NF-3  Аудит promote

Каждая операция promote фиксируется в едином аудит-логе (T-0016) с идентификатором
инициирующего субъекта, артефактом и временем. Операция не проходит без записи в аудит.

### NF-4  Нет отдельной БД по умолчанию

Добавление тиров не требует провижнинга нового Postgres-контейнера или новой сервисной
схемы. Всё работает в существующей БД тенанта (single-silo из tenancy ADR §5).

## 5. Out of Scope

1. **Bundle-coherence (BPMN↔форма↔схема↔гранты)** — T-0082 (E12.1). T-0087 описывает
   модель тиров; когерентный коммит связки — зона T-0082.
2. **Config-агент как первоклассный сотрудник** — T-0077 (E11.6). T-0087 описывает тир
   `draft` как разрешённую зону записи; governance-аппарат агента — T-0077.
3. **Симуляция (прогон в draft-тире)** — T-0130. T-0087 даёт draft-тир; режимы прогона —
   T-0130.
4. **Camunda-grade маппинг live-инстансов** — on-demand эскалация по T-0082/T-0071 scope.
5. **Физический контур (отдельная БД)** — on-demand, вне дельты T-0087.
6. **UI promote-экрана** — дизайн-задача, не build; T-0087 задаёт API/контракт.
7. **Миграция данных между тирами** — data не копируются; T-0087 лишь это фиксирует;
   expand/contract schema — T-0082.
8. **Changelog и diff-поверхность для promote** — T-0084 (валидатор changelog↔diff).

## 6. Критерии приёмки

### AC-1  Тир-атрибут у конфигурационных артефактов

```
Fitness (schema):
  В схеме БД у таблиц конфигурационных артефактов
  (process_definition, form_definition, object_schema, grant, dmn_table, nav_config)
  существует колонка tier с check-constraint (tier IN ('draft', 'published')).
  NOT NULL с DEFAULT 'draft'.
  Верификация: migration-тест проверяет наличие constraint на каждой таблице.
```
`verifiable_as: fitness`

### AC-2  Прямая запись в published-тир отклоняется

```
Test (integration):
  POST /api/artifacts/<id>/edit с телом правки для артефакта с tier='published'
  → HTTP 409 (или 403) с кодом ошибки PUBLISHED_LOCKED.
  Артефакт в БД не изменяется (сравнить до/после).
  Проверить для минимум двух типов артефактов: process_definition и form_definition.
```
`verifiable_as: test`

### AC-3  Promote переносит только конфиг, не данные

```
Test (integration):
  1. В draft-тире создать конфигурационный артефакт A и N≥1 записей данных D
     (например, записи реестра, помеченные tier='draft').
  2. Выполнить promote A → published.
  3. Проверить: A.tier = 'published', count артефакта в published = 1.
  4. Проверить: записи данных D НЕ появились в published-контексте
     (count D WHERE tier='published' = 0).
```
`verifiable_as: test`

### AC-4  Promote — атомарная транзакция

```
Test (integration):
  Смоделировать сбой в середине promote (например, исключение после обновления
  tier у артефакта, до записи аудита).
  → Артефакт остаётся в draft-тире (tier не изменился).
  → Аудит-событие promote не записано.
  → Нет артефактов в промежуточном состоянии (tier не равен ни 'draft', ни 'published').
```
`verifiable_as: test`

### AC-5  Promote фиксируется в аудит-логе

```
Test (integration):
  Выполнить promote артефакта A пользователем U.
  Запросить аудит-лог после promote.
  → Присутствует запись с event_type = 'artifact.promoted',
    artifact_id = A.id, actor_id = U.id, tier_from = 'draft', tier_to = 'published'.
  → Запись создана атомарно с изменением tier (нет promote без аудита).
```
`verifiable_as: test`

### AC-6  Draft-данные не видны в published-контексте

```
Test (integration):
  Сидировать ≥1 запись данных (record, audit-event пометить tier='draft',
  либо process-instance с draft-тиром).
  Выполнить GET /api/records в published-контексте (без explicit draft-флага).
  → Ни одна draft-запись не появляется в ответе.
  → Аналогично для process instances: GET /api/instances → 0 draft-инстансов.
```
`verifiable_as: test`

### AC-7  Promote недоступен агенту без human-gate

```
Test (unit / integration):
  Попытка вызова promote через MCP-инструмент агента (или service-token агента)
  без сопутствующего human-confirmation токена
  → отклонена с 403 / FORBIDDEN_AGENT_SELF_PROMOTE.
  Promote с валидным human-confirmation токеном → 200 OK.
```
`verifiable_as: test`

### AC-8  Физический контур не провижнится автоматически

```
Fitness (code review / config):
  В стартовом пути провижнинга тенанта (genesis / tenant onboarding)
  отсутствует вызов provisioning нового Postgres-контейнера или новой БД
  на основании наличия двух тиров.
  Grep: нет вызова `createDatabase` / `provisionContour` / эквивалента
  в путях автоматического провижнинга.
```
`verifiable_as: fitness`

### AC-9  Тиры ортогональны SDLC-окружениям Choros

```
Fitness (config):
  В конфигурации приложения (docker-compose dev / prod, env vars)
  нет маппинга tier='draft' → dev-окружение Choros и tier='published' → prod.
  Приложение в dev-окружении Choros обслуживает оба тира клиента.
  Тест: можно создать published-артефакт в dev-экземпляре Choros без ошибки.
```
`verifiable_as: test`

### AC-10  Promote-путь: только через явный API, не через прямую запись в tier

```
Fitness (code / architectural):
  В кодовой базе нет путей, где tier='published' присваивается прямым UPDATE
  вне модуля promote (например, UPDATE artifact SET tier='published' без вызова
  promote-сервиса).
  Grep: все присвоения tier='published' — только через promoteTier() / аналог.
```
`verifiable_as: fitness`

## 8. Примечания для архитектора

- T-0082 (bundle-coherence) и T-0087 (тиры) — разные оси. T-0087 задаёт тир-атрибут
  и контракт promote; T-0082 задаёт когерентность связки внутри каждого тира.
  Architect должен проектировать их совместимо, но не сливать.
- Модель тиров должна учитывать tenant_id-скоупинг из T-0013/T-0115: tier — атрибут
  в контексте тенанта, не глобальный.
- Аудит promote должен использовать audit_event из T-0016 (append-only, hash-chain).
- Human-gate для promote — это место AC-7; конкретный UI/механизм human-confirmation
  выбирает архитектор, AC проверяет что агент без него получает 403.
