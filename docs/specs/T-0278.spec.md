# T-0278 — ТЭЛ deploy-acceptance click-through (acceptance criteria)

> Фаза SPEC. Аналитик. Хэндофф = `docs/specs/T-0278.spec.contract.json` (schema-валидирован)
> и JSON в финальном сообщении. Здесь — человекочитаемая полная спека.

## 1. Контекст и корень проблемы

Подтверждённая «дыра деплоя»: задеплоенный Choros — read-only витрина. Из 8 экранов
рабочих create-путей в UI ровно **два**:

- E9 — отправка формы: `POST /api/forms/:formId/submit` (src/http/forms.ts) → 200 + persist record.
- E7 — claim в инбоксе: `POST /api/inbox/:id/claim` (src/http/inbox.ts) → 200 + смена состояния.

Нет аффорданса **«запустить процесс»**: кнопка «Новая задача» на экране inbox
жёстко `disabled` (web/src/app-shell/shell.jsx:152-160, комментарий явно фиксирует
forward-obligation `POST /api/processes/start`); HTTP-роута start-instance не
существует (src/http/processes.ts экспонирует ТОЛЬКО `GET /api/processes` и
`GET /api/processes/:id` над seed/pack-данными). Экран processes
(web/src/screens/screen-processes.jsx) — read-only таблица; единственное действие
«Открыть» делает `navigate('/audit')`.

Корень дефекта: CI-гейт принимает «зелёное на ветке» (tsc + eslint + fitness +
vitest) БЕЗ доказательства «пользователь может кликнуть». Нет browser-E2E
(playwright/cypress в package.json ОТСУТСТВУЮТ) и нет deploy-acceptance-гейта.
`fitness:flowable` проверяет движок (deploy-bpmn + smoke), но не пользовательский
путь сквозь собранный web → HTTP → данные.

## 2. Ратифицированное направление (ВХОД, не вопрос)

**ТЭЛ-согласование = приёмочный эталон MVP**; демо = ЛИНЕЙНЫЙ ТЭЛ-путь
(choros-product-direction-tel). Эта спека превращает направление в
машинно-проверяемые критерии приёмки для deploy-acceptance гейта. Направление НЕ
переоткрывается.

## 3. Что строим (одно предложение)

Deploy-acceptance гейт, который против окружения, эквивалентного dev (реальный
стек + собранный web/dist), браузером проходит канонический **линейный ТЭЛ**
click-through от запуска процесса инициатором до завершённого согласования и
наблюдаемого результата, и проваливается, если хоть один шаг не кликабелен.

## 4. Канонический линейный ТЭЛ-путь (источник: seed/demo/tel-scenario.ts + docs/demo/T-0218-walkthrough.md)

Сценарий уже описан как 5-экранный straight-through ТЭЛ. Демо-сделка (фикстура,
не реальные данные): договор оказания услуг 5 500 000 ₽ (≥ порога ТЭЛ §1.4 = 5 млн ₽),
поэтому срабатывают оба агентских слота. Канонический путь как
последовательность пользовательских шагов в UI:

| Шаг | Экран | Персона | Действие пользователя | Наблюдаемый результат |
|---|---|---|---|---|
| **U1 · Запуск** | processes | `e-orlov` (инициатор) | Видит enabled-кнопку «Запустить процесс», кликает, выбирает канонический ТЭЛ-процесс | Создан process instance (виден в списке processes) + создана первая user-task инициатора |
| **U2 · Подача** | forms (FormViewer, E9) | `e-orlov` | Заполняет форму заявки (предмет, сумма 5,5 млн, обоснование), отправляет | Серверная валидация прошла; record persisted; задача S2 падает в инбокс |
| **U3 · Триаж** | inbox / карточка (E7) | `a-intake` (агент-слот S2, dormant→детерминированный) | (Агентский шаг) классификация/маршрут заполнены; путь продолжается к согласующему | Задача согласования адресована роли согласующего, видна как pool-задача |
| **U4 · Согласование** | inbox + карточка (E7) | `e-larina` (согласующий) | Берёт задачу из пула (claim), затем жмёт «Согласовать» (card action = transition + грант approve + audit) | Инстанс перешёл по transition; решение человека записано |
| **U5 · Завершение/результат** | processes / audit | `e-owner` (наблюдатель) | Открывает завершённый инстанс / аудит | Инстанс в статусе done; вся цепочка (intake + люди) видна tamper-evident |

Примечания к пути:
- Путь СТРОГО линейный (без циклов доработки и отказ-веток — это NF-границы T-0218).
- Шаг U3 (агентский) на day-1 проходит детерминированно (agent_card DORMANT,
  llm_* NULL → ZERO платных LLM; defer/детерминированный stub). Moat (агент не
  может self-approve) — структурный PDP-deny, проверяется как инвариант, но
  выходит за линейный happy-path click-through (см. out_of_scope §7).
- S3 legal-precheck (≥5 млн) уже имеет живой мотор T-0233 со stub-портом; для
  линейного click-through он либо проходит детерминированно, либо не блокирует
  переход к U4. Гейт проверяет КЛИКАБЕЛЬНОСТЬ пути, не повторяет юнит-логику мотора.

## 5. Функциональные требования

- F1. Канонический линейный ТЭЛ должен быть **физически запускаем** в задеплоенном
  стенде: существует deployable/seeded ТЭЛ process-definition (сейчас его НЕТ — см.
  §6 M1), который инициатор может стартовать через UI.
- F2. На экране processes (или inbox) есть **видимая, enabled** кнопка запуска
  канонического ТЭЛ; клик инициирует старт инстанса.
- F3. Существует HTTP-роут start-instance (форвард-обязательство shell.jsx:
  `POST /api/processes/start` или эквивалент), принимающий ключ процесса +
  начальные переменные, возвращающий идентификатор созданного инстанса; tenant-scoped.
- F4. Старт инстанса материализует первую user-task инициатора так, что U2 (форма)
  достижима из UI.
- F5. Отправка формы заявки (E9) на старте инстанса persist-ит record и продвигает
  процесс к шагу согласования (задача появляется в инбоксе адресата-роли).
- F6. Согласующий может взять задачу согласования из пула (E7 claim) и совершить
  card-action «Согласовать» (transition + грант approve + audit-событие).
- F7. После согласования инстанс достигает завершения; завершённый инстанс и его
  результат наблюдаемы через UI (processes/audit), цепочка видна в аудите.
- F8. Deploy-acceptance гейт автоматизирует U1–U5 как browser-E2E против собранного
  web/dist + живого HTTP + данных и падает, если любой шаг не кликабелен (нет
  enabled-кнопки, не-200 на write-роуте, инстанс не создан/не продвинулся/не
  завершён, результат не виден).

## 6. НЕДОСТАЮЩИЕ create-аффордансы (вход для декомпозиции архитектора — НЕ проектируем здесь)

- **M1. Канонический ТЭЛ process-definition отсутствует.** Поиск по
  *.bpmn/*.xml в seed/ config/ не находит ни одного ТЭЛ-процесса (есть только
  config/flowable/processes/choros-smoke.bpmn20.xml и
  seed/vendor-crm/processes/customer-onboarding.bpmn). ТЭЛ-сценарий существует как
  TS-seed (seed/demo/tel-scenario.ts) + offline-нарратив
  (scripts/demo-tel-walkthrough.ts), но НЕ как запускаемый процесс. Без
  deployable/seeded канонического ТЭЛ стартовать нечего. Требование: канонический
  линейный ТЭЛ должен быть представлен как deployable process-definition,
  детерминированно сидируемый в acceptance-стенд. (Это субстрат уже ратифицированного
  направления — не новое продуктовое поведение; см. §9.)
- **M2. start-instance HTTP-роут отсутствует** (нет POST в src/http/processes.ts).
  Форвард-обязательство уже зафиксировано в shell.jsx как `POST /api/processes/start`.
- **M3. start-instance UI-кнопка отсутствует** (кнопка «Новая задача» жёстко
  `disabled` в shell.jsx; экран processes без действия запуска).
- **M4. Связка старт → первая user-task → форма (E9).** Сейчас processes/inbox
  обслуживаются из seed/pack, не из движка; чтобы путь был кликабелен, старт должен
  порождать реальную задачу/форму, наблюдаемую теми же экранами.
- **M5. Browser-E2E инструментарий отсутствует** (нет playwright/cypress). Гейт
  деплой-приёмки требует браузерного драйвера, гоняемого в CI.

## 7. Out of scope (явно — НЕ тянем в этот гейт)

- O1. E8 — визуальный BPMN-авторинг save-to-server (канвас в локальный файл vs
  `POST /api/process-defs`): отдельный product-scope, не часть линейного ТЭЛ
  click-through MVP-приёмки.
- O2. E2 — UI создания оргструктуры (write-API есть, UI создания нет): отдельный
  product-scope, не в этот гейт.
- O3. Циклы доработки / отказ-ветки ТЭЛ (демо строго линейна, T-0218 NF).
- O4. Moat-сцена (агент пытается self-approve → PDP-deny) и degraded/defer-сцены
  как отдельные демо-доказательства — существующие инварианты, но не часть
  линейного happy-path click-through этого гейта.
- O5. Живой провод LLM для intake/legal-precheck (deploy-time, founder-gated);
  day-1 проход детерминирован (dormant→defer / stub).
- O6. Биллинг, мультивертикальность, внешний публичный API.

## 8. Non-functional требования

- NF1. **Интеграционная честность (D-056).** Гейт гонит против окружения,
  эквивалентного dev: реальный стек (postgres + flowable + choros + собранный
  web/dist через `vite build`), не моки и не in-memory-fallback. Аффордансы должны
  быть кликабельны в той же конфигурации, что увидит пользователь.
- NF2. **Test-discovery исключает worktree-каталоги.** Acceptance-прогон не
  подхватывает тесты из стейл git-worktree (уже зафиксировано в vitest.config.js:
  exclude `.claude/**`, `../choros-wt/**`, `web/**`); browser-E2E аналогично
  скоупится только на чекаут гейта (FE-2026-W24-0005).
- NF3. **Детерминированный seed.** Канонический ТЭЛ-стенд сидируется
  детерминированно и идемпотентно (повторный прогон — no-op), без платных LLM
  (agent_card DORMANT), без реальных клиентских данных (фикстура T-0218/T-0233).
- NF4. **Tenant-scoping start-instance.** Старт инстанса tenant-scoped: нельзя
  стартовать процесс в чужом тенанте (RLS / withTenantTx-паттерн, как в
  process-defs.ts); попытка кросс-тенант → отказ.
- NF5. **Фейл-чест.** Гейт обязан падать (а не зеленеть/пропускать), если стенд не
  поднят, аффорданс не кликабелен, или путь не доходит до завершения — отсутствие
  доказательства клика = красный гейт, не «зелёное на ветке».

## 9. BLOCKING-вопросы

Истинно блокирующая развилка («есть ли deployed ТЭЛ process-def, который можно
стартовать, или нужно его seed-ить») **разрешена по коду самим аналитиком**:
deployable ТЭЛ process-definition сейчас отсутствует (§6 M1), но это субстрат уже
ратифицированного направления (линейный ТЭЛ как приёмочный эталон), а не новое
продуктовое поведение — направление и канонический 5-шаговый путь уже зафиксированы
в seed/demo/tel-scenario.ts и подписанном T-0218. Поэтому требование «сделать
канонический ТЭЛ запускаемым» — вход для архитектора (M1), не вопрос фаундеру.

**BLOCKING-вопросов нет. Статус: ready.**
