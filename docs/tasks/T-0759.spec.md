## 1. Problem

`isInstanceParticipant` (`src/http/process-projection.ts`, T-0756) grants participant
status to an actor via three clauses:

1. the actor **appears as an actor** in the instance's append-only `audit_event` track
   (started / approved / claimed / next_task) — they **acted** on it;
2. the actor **holds the role** of a task ever addressed on the instance
   (`getRoleSlugsForActor`, ACTOR_ACTIVE-gated since T-0738); or
3. the actor is the tenant **owner** (`isGenesisOwnerForTenant`, deactivation-safe since
   T-0658).

Clause (1) read the audit track only — it never checked whether the matched identity is
**currently** active. T-0756's spec §1.2 argued this was harmless ("a deactivated
participant … is still denied the *live* record projection because canOpen = READ-PDP is
separately fail-closed and the skeleton carries no source-record field data"). The
review (`T-0756.review.json`, finding N1) found that reasoning understates the actual
exposure: the participant tier's `sourceRecord` projection is `{id, title, typeLabel,
canOpen, appId?}` — **`title` is populated regardless of `canOpen`**. A deactivated actor
who genuinely acted on an instance in the past therefore still received, during the
residual ~300s window their already-issued access-JWT stays valid after deactivation
(T-0702 / T-0726's window), **200 + the participant skeleton + the source record's human
title** — a title-only disclosure of a record they otherwise have no live authority over.

T-0723 introduced `isInstanceParticipantBatch` (the LIST-side sibling used by
`filterProjectionsByReadVisibility` for record-less rows) with the **identical** clause
(1) gap — it was flagged as N2 in that task's `pr-handoff.json` `nits` and deferred here.

## 2. Fix — reuse `ACTOR_ACTIVE_SQL`, not a bespoke predicate

Clause (1) in **both** `isInstanceParticipant` and `isInstanceParticipantBatch` now
requires the matched identity to be a **currently active** `choros.employee` row, using
the SAME named predicate constant clause (2) already carries via `getRoleSlugsForActor`
(T-0738): `ACTOR_ACTIVE_SQL` (`src/db/actor-authority-gate.ts`, `"deactivated_at IS
NULL"`). No second/bespoke deactivation literal is introduced.

### 2.1 `isInstanceParticipant` (single-instance, DETAIL)

After the audit-track query resolves the `actors`/`roles` sets, clause (1) first
determines **which** identity matched (`actorSlug`, or — failing that — the distinct
`fallbackSlug`, mirroring the T-0366 primary→fallback shape `getRoleSlugsForActor` already
uses), then issues **one** point lookup:

```sql
SELECT id FROM choros.employee
 WHERE tenant_id = $1 AND slug = $2 AND deactivated_at IS NULL LIMIT 1
```

A non-empty result grants clause (1); an empty result (no row, or a row with
`deactivated_at` set) falls through to clauses (2)/(3). A DB error in the check denies
(fail-closed), matching every other resolver in this module.

### 2.2 `isInstanceParticipantBatch` (batched, LIST record-less filter)

Kept a **separate function** from `isInstanceParticipant` (T-0723's own discipline — the
already-tested single-instance path is not touched for the sake of batching). The active
status of `actorSlug`/`fallbackSlug` is **actor-level**, not instance-level — exactly like
clauses (2)/(3) — so it is resolved **ONCE** for the whole page, not per instance:

- Skipped entirely when the batch's audit rows carry no actor data at all (`anyActors`,
  mirroring the existing `anyRoles` guard around clause (2)'s `getRoleSlugsForActor`
  call).
- Otherwise, up to two point lookups (`actorSlug`, and the distinct `fallbackSlug` if
  present) — the SAME query shape as §2.1, executed once for the batch, not once per
  instance (no N+1: `filterProjectionsByReadVisibility` calls
  `isInstanceParticipantBatch` a single time per LIST page, unchanged from T-0723).
- Per instance, clause (1) now requires **both** "this instance's audit track names
  `actorSlug`/`fallbackSlug`" **and** "that specific identity resolved active" in the
  batch-level lookup.

### 2.3 Equivalence between the two paths

Both functions apply the exact same authority: an audit-track match only counts when the
matched identity is currently active, using the byte-identical `ACTOR_ACTIVE_SQL`
predicate literal. They intentionally use different query SHAPES (`isInstanceParticipant`:
per-call point lookups; `isInstanceParticipantBatch`: the same point-lookup shape but
resolved once for the whole page) — the same asymmetry T-0723 already established for
clauses (2)/(3) (batched `getRoleSlugsForActor`/`isGenesisOwnerForTenant` calls vs.
per-call). Behavioral equivalence is pinned by a live-PG test pair that exercises the
SAME fixture (a deactivated former audit-actor on a record-less instance) through BOTH
DETAIL (`GET /api/processes/:id`) and LIST (`GET /api/processes`) — see §4.

## 3. Registration in the anti-recurrence gate

`isInstanceParticipant`/`isInstanceParticipantBatch` now perform a direct `slug = $N ...
deactivated_at IS NULL` employee lookup inside `src/http/process-projection.ts` — a NEW
authority actor-resolver shape in that file (previously zero; all its employee lookups
went through imported, already-registered resolvers). Both functions are added to
`ci/checks/actor-authority-deactivation-gate.sh`'s `AUTHORITY_RESOLVERS` registry (FF-0662-1/2
accounting scan), and to the mirrored doc registry in `src/db/actor-authority-gate.ts`
(entries H/I, kept in sync per that file's own header comment).

### RED→GREEN (anti-case)

Each of the three new anti-case tests (DETAIL live-PG, LIST live-PG, unit) follows the
SAME shape: seed a fresh employee, have them genuinely act on a record-less instance
(audit `actor` field), assert they ARE a participant (200 skeleton / present on LIST) —
the "before" sanity check — then set `deactivated_at`, re-request as the SAME actor, and
assert the door is now closed (404 on DETAIL; absent from LIST `instances[]`). Reverting
the clause-(1) active-check (`git stash` the `src/http/process-projection.ts` diff) flips
all three RED: the deactivated actor gets 200 + the source-record title back.

### Regressions guarded

- **Active participant still sees it** — SRP-1/SRP-3/SRP-4/SRP-7 (T-0756, unchanged
  actors, never deactivated) and the T-0723 "actor who STARTED the record-less instance"
  DETAIL/LIST tests all stay 200/present. Two of the latter needed a **fixture fix, not a
  behavior change**: their synthetic "starter" slugs were previously arbitrary unseeded
  strings (clause (1) never checked employee existence before this task) — now that
  clause (1) requires a REAL, currently-active `choros.employee` row, both tests seed the
  starter via `seedEmployee` before asserting participant status (realistic: a genuine
  participant IS a real employee).
- **Unit fake-pool routing** (`src/__tests__/processes-read-visibility.test.ts`):
  `getRoleSlugsForActor`'s own employeeId-resolve query and this task's new clause-(1)
  active-check share the exact same bare `FROM choros.employee ... slug = $2 ...`
  shape (by design — same predicate, same intent). The shared `makeFakePool` now answers
  that shape "active" for any slug the test names, unless listed in the new
  `opts.deactivatedSlugs` — every pre-existing test (none of whose actors were meant to be
  deactivated) is unaffected; two custom inline "tracking pool" tests got the same
  one-line addition.

## 5. What to attack (judge)

1. **Bypass via `fallbackSlug`.** Confirm a deactivated `actorSlug` cannot ride a
   still-active, DISTINCT `fallbackSlug` unless that fallback identity is ALSO the one
   that appears in the audit track for this specific instance (clause (1) requires the
   matched identity itself to be active, not "any identity of this caller").
2. **N+1 on the batch path.** `isInstanceParticipantBatch`'s new active-check queries
   (`actorSlugActive`/`fallbackSlugActive`) run at most twice **total per LIST page**, not
   per instance — verify via the existing "no record-bound projections… participant query
   still runs" instrumented-pool unit test (still asserts a single `confirmed_by` audit
   query) plus a read of the diff (`anyActors` gates the whole active-check block once).
3. **Clause (2)/(3) untouched.** `getRoleSlugsForActor`/`isGenesisOwnerForTenant` calls
   and their existing ACTOR_ACTIVE/deactivation-safe behavior are byte-unchanged — only
   clause (1)'s audit-actor branch was touched in both functions.
4. **Registry gaming.** `isInstanceParticipant`/`isInstanceParticipantBatch` are now
   registered `AUTHORITY_RESOLVERS` entries — confirm FF-0662-1's lookup-vs-predicate
   count still holds if a future edit adds a THIRD un-gated `slug = $` lookup to either
   function (the accounting scan is the anti-recurrence teeth, not just the registration).
5. **Title leak fully closed, not narrowed.** SRP-8/the LIST anti-case assert the raw HTTP
   body no longer contains the source record's title value at all (404 body), not merely
   `canOpen:false` — the whole skeleton is gone, matching the fail-closed posture of every
   other non-participant/non-reader path (SRP-2).
