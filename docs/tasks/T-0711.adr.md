# ADR T-0711 — пин application_id в резолве живой схемы + детерминированный фолбэк

Статус: accepted. Контекст: docs/tasks/T-0711.spec.md.

## 1. Решение

Опциональный параметр `applicationId?: string | null` добавлен (строго
аддитивно, без изменения существующих сигнатур по позиции) к:

- `resolveLiveRecordSchema` / `resolveLiveSchemaFieldKeys` /
  `resolveLiveCollectionSubKeys` (`src/db/live-form-schema.ts`);
- `classifyLayoutSave`, `deriveFieldsFromLayout` (`src/http/binding.ts`).

SQL шага 1 — ОДИН statement на обе ветки (pinned / unpinned):

```sql
SELECT application_id, target_registry_slug
  FROM choros.process_app_binding
 WHERE tenant_id = $1
   AND process_key = $2
   AND ($3::uuid IS NULL OR application_id = $3)
 ORDER BY created_at ASC, id ASC
 LIMIT 1
```

HTTP: `POST /api/forms/binding` и `POST /api/forms/document-ops` принимают
опциональный `application_id`/`applicationId` (dual-casing — та же конвенция,
что `process_key`/`processKey` в этих же роутах); непустое значение проходит
`assertUuidShape` (→ 400 при мусоре). UI: `persistLayout` шлёт
`application_id: selectedAppId` (только непустой).

## 2. Выбор порядка фолбэка: `ORDER BY created_at ASC, id ASC`

Когда `applicationId` не передан, а привязок 2+ — какую вернуть?

**Выбрано: старейшая привязка (created_at ASC), tie-break id ASC.**

Почему именно так:

1. **Совместимость с фактической историей.** До появления мульти-привязок у
   process_key была ровно одна строка — как правило, самая ранняя. Все
   legacy-вызовы (floor1-editor, агентские боты, старые формы) до сих пор
   живут в мире «процесс = одно приложение»; старейшая строка — это та самая
   привязка, против которой эти формы исторически создавались и валидировались.
   Новее-добавленная вторая привязка не должна МОЛЧА перехватывать резолюцию
   у существующих форм — это был бы behaviour-change для не-мигрированных
   вызовов ровно того сорта, который задача устраняет.
2. **Стабильность во времени.** `created_at` строки привязки неизменяем
   (обновления идут upsert'ом полей, не пересозданием), поэтому результат
   фолбэка не «плавает» при UPDATE привязки. Альтернатива `updated_at DESC`
   («самая свежая») меняла бы резолюцию при каждом ре-апсерте любой из
   привязок — недетерминизм по времени, хоть и детерминизм по запросу.
3. **Tie-break `id ASC`** — `created_at` (bigint millis) двух строк может
   совпасть (сиды/миграции пишут 0); `id` (uuid, часть PK) уникален всегда —
   полный порядок гарантирован при любых данных.

Отвергнутые альтернативы:

- **`updated_at DESC` («самая свежая»)** — см. п.2: ре-апсерты двигают выбор.
- **Ошибка/`null` при 2+ привязках без пина (fail-closed на неоднозначность)**
  — честнее концептуально, но это моментальный регресс для floor1-editor и
  всех legacy-каналов, где приложение физически неоткуда взять: их формы
  перестали бы сохраняться вовсе. Неоднозначность там РЕАЛЬНА, но правильное
  лечение — протягивать пин и в эти каналы (follow-up), а не ломать их.
- **Два отдельных SQL (pinned/unpinned)** — точка дрейфа: предикаты со
  временем расходятся. `$3::uuid IS NULL OR …` держит обе ветки в одном
  тексте; планировщик PG нормально сворачивает константный `IS NULL`.

## 3. Fail-closed семантика пина

- Малформенный `applicationId` (не UUID-shape) на уровне резолвера → `null`
  БЕЗ единого запроса (зеркало существующей проверки `tenantId`). Молчаливое
  игнорирование мусорного пина воскресило бы ровно ту неоднозначность,
  которую параметр закрывает. На HTTP-уровне до этого не доходит —
  `assertUuidShape` даёт честный 400.
- Валидный, но несуществующий/чужой `applicationId` → 0 строк → `null` →
  409 WRONG_FLOOR в гейте. НЕ фолбэк на другую привязку: подстановка чужой
  строки = та же дыра уровнем ниже. RLS+tenant-предикат уже отрезают чужой
  тенант.

## 4. Инварианты, которые сохранены

- `classifyLayoutSave` передаёт ОДИН и тот же `applicationId` в оба резолвера
  (field-keys и collection-subKeys) — расщепление на две разные привязки
  внутри одного save невозможно (юнит-тест AC-4).
- `deriveFieldsFromLayout` получает тот же пин, что и гейт этого же save —
  поля деривуются из ТОЙ ЖЕ схемы, что только что валидировала форму.
- Отсутствие `application_id` в теле запроса = прежний контракт (плюс
  детерминизм) — ни один существующий клиент не ломается.
- Анти-кейс: параметр — данные запроса; никаких слагов/uuid-литералов в src/.

## 5. Пересечение с T-0682 (для мержа)

`web/src/forms/FormDesigner.jsx` параллельно правит T-0682 (мержится первым).
Изменения T-0711 в этом файле минимальны и локальны:
- call-site кнопки «Сохранить раскладку»: +1 строка аргумента `selectedAppId,`
  в вызов `persistLayout(...)`;
- сигнатура `function persistLayout(...)`: +параметр `applicationId`;
- тело `persistLayout`: `...(applicationId ? { application_id: applicationId } : {})`
  в body + докблок T-0711.
При конфликте ребейза: сохранить обе правки; контракт — «selectedAppId идёт
шестым аргументом persistLayout и уходит на сервер как application_id».
