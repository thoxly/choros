# ADR T-0726 — actor-active-route-coverage: статический гейт универсальности ACTOR_ACTIVE

Статус: accepted. Контекст: R-3 из судейского вердикта T-0702
(`T-0702.review.md`), усиленный оценкой T-0714
(`docs/tasks/T-0714.assessment.md`). Родительские гейты: FF-0328
(`ci/checks/http-route-auth-coverage.sh`, T-0328) и FF-0662
(`ci/checks/actor-authority-deactivation-gate.sh`, T-0658/T-0662).

## 1. Проблема (R-3)

T-0702 (KC session-revocation при деактивации) подтвердил и честно
задокументировал: Choros валидирует access-JWT **чисто offline** (JWKS +
`exp`, `src/http/auth.ts`), без per-request round-trip к Keycloak за
состоянием сессии. `revokeUserSessions` (T-0702) гасит SSO-сессию и
refresh-токены, но **не может** инвалидировать уже выданный access-токен —
тот остаётся криптографически валиден до собственного `exp` (~300s, realm
TTL). В этом окне держатель токена проходит AUTHENTICATION (`withAuth`,
FF-0328 доказывает это универсально — 100% роутов).

Настоящая гарантия против деактивированного держателя — не аутентификация, а
**авторизация**: 7 authority-резолверов (T-0658/T-0662,
`ci/checks/actor-authority-deactivation-gate.sh` → `AUTHORITY_RESOLVERS`),
каждый несущий предикат `deactivated_at IS NULL` (маркер `ACTOR_ACTIVE_SQL`,
`src/db/actor-authority-gate.ts`). FF-0662 доказывает, что каждый
*зарегистрированный* резолвер несёт предикат, и что ни один *новый*
employee-slug-lookup не проскальзывает мимо инвентаря (accounting-скан).

Судья T-0702 (R-3) зафиксировал недоказанное звено: **ничто не проверяет,
что каждый отдающий данные роут вообще ДОХОДИТ до одного из этих 7
резолверов**. Роут может быть honest, withAuth-покрытым, tenant-scoped через
`resolveActorTenant` — и при этом НИКОГДА не вызывать ни один
authority-резолвер. `resolveActorTenant` сам НЕ проверяет `deactivated_at`
(он в ALLOWLIST FF-0662 именно как "не authority" — резолвит тенант, не
грант). T-0714 нашёл ровно такой роут живьём: `GET /api/processes[/:id]` —
withAuth-покрыт, tenant-scoped, но не вызывает ни один authority-резолвер;
деактивированный сотрудник с живым токеном получает ПОЛНЫЙ прежний доступ на
всё окно `exp`, а не только "residual PDP-deny" узость, которую предполагает
ADR-T0658 §9.

T-0726 строит статический fitness-гейт, доказывающий (или опровергающий)
универсальность этого звена по всему `src/http`.

## 2. Спроектированная аппроксимация

Полный call-graph-анализ ("роут → цепочка вызовов → один из 7 резолверов")
недостижим честной bash-эвристикой (см. red-lines практики T-0662:
"grep-ripple by one function name misses others" — тот же класс проблемы на
уровень выше). Выбрана следующая аппроксимация.

### 2.1 Гранулярность: ПО РОУТУ, не по файлу

`http-route-auth-coverage.sh` (FF-0328) работает на уровне ФАЙЛА: "файл
содержит `withAuth(` где-то" = покрыт. Это осознанно достаточно для
АУТЕНТИФИКАЦИИ (один `withAuth`-паттерн, применяемый единообразно). Для
АВТОРИЗАЦИИ файловая гранулярность даёт ложноотрицательный результат — живой
пример найден в этой самой задаче: `src/http/files.ts` регистрирует ОБА
`GET /api/records/:recordId/files` (LIST, НЕ авторизован — намеренно,
FF-NOACL, T-0521 п.1) и `GET /api/files/:fileVersionId/download` (АВТОРИЗОВАН
через `resolver.resolveRecordOp` → `getGrantsForSubject`) **в одном файле**.
Файловая гранулярность видит "файл содержит авторизацию где-то" и пропускает
LIST мимо гейта — ровно та дыра, которую гейт должен ловить.

**Решение:** блок роута = от его `.register(` до СЛЕДУЮЩЕГО `.register(` в
том же файле (или EOF). Не brace/paren-tracked (упрощение), но на всех ~80
живых роутах (self-test + живой прогон) ни одного случая неверной атрибуции
не замечено — паттерн "один хендлер на `.register(` вызов" держится
единообразно по всей `src/http`.

### 2.2 Маркеры: 7 зарегистрированных резолверов + верифицированные производные

`ACTIVE_MARKERS` = дословный список `AUTHORITY_RESOLVERS` из FF-0662 (7 имён)
+ производные примитивы, каждый **верифицирован вручную, один раз**, что он
компонует один из 7 (не второй authority-путь, NF-5-совместимо):

| маркер | верификация (file:line) |
|---|---|
| `isRecordReadable` | `core/read-visibility.ts` — чистый предикат, гранты приходят от `resolveReadVisibility` |
| `resolveReadVisibility` | `server.ts:882-892` → `getGrantsForSubject` |
| `resolveFieldVisibility` | `server.ts:865-868` → `getGrantsForSubject` |
| `reportAggReadVisibility` | `server.ts:989-995` → `getGrantsForSubject` |
| `checkReadGrant` | `report-page-render.ts` → цепочка `defaultCheckReadGrant` (ADR-T0658 §3.3) |
| `resolveActorPrivilege` | `src/db/sandbox-gate-dao.ts:54-71` → `loadAdminContext` + `getGrantsForSubject` напрямую |
| `resolveRecordOp` | `server.ts:1344-1354` (`fileReadResolver`) → `makeDbGrantSource(grantsPool)` → `getGrantsForSubject` (`grants-dao.ts:397-403`) |
| `getFileContentUrl` | `core/file-attachment.ts` → `resolver.resolveRecordOp` (см. выше) |
| `requirePrivilege` | конвенция имени file-local хелпера; конкретный проверенный экземпляр — `solution-publish.ts:485-496` → `resolveActorPrivilege` |

Регекс матчится ТОЛЬКО внутри блока роута, на non-comment строках (та же
lesson T-0143, что и в FF-0328/FF-0662).

### 2.3 Скоуп: только GET

Мотивация R-3 — READ-экспозиция живому-но-деактивированному JWT. POST/PUT/
PATCH/DELETE обычно эхо валидированного входа, а не широкое чтение;
расширение на все глаголы умножило бы площадь аудита без пропорционального
сигнала для ЭТОГО класса бага. Явно задокументированное сужение скоупа, а не
молчаливое (ADR §"что НЕ доказывает" п.3 в самом скрипте).

### 2.4 Честные пределы (что гейт НЕ доказывает)

1. **Не call-graph-доказательство.** Маркер, видимый ТОЛЬКО в module-scope
   хелпере, объявленном ДО первого `.register(` в файле (напр.
   `requirePrivilege()`/`checkAdminGrant()` — локальные обёртки), невидим
   скану даже когда роут реально его вызывает. Два живых случая найдены и
   закрыты ВРУЧНУЮ через `ROUTE_WHITELIST §D` (см. §4) вместо расширения
   механизма (preamble-инклюзия пробовалась и отвергнута — см. §3).
2. Блок = "до следующего `.register(`", не brace-tracked — см. §2.1.
3. Только GET — см. §2.3.
4. Не проверяет ПРАВИЛЬНОСТЬ вызова резолвера (правильный tenant/operation) —
   это зона FF-0662 (резолвер-предикат) и FF-0328 (аутентификация), не эта.
5. **Статус: informational**, не в `npm run fitness` — см. §5.

## 3. Отвергнутая альтернатива: preamble-инклюзия

Первая попытка закрыть предел #1 (§2.4): расширить блок роута, включив весь
"преамбул" файла (от начала файла/от начала `export function
register...Routes` до первого `.register(`) — это ловит module-scope хелперы
типа `requirePrivilege`/`defaultCheckAdminGrant`.

**Отвергнуто**: преамбул почти ВСЕГДА содержит IMPORT STATEMENTS, которые
текстово содержат имена маркеров ЛЮБОГО импортируемого резолвера/типа —
конкретно `files.ts:62` импортирует `getFileContentUrl` (маркер) в преамбуле,
что сделало бы `GET /api/records/:recordId/files` (LIST, реально НЕ
авторизован, FF-NOACL) ЛОЖНО зелёным просто потому что файл ГДЕ-ТО
импортирует авторизованную функцию для ДРУГОГО роута — ровно та дыра §2.1
снова, но через преамбул вместо файловой гранулярности. Попытка исключить
import-блок текстовым правилом ("последняя `from "...";` строка в первых N
строк") добавляла хрупкую эвристику ради закрытия ДВУХ конкретных случаев.

**Решение**: ДВА живых случая (`solution-publish.ts` publish-preview,
`notification-prefs.ts` GET `/api/notification-preferences`) закрыты ВРУЧНУЮ
через `ROUTE_WHITELIST §D` с цитатой (file:line + что резолвер компонует) —
тот же паттерн, что FF-0662 использует для R2-P3-1 (принятый предел вместо
хрупкой мех. дотяжки). Узкая-но-настоящая гарантия > широкая-но-дырявая
(явное указание задачи).

## 4. Whitelist — категории и обоснование

`ROUTE_WHITELIST` в скрипте — единоразовая (2026-07-10) инвентаризация живого
GET-поверхности `src/http`, сгруппированная по причине:

- **§A pre-login** (3 роута, `auth.ts`) — актора ещё нет; зеркалит прецедент
  T-0328 `register.ts` ("Anonymous BY DESIGN").
- **§B self-scoped** (9 роутов) — запрос/ответ скоупится СОБСТВЕННЫМ id
  актора (notifications recipient_id, user-prefs, assistant threads,
  list-views ownerVisibilityClause self∪common). Не authority-решение — нет
  чужих данных, которые деактивация должна была бы закрыть.
- **§C vendor-signed** (2 роута, `vendor-activation.ts`) — не Choros-актор
  вообще (Ed25519-подписанный vendor-домен); зеркалит T-0328 §3.2/§3.5.
- **§D verified-via-local-wrapper** (2 живых + 1 документационная запись) —
  §2.4/§3 предел, закрытый вручную с цитатой.
- **§E tenant-uniform config/catalog** (~30 роутов) — определения/конфиг,
  единообразные для всех активных членов тенанта, без per-employee
  grant-решения (process-defs, applications, sections, dmn-rule-tables,
  registry-defs, rights.ts role-каталог — зеркалит T-0328 rights.ts
  precedent, agents-list роструар, report-pages ОПРЕДЕЛЕНИЯ страниц [не
  рендер-данные — те уже маркер=Y], spend.ts [ратифицировано в файле:
  "Authz: any tenant member can view spend"], files.ts LIST [ратифицировано
  T-0521 п.1, FF-NOACL], org.ts roster — зеркалит ADR-T0658 §3.4 "display
  list" доктрину).

Категории §A-D — верифицированы построчным чтением кода/комментариев.
Категория §E верифицирована смесью построчного чтения (spend.ts, files.ts,
list-views.ts, rights-sod.ts) и структурного паттерна по имени
ресурса/таблицы (definition/catalog/binding/config — не record/grant/audit).
Это **честно слабее**, чем §A-D, и явно так документировано в самом скрипте
("НЕ exhaustive re-verification"); НОВЫЙ роут не на этом списке обязан пройти
собственную триаж, гейт не расширяет §E автоматически.

  мержа).

### 5.2 Новые находки этой задачи

- `record-links.ts:GET:/api/records/:id/links` — файл САМ документирует
  (строка ~31): "no field-level PDP here (no grant resolver threaded to this
  route)" — структурный ACL только через RLS.
- `grant-trail.ts:GET:/api/grant-trail` — полный tenant-wide журнал
  grant-назначений (кто держит какую роль, кем и когда подтверждено) отдаётся
  любому члену тенанта без единой authority-проверки.
- `rights-change-requests.ts:GET:/api/rights/change-requests` — список
  pending-заявок на изменение прав (тот же класс чувствительности, что
  grant-trail), без authority-проверки.
- `rights-sod.ts:GET:/api/rights/sod-check?subjectId=<slug>` — `subjectId`
  по умолчанию = сам актор, но ПЕРЕОПРЕДЕЛЯЕМ вызывающим на ЛЮБОЙ чужой slug
  без privilege-проверки — межсотрудничий SoD-отчёт открыт кому угодно.
- `operational-analytics.ts:GET:/api/operational-analytics[/export]` —
  `loadRecordSumsByPeriod` суммирует `record.data->>'field_key'` по ВСЕМ
  записям тенанта без READ-PDP фильтра — паритетный разрыв с уже закрытым
  Floor-1-агрегатом (T-0632, `reportAggReadVisibility`).
- `audit.ts:GET:/api/audit`, `/api/audit/export`, `/api/audit/:instanceId` —
  файл САМ документирует (строки ~630-638): "FORWARD-OBLIGATION: no PDP gate
  in dev slice. Hardening MUST add PDP check... all three routes must be
  closed together in the hardening pass."
- `inbox.ts:GET:/api/inbox[/:id]` — базовый tenant-open список задач; ролевой
  фильтр пул-вкладки идёт через `resolveRolesForActor` → `getRoleSlugsForActor`,
  который сам НЕ несёт `deactivated_at` (ALLOWLIST FF-0662 отмечает, что его
  единственный ПИШУЩИЙ consumer — claim/approve — несёт СВОЙ локальный гейт;
  ЭТОТ read-путь такого локального гейта не имеет).
- `report-page-render.ts:GET:/api/process-analytics` — tenant-wide
  cycle-time/actor-breakdown агрегат; комментарий в коде говорит только "no
  anonymous analytics" (аутентификация), не авторизация — родственные роуты
  в ТОМ ЖЕ файле (`/render`, `/export`, `/data`) несут `checkReadGrant`, этот
  — нет.

Ни один finding не является кросс-тенантной дырой (RLS + `resolveActorTenant`
из актора, не заголовка, держат tenant-изоляцию всюду) — все строго
внутритенантные, и все — расширение того же R-3/T-0714 класса: живой
JWT-держатель (активный ИЛИ деактивированный на остаточное окно) получает
доступ, минуя authority-резолвер.
