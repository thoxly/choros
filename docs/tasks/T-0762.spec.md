# Spec · T-0762 — слишком длинное имя/фамилия при создании учётки ошибочно репортится как невалидный email

**Phase:** DIAGNOSE + BUILD · **Status:** ready · **Date:** 2026-07-13
**Class:** users/UX P4, R-2 из ревью T-0748. **Root class:** product-defect (misattributed error —
та же честная-атрибуция дыра T-0748 закрыло для character-класса, но НЕ для length-класса).

## 1. Symptom

T-0748 (merge, dev@6c7aff0f history) научил `createHumanUser` (`src/keycloak/admin-port.ts`)
различать Keycloak-ошибку 400 «недопустимые символы в имени» (`error-person-name-invalid-
character`) от настоящей невалидной почты — новый код `NAME_INVALID_CHARACTERS`. Собственный
ревью T-0748 (R-2, nit, non-blocking) вживую пробировал СОСЕДНИЙ случай, явно НЕ входивший в
scope задачи (spec T-0748 §7 «Out of scope» отказывался только от переизобретения набора
символов, не от length-валидатора): слишком длинное `firstName` (300 символов, однословный
`display_name`, который `splitDisplayName` дублирует и в firstName, и в lastName) даёт живое тело
KC `{"field":"firstName","errorMessage":"error-invalid-length-too-long",...}` — этот
`messageKey` НЕ содержит подстроки `"person-name"`, поэтому `isPersonNameCharacterError`
корректно возвращает `false`, и запрос падает в СТАРЫЙ безусловный дефолт `EMAIL_INVALID` — та же
самая ошибочная атрибуция, что T-0748 уже закрыло для character-класса, но осталась открытой для
length-класса.

Владелец, который вводит `display_name` без пробелов длиной, близкой к клиентскому
`DISPLAY_NAME_MAX=256` (`web/src/screens/users-form.js`), видит ложное сообщение «email must be a
valid email address» — сообщение указывает на неверное поле; реальная причина (слишком длинное
имя) не названа вовсе.

## 2. Root cause

`makeHttpKeycloakUserPort().createHumanUser`'s `if (createResp.status === 400)` branch
(`src/keycloak/admin-port.ts`, до этого фикса) проверяло ТОЛЬКО character-класс
(`isPersonNameCharacterError`) и безусловно падало в `EMAIL_INVALID` для всего остального. KC's
declarative user-profile (`config/keycloak/realm-choros.json`) объявляет для firstName/lastName
ДВА независимых валидатора в одном JSON-объекте — `"length":{"max":255}` И
`"person-name-prohibited-characters":{}` — T-0748 закрыло атрибуцию только для второго, оставив
первый непокрытым тем же классом бага, который T-0748 само же и исправляло для character-класса.

## 3. Живое подтверждение формы ошибки KC (LIVE, не из памяти)

Прогнано против уже поднятого `t-0633-keycloak-1` (:8180, тот же образ/realm/choros-registrar
client_credentials путь, что и `createHumanUser` сам использует, и тот же контейнер, что T-0748's
собственный судья использовал для своего R-2 пробника). 2026-07-13. Ни один пробник не оставил
orphan-пользователя в KC (проверено `GET .../users?username=...&exact=true` после каждого — `[]`
во всех трёх RED-случаях).

```
POST /admin/realms/choros/users  {..., "firstName":"A"×300, "lastName":"A"×300, ...}  (оба поля > 255, single-token display_name дублирует)
-> HTTP 400 {"errors":[
     {"field":"lastName","errorMessage":"error-invalid-length-too-long","params":["lastName",null,255]},
     {"field":"firstName","errorMessage":"error-invalid-length-too-long","params":["firstName",null,255]}
   ]}

POST /admin/realms/choros/users  {..., "firstName":"B"×300, "lastName":"Petrov", ...}  (только firstName > 255)
-> HTTP 400 {"field":"firstName","errorMessage":"error-invalid-length-too-long","params":["firstName",null,255]}

POST /admin/realms/choros/users  {..., "firstName":"Иван","lastName":"Петров-Сидоров", ...}
-> HTTP 201   (ordinary control — unaffected)
```

Два различимых shape'а — те же, что extractKcFieldErrors (T-0748) УЖЕ парсит для character-класса:
single-object `{field, errorMessage}`, когда ровно ОДНО поле превышает предел (обычное
двухсловное имя с одним длинным токеном), и `{errors:[...]}` array, когда single-token
`display_name` дублируется splitDisplayName в оба поля и ОБА превышают предел одновременно. Это
подтверждает R-2's находку байт-в-байт (тот же `messageKey`, та же структура params
`[field, null, 255]`).

## 4. Fix

`src/keycloak/admin-port.ts`:
- New `isPersonNameLengthError(fieldErrors)` — true iff any entry has `field ∈ {firstName,
  lastName}` AND `errorMessage` contains `"invalid-length"` (substring match, тот же
  point-release-drift-tolerant подход, что `isPersonNameCharacterError`). Переиспользует
  СУЩЕСТВУЮЩИЙ `extractKcFieldErrors` (T-0748) — не новый парсер тела, тот же путь.
- `createHumanUser`'s 400 branch: проверка ПОСЛЕ `isPersonNameCharacterError` (character-класс не
  трогается, порядок сохранён), НО ПЕРЕД безусловным `EMAIL_INVALID` дефолтом → бросает
  `err.code = "NAME_TOO_LONG"`. Любой 400, не попавший НИ в один из двух firstName/lastName
  классов — настоящий bad email, unparseable body, KC-side drift на другом поле — падает в
  ТОЧНО ТОТ ЖЕ EMAIL_INVALID, что и раньше (регресс невозможен по построению: новая проверка
  чисто аддитивна, между существующей проверкой и существующим дефолтом).

`src/http/user-mgmt.ts` (`POST /api/users` catch block): новая ветка
`if (code === "NAME_TOO_LONG")` бросает `HttpError(400, "NAME_TOO_LONG", "отображаемое имя
слишком длинное — Keycloak допускает не более 255 символов на имя или фамилию; сократите имя и
попробуйте снова")` — честное русское сообщение, размещено ПОСЛЕ существующей ветки
`NAME_INVALID_CHARACTERS` и ПЕРЕД финальным `AUTH_UNAVAILABLE` фолбэком (чисто аддитивно).

`web/src/screens/users-form.js` (`mapUserError`): новый `status===400 && code==='NAME_TOO_LONG'`
case → `{ field: 'display_name', message: serverMsg || <честный русский дефолт> }`. Тот же
`display_name`-якорь, что и `NAME_INVALID_CHARACTERS` — механизм якоря уже существует
(`screen-users.jsx`), JSX не тронут.

`src/keycloak/fake-user-port.ts`: новый one-shot switch `failOnNameTooLong` (зеркалит
`failOnNameInvalid`), чтобы DB-интеграционный тест мог гнать новую ветку `user-mgmt.ts` без живого
KC.

## 5. Acceptance criteria

- **AC-1** KC 400 с `{field:"firstName"|"lastName", errorMessage:"error-invalid-length-too-long"}`
  (single-object shape, одно поле превышает предел) → `createHumanUser` бросает `NAME_TOO_LONG`.
- **AC-2** KC 400 с `{errors:[...]}` array shape (оба поля превышают предел одновременно —
  single-token displayName-дубликация) → всё равно `NAME_TOO_LONG`.
- **AC-3** KC 400 с `{errors:[...]}` mixed shape (email invalid И firstName too long одновременно)
  → `NAME_TOO_LONG` (length-проблема не маскируется соседней email-проблемой).
- **AC-4 (regression)** Character-класс (T-0748's own class, `error-person-name-invalid-
  character`) по-прежнему → `NAME_INVALID_CHARACTERS`, НЕ `NAME_TOO_LONG` — две проверки не
  кросс-фейрят друг друга.
- **AC-5 (regression)** Настоящий bad-email 400 (`error-invalid-email`) → неизменный
  `EMAIL_INVALID`.
- **AC-6 (regression)** Unparseable/empty body → неизменный `EMAIL_INVALID` safe default.
- **AC-7 (regression)** Length-ошибка на несвязанном поле (например, `username`) →
  `EMAIL_INVALID` (только firstName/lastName length-ошибки маппятся в `NAME_TOO_LONG`, нет
  overbroad matching).
- **AC-8** `POST /api/users` c KC `NAME_TOO_LONG` → `400`, `error.code = "NAME_TOO_LONG"`,
  честное русское сообщение называет «имя» + «длин» (не «email»).
- **AC-9 (regression)** `POST /api/users` с KC-side `EMAIL_INVALID` (defense-in-depth path)
  по-прежнему → `400 VALIDATION` с точным прежним email-текстом, не задет новой веткой.
- **AC-10 (regression)** Обычный двухсловный `display_name` (например, «Иван Петров») по-прежнему
  создаёт `201` — happy path не тронут.
- **AC-11 (web)** `mapUserError(400, {error:{code:'NAME_TOO_LONG', message:'...'}})` возвращает
  `{field:'display_name', message: <server message>}`.
- **AC-12 (web mount)** Реальный DOM-mount `<UsersScreen/>` с мокнутым KC `NAME_TOO_LONG` 400
  показывает честный хинт «слишком длинное» на поле «Отображаемое имя»
  (`aria-invalid="true"`), НЕ на Email; вводящий-в-заблуждение email-текст отсутствует в
  диалоге целиком.

## 6. Live proof

§3 above IS the live proof (реальный KC 25.0.6, `t-0633-keycloak-1`, choros-registrar
client_credentials — тот же путь, что `createHumanUser` сам использует; тот же контейнер, что
T-0748's собственный судья использовал для своей R-2 находки). Оба live-подтверждённых body shape
воспроизведены байт-в-байт (одно поле / оба поля) плюс control-201 для обычного имени. Ни одного
orphan-пользователя не оставлено (проверено после каждого пробника). Юнит-тесты
(`src/__tests__/admin-port.test.ts`, AP-10) реплеят эти EXACT live-наблюдённые body shapes через
локальный stub HTTP-сервер — тот же proportional подход, что T-0748's собственный AP-9 (стаб, не
живой KC, для детерминизма CI; live-пробник — то, что якорит стаб-тела в реальности).

## 7. Out of scope

- `DISPLAY_NAME_MAX=256` (client-side, `users-form.js`) не сужен до KC's 255-per-field предела —
  T-0748's собственный ревью (R-2) уже отметил это как non-blocking follow-up-кандидат отдельно
  от честной атрибуции; сужение границы — отдельное продуктовое решение (не каждый 256-символьный
  `display_name` бьёт по KC-пределу — только single-token без пробела), эта задача чинит ТОЛЬКО
  честность сообщения об ошибке, не саму границу.
- Никакой попытки заранее валидировать длину `display_name` на клиенте/сервере ДО вызова KC per
  firstName/lastName (потребовало бы предугадывать splitDisplayName-результат до отправки; KC —
  authority по факту, тот же принцип, что T-0748 §7).
- Self-registration (`src/core/register.ts`) не передаёт `displayName` вовсе (T-0741 §6,
  unchanged) — этот класс ошибки там не может возникнуть.
