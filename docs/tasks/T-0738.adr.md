# ADR T-0738 — getRoleSlugsForActor теряет держатели deactivated_at (P1, substrate)

- **Статус:** реализовано (impl-фаза, coder)
- **Контекст:** T-0726 (`docs/tasks/T-0726.adr.md` §5.2, finding
  `inbox.ts:GET:/api/inbox[/:id]`), родитель T-0658/T-0662 (`ACTOR_ACTIVE_SQL`,
  `src/db/actor-authority-gate.ts`), T-0702 (residual JWT-window)
- **Область:** `getRoleSlugsForActor` (`src/db/grants-dao.ts:431`) — единственный
  production-вызыватель: `resolveRolesForActor` в `src/http/inbox.ts`

## 1. Проблема

Судья T-0726 подтвердил: `getRoleSlugsForActor` резолвит employee по
`slug + tenant_id` **без** `deactivated_at IS NULL` — единственный оставшийся
employee actor-lookup в кодовой базе без предиката деактивации (все прочие
authority-резолверы T-0658/T-0662 его несут). Аллоулист-запись в
`ci/checks/actor-authority-deactivation-gate.sh` («DOWNSTREAM-GUARDED
authority projection») оправдывала отсутствие предиката тем, что «единственный
consumer — `inbox.ts` — несёт СВОЙ локальный гейт деактивации ПЕРЕД вызовом».

Это **верно для WRITE-путей и НЕВЕРНО для READ-пути**:

| путь | локальный гейт `findEmployeeById` + `deactivatedAt != null` | когда относительно `resolveRolesForActor` |
|---|---|---|
| `POST /api/inbox/:id/claim` | есть (inbox.ts ~1857-1871) | **ДО** вызова (~1893) — деактивированный никогда не доходит до резолвера |
| `POST /api/inbox/:id/action` (approve, прямой инстанс) | есть (~2271-2278) | **ДО** вызова (~2300) |
| `POST /api/inbox/:id/action` (approve, defer) | есть (~2160-2163) | **ПОСЛЕ** вызова (~2141) — не эксплуатируемо (запись всё равно блокируется до побочных эффектов), но нарушает заявленный инвариант «гейт ПЕРЕД вызовом» |
| `GET /api/inbox` (LIST, пул-вкладка) | **отсутствует** | — |
| `GET /api/inbox/:id` (DETAIL) | не вызывает `resolveRolesForActor` вовсе (см. §4) | — |

`GET /api/inbox` вызывает `resolveRolesForActor(actor, inboxTenantId)`
(inbox.ts ~1540) без какого-либо локального гейта. `myRoles` идёт в `inTab`
(inbox.ts ~1187-1200) и решает членство в пул-вкладке: `item.pool === true &&
myRoles.includes(item.role)`. Деактивация (T-0583/migration 125) отключает
УЧЁТНУЮ ЗАПИСЬ, но не автоматически ревокирует `role_assignment`
(ADR-T0658 §"Дыра №2" — «деактивированный = не держатель», но
`role_assignment`-строка переживает деактивацию, если её не отозвали
отдельно). Итог: держатель ещё живого access-JWT (offline-JWKS, ~300s
остаточное окно, T-0702), уже уволенный/деактивированный, видел непустую
пул-вкладку (и ненулевой `counts.pool`) для роли, которую когда-то держал —
до момента, пока `role_assignment` не будет отозван отдельно.

Не кросс-тенантная дыра (RLS + tenant-scoping не тронуты) — строго
внутритенантный, той же категории, что остальные находки T-0726 (живой
JWT-держатель обходит authority-резолвер на READ-пути).

## 2. Решение — фикс резолвера (не per-consumer гейт)

Добавлен `AND ${ACTOR_ACTIVE_SQL}` (`src/db/actor-authority-gate.ts`, тот же
именованный предикат, что несёт `getGrantsForSubject`) в **обе** SQL-выборки
`getRoleSlugsForActor`: первичную (`slug = actorSlug`) и T-0366-фолбэк
(`slug = fallbackSlug`, KC seed-персоны).

**Почему фикс резолвера, а не пятый bespoke-гейт в `inbox.ts`:** T-0662 уже
задокументировал урок («пять копий одного предиката — симптом отсутствия
единого слоя»; whack-a-mole). Правка резолвера закрывает READ-путь СЕЙЧАС и
защищает от рецидива на КАЖДОМ будущем вызывателе — не только на текущих
четырёх. WRITE-пути (claim/approve) получают это как **defence-in-depth**
(они уже не достигали резолвера с деактивированным актором благодаря своим
локальным гейтам) — поведение для НИХ байт-идентично.

**Почему не `includeDeactivated`-параметр:** единственный production-
вызыватель (`resolveRolesForActor`) используется ИСКЛЮЧИТЕЛЬНО для резолюции
СОБСТВЕННЫХ ролей действующего актора (self-authority: «какие роли держит
ЭТОТ actor для PDP-решения claim/approve/pool-видимости»), никогда — для
отображения ролей ЧУЖОГО (в т.ч. уволенного) сотрудника административным
экраном. В кодовой базе нет ни одного сценария «админ смотрит роли уволенного
сотрудника через getRoleSlugsForActor» (в отличие от, например,
`pdp-explain.ts:loadSubjectGrants`, который явно DISPLAY и остаётся в
аллоулисте T-0662 нетронутым). Параметр добавлял бы неиспользуемую развилку
без вызывателя, который бы её включил — лишняя площадь. Если такой сценарий
появится, он либо получит собственный DISPLAY-путь (как `pdp-explain.ts`),
либо резолвер обрастёт параметром тогда, с реальным вызывателем в руках.

### 2.1 Эффект на каждого вызывателя (грепнуты все — `grep -rn
getRoleSlugsForActor src/`)

| вызыватель | было (деакт. актор) | стало | регресс? |
|---|---|---|---|
| `GET /api/inbox` (LIST, пул-вкладка/бейджи) — inbox.ts ~1540 | `myRoles` включал роли деактивированного → пул-вкладка непуста | `myRoles = []` → пул-вкладка/бейдж честно пусты | **ФИКС**, не регресс — ни один активный актор не резолвит через `deactivated_at IS NULL` иначе |

Активный актор (deactivated_at IS NULL уже) — предикат no-op, поведение
байт-идентично.

## 3. Анти-кейс

Фикс — общий предикат на резолвере, без кейс-контента: никаких хардкод-slug/
tenant/role литералов ни в SQL, ни в тестах (все фикстуры — `uuid()`-суффикс,
мирроря `grants-dao-subject-deactivation.db.test.ts` / T-0658).

## 4. Отдельно — `GET /api/inbox/:id` (DETAIL) НЕ вызывает `resolveRolesForActor`

Разведка показала: DETAIL-роут (inbox.ts:1657) находит item через
`findInboxItems(actor)` (tenant-scoped, без ролевого фильтра) и не вызывает
`resolveRolesForActor`/`getRoleSlugsForActor` вовсе — «tenant-open список»
по конструкции (T-0726 ADR §5.2 группирует `[/:id]` вместе, так как оба лежат
в одном finding-блоке route-scan'а, не потому что `/:id` реально зовёт
резолвер). Это ШИРЕ скоупа T-0738 (не про деактивацию — про то, что DETAIL
вообще не проверяет ролевую адресацию для ЛЮБОГО актора, включая активного) —
не трогаю, отдельный вопрос от текущего security P1.

## 5. Гейт `actor-active-route-coverage.sh` (T-0726, informational) — честно, не механически

`ACTIVE_MARKERS` в этом гейте (файл владения T-0726, я его не трогаю — правка
чужого `ci/checks/*.sh` без санкции = frozen-thaw, T-0146) — фиксированный
список из 7 зарегистрированных authority-резолверов + верифицированных
производных. **`getRoleSlugsForActor`/`resolveRolesForActor` в этом списке
не было и не появилось** (в отличие от T-0721, чей фикс МЕХАНИЧЕСКИ вошёl в
скан, потому что *использовал* уже-маркерный `isRecordReadable`). Прогон
ДО/ПОСЛЕ фикса (см. `T-0738.pr-handoff.json`) показывает: находки
`inbox.ts:GET:/api/inbox` и `inbox.ts:GET:/api/inbox/:id` **остаются** в
списке finding — это ЧЕСТНЫЙ предел текстового скана (ADR-T0726 §2.4 п.1:
«Не call-graph-доказательство»), а не признак того, что фикс не сработал.
Реальная уязвимость закрыта и доказана live-PG тестами (§6); маркер-реестр
T-0726 — governance другой задачи (потребовал бы либо founder-санкцию, либо
`auto-sanction-additive` с Враг-аттестацией на ЧУЖОЙ файл — вне периметра
substrate-фикса P1). Я НЕ добавлял тривиальный/театральный вызов
зарегистрированного маркера ради того, чтобы скан позеленел — это ровно
паттерн evasion, который сам T-0662 self-test (3) ловит («dead reference
рядом с un-gated lookup»). Флагую как естественный follow-up для владельца
T-0726: одна аддитивная строка в `ACTIVE_MARKERS` (`getRoleSlugsForActor`)
с цитатой на этот ADR.

## 6. Тесты (живой PG :55432)

Новый файл `ci/checks/db/grants-dao-role-slug-deactivation.db.test.ts`:

- **AC-1** — деактивированный актор (роль назначена, `role_assignment`
  не отозван) → `getRoleSlugsForActor` возвращает `[]`.
- **AC-1+** — позитивный контроль: активный актор с идентичной формой
  назначения → роль резолвится (без регресса).
- **AC-2** — T-0366 фолбэк: деактивированный primary + активный fallback
  (`preferred_username`) → фолбэк резолвит роли (фолбэк не подавлен самим
  фактом деактивации primary — он получает свой независимый чек).
- **AC-2+** — деактивированный fallback → `[]` (предикат применён к обеим
  выборкам).
- **AC-3 (HTTP, live-PG)** — `GET /api/inbox?tab=pool` реальным роутом:
  деактивированный держатель роли не видит адресованную ему pool-задачу
  (`items` пуст, `counts.pool === 0`); позитивный контроль — активный
  держатель той же роли видит задачу.
