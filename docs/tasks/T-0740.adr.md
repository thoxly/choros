- **Статус:** реализовано частично по дизайну (impl-фаза, coder) — (A) закрыто,
  (B) НЕ закрыто (frozen, не auto-additive-safe; см. §5)

  закрыл `getRoleSlugsForActor`/`resolveRolesForActor` (несут
  `deactivated_at IS NULL`), но НЕ трогал `ci/checks/actor-active-route-
  coverage.sh` (T-0726, «файл владения не я»), явно флагуя это как follow-up.
  Родители: T-0658/T-0662 (`ACTOR_ACTIVE_SQL`), T-0726 (route-coverage гейт),
  T-0736/T-0737/T-0739 (та же security-волна, все смержены в базу этой задачи).
- **Область:** `ci/checks/actor-active-route-coverage.sh` (ACTIVE_MARKERS),
  `ci/checks/actor-authority-deactivation-gate.sh` (AUTHORITY_RESOLVERS/
  ALLOWLIST, НЕ тронут), `src/http/inbox.ts` (комментарий), `docs/design/
  T-0152-security-invariants-catalog.md` (новая семья §7.7).

## 1. Проблема

Живой прогон `bash ci/checks/actor-active-route-coverage.sh` на базе
`dev@12624db6` показывал **2 находки**:

```
FINDING [FF-726-1]: inbox.ts:GET:/api/inbox (lines 1435-1656)
FINDING [FF-726-1]: inbox.ts:GET:/api/inbox/:id (lines 1657-1789)
SUMMARY: 77 GET routes audited — 20 marker-covered, 55 whitelisted, 2 findings
```

Обе — тот же класс «module-scope helper невидим блок-скану» (ADR-T0726 §2.4
п.1), что уже задокументирован для `notification-prefs.ts`/`solution-
publish.ts`/`audit.ts`. Гейт T-0662 (`actor-authority-deactivation-gate.sh`)
живой и зелёный, но его 7 `AUTHORITY_RESOLVERS` не совпадают буквально с
`ACTIVE_MARKERS` T-0726 — `getRoleSlugsForActor`/`resolveRolesForActor` несут
предикат (добавлен T-0738), но ни гейт T-0726, ни реестр T-0662 их не знают
как «зарегистрированные authority-примитивы».

## 2. Разведка — hand-verify каждой находки отдельно (не одна и та же причина)

### 2.1 `GET /api/inbox` — ЗАКРЫТО (T-0738), просто не отражено в реестре

`inbox.ts:1540`: `const myRoles = await resolveRolesForActor(actor,
inboxTenantId);` — литерально внутри блока этого роута (1435-1656).
`resolveRolesForActor` (`inbox.ts:428-439`, module-scope helper, объявлен
ДО первого `.register(` в файле) **композирует** `getRoleSlugsForActor`
напрямую (`inbox.ts:439`), без обхода.

`getRoleSlugsForActor` (`src/db/grants-dao.ts:431-494`) — hand-verified:
несёт `${ACTOR_ACTIVE_SQL}` на ОБЕИХ SQL-выборках:
- первичная (`grants-dao.ts:470`): `` `SELECT id FROM choros.employee WHERE
  tenant_id = $1 AND slug = $2 AND ${ACTOR_ACTIVE_SQL} LIMIT 1` ``
- T-0366-фолбэк (`grants-dao.ts:484`): та же форма, `slug = fallbackSlug`.

Добавлено T-0738 (см. inline-комментарий `grants-dao.ts:444-467`, явно
цитирует финдинг T-0726). **Вывод:** резолвер РЕАЛЬНО несёт гейт — маркер
легитимен, не маскировка.

### 2.2 `GET /api/inbox/:id` — НЕ ЗАКРЫТО, реальный отдельный gap

`inbox.ts:1657` (DETAIL-роут) вызывает `findInboxItems(actor)`
(`inbox.ts:1667`) — **tenant-scoped, БЕЗ ролевого фильтра**; ни
`resolveRolesForActor`, ни `getRoleSlugsForActor`, ни любой другой
authority-резолвер НЕ вызывается нигде в достижимом графе этого роута.
T-0738 сам это констатировал (`docs/tasks/T-0738.adr.md` §4): «DETAIL-роут
находит item через `findInboxItems(actor)` (tenant-scoped, без ролевого
фильтра) и не вызывает `resolveRolesForActor`/`getRoleSlugsForActor` вовсе
— tenant-open список по конструкции... ШИРЕ скоупа T-0738 (не про
деактивацию — про то, что DETAIL вообще не проверяет ролевую адресацию для
ЛЮБОГО актора, включая активного) — не трогаю, отдельный вопрос».

**Решение: НЕ добавлять маркер для этой находки.** Это ровно evasion-
паттерн, который сам T-0662 self-test (case 3) и эта задача прямым текстом
запрещают («НЕ добавляй маркер, если резолвер НЕ несёт гейт»). Находка
остаётся **честной FINDING** после этой задачи — трек как follow-up
(см. §7).

## 3. Frozen-статус ОБОИХ файлов — эмпирическая проверка, не теория

`coder.md` §8(б): «Chужие `ci/checks/*.sh` не трогай... правка чужого
frozen-чека = frozen-thaw (T-0146)». Задача явно предупреждала об этом
только для (B); для (A) — нет. Проверено эмпирически на живой ветке
(не синтетика): пробный однострочный комментарий-пробник в
`actor-active-route-coverage.sh` → `bash ci/checks/frozen-checks-
immutable.sh` → `FAIL [FF-FCI1]: ... belongs to task 'T-0726' ...
not T-0740`. **Оба файла — И T-0726-owned, И T-0662-owned — одинаково
frozen относительно T-0740**; различие «(A) informational vs (B) wired-
in-fitness» не встроено в механику T-0146 (глоб `ci/checks/[^/]+\.sh$`
не различает статус).

Ретроспективная проверка (`git worktree` на `018d2ac8` = реальный
`dev`-tip ДО мержа T-0737): T-0737 реально правил `actor-active-route-
coverage.sh` (ROUTE_WHITELIST §D, audit.ts×3) БЕЗ записи в
`frozen-sanctions.jsonl` — на настоящем историческом BASE_REF гейт бы
провалился. T-0736, напротив, ЯВНО избежал правки файла («Findings T-0726
12→9, без правки чужого гейт-файла», `T-0736.adr.md` §7), а T-0738 явно
отказался («правка чужого ci/checks/*.sh без санкции = frozen-thaw...
Флагую как естественный follow-up для владельца T-0726: auto-sanction-
additive с Враг-аттестацией», `T-0738.adr.md` §5). **T-0738's собственный
вывод — ровно план этой задачи.** Разрыв между T-0736/T-0738 (осторожно) и
T-0737 (без учёта T-0146) зафиксирован как friction-находка (см. §8), не
блокирует эту задачу.

## 4. Решение (A) — auto-additive frozen-thaw, не founder

Механизм `ci/checks/auto-sanction-additive.sh` (T-0232, FF-FCI13) позволяет
task-ветке править ЧУЖОЙ `ci/checks/*.sh`, если правка МЕХАНИЧЕСКИ додекана
аддитивна (A-1..A-4 над BASE_REF) И несёт валидную Враг-аттестацию (семья ⊆
каталог T-0152, семья's Enforced-by покрывает правимый файл, corpus_ref —
предок HEAD с тем же corpus-блобом, enemy_segment непуст). Ни один из этих
критериев не требует founder-действия — это D-007-совместимая машинная
верификация, соответствует принципу «фаундеру только деньги/продукт/
секреты/необратимое» (over-escalation на founder за реестр-маппинг был бы
дефектом).

**Шаг 1 — каталог:** добавлена новая семья `### 7.7 ACTOR-ACTIVE` в
`docs/design/T-0152-security-invariants-catalog.md` (§7, «Дополнительные
инварианты, найденные в коде» — секция ИМЕННО для этого класса добавлений,
сам каталог документирует себя как «НЕ заморожен сейчас», append-only по
духу). Enforced-by перечисляет ОБА файла (`actor-authority-deactivation-
gate.sh`, `actor-active-route-coverage.sh`) + 7 живых `db/*deactivat*` тестов.

**Шаг 2 — правка (чисто additive, 2 новых записи перед закрывающей `)`):**

```
"resolveRolesForActor"       # src/http/inbox.ts:428-439 — module-scope helper ...
"getRoleSlugsForActor"       # src/db/grants-dao.ts:431-494 — carries ${ACTOR_ACTIVE_SQL} ...
```

**Шаг 3 — sanction-строка** (`ci/checks/data/frozen-sanctions.jsonl`,
append-only, НЕ захватывается T-0146 glob'ом): `task:"T-0740"`,
`file:"ci/checks/actor-active-route-coverage.sh"`, `sanctioned_by:
"auto_additive"`, `families:["ACTOR-ACTIVE"]`, `corpus_ref` = merge-base
`dev@12624db6` (предок HEAD, corpus.jsonl-блоб идентичен HEAD — не трогали
корпус), `enemy_segment: "ci/checks/db/grants-dao-role-slug-deactivation.
db.test.ts"` (реальный, релевантный, T-0738's live-PG adversarial-пруф
именно этого предиката).

**Верификация (не самозаявление):**
```
$ bash ci/checks/auto-sanction-additive.sh --verify T-0740 \
    ci/checks/actor-active-route-coverage.sh 12624db6... "$SANCTION_JSON"
PASS [A-1..A-4]: additive against BASE_REF
PASS [ATTEST-R1b]: family 'ACTOR-ACTIVE' covers the thawed file
PASS [ATTEST-R1a]: corpus_ref ancestor of HEAD, blob matches HEAD
PASS [ATTEST]: enemy_segment declared
→ exit 0, bypass ALLOWED

$ bash ci/checks/frozen-checks-immutable.sh
SANCTION [FF-FCI13]: ... T-0740 carries an AUTO-ADDITIVE frozen-sanction ... ALLOWED
PASS: frozen-checks-immutable — all ci/checks/*.sh changes are owned by T-0740
```

Зелено на РЕАЛЬНОЙ ветке, не постфактум-синтетика.

## 5. Решение (B) — actor-authority-deactivation-gate.sh НЕ тронут (frozen, не auto-additive-safe)

Запрошенная правка — промоушен `getRoleSlugsForActor` из `ALLOWLIST` в
`AUTHORITY_RESOLVERS` (T-0662, `actor-authority-deactivation-gate.sh`).
Оценено на auto-additive-совместимость:

- Промоушен требует **удаления** строки `"src/db/grants-dao.ts:
  getRoleSlugsForActor"` из `ALLOWLIST` (и её объясняющего комментария
  «DOWNSTREAM-GUARDED authority projection», ставшего частично устаревшим)
  И добавления её в `AUTHORITY_RESOLVERS` — это МУТАЦИЯ существующего члена
  (смена классификации), не чистое добавление. `A-1` (byte-preservation
  ВСЕХ непустых BASE_REF-строк, включая комментарии) это запрещает
  структурно.
- Альтернатива — оставить строку в ОБОИХ массивах (дублирование вместо
  переноса) — механически проверена и **отклонена самим auto-sanction-
  additive.sh**: сущность `"src/db/grants-dao.ts:getRoleSlugsForActor"`
  уже присутствует в `base_ents` (ALLOWLIST), поэтому добавление ТОЙ ЖЕ
  строки в `AUTHORITY_RESOLVERS` не вводит НОВУЮ сущность → `A-4` FAIL
  («delta line only references existing entities»). Это ровно случай R-1-
  ABSENT-AT-BASE, который self-test (4c/case I) целенаправленно ловит —
  машина права: реклассификация существующего security-предиката —
  осознанное решение, не механическая аддитивность.

**Вывод:** (B) требует **founder-класс санкции** (`FF-FCI12`, через реальный
`founder_decide` control-plane, НЕ через самозапись строки — самозапись
`sanctioned_by:"founder"` без реального founder-решения была бы forgery,
ровно evasion-паттерн, RL-1/RL-2 boundary). Coder-роль не инициирует
founder-решения за рутинный registry-мейнтенанс (over-escalation — тоже
дефект, см. founder-escalation-boundary). **(B) НЕ реализовано.** Точный
diff для будущего founder-санкционированного захода:

```diff
--- ci/checks/actor-authority-deactivation-gate.sh (ALLOWLIST)
- "src/db/grants-dao.ts:getRoleSlugsForActor"
--- ci/checks/actor-authority-deactivation-gate.sh (AUTHORITY_RESOLVERS)
+ "src/db/grants-dao.ts:getRoleSlugsForActor"
```
плюс обновление ALLOWLIST-комментария (сейчас `actor-authority-
deactivation-gate.sh:168-175` — «DOWNSTREAM-GUARDED... inbox.ts:1413/1631»
устарело вдвойне: (1) предикат теперь несёт сам резолвер, не только
downstream-гейт; (2) номера строк `inbox.ts:1413/1631` больше не совпадают
с текущими ~1868/~2276 после дрейфа файла).

## 6. `src/http/inbox.ts:~2265` — устаревший комментарий (не frozen, правлю)

Комментарий у approve-гейта (`inbox.ts:2261-2271`) утверждал
«`getRoleSlugsForActor` does not filter on `employee.deactivated_at`» —
верно ДО T-0738, ложно ПОСЛЕ (§2.1). Переписан: объясняет, что локальный
`findEmployeeById`-гейт теперь **defence-in-depth** (резолвер сам фильтрует
с T-0738), не единственный барьер. `src/http/inbox.ts` — не `ci/checks/
*.sh`, T-0146 не применяется, правка прямая.

## 7. Известный незакрытый gap — `GET /api/inbox/:id`

Тот же класс, что T-0721 закрыл для `GET /api/processes/:id` (ADR-T0726
цитирует прецедент), но НЕ применён к inbox: DETAIL-роут вообще не
проверяет, адресована ли задача актору (ни по роли, ни по деактивации) —
tenant-open для ЛЮБОГО члена тенанта, активного или нет. T-0738 уже
флагнул это (§4 там) как «отдельный вопрос». Эта задача НЕ чинит его
(не про реестр-реконсиляцию, реальный продуктовый P1/P2 фикс) — оставлен
как честная `FINDING [FF-726-1]` (1 находка после этой задачи), фолоу-ап
предложен через spawn_task (см. финальный отчёт).

## 8. Friction-находка (не блокирует эту задачу)

`frozen-checks-immutable.sh`'s `BASE_REF` резолвится через ЛОКАЛЬНЫЙ `dev`/
`origin/dev` REF в момент запуска — если та ветка/воркдир уже смержена в
`dev` (или `dev`-ref не зафетчен свежо), диагностика post-hoc даёт ложно-
зелёный результат (ретроспективный `merge-base(dev, HEAD)` схлопывается в
`HEAD`, диф пуст). Это, вероятно, объясняет, как T-0737 прошло правку
чужого frozen-файла без санкции и без обнаружения ревью/CI. Структурная
дыра в самом T-0146 гейте (не специфична для T-0740) — не чиню здесь (чужой
frozen-файл), флагую как отдельный follow-up.
