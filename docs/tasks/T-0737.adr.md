# ADR T-0737 — audit-surface READ-PDP/ACTOR_ACTIVE gate (GET /api/audit, /export, /:instanceId)

- **Статус:** реализовано (impl-фаза, coder)
- **Контекст:** судья T-0726 (`docs/tasks/T-0726.adr.md` §5.2) подтвердил живой
  finding: `audit.ts` сам документирует (`FORWARD-OBLIGATION`, было на строках
  ~630-638) "no PDP gate in dev slice... all three routes must be closed
  together" — security P1
- **Область:** `src/http/audit.ts` — `GET /api/audit`, `GET /api/audit/export`,
  `GET /api/audit/:instanceId`

## 1. Проблема

Три GET-роута аудит-поверхности несли РАЗНЫЙ уровень защиты:

| роут | ДО этой задачи |
|---|---|
| `GET /api/audit` | REAL owner-only гейт (`loadAdminContext` + `holdsAuditRead`, T-0500 review) — уже был закрыт продуктово, но **невидим** статическому гейту `actor-active-route-coverage.sh` (T-0726), т.к. вызов живёт в module-scope хелпере `handleGetAuditLog`, объявленном ДО первого `.register(` в файле — тот же класс слепоты, что ADR-T0726 §2.4 п.1 документирует для `notification-prefs.ts`/`solution-publish.ts` |
| `GET /api/audit/export` | только присутствие `x-dev-user` (dev) / валидный токен (keycloak) — **КТО** не проверялся вообще |
| `GET /api/audit/:instanceId` | **НИКАКОЙ** проверки сверх `withAuth` — в dev-режиме `withAuth` — no-op, значит запрос без единого заголовка получал демо-трейс |

Живой `bash ci/checks/actor-active-route-coverage.sh` (T-0726) до фикса:
все три роута — findings (`77 GET routes audited — 13 marker-covered, 52
whitelisted, 12 findings`).

## 2. Решение

Единственный переиспользуемый гейт — `requireAuditRead(pool, req)`
(`src/http/audit.ts`), применённый ко ВСЕМ ТРЁМ роутам:

```
extractActor(req, pool)        // keycloak: sub/preferred_username → slug (401 fail-closed)
                                // dev: x-dev-user header (401 если отсутствует)
  → resolveActorTenant(pool, actorId)   // 403 ACTOR_TENANT_UNRESOLVED, если неизвестен
    → loadAdminContext(pool, tenantId, actorId, now)   // T-0662 authority-резолвер #3
      → holdsAuditRead(admin) === admin.isGenesisOwner  // 403 ADMIN_GATE_REJECTED
```

Никакого нового authority-пути: `loadAdminContext` — один из 7
зарегистрированных `AUTHORITY_RESOLVERS`
(`ci/checks/actor-authority-deactivation-gate.sh`), уже нёсший
`ACTOR_ACTIVE_SQL` (`deactivated_at IS NULL`) предикат и уже использовавшийся
ровно для этой же цели на `GET /api/audit` (T-0500). `holdsAuditRead` —
существовавшая с T-0500 чистая функция, не тронута.

### 2.1 Кто вправе читать аудит — owner-only, без расширения

**Решение:** genesis-owner ONLY, буквально та же политика, что T-0500-ревью
уже установил для `GET /api/audit`.

**Почему:** аудит-журнал тенанта несёт ВСЕ действия организации (гранты,
auth-события, решения агентов) — это максимально чувствительная
поверхность. Разведка (`grep -rn "loadAdminContext(" src/http/*.ts`,
~45 живых точек вызова) показала, что `mgmt_object:*`-грант — точечный
(один тип объекта: department/position/employee), а не "видеть весь
журнал". T-0500's собственный review-комментарий в файле уже зафиксировал
это явно: "a mgmt_object:* grant covers a SINGLE object type... MUST NOT
open the entire journal". `/export` и `/:instanceId` отдают демо-данные
(не реальный `audit_event`), но файл САМ группирует их под ОДНО forward-
obligation с `/api/audit` — фикс продолжает эту же группировку, не
изобретает более узкую или более широкую политику для двух из трёх
роутов одной поверхности.

### 2.2 Отказ = 403 (не 404) — эталон сиблинга `/api/audit`

**Решение:** недостаточно полномочий → `403 ADMIN_GATE_REJECTED` на всех
трёх роутах (не honest-404, в отличие от T-0721's `/api/processes/:id`).

**Почему:** прямой эталон — сам `GET /api/audit` (T-0500), единственный
из трёх роутов этой поверхности, УЖЕ имевший осознанный authz-дизайн:
`403` для аутентифицированного-но-неавторизованного, `401` для
неаутентифицированного. Наличие журнала аудита тенанта не является
секретом (в отличие от существования конкретной записи в T-0721) — скрывать
его через 404 не даёт никакой доп. гарантии и расходится с уже
зафиксированным прецедентом на этой же поверхности. Консистентность внутри
ОДНОГО файла/ОДНОЙ функции-гейта важнее теоретического выбора.

### 2.3 Пул недоступен (memory-режим) → 503, не fail-open

**Решение:** `pool === undefined` → `503 AUDIT_UNAVAILABLE` на всех трёх
роутах, ДО вызова `requireAuditRead` (гейту нужен живой DB-коннект, чтобы
резолвить admin-контекст — без него авторизацию доказать нельзя).

**Почему:** прямое расширение уже существовавшего паттерна `GET /api/audit`
("no real audit store to read — fail HONESTLY (503) rather than fall back
to a fake timeline", T-0500). Раньше `/export` и `/:instanceId` работали
БЕЗ пула (чисто in-memory demo-данные) — теперь пул нужен ТОЛЬКО для
гейта, не для данных, но авторизация не может fail-open просто потому что
данные тривиальны.

### 2.4 Единая функция `requireAuditRead`, не инлайн-дублирование на каждый роут

**Развилка:** статический гейт `actor-active-route-coverage.sh` (T-0726)
видит маркеры-резолверы ТОЛЬКО текстово внутри блока САМОГО роута (от его
`.register(` до следующего) — module-scope хелпер, объявленный раньше
первого `.register(` в файле, невидим скану (§2.4 п.1 того ADR). Это ровно
ситуация, в которой уже оказался `GET /api/audit` (см. §1).

**Решение:** ОДНА shared-функция `requireAuditRead`, вызываемая всеми
тремя роутами, ЗАРЕГИСТРИРОВАНА в `ROUTE_WHITELIST §D`
(`ci/checks/actor-active-route-coverage.sh`) с цитатой (`audit.ts:554-569`)
— тот же приём, что уже применён для `notification-prefs.ts`'s
`checkAdminGrant` и `solution-publish.ts`'s `requirePrivilege`.

**Почему не инлайн-дублирование (что сделало бы каждый роут маркер-
covered БЕЗ whitelist):** три копии одинаковой 5-строчной authority-цепочки
были бы более хрупкими при будущем изменении политики (например, если
founder решит открыть аудит второму ярусу) — пришлось бы синхронно
править 3 места, легко разойтись. Whitelist §D — санкционированный
ADR-T0726 механизм именно для этого класса (module-scope wrapper,
verified-once, cited). Выбрана меньшая площадь для будущих ошибок над
механической видимостью скана без документации.

## 3. Fitness-функции / гейты

- **`ci/checks/actor-active-route-coverage.sh`** (T-0726, informational) —
  все три `audit.ts` роута теперь на `ROUTE_WHITELIST §D` с цитатой на
  `requireAuditRead` (`audit.ts:554-569`). Живой прогон: **12 → 9 findings**
  (52 → 55 whitelisted, marker-covered без изменений — закрыто через
  whitelist, не через видимый маркер). `--self-test` зелёный.
- **`ci/checks/actor-authority-deactivation-gate.sh`** (FF-0662) — без
  изменений: `requireAuditRead` не вводит НИ ОДНОГО нового actor
  slug-lookup (переиспользует `extractActor`/`resolveActorTenant`/
  `loadAdminContext`, все уже в реестре/allowlist). FF-0662-1/2 зелёные.
- **`ci/checks/audit_append_only.sh`** — не тронут (append-only DDL
  audit_event/audit_head), зелёный.
- **`ci/checks/http-route-auth-coverage.sh`** (T-0328) — все три роута
  остаются `withAuth`-wrapped; `x-dev-user` в `extractActor` по-прежнему
  gated за `getAuthContext(req) === undefined` веткой (FF-0328-2). Зелёный.
- **`ci/checks/anti-case-lock.sh`** (D-064) — новые тестовые фикстуры не
  вводят ни одного литерала из денай-листа (`e-larina`/`e-orlov`/...);
  дженерик-имена (`e-owner`, `e-nonowner`, `e-member-active`). Зелёный.

## 4. Тесты

- **`src/__tests__/audit-export-instance-authz.test.ts`** (НОВЫЙ) —
  детерминированный stub-pool (та же техника, что T-0500's
  `audit-log.test.ts`): owner → 200 (regression-safe demo shape) на обоих
  роутах; неизвестная инстанция → 404; отсутствие `x-dev-user` → 401 на
  ОБОИХ (ключевое новое покрытие для `/:instanceId`, который раньше не имел
  ВООБЩЕ никакого гейта); non-owner (с mgmt-грантом или без) → 403; пул не
  подключён → 503; `/export` не перехватывается роутом `/:instanceId`.
- **`ci/checks/db/audit-route-deactivation-gate.db.test.ts`** (НОВЫЙ, живой
  PG) — реальный `http.Server` + реальный `choros_migrator` Pool (мирроит
  production-wiring `server.ts:595`): ДЕАКТИВИРОВАННЫЙ tenant-owner (живой
  `x-dev-user`-токен = его slug) → 403 на всех трёх роутах; активный
  НЕ-owner член тенанта → 403 на всех трёх; позитивный контроль — активный
  owner → 200 на всех трёх (легитимный читатель не сломан). Резолверный
  уровень deactivation-предиката УЖЕ доказан
  `ci/checks/db/org-admin-deactivation.db.test.ts` (T-0658) — этот файл
  доказывает WIRING (роут реально доходит до резолвера и подчиняется его
  вердикту), не переоткрывает предикат.
- **`src/__tests__/audit.e2e.test.ts`** / **`audit-export.e2e.test.ts`**
  (ОБНОВЛЕНЫ) — envelope-паттерн (503 без БД / loose-check с БД), byte-shape
  проверки перенесены в детерминированный stub-pool файл выше — прежние
  тесты полагались на то, что `/export`/`/:instanceId` работают БЕЗ гейта
  вообще, что и было дырой.

## 5. Отклонения от спеки

Нет. changes_product=0 в handoff — это исправление контура авторизации на
уже существующих роутах (READ), не новая продуктовая функциональность;
live_proof не требуется по тому же основанию, что и прежние
substrate/security-задачи такого профиля (T-0662, T-0726).
