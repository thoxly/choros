## 1. Проблема

Живой прогон `bash ci/checks/actor-active-route-coverage.sh` на базе
`dev@b983ecff`:

```
FINDING [FF-726-1]: rights-intents.ts:GET:/api/rights/intents/substitution-coverage
                    (lines 977-1037) — no ACTIVE_MARKERS hit ...
SUMMARY: 78 GET routes audited — 22 marker-covered, 55 whitelisted, 1 findings
```

Роут (T-0745) резолвит вызывающего через `extractActor` + `resolveTenant` —
**display-only** identity mapping (T-0662 doctrine, `actor-authority-
gate.ts`'s явный список «NOT AN AUTHORITY RESOLVER»: `resolveActorSlugFromAuth`
и производные ДЕЛИБЕРАТИВНО не гейтятся на активность, иначе сломался бы показ
имени уволенного). Ни один из 7 зарегистрированных T-0662 `AUTHORITY_RESOLVERS`
не вызывается нигде в достижимом графе роута — только `role_assignment`-чтение
без проверки деактивации ВЫЗЫВАЮЩЕГО. Последствие: держатель ещё живого
access-JWT (T-0702, ~300s остаточное окно, offline-JWKS) — уже деактивированный
— мог запросить ЛЮБУЮ пару `(role_id, substitute_employee_id)` и получить
`provides_coverage` (boolean) + `holder_count` (number): честный
role-membership-оракул для конкретной пары, хотя ни идентичности держателей,
ни списка не отдаётся напрямую.

## 2. Разведка — что реально отдаёт роут и кому он нужен

`registerSubstitutionCoverage` (T-0745 doc-comment, rights-intents.ts:941-970):
серверный REUSE `substituteProvidesCoverage` (T-0744, `core/substitution.ts`) —
тот же инвариант, что роутер/claim-гейт/owner-claim уже разделяют. Вызывается
из `web/src/screens/rights/ra-intents.jsx`'s `useSubstitutionCoverage` — ОБА
формы `SubstituteForm` (админ) и `SelfAbsenceForm` (self-service) дергают его
при выборе роли+замещающего, чтобы показать баннер «замещающий сейчас не
держит роль». T-0745 explicitly гейтнул роут «тем же минимальным баром, что
`registerSelfAbsence`'s WRITE (`extractActor` + `resolveTenant`, БЕЗ admin-
гейта)» — **но не заметил**, что `registerSelfAbsence`'s WRITE несёт СВОЙ
собственный inline `slug = $2 AND ${ACTOR_ACTIVE_SQL}` резолв ВЫЗЫВАЮЩЕГО
(T-0662 resolver D, `actor-authority-gate.ts` строка 33), который READ-роут
T-0745 не реюзнул и не продублировал. Self-service parity была скопирована
только наполовину: «без admin-гейта» — да; «но всё равно ACTOR_ACTIVE на
самого вызывающего» — нет.

Сверка с сиблингами `registerSubstitute`/`registerUrgentRevoke`/`registerHire`/
`registerFire` — ВСЕ четыре роутят через `loadAdminContext` (T-0662 resolver
B2, admin-гейт, несёт `ACTOR_ACTIVE_SQL`). `registerSelfAbsence` — единственный
authority-WRITING хендлер в файле БЕЗ `loadAdminContext` (self-service, admin-
гейт намеренно отсутствует), поэтому несёт СВОЙ bespoke резолв. T-0745's READ
скопировал именно этот (единственный «безадминный») сиблинг по духу, но
пропустил его единственную защиту.

## 3. Решение — (а), не (б)

Задача предложила два варианта: (а) гейтнуть на ACTOR_ACTIVE как сиблинги, или
(б) whitelist §D с обоснованием безвредности. **Выбрано (а).** Обоснование
недостаточности (б): `provides_coverage` + `holder_count` — это не «просто
boolean» в вакууме, это ОТВЕТ НА ВОПРОС «держит ли КОНКРЕТНЫЙ employee_id
КОНКРЕТНУЮ role_id» — ровно тот факт, который `rights-overview.ts`'s
self-scope проекция для ОБЫЧНОГО (не-admin) АКТИВНОГО сотрудника намеренно
СКРЫВАЕТ («держателей ЧУЖИХ ролей не видно», T-0745 doc-comment строки 947-957,
явная причина, почему T-0745 вообще понадобился НОВЫЙ read). Раз этот факт уже
признан достаточно чувствительным, чтобы обычный АКТИВНЫЙ сотрудник не видел
его через штатный `tenant-state` эндпоинт (только через целевой self-service
роут), то ДЕАКТИВИРОВАННЫЙ актор — не являющийся более легитимной стороной
self-absence/substitute-флоу, ради которого этот роут вообще существует, —
тем более не должен его получать. Whitelist §D требует ЧЕСТНО доказать
безвредность; здесь это невозможно — реальный enumeration-вектор (перебор
`substitute_employee_id` по UUID'ам из уже tenant-open `GET /api/org` для
известной `role_id`) даёт деактивированному холдеру ровно ту карту ролей,
которую продукт целенаправленно прячет от рядового АКТИВНОГО члена.

## 4. Реализация

Новая функция `resolveActiveActorEmployeeId` (rights-intents.ts, перед
`registerSubstitutionCoverage`) — **независимая** от `registerSelfAbsence`'s
inline lookup копия ТОЙ ЖЕ формы (`slug = $2 AND ${ACTOR_ACTIVE_SQL}`), НЕ
рефакторинг в общий helper: извлечение общего кода потребовало бы, чтобы
`registerSelfAbsence`'s тело больше не содержало предикат ТЕКСТОМ — это
сломало бы `actor-authority-deactivation-gate.sh`'s FF-0662-1 для уже
зарегистрированного резолвера D (`func_body` брейс-трекает буквальное тело
функции; вызов чужого helper'а не матчится тем же regex'ом). Две независимые
копии — цена простоты и нулевого риска для существующего зелёного гейта.

```ts
const activeEmployeeId = await resolveActiveActorEmployeeId(pool, tenantId, actorId);
if (activeEmployeeId === null) {
  throw new HttpError(404, "NOT_FOUND", "actor employee record not found");
}
```

Вызывается ДО holder-set чтения (нулевой лишний запрос на деактивированном
пути). **Отказ = 404 NOT_FOUND «actor employee record not found»**, байт-в-
байт та же форма, что `registerSelfAbsence`'s собственный отказ (T-0658 FIX-1)
— консистентность с сиблингом (задача явно просила сверить политику).

Резолвер зарегистрирован **8-м** `AUTHORITY_RESOLVERS` (T-0662,
`actor-authority-deactivation-gate.sh`) и зеркалирован в `ACTIVE_MARKERS`
Group 1 (T-0726, `actor-active-route-coverage.sh`) — оба гейта явно
инструктируют мирроринг («Group 1 is the T-0662 AUTHORITY_RESOLVERS registry
verbatim... changes there must be mirrored here»). `src/db/actor-authority-
gate.ts`'s doc-comment реестр (A/B1/B2/C/D/E/F) получил запись **G** для
консистентности документации (не frozen, обычная правка).
