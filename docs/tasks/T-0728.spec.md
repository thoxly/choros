# Мини-спека + ADR · T-0728 — person-поля на канбане показывают исполнителя

- **Task:** T-0728 · продукт Choros · эпик E-UX-HUMAN T-0647 · столп 2 (интерфейс-из-блоков-на-данных) / анти-UUID (столп 4)
- **База:** свежий `dev`, уже несущий T-0698 (общий хелпер `buildEmployeesById`,
  `PersonCell`/`PersonFieldValue` с `deactivated`-сигналом).
- **Источник:** N2 из ревью T-0698.
- **Тип:** точечная протяжка существующего механизма во ВТОРОЙ display-mode.
  Не редизайн канбана, не новый компонент рендера.

## 1. Разведка — где рвётся протяжка

`formatCellValue` (`web/src/screens/records-form.js:1195-1295`) уже умеет
`person`-тип: непустое значение → сентинел `PERSON_CELL_ASYNC` (T-0673) —
резолв id→имя асинхронный (батч-загрузка `/api/org`), поэтому синхронная
`formatCellValue` физически не может отдать строку.

Таблица записей (`screen-app-records.jsx`) уже правильно диспатчит сентинел
на `PersonCell` (компонент, ActorChip, `deactivated`-проп — T-0673/T-0698) и
батч-грузит `employeesById` через общий `buildEmployeesById` (T-0698),
гейтуя фетч на `hasPersonColumn`.

Канбан (`kanban-board.jsx`, T-0582) — ВТОРОЙ display-mode над ТЕМИ ЖЕ
записями (`screen-app-records.jsx` рендерит `<KanbanBoard>` вместо таблицы,
когда `activeView.type === 'kanban'`, тот же `GET /api/records?view_id=`,
FF-K-4) — не знал об этом контракте вовсе:

1. `KanbanCard`'s field-loop (`kanban-board.jsx:98-98`, до фикса) делал
   `const displayVal = typeof rendered === 'string' ? rendered : '—';` —
   ЛЮБОЙ non-string возврат `formatCellValue` (все три асинк-сентинела:
   `RELATION_CELL_ASYNC`/`FILE_CELL_ASYNC`/`PERSON_CELL_ASYNC`) молча падал
   в «—». Person-поле на карточке ВСЕГДА показывало «—», независимо от
   того, назначен исполнитель или нет.
2. `<KanbanBoard>` не получал `employeesById` ВООБЩЕ — проп не существовал
   ни в сигнатуре компонента, ни в вызове из `screen-app-records.jsx`. Даже
   почини п.1 диспатч, резолвить id→имя было бы нечем.

Оба обрыва — до персон-специфичного рендера; чинить только один не работает
(тот же паттерн двух независимых обрывов, что ADR-T0698 §2 задокументировал
для `deactivated_at`).

## 2. Кому передаётся employeesById в table-режиме (эталон)

`screen-app-records.jsx`: `employeesById` — стейт, батч-грузится ОДИН раз на
экран через `fetchEmployees()` → `buildEmployeesById(list)` (T-0698's «ONE
canonical» хелпер), гейт `hasPersonColumn = columns.some(c => c.type ===
'person')`. `columns` — производная от `activeView.config.columns`; у
kanban-конфига (`{group_by_field, card_fields, columns_order, filters,
sort}`, `list-view-panel.jsx` `KanbanConfigEditor`) НЕТ поля `columns` —
поэтому в kanban-режиме `columns` откатывается на `schemaColumns` (ПОЛНЫЙ
каталог полей набора), а не на card_fields-подмножество. Следствие: гейт
`hasPersonColumn` уже корректно взводится, когда в СХЕМЕ есть хоть одно
person-поле — консервативно чуть шире, чем «есть person среди card_fields»,
но НИКОГДА не пропускает случай, когда он реально нужен. Не трогается этой
задачей (уже работает верно для обоих режимов).

## 3. Functional

- F1. `<KanbanBoard>` принимает новый проп `employeesById` (дефолт — пустая
  стабильная `Map`, не `undefined` — `PersonCell` уже терпит не-`Map`, но
  явный дефолт документирует контракт и не аллоцирует новую `Map` на каждый
  рендер).
- F2. `screen-app-records.jsx` передаёт СВОЙ уже существующий `employeesById`
  стейт в `<KanbanBoard employeesById={employeesById} .../>` — НЕ второй
  фетч/стейт, тот же батч-загруженный ресурс.
- F3. `employeesById` протянут через `KanbanBoard` → `KanbanColumnView` →
  `KanbanCard` (проп с тем же именем на каждом хопе — без переименования).
- F4. Диспатч-решение «person-поле → `PersonCell` / иначе → текст» вынесено
  в чистую функцию `resolveCardFieldCell` (`kanban-board.js`) — тот же
  паттерн, что `resolveCardLabel` (T-0626): `KanbanCard` использует
  `useCallback`, поэтому его render-тело нельзя вызвать напрямую в
  hook-free vitest-тире этого репо; решение живёт СНАРУЖИ, тестируемо без
  React.
- F5. Person-ячейка рендерится через `<PersonCell personId={...}
  employees={employeesById} />` — ИМПОРТИРОВАННЫЙ из `field-renderer.jsx`
  компонент (см. §4 ниже), НЕ второй хендролленный `ActorChip`-обёртка.
  `deactivated`-сигнал идентичен таблице (тот же компонент, тот же
  `ActorChip`, тот же `chs-exec--deactivated` визуал).
- F6. Anti-UUID: ни при каком исходе (резолвится/не резолвится/пусто) сырой
  UUID не рендерится напрямую — либо `PersonCell` (резолвит имя ИЛИ честно
  показывает raw slug через `ActorChip`'s `resolved:false`-контракт, не
  голый bare-child), либо «—» для пустого значения.

## 4. Design — канонический дом PersonCell

`PersonCell` раньше жил ТОЛЬКО в `screen-app-records.jsx` (локальная
функция, не переиспользуемая). Два варианта:

- (a) Импортировать `PersonCell` из `screen-app-records.jsx` в
  `kanban-board.jsx` — создаёт ЦИКЛИЧЕСКИЙ импорт
  (`screen-app-records.jsx` уже импортирует `{ KanbanBoard }` из
  `kanban-board.jsx`). ESM циклы иногда работают, но это хрупко и не
  прецедент в этой кодовой базе.
- (b) **Выбрано.** Переместить `PersonCell` в `web/src/forms/field-renderer.jsx`
  — файл, УЖЕ владеющий `fetchEmployees()`/`buildEmployeesById` (T-0698's
  «ONE canonical» employee-data-layer). `screen-app-records.jsx` импортирует
  оттуда (было: локальное определение) и ре-экспортирует
  (`export { PersonCell };`) для обратной совместимости существующих
  импортов/тестов. `kanban-board.jsx` импортирует оттуда напрямую. Ноль
  циклов, один источник правды — соответствует D-064 anti-parallel-resolver
  дисциплине (не плодить второй резолвер одного и того же факта).

## 5. Non-functional / anti-case

- N1. Zero new read path: `employeesById` — та же батч-загрузка
  (`GET /api/org` через `fetchEmployees()`), НИ одного нового
  fetch/эндпоинта.
- N2. Relation/file сентинелы (`RELATION_CELL_ASYNC`/`FILE_CELL_ASYNC`) на
  канбане остаются вне охвата — по-прежнему деградируют в «—»
  (соразмерность: постановка явно про person-поля, N2 из ревью T-0698 не
  просит закрыть все три сентинела разом).
- N3. Anti-case (D-064): нет доменных литералов; `resolveCardFieldCell`
  работает с произвольным `key`/`meta`/`data`, ничего кейс-специфичного.

## 6. Acceptance criteria

- AC-1: канбан-карточка с person-полем, у которого назначен исполнитель →
  показывает имя-чип (ActorChip), НЕ «—» и НЕ сырой id/UUID.
- AC-2: тот же исполнитель деактивирован → чип несёт `deactivated`-сигнал
  (приглушённый стиль, `chs-exec--deactivated`) — идентично `PersonCell` в
  таблице записей.
- AC-3: person-поле без значения → «—» (не крашится, не «undefined»).
- AC-4: person-поле со значением, отсутствующим в `employeesById` (ещё не
  загружено / удалённый сотрудник) → честная деградация через `ActorChip`'s
  `resolved:false` (raw slug виден, но НЕ голым bare-child — anti-uuid-actor-
  render гейт не триггерится, т.к. рендер идёт через `<PersonCell>`).
- AC-5: `employeesById` — ТОТ ЖЕ стейт, что таблица использует (не второй
  fetch) — доказано source-text wiring-тестом.
- AC-6: `tsc`/targeted vitest/vite build зелёные; anti-uuid-actor-render +
  self-test, ux-g2-theme-pairing, anti-case-lock — PASS.

## 7. Out of scope

- Relation/file сентинелы на канбане (остаются «—», как были).
- Редизайн карточки/канбана целиком.
- Серверные изменения — read-путь (`GET /api/org`, `GET /api/records`) не
  трогается, чисто клиентская протяжка уже существующих данных.
