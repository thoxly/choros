# T-0760 — engine-drive db-лейн нечестен локально (grant-сид + timeout-запас)

Fitness/тест-гигиена, substrate. Приоритет 40. Вскрыто T-0672 (risks[4] /
`note_for_followup`) — оба дефекта отмечены как "вне scope" на месте находки и
отложены сюда.

## 1. Что было сломано

### (а) `ci/checks/db/engine-drive-generic.db.test.ts` — 403 на чистой локальной БД

**Симптом:** на чистом `dev@fd0ad0f7` c живым Postgres (`:55432`) И живым
Flowable (`:8082`) 3 из 4 тестов красные — `POST /api/inbox/:id/action
{action:"approve"}` возвращает `403 NOT_ELIGIBLE` вместо `200`.

**Корень:** `seedApproverGrant` (сид самого теста, написан для T-0571) вставляет
`role_assignment` со `SET proposed_by = actorSlug` (шестой параметр `$6`) но
БЕЗ `confirmed2_by`:

```sql
-- было (до фикса), проецируется на колонки:
-- (..., source, granted_by, proposed_by, confirmed_by, created_at, updated_at)
VALUES ($1, $2, $3::uuid, $4, $5::jsonb, NULL, NULL, 'genesis',
        $6::text, $6::text, $6::text, 0, 0)
--                        ^^^^^^^^^^^^^ proposed_by = actorSlug (НЕ NULL)
```

T-0605 (build f952c8b0, смержен ПОСЛЕ T-0571 — порядок подтверждён `git log`:
T-0605 на строке 811, T-0571 на строке 951 в `git log --oneline --all`, т.е.
T-0605 более свежий) сделало КАНОНИЧЕСКИМ единый предикат активации назначения
в `getRoleSlugsForActor` (`src/db/grants-dao.ts:515-525`):

```sql
WHERE ra.confirmed_by IS NOT NULL
  AND (ra.confirmed2_by IS NOT NULL OR ra.proposed_by IS NULL)
```

Смысл предиката (T-0605/T-0397 dual-control): строка с `proposed_by` УСТАНОВЛЕННЫМ,
но `confirmed2_by` = NULL читается как «предложение назначения, ждущее ВТОРОЙ
подписи» — PDP-неактивна ПО ЗАМЫСЛУ (это ровно тот механизм, который закрывает
dual-control дыру T-0397). Сид T-0571 ставил `proposed_by = actorSlug` (видимо,
трактуя параметр как «кто оформил» вообще, не как машину предложения), и
`confirmed2_by` никогда не заполнялся (колонки не было в insert-списке) →
предикат `(confirmed2_by IS NOT NULL OR proposed_by IS NULL)` = `(FALSE OR
FALSE)` = `FALSE` → строка ИСКЛЮЧЕНА из «активных» назначений →
`getRoleSlugsForActor` возвращает `[]` → `resolveRolesForActor` возвращает `[]`
→ `inbox.ts` (~2437-2448) видит `!myRoles.includes(task.role)`, нет Tier-2 и нет
owner-orphan путей → `403 NOT_ELIGIBLE`.

**Это НЕ разница «полный CI сидит X, локальный лейн — нет».** GitHub Actions'
`db`-job (`.github/workflows/ci.yml`) гоняет `npm run fitness:db` БЕЗ Flowable
(Flowable поднимается только в отдельном `flowable`-job, который `fitness:db`
не запускает) — так что этот файл в автоматическом CI ВСЕГДА молча скипает
(`requireDbAndFlowable`), и 403 там никогда не проявляется. Единственные
прогоны, где тест реально доходил до `POST /api/inbox/:id/action` против
живого движка — ручные LIVE_PROOF-сессии судей (см. T-0672.pr-handoff.json:
`risks_for_judge[4]` и `note_for_followup`), которые СИД поменять для верного
предиката не догадались/не смогли — задача была помечена «вне scope» и
делегирована сюда.

**Фикс:** `seedApproverGrant` теперь пишет `proposed_by = NULL` и явно
`confirmed2_by = NULL` — та же форма прямого/genesis-гранта, что использует
`T-0750-inbox-detail-authority.db.test.ts`'s `seedAssignment` (эталонный,
пост-T-0605 сид):

```sql
VALUES ($1, $2, $3::uuid, $4, $5::jsonb, NULL, NULL, 'genesis',
        $6::text, NULL, $6::text, NULL, 0, 0)
--                       ^^^^          ^^^^
--                proposed_by=NULL   confirmed2_by=NULL
```

Предикат становится `confirmed_by IS NOT NULL (TRUE) AND (confirmed2_by IS NOT
NULL (FALSE) OR proposed_by IS NULL (TRUE))` = `TRUE` → строка активна.

**НЕ тронут прод-authz.** Правка ограничена тестовым сид-хелпером
(`ci/checks/db/engine-drive-generic.db.test.ts`); `src/db/grants-dao.ts`
(канонический предикат T-0605) и `src/http/inbox.ts` (гейт approve) — байт-в-байт
как были.

### Побочная находка (вскрыта фиксом (а), НЕ отдельный дефект продукта)

Починка сида впервые позволила control дойти до ВТОРОГО approve-вызова в
тесте `idempotent repeat (AC-8)` (раньше он падал на ПЕРВОМ вызове с 403, до
второго дело не доходило). Он ожидал `404 NOT_FOUND` — контракт ДО T-0688.
T-0688 (`fb367491`, судья 3× approved, «stale-drawer» фикс) сделал
`POST /api/inbox/:id/action` для уже-завершённого (в фоне) шага честным `200
{engine:"already"}` вместо вводящего в заблуждение `404`
(`src/http/inbox.ts:2211-2227`, проверка через `listInstanceProjections` перед
`404`). Тестовая ассерция была НИКОГДА реально не прожита живьём (see above —
403 на первом вызове маскировал её) — обновлена на актуальный,
задокументированный судейский контракт (`200 {status:"done", engine:"already"}`),
без изменения продукт-кода.

### (б) `ci/checks/db/engine-drive-completedby.db.test.ts` — testTimeout == driveDeadlineMs

Каждый `it(...)` вызывал `reconcileInstanceEngineDrive(..., {driveDeadlineMs:
60000})`, а сам файл не задавал явный per-test timeout → падал на
suite-wide `vitest.config.js` дефолте `testTimeout: 60000` (T-0646). Это РОВНО
та же величина, что и `driveDeadlineMs` — нулевой запас. Судья T-0672
(`docs/tasks/T-0672.review.json`, `issue`/`suggestion` в конце файла) поймал
это живьём: на холодном/эмулированном Flowable первый deploy JIT-прогрев
дважды из трёх уронил тесты по vitest-таймауту РАНЬШЕ, чем сработал бы
собственный `driveDeadlineMs`-таймаут драйва (61.2s GREEN-тест на тёплом
движке — уже сверх 60000).

**Фикс:** явный третий параметр `it(name, fn, timeoutMs)` на каждом из 3
тестов:
- GREEN / RED-mutation (по одному drive на тест): `120_000`
  (`driveDeadlineMs` 60000 + 60s запас — ровно предложение судьи).
- idempotent (ДВА последовательных drive: initial + re-drive): `150_000`
  (запас над одним «доминирующим» drive; второй re-drive на уже-ended
  инстансе на практике почти мгновенный — не полный 2×60000 потолок, но и не
  голый 120000).

Это НЕ меняет `driveDeadlineMs` (семантика продукта — сколько реконсайл
драйва ждёт живой движок) и не трогает suite-wide `vitest.config.js`
(`testTimeout: 60000` остаётся дефолтом для всех остальных файлов — только
эти 3 теста получают собственный, больший бюджет).
