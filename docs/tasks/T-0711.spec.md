# T-0711 — resolveLiveRecordSchema: резолв привязки по выбранному приложению + детерминизм

Родитель: эпик E-FORMS T-0479. Источник: ревью T-0706 (finding P2 #37) + T-0669.
Приоритет: P2. Столп 2/3 (интерфейс-из-блоков-на-данных + бесшовность).

## 1. Проблема (как есть, до задачи — разведано по коду, не по спеке)

`resolveLiveRecordSchema` (`src/db/live-form-schema.ts`) — единственный
резолвер «какая живая схема (registry_def.record_schema) валидирует форму
процесса». Шаг 1 его SQL до задачи:

```sql
SELECT application_id, target_registry_slug
  FROM choros.process_app_binding
 WHERE tenant_id = $1 AND process_key = $2
 LIMIT 1            -- ни фильтра по application_id, ни ORDER BY
```

При этом натуральный ключ таблицы — `UNIQUE (tenant_id, process_key,
application_id)` (migrations/075): ОДИН процесс МОЖЕТ быть привязан к
НЕСКОЛЬКИМ приложениям. `BindProcessModal` (экран «Процессы») это не
запрещает, а пикер «Приложение» FormDesigner (T-0669,
`boundAppIdsForProcess`) честно предлагает ВСЕ привязанные приложения как
валидные варианты.

Следствия для процесса с 2+ привязками:

1. **Произвол планировщика.** `LIMIT 1` без `ORDER BY` — Postgres вправе
   вернуть ЛЮБУЮ строку; выбор может меняться между запросами/вакуумами/
   планами. Гейт `classifyLayoutSave` и дериватор `deriveFieldsFromLayout`
   валидируют/строят поля против НЕДЕТЕРМИНИРОВАННОЙ схемы.
2. **Игнорируется выбор пользователя.** Автор выбрал приложение B в пикере —
   сервер мог валидировать против схемы приложения A: ложный 409 WRONG_FLOOR
   на корректной форме ИЛИ (хуже) молчаливо-успешный save против чужой схемы.
3. T-0706 усилил иллюзию точности: UI уверенно показывает «Набор полей задан
   привязкой процесса: X» для ВЫБРАННОГО приложения, а сервер мог резолвить
   другое.

Выбранное приложение (`selectedAppId`) до сервера НЕ доходило вовсе:
`persistLayout` (`web/src/forms/FormDesigner.jsx`) слал только
`{process_key, form_key, layout}`.

## 2. Все call-sites (разведка)

- `resolveLiveRecordSchema` ← `resolveLiveSchemaFieldKeys`,
  `resolveLiveCollectionSubKeys` (тот же файл), `deriveFieldsFromLayout`
  (`src/http/binding.ts`), unit-тесты T-0681.
- `resolveLiveSchemaFieldKeys` ← `classifyLayoutSave` (`src/http/binding.ts`),
  `floor1-editor.ts` (роут `/edits`, doc-валидация).
- `resolveLiveCollectionSubKeys` ← `classifyLayoutSave`.
- `classifyLayoutSave` ← `POST /api/forms/binding` (человеческий save,
  binding.ts) и `POST /api/forms/document-ops` (агентский шов,
  forms-document-ops.ts).

Каналы, где выбранное приложение ДОСТУПНО: FormDesigner (`selectedAppId`).
Каналы, где НЕДОСТУПНО: FormBuilder (fields-only путь — гейт не зовётся),
floor1-editor `/edits` (нет пикера приложения в теле), legacy-вызовы,
агентские вызовы document-ops без знания привязки.

## 3. Решение

1. **Опциональный `applicationId`** (4-й/5-й параметр) у всех трёх резолверов
   `live-form-schema.ts`, у `classifyLayoutSave` и `deriveFieldsFromLayout`.
   Один SQL на обе ветки: `AND ($3::uuid IS NULL OR application_id = $3)`.
2. **Детерминизм без пина**: `ORDER BY created_at ASC, id ASC` — старейшая
   привязка (обоснование выбора порядка — ADR §2).
3. **Fail-closed на мусорный пин**: не-UUID `applicationId` → `null` (→ 409 в
   гейте), НЕ молчаливое игнорирование (иначе неоднозначность возвращается).
   Несуществующий (но валидный) UUID → 0 строк → `null` → 409.
4. **HTTP-протяжка**: `POST /api/forms/binding` и `POST /api/forms/document-ops`
   принимают опциональный `application_id`/`applicationId` (dual-casing, как
   process_key). UUID-shape guard → 400. Отсутствие поля = прежнее поведение
   (плюс детерминизм).
5. **UI-протяжка**: `persistLayout(…, applicationId)` шлёт `application_id:
   selectedAppId` — только когда непустой.

## 4. Acceptance criteria

- **AC-1** Процесс с ДВУМЯ привязками к приложениям A и B (разные
  registry_def со РАЗНЫМИ схемами): `resolveLiveRecordSchema(..., appB)`
  возвращает схему B, `(..., appA)` — схему A (live-PG тест).
- **AC-2** Без `applicationId` при 2+ привязках — результат детерминирован:
  старейшая привязка (`created_at`, tie-break `id`), не произвол планировщика
  (live-PG тест: старейшая строка намеренно НЕ первая вставленная физически).
- **AC-3** Валидный-но-несуществующий `applicationId` → `null` (fail-closed);
  малформенный → `null` без единого SQL-запроса.
- **AC-4** `classifyLayoutSave` протягивает ОДИН `applicationId` в ОБА
  резолвера (field-keys + collection-subKeys) — никогда в один из двух.
- **AC-5** `POST /api/forms/binding` c `application_id` приложения B и
  layout с полем схемы B → 201; тот же layout с `application_id` приложения A
  (у A другой набор полей) → 409 WRONG_FLOOR (live-PG тест).
- **AC-6** Обратная совместимость: все существующие call-sites без
  `applicationId` компилируются и проходят без изменений поведения для
  процесса с одной привязкой (существующие suites live-form-schema /
  classifyLayoutSave / binding зелёные без правок стабов).
- **AC-7 (анти-кейс, D-064)** Ни одного кейс-литерала в `src/`; фикстуры
  тестов нейтральные; `anti-case-lock.sh` зелёный.

## 5. Вне скоупа

- UI-выбор приложения для floor1-editor `/edits` и FormBuilder — там нет
  пикера приложения; они получают детерминизм-фолбэк (честное улучшение без
  изменения контрактов).
- Запрет мульти-привязки процесса или UNIQUE(tenant, process_key) — природа
  данных легитимна (одна модель процесса обслуживает 2 приложения).
- `step-applier`/`process-instance-resolver` резолвят привязку по СВОИМ путям
  (instance-контекст) — не трогаем.
