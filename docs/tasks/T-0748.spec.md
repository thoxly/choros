# Spec · T-0748 — display_name с спецсимволами ("Bot #1", "A&B") ошибочно репортится как невалидный email

**Phase:** DIAGNOSE + BUILD · **Status:** ready · **Date:** 2026-07-11
**Class:** users/UX, NF-1 из ревью T-0741. **Root class:** product-defect (misattributed error —
честная атрибуция нарушена generic-фолбэком).

## 1. Symptom

T-0741 (merge 29f2d62d) начал отправлять Keycloak `firstName`/`lastName`, производные от
`display_name` формы «Создать учётку» (`splitDisplayName`, `src/keycloak/admin-port.ts`).
`config/keycloak/realm-choros.json` объявляет для обоих полей валидатор
`person-name-prohibited-characters` (KC-25 declarative user profile) — тот же самый, что T-0741's
own doc уже называет «authority on legal characters». Владелец, который вводит `display_name`
со спецсимволами (например, для агента/бота с именем «Bot #1» или сотрудника «A&B» — не только
человеческое ФИО, поле свободного текста) теперь триггерит KC 400 на этом валидаторе.

`createHumanUser`'s 400-branch (`admin-port.ts`, до этого фикса) не различал ПРИЧИНУ 400 —
любой статус 400 от `POST /admin/realms/choros/users` безусловно маппился в `EMAIL_INVALID`.
`user-mgmt.ts` затем превращал это в `HttpError(400, "VALIDATION", "email must be a valid email
address...")`. Владелец, введший ВАЛИДНЫЙ email и `display_name="Bot #1"`, видел ложное
сообщение об email — сообщение указывало на неверное поле, реальная причина (недопустимые
символы в имени) не называлась вовсе.

## 2. Root cause

`makeHttpKeycloakUserPort().createHumanUser`'s `if (createResp.status === 400)` branch
(`src/keycloak/admin-port.ts`, до фикса — строка ~519) безусловно бросал `EMAIL_INVALID`,
не читая тело ответа KC. Это было корректно ДО T-0741 (единственный 400 от этого эндпоинта был
`error-invalid-email` — T-0625's defense-in-depth), но T-0741 добавило firstName/lastName в
payload, открыв ВТОРОЙ класс 400 (person-name validator) через ТОТ ЖЕ HTTP-статус — фолбэк
перестал быть безопасным default и стал маскировать новый класс ошибки под старый код.

## 3. Живое подтверждение формы ошибки KC (LIVE, не из памяти)

Прогнано против локального KC 25.0.6 (`t-0633-keycloak-1`, :8180, тот же образ/realm, что
T-0734/T-0741), `choros-registrar` client_credentials — тот же путь, что `createHumanUser`.
2026-07-11.

```
POST /admin/realms/choros/users  {..., "firstName":"Bot","lastName":"#1", ...}
-> HTTP 400 {"field":"lastName","errorMessage":"error-person-name-invalid-character","params":["lastName"]}

POST /admin/realms/choros/users  {..., "firstName":"A&B","lastName":"Ivanov", ...}
-> HTTP 400 {"field":"firstName","errorMessage":"error-person-name-invalid-character","params":["firstName"]}

POST /admin/realms/choros/users  {..., "email":"not-an-email", "firstName":"Ivan","lastName":"Petrov", ...}
-> HTTP 400 {"field":"email","errorMessage":"error-invalid-email","params":["email","not-an-email"]}

POST /admin/realms/choros/users  {..., "email":"not-an-email", "firstName":"Bot#1", ...}   (both bad)
-> HTTP 400 {"errors":[
     {"field":"email","errorMessage":"error-invalid-email","params":["email","not-an-email"]},
     {"field":"firstName","errorMessage":"error-person-name-invalid-character","params":["firstName"]}
   ]}

POST /admin/realms/choros/users  {..., "firstName":"Иван","lastName":"Петров-Сидоров", ...}
-> HTTP 201   (ordinary Cyrillic name, hyphen — unaffected control)
```

Two distinguishable shapes: a **single-object** `{field, errorMessage}` when exactly one field
fails, and an **`{errors:[...]}` array** when multiple fields fail in the same request. The
person-name validator's `errorMessage` is `error-person-name-invalid-character` — always on
`field:"firstName"` or `field:"lastName"`, never on `email`. No orphan Keycloak user is left
behind on ANY of the 400 cases (KC rolls the create back on validation failure — confirmed: none
of the 4 throwaway `t0748-red-*` usernames existed after the probe; only the successful `t0748-
green-1` needed cleanup).

## 4. Fix

`src/keycloak/admin-port.ts`:
- New `extractKcFieldErrors(body)` — parses BOTH live-confirmed 400 shapes (single-object and
  `{errors:[...]}` array) into a uniform `{field?, errorMessage?}[]`. Returns `[]` on any
  unparseable/unrecognized body (safe default, mirrors `extractKcErrorMessage`'s own contract).
- New `isPersonNameCharacterError(fieldErrors)` — true iff any entry has
  `field ∈ {firstName, lastName}` AND `errorMessage` contains `"person-name"` (substring match,
  not exact-key, so a KC point-release that reshapes the messageKey suffix still matches; narrow
  enough it can only fire on those two fields).
- `createHumanUser`'s 400 branch: if `isPersonNameCharacterError` → throw
  `err.code = "NAME_INVALID_CHARACTERS"`. Otherwise → **UNCHANGED** `EMAIL_INVALID` fallback
  (exact prior behavior — any 400 not carrying a firstName/lastName person-name error, including
  a genuine bad email, an unparseable body, or KC-side validation drift on some other field,
  still maps to `EMAIL_INVALID`).

`src/http/user-mgmt.ts` (`POST /api/users` catch block): new
`if (code === "NAME_INVALID_CHARACTERS")` branch throwing
`HttpError(400, "NAME_INVALID_CHARACTERS", "отображаемое имя содержит недопустимые символы —
уберите спецсимволы (<, &, #, кавычки, скобки) и попробуйте снова")` — honest Russian message,
placed BEFORE the generic `AUTH_UNAVAILABLE` fallback, AFTER the existing `EMAIL_INVALID` branch
(so `EMAIL_INVALID`'s own behavior is untouched — new branch is purely additive).

`web/src/screens/users-form.js` (`mapUserError`): new `status===400 && code==='NAME_INVALID_
CHARACTERS'` case → `{ field: 'display_name', message: serverMsg || <fallback> }`. Anchors the
error on the «Отображаемое имя» input (`screen-users.jsx`'s existing generic `mapped.field`
wiring — no JSX changes needed, the field-anchor mechanism already exists for `EMAIL_TAKEN`/
`login`).

`src/keycloak/fake-user-port.ts`: new one-shot switch `failOnNameInvalid` (mirrors
`failOnLoginTaken`) so the DB-integration test suite can drive `user-mgmt.ts`'s new branch
without a live KC.

## 5. Acceptance criteria

- **AC-1** A KC 400 with `{field:"lastName"|"firstName", errorMessage:"error-person-name-invalid-
  character"}` (single-object shape) → `createHumanUser` throws `NAME_INVALID_CHARACTERS`.
- **AC-2** A KC 400 with `{errors:[...]}` array shape carrying a firstName/lastName person-name
  entry (mixed with other field errors, e.g. email also bad) → still `NAME_INVALID_CHARACTERS`
  (the name problem is not masked by a co-occurring email problem).
- **AC-3 (regression)** A KC 400 with `{field:"email", errorMessage:"error-invalid-email"}` →
  UNCHANGED `EMAIL_INVALID`.
- **AC-4 (regression)** A KC 400 with an unparseable/empty body → UNCHANGED `EMAIL_INVALID`
  (safe default, exact prior behavior).
- **AC-5 (regression)** A KC 400 on an unrelated field (e.g. `username`) → `EMAIL_INVALID` (only
  firstName/lastName person-name errors map to the new code — no over-broad matching).
- **AC-6** `POST /api/users` with a KC `NAME_INVALID_CHARACTERS` → `400` with `error.code =
  "NAME_INVALID_CHARACTERS"` and a Russian message naming the actual problem ("имя" +
  "символ"), NOT containing the email-validation text.
- **AC-7 (regression)** `POST /api/users` with KC-side `EMAIL_INVALID` (defense-in-depth path)
  still → `400 VALIDATION` with the exact prior "email must be a valid email address" message,
  unaffected by the new branch inserted above it.
- **AC-8 (regression)** An ordinary two-word `display_name` (e.g. "Иван Петров") still creates
  `201` — the happy path (T-0741's own scope) is untouched.
- **AC-9 (web)** `mapUserError(400, {error:{code:'NAME_INVALID_CHARACTERS', message:'...'}})`
  returns `{field:'display_name', message: <server message>}`.

## 6. Live proof

§3 above IS the live proof (real KC 25.0.6, `t-0633-keycloak-1`, choros-registrar
client_credentials — the exact path `createHumanUser` itself uses). All 5 probed shapes recorded
verbatim; no orphan users left behind. The unit tests in `src/__tests__/admin-port.test.ts` (AP-9)
replay these EXACT live-observed body shapes through a local stub HTTP server (not the real KC —
proportional per the existing `AP-6`/`AP-8` convention for this file, which already stubs KC's
409 disambiguation the same way) — the live probe in §3 is what anchors those stub bodies to
reality rather than to a guess at KC's error shape.

## 7. Out of scope

- No change to `splitDisplayName` itself — the split algorithm is unaffected; this task is
  purely about honest error ATTRIBUTION when KC subsequently rejects the split result's
  characters.
- No attempt to pre-validate `display_name` characters client/server-side before calling KC
  (would require re-implementing KC's own `person-name-prohibited-characters` character set —
  T-0741's own doc already establishes KC as the authority on legal characters, not this
  codebase; duplicating that ruleset risks drifting from it).
- Self-registration (`src/core/register.ts`) does not pass `displayName` at all (T-0741 §6,
  unchanged) — this class of error cannot occur on that path.
