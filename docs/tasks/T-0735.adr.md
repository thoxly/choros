# ADR-T0735 (T-0654-b) — грид «Процессы» + доводка деталки

Спека: `docs/tasks/T-0735.spec.md`. Родитель-ADR: `docs/design/ADR-T0654-processes-split.md`.
Статус: `ready`. Только web (`web/src/**`). Сервер части A — контракт готов, НЕ трогаем.

## Решение (одним абзацем)

Секция живых инстансов в `screen-processes.jsx` переписывается со «скролл-щели» на серверно-фильтруемый
грид, потребляющий часть A: тулбар (поиск-debounce / селект определения / селект статуса / диапазон дат /
тумблер «мои») → query-параметры `GET /api/processes`; пагинация читает `{total,limit,offset}` и растёт
«Показать ещё». Стартер рисуется `<ActorChip>` по `starterName/starterType/starterId`. Деталка
(`screen-process-instance.jsx`) добирается: стартер именем в сайдбаре, «Связанные задачи» → `/inbox?instance=<id>`,
запись-источник поднята в строку заголовка ссылкой; инбокс сеет фильтр из `?instance=` URL. Чистая логика
грида (парс query, дебаунс, пагинация-состояние) — не в этой задаче нового ядра нужно (сервер = ядро);
UI-состояние держим в компоненте, повторяя проверенный паттерн инбокса (T-0653/T-0401).

## Почему НЕ переиспользуем `ListViewPanel`

Родитель-ADR это уже отверг: `ListViewPanel` завязан на `registry_def`/`schemaColumns`/типы полей записей —
адаптация под non-records source непропорциональна. Грид рендерится по СТАТИЧЕСКОМУ каталогу
`PROCESSES_VIEW_COLUMNS` (5 платформенных ключей) фиксированной честной раскладкой; сохранённые ЛИЧНЫЕ виды
процессов (колонки on/off) — отдельный follow-up. Плотность (comfortable/compact) персистится через тот же
`user_pref`-примитив, что и личный вид инбокса (T-0651/T-0653), ключ `processes.view` — honest-degrade
(нет префа → comfortable).

## Маппинг колонок каталога → ячейки (стабильные ключи → человеко-лейблы)

| ключ каталога | лейбл (видимый) | ячейка |
|---------------|-----------------|--------|
| `name`    | Процесс       | человеко-имя определения (`inst.name`) + маркер статуса |
| `process` | Текущий шаг   | `inst.node`/`inst.nodes` (concurrent-ветки T-0456), `<Mono>` |
| `status`  | Статус        | `<StatusChip>` |
| `started` | Запущен       | `inst.started` (`<Mono>`) |
| `actor`   | Кто запустил  | `<ActorChip type=starterType name=starterName id=starterId>` |

Плюс всегда-видимая колонка действия «Открыть» → `/processes/:id` (не в каталоге видов: не скрываемая,
иначе строку не открыть). Инстанс-UUID из грида УБРАН (анти-кейс: находят по имени заявки).
Дисамбигуатор заявки — `<RecordRef recordId=…>` под именем (резолвит title, ссылка), когда инстанс
запущен из записи (`recordId`).

## Фильтр по определению — источник опций

Селект определения показывает человеко-ИМЯ, фильтрует по `procKey` (`?definition=procKey`). Опции берём из
`GET /api/process-catalog` (`definitions[] = {name, process_key}`) — полный список определений тенанта, не
только тех, у кого инстанс на текущей странице. Это data-fetch для дропдауна, не рендер каталог-UI.

## Дебаунс / пагинация / гонки (паттерн инбокса)

- `q` дебаунсится 250мс (`setTimeout`); прочие контролы (definition/status/date/mine) — немедленный релоуд.
- Смена ЛЮБОГО фильтра сбрасывает `offset=0` (страница с нуля).
- Монотонный `loadSeq`-токен (T-0653 defect #11): поздний ответ на устаревший запрос отбрасывается —
  два in-flight релоуда не топчут друг друга.
- «Показать ещё»: `offset += limit`, ответ аппендится; привязан к текущему токену (полный релоуд отменяет аппенд).

## AC-B6 отложен в T-0654-c (осознанное отклонение)

Родитель-split велит «переехать каталог в часть C». Удаление секции каталога с /processes ДО постройки
её нового дома (отдельный экран зоны «Конструктор», часть C = T-0654-c) осиротило бы живой функционал:
список определений, «Настроить триггер» (единственный вход в binding-config), «Правила ветвления»
(единственный вход в DMN-редактор для определения). Порядок «B раньше C» существует ради deep-link C→B, а
НЕ ради преждевременного удаления. Поэтому B строит грид как ведущую секцию и ОСТАВЛЯЕТ
`ProcessCatalogSection` ниже без изменений; фактический переезд+удаление — часть C. Зафиксировано в handoff
как `deviations_from_adr`.

## Fitness-функции (машинно-проверяемые)

- **FF-UX-1 (anti-uuid).** Ни грид, ни деталка не рендерят сырой actor/record-id голым JSX-child. Стартер →
  `<ActorChip>`, запись → `<RecordRef>`. Гейт: `ci/checks/ux/anti-uuid-actor-render.sh` (REQUIRED).
- **FF-UX-2 (anti-case).** Нет кейс-констант в добавленных строках (слаги/имена процессов/домен-словарь).
  Гейт: `ci/checks/anti-case-lock.sh` + `detel-*`.
- **FF-UX-3 (jargon).** Нет `T-\d{3,}`/`telLinear`/кодов в ВИДИМОМ тексте (комментарии — можно).
  Гейт: `ci/checks/ux/ux-g5-jargon-denylist.sh`.
- **FF-UX-4 (no-fake-buttons).** Ни одной новой `aria-disabled`-кнопки без видимой причины; каждый
  enabled-контрол что-то делает (сеть/навигация/видимое изменение). Гейт: `ci/checks/ux/ux-g7-no-fake-buttons.sh`.
- **FF-UX-5 (theme-pairing).** Только `--chs-*` токены, kit-компоненты; обе темы читаемы. Гейт:
  `ci/checks/ux/ux-g2-theme-pairing.sh` (не трогаем tokens.css → зелёный по построению).
- **FF-B (грид ↔ сервер).** Тест: `?q/?status/?mine/?definition/?started_*/?limit/?offset` прокидываются в
  fetch; ответ `{total,limit,offset}` управляет «Показать ещё»; стартер-имя (не UUID) в строке.
- **FF-D (деталка).** Тест: стартер-имя через ActorChip (не UUID); «Связанные задачи» ведут `/inbox?instance=<id>`;
  запись-источник ссылкой в заголовке; инбокс сеет `?instance=` из URL.
