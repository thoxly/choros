# T-0764 — CI honesty: Flowable-gated db-tests actually run + T-0605 seed audit

Ci/observability, substrate. Follow-up from T-0760's nits: N1 (CI never runs
`fitness:db` with a live Flowable → `requireDbAndFlowable`-gated tests silently
skip in every automated run) + N2 ("~14 other db-tier test files" grep-matched
the same pre-T-0605 `role_assignment` seed shape T-0760 fixed — never
individually verified).

## 1. CI fix — new `db-flowable` job

**Root cause (confirmed by reading `.github/workflows/ci.yml` before any
change):** the `db` job pins its own `postgres:16` service and runs
`npm run fitness:db` (= `vitest run --dir ci/checks/db`), but starts NO
Flowable. The separate `flowable` job brings up `docker compose up -d postgres
flowable` and runs Flowable-specific smoke scripts, but never calls
`npm run fitness:db`. Five `ci/checks/db/*.db.test.ts` files gate their live
assertions behind a local `requireDbAndFlowable()` helper:

```ts
function requireDbAndFlowable<T>(fn: () => Promise<T>): () => Promise<T | void> {
  return async () => {
    if (!hasDb) { console.log('[skip] DATABASE_URL not set'); return; }
    if (!flowableReachable) { console.log('[skip] Flowable not reachable...'); return; }
    return fn();
  };
}
```

In the `db` job `flowableReachable` is always `false` → these five files have
**never executed a single assertion in any automated GitHub Actions run**:

- `ci/checks/db/engine-drive-generic.db.test.ts`
- `ci/checks/db/engine-drive-completedby.db.test.ts`
- `ci/checks/db/detel-base-task-role.db.test.ts`
- `ci/checks/db/detel-rollup-to-variables.db.test.ts`
- `ci/checks/db/formula-derived.db.test.ts`

**Fix:** a new job `db-flowable` (`.github/workflows/ci.yml`, inserted
between `flowable` and `stack`) that:

1. Brings up `docker compose up -d postgres flowable` — the SAME compose
   substrate the `flowable`/`stack`/`kc`/`deploy-acceptance` jobs already use
   (schema `flowable` is created by `config/postgres/002-flowable-schema.sql`
   on first Postgres init — no new provisioning needed).
2. Waits for Flowable readiness (`ci/checks/flowable/wait-ready.sh`, its own
   120s internal timeout — covers the ~30-60s Flowable JVM cold-start).
3. Runs migrations twice (apply + idempotency re-run, matching the `db` job's
   own pattern) and `npm run fitness:db:setup-template` (the T-0147
   db-isolation harness's per-test-clone template).
4. Runs the **full** `npm run fitness:db` suite — not a hand-picked file
   list. A hardcoded "these are the Flowable-gated files" whitelist would
   itself rot the moment a new `requireDbAndFlowable()` test is added and this
   workflow file isn't touched to match — exactly the silent-skip failure
   class this task exists to close. The ~175 non-Flowable-gated files simply
   re-run redundantly (cheap, no Flowable dependency); only the 5 files above
   newly execute for real.
5. Stops both services (`docker compose stop flowable postgres`).

**Deliberately NOT added to `deploy-dev.needs` yet** — same advisory-first
discipline the `deploy-acceptance` job already documents (T-0274 EXACT
FLIP-CONDITION): a job must be proven green in the actual GitHub/self-hosted
runner before it can safely gate the dev auto-deploy. It binds the same fixed
compose ports (55432/8082) as `flowable`/`stack`/`kc`/`deploy-acceptance` —
safe only because the self-hosted runner already serializes job execution
(T-0703). A follow-up task should flip it into `deploy-dev.needs` once proven
green on the actual runner.

**Verified locally** (not just written): stood up an ISOLATED, fully fresh
`docker compose` stack (`COMPOSE_PROJECT_NAME=t0764fresh`, ports 55499/8099 —
not the shared long-running dev containers) to reproduce exactly what a fresh
CI runner sees, ran migrations + template setup + the full sequence the new
job specifies. See §2 for what that run found.

`ci/checks/ci-workflow-lint.sh` — PASS (unchanged; the new job doesn't affect
any of the 5 checks it runs: `db` job still exists, still pins `postgres:16`,
still runs the migration runner ≥2×, still runs the live db probe suite,
`vitest.config.js` worktree-exclusion unaffected).

## 2. What the new job's first real run found (NOT a seed-hygiene bug — a
   second, independent class of test staleness)

Running `ci/checks/db/detel-rollup-to-variables.db.test.ts` against a real
Flowable for the first time (it has silently skipped since T-0575/T-0603)
surfaced a **genuinely flaky, previously-invisible test-fixture bug** —
unrelated to the T-0605 `role_assignment` pattern in §3 below.

**Symptom:** 0-3 of the file's 3 tests fail, non-deterministically across
runs (observed 1/3, 3/3, and 2/3 failures across three consecutive RED-control
runs — see §2.3).

**Root cause #1 (registry-primary-ordering coin-flip):**
`getOnCreateBinding` (T-0606, migration 122,
`src/db/binding-trigger-dao.ts:145-184`) resolves a `NULL
trigger_registry_id` binding against "the application's primary registry" —
defined as `ORDER BY rd.created_at ASC, rd.id ASC LIMIT 1` over the
application's non-system registries. This test's `seedChildRegistry` /
`seedParentRegistry` helpers both insert with a **literal `created_at = 0`**
— every registry in a given test ties on `created_at`, so the tiebreak falls
through to `id ASC`: whichever of the two registries' random `uuid()`s sorts
alphabetically first becomes "primary". The test always posts records against
the PARENT registry and always leaves `seedOnCreateBinding`'s
`trigger_registry_id` at its old default (`NULL`) — so whether the binding
actually matches depends entirely on a coin flip of two random UUIDs. When
the CHILD registry wins the draw, `getOnCreateBinding` returns `null`, the
on_create trigger is silently skipped (by design — "if flowable is not
configured, skip silently"; here it's "if no matching binding", same
honest-degrade path), the record is created (`201`) but **no process ever
starts** — `resolveInstanceIdForRecord` then throws "no process.started audit
event found".

**Root cause #2 (field-mapping key mismatch, T-0603 embedded flavor only):**
the shared `seedOnCreateBinding` helper hardcodes
`field_mapping = { amount: 'totalAmount' }`. That matches the child-records
rollup flavor (`seedParentRegistry`'s field is named `totalAmount`) but NOT
the embedded rollup flavor added later by T-0603 (`seedEmbeddedRollupRegistry`'s
field is named `total`). For the embedded test, `projectEngineVariables` reads
`projectionSource['totalAmount']` — always `undefined` on that registry — so
the JUEL gateway condition `${amount > 500000}` is always `false`, and the
instance always takes the DEFAULT branch regardless of the actual (correctly
summed) rollup value.

**Both are TEST-FIXTURE bugs, not product bugs** — confirmed by reading
`src/http/records.ts`'s on_create block, `src/db/derived-fields-dao.ts`
(`computeAllDerivedFields`/`computeEmbeddedRollup`), and `src/core/rollup-contract.ts`:
the derived-field compute and engine-variable projection code is correct and
unchanged; the test's OWN seed helpers drifted out of sync with T-0606's later
registry-scoping contract and with the newer embedded-rollup field-naming
convention. This is the same *species* of defect as T-0760's finding (a test
correct at authoring time, silently invalidated by a LATER, unrelated change
to canonical semantics, never re-verified because the whole file always
skipped in CI) — just a different mechanism than the `role_assignment`
pattern.

**Fix** (`ci/checks/db/detel-rollup-to-variables.db.test.ts`): `seedOnCreateBinding`
now takes an explicit `triggerRegistryId` parameter (required — no more NULL/
coin-flip inference) and an explicit `fieldKey` parameter (defaults to
`'totalAmount'`, matching the child-records flavor; the T-0603 call site now
passes `'total'`). This mirrors the canonical idiom already established in
`ci/checks/db/approval-registry-guard.db.test.ts`'s own `seedOnCreateBinding`
(itself the T-0606 test), which already takes an explicit
`triggerRegistryId: string | null` parameter.

## 3. Seed audit — the "~14 other db-tier files" from T-0760's N2 nit

T-0760's `seedApproverGrant` bug: `role_assignment` seeded with
`proposed_by = actorSlug` (a non-NULL value) and NO `confirmed2_by` column at
all. T-0605's canonical assignment-active predicate
(`src/db/grants-dao.ts:515-525`, `getRoleSlugsForActor`):

```sql
confirmed_by IS NOT NULL AND (confirmed2_by IS NOT NULL OR proposed_by IS NULL)
```

reads such a row as "a dual-control proposal still awaiting its second
signature" — PDP-inactive by design. T-0760's reviewer grepped `~14 other
db-tier test files` matching a loose pattern (`proposed_by, confirmed_by,
created_at` column list with no `confirmed2_by`) and flagged them
unverified.

**Method:** grepped every `ci/checks/db/*.ts` file for
`INSERT INTO choros.role_assignment` (58 files matched, a superset of the
reviewer's loose ~14 estimate), then read each INSERT's exact column list +
VALUES clause to classify it against the T-0605 predicate.

### 3.1 Classification

| Class | Count | Example shape |
|---|---|---|
| **Honest** — `proposed_by` explicit `NULL`, or the column omitted entirely (defaults NULL) | 44 | `T-0750-inbox-detail-authority.db.test.ts` (the эталон), `records_delete.db.test.ts` post-fix, etc. |
| **Deliberate dual-control fixture** — `proposed_by` intentionally parametrized to seed a semi-confirmed row, because THAT is the specific thing under test (dual-control approve/reject gate, eligibility-of-pending-proposal) | 6 | `grants-dao-dual-control.db.test.ts`, `rights-change-requests-deactivated-approver.db.test.ts` (`seedPendingAssignment`, explicit doc comment "A SEMI-CONFIRMED role_assignment"), `rights-eligibility-sew.db.test.ts` (`proposed: boolean` param), `rights-overview.db.test.ts` (full 3-state fixture), `role-assignment.test.ts` AC-11 (schema-nullability test, not a PDP test) |
| **Stale (pre-T-0605 shape, matches T-0760's exact bug pattern)** | **7** | see §3.2 |
| Not applicable (production `src/*.ts`, not a test seed) | 1 | excluded from count |

### 3.2 The 7 stale seeds — found, fixed, and why they were harmless (unlike T-0760's)

All 7 share IDENTICAL boilerplate — literally byte-for-byte the SAME
pre-T-0760 shape `engine-drive-generic.db.test.ts` had:

```sql
VALUES ($1, $2, $3::uuid, $4, $5::jsonb, NULL, NULL, 'genesis', $6::text, $6::text, $6::text, 0, 0)
--                                                              proposed_by=$6  confirmed_by=$6, no confirmed2_by column
```

1. `ci/checks/db/actor-resolve-seeded-persona.db.test.ts`
2. `ci/checks/db/app_secret_store.test.ts`
3. `ci/checks/db/applications_delete_cascade.db.test.ts`
4. `ci/checks/db/approval-registry-guard.db.test.ts`
5. `ci/checks/db/llm_connection_registry.test.ts`
6. `ci/checks/db/records_delete.db.test.ts`
7. `ci/checks/db/registry_def_cascade_relation.db.test.ts`

**Why these did NOT cause a 403/skip/false-green (unlike T-0760's case):**
all 7 grant the role slug `'tenant-owner'` specifically to make the seeded
actor a genesis owner. The ONLY consumer of that specific row is
`isGenesisOwnerForTenant` (`src/db/org.ts:747-774`):

```sql
WHERE ... AND r.slug = 'tenant-owner' AND ra.confirmed_by IS NOT NULL AND ...
```

This owner short-circuit checks **only `confirmed_by IS NOT NULL`** — it does
NOT reference `confirmed2_by` or `proposed_by` at all (unlike
`getRoleSlugsForActor`, the function T-0760's bug actually went through).
So the stale shape was cosmetically non-canonical but functionally inert for
these 7 files: `applications_delete_cascade.db.test.ts` even carries an
explicit comment ("Role slug MUST be exactly 'tenant-owner' —
isGenesisOwnerForTenant keys on it") confirming this was the intended
consumer all along.

**Empirical confirmation (not just code-reading):** ran all 7 files' 56 tests
against a live Postgres+Flowable BEFORE touching the seed shape — 56/56
GREEN. Applied the fix (`proposed_by = NULL`, matching the
`T-0750-inbox-detail-authority.db.test.ts` эталон exactly). Ran again — still
56/56 GREEN, byte-identical outcome. This is the honest "RED control" for
these 7: there is no RED to control for, because `isGenesisOwnerForTenant`
never read the field that was wrong. The fix is still applied because the
non-canonical shape is a **latent landmine** — if `isGenesisOwnerForTenant`
is ever tightened to the canonical T-0605 predicate (a very plausible future
refactor, since every OTHER assignment-activity check in the codebase already
uses it), these 7 seeds would silently start 403'ing with no code change on
their end, reproducing exactly the T-0760 class of bug.

**Separate, deeper finding surfaced by this audit (NOT fixed here, flagged for
follow-up):** `isGenesisOwnerForTenant` itself does not enforce the T-0605
dual-control predicate at all. If the `'tenant-owner'` role assignment can
EVER legitimately go through the two-approver proposal workflow in production
(i.e. `proposed_by` gets set with `confirmed2_by` still NULL, meaning "one of
two required approvers has signed off on making X the owner"), this function
would treat that PENDING, single-signature proposal as an ALREADY-ACTIVE
owner grant — a genesis-owner privilege-escalation gap distinct from anything
T-0605/T-0760/T-0764 touched. Whether this is reachable depends on whether
the product ever proposes `'tenant-owner'` through the dual-control UI path
(not established either way here) — this is a product-security question that
deserves its own investigation, not a seed-hygiene fix, and is out of scope
for T-0764.
