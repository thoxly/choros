# ADR T-0722 — видимость LIST-строки наследуется от READ-видимости записи-источника

- **Статус:** реализовано (impl-фаза, coder)
- **Контекст:** T-0714 (архитектурная оценка, ратифицирована ADR-T0570 +
  доктрина F2), P2 из follow-up-списка §7 п.2; T-0721 (P1, DETAIL-гейт, база
  этой ветки)
- **Область:** `GET /api/processes` (LIST), фаза 2 из 3

## 1. Решение

Присутствие инстанса в `GET /api/processes`'s `instances[]` теперь = READ-
видимость записи-источника инстанса (`recordId`), решается ЕДИНЫМ authority-
путём — `isRecordReadable` (T-0570) через `filterProjectionsByReadVisibility`
(новая батчевая обёртка над той же математикой, что `isInstanceDetailVisible`
T-0721 уже использует для DETAIL).

Реализация — две точки (не четыре, в отличие от T-0721 — `server.ts` и
`process-start.ts` НЕ тронуты, см. §2.1):

1. **`src/http/process-projection.ts`** — новая функция
   `filterProjectionsByReadVisibility(pool, tenantId, projections, grants,
   ancestry, nowMs)`: собирает DISTINCT UUID-формы `recordId` по входному
   массиву, батчево резолвит их ancestry ОДНИМ SQL-запросом
   (`loadRecordRowAncestryBatch`, `withTenant`, `id = ANY($2::uuid[])`),
   фильтрует массив: record-less → оставить; recordId не резолвится →
   отбросить (honest-deny); иначе → `isRecordReadable(...)`.
2. **`src/http/processes.ts`** — LIST-хендлер (`GET /api/processes`)
   вызывает `startDeps.resolveReadVisibility(...)` →
   `filterProjectionsByReadVisibility(...)` **ДО** `overlayDetailLiveSteps`
   (экономит live-engine round-trip на отброшенных инстансах) и до сборки
   ответа. `?record=`-фильтр (T-0708) применяется, как и раньше, ПОСЛЕ.

## 2. Развилки и обоснование

### 2.1 Нет изменений в `server.ts` / `process-start.ts`

**Решение:** `resolveReadVisibility` (тип `ProcessReadVisibilityResolver`,
поле на `StartInstanceDeps`) уже существует и уже wired в `server.ts` —
T-0721 закрыла "wiring asymmetry" (`registerProcessesRoutes` не получало
резолвер) ОДИН РАЗ для ВСЕГО `startDeps`-объекта, который ОБА хендлера
(`GET /api/processes` и `GET /api/processes/:id`) уже разделяют.

**Почему:** резолвер — per-request функция `(actorSlug, tenantId, nowMs) =>
{grants, ancestry}`, не привязана к конкретному роуту. LIST-хендлер просто
вызывает ТОТ ЖЕ инжектированный резолвер, что DETAIL уже вызывает — нулевая
новая инфраструктура, нулевой риск рассинхрона composition (T-0714 §3
"registerProcessesRoutes never got a resolver" был симптомом ОТСУТСТВИЯ
инжекции на весь объект deps, не отсутствия per-route wiring; T-0721 уже
исправила корень).

### 2.2 Батч, не N+1 (расхождение с DETAIL's `loadRecordRowAncestry`)

**Решение:** `filterProjectionsByReadVisibility` делает ОДИН
`SELECT ... WHERE id = ANY($2::uuid[])` для ВСЕХ recordId разом, а не
вызывает `isInstanceDetailVisible` (и, транзитивно, `loadRecordRowAncestry`)
в цикле по каждому инстансу списка.

**Почему:** DETAIL обрабатывает РОВНО ОДИН инстанс за запрос — 1 SQL-запрос
приемлем. LIST обрабатывает до 200 (внутренний cap `readEvents`) — цикл из
до-200 отдельных SELECT на запрос был бы явным N+1-паттерном, нарушающим
принцип "гранты/ancestry резолвятся ОДИН РАЗ, дальше — O(1)-проверка",
который `records.ts`'s LIST READ-PDP и `isRecordReadable`'s собственный
doc-comment ("Caller resolves grants/ancestry ONCE per HTTP request; this
function is the O(1)-per-row check") уже устанавливают как норму. Батчинг
здесь — тот же паттерн, что `resolveDefinitionNames`/`resolveActorKinds` уже
применяют в ЭТОМ ЖЕ модуле (`process-projection.ts`) для СВОИХ N-элементных
резолвов — не новый приём, продолжение существующей дисциплины файла.
`isInstanceDetailVisible` (DETAIL) остаётся НЕТРОНУТОЙ — не рефакторена в
термин батчевой функции, чтобы не расширять диф T-0721 сверх необходимого
(роль-правило #5, соразмерность); обе функции реюзят ОДНУ И ТУ ЖЕ
`isRecordReadable`, отличается только форма ancestry-резолва (1 vs N).

### 2.3 Фильтр — не "SQL WHERE на предикате", а батч + чистая in-memory фильтрация (осознанное отклонение от буквы задачи)

**Задача просила:** "фильтр в SQL WHERE (не пост-фильтр по уже-собранной
странице)".

**Решение:** предикат `isRecordReadable` (containment-математика лattice:
`isNarrowerOrEqual`/`isEffective` над org/resource-ancestry) — НЕ SQL-
выразим НАПРЯМУЮ (это не колоночное условие, это графовый обход по
`AncestryOracle`, включающий org-иерархию). `records.ts`'s ЕДИНСТВЕННЫЙ
существующий прецедент READ-PDP на LIST (T-0570, `records.ts:1975-1993`)
делает РОВНО ТО ЖЕ САМОЕ: "filter the already-loaded page ... — no per-row
DB call" (дословный комментарий в коде) — т.е. пост-фильтрация
СОБРАННОГО результата, а не WHERE-предикат.

**Что реально закрывает букву задачи:** беспокойство задачи было не про
"WHERE vs filter()" синтаксически, а про КОНКРЕТНЫЙ класс бага — T-0710
(`process-projection.ts:917-925`, тот же файл), где пост-фильтр ПОСЛЕ
`ORDER BY ... LIMIT`-окна давал ложноотрицательный результат для инстанса,
чьи строки физически не попали в page. Этот риск здесь **закрыт иначе**:
(а) `GET /api/processes` не имеет клиентской пагинации/count вовсе — нет
второго числа, которое могло бы рассинхрониться с фильтрованным списком
(см. spec §4.1); (б) внутренний `readEvents`'s `limit=200`-cap —
пред-существующий, независимый от этой задачи, не ухудшается фильтром
(фильтр сужает РЕЗУЛЬТАТ фолда, не участвует в том, ЧТО фолд туда положил).
Т.е. дух требования (a)/(b) — "числа, которые видит клиент, должны отражать
ТОЛЬКО видимое, не всё" — выполнен буквально: единственное число, которое
клиент видит (`instances.length`), вычисляется ПОСЛЕ фильтра. Буква "SQL
WHERE" — нет (архитектурно невозможна без переписывания `isRecordReadable`
в SQL, что противоречило бы NF-5 "единая authority-математика"); задокумен-
тировано как осознанное, а не молчаливое отклонение (роль-правило #4).

### 2.4 Record-less инстансы — не сужены (симметрично Фазе 1)

Идентично T-0721 §2.2: `recordId === undefined` → инстанс остаётся видимым
безусловно. Explicit-launch (`/api/processes/start`) инстансы не имеют
process-definition-scoped read-гранта в латтисе сегодня (Фаза 3, `could`,
вне объёма обеих задач).

### 2.5 Malformed recordId — pre-filtered, не отдан на volNGE Postgres cast-ошибку

**Решение:** `filterProjectionsByReadVisibility` пропускает через
`UUID_RE.test(v)` (уже существующий в модуле) ПЕРЕД тем, как класть recordId
в батчевый `ANY($2::uuid[])`-запрос.

**Почему:** DETAIL's `loadRecordRowAncestry` НЕ делает эту пре-валидацию —
приемлемо, т.к. ошибка `SELECT` для ОДНОГО инстанса ловится
per-request try/catch DETAIL-хендлера и деградирует к честному 404 для
ТОЛЬКО ЭТОГО запроса. Для LIST тот же необработанный cast-ошибка на ОДНОЙ
плохой строке уронила бы batched-SELECT ЦЕЛИКОМ — то есть ВЕСЬ список
пропал бы из-за одной legacy/malformed строки (не honest-degrade, а полный
отказ поверхности). Пре-валидация избегает этого — non-UUID recordId
трактуется как "не резолвится" (honest-drop), симметрично отсутствующей
записи, без похода в БД.

  НОВЫЙ) — LIST-хендлер (`GET /api/processes`, отличный от `:id`-роута)

  gate-free LIST-хендлер, (b) `pg`-импорт.
- **FF-INST-VIS-4** (`ci/checks/process-list-tenant-scope-additive.sh`,
  НОВЫЙ) — READ-PDP предикат — ДОПОЛНИТЕЛЬНЫЙ `AND` внутри tenant-скоупа:
  вызов `filterProjectionsByReadVisibility(` идёт ПОСЛЕ
  `listInstanceProjections(` в исходном порядке хендлера (сужает, не
  заменяет); `loadRecordRowAncestryBatch` сам tenant-scoped (`withTenant` +
  явный `tenant_id = $1`). `--self-test` сажает: (a) фильтр без
  предшествующего tenant-scoped фетча, (b) батчевый SELECT без tenant_id.
  Живой (live-PG) регресс: актор тенанта A с широким READ-грантом не видит
  инстанс тенанта B в LIST (`ci/checks/db/processes-read-visibility.db.test.ts`).

## 4. Отклонения от постановки задачи

Одно, задокументированное явно (§2.3): фильтр реализован как батч + чистая
in-memory `isRecordReadable`-фильтрация над уже tenant-scoped результатом,
не как SQL `WHERE`-предикат на самой containment-математике — та же
архитектура, что `records.ts`'s T-0570 READ-PDP на LIST уже использует
(единственный существующий прецедент в кодовой базе), и единственная
архитектурно согласованная опция без дублирования authority-математики в
SQL (NF-5). Требование (b) ("пагинация/счётчики после фильтра") выполнено
буквально — единственное число, которое видит клиент (`instances.length`),
вычислено после фильтра; требование (a) о T-0710-классе бага (LIMIT-окно
скрывает реально существующий ряд) не применимо — не введено этой задачей и
не ухудшено ей (см. spec §4.1).

Нет отклонений от оценки T-0714 (следует опции (c), Фаза 2, включая явно
зафиксированные ограничения — record-less fallback, отсутствие
process-definition-scoped гранта).
