## 1. The vacuity, exactly

FF-5's router.ts branch (lines 46-58, unchanged by this task):

```bash
if git diff --quiet origin/dev -- src/http/router.ts 2>/dev/null; then
  echo "  [OK] src/http/router.ts unchanged relative to origin/dev"
else
  # If origin/dev doesn't exist (local worktree), check against HEAD of base
  if git diff --quiet HEAD -- src/http/router.ts 2>/dev/null; then
    echo "  [OK] src/http/router.ts unchanged in this branch"
  else
    echo "  FAIL: src/http/router.ts has been modified (must not be touched, AC-19)" >&2
    FAIL=1
  fi
fi
```

The comment claims the inner `git diff HEAD` fallback exists for the case *"origin/dev
doesn't exist (local worktree)"*. But bash's `if`/`else` cannot distinguish **why** the
outer `git diff --quiet origin/dev` returned non-zero — it merges two different causes
into the same `else` branch:

1. `origin/dev` is genuinely unreachable (unknown-revision error, exit 128) — the
   documented case.
2. `origin/dev` **is** reachable and the diff **is** genuinely non-empty (exit 1) — i.e.
   router.ts really was changed relative to the branch's base. This is exactly the
   violation FF-5 exists to catch.

Both funnel into the same fallback: `git diff --quiet HEAD -- src/http/router.ts`. This
compares the **working tree against its own HEAD** — i.e. only *uncommitted* changes.
Once a router.ts edit is **committed**, the working tree equals HEAD by definition, so
this fallback is *always* quiet, regardless of what changed relative to `origin/dev`/`dev`.
Case 2 is therefore vacuous: the one case where the outer check correctly detected a real
violation is exactly the case where the fallback silently un-detects it.

This matches T-0763's own `pr-handoff.json` observation (line 29, `fitness_gates_run`):
FF-5 *"FAIL while uncommitted... PASS after commit (falls through to its own
working-tree-vs-HEAD fallback, which is trivially empty once committed)"* — documented
there as the mechanism that let router.ts edits land, not yet recognized as a security
gap in its own right. T-0763's spec.md §2.1 traced the same fallback letting four prior
additive changes through (T-0072/T-0109/T-0518/T-0573) — none of those are malicious, but
the mechanism does not distinguish additive-and-reviewed from anything else once
committed.

## 2. Scope decision: (a) fix the branch, not (b) drop it

FF-5 (`ci/checks/worker-auth-public-surface.sh`) is registered once in `npm run fitness`
(`package.json`) and, on a clean tree, checks **four** independent invariants (AC-19):

1. `DEV_USER_HEADER` exported from `src/http/auth.ts`
2. `registerExternalWorkerRoutes` exported from `src/http/externalWorker.ts`
3. `registerAuthRoutes` exported from `src/http/auth.ts`
4. `createServer` exported from `src/server.ts`
5. `src/http/router.ts` unchanged relative to `origin/dev` (the vacuous one)

Only #5 is about router.ts. `ci/checks/agent-hire-frozen-additive.sh` (FF-HIRE-4) *also*
checks router.ts, but under a **different, weaker** policy:

| | FF-5 (AC-19, this file) | FF-HIRE-4 (T-0042) |
|---|---|---|
| router.ts policy | must be **fully unchanged** | **additive-only** (0 deleted lines; new lines allowed) |
| BASE resolution | `origin/dev` direct diff, vacuous `HEAD` fallback | `git merge-base HEAD origin/dev` → `dev` → `HEAD~1` fallback chain |
| Purpose | public API surface frozen (AC-19) | agent-hire routes may be *added* to router.ts/auth.ts without deleting existing dispatch |

FF-HIRE-4 explicitly *permits* additions to router.ts (that is its entire purpose — see
its own header: *"For router.ts and auth.ts (allowed additive additions): assert deleted
lines == 0"*). If FF-5's router.ts branch were simply removed in favor of FF-HIRE-4 (option
b), the net effect would be a **silent weakening** of AC-19: a task could add new route
registrations to router.ts (satisfying FF-HIRE-4's 0-deletions rule) and no gate would any
longer enforce "must not be touched at all." That is a reclassification of what AC-19
means, not a additive-only cleanup — out of scope for this task, and not requested by the
T-0763 finding (which flagged the vacuity, not the router.ts-unchanged policy itself).

**Decision: (a).** FF-5 guards three invariants FF-HIRE-4 knows nothing about, and its
router.ts invariant is strictly stronger than FF-HIRE-4's — so FF-HIRE-4 does not subsume
it. The fix targets only the vacuous fallback.

## 3. Fix: an additive, authoritative merge-base check

`worker-auth-public-surface.sh` line 2 (`# FF-5 (static-now, AC-19): ...`) carries no
`T-XXXX` header — a legacy, pre-T-0146 check. Under `frozen-checks-immutable.sh`
(FF-FCI11: *"Чек без T-ID заголовка (legacy) считается чужим → FAIL"*), it is treated as
foreign to every task, including this one, so any edit needs a sanction. Because
`git merge-base`-correctness is a clarification, not a weakening (it only makes the
existing "router.ts unchanged" invariant fire when it should, never loosens it), this is
handled as an **auto_additive** sanction (T-0232), not a founder-class one — consistent
with the task's own framing (*"уточнение merge-base = не ослабление, additive-санкция
ок"*) and with precedent (T-0740/T-0751/T-0759 auto_additive-thawed peer `ci/checks/*.sh`
files under the same class).

Given `auto-sanction-additive.sh`'s A-1 rule (every non-empty BASE_REF line, **including
comments**, must be present byte-identical in HEAD — no line may be deleted or mutated,
only new lines appended), the fix cannot rewrite the buggy fallback in place. Instead, a
new, independent block is **appended** after the existing (untouched) router.ts branch:

```bash
FF5_ROUTER_BASE=$(git merge-base HEAD origin/dev 2>/dev/null \
  || git merge-base HEAD dev 2>/dev/null \
  || git rev-parse HEAD~1 2>/dev/null \
  || echo "")
if [ -n "${FF5_ROUTER_BASE}" ]; then
  if git diff --quiet "${FF5_ROUTER_BASE}" -- src/http/router.ts 2>/dev/null; then
    echo "  [OK] src/http/router.ts unchanged relative to merge-base (T-0766 authoritative check)"
  else
    echo "  FAIL: src/http/router.ts has been modified relative to merge-base (must not be touched, T-0766 authoritative check)" >&2
    FAIL=1
  fi
else
  echo "  WARN: T-0766 authoritative merge-base check could not resolve a base commit; relying on the legacy check above" >&2
fi
```

The `BASE` resolution mirrors FF-HIRE-4's exact fallback chain (`merge-base HEAD
origin/dev` → `merge-base HEAD dev` → `HEAD~1`) — the reviewer-confirmed-correct pattern
named in the task brief. `FAIL` is a script-global variable set (never reset to 0)
anywhere in this file; it is checked once, at the very end, after every branch has run.
Because this new block runs independently and sets `FAIL=1` on its own finding, the
legacy block immediately above it can keep printing a (possibly vacuous) `[OK]` — it no
longer matters, since `FAIL` is a monotonic OR across both blocks. The legacy block is
deliberately left as dead-but-harmless weight rather than restructured, because
restructuring it (e.g. making the outer `if` route to the new BASE) would require
deleting or editing its existing lines, which A-1 forbids under an auto_additive sanction.

**Verified additive:** `git diff <BASE_REF> HEAD -- ci/checks/worker-auth-public-surface.sh`
is 24 insertions, 0 deletions (`grep -c '^-[^-]'` = 0). `ci/checks/auto-sanction-additive.sh
--verify T-0766 ci/checks/worker-auth-public-surface.sh <BASE_REF> <sanction-json>` passes
A-1..A-4 + attestation (§5).

## 4. Proof: vacuity → honesty (live, on this branch)

Reproduced **before** any fix was applied (baseline `095ae0d2`, clean gate PASSes on a
clean tree first):

```
$ echo '// T-0766-PROOF-BEFORE: temporary test line' >> src/http/router.ts
$ git add src/http/router.ts && git commit -m "..."
$ bash ci/checks/worker-auth-public-surface.sh
  [OK] src/http/router.ts unchanged in this branch     # <- vacuous
[FF-5] PASS: all public API surface checks passed.
$ echo $?
0
```

`origin/dev` **was** reachable in this worktree (`git rev-parse origin/dev` resolves to
the same commit as `dev`, the branch's own merge-base) — so the outer check correctly
detected the diff and fell into the `else`; the message even flipped from *"unchanged
relative to origin/dev"* to *"unchanged in this branch"*, proving the fallback branch
executed. It then vacuously passed anyway. The proof commit was reverted
(`git reset --hard 095ae0d2...`) before implementing the fix.

Reproduced **after** the fix (commit `566cb66f`, same exact probe):

```

$ git add src/http/router.ts && git commit -m "..."
```
