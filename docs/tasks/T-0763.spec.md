## 1. Problem (1): router.ts masks non-HttpError

`Router.dispatch()` has three sites where a caught exception is checked
`instanceof HttpError` and, on the `else` branch (anything NOT an `HttpError` —
a genuine bug, a driver-level error like Postgres `22P02`, a null-deref, etc.),
was sending `sendErrorEnvelope(res, 500, "INTERNAL", "internal server error")`
with **zero server-side trace**:

1. the async route-handler catch (`result.catch(...)` inside the main matched-route branch),
2. the fallback handler's **sync** throw catch,
3. the fallback handler's **async** rejection catch.

T-0249's CE-1 live-wire (wiring `buildCompletionEffectRegistry` into the
production composition root) hit exactly this: `runIssueKey` wrote a slug into
a UUID-typed `actor_event` column, Postgres threw `22P02 invalid_text_representation`,
and the ONLY thing that reached anyone was `{error:{code:"INTERNAL",message:"internal
server error"}}` on the HTTP response — no stack, no message, nothing in the
server log. The bug was found only because the reviewer ran a **standalone
`tsx` repro script** that called `runCompletionEffect` directly, bypassing the
router entirely. In production this class of bug (any non-HttpError thrown
inside a handler) would have been diagnosable only by reproducing it outside
the HTTP path — the router actively discarded the one piece of evidence that
would have pointed straight at the cause.

## 2. Fix (1): `logUnexpectedError` — server log only, client response unchanged

A new function `logUnexpectedError(method, pathname, err)` (added just above
the `Router` class, `src/http/router.ts`) is called at all three sites,
**immediately before** the existing `sendErrorEnvelope(res, 500, "INTERNAL", ...)`
call — never instead of it, never delaying it:

```ts
function logUnexpectedError(method: string, pathname: string, err: unknown): void {
  const detail = err instanceof Error ? (err.stack ?? err.message) : String(err);
  console.error(`[router] unhandled non-HttpError on ${method} ${pathname}: ${detail}`);
}
```

- **HttpError path is untouched** — no new logging on the expected-error
  branch (avoids log-spam on ordinary 4xx/409/etc. domain errors; pinned by
  new tests).
- **Client-facing response is byte-identical to before**: still
  `{error:{code:"INTERNAL",message:"internal server error"}}`, HTTP 500. The
  logging call reads nothing from `res` and writes nothing to it — it cannot
  change what the client receives, by construction (it runs strictly before
  the pre-existing `sendErrorEnvelope` call, which is untouched).
- **console.error** matches the pre-existing codebase convention (grep across
  `src/`: `externalTaskBridge.ts`, `timer-firing-loop.ts`, `assistant.ts`,
  `inbox.ts`, `process-gen-loop.ts`, `agent-dispatch-loop.ts`, ... all use bare
  `console.error`/`console.warn` for non-fatal/diagnostic server-side logging;
  no dedicated logger port exists in this codebase). `npx eslint` flags it as
  the same pre-existing `no-console` **warning** (not error) every one of
  those call sites already carries — 0 new eslint errors.

### 2.2 What is logged, and why it does not leak

Only three inputs ever reach `logUnexpectedError`:

- `method` — the already-uppercased HTTP method (`GET`, `POST`, ...), computed
  earlier in `dispatch()` from `req.method`.
- `pathname` — the URL **with the query string stripped** (`dispatch()`
  already splits on `?` before routing; the query string, which is the part
  most likely to carry PII/tokens in a URL, is never passed to the logger).
- `err` — whatever the handler threw. If it is an `Error`, its own
  `.stack`/`.message`; if not, `String(err)`.

**Not logged, ever**: request headers (never read), request/response body
(never read — `readJsonBody`/`readRawBody` are separate call sites the
handler itself invokes, `logUnexpectedError` has no access to the buffered
body), cookies, auth tokens. This mirrors exactly what the task's no-leak
class of gates already enforces elsewhere (`ci/checks/user-mgmt-no-secret-leak.sh`
FF-583-7, `ci/checks/precheck-secret-custody.sh` FF-LP-8): only route +
error-shape diagnostics, never payload contents. A handler that itself puts a
secret into an `Error`'s `.message` (e.g. embedding a raw password in a thrown
error) would leak it via this log exactly as it always would have leaked via
any other `console.error` call in that handler — this task does not introduce
a new secret-bearing surface, it only stops discarding what a thrown `Error`
already carries. All existing FF-583-7/FF-LP-8/FF-25/FF-1 gates re-verified
green (§4).

## 3. Evaluation (2): canonicalize slug→UUID, or keep the adapter?

**Recommendation: keep the adapter, do not canonicalize now.** Canonicalizing
is real but not small, and the current fail-closed adapter is a defensible,
already-reviewed (T-0249 r2, judge-approved) permanent shape — not a stopgap
that obviously needs unwinding.

### 3.1 What's actually going on

- `src/core/actor-event.ts`'s `ActorEventInput`/`ActorEventWriter` contract is
  explicit and has been frozen since T-0019: `actor` = "the performer
  (**employee.id**, NOT NULL)", `roleAtEvent` = a role id. The production
  writer (`PgSodSource`, migration 013/018) types these columns UUID. This is
  the canonical contract — it was never ambiguous.
- `runIssueKey` (`src/runtime/customer-onboarding/issue-key.ts`, T-0244) uses
  `subject.subjectId` for **two** purposes at once: (a) the PDP `resolveFor`
  subject identity, and (b) the `actor`/`roleAtEvent` value it hands to
  `appendActorEvent`. In every caller today `subject.subjectId` is populated
  from an **actor slug** (e.g. `applyIssueKeyStep` → `resolveActorSlugFromAuth`
  upstream in the HTTP layer), because the PDP/grants-dao side of the system
  works in slug space (`getGrantsForSubject`, `getRoleSlugsForActor`, etc.).
- The T-0249 composition root (`src/composition/completion-effects-root.ts`,
  `makeSlugResolvingActorEventWriter`) closes the gap with a **fail-closed**
  adapter: it wraps the real `PgActorEventWriter` and resolves
  `actor`/`roleAtEvent`/`onBehalfOf` slugs to their tenant-scoped
  `employee.id`/`role.id` UUIDs immediately before delegating, throwing (→ the
  effect fails → the caller's transaction rolls back, T-0249's CE-2) on an
  unresolvable slug rather than silently writing a bad row or skipping the
  event.

### 3.2 Why canonicalizing (pushing slug→UUID resolution into `runIssueKey`
itself, or changing the `ActorEventWriter` contract to accept slugs) is not a
small change

- It would mean **either** (a) every caller of `runIssueKey` resolves the slug
  to a UUID before calling in — but `runIssueKey` also uses the SAME
  `subject.subjectId` for the PDP `resolveFor` call, which expects a slug
  (grants-dao is slug-keyed), so the caller would need to carry BOTH forms and
  `runIssueKey`'s signature would need a second field — a real interface
  change, not a rename; **or** (b) `ActorEventWriter.appendActorEvent`
  accepts slugs and every implementation (the real `PgActorEventWriter`, the
  in-memory `makeInMemoryActorEventStore` test double used pervasively) grows
  its own resolution logic — which either duplicates the adapter's resolution
  code in N places or forces the in-memory test double to fake a slug↔UUID
  mapping it currently has no reason to know about.
- **Blast radius, measured**: `src/runtime/customer-onboarding/__tests__/issue-key.test.ts`
  (420 lines) and `src/adapters/__tests__/t0242-entitlement-port.test.ts` both
  build `IssueKeyDeps` around `makeInMemoryActorEventStore` and pass slug
  strings (`"e-owner"`, role slugs) as `actor`/`roleAtEvent` throughout — this
  is the existing, reviewed, working test contract for the whole module, not
  an oversight. `ci/checks/db/T-0249-onboarding-chain.db.test.ts` and
  `ci/checks/db/T-0249-action-route-effect.db.test.ts` (both landed the same
  day as this task, T-0249 r2) exercise the SAME live-PG path this adapter
  protects. Touching the contract ripples through all four files plus
  `fireCardAction` (`src/core/card-action.ts`), the OTHER production
  `appendActorEvent` caller, which is currently dormant (no live HTTP caller
  yet per `src/composition/issue-key-live.ts`'s own doc comment) but shares
  the same `ActorEventWriter` port.
- The adapter is **already the reviewed, shipped shape**: T-0249's judge
  (`docs/tasks/T-0249.review.json`, r2, `MERGE-READY`) explicitly reviewed and
  approved this exact adapter as the fix for the live 22P02 finding — it is
  not an unreviewed stopgap, it is the accepted resolution.
- Per this task's own instruction ("если канонизация большая/рискованная,
  сделай ТОЛЬКО (1) + напиши в спеке рекомендацию по (2) как отдельную
  задачу"), (1) is delivered in full; (2) is this write-up, not code.

### 3.3 Recommendation as a standalone follow-up (not built here)

If/when a second slug-speaking `ActorEventWriter` caller goes live (the most
likely trigger: `fireCardAction`'s `transition` path getting a real HTTP
route), that is the natural point to revisit: either (a) give
`makeSlugResolvingActorEventWriter` a home as a shared, exported adapter
(`src/composition/` or `src/core/`) that both callers wrap their writer with —
a small, additive, LOW-risk step that stops the pattern from being
copy-pasted per composition root — or (b) do the fuller canonicalization
described in §3.2 if by then enough callers exist to justify moving the
resolution into `runIssueKey`/the contract itself. Filing this as its own
task (not raised here) keeps T-0763 to the observability fix it was scoped
for.

### New tests (`src/__tests__/router.test.ts`, describe "T-0763: non-HttpError server-side logging")

1. Async handler non-HttpError → `console.error` called once, message contains
   the thrown error's text + `GET`/`/boom`; HTTP body is the generic
   `{error:{code:"INTERNAL",message:"internal server error"}}` and does
   **not** contain the thrown message.
2. Sync-throw-wrapped-as-rejection non-HttpError → same shape.
3. `HttpError` path → `console.error` **not** called (regression guard: no
   log-spam on expected domain errors).
4. Fallback sync throw non-HttpError → logged, response generic (includes a
   deliberately secret-looking string `token=abc123` in the thrown message, to
   pin that it never reaches `capture.body`).
5. Fallback async rejection non-HttpError → logged, response generic.
6. Fallback `HttpError` path → `console.error` not called.

All 19 pre-existing `router.test.ts` cases (including `AC-10: async handler
rejection (non-HttpError) → 500 no stacktrace`, which already pinned the
response-body half of this contract) pass unmodified.

## 5. What to attack (judge)

1. **The leak check itself.** Confirm `capture.body` genuinely never contains
   the thrown error's message/stack in any of the 6 new tests — re-run with a
   deliberately-more-sensitive thrown message (e.g. embed a fake bearer
   token) and grep the raw HTTP response bytes, not just the parsed JSON.
2. **The additive-only claim.** Re-run `git diff dev -- src/http/router.ts |
   grep '^-[^-]'` yourself and confirm it's empty; read the diff and confirm
   every hunk is a pure insertion (no line's content changed, only new lines
   appeared).
3. **The FF-5 "vacuous fallback" claim (§2.1).** This is the one process
   finding in this task with teeth beyond router.ts's own diff: verify
   independently that `worker-auth-public-surface.sh` really does pass once a
   `router.ts` change is committed (by design of its own fallback branch, not
   by an accident of this specific diff) — i.e. that this isn't a fluke of
   this particular changeset. If the judge considers that fallback itself a
   defect in FF-5 (silently vacuous once committed), that is a legitimate
   separate finding to raise — this task neither strengthens nor exploits it,
   it only documents the existing behavior it depends on to land at all.
4. **HttpError silence is deliberate, not an oversight.** Confirm no test
   asserts `console.error` is called on an `HttpError` path — tests 3 and 6
   assert the opposite (`not.toHaveBeenCalled()`).
5. **§3's canonicalize-vs-adapter judgment.** Independently size the ripple
   (§3.2's file list) if unconvinced the deferral is justified; the claim
