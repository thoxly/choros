# Оценка · T-0714 — Видимость инстансов процессов: достаточен ли tenant-скоуп для `GET /api/processes`?

- **Task:** T-0714 (architecture-оценка, substrate) — флаг судьи из ревью T-0708
- **Phase:** ASSESSMENT (architect); выход — рекомендация + черновики follow-up, НЕ правка `src/`
- **Date:** 2026-07-10
- **Тип:** ОЦЕНКА архитектурной развилки. Код продукта не меняется.
- **Reads-through (не противоречить):** ADR-T0570 (READ-PDP записей), ADR-T0278/§2.3
  (проекция процессов через `audit_event`, live-per-instance-запрос отвергнут как
  несоразмерный), product-decisions F2 (результат шага = сущность), карта примитивов §7 п.1
  (ратифицированный default-open внутри тенанта через сидированный грант).

---

## 1. Контекст и вопрос

Ревью T-0708 (`T-0708.review.json`, находка `tenant-scope`) зафиксировало **pre-existing**
(не регресс T-0708): маршрут `GET /api/processes` не имеет **per-instance / per-process**
PDP-проверки сверх членства в тенанте. Любой аутентифицированный член тенанта (и любой
**агент/ассистент** через тот же API — столпы 4/6) видит **все** инстансы процессов тенанта,
независимо от прав на конкретный процесс, инстанс или запись-источник.

Задача: оценить, нужен ли PDP-фильтр видимости на список/деталь инстансов, или tenant-скоуп
достаточен по модели прав продукта. Это развилка, окупающая архитектурную оценку, потому что
она (а) относится к фундаменту столпов 4/6 (агент-как-сотрудник в контуре прав), который
ADR-T0570 §1 закрывал для записей, и (б) создаёт асимметрию с уже действующим READ-PDP записей.

## 2. Находки: что и где реально проверяется (файлы:строки)

### 2.1 Что enforced на `GET /api/processes` сегодня

- `src/http/processes.ts:556-614` — `GET /api/processes`, обёрнут `withAuth`. В DB-режиме:
  `resolveActorSlugForRead(req)` → `startDeps.resolveActorTenant(actorSlug)` →
  `listInstanceProjections(pool, tenantId)`. **Единственная граница видимости — tenantId**,
  резолвленный из актора (не из заголовка), плюс RLS. Никакого per-instance/per-process
  предиката. Фильтр `?record=<id>` (T-0708, строки 557-587) применяется ПОСЛЕ tenant-скоупа и
  может только СУЗИТЬ — не расширяет.
- `src/http/process-projection.ts:820-895` (`readEvents`) + `995-1112`
  (`listInstanceProjections`) — читает `choros.audit_event` под `withTenant` (SET LOCAL
  `choros.tenant_id` + явный `WHERE tenant_id = $1`). **Скоуп — только тенант**; ни грантов, ни
  ancestry, ни read-visibility в fold нет.
- `src/server.ts:681-703` — `registerProcessesRoutes` получает `pool`, `flowable`,
  `resolveActorTenant`, `resolveActorsDisplay`. **`resolveReadVisibility` НЕ передаётся** — в
  отличие от `registerRecordRoutes` (см. 2.2). Крючка под read-PDP на процессах нет вовсе.

### 2.2 Прецедент: записи УЖЕ проходят per-record READ-PDP (действует в проде)

- `src/http/records.ts:1978-1990` (LIST) и `2059-2071` (DETAIL) — фильтр `isRecordReadable(...)`
  по покрывающим READ-грантам актора; запись без покрытия отдаёт honest-404, неотличимый от
  not-found (не выдаёт существование).
- `src/core/read-visibility.ts:1-95` — чистый предикат `isRecordReadable`, использующий ту же
  `isNarrowerOrEqual`/`isEffective` из `grant-lattice.ts` (единая authority-математика, не второй
  путь).
- `src/server.ts:882-892` — `resolveReadVisibility` **wired в проде** (`getGrantsForSubject` +
  `loadTenantOrgAncestry` → `makeResourceAncestryOracle`). Тот же блок повторно wired для
  Floor-1 агрегатов (`src/server.ts:989-999`, T-0632, «SECURITY, столп 4»).
- Ратифицированное фаундером решение (ADR-T0570 шапка): «default-open **внутри тенанта** через
  сидированный грант; сужение = настройка грантов». То есть модель прав продукта — НЕ
  «tenant=открыто навсегда», а «tenant-default-open + рычаг сужения через record-scoped гранты».
  **У процессов рычага сужения не существует.**

### 2.3 Инбокс: смешанный прецедент (частично per-role)

- `src/http/inbox.ts:9-21` — инвариант «задача адресована РОЛИ». Вкладка «Все» = «все задачи,
  видимые тенанту актора» (tenant-open, как процессы); вкладка «Из пула» = только НЕзанятые
  задачи роли, которую актор ДЕРЖИТ (per-role фильтр). Значит прецедент per-instance-сужения в
  процессной зоне частично есть (пул), но основной список — tenant-open.

### 2.4 Что конкретно возвращается (поверхность утечки)

**LIST `GET /api/processes`** (через `projectionToInstance`, `processes.ts:213-257` +
`InstanceProjection`, `process-projection.ts:114-193`) на каждый инстанс тенанта:
`definitionName` (человеческое имя процесса), `procKey`, текущий `step`/`nodes`, `status`,
`startedAt`, `starterActorKind` (human/agent), `stepsDone/stepsKnownTotal`, **`recordId`
(сырой UUID записи-источника)**.

**DETAIL `GET /api/processes/:id`** (`processes.ts:631-686` + `fetchInstanceHistoryDetail`,
`339-411`) дополнительно: **`variables`** — сырые исторические переменные Flowable
(`getHistoricVariableInstances`, `{name, value:unknown}[]`) — и полная `history` шагов с
`completedBy`/`completedByName`/`completedByType` (кто выполнил каждый шаг). Комментарий
`processes.ts:650-657` прямо фиксирует проектное решение: «under the SAME tenant-membership gate
… do not widen visibility beyond what this page already grants» — но страница уже даёт
tenant-wide, поэтому это и есть расширение до tenant-wide.

## 3. Оценка утечки на реальной схеме (по чувствительности)

### P1 — DETAIL `variables` (высокая, НЕ митигируется клиентом)

`GET /api/processes/:id` отдаёт **сырые переменные процесса** любому члену тенанта и любому
агенту. По F2-доктрине (product-decisions.md:138) источник правды — **запись**, а не «контекст
процесса»; но переменные Flowable де-факто несут те же бизнес-значения (суммы, вердикты, значения
полей формы), что на плоскости записей защищены field-visibility (T-0081) и READ-PDP (T-0570).
Это **обход** тех самых гейтов: одна и та же сумма редактируется/скрывается на записи, но
отдаётся сырой как переменная процесса. Клиент это НЕ смягчает (в отличие от P2). Это острая
кромка.

### P2 — LIST: существование + тип процесса + шаг + record-UUID (умеренная, частично митигируется)

Список раскрывает всем: какие процессы идут («Возврат средств клиенту», «Проверка контрагента
(KYC)»), на каком шаге, кем запущены, и **сырой `recordId`** записи-источника. Смягчение:
клиентский `RecordRef` (`web/src/components/components.jsx:293-345`) резолвит ТАЙТЛ записи через
`GET /api/records/:id`, который **сам READ-PDP-гейтед** (honest-404 → `RecordRef` показывает
`denied` → сырой UUID-чип, НЕ тайтл). То есть **тайтл записи не утекает** тем, кто не может её
читать. Но: (1) сырой `recordId`, `definitionName` и `step` **всё равно** в ответе API; (2)
митигация — клиентская и best-effort: прямой вызов API / агент (столп 4) получают сырой `recordId`
и метаданные независимо. Итог — это enumeration/existence-сайдченнел вокруг READ-PDP записей.

### P3 — DETAIL `history.completedBy*` (умеренная)

Кто выполнил каждый шаг (участники) — раскрывается любому члену тенанта.

**Кросс-тенант утечки НЕТ** — tenant-скоуп enforced через `resolveActorTenant` (из актора, не из
заголовка) + RLS/явный `WHERE tenant_id=$1`. Дефект строго **внутри-тенантный**.

**Влияние на столпы 4/6.** Агент, дергающий `/api/processes`, получает полный список инстансов
тенанта и переменные любого инстанса вне своих грантов — прямо подрывает «агент = сотрудник в
контуре прав» (столп 4) и «ассистент в контуре прав» (столп 6), т.е. тот самый фундамент, ради
которого ADR-T0570 §1 вводил READ-PDP на записи. Процессы — дыра в уже залатанном фундаменте.

## 4. Референс: как решают BPM-платформы (знание)

- **Camunda 7/8:** READ на `HistoricProcessInstance` — отдельное permission в Authorization
  Service, скоупится по **process-definition key** (а не «всё в тенанте»). Плюс identity-links
  (candidate users/groups, starter). Историческая видимость по умолчанию НЕ tenant-wide-open, если
  включён authorization-checks-for-history.
- **Flowable:** identity-links на process/task (starter, candidate groups); историю обычно
  фильтруют на уровне приложения по involvement (участник/стартер) либо по группам.
- **ELMA365:** видимость экземпляров процесса определяется ролью/участием (инициатор,
  исполнитель, наблюдатели), а не плоским «все в организации».

Индустриальная норма — **per-process-definition + per-instance (участник/стартер)**
read-авторизация, а не tenant-wide-open. Это поддерживает добавление фильтра, но НЕ обязательно
тяжёлого per-instance грант-объекта.

## 5. Опции

### Опция (a) — tenant-скоуп достаточен (статус-кво)
Оставить как есть; считать список инстансов «операционной прозрачностью внутри тенанта».
- **За:** просто; согласуется с вкладкой «Все» инбокса; кросс-тенант закрыт.
- **Против (отвергнуто):** противоречит ратифицированной доктрине (default-open **с рычагом
  сужения через гранты** — у процессов рычага НЕТ). Создаёт асимметрию с действующим READ-PDP
  записей и **обход** field-visibility через `variables` (P1). Подрывает фундамент столпов 4/6,
  который записи только что закрыли. Расходится с индустриальной нормой. → **Отвергается** как
  оценочная рекомендация: острая кромка P1 остаётся открытой.

### Опция (b) — полноценный per-instance грант-объект (латтис-ресурс на инстанс)
Сделать инстанс first-class ресурсом латтиса, чеканить read-гранты на инстанс.
- **За:** максимально гранулярно.
- **Против (отвергнуто):** инстансы не ресурсы латтиса; чеканка per-instance грантов —
  несоразмерна (дух D-061 «no new table», и ADR-T0278 §2.3 уже отверг live-per-instance-запросы
  как несоразмерные для read-пути). Over-engineering; новая authority-поверхность. → **Отвергается.**

### Опция (c) — видимость инстанса НАСЛЕДУЕТСЯ от записи-источника (рекомендуется)
По доктрине данных (сущность = источник правды, процесс = механика; F2): видимость инстанса =
READ-видимость его записи-источника. Переиспользовать **существующий wired-примитив**
`isRecordReadable` по `recordId` (тот же `resolveReadVisibility`, что у записей — единый
резолвер, без второго authority-пути). Фазами:
- **Фаза 1 (must, P1):** гейтить DETAIL (`variables` + `history` + `completedBy*`) предикатом
  READ-видимости записи-источника. Закрывает острую кромку; honest-degrade когда резолвер не
  wired (как у записей). Для инстансов БЕЗ `recordId` (явный запуск, не create=start) —
  fallback на process-definition-level read-грант или tenant-default-open (см. Фаза 3).
- **Фаза 2 (should, P2):** фильтровать LIST тем же предикатом — инстансы записей, недоступных
  актору на чтение, не светят имя процесса + record-UUID. Метаданные инстансов без `recordId`
  остаются tenant-default-open (честит ратифицированный дефолт).
- **Фаза 3 (could, record-less):** process-definition-scoped read-грант для инстансов без
  записи-источника (роль видит типы процессов, которые ведёт) — согласуется с Camunda-моделью.
- **За:** доктрино-согласовано (F2 + карта примитивов §7); переиспользует уже wired-инфраструктуру
  (`isRecordReadable`, `resolveReadVisibility`, `getGrantsForSubject`, ancestry-оракул), т.е.
  соразмерно; закрывает обход field-visibility; чинит фундамент столпов 4/6; единый резолвер.
- **Против:** нужен инстанс→запись reverse-lookup в read-пути (у create=start уже есть `recordId`
  в проекции; у record-less нужна политика Фазы 3); дисциплина display-plane isolation (`processes.ts`
  не импортирует pg/db — резолвер инжектится, предикат живёт в `process-projection.ts`).

## 6. Рекомендация

**Опция (c), фазами.** Tenant-скоупа НЕ достаточно по модели прав продукта: ратифицированный
дефолт — «default-open + рычаг сужения через гранты», и записи этот рычаг уже реализуют, а
процессы — нет, создавая (P1) обход field-visibility/READ-PDP через `variables` и (P2/P3)
enumeration/participant-сайдченнел, что бьёт по фундаменту столпов 4/6.

**Приоритет — Фаза 1 (DETAIL `variables`/`history`)**: это единственная кромка с высокой
чувствительностью, НЕ митигируемая клиентом, и прямой обход уже действующих гейтов записей.
Фаза 2 (LIST) — should; Фаза 3 (record-less) — could/политика. Соразмерность соблюдена:
инфраструктура READ-PDP уже wired и переиспользуема, новый authority-путь не заводится.

### Fitness-функции, которые ДОЛЖНЫ нести impl-задачи (архитектурные границы как код)
- **FF-INST-VIS-1 (гейт DETAIL):** `GET /api/processes/:id` для актора без READ-видимости
  записи-источника инстанса НЕ отдаёт `variables`/`history`/`completedBy*` (honest-404 или
  редакция). `ci_check`: новый adversarial e2e (актор без гранта на запись → 404/пусто на
  detail; актор с грантом → видит). Аналог `records.ts:2059-2071`.
- **FF-INST-VIS-2 (единый резолвер, нет второго authority-пути):** гранты read-видимости
  инстансов приходят из ТОГО ЖЕ `getGrantsForSubject`/`isRecordReadable`/ancestry-пути, что у
  записей. `ci_check`: grep-тест — процессная wiring переиспользует ту же фабрику
  `resolveReadVisibility` (`src/server.ts:882-892`), не заводит параллельную.
- **FF-INST-VIS-3 (display-plane isolation сохранена):** `src/http/processes.ts` по-прежнему не
  импортирует `pg`/`src/db/*`; предикат живёт в `process-projection.ts`, резолвер инжектится
  опционально (honest-degrade). `ci_check`: существующие `ci/checks/**` display-plane-грепы
  (start-route-isolation / pack-serve-no-write) остаются зелёными.
- **FF-INST-VIS-4 (tenant-изоляция неприкосновенна):** read-PDP предикат — ДОПОЛНИТЕЛЬНЫЙ `AND`
  внутри tenant-скоупа, никогда не замена. `ci_check`: тест «актор тенанта A не видит инстанс
  тенанта B» продолжает проходить.

### runtime_target
Сервер (существующий dev-стек, `grantsPool` + Flowable). Внешних ресурсов не требуется — вся
READ-PDP-инфраструктура уже wired.

### Эскалация
Не требуется. Развилка leverage-значима (фундамент столпов 4/6), но решение **уже
ратифицировано** фаундером в общем виде (ADR-T0570: default-open + сужение через гранты) и
доктриной F2 (сущность = источник правды). Рекомендация лишь распространяет уже принятую модель
на процессы-инстансы через переиспользование существующих примитивов — это применение
ратифицированного, а не новый продуктовый выбор. Приоритезация фаз (1 обязательна, 2/3 —
should/could) — на усмотрение оркестратора/фаундера.

## 7. Предлагаемые follow-up задачи (черновые заголовки; создаёт оркестратор, НЕ здесь)

1. **[P1, must] Гейт DETAIL `/api/processes/:id` по READ-видимости записи-источника** — инжектить
   `resolveReadVisibility` в `registerProcessesRoutes`; в `process-projection.ts`/детальном пути
   гейтить `variables`+`history`+`completedBy*` через `isRecordReadable(recordId)`; honest-degrade
   когда резолвер absent; для record-less инстансов — временно tenant-default-open (до задачи 3).
   Несёт FF-INST-VIS-1..4. LIVE_PROOF: актор без гранта на запись → detail без переменных.
2. **[P2, should] Фильтр LIST `/api/processes` по той же READ-видимости** — инстансы записей вне
   read-грантов актора выпадают из списка (honest-narrow); метаданные record-less инстансов
   остаются tenant-default-open. Переиспользует предикат задачи 1.
3. **[P3, could] Process-definition read-грант для record-less инстансов** — видимость инстансов
   без записи-источника по read-гранту на process-definition (роль видит типы процессов, которые
   ведёт); согласовать с Camunda-моделью и латтис-скоупами.
4. **[hardening, опционально] Не помещать чувствительные значения в переменные процесса** — ревью
   emit-сайтов: по F2 бизнес-истина живёт в записи (гейтед), переменные Flowable держать
   минимальными (id/ключи корреляции), чтобы `variables`-поверхность была наименее чувствительной
   by-design, а не только по PDP-фильтру.
