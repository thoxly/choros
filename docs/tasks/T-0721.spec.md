# T-0721 — mini-spec: DETAIL read-visibility gate for `GET /api/processes/:id`

- **Task:** T-0721 (security/PDP, P1 follow-up из оценки T-0714)
- **Reads-through:** `docs/tasks/T-0714.assessment.md` (архитектурная оценка,
  опция (c), фаза 1), ADR-T0570 (READ-PDP записей), product-decisions F2
  (сущность = источник правды).

## 1. Проблема

`GET /api/processes/:id` отдавал сырые `variables` (значения переменных
Flowable) + `history` (шаги, `completedBy*`) любому аутентифицированному члену
тенанта, гейтясь только tenant-membership. Та же бизнес-датума (суммы,
вердикты, значения полей) на плоскости записи уже защищена
field-visibility (T-0081) и READ-PDP (T-0570) — DETAIL был side-door вокруг
обоих.

## 2. Объём (in scope)

Фаза 1 из оценки T-0714 (§5 опция c): **только DETAIL**
(`GET /api/processes/:id`). LIST (`GET /api/processes`) НЕ трогается —
Фаза 2, отдельная follow-up-задача.

Гейтится: `variables`, `history` (включая `completedBy`/`completedByName`/
`completedByType`/`completedByDeactivated`). Остальные поля ответа
(`id`, `procId`, `status`, `node`, `nodes`, `started`, `progress`, `execs`,
`recordId`, `definitionName` — из `projectionToInstance`) НЕ гейтятся этой
задачей — они уже проходят tenant-scope через `listInstanceProjections`.

## 3. Дизайн (реюз, не bespoke)

Видимость DETAIL инстанса = READ-видимость его записи-источника
(`recordId`), решается ЕДИНЫМ резолвером:

- `isRecordReadable` (`src/core/read-visibility.ts`, T-0570, pure) — без
  изменений, реюз as-is.
- `resolveReadVisibility` — НОВЫЙ инжектируемый резолвер на
  `StartInstanceDeps` (`ProcessReadVisibilityResolver`,
  `src/http/process-start.ts`), возвращающий `{grants, ancestry}`.
  Production-wiring в `src/server.ts` (registerProcessesRoutes) — БАЙТ-В-БАЙТ
  та же композиция `getGrantsForSubject` + `loadTenantOrgAncestry` →
  `makeResourceAncestryOracle`, что `registerRecordRoutes`'s
  `resolveReadVisibility` (server.ts:882-892) и Floor-1's
  `reportAggReadVisibility` (server.ts:989-999) уже используют. Не заводит
  параллельную authority-математику.
- `isInstanceDetailVisible` — НОВАЯ функция в `src/http/process-projection.ts`
  (этот модуль уже импортирует `pg`, в отличие от `processes.ts` —
  FF-DISPLAY-4/FF-INST-VIS-3 дисциплина сохранена). Делает:
  1. `recordId === undefined` → `true` (record-less, см. §4).
  2. Иначе — reverse-lookup `recordId → {registryId, applicationId}`
     (`loadRecordRowAncestry`, один SELECT `choros.record JOIN
     choros.registry_def`, tenant-scoped через существующий модульный
     `withTenant`). Запись не резолвится → `false` (честный deny).
  3. `isRecordReadable(rowAncestry, grants, ancestry, nowMs)`.

`src/http/processes.ts` (DETAIL route handler) вызывает резолвер +
предикат ДО композиции `fetchInstanceHistoryDetail` — деньед-инстанс никогда
не трогает `flowable.getHistoricVariableInstances`/`getHistoricActivityInstances`.

## 4. Решения (проектные развилки)

### 4.1 Отказ = 404 (не 403)

Эталон — `GET /api/records/:id` (T-0570, `records.ts:2059-2071`): запись без
покрывающего READ-гранта отдаёт `404 NOT_FOUND` — неотличимо от
несуществующей/чужого тенанта (не палит существование). DETAIL повторяет ТОТ
ЖЕ error-shape (`HttpError(404, "NOT_FOUND", "instance not found")`),
которым этот роут УЖЕ отвечает на "инстанс не найден" — денай и not-found
теперь делят один код, консистентно.

### 4.2 Record-less инстансы — НЕ сужены (Фаза 1)

Инстанс без `recordId` (явный запуск через `/api/processes/start`, не
create=start) остаётся видим как раньше (tenant-default-open). Это
пред-существующее поведение, честная достройка — process-definition-scoped
read-грант для record-less инстансов — это Фаза 3 оценки T-0714, отдельная
задача — заводится оркестратором отдельно от этой (T-0714 §7 п.3).

### 4.3 Владелец (genesis/tenant-owner) видит всё — БЕЗ bespoke-ветки

Расследование: `records.ts`'s READ-PDP НЕ вызывает `isGenesisOwnerForTenant`
напрямую. Владелец видит всё через ОБЫЧНЫЙ путь — migration 117
(`default_read_grant_backfill`) сеет `role-reader` + `RESOURCE_ROOT`-scoped
READ-грант, назначенный tenant-owner (и assistant-agent), delegable=true.
Т.е. "владелец = default-open" — это СВОЙСТВО грантов, не отдельная
authority-ветка. DETAIL-гейт повторяет ТОТ ЖЕ путь (тот же
`resolveReadVisibility`) — владелец автоматически видит DETAIL без
дополнительного кода. Доказано live-PG-тестом (`ci/checks/db/
processes-read-visibility.db.test.ts`, describe "tenant-owner... sees
DETAIL").

### 4.4 Исполнитель шага без READ на запись — allowlist НЕ реализован

Расследовано: единственный UI-путь, которым держатель задачи ("исполнитель")
взаимодействует с инстансом, — `GET /api/inbox/:id` +
`POST /api/inbox/:id/action` (`src/http/inbox.ts:1608-1726`). Ответ
`GET /api/inbox/:id` — `{item, projection}`, где `projection` = сырая
`InstanceProjection` (id/procKey/status/step/startedAt) — БЕЗ `variables`,
`history`, `completedBy*`. Фронтенд (`web/src/screens/screen-inbox.jsx`,
`TaskDetailPanel`) НИКОГДА не вызывает `GET /api/processes/:id` — кнопка
«Задачи этого процесса» (`onFilterByInstance`, T-0653) фильтрует ИНБОКС по
инстансу, не открывает деталку процесса. `ProcessRef` в списке задач — это
label-компонент (резолвит имя процесса/записи через уже-гейтед
`GET /api/records/:id`), не ссылка на DETAIL. Вывод: исполнитель делает свою
работу ПОЛНОСТЬЮ через инбокс-плоскость, не нуждаясь в DETAIL. Легитимного
сценария не найдено → allowlist НЕ реализован (роль-правило «не выдумывай
шире» — добавление незапрошенной ветки было бы feature creep).

## 5. Fitness-функции

- **FF-INST-VIS-1** (`ci/checks/process-detail-read-gate.sh`) — статический
  гейт: DETAIL-роут `processes.ts` импортирует `isInstanceDetailVisible`,
  ссылается на `resolveReadVisibility` И `isInstanceDetailVisible(` внутри
  хендлера, вызов предиката ПРЕДШЕСТВУЕТ `fetchInstanceHistoryDetail(` по
  порядку строк, денай падает в тот же honest-404. `--self-test` сажает
  gate-free фикстуру и убеждается, что предикат её ловит.
- **FF-INST-VIS-2** (`ci/checks/process-detail-single-resolver.sh`) — запрет
  второго authority-пути: `process-projection.ts` реюзает
  `isRecordReadable` (не переопределяет), ни один из трёх процессных модулей
  не импортирует `isNarrowerOrEqual`/`isEffective` напрямую, не шлёт bespoke
  SQL по `choros."grant"`, а `server.ts`'s wiring-окно реально зовёт
  `getGrantsForSubject`/`loadTenantOrgAncestry`/`makeResourceAncestryOracle`.
  `--self-test` сажает bespoke-grant-SQL и прямой lattice-math импорт,
  убеждается, что оба ловятся.

  не резолвится → deny; record-less → всегда visible; LIST не задет;
  `isInstanceDetailVisible` напрямую (4 теста).
- Live-PG (`ci/checks/db/processes-read-visibility.db.test.ts`, T-0147

  грантом; owner-parity; record-less fallback; honest-degrade (pre-gate
  сервер); tenant-isolation (A не резолвит инстанс B).
- Регрессия: весь существующий unit-набор `processes*`/`process-start*`
  (78 тестов) остаётся зелёным без изменений — honest-degrade гарантирует
  байт-в-байт прежнее поведение там, где `resolveReadVisibility` не
  инжектирован (все существующие фикстуры).
