# T-0755 — DIAGNOSIS: create=start silently stalls at the agent «Триаж» step

**Priority:** P0  **Status:** DIAGNOSED — STOP before fix (architectural / product decision required).
**Origin:** live-proof T-0691 (E16 capstone) P0 finding — `docs/live-proof/T-0691-e16-capstone.json`, evidence `docs/live-proof/T-0691-evidence/`.

---

## 1. Symptom (reproduced live in T-0691)

A user creates a record in the «tel-approval» app → the `on_create` binding starts the
bound process `telLinear` (create=start **works**). The process auto-skips «Подача заявки»
and lands on **«Триаж»**, an AGENT external serviceTask (`flowable:topic="tel-intake"`).
In the running/deployed stack **nothing completes it** → the instance parks at «Триаж»
**forever**; the human «Согласование» step never surfaces in any inbox. T-0691 could only
reach the approvable state by manually injecting the missing `task_completed` outbox row
(the P0 bypass documented in the manifest `bypasses[0]`).

Green CI masked this: the CI e2e journey and the test harness stand in for the absent worker
(see §3).

## 3. Root cause — MIXED (а primary + б + в)

- **(а) Deployed gap — PRIMARY.** The platform has **no production runtime path** to complete
  agent/deterministic external tasks on the `tel-intake` topic. The agent-dispatch loop drives
  only `agent-step` (by explicit design, docker-compose:205, agent-dispatch-loop.ts:13-16);
  no separate triage/deterministic worker service exists (tel-linear-smoke.sh:8-11 "day-1
  DORMANT/stub"). Only the test harness (`bridge-smoke-runner.ts`) and the CI e2e journey
  complete it — hence "green in CI, dead live."

- **(б) Seed/case-content leak — SECONDARY (D-064).** `telLinear` is a **demo** process
  (`@demo-seed`, migrations 085/087/090; skipped when `CHOROS_SEED_DEMO=off`). Its triage step
  uses a **bespoke `tel-intake` topic** distinct from the ONE canonical `agent-step` topic the
  platform actually drives. The **generic** create=start primitive is therefore gated by
  **case-specific process content** — an agent step on an un-driven topic. Per D-064, an
  unhandled case-specific step must not silently gate a platform primitive.

- **(в) Missing live-agent wiring — TANGENTIAL (T-0679 class).** Even the seeded dormant
  keystone agent `a-triage` (migration 090), which was meant to defer this step to a human, is
  **not referenced by the BPMN** (no `agentRef`/`agentEmployeeId`), so the intended
  dormant-defer-to-human never fires. The step has an agent persona in its documentation but no
  runtime agent binding.

---

## 4. Why NO fix was shipped (STOP per Phase-2 guardrail)

There is **no clean, self-contained, provable fix** that makes create=start reach the human
step out-of-box without first taking an **architectural/product decision** about *which
runtime model owns triage completion in production*. Every candidate either introduces a new
service, ripples into CI/test contracts that enshrine `tel-intake`, or relies on an agent-step
live path that has itself never been proven end-to-end against real Flowable (no CI drives
`agent-step` through a live engine; the DB tests use `jobStore` directly). Details per option
in §5. This is exactly the case the task flags as "should there be a built-in triage worker?
→ do NOT build, escalate."

Additionally, the "honest-surface" option (show "ожидает агента / агент не настроен" instead
of a silent forever-park) is itself **decision-dependent**: the correct message differs
depending on whether the triage step is *supposed* to have a worker (then: "processing") or is
by-design human-gated (then: "agent not configured"). It cannot be written correctly before
§5 is decided. (It would also not satisfy the P0's core requirement — reaching the human step.)

## 5. Options (for the founder / architecture decision)

### Option A — Build a production deterministic-triage worker (own the `tel-intake` topic)
Add a small runtime loop that fetchAndLocks `tel-intake` jobs and completes them pass-through
(the production analogue of `bridge-smoke-runner`), letting `evaluateGatewayAtTriage` run at
completeTask. Mirrors the design intent ("детерминированно через fetchAndLock/completeTask,
тот же bridge-механизм что в choros-smoke").
- **Pros:** keeps the `tel-intake` seam design intact; no BPMN/CI-contract churn; makes
  choros-smoke-class deterministic external tasks completable in prod generally.
- **Cons:** a **new platform service** = the "built-in triage worker" architectural decision.
  Founder-scope. Also leaves (в) unaddressed (no real agent does the triage; it's a stub
  pass-through).

### Option B — Fold triage into the canonical agent-step dispatch path
Re-topic the demo triage `tel-intake → agent-step` and stamp `<flowable:field
name="agentEmployeeId">d0000000-…-0006</…>` + `roleId=e0000000-…-0005` so the **already-wired
dormant dispatcher** runs it (defer-to-human → close step → gateway → «Согласование»), using
the seeded `a-triage` keystone (fixes а+б+в at once).
- **Pros:** uses the real, already-built platform runtime path; removes a legacy case-topic
  (D-064-honest); the seeded keystone finally does its job.
- **Cons:** (1) **ripples into CI/test contracts** that enshrine `tel-intake`:
  `src/__tests__/dmn-gateway.test.ts:635-638` (asserts `flowable:topic="tel-intake"`),
  `e2e/journeys/tel-gateway-routing.journey.ts` + `.github/workflows/ci.yml:411`
  (`FLOWABLE_TOPICS=tel-intake`) — not self-contained. (2) Relies on the **agent-step live
  path** (Flowable surfacing `flowable:field` as external-task variables at fetchAndLock;
  worker-id-matched completeTask) which is **unproven end-to-end live** — itself a latent
  "green-CI/dead-live" surface that must be validated first.

### Option C — Re-author the demo so create=start proves the primitive without an agent gate
Make the demo's `on_create` process land on a **human** «Согласование» step immediately after
skip-submit (drop/relocate the agent triage from the create=start path, or bind create=start
to a triage-free process). Proves the GENERIC create=start → human-step primitive out-of-box.
- **Pros:** smallest blast radius on the *primitive*; anti-case-clean (no case step gates the
  primitive); no new service.
- **Cons:** removes the agent-in-the-loop demo value from create=start; a demo/product-shape
  decision, not pure plumbing.

### Recommendation
**B is the most product-faithful** (agents-as-employees, столп 4; one canonical runtime path)
**but must be gated behind first proving the `agent-step` live path end-to-end** (a prerequisite
task) — otherwise it trades one green-CI/dead-live gap for another. If a fast, honest
out-of-box create=start proof is needed sooner, **C** delivers it with the least risk. **A**
is the right long-term answer only if the product wants a general deterministic-external-task
completer in prod. All three are founder/architecture calls — hence STOP.

---

## 6. Honest bottom line
**create=start is genuinely broken at the platform level in deployment** for any process whose
first post-submit step is an agent/deterministic external task on a topic the runtime does not
drive (today: every `on_create`→`telLinear` instance). It does not silently *fail* — it
silently *parks* with a stale «Подача заявки / ОЖИДАНИЕ» projection (T-0691 minor finding P2),
which is worse (looks alive, is dead). The mechanism that made this pass CI is the test
harness / e2e journey standing in for a production worker that was never built.
