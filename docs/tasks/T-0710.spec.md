# Мини-спека + ADR · T-0710 — три P2-дефекта видимости процессов/инбокса (E16, capstone T-0691)

- **Task:** T-0710 · продукт Choros · эпик E16 · P2 из capstone T-0691 LIVE_PROOF
- **База:** свежий `dev`, уже несущий T-0709 (resolveLiveNodesByInstance — каталог+деталка)
  и T-0718 (тот же оверлей для `GET /api/inbox/:id`).
- **Тип:** точечный фикс трёх независимых дефектов видимости. Не редизайн IA.

---

## 1. Разведка — что уже есть, что осталось непокрытым

T-0709/T-0718 построили `resolveLiveNodesByInstance` + `overlayLiveSteps`
(`src/core/process-catalog-view.ts:274-453`) — best-effort оверлей ЖИВОГО активного
узла движка поверх снапшот-проекции (`listInstanceProjections`,
`src/http/process-projection.ts:995-1170`), общий для каталога, `/api/processes[/:id]`
и `/api/inbox/:id`. Оверлей корректен, КОГДА движок достижим и у инстанса есть живая
активная задача.

Непокрытая ветка (все три дефекта живут здесь): когда движок НЕ отвечает данными для
инстанса (офлайн-стенд, легаси-инстанс без соответствующей живой Flowable-записи,
устаревшая/неполная аудит-цепочка) — `overlayLiveSteps` честно возвращает проекцию
БЕЗ изменений (`process-catalog-view.ts:301`), и потребитель падает обратно на
СНАПШОТ, который сам по себе строился с дефектом (§2) независимо от T-0709.

## 2. Дефект #1 — «Текущий шаг» деталки инстанса даёт ДВА шага для легаси-инстанса

### Корень

`listInstanceProjections` (`src/http/process-projection.ts:995-1170`, до фикса) строил
`concurrentSteps` так: «толкни базовый `task_step`, ЕСЛИ его `task.approved` ещё не
пришёл» + «добавь все PENDING `process.next_task` шаги» — без проверки, не был ли
базовый шаг УЖЕ вытеснен существованием `next_task`-строки. Сестринская функция
`listInstanceInboxTasks` (та же файл, T-0608, «пункт б») уже несёт этот инвариант:
«ЛЮБОЙ `process.next_task`-ряд для инстанса — доказательство, что движок уже сдвинулся
дальше базового шага, НЕЗАВИСИМО от того, записан ли `task.approved` для базового ряда»
(все 4 эмит-сайта `process.next_task` подтверждают это ЖИВЫМ вызовом
`getActiveUserTasks` перед записью). `listInstanceProjections` этот инвариант не
наследовал — при легаси/неполной аудит-цепочке (базовый `task.approved` потерян/не
записан) она показывала И базовый, И следующий шаг как «конкурентные AND-split ветки»,
хотя они СЕКВЕНЦИАЛЬНЫ. Инстанс-деталка (`web/src/screens/screen-process-instance.jsx:355-368`,
`nodes.length > 1` → рендер каждой ветки отдельной строкой) показывала это как ДВА
активных узла.

Живой пример из T-0709 LIVE_PROOF (`docs/live-proof/T-0709.md`, «смежная находка»):
инстанс `99573238` — реальный движок нёс ОДНУ userTask, аудит нёс стухшую вторую.

### Минимальный фикс

`process-projection.ts` (`listInstanceProjections`):
1. `instancesWithAnyNextTask: Set<string>` — те же данные, что `listInstanceInboxTasks`
   уже собирает под именем `instancesWithNextTask` (T-0608), но локально для этой
   функции (не эскортировать через модульную границу — минимальный диф).
2. Базовый шаг попадает в `concurrentSteps` ТОЛЬКО когда `!baseApproved &&
   !baseSuperseded` (было: только `!baseApproved`).
3. Побочный эффект, необходимый для непротиворечивости (см. ниже): единичные поля
   `step`/`role` проекции (используемые БЕЗ массива на `/api/process-catalog` и в
   инбокс-дровере `projection.step`, `web/src/screens/screen-inbox.jsx:842`) теперь
   следуют `concurrentSteps[0]` вместо безусловного эха базового `task_step`/`task_role`
   — иначе фикс п.2 создал бы РАСХОЖДЕНИЕ между `nodes[]` (деталка, верно) и `step`
   (каталог/дровер, всё ещё стухший) — тот самый класс дивергенции, который T-0709
   закрывал. Обнаружено db-тестом (regression-кейс #3, см. §5) — без этого шага
   правильно-аудированный 6M-branch кейс (approved base + pending next_task) тоже
   регрессировал бы на singular-полях.

Anti-case: никаких строковых литералов шагов/ролей в фиксе — все значения приходят из
уже прочитанного `payload`.

## 3. Дефект #2 — `GET /api/inbox?instance=<id>` игнорируется

### Корень

Параметр `instance` никогда не парсился. Хуже: `const query = parseQuery(req.url)`
выполнялся ПОСЛЕ `findInboxItems(actor)` (`src/http/inbox.ts`, было: строка ~1509 до
~1517) — физически поздно, чтобы протянуть фильтр в источник данных, даже если бы
парсинг был. А источники (`listInstanceInboxTasks` / `listDeferredInboxTasks`) читают
`choros.audit_event` с `ORDER BY occurred_at ASC/DESC LIMIT N` (N=200/100 по умолчанию,
`process-projection.ts:820-895` `readEvents`, `deferred-inbox-store.ts:108-131`) —
пост-фильтр по УЖЕ полученной (усечённой) странице был бы нечестным: инстанс, чья
`process.started`-строка не попала в самые старые/новые N строк тенанта, был бы
невидим, даже если бы фильтр применялся правильно.

### Минимальный фикс

Фильтр протянут ДО SQL, не после:
1. `readEvents` (`process-projection.ts`) принимает опциональный `instanceId` и
   добавляет `AND payload->>'inst' = $N` во ВСЕ 4 запроса (у всех событий —
   `process.started`/`instance.ended`/`task.approved`/`process.next_task` — payload
   несёт `inst`). `listInstanceInboxTasks` принимает `opts.instanceId` и пробрасывает.
2. `listDeferredInboxTasks` (`src/db/deferred-inbox-store.ts`) принимает
   `opts.instanceId`, фильтрует по `payload->>'instance_id'` (НЕ по `inst` — у
   defer-строк `inst`=`subject` вида `agent:<id>`, реальный Flowable-id лежит в
   отдельном `payload.instance_id`, T-0638 F1; смешивать поля было бы нечестно).
3. `findInboxItems` получает 4-й опциональный параметр `instanceFilter`, применяет его
   к seed-фикстурам in-memory (маленький константный массив — угрозы усечения нет) и
   пробрасывает в оба SQL-источника.
4. Роут `GET /api/inbox`: парсинг `query`/`instanceParam` поднят ДО reconcile-блоков
   и вызова `findInboxItems`, значение передаётся первым же вызовом.

db-тест (`ci/checks/db/T-0710-inbox-instance-filter.db.test.ts`, часть 1) доказывает
именно нечестность старого паттерна: при `limit=3` и 5 инстансах ненаправленный
`listInstanceInboxTasks` теряет самый новый (целевой) инстанс; тот же вызов со
`instanceId` находит его независимо от `limit`.

Frontend НЕ тронут: существующая кнопка «Задачи этого процесса»
(`web/src/screens/screen-inbox.jsx:1290-1296`) уже использует клиентский `?process=`
(подстрочный match по `inst`/`procKey`/`processName`) — рабочий, но не SQL-честный
механизм. Перевод этой кнопки на `?instance=` — естественный follow-up, вне объёма
этой задачи (не тронут рендер → нет обязательных web-тестов по правилу задачи).

## 4. Дефект #3 — пагинация ~28 строк, эскалации хоронят старые approver-задачи

### Корень

`findInboxItems`'s merge: `merged = [...dedupedDefer, ...dedupedInstance]`
(`src/http/inbox.ts`, ~1156) — ВСЕ defer-строки (агентские эскалации, `escalated:true`
по построению, T-0638 F7) всегда идут ПЕРЕД любой instance-строкой, независимо от
возраста. Дефолтная (без `?sort=`) выдача `GET /api/inbox` не переупорядочивает this —
только `?sort=sla` сортирует (по убыванию срочности). При достаточном потоке эскалаций
старые обычные approver-waiting задачи структурно вытесняются за дефолтный размер
страницы.

### Минимальный фикс

Новая чистая функция `stableSortEscalatedLast` (`src/http/inbox.ts`, рядом с
`isEscalated`): стабильный partition — не-эскалированные первыми, эскалированные
последними, относительный порядок внутри каждой группы сохранён (`Array.sort`
гарантированно стабилен, ES2019+). Применяется к `filtered` ТОЛЬКО когда `sort !==
"sla"` (явный запрос срочности не трогаем — эскалации там и так обычно наверху по
факту минимального SLA-запаса). На вкладке «Эскалации» (все элементы уже эскалированы)
— no-op. Никакой новой IA/вкладки/группировки не добавлено.
