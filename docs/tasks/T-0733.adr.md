# ADR T-0733 — резолвер имён org-tree узлов для department.moved/position.moved (R-1 из ревью T-0712)

- **Статус:** реализовано (impl-фаза, coder)
- **Контекст:** ревью T-0712 (эпик E-UX-HUMAN T-0647, столп 4 анти-UUID) —
  finding R-1: `department.moved`/`position.moved` в `/audit` рендерят цель
  сырым `MonoId` (id узла), в то время как `employee.moved` уже резолвит цель
  в человеко-имя через `ActorChip` (T-0712, батч-резолвер `actor-resolver.ts`,
  T-0648). T-0712's собственный handoff явно зафиксировал это как отложенный
  follow-up: *"резолвер имён department/position не существует в кодовой
  базе, заводить его — отдельный follow-up... не входит в объём P3-фикса"*.
  T-0733 — этот follow-up.
- **Область:** `src/db/node-resolver.ts` (новый), `src/http/audit.ts`,
  `web/src/components/components.jsx` (NodeRef), `web/src/screens/screen-audit.jsx`,
  `web/src/screens/screen-audit.logic.js`

## 1. Проблема

`department.moved`/`position.moved` — единственные два из трёх `.moved`-типов
(наряду с `employee.moved`), чья цель — не сотрудник, а УЗЕЛ org-дерева
(`choros.department`/`choros.position`). `audit-read-dao.ts` (T-0712) уже
кладёт в `target` реальный id узла (из `subject`-колонки писателя,
`seed-write.ts`), но `src/http/audit.ts` резолвит `targetDisplay` ТОЛЬКО для
`employee.moved` (через `batchResolveActors`, employee-таблица) — для двух
node-типов `targetDisplay` был жёстко `null`, и клиент (`screen-audit.jsx`)
падал на прежний `MonoId`-чип с сырым UUID узла.

Узел БЫ мог резолвиться в имя — `choros.department.display_name` /
`choros.position.title` уже существуют и уже читаются в других местах
(`org.ts::listOrgTree`), просто НИКТО не собирал их в батч-резолвер для этой
конкретной точки чтения.

## 2. Решение

### 2.1 Отдельный резолвер, не расширение actor-resolver.ts

**Решение:** новый модуль `src/db/node-resolver.ts` —
`batchResolveOrgNodes(pool, tenantId, departmentIds, positionIds)` +
`resolveNodeDisplay(resolved, id, kind)` — СИБЛИНГ `actor-resolver.ts`, не
правка существующего.

**Почему:** узел org-дерева — НЕ актор (нет `kind`, нет `deactivated_at`, нет
человеко/агентской идентичности; `EXEC_META`/`ActorChip` не имеют глифа для
"узла"). Смешение в одну функцию заставило бы либо (а) фальшиво выдавать узлу
тип `human`/`agent`/`service` (искажение — отдел выглядел бы как системный
актор), либо (б) раздувать `ResolvedActor` необязательными полями только для
двух вызывающих мест. Отдельный модуль с параллельной, но НЕ идентичной
формой (`{id, name, kind, resolved}` вместо `{id, name, type, deactivated,
resolved}`) — точнее отражает разницу сущностей и не трогает уже
адверсарно провренный `actor-resolver.ts` (T-0648/T-0685).

### 2.2 ОДИН запрос на department+position через UNION ALL

**Решение:** `batchResolveOrgNodes` — ОДИН SQL-запрос
(`SELECT ... FROM choros.department ... UNION ALL SELECT ... FROM
choros.position ...`), а не два отдельных запроса и не запрос на строку.

**Почему:** id отдела и id должности — разные UUID-колонки из разных таблиц,
их нельзя резолвить одним `WHERE id = ANY($2)` на одну таблицу (в отличие от
`batchResolveActors`, где employee — ОДНА таблица для слага И id). `UNION
ALL` с двумя независимыми `ANY($2::text[])`/`ANY($3::text[])` даёт РОВНО ОДИН
round-trip независимо от того, сколько отделов/должностей на странице —
пустой список с одной стороны (`ANY('{}')`) не матчит ничего и не роняет
запрос (проверено `node-resolver.test.ts` case (f)). Та же O(1)-дисциплина,
что T-0648 установил для акторов (см. `actor-resolver.ts`'s собственный
doc-comment про N+1).

### 2.3 Матч только по `id`, не по slug

**Решение:** `batchResolveOrgNodes` матчит СТРОГО по `id::text = ANY(...)`,
без альтернативного матча по slug (в отличие от `batchResolveActors`, которая
матчит по slug ИЛИ id).

**Почему:** `PATCH /api/departments/:id` / `/api/positions/:id`
(`seed-write.ts`) принимают ТОЛЬКО сырой UUID `:id` (`assertUuidShape`) — нет
клиентского URL-параметра по slug для этих двух сущностей (в отличие от
employee, где часть путей исторически принимала slug). `subject`-колонка,
которую пишет `.moved`-эвент, — всегда этот же raw `id`
(`seed-write.ts:924/1018` — `subject: deptId`/`subject: posId`, где
`deptId = params["id"]`). Слаг-матч добавил бы мёртвый код без вызывающей
стороны.

### 2.4 Честная деградация удалённого узла — БЕЗ soft-delete аналогии

**Решение:** `resolveNodeDisplay` при промахе возвращает `{id, name: id,
kind, resolved: false}` — ТОТ ЖЕ контракт, что `resolveActorDisplay`. Клиент
(`NodeRef`, `components.jsx`) демотирует UUID-подобное `name` (переиспользует
`isMachineActorLabel`, тот же гард, что `ActorChip` T-0685) и рендерит
`"Отдел удалён"`/`"Должность удалена"` вместо сырого id.

**Почему НЕ soft-delete предикат:** `choros.department`/`choros.position`
(миграции 014/015) НЕ несут `deactivated_at` — в отличие от employee (миграция
125). `DELETE /api/departments/:id`/`/api/positions/:id` (AC-9,
isGenesisOwner-only) — ЖЁСТКОЕ удаление строки. Значит промах резолвера для
`.moved`-цели ВСЕГДА означает "узла больше нет" (или, defensively,
кросс-тенантный id) — нет промежуточного "деактивирован, но виден" состояния,
которое есть у сотрудника. Честный фоллбэк формулирует ИМЕННО это ("удалён"),
а не молчаливо копирует employee-семантику "деактивирован".

### 2.5 NodeRef — отдельный примитив, не расширение ActorChip

**Решение:** новый компонент `NodeRef` (`components.jsx`) — не проп
`type="department"` внутрь `ActorChip`.

**Почему:** `ActorChip`'s глиф (`EXEC_META`/`ExecGlyph`) закодирован ровно на
три акторских вида (круг/ромб/квадрат = human/agent/service) — департамент,
нарисованный квадратом "Сервис", читался бы как системный актор, а не как
организационный узел. `NodeRef` — параллельный, минимальный примитив: имя
первично, id — только в tooltip (то же поведение по умолчанию, что `showId
=false` у `ActorChip`), честная деградация через тот же UUID-демоушен-гард.
Клиентский выбор между `ActorChip`/`NodeRef` — по `ev.action`
(`isOrgNodeMoveAction`, `screen-audit.logic.js`), не по форме
`targetDisplay` — симметрично тому, как `execTypeOf(ev.action)` уже управляет
рельсовым глифом.

## 4. Тесты

- **`src/__tests__/node-resolver.test.ts`** (НОВЫЙ) — 10 сценариев, мокнутый
  pool, зеркалит `actor-resolver.test.ts`: (a) department резолвится по id,
  (b) position резолвится по id, (c) ОДИН запрос резолвит department+position
  вместе (нет N+1/второго round-trip), (d) промах — честный фоллбэк, не
  ошибка, (e) пустой инпут с ОБЕИХ сторон → ноль запросов, (f) department-only
  страница (`positionIds=[]`) резолвится чисто, (g) tenant-scope — параметр
  запроса = переданный tenantId (defence-in-depth), (h)
  `resolveNodeDisplay(_, null/undefined/"")` → честный пустой фоллбэк, (i)
  дубликаты id дедуплицируются до запроса.
- **`web/src/components/node-ref.test.jsx`** (НОВЫЙ) — `NodeRef` напрямую
  (без хуков, без DOM, мирроит `actor-chip.test.jsx`): резолвленное имя
  первично/id только в tooltip; НЕРЕЗОЛВЛЕННЫЙ узел (`name === id === UUID`)
  — UUID НИКОГДА в видимом тексте, честный фоллбэк
  "Отдел удалён"/"Должность удалена"; визуальный маркер
  `chs-noderef--unresolved`; неизвестный kind → дженерик "Узел".
- **`src/__tests__/audit-log.test.ts`** (РАСШИРЕН) — стаб-pool получил ветку
  для UNION ALL node-запроса; 2 существовавших теста (department.moved/
  position.moved) обновлены с `targetDisplay: null` на резолвленную форму;
  добавлен блок "(8) T-0733": удалённый department/position → честный
  фоллбэк; кросс-тенантный узел не резолвится (параметр запроса = tenantId
  ВЫЗЫВАЮЩЕГО, никогда не второй тенант); одна страница со смешанными

  `.moved`-эвентов вообще не дёргает node-резолвер.

  `NodeRef`); `employee.moved` не затронут регрессией (по-прежнему
  `ActorChip`, ноль `NodeRef`).
- **`ci/checks/db/org-move-api.db.test.ts`** (РАСШИРЕН, живой PG) — на ТОМ ЖЕ

## 5. Отклонения от спеки

Нет содержательных отклонений. Единственная уточняющая деталь: `NodeRef` —
новый примитив (не переиспользование `ActorChip`) — обоснование в §2.5 выше;
это МИНИМАЛЬНОЕ дополнение (один компонент, без нового CSS-фреймворка,
переиспользует `isMachineActorLabel`/`asRenderableText` из существующего
кита), соразмерное объёму R-1-фикса, не расширение за пределы задачи.

`live_proof`: стенд offline в этой сессии (см. `T-0733.pr-handoff.json`
`live_proof_plan`) — живой PG-проход (`ci/checks/db/org-move-api.db.test.ts`
`AC-audit-read-node`) уже доказывает серверную половину сквозняком на реальном
Postgres; фронтовый рендер (браузер) — по `live_proof_plan`.
