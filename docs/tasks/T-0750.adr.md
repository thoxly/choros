# ADR T-0750 — GET /api/inbox/:id authority gate (P1, substrate, ACTOR_ACTIVE wave finale)

- **Статус:** реализовано (impl-фаза, coder)
- **Контекст:** T-0740 ADR §7 («известный незакрытый gap»), T-0726 ADR §5.2
  (finding `inbox.ts:GET:/api/inbox[/:id]`), T-0738 (закрыл LIST-путь того же
  класса). Родители: T-0658/T-0662 (`ACTOR_ACTIVE_SQL`), T-0726 (route-
  coverage гейт), T-0721 (прецедент для `GET /api/processes/:id`).
- **Область:** `src/http/inbox.ts` (`GET /api/inbox/:id` handler, ~1708-1780),
  `src/__tests__/inbox-detail-live-step.test.ts` (актуализация под новый
  гейт), `ci/checks/db/T-0750-inbox-detail-authority.db.test.ts` (новый,
  live-PG). **Ни один `ci/checks/*.sh` не тронут** — резолвер уже
  зарегистрирован в `ACTIVE_MARKERS` (T-0740), гейт реагирует на сам ФАКТ
  вызова в теле роута.

## 1. Проблема

Судьи T-0740 + T-0726 подтвердили: `GET /api/inbox/:id` находил задачу через
`findInboxItems(actor)` — tenant-scoped, БЕЗ ролевого фильтра и без единого
authority-резолвера в достижимом графе роута. `actor-active-route-
coverage.sh` (FF-726-1) показывал ровно 1 находку на базе `dev@99b590c8`:

```
FINDING [FF-726-1]: inbox.ts:GET:/api/inbox/:id (lines 1708-1840) — no ACTIVE_MARKERS hit ...
SUMMARY: 77 GET routes audited — 21 marker-covered, 55 whitelisted, 1 findings
```

Последствие: держатель ещё живого access-JWT (T-0702, ~300s остаточное
окно) — деактивированный, посторонний член тенанта, или просто любой
знающий/угадавший `id` — получал 200 с полным содержимым задачи (`item` +
`projection`) по прямому запросу `GET /api/inbox/<id>`, независимо от того,
адресована ли она ему. LIST (`GET /api/inbox`) уже закрыт T-0738 через
`resolveRolesForActor` (композирует `getRoleSlugsForActor`, несёт
`ACTOR_ACTIVE_SQL` на обеих SQL-выборках) — это последняя находка гейта.

## 2. Разведка — как DETAIL адресует задачу

`item.role` — инвариант задачи («Role/position the task is ADDRESSED TO»,
doc-comment `InboxItem.role`), присутствует независимо от claim-состояния.
`item.pool` — решает **claim-eligibility** (T-0365: «pool tab» = адресат
может ВЗЯТЬ задачу), а НЕ read-visibility: как только задачу берут,
`pool` становится `false`, но `role` не меняется. `item.mine` — вычисляется
относительно ЗАПРАШИВАЮЩЕГО актора (`devUserId === claim.claimedBy`) уже
внутри `findInboxItems`, независимо от роли.

Критично: UI (`web/src/screens/screen-inbox.jsx` `renderTaskRow`) открывает
ОДИН И ТОТ ЖЕ `GET /api/inbox/:id` из ЛЮБОЙ вкладки (`all`/`mine`/`pool`/
`esc`) для ЛЮБОЙ строки — `onClick={openDetail}` на каждом `<tr>`,
безусловно. Существующий юнит-тест (`inbox-detail.test.ts`, «200 + item
shape for a known seed task») открывает `list.items[0]` (первая строка
дефолтной `tab=all`, НЕ пул, НЕ mine — `t1`, `execType:"agent"`, роль
`fin-appr`) актором `e-larina`, который **держит** роль `fin-appr`, но НЕ
взял и не может взять эту (агентскую) задачу. Это доказывает: продукт УЖЕ
трактует «адресат» как «держит роль задачи», а не «взял/может взять» —
сужение до `pool && myRoles.includes(role)` сломало бы этот тест (и реальный
клик по «all»/«esc» вкладке на непул-строке) — не security-фикс, а
регресс.

## 3. Решение — реюз резолвера LIST, три ортогональных допуска

`GET /api/inbox/:id` теперь вызывает **тот же** `resolveRolesForActor`
(inbox.ts:428-439, hand-verified T-0740 composes `getRoleSlugsForActor`,
`ACTOR_ACTIVE_SQL` на обеих SQL-выборках) — ни одного нового authority-пути.
Видимость (после того как `item` уже найден):

```ts
const detailTenantId = await resolveTenant(actor);
const myRoles = await resolveRolesForActor(actor, detailTenantId);
let isDetailOwner = false;
if (actor) {
  try {
    isDetailOwner = await isGenesisOwnerForTenant(getOrgPool(), detailTenantId, actor, Date.now());
  } catch { isDetailOwner = false; }
}
if (item.mine !== true && !myRoles.includes(item.role) && !isDetailOwner) {
  throw new HttpError(404, "NOT_FOUND", "task not found");
}
```

Три допуска, независимые и достаточные (`OR`):

1. **`item.mine === true`** — текущий claimant/assignee (тот же предикат,
   что LIST's `inTab("mine")`; независим от роли — claim переживает
   последующую смену роли, симметрично LIST).
2. **`myRoles.includes(item.role)`** — держит роль, на которую задача
   АДРЕСОВАНА, **безусловно к `item.pool`** (§2: role-addressing — инвариант
   задачи, `pool` решает только claim-eligibility). Это НЕ то же самое, что
   «pool»-вкладочный гейт (`pool === true && myRoles.includes(role)`) —
   узкое до pool-only сужение сломало бы (а) существующий юнит-тест §2,
   (б) реальный клик по «all»/«esc» вкладке на уже-взятой/агентской строке.
3. **`isGenesisOwnerForTenant`** — овершайт владельца тенанта; тот же
   deactivation-safe предикат (`org.ts`, `deactivated_at IS NULL` встроен),
   что уже реюзается в этом файле для orphan-claim
   (`isOwnerOrphanClaimEligible`, T-0744) — не bespoke SQL. Fail-closed:
   ошибка БД никогда не даёт bypass (try/catch → `false`).

Деактивированный актор отсекается **в обоих** ветках (2) и (3):
`getRoleSlugsForActor`'s `ACTOR_ACTIVE_SQL` (T-0738) резолвит `myRoles = []`
для деактивированного держателя роли; `isGenesisOwnerForTenant` независимо
несёт свой `deactivated_at IS NULL` (T-0658). Деактивированный
адресат/владелец с ещё живым остаточным JWT (T-0702) получает **тот же**
честный 404, что и посторонний.

## 4. Развилки

### 4.1 Отказ = 404, не 403

Тот же прецедент, что T-0721 (`GET /api/processes/:id`) и исходный T-0570
(`GET /api/records/:id`): honest-404, НЕ подтверждает существование ресурса
неавторизованному/деактивированному запросчику. Роут уже отвечал 404 для
«item не найден» (`if (!item) throw new HttpError(404, ...)`) — новая ветка
переиспользует **байт-идентичный** код/сообщение, отказ по авторизации
неотличим от отказа по отсутствию.

### 4.2 `myRoles.includes(item.role)` безусловно к `item.pool` — не только для непокинутых pool-задач

Разобрано в §2/§3 п.2 — единственная развилка, требовавшая эмпирической
проверки (не теоретическая). Узкий вариант (`pool && role`) МЕХАНИЧЕСКИ
предпочтительнее выглядел («ровно тот же предикат, что pool-вкладка»), но
сломал реальный существующий тест и реальный UI-путь. Широкий вариант
(безусловно к `pool`) — байт-совместим с текущим продуктовым поведением
везде, где оно уже проверяется тестами, и логически корректен (role — это
факт адресации задачи, а не факт её текущей доступности к взятию).

### 4.3 Владелец — добавлен, не в исходном судейском finding

Задача явно предложила рассмотреть `assignee ИЛИ владелец` в политике
видимости (сверка с LIST-логикой). `isGenesisOwnerForTenant` уже
используется в этом файле для ровно того же класса «владелец видит/делает
больше обычного члена» (orphan-claim, T-0744) — реюз без нового кода,
единственный резолвер, а не второй bespoke путь.

### 4.4 `ci/checks/actor-active-route-coverage.sh` НЕ тронут

`resolveRolesForActor`/`getRoleSlugsForActor` уже в `ACTIVE_MARKERS`
(T-0740, Group 2) — гейт текст-сканит ТЕЛО роута на упоминание маркера, не
владеет каталогом. Вызов `resolveRolesForActor(actor, detailTenantId)`
внутри блока `.register("GET", "/api/inbox/:id", ...)` **механически**
закрывает находку — ни единой правки `ci/checks/*.sh` не потребовалось.
Верифицировано живым прогоном (§6).

## 7. Отклонения от спеки

Нет. Задача явно предложила рассмотреть policy «роль-адресат ИЛИ assignee
ИЛИ владелец» — реализовано буквально (§3), выбор резолвера (а) вместо (б)
обоснован разведкой (§2: DETAIL адресует по РОЛИ, не по записи-источнику —
в отличие от `GET /api/processes/:id`, T-0721, у инбокс-задачи нет
`recordId`-based read-visibility прецедента, который был бы применим здесь;
`isRecordReadable` не реюзан, потому что задача не читает через запись).
