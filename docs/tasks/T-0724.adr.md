# ADR T-0724 — list_registries: introspection-тул конфигуратора, реюз DAO пикера

- **Статус:** реализовано (impl-фаза, coder)
- **Контекст:** T-0700 ревью (N1, "агент обязан угадывать targetRegistrySlug");
  `docs/tasks/T-0724.spec.md`
- **Область:** `src/core/assistant-configurator.ts`, `src/http/assistant.ts`

## 1. Решение

Один новый READ-ONLY тул конфигуратора, `list_registries`
(`TOOL_LIST_REGISTRIES`, `src/core/assistant-configurator.ts`), и ОДНА новая
функция-мост в HTTP-слое, `fetchRegistryListCandidates`
(`src/http/assistant.ts`), которая **реюзает `listRegistryDefs`
(`src/http/registry-defs.ts`) дословно** — ту же DAO, что `GET
/api/registry-defs` (человеческий бинд-пикер, T-0681) и `rights-resources.ts`
(T-0609) уже используют. Ни одной новой SQL-строки.

```ts
// src/http/assistant.ts
export async function fetchRegistryListCandidates(
  pool: pg.Pool,
  tenantId: string,
): Promise<RegistryListCandidate[]> {
  try {
    const rows = await listRegistryDefs(pool, tenantId, null); // ← реюз, не новый SQL
    return rows.map((r) => ({
      id: r.id, slug: r.slug, displayName: r.display_name, applicationId: r.application_id,
    }));
  } catch {
    return []; // honest-degrade — тул тогда честно отвечает «0 реестров»
  }
}
```

`processToolCall` (pure core) фильтрует этот предзагруженный список ЧИСТО по
`args.applicationId`, если он задан — никакого IO внутри core (файл остаётся
`PURE`, как заявлено в его собственной шапке).

## 2. Развилки и обоснование

### 2.1 Почему реюз `listRegistryDefs`, а не `fetchRegistryDefCandidates` (T-0463)

`src/http/assistant.ts` УЖЕ содержит функцию `fetchRegistryDefCandidates`
(T-0463) — но это ДРУГОЙ резолвер: собственная inline-SQL-строка (`SELECT id,
slug, display_name FROM choros.registry_def WHERE tenant_id = $1`), без
`application_id`, написанная для дедупа `relate_application`
(«есть ли уже приложение с таким именем»), НЕ для UI-паритета. Задача явно
требует реюз ИМЕННО резолвера человеческого пикера — им является
`listRegistryDefs`, не `fetchRegistryDefCandidates`. Две функции продолжают
сосуществовать (у них разные потребители и разные формы результата —
`fetchRegistryDefCandidates` не несёт `applicationId`, `list_registries`
без него бесполезен), но ОБЕ в итоге читают ту же таблицу через РАЗНЫЕ
пути — трогать/сливать их в этой задаче не требовалось (не входит в
критерии приёмки, расширило бы диф без необходимости, T-0463's own suite
осталась бы под риском регресса).

Альтернатива — переписать `fetchRegistryDefCandidates`, чтобы она тоже шла
через `listRegistryDefs` и производила ОБЕ формы данных одним запросом
(избежать второго round-trip к БД за ход диалога) — рассматривалась, но
ОТВЕРГНУТА: `fetchRegistryDefCandidates` тестово не покрыта своим собственным
suite'ом, трогать её ради чужой задачи — рассинхрон объёма (§5 роли coder,
«Реализуй ровно объём спеки»). Один лишний `SELECT` за ход диалога — не
архитектурная проблема (тот же паттерн `existingRegistryDefs`/T-0463
уже платит эту цену для СВОЕЙ выборки).

### 2.2 Контур прав — граница тенанта, не новый ACL

Разведка (`docs/tasks/T-0724.spec.md` §2.3) показала: `listRegistryDefs` не
имеет per-registry ACL — единственная граница — тенант (+опционально
приложение), обеспеченная RLS (`withTenantTx`). `rights-resources.ts`
(T-0609) уже реюзает ту же DAO и подтверждает это в своей шапке. Значит
паритет «бот ≤ человек» достигается АВТОМАТИЧЕСКИ переиспользованием той же
выборки — вводить отдельный PDP-слой для `list_registries` было бы (а) шире
объёма задачи, (б) создало бы РАССИНХРОН с человеческим пикером (пикер сам
никакого доп. PDP не проходит) — то есть сделало бы бота СТРОЖЕ человека,
а не паритетным, что тоже нарушение инварианта бот==человек (в другую
сторону).

Дополнительно: тул-цикл конфигуратора уже гейтится `hasAuthoringDraftGrant`
ДО любого тул-диспетча (строже, чем «просто аутентифицирован», что
достаточно для `GET /api/registry-defs`). `list_registries` наследует этот
гейт бесплатно — отдельной проверки внутри `processToolCall` не требуется.

### 2.3 Почему НЕ HTTP-роут, а тул внутри существующего цикла

`list_registries` НЕ регистрирует новый `POST`/`GET` — целиком живёт внутри
`CONFIGURATOR_TOOLS`/`processToolCall`, тем же путём, что все остальные тулы
конфигуратора. Данные (`registryListCandidates`) предзагружаются ОДИН РАЗ на
входящее сообщение (`src/http/assistant.ts`, рядом с `cfgCandidates`) и
передаются ЧЕРЕЗ `runConfigurator` → `runConfiguratorLoop` →
`processToolCall` — шестым по счёту параметром (после `existingRegistryDefs`,
T-0463), с default `= []` на каждом уровне, чтобы существующие вызовы (тесты,
другие потребители `handleConfigurator`) остались обратно совместимы без
правок сигнатур со своей стороны.

### 2.4 Форма результата — без лишних полей

`toolResultContent` тула — `{ status, applicationId, count, registries:
[{slug, displayName}] }`. Сознательно НЕ отдаётся `id` (raw UUID реестра),
`record_schema`, `created_at` и т.п. — LLM'у для заполнения
`targetRegistrySlug` нужен ТОЛЬКО `slug` (что писать) и `displayName`
(понять, какой реестр имеется в виду по имени пользователя) — то же самое,
что `registryTargetOptions` отдаёт человеческому пикеру
(`{value: slug, label: "<name> (<slug>)"}`, `web/src/screens/process-
catalog.js`). Меньше полей — меньше площадь для утечки нерелевантных
внутренних деталей в LLM-контекст (context hygiene, не только права).

### 2.5 Пустое приложение / пустой инжектированный список — честный ответ, не ошибка

И на уровне ядра (`registryListCandidates=[]` дефолт, фильтр по
несуществующему `applicationId` даёт пустой массив), и на уровне HTTP-моста
(`fetchRegistryListCandidates` ловит ошибку БД → `[]`) — тул ВСЕГДА
отвечает `{status: "ok", count: 0, registries: []}`, никогда не бросает.
Мотивация: пустой реестровый список для нового/только что созданного
приложения — ЗАКОННОЕ, частое состояние (не деградация), а честный "0" учит
LLM не звать `author_binding` с выдуманным `targetRegistrySlug`, когда
реестров ещё нет — тул сам сигнализирует «используй дефолтный реестр,
альтернативы нет».

## 3. Инварианты, которые сохранены

- `listRegistryDefs`/`GET /api/registry-defs` — БЕЗ ИЗМЕНЕНИЙ (byte-
  identical), реюз только на чтение.
- `TOOL_AUTHOR_BINDING`/`targetRegistrySlug` (T-0700) — БЕЗ ИЗМЕНЕНИЙ;
  `list_registries` — новый ПРЕДШЕСТВУЮЩИЙ шаг, не замена/не пересечение.
- `processToolCall` остаётся ЧИСТОЙ (никакого pg/http/fetch внутри core) —
  `keyed-digest-core-purity.sh`/`no-env-in-core.sh` гейты не задеты (новый
  код в `assistant-configurator.ts` не импортирует ничего запрещённого).
- `hasAuthoringDraftGrant` — единственный гейт прав перед тул-циклом,
  `list_registries` НЕ вводит второй.
- Анти-кейс (D-064 §5): фикстуры тестов нейтральные (`orders`/`invoices`/
  `t0724-*`), ни одного бизнес-кейс-литерала в `src/`.

## 4. Живое доказательство (что осталось непрожитым)

Серверная механика (реюз DAO, тенант-скоуп, фильтр по приложению, пустой
ответ) доказана unit (`src/__tests__/assistant-configurator.test.ts`,
AC-T724-1..5) и живым Postgres (`ci/checks/db/T-0724-list-registries-
candidates.db.test.ts`, два тенанта, RLS-изоляция). Непрожитым остаётся
LLM-звено — реальная модель, читая текст пользователя, действительно
вызывает `list_registries` ПЕРЕД `author_binding` и берёт слаг из ответа, а
не угадывает его. Стенд (Tailscale 100.121.76.86:3000) на момент сессии —
см. `live_proof_plan` в `T-0724.pr-handoff.json`.
