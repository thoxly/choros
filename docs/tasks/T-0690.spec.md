# T-0690 — Author-of-own-draft delete floor for applications

## Problem (P2 из live-proof T-0689)

`DELETE /api/applications/:id` (T-0566, `assertMayDeleteConfig`,
`src/http/applications.ts`) required `isOwnerOrAdmin` OR the `authoring_draft`
capability grant. A rank-and-file author who created their OWN **draft**
application (never published, never granted `authoring_draft` explicitly) got
`403 FORBIDDEN` trying to delete it — contradicting the product model
("draft = personal sandbox of the author", столп 5) and blocking cleanup: the
live-proof runs T-0684/T-0687/T-0689 all left test-app residue that had to be
removed by hand via SQL because the acting persona could not delete their own
throwaway draft through the API.

## Key finding — the DB had no authorship fact to check

`choros.application` (migration 003) carried no `created_by` column at all —
unlike `choros.record` (migration 005) and `choros.list_view` (migration 123),
which already carry a plain, unconstrained `created_by text` (actor slug).
There was no way to even ASK "who authored this application", so no per-row
self-service floor could exist prior to this task.

## Decision — mirror the T-0623 record floor, exactly

`records.ts`'s `deleteRecord` already ships the identical shape of floor for
`choros.record` (T-0623, столп-4): a non-privileged actor may delete a row they
created themselves; a config-privileged actor (owner/admin OR `authoring_draft`)
may delete any row. T-0690 reuses that EXACT authz shape for applications,
narrowed by the `tier` axis records don't have:

**A non-privileged actor may delete an application iff `created_by = actor AND
tier = 'draft'`, in their own tenant.** A config-privileged actor's authority is
unchanged (deletes anything, draft or published, exactly as before T-0690).

### Why `tier = 'draft'` is part of the floor (not just `created_by`)

"Draft = personal sandbox" stops applying the moment the application is
published — a published app is a shared, live artifact other actors may depend
on (bound processes, records, report pages). Publishing is the actor's own
deliberate promotion out of the sandbox; deletion authority contracts back to
owner/admin/authoring_draft at that point, symmetric with the `tier_published_
locked` trigger (migration 049/050) that already locks direct UPDATE/DELETE of
published config rows outside the sanctioned `promoteTier` bypass.

## Migration — `133_application_created_by.sql`

```sql
ALTER TABLE choros.application
  ADD COLUMN IF NOT EXISTS created_by text NULL;
```

Additive, idempotent, no RLS/PK change (`known_tenant_tables.txt` unaffected —
same rule migration 049 already documents for tier). **Nullable, not backfilled**:
`createApplication` never wrote an `application.created` audit event, so there
is no honest source to derive historical authorship from — pre-migration rows
get `created_by = NULL`, which never equals any actor slug, so they stay locked
to owner/admin/authoring_draft (the unchanged, safe default). Only applications
created AFTER this migration (via the one HTTP create path, `POST
/api/applications`) carry a real author and can use the new floor.

## AC — the four boundaries, one test each

1. **Own draft → 204.** `created_by = actor`, `tier = 'draft'` → the actor may
   delete; full cascade (see below), `application.deleted` audit records the
   real actor.
2. **Own published → 403.** Same actor, same app, but `tier = 'published'` →
   still 403 for a non-privileged caller (the floor is draft-only).
3. **Someone else's draft, same tenant → 403.** `created_by ≠ actor` → 403
   regardless of tier.
4. **Authorship-slug match across tenants → 404, never leaks.** `tenantId` is
   resolved server-side from the AUTHENTICATED actor
   (`resolveActorTenant(actor)`) and is never client-supplied; the
   `FOR UPDATE`-locked existence read is `WHERE tenant_id = <actor's own tenant>
   AND id = $id`. A draft application in a DIFFERENT tenant, even one whose
   `created_by` happens to equal the caller's slug (name collision), is never
   even visible to the query — RLS + the tenant-scoped predicate win before
   `created_by` is ever compared. 404, not 403 (never confirms existence of a
   row the caller cannot reach).
5. **Regression (existing test, unchanged):** owner/admin deletes an app they
   did NOT author (`created_by = NULL` in the pre-existing cascade test fixture)
   → still 204. Proves `actorIsConfigPrivileged` short-circuits the new floor
   exactly as before — the privileged path is untouched code.

No TOCTOU window: existence, ownership (`created_by`), and tier are read in ONE
`SELECT ... FOR UPDATE` inside the same tx that performs the delete
(`deleteApplicationCascade`) — mirrors `deleteRecord`'s locked read exactly.

## Cascade completeness (mandatory check per the task)

Verified against the live schema (`information_schema` FK enumeration) which
tables reference `choros.application` and how:

| child table | FK column | `ON DELETE` | cascaded before T-0690? |
|---|---|---|---|
| `registry_def` | `application_id` | `NO ACTION` | yes — explicit `DELETE` (step 3d) |
| `process_app_binding` | `application_id` | `NO ACTION` | yes — explicit UNBIND (step 5) |
| `report_page` | `app_id` | `NO ACTION` | **no — gap, closed by T-0690** |
| `list_view` | `application_id` | `NO ACTION` | **no — gap, closed by T-0690** (list_views scoped via `registry_def_id` were already covered by that FK's `ON DELETE CASCADE`; only application-scoped list_views were missed) |
| `doc_page` | `app_id` (nullable) | `NO ACTION` | **no — gap, closed by T-0690** |

`report_page`/`doc_page`'s OWN dependents (`report_page_dep`, `doc_log`,
`doc_ref`) already carry `ON DELETE CASCADE` from their parent, so deleting the
three newly-covered rows is enough — no further explicit deletes needed.

This gap **pre-dates T-0690** (it affected owner/admin deletes too, since day
one of T-0566) and is not introduced by the authz change — but widening
deletion to ordinary draft authors makes the path exercised far more often in
practice (a draft app under active construction plausibly already has a
report page or a custom list view bound to it), and the task explicitly
mandates verifying "не оставляй сирот" for the cascade. Closed in the SAME
function, same tx, same FK-safe-order style as the rest of the cascade; audit
payload gained `report_pages_removed` / `list_views_removed` / `doc_pages_removed`
counters alongside the existing `records_removed` / `fieldsets_removed` /
`processes_unbound`.

**Not touched (deliberately out of scope):** `cross_app_ref`,
`registry_schema_history`, `template_dep`, `template_def` — already fully
handled by the pre-existing T-0566 cascade (registry_def-scoped, step 3c).

## Non-scope

- No frontend changes. `web/src` has **no** DELETE-application call site today
  (grepped `method:.*DELETE` + `applications/\${` — zero hits) — this is a
  pure backend authz fix; a "delete my draft app" UI button is a separate,
  unstarted follow-up.
- No change to the `authoring_draft`-grant privileged path (untouched code,
  covered by the existing owner/admin regression test — see AC #5 above).
- `created_by` is now also serialized in `GET`/`POST`/`PATCH` responses
  (`serializeApplication`) — additive field, mirrors `record`/`list_view`'s
  existing shape; no existing test asserts an exact/closed response shape that
  this would break (verified: `applications_crud.test.ts` +
  `sections_crud.test.ts`, 21/21 green).

## Incident note (unrelated to the code change, but load-bearing for the handoff)

During RED/GREEN verification a `git stash push`/`pop` cycle collided with a
CONCURRENT coder session in a sibling worktree of the SAME repository
(`task/T-0756`) — `refs/stash` is a single, repo-wide ref shared across all
worktrees of one `.git`, not per-worktree. The two sessions' stash entries got
swapped: T-0756's uncommitted `process-projection.ts`/`processes.ts`/
`components.jsx`/`screen-process-instance.jsx` changes landed in THIS
worktree's working tree, and this task's `applications.ts` fix landed in
T-0756's. Diagnosed via `git diff` comparison (T-0756's leaked copy of this
fix was byte-identical to the redone version — confirmed no content was lost),
resolved by restoring this worktree's foreign files to `HEAD` (after saving a
patch backup) and redoing this task's edits from scratch; T-0756's own
worktree was **not** touched (out of this task's write scope). See the final
handoff message for the full incident report — this is a factory-wide `git
stash`-in-shared-`.git` hazard, not specific to this task.
