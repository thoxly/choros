# T-0701 — Диагноз: `doc-regen.db.test.ts` таймаутит (5000ms flake)

**Роль:** diagnostician (фаза DIAGNOSE)
**Дата:** 2026-07-10
**Файл симптома:** `ci/checks/db/doc-regen.db.test.ts`
**Инфра:** локальный PG `localhost:55432` (docker `choros-postgres-1`), template `choros_test_template_1b66f57f`.

---

## 1. Симптом

`ci/checks/db/doc-regen.db.test.ts` временами превышает дефолтный per-test
таймаут vitest (5000 ms) и роняет полный прогон `npm run fitness:db` (1320/1322).
Флейк по описанию воспроизводился «в изоляции на чистом дереве» и портил
throughput CI (pre-existing флейк doc-pipeline).

Отдельные тесты внутри файла — не мгновенные: `F-2` (прогоняет REGEN **дважды**)
и `F-1` — самые тяжёлые. Они не детерминированно медленные: их время растёт
пропорционально задержке одного round-trip к Postgres.

## 2. Инструментовка (доказательство, не гипотеза)

Соло-прогон файла (`vitest run --dir ci/checks/db --no-file-parallelism doc-regen.db`,
warm-cache, idle) — 3 повтора **до фикса**:

| тест | pass 1 | pass 2 | pass 3 |
|------|-------:|-------:|-------:|
| F-1 (1 REGEN + чтения) | 1552 | 1160 | 1195 |
| **F-2 (2 REGEN)**       | **1968** | **2008** | **2021** |
| file total (17 тестов) | 8756 | 7989 | 8789 |

Профиль **одного** вызова `runRegen` (инструментованный tsx-скрипт против того же
живого PG, роль `choros_app`):

```
{ pageCount: 270, refCount: 1844,
  tSnap: 256.4, tRead: 50.4, tPlan: 15.2, tUpsert: 132.4, tRefs: 720.6 }
refs INSERTs = 1844 took 721ms (0.39 ms/ref); upserts = 270 took 132ms
```

Разбор: из ~1174 ms одного REGEN **721 ms (≈80 % DB-времени)** уходит на вставку
doc_ref. `src/db/doc-page-store.ts::setDocRefs` вставляла рефы **по одному
round-trip на реф** в последовательном `for (const ref of refs)` цикле —
**1844 отдельных `INSERT` round-trip'а на один REGEN**. `F-2` делает REGEN дважды
⇒ ~3700 round-trip'ов ⇒ ~2 s даже вхолостую.

## 3. Корень (root cause)

**N+1 write в `setDocRefs`.** Wall-clock теста ≈ (число round-trip'ов) ×
(латентность одного round-trip). Число round-trip'ов было зашито большим и
постоянным (1844/REGEN, 3700 для F-2). Латентность одного round-trip —
переменная: под нагрузкой полного `fitness:db`, при холодном FS-кэше и при
конкуренции за тот же Postgres (другие агенты гоняют свои db-тесты параллельно,
как и предупреждает задача) она растёт в 3–4×. Умножение большого постоянного
числа round-trip'ов на выросшую латентность и пробивает потолок 5000 ms — это и
есть механика флейка. Это не «медленный запрос» и не «отсутствующий индекс»:
одиночный INSERT дешёвый (0.39 ms), проблема — их **количество**.

`assembleStaticSnapshot` (256 ms cold / 65 ms warm — двойной обход 595 `.ts` +
обход репо за `.bpmn`) — вторичный CPU/FS-расход; он **не** зависит от латентности
PG, поэтому не является драйвером именно *флейка* (флейк = переменная величина).
Не трогаю (пропорциональность).

**root_class = product-defect.** Это одиночный дефект перформанса в продуктовом
store-хелпере Choros (`src/db/doc-page-store.ts`), а не системное правило фабрики,
которое надо править в инструкциях/ADR. Фикс — в коде продукта, задача бэклога
разработки, ровно как классифицирует роль diagnostician (§3).

## 4. Фикс

`src/db/doc-page-store.ts::setDocRefs` — цикл «один INSERT на реф» заменён на
**батчевый multi-row INSERT с чанкованием** (`CHUNK = 500`):

- `tenant_id` (`$1`) и `page_id` (`$2`) константны на весь вызов — переиспользуются
  каждой VALUES-строкой; на строку приходится 4 варьируемых параметра
  (`id, ref_kind, ref_target, created_at`). Bind-параметров на statement =
  `2 + 4·CHUNK` ≤ 2002 — далеко под лимитом Postgres 65535.
- Семантика сохранена **точно**: те же колонки, тот же
  `ON CONFLICT (tenant_id, page_id, ref_kind, ref_target) DO NOTHING`,
  тот же возврат `{ set: refs.length, deleted }`, тот же предшествующий DELETE
  «рефов не из планового набора».
- Round-trip'ы на рефы падают с `refs.length` (1844) до `⌈refs.length/500⌉` на
  страницу (≈1 на страницу, ~270 на REGEN).

Таймаут **не** поднимал: корень — амплификация round-trip'ов, а не легитимно
долгая работа.

## 5. Доказательство (после фикса)

Соло-прогон, 3 повтора **после фикса**:

| тест | pass 1 | pass 2 | pass 3 |
|------|-------:|-------:|-------:|
| F-1  | 995 | 860 | 997 |
| **F-2** | **1235** | **1401** | **1265** |
| file total | 6486 | 6003 | 6783 |

Повторный профиль одного REGEN после фикса:

```
{ pageCount: 270, refCount: 1844, tSnap: 237.1, tRead: 7.2, tUpsert: 149.3, tRefs: 323.0 }
POST-FIX: refs = 1844 took 323ms; upserts = 270 took 149ms
```

- `tRefs`: 721 ms → 323 ms (round-trip'ы на рефы 1844 → ~270 батчевых).
- Худший тест F-2: ~2021 ms → ~1401 ms. Запас до 5000 ms вырос с **2.5×** до **3.6×**
  (headroom под контеншн-латентность +44 %).
- Сиблинги, использующие тот же `setDocRefs`, зелёные и ускорены:
  `doc-reconcile.db` (15) 6518 ms, `doc-summary.db` (7) 4562 ms, `doc-pipeline.db` (24) 329 ms — 46/46 pass.
- `tsc --noEmit` = 0, `eslint src/db/doc-page-store.ts` = 0, `npm run build` OK.

## 6. Фальсифицируемость

- **Гипотеза:** флейк-таймаут вызван N+1 write-амплификацией в `setDocRefs`
  (число round-trip'ов ∝ числу рефов), а не медленным запросом/индексом.
- **Предсказание:** схлопывание 1844 INSERT-round-trip'ов в ~270 батчевых
  снижает время самого тяжёлого теста (F-2) минимум на ~25 % и убирает главный
  множитель латентности; ни один запрос не требует нового индекса.
- **Опровергается, если:** после батчинга F-2 не ускоряется значимо (⇒ узкое
  место было не в round-trip'ах рефов, а в снапшоте/upsert/плане), ЛИБО падает
  инвариант идемпотентности F-2 (`ref count stable across runs`) / закрытого
  словаря F-1 ⇒ батч изменил семантику. По факту: F-2 −30 %, все инварианты зелёные.

## 7. Вторичное наблюдение (вне скоупа T-0701)

`upsertDocPage` вызывается по одному round-trip на страницу (270/REGEN) — тоже
N+1, но: (а) возвращает per-page `action` и `resolvedId`, нужные вызывающему
циклу (счётчик `pagesUpserted`, решение о `appendDocLog`), поэтому батчинг
инвазивнее и меняет контракт трёх вызывающих (regen/reconcile/summary);
(б) это 149 ms против 721 ms у рефов — не доминанта. По проПорциональности не
трогаю; кандидат в follow-up, если doc-pipeline снова начнёт подпирать таймаут.
