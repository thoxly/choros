# T-0767 — isGenesisOwnerForTenant/loadAdminContext НЕ энфорсят T-0605 dual-control disjunct

Security/dual-control, substrate. Finding surfaced by T-0764's review (own
spec §3.2, `docs/tasks/T-0764.spec.md`): `isGenesisOwnerForTenant` and
`loadAdminContext` (`src/db/org.ts`) — the OWNER/ADMIN authority path that
SHORT-CIRCUITS the grant PDP — resolve `role_assignment` activity on
`confirmed_by IS NOT NULL` alone, unlike every other assignment-activity
reader (`getRoleSlugsForActor`/`getGrantsForSubject`, `src/db/grants-dao.ts`),
which additionally requires the T-0605 canonical disjunct
`(confirmed2_by IS NOT NULL OR proposed_by IS NULL)`.

## 1. The gap, precisely

T-0605 (`docs/handoff/T-0605.pr-handoff.json`) established the canonical
assignment-active predicate — a `role_assignment` row is PDP-active iff:

```sql
confirmed_by IS NOT NULL
AND (confirmed2_by IS NOT NULL OR proposed_by IS NULL)
AND in-window
```

The `OR proposed_by IS NULL` disjunct exists because a ROUTINE assignment
(never proposed through the escalation path) is active on one confirm even to
a critical role, while a genuinely ESCALATING (semi-confirmed) assignment —
`proposed_by` set, `confirmed2_by` still NULL — must stay inactive until a
DISTINCT second approver signs. This is enforced identically in
`getRoleSlugsForActor` and `getGrantsForSubject` (`grants-dao.ts`), and in the
JS-side equivalent in `rights-overview.ts`.

`src/db/org.ts`'s two resolvers never carried it:

- `isGenesisOwnerForTenant` — the single query resolving whether an actor
  holds `tenant-owner`.
- `loadAdminContext` — step 1 (an INLINED copy of the same owner-check query)
  and step 2 (loads ALL confirmed, in-window assignments for the actor, whose
  roles step 3 then mines for delegable `mgmt_object:*` grants).

All three queries carried `ra.confirmed_by IS NOT NULL` and the validity
window, but never referenced `confirmed2_by`/`proposed_by` at all.

**Why this matters more than an ordinary PDP gap:** owner/admin authority
resolved by these two functions SHORT-CIRCUITS the grant PDP entirely.
`capability-grants-dao.ts` (`canConfigureLlmConnection` /
`canActorOperateSystemAgents`), `validateAdminDelegation`, and ~11 seed-write
mgmt paths (`assertOrgObjectAuthority` in `seed-write.ts` / `user-mgmt.ts` /
`rights-intents.ts`) call `isGenesisOwnerForTenant`/`loadAdminContext` BEFORE
(or instead of) `getGrantsForSubject`. A row that was merely PROPOSED — one
signature short of the second, distinct approval T-0605 requires — would have
granted FULL tenant-owner authority (or full delegable `mgmt_object:*` admin
authority) through this path, even though the exact same row correctly
resolves as inactive through every other authority reader in the codebase.

**Status: real, but DORMANT.** T-0764's audit read all 58 `role_assignment`
INSERT sites in `src/` + `ci/checks/db/` individually against the T-0605
predicate: 44 honest (`proposed_by` NULL/omitted), 6 deliberate dual-control
test fixtures (none of them assign `tenant-owner`), 7 stale-shape seeds
(fixed in T-0764 to `proposed_by = NULL`) — zero live INSERTs anywhere set
`role_assignment.proposed_by` non-null today. No current write path proposes
a `tenant-owner` (or any) assignment through the two-approver flow. The gap
is a structural landmine: the moment any future feature lets a `role_assignment`
go through `proposed_by`-set semi-confirmation (e.g. an "assignment requires
2 approvers for elevated roles" feature, or a UI that reuses the existing
`grant`-level propose/confirm/confirm2 machinery at the assignment level),
`org.ts`'s owner/admin path would silently inherit a privilege-escalation
hole that every other authority reader in the codebase already closed.

## 2. Decision: (a) — close the gap in both resolvers, at the source

Chosen over the lock-test-only option (b). Rationale:

- **Dormant now ≠ dormant forever.** A lock-test pins today's absence of a
  live exploit path but does nothing to stop the NEXT feature from wiring a
  new `proposed_by`-setting write path straight into `org.ts`'s resolvers
  without ever re-deriving the T-0605 predicate — exactly the failure mode
  T-0764 flagged this as a "latent landmine" for. Fixing the resolver closes
  the hole structurally: any future write path automatically inherits the
  correct read-side gate, the same way `getRoleSlugsForActor`'s callers
  already do.
- **Every prerequisite condition the task asked me to verify held:**
  `assignmentActiveDualControlPredicate("ra")` reduces to `TRUE` whenever
  `proposed_by IS NULL` — the shape of every live row today (§4) — so the fix
  cannot narrow the CURRENT active genesis-owner's authority. There is no
  "this changes production behavior today" risk to weigh against the
  structural fix.
- **No bespoke re-derivation.** T-0605's predicate was already duplicated
  as an identical string literal in TWO places inside `grants-dao.ts`
  (`getRoleSlugsForActor`, `getGrantsForSubject`) — the exact whack-a-mole
  shape T-0662's `ACTOR_ACTIVE_SQL` was invented to stop for the deactivation
  predicate. Rather than adding a THIRD/FOURTH/FIFTH bespoke copy of the
  literal into `org.ts`, this task extracts a single named export
  `assignmentActiveDualControlPredicate(alias)` (`src/db/grants-dao.ts`,
  next to the existing `criticalGrantPredicate` precedent) and backfills
  BOTH of `grants-dao.ts`'s own call sites to use it too — so all FOUR
  `role_assignment`-activity queries in the codebase (2 in `grants-dao.ts`,
  2 in `org.ts`) now read from one source, not four copies of a string.

## 3. The fix

`src/db/grants-dao.ts` — new export, placed immediately after
`CRITICAL_GRANT_PREDICATE_BARE`:

```ts
export function assignmentActiveDualControlPredicate(alias: string): string {
  const p = alias ? `${alias}.` : "";
  return `(${p}confirmed2_by IS NOT NULL OR ${p}proposed_by IS NULL)`;
}
```

`getRoleSlugsForActor` and `getGrantsForSubject`'s own two occurrences of the
literal `(ra.confirmed2_by IS NOT NULL OR ra.proposed_by IS NULL)` are
replaced with `${assignmentActiveDualControlPredicate("ra")}` — byte-identical
generated SQL (verified: the existing unit test `grants-dao.test.ts`'s 30
tests, which assert against the literal SQL text via regex router mocks,
pass unmodified — see §5).

`src/db/org.ts` — the fragment is imported and appended to all three
`role_assignment` queries:

1. `isGenesisOwnerForTenant`'s single query — `AND ${assignmentActiveDualControlPredicate("ra")}`
   after the existing `confirmed_by`/window predicates.
2. `loadAdminContext` step 1 (the inlined owner-check, structurally identical
   query to #1) — same addition.
3. `loadAdminContext` step 2 (the assignment-load feeding step 3's
   `mgmt_object:*` grant mining) — same addition.

`loadAdminContext` step 3 (the per-role `mgmt_object:*` grant query) is
**deliberately untouched** — it is a separate axis (grant-row confirmation,
not assignment-row dual-control) and out of scope for this task; see §6.

## 4. No-op proof for the CURRENT genesis-owner path

Claim: for every `role_assignment` row that exists in production today (or
in any test fixture except the ones this task added), `proposed_by IS NULL`
— so `assignmentActiveDualControlPredicate` evaluates to
`(NULL IS NOT NULL OR TRUE)` = `TRUE`, i.e. a pure no-op AND clause. The added
predicate can only ever REMOVE rows where `proposed_by` is set AND
`confirmed2_by` is NULL — a shape T-0764's full audit already confirmed does
not exist in any live write path or the 58 audited seed files.

Proven two ways:

1. **Static**: T-0764's exhaustive audit (referenced above) — 58/58
   `role_assignment` INSERT sites individually read, zero with
   `proposed_by` set outside a deliberate dual-control fixture, and none of
   those 6 fixtures target `tenant-owner` or feed `loadAdminContext`/
   `isGenesisOwnerForTenant` (confirmed again in this task — see §5, "no
   regression in touched call sites").
2. **Live**: the new probe `ci/checks/db/T-0767-owner-admin-assignment-dual-control.db.test.ts`
   seeds THREE `role_assignment` shapes per resolver (routine
   `proposed_by=NULL`; semi-confirmed `proposed_by` set + `confirmed2_by`
   NULL; fully dual-confirmed `proposed_by` set + `confirmed2_by` set) against
   both a `tenant-owner` assignment (`isGenesisOwnerForTenant` +
   `loadAdminContext` step 1) and an admin-role assignment holding a
   delegable `mgmt_object:*` grant (`loadAdminContext` steps 2+3). The
   routine and dual-confirmed shapes assert **unchanged** (`true`/non-empty)
   behavior — AC-owner-2/3, AC-admin-2/3/4 — regression controls for the
   ACTIVE genesis-owner/admin path. Only the semi-confirmed shape asserts the
   NEW `false`/`[]` outcome — AC-owner-1, AC-admin-1a/1b.

## 6. What was found but deliberately NOT fixed here (scope discipline)

`loadAdminContext` step 3 — the per-assignment `mgmt_object:*` grant query —
has **no `confirmed_by`/`confirmed2_by` predicate on the `grant` row at all**:

```sql
SELECT g.id, ... FROM choros."grant" g
 WHERE g.tenant_id = $1 AND g.role_id = $2
   AND g.resource_type LIKE 'mgmt_object:%' AND g.delegable = true
   AND (g.valid_from IS NULL OR g.valid_from <= $3)
   AND (g.valid_until IS NULL OR g.valid_until > $3)
```

This is a SEPARATE, real-looking gap (an unconfirmed or single-approver
`mgmt_object:*` grant proposal would delegate admin authority through
`loadAdminContext`), but it is a GRANT-row confirmation axis (T-0397/T-0044's
`criticalGrantPredicate` + `confirmed_by`/`confirmed2_by` on `choros."grant"`),
not the T-0605 ASSIGNMENT-row axis this task was scoped to. Fixing it would
require deciding whether `mgmt_object:*` delegable grants are "critical" by
the T-0040/T-0044 classification (they plausibly always are, since they
delegate admin authority) and is a materially different investigation.
Flagged as a follow-up, not folded into this diff, per D-064 anti-scope-creep
discipline — a finding surfaced in passing gets its own task, not a drive-by
fix riding on an unrelated PR.
