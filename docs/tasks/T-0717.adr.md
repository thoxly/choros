# ADR T-0717 — RelatedProcessRow рендерит keyDemoted (не новый резолвер имён)

Статус: accepted. Контекст: `docs/tasks/T-0717.spec.md`.

## 1. Решение

`web/src/screens/screen-record-detail.jsx`, `RelatedProcessRow`:

```diff
 function RelatedProcessRow({ instance }) {
-  const { title } = deriveInstanceTitle(instance);
+  const { title, keyDemoted } = deriveInstanceTitle(instance);
   ...
-        <span style={{ ...valueStyle, color: 'var(--chs-color-accent)', fontWeight: '500' }}>
-          {title}
-        </span>
+        <span style={{ display: 'flex', alignItems: 'center', gap: 'var(--chs-space-2)', minWidth: 0 }}>
+          <span style={{ ...valueStyle, color: 'var(--chs-color-accent)', fontWeight: '500' }}>
+            {title}
+          </span>
+          {keyDemoted && (
+            <Mono style={{ fontSize: 'var(--chs-text-xs)', color: 'var(--chs-color-text-muted)' }}>
+              {keyDemoted}
+            </Mono>
+          )}
+        </span>
```

`Mono` уже импортирован в этот файл (`../components/components.jsx`) — ни
одного нового импорта. Стиль демотированного чипа (`fontSize: 'var(--chs-text-xs)'`,
`color: 'var(--chs-color-text-muted)'`) — байт-в-байт скопирован из
`screen-process-instance.jsx`'s собственного `keyDemoted`-рендера (строки
344-347), а не изобретён заново — одна и та же визуальная конвенция для
одного и того же поля контракта `deriveInstanceTitle`.

`deriveInstanceTitle` (`process-instance.logic.js`, T-0684) — НЕ ТРОНУТ. Это
намеренно: функция уже возвращает всё нужное (`title` + `keyDemoted`); дефект
был в том, что ОДИН из двух потребителей отбрасывал половину контракта, а не
в том, что резолвер сам недостаточен.

## 2. Отвергнутые альтернативы (реальный источник имени для source=engine)

Задача изначально просила «дать движковым процессам человеко-имя из BPMN
name / process-definition display». Разведаны и отклонены ДВА конкретных
источника:

### 2.1. Читать `config/flowable/processes/*.bpmn20.xml` на сервере

`config/flowable/processes/tel-linear.bpmn20.xml` РЕАЛЬНО содержит
`<process id="telLinear" name="Канонический линейный ТЭЛ" …>` — заманчиво
распарсить `name` за счёт уже существующего `tokenize()`
(`src/core/bpmn-xml-parser.ts`, тот же токенайзер, что
`bpmn-deploy-normalizer.ts` уже использует для поиска `<process>`-элемента —
переиспользование, не второй парсер).

**Отклонено**: `Dockerfile` (стадия `runtime`) копирует ТОЛЬКО `dist/`,
`web/dist/`, `migrations/`, `ops/docker-entrypoint.sh` — `config/` НЕ
копируется в образ вообще. На реальном развёрнутом стенде (контейнер) файла
физически нет; чтение вернуло бы `null` всегда, работая только при локальном
`npm run dev` из чекаутнутого репозитория. Решение, которое выглядит зелёным
локально и молчит на проде — хуже отсутствия решения (нечестный сигнал: код
"работает", но фактическое поведение на стенде, где живая находка T-0708 и
была замечена, не меняется ни на бит).

### 2.2. Живой запрос к Flowable REST (`GET /repository/process-definitions`)

Flowable РЕАЛЬНО хранит `name`, распарсенное движком из BPMN при деплое,
доступное живым GET-запросом — и движок доступен из контейнера (в отличие от
§2.1). Паттерн батч-запроса с honest-degrade + bounded deadline уже есть
(`overlayDetailLiveSteps`, `LIVE_OVERLAY_DEADLINE_MS`, `src/http/processes.ts`)
— технически воспроизводимо без второго резолвера, продолжением того же
`processes.ts`.

**Отклонено (SECURITY)**: `process_key` — НЕ Flowable-tenant-partitioned
идентификатор в этой системе. `deployBpmn`/`startInstance`
(`src/core/flowable-client.ts`) никогда не передают нативный Flowable
`tenantId` параметр; `resolvedKey` уникален только ВНУТРИ Choros-тенанта
(`src/http/process-defs.ts`: `getLatestVersion(client, tenantId, candidate)`
— коллизия проверяется per-tenant, не глобально). Если тенант A и тенант B
независимо создадут процесс с одинаковым slug-ключом (реалистично — оба
"approval" → "soglasovanie"/"approval" через `slugify-process-key.ts`),
Flowable трактует их как ОДИН ключ (вторая версия того же definition, а не
изолированный неймспейс). Резолюция имени по голому ключу — без tenant-safe
корреляции (например по `deployment_id`, которого у engine-only определений
`choros.process_definition` НЕТ по определению — иначе они не были бы
`source=engine`) — риск показать тенанту A человеко-имя ЧУЖОГО одноимённого
процесса тенанта B. Это РОВНО класс утечки, который T-0616 §F-1
(`resolveDefinitionNames` regression-pin, `ci/checks/db/process-projection.test.ts`)
закрывал для существующего резолвера; чинить это правильно означает СНАЧАЛА
дать Flowable-деплоям нативный `tenantId` (правка `flowable-client.ts` +
`process-defs.ts` + бэкфилл существующих деплоев) — самостоятельная задача с
собственным ADR, не P3-размера.

### 2.3. Почему выбранное решение безопасно от обеих проблем

`keyDemoted` = `instance.procId` — то же самое значение, что УЖЕ приходит в
каждом элементе `GET /api/processes?record=<id>` (существующий,
тенант-заскоупленный на сервере wire-контракт: `listInstanceProjections(pool,
tenantId)` под RLS, T-0301/T-0616 F-1). Рендер `keyDemoted` не читает НИ
локальный файл, НИ Flowable живьём — это чисто клиентская проекция уже
полученных, уже тенант-безопасных данных. Ноль новых серверных путей, ноль
новых межтенантных поверхностей.

## 3. Инварианты, которые сохранены

- AC «никогда голый ключ как PRIMARY» (`deriveInstanceTitle`'s собственный
  контракт) — не тронут: `title` остаётся честным generic «Процесс» для
  engine-only инстансов; `keyDemoted` — ВСЕГДА вторичный демотированный чип,
  никогда не заменяет `title`.
- `fallbackDefinitionName("telLinear") === "telLinear"` (FF-1, T-0616,
  `src/core/process-catalog-view.ts`) — не тронут; этот ADR не модифицирует
  ни один резолвер имён на сервере.
- Ноль новых HTTP/engine round-trips.
