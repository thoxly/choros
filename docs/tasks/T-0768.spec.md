# T-0768 — loadAdminContext step 3 carries NO grant-row dual-control predicate at all

Security/dual-control, P1, **LIVE** (not dormant — a real finding from
T-0767's own review, `docs/tasks/T-0767.spec.md` §6). `loadAdminContext`
step 3 (`src/db/org.ts`) — the query that loads delegable `mgmt_object:*`
grants for each of an actor's confirmed role assignments — carried **no
`confirmed_by`/`confirmed2_by` predicate on the `grant` row whatsoever**.
`getGrantsForSubject` step 3 (`src/db/grants-dao.ts`) already enforces the
correct T-0397 grant-row dual-control predicate on the exact same table; the
two paths had diverged.

## 1. The gap, precisely

T-0397 established the canonical grant-row-active predicate — a `grant` row
is PDP-active iff:

```sql
confirmed_by IS NOT NULL
AND in-window
AND (NOT <criticalGrantPredicate> OR confirmed2_by IS NOT NULL)
```

`criticalGrantPredicate(alias)` (`src/db/grants-dao.ts`, exported since
T-0675) is the fail-closed classifier for the four T-0040/T-0044 escalation
axes: (a) `operation IN ('approve','transition')`, (b) `resource_type =
'effect_resource' AND operation = 'invoke'`, (c) `operation = 'read'` with a
sensitive clearance marker, Q-2 `operation = 'read'` with a present-but-
garbage clearance marker.

`getGrantsForSubject` step 3 interpolates this predicate correctly (it is the
canonical resolver — every other PDP consumer routes through it). Before this
fix, `loadAdminContext` step 3's query was:

```sql
SELECT g.id, g.role_id, g.resource_type, g.resource_facet,
       g.operation, g.scope, g."constraint", g.delegable,
       g.granted_by, g.valid_from, g.valid_until, g.created_at
  FROM choros."grant" g
 WHERE g.tenant_id = $1
   AND g.role_id = $2
   AND g.resource_type LIKE 'mgmt_object:%'
   AND g.delegable = true
   AND (g.valid_from  IS NULL OR g.valid_from  <= $3)
   AND (g.valid_until IS NULL OR g.valid_until  > $3)
```

No `confirmed_by`, no `criticalGrantPredicate`, no `confirmed2_by` — the
window/delegable/prefix filters were the ONLY gate. Two distinct failure
modes stacked on top of each other:

1. **Single-confirmation bypass on CRITICAL grants** (the P1 named in the
   task): a `mgmt_object:tier_promote` grant with `operation = 'transition'`
   is CRITICAL by `criticalGrantPredicate` axis (a) — the exact literal
   `artifacts.ts`'s real tier-promote consumer checks
   (`defaultCheckTierPromoteGrant`, `src/http/artifacts.ts:230-241`). Proposed
   via `POST /api/grants` (`src/http/grants.ts` ~928, the escalating branch),
   it lands semi-confirmed: `confirmed_by = <first approver>`,
   `confirmed2_by = NULL` — by the T-0397 contract, NOT yet PDP-active. Before
   this fix it STILL reached `adminGrants`, and every consumer that trusts
   `loadAdminContext` (artifacts.ts tier-promote gate, `secret-handle.ts`,
   `llm-config.ts`, `seed-write.ts`, `agents.ts`, `user-mgmt.ts`,
   `rights-intents.ts` — the ~11 mgmt paths behind
   `assertOrgObjectAuthority`/`validateAdminDelegation`) authorized on ONE
   confirmation instead of the required two.
2. **Zero-confirmation gap** (found while building the live probe, §4): a
   grant with `confirmed_by IS NULL` — the migration-020/030/031 "proposed"
   contract state — was ALSO admitted, regardless of criticality. Defence-in-
   depth closed by the same fix (§3).

Failure mode 1 is **REAL, not dormant**: unlike T-0767's `proposed_by` axis
(no live write path sets it), `grants.ts`'s escalating-branch INSERT is the
live, reachable `POST /api/grants` write path for EVERY critical grant
proposal today — this is the day-1 shape a semi-confirmed critical
`mgmt_object:*` grant takes in production, not a hypothetical future feature.

## 2. Decision: reuse `criticalGrantPredicate`, mirror the T-0675 precedent

`criticalGrantPredicate(alias)` was exported in T-0675 specifically so a
SECOND authority path (the `application/read` gate in
`report-page-render.ts`) could enforce the identical T-0397 grant-row
predicate without re-deriving the four escalation axes — see that file's
own comment (`src/http/report-page-render.ts:294-311`) for the prior
occurrence of this exact bug class (`defaultCheckReadGrant` had the SAME
missing-`confirmed_by`/`confirmed2_by` shape T-0768 has now).

T-0768 is the SAME fix applied to a THIRD site: import
`criticalGrantPredicate` from `grants-dao.js` into `org.ts` (already
importing `assignmentActiveDualControlPredicate` from the same module, per
T-0767) and append the identical clause shape T-0675 used:

```ts
AND g.confirmed_by IS NOT NULL
AND (
      NOT ${criticalGrantPredicate("g")}
      OR g.confirmed2_by IS NOT NULL
    )
```

No bespoke re-derivation of the four axes — the SAME exported classifier
function `getGrantsForSubject` step 3 and `report-page-render.ts` both
already interpolate into their own canonical grant reads.

## 3. The fix

`src/db/org.ts`:

- New import: `criticalGrantPredicate` added to the existing
  `grants-dao.js` import line (alongside `assignmentActiveDualControlPredicate`).
- `loadAdminContext` step 3's grant query gains two clauses after the
  existing window predicates:
  ```sql
  AND g.confirmed_by IS NOT NULL
  AND (
        NOT <criticalGrantPredicate("g")>
        OR g.confirmed2_by IS NOT NULL
      )
  ```

Non-critical delegable `mgmt_object:*` grants (e.g. `mgmt_object:employee` /
`update`) are unaffected: `NOT criticalGrantPredicate` is `TRUE` for them, so
the `OR` short-circuits and `confirmed2_by` is never required — matching
every existing non-critical admin-grant fixture in the codebase (T-0658/
T-0767's `mgmt_object:employee`/`update` pattern) unchanged, as long as
`confirmed_by` is set (see §6 for the fixtures that needed a matching fix).

## 5. Unity of authority proof (AC-4)

For the SAME actor/role, `loadAdminContext.adminGrants` and
`getGrantsForSubject`'s mgmt_object-shaped, delegable subset resolve to the
**identical grant-id set** — `[dualConfirmedCriticalGrant, nonCriticalGrant]`
in the fixture, both before AND after accounting for every axis. This is not
a coincidence of the fixture: both queries now interpolate the SAME
`criticalGrantPredicate(alias)` function call and the SAME `confirmed_by IS
NOT NULL` literal — one classifier, two call sites, byte-compatible
predicate shape (the only structural difference is `role_id = $2` per-role
vs `role_id = ANY($2::uuid[])` batched, and `getGrantsForSubject` doesn't
pre-filter on `resource_type LIKE 'mgmt_object:%' AND delegable = true` since
it returns the full `Grant[]` — the test applies that same filter to its
result before comparing, matching what `loadAdminContext` itself pre-filters
in the query).

## 6. Fixture debt uncovered and fixed (three files)

Running the FULL `npm run fitness:db` after the fix (not just the targeted
sweep) surfaced three pre-existing `ci/checks/db/*.ts` fixtures that seeded a
`mgmt_object:*` grant via a raw `INSERT` **omitting the `confirmed_by`
column from the column list** — so it silently defaulted to `NULL`
(migration 030: `confirmed_by text NULL`, no default). These fixtures were
only ever "working" because `loadAdminContext` step 3 had no
`confirmed_by` predicate at all — i.e. they were unknowingly relying on the
exact bug this task fixes (failure mode 2, §1). All three test files
otherwise exercise ORTHOGONAL authority logic (agent-instruction promote
scope, schema-destructive apply gate, employee-account read-parity) — their
intent was clearly "an active, confirmed, delegable grant," not "test the
confirmation-state axis." Fixed by adding the missing column(s) with the
`'seed'`-convention values used throughout the rest of the codebase:

- `ci/checks/db/T-0645-agent-instruction-promote-scope.db.test.ts` — TWO
  grants fixed: `mgmt_object:tier_promote`/`transition` (CRITICAL — needed
  BOTH `confirmed_by='seed'` AND `confirmed2_by='seed2'` to stay a realistic
  "attacker already holds this authority" shape) and
  `mgmt_object:agent`/`update` (non-critical — `confirmed_by='seed'` only).
- `ci/checks/db/schema_change_api_ac7b.test.ts` — `mgmt_object:schema_destructive`/`apply`
  (non-critical — `confirmed_by='ac7b-test'` only, matching the file's own
  `granted_by` convention).
- `ci/checks/db/user-mgmt.db.test.ts` (T-0630) — `mgmt_object:employee`/`read`,
  no clearance marker (non-critical — `confirmed_by=<owner slug>` only).

None of these three fixes touch security-relevant assertion logic — they
only add the missing confirmation column(s) so the fixture represents the
state its own test narrative already claimed ("a confirmed, delegable
grant"). Re-run after the fix: all three files GREEN (§7).
