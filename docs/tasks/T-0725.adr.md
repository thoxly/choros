# ADR T-0725 — честная ошибка на мульти-привязке без пина (агентский шов document-ops)

Статус: accepted. Контекст: docs/tasks/T-0725.spec.md; ревью docs/../T-0711.review.md
(non-blocking finding N-1, §6); T-0711 ADR §2 (`docs/tasks/T-0711.adr.md`).

## 1. Решение

Добавлена ОДНА новая функция, `listProcessAppBindingCandidates`
(`src/db/live-form-schema.ts`), и ОДИН новый пре-флайт-гейт в
`POST /api/forms/document-ops` (`src/http/forms-document-ops.ts`), СТРОГО
аддитивно — ни одна существующая сигнатура/фолбэк не изменены.

```sql
-- listProcessAppBindingCandidates: перечисляет ВСЕ привязки процесса
-- (не LIMIT 1) для честного "сколько их?" — НЕ используется
-- resolveLiveRecordSchema (тот резолвер и его фолбэк — БЕЗ ИЗМЕНЕНИЙ).
SELECT pab.application_id, a.slug, a.display_name
  FROM choros.process_app_binding pab
  LEFT JOIN choros.application a
         ON a.tenant_id = pab.tenant_id AND a.id = pab.application_id
 WHERE pab.tenant_id = $1
   AND pab.process_key = $2
 ORDER BY pab.created_at ASC, pab.id ASC
```

Хендлер `document-ops` (после успешного `getBindingLayout`, ДО
`applyDocumentOp`/`classifyLayoutSave`):

```ts
if (!applicationId) {
  const candidates = await listProcessAppBindingCandidates(client, tenantId, processKey);
  if (candidates.length > 1) {
    throw new HttpError(422, "AMBIGUOUS_APPLICATION", /* лист кандидатов */);
  }
}
```

## 2. Детектор «мульти-привязка без пина»

**Детектор = COUNT(`process_app_binding` строк для `(tenant_id,
process_key)`) > 1 И `applicationId` отсутствует в запросе.**

- Запрос сам по себе (наличие `applicationId`) — единственный вход:
  присутствие ЛЮБОГО значения (валидного или нет) отключает гейт целиком —
  малформенный пин уже честно отклоняется РАНЬШЕ, на `assertUuidShape`
  (400 VALIDATION, до транзакции), так что до пре-флайта попадает либо
  `null` (не прислали), либо валидный UUID (прислали — гейт неприменим,
  дальше решает `classifyLayoutSave`/T-0711 — совпадает или честный 409).
- Считаются ВСЕ строки `process_app_binding` для `process_key`, без
  фильтра по `application_id` (в отличие от `resolveLiveRecordSchema`'s
  `LIMIT 1`) — это отдельный, более широкий запрос, специально для подсчёта.
- **1 привязка → гейт НЕ срабатывает** (независимо от пина) — единственная
  привязка однозначна по определению; фолбэк (или её же выбор) корректен.
- **0 привязок → гейт НЕ срабатывает** — не эта задача: `classifyLayoutSave`
  уже честно 409 WRONG_FLOOR через существующий fail-closed путь
  (`resolveLiveRecordSchema` возвращает `null` при отсутствии привязки).
  Дублировать эту проверку было бы вторым гейтом на тот же случай.
- **2+ привязки, `applicationId` отсутствует → 422 AMBIGUOUS_APPLICATION.**

## 3. Почему ПРЕ-ФЛАЙТ, а не правка фолбэка внутри `resolveLiveRecordSchema`

T-0711 ADR §2 уже разобрал и ОТВЕРГ вариант «ошибка на 2+ привязках без
пина» — НО глобально, для ВСЕХ вызывающих `resolveLiveRecordSchema`
(включая `floor1-editor.ts`/`/edits` и `FormBuilder`, у которых физически
нет пикера приложения в теле запроса). Там ошибка была бы регрессом: форма
просто перестала бы сохраняться, а взять пин ей неоткуда.

`document-ops` — единственный из этих каналов, где пин РЕАЛЬНО достижим
(агент может прислать `applicationId`, ему просто не обязательно). Поэтому
эта задача:

- **НЕ трогает** `resolveLiveRecordSchema`/`resolveLiveSchemaFieldKeys`/
  `resolveLiveCollectionSubKeys`/`classifyLayoutSave` — их сигнатуры,
  SQL и фолбэк остаются БУКВАЛЬНО как в T-0711 (проверено: T-0711 db-suite
  7/7 и unit-suite 7/7 зелёные без единой правки этого набора).
- Добавляет гейт КАК ОТДЕЛЬНЫЙ, дополнительный пре-флайт-шаг ТОЛЬКО в
  `forms-document-ops.ts`'s хендлере — единственном месте, физически
  способном заранее узнать «есть пин или нет» и решить «спросить» вместо
  «угадать».
- Это ровно тот follow-up, который T-0711 ADR §2 сам предсказал: «правильное
  лечение — протягивать пин и в эти каналы (follow-up), а не ломать их» —
  для `document-ops` протяжка уже была (T-0711); T-0725 добавляет «а если
  протянутого пина нет и он реально нужен — спроси, не гадай».

## 4. Текст ошибки — машиночитаемый + человеко-подсказка

```json
{
  "error": {
    "code": "AMBIGUOUS_APPLICATION",
    "message": "Process \"<processKey>\" is bound to 2 applications — pass applicationId to pick which schema this save targets (no pin means no guess). Candidates: <displayName|slug|id> (applicationId=<uuid>); <displayName|slug|id> (applicationId=<uuid>)."
  }
}
```

- **Машиночитаемая часть**: `error.code = "AMBIGUOUS_APPLICATION"` —
  стабильный, отличимый от `WRONG_FLOOR`/`NOT_FOUND`/`VALIDATION` — агент-
  драйвер может программно распознать «нужно уточнение» и, например,
  перечислить кандидатов пользователю или повторить запрос с конкретным
  `applicationId` без повторного похода за списком (все id уже в
  `message`).
- **Человеко-подсказка**: `error.message` — русский/английский текст роута
  не принципиален (роут уже смешивает языки в существующих сообщениях,
  например `WRONG_FLOOR`), но структура «что случилось → что делать →
  варианты» — та же, что `relation-cascade.ts`'s `ask`-паттерн
  («Несколько приложений с названием «X» — уточните…») и
  `assistant-configurator.ts`'s `edit_jsonschema` doc-комментарий
  («ambiguous → ASK, no guess»). Для КАЖДОГO кандидата: имя (display_name,
  фолбэк slug, фолбэк сам id) + явный `applicationId=<uuid>` — тот самый
  формат, который агент должен прислать повторно.
- HTTP-код **422** (не 400/409): well-formed запрос, семантически
  неисполнимый без доп. информации — тот же прецедент, что
  `floor1-editor.ts`'s `422 UNKNOWN_FIELD` (fieldKey не в привязке —
  однородная семья «структурно корректно, но неразрешимо без уточнения»),
  не путается с `WRONG_FLOOR` (409, контентная классификация Floor-1/2) или
  `VALIDATION` (400, форма запроса).

## 5. Единственная привязка — гейт НЕ ломает

Гейт читает `applicationId` только когда каллер его НЕ передал; в этом
случае решает по количеству. Один-единственный кандидат — гейт молчит,
дальше идёт РОВНО прежний путь (`classifyLayoutSave(…, null)` →
`resolveLiveRecordSchema` → детерминированный фолбэк на ту же единственную
строку). Доказано unit (`forms-document-ops-application-id.test.ts`, AC-d) и
live-PG (`T-0725-document-ops-application-id-gate.db.test.ts`, AC-d):
`PROC_SINGLE` без пина → `200`, поведение идентично T-0711.

## 6. Паритет бот==человек — что именно закрыто

- **Человек** (FormDesigner): пикер приложения структурно ВСЕГДА выбран,
  `selectedAppId` ВСЕГДА уходит на сервер (T-0711 review §1(а)) — сохранение
  ВСЕГДА против явно выбранной схемы. Не менялось этой задачей.
- **Агент, до T-0725**: мог прислать пин (опционально), на мульти-привязке
  без пина ТИХО получал схему старейшей привязки — возможно не ту, без
  сигнала.
- **Агент, после T-0725**: пин остаётся ОПЦИОНАЛЬНЫМ (агент по-прежнему НЕ
  ОБЯЗАН его слать — задача НЕ вводит required-параметр, это осталось бы
  разрывом контракта с существующими вызовами на одной привязке). Но когда
  омиссия пина РЕАЛЬНО неоднозначна (2+ привязки), агент либо (а) знает,
  какое приложение имеет в виду, и присылает `applicationId` — получает ТОТ
  ЖЕ результат, что человек с тем же выбором в пикере; либо (б) не знает —
  получает честный `422` с перечнем вариантов вместо тихого промаха. Асимметрия
  «человек всегда попадает в свою схему, агент может тихо промазать» —
  закрыта: агент либо попадает, либо честно блокируется, никогда не
  промазывает молча.

## 7. Инварианты, которые сохранены

- `resolveLiveRecordSchema`/`classifyLayoutSave`/`deriveFieldsFromLayout` —
  сигнатуры и поведение НЕ изменены (T-0711 остаётся source of truth для
  резолюции; T-0725 добавляет только пре-флайт-отказ ДО их вызова).
- `floor1-editor.ts`, `FormBuilder`, `POST /api/forms/binding`
  (человеческий путь) — НЕ изменены; их suites зелёные без правок.
- Один судья контента (`classifyFloorBoundary` через `classifyLayoutSave`)
  остаётся ЕДИНСТВЕННЫМ Floor-1/2 гейтом; новый `422`-гейт — это
  ПРЕДВАРИТЕЛЬНЫЙ структурный вопрос «какая схема?», решаемый ДО того, как
  контент-гейт вообще получает шанс сработать — не второй контент-гейт, а
  вопрос на уровень ниже.
- Анти-кейс: фикстуры тестов (`t0725-*`) нейтральны; ни одного
  бизнес-кейс-литерала в `src/`.
