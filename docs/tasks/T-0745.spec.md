замещения вариант (в) + T-0720/T-0731 честные тексты — уже смержены).

Реализует UX-часть рекомендации T-0729 (§3 вариант б, §6 второй follow-up):
предупреждение при выборе замещающего, не держащего роль, + вывод уже

Вариант (в) (роутинг+owner-claim) уже сделан T-0744 — эта задача НЕ трогает
`inbox.ts`/`executor-resolver.ts`. Вариант (а) (авто-эскалация) — дверь
фаундеру, не в этой задаче.

## 1. Объём (ровно из оценки, без расширения)

1. **Предупреждение.** При выборе замещающего в `SubstituteForm`/
   `SelfAbsenceForm` (`web/src/screens/rights/ra-intents.jsx`), который НЕ
   держит выбранную роль — inline-баннер: пока пул покрыт, ничего не меняется;
   если пул опустеет, задача уйдёт **владельцу тенанта** (T-0744 owner-claim),
   не замещающему — если нужно гарантировать доступ именно ему, есть чекбокс
   ниже.
2. **`force_tier2` в форму.** Чекбокс «выдать замещающему собственный
   временный доступ сразу» — пробрасывает существующий API-параметр
   `force_tier2` (`rights-intents.ts:744,1231`, уже валидируется и минтит
   Tier-2 grant; ноль новой серверной механики).

НЕ в объёме: аннотация каждой опции пикера «кто держит роль» (§3 вариант б
п.1 — заявлено оценкой как доп. UX, не названо в этой задаче явно; добавлять
не буду — соразмерность, ось 5). НЕ в объёме: variant (в) роутинг (T-0744,
уже сделано). НЕ в объёме: variant (а) авто-эскалация (дверь фаундеру).

## 2. Данные: нужен ли новый read? (да — минимальный, переиспользующий предикат)

Разведка (см. `docs/tasks/T-0729.assessment.md` §2.2/§7, `Как форма узнаёт
держателей роли`):

- `GET /api/org/tenant-state` (справочник employees/roles/departments,
  `useOrgDirectory` в ra-intents.jsx) — id+slug ТОЛЬКО, без role_assignment.
  Не годится: нет данных о держателях.
- `GET /api/rights/tenant-state` (`rights-overview.ts`) — для
  `can_manage=true` (админ/owner) отдаёт `roles[].assignments[]` со ВСЕМИ
  держателями каждой роли; но для `can_manage=false` (self-scope, обычный
  сотрудник) ассигнменты **намеренно фильтруются** к
  `employee_id = caller` (privacy) — держателей ЧУЖИХ ролей не видно. Это
  ломает self-absence для не-админа (ложный негатив: "не держит", хотя
  держит) — неприемлемо.
- `getHoldersForRole` (DAO, `src/db/grants-dao.ts:533`) — по role SLUG, уже
  используется executor-resolver'ом, но НЕ выведен по HTTP.

**Решение:** новый read `GET /api/rights/intents/substitution-coverage`
(`role_id`, `substitute_employee_id` query) в `rights-intents.ts` (тот же
файл, что уже пишет substitute/self-absence — не новый write-периметр,
`rights-ui-no-new-write.sh` матчит только POST на `grants|role-assignments`).
Гейт: тот же минимальный бар, что у self-absence-записи (`extractActor` +
`resolveTenant`, БЕЗ доп. admin-гейта) — иначе обычный сотрудник, заполняющий
«Я в отпуске», не смог бы получить предупреждение вовсе (self-service
паттерн уже существует: self-absence пишет без admin-гейта на само окно).
Запрос строит `holderSet` держателей роли ТЕМ ЖЕ предикатом, что уже дважды
используется в этом файле для определения tier (`role_assignment`,
`confirmed_by IS NOT NULL`, in-window) — БЕЗ исключения absent/substitute
(нам нужно знать держит ли САМ замещающий), затем вызывает
**T-0744's `substituteProvidesCoverage({ ttlGrantId: null, substituteEmployeeId },
holderSet)`** — буквальный реюз предиката (не новое определение "держит
роль"). Ответ: `{ role_id, substitute_employee_id, provides_coverage,
holder_count }` — минимален, ID держателей не палятся (только count).

## 3. Предупреждение: клиентское или серверное?

**Гибрид, но решающий сигнал — с сервера** (сервер вычисляет
`provides_coverage`, UI лишь рендерит): чисто клиентское было бы неточным
(клиент не имеет достоверных данных о держателях без нового read, см. §2);
чисто серверная advisory-валидация в ответе 201 (как в оценке §3 "advisory
`substitute_holds_role`") подошла бы для пост-сабмита, но предупреждение
нужно **до** сабмита (SubstituteForm требует все 5 полей до включения
кнопки — после сабмита поздно передумывать про `force_tier2`). Поэтому:
GET-read на каждое изменение (roleId, substituteId) — некритичный доп.
запрос (аналог уже существующего паттерна `useOrgDirectory`/dictionaries
fetch), не блокирует сабмит (баннер — не гейт, кнопка не дизейблится).
**НЕ блокирует** — легитимный паттерн (не-держатель как вежливый Tier-1
stand-in, пока пул покрыт) остаётся доступен без опции.

## 4. Текст (честность, консистентность с T-0720/T-0731)

Ноль жаргона «Tier-N» в видимом тексте (тот же принцип, что
`substituteResultMessage`/`selfAbsenceResultMessage`). Формулировка отражает
РЕАЛЬНОЕ поведение системы ПОСЛЕ T-0744 (не до): при опустошении пула задача
уходит **владельцу тенанта** (уже установленный в продукте термин —
`screen-org.jsx`/`screen-users.jsx` "владельцу тенанта"), не замещающему.
Чекбокс `force_tier2`: «выдать замещающему собственный временный доступ
сразу» + честный hint «ограниченный временный грант (не шире прав
замещаемой роли), независимо от того, есть ли другие держатели» — та же
формулировка, что уже используют статичные подсказки обеих форм
("ограниченный временный грант", "не шире").
