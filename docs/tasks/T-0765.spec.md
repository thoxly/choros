# T-0765 — mini-spec: fake-pool now gates ACTOR_ACTIVE by SQL TEXT, not just query shape

- **Task:** T-0765 (substrate, tests/fake-green, R-2 из ревью T-0759)
- **Origin:** `docs/tasks/T-0759.pr-handoff.json` `friction_events`/nits — the reviewer
  flagged (R-2) that the fake-pool the T-0759 unit tests run against does not actually
  gate on the SQL text of the ACTOR_ACTIVE predicate; it infers "deactivated" purely from
  the shared query SHAPE plus the `deactivatedSlugs` fixture list. Real guard coverage for
  the ACTOR_ACTIVE closure was therefore live-PG-only (`ci/checks/db/processes-read-visibility.db.test.ts`)
  and the fitness gate `actor-authority-deactivation-gate.sh` (FF-0662) — the pure-unit
  file (`src/__tests__/processes-read-visibility.test.ts`, fake pool, no live Postgres)
  was fake-green with respect to this specific predicate: deleting it from the prod SQL
  did not turn the unit suite red. Same class as T-0715 (jsdom mount-tests catching
  fake-green UI mocks) — a fake test double that infers the real system's behavior from
  something OTHER than the actual query it executes.

## 1. Diagnosis — how the fake-green happened

`src/http/process-projection.ts`'s `isInstanceParticipant` / `isInstanceParticipantBatch`
clause (1) (T-0759) issues a point lookup:

```sql
SELECT id FROM choros.employee
 WHERE tenant_id = $1 AND slug = $2 AND deactivated_at IS NULL LIMIT 1
```

(`deactivated_at IS NULL` == the named constant `ACTOR_ACTIVE_SQL`,
`src/db/actor-authority-gate.ts`.)

The unit test file's shared `makeFakePool` (T-0723/T-0759-era) routed this query — and the
byte-identical-shape lookup `getRoleSlugsForActor` issues for its own employeeId-resolve —
by matching the query's SHAPE alone:

```js
if (/FROM\s+choros\.employee/i.test(text) && !/role_assignment/i.test(text)) {
  const slugArg = Array.isArray(values) ? values[1] : undefined;
  if (typeof slugArg === "string" && !(opts.deactivatedSlugs ?? []).includes(slugArg)) {
    return { rows: [{ id: `emp-${slugArg}` }] };
  }
  return { rows: [] };
}
```

It never inspected `text` for the presence of `ACTOR_ACTIVE_SQL` — a slug in
`opts.deactivatedSlugs` was denied **regardless of what the SQL actually said**. A mutant
that deletes `AND ${ACTOR_ACTIVE_SQL}` from the prod point-lookup still matches this SAME
regex shape with the SAME `$2` argument, so the fake pool kept returning `{rows: []}` for
a "deactivated" slug even though the mutated query would, against a real Postgres, find
the row (a deactivated employee's row is never deleted — only `deactivated_at` is set;
removing the predicate from the WHERE clause makes the row visible again). The fake pool
was silently doing the predicate's job ITSELF, in JS, independent of whether the SQL under
test actually carried it — so the SQL text was untested. Confirmed empirically (§3):
deleting the predicate from the prod point-lookup left all 28 unit tests GREEN.

The class: a test double that re-implements the production invariant from a SEPARATE
source of truth (here: an out-of-band JS list keyed by query SHAPE) instead of deriving
its answer from the actual artifact under test (the SQL string) can never detect a
regression in that artifact — the double just keeps enforcing its own copy of the rule.

## 2. Fix — fake pool derives "gated?" from the SQL text itself

`src/__tests__/processes-read-visibility.test.ts`'s `makeFakePool` now imports the SAME
`ACTOR_ACTIVE_SQL` constant the prod code imports
(`import { ACTOR_ACTIVE_SQL } from "../db/actor-authority-gate.js"`) and checks
`text.includes(ACTOR_ACTIVE_SQL)` before applying `deactivatedSlugs` filtering:

```js
if (/FROM\s+choros\.employee/i.test(text) && !/role_assignment/i.test(text)) {
  const slugArg = Array.isArray(values) ? values[1] : undefined;
  if (typeof slugArg !== "string") return { rows: [] };
  const isDeactivated = (opts.deactivatedSlugs ?? []).includes(slugArg);
  const carriesActiveGate = text.includes(ACTOR_ACTIVE_SQL);
  if (isDeactivated && carriesActiveGate) return { rows: [] };
  return { rows: [{ id: `emp-${slugArg}` }] };
}
```

This mirrors real Postgres semantics honestly: a deactivated employee's row still EXISTS
(`deactivated_at` is set, the row is never deleted) — a bare `slug = $2` lookup WITHOUT the
predicate finds it regardless of deactivation status; only a lookup that actually names the
predicate excludes it. So:

- **Current prod code** (predicate present on all 3 point-lookup call sites — DETAIL's one,
  BATCH's two): `carriesActiveGate` is `true` for every one of them → `deactivatedSlugs`
  filtering applies exactly as before → all pre-existing T-0759 tests keep passing
  unchanged (§4).
- **Mutant** (predicate deleted from a call site): `carriesActiveGate` is `false` for THAT
  query → the fake pool now finds the row (active) regardless of `deactivatedSlugs` → the
  matched T-0759 "deactivated actor is denied" test(s) get a 200/visible result they assert
  against as 404/absent → RED (§3).

This is option (a) from the task brief — the fake pool now SIMULATES the predicate's
semantics from the query text, not from a slug-keyed side list. No option-(b) skip/comment
fallback was needed.
