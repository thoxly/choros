# T-0641 — lane/timer publish mappers: unprotected xmlns:flowable + draft-save mutation

Follow-up: T-0635 (P0-4, LIVE_PROOF T-0586). Столп 4 (агенты-с-правами) / столп 1
(движок). Приоритет 60.

## 1. Дефект (разведано по коду, не по спеке)

T-0635 fixed `agent-task-external-mapper.ts` (T-0460) so it (a) only runs at
publish time, on a local variable never written back to `bpmn_xml`, and (b)
guarantees `xmlns:flowable="http://flowable.org/bpmn"` is declared on
`<definitions>` before it stamps any `flowable:*` content — the modeler's
`choros-moddle-extension.js` registers ONLY the `choros` namespace, so a real
modeler export never carries `xmlns:flowable`; Flowable's deploy-time SAX
parser rejects an unbound `flowable` prefix with `AttributePrefixUnbound`.

`lane-role-mapper.ts` (T-0457) and `timer-escalation-mapper.ts` (T-0458) inject
the exact same kind of content — bare `flowable:candidateGroups="…"` attributes,
and (timer mapper) native `<timeDuration>`/`<timeDate>` timer bodies — but
neither ever called an `ensureFlowableNamespace`-style guard. WORSE: unlike the
agent-task mapper (relocated to publish-time-only by T-0635), both were still
invoked at **draft-save time** (`POST /api/process-defs`,
`src/http/process-defs.ts:512-540` pre-fix) and their transformed output was
persisted straight into `choros.process_definition.bpmn_xml`.

Confirmed by direct code read (`git log dev --oneline --grep="T-0641"` showed
only the T-0635 merge commit noting "lane/timer xmlns gap→T-0641" as an open
follow-up — not yet fixed):

- `grep -n "mapLanesToCandidateGroups\|mapTimerEscalation" src/http/process-defs.ts`
  showed both called ONLY inside the `POST /api/process-defs` handler
  (draft-save), never inside `publishProcessByKey`.
- Neither `lane-role-mapper.ts` nor `timer-escalation-mapper.ts` imported or
  called `ensureFlowableNamespace` (`agent-task-external-mapper.ts`).
- The pure mapper unit tests (`lane-role-mapper.test.ts`,
  `timer-escalation-mapper.test.ts`) never caught this because every fixture
  hand-declares `xmlns:flowable="http://flowable.org/bpmn"` up front — they
  test the string-rewrite in isolation, not the realistic no-namespace
  modeler-export shape T-0635's regression tests use.

### Two live defects

1. **AttributePrefixUnbound on publish.** A process with a lane (role wiring)
   or a timer/deadline event, but **no** `agentTask`, published with an
   UNBOUND `flowable` prefix — a real Flowable deploy rejects it. Only a
   process that ALSO happens to contain a fresh (not-already-external)
   agentTask was protected, because `mapAgentTaskToExternal`'s own namespace
   guard fired incidentally for the whole document.
2. **Draft mutation.** `POST /api/process-defs` persisted the
   lane/timer-transformed XML (bare `flowable:candidateGroups` / materialised
   timer bodies) into `bpmn_xml`, unlike every other publish-transform mapper
   post-T-0635. Re-opening that draft in the modeler risked the same class of
   "unparsable content" friction T-0635 fixed for agentTask (an unknown
   `flowable:*` attribute/element the choros-only moddle extension doesn't
   recognise), and made a lane/timer edit-then-republish non-deterministic
   (idempotency guards mask most cases, but the draft was no longer the
   author's literal input).

### Adjacent case (identified by the T-0635 skeptic, verified in code)

An agentTask that is **already** external (`flowable:type="external"` already
present — `mapAgentTaskToExternal`'s `alreadyExternal` skip path) never
triggers that mapper's own `wired`-conditional `ensureFlowableNamespace` call.
If the SAME document also has a lane or timer that injects
`flowable:candidateGroups`, the document is emitted with an unbound `flowable`
prefix even in a document that DOES contain an agentTask — because the one
mapper capable of guaranteeing the namespace never fires on this run. This
proves per-mapper guards are not sufficient; the fix must not depend on which
mapper actually happened to be the one that ran.

## 2. Chokepoint design (ADR)

**Decision:** one centralized, unconditional, idempotent
`ensureFlowableNamespace(...)` call in `publishProcessByKey`
(`src/http/process-defs.ts`), placed immediately AFTER every publish-time
mapper (lane → timer → agent-task → userTask-role, the full chain) has had a
chance to inject `flowable:*` content, and BEFORE `lintBpmn` /
`normalizeBpmnForDeploy` / `flowable.deployBpmn` see the document.

**Rejected alternative:** copy the `wired`-conditional
`ensureFlowableNamespace` guard pattern (already present in
`agent-task-external-mapper.ts` since T-0635, and in `user-task-role-mapper.ts`
since T-0642) into `lane-role-mapper.ts` and `timer-escalation-mapper.ts` too.
Rejected because: (a) it would spread the SAME guard logic across three (soon
four) files — the exact kind of duplication that let this bug slip through
once already; (b) it does not close the adjacent already-external case (§1) —
a per-mapper guard only protects the document when THAT mapper is the one that
emits new content in a given publish, not when an EARLIER mapper in the chain
already did.

`ensureFlowableNamespace` is already idempotent (no-ops when `xmlns:flowable`
is already declared — by any prior mapper's own guard, or by this chokepoint,
or by a hand-authored document), so calling it once, unconditionally, at the
end of the mapper chain is always safe and requires no `wired`-flag
bookkeeping in the caller. The pre-existing per-mapper guards in
`agent-task-external-mapper.ts` / `user-task-role-mapper.ts` are left in place
(harmless defense-in-depth, zero behavioural change, zero regression risk to
their own T-0635/T-0642 tests) — the chokepoint is the new AUTHORITATIVE
guarantee; the per-mapper guards are no longer load-bearing but are not worth
the risk of removing.

**Relocation:** `mapLanesToCandidateGroups` and `mapTimerEscalation` calls
moved out of `POST /api/process-defs` (draft-save) entirely — draft-save now
persists the author's `bpmnXml` verbatim, byte-identical, exactly mirroring
how T-0635 already treats `mapAgentTaskToExternal`. Both mappers now run
inside `publishProcessByKey`, chained on a **local** variable
(`row.bpmn_xml → lanedXml → timedXml → agentWiredXml → roleWiredXml →
publishXml (chokepoint)`), never written back to the `process_definition` row.

**Side-effect fix (necessary, not scope creep):** `buildUnfilledRoleWarnings`
(the advisory "role has no holders" publish warning) was reading
`row.bpmn_xml` — the raw draft. Once lane/timer relocate out of draft-save,
`row.bpmn_xml` no longer carries their `candidateGroups` at all (mirroring how
it never carried T-0642's `assignedRoleId`-derived ones either, a
pre-existing, unnoticed gap from that task). Switched to read the fully
publish-wired `publishXml` instead, so the warning now correctly covers every
`candidateGroups` source (lane, timer, agent-task-adjacent userTask, panel
`assignedRoleId`), not a subset.

## 3. Acceptance criteria

- **AC-1 (RED→GREEN gate 1)** A lane-only process (userTask in a named lane,
  no `agentTask` anywhere) publishes without `AttributePrefixUnbound`: the
  deployed XML `deployBpmn` receives declares `xmlns:flowable` AND carries the
  lane-derived `flowable:candidateGroups`.
- **AC-2 (gate 2)** A timer-only process (boundary timer + escalation target,
  no lane, no `agentTask`) publishes the same way: `xmlns:flowable` declared,
  native `<timeDuration>` body materialised, escalation-target
  `candidateGroups` wired.
- **AC-3 (gate 3)** `POST /api/process-defs` (draft-save) persists the
  author's `bpmnXml` byte-identically for both a lane-only and a timer-only
  document — no `flowable:candidateGroups`, no materialised timer body, no
  `xmlns:flowable` leaks into the persisted row. Publishing does not
  retroactively mutate the persisted draft. A `GET` after save round-trips the
  exact posted XML.
- **AC-4 (gate 4, adjacent case)** An agentTask already external
  (`flowable:type="external"` present, `alreadyExternal` skip path — its own
  guard silent) plus a lane wrapping a plain userTask still deploys with
  `xmlns:flowable` declared exactly once — proving the chokepoint, not a
  per-mapper guard, is what closes the gap.
- **AC-5 (regression)** All T-0635 (`process-defs.agentxml-draft.test.ts`,
  `agent-task-external-mapper.test.ts`, `process-defs.agentref.test.ts`) and
  T-0642 (`process-defs.usertask-role.test.ts`, `user-task-role-mapper.test.ts`)
  tests remain green, unmodified.
- **AC-6** `tsc --noEmit` clean; `lane-role-mapper.test.ts` /
  `timer-escalation-mapper.test.ts` (pure transform unit tests) untouched and
  green.
- **AC-7 (анти-кейс, D-064)** No new case-literal content under `src/`
  (`anti-case-lock.sh` clean against baseline — verified).

## 4. Вне скоупа

- Removing the now-redundant per-mapper `ensureFlowableNamespace` calls inside
  `agent-task-external-mapper.ts` / `user-task-role-mapper.ts` — left as
  harmless defense-in-depth (see §2); removing them is a pure cleanup with no
  behavioural upside and nonzero risk to already-merged T-0635/T-0642
  regression coverage.
- A live-proof against a real Flowable instance (this task's gates are unit
  gates against a mocked `FlowableClient`, matching the exact test discipline
  T-0635/T-0642 already established for this defect class — `deployBpmn`'s
  mock call arguments are the observable proxy for "would not have hit
  AttributePrefixUnbound at a real SAX parser").
