# T-0724 — list_registries: introspection-тул конфигуратора (реестры приложения)

Родитель: эпик E-FORMS T-0479. Источник: ревью T-0700 (N1, "агент обязан
угадывать targetRegistrySlug"). Приоритет: N1 из T-0700. Столп 5 (АГЕНТЫ-с-
правами-как-сотрудники, инвариант бот==человек).

## 1. Проблема (как есть, до задачи — разведано по коду, не по спеке)

T-0700 добавил `targetRegistrySlug` в схему инструмента `author_binding`
(`TOOL_AUTHOR_BINDING`, `src/core/assistant-configurator.ts`) — конфигуратор-
ассистент теперь МОЖЕТ привязать процесс к не-дефолтному реестру приложения,
чего раньше не мог в принципе (параметр не был объявлен в схеме). Но T-0700
дал только ПОЛОВИНУ паритета: человек в UI (`screen-processes.jsx`,
`BindProcessModal`) видит РЕАЛЬНЫЙ список реестров приложения в пикере
«Реестр результата» (`GET /api/registry-defs?application_id=...`) — ассистент
же обязан УГАДАТЬ точный `slug` реестра из текста разговора. Угаданный slug,
которого у приложения нет, сервер честно отклоняет
(`author_binding: реестр «…» не найден…`, `src/http/assistant.ts` case
`author_binding`) — но это узнаётся только ПОСЛЕ попытки, не ДО. Человек
никогда не оказывается в этой ситуации: его пикер физически не даёт выбрать
несуществующий реестр.

Асимметрия: человек ВИДИТ варианты и выбирает; бот ДОЛЖЕН ЗНАТЬ вариант
заранее (из памяти диалога, домыслить по названию) — бот≠человек, именно тот
класс дыр, что столп 5 требует закрывать.

## 2. Разведка

### 2.1 Схема тулов конфигуратора (как T-0700 добавил параметр)

`CONFIGURATOR_TOOLS` (`src/core/assistant-configurator.ts`) — фиксированный
список `ToolDeclaration` (OpenAI-совместимый function-calling формат), которые
LLM видит в каждом раунде `runConfiguratorLoop`. Все текущие тулы —
АВТОРСКИЕ (пишут в DRAFT): `create_application`, `relate_application`,
`author_binding`, `edit_jsonschema`, `emit_form`, `author_dmn`,
`generate_process`, `request_promote`, плюс `propose_plan` (планирует, не
пишет). READ-ONLY интроспекции — НЕТ НИ ОДНОЙ. `processToolCall` (тот же
файл) — ЧИСТАЯ функция (без pg/http/fetch, `PURE` — заявлено в шапке файла):
любые данные, которые нужны инструменту, ДОЛЖНЫ быть предзагружены HTTP-
слоем и переданы АРГУМЕНТОМ в `runConfiguratorLoop`/`processToolCall` — точно
так же, как `existingRegistryDefs` (T-0463, для дедупа `relate_application`)
уже устроен: HTTP-слой (`src/http/assistant.ts`) грузит ОДИН РАЗ на ход
диалога, core фильтрует чисто.

### 2.2 Откуда человеческий UI-пикер берёт список реестров

`BindProcessModal` (`web/src/screens/screen-processes.jsx`, T-0681) —
`useEffect` на смену `applicationId`:

```js
fetch(`/api/registry-defs?application_id=${encodeURIComponent(applicationId)}`, { headers: authHeaders() })
```

`GET /api/registry-defs` (`src/http/registry-defs.ts`, роут
`registerRegistryDefCrudRoutes`) читает через **`listRegistryDefs(pool,
tenantId, applicationId)`** — экспортируемый DAO (T-0609 УЖЕ реюзает его
дословно для `src/http/rights-resources.ts`, комментарий в файле прямо
говорит: «exported so src/http/rights-resources.ts can reuse the SAME tenant-
scoped read (no second registry-listing query invented)»). Это ТРЕТЬЕ место
реюза после T-0609 (rights-resources) — конвенция репозитория для «список
реестров» ОДНА функция, не своя SQL-строка на каждого потребителя.

Веб-слой конвертирует ответ через `registryTargetOptions(rows)`
(`web/src/screens/process-catalog.js`): `{ value: r.slug, label:
"<display_name> (<slug>)" }` — т.е. человек видит РОВНО пару slug + человеко-
имя, ничего больше (не raw UUID, не схему полей).

### 2.3 Контур прав (кто что видит)

`listRegistryDefs` — единственная граница: `WHERE tenant_id = $1 [AND
application_id = $2]`, выполняется внутри `withTenantTx` (RLS через `SET
LOCAL choros.tenant_id`). **Нет отдельного per-registry ACL** — любой
аутентифицированный актор тенанта, дошедший до этого роута (`withAuth`),
видит ВСЕ реестры тенанта/приложения. `rights-resources.ts` (T-0609)
подтверждает это в своей шапке: «reuses the EXISTING listApplications
… и listRegistryDefs … DAOs verbatim — both already RLS-scoped via
withTenantTx». Т.е. контур прав человеческого пикера = ГРАНИЦА ТЕНАНТА (+
опционально приложения), не более тонкая гранулярность.

Для бота это означает: `hasAuthoringDraftGrant` (уже вызывается ПЕРЕД любым
тул-диспетчем в `runConfigurator`/`handleConfigurator`) — строже, чем «просто
аутентифицирован» (нужен grant `authoring_draft` в пересечении agent∩user).
Любой актор, ДОШЕДШИЙ до тул-цикла конфигуратора, уже прошёл более строгий
гейт, чем тот, что стоит перед человеческим `GET /api/registry-defs`. Значит
переиспользование ТОЙ ЖЕ тенант-скоупнутой выборки для `list_registries` не
может дать боту БОЛЬШЕ, чем видит человек — контур соблюдён по построению,
без нового ACL-слоя.

## 3. Решение

### 3.1 Новый тул `list_registries`

`TOOL_LIST_REGISTRIES` (`src/core/assistant-configurator.ts`) — READ-ONLY,
никогда не производит `ApprovedOp`/`BlockedOp`/`PendingPromote`.

- **Вход:** `applicationId?: string` (UUID). Пусто — перечисляются реестры
  ВСЕХ приложений тенанта (тот же режим, что `GET /api/registry-defs` без
  `?application_id=`).
- **Выход** (`toolResultContent`, JSON): `{ status: "ok", applicationId,
  count, registries: [{ slug, displayName }, …] }` — РОВНО та пара полей,
  что видит человек в пикере (`registryTargetOptions`), никаких лишних
  полей (id/схема/created_at не отдаются — не нужны боту, чтобы назвать
  `targetRegistrySlug`).
- **Пустое приложение → `count: 0, registries: []`** — честный пустой
  список, не ошибка.

### 3.2 Данные — предзагрузка тем же DAO, что и пикер

`fetchRegistryListCandidates(pool, tenantId)` (`src/http/assistant.ts`) —
вызывает **`listRegistryDefs(pool, tenantId, null)`** (реюз, НЕ новый SQL) и
мапит строки в `RegistryListCandidate { id, slug, displayName,
applicationId }`. Вызывается ОДИН РАЗ за ход диалога (рядом с уже
существующим `fetchRegistryDefCandidates` для T-0463 relation-cascade —
СХОЖИЙ, но не тот же вызов: `fetchRegistryDefCandidates` не несёt
`applicationId`, нужен только `list_registries`). Honest-degrade на ошибке
БД → `[]` (тул тогда честно отвечает «0 реестров», не 500).

`processToolCall` (чистая функция) получает `registryListCandidates` 6-м
параметром (после `existingRegistryDefs`) и фильтрует ЧИСТО: `applicationId`
задан → `registries.filter(r => r.applicationId === applicationId)`; иначе —
весь список. Никакого IO внутри core.

### 3.3 Как ассистент использует: list → bind

Системный промпт (`CONFIGURATOR_DEFAULT_SYSTEM_PROMPT`) учит: когда
пользователь просит направить результат шага в КОНКРЕТНЫЙ (не дефолтный)
реестр — СНАЧАЛА вызвать `list_registries` (реестры нужного приложения),
получить РЕАЛЬНЫЕ `slug`, и только ПОТОМ вызвать `author_binding` с
`targetRegistrySlug` из этого списка. `list_registries` объявлен В СХЕМЕ
`CONFIGURATOR_TOOLS` ПЕРЕД `author_binding` — символизирует порядок
использования, но LLM решает раунды сама (`MAX_TOOL_ROUNDS=5` уже
поддерживает многораундовый тул-диспетч — ничего нового здесь не нужно).

## 4. Acceptance criteria

- **AC-a** `list_registries` объявлен в `CONFIGURATOR_TOOLS`, `applicationId`
  — НЕ в `required[]` (опционален, как и `targetRegistrySlug` у T-0700).
- **AC-b** Тул НИКОГДА не производит `ApprovedOp`/`BlockedOp`/
  `PendingPromote` — чисто читает.
- **AC-c** Скоуп по `applicationId` — реестры ДРУГОГО приложения НЕ попадают
  в ответ (бот ≤ человек: тот же контур, что `GET /api/registry-defs
  ?application_id=`). Без `applicationId` — весь тенант (не шире, чем
  `GET /api/registry-defs` без фильтра).
- **AC-d** Приложение без реестров (или полностью пустой инжектированный
  список) → честный `count: 0, registries: []`, не ошибка/крэш.
- **AC-e** Живой Postgres: `fetchRegistryListCandidates` реюзает
  `listRegistryDefs` — реестр из ДРУГОГО тенанта НИКОГДА не попадает в
  результат (RLS/тенант-граница = тот же контур, что упирается человек на
  `GET /api/registry-defs`).
- **AC-f** Два раунда: `list_registries` → `author_binding` с
  `targetRegistrySlug`, взятым из ответа `list_registries` → `ApprovedOp`
  несёт этот slug дословно (реюз T-0700 pass-through, без изменений
  исполнения).
- **AC-g (анти-кейс, D-064)** Ни одного кейс-литерала (закупки/сделки/…) в
  `src/`; фикстуры тестов нейтральные (`orders`/`invoices`/`t0724-*`);
  `anti-case-lock.sh` зелёный без роста агрегата.

## 5. Вне скоупа

- Новый роут/HTTP-эндпоинт — НЕ нужен: `list_registries` целиком живёт
  внутри существующего тул-цикла конфигуратора (`POST /api/assistant/...`,
  роут не меняется, только данные, которые ему доступны).
- Изменение `listRegistryDefs`/`GET /api/registry-defs` — НЕ трогается,
  реюз дословный (T-0609-style).
- Отдельный ACL/PDP на уровне реестра — контур УЖЕ = граница тенанта (см.
  §2.3); вводить более тонкую гранулярность не требуется этой задачей и
  расходилось бы с тем, что видит сегодняшний человеческий пикер (было бы
  «бот < человек», не паритет).
- `list_applications` (аналогичный тул для приложений) — отдельный,
  несделанный разрыв (бот не знает `applicationId`, если сам не создавал
  приложение в этом ходе) — не входит в эту N1-находку T-0700, которая была
  ИМЕННО про `targetRegistrySlug`.
