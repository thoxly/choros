# T-0722 — mini-spec: LIST read-visibility filter for `GET /api/processes`

- **Task:** T-0722 (security/PDP, P2 follow-up из оценки T-0714)
- **Reads-through:** `docs/tasks/T-0714.assessment.md` (архитектурная оценка,
  опция (c), фаза 2), `docs/tasks/T-0721.adr.md`/`T-0721.spec.md` (фаза 1,
  DETAIL-гейт, УЖЕ смержена в базу этой ветки), ADR-T0570 (READ-PDP записей),
  product-decisions F2 (сущность = источник правды).

## 1. Проблема

`GET /api/processes` (LIST) отдаёт **всем** членам тенанта (и любому агенту
через тот же API — столпы 4/6) человекочитаемое имя процесса
(`definitionName`), текущий шаг (`node`/`nodes`), статус и **сырой `recordId`**
записи-источника — для **каждого** инстанса тенанта, независимо от того,
держит ли актор READ-грант на эту запись. Клиентский `RecordRef` смягчает
раскрытие ТАЙТЛА записи (сам гейтед READ-PDP T-0570, honest-404 → чип с сырым
UUID), но сырой `recordId` + метаданные инстанса **остаются в ответе API**
независимо от клиентской митигации — прямой вызов `curl`/агент получает их
без всякого смягчения. Это enumeration/existence-сайдченнел вокруг READ-PDP
записей (T-0714 §3 P2).

## 2. Объём (in scope)

Фаза 2 из оценки T-0714 (§5 опция c): **только LIST** (`GET /api/processes`).
DETAIL (`GET /api/processes/:id`) уже гейтится T-0721 (база этой ветки) —
не трогается повторно.

Гейтится: присутствие/отсутствие инстанса В СПИСКЕ целиком (весь объект —
`definitionName`, `procId`, `step`/`nodes`, `status`, `recordId`, и т.д.).
Инстанс, недоступный по READ-видимости его записи-источника, **не появляется
в массиве `instances`** — honest-narrow, не редакция отдельных полей (в
отличие от field-visibility, которая редактирует поля ВНУТРИ видимой строки;
здесь вся строка либо видна, либо отсутствует — нет частично-видимого
инстанса).

Вне объёма: Фаза 3 (process-definition-scoped read-грант для record-less
инстансов) — record-less инстансы остаются tenant-default-open, как и в
Фазе 1/до этой задачи (см. §4).

## 3. Дизайн (реюз, не bespoke)

Видимость LIST-строки = READ-видимость её записи-источника (`recordId`),
решается ЕДИНЫМ резолвером — **той же** authority-цепочкой, что DETAIL:

- `isRecordReadable` (`src/core/read-visibility.ts`, T-0570, pure) — без
  изменений, реюз as-is (третий потребитель после records.ts и
  process-projection.ts's DETAIL-гейт).
- `resolveReadVisibility` (`ProcessReadVisibilityResolver`,
  `src/http/process-start.ts`) — **уже** инжектирован на `StartInstanceDeps`
  T-0721-ом и **уже** wired в `src/server.ts` (byte-identical composition
  `getGrantsForSubject` + `loadTenantOrgAncestry` →
  `makeResourceAncestryOracle`). LIST-хендлер реюзит **ТОТ ЖЕ** `startDeps`
  объект DETAIL уже использует — **нулевые изменения в `server.ts`**: T-0721
  уже закрыла "wiring asymmetry" (`registerProcessesRoutes` получало
  резолвер), эта задача просто вызывает его из ВТОРОГО хендлера (LIST) на
  том же файле.
- `filterProjectionsByReadVisibility` — НОВАЯ функция в
  `src/http/process-projection.ts` (тот же модуль, что `isInstanceDetailVisible`
  — уже импортирует `pg`, `processes.ts` остаётся display-plane-pure,
  FF-DISPLAY-4/FF-7-3). Батчевая (не N+1) версия того же паттерна:
  1. Собрать DISTINCT `recordId` по всем `projections` (record-less и
     не-UUID-формы recordId исключены из батча — не трогают БД).
  2. ОДИН SELECT `choros.record r JOIN choros.registry_def rd ... WHERE
     r.tenant_id = $1 AND r.id = ANY($2::uuid[])` (`loadRecordRowAncestryBatch`,
     `withTenant`, tenant-scoped) — batched sibling of DETAIL's
     `loadRecordRowAncestry` (тот делает 1 SELECT на 1 инстанс; LIST не может
     себе позволить N SELECT на N инстансов).
  3. Фильтр `projections.filter(...)`: record-less → оставить (unnarrowed,
     см. §4); recordId резолвится → `isRecordReadable(...)`; recordId НЕ
     резолвится (удалена/foreign/malformed) → honest-drop.

`src/http/processes.ts` (LIST route handler, `GET /api/processes`) вызывает
резолвер + фильтр **ДО** `overlayDetailLiveSteps` (не тратит live-engine
round-trip на инстанс, который всё равно будет отброшен — тот же порядок,
что DETAIL уже применяет относительно `fetchInstanceHistoryDetail`) и **ДО**
сборки ответа.

## 4. Решения (проектные развилки)

### 4.1 Фильтр — SQL-уровень (батч), не пост-фильтр по уже собранной СТРАНИЦЕ

`GET /api/processes` **не имеет** клиентской пагинации сегодня (нет
`limit`/`offset`/`cursor` query-параметров, нет `total`/`nextCursor` в ответе
— `{ instances: [...] }` целиком). Риск "пагинация врёт счётчиком" (класс
бага, который T-0710 уже чинил для `?instance=`-скоупа: пост-фильтр ПОСЛЕ
`ORDER BY ... LIMIT 200`-окна `readEvents` мог давать ложный "не найдено" для
РЕАЛЬНО существующего инстанса, чьи audit-строки выпали за пределы
oldest-200-окна) здесь **не применим тем же образом**: `readEvents`'s
`limit=200` — внутренний safety-cap (не выставлен клиенту, не связан с READ-
PDP), пред-существующий и вне объёма этой задачи (не ухудшается этой
задачей — фильтр применяется К РЕЗУЛЬТАТУ уже-ограниченного фолда, СТРОГО
СУЖАЯ его, как и предыдущий `?record=`-фильтр T-0708 уже делает на том же
файле, `processes.ts:588`).

Вместо raw SQL WHERE (containment-математика `isNarrowerOrEqual`/`isEffective`
— НЕ SQL-выразимая, это тот же прецедент, что `records.ts:1975-1993`
документирует явно: "filter the already-loaded page ... no per-row DB call")
фильтр реализован как: (а) ОДИН батчевый SQL-запрос собирает ancestry для
ВСЕХ recordId разом (не N+1, не пер-инстанс round-trip); (б) чистая
in-memory предикат-фильтрация `isRecordReadable` над РЕЗУЛЬТАТОМ этого
запроса. Это тот же паттерн, что `records.ts`'s LIST READ-PDP (T-0570)
использует для СВОЕЙ (тоже настоящей, курсорной) пагинации — прецедент
внутри кодовой базы, не новая архитектура.

**Пагинация/счётчики после фильтра (§ГТЗ (б)):** отклик LIST не несёт
отдельного `total`/`count` поля — единственный массив `instances` **и есть**
финальный видимый набор, собранный ПОСЛЕ фильтра, ДО сериализации ответа.
Нет второго "число" для рассинхрона с ним.

### 4.2 Record-less инстансы — не сужены (симметрично Фазе 1)

Идентично `isInstanceDetailVisible`: `recordId === undefined` →
инстанс остаётся В СПИСКЕ безусловно. Явный запуск через
`/api/processes/start` (не `create=start`) сегодня не имеет
process-definition-scoped read-гранта в латтисе — сужать эту ветку означало
бы придумывать новый authority-объект (Фаза 3, `could`, вне объёма).

### 4.3 Malformed/foreign recordId — honest-drop, без запроса к БД

`loadRecordRowAncestryBatch` получает на вход только UUID-формы recordId
(pre-filtered `UUID_RE.test(v)` — переиспользует уже существующий в модуле
`UUID_RE`/`assertUuid`). Не-UUID recordId (legacy/malformed строка) **не
попадает** в `ANY($2::uuid[])` (иначе Postgres кинул бы cast-ошибку на ВЕСЬ
батч из-за ОДНОЙ плохой строки — не honest-degrade, а полный отказ списка) —
трактуется как "не резолвится" → honest-drop, не 500. Это строже, чем
`isInstanceDetailVisible`'s `loadRecordRowAncestry` (тот не пре-валидирует
форму — приемлемо там, т.к. ошибка одного `SELECT` для ОДНОГО инстанса
падает в существующий per-request try/catch DETAIL-хендлера и деградирует к
404, не роняя ничего чужого; для LIST тот же паттерн уронил бы ВЕСЬ список
одной плохой строкой — отсюда более строгая пре-валидация здесь).

### 4.4 Порядок относительно live-overlay и `?record=`-фильтра

READ-visibility фильтр применяется **ДО** `overlayDetailLiveSteps` (экономит
live-engine round-trip на отброшенных инстансах) и **ДО** существующего
`?record=`-фильтра T-0708 (`filterInstancesByRecord`, применяется после
маппинга в `ProcessInstance[]`, как и раньше — он и так только СУЖАЕТ уже
tenant-scoped список, теперь этот список ещё раз сужен READ-PDP до него;
порядок коммутативен для чистого пересечения множеств, но READ-PDP первым
избегает лишней live-overlay работы).

## 5. Honest-degrade (NF-2)

`startDeps.resolveReadVisibility` отсутствует → LIST **байт-в-байт** прежнее
поведение (только tenant-scope, без READ-PDP-сужения) — тот же контракт, что
DETAIL уже соблюдает.

## 6. Fitness-функции

- **FF-INST-VIS-3** (`ci/checks/process-list-display-plane-isolation.sh`):
  LIST-хендлер реально зовёт `filterProjectionsByReadVisibility(` (гейт
  wired, не только импортирован) — В ДОПОЛНЕНИЕ, `processes.ts` по-прежнему
  не импортирует `pg`/`src/db/*` (реюз/усиление FF-7-3 специально для НОВОГО
  LIST-кода этой задачи, не полагается только на существующий generic-чек).
- **FF-INST-VIS-4** (`ci/checks/process-list-tenant-scope-additive.sh`):
  READ-PDP предикат — ДОПОЛНИТЕЛЬНЫЙ `AND` внутри tenant-скоупа: вызов
  `filterProjectionsByReadVisibility(` в LIST-хендлере идёт ПОСЛЕ
  `listInstanceProjections(` (сужает уже tenant-scoped результат, никогда не
  заменяет его); батчевый `loadRecordRowAncestryBatch` сам tenant-scoped
  (`withTenant` + явный `WHERE tenant_id = $1`). Живой (live-PG) тест:
  актор тенанта A с широким READ-грантом не видит инстанс тенанта B в LIST.

## 7. Live proof

Два юзера на стенде: актор с READ-грантом на запись видит соответствующий
инстанс и в LIST, и в DETAIL; актор без гранта не видит его НИ там, НИ там
(список короче на одну строку, а не просто DETAIL этой строки 404-ит).
