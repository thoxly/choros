# ADR T-0732 — человеко-имя для движковых (source=engine) процессов из BPMN `<process name>`

**Задача:** O-1 из ревью T-0717 (эпик E16 T-0349, столп 2). Движковые процессы
(`source=engine` — задеплоенные прямо в Flowable из `config/flowable/processes/*`,
БЕЗ строки в `choros.process_definition`) различимы в UI лишь по camelCase-ключу
(`telLinear`) — machine-leak. Дать НАСТОЯЩЕЕ человеко-имя из реального BPMN
`<process name="…">`.

**Статус:** ready
**Runtime target:** сервер (GT-4) — читает/пишет `choros` PG на живом стенде; без
внешних ресурсов сверх уже используемых (PG + Flowable).

---

## 1. Разведка (по КОДУ, не по памяти) — что установлено

### 1.1 Как имя доходит до `deriveInstanceTitle` (web)
`web/src/screens/process-instance.logic.js::deriveInstanceTitle(instance)` (T-0684):
берёт `instance.name` и `instance.procId`.
- `name !== key` → primary = `name` (человеко-имя), key демотируется во вторичный `<Mono>`-чип.
- `name === key` (или name пуст) → primary = generic «Процесс», key демотируется. **AC «никогда голый ключ» свят.**

`instance.name` = `p.definitionName` (`src/http/processes.ts:270`), а `definitionName`
резолвит **`resolveDefinitionNames`** (`src/http/process-projection.ts:1143`):
```
SELECT name FROM choros.process_definition WHERE tenant_id=$1 AND process_key=ANY($2) …
```
для ключей без строки — `fallbackDefinitionName(key)` = **сам ключ**
(`src/core/process-catalog-view.ts:99`, T-0616 F-2 убрал ТЭЛ-хардкод; фолбэк теперь
единообразно = ключ). Поэтому у движкового процесса `name === procId === key` →
`deriveInstanceTitle` демотирует до «Процесс» + keyDemoted. **Это и есть дефект.**

`resolveDefinitionNames` — ЕДИНСТВЕННЫЙ общий резолвер: его зовут И
`listInstanceProjections` (список+деталь+`RelatedProcessRow`, симптом T-0717), И
`listInstanceInboxTasks` (инбокс `processName`). Один фикс покрывает три поверхности.

Каталог (`GET /api/process-catalog`) — ОТДЕЛЬНЫЙ путь: `buildCatalogDefinitions`
(`process-catalog-view.ts:116`, PURE) для движковых дефиниций ставит
`name = fallbackDefinitionName(key) = key`. Тоже machine-leak → тоже покрываем.

### 1.2 Где парсится BPMN и что реально в `<process name>`
Реальные значения в конфиге (DATA, не платформенный литерал):
- `config/flowable/processes/tel-linear.bpmn20.xml`: `<process id="telLinear" name="Канонический линейный ТЭЛ" …>`
- `config/flowable/processes/choros-smoke.bpmn20.xml`: `<process id="chorosSmoke" name="Choros Smoke Process" …>`

Есть готовый общий токенизатор `src/core/bpmn-xml-parser.ts::tokenize` (fail-closed,
энтити-декод, prefix-strip), которым уже пользуется `bpmn-deploy-normalizer.ts`. Им
и извлекаем `<process>`/`id`/`name` — не самописный regex.

### 1.3 Ключевые ограничения (два, оба ПОДТВЕРЖДЕНЫ кодом — T-0717 §review)
1. **`config/*` мёртв в проде** — не копируется в Docker `runtime`-образ (`Dockerfile`).
   Чтение BPMN в рантайме на стенде вернёт `null`. → имя надо ХРАНИТЬ в своей БД,
   писать в момент deploy (когда файл доступен), читать в рантайме из БД.
2. **Flowable `process_key` НЕ tenant-partitioned** — `deployBpmn`/`startInstance`
   (`flowable-client.ts`) не передают нативный Flowable `tenantId`. Резолв имени по
   голому ключу через живой `GET /repository/process-definitions` рискует показать
   тенанту A имя одноимённого процесса тенанта B — **класс утечки T-0616 §F-1**.
   → имя надо резолвить из СВОЕЙ tenant-scoped таблицы под RLS.

## 2. Решение и отвергнутые альтернативы

### Выбрано: **вариант (a′)** — отдельная tenant-scoped таблица-оверлей `choros.engine_process_name`

Хранит `(tenant_id, process_key) → name` для движковых (без modeler-строки) процессов.
`resolveDefinitionNames` и `buildCatalogDefinitions` консультируют её как СРЕДНИЙ ярус:
**modeler-строка → engine-оверлей → голый ключ (фолбэк keyDemoted)**.

Почему это — а НЕ буквальный вариант (a) «строка в `choros.process_definition`»
(предложенный задачей как «проще/безопаснее — но проверь по коду»): **проверка по
коду показала, что строка в `process_definition` РИППЛИТ и ЛОМАЕТ инварианты**, где
«движковый процесс = ОТСУТСТВИЕ строки» — это несущий контракт таблицы:
- `process-start.ts:351-353` (sandbox-гейт): `definitionIsDraft = hasDefinitionRow && !definitionPublished`. Любая новая строка со `status='draft'`/`'deployed'` → `hasDefinitionRow=true` → **обычные юзеры получают 409 SANDBOX_NOT_RUNNABLE на старте telLinear** (коммент :344-346 прямо гарантирует «directly-deployed без строки НЕ блокируются»).
- `inbox.ts:753-763` (draft-only-скрытие): строка со `status≠'published'` → ключ попадает в draft-only → **задачи telLinear скрываются из инбокса**.
- `process-catalog-view.ts:129-152` + `listProcessDefRows`: строка → движковый процесс переклассифицируется в `source='modeler'`, всплывает в модельере как редактируемая дефиниция (нужен фейковый `bpmn_xml NOT NULL`, `version`, `status`).
- CHECK `status IN ('draft','published')` не имеет значения для «engine».

Таким образом вариант (a) **НЕ проще/безопаснее**: он трогает 4 потребителя с
регрессионным риском в authz/видимости. Оверлей-таблица трогает РОВНО ОДИН
read-резолвер (+каталог) и НОЛЬ authz/видимости — тонкое ядро, логика на границе
(рубрика ось 5). Обе цели задачи достигнуты: своя tenant-scoped таблица обходит и
config-вне-Docker (пишем на deploy, читаем из БД), и Flowable-tenant-partition
(RLS + явный `WHERE tenant_id`).

### Отвергнутые альтернативы
| Вариант | Почему нет |
|---|---|
| (a) строка в `choros.process_definition` | Ломает sandbox-гейт (409 на старте), инбокс-draft-скрытие, каталог-классификацию — «движковый = нет строки» несущий инвариант (см. выше). |
| (b) живой `GET /repository/process-definitions` к Flowable на чтение | Flowable `process_key` не tenant-partitioned → межтенантная утечка имени (T-0616 §F-1). Плюс лишний сетевой хоп на каждый read. |
| Чтение `config/*.bpmn20.xml` в рантайме | `config/` не в Docker-образе → `null` на живом стенде (T-0717 §1a). |
| ТЭЛ-имя обратно в `fallbackDefinitionName` (хардкод в src) | Регресс T-0616 F-2 + anti-case-lock (репо-wide `telLinear` baseline). Имя обязано быть DATA, не платформенным литералом. |

## 3. Объектная модель / контракты

### 3.1 Таблица `choros.engine_process_name` (миграция 131 — схема; T-0013)
| поле | тип | прим. |
|---|---|---|
| `tenant_id` | uuid NOT NULL | ведущий в PK; RLS-предикат |
| `process_key` | text NOT NULL | Flowable/choros ключ (напр. `telLinear`) |
| `name` | text NOT NULL | человеко-имя из `<process name>` |
| `created_at` | bigint NOT NULL | ms |
| `updated_at` | bigint NOT NULL | ms |

PK `(tenant_id, process_key)`. ENABLE+FORCE RLS, ОДНА isolation-policy
`current_setting('choros.tenant_id', true)::uuid` (USING+WITH CHECK),
`GRANT SELECT,INSERT,UPDATE,DELETE … TO choros_app`, запись в
`ci/checks/known_tenant_tables.txt` (иначе `schema.test.ts` строгий-режим красный;
`cross_tenant.test.ts` автоматически покрывает RLS новой таблицы).

### 3.2 Миграция 132 — `@demo-seed` доставка имён на стенд (фикстура)
Идемпотентный `INSERT … ON CONFLICT (tenant_id, process_key) DO NOTHING` для DEV-тенанта
(`a0000000-…-0001`): `telLinear → «Канонический линейный ТЭЛ»`,
`chorosSmoke → «Choros Smoke Process»` — значения из `<process name>` соответствующих
BPMN. Помечена `@demo-seed` (skip при `CHOROS_SEED_DEMO=off`), тот же паттерн, что
085 (tel-binding seed). **Это фикстура (tenant-data), НЕ платформенный литерал** —
anti-case-lock сканирует `src/`+`web/src/`, НЕ `migrations/`. Это надёжная доставка
на прод (мигратор всегда исполняется; миграции ЕСТЬ в образе, в отличие от `config/`).

### 3.3 Чистый парсер (core) — общий deploy-time примитив
`src/core/bpmn-process-meta.ts`:
```
parseBpmnProcessMeta(bpmnXml: string): { processKey: string; name: string } | null
```
Через `tokenize`: первый `<process>` (open/self-close) с непустым `name` и `id` →
`{ processKey: id, name }`. `null` при отсутствии `<process>`/`name`, parse-error,
или пустых значениях. PURE, NO литералов имён процессов. Это механизм «парс
`<process name>` при deploy» — любой server-side deploy-путь (будущий эндпоинт /
расширенный acceptance-bootstrap) им парсит имя, затем зовёт `registerEngineProcessName`.

### 3.4 DB-хелперы (pg-слой) — общий резолвер (single source)
`src/db/engine-process-name.ts` (client-based → tenant-scope у ВЫЗЫВАЮЩЕГО, как весь
модуль process-projection):
```
registerEngineProcessName(client, tenantId, processKey, name, nowMs): Promise<void>
  // INSERT … ON CONFLICT (tenant_id, process_key) DO UPDATE SET name, updated_at
selectEngineProcessNames(client, tenantId, keys): Promise<Map<string,string>>
  // SELECT process_key,name … WHERE tenant_id=$1 AND process_key=ANY($2::text[])
```
Обе — ЯВНЫЙ `WHERE tenant_id=$1` поверх RLS (defense-in-depth, зеркало T-0616 F-1).
`selectEngineProcessNames` — ЕДИНСТВЕННЫЙ read-оверлей, зовётся из ОБОИХ дисплей-путей.

### 3.5 Read-врезки
- `process-projection.ts::resolveDefinitionNames`: внутри ТОГО ЖЕ `withTenant`-блока
  после `process_definition`-SELECT, для НЕрезолвленных ключей →
  `selectEngineProcessNames(client, tenantId, unresolved)` → затем `fallbackDefinitionName`.
  Порядок: modeler > engine-оверлей > ключ. Покрывает список/деталь/инбокс.
- `process-catalog-view.ts::buildCatalogDefinitions(defRows, projections, engineNames?)`:
  движковая ветвь `name = engineNames?.get(key) ?? fallbackDefinitionName(key)`. PURE.
- `process-catalog.ts` (handler): в `withTenantTx`-блоке резолвит `selectEngineProcessNames`
  по движковым ключам (те, что не в `defRows`) и передаёт map в `buildCatalogDefinitions`.

**Web НЕ трогаем**: `deriveInstanceTitle` уже корректно делает `name !== key → primary`;
keyDemoted-рендер (T-0717) на месте. Фикс чисто серверный — делает `name` настоящим.

## 5. Трассировка критериев приёмки

| AC | покрыто |
|---|---|
| deploy BPMN с name → tenant-scoped запись имени | `parseBpmnProcessMeta`+`registerEngineProcessName` (§3.3-3.4), db-тест round-trip |
| движковый процесс в деталке/каталоге → человеко-имя вместо keyDemoted | `resolveDefinitionNames`-оверлей (деталь/список/инбокс) + `buildCatalogDefinitions`-оверлей (каталог) (§3.5) |
| БЕЗ name в BPMN → фолбэк keyDemoted (не голый ключ) | парсер → `null`; резолвер → `fallbackDefinitionName`=ключ; `deriveInstanceTitle` демотирует (web не тронут) |
| межтенантно: тот же ключ в другом тенанте не течёт | FF-2, явный `WHERE tenant_id`+RLS, db cross-tenant тест |
| анти-кейс: имён процессов нет в src | имена только в BPMN-DATA + `@demo-seed` миграции (фикстуры); `anti-case-lock.sh` |

## 6. Границы / что НЕ делаем
- Не трогаем `process_definition`, `process-start` sandbox-гейт, инбокс draft-скрытие,
  каталог source-классификацию (движковый процесс остаётся `source=engine`).
- Не строим HTTP-эндпоинт deploy (несоразмерно P3): доставка имени на стенд —
  `@demo-seed` миграция; `parse+register` — переиспользуемый примитив (тесты + будущее).
- Не трогаем web (`deriveInstanceTitle`/keyDemoted уже верны — фикс чисто серверный).
