# T-0756 — Process → «Запись-источник»: read-through projection with per-hop ACL

Epic **E16** (UI-binding: triggers / entry-points / step-outcomes / **links**), parent **T-0349**.
Origin: live-proof **T-0691** capstone finding **P1** (RED).

## 0. Problem (from live-proof T-0691, browser, zero-bypass on the observed step)

On the process card `/processes/<inst>` the **«ЗАПИСЬ-ИСТОЧНИК»** block:

1. renders the source record as a **RAW UUID** (`a79e2602-…`) — no human title; and
2. `GET /api/records/<заявка>` returns **404** for the acting approver (200 only for the
   record's creator) → the person who just **acted on the process** cannot open, and cannot
   even *name*, the record the process is about.

The frontend primitive `RecordRef` (web/src/components/components.jsx) resolves the title by
fetching `GET /api/records/:id`; on **any** non-OK response it falls to
`<MonoId chip>{recordId}</MonoId>` — i.e. the raw UUID. So the 404 is the *direct* cause of
BOTH symptoms.

### 0.1 Why the record 404s while the process card is visible — the real mechanics

The DETAIL gate **T-0721** (`isInstanceDetailVisible`, process-projection.ts) already inherits
`GET /api/processes/:id` visibility from the source record's READ-visibility
(`isRecordReadable`, the T-0570 predicate). Its live-PG test **FF-INST-VIS-1a** pins: an actor
with **zero covering READ grant** on the source record gets **404 on the process detail**.

Therefore, since the acting approver **DID** see the full process card (history + starter, B5
screenshot), they **hold** a covering READ grant (`isRecordReadable = true`). Their
`GET /api/records/:id` 404 is then **NOT** READ-PDP — it is the **sandbox/draft gate**
(`getRecordDetail` + `sandboxReadPredicate`, T-0558): the source application is **draft-tier**,
the approver is neither its creator nor sandbox-privileged, so the record card is hidden from
them even though READ-PDP would allow it. (The record's *creator* passes via the creator-escape
→ 200.) This task's fix must be honest to **both** denial causes.

Independently, E16 §6 requires that a **participant** of a process — «действующий участник»,
someone entitled to act on the instance — sees a **read-through projection** of the source
record (human title + minimal orientation), never a hard 404 and never a raw UUID; the full
record stays under READ-PDP + the sandbox gate.

## 1. ADR — decision: per-hop ACL read-through projection on the process detail

### 1.1 The two-tier visibility model (E16 §6)

`GET /api/processes/:id` gains a **participant tier** beside the existing T-0721 detail tier:

| caller relation to instance | process skeleton (status/step/progress/starter) | variables / history / completedBy* | `sourceRecord` safe projection |
|---|---|---|---|
| **reader** — holds READ on source record (`isInstanceDetailVisible = true`, T-0721) | ✅ | ✅ (unchanged) | ✅ |
| **participant** — acts on the instance but lacks source-record READ (NEW) | ✅ | ❌ (withheld) | ✅ |
| neither | — | — | **404** (unchanged, fail-closed) |

- The **reader tier is byte-identical to T-0721** — variables/history stay gated by
  `isInstanceDetailVisible`, which is still called **before** `fetchInstanceHistoryDetail`
  (FF-INST-VIS-1c preserved). No new field is exposed to a reader beyond `sourceRecord`.
- The **participant tier** is NEW and additive: a participant who cannot READ the source record
  now sees the instance **skeleton** (id/status/step/progress/starter — exactly what the inbox
  already shows a participant: T-0750 inbox-detail precedent) + the **safe `sourceRecord`
  projection**, but **NO variables/history** (those stay reader-only). This closes the E16 §6
  gap without widening the T-0721 threat surface: the process's *working data* remains gated.
- **Non-participant without READ → 404**, identical to today (existence never confirmed).

### 1.2 Per-hop ACL — the participant relation (`isInstanceParticipant`)

An actor is a **participant** of instance `I` iff (tenant-scoped, fail-closed), reusing the
**already-merged** authority resolvers — no second authority math:

1. the actor **appears as an actor** in `I`'s append-only `audit_event` track (started /
   approved / claimed / next_task) — they **acted** on the instance; OR
2. the actor **holds the role** of a task ever addressed on `I` (`getRoleSlugsForActor`,
   grants-dao.ts — ACTOR_ACTIVE-gated, T-0738 — ∩ the instance's audit `task_role` set) —
   they are **eligible to act**; OR
3. the actor is the tenant owner (`isGenesisOwnerForTenant`, org.ts — deactivation-safe,
   T-0658).

A **deactivated** actor fails all three (ACTOR_ACTIVE_SQL on (2); `deactivated_at IS NULL` on
(3); an audit-actor match in (1) is a *past* action, but a deactivated participant with only a
past action and no live role/owner is still denied the *live* record projection because canOpen
= READ-PDP is separately fail-closed and the skeleton carries no source-record field data).

### 1.3 The safe source-record projection (`resolveSourceRecordProjection`)

`sourceRecord = { id, title, typeLabel, canOpen, appId? }`:

- **`title`** — the record's human title via `pickTitleFieldKey` (registry-title-field.ts, the
  schema-aware picker: explicit `x-title-field` → title-like key → first plain-textual field)
  applied to `record.data`, with a data-only fallback (first non-empty string scalar), else a
  neutral `«{typeLabel} · <id8>»`. This is the SAME product-standard record label full readers
  see — **one** field value (the designated title), never arbitrary/other fields.
- **`typeLabel`** — the governing `registry_def.display_name` (the record's *type*), never a
  case literal.
- **`canOpen`** — the record is actually openable by this actor = `isRecordReadable` (READ-PDP,
  T-0570) **AND** sandbox-openable (`actorIsPrivileged || tier ≠ 'draft' || created_by ==
  actor`, mirroring `getRecordDetail`'s `sandboxReadPredicate`). Only when `canOpen` does the UI
  offer the navigable «открыть» link. `actorIsPrivileged` = `resolveActorPrivilege`
  (sandbox-gate-dao.ts) — the SAME resolver records.ts falls back to.
- **`appId`** — `application_id`, included **only when `canOpen`** (the navigation target is
  meaningless when the record can't be opened).

Honest-degrade (NF-2): when `resolveReadVisibility` is not wired (pre-T-0721 posture),
`canOpen` degrades to sandbox-only (READ-PDP treated as open, matching records.ts's degrade).

### 1.4 Security boundaries (the invariants a judge attacks)

- **No full-record disclosure.** The participant tier exposes exactly `{id, title, typeLabel,
  canOpen, appId?}` — one designated title value + the type. `record.data` (all other fields) is
  **never** serialized on this path. The full record stays behind `GET /api/records/:id` (RLS +
  sandbox + READ-PDP + field-visibility), untouched.
- **Tenant/RLS untouched.** Every new read is tenant-scoped (`SET LOCAL choros.tenant_id` +
  explicit `tenant_id = $1`); RLS is the first, unconditional gate. Cross-tenant → the instance
  never resolves in the projection fold → 404 (NF-3).
- **Fail-closed.** Not a participant AND not a reader → the SAME `HttpError(404, "NOT_FOUND")`
  (FF-INST-VIS-1d). A DB error in any authority resolver denies (never grants).
- **Single authority path (FF-INST-VIS-2).** READ-PDP containment is ONLY `isRecordReadable`;
  role-eligibility is ONLY `getRoleSlugsForActor`; owner is ONLY `isGenesisOwnerForTenant`;
  sandbox privilege is ONLY `resolveActorPrivilege`. No bespoke grant/lattice math, no raw
  `choros."grant"` SQL in processes.ts / process-projection.ts / process-start.ts.
- **canOpen never over-promises.** It is `true` only when `GET /api/records/:id` would actually
  return 200 for this actor (READ-PDP ∧ sandbox), so the «открыть» link never dead-ends in a
  404 — the exact live-proof symptom.

### 1.5 Entry point choice

**In the process detail response** (`GET /api/processes/:id`), NOT a separate record endpoint.
Rationale: it reuses the already-merged T-0721 authority path in-place (the handler already
resolves `grants`/`ancestry`/`recordId`/`actor`/`tenantId`), keeps `processes.ts`
display-plane-pure (all pg lives in `process-projection.ts`, imported), and delivers the
projection to `RecordRef` **pre-resolved** so the frontend makes **no** `records/:id` fetch that
would 404 → no raw-UUID fallback. A participant reaches this response through the NEW participant
tier (§1.1); a reader through the existing tier.

## 2. Acceptance criteria (machine-checkable)

- **AC-1 (reader unchanged + projection).** A reader (covering READ grant) gets 200 with
  variables/history (T-0721 unchanged) **and** `body.sourceRecord = {id, title, typeLabel,
  canOpen:true, appId}` when the source app is published. *(live-PG)*
- **AC-2 (RED→GREEN core — participant sees safe projection, no 404).** A **participant** (holds
  the instance's task role, zero source-record READ grant) — who today gets **404** on
  `GET /api/processes/:id` (FF-INST-VIS-1a) — now gets **200** with the skeleton +
  `body.sourceRecord = {id, title, typeLabel, canOpen:false}` and **NO `variables`/`history`**.
  Reverting the participant tier → back to 404 → this assertion RED. *(live-PG)*
- **AC-3 (canOpen honest to sandbox/draft).** A reader whose covering READ grant passes but whose
  source app is **draft-tier** and who is **not** its creator → 200, `sourceRecord.canOpen ===
  false`, `sourceRecord.appId === undefined`, but `sourceRecord.title` present (the exact
  live-proof case). The record's **creator** → `canOpen === true`. *(live-PG)*
- **AC-4 (fail-closed).** A tenant member who is neither a participant nor a reader → **404**
  (unchanged). *(live-PG)*
- **AC-5 (no field leak).** On the participant tier, `JSON.stringify(body)` contains the title
  value but **none** of the record's other `data` field values, and no `variables`/`history`
  keys. *(live-PG)*
- **AC-6 (cross-tenant).** A tenant-A actor requesting a tenant-B instance id → 404. *(live-PG)*
- **AC-7 (record-less instance).** An instance with no `recordId` → no `sourceRecord` key; detail
  behaviour unchanged (T-0721 record-less = tenant-default-open). *(unit + live-PG)*
- **AC-8 (frontend — no raw UUID).** `RecordRef`, given a `projection` prop, renders `title`
  (never the raw UUID) — a link iff `canOpen && appId`, plain text otherwise; it makes **no**
  `records/:id` fetch. `screen-process-instance` passes `instance.sourceRecord`. *(web unit)*
- **AC-9 (anti-case / D-064).** No case slug/persona/business literal added under `src/` or
  `web/src/` (`role-approver`, `soglasovanie`, `tel-`, `Согласование`, `e-larina`, `e-orlov`,
  `telLinear`, …). Case lives in seed/tests only. *(fitness anti-case gates)*
- **AC-10 (isolation gates green).** `process-detail-read-gate.sh`,
  `process-detail-single-resolver.sh`, `read-pdp-*`, `actor-active-route-coverage.sh` stay green
  (isInstanceDetailVisible still precedes fetchInstanceHistoryDetail; single-resolver preserved).

## 3. Out of scope / boundaries

- The P0 triage-parking finding of T-0691 (create=start stalls at the agent step) is **T-0755**,
  not this task.
- Widening what **variables/history** a *reader* sees is out of scope — reader tier is
  byte-identical to T-0721.
- Process-definition-scoped read grants for **record-less** instances (T-0714 §5 phase 3) remain
  a follow-up.
- This task does **not** change the sandbox/draft gate itself (a draft app staying hidden from
  non-creators is correct); it only makes the process→record **link** honest about it (title +
  no dead «открыть» link).
