## Части и критерии приёмки

### Часть A — Сервер: query-параметры + пагинация (ЗОНА «Работа», ФУНДАМЕНТ) — СТРОИТСЯ СЕЙЧАС

`GET /api/processes` сейчас принимает только `?record=` (T-0708); ни поиска, ни фильтров,
ни пагинации — отдаёт всё разом.

- **AC-A1** `?q=` — регистронезависимый поиск по человеко-имени определения, ключу процесса,
  id инстанса и текущему шагу. Пустой/пробельный → нет фильтра.
- **AC-A2** `?definition=<procKey>` — точный фильтр по ключу определения.
- **AC-A3** `?status=<running|waiting|done|failed>` — точный фильтр по статусу.
- **AC-A4** `?started_from=`/`?started_to=` — границы по времени старта (epoch-ms ИЛИ ISO);
  инклюзивно; инстанс с неизвестным временем старта (seed/pack без numeric) границей НЕ
  отсекается (нельзя судить — «unknown проходит опциональный фильтр»).
- **AC-A5** `?mine=1` — только инстансы, запущенные ТЕКУЩИМ актором (`starterId === actorSlug`);
  инстанс без известного стартера при `mine` отсекается (честно: спросил свои).
- **AC-A6** `?limit=`/`?offset=` — серверная пагинация. `limit` clamp 1..200 (дефолт 200 —
  без пагинации поведение не регрессирует), `offset ≥ 0`. Ответ несёт `{ instances, total,
  limit, offset }`; `total` = размер отфильтрованного набора ДО среза (не фабрикуется).
- **AC-A7** Детерминированная сортировка: по времени старта DESC, tiebreak по id ASC —
  тотальный порядок (одинаковые входы → одинаковый выход, повторяемо).
- **AC-A8** Фильтры применяются ПОСЛЕ tenant-scoped-проекции → никогда не расширяют
  видимость (инвариант T-0708 сохранён). `?record=` продолжает работать и КОМПОНУЕТСЯ
  с новыми фильтрами.
- **AC-A9** Стартер на проводе: `InstanceProjection.starterActorId` (= `row.actor`);
  `ProcessInstance` дополнен additive-полями `startedAtMs`, `starterId`, `starterName`,
  `starterType` (имя резолвится батчем через `resolveActorsDisplay` T-0648, best-effort:
  недоступно → поле отсутствует, но `starterId`/`starterType` из проекции остаются).
- **AC-A10** Дисплей-плоскость чиста: `processes.ts` не импортирует `pg`/`src/db/*`
  (FF-DISPLAY-4/FF-7-3), live-overlay применяется ТОЛЬКО к странице (≤ limit engine-читок).

### Часть B — Web: экран «Процессы» = грид (ЗОНА «Работа») — ПРЕДЛОЖЕНО К ДРОБЛЕНИЮ (T-0654-b)

- **AC-B1** Инстансы в полноценном гриде (не скролл-щель): колонки из
  `PROCESSES_VIEW_COLUMNS` (name/process/status/started/actor), плотность из вида.
- **AC-B2** Серверные контролы: поиск (debounce), селект определения, селект статуса,
  диапазон дат, тумблер «мои» → передаются в query-параметры части A.
- **AC-B3** Пагинация: контрол «страница N из M» / load-more; читает `total`/`limit`/`offset`.
- **AC-B4** Стартер именем (`starterName`+`ActorChip`), а не только глиф типа.
- **AC-B5** Empty/Loading/Error честные; без мёртвых affordance; контраст ≥ WCAG AA обе темы
  (UX-гейт G2/G5/G7).
- **AC-B6** Каталог/связи с экрана «Процессы» УХОДЯТ (переезжают в часть C); экран
  «Процессы» = только живые инстансы оператора.

### Часть C — Web: «Каталог процессов» карточками (ЗОНА «Конструктор») — ПРЕДЛОЖЕНО К ДРОБЛЕНИЮ (T-0654-c)

- **AC-C1** Новый экран в зоне `constructor` (nav-config, capability `authoring_draft`,
  маршрут напр. `/process-catalog`), рядом с Модельером.
- **AC-C2** Определения карточками: имя, статус, версия(и), счётчик инстансов.
- **AC-C3** Клик по счётчику инстансов → экран «Процессы» с `?definition=<procKey>`
  (deep-link в грид части B).
- **AC-C4** Триггеры-связи ПРЯМО на карточке (третья таблица «Связи» исчезает).
- **AC-C5** Кнопки «В модельер» / «Правила ветвления (DMN)» на карточке.
- **AC-C6** Дубль «+ Новый процесс» убран (одна точка создания).
- **AC-C7** UX-гейты G2/G5/G7; без фейковых кнопок.

### Часть D — Деталка экземпляра (ЗОНА «Работа», доводка) — ПРЕДЛОЖЕНО К ДРОБЛЕНИЮ (в T-0654-b)

- **AC-D1** «Запущен: <Имя> (<тип>)» — стартер именем через `starterName`/`starterType`
  (часть A их отдаёт) + `<ActorChip>`.
- **AC-D2** «Связанные задачи» → ссылка `/inbox?instance=<id>`; инбокс сеет фильтр из URL
  (реюз серверного `?instance=` T-0710) + чип «задачи этого процесса».
- **AC-D3** Заголовок «Имя процесса · Запись-источник» ссылкой (поднять `<RecordRef>`).

## Дробление (рекомендация архитектора)

Полный T-0654 = 2 продуктовые зоны + ~1000 LOC нового UI (переписать один экран + новый
экран с nav). Это мега-диф для одного честного ревью. Разбито (порядок ОБЯЗАТЕЛЕН — часть C
deep-линкует в грид части B, поэтому B раньше C):

1. **T-0654-a (СЕЙЧАС)** — часть A: сервер query-параметры + пагинация + стартер-идентичность.
   Тонкое ядро, детерминированные db/unit-тесты, без UI. Разблокирует B и C.
2. **T-0654-b** — часть B (грид «Процессы») + часть D (доводка деталки). Одна связная
   «Работа»-история; потребляет часть A.
3. **T-0654-c** — часть C (Каталог, «Конструктор»-зона). Отдельный самодостаточный экран.
4. **Часть 3 спеки (модельер-имя) — НЕ задача: закрыта T-0684** (верификация в приёмке).

Анти-кейс (D-064): «рядовой без грантов конструктора находит СВОЙ процесс среди 200 по
имени заявки, фильтром `мои`+поиском, ни разу не увидев UUID, и открывает честную деталку
со стартером-именем».
