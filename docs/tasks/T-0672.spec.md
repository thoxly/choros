# T-0672 — «в истории процесса видно, КТО завершил шаг» (completedBy)

Столп 1/4 (движок / агенты-как-сотрудники). Приоритет 54. Вскрыто финальным
LIVE_PROOF T-0665/T-0648.

## 1. Разрыв (что было сломано)

Завершение userTask человеком через UI («Выполнить шаг» → `POST /api/inbox/:id/action`
`{action:"approve"}`) НЕ писало «кто завершил» в историю Flowable. `GET
/api/processes/:id` отдавал `completedBy: null` сразу после реального UI-завершения.

Рендер шага (`HistoryStepRow`, T-0648) и читатель — КОРРЕКТНЫ. Разрыв **выше по
потоку — на стороне ЗАПИСИ**:

- Читатель `src/http/processes.ts` (`fetchInstanceHistoryDetail`) мапит
  `completedBy: a.assignee`, где `a` берётся из
  `flowable.getHistoricActivityInstances(instanceId)` → поле `assignee`
  историка активности (`act_hi_actinst.assignee`).
- Писатель `src/http/process-projection.ts` (`reconcileInstanceEngineDrive`,
  пост-approve путь) звал `engine.completeUserTask(engineTaskId)` — **БЕЗ
  предварительного claim/set-assignee**. Flowable пишет `act_hi_actinst.assignee`
  ТОЛЬКО если задача была assigned/claimed; голый complete кандидат-групповой
  (не-assigned) задачи оставляет assignee = NULL.

Эмпирически подтверждено против `flowable/flowable-rest:7.1.0`:
- `POST {action:"complete"}` без claim → историк `assignee = null` (= баг).
- `POST {action:"claim",assignee}` затем `POST {action:"complete"}` →
  историк `assignee = <slug>` (= то, что читает `completedBy`).
- Повторный claim ТЕМ ЖЕ actor идемпотентен (HTTP 200).

## 2. Точка фикса

**`reconcileInstanceEngineDrive`** (`src/http/process-projection.ts`), ветка
`if (engineTaskId)` — единственная точка, где резолвится живая engine-task ДЛЯ
завершения (обе под-ветки: literal-defKey для `process.next_task` и
resolve-by-instance для базового `process.started` шага сходятся сюда).

Перед `completeUserTask` вставлен CLAIM на действующего актора:
`engine.setTaskAssignee(engineTaskId, args.actor)`.

`args.actor` = `extractActorSlug(req)` — employee-slug человека, нажавшего
«Выполнить шаг» (напр. `e-larina`). Ровно тот slug, который читатель резолвит
через `resolveActorsDisplay(tenantId, slugs)` в `completedByName`/`Type`.

Новый метод порта — `FlowableClient.setTaskAssignee?(taskId, assignee)` →
`POST {baseUrl}/runtime/tasks/{taskId}` body `{action:"claim",assignee}`.
OPTIONAL на интерфейсе `FlowableClient` и на `EngineDriveReconcilePort` (как
`getHistoric*`): десятки частичных тест-стабов и reconcile-on-read сеть (где
завершения нет) не требуют изменений.

### Гарантии
- **Best-effort + non-fatal.** Решение человека (`task.approved`) уже
  закоммичено выше по потоку; провал claim НЕ блокирует завершение — `completedBy`
  деградирует к до-фиксовому NULL (не хуже сегодняшнего) и логируется, НЕ
  всплывает как 502. Сохраняет контракт T-0571.
- **Идемпотентность re-click цела.** Claim выполняется только когда есть активная
  engine-task (`engineTaskId != null`). На re-click после завершения активных
  задач нет → `alreadyEnded`, claim не зовётся. Тот же actor re-claim = HTTP 200.
- **Инвариант T-0441 не задет.** `appendInstanceEnded` вызывается там же и только
  при `engine.isInstanceEnded` — claim/complete выше по коду не меняет этот путь.
- **defer-путь агента (T-0638) покрыт.** Там `actor` = человек-резолвер defer-карты
  → корректный «кто завершил».
- **Гвард пустого actor.** Claim пропускается для пустого/blank slug (не аттрибутим
  задачу пустому assignee), но задача всё равно завершается.

## 3. AC (acceptance criteria)

- **AC-1 (RED→GREEN, живой движок).** После реального завершения userTask через
  drive историк активности несёт `assignee = <actor>` (= `completedBy`);
  до фикса (та же прогонка со снятым `setTaskAssignee`) — `null`.
- **AC-2 (порядок).** `setTaskAssignee(engineTaskId, actor)` строго ПЕРЕД
  `completeUserTask` (Flowable пишет историк только если assignee стоит на момент
  complete).
- **AC-3 (обе ветки).** Claim происходит и на literal-defKey, и на
  resolve-by-instance (базовый шаг) путях.
- **AC-4 (non-fatal).** Провал claim → шаг всё равно завершается, результат — не 502.
- **AC-5 (backward-compat).** Порт-стаб без `setTaskAssignee` завершает как прежде.
- **AC-6 (идемпотентность).** Re-drive завершённого инстанса → `alreadyEnded`,
  ранее записанный assignee не затирается.
- **AC-7 (читательское поле).** `getHistoricActivityInstances(...).assignee` (объект,
  который потребляет `processes.ts`) несёт actor → `completedBy` резолвится.
