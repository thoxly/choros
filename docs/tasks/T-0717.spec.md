# T-0717 — «Процессы по этой записи»: движковые (source=engine) процессы неразличимы

Родитель: эпик E16 T-0349. Источник: LIVE_PROOF T-0708 (`docs/live-proof/T-0708.md`,
находка «P3, spec-compliant → follow-up T-0717»), стенд dev@ce792ded.
Приоритет: P3. Столп 3 (бесшовность) / D-064 (человеко-слой, никогда голый ключ).

## 1. Проблема (разведано по коду, не по спеке)

`deriveInstanceTitle` (`web/src/screens/process-instance.logic.js`, T-0684)
корректно НИКОГДА не показывает голый машинный ключ как заголовок: когда у
процесса нет реального человеко-имени (`instance.name === instance.procId` —
сервер честно эхоит ключ, `resolveDefinitionNames` /
`src/http/process-projection.ts` не нашла строки `choros.process_definition`
для этого `process_key`), функция возвращает `{ title: 'Процесс', keyDemoted:
<raw key> }` — тот же честный generic, что и `deriveProcessRefPrimary`/
`deriveStepLabel` используют для своих машинных ключей.

`keyDemoted` существует РОВНО для одной цели — дать вторичный, демотированный,
но ВИДИМЫЙ признак различения, когда primary-имя не различает. Он уже
корректно рендерится в `screen-process-instance.jsx` (карточка инстанса,
строки ~333-349 — `<Mono>{keyDemoted}</Mono>` мета-строкой под заголовком).

Но `RelatedProcessRow` (`web/src/screens/screen-record-detail.jsx`,
секция «ПРОЦЕССЫ ПО ЭТОЙ ЗАПИСИ», T-0708) деструктурирует ИЗ ТОГО ЖЕ
`deriveInstanceTitle(instance)` ТОЛЬКО `{ title }` — `keyDemoted`
отбрасывается целиком, нигде не рендерится (ни как текст, ни как title-атрибут).
Итог: запись с несколькими движковыми (`source=engine`, т.е. без строки
`choros.process_definition` — например `telLinear`, деплоенный напрямую в
Flowable из `config/flowable/processes/tel-linear.bpmn20.xml`, см.
`src/http/process-catalog.ts` header-комментарий) процессами показывает
несколько ВИЗУАЛЬНО ИДЕНТИЧНЫХ строк «Процесс» подряд — AC «никогда голый
ключ» соблюдён, но пользователь не может различить, какая строка — какой
процесс, не кликая в каждую по очереди.

Формулировка находки T-0708 упоминает и блок «Запись-источник»
(`screen-process-instance.jsx`, сайдбар инстанса, `hasSourceRecord`) — это
СОСЕДНИЙ, а не отдельно сломанный узел: `keyDemoted` там уже рендерится
(строки 344-347), «Запись-источник» — просто визуально СОСЕДНЕЕ поле в ТОМ ЖЕ
сайдбаре под тем же generic-заголовком. Разведка (grep всех 4 использований
`deriveInstanceTitle` в репозитории) подтверждает: `keyDemoted` теряется РОВНО
в одном месте — `RelatedProcessRow`.

## 2. Почему НЕ «дать движковым процессам настоящее человеко-имя» (рассмотрено и отклонено)

Задача изначально формулировалась как «дать движковым процессам человеко-имя
из BPMN name». Два кандидата на источник такого имени рассмотрены и ОБА
отклонены — см. ADR §2 для полного разбора:

1. **Локальный файл `config/flowable/processes/*.bpmn20.xml`** (в нём
   РЕАЛЬНО есть `<process name="Канонический линейный ТЭЛ">`) — но `Dockerfile`
   НЕ копирует `config/` в рантайм-образ (`COPY --from=app-builder /app/dist`,
   `web/dist`, `migrations/`, `ops/docker-entrypoint.sh` — и всё). На
   РЕАЛЬНОМ развёрнутом стенде (где и была живая находка T-0708) этот файл
   физически отсутствует — чтение сработало бы только в dev-чекауте
   репозитория, тихо ничего не давая в проде. Нечестное решение (работает в
   тесте, молчит в бою).
2. **Живой запрос к Flowable REST** (`GET /repository/process-definitions`,
   `name` резолвится движком из BPMN при деплое) — реально доступно и в
   контейнере. НО пространство `process_key` в Flowable ГЛОБАЛЬНОЕ, не
   тенант-партиционировано: `deployBpmn`/`startInstance`
   (`src/core/flowable-client.ts`) никогда не передают нативный Flowable
   `tenantId`, а `resolvedKey` (`src/http/process-defs.ts`) уникален только
   ВНУТРИ Choros-тенанта (`getLatestVersion(client, tenantId, candidate)`).
   Резолюция имени ПО ГОЛОМУ КЛЮЧУ рискует показать тенанту A человеко-имя
   ОДНОИМЁННОГО процесса тенанта B — межтенантная утечка ровно того класса,
   который T-0616 §F-1 (regression-pin) закрывал для `resolveDefinitionNames`.
   Без tenant-safe корреляции (напр. по `deployment_id`, которого у
   engine-only определений в `choros.process_definition` нет по определению)
   это небезопасно чинить в рамках P3.

Обе опции добавили бы либо мёртвый, либо небезопасный код — не
пропорционально задаче (соразмерность, ось 5). Follow-up на «безопасный живой
резолв движкового имени» — вне периметра (см. §5).

## 3. Решение

Чисто презентационный фикс в ОДНОМ месте, БЕЗ нового резолвера, БЕЗ нового
запроса: `RelatedProcessRow` начинает деструктурировать `keyDemoted` из ТОГО
ЖЕ вызова `deriveInstanceTitle(instance)`, который она уже делает, и рендерит
его тем же демотированным `<Mono>` (муted, `--chs-text-xs`), что уже
используется в `screen-process-instance.jsx` — одна и та же визуальная
конвенция для одного и того же поля в двух местах. `keyDemoted` рендерится,
когда присутствует (для процесса с реальным modeler-именем — тоже, зеркалит
поведение карточки инстанса: технический ключ — всегда доступная вторичная
трассируемость, не только fallback-заплатка).

Нулевые новые сетевые запросы: `procId` уже приходит в каждом элементе
`GET /api/processes?record=<id>` (тот же wire-контракт `ProcessInstance`,
`src/http/processes.ts`), `deriveInstanceTitle` уже вызывается — меняется
только то, какие поля результата используются на рендере.

## 4. Acceptance criteria

- **AC-1** Инстанс с реальным modeler-именем (`name !== procId`):
  `RelatedProcessRow` рендерит primary=имя + демотированный `keyDemoted` рядом
  (как раньше — рендерился только primary; теперь плюс мета-чип, не регресс).
- **AC-2** Движковый (`source=engine`, `name === procId`) инстанс: primary
  остаётся честным generic «Процесс» (AC «никогда голый ключ» не тронут), но
  теперь ВИДИМ демотированный `keyDemoted` (сырой `procId`) рядом — две строки
  РАЗНЫХ движковых процессов в одной секции визуально различимы по этому
  чипу.
- **AC-3** Инстанс без `procId` вовсе (edge-case, `keyDemoted === null`):
  чип не рендерится — не `undefined`/пустой узел (мутационно эквивалентно
  существующему тесту `deriveInstanceTitle(null).title` в
  `process-instance.logic.test.js` — та функция не трогается).
- **AC-4** НЕ-engine источники (обычные записи с одним модельным процессом,
  без второго инстанса) не регрессировали: существующие тесты
  `screen-record-detail.test.jsx` («renders each instance through the SAME
  human-layer primitives…») остаются зелёными без правки их ожиданий (кроме
  добавления keyDemoted-assertion).
- **AC-5 (анти-кейс, D-064)** Ни одного нового кейс-литерала (конкретного
  имени процесса вроде `telLinear`/«Канонический линейный ТЭЛ») в `src/`/
  `web/src/` — только в тестовых фикстурах, нейтральные значения где нужен
  пример. `anti-case-lock.sh` зелёный без изменения baseline.

## 5. Вне скоупа

- Безопасный (tenant-scoped) живой резолв человеко-имени движкового
  определения через Flowable REST (`GET /repository/process-definitions`) —
  требует либо нативного Flowable `tenantId` на деплое/старте (более широкая
  правка `flowable-client.ts`+`process-defs.ts`+миграция существующих
  деплоев), либо tenant-safe корреляции по `deployment_id` — самостоятельная
  задача, не P3.
- Бэкфилл `choros.process_definition`-строки для `telLinear` (сделал бы его
  «modeler»-процессом задним числом) — исказил бы `source: 'engine'|'modeler'`
  семантику каталога (T-0270/T-0616), не относится к этой задаче.
- `screen-process-instance.jsx` — `keyDemoted` там уже рендерится корректно,
  изменений не требует.
