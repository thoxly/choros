# ADR T-0721 — видимость DETAIL инстанса наследуется от READ-видимости записи-источника

- **Статус:** реализовано (impl-фаза, coder)
- **Контекст:** T-0714 (архитектурная оценка, ратифицирована ADR-T0570 +
  доктрина F2), P1 из follow-up-списка §7 п.1
- **Область:** `GET /api/processes/:id` (DETAIL), фаза 1 из 3

## 1. Решение

Видимость `variables`/`history`/`completedBy*` на `GET /api/processes/:id`
теперь = READ-видимость записи-источника инстанса (`recordId`), решается
ЕДИНЫМ authority-путём — `isRecordReadable` (T-0570, `src/core/
read-visibility.ts`), без второй authority-математики.

Реализация — три точки:

1. **`src/http/process-start.ts`** — новый тип
   `ProcessReadVisibilityResolver` (структурно идентичен `ReadVisibilityResolver`
   из `records.ts` / `ReportAggReadVisibilityResolver` из
   `report-page-render.ts`) + новое ОПЦИОНАЛЬНОЕ поле
   `resolveReadVisibility?` на `StartInstanceDeps`.
2. **`src/http/process-projection.ts`** — новая функция
   `isInstanceDetailVisible(pool, tenantId, recordId, grants, ancestry, nowMs)`:
   record-less → `true`; иначе reverse-lookup `recordId →
   {registryId, applicationId}` (новый приватный `loadRecordRowAncestry`,
   один `SELECT ... JOIN`, через уже существующий модульный `withTenant`) →
   `isRecordReadable(...)`. Живёт здесь (не в `processes.ts`), потому что этот
   модуль УЖЕ импортирует `pg` — `processes.ts` остаётся display-plane-pure
   (FF-DISPLAY-4/FF-7-3, неприкосновенно).
3. **`src/http/processes.ts`** — DETAIL-хендлер вызывает
   `startDeps.resolveReadVisibility(...)` → `isInstanceDetailVisible(...)`
   ДО `fetchInstanceHistoryDetail(...)`; `false` → падает в ТОТ ЖЕ
   `HttpError(404, "NOT_FOUND", "instance not found")`, которым роут уже
   отвечает на "инстанс не найден".
4. **`src/server.ts`** — production-wiring: композиция БАЙТ-В-БАЙТ идентична
   `registerRecordRoutes`'s `resolveReadVisibility` (server.ts:882-892) —
   `getGrantsForSubject` + `loadTenantOrgAncestry` →
   `makeResourceAncestryOracle` с пустым `rowIndex`. Выравнивает асимметрию,
   которую T-0714 нашла (`registerProcessesRoutes` не получал резолвер
   вовсе).

## 2. Развилки и обоснование

### 2.1 Отказ = 404, не 403

**Решение:** honest-404, byte-identical error shape с "instance not found".

**Почему:** T-0570 уже установил прецедент для ТОЙ ЖЕ данные (запись):
`GET /api/records/:id` без покрывающего READ-гранта отдаёт 404, не 403 —
явно, чтобы не подтверждать существование ресурса неавторизованному
запросчику (records.ts:2059-2071, комментарий "FR-5/AC-2"). Консистентность
между двумя API-плоскостями, читающими один и тот же authority-факт,
важнее теоретической RESTful-чистоты 403. Задача прямо просила "эталон —
как /api/records/:id отвечает" — реализовано буквально: тот же код, тот же
message-текст, та же семантика неразличимости.

### 2.2 Record-less инстансы — не сужены (пред-существующее поведение)

**Решение:** `recordId === undefined` → `isInstanceDetailVisible` = `true`
безусловно.

**Почему:** T-0714 §5 явно фазирует это как "Фаза 3, could" — process-
definition-scoped read-грант для инстансов без записи-источника. Сужать это
здесь означало бы придумывать НОВЫЙ authority-объект (грант на process-
definition), которого не существует в латтисе сегодня — вне объёма Фазы 1
(P1, "не добавляй фич сверх критериев приёмки"). Инстансы без `recordId`
сегодня — это ТОЛЬКО явный запуск через `/api/processes/start`
(`process-start.ts`, не `create=start`-триггер) — их видимость остаётся
байт-в-байт прежней.

### 2.3 Владелец видит всё — без bespoke-ветки

**Решение:** никакой отдельной `isGenesisOwnerForTenant`-проверки на
DETAIL-роуте не добавлено.

**Почему:** разведка показала, что `records.ts`'s READ-PDP (T-0570) САМ не
вызывает `isGenesisOwnerForTenant` — владелец получает default-open
видимость через migration 117 (`default_read_grant_backfill`): роль
`role-reader` с READ-грантом на `RESOURCE_ROOT`-сентинел, назначенная
tenant-owner employee (и assistant-agent) при регистрации тенанта. Это
СВОЙСТВО грантов, не отдельный код-путь. Реюзуя ТОТ ЖЕ `resolveReadVisibility`,
DETAIL-гейт автоматически наследует это свойство — владелец видит DETAIL без
единой новой строки кода для этого случая. Доказано live-PG-тестом (сеется
employee с ролью `tenant-owner` + migration-117-shaped `role-reader` грант →
200 на DETAIL).

### 2.4 Исполнитель шага без READ на запись — allowlist НЕ реализован

**Решение:** никакого allowlist "актор = assignee живой задачи инстанса" не
добавлено.

**Расследование (обязательное условие задачи — "если найдёшь легитимный
сценарий... реализуй; НЕ выдумывай шире"):**

- `GET /api/inbox/:id` (`src/http/inbox.ts:1608-1726`) — единственный
  HTTP-путь, которым держатель задачи открывает детали своей работы. Ответ:
  `{item, projection}`. `projection` = сырая `InstanceProjection`
  (`inst`/`procKey`/`status`/`step`/`startedAt`/`concurrentSteps`/...) — БЕЗ
  `variables`, `history`, `completedBy*`. Эти поля физически отсутствуют в
  ответе инбокс-детали сегодня, до и после T-0721.
- `web/src/screens/screen-inbox.jsx`'s `TaskDetailPanel` (drawer, открывается
  кнопкой «Открыть» на строке задачи) НИКОГДА не запрашивает
  `GET /api/processes/:id`. Единственная кнопка, связанная с инстансом
  («Задачи этого процесса», `onFilterByInstance`, T-0653/UX-study §4) —
  фильтрует ИНБОКС по `inst`, не открывает деталку процесса.
  `POST /api/inbox/:id/action` (approve) тоже не читает DETAIL перед
  действием.
- `ProcessRef` (`web/src/components/components.jsx`), отображаемый в строке
  инбокс-задачи, — label-компонент: резолвит человекочитаемое имя
  записи/процесса через `GET /api/records/:id` (который САМ уже гейтед
  READ-PDP с T-0570) — не ссылка на `/processes/:id`.

**Вывод:** исполнитель полностью выполняет свою работу через
инбокс-плоскость (`GET /api/inbox/:id` + `POST /api/inbox/:id/action`),
которая не потребляет `variables`/`history`/`completedBy*` НИКАК. Легитимного
сценария "исполнитель без READ на запись должен видеть DETAIL, чтобы
выполнить свой шаг" в текущей продуктовой поверхности не найдено. Задача,
которую этот гейт закрывает (T-0714 §3, P1), — это отдельная "деталка
процесса" страница (`screen-process-instance.jsx`, каталог `/processes`,
доступная ЛЮБОМУ члену тенанта, не только держателю задачи) — именно её и
только её сужает этот фикс. Добавление незапрошенного allowlist было бы
расширением объёма без продуктового требования (роль-правило #5).

## 3. Fitness-функции (архитектурные границы как код)

- **FF-INST-VIS-1** — `ci/checks/process-detail-read-gate.sh`: DETAIL-хендлер
  реально зовёт `resolveReadVisibility` → `isInstanceDetailVisible(` в
  правильном порядке (до `fetchInstanceHistoryDetail(`), денай падает в
  честный 404. `--self-test` сажает gate-free фикстуру.
- **FF-INST-VIS-2** — `ci/checks/process-detail-single-resolver.sh`: нет
  второго authority-пути — `process-projection.ts` реюзает
  `isRecordReadable`, не переопределяет; ни `processes.ts`, ни
  `process-projection.ts`, ни `process-start.ts` не импортируют
  `isNarrowerOrEqual`/`isEffective` напрямую и не шлют bespoke SQL по
  `choros."grant"`; `server.ts`'s wiring реально зовёт
  `getGrantsForSubject`/`loadTenantOrgAncestry`/`makeResourceAncestryOracle`
  (не параллельную композицию). `--self-test` сажает оба класса нарушений.
- **FF-INST-VIS-3** (display-plane isolation) — покрыта уже существующим
  `ci/checks/start-route-isolation.sh` (FF-7-3): `processes.ts` по-прежнему
  не импортирует `pg`/`src/db/*` — проверено, гейт остаётся зелёным
  байт-в-байт (не создавал новый чек, реюз существующего).
- **FF-INST-VIS-4** (tenant-изоляция) — покрыта live-PG тестом
  (`ci/checks/db/processes-read-visibility.db.test.ts`, describe "tenant
  isolation"): PDP-предикат — ДОПОЛНИТЕЛЬНЫЙ `AND` внутри
  `listInstanceProjections`'s tenant-scope, никогда не замена (актор тенанта
  A с широким грантом всё равно не резолвит `inst`-id тенанта B, потому что
  `projections.find((p) => p.inst === instanceId)` уже не находит совпадения
  в тенант-скоупнутом списке).

## 4. Отклонения от оценки T-0714

Нет. Реализация строго следует опции (c), Фаза 1, включая явно
зафиксированные в оценке ограничения (record-less fallback, приоритет
DETAIL над LIST). Инвестигация "исполнитель без READ" (§2.4 выше) —
предписанный оценкой шаг ("если найдёшь... реализуй; иначе не выдумывай"),
результат — отрицательный, задокументирован, allowlist не добавлен.

## 5. Live proof

См. `T-0721.pr-handoff.json`'s `live_proof_plan` — два юзера на стенде:
один с READ-грантом на запись видит и запись, и деталь процесса; второй без
READ-гранта не видит ни запись (уже гейтед T-0570), ни деталь процесса
(новый гейт этой задачи).
