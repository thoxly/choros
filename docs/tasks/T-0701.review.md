## 1. Семантика `setDocRefs` — сохранена ТОЧНО (ось 1/2)

Сравнение старого цикла (`git show dev:src/db/doc-page-store.ts`) с новым:

| аспект | старый | новый | вердикт |
|---|---|---|---|
| колонки | `(tenant_id,id,page_id,ref_kind,ref_target,broken,created_at)` | те же | ✅ |

| возврат `set` | **`refs.length`** (безусловный `set++` внутри цикла — НЕ реально вставленные) | `set = refs.length` | ✅ идентично |
| `deleted` | `rowCount` DELETE | не тронут | ✅ |

**Ключевой разбор возврата (запрос задачи):** старый код считал `set` как `refs.length`,
а НЕ как реально вставленные строки — `set++` стоял безусловно, вне зависимости от того,
проглотил ли `DO NOTHING` дубль. Новый `set = refs.length` воспроизводит это ПОБАЙТОВО.
Поведение при дублях НЕ изменилось → не blocking. (Пред-существующая особенность: `set`
переучитывает при дублях; это НЕ регресс данной задачи.)

**Индексация параметров** (проверена трассировкой): `params=[tenantId,pageId]`, для ref#1
`base=2` → `$3=id,$4=ref_kind,$5=ref_target,$6=created_at`; ref#2 `base=6` → `$7..$10`.
Плейсхолдеры совпадают со сдвигом. ✅

**Порядок вставки:** ON CONFLICT — множественная семантика; при интра-batch дубле на
арбитре PG оставляет ПЕРВУЮ строку VALUES (= первый элемент массива), ровно как старый
последовательный цикл. Порядок семантически неважен и совпадает. ✅

## 2. Интра-batch ON CONFLICT — ЖИВОЙ SQL (ось 3, классическая ловушка)

Прогнал против реального PG (`choros-postgres-1`, таблица-двойник с PK + тем же UNIQUE):

- **CASE A** — две VALUES-строки с ОДИНАКОВЫМ `(tenant,page,ref_kind,ref_target)`, разными `id`,
  `ON CONFLICT (…) DO NOTHING`: → `INSERT 0 1`, финально **1 строка, БЕЗ ошибки**. Дубль
  проглочен внутри одного statement. ✅ Ловушка НЕ срабатывает.
- **CASE C** (контроль) — тот же интра-batch дубль, но `DO UPDATE`: →
  `ERROR: ON CONFLICT DO UPDATE command cannot affect row a second time`. Подтверждает: пресловутая
  ошибка «cannot affect row a second time» специфична для **DO UPDATE**, которого в фиксе НЕТ.
- **CASE B** — две строки с ОДИНАКОВЫМ `id`, разным target (коллизия по PK, не по арбитру): →
  `ERROR: duplicate key … t2_pkey`. НО: старый по-строчный код упал бы так же (2-й INSERT бьёт PK),
  И `id` каждого рефа = `randomUUID()` (`src/core/doc-regen.ts:334`) → интра-batch коллизия `id`
  невозможна на практике. Не регресс, не достижимо.

**Вывод по ловушке:** `DO NOTHING` (а не `DO UPDATE`) — правильный выбор; интра-statement дубли
на арбитре PG молча пропускает. Фикс безопасен на живом PG.
