# ADR / Assessment · T-0729 — Tier-1 тупик замещения (столп 3)

**Phase:** DESIGN (оценка, не реализация). **Status:** ready — с одной дверью к
фаундеру (см. §5). **Epic:** T-0585. **Origin:** N2 из ревью T-0720.
**Дата:** 2026-07-10. **Автор:** architect.

Задача — ОЦЕНКА трёх вариантов лечения тупика и рекомендация. Код продукта не
менялся. Выход — этот ADR + черновые заголовки follow-up.

---

## 1. Контекст

Достижимый нормальный путь заводит процесс в тупик:

1. Сотрудник (или админ) объявляет отпуск/подмену и выбирает замещающего,
   который **сам не держит роль**.
2. Система определяет **Tier-1** (роль сейчас покрыта ДРУГИМ держателем) →
   грант замещающему **не минтится** (`ttl_grant_id = NULL`).
3. Позже покрывающий пул **опустевает** (последний держатель деактивирован /
   уволен / его `role_assignment` истёк по времени / он сам ушёл в отпуск).
4. Маршрутизатор оставляет замещающего единственной целью роли (эффективный пул
   = {замещающий}).
5. Замещающий жмёт «взять» → claim-гейт (`resolveTier2SubstitutionClaim`,
   фильтр `ttlGrantId !== null`) отсеивает Tier-1 → **403 NOT_ELIGIBLE**.
6. Задача **застревает**: эффективный пул непустой (в нём замещающий) → на
   владельца она **не падает**. `ttl_grant_id` остаётся `NULL` навсегда —
   механизма авто-эскалации Tier-1→Tier-2 нет.

T-0720 / T-0731 сделали UI-тексты честными («роль покрыта другими держателями,
временный доступ не выпускался, задачи перенаправляются в рамках его собственных
прав»), но **сам тупик остался** — тексты лишь перестали обещать несуществующую
авто-эскалацию.

## 2. Реальность (файлы:строки — верю коду, не памяти)

### 2.1 Tier определяется ОДИН РАЗ снимком пула на момент объявления
`src/http/rights-intents.ts:775-784` (`registerSubstitute`), симметрично в
`registerSelfAbsence` (~1267+):
```
SELECT employee_id FROM role_assignment
 WHERE role_id=$2 AND employee_id<>absent AND employee_id<>substitute
   AND confirmed_by IS NOT NULL AND (valid_until IS NULL OR valid_until>now)
 LIMIT 1
→ tier2 = forceTier2 || poolRows.length === 0
```
Tier-1 = «существует ЛЮБОЙ ТРЕТИЙ держатель, кроме отсутствующего и
замещающего». **Замещающего на держание роли НЕ проверяют.** Tier заморожен;
пул динамичен. Это и есть корень (см. §2.7).

### 2.2 Escape-hatch `force_tier2` ЕСТЬ в API, но НЕ выведен в форму
`rights-intents.ts:744` и `:1231` читают `body.force_tier2` → минтят грант
немедленно вне зависимости от пула. Но `web/src/screens/rights/ra-intents.jsx`
(`SubstituteForm`/`SelfAbsenceForm`) поля `force_tier2` **не имеет** — пользователь
не может выбрать «дай замещающему собственный временный доступ сразу». Готовый
предохранитель существует, но недоступен из UI.

### 2.3 Замещающий выбирается свободно из ВСЕХ сотрудников
`ra-intents.jsx:370-372` — `OrgPicker` «Замещает» `options={dir.employees}`, без
фильтра/аннотации «держит ли роль». Ничто не мешает выбрать не-держателя.

### 2.4 Живой маршрутизатор добавляет замещающего tier-агностично
`src/http/inbox.ts` `resolveExecutorFallbackBatch:636-702` (путь B — единственный
задействованный в проде; путь A `resolveExecutor` в `executor-resolver.ts:216-267`
имеет ТУ ЖЕ ошибку, но dormant — порт `deps.substitution` нигде не инжектится,
см. T-0588 §1.2). Строки `662-675`: для каждого держателя с активным правилом —
`effective.delete(absent); effective.add(substitute)` **безусловно**, не глядя на
tier/`ttl_grant_id`. Строки `692-694`: непустой эффективный пул ⇒ fallback НЕ
срабатывает. → Tier-1-не-держатель «маскирует» опустевшую роль.

### 2.5 Claim-гейт честно отсеивает Tier-1 (fail-closed — это правильно)
`inbox.ts:1893-1912`: `myRoles = resolveRolesForActor` (→ `getRoleSlugsForActor`,
`grants-dao.ts:431-522` — **только `role_assignment`**, у замещающего роли нет).
При промахе → `resolveTier2SubstitutionClaim` (`inbox.ts:1366-1403`), фильтр
`r.ttlGrantId !== null` (строка **1378**, комментарий: «Tier-1 substitutes already
hold the role via role_assignment»). Для Tier-1-не-держателя правил нет → `undefined`
→ **403** (строка 1909-1911). Гейт верен; ложен инвариант в его комментарии.

### 2.6 `routed_to_fallback` — ТОЛЬКО ДИСПЛЕЙ-маркер; владелец claim-нуть НЕ может
`inbox.ts:235` — поле `routed_to_fallback?: "role_unfilled"`. `:699-700` —
`ownerSlug` резолвится и... `void ownerSlug` (не используется для назначения/
eligibility). Claim-гейт (§2.5) НЕ имеет owner-short-circuit → **владелец,
не держащий роль, на role_unfilled-задаче тоже получит 403**. Это
**пред-существующая дыра F6/F7**: маркер «роль не заполнена» показывается, но
владелец не может ВЗЯТЬ задачу. `isGenesisOwnerForTenant` (`org.ts:747`, по
slug) существует, но в claim-путь не подключён. → важно для варианта (в): голого
роутинга на владельца НЕДОСТАТОЧНО.

### 2.7 Ратифицированная модель (T-0035 / T-0639) и где она треснула
`docs/design/T-0035-substitutions.adr.md` §24: «no new authority algebra, tier
frozen; substitution = routing/declaration layer». Строка про Tier-1: *«when
another employee already holds the role_id … the stand-in acts under **their own
role authority**»*. Модель **конфликтует сама с собой в реализации**: условие
Tier-1 проверяет «есть другой держатель B», а claim-механика Tier-1 предполагает
«сам stand-in держит роль». Эти два факта совпадают, только если stand-in И ЕСТЬ
тот держатель. Код (§2.1) их развёл: Tier-1 выбирается при любом третьем B, а
stand-in может быть не-держателем. T-0588 §1.3 прямо кодифицировал ложную посылку:
«Tier-1 … заместитель по определению УЖЕ держит роль → разрыва нет». **Разрыв
есть.** T-0729 — его манифестация.

### 2.8 Авто-эскалации / ре-тиринга нет
`grep` по `src/` не находит пути, повышающего Tier-1→Tier-2 или переустанавливающего
`ttl_grant_id`. Заморожено на объявлении.

**Корневой диагноз:** двух-tier-модель смешивает *«в пуле есть другой держатель»*
(проверяется, замораживает tier) и *«замещающий лично держит роль»* (не
проверяется никогда). Снимок на момент объявления трактуется как стоячий
инвариант; когда покрывающий пул опустевает под Tier-1-не-держателем, роль
фактически пуста, но роутинг этого не признаёт, а claim-гейт — признаёт (403).
Рассинхрон роутинга и гейта = тупик.

## 3. Три варианта (дизайн каждого)

### Вариант (а) — АВТО-ЭСКАЛАЦИЯ Tier-1→Tier-2 (минт гранта при опустошении пула)

**Идея.** Детектить опустошение покрывающего пула для активного Tier-1-правила и
минтить Tier-2 subset-грант замещающему (проставить `ttl_grant_id`, перевести
правило в Tier-2).

**Где хук.** Опустошение наступает по 4 независимым событиям:
(i) деактивация последнего держателя (`user-mgmt.ts` PATCH), (ii) увольнение
(`registerFire`), (iii) **истечение `role_assignment.valid_until` по времени —
события НЕТ**, (iv) Tier-1-отпуск самого покрывающего держателя. Write-хук
закрывает только (i)/(ii); (iii)/(iv) требуют **ленивой** переоценки на
route/claim-time (при эффективном пуле = {Tier-1-замещающий}).

**Что минтит.** Ветка Tier-2 из `registerSubstitute:788-889` (subset-гейт
`validateNarrowing`, `delegable=false`, `eligibleForTier2`) — вынести в общий
минтер и вызвать из детектора.

**Идемпотентность.** Минт под tenant-tx с гардом `ttl_grant_id IS NULL`; повтор
видит non-null → no-op. Конкурентные claim'ы разруливает та же tx.

**Откат при возврате держателя.** Нужен ОБРАТНЫЙ хук на реактивацию/конец окна
отсутствия покрывающего: revoke авто-гранта (`valid_until=now`) + сброс
`ttl_grant_id=NULL` (downgrade назад в Tier-1). Это **мутабельный tier-стейт-
машина**, прямо противоречащий frozen-tier ADR. TTL-грант сам истечёт в конце
окна, но «возврат раньше окна» — bespoke-revoke.

**Сложность:** ВЫСОКАЯ (детектор на 2 write-путях + ленивый путь; общий минтер;
обратные хуки; tier-стейт-машина). **Security:** ЧУВСТВИТЕЛЬНО — система **сама
выдаёт стоячую делегированную власть** по автоматическому триггеру, без свежей
человеческой авторизации именно этой эскалации (особенно в self-absence, где
admin-гейта нет вовсе). Subset-гейт не даёт расшириться, но пересекается грань
«роутинг-удобство → выдача доступа». **Обратимость:** частичная. **Соответствие
T-0035:** НАРУШАЕТ (вводит новую authority-механику и мутабельный tier).

### Вариант (б) — ФОРМА предупреждает/ограничивает выбор не-держателя

**Идея.** При выборе замещающего, не держащего роль, форма предупреждает и/или
даёт явный опт-ин в Tier-2.

**Реальность.** На момент объявления пул НЕ пуст (иначе это уже Tier-2) —
«не-держатель» это не ошибка сейчас, а *будущий* риск. Жёсткая блокировка
запретила бы легитимный паттерн (не-держатель как вежливый stand-in, пока пул
покрывает — ровно то, для чего Tier-1). → **предупреждать, не блокировать.**

**UX.** (1) Аннотировать в пикере «Замещает», кто держит роль (нужен read
держателей выбранной роли — `getHoldersForRole`); (2) при выборе не-держателя —
inline-баннер «этот сотрудник не держит роль X; если пул опустеет, он не сможет
брать задачи — включите “собственный временный доступ”, чтобы гарантировать
покрытие»; (3) **вывести чекбокс `force_tier2`** (§2.2 — уже есть в API!) как
«выдать замещающему собственный временный доступ сразу».

**Серверная валидация.** `registerSubstitute`/`self-absence` в ответе 201 отдают
advisory-поле `substitute_holds_role: false` / `coverage: "pool_dependent"` (без
отклонения). UI показывает.

**Сложность:** НИЗКАЯ-СРЕДНЯЯ (аддитивно, read держателей + баннер + advisory-
поле + проброс `force_tier2`). **Security:** нет — доступ не меняется, только
информирует/даёт явный человеческий опт-ин. **Обратимость:** тривиальная.
**Соответствие T-0035:** полное. **Ограничение:** СНИЖАЕТ вероятность тупика, но
**не устраняет** — пользователь всё равно может выбрать не-держателя (легитимно),
а покрывающий держатель может уйти позже, чего предупреждение на объявлении не
предвидит. (б) — смягчение, не фикс.

### Вариант (в) — ФОЛБЭК-РОУТИНГ владельцу (застрявшая задача падает владельцу)

**Идея.** Признать, что Tier-1-замещающий-не-держатель **не является покрытием**,
и когда эффективный пул схлопывается только до таких — роль **фактически пуста**
→ существующий путь F6/PD-10 «роль не заполнена → владелец».

**Где хук (в1, роутинг).** `resolveExecutorFallbackBatch` (`inbox.ts:662-675`).
Замещающего добавлять в эффективный пул ТОЛЬКО если он даёт покрытие:
`rule.ttlGrantId !== null || holders.includes(rule.substituteEmployeeId)`.
Отсутствующего держателя удаляем всегда. Тогда:
- здоровый Tier-1 с третьим держателем B: B остаётся в пуле (у него правила нет)
  → пул непуст → без fallback. ✓
- B ушёл, замещающий — не-держатель Tier-1: пул пуст → **fallback на владельца**
  (`routed_to_fallback:"role_unfilled"`, уже реализовано). ✓
Тот же предикат применить к `executor-resolver.ts:248-267` (путь A) и вынести в
чистую `substituteProvidesCoverage(rule, holderSet)` (общий контракт обоих путей).

**Где хук (в2, claim-eligibility — ОБЯЗАТЕЛЬНО, иначе тупик переезжает на
владельца, §2.6).** Добавить в claim/approve-гейт owner-ветку по образцу
`resolveTier2SubstitutionClaim`: если `isGenesisOwnerForTenant(actor)` И
эффективный пул роли пуст (та же проверка, что в в1) → claim разрешён. Гейт по
пустому пулу критичен: владелец берёт ТОЛЬКО осиротевшую задачу, а не любую
pool-задачу с живыми держателями (иначе обход pool-дисциплины). Закрывает и
пред-существующую дыру §2.6.

**Кто «владелец» / как детектится застревание.** Владелец = genesis
`tenant-owner` (`findTenantOwnerSlug` / `isGenesisOwnerForTenant`). Застревание
детектится **структурно на route/read-time** (эффективный пул claim-eligible
исполнителей пуст) — без таймеров/watchdog, срабатывает на следующем чтении
инбокса. Деактивированный владелец → `unresolvable` (уже покрыто T-0588 FR-2/AC-7).

**Сложность:** НИЗКАЯ-СРЕДНЯЯ (правка предиката пула в 2 местах + owner-ветка в
claim/approve; переиспользует существующий fallback + F7). **Security:** БЕЗОПАСНО
— **ничего не минтит**; даёт владельцу (у кого и так высшая власть в тенанте и кто
по F6/PD-10 назначен last-resort исполнителем) взять осиротевшую задачу. Fail-
closed по духу. **Обратимость:** полная. **Соответствие T-0035/T-0639:**
ОТЛИЧНОЕ — не вводит ни новой authority-механики, ни мутабельного tier; лишь
приводит роутинг в согласие с claim-гейтом и с посылкой Tier-1 («покрывает
другой»); использует тот же `FallbackReason:"role_unfilled"`.

## 4. Рекомендация

**Основной фикс — (в) + дополняющий UX (б); (а) отклонить как автоматический
механизм.**

Обоснование одним абзацем: тупик — это рассинхрон между роутингом (считает
Tier-1-не-держателя покрытием) и claim-гейтом (не считает). Ратифицированная
модель уже даёт правильный ответ: Tier-1 значит «замещающий власти НЕ получает,
покрывает пул»; когда пул опустел, роль честно «не заполнена» → путь F6/PD-10
«к владельцу». **(в)** приводит роутинг в согласие с гейтом и с моделью, **ничего
не выдавая автоматически** (минимум, полностью обратимо, ноль новой authority-
механики), и попутно чинит пред-существующую дыру §2.6 (владелец реально может
взять осиротевшую задачу). **(б)** дополняет: предупреждает о выборе не-держателя
и **выводит уже существующий `force_tier2`** (§2.2) — пользователь, которому нужно
гарантированное покрытие не-держателем, делает это осознанным человеческим опт-ином
в Tier-2 *заранее*, а не автоматом задним числом. **(а)** отклонён: он превращает
роутинг-удобство в автоматическую выдачу стоячей власти по машинному триггеру,
противоречит frozen-tier ADR, плохо откатывается (bespoke-revoke при возврате
держателя) и security-чувствителен — и он **не нужен**, потому что (в) снимает
тупик, ничего не минтя, а (б) даёт явный путь для тех, кому нужен Tier-2.

Важное следствие: с (в) осиротевшую задачу берёт ВЛАДЕЛЕЦ, а не назначенный
замещающий. Это модель-консистентно (хочешь, чтобы работал именно замещающий →
это Tier-2, а Tier-2 уже доступен через `force_tier2`). Продуктовый вопрос «должна
ли система вместо владельца авто-повышать назначенного замещающего до Tier-2» —
это дверь к фаундеру (§5), но она НЕ блокирует разблокировку сегодня.

## 5. Дверь-классификация (D-063)

**Рекомендованный путь (в)+(б) = МАШИНА владеет.** Это чистая механика + UX:
- (в) не меняет, как система выдаёт доступ — чинит роутинг-баг так, что застрявшая
  задача доходит до владельца (у кого власть уже есть); owner-fallback для
  незаполненной роли — уже ратифицированное поведение (F6/PD-10, T-0588 AC-6).
- (б) — предупреждение + проброс уже существующего `force_tier2`; доступ не меняет.

Предлагаю завести это как build-задачи (см. §6), оркестратор ставит в очередь.

**ОТДЕЛЬНО — одна дверь «продукт» к фаундеру (открытый вопрос, НЕ блокирует (в)):**
вариант (а) — авто-повышение замещающего до Tier-2 — это про то, *как система
раздаёт доступ* (столп 3), поэтому если фаундер захочет именно его, это дверь.
Формулировка для эскалации:

> **business_summary (дверь «продукт»):**
> **Контекст.** Когда сотрудник уходит в отпуск и назначает замещающего, который
> сам не держит роль, система сейчас (после фикса (в)) при опустошении покрывающего
> пула отдаёт осиротевшие задачи ВЛАДЕЛЬЦУ компании, а не назначенному замещающему.
> Это безопасно и честно, но «не тот человек» с точки зрения намерения сотрудника.
> **Опция 1 (рекомендация машины, реализуется по умолчанию):** задача падает
> владельцу; кто хочет, чтобы работал именно замещающий, заранее ставит галочку
> «выдать собственный временный доступ» (Tier-2). Человек в контуре, ноль
> авто-выдачи прав.
> **Опция 2:** система АВТОМАТИЧЕСКИ повышает назначенного замещающего до Tier-2
> (выдаёт ему временный ограниченный доступ) в момент опустошения пула — задачу
> берёт замещающий, не владелец. Удобнее для сотрудника, но система сама раздаёт
> стоячую власть по машинному триггеру (в self-absence — вообще без участия
> админа), и нужен откат при возврате держателя.
> **В чём не уверен:** приемлемо ли для вас, чтобы система выдавала делегированный
> доступ БЕЗ явного человеческого «да» в момент выдачи. Если «только с явным
> опт-ином» — Опция 1 закрывает всё. Если «удобство важнее, авто-выдача в
> пределах subset-гейта ок» — берём Опцию 2 (отдельная задача, security-ревью).

Моё явное решение: **реализовать (в)+(б) как машину сейчас**; дверь (а) —
поднять фаундеру как открытый продуктовый вопрос, но НЕ ждать её для снятия
тупика.
