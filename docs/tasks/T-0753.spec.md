# T-0753 — Committed BUILDER fixture credential for the Конструктор-зона (substrate)

## Problem (LIVE_PROOF substrate gap)

The Конструктор / draft-authoring surface (`/process-catalog` under
`authoring_draft`, records/schema/list-view/solution-publish edits) is gated by
the **`authoring_draft`** capability (`resolveActorPrivilege`,
`src/db/sandbox-gate-dao.ts` → `decideDraftVisibility`, `src/core/sandbox-gate.ts`).

`authoring_draft` is a **choros-DB grant**, NOT a Keycloak role. The resolution
chain a logged-in human must satisfy is:

```
KC token (preferred_username) ──resolveActorSlugFromAuth──▶ employee.slug
   └─ role_assignment (confirmed, in-window) ──▶ role
        └─ grant(resource_type='authoring_draft', confirmed) ──▶ capability
```

The only committed KC fixtures (`config/keycloak/realm-choros.json`) are the 7
ТЭЛ personas (e-kravtsova … e-belov) — **none holds `authoring_draft`** — plus
agent service accounts. The genesis owner **e-owner** (who *would* pass via
owner/admin) is deliberately **NOT** in the committed realm: it is the founder's
tenant-owner account, provisioned out-of-band; committing it would let a
realm-reimport reset the founder's password (memory: `choros-founder-cred-lockout`).

Net: no committed, loginable identity can reach the Конструктор-зона →
owner/builder-scoped screens are un-livable even on a live stand.

## Key finding — the builder persona already exists DB-side

`migrations/088_configurator_authoring_draft_grant_seed.sql` already seeds the
FULL authority chain for a dedicated **non-owner** persona `e-configurator`:

- `role` **role-configurator** (`e0…0008`)
- `employee` **e-configurator** (`d0…0016`, `kind='human'`)
- confirmed `role_assignment` e-configurator → role-configurator (`f0…0007`)
- confirmed `grant` **authoring_draft / create** (`e2…001a`) + **update** (`e2…001b`)
  on role-configurator (DRAFT-ONLY; zero `authoring_published`).

Migration 104 additionally grants role-configurator an L4 `capability` grant and
its header states: *"the NON-owner e-configurator is the testable holder"*.
Migration 088's own header calls e-configurator the *"test human persona to log
in as."*

The gap is documented verbatim in `src/db/org.ts` (resolveActorSlugFromAuth,
T-0633 note): *"'e-configurator' (migrations/088) are kind='human' employees
with NO row in config/keycloak/realm-choros.json"* — i.e. the DB side is built,
but the KC credential to authenticate as it was never committed.

## Decision — reuse, don't mint a new persona

Add ONE committed KC user for the **existing** migration-088 persona
`e-configurator` (username = employee slug, resolved via the
`preferred_username` fallback). This closes the substrate gap with **zero new
migration / seed / UUID management** and maximal reuse — strictly smaller scope
than minting a fresh `e-builder` persona (which would duplicate migration 088's
entire chain). The task suggested the name `e-builder` ("напр."); the capability
axis (`authoring_draft`) is identical, so the pre-built `e-configurator` **is**
the builder fixture. `authoring_draft` = the "constructor/builder" capability;
role-configurator (pillar 5, "настройка-через-ИИ") is the same axis.

### The added user (mirrors e-larina/e-belov shape exactly)

```json
{
  "username": "e-configurator",
  "email": "e-configurator@choros.dev",
  "firstName": "К.",
  "lastName": "Конфигуратор",
  "enabled": true,
  "emailVerified": true,
  "attributes": { "actor_type": ["human"] },
  "credentials": [{ "type": "password", "value": "dev-pw-configurator", "temporary": false }]
}
```

- **actor_type correctness (T-0734):** `actor_type` is a scalar `["human"]`
  attribute; the realm's declarative-user-profile component (KC25) already
  declares `actor_type` as a MANAGED, admin-editable, options-`[human,agent]`
  attribute, so import persists it (identical mechanism to every existing human
  fixture). No profile change needed.
- **Additive:** a NEW user object; touches no existing user. A realm-reimport
  creates `e-configurator` and leaves e-owner / e-larina / … untouched (their
  passwords + actor_type unchanged — their objects are byte-identical).
- **NOT owner/admin:** e-configurator holds only role-configurator
  (authoring_draft + L4 capability); no `mgmt_object:*` grant, not the genesis
  owner. `resolveActorPrivilege` → `{ isOwnerOrAdmin:false,
  hasAuthoringDraftGrant:true }`. Cleanly separate from the e-owner founder;
  cannot escalate to owner.

## Security / gate notes

- **e-owner untouched** — not added, not modified. Reimport does not reset the
  founder owner credential.
- **no-committed-secret (FF-1):** scans compose + migrations only — unaffected.
- **no-prod-secret (FF-11):** `dev-pw-` is an explicitly-allowed dev-credential
  pattern in the realm JSON (banned only in `src/`); precedent = every existing
  `dev-pw-*` fixture. Realm carries the "DEV ONLY" label. Legit fixture, not a leak.
- **anti-case-lock:** scans `src/` + `web/src/` code against the ТЭЛ-persona
  denylist; a realm-config fixture user is out of scope.
- **fixture-users (FF-7):** subset check on the 7 ТЭЛ personas — an 8th user is
  allowed; still passes.
- **actor-type mint-collision guard (T-0633):** unaffected — the anti-collision
  guard blocks *product routes* (register / POST /users) from minting a KC
  username colliding with a seeded human slug. Realm-import is the sanctioned
  out-of-band operator provisioning path (same class as the genesis owner) and
  is exactly how a seeded-persona credential is meant to be introduced.

## Proof (substrate — local KC is the live-proof surrogate)

1. Disposable KC (fresh store) imports the patched realm → `e-configurator`
   created.
2. ROPC (`grant_type=password`, `client_id=choros-api`) as
   e-configurator/dev-pw-configurator → 200 + access_token.
3. Decode token: `preferred_username=e-configurator`, `actor_type=human`,
   `aud` contains `choros-api`.
4. choros DB (migration 088 applied): confirm the chain e-configurator →
   role-configurator → confirmed authoring_draft grant resolves (SQL replicating
   getGrantsForSubject) → `hasAuthoringDraftGrant=true`.
5. Regression: e-owner / e-larina objects unchanged (git diff = pure addition).
