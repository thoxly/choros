## 1. Решение (механизм одним абзацем)

**Пилот — продуктовое понятие „ограниченный боевой запуск published-процесса", а НЕ вторая
подсистема авторизации.** Срез пилота декларируется тремя осями, каждая из которых —
**живой** примитив решётки T-0018: **узел оргдерева** (`{kind:"node", hierarchy:"org", …}`,
кто участвует) ⊓ **интервал суммы** (`{kind:"interval", axis, lo, hi}`, какие кейсы) +
**срок** (`Grant.validUntil`, окно `isEffective`, когда заканчивается). Декларация среза
**компилируется** в грант-кортежи published-бандла: scope каждого пилотного гранта =
`set([ node, interval ])` (комбинация через `meet`/⊓), `validUntil` = срок. Эти гранты —
**монотонное сужение** (`пилотный.scope ⊑ полный.scope`) полного скоупа процесса, и каждый
проходит **живой** `validateNarrowing` относительно санкционированного владельцем. Граница
пилота **обеспечена решёткой**: кейс вне среза не обрабатывается пилотной версией как
**следствие резолюции грантов** (`resolveFor` → `isNarrowerOrEqual`/`isEffective` его не
покрывают), а не отдельным if-фильтром. Пилот — published+боевой (эффект-гранты T-0034
действуют по-настоящему), что является **точной противоположностью** симуляции T-0130
(draft+стабы). Жизненный цикл `запланирован → активен → {расширен | откачен | истёк}`
наблюдаем в **едином** аудите; расширение до полного прода — **ослабление среза под
human-gate**; откат — **drain-by-default**. Пилот не вводит ни нового authority-store, ни
второго scope-алгоритма, ни второго аудит-лога, ни процессного if-фильтра.

## 2. Природа пилота: боевой live-запуск (граница GRAN-1 с симуляцией) — AC-4, NF-2

**Пилот = published, реальные эффекты, ограниченные срезом. Симуляция = draft, эффекты
застаблены.** Это **неустранимая граница построения**, а не режим:

| | **Пилот (T-0132)** | **Симуляция (T-0130)** |
|---|---|---|
| Тир бандла | **published** (после промоута) | **draft** |
| Эффект-гранты T-0034 | **действуют** (письма/1С/платежи реальны) | **застаблены fail-closed** (`draft-аффин`) |
| Кейсы | реальные кейсы живых сотрудников | статисты, не-боевой прогон |
| Аудит | боевой, **НЕ помечен `test`** | помечен `test:true`, исключён из комплаенс-выгрузки |
| Что ограничивает срез | **охват** (кто/что/когда), а НЕ «боевость» | сам режим не-боевой |

**Срез ограничивает охват, а НЕ боевость.** Пилотный кейс — **боевой**: он внутри среза, и
для него эффекты реальны. Перепутать пилот с симуляцией = катастрофа (либо боевые эффекты в
«тесте», либо «пилот» без реальной нагрузки), поэтому ADR **запрещает** режим, в котором
пилот частично «не боевой». Нет флага `simulate=true`, гасящего эффекты пилота; нет «полу-
боевого» пилота.

## 3. Объектная модель — продуктовое понятие `Pilot` (НОВОЕ) поверх живых грантов

> Это **продуктовое понятие**, а не scope-механизм. Сущность `Pilot` — **тонкий
> декларативный слой**: она хранит срез **на уровне понятий** и ссылается на гранты, которые
> уже несут scope. Авторитет живёт в грантах (T-0018), не в `Pilot`.

### 3.1 `PilotDeclaration` — срез на уровне понятий (two-floor верхний этаж) **[НОВАЯ B-1]**

| Поле | Тип | Значение |
|---|---|---|
| `tenantId` | `string` | тенант (T-0013 изоляция) |
| `pilotId` | `string` | идентификатор пилота |
| `implementationId` | `string` | какой published-бандл раскатываем (T-0129) |
| `bundleVersion` | `string` | конкретная промоутнутая версия бандла (предусловие — промоут совершён) |
| `nodeAxis` | `{ hierarchy:"org"; nodeId; nodeLevel }` | узел оргдерева — «кто участвует» (компилируется в `node`) |
| `amountAxis` | `{ axis:string; lo:number; hi:number } \| null` | интервал суммы — «какие кейсы» (компилируется в `interval`); `null` = без ограничения по сумме |
| `validUntil` | `number \| null` | срок (epoch ms) — «когда заканчивается»; `null` = бессрочно (= полный прод по сроку) |
| `state` | `PilotState` | состояние (см. §4) |
| `createdBy` | `string` | владелец процесса, объявивший пилот |

### 3.2 `PilotGrantBinding` — связка декларации с живыми грантами **[НОВАЯ B-1]**

| Поле | Тип | Значение |
|---|---|---|
| `pilotId` | `string` | к какому пилоту относится |
| `grantId` | `string` | id гранта пилота (живой `Grant`, T-0018) |
| `derivedScope` | `ScopeElement` | `set([ node, interval ])` или `node` (если `amountAxis=null`), полученный через `meet`/⊓ |

> `PilotGrantBinding` — это и есть «отличимость по принадлежности к пилоту» (FR-7): пилотные
> гранты — **обычные боевые гранты**, помеченные принадлежностью к `pilotId`, а НЕ отдельный
> класс грантов и НЕ второй scope-store.

### 3.3 Компиляция понятия → грант-кортежи (машинный слой, NF-5/NF-6) — AC-1, AC-2

`PilotDeclaration` **компилируется** (машинно, под карточкой внедрения) в scope каждого
пилотного гранта:

```
derivedScope(decl) =
  decl.amountAxis === null
    ? { kind:"node", hierarchy:"org", nodeId: decl.nodeAxis.nodeId, nodeLevel: decl.nodeAxis.nodeLevel }
    : meet(
        { kind:"node", hierarchy:"org", nodeId: decl.nodeAxis.nodeId, nodeLevel: decl.nodeAxis.nodeLevel },
        { kind:"interval", axis: decl.amountAxis.axis, lo: decl.amountAxis.lo, hi: decl.amountAxis.hi },
        ancestryOracle
      )            // ⇒ { kind:"set", members:[node, interval] }  (живой meet, grant-lattice.ts:367)

grant.scope     = derivedScope(decl)
grant.validUntil = decl.validUntil ?? undefined   // живой isEffective, grant-lattice.ts:497
```

**Интервал суммы — это grant-предикат (`interval`-элемент scope), участвующий в той же
`⊑`-проверке `isNarrowerOrEqual`, что и любой scope, а НЕ внешний процессный if-фильтр**
(AC-2, FR-2). «Договоры до 100 тыс.» = `{kind:"interval", axis:"amount", lo:0, hi:100000}`
внутри scope гранта, проверяемый `validateNarrowing` на write-time и `resolveFor` на
read-path. Пилот **НЕ** реализуется как `if (case.amount <= 100000)` в коде процесса поверх
неограниченных грантов — это разорвало бы единый источник истины авторизации (T-0018 NF-1).

## 4. State machine жизненного цикла пилота — AC-6

### 4.1 Состояния `PilotState` **[НОВАЯ B-2]**

```
                          расширить (human-gate, §6)
                       ┌──────────────────────────────► РАСШИРЕН ──► (полный прод)
                       │
ЗАПЛАНИРОВАН ──старт──► АКТИВЕН ──откат (drain, §7)───► ОТКАЧЕН
   (gen draft         (гранты    │
    grants,           эффективны └──valid_until прошёл (АВТО, §4.3)──► ИСТЁК
    state=planned)    в срезе)
```

| Состояние | Человеко-видимое значение | Эффект на резолюцию грантов |
|---|---|---|
| `запланирован` | срез объявлен, пилот ещё не запущен | пилотные гранты **не эффективны** (`validFrom` в будущем / гранты не активированы) ⇒ `resolveFor` их не учитывает |
| `активен` | боевой запуск идёт в пределах среза | пилотные гранты **эффективны** в пределах среза: `isEffective(now)=true` ∧ `isNarrowerOrEqual(handle, set([node,interval]))` |
| `расширен` | срез ослаблен до полного прода (§6) | гранты расширены (новый промоут), пилотный срез снят |
| `откачен` | пилот свёрнут оператором (§7) | пилотные гранты дезактивированы (revoke/`validUntil=now`) ⇒ нулевая возможность; новые кейсы не стартуют |
| `истёк` | срок `validUntil` прошёл (§4.3) | пилотные гранты по `isEffective(now)=false` ⇒ нулевая возможность, **автоматически** |

### 4.2 Каждое состояние имеет наблюдаемый эффект на резолюцию

Состояние пилота — **не отдельная проверка**, а проекция на эффективность грантов: «активен»
⇒ гранты в срезе резолвятся `resolveFor`; «откачен/истёк» ⇒ те же гранты по
`isEffective`/`isNarrowerOrEqual` возможности не дают. Единый PDP (T-0021), ноль второго
чокпойнта.

### 4.3 Авто-истечение по сроку — `valid_until` = TTL = снятая возможность

Переход `активен → истёк` **автоматический, без ручного действия**: он есть прямое
следствие живого `isEffective(grant, now)` (`grant-lattice.ts:497`) — когда `now ≥
validUntil`, грант перестаёт быть эффективным, и `resolveFor` (`:511`) его отбрасывает.
Никакого таймера-демона «закрой пилот» в авторитете не нужно — TTL встроен в read-path
(T-0018 §4.5). Отображение состояния `истёк` в карточке — производное от `now ≥ validUntil`.

## 5. Граница среза обеспечена решёткой: кейс вне среза не попадает в пилот — AC-5

**Кейс вне среза не обрабатывается пилотной версией как СЛЕДСТВИЕ резолюции грантов, а НЕ
отдельной проверкой** (FR-5). Для кейса с суммой выше интервала / узлом вне поддерева / по
истёкшему сроку: грант, несущий полномочие на шаг пилотного процесса, по `isNarrowerOrEqual`
(`grant-lattice.ts:279` для interval, `:270` для node) / `isEffective` (`:497`) к этому
кейсу **не применим** — `resolveFor` (`grant-resolver.ts:489`) вернёт `no_grant`. Граница
пилота — **выход PDP**, не if в движке.

**Маршрутизация остатка (SEAM-2) — РЕШЕНО (design-owned, консервативный дефолт):** кейс вне
среза **маршрутизируется по полному/старому процессу** (не-пилотной версии бандла), а не
отклоняется и не ставится в очередь. Обоснование: drain-by-default петли (T-0129 §10.3)
держит старую версию доигрывающей; вне-срезовый кейс — для пилотной версии «не существует»,
он идёт по той версии, чьи гранты его покрывают. Это **не продуктовый блокер** (все варианты
выразимы на принятых примитивах: резолюция T-0021 + версионирование бандла T-0129); помечено
как **design-owned**. Жёсткие альтернативы (отклонение/очередь до расширения) — Stage-2, не
меняют объём MVP.

## 6. Расширение пилота → полный прод как ослабление среза под human-gate — AC-8

**Расширение = ослабление среза, проходящее тот же write-time subset-гейт T-0018.**
Расширение узла до всей оргструктуры / снятие интервала суммы / снятие срока — это **более
широкий scope** относительно текущего пилотного. ADR **НЕ вводит обхода `validateNarrowing`**
(`grant-lattice.ts:408`): расширение проверяется тем же гейтом относительно того, что вообще
санкционировано **владельцем-тенантом** — нельзя «расшириться» за пределы полного скоупа
процесса, разрешённого владельцем (FR-3). Полный прод = срез снят полностью (`node` = корень
оргструктуры, `interval` снят, `validUntil = null`).

**Human-gate (в духе промоута T-0129 FR-11 / extensibility §4):** расширение проходит под
**подтверждением человека** — осознанное решение «я проверил пилот и расширяю», а НЕ
формальный клик. Самоприменение расширения (self-elevation) структурно невозможно: расширение
— это новый промоут с human-gate, не self-apply (T-0129 §10.1).

## 7. Откат пилота — обратимая операция без боевого «мусора» — AC-9

**Откат:** пилотные гранты **дезактивируются** (revoke или `validUntil = now`) ⇒ срез
закрывается, новые кейсы по пилотному процессу **не стартуют** (`resolveFor` их грантов не
резолвит).

**Политика по уже запущенным в пилоте боевым инстансам — drain-by-default (РЕШЕНО,
design-owned):** in-flight боевые инстансы **доигрывают по версии бандла, на которой
стартовали** (как при эволюции T-0129 §10.3 / extensibility §7) — это **консервативный
дефолт**. Принудительная остановка in-flight (kill) — **отдельный риск, Stage-2** (SEAM-3),
не дефолт.

**Откат НЕ порождает боевых эффектов-«призраков» и НЕ переписывает уже совершённые боевые
эффекты пилота:** письма/платежи/1С-записи, реально сделанные в пилоте, **реальны и
остаются** в едином аудите. Откат закрывает будущее, не стирает прошлое.

## 8. Мониторинг и аудит — единый боевой лог, без второго лога — AC-7, AC-11

**Мониторинг пилота — срез ЕДИНОГО аудита по принадлежности к пилоту, без второй
телеметрии** (FR-7, FR-11). Человеку, решающему расширить/откатить, видно: какие реальные
кейсы прошли через срез, их исходы/маршруты, сбои/отказы прав/эффектов. Источник —
**существующий** `appendAuditEvent` (T-0031) / `GrantAuditEvent` (`grant-lattice.ts:91`).

**Пилотные события — боевые:** в отличие от прогона T-0130 (`test:true`, исключён из
комплаенс-выгрузки), события пилота **НЕ помечены `test`** и **НЕ исключаются** из
комплаенс-экспорта. Они отличимы по принадлежности к пилоту (`pilotId` в событии), но это
**боевая активность**. Старт/расширение/откат пилота и установка/снятие пилотных грантов
пишутся в единый лог как любая боевая грант-операция. Вокабуляр расширяет наследованный из
T-0129 (`impl.pilot.proposed`) пилот-фазой: `pilot.started` / `pilot.expanded` /
`pilot.rolled_back` / `pilot.expired` — добавки в **тот же** sink, не второй лог.

## 9. UX-инвариант two-floor: пилот — действие в карточке внедрения — AC-14

ADR удерживает **two-floor** (NF-5/NF-6): владелец процесса задаёт пилот **на уровне
понятий** — «этот отдел, договоры до 100 тыс., на месяц» — как **действие/вкладку в карточке
внедрения**, а **НЕ** редактируя гранты/решётку руками и **НЕ** как ручной редактор
scope-решётки. Перевод понятия (`PilotDeclaration`) в элементы решётки (`set([node,
interval])` + `validUntil`) — **машинный слой** под карточкой (§3.3), не задача клиента. Пара
draft/published и элементы решётки остаются машинным слоем. (Детальный UX — производная
задача B-4; здесь фиксируется лишь инвариант.)

## 10. Связь с петлёй T-0129 и промоутом (SEAM-1) — AC-10

Пилот — **фаза петли T-0129** в порядке рамки §2 (`прогон → пилот → промоут → прод`), между
прогоном и полным продом. Родительское требование — **T-0129 FR-10**; T-0132 — **детализация
именно этой фазы**, НЕ переоткрытие петли. **Промоут draft→published (T-0129 FR-11) —
предусловие пилота:** пилот раскатывает уже промоутнутый published-бандл на ограниченный срез
(`bundleVersion` в `PilotDeclaration` ссылается на промоутнутую версию). T-0132 **НЕ
переоткрывает промоут и НЕ дублирует петлю** (SEAM-1).

**Стык пилот↔промоут (SEAM-1) — РЕШЕНО (design-owned):** T-0129 §10.1 уже именует scope
пилота как `set([node, interval])` + `valid_until` и предоставляет impl-операцию
`propose_pilot_scope` (`impl.pilot.proposed`). T-0132 **наследует** этот контракт: его
`PilotDeclaration.{nodeAxis, amountAxis, validUntil}` — продуктовая форма того же scope, а
компиляция §3.3 даёт ровно `set([node, interval])` + `validUntil`. Точная стыковка «промоут
произвёл published-бандл → пилот раскатывает на срез» — совместная работа ADR T-0129/T-0132
на DESIGN; противоречия нет (оба используют `set([node,interval])`+TTL).

## 14. Rejected alternatives

| Опция | Почему отвергнута |
|---|---|
| Пилот как **отдельный if-фильтр** в движке поверх неограниченных грантов («`if case.amount ≤ 100000`») | Разрывает единый источник истины авторизации (T-0018 NF-1): граница пилота стала бы необеспеченной решёткой, аудит/резолюция её бы не видели. Срез обязан быть `interval`-grant-предикатом (FR-2, AC-2). |
| Новая сущность-**scope** «пилотный диапазон» (второй scope-механизм) | `interval`/`node` уже ЖИВЫ в `grant-lattice.ts` и обслужены `meet`/`isNarrowerOrEqual`. Новый примитив = переизобретение, прямо запрещён рамкой §2 п.5 и NF-1/AC-12. |
| **Второй аудит-лог** для пилотной телеметрии | Пилот — боевая активность; параллельный лог раздваивает истину и комплаенс. Мониторинг = срез единого `appendAuditEvent` по `pilotId` (FR-7/FR-11). |
| **Флаг `simulate`/частично-боевой** пилот | Стирает границу GRAN-1 с симуляцией (NF-2): либо боевые эффекты в «тесте», либо «пилот» без нагрузки. Пилот всегда published+боевой; симуляция всегда draft+стаб. |
| **Принудительная остановка in-flight** инстансов при откате как дефолт | Агрессивно: убивает реальные боевые кейсы на полпути. Дефолт — drain (T-0129 §10.3); kill — отдельный риск Stage-2 (SEAM-3). |
| Таймер-демон «закрой пилот по сроку» в авторитете | Избыточно: `valid_until` = TTL встроен в живой `isEffective` на read-path (`grant-lattice.ts:497`). Авто-истечение — следствие резолюции, не отдельный процесс. |
