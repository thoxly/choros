## 1. Контекст и проблема

Зона РАБОТА в T-0538 содержит два фиксированных пункта (`inbox`, `processes`) и явный задел: «динамические «Разделы» E16/T-0349 — зона РАБОТА оставляет место». Финальное решение фаундера (D-063): нав-секционирование приложений принадлежит **E-NAV-IA** (T-0349 и E16 отвечают за рантайм-привязку процессов: триггеры/точки входа/исходы/связи — не за группировку приложений в боковой панели).

Сегодня приложения пользователя отображаются только в экране «Приложения» (КОНСТРУКТОР), как плоский список `GET /api/applications`. В зоне РАБОТА нет навигационного доступа к конкретным приложениям по бизнес-функции. Пользователь, которому нужна «Закупка», не видит её в сайдбаре: он должен искать в общем списке.

**Проблема: зона РАБОТА не отражает бизнес-структуру тенанта.** Приложения группируются по бизнес-функции (Финансы / HR / Продажи), заданной внедренцем или агентом. Эти группы — «Разделы» — должны строиться из данных, а не хардкодиться. При пустом разделе или приложении без раздела нав не теряет приложение.

**Данность (решения фаундера):**
- Раздел = атрибут «бизнес-функция» приложения. Создание/удаление/переименование раздела — пользовательское действие.
- Нав отражает данные: `GET /api/applications` → группировка по `section` → нав-секции зоны РАБОТА.
- Видимость конкретных приложений гейтится реальными грантами (связь T-0539).

## 2. Решение (load-bearing)

**Завести поле `section TEXT NULL` в `choros.application` (миграция). Сайдбар строит подсекции зоны РАБОТА динамически: `GET /api/applications` → клиентская группировка по `app.section` → нав-секции. Приложение без `section` → fallback-секция «Другое» (не теряется). Создание/удаление/переименование раздела = пользовательское действие через UI-жест в экране «Приложения» (поповер строки или inline-edit) или через агента (PATCH/PUT `/api/applications/:id`). Граница с E16: рантайм-привязка (триггеры/точки входа/исходы/связи) — НЕ здесь; E16 знает о процессах, T-0540 знает о `app.section`. Видимость: каждое приложение в нав гейтируется ресурс-грантом на read через T-0539; секция без ни одного видимого приложения не рендерится. Комментарий в nav-config.js, указывающий «E16 добавит динамические разделы» — исправить на E-NAV-IA (doc-follow-up для impl).**

Решение пропорционально: один nullable столбец `section` в существующей таблице (additive-safe migration), клиентский хелпер группировки (чистая функция над массивом приложений), расширение render-логики зоны РАБОТА в `shell.jsx` — без нового роутера, без новых permission-движков, без нового таблицы.

### 2.1 Почему поле в `application`, а не отдельная таблица `section`

Раздел — **атрибут классификации приложения**, не самостоятельная сущность с поведением. Отдельная таблица `section` (со своим `id`) потребует: отдельной таблицы + FK в `application.section_id` + CRUD-эндпоинтов для секций + DDL-рисков при переименовании. При этом ничего не выигрывает: раздел не имеет собственного жизненного цикла вне приложений (нет смысла держать пустой раздел без приложений), нет никаких атрибутов раздела кроме имени, и нет требования глобальной уникальности или кросс-реферирования. Свободный текст `section TEXT NULL` — стандартный паттерн тегирования/группировки (прецедент: `description TEXT NULL` в той же таблице). Список разделов = `SELECT DISTINCT section FROM application WHERE section IS NOT NULL`. Переименование раздела = `UPDATE application SET section='...' WHERE section='...'` (пакетно через UI или агент).

**Отклонённые альтернативы — §3.**

### 2.2 Почему клиентская группировка, а не серверный эндпоинт «секции»

Клиент УЖЕ тянет `GET /api/applications` для экрана «Приложения». Сайдбар может потреблять те же данные через общий кэш (или отдельный лёгкий фетч). Серверный эндпоинт «секции» — это обёртка над `SELECT DISTINCT section`, которая ничего не добавляет кроме RTT. Группировка — чистая функция `groupBySection(apps[]) → { section: string|null, items: App[] }[]`, нулевые зависимости. Обновление нава при смене раздела = инвалидация кэша `applications` (тот же паттерн, что обновление списка при создании приложения в screen-apps.jsx).

## 3. Rejected alternatives

| Option | Why not |
|---|---|
| **Отдельная таблица `nav_section` (id, label, order) + FK в application** | Раздел — атрибут классификации, не сущность с поведением. Отдельная таблица: лишний DDL, FK, CRUD. «Пустой раздел» без смысла. Список разделов = `SELECT DISTINCT section`. Переименование = batch UPDATE. Текстовый атрибут достаточен для MVP. |
| **Брать секционирование из существующего `modules-nav.ts` NavSection** | `NavSection` в `modules-nav.ts` — это иерархия nav_version в конструкторе (Section→App→Form/List — для сборки решений агентом). Это ДРУГОЙ уровень: он описывает структуру конструктора, а не боковую панель пользователя. Смешение двух уровней создаст неявную зависимость между конструктор-конфигом и боковой панелью. |
| **Хардкодить разделы в nav-config.js** | Нарушает решение фаундера «нав отражает данные». Каждое изменение бизнес-структуры тенанта требовало бы правки кода. Внедренец и агент должны управлять разделами через данные, не деплоем. |
| **Серверный эндпоинт `GET /api/nav/sections`** | Дублирует `GET /api/applications`. Группировка — чистая клиентская функция над уже доступными данными. Дополнительный RTT без пользы; нарушает принцип «одна истина» (приложения уже несут `section`). |
| **Порядок разделов фиксирован алфавитом** | Убивает возможность пользователя расставить разделы в удобном порядке. Нужен `section_order INT NULL` или explicit-order через отдельный поиск. MVP: порядок = алфавитный (честная деградация); шаг 2 = `section_order` если UX-фидбек требует. Не блокирует дизайн. |
| **Приложение без раздела — скрыть из нава** | Потеря приложения из нав — нарушение принципа «не теряется ни одно доступное приложение» (аналог FF-MAP T-0538). Fallback-секция «Другое» (или «Общее») держит все неклассифицированные приложения. |

## 4. Модель данных (§а)

### 4.1 Где живёт «бизнес-функция / раздел»

**Атрибут `section TEXT NULL` в таблице `choros.application`.**

Сегодняшняя схема (`migrations/003_application.sql`):
```sql
CREATE TABLE choros.application (
  tenant_id    uuid NOT NULL,
  id           uuid NOT NULL,
  slug         text NOT NULL,
  display_name text NOT NULL,
  description  text NULL,
  created_at   bigint NOT NULL,
  updated_at   bigint NOT NULL,
  PRIMARY KEY (tenant_id, id),
  UNIQUE (tenant_id, slug)
);
```

**Нужна additive migration (N+1 слот, например `108_app_section.sql`):**
```sql
-- 108 · application.section — бизнес-функция/раздел для группировки в нав РАБОТА (T-0540)
--
-- Additive-safe: добавляем NULL-колонку → нет блокировки существующих строк.
-- Нет NOT NULL, нет DEFAULT (кроме NULL): NULL = «раздел не задан» → fallback-секция.
-- Нет отдельной таблицы sections — см. ADR T-0540 §3.
-- Нет индекса на section по умолчанию: нав тянет все приложения тенанта (список маленький),
-- SELECT DISTINCT делается по уже загруженным данным. Если нужен индекс → additive позже.

ALTER TABLE choros.application
  ADD COLUMN IF NOT EXISTS section text NULL;
```

Изменение **additive-safe**: nullable-колонка, нет NOT NULL, нет CONSTRAINT.

### 4.2 Как раздел заводится и правится

| Операция | Шов | Кто |
|---|---|---|
| **Создать раздел** | Создать/отредактировать приложение → указать `section` в поле «Раздел» | Внедренец (в UI: экран «Приложения»), агент (PATCH `/api/applications/:id`) |
| **Переименовать раздел** | `UPDATE application SET section='Новое' WHERE section='Старое'` через batch-UI (поповер в строке) или агент | Внедренец / агент |
| **Удалить раздел** | Очистить `section` (`section = NULL`) у всех его приложений → они переходят в fallback | Внедренец / агент |
| **Переместить приложение в другой раздел** | Изменить `section` у одного приложения | Внедренец / агент |

**Нет отдельного CRUD-контроллера «Раздел»** — операции реализуются через существующий эндпоинт `PATCH /api/applications/:id` (добавить поле `section` в payload) и экран «Приложения».

### 4.3 API-шов (impl-зависимость)

```
POST /api/applications    body { slug, display_name, description?, section? }
PATCH /api/applications/:id  body { section? }  ← НОВЫЙ (или расширение существующего)
GET  /api/applications    → { applications: [{ id, slug, display_name, description, section, tier, created_at, ... }] }
```

`GET /api/applications` обязан возвращать поле `section` (null или строка). Это additive — старые клиенты игнорируют поле.

## 5. Как сайдбар строит подсекции зоны РАБОТА (§б)

### 5.1 Источник данных

Сайдбар при буте тянет приложения тенанта (тот же `GET /api/applications` что и экран «Приложения»; можно переиспользовать кэш через React context или SWR-ключ). Данные обновляются при:
- создании приложения (уже реализовано: `handleCreated → load()`),
- смене раздела у приложения (инвалидация кэша),
- смене тенанта (уже обрабатывается `active-tenant.js`).

### 5.2 Группировка (чистая функция)

```js
// web/src/app-shell/nav-sections.js  (новый файл, zero-dep)

/**
 * @typedef {{ id: string, slug: string, display_name: string, section: string|null, tier: string }} App
 * @typedef {{ section: string, fallback: boolean, apps: App[] }} NavAppSection
 */

const FALLBACK_SECTION = 'Другое';

/**
 * Группирует приложения по полю `section` для нав зоны РАБОТА.
 * - Приложения без section → fallback-секция 'Другое' (не теряются).
 * - Секции сортируются: именованные — по алфавиту, fallback — всегда последней.
 * - Пустой массив apps → пустой результат (нет секций).
 *
 * @param {App[]} apps
 * @returns {NavAppSection[]}
 */
export function groupAppsBySection(apps) {
  if (!Array.isArray(apps) || apps.length === 0) return [];
  const map = new Map();  // section label → App[]
  const fallback = [];
  for (const app of apps) {
    if (app.section) {
      if (!map.has(app.section)) map.set(app.section, []);
      map.get(app.section).push(app);
    } else {
      fallback.push(app);
    }
  }
  const named = [...map.entries()]
    .sort(([a], [b]) => a.localeCompare(b, 'ru'))
    .map(([section, items]) => ({ section, fallback: false, apps: items }));
  if (fallback.length > 0) {
    named.push({ section: FALLBACK_SECTION, fallback: true, apps: fallback });
  }
  return named;
}
```

**Инвариант:** ни одно приложение из `apps[]` не теряется (`sum(section.apps.length) === apps.length`).

### 5.3 Рендер зоны РАБОТА в сайдбаре

Зона РАБОТА в `shell.jsx` рендерит:

1. Фиксированные пункты (из T-0538 `ZONES.find(z=>z.id==='work').items`): `inbox`, `processes`.
2. Динамические секции из `groupAppsBySection(apps)`:
   - Каждая `NavAppSection` рендерится как подзаголовок секции (`chs-nav__section-label`) + список пунктов-приложений (`chs-nav__item` с `onClick → navigate('/app-records/' + app.id)`).
   - Fallback-секция рендерится только если в ней есть приложения.
   - Пустой `apps[]` или `sections.length === 0` → зона РАБОТА рендерит только фиксированные пункты (честная пустота, T-0306).

### 5.4 Навигация к приложению из нава

Клик на пункт приложения в сайдбаре → `navigate('/app-records/' + app.id)` (экран записей). Это существующий маршрут (уже используется в `AppActions` в `screen-apps.jsx`). Маршрут **не меняется** — инвариант T-0538 §6.

### 5.5 Пустой раздел / приложение без раздела (fallback)

| Кейс | Поведение |
|---|---|
| Приложение с `section='Финансы'`, единственное в разделе | Раздел «Финансы» с одним пунктом. Пункт виден (нет правила «раздел только с ≥2»; пустой раздел не рендерится, но раздел с одним приложением рендерится). |
| Приложение с `section = NULL` | Попадает в fallback-секцию «Другое» в конце списка. |
| Все приложения с `section = NULL` | Одна fallback-секция «Другое» со всеми. |
| Нет приложений (`apps = []`) | Нет секций; зона РАБОТА рендерит только фиксированные пункты (`inbox`, `processes`). |
| Пользователь без ни одного приложения с read-грантом | Нет секций (T-0539 фильтрует); зона РАБОТА — только `inbox`/`processes`. |

## 6. Создание/удаление/переименование раздела (пользовательское действие) (§в)

### 6.1 Где в UI

Управление разделом встроено в экран «Приложения» (`screen-apps.jsx`):

- **Создать/изменить раздел приложения**: поповер строки приложения (кнопка «…»→ «Изменить раздел») → inline-форма с полем `section` (или отдельная модалка). Submit → `PATCH /api/applications/:id { section: 'Финансы' }` → обновление кэша → нав перестраивается.
- **Переименовать раздел глобально** (все приложения раздела): действие «Переименовать раздел» на уровне группы в экране «Приложения» (если добавить группировку и в этот экран) → `PATCH` батч или серверный эндпоинт `PATCH /api/applications?section=Старый { section: 'Новый' }`. MVP: достаточно пооднного-по-одному.
- **Удалить раздел**: очистка `section` у всех приложений через тот же поповер («Убрать из раздела»).

### 6.2 Через агента

Агент (E16/AI-консоль) эмитит `PATCH /api/applications/:id { section: '...' }` как часть операции конфигурации тенанта. Поле `section` появляется в payload так же, как `display_name` или `description`.

### 6.3 Что НЕ является пользовательским действием раздела

- Создание маршрута в SPA (маршруты не меняются — инвариант T-0538 §6).
- Управление грантами на приложение — это T-0539.
- Управление процессами/триггерами/исходами — это E16.

## 7. Граница с E16 (§г)

| Аспект | T-0540 (ЗДЕСЬ) | E16 (НЕ ЗДЕСЬ) |
|---|---|---|
| Что такое «приложение» в боковой панели | `app.section` — атрибут группировки; нав строится из данных приложений | — |
| Рантайм-привязка (entry-points, triggers, outcomes, relations) | НЕ здесь | E16 привязывает процессы к приложениям: точки входа, триггеры, исходы, связи между объектами |
| Строки «Запустить процесс», «Перейти к задаче» в контексте приложения | НЕ здесь | E16 добавляет action-entry-points в карточку/экран приложения |
| Раздел как имя бизнес-функции | T-0540: поле `app.section`, управляется через UI/агент | E16 может использовать тот же `app.section` для контекста привязки — не конфликт |
| BPMN-процессы | НЕ здесь | E16 |
| Нав-секции боковой панели | T-0540 | — |

**Инвариант:** T-0540 и E16 не конфликтуют. E16 читает `app.section` как контекст (если нужен), но не владеет им. T-0540 не знает о процессах.

## 8. Видимость: гейт грантами (связь T-0539) (§е)

T-0539 (capability-nav-visibility) зафиксировал как non-goal #1: «ресурс-гранулярный фильтр пунктов РАБОТЫ (конкретные приложения по read-гранту) — задел E16». T-0540 — это и есть тот задел.

**Механизм (impl-зависимость T-0539+T-0540):**

Сервер: `GET /api/applications` уже гейтится тенант-изоляцией (RLS). Если T-0539 добавляет ресурс-гранты на конкретные приложения (read-грант `application:{id}:read`), то `GET /api/applications` фильтрует список до разрешённых. Клиент ничего не меняет: `groupAppsBySection(apps)` работает поверх уже отфильтрованного списка.

**Секция без ни одного видимого приложения не рендерится** (нет пустых секций-заголовков в нав — это шум, аналог правила T-0538 «заголовок без выбора = шум»).

Если T-0539 ресурс-фильтр ещё не реализован: `GET /api/applications` возвращает все приложения тенанта (как сейчас) → все приложения видны в нав → нет регрессии. T-0540 безопасно деплоится независимо от T-0539.

## 9. Исправление комментария nav-config.js (§д)

**Текущий комментарий в `nav-config.js` (строки ~33–35):**
```js
// «Раздел» (Финансы/HR/Продажи) — лёгкий конструкт группировки приложений по
// бизнес-функции, создаётся внедренцем/агентом. Пока не построен динамически:
// приложения группируются статично в «Работа». E16 добавит динамические разделы
// поверх этой IA-основы (T-0349).
```

**Должен стать (после impl T-0540):**

## 10. Impl-зависимости (runtime — НЕ блокируют дизайн)

1. **Миграция `108_app_section.sql`** — `ALTER TABLE choros.application ADD COLUMN IF NOT EXISTS section text NULL`. Требует dev PG (container-стек). Additive-safe.
2. **Обновление `GET /api/applications`** — добавить `section` в SELECT и DTO (`src/http/applications.ts`).
3. **Обновление `PATCH /api/applications/:id`** — добавить поле `section` в payload и update-запрос.
4. **Новый хелпер `groupAppsBySection`** — `web/src/app-shell/nav-sections.js` (zero-dep, чистая функция).
5. **Расширение render-логики зоны РАБОТА** — `web/src/app-shell/shell.jsx`: тянет `applications`, передаёт в `groupAppsBySection`, рендерит секции.
6. **Поле `section` в `CreateAppModal`** — опциональное поле «Раздел» при создании приложения (`screen-apps.jsx`).
7. **Действие «Изменить раздел»** в поповер `AppActions` (`screen-apps.jsx`) + поле в модалке редактирования.
