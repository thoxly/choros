# ADR T-0057 — Язык исполняемого кода Choros в MVP: TS-only ядро vs TS+Python с дня 1

Статус: **DRAFT — pending founder ratification** (гейт GT-1)
Фаза: DESIGN задачи T-0057 (S-3). Вход: `docs/specs/T-0057-ts-vs-python.spec.md`.
Рекомендация архитектора: **В-C — TS-only MVP-контур + зарезервированная external-task-граница для Python в Stage 2.**
Refs (ратифицированное, НЕ пересматривается): `docs/design/stack-and-fleet-ops.md` §1/§2, `docs/design/tenancy-and-delivery.md`, `CONCEPT.md` §5/§6/§12/§13.

> Этот ADR НЕ решает вопрос — он готовит решение к подписи фаундера. Выбор языка/языков
> исполняемого кода MVP и границы «Python — Stage 2» ратифицирует фаундер (GT-1). Документ
> обязан дать реальный выбор: ниже честно показаны trade-offs всех трёх вариантов, а не
> подгонка под гипотезу заголовка бэклога.

## 0. Решаемый вопрос (из спеки)

На каком языке/языках живёт **прикладной** исполняемый код Choros в MVP, и где проходит
граница «Python — Stage 2». Декомпозиция: РВ-1 язык ядра MVP; РВ-2 граница Stage 2 по
классам кода; РВ-3 статус строки CONCEPT §6 «агентский рантайм = Python».

**Вне рамок** (не переоткрывается этим ADR): JVM/Flowable-движок (ратифицирован stack ADR §1
как «чёрный ящик уровня Postgres», его Java «не считается языком стека»); React/TS-фронт
(CONCEPT §6); выбор конкретного агентского фреймворка (ADK vs LangGraph vs TS-аналог);
S-1 (движок), S-2 (домен); юридический разбор лицензий/152-ФЗ.

## 1. Собранные данные (Д-1…Д-6) — факт-база, не «по ощущениям»

Всё проверено на ветке `task/T-0057-ts-vs-python-adr` (база dev), репозиторий Choros.

### Д-1 — рантаймы на один silo-контур по вариантам

Источник: `docker-compose.yml` (сейчас: только `postgres:16`), stack ADR §1 (полный контур =
Node-ядро + Flowable embedded-JVM + Postgres + Keycloak + Caddy), CONCEPT §12.

«Рантайм» в смысле К-1 = **исполнитель прикладного/агентского кода, который мы обновляем и
покрываем ops-органами**. Postgres/Keycloak/Caddy — инфраструктурные образы (как и движок,
но движок отдельно помечен P1-риском в stack ADR §59), их считаем по одному разу во всех
вариантах; разница между вариантами — ровно по числу **прикладных языковых рантаймов**.

| Вариант | Прикладные языковые рантаймы на контур | Счёт |
|---|---|---|
| В-A TS-only | Node/TS (ядро+воркеры+ops) + JVM-движок (ратифицирован, «не язык стека») | **2** |
| В-C TS-ядро + Python-Stage-2 | Node/TS + JVM-движок; Python — НЕ в MVP-контуре, граница зарезервирована | **2** (в MVP) |
| В-B TS+Python day-1 | Node/TS + JVM-движок + **Python-агентский рантайм** | **3** |

Цена третьего рантайма в В-B (на КАЖДЫЙ из 200–300 контуров целевого флота): +образ
(Python+зависимости агентского фреймворка, типично 200–800 МБ), +базовая память процесса,
+отдельная поверхность обновлений/CVE (pip-граф агентского фреймворка обновляется чаще ядра),
+третий класс ops-органов (см. Д-/К-6). Умножение на флот — это и есть весовой множитель К-1/К-6.

### Д-2 — агентские сценарии MVP × покрытие TS-SDK

Источник: **CONCEPT §13 (роадмап) — решающий факт**. Роадмап продукта САМ помещает агентский
рантайм в **Этап 2**, не в MVP:

- «**MVP — ядро ценности**: Flowable как инфраструктура · оргструктура + роли + замещения ·
  инбокс задач · bpmn-js модельер · формы на form-js · **external worker API + документация**.»
- «**Этап 2 — агенты**: Агентский рантайм (Python, MCP, guardrails, аудит) · 2–3 готовых агента.»

**Вывод Д-2: в MVP нет ни одного обязательного агентского сценария.** MVP везёт *контракт*
external worker (граница), а не агентов-исполнителей. Значит «нужен ли Python-рантайм в
MVP-контуре» упирается не в зрелость TS-агентских SDK (это вопрос Этапа 2), а в то, нужен ли
вообще исполняемый агент в MVP — по роадмапу нет. Это снимает В-B по существу, а не по вкусу.

### Д-3 — TS external-task клиент к движку: УЖЕ ПОСТРОЕН

Источник: `src/http/externalWorker.ts` (+ `src/core/jobStore.ts`, e2e-тест
`src/__tests__/externalWorker.e2e.test.ts`, зелёный).

Граница «ядро ↔ воркер» в Choros — это **языко-нейтральный HTTP-контракт**, уже реализованный
в TS на стороне ядра:

- `POST /jobs` — enqueue job (topic, variables, retries) → 201 Job;
- `POST /external-task/fetch-and-lock` — pull с лизом (workerId, topics[], maxJobs, lockDurationMs);
- `POST /external-task/:id/complete` — (workerId);
- `POST /external-task/:id/fail` — (workerId, retries, retryTimeoutMs) + backoff/DLQ.

Это ровно pull/external-task-паттерн CONCEPT §5 («воркер на любом языке: Java, Python, JS,
.NET»). Контракт стоит на стороне ядра; воркер по ту сторону HTTP — **любой язык**. Зрелость
«TS external-task клиента к S-1-движку» в смысле спеки нерелевантна для day-1: ядро —
*сервер* этого контракта (мы его написали), а не клиент чужого движка; Flowable-мост к
*движку* — отдельная сторона (sealed-контракт `ci/checks/flowable-bridge-contract.sh`,
T-0058+), и он тоже TS со стороны ядра.

**Следствие для К-7: граница для Python в Stage 2 не «зарезервирована на бумаге» — она уже
существует и оттестирована как HTTP-API.** Python-воркер Stage 2 = новый HTTP-клиент к
существующим эндпоинтам, ноль изменений в ядре.

### Д-4 — зрелость TS-агентских фреймворков vs Python (ADK/LangGraph)

Письменно (К-3/К-4, найм/экосистема — экспертное обоснование, не «очевидно»):

На дату ADR Python-экосистема агентов (Google ADK, LangGraph, расширенный tool/memory-слой)
объективно богаче и зрелее TS-аналогов — это и есть мотив строки CONCEPT §6. **Но** этот
разрыв материален только когда мы *исполняем* агента, т.е. на Этапе 2 (Д-2). Для MVP, где
исполняемых агентов нет, разрыв не оплачивается ничем. Привязывать выбор языка MVP-контура к
зрелости фреймворка, который понадобится на следующем этапе, = платить за Stage-2-экосистему
ценой Stage-1-сложности (третий рантайм × флот) до того, как она даёт ценность. Решение о
*фреймворке* (ADK vs LangGraph vs TS) принимается на входе в Этап 2, когда известны конкретные
агентские кейсы — и оно не требует, чтобы Python приехал в MVP-контур заранее.

### Д-5 — BYO-LLM / провайдерские интеграции MVP × TS-SDK

Источник: CONCEPT §12, tenancy-and-delivery.md §8 (152-ФЗ, on-prem).

«Агентский рантайм работает с **любым LLM-эндпоинтом** (OpenAI-compatible API) — облако,
прокси или локальная модель в контуре клиента. **LLM-провайдер — конфигурация, не
зависимость**» (§12). РФ-локальные/152-ФЗ-модели подключаются как OpenAI-совместимый эндпоинт.
Следствие: интеграция с LLM — это HTTP к OpenAI-совместимому URL, тривиально покрывается из
TS (`fetch`); никакой критичной интеграции, доступной *только* в Python, для MVP не выявлено
(в MVP исполняемых агентов нет вовсе — Д-2). Привязка к конкретному провайдерскому Python-SDK
противоречила бы инварианту «провайдер = конфигурация».

### Д-6 — путь Python-воркера к данным тенанта (только для В-B)

Источник: `ci/checks/single-resolver.sh` (FF-A5: `resolveHandle` — единственная точка
handle→record), `ci/checks/cross-tenant-fitness.sh` (T-0115: choros_app + FORCE RLS,
single изоляционный код-путь), T-0018/T-0021 (grant-resolver/PDP), T-0028
(`flowable-bridge-contract.sh`: всякий мост валидирует `assertVariableValue` и роутит мутации
через `resolveFor`).

Инвариант ратифицированного ядра: **любой код, читающий/меняющий данные тенанта, проходит
ОДИН резолвер (PDP) + tenant-RLS**. Два допустимых пути для Python-воркера:

- **(а) Python ходит только через HTTP-API ядра** (external-task complete/fail + доменные
  эндпоинты). Тогда он НЕ «второй путь к данным»: авторизация и RLS остаются в TS-ядре, Python
  не касается БД. Это совместимо с инвариантом — и это путь, который external-task-граница
  навязывает архитектурно (воркер видит только job-payload и REST).
- **(б) Python ходит в Postgres напрямую.** Тогда PDP/grant-resolver и tenant-RLS-дисциплину
  пришлось бы **продублировать на втором языке** — это прямое нарушение «один резолвер»
  (`single-resolver.sh`) и `cross-tenant-fitness`, **red-line-риск 152-ФЗ** (две модели
  изоляции расходятся — сам по себе аудит-риск, tenancy-doc §7 «две модели изоляции…
  аудит-риск»).

**Вывод Д-6:** даже в В-B приемлем только путь (а). Но путь (а) = именно external-task-граница,
которая в В-C и так есть без Python в контуре. То есть В-B не даёт по К-2 ничего сверх В-C,
а лишь добавляет рантайм и риск ошибочно выбрать путь (б).

## 2. РВ-1 / РВ-2 / РВ-3 — прямые ответы

### РВ-1 — язык ядра MVP

**TS-only.** Ядро (API, оргмодель/RBAC, объектная модель, мост к движку/outbox, серверный
рендер форм, ops-каталог, UI) остаётся 100% TypeScript (Node ≥20, единственная рантайм-зависимость
`pg`). Python в обязательный MVP-контур не входит. Это подтверждает текущее фактическое
состояние кодовой базы (Python отсутствует) и stack ADR §1 («Node/TS-ядро»).

### РВ-2 — граница Stage 2 по классам кода

| Класс кода | Вердикт | Обоснование |
|---|---|---|
| (а) Агентский рантайм (LLM-агенты как external worker) | **Python Stage 2** | CONCEPT §13: агенты = Этап 2. Подключается через уже существующую external-task HTTP-границу (Д-3). В MVP не реализуется и не поставляется. |
| (б) ML/инференс-воркеры | **Python Stage 2** (не-цель MVP) | Той же external-task-границей; ни одного ML-сценария в MVP-роадмапе нет. |
| (в) ops/эксплуатационные скрипты | **TS day-1** | Ops-каталог уже TS (`ops/catalog/run_vacuum.ts`, `queue_stats.ts`); CI-fitness = bash (`ci/checks/*.sh`). Stack ADR §2: ops-органы edут с контуром. Никакой потребности в Python. |
| (г) Модули расширения / authoring (config-as-code) | **TS day-1** | extensibility-and-authoring.md: код-native кастом = sandbox-iframe (фронт/TS), RBAC в TS-ядре, «binding-валидируемый». Не Python. |
| (д) BYO-LLM / провайдерские интеграции | **TS day-1** (через границу) | LLM = OpenAI-совместимый HTTP-эндпоинт = конфигурация (Д-5). Покрывается из TS; исполняется агентом (Этап 2) или прямым HTTP. |

### РВ-3 — статус строки CONCEPT §6 «агентский рантайм = Python (ADK/LangGraph)»

**СМЯГЧИТЬ (не отвергнуть, не унаследовать буквально).** §6 верна по сути: когда дойдём до
*исполнения* агентов (Этап 2), Python/ADK/LangGraph — обоснованный выбор рантайма агента ЗА
границей ядра (external worker). Смягчение: §6 НЕ означает, что Python-рантайм обязан приехать
в MVP-контур с дня 1. Сама §6 формулирует Python как external worker («подключается тем же
механизмом»), а §5 фиксирует «решение обратимо: сервис выносится, когда появляется реальная
граница… не раньше». Для MVP реальной границы-агента ещё нет (Д-2) — значит по букве самого
CONCEPT Python в MVP-контур не въезжает. Строка §6 описывает *язык будущего агентского
воркера*, а не *язык MVP-контура*.

## 3. Три варианта × семь критериев (go/no-go для MVP)

Легенда: ✅ выгодно / ⚠️ нейтрально-с-оговоркой / ❌ невыгодно-для-MVP.

### В-A — TS-only day-1 (Python вообще не цель, даже как зарезервированная граница)

| К | Оценка |
|---|---|
| К-1 рантаймы в silo | ✅ 2 (node+JVM) × флот |
| К-2 единый аудит/RLS | ✅ один резолвер, один язык доступа к данным |
| К-3 найм/AI-кодген | ✅ один язык, минимум стыков; ревью вслепую проще всего (§6) |
| К-4 экосистема агентов/BPMN-клиентов | ⚠️ агентская экосистема Python недоступна — но в MVP агентов нет (Д-2); BPMN-мост TS уже есть (Д-3) |
| К-5 BYO-LLM | ✅ OpenAI-совместимый HTTP из TS (Д-5) |
| К-6 fleet-ops покрытие | ✅ 2 класса ops-органов × флот |
| К-7 обратимость | ⚠️ риск: если В-A трактовать как «границу не резервируем», Python Stage 2 потребует достроить контракт. **Но фактически граница УЖЕ построена (Д-3)** — значит запирания нет даже в В-A. |

**Вердикт В-A: GO-для-MVP технически**, но В-A и В-C на day-1 неотличимы по коду (оба
TS-only-контур), а В-A слабее формулировкой обратимости (не называет границу как
зафиксированный Stage-2-шов). Практически В-A ⊂ В-C.

### В-B — TS+Python day-1 (Python-агент обязателен в MVP-контуре)

| К | Оценка |
|---|---|
| К-1 рантаймы в silo | ❌ 3 (node+JVM+Python) × 200–300 контуров |
| К-2 единый аудит/RLS | ⚠️→❌ приемлем только если Python ходит через API ядра (путь «а», Д-6); прямой БД-доступ = red-line дубль RLS/PDP. Добавляет соблазн ошибки без выгоды. |
| К-3 найм/AI-кодген | ❌ второй язык + стык TS↔Python, который фаундер ревьюит вслепую — прямое нарушение «минимум языков/стыков» §6 |
| К-4 экосистема агентов | ✅ Python-экосистема доступна — но оплачивается до того, как есть агентский кейс (Д-2/Д-4) |
| К-5 BYO-LLM | ⚠️ не лучше В-C: провайдер = конфигурация в любом варианте |
| К-6 fleet-ops покрытие | ❌ 3-й класс ops-органов (диагностика+починка Python) × каждый контур (stack ADR §2 DoD) |
| К-7 обратимость | n/a (Python уже внутри) |

**Вердикт В-B: NO-GO для MVP.** Платит тройную цену (рантайм × флот, ops-класс × флот, второй
язык под слепое ревью + red-line-соблазн прямого БД-доступа) за экосистему, для которой в
MVP-роадмапе НЕТ ни одного исполняемого агентского сценария (Д-2). Чистый минус по 4 из 7
критериев, плюс по К-4 — преждевременный.

### В-C — TS-ядро + Python-как-Stage-2-расширение (граница зарезервирована)

| К | Оценка |
|---|---|
| К-1 рантаймы в silo | ✅ 2 (node+JVM) в MVP × флот; Python приедет только когда даст ценность |
| К-2 единый аудит/RLS | ✅ один резолвер; Stage-2-Python архитектурно заперт на путь «через API ядра» (external-task видит только job-payload+REST, не БД) → инвариант сохранён by design (Д-6) |
| К-3 найм/AI-кодген | ✅ MVP — один язык; стык TS↔Python появляется только на Этапе 2 и только за HTTP-границей |
| К-4 экосистема агентов | ✅ дверь в Python-экосистему открыта (граница есть), но не оплачивается раньше Этапа 2 |
| К-5 BYO-LLM | ✅ как В-A |
| К-6 fleet-ops покрытие | ✅ 2 класса ops-органов в MVP; 3-й добавляется вместе с агентами на Этапе 2 |
| К-7 обратимость | ✅ **доказано не на бумаге, а кодом**: external-task HTTP-контракт (`/jobs`, `/external-task/fetch-and-lock|complete|fail`) уже реализован и e2e-зелёный (Д-3). Python Stage 2 = новый HTTP-клиент, ноль правок ядра. |

**Вердикт В-C: GO — рекомендуется.** Берёт всё лучшее В-A (2 рантайма, один язык, единый
резолвер) и явно фиксирует Stage-2-шов как уже-построенную границу, закрывая К-7 фактом, а не
обещанием. Не закрывает дверь в Python-экосистему и не платит за неё до Этапа 2.

## 4. Рекомендация фаундеру

**В-C: TS-only MVP-контур + зарезервированная (де-факто уже построенная) external-task-граница
для Python в Stage 2.**

Обоснование одним абзацем: MVP-роадмап продукта сам помещает агентов в Этап 2 (CONCEPT §13),
поэтому в MVP нет ни одного исполняемого агентского/ML-сценария, ради которого Python должен
въехать в каждый из 200–300 silo-контуров (К-1/К-6 × флот). Граница, через которую Python
подключится позже, — не гипотеза: HTTP external-task-контракт ядра уже реализован и
e2e-протестирован (`src/http/externalWorker.ts`), поэтому Stage-2-Python = новый HTTP-клиент
без переписывания ядра (К-7 закрыт фактом). Это прямо реализует весовой принцип §6 «минимум
языков/стыков под слепое ревью» и §5 «логику на границу, обратимо, не раньше реальной нужды».
В-A практически совпадает с В-C на day-1, но В-C сильнее формулирует обратимость; В-B —
NO-GO (тройная цена за экосистему без MVP-кейса + red-line-соблазн второго пути к данным).

### Trade-off, который фаундер берёт сознательно (честно)

- **Что теряем, выбрав В-C/TS-only-MVP:** на Этапе 2, когда дойдём до агентов, нужно будет
  *выбрать и поднять* Python-рантайм и оплатить +1 ops-класс × флот — эта работа отложена, не
  отменена. Если фаундер планирует флагманский агентский кейс **внутри самого MVP** (раньше
  Этапа 2 по §13), то В-B перестаёт быть преждевременным — тогда вопрос пересматривается (см.
  границу пересмотра). Это единственное условие, при котором В-C проигрывает.
- **Что НЕ теряем:** дверь в Python-экосистему (ADK/LangGraph) и в воркеры на любом языке —
  граница построена; БYO-LLM/локальные-РФ-модели (провайдер = конфигурация, Д-5).

## 5. Граница пересмотра решения (revisit trigger)

Решение пересматривается (re-open этого ADR), если выполнится ЛЮБОЕ:

1. **Агентский/ML-сценарий въезжает в MVP-объём** (раньше Этапа 2 по CONCEPT §13) и его нельзя
   реализовать как TS-воркер за HTTP-границей — тогда сравнивать В-B заново на конкретном кейсе.
2. **Критичная для MVP интеграция доступна ТОЛЬКО через Python-SDK** (не покрывается
   OpenAI-совместимым HTTP и не выносима за external-task-границу) — опровергает Д-5.
3. **Зрелость TS-агентских/LLM-SDK окажется блокером уже на Этапе 2** настолько, что
   откладывать Python до Этапа 2 дороже, чем поднять его в MVP-контуре заранее — но это смещает
   границу внутри В-C (когда), а не отменяет В-C (что), пока выполнен п. ниже.

Граница пересмотра НЕ срабатывает от: появления более зрелого TS-агентского фреймворка
(усиливает В-C), от роста флота (усиливает В-C — цена Python растёт линейно по контурам).

### Как выглядит Python-Stage-2-шов (для В-C) — проверено в коде

Воркеры через external-task API на **любом языке — это УЖЕ есть**, не «надо построить»:
`src/http/externalWorker.ts` поднимает `/jobs`, `/external-task/fetch-and-lock`,
`/external-task/:id/complete`, `/external-task/:id/fail` (lease, retries, backoff, DLQ),
e2e-тест `src/__tests__/externalWorker.e2e.test.ts` зелёный. Python-агент Stage 2 = процесс,
который дёргает эти эндпоинты по HTTP; данные тенанта он видит только как job-payload + ответы
доменного API ядра (путь «а» из Д-6), в БД напрямую не ходит → инвариант «один резолвер» +
tenant-RLS сохранён by design. Ядро не меняется ни на строку.
