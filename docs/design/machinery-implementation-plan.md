# Choros — План реализации машинерии (S0–S5) — итог дебатов

> Как строить несущую машинерию (шов «шаг→сущность», журнал событий, резолюция
> исполнителя, DMN-провод) в свете доктрины владения данными. Итог структурированного
> разбора: **доктрина → анализ подсистем → адверсариальные дебаты → судьи → план**.

Версия документа: 0.1 · Дата: 2026-06-19 · Статус: решение (ADR) — ЧЕРНОВИК на подпись фаундера

> Основание: двухфазная мульти-агентная проработка (2026-06-19).
> **Фаза 1** (анализ): 5 параллельных разборов подсистем в `dev` + синтез → порядок
> сборки S0–S5 + 4 подтверждённые развилки (из 16; 12 отсеяны как предрешённые).
> **Фаза 2** (дебаты): по каждой развилке 2 камеры × 2 раунда + 3 независимых судьи +
> синтез вердикта + интеграция — 33 агента. **Все 4 вердикта — единогласный (3/3)
> УСЛОВНЫЙ синтез**, заземлённый перепроверкой кода на ветке `dev` (edb1dd1).
> Расширяет [process-data-ownership-and-metrics.md](process-data-ownership-and-metrics.md);
> не пересматривает принятое.

## 1. Решение в одной строке

**Машинерия не имеет глобальных ответов «всегда A / всегда B» — каждая развилка
решается УСЛОВНО, по классу: класс шага (F1), слой длительности (F2), тип исполнителя
(F3), число входов в шлюз (F4). Сквозной факт, перепроверенный в коде: применитель
«шаг→сущность» НЕ построен ни для одной формы (`flowable-client.ts:442` = заглушка
`void resolveFor`; `createRecord` имеет 2 call-site, оба HTTP, ноль из процесса) —
поэтому аргумент «дешёвого переиспользования» аннулирован для всех развилок, и
несущей фазой становится S1 со СКРЫТЫМ вторым блокером: отсутствует резолвер
«запуск процесса → целевая запись/реестр» (`getBinding` отдаёт форма→список-полей,
а НЕ инстанс→record-id). Порядок S0→S5 из Фазы 1 не меняется; решения развилок
ложатся в него без переупорядочивания.**

## 2. Вердикты по 4 развилкам (все — synthesis, 3/3 судей)

| # | Развилка | Вердикт | Founder-гейт |
|---|---|---|---|
| **F1** | Гранулярность «результат шага = сущность» | **Условный дефолт по классу шага.** A (реестр «Согласование» + cross_app_ref, append-only) = дефолт для согласований/ревью/решений, кардинальности 1-ко-многим, истории кругов reject→rework→re-approve и **при сомнении в кардинальности**. B (поля inline на основной сущности) = явный opt-in **только** для подтверждённо-1:1-эфемера (single-actor, без истории, галочка «ознакомлен»). | **ОДНА** амортизируемая санкция на **ТИП** реестра (не на процесс) |
| **F2** | Субстрат журнала метрик | **A-prime сейчас, B при доказанном пороге.** Фаза 1: 6 переходов §4.2 через `appendAuditEvent` в `audit_event` + индекс по payload + materialized-view (без новой таблицы). Фаза 2: выделенная `transition_event` **только после профилирования** (contention за `audit_head` / prune-боль при no-DELETE / self-join не лечится индексом). | Сейчас нет; gate только если профайл докажет |
| **F3** | Где живёт claim-state при внешнем Flowable | **Расщепить по типу исполнителя.** Человек-из-пула (несущий UX, default) = choros-owned: новая `user_task_claim` с `partial-unique (tenant_id, task_id) WHERE state='claimed'` в ОДНОЙ tenant-RLS tx с грант-чеком и эмиссией `task.claimed`. Agent/service на external-task = Flowable-owned (движковый `fetchAndLock`-лок, без второго арбитра). | Санкция на таблицу `user_task_claim` |
| **F4** | Локус вызова DMN-evaluate | **A pre-compute по умолчанию** (gateway-переменная через `completeTask`+outbox, движок остаётся внешним) + **обязательный late-compute на triage-шве**. Переключение на B (authed inbound route) только при multi-inflow или out-of-band правках. | DB-гейта нет; эскалировать лишь продуктовую семантику in-flight |

(эфемерное состояние теряется при рестарте).

## 3. План сборки S0–S5 (решения развилок применены)

### S0 — Общий субстрат (предшественник, НЕ доктринальный шаг)
- (a) **Живой DB `getGrants` DAO** — заменить in-memory `rolesForUser` (`inbox.ts:152`,
  дублируется `:514/:753/:829`) реальным PDP-источником (провод уже есть в
  `grant-resolver.ts`/`pdp-explain.ts`/`grants.ts`, консолидировать в DAO).
- (b) **Единый payload-контракт перехода**, нейтральный к форме A/B:
  `{tenant_id, instance_id, process_key, activity, actor, actor_type, ts, duration_ms}`
  + доменный вердикт. Метрики §4 не зависят от формы результата. Кладётся в payload
  `audit_event` (F2 Фаза 1, без новой таблицы).
- **Founder-гейт: нет** (аддитивная проводка существующих примитивов).

### S1 — Шов «шаг → сущность» (НЕСУЩИЙ; точка реализации F1, F4-write, F3-факт)
- Заменить заглушку `void resolveFor` (`flowable-client.ts:442`) **реальным applier**
  на `completeTask` по образцу `createRecord` (write+audit+guard в одной tenant-tx).
- **Истинный блокер обоих вариантов:** построить отсутствующий резолвер
  **«instance-run → целевая запись/реестр»** (`getBinding` сегодня = форма→fields-list,
  не инстанс→record-id). Без него ни A, ни B нереализуемы.
- Applier **ветвится по классу шага** (F1): append в реестр «Согласование» (A, дефолт)
  ИЛИ resolve+update основной записи (B, opt-in для 1:1-эфемера).
- F4: S1 хостит запись gateway-переменной (A pre-compute через тот же `completeTask`+outbox).
- F2: `duration` вычисляется один раз на `completeTask` и эмитится через outbox (мигр.024) в одной tx.
- Достроить runtime-проводку `cross_app_ref` (A): `resolveHop` (`cross-app-ref.ts:227`)
  сейчас орфан; миграция 068 (RLS+ref_field) есть, но не вызывается.
- **Founder-гейт: ДА (F1)** — создание **ТИПА** реестра «Согласование» = одна
  амортизируемая санкция ПЕРЕД S1. Сам applier-шов и резолвер адресации
  governance-нейтральны. B-ветвь (`updateRecord`) санкции не требует.

### S2 — Резолюция исполнителя через PDP (ЯДРО F3)
- **Безусловно:** удалить `const CLAIMED: Map` (`inbox.ts:168`, `.clear()` `:864`);
  перевезти зеркало `forms.ts`.
- **Человеческая ветка (B):** грант-чек (живой `getGrants` из S0) + INSERT в
  `user_task_claim` под partial-unique + эмиссия `task.claimed` — **в ОДНОЙ tenant-RLS
  tx** (иначе TOCTOU-окно возвращается). Ноль round-trip к Flowable.
- **Agent/service-ветка (A):** резолюция через движковый `fetchAndLock`-лок, без
  Postgres-арбитра; идемпотентность держит outbox (мигр.024).
- `user_task_claim` — **проекция** (lock-примитив + текущий снимок), НЕ источник
  истории; история = append-only `audit_event` (§4.1).
- `actor_type` берётся из PDP (`employee.kind`→{human,agent,service}), не из движкового kind.
- **Founder-гейт: ДА (F3)** — новая таблица `choros.user_task_claim` (миграция №076,
  partial-unique + FORCE RLS паттерн 006) как named-additive.

### S3 — Полный журнал переходов (центр F2 Фаза 1; замыкание F3 lifecycle)
- F2 Фаза 1: эмитить 6 переходов §4.2 через `appendAuditEvent` + CREATE INDEX по
  payload + materialized-view; GROUP BY-аналитика = `report-page-render.ts`.
- F3: `actor_type`-эмиссия замыкается для обеих веток; **reaper/sweep зависших
  человеческих claim** (паттерн lock-sweep мигр.029) встаёт переходом
  `claimed→released-by-timeout` — обязателен (у Postgres-partial-unique нет lease-TTL
  даром, в отличие от движкового `lockExpirationTime`).
- **Founder-гейт: нет** (CREATE INDEX + mat-view на существующей 006 = миграция, не
  tenant-таблица; проходит defer-no-new-table D-061).

### S4 — Формы-из-схемы
- Развилками F1–F4 **не затрагивается**. Верифицировать, что форм-стор живёт в DB,
  а не в памяти (хвост удаления `RECORDS Map` из S2).
- **Founder-гейт: нет.**

### S5 — DMN-рантайм-провод (реализация F4)
- DMN/gateway-evaluate (чистая функция) пишет вердикт через **тот же S1-applier**
  (A pre-compute: gateway-переменная через `completeTask`+outbox; Flowable остаётся
  внешним REST). **Обязательный late-compute на triage-шве.**
- Добавить `exclusiveGateway` + условные `sequenceFlow` в эталонный `tel-linear.bpmn`
  (его там нет — процесс линейный).
- **Founder-гейт: нет DB-санкции.** Эскалировать **продуктовую** семантику in-flight
  rule-change (см. §4).

## 4. Что требует решения фаундера

> **РЕШЕНО фаундером 2026-06-19:** (1) **обе таблицы одобрены** — тип реестра
> «Согласование» (перед S1) + `user_task_claim` (перед S2); санкция записана через
> `approve_task` на T-0335/T-0338 (CI frozen-check sanction оформляется build-агентом
> при создании самой миграции). (2) **Три продуктовых дефолта §8 приняты:**
> in-flight rule-change → новые запуски по новому правилу, живые доигрывают по старому;
> ретеншн → телеметрия живёт вместе с аудитом, выделение/чистка только после профайла;
> multi-approver эталон → строим по живому клиентскому кейсу, не впрок (A-дефолт пока на
> принципе). (3) Машинерия (E15, T-0330..T-0340) получила **приоритет над E13/E14**
> (stage 1, входные S0 на priority 94–96). Ниже — исходная формулировка гейтов.

**Governance-гейты (перед соответствующей фазой, лучше запросить батчем заранее):**
1. **Перед S1 (F1):** санкция на **ТИП** реестра «Согласование» (registry_def +
   cross_app_ref-класс). Одна, амортизируется на все согласования.
2. **Перед S2 (F3):** санкция на новую таблицу `user_task_claim` (человеческий claim-путь).
3. **После S5, условно (F2):** `transition_event` — **только** после профилирования,
   доказавшего боль (T-0278 п7). Преждевременно не эскалировать.

**Продуктовые точки §8 (решения фаундера, не DB-гейты):**
- **In-flight rule-change (F4):** применять изменённые DMN-правила к уже запущенным
  инстансам или только к новым запускам?
- **Линия ретеншна (F2):** где граница «compliance-факт (вечный `audit_event`) vs
  эфемерная телеметрия (`transition_event`)».
- **Эталон F1 (честный нюанс):** A-дефолт опирается на нормативные таблицы доктрины +
  риск необратимости, **но реальный multi-approver процесс (директор+юрист) НЕ собран** —
  все построенные BPMN (`tel-linear.bpmn`, `customer-onboarding.bpmn`) single-approver.
  Нужен ли реальный 2-approver процесс в MVP, чтобы A-дефолт имел построенный эталон.

## 5. Остаточные риски

- **S1 = двойной критический путь:** applier-шов И отсутствующий резолвер адресации
  оба несущие и оба отсутствуют. Если резолвер недооценить — S1 раздувается и блокирует S2–S5.
- **F1 эталон не построен:** «директор+юрист» живёт только в прозе §8; A-дефолт стоит
  на принципе, а не на собранном multi-approver процессе.
- **F3 reaper-долг:** человеческий claim под partial-unique без встроенного lease-TTL —
  без `claimed→released` reaper зависший claim блокирует задачу навсегда.
- **Два отдельных гейта** (тип-реестр + `user_task_claim`) = два цикла ожидания
  фаундера; рекуррентный new-table false-red (класс D-060, паттерн T-0183) может
  задержать обе несущие фазы — запрашивать заблаговременно одним батчем.
- **F2 порог субъективен:** «contention / prune-боль / self-join» требует реального
  профилирования на живом стеке (4-8 vCPU §11); риск over-build (преждевременная
  `transition_event`) или latency-долга.
- **Шов claim-проекция↔токен** (F3) и **шаг→сущность↔позиция токена** (F1) —
  eventual-сверка на стыке lifecycle; при сбое outbox/идемпотентности возможен дрейф.
  Один шов, но требует мониторинга failure-modes, которые §5 обещает поглотить.
- **F4 late-compute обязателен**, но условие переключения на B (multi-inflow) может
  наступить незаметно при эволюции процессов в конструкторе — риск молча-устаревшего
  gateway-результата.
