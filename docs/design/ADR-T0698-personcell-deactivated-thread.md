# ADR-T0698 — где рвётся протяжка deactivated_at до PersonCell, и почему boolean

Status: ready
Task: T-0698 (anti-UUID/столп 4, D-064)
Base: dev, branch `task/T-0698`

## 1. Problem

`PersonCell` (T-0673, `web/src/screens/screen-app-records.jsx`) рендерит
person-поле записи через `ActorChip` с `deactivated={Boolean(hit &&
hit.deactivated)}`. Судья T-0673 нашёл: этот проп в проде ВСЕГДА `false`,
а юнит-тест на это зелёный, потому что строит `employees` вручную
(`new Map([['emp-slug-1', {..., deactivated: true}]])`) — фикстура, которую
реальный код никогда не производит.

## 2. Где именно рвётся цепь

Проследил цепь от источника данных до потребителя:

```
choros.employee.deactivated_at (миграция 125, bigint epoch-ms | NULL)
   │
   ▼
listOrgTree()  (src/db/org.ts)         ← ОБРЫВ #1: SQL не селектил колонку,
   │                                      OrgPerson-тип не нёс поля вовсе
   ▼
GET /api/org  (src/http/org.ts)        ← чистый passthrough, ничего не решал
   │
   ▼
fetchEmployees()  (web/.../field-renderer.jsx) ← ОБРЫВ #2: плоский push
   │                                      копировал только {id,name,position},
   │                                      деактивация терялась ВТОРОЙ раз
   ▼
employeesById Map  (screen-app-records.jsx)  ← корректный passthrough
   │
   ▼
PersonCell → ActorChip.deactivated      ← уже корректно читал hit.deactivated
```

Два независимых обрыва, оба до `PersonCell`. Чинить только один звено
(например, только `fetchEmployees()`) ничего бы не исправило — колонка не
доходила даже до HTTP-ответа. Чинить только `listOrgTree` тоже недостаточно —
`fetchEmployees()`'s явный список полей (`{id, name, position}`) отбросил бы
новое поле молча (JS-объект-литерал не копирует «лишние» поля исходника).

## 3. Decision — boolean на выходе `listOrgTree`, не сырая `deactivated_at`

`OrgPerson.deactivated` — `boolean`, вычисленный в `listOrgTree` как
`e.deactivated_at != null`. Сырой epoch-ms timestamp НИКОГДА не покидает
`src/db/org.ts`.

### 3.1 Почему не отдать сырую `deactivated_at`

Два довода, оба указывают в одну сторону:

- **Приватность/минимизация**: `deactivated_at` — это ТОЧНАЯ метка времени
  увольнения/деактивации сотрудника. `GET /api/org` уже широко читаем (ЛЮБОЙ
  аутентифицированный член тенанта — маршрут только `withAuth`, без
  `mgmt_object:*` гейта; он питает `PersonPicker` на форме записи для всех).
  Отдавать ТОЧНОЕ время каждому сотруднику — не то, что просит продуктовый
  кейс («видно, что исполнитель уволен»); кейсу достаточно факта, не даты.
  Меньше данных наружу — меньше поверхность для нежелательного вторичного
  использования (например, вычисление стажа/дат увольнения по всей
  организации из простого GET-запроса, доступного каждому).
- **Согласованность с существующим прецедентом**: единственное уже
  существующее место, где этот сигнал покидает `src/db/`, —
  `src/db/actor-resolver.ts::batchResolveActors` (T-0648), которое строит
  `ResolvedActor.deactivated: row.deactivated_at != null` — тоже boolean,
  тоже с тем же самым SQL-паттерном (`deactivated_at != null`). `ActorChip`
  (`web/src/components/components.jsx`) принимает ровно `deactivated:
  boolean` — компонент физически не ожидает дату. Отдать здесь сырую дату
  означало бы завести ВТОРОЙ, несогласованный контракт для одного и того же
  визуального сигнала — ту же ошибку дублирования, от которой уже
  предостерегает T-0658/D-064 (не множить параллельные резолверы одного и
  того же факта).

### 3.2 Отклонённая альтернатива — не протягивать (снять prop+тест)

Задача явно запрещает этот путь, если протяжка реальна. Продуктовый кейс
подтверждён: инбокс/audit/grant-trail уже показывают маркер деактивации
через `ActorChip` (T-0648) — то же самое ожидание естественно для записи с
person-полем (кто исполнитель, жив ли ещё его аккаунт). Снять проп означало
бы наблюдаемый регресс относительно уже принятого продуктового стандарта
(деактивация видна везде, где показан актор) и не то, что просит задача.

## 4. Fix — два аддитивных изменения, по одному на каждый обрыв

1. `src/db/org.ts::listOrgTree` — `empRows`-запрос добавляет
   `e.deactivated_at` в SELECT (было: `id, slug, display_name, kind`);
   маппинг в `OrgPerson` добавляет `deactivated: e.deactivated_at != null`.
   `OrgPerson`-тип получает `deactivated?: boolean` (опционально — dev-no-db
   `ORG_SEED`-фоллбэк в `src/http/org.ts` не несёт этого поля и остаётся
   валидным `OrgPerson`, ноль правок в `ORG_SEED`).
2. `web/src/forms/field-renderer.jsx::fetchEmployees()` — плоский push
   получает `deactivated: Boolean(p.deactivated)`, аддитивно к уже
   существующему `position` (T-0649 прецедент того же паттерна: "существующие
   вызывающие читают только .id/.name, лишнее поле не мешает").

`PersonCell` НЕ меняется — его код уже был корректен (T-0673); чинится
только источник данных, которым он кормится.

## 5. Test honesty — почему старый тест был ложным и что его чинит

Старый тест (`screen-app-records.test.jsx`, "threads deactivated through
when the batch entry carries it") строит:

```js
const employees = new Map([['emp-slug-1', { id: 'emp-slug-1', name: 'К. Орлов', deactivated: true }]]);
```

Это доказывает ТОЛЬКО, что `PersonCell` правильно читает `hit.deactivated` —
корректный, но узкий unit-тест на компонент в изоляции. Он НЕ доказывает
(и не может доказать), что производственная `Map` — та, что реально строит
`screen-app-records.jsx` из `fetchEmployees()`'s списка — когда-либо содержит
ключ `deactivated`. До этого фикса она не содержала НИКОГДА (оба обрыва §2),
поэтому «зелёный тест» маскировал полностью нерабочую фичу — ЛОЖНОЕ
покрытие ровно того класса, что просит закрыть задача.

Тест ОСТАВЛЕН как есть (он корректен на своём уровне — прямой вызов
`PersonCell({...})` с любой формой `employees`, включая рукотворную, — это
законный unit-тест компонента). Комментарий над `PersonCell` в
`screen-app-records.jsx` дополнен, явно называя это ограничение и указывая
на новый честный тест. ДОБАВЛЕН новый тест
(`screen-app-records.test.jsx`, "real /api/org response shape…"), который:

1. мокает `globalThis.fetch` реалистичным `/api/org`-ответом (форма
   `{departments:[{positions:[{title, people:[{id,name,type,deactivated}]}]}]}`,
   один деактивированный + один активный human);
2. вызывает РЕАЛЬНЫЙ `fetchEmployees()` (не фейковую функцию);
3. строит `Map` ТЕМ ЖЕ выражением, что `screen-app-records.jsx` использует
   (`new Map(list.map((e) => [e.id, e]))`);
4. передаёт эту Map в `PersonCell` и проверяет `el.props.deactivated` для
   обоих id.

Дополнительно расширен серверный `field-renderer-t0649.test.jsx`'s
`toEqual`-тест формы (`'flattens human employees to {id, name, position}'`) —
он проверяет ТОЧНУЮ форму объекта, поэтому падает мутационно на добавление
`deactivated`, если реализация когда-нибудь перестанет его копировать.

## 6. Security invariant preserved

- Тенант-изоляция не меняется: `listOrgTree`'s `withTenant`/`WHERE
  tenant_id = $1` не трогается — новая колонка добавлена в уже
  тенант-scoped запрос.
- Authority-паритет не меняется: `GET /api/org` уже не гейтуется
  `mgmt_object:*` (просто `withAuth`) — это НЕ новый read-гейт вопрос (в
  отличие от T-0630); маркер деактивации не более чувствителен, чем уже
  раскрываемые имя/должность/тип этого же ответа.
- Zero new authority path (D-064/T-0658 дисциплина): `listOrgTree` — НЕ
  authority-резолвер (не решает "может ли актор Х"), это read-projection
  оргструктуры; добавление колонки в SELECT не создаёт нового резолвера прав
  и не дублирует `getGrantsForSubject`/`isGenesisOwnerForTenant`/
  `loadAdminContext`.

## 7. Alternatives rejected

- **Отдать сырую `deactivated_at`** — избыточная детализация (точная дата
  увольнения) для широко читаемого эндпоинта; создаёт второй несогласованный
  контракт с T-0648's boolean-прецедентом. Отклонено (§3.1).
- **Снять prop+тест вместо протяжки** — прямо запрещено постановкой, когда
  протяжка реальна; регрессирует относительно уже принятого продуктового
  стандарта (деактивация видна на ЛЮБОМ ActorChip). Отклонено (§3.2).
- **Чинить только `fetchEmployees()` (без `listOrgTree`)** — бессмысленно:
  поле физически отсутствует в HTTP-ответе, копировать нечего. Отклонено (§2).
- **Заменить старый тест, а не дополнить** — рукотворный тест сам по себе
  корректен как unit-тест компонента (не переизобретает форму `/api/org`),
  удалять его — потеря покрытия на случай регрессии самого `PersonCell`.
  Оставлен + дополнен комментарием + новым интеграционным тестом (§5).
