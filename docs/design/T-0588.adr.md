# ADR · T-0588 — Замещение и эскалация (столп 3: люди/агенты с правами)

**Status:** ready · **Phase:** DESIGN · **Base:** dev@c57e1d6, branch `task/T-0588-substitution` · **Spec:** `docs/specs/T-0588-substitution-escalation.spec.md` (4744251)

## 1. Проблема (две дыры, разведка кода)

Обе дыры — **предикаты чтения/claim-чека**, не отсутствие модели. Модель `substitution_rule` (миграция 036, T-0035) и запись правил (`/api/rights/intents/substitute`, `SubstituteForm`) уже живые; `employee.deactivated_at` (миграция 125, T-0583) задеплоено.

**Дыра №1 — claim-eligibility не видит Tier-2 substitution** (`src/http/inbox.ts:1349-1355`). `POST /api/inbox/:id/claim` проверяет право строго через `resolveRolesForActor → getRoleSlugsForActor` (`grants-dao.ts:387`), который читает `role_assignment`. Tier-2-заместитель держит **grant** (TTL, `delegable=false`), а не `role_assignment`, → 403 `NOT_ELIGIBLE` при живом правиле. (Tier-1 безопасен: заместитель уже держит роль независимо.)

**Дыра №2 — деактивация не фильтруется в резолве держателей** (`grants-dao.ts:461-482` `getHoldersForRole`, `:497-518` `findTenantOwnerSlug`). JOIN `employee`, но без `deactivated_at IS NULL`. Уволенный остаётся в пуле роли и может стать fallback-владельцем; новые задачи льются тому, кто не может войти в KC — продуктовое зависание.

## 2. Решение (ноль миграций, строго аддитивно)

### FR-1 — claim учитывает Tier-2 (локально, в claim-эндпоинте)

После существующего чека `taskRole in myRoles` (оставляем как есть), при промахе — **дополнительная** ветка:

1. `getActiveSubstitutionsForSubstitute(pool, tenantId, actorSlug, nowMs)` — **новый аддитивный ридер** в `substitution-dao.ts`, зеркало `getActiveSubstitutionsForEmployee`, но по `sr.substitute_employee_id` (confirmed + in-window, `SUBST_SELECT`+`mapRow`).
2. Отобрать правила с `roleId === taskRole`, `ttlGrantId !== null` (Tier-2), org-scope которых покрывает scope задачи (`resolveSubstitution` / `isNarrowerOrEqual`; scope задачи = `BOTTOM` когда неизвестен, как в `resolveExecutor`). `nowMs` = момент claim → протухшее правило не проходит.
3. Есть совпадение → claim разрешён; в `task.claimed` пишем `on_behalf_of: <absentSlug>`.

Почему не расширять `getRoleSlugsForActor`: он читается и на approve-пути; сворачивать замещённые роли в «роли, которые актёр держит лично» = утечка авторитета за пределы claim-действия (Tier-2 намеренно сужен). Держим проверку **локальной** для claim.

### Семантика on_behalf_of (T-0019 контракт, БЕЗ миграции)

Колонка `on_behalf_of` живёт на **`actor_event`** (миграция 018), НЕ на хеш-цепочном `audit_event`, куда пишется `task.claimed`. Канонический `appendAuditEvent` имеет фиксированный набор колонок в preimage row-hash. Поэтому on_behalf_of кладём в **`task.claimed.payload`** (JSONB, свободная форма) — ноль миграций, ноль изменений хеш-преимиджа. `appendTaskClaimed` получает опциональный `onBehalfOf?: string` (аддитивно; для обычного claim ключ отсутствует → байт-идентично сегодня). После `valid_until` право исчезает само — правило перестаёт быть in-window, никакого явного отзыва (полуоткрытый интервал `[from, until)`).

### FR-2 — держатели/fallback исключают деактивированных

Добавить `AND e.deactivated_at IS NULL` в `getHoldersForRole` и `findTenantOwnerSlug`. Для консистентности — тот же предикат в `findTenantOwnerEmployeeId` и `getAuthoringDraftHolderEmployeeIds` (деактивированный не должен быть и получателем нотификаций). Четыре явных локальных правки, без новой абстракции-фрагмента (NF-2, стиль файла).

### FR-3/FR-4 — падают из FR-2 бесплатно

Деактивация убирает держателя из **сырого пула**, который читает `resolveExecutorFallbackBatch` (путь B, `inbox.ts:441`). Его лесенка уже: suppress-absent + add-substitute (Tier-1 → заместитель) → пустой эффективный пул → `routed_to_fallback:"role_unfilled"`. Путь A `resolveExecutor` уже возвращает `kind:"unresolvable"` когда и владелец деактивирован (FR-2 сделает `findTenantOwnerSlug`→null). **Никакого нового кода эскалации.**

### FR-5 — путь A НЕ подключаем

`resolveExecutor` не вызывается ни одним прод-путём (разведка §1.2 подтверждена). Прод-маршрутизация = путь B + claim-эндпоинт. FR-1..FR-4 реализуются там. Унификация A/B = ND-3 (долг).

### Семантика деактивированного (реши, §3 инструкции)

Деактивированный = **не держатель** (резолв/пулы/fallback-owner). Существующие claim'ы деактивированного **остаются висеть как есть** (claimed-by-<slug>) — минимально-честный вариант: claim это факт в append-only `audit_event` + lock-строка; фикс — это READ-фильтр резолва, не мутация claim'ов. Авто-переоткрытие потребовало бы новой sweep-семантики и политики (reopen/escalate/hold), которую спека не санкционирует. Скоуп — только **новая** маршрутизация (AC-5/6/7 говорят «Новая задача»).

- **Claim ≠ гранты чтения.** Мы разрешаем только *забрать задачу роли*; гранты чтения уже сминчены substitution-механикой (T-0035), новую видимость не выдаём.
- **Протухшее правило.** `nowMs` = момент claim; `isRuleEffective` отсекает `valid_until <= nowMs` и `confirmed_by IS NULL`. Регресс покрыт AC-2.
- **TOCTOU claim-lock** не трогаем — `insertClaimLock` остаётся хардлоком; Tier-2-ветка только меняет вердикт eligibility ДО транзакции.
- **Tenant-изоляция** — все ридеры внутри `withTenantReadTx` (RLS), новый ридер тоже.

## 8. Миграции

**Ноль.** Обе дыры — SQL-предикаты + один DAO-ридер + один payload-ключ (JSONB). `on_behalf_of` в audit не требует колонки (payload свободной формы; колонка `on_behalf_of` — на `actor_event`, не на `audit_event`). Ни структурного изменения, ни нового номера (следующий свободный был бы 128 — не нужен).
