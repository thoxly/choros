# UX-исследование Choros — 2026-07-05

**Заказ фаундера:** сайдбар (группировка, перенос сущностей, drag-n-drop, движимость); поле даты и проверка остальных полей; сквозное изгнание UUID из человеческого слоя («Исполнитель: 3462410f-…», «процесс: 5ec293d1-…»); управление Задачами при десятках/сотнях + персональная глубина; то же для Процессов + разнесение страницы «всё в кучу».

**Метод:** живое проживание на стенде (t0586-admin, Dev Silo: 21 приложение, 23 задачи, 33 процесса) + разведка кода `dev@a4a7e0e` двумя агентами (навигация/списки; поля/идентификаторы). Всё, что ниже, — проверено либо кликом, либо file:line.

## 0. Главный диагноз: один корень у всех пяти жалоб

Все пять зон — симптомы **одной болезни: продукт построен как набор операций над API, а не как рабочее место человека**. Конкретно три системных корня:

1. **Машинный слой протекает в человеческий.** UUID, слаги, ключи движка (`legal_precheck`, `sf-start-submit`, `novyy-protsess-6`, `dd/mm/yyyy`, «Запись d6f0ac0f…») показываются как контент. Где на это была отдельная задача — закрыто (имя процесса T-0614, автор записи T-0608); где задачи не было — течёт. Правила нет, есть точечные фиксы.
2. **Нет слоя персонального рабочего места.** Представления списков (T-0581) — общие на тенант («не приватно лично для вас» — прямо в UI); сайдбар не настраивается и не сворачивается; никакого user-prefs хранилища в продукте нет вообще. «Настроить глубину под себя» сегодня негде хранить.
3. **Каждый список — своя поделка.** Инбокс: табы+1 фильтр+SLA-sort+пагинация. Процессы: **ничего** (`GET /api/processes` не принимает ни одного query-параметра). Записи: полноценный list_view (колонки/фильтры/сортировка/канбан). Три списка = три разных UX. А это ровно столп 2 — «интерфейс из блоков НА ДАННЫХ»: у платформы уже есть зрелый блок «список», но он прибит гвоздями к одному источнику данных.

**Связь со столпами:** все пять жалоб живут в столпе 2 (интерфейс из блоков) и напрямую подрывают столп 4: агенты, которые должны быть «сотрудниками с правами», в UI выглядят как `3462410f-c98a-…` — то есть главный дифференциатор продукта на экране неотличим от бага.

## 1. Сайдбар

### Что есть (факты)

- ~43 пункта одной нескроллируемой-по-группам колонкой: Обзор → РАБОТА (2) → **21 приложение «Без раздела»** → КОНСТРУКТОР (5) → НАБЛЮДАЕМОСТЬ (7) → АДМИНИСТРИРОВАНИЕ (8, с подгруппами). Рендер: `web/src/app-shell/shell.jsx:974-1137`, конфиг `nav-config.js`.
- **Разделы уже сущность** (T-0551/52: `choros.section`, `sort_order`, CRUD `src/http/sections.ts`), но в тенанте их **0** — потому что управление спрятано от места боли: создать раздел можно только на экране `/sections` (зона Конструктор), перенести приложение — только на `/apps` через меню строки → модалка. **Из самого сайдбара нельзя ничего**: ни создать раздел, ни перенести, ни переименовать, ни свернуть.
- DnD-библиотек в проекте нет вовсе (`web/package.json`); переупорядочивание везде кнопками ▲/▼ (осознанный паттерн доступности, `list-view-panel.jsx:12-15`). Collapse/resize сайдбара нет (`app.css` — фикс-ширина).
- Хорошее, что надо сохранить: ⌘K-палитра строится из того же NAV (не разъезжается); зоны видимости серверные fail-closed (`/api/me/nav-capabilities`) — рядовой видит только РАБОТУ; «раздел без видимых приложений не рендерится».

### Решение — «сайдбар как рабочее место», три хода

**A. Структурная диета (не трогая права).** Рабочий слой — постоянный: Обзор, Мои задачи **(+счётчик — число уже есть в API)**, Процессы, разделы с приложениями. Всё остальное — collapsible-группы, **свёрнутые по умолчанию**: Конструктор, Наблюдаемость, Администрирование. Состояние сворачивания — per-user (см. user-prefs ниже). Это одним махом превращает 43 пункта в ~10 видимых, ничего не пряча.

**B. Управление на месте боли.** Прямо в сайдбаре: кнопка «+ Раздел» у заголовка списка приложений; контекст-меню приложения (⋯ или правый клик): «Переименовать», «В раздел →», «Настроить поля», «Скрыть у меня». Инлайн-переименование раздела. API для всего этого уже существует (`PATCH /api/applications/:id {section_id}`, `PATCH /api/sections/:id`) — нужен только UI-слой.

**C. Drag-and-drop поверх кнопок, не вместо.** Перетаскивание приложения между разделами и разделов между собой; кнопки ▲/▼ остаются (клавиатурная доступность — существующий принцип проекта). Реализация — ручной HTML5 DnD, как уже сделано в канбане T-0582 (прецедент в кодовой базе, библиотека не нужна). Персист — те же `sort_order`/`section_id`.

**Не делать:** вложенные разделы (ADR T-0551 §6 сознательно отверг — правильно, пока приложений десятки, а не сотни); мегаменю; «двигающийся» floating-сайдбар — движимость закрывается collapse-режимом (иконки) + persist, это дешевле и предсказуемее.

**AI-угол (столп 5):** «разложи мои 20 приложений по разделам» — идеальная команда ассистенту, но только ПОСЛЕ того, как появится ручной механизм на месте: ассистент вызывает те же API.

## 2. Поля ввода в записях

### Что есть (факты, живьём + код)

Единый рендерер — `web/src/forms/field-renderer.jsx` (везде: записи, формы задач). UI-kit нет — всё нативные инпуты:

| Поле | Сегодня | Боль живьём |
|---|---|---|
| Дата | нативный `<input type="date">` (`field-renderer.jsx:1431`) | «Стрёмный вид» подтверждён: серое `dd/mm/yyyy`, микро-иконка, вид зависит от браузера/локали. Клавиатурный ввод при этом **работает** (05072026 → принялось). В списке дата рендерится сырым ISO `2026-07-05`. Типа «дата+время» **нет вообще** в таксономии. Дата внутри collection-строк — навсегда голый текст (`x-date` не рекурсирует — задокументированная дыра, тот же класс, что «Дата лоссовая» с приёмки 30.06) |
| Money | `<input type="number">` + значок ₽ | ₽ **висит обрезанным за границей поля**. Хуже: ввёл `150000.5` → список показывает **«150 001 ₽»** — копейки молча округлились. Это уже не UX, это целостность данных |
| Сотрудник (person) | голый `<select>` без поиска | На стенде **мёртв**: `GET /api/org` → **401** (при живой сессии — POST записи в тот же момент 201) → серый бокс «Не удалось загрузить список сотрудников», без retry, ввести нельзя |
| Relation | текст-фильтр + `<select size=N>`, грузит все записи разом | не автокомплит; на сотнях записей развалится |
| Multi-select | список чекбоксов | без поиска, не масштабируется |
| Select | ок | варианты задаются plain-textarea построчно в схема-редакторе |

Схема-редактор (создание полей) заставляет придумать **три слоя машинных имён руками**: слаг приложения → слаг «набора полей» (протёкшая внутренняя концепция registry_def) → латинский ключ каждого поля. Плюс: на сабмите длинной формы поймал ложное «Сессия не авторизована — войдите заново», хотя повторный клик прошёл (транзиентный 401 без авто-retry). Плюс в авто-списке **две колонки «Создано»**, одна вечно «—».

### Решение

**Мини-набор полевых контролов** (свой, в духе репо, без библиотеки) — один раз, для всех форм сразу, т.к. рендерер един:

1. **DateInput**: стилизованный триггер «05.07.2026 📅» (локализованный показ), поповер-календарь; хранение ISO как сейчас; в списках/деталках дата всегда форматируется локалью, не ISO. Добавить тип **datetime** в таксономию (ревизия типов это уже фиксировала). Починить `x-date` в collection.
2. **MoneyInput**: ₽ внутри поля, разряды при вводе (150 000,50), копейки честно храним и показываем. **Отдельно — багфикс округления** (P1, данные).
3. **PersonPicker**: поиск по имени, «имя + должность», честная ошибка с кнопкой «Повторить». **Отдельно — багфикс `GET /api/org` 401** для админа тенанта (P1: person-поле сейчас неюзабельно).
4. **RelationPicker**: async-автокомплит (debounce + server-side поиск по title).
5. **MultiSelect**: чипы + поиск при >7 вариантов.
6. Схема-редактор: **авто-слаги** транслитом из названия (приложение, набор, ключи полей) со свёрнутым «продвинутым» режимом для ручного ключа; спрятать «набор полей» за дефолт (создавать «main» автоматически при первом «Настроить поля»); select-варианты — теговый инпут вместо textarea.
7. Мелочь: убрать дублирующую колонку «Создано»; авто-retry на транзиентный 401 вместо «войдите заново».

## 3. UUID → человеческие имена (сквозная зачистка)

### Карта течей (проверено по коду, 13 мест)

Полная таблица — в отчёте разведки; сжатая картина:

- **«Исполнитель: 3462410f-…»** — это `claimedBy` без резолва в имя в ОБОИХ путях инбокса (`src/http/inbox.ts:786` и `:875`); резолвер `findEmployee` уже импортирован в файл и применён к соседней ветке — дыра бэка.
- **«процесс: 5ec293d1-…»** — конкретно этот случай закрыт T-0614 (имя определения резолвится), но в колонке «Процесс» инбокса по-прежнему светится UUID инстанса моноширинным как основной идентификатор; деталка задачи показывает «Шаг: legal_precheck», «Инстанс: agent:» (пусто).
- Аудит (`screen-audit.jsx:29`), история переходов инстанса (`screen-process-instance.jsx:122,156`), grant-trail, «Топ исполнителей» аналитики — везде сырой `actor`/`assignee`, и **ни один читатель `audit_event` не джойнит к сотрудникам** (дыра бэка, общая).
- Person-ячейки в списках записей и деталке — raw id, хотя `/api/org` уже отдаёт имена (дыра фронта).
- «Запись-источник» на инстансе — голый UUID без title и без ссылки (дыра фронта).
- История шагов — `sf-start-submit sequenceFlow` (машинные id BPMN вместо имён узлов).
- Заголовок записи — «Запись d6f0ac0f…» в крошках и на странице.

### Решение — правило + два примитива + гейт, не 13 точечных фиксов

1. **Дизайн-закон** (в CLAUDE.md/OBLIK-гейт): *UUID и машинный ключ не являются контентом. Человеку показывается имя; машинный id — только вторичной моно-меткой, тултипом или копи-кнопкой.*
2. **Примитив бэка: batch-резолвер акторов.** Одна функция/view `actor_display(slug|uuid)` (сотрудники + **агенты** + сервисы) + LEFT JOIN во всех читателях `audit_event` и инбокса. Закрывает разом ~7 мест. Критично: **агент должен резолвиться в имя агента из реестра** — «⚙ Юрист-прекчек (агент)», иначе столп 4 невидим.
3. **Примитив фронта:** `<ActorChip>` (тип-глиф + имя, тултип с id) и `<RecordRef>` (title записи + ссылка, лениво по `GET /api/records/:id`) — применить в инбоксе, инстансе, аудите, списках.
4. **Анти-рецидив гейт:** фитнес-проба «в отрендеренном тексте страниц нет `[0-9a-f]{8}-[0-9a-f]{4}-…` вне моно-меток» (рецидивы — доказанная болезнь фабрики: T-0371→T-0633).
5. Заголовки/имена: запись в крошках — по title-полю; шаги истории — по `name` узла BPMN (он есть в определении).

## 4. Задачи: от списка к рабочему инбоксу

### Что есть (факты)

Табы Все/Мне/Из пула/Эскалации (сервер, T-0500-серия), фильтр по типу исполнителя, SLA-sort, пагинация «Показать ещё». Этого мало и вот чего нет: **текстового поиска нет ни в UI, ни в API** (`parseQuery` знает только tab/exec/sort/page); фильтров по процессу/приложению/дедлайну нет; группировки нет; сохранённых представлений нет. Строка **не кликабельна** — только ссылка «Открыть», и та не у всех строк; колонки Дедлайн/Действие обрезаются вьюпортом. Десять задач подряд называются «Подача заявки» — различить можно только по UUID. В API уже есть, но не показывается: `doubt_reason` (агент сомневается — T-0221), `routed_to_fallback` (роль не заполнена — T-0380), `messageCatch` (ждёт сообщения). Деталка задачи не ссылается ни на запись, ни на инстанс.

### Решение

1. **Обобщить list_view до view-примитива платформы** — это стержневое решение исследования. Сегодня `list_view` жёстко привязан к `registry_def_id`; нужен `source: records|inbox|processes`. ADR T-0581 уже предусмотрел `owner_actor nullable` для **per-user** представлений — вот и «каждый настроит глубину под себя»: личные сохранённые виды + общие тенантные. Требуется маленький **user-prefs store** — он же нужен сайдбару (collapse) и плотности таблиц. Один механизм закрывает «под себя» везде.
2. **Инбоксу — серверные q=, фильтры (процесс, приложение, статус, дедлайн-диапазон), группировку по процессу** (свёртки с каунтами) — по образцу того, что у инбокса уже есть (server-side tab/exec/sort доказали паттерн).
3. **Контекст в имени задачи:** «Подача заявки — *Заявка на аренду офиса*» (title записи-источника через `recordId`); вся строка кликабельна; в деталке — ссылки на запись и на инстанс (сейчас «Связанные задачи» с инстанса ведут на ОБЩИЙ инбокс — должно фильтровать по инстансу).
4. **Показать агентские сигналы** (столп 4): бейдж «агент сомневается: причина», «эскалировано: роль не заполнена», «ждёт сообщения» — поля уже едут по wire и выбрасываются.

## 5. Процессы: разнести кучу

### Что есть (факты)

Одна страница `/processes` = три таблицы подряд без табов (`screen-processes.jsx:467-625`): (1) живые инстансы — **в скролл-щели высотой в одну строку** (25 инстансов в окошке!); (2) определения — «Новый процесс» ×6 с ключами `novyy-protsess-2..6`; (3) связи-триггеры. Двойная кнопка «+ Новый процесс» на одном экране. `GET /api/processes` — **ноль параметров**: ни поиска, ни фильтра, ни пагинации, всё разом. Версий в UI нет (показывается только последняя), «кто запустил» — только тип (human/agent), не имя. Деталка инстанса: UUID в заголовке, история с `sf-start-submit sequenceFlow`, запись-источник UUID-ом без ссылки.

### Решение

1. **Разделить по ролям пользователя, а не по таблицам БД:**
   - **«Процессы» (зона Работа)** = живые инстансы. list_view-грид: поиск, фильтры (определение, статус, дата старта, «мои»), server-side пагинация (расширить API по образцу инбокса). Это страница оператора.
   - **«Каталог процессов» (зона Конструктор)** = определения. Карточка определения: имя, статус, версии, счётчик инстансов (клик → фильтрованный список живых), **триггеры-связи прямо на карточке** (третья таблица исчезает), кнопки «В модельер»/«Правила ветвления».
2. **Гигиена имён у корня:** модельер обязан требовать имя при создании/публикации (не молчаливое «Новый процесс» — отсюда весь мусор `novyy-protsess-N`); ключ — авто из имени, редактируемый до первой публикации.
3. **Инстанс-деталка:** заголовок «Канонический линейный ТЭЛ · Заявка на аренду офиса» (имя + запись-источник ссылкой), шаги — именами узлов, «Связанные задачи» — фильтр по инстансу, «Запущен: Иванов И. (человек)» — резолв стартера (сейчас известен только тип; стартер-имя добрать из engine-переменных/аудита).
4. **Персональная глубина** — тот же view-примитив из §4, source=processes.

## 6. Администрирование: Доступ / Пользователи / Агенты / Оргструктура

*(добавлено по второй порции находок фаундера; всё перепроверено живьём + по коду)*

### Что есть (факты)

**«Доступ» (/rights):**
- **«Экспорт прав» (топбар) — фейковая кнопка by design.** `shell.jsx:360-369`: `aria-disabled` + `preventDefault`, пояснение «функция в разработке» — только для скринридера (`chs-sr-only`). Зрячий видит обычную кнопку, которая молча не работает. Экспорт-эндпойнта на беке не существует вовсе.
- **Вкладка «Журнал» — краш всего приложения.** Живьём: клик → `/rights/trail` → **белый экран целиком** (исчезает даже сайдбар). Консоль: React error #31 — в рендер прилетает **объект `{type, name}`** вместо строки. Диагноз: wire-контракт `/api/grant-trail` уже отдаёт типизированного актора (ровно данные под `<ActorChip>` из §3!), а UI ждёт строку (комментарий `ra-grant-trail.jsx:40` «actor and subject are plain strings» — устарел). Внутри журнала есть ещё одна кнопка «Экспорт» **вообще без onClick** (`ra-grant-trail.jsx:153`) — не помечена disabled, просто мертва.
- **«Нет способа управления» — на самом деле управление ЕСТЬ, но похоронено.** Формы «Назначить роль сотруднику» и «Дать роли право» работают (`POST /api/role-assignments`, `POST /api/grants`) — но живут в самом низу карточки роли под фолдом, без якорей сверху. Фаундер-владелец их не нашёл — discoverability ноль. (Для пользователей без `can_manage` формы честно не монтируются — это правильно.)
- Вкладка «Каталог ролей» (/rights/editor) — статус demo: гранты роли из БД в редактор не подгружаются.

**«Пользователи» (/users):** display_name уже рендерится, но у учёток, созданных до миграции 126, `login=NULL` → в списке светится сырой KC-UUID (`user-mgmt.ts:462-472`, видно живьём: «2e082a32-25ff-…»). Почти все учётки «вне оргструктуры». Нет поиска. И главное —

**Несогласованность трёх экранов — это не «чтоли», это факт архитектуры UI.** В модели всё едино: `employee` — центральная сущность (human|agent), учётка (/users) — её логин-обвязка через KC, права (/rights) — назначения на её `employee_id`. Но экраны — три острова: **ни одного перехода** `/users ↔ /org ↔ /rights` в коде нет (grep пуст); «все роли этого человека» не показывает ни один экран; кнопка «Права и доступ» из карточки исполнителя в оргструктуре ведёт на общий /rights **без контекста** (`onOpenRights(undefined)`, `screen-org.jsx:495-497`).

**«Агенты» (/agents):** стена одинаковых деградированных карточек — у каждой «должность не назначена» + «НУЖНА LLM» + один и тот же hint-текст ×N. При этом «агент = должность в оргструктуре» — архитектурный принцип продукта (`screen-agents.jsx:16-19`), т.е. агенты в этом тенанте не подключены к своему же главному механизму, и UI не ведёт чинить (нет действия «назначить должность» на карточке). Переходов к правам агента нет. Детальная карточка (модель/бюджет/автономия) честно не подключена к API.

**«Оргструктура» (/org):**
- **«+ Исполнитель» (топбар) — та же фейковая кнопка**, что «Экспорт прав» (`shell.jsx:337-355`): aria-disabled + preventDefault, подсказка «добавляйте в панели слева» — снова только sr-only. Рабочие кнопки («+ Подразделение / + Должность / + Сотрудник / + Роль / Назначить роль») — слева над деревом, все живые.
- **Перемещения НЕТ на уровне API.** `screen-org.jsx:40-45` честно: «There is NO update/PATCH route for any org entity — create + delete only». На беке ни одного PATCH/PUT для employee/position/department (`seed-write.ts`). Реорганизация сегодня = удалить + создать заново (рвёт историю и id). **DnD, который просится, вешать не на что — сначала move-API.**
- В карточке исполнителя тоже светится сырой id (`<MonoId>{person.id}</MonoId>`, для людей со slug=KC-sub — UUID).

### Решение

1. **Правило «нет фейковых кнопок»** (в OBLIK/UX-гейт): контрол либо работает, либо видимо-disabled с *видимым* тултипом «в разработке» (sr-only подсказка зрячему не помогает — сейчас обе топбарные заглушки выглядят рабочими), либо не рендерится. Немедленно: «Экспорт прав» и «+ Исполнитель» → видимый disabled-стиль + тултип; мёртвый «Экспорт» в журнале → реализовать (CSV из уже существующего `GET /api/grant-trail` — тривиально) или убрать.
2. **P1: краш /rights/trail.** Рендерить объект актора через `<ActorChip>` — это буквально первое применение примитива из §3: данные уже приходят в нужной форме `{type, name}`.
3. **Identity hub вместо трёх островов.** Одна карточка исполнителя (человек/агент) с гранями: оргместо, учётка (логин/статус), роли и права, для агента — LLM/должность/активность. Достижима с /org, /users, /agents, /rights; «Права и доступ» — с контекстом employee. Это и есть ответ на «несогласованность с пользователями»: не переделывать три экрана порознь, а дать им общий узел.
4. **Move-API оргструктуры** (PATCH employee/position/department: parent, name) — предпосылка для DnD и переименования. Затем **DnD в дереве** по тому же паттерну, что сайдбар (§1): перетаскивание сотрудника между должностями/отделами, с кнопочным fallback «Переместить в…» в меню узла.
5. **/rights discoverability:** действия «Назначить роль» / «Дать право» — кнопками в шапке карточки роли (формы в дровер), а не простынёй под фолдом; бейдж «только просмотр» для читателей.
6. **/agents:** свернуть повторяющиеся деградации в один статус-бейдж на карточке («⚠ не в оргструктуре · нет LLM») с действием прямо на месте («Назначить должность», «Привязать LLM»); ссылка «Права агента» → identity hub. Backfill login для до-миграционных учёток (убирает UUID-логины в /users).

## 7. Слаг-ад: машинные имена на вводе

*(третья порция находок фаундера: «куда не тыкнешь — везде нужно ввести slug и название, ад при создании решений руками»)*

Это зеркало §3: там машинные имена текут на **вывод** (UUID как контент), здесь продукт требует их на **вводе**. Полная карта — слаг/ключ придумывает человек в **11 местах**:

| # | Где | Поле | file:line |
|---|---|---|---|
| 1 | Создание приложения | «Слаг» (`my-app`) | `screen-apps.jsx:141` |
| 2 | Набор полей | «Слаг набора полей» (`my-registry`) | `screen-app-schema.jsx:1097` |
| 3 | Каждое поле схемы | «Ключ поля» (`field_key`) | схема-редактор, на каждое поле |
| 4 | Подразделение | «Слаг» (`sales`) | `org-crud.js:212` |
| 5 | Должность | «Слаг» (`lead`) | `org-crud.js:223` |
| 6 | Сотрудник | «Слаг» (`j-doe`) | `org-crud.js:235` |
| 7 | Роль | «Слаг» (`approver`) | `org-crud.js:246` |
| 8 | Найм агента | «Слаг» | `screen-agents.jsx:385` |
| 9 | SoD/intents форма | «Slug сотрудника» (`e-petrov`) | `ra-intents.jsx:142` |
| 10 | Модельер: свойства шага | «Ключ процесса»; «Форма/набор полей (ключ)»; **«Перечислите ключи видимых полей» текстом** | `bpmn-properties-panel.jsx:469,789,807,899` |
| 11 | Учётка | «Логин» | `/users` — единственное оправданное место (это логин входа) |

Усугубляет: **пикеры существующих сущностей тоже говорят на машинном** — селекты в орг-модалках подписаны слагами, не названиями (`org-crud.js:202-205`: `label: p.slug`), т.е. даже выбор готового требует помнить машинные имена.

**Цена в цифрах:** собрать один кейс руками (приложение + набор + ~8 полей + отдел + должность + 2 сотрудника + роль + процесс + формы двух шагов) = **~15–30 рукописных машинных имён**, каждое с грамматикой `^[a-z0-9][a-z0-9-]{0,63}$` и 409 при коллизии. Это прямое нарушение сквозного требования столпов («всё ОЧЕНЬ удобно и просто в настройке») и метрики «время собрать кейс без правки платформы».

Хорошая новость: грамматика слага уже едина по всему продукту (`SLUG_RE` — «one slug grammar across apps, registries, org», `org-crud.js:8-17`), а ключ процесса в модельере УЖЕ автогенерится транслитом (`novyy-protsess-N` — отсюда и мусор в §5). Т.е. генератор фактически существует, просто не применён к остальным 10 местам и не дружит с осмысленными именами.

### Решение

1. **Правило-близнец §3:** *машинное имя человек не придумывает — оно генерируется из названия.* Один серверный генератор: транслит названия → слаг по единой грамматике, коллизия → суффикс `-2/-3` (уникальность решается атомарно на беке: slug в POST становится опциональным во всех create-эндпойнтах).
2. **Один UI-компонент `SlugField`:** пользователь вводит только «Название»; под полем живая подпись «будет создан как `zakupki-oborudovaniya` · изменить» — раскрытие для продвинутых, редактируемо до создания, immutable после. Применить во всех местах 1–9.
3. **«Набор полей» спрятать вовсе** (см. §2.6): первый «Настроить поля» создаёт набор `main` автоматически; ключи полей — автогеном из названий полей.
4. **Модельер (§10 из таблицы — самое больное):** вместо рукописного текст-списка ключей — мультиселект полей из схемы привязанного приложения (схема уже доступна по `registry_def`); ключ процесса — авто из имени процесса (уже так, оставить но требовать имя, §5.2).
5. **Пикеры — на человеческий:** везде «Название (slug)» вместо голого слага в опциях селектов.
6. **AI-угол (столп 5):** ассистент, собирающий решение, использует тот же серверный генератор — ни человек, ни ИИ не изобретают машинные имена.

## Предлагаемая нарезка (3 волны)

**Волна A — «перестань показывать машину человеку» (быстрые, болят ежедневно):**
актор-резолвер бэка + `<ActorChip>`/`<RecordRef>` (§3.2-3); **P1-краш /rights/trail** (первое применение ActorChip); правило «нет фейковых кнопок» + видимый disabled у «Экспорт прав»/«+ Исполнитель» + экспорт журнала CSV; поднять формы управления правами из-под фолда (§6.5); DateInput/MoneyInput/PersonPicker + P1-багфиксы (money-округление, `/api/org` 401, x-date в collection, двойное «Создано», backfill UUID-логинов); кликабельная строка задач + контекст записи в имени + ссылки из деталки; сайдбар: collapse групп со свёрнутым дефолтом + «+ Раздел» и контекст-меню приложения на месте; модельер требует имя; анти-UUID гейт; **авто-слаги везде** (серверный генератор + `SlugField`, §7 — слаг опционален во всех create-эндпойнтах, человек вводит только название).

**Волна B — «масштаб и под себя»:**
view-примитив (source=inbox|processes, owner_actor per-user) + user-prefs store; поиск/фильтры/группировка инбокса (сервер+UI); разнесение `/processes` на оператора и каталог + серверная пагинация инстансов; **identity hub исполнителя** (учётка+оргместо+права+LLM, переходы /users↔/org↔/rights↔/agents); **move-API оргструктуры + DnD дерева**; DnD сайдбара поверх ▲/▼; RelationPicker-автокомплит, MultiSelect-чипы; агентские сигналы в инбоксе; статус-бейджи и действия на месте в /agents; модельер: мультиселект полей вместо рукописного списка ключей (§7.4); пикеры «Название (slug)» вместо голых слагов.

**Волна C — «AI-first полировка» (столп 5):**
ассистент раскладывает приложения по разделам, создаёт/настраивает личные виды («покажи мои задачи по закупкам с дедлайном на этой неделе — сохрани как вид»); плотность/счётчики; datetime-тип.

Каждая волна по D-064 должна закрываться LIVE_PROOF-кейсом рядовым сотрудником, не владельцем (пример анти-кейса: «сотрудник без грантов конструктора находит свою задачу среди 200 по названию заявки и выполняет её, ни разу не увидев UUID»).
