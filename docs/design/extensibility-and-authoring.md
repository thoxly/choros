# Choros — Extensibility, Authoring & Customer Lifecycle (ADR)

> Как Choros даёт нетехничному mid-market клиенту ГЛУБОКУЮ кастомизацию под себя,
> не превращаясь в инженерно-тяжёлый дорогой продукт — модель авторинга,
> системный config-агент, версионность и среды клиента вокруг одного хребта.

Версия документа: 0.1 · Дата: 2026-06-08 · Статус: решение (ADR) — ЧЕРНОВИК на подпись фаундера

> Основание: tenancy-grade research + адверсариальный дебат (2 камеры × 2 раунда) +
> 3 независимых судьи. Вердикт: камера A (code-native substrate) выигрывает рамку
> (8.5 / 8 / 7.5), но финал — СИНТЕЗ: структура A + дисциплина безопасных дефолтов
> B. Confidence по round-trip-устойчивости агент-авторского кода — medium
> (vendor-documented cliff, см. §11). Документ фиксирует результат как ADR.

---

## 1. Решение в одной строке

**Артефакт авторинга — ДВУХЭТАЖНЫЙ над одним named-binding контрактом: Floor-1 —
декларативный JSON-Schema + UI-schema (кнопочный, zero-LLM, бэкенд-валидируемый,
переживает агента-офлайн) как дефолтная поверхность; Floor-2 — agent-authored код
(React-презентация, DMN, External-Task) как governed-потолок БЕЗ палитры-ограничения,
для «глубокой кастомизации под себя». Между ними — декларативный СРЕДНИЙ слой (DMN +
expression-visibility). Системный config-агент = сотрудник (§3 CONCEPT): авторит
ТОЛЬКО в DRAFT, promote и весь деструктив — human-gated. Версионирование — git-под-
капотом (когерентный коммит связки), наружу — семантический changelog + one-click
promote. Среды — два ЛОГИЧЕСКИХ тира (draft→published) в одном silo, prod managed/
locked, данные не копируются.**

Это разрешает центральное напряжение founder'а РЕЛОКАЦИЕЙ, а не компромиссом:
**агент = локус простоты, код = локус мощи, детерминированный Floor-1 = локус
автономии тривиальной правки, единый control plane (§3/§8) = локус governance.**
Не «дорого и инженерно-сложно» (логический дефолт сред, drain-дефолт, Floor-1 без
LLM) и не «примитивно с обрывом» (нет палитры-потолка для глубокой кастомизации).

| Развилка | Решение | Реализуем сейчас? |
|---|---|---|
| Модель авторинга (хребет) | **two-floor**: config-primary Floor-1 + code-substrate Floor-2; код-primary для структуры (§7 ordering), config-primary для field-edit | Floor-1 + DMN-middle — **day-1**; Floor-2 git-машинерия — инкрементально |
| Системный config-агент | **сотрудник в оргструктуре** (роль→MCP-tools, бюджет, граница, единый аудит); **DRAFT-only**, promote human-gated | да, day-1 (governance-аппарат) |
| Модули / справочники | универсальный 2-3-уровневый Section→App→Form; системные справочники **core-owned, extend-not-replace** | да, day-1 |
| Кросс-приложенческие данные | **references, not copies**; ACL на каждом hop; **redacted-проекция** при нехватке прав | да, day-1 (это уже §7) |
| Версионность связки | **git-под-капотом**, когерентный коммит (BPMN+форма+схема+grants); наружу changelog | **bundle-coherence day-1**; полный git+diff — инкрементально |
| Миграция инстансов | **DRAIN-by-default**; Camunda-mapping = on-demand эскалация внутри red-lines; per-record expand/contract | drain — day-1; mapping-UI — on-demand |
| Среды клиента | **2 логических тира** (draft→published) в одном silo; prod managed/locked | да, day-1 |

## 2. Откуда это решение и что в CONCEPT §7 несущее

CONCEPT §5/§7 уже фиксирует: «формы кодом (AI-generated), а не конструктором» —
**named moat** (§4), и §7 ОРДЕРИТ архитектуру код-первой дословно: «Пользователь
описывает форму текстом → LLM генерирует React-компонент + JSON Schema →
предпросмотр → версионирование вместе с процессом… Fallback для тривиальных форм —
form-js». Code-gen — **named primary**, form-js — **explicitly-labeled fallback**.

Адверсариальный дебат проверил спорную точку против источника. Вердикт (все 3 судьи):

- **Камера A победила рамку**, но только в форме Round-2 — потому что поглотила
  лучшее у B в two-floor модель. Камера B инвертировала собственное основание
  (подняла fallback в primary). Под целевого клиента («технически НЕ силён, но
  хочет глубокой кастомизации» — §4) палитра-обрыв B — не редкое исключение, а
  **нормальный случай**.
- **Два технических аргумента A держатся по источнику.** (1) Бэкенд-валидация
  требует, чтобы СХЕМА была декларативной (она такая в обеих позициях — §7), НЕ
  презентация; React поверх декларативного JSON-Schema-контракта полностью бэкенд-
  валидируем. (2) Governance-дихотомия B ложна: §8 «агент предлагает — человек
  подтверждает» **артефакт-агностично**; риск эскалации — свойство self-apply-vs-
  gated-promote, не code-vs-config.
- **Финал = синтез.** A-структура (код-substrate, ceiling-free) + ВЕСЬ безопасный
  floor B (config-primary Floor-1, drain-default, DMN-middle, логические среды,
  managed-prod, redacted-проекции) + B-дисциплина человеко-читаемой ревью-
  поверхности. Это **одна поверхность с двумя этажами, а не два продукта**.

Этот документ не пересматривает CONCEPT §7 — он доводит его ordering до инженерного
решения, привив floor-дисциплину проигравшей стороны как несущий инвариант.

## 3. Три ортогональные оси (чтобы не было ложной дихотомии «код ИЛИ конфиг»)

Ключ, снявший спор камер: это **три независимые оси**, а не одна развилка.

- **Ось A — этаж выразительности.** Каким артефактом выражается правка: Floor-1
  (декларативная схема, кнопки) → Middle (DMN/expression) → Floor-2 (код)? Каждая
  правка маршрутизируется на САМЫЙ НИЗКИЙ достаточный этаж. Код — последний этаж, не
  первый.
- **Ось B — governance промоушна.** Кто применяет правку: self-apply (запрещено для
  ОБОИХ этажей в prod) или gated-promote (человек подтверждает)? Governance — свойство
  ЭТОЙ оси, не оси A.
- **Ось C — физический дефолт сред.** Сколько контуров: логические тиры в одном silo
  (дефолт) или отдельный физический контур (редкая on-demand эскалация)?

Оси совместимы над одним артефактом и одним silo (tenancy-ADR §3). Палитра/конструктор
B путал ось A с осью B («config=governable»); камера A показала их ортогональность.

## 4. Развилка 1 (ХРЕБЕТ) — модель авторинга: TWO-FLOOR

> Прямой вопрос founder'а: код vs структура, где граница, что эмитит «системный
> config-агент» и под каким governance.

**Решение: код — substrate, config — floor. Граница машинно-проверяема, не на вкус
агента.**

### Этажи (ось A)

- **Floor-1 — декларативный, config-primary (ДЕФОЛТ-поверхность).** JSON Schema +
  UI-schema, привязка через named-binding (`field-key == variable-name`),
  бэкенд-валидация против объектной схемы (§7: фронт не доверен). **Кнопочно**
  редактируется нетехничным клиентом: relabel, hide field, toggle required. **Zero-LLM,
  детерминированно, ПЕРЕЖИВАЕТ агента-офлайн.** Это §7 form-js fallback, поднятый до
  этажа-дефолта. Снимает класс отказа «agent-SPOF на рутинной правке живой формы» —
  самый частый кейс изменения у целевого клиента.
- **Middle — декларативный (условная логика без кода).** DMN-таблицы (§13 CONCEPT) +
  expression-based visibility/validation: условные поля, бизнес-правила, маршрутизация.
  Сюда маршрутизируется ВСЁ, что выразимо декларативно, — клиент получает глубокую
  логику кликами, **не упираясь в код преждевременно**.
- **Floor-2 — код-substrate (governed-потолок, БЕЗ палитры-ограничения).** React-
  презентация над named-binding контрактом, DMN, External-Task workers, object-schema
  миграции. **Нет палитры, которую можно перерасти; нет «sorry, not configurable».**
  Это niche §4. Раздельные классы Floor-2: (а) код из vetted-палитры компонентов
  (детерминированно валидируем, переживает round-trip) для стандартных виджетов; (б)
  истинно-новый кастом-компонент → sandbox-iframe (§7), **флагованный и редкий** —
  единственное место round-trip-cliff'а (см. §11 риск).

**Несущий инвариант хребта:** код Floor-2 НЕ мутирует состояние процесса напрямую —
он презентация/интеракция над **тем же** named-binding, валидируемым на бэке. Тонкое
ядро (§5) сохранено: императивная логика уходит в DMN-middle + External-Task, форма-код
заперт в sandbox-iframe и трогает состояние только через валидируемый binding. BPMN-ядро
остаётся чёрным ящиком с reference-токенами.

### Системный config-агент: в оргструктуре, под §3/§8

«Системный агент, который настраивает интерфейс» — это **первоклассный СОТРУДНИК**
(§3 CONCEPT), а не новый неаудируемый privilege-path:

- **Он в оргструктуре?** Да. Карточка: роль → права → доступные MCP-инструменты
  (`emit_form_code`, `edit_jsonschema`, `author_dmn`, `scaffold_external_worker`,
  `write_object_migration`, `author_instance_mapping`, `open_draft_branch`,
  `request_promote`), явный токен/деньги/действия-бюджет, граница автономии.
- **Аудит?** Каждое действие — в едином аудит-логе, ровно как у исполнителя-агента.
- **Гейт на промоушн?** Агент авторит **ТОЛЬКО в DRAFT**; promote — human-gated
  (deploy ≠ active). Это **дословная** реализация §8 «агент предлагает — человек
  подтверждает» для системной конфигурации.
- **Self-apply в prod запрещён для ОБОИХ этажей** — риск эскалации живёт в гейте
  (ось B), не в формате артефакта. Агент, само-применяющий CONFIG в prod, ровно
  столь же неаудируем, как код. Дихотомия «config=safe / code=escalation» не держится.

### RED-LINES — категорический human-confirm, default-DENY на необратимость

Не enumerated-allowlist опасного (любая необратимая операция вне списка прошла бы как
«безопасная»), а **default-DENY на необратимость** (симметрично RLS default-DENY,
tenancy §9). Категорически human-gate: drop/rename поля, lossy type-change, lossy
live-migration, delete/rename core/system-directory-поля. Подтверждение — **семантическое**
(«поле X удаляется, данные теряются»), не техническое.

## 5. Развилка 2 — модули / разделы + системные справочники

> Прямой вопрос: группировка; что системное/редактируемое vs заблокированное ядром.

**Решение: универсальная навигация, core-owned системные справочники, extend-not-replace.**

- **Группировка:** 2-3-уровневый контейнер **Section → Application/Module → Form/List**
  (§7 CONCEPT: «Приложения = справочники и реестры: контрагенты, договоры, заявки»;
  ближайший RU-аналог по NAV-форме — ELMA365 Section→App→form). Стабильный неломаемый
  левый сайдбар с пресет-секциями + ограниченный reorder. Агент эмитит nav как
  версионированный config-файл; человеко-видимая структура фиксирована и предсказуема.
- **КРИТИЧНО — отличие от ELMA:** мы берём NAV-СКЕЛЕТ ELMA (универсальный IA), но
  **отвергаем конструктор как модель авторинга** — §4 (niche «формы кодом, не
  конструктором») и §14 red-flag «не повторять ELMA целиком». Тот же скелет навигации,
  код-native авторинг под ним.
- **Системные справочники (контрагенты, оргструктура, пользователи) — CORE-OWNED класс,
  extend-not-replace:** клиент/агент могут **ДОБАВИТЬ** кастом-поле (схемой/кодом), но
  ядро **БЛОКИРУЕТ** delete/rename/overwrite стандартных авто-заполняемых полей (red-line).
  Это гарантирует безопасные апгрейды и целостность.
- **Справочник людей/пользователей = read-mostly проекция Keycloak** (tenancy-ADR §6:
  Keycloak = auth+федерация, RBAC в TS-ядре), НЕ CRUD-таблица. Код-native не означает,
  что агент переписывает core-справочники; означает, что клиент-изобретённые модули/
  каталоги достижимы без палитры-потолка.

## 6. Развилка 3 — кросс-приложенческие данные

> Прямой вопрос: как сущности ссылаются друг на друга; права при кросс-ссылках.

**Решение: references, not copies (это уже §7 дословно) — обе камеры согласны, ни одна
не ослабляет.**

- **Ссылка хранит ID**, tenant-scoped `(tenant_id, id)` (tenancy §4); внешние поля
  читаются живым lookup/rollup. **Weak reference** (независимая безопасность) = дефолт;
  **strong** (master-detail, cascade) = явный и редкий.
- **ACL форсится на КАЖДОМ hop traversal** — dot-walking НЕ обходит безопасность. При
  нехватке прав на связанную запись кросс-ссылка возвращает **РЕДАКТИРОВАННУЮ проекцию**
  (label/id only) — прямая реализация гарантии §3: агент-«закупщик» видит заявку, но НЕ
  финансовые поля контрагента.
- **Канонический дом per-role видимости поля — ОДИН:** record-level RBAC на JSONB, а
  форма накладывает **UI-policy слой поверх ОДНОЙ формы** (most-restrictive-wins), не N
  форкнутых форм.
- **Traversal hard-capped** (Salesforce-style hop-limit, no rollup-of-rollup) против
  циклов; кросс-объектные агрегаты **eventually-consistent** — защита 4-8 vCPU сервера
  (§11).
- **Кросс-процессные данные** — через ОТДЕЛЬНЫЙ авторизованный RLS-канал (server-side,
  tenancy §9), **НИКОГДА** через BPMN process-переменные. Форма-код Floor-2 читает
  кросс-app данные ТОЛЬКО через этот авторизованный, RLS-gated, redaction-aware канал —
  то, что форма стала кодом, здесь не меняет ничего.

## 7. Развилка 4 — версионность + миграция инстансов

> Прямой вопрос: единица версионирования, связка процесс↔форма↔схема, откат, что с in-flight.

**Решение: git-под-капотом для когерентности+аудита, drain-by-default для in-flight,
Camunda-mapping — только on-demand эскалация.**

### Единица версионирования и связка

Движок версионирует форму лишь как указатель (`formId`), значит связку
**BPMN ↔ форма-код ↔ form-JSON-Schema ↔ object-schema ↔ role/agent/MCP-grants** надо
версионировать КОГЕРЕНТНО, иначе — security-десинк (дренируемый старый инстанс агента
получает MCP-инструмент, которого в его версии не было). Решение:

- **Под капотом — git-ref:** content-addressed, атомарно-когерентный коммит
  гетерогенной связки. Даёт когерентность И diff/traceability — строгий superset
  governance-сигнала над opaque-bundle (который прячет diff и реимплементирует худший git).
- **Наружу — семантический changelog + one-click promote.** Founder/клиент НЕ управляет
  git/ветками (MEMORY founder-no-branch-mgmt): touchpoint = review-dev + promote, та же
  форма, что в собственном SDLC Choros (environments.md: dev←dev auto, prod←main
  founder-gated). Human-facing surface — **СЕМАНТИЧЕСКИЙ** changelog («добавлено поле X,
  мягкая миграция Y, БЕЗ потери данных»), НЕ raw code-diff и НЕ «bundle v7→v8». Git-diff —
  латентный актив для технического человека клиента, не первичный UX.

### In-flight инстансы (§14 CONCEPT — день-1 риск)

- **DRAIN-by-default — ЖЁСТКИЙ дефолт** (нативное поведение Flowable, §6): старые
  инстансы доигрывают на своей версии. **Per-record expand/contract** делает «доиграть
  на старой схеме» РЕАЛЬНЫМ.
- **Camunda-grade `fromActivity→toActivity` mapping** — авторит АГЕНТ, **on-demand
  ЭСКАЛАЦИЯ внутри red-lines**, не дефолт: транзакционно, wait-state-only, без смены
  типа элемента, auto-map только совпадающих ID. Делать mapping дефолтом = тяжёлый UI,
  которого mid-market не хочет.
- **Откат:** package-rollback **заблокирован**, пока живы старые инстансы на старой
  версии; rollback forward-only / компенсирующий (expand/contract, deprecation-first).
  Lossy-миграция + rollback при живых инстансах = red-lined human-gate.
- **Config-vs-data split строго:** промоутится только метаданные, прод-данные не
  копируются между средами.

## 8. Развилка 5 — среды клиента: САМЫЙ ЛЁГКИЙ работающий вариант

> Прямой вопрос: сколько сред по дефолту, промоушн конфигурации, изоляция тестовых
> данных — для НЕТЕХНИЧНОГО клиента.

**Решение: два ЛОГИЧЕСКИХ тира в одном silo, prod managed/locked, данные не копируются.
Физический контур — редкая on-demand эскалация (ось C).**

- **ДЕФОЛТ = 2 логических тира (draft → published) в ОДНОМ silo-DB.** Данные НИКОГДА не
  копируются (config-only promotion) — дешёвый test-before-prod (модель Retool draft↔live
  / Power-Platform managed-solution). Respects 4-8 vCPU home server (§11) и анти-дорого
  мандат founder'а.
- **Prod — «managed/locked»:** прямые правки в проде невозможны — убивает дрейф
  «работало в dev, сломалось в prod» (корень дрейфа флота tenancy §10).
- **Изоляция тестовых данных:** копия прод-данных в sandbox — отдельная дорогая редко-
  обновляемая ось, НЕ дефолт. Третий контур с изолированными интеграционными кредами
  (1С/ERP) или нагрузочным — **только on-demand**, для клиента, которому реально нужна
  изоляция.
- **Физический контур — on-demand, НЕ норма** (ось C). Поскольку артефакт-модель уже
  git+deploy, реальный изолированный контур достижим конфиг-флипом, без редизайна
  продукта, — но **не предлагается дефолтом**, иначе продукт сползёт в «инженерно-тяжёлый
  дорогой».
- **Ортогональность (важно по брифу):** эта ось (draft/published версий артефактов
  ВНУТРИ продукта клиента) ортогональна dev/prod-средам САМОГО Choros (environments.md /
  branching.md — SDLC Choros, не клиента). Та же git-форма, **разные оси** — не путать.

## 9. Обязательные day-1 инженерные гарды (несущие, блокирующие)

Не «потом», а условие корректности, чтобы не было дорого ретрофитить:

1. **Floor-1 действительно автономен и ПОЛОН.** Все field-level правки (relabel /
   hide / toggle-required / порядок / help-text), не токен-подмножество — кнопочные,
   zero-LLM, переживают агента-офлайн. Иначе agent-SPOF становится системным.
2. **Машинно-проверяемая граница Floor-1 ↔ Floor-2.** Формальное, документированное,
   предсказуемое правило, КАКАЯ правка тривиальна (Floor-1) vs структурна (Floor-2).
   Без него агент маршрутизирует тривиальное в код (зря теряя детерминизм) или
   структурное в Floor-1 (тихо ломая инвариант) — обрыв B возвращается в маскировке.
3. **Единый источник истины `field-key == variable-name`** + compat-проверка между
   этажами: кнопочно скрыли поле в схеме, а Floor-2 код на него ссылается → блокирующая
   ошибка, не тихий рассинхрон.
4. **Блокирующий CI-тест на КОГЕРЕНТНОСТЬ связки** form-schema ↔ object-schema ↔ MCP-grants
   по версиям (симметрично §9 cross-tenant CI-гарду tenancy) — ДО того, как git-под-капотом
   считается готовым. Баг в самой системе версионирования = та security-регрессия, которую
   механизм призван предотвратить.
5. **Per-record expand/contract object-schema versioning** заложить в модель данных с
   day-1 (§14 «потом дорого»). Деструктив — expand/contract + deprecation-first + бэкап
   перед деструктивным шагом.
6. **DRAIN-by-default + managed/locked prod** как жёсткие дефолты; Camunda-mapping и
   физический контур — только за явным human-gate.
7. **Default-DENY на необратимость** в red-lines (не enumerated-allowlist): любая
   необратимая операция по умолчанию требует human-confirm.
8. **Config-агент = сотрудник с day-1 governance-аппаратом:** роль→MCP-tools, бюджет,
   граница, единый аудит, DRAFT-only, self-apply-в-prod запрещён для обоих этажей.
9. **Независимый детерминированный валидатор changelog ↔ diff** (автотесты формы перед
   promote, schema-compat-check): семантический changelog НЕ может быть единственной
   гарантией — агент авторит И код, И summary (конфликт интересов в ревью).
10. **Sandbox-iframe Floor-2-код достигается НАМЕРЕННО, не случайно** — флагован, редок,
    богато инструментирован (round-trip-cliff живёт здесь).

## 10. Связь с уже принятым

- **tenancy-ADR (silo / один артефакт / RLS):** среды клиента — логические тиры ВНУТРИ
  одного silo (tenancy §5), физический контур — редкая эскалация (ось C симметрична
  двум ортогональным осям tenancy §3). Кросс-ссылочный read — через RLS-канал (tenancy

  two-floor — это конфигурация поверх образа, не форк.
- **Агент = сотрудник (§3 CONCEPT):** config-агент — буквально та же абстракция
  (роль→MCP-tools, бюджет, граница, единый аудит), что исполнитель-агент. «ИИ настраивает
  систему» governable через §3, а не новый privilege-path.
- **Формы кодом (§7):** документ — литеральное чтение §7 ordering (code-primary,
  form-js fallback), не его пересмотр. Floor-1 = §7 form-js fallback, поднятый в floor.
- **§8 «агент предлагает — человек подтверждает»:** дом governance промоушна (ось B),
  артефакт-агностично — применяется к коду и конфигу идентично.
- **SDLC-ветки Choros vs среды клиента:** environments.md / branching.md — про SDLC
  САМОГО Choros; среды клиента (§8 этого ADR) — отдельная ось. Та же git-форма, не путать
  (явное предупреждение брифа).

## 11. Открытые вопросы / точки решения фаундера

- **AGENT-SPOF на Floor-2 (неустраним, требует инструментации).** Любое структурное/
  компонентное/логическое изменение зависит от недетерминированной LLM-переэмиссии.
  **Нужны метрики:** какая ДОЛЯ реальных правок целевого клиента — Floor-1
  (детерминированных) vs Floor-2? Если Floor-2 частый у «хочет глубокой кастомизации» —
  SPOF системный, нужен явный SLA/фоллбэк на ручной код-путь для технического оператора.
  *Точка решения: порог доли Floor-2, при котором эскалируем.* (confidence: medium)
- **Review-trust поверхность.** One-click promote безопасен ровно настолько, насколько
  семантический changelog верен; нетехничный клиент не может проверить React/migration-diff.
  Red-lines ловят КАТЕГОРИЧЕСКИ деструктивное, но НЕ семантически-неверную структурно-
  валидную правку. *Точка решения: насколько богат независимый валидатор changelog↔diff
  до того, как one-click promote открывается нетехничному клиенту.* (confidence: medium)
- **Round-trip decay на агент-авторских кастом-компонентах.** Новый компонент, написанный
  самим агентом, — место, где будущий агент/другая версия модели может не отыграть свой
  прежний код. «Агент сопровождает» снижает, но не стирает vendor-documented cliff.
  *Точка решения: held-out политика — что делать, когда round-trip ломается на проде.*
  (confidence: medium — это самый durable остаточный риск)
- **Day-1 стоимость git-под-капотом + per-record expand/contract** ВЫШЕ, чем opaque
  bundle, для малой команды. *Решение по секвенированию (рекомендация): сначала Floor-1 +
  drain-default + логические среды + bundle-coherence CI-гард; полная git+migration
  машинерия Floor-2 — инкрементально.* (confidence: high по секвенированию)
- **Формализация границы Floor-1 ↔ Floor-2:** точное машинно-проверяемое правило (гард
  §9.2) — нужен формальный спек до первого Floor-2-релиза. (confidence: medium)
- **ELMA-trap при дрейфе к палитре:** если под давлением простоты vetted-палитра станет
  де-факто потолком (а код-escape — заброшенным), продукт сползёт в конструктор §4-niche-
  to-avoid. *Точка продуктовой дисциплины, не архитектуры: «палитра-ускоритель vs палитра-
  потолок».* (confidence: medium)

## 12. Прямой ответ на центральное напряжение

**Как НЕ стать «инженерно сложным и дорогим», оставшись мощным:**

| Сила тянет к «дорого/сложно» | Контр-дефолт, удерживающий «дёшево/управляемо» |
|---|---|
| Код-substrate Floor-2 | Floor-1 кнопочный zero-LLM дефолт + DMN-middle — код достигается ПОСЛЕДНИМ |
| Git-когерентность связки | Наружу — семантический changelog + one-click; git скрыт, founder не трогает ветки |
| Camunda-grade live-migration | DRAIN-by-default; mapping — редкая on-demand эскалация за red-line |
| Реальные изолированные контуры | 2 логических тира в одном silo — дефолт; физический контур on-demand |
| Кастом-компоненты | sandbox-iframe флагован, редок, инструментирован — намеренная редкая точка |

**Как НЕ стать «примитивным с обрывом», оставшись простым:** нет палитры-потолка
(Floor-2 = реальный код для «глубокой кастомизации под себя» — niche §4); дифференциатор
доходит до мета-уровня (систему настраивает governed агент-сотрудник под §3/§8 — moat,
который конструктор-конкурент не копирует, не бросив конструктор). У финала **ДВА этажа**:
B-floor + governed A-ceiling; у чистого config-конкурента — только один.
