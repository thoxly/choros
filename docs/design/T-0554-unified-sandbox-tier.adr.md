# ADR · T-0554 — Единая песочница «приложение + процесс» (tier / promote)

**Phase:** DESIGN · **Status:** needs-founder-decision (модель — развилка, см. §4) · **Date:** 2026-06-30
**Task:** T-0554 [platform / substrate]
**Origin:** приёмка 2026-06-30 (вопрос фаундера: «приложение в draft — как образовалась боевая задача? у нас же есть разделение на песочницу»).
**Ratified context (НЕ переоткрывать):** `docs/product-decisions.md` — **PD-12** (среды/песочница на уровне enterprise, без жаргона тест/дев), **PD-21/PD-22** (генерация в песочницу DRAFT → ревью → публикация; песочница→продуктив = `promote`).
**Foundation (факты кода):** `src/core/env-tier.ts` (T-0087: `Tier=draft|published`, `assertWritable`, `decidePromote`); `src/http/artifacts.ts` (`promoteTier` — единственный, кто пишет `published`); `src/core/document-render.ts:437` (шаблон гейтится `tier!=="published"`); `src/http/process-defs.ts:13,26-27` (publish-гейт BPMN → `deployBpmn`); `src/http/applications.ts:204` (PATCH БЕЗ tier); `src/http/inbox.ts` (tier НЕ читается).

---

## 1. Проблема

«Статус» приложения (`application.tier ∈ {draft, published}`, дефолт `draft`) **обещает
песочницу, но не обеспечивает её**:

- **нет действия `promote`** для приложения — `PATCH /api/applications/:id` меняет только
  `section/display_name/description` (applications.ts:204); кнопки «Опубликовать» нет →
  приложение навсегда `draft`;
- **рантайм не гейтится по `app.tier`** — `inbox.ts` и движок tier не читают; данные
  записываются, процессы исполняются, задачи создаются независимо от статуса;
- следствие: `draft`-приложение используется живым **опубликованным** процессом без
  изоляции. Бейдж `DRAFT` — декоративный.

**Контраст — у процессов песочница РЕАЛЬНА.** BPMN-процесс исполняется только после явной
публикации: `POST /api/process-defs/:key/publish → lint → deployBpmn` (process-defs.ts);
CRUD процесса движок не трогает. Именно поэтому «боевые» задачи в приёмке существуют — был
опубликован и запущен процесс `acceptance-demo`, а вовсе не «протекло» draft-приложение.

**Корень — три несогласованных механизма «черновик→боевое»:**

| Примитив | Механизм границы | Состояние |
|----------|------------------|-----------|
| Процесс (BPMN) | `publish` → `deployBpmn` (process-defs.ts) | **работает** |
| Документ-шаблон | `tier!=="published"` (document-render.ts) | работает |
| Бандл/артефакт | `promoteTier` + `env-tier` (T-0087, artifacts.ts) | примитив есть |
| **Приложение** | `application.tier` | **декоративен — без promote и без гейта** |

PD-12/21/22 описывают **одну** песочницу (DRAFT) и **один** `promote` для решения целиком —
а в коде их три-четыре, и приложение из этой картины выпало.

## 2. Что доказано (приёмка)

- 5 приложений — все `draft`; promote-пути нет (API/UI).
- 2 задачи в инбоксе — userTask'и инстанса `07a450cb…`, `procKey=acceptance-demo`,
  `role-approver`, `waiting`. Источник — опубликованный процесс, не приложение.
- `inbox.ts` / engine-drive по tier не фильтруют.

## 3. Цель

Единая, **честная** модель «песочница → продуктив» для решения целиком (приложение + данные
+ процесс + формы): одно действие `promote`, согласованный рантайм-гейт, и `app.tier`,
который что-то значит, либо честно удалён.

## 4. Развилка модели — РЕШЕНИЕ ФАУНДЕРА

Три взаимоисключающих направления. Выбор за фаундером — он определяет impl.

**Опция A — per-app promote + рантайм-гейт.** Завести `POST /api/applications/:id/promote`
(draft→published через `decidePromote`/`assertWritable` T-0087) и гейтить рантайм: пока
приложение `draft`, его данные/процессы — sandbox-only.
*За:* локально, переиспользует env-tier. *Против:* плодит ЕЩЁ один promote рядом с
process-publish и bundle-promote; «решение» промоутится по кускам, рассинхрон возможен.

**Опция B — убрать статус у приложения; граница только у процессов.** Приложение — это
реестр данных, всегда «живой»; единственная исполнимая граница — `publish` процесса. Снять
декоративный `tier` с приложения (честно: он ничего не значил).
*За:* минимум, убирает ложное обещание. *Против:* противоречит PD-12/22 (генерация в
DRAFT-песочницу с ревью перед продуктивом) — теряем sandbox для данных/форм.

**Опция C — bundle-promote (рекомендуется).** Единица песочницы и публикации — **решение-
бандл** (приложение + связи + процесс + формы), как в PD-21/22 (генерация one-shot бандлом).
`promote` атомарно публикует весь бандл; `app.tier` и process-publish становятся **проекцией
состояния бандла**, а не самостоятельными осями. Опирается на существующий `env-tier` +
`artifacts.promoteTier`.
*За:* совпадает с уже ратифицированной картиной (PD-12/21/22), один `promote`, нет
рассинхрона примитивов, «published-lock» (`assertWritable`) применяется единообразно.
*Против:* крупнее; требует определить границу бандла и взаимодействие с уже-опубликованными
процессами.

**Рекомендация: C.** Это единственный вариант, замыкающий PD-12/21/22 без третьего
параллельного promote; A — частный шаг к C; B противоречит ратифицированному видению
песочницы для данных.

## 5. Scope после выбора (ориентир для C)

- модель «бандл» (что входит, как версионируется), `promote`-сервис поверх `env-tier`;
- рантайм-гейт: sandbox-данные/процессы видимы только владельцу/админу (грант
  `authoring_draft`, PD-22), боевые — всем по грантам;
- `app.tier` → проекция бандла; убрать декоративный «вечный draft»;
- согласовать с process-publish (опубликованный процесс не может зависеть от sandbox-app);
- UI: явное «Опубликовать решение» с ревью (PD-22: «не рендерим всё в чате»).

## 6. Вне scope / non-goals

Мульти-среда enterprise (>2 tier), отдельная sandbox-схема/тенант (silo-only сейчас —
[[choros-tenancy-decision]]), миграция уже-боевых процессов. Конкретный DDL/эндпоинты — после
выбора модели.
