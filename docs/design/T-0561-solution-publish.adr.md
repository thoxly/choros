## 1. Проблема (приёмка 2026-06-30)

«Статус: draft» у приложения декоративен — сменить на боевое нечем. С построенной песочницей
(T-0557/0558) статус теперь реален: **draft = видит только владелец, процессы не идут;
published = видит команда, процессы работают**. Нужна кнопка «Опубликовать». Но решение редко
= одно приложение: бывает справочник (одно приложение), приложение+процесс, главное+справочники.
Пользователь тестирует e2e ВСЁ вместе и публикует вместе, потом правит по кусочку и публикует
заново (решение фаундера — сценарий).

## 2. Решение (PD-26): публикация связки, derived + прозрачно

«Опубликовать» на приложении:
1. **Derive связанный набор (1 hop, не транзитивно):** само приложение + приложения-справочники,
   на которые оно ПРЯМО ссылается (поля-`x-relation` → target registry/app) + процессы,
   привязанные к нему (`process_app_binding`) + формы шагов этих процессов.
2. **Показать confirm-список** «Будет опубликовано: приложение X · справочник Y · процесс Z ·
   форма шага» — граница честно видна ПЕРЕД действием.
3. **Промоут всего вместе**, переиспользуя существующую машинерию (`promoteTier` для приложений/
   registry_defs + `publishProcessByKey` для процессов, T-0465) — **новой сущности «Решение»
   НЕ заводим** (в духе «собери из примитивов»; граница = связи, а не контейнер).
4. **Per-item результат вместо `partial`:** список превращается в результаты `✓/✗ причина`.
   Ошибся процесс — видно «✗ процесс: <причина>», чинишь и жмёшь заново. **Статус `partial`
   НЕ хранится и не показывается** — есть только «что доехало» (снимает бывшую развилку №2).
5. **Итерация:** правка опубликованной части (процесс/приложение/форма/роль) помечает «есть
   неопубликованные изменения»; «Опубликовать заново» промоутит **только изменённые** части
   (модельер уже умеет republish процесса; здесь — тот же промоут для приложения/форм).

Справочник без связей → список из одного приложения (вырожденный случай, без церемоний).

### 2.1 Где считается граница
`x-relation`-цели (прямые) + `process_app_binding` по этому приложению. 1 hop — предсказуемо и
показывается пользователю; транзитивное замыкание НЕ берём (мутная граница). Если приложение —
часть AI-бандла (`bundle_id`), можно предложить бандл целиком (естественно ложится, но не v1-блокер).

## 3. UI
- `screen-apps.jsx`: «Статус»-чип → действие «Опубликовать решение» (и в `screen-app-records`/
  `screen-app-schema`, где решение редактируется). Confirm-диалог со списком (паттерн
  `screen-assistant.jsx` bundlePromote). Тост + результаты по пунктам. «Есть неопубликованные
  изменения» — бейдж/подсказка на приложении. touches `web/` → **UX_REVIEW**.
- Backend: эндпоинт «собрать связанное для приложения → превью» + «промоут набора» (reuse
  solution-bundles/promote; тонкий derive-запрос сверху).

## 4. Отклонённые альтернативы
- **Только приложение** (одиночный промоут) — не отражает «тестим и публикуем вместе» (сценарий фаундера).
- **Явная сущность «Решение»** (контейнер + экран) — чётче для крупных случаев, но новый концепт;
  derived+прозрачно даёт то же без концепта (соло-минимализм). Можно дорасти позже.
- **Транзитивная граница** — мутно; берём 1 hop + видимый список.

## 5. Приёмка
- e2e на dev: приложение со справочником и процессом → «Опубликовать» показывает 3 пункта →
  подтверждаю → все боевые, DRAFT-невидимость снята (sandbox-гейт), процесс запускается;
  ломаю схему процесса → повторная публикация показывает «✗ процесс» и не роняет остальное;
  правлю форму → «есть неопубликованные изменения» → republish промоутит только форму.
- Справочник без связей → список из одного приложения.

## 6. Вне scope
Явная сущность «Решение»; транзитивные связи; мульти-среда (>2 tier). Реюз промоута T-0465 — не переписываем.
