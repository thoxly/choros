# Choros — Tenancy & Delivery

> Как Choros изолирует данные множества компаний-клиентов и как поставляется
> (self-hosted / SaaS), оставаясь одной кодовой базой и одним аудит-нарративом.

Версия документа: 0.1 · Дата: 2026-06-08 · Статус: решение (ADR) — принято фаундером

> Основание: исследование + адверсариальный спор агентов (6 направлений research,
> 2 камеры × 2 цикла дебатов, 3 независимых судьи; консенсус — strong). Документ
> фиксирует результат как архитектурное решение. Confidence по 152-ФЗ — medium
> (web-sourced), требует юридической валидации (см. §12).

---

## 1. Решение в одной строке

**Модель данных ядра — multi-tenant-aware с первого дня (`tenant_id` сквозь всю
схему); физический дефолт развёртывания для целевого РФ-mid-market — silo (один
клиент = один изолированный контур). Всё это — над ОДНИМ артефактом и ОДНОЙ
схемой; режим развёртывания — конфигурация, не ветка кода.**

| Развилка | Решение | Реализуем сейчас? |
|---|---|---|
| Модель данных (core_model) | **multi-tenant-first** (`tenant_id`, scoped-уникальность) | да, day-1 |
| Изоляция (isolation) | **hybrid**: silo — дефолт; pooled-RLS — заложен в фундамент | **только silo**; pooled отложен |
| Identity (Keycloak) | dedicated realm на silo-контур; shared realm + Organizations — для будущего pooled | dedicated realm (silo) |
| Кодовая база | **один артефакт**, режим = конфигурация | да |

**Тенант = одна компания-клиент** (её оргструктура, роли, процессы, задачи, данные,
аудит). Целевые 150–300 человек — это пользователи ВНУТРИ одного тенанта; тенантов
(клиентов) — десятки на старте, потенциально сотни.

## 2. Что не так с CONCEPT.md §12 и как правильно

CONCEPT.md §12 сводил тенантность к фразе «Flowable нативно поддерживает
multi-tenancy — в SaaS тенанты на общей инсталляции». Это **инженерно-неверное
основание для дизайна** по двум причинам:

1. **Flowable MT покрывает только таблицы движка** (`TENANT_ID_` на engine-таблицах)
   и **не фильтрует автоматически** — приложение обязано само навязывать границу.
   Вся ценность Choros — оргструктура, роли, инбокс, аудит-лог, объектная модель
   (JSONB) — живёт в TS-ядре и **изоляции от движка не получает**. Тенантность ядра
   проектируется с нуля.
2. **«тенанты на общей инсталляции» преждевременно фиксирует pooled** — а для
   целевого РФ-mid-market дефолт обратный (silo).

Формулировка §12 в CONCEPT.md исправлена и ссылается на этот документ.

---

## 3. Две ортогональные оси

Ключ, снявший ложную дихотомию «pooled ИЛИ silo»: это **две независимые оси**, а не
одна.

- **Ось A — инвариант модели данных.** Заложен ли `tenant_id` в схему так, что
  данные разных тенантов структурно неслияемы (scoped-уникальность, FK, индексы)?
- **Ось B — физический дефолт развёртывания.** Сколько тенантов живёт в одной
  инсталляции — много (pooled) или один (silo)?

Оси **совместимы над одной схемой**: модель всегда multi-tenant-aware (ось A), а
сколько тенантов положить в инсталляцию — выбор развёртывания (ось B). Паттерн
зрелых dual-delivery вендоров (GitLab Cells, Sentry, Mattermost, PostHog,
Discourse): *pooled внутри ячейки, ячейка = граница изоляции/масштаба* — а не
«1 компания = 1 БД» как закон природы.

## 4. Развилка 1 — модель данных: MULTI-TENANT-FIRST

**Решение:** `tenant_id` — сквозной атрибут модели с миграции №1. Уникальность —
**scoped**: `(tenant_id, id)`, не глобальный `id`. `tenant_id` — **ведущая колонка**
каждого составного индекса и FK. `tenant_id NOT NULL` везде.

**Почему сейчас, а не потом — рычаг обратимости.** Добавить scoped-ключ на чистом
листе стоит ~0 человеко-часов. Ретрофит уникальности по живым данным — отдельный
многолетний проект (опыт GitLab Cells, Mattermost). Сейчас модели данных ещё нет:
`src/core/types.ts` (`Job`) без `tenantId`, `jobStore` на глобальном `randomUUID`,
`grep tenant` по репозиторию пуст — самый дешёвый момент.

**Ловушка «декоративного `tenant_id`».** Константный `DEFAULT_TENANT` — это
single-tenant с декоративной колонкой, НЕ tenant-aware: при N=1 глобальная и
scoped-уникальность неотличимы, и ничто не давит схему к scoped-ключам. Защита —
CI-тест, гоняющий миграции с **≥2 тенантами** (см. §9).

On-prem = вырожденный 1 тенант той же scoped-схемы, не отдельная ветка.

## 5. Развилка 2 — изоляция: HYBRID (silo сейчас, pooled заложен)

**Целевая архитектура — hybrid:**

- **silo** — изолированный контур на тенанта (своя БД/стек). **Дефолт** для целевого
  РФ-mid-market / regulated / on-prem.
- **pooled-RLS** — много тенантов в общей БД, изоляция строк через Row-Level Security
  (RLS). Первоклассный второй режим над **той же схемой**.
- **bridge** (схема-на-тенанта) — **отвергнут**: раздувание каталога в нижних сотнях
  без юридического выигрыша.
- Переключатель режима — **тир тенанта** (см. §12).

**Решение фаундера по реализации (2026-06-08): строим только silo сейчас.**
Pooled-режим заложен в фундамент, но не достраивается до появления массового
дешёвого SaaS-тарифа. Обоснование: dev-среда на сервере фаундера — уже silo; первые
продажи РФ mid-market — почти всегда свой контур; pooled-экономия не нужна на
десятках тенантов.

**Критический инвариант (НЕ отложен): RLS-аппарат активен ВЕЗДЕ, включая silo с
N=1.** Иначе возникают две модели изоляции, которые расходятся — это сам по себе
аудит-риск 152-ФЗ. Один код-путь изоляции строк: в silo он охраняет границу одного
тенанта, в pooled — многих. См. §9.

**Почему silo — дефолт (по безопасности и GTM, не по закону):**

- Side-channel (CVE-2025-8713 — утечка через статистику планировщика),
  noisy-neighbor, context-bleed под PgBouncer transaction-pooling — это
  **структурные** дыры общего пула, которые дисциплина кода закрыть **не может**.
  Silo стирает весь класс физически (нет общего пула).
- Служба ИБ РФ-клиента покупает **контур**, а не политику строк в общей БД. Один
  cross-tenant-инцидент = смерть GTM на этом рынке.

(Закон silo НЕ требует — см. §8. Дефолт обоснован безопасностью + продаваемостью.)

## 6. Развилка 3 — Identity (Keycloak): симметрично изоляции

- **silo-контур → dedicated realm.** `iss` (realm) сам однозначно идентифицирует
  тенанта — cross-tenant токен физически не приходит в чужую ячейку. Полное
  realm-management delegation из коробки. Нативный IdP-brokering к корпоративному
  AD/LDAP клиента (РФ mid-market 150–300 почти всегда с AD) без
  email-routing-эвристик. **Это режим, который строим сейчас.**
- **pooled-ячейка → shared realm + Keycloak Organizations** (GA 26.x): per-org
  IdP-brokering по email-домену, масштаб до тысяч. Заложено, отложено вместе с
  pooled.
- В silo shared-realm вырождается в единственный realm — модели сходятся, код не
  раздваивается.
- **Tenant self-service RBAC живёт в TS-ЯДРЕ в обоих режимах** (Keycloak
  Organizations delegation незрел — issue #42781). Keycloak держим строго как
  auth + федерацию.
- **Обязательно day-1:** ядро валидирует `iss` / `aud` / `tenant-claim` на **каждом**
  запросе, не только подпись JWT — defense-in-depth даже в silo.

---

## 7. Развилка 4 — кодовая база: ОДИН АРТЕФАКТ

**Один образ, один source, без форка SaaS/on-prem.** Единогласно: обе камеры
дебатов, все три судьи, все 5 изученных dual-delivery вендоров.

- Режим развёртывания (silo-cell | pooled-cell), число тенантов, realm-стратегия =
  **конфигурация + реестр ячеек + обёртка** (`docker-compose` для silo/on-prem, Helm
  для будущего pooled SaaS), **НЕ ветка `src/`**.
- RLS-аппарат активен в обоих режимах, включая silo с N=1 (**path-identity**: один
  код-путь миграций и изоляции → один аудит-нарратив для 152-ФЗ, нулевой дрейф).
- SaaS-only фичи (billing / quota / AI-тарификация) — feature-флаги / закрытые модули
  поверх образа (по образцу Sentry FSL), не форк.

Форк удвоил бы поверхность миграций, тестов изоляции и 152-ФЗ-аудита для маленькой
команды — прямой убийца экономики dual-delivery.

## 8. 152-ФЗ / GDPR

> Confidence — MEDIUM (web-sourced). **Подтвердить с юристом** перед обещанием
> регулируемому покупателю (см. §12).

**Резидентность (жёсткое требование 152-ФЗ, ст. 18 ч. 5; ред. с 01.07.2025 /
ФЗ-23):** первичная запись/систематизация/хранение ПДн граждан РФ — через БД
физически в РФ. Деплой на сервер фаундера в РФ этому соответствует. Штрафы за
нарушение локализации — до 6 млн ₽ (первично) / 18 млн ₽ (повторно).

**Ключевое разделение: закон требует РЕЗИДЕНТНОСТИ, а НЕ изоляции-на-тенанта.** Для
целевого mid-market (данные сотрудников/клиентов, не спецкатегории, <100k субъектов,
угрозы 3-го типа → УЗ-3/УЗ-4 по ПП-1119 + приказ ФСТЭК №21) pooled + `tenant_id` +
RLS на аттестованной РФ-инфраструктуре **законен**; физического разделения
оборудования закон не вынуждает (логическое сегментирование допустимо). GDPR Art. 32
(risk-based) — логическая изоляция тоже допустима при наличии контролей.

**Значит silo — выбор по безопасности/GTM, а не по закону.** На silo комплаенс
закрыт с запасом.

**Триггеры ОБЯЗАТЕЛЬНОГО silo** (даже если когда-то появится pooled): спецкатегории
ПДн (медицина → УЗ-1/УЗ-2), >100k субъектов, ГИС/госзаказ (обязательная аттестация
по приказу ФСТЭК №17), enterprise-контракт.

**Как решение закрывает комплаенс:**

- cross-tenant leak (тяжелейший инцидент: ст. 13.11 КоАП + GDPR Art. 33) структурно
  застрахован scoped-уникальностью day-1 — встроен в БД, не в дисциплину.
- RLS везде → одна модель изоляции → один аудит-нарратив, нет дрейфа.
- Один артефакт → аудит-поверхность не удваивается.
- Аудит-лог сам tenant-scoped, между тенантами не протекает (day-1 инвариант).

## 9. Обязательные day-1 инженерные гарды (несущие, блокирующие)

Не «потом», а условие корректности с первой миграции:

1. Приложение коннектится к Postgres **non-owner / non-superuser / non-BYPASSRLS**
   ролью; на каждой tenant-таблице — `FORCE ROW LEVEL SECURITY` + политика
   **default-DENY**.
2. Tenant-контекст — **только** через `SET LOCAL` / `set_config(..., true)` в явной
   транзакции (иначе PgBouncer transaction-pooling протекает между запросами).
3. `tenant_id` — **ведущая колонка** всех составных индексов и FK.
4. Блокирующий **CI-тест на cross-tenant-утечку** от РЕАЛЬНОЙ app-роли (не
   привилегированной).
5. Блокирующий **CI-тест миграций с ≥2 тенантами** — иначе scoped-ключ молча
   выродится в глобальный при N=1.
6. **Аудит-лог сам tenant-scoped** и не протекает между тенантами.
7. **Fail-closed tenant-context** в async / таймерных / фоновых исполнителях ядра и
   во Flowable external-worker — при отсутствии tenant-контекста операция падает, а
   не выполняется глобально.

## 10. Минимальный control-plane для silo-флота

Десятки изолированных контуров создают риск **дрейфа флота** (тенант на старой
версии, не идущий бэкап — тихо до инцидента). Обязательно **с первого десятка**
silo-тенантов, не «когда дорастём»:

- **Реестр ячеек** — машинно-читаемый список тенантов: тир, режим, версия, эндпоинт,
  статус.
- **CI-матрица версий миграций** — гарантия, что миграции применимы по всему флоту.
- **Централизованный мониторинг** бэкапов и миграций по всем контурам.

## 11. Приоритет реализации

Порядок (решение фаундера 2026-06-08):

1. **Сейчас, бесплатно:** scoped-модель данных (`tenant_id`, `(tenant_id, id)`) +
   RLS-аппарат-везде + day-1 гарды (§9).
2. **Первая форма поставки:** silo-ячейка через `docker-compose` (она же — dev-среда
   фаундера и первые продажи) + минимальный control-plane (§10).
3. **Отложено (заложено в фундамент):** pooled-режим, shared realm + Organizations,
   billing/quota, провижининг pooled-ячеек — строим, когда/если появится массовый
   дешёвый SaaS-тариф.

## 12. Открытые вопросы и точки решения

- **152-ФЗ — юридическая валидация** (action item): подтвердить с юристом, что
  связывающее требование = резидентность РФ + контроль доступа + аудит (а не
  БД-на-тенанта), перед обещанием pooled-RLS регулируемому покупателю.
- **Точное определение триггера тира:** какие атрибуты тенанта (спецкатегории ПДн /
  >100k субъектов / ГИС / enterprise / собственный AD) переключают режим; где
  хранится тир (реестр ячеек) — формализовать как машинно-читаемое поле.
- **Миграция `jobStore`:** при переходе `Map<string, Job>` → Postgres — составной
  ключ `(tenantId, id)`; как 7 unscoped-методов
  (`getById` / `listByTopic` / `listByState` / `listByTopicAndState` / `fetchAndLock`
  / `complete` / `fail`) несут `tenant_id`; точное место RLS-политики.
- **Tenant onboarding-контракт:** провижининг silo-ячейки (`docker-compose`); для
  будущего Flowable multi-schema — предрегистрация в `TenantInfoHolder`
  (двухшаговая координация).
- **Пропагация tenant-контекста** в async/фоновых/external-worker — где fail-closed
  гард (см. §9, п. 7).

## 13. Эволюция 2027+ (отложено по консенсусу)

При росте до **тысяч** тенантов: становится ли «pooled-внутри-ячейки» (модель зрелых
cell-вендоров) дефолтом, вытесняя silo? Решение другого масштаба, с control-plane на
руках — преждевременно принимать сейчас на десятках тенантов. Не блокирует
сегодняшнее решение; зафиксировано как точка пересмотра.
