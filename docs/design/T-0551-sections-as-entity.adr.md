# ADR · T-0551 — Разделы как первоклассная сущность (ELMA-папки)

**Phase:** DESIGN · **Status:** ready · **Date:** 2026-06-30
**Task:** T-0551 [E-NAV-IA] (родитель T-0537)
**Product decision:** `docs/product-decisions.md` · **PD-24** (founder-approved 2026-06-30)
**Supersedes:** `docs/design/T-0540-dynamic-sections.design.md` §2.1 + §3 — РЕВЕРС решения «раздел = атрибут-строка». T-0540 (динамическая группировка из `application.section TEXT`) уже в продукте; эта задача поднимает раздел до сущности.
**Foundation (НЕ противоречит, дорабатывает):** `migrations/003_application.sql` (таблица `choros.application`); T-0540 миграция `section TEXT NULL`; `web/src/app-shell/shell.jsx` (`groupAppsBySection`); `web/src/app-shell/nav-sections.js`; `web/src/screens/screen-apps.jsx` (поповер строки «Изменить раздел», модалка `SetSectionModal`); `src/http/applications.ts` (`PATCH /api/applications/:id {section}`). Tenant-изоляция — по инварианту T-0013 (каждая tenant-таблица: `tenant_id` ведущий, RLS FORCE, default-DENY).
**Runtime target:** добавляет таблицу + FK → миграция против container/dev PG. Дизайн не блокируется зависимостью.

## 1. Контекст и проблема

T-0540 ввёл разделы как **свободный текст** `application.section` и сознательно отклонил
отдельную таблицу (§2.1): «раздел не имеет собственного жизненного цикла вне приложений…
свободный текст — стандартный паттерн тегирования». На практике это даёт дыры, вскрытые
приёмкой 2026-06-30:

- **нет устойчивой идентичности** — переименование = `UPDATE … WHERE section='старое'`
  по всем приложениям; опечатка плодит раздел-призрак;
- **нет порядка** — сайдбар сортируется по алфавиту, бизнес-важность не выразить;
- **нет управления** — раздел нельзя «создать», «удалить», переупорядочить как объект;
  «как добавить в раздел / как создать раздел» из UI неочевидно (свободный ввод);
- **магическая свалка** — пустой `section` → раздел «Другое» (звучит как ошибка, а не
  как осознанное «без раздела»).

**Лицо продукта — ELMA** (`docs/design/`-доктрина data-ownership). В ELMA365 разделы —
первоклассные папки левого меню: создаёшь, именуешь, кладёшь приложения, сортируешь,
позже — доступ. Свободный тег этому «лицу» не соответствует.

## 2. Решение (load-bearing)

**Раздел — управляемая сущность рабочего пространства (папка), а не атрибут приложения.**

Новая tenant-таблица `choros.section`:

| колонка       | тип            | примечание |
|---------------|----------------|------------|
| `tenant_id`   | uuid NOT NULL  | ведущий столбец PK/индексов/FK (инвариант T-0013); RLS FORCE |
| `id`          | uuid NOT NULL  | PK `(tenant_id, id)` |
| `name`        | text NOT NULL  | уникальность scoped: `UNIQUE (tenant_id, name)` |
| `sort_order`  | integer NOT NULL DEFAULT 0 | порядок в нав; ties → `name` |
| `created_at`/`updated_at` | bigint (ms) | как в `application` |

`application.section_id uuid NULL REFERENCES section(tenant_id, id)` (составной FK с
`tenant_id`). **`section_id IS NULL` → бакет «Без раздела»** (переименовать «Другое»;
это валидное состояние, не fallback-аварийный).

**Жизненный цикл (важно — отличие от тега):**
- раздел существует **без приложений** (пустой раздел рендерится в управлении, но в нав
  РАБОТА — только если в нём есть видимые приложения, см. §2.3);
- **DELETE раздела — мягкий**: `UPDATE application SET section_id=NULL WHERE section_id=$1`
  затем `DELETE FROM section`. Приложения НЕ удаляются (ответ на «как удалить раздел»).

### 2.1 API

| метод | путь | поведение |
|-------|------|-----------|
| `GET`    | `/api/sections` | разделы тенанта, отсортированы `sort_order, name` |
| `POST`   | `/api/sections {name}` | 201; 409 при дубле имени в тенанте |
| `PATCH`  | `/api/sections/:id {name?, sort_order?}` | переименование/порядок; идентичность сохраняется |
| `DELETE` | `/api/sections/:id` | мягкий: приложения → `section_id=NULL`, затем удаление раздела |
| `PATCH`  | `/api/applications/:id {section_id}` | **заменяет** `{section}` (строку) из T-0540 |

Все — `withAuth`, tenant-scoped, RLS. `section_id` валидируется как принадлежащий тому же
тенанту (404, если чужой/несуществующий).

### 2.2 UI (зона КОНСТРУКТОР + нав РАБОТА)

- **Управление разделами**: список + создать / переименовать-инлайн / drag-упорядочить /
  удалить (с подтверждением «N приложений переедут в “Без раздела”»).
- **Назначение у приложения**: `SetSectionModal` («Изменить раздел») → **выбор из списка
  разделов** + «＋ Создать новый раздел» inline. Свободный текстовый ввод убирается →
  нет опечаток-призраков.
- **Нав-рендеринг**: `groupAppsBySection` (shell.jsx / nav-sections.js) — со строки на
  сущность: группировать по `section_id`, заголовок = `section.name`, порядок =
  `section.sort_order`; «Без раздела» — последним.

### 2.3 Видимость (связь T-0539, без регресса)

Каждое приложение в нав по-прежнему гейтится ресурс-грантом на read (T-0539). Раздел без
ни одного видимого приложения в зоне РАБОТА не рендерится (как в T-0540). В экране
**управления** разделами видны все разделы тенанта (это конструктор, не операторская нав).

## 3. Миграция (additive-safe + backfill)

1. `CREATE TABLE choros.section …` (+ RLS FORCE, default-DENY, политика по
   `current_setting('choros.tenant_id')` — паттерн T-0013).
2. `ALTER TABLE choros.application ADD COLUMN section_id uuid NULL` + составной FK.
3. **Idempotent backfill** (generic, для всех тенантов):
   ```sql
   INSERT INTO choros.section (tenant_id, id, name, sort_order, created_at, updated_at)
   SELECT DISTINCT a.tenant_id, gen_random_uuid(), a.section, 0, <now>, <now>
   FROM choros.application a
   WHERE a.section IS NOT NULL
     AND NOT EXISTS (SELECT 1 FROM choros.section s
                     WHERE s.tenant_id=a.tenant_id AND s.name=a.section);
   UPDATE choros.application a SET section_id = s.id
   FROM choros.section s
   WHERE s.tenant_id=a.tenant_id AND s.name=a.section AND a.section_id IS NULL;
   ```
   На текущем dev — выполнится вхолостую (везде `section IS NULL`), но защищает контуры с
   данными. Чистый переход без потери группировок.
4. `application.section` (строка) — пометить **deprecated** в комментарии; снести
   отдельной миграцией следующей версии (а не в этой — обратимость).
5. Doc-follow-up из T-0540 (комментарий «E16 → E-NAV-IA» в nav-config.js) — если ещё не
   закрыт, закрыть здесь.

## 4. Отклонённые альтернативы

- **Оставить тег-строку (статус-кво T-0540).** Отклонено решением фаундера PD-24: не
  даёт идентичности/порядка/управления и расходится с ELMA-лицом.
- **Курируемый тег (строка + combobox + bulk-rename).** Дешевле, но переименование
  всё ещё трогает каждое приложение, порядок негде хранить, и миграция «строка→сущность»
  позже (когда накопятся данные) болезненнее, чем сейчас. Отклонено.
- **Иконки / доступ / вложенность в v1.** Отложено (задел): сущность это позволяет
  включить аддитивно, но MVP — соло-экономика, минимум поверхностей.

## 5. Fitness / приёмка

- e2e на dev: создать раздел → назначить приложение → раздел и приложение видны в нав
  РАБОТА в заданном порядке; переименовать раздел → имя меняется во всех местах без
  правки приложений; удалить раздел → приложения уезжают в «Без раздела», не пропадают.
- migration-check: backfill идемпотентен (повторный прогон — ноль изменений); RLS на
  `section` (кросс-тенант SELECT/INSERT — deny).
- API-check: `section_id` чужого тенанта → 404; дубль имени → 409.

## 6. Вне scope (явно)

Иконки/цвет раздела; доступ «кто видит раздел» (зона «Исполнители и доступ»); вложенные
разделы; перенос процессов/инбокса под разделы (рантайм-привязка — E16/T-0349, не здесь).
