## 1. Decision (суть)

**Симуляция — НЕ отдельная подсистема и НЕ движок: это `simulation_run` — конечный
автомат прогона над бандлом в draft-тире**, потребляющий уже принятые механизмы
(линтер T-0027, PDP T-0021, эффект-стабы поверх T-0034, бюджет T-0023, аудит T-0016)
и добавляющий ровно три вещи, которых в ядре ещё нет: **(1) эфемерного draft-субъекта
(«статиста»)**, который играет RoleRef без записи в живую решётку; **(2) draft-аффинный
перехват эффектов** (структурное производное T-0034, не флажок); **(3) A/B-обвязку
сценарного прогона** (тот же сценарный набор × вектор `(process_variant, model)`).
Ноль новых authority-store, ноль второго резолвера, ноль второго аудит-лога, ноль
параллельной решётки (NF-5).

**Три режима — три ИСПОЛНИТЕЛЯ одного `simulation_run` по нарастающей цене**, а не три
подсистемы:

| Режим | Исполнитель | Цена | Что доказывает | На чём построен |
|---|---|---|---|---|
| **1 — расчёт маршрутов** | чистая функция `computeRoutes(bundle, cases)` БЕЗ движка | мгновенно, ноль I/O | маршруты/адресаты/линт (~90% ошибок проектирования) | **расширение T-0027** (консумент `lintBpmn`) |
| **2 — автопрогон** | реальные draft-инстансы (Flowable), люди = **статисты** | токены LLM + движок | привязка форм↔данные, реальные переходы статусов, **реальный резолв прав** | draft-тир §8 + Flowable (T-0058) + PDP (T-0021) |
| **3 — репетиция людьми** | те же draft-инстансы, задачи живым людям в боевой инбокс с маркером `test:true` | время людей | понятность формы в боевом UI | draft-инстансы + инбокс |

**Граница «прошла» — структурно двухчастная (FR-15):** `verdict.deterministic`
(машинный pass/fail, **допустимый авто-гейт**: нет тупиков, маршруты ожидаемы, права
резолвятся, статусы переходят, эффекты застаблены) и `verdict.advisory` (LLM/человеческий
**сигнал, НЕ гейт промоута**). Промоут остаётся human-gate (extensibility §4/§8) —
симуляция его НЕ автоматизирует.

**Red-lines выражены как ОТНЯТЫЕ ВОЗМОЖНОСТИ, структурно (§7):** из draft физически
нельзя произвести внешний эффект (перехват — производное draft-тира поверх T-0034, не
настройка); статист физически не может оказаться принципалом в published-решётке (он
не `employee`, не имеет grant-строки, не имеет assignment). Подделать можно только
red-line-операцией под human/dual-control (T-0044) — fitness FF-3/FF-4 это машинно
сторожат.

**Соразмерность (рубрика ось 5):** day-1 ядро = режим 1 (чистая функция, ноль инфры);
режимы 2/3 — MVP-late (после T-0058 Flowable live). `simulation_run` — проекция/обвязка
поверх принятых сущностей, не новая authority-таблица (§9).

## 2. Где живёт симуляция: `simulation_run` как обвязка, не движок (FR-1, AC-1)

Симуляция — **draft-тир той же системы** (extensibility §8), НЕ параллельная система
(явное утверждение AC-1). Сущность прогона:

```
simulation_run {
  run_id            : uuid
  implementation_id : uuid              // FK → implementation (T-0129 §2)
  bundle_id         : uuid              // предмет прогона (T-0129 §5); tier ДОЛЖЕН быть "draft"
  bundle_version    : int               // фиксируется на старте прогона (сопоставимость A/B)
  mode              : "routes" | "autorun" | "rehearsal"   // режим 1/2/3
  variant           : RunVariant        // (process_variant, model) — параметр A/B (§6)
  scenarios         : ScenarioRef[]      // набор сценариев (§5.2)
  budget_cap        : BudgetCap          // лимит прогона (§8, поверх T-0023)
  status            : "running" | "passed_det" | "failed_det" | "halted_budget" | "aborted"
  verdict           : RunVerdict         // двухчастный (§ FR-15 / §5.4)
  test_marker       : true               // КОНСТАНТА: всё, что пишет прогон, помечено test
}
```

**Инвариант размещения (AC-1, AC-14):** `simulation_run.bundle.tier === "draft"`
проверяется на старте; прогон, целящийся в `published`-бандл, отвергается fail-closed
ДО любого исполнения. Это первая из гарантий шва T-0129 §11 («`bundle.tier` детерминированно
отличим»). Оргструктура при прогоне — **одна, живая, read-only** (FR-1): прогон её
читает (резолвит RoleRef в адресатов), но НЕ создаёт узлов и НЕ копирует оргдерево.
`simulation_run` НЕ дублирует жизненный цикл инстанса процесса (T-0068) — это мета-уровень
«как бандл проверялся», ортогональный «как бежит инстанс».

`simulation_run.phase`-связь: прогон — наполнение фазы `simulation` петли T-0129 (§2 там);
T-0130 владеет внутренней механикой прогона, T-0129 — переходами фаз.

## 3. Режим 1 — статический расчёт маршрутов: КОНСУМЕНТ T-0027, не расширение линтера (FR-4, FR-5, FR-6)

**Развилка спеки «расширение T-0027 или потребитель его контракта?» — РЕШЕНА:
потребитель + отдельная чистая функция расчёта маршрутов.** Линтер T-0027 (`lintBpmn`)
проверяет *синтаксис/handle-дисциплину BPMN* и остаётся **единственным линтером**
(вызывается как есть). Расчёт маршрутов — *семантическое протаскивание атрибутов через
шлюзы/DMN* — это НЕ задача `lintBpmn` и НЕ дописывается внутрь него (это сломало бы
freeze T-0027 и смешало бы две ответственности). Поэтому режим 1 = **новая чистая
функция `computeRoutes`**, которая (а) сначала зовёт `lintBpmn(bundle.process)` как
fail-closed предусловие, (б) затем детерминированно вычисляет маршруты.

```
computeRoutes(bundle: Bundle, cases: SyntheticCase[]): RouteResult

1. lint = lintBpmn(bundle.components.process)          // T-0027, как есть
   if (!lint.ok) return { ok: false, lint, routes: [] } // fail-closed: не считаем по сломанному BPMN
2. для каждого case ∈ cases:
     протащить case.attributes через шлюзы BPMN + DMN-таблицы бандла  // чистое вычисление
     для каждого user/serviceTask на маршруте: резолвить RoleRef → адресат в живой оргструктуре
   → RouteRow { caseId, path: stepId[], assignees: { stepId → RoleRef → resolvedActor[] } }
3. NOT-PROVEN: { forms_bound_to_data, statuses_actually_transition, rights_resolve_at_runtime, form_human_understandable }
   → ВСЕГДА присутствует в выходе (FR-6, AC-6)
```

**`computeRoutes` — чистая функция без I/O (NF-2):** равные `(bundle, cases)` → равный
выход; пригодна к запуску при каждой правке черновика без развёртывания движка. Адресат
резолвится против read-only оргструктуры через **тот же ancestry/role-механизм T-0018/T-0022**
(не вторая адресная логика). DMN-вычисление — детерминированный консумент DMN-таблиц
бандла; режим 1 НЕ запускает движок (NF-2).

**Выход доказывает / НЕ доказывает (FR-6, AC-6) — обязательное поле `not_proven`:**
доказывает корректность DMN/шлюзов/адресации (~90% ошибок). НЕ доказывает: формы↔данные,
реальные переходы статусов, рантайм-резолв прав, понятность формы. Отсутствие `not_proven`
у результата режима — **брак** (FF-2).

## 4. Режим 2 — автопрогон: статист как эфемерный draft-субъект (FR-7, FR-8, FR-9)

### 4.1 Реальные draft-инстансы на синтетике (FR-7, AC-7)

Режим 2 запускает **реальные инстансы процесса в draft-тире** (Flowable substrate,
SEAM-3) на синтетических данных. Человеческие шаги (`userTask`) исполняют **агенты-статисты
по сценарию**. Выход — трасса исполнения: переходы статусов, **резолюции прав (через
PDP T-0021)**, заполнения форм, циклы доработки/сброс виз. Доказывает то, чего не видит
режим 1: формы привязаны к данным; статусы реально переходят; **права реально резолвятся**
— вскрывает «у роли нет гранта на переход» ДО живого человека. НЕ доказывает: понятность
формы человеку (режим 3); реальные внешние интеграции (застаблены — §7).

### 4.2 Статист — эфемерный draft-субъект, НЕ сотрудник (FR-9, NF-3, AC-8)

**Развилка спеки «КАК статист исполняет шаг без прав в решётке» — РЕШЕНА:
эфемерный `ResolveSubject` с draft-аффинным role-overlay, исполняющий шаг через тот же
PDP T-0021, БЕЗ записи в published-решётку.**

Ключ — `ResolveSubject` в T-0021 **identity-only** (нет human/agent-флага; §4.2 T-0021).
PDP резолвит права субъекта через `GrantSource.getGrants(subject, now)`. Статист — это
**эфемерный субъект прогона** с особым `GrantSource`-оверлеем, **scoped к `run_id` и
draft-тиру**:

```
StatistSubject  (эфемерный, живёт ТОЛЬКО в контексте simulation_run)
  kind        : "statist"                 // отличим от employee/agent
  run_id      : uuid                      // привязка к прогону; вне него субъект не существует
  plays_role  : RoleRef                   // РОЛЬ, которую играет (напр. "Главбух"), ССЫЛКА — не assignment
  model       : ModelRef                  // LLM-модель статиста (параметр A/B, §6)

// Резолв прав статиста: draft-аффинный overlay поверх роли, БЕЗ published-строк
DraftStatistGrantSource.getGrants(subject, now):
  if subject.kind !== "statist" → делегировать обычному GrantSource (не трогаем не-статистов)
  иначе:
    grants = гранты РОЛИ subject.plays_role, спроецированные с tier-меткой "draft"
    // проекция — ЧТЕНИЕ грантов роли из решётки T-0018, НЕ создание assignment к субъекту
    каждый грант помечен draft-аффинным (эффективен только над bundle.tier="draft")
    return grants
```

**Почему это НЕ нарушает решётку (AC-8):** статист никогда не получает строку в
`employee`, никогда не получает строку в `grant`/published-решётке, никогда не получает
`role_assignment` (T-0022). Он *читает* гранты роли, которую играет, и исполняет шаг через
**тот же `resolveFor`** (T-0021), что и настоящий принципал — поэтому «нет гранта на
переход» вскрывается ТОЧНО так, как в проде (это и есть ценность режима 2). Разница —
источник грантов инъектирован (`DraftStatistGrantSource`-overlay) и **scoped к draft +
run_id**; в `published`-тире overlay не активируется (статист физически не может
резолвиться в проде).

**Жизненный цикл (NF-3, AC-8):** статист создаётся для прогона, существует только в
контексте `run_id`, **не переживает завершение прогона как принципал**. По завершении/
аборту прогона — gone (никаких persisted-строк-принципала). Запрещено и сторожится
(FF-3): статист в справочнике людей/пользователей; статист с grant-строкой в published;
статист с role-assignment в живой решётке; статист, переживший прогон.

**Соотношение с config-агентом/внедренцем (design-owned):** статист — НЕ агент-сотрудник
(в отличие от внедренца T-0129 §3, который — настоящий `employee kind='agent'`). Статист —
**машинерия прогона**, эфемерный субъект. Это прямое следствие frozen-seam T-0129 §8.2
(«статист *играет* RoleRef, не создаёт `employee`»); T-0130 даёт механизм (overlay), не
переоткрывает инвариант.

### 4.3 LLM-статист: модель, бюджет, fail-closed стоп (FR-9, FR-14)

Агентный шаг статиста жжёт токены. `StatistSubject.model` — параметр прогона (§6).
Стоимость каждого LLM-вызова статиста списывается в `spend_ledger` (T-0023) под
`budget_cap` прогона; при достижении лимита прогон **останавливается fail-closed**
(`status = "halted_budget"`, §8) — не «молча жжёт».

## 5. Режим 3 — репетиция людьми + сценарии + двухчастный вердикт (FR-10, FR-11, FR-15)

### 5.1 Тест-задачи в боевом инбоксе с маркером (FR-10, FR-11, AC-9)

**Развилка спеки «механика маркера/фильтрации/неучёта в статистике» — РЕШЕНА:
маркер — структурное свойство ИСТОЧНИКА задачи (draft-инстанс), а не редактируемый флаг
на самой задаче.**

Режим 3 направляет задачи draft-инстанса **настоящим сотрудникам в их обычный инбокс**
(не отдельный кабинет — FR-10), помеченные как тест. Маркер:

```
inbox задачи строится из источника инстанса; task.is_test := (instance.bundle.tier === "draft")
```

- **Маркер выводится, не хранится-редактируемо:** `is_test` — производное от `tier`
  инстанса-источника. Снять маркер у тестовой задачи нельзя, не сменив тир инстанса (а
  тир инстанса в draft неизменяем — это draft-инстанс). Это закрывает «спутать с боевой»:
  боевая задача физически рождается из `published`-инстанса, тестовая — из `draft`.
- **Фильтрация UI:** инбокс показывает тестовые задачи с неотличимым визуальным маркером
  «тест» в боевом интерфейсе (UX-деталь — отдельная задача, §11; здесь — инвариант).
- **Неучёт в статистике/комплаенсе:** действия над тест-задачами пишутся в единый аудит
  с `test:true` (§ FR-3) и **исключаются из комплаенс-экспорта и боевых метрик** — тем же
  фильтром, что аудит-маркер (одна точка истины, не второй учёт).
- **Ноль боевых эффектов:** тест-задача исполняется в draft-инстансе → §7 (эффекты
  застаблены) применяется автоматически; режим 3 НЕ порождает боевых записей/эффектов
  (FR-11).

Доказывает: понятность форм/интерфейса реальным людям; жизнеспособность в руках людей.
НЕ доказывает: полноту маршрутно-правовой проверки (её сделали режимы 1–2; режим 3 = 2–3
кейса руками) (FR-11, AC-6).

### 5.2 Сценарий — общий вход режимов (FR-7, FR-12)

```
Scenario {
  scenario_id : uuid
  cases       : SyntheticCase[]           // атрибуты синтетических кейсов (вход режима 1)
  decisions   : StepDecision[]            // последовательность решений статистов (вход режима 2)
                                          // "Главбух: согласовать; на 3-м круге вернуть с замечанием"
  expected    : ExpectedOutcome           // ожидаемые маршруты/исходы — для детерм. вердикта
}
SyntheticCase { caseId, attributes: Record<string, JsonValue> }   // НЕ из реальных справочников (out-of-scope спека §4)
```

### 5.3 Аудит прогона помечен и неснимаемо (FR-3, AC-3)

Все действия прогона (расчёт, инстансы, шаги статистов, человеческие тест-действия,
стаб-эффекты) пишутся в **единый ledger** (T-0016/T-0019) через `appendAuditEvent` с
`test:true`. Признак **не снимаем постфактум** (append-only ledger + флаг в событии —
переклассификация невозможна без записи нового события; исходное `test:true`-событие
неизменно). Исключение из комплаенс-экспорта — фильтр по флагу, не второй лог (NF-5).

### 5.4 Двухчастный вердикт (FR-15, AC-13)

```
RunVerdict {
  deterministic : {                       // МАШИННЫЙ pass/fail — допустимый авто-гейт
    no_deadlocks        : boolean         // из lint (режим 1)
    routes_match        : boolean         // computeRoutes == scenario.expected
    rights_resolve      : boolean         // PDP не вернул deny на легитимных переходах (режим 2)
    statuses_transition : boolean         // движок реально перевёл статусы (режим 2)
    effects_stubbed     : boolean         // 0 реальных внешних эффектов, N стаб-записей (§7)
    pass                : boolean          // AND всех выше
  }
  advisory : {                            // СИГНАЛ — НЕ гейт промоута
    agent_answer_quality : Signal[]       // LLM-оценка качества ответов статистов (режим 2)
    form_understandability : Signal[]     // обратная связь людей (режим 3)
  }
}
```

**Инвариант (AC-13):** `deterministic.pass` может быть гейтом (машинно); `advisory`
гейтом промоута быть НЕ может. Промоут draft→published — **human-gate** (extensibility
§4/§8): человек подтверждает проверенные сценарии (T-0129 §10.2), симуляция его НЕ
автоматизирует. Это сторожится FF-5 (баним «advisory автогейтит промоут»).

## 6. A/B LLM на сценариях (FR-12, NF-4, AC-10)

A/B — **тот же сценарный набор × вектор вариантов**. Вариант прогона:

```
RunVariant { process_variant : BundleVersionRef    // вариант процесса (X vs Y)
             model           : ModelRef }           // LLM-модель агентных шагов/статистов (X vs Y)

abComparison(scenarios: Scenario[], variants: RunVariant[]):
  для каждого variant ∈ variants:
    run = simulate(scenarios, variant)              // ИДЕНТИЧНЫЙ scenarios набор (NF-4)
  → ABResult {
      per_scenario : { scenarioId → { [variantKey]: { outcome, det_verdict, advisory_quality } } }  // поэлементно X vs Y
      cost         : { [variantKey]: { tokens, money } }   // агрегат из spend_ledger (T-0023)
    }
```

**`model` — параметр прогона, НЕ свойство бандла (frozen seam T-0129 §11/§8.3):** агентные
шаги бандла несут параметризуемое `model`-поле; A/B **варьирует `model`, не меняя бандл**.
Это уже гарантировано бандлом (T-0129 §11: «агентные шаги несут model-поле»). T-0130
*потребляет* эту гарантию — НЕ требует нового поля.

**NF-4 сопоставимость:** A/B обязан гонять **идентичный** `scenarios` + синтетику на
сравниваемых вариантах — иначе разница относилась бы к входу, не к варианту. Сторожится
FF-6 (детерминированный `scenarios`-хэш одинаков для всех вариантов одного `abComparison`).
Стоимость каждого варианта — агрегат `spend_ledger` (один источник цены, не отдельный
счётчик — §8).

## 7. Red-lines как ОТНЯТЫЕ ВОЗМОЖНОСТИ (структурно, §7) (FR-13, NF-1, AC-11, AC-14)

### 7.1 Перехват эффектов — производное T-0034, не флажок (FR-13, AC-11)

**Развилка «перехват эффектов структурный, не флажок» — РЕШЕНА: draft-аффинность
эффект-грантов.** В draft-тире `verifyEffectGrants` (T-0034) **возвращает deny по
построению** — эффект-грант не эффективен над `tier="draft"`. Механически это **то же
самое draft-аффинное правило**, что и для грантов статиста (§4.2): грант эффективен
только над тиром, которому он аффинен; published-эффект-грант не аффинен draft-инстансу.

Поток эффект-вызова в draft (например `sendTask` «отправить письмо»):
```
draft-инстанс достигает шага с EffectDeclaration
 → PDP/gateway зовёт verifyEffectGrants(declarations, grants, now, ...)
 → в draft-тире эффект-гранты НЕ эффективны → result.ok = false  (deny by construction)
 → вместо реального коннектора вызывается СТАБ:
     stub записывает "отправил бы письмо X" в test-аудит (test:true)
     реального вызова НЕ происходит — 0 отправок
```

**Это отнятая возможность, не настройка (AC-14, NF-1):** из draft физически нельзя
произвести реальный внешний эффект, **независимо от наличия эффект-гранта у играемой
роли** (грант есть, но он не аффинен draft → не эффективен). Семантика fail-closed: при
любой неопределённости (неизвестный эффект, незастабленный коннектор) —
деньги/письма/вызовы НЕ уходят; прогон фиксирует попытку, не выполняет (FR-13). «Симуляция,
пославшая реальное письмо контрагенту, — катастрофа доверия» — это **запрещённое
состояние**.

**Тест red-line (AC-11):** draft-инстанс с шагом «отправить письмо» ПРИ НАЛИЧИИ
эффект-гранта у играемой роли → **0 реальных отправок, ≥1 запись стаба**. Сторожится FF-4.

### 7.2 Изоляция эффектов абсолютна и невыключаема (NF-1, AC-14)

Никакой режим симуляции не может произвести наблюдаемый снаружи эффект (внешний вызов,
боевая запись, комплаенс-строка). Изоляция — **свойство построения** (draft-аффинность +
стаб), НЕ настройка, которую можно выключить из draft. Нет API/флага «разрешить эффекты в
этом прогоне». Единственный путь к реальному эффекту — промоут в published (human-gate),
после которого это уже не симуляция.

### 7.3 Статисты структурно вне published-решётки (FR-9, AC-8)

См. §4.2. Статист — эфемерный draft-субъект; published-решётка для него структурно
недостижима (нет `employee`, нет grant-строки, нет assignment; overlay не активен над
published). Подделать = выдать red-line published-грант под human/dual-control (T-0044) —
сторожится FF-3.

## 8. Бюджет / лимит прогона — потребитель T-0023, fail-closed стоп (FR-14, AC-12)

**Развилка «точную привязку к T-0023 определит ADR» — РЕШЕНА: прогон — потребитель
существующей схемы T-0023, без нового учётчика.**

```
BudgetCap { instance_budget_id : uuid     // T-0023 instance_budget (ceiling, currency)
            agent_budget_id?   : uuid }    // T-0023 agent_budget статистов (опц.)

на КАЖДЫЙ LLM-вызов статиста / агентный шаг прогона:
  reservation (T-0023, idempotent tool_call_id) → spend_ledger append (T-0023)
  если two-ceiling AND-gate (T-0023 §1.3) исчерпан:
    прогон → status = "halted_budget"  (fail-closed: останавливается, не продолжает жечь)
```

Лимит — **параметр прогона**, опирается на `instance_budget`/`agent_budget`/`reservation`/
`spend_ledger` (T-0023) **как есть**: симуляция = потребитель reserve→finalize/release-цикла
(T-0023 §1.3), не новый бюджет-механизм (NF-5). A/B агрегирует стоимость по варианту из
**того же `spend_ledger`** (§6) — один источник цены. Fail-closed стоп при исчерпании —
FF-7. Замечание: рантайм-энфорсмент reserve/AND-gate — E5.9 (Stage-2, T-0023 §1.3); день-1
T-0130 фиксирует ПРИВЯЗКУ и инвариант стопа, исполнение наследует E5.9 (MVP-late, §11).

## 13. Fitness functions (исполнимые, с self-test) (§13)

> T-0130 — **design-only**; артефакт фазы — ADR (документ). Поэтому fitness — **doc-structure
> линтеры**: машинно проверяют, что ADR содержит именованные секции/утверждения/ссылки на
> основы и НЕ содержит запрещённых конструкций. **Каждый чек обязан УМЕТЬ падать**:
> поставляется с `--self-test`, прогоняющим проверку против намеренно-сломанной фикстуры
> и требующим, чтобы чек на ней покраснел (фикстура-нарушитель проходит ⇒ чек сломан ⇒
> сам падает). Это прямая реализация «чек обязан уметь падать». Поведенческие fitness
> (что реально делает код прогона) рождаются в build-задачах §11 (B-1..B-7) и наследуют
> уже-зелёный аппарат T-0027/T-0021/T-0034/T-0023/T-0018 — без дублирования.

| ID | Rule | ci_check |
|---|---|---|
