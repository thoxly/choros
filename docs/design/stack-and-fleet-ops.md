# ADR: Стек Choros и агентный Fleet-ops

Статус: **ratified** (фаундер, 2026-06-10)
Источник: multi-agent дебаты (4 стойки × 2 раунда, 3 судьи) + ответы фаундера на decision-gate.

---

## 1. Решение по стеку

**Node/TS-ядро + Flowable (embedded JVM) как движок процессов + один PostgreSQL на всё + Keycloak + Caddy. Redis — позже по триггеру. Kafka/Temporal — нет.**

| Слой | Выбор | Роль |
|---|---|---|
| Прикладное ядро | Node ≥20 + TS, plain `node:http`, zero-dep в доменной логике | API, инбокс (authoritative), RBAC, оргструктура, объектная модель |
| Движок процессов | **Flowable 7** (Apache 2.0), embedded JVM, чёрный ящик | Токены, BPMN-семантика (parallel/inclusive join, interrupting boundary, message correlation, event-subprocess), live-migration инстансов. Java не пишем — только external-task контракт |
| База данных | **PostgreSQL 16, один инстанс на контур**; схемы `ACT_*` (движок, Liquibase) + `choros_*` (ядро, наши миграции) | Стор + очередь (`FOR UPDATE SKIP LOCKED`) + прикладные таймеры (`due_at` + partial index) + outbox + аудит |
| Очередь работ | Postgres-таблица `job` — наследник `jobStore` (fetchAndLock/complete/fail/lease 1:1) | At-least-once, lease, экспоненциальный backoff (`available_at`), DLQ |
| Журнал | `event_log` append-only + monotonic offset-курсор (поллинг, не LISTEN/NOTIFY-как-шина) | Аудит 152-ФЗ и outbox — один субстрат; контракт = дешёвая миграция на брокер, если когда-нибудь понадобится |
| Кэш | in-process LRU → Redis при S2 (вторая app-нода) | RBAC-решения (versioned-key), оргструктура, дефиниции, инбокс-агрегаты |
| Identity | Keycloak, dedicated realm на тенанта | Auth не пишем; realm = граница тенанта |
| Шлюз | Caddy | TLS, reverse-proxy |
| Деплой | docker-compose, **silo-per-tenant** (ось B), модель данных multi-tenant-first + FORCE RLS day-1 (ось A) | Физическая изоляция; путь роста S0→S4 без переписывания |

### Пройденный decision-gate (ответы фаундера, 2026-06-10)

Условие: движок берём, только если процессы реально требуют богатый BPMN.

- Parallel/inclusive gateway с join — **да**
- Interrupting boundary timer — **да**
- Message correlation — **да**
- Event-subprocess / compensation — не определено (в Flowable есть бесплатно)
- Migration запущенных инстансов — **да, с развитием продукта** (заложиться сейчас)

→ **Вердикт: Flowable.** Граница ответственности: диспетчер задач/таймеров — наш (Postgres, доказано прототипом `jobStore`); продвижение токена в графе при событии — движка (годы инженерии, баги дороже всего).

### Отвергнуто

- **Temporal**: процессное состояние уезжает в persistence-схему без RLS (ломает 152-ФЗ-инвариант), убивает BPMN-дифференциатор, оверкилл на 1–2 порядка для silo.
- **Kafka/event-sourcing как ядро**: ни одной способности на целевой нагрузке, которой нет у Postgres + `event_log`. Взята только журнальная дисциплина.
- **Полностью свой движок**: токен-семантику и live-migration не воспроизводим за разумное время; после «да» на gate закрыт.

### Нагрузка и запас (обоснование «без Kafka не умрём»)

Целевая: 200–300 тенантов, ~25k активных пользователей, ~200k новых инстансов/день, ~0.6M живых инстансов, ~1.2M активных таймеров, пик записи — сотни tx/s на весь флот. При silo: **единицы rps и доли tx/s на контур** — запас 2–3 порядка. Буфер всплесков встроен: очередь `job` + `event_log`-курсор (семантика брокера без брокера). Триггер пересмотра: устойчивый ингест >тысяч событий/с в одну точку или нужда в multi-consumer replay.

### Путь масштабирования (триггер-метрики)

| Стадия | Setup | Триггер перехода |
|---|---|---|
| S0 (1 бокс) | compose: PG + Flowable + Core + Keycloak + Caddy, LRU-кэш | p95 API >300мс / CPU >70% sustained |
| S1 (1–2 маш.) | PG на свою машину (NVMe), PgBouncer, партиции истории | запись >150 tx/s sustained / timer-lag p95 >30с |
| S2 (2–4 маш.) | 2–3 Core-ноды + Redis + read-реплика | timer-lag p95 >60с / CPU движка >75% / таймеров >~2M |
| S3 (4+ маш.) | кластер Flowable-нод на общей БД | потолок записи primary (>500 tx/s, vacuum не успевает) |
| S4 (страховка) | cells: группы тенантов на своём PG+Flowable, маршрутизация по tenant_id | на целевой нагрузке не достигается |

### Открытые риски

1. **Блокирующий OSS-спайк Flowable до интеграции**: history-cleanup на наших объёмах + deadletter-управление в OSS-версии. Если Enterprise-only → Operaton (запасной, зрелость не доказана).
2. JVM как второй рантайм: timer-lag и GC — P1-метрики day-1; чинится агентным runbook (см. Fleet-ops).
3. `ACT_*` не накрыть RLS: в silo вырождено; **pooled заблокирован red-line** до доказанного механизма изоляции движка.
4. Eventual-consistency движок↔ядро навсегда (outbox, идемпотентность по event_id); инбокс строго консистентен в одной сессии ядра.

### Порядок работ

1. `job`/`inbox_task`: Map → Postgres, `available_at`, partial-индексы (убивает O(n)-скан, оживляет backoff).
2. `tenant_id` + FORCE RLS + non-BYPASSRLS-роль + CI-тест cross-tenant-утечки.
3. Двухфазный tenant-scoped timer-dispatcher (SECURITY DEFINER discovery-агрегат → per-tenant `SET LOCAL` execution).
4. OSS-спайк Flowable (единственный оставшийся gate).
5. Интеграция Flowable: deploy BPMN, external-task мост, outbox-поток, `choros_archive`.

## 2. Fleet-ops: агентное самообслуживание (требование фаундера, day-1)

Choros эксплуатируется без ops-команды: **диагностика, починка и обслуживание выполняются ИИ-агентами**; фаундеру летят конкретные задачи (в т.ч. упреждающие — «через ~3 недели кончится диск»), авто-исполнение на проде принято осознанно (T0–T1).

### Две плоскости (где что живёт)

**«Органы» — в продукте (этот репозиторий).** Каждый контур Choros рождается чинимым:
- машиночитаемый health-контракт (timer-lag, GC/heap, autovacuum-долг, диск+тренд, статус restore-drill);
- **каталог ops-операций** — идемпотентные, ограниченные, скриптованные действия (capability-not-text): `restart_engine`, `bump_heap(max)`, `run_vacuum`, `detach_old_partitions`, `rolling_upgrade`, `restore_drill`;
- локальный watchdog для T0.
DoD компонента: «готов» = «агент умеет его диагностировать и чинить через каталог». Органы едут и в on-prem-сборку.

**«Мозг» — fleet control-plane, отдельный контур на нашей стороне.** Часть продукта Choros-SaaS (не фабрики): агенты Sentinel (наблюдение/тренды) → Diagnost (контекст+диагноз) → Operator (действие из каталога по ярусу) → верификация по метрике-симптому; Forecaster материализует упреждающие T2-задачи фаундеру. Переиспользует механику конверта Demiurge: deadman, бюджет действий, freeze при регрессии после действия, founder-gate.

**Почему мозг НЕ внутри фабрики (Demiurge):** разделение кредов (у фабрики — права на код, у ops — на прод; смешивать нельзя) и независимость отказов (фабрика может лежать/обновляться — эксплуатация клиентов не зависит). Связь между плоскостями — только задачами: ops-мозг при «чинится кодом, не действием» создаёт задачу в фабрике; фабрика собирает фикс → dev → founder promote → ops-мозг раскатывает по флоту (canary → fleet).

### Ярусы автономии

| Ярус | Что | Аппрув |
|---|---|---|
| T0 | рестарт контейнера, vacuum, очистка кэша, ротация логов, restore-drill | авто, лог |
| T1 | bump heap в квоте, app-нода в compose, detach партиций | авто + отчёт |
| T2 | диск/сервер/деньги, major-upgrade флота, перенос контура | задача фаундеру |
| T3 | удаление данных, restore поверх живой БД, отключение RLS/аудита | только человек |

### Предохранители

Silo = естественный blast-radius (действие на контуре X не трогает остальных). Canary-контур для рискованных действий. Обязательная верификация после каждого действия (метрика-симптом вернулась в норму, иначе freeze+эскалация). Бюджет действий/час на флот. **Еженедельный restore-drill агентами = верхняя граница ущерба любого плохого авто-действия.** Append-only ops-журнал (та же event_log-дисциплина) — аудит «кто что делал с контуром клиента» и корпус для playbook'ов.
