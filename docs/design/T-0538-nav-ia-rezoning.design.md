## 1. Контекст и проблема

Сегодняшняя IA (T-0355) делит сайдбар на **два** пространства — АВТОРИНГ и РАБОТА — визуальным разделителем (`shell.jsx` §707). За пол-года это пространство «РАБОТА» превратилось в свалку: туда стекли `Исполнители и доступ` (оргструктура+агенты+права), `Наблюдаемость` (6 пунктов) и `Конфигурация` (3 LLM-пункта). Нав-аудит (`docs/ux-audit-2026-06-29.md`) и разбор nav-IA в памяти зафиксировали:

- **Системные/админские пункты свалены в «Работу»** — конечный пользователь видит «Права и доступ», «LLM-подключение», «Промпт ассистента» рядом со своими «Мои задачи». Это шум и неверная ментальная модель.
- **Нет меню пользователя.** Идентичность (имя/роль) показана в подвале сайдбара, но это не интерактивный аккаунт-центр: «Выйти» — отдельная плавающая кнопка (`shell.jsx` §762), смены организации / профиля / уведомлений-настроек / темы нет в одном месте.
- **ThemeToggle живёт в топбаре** (`shell.jsx` §354) — занимает место на каждом экране, хотя это разовая настройка аккаунта.
- **Справочники-конструкты** (критичность, SoD, каталог ролей, повседневные операции/интенты) сегодня — суб-вкладки экрана «Права» (`RIGHTS_TABS`), смешаны с операционным просмотром грантов. Это разные жанры: «настраиваю справочник» vs «смотрю, кто что может».

Цель T-0538: пересобрать nav в **4 операционные зоны**, ввести **аккаунт-поповер**, вынести **справочники** в Администрирование — так, чтобы impl-прогон собрал без открытых вопросов, маршруты НЕ менялись, а поля nav-модели были готовы под capability-фильтр T-0539.

## 2. Решение (load-bearing)

**Пересобрать nav-конфиг в плоскую модель `NavZone[] → NavItem[]` с четырьмя зонами (РАБОТА · КОНСТРУКТОР · НАБЛЮДАЕМОСТЬ · АДМИНИСТРИРОВАНИЕ); каждый `NavItem` несёт мета-поля `{ zone, audience, capability, frequency, order }`. Поля `capability`/`audience` ОБЪЯВЛЯЮТСЯ сейчас (задел под T-0539), но фильтрация НЕ реализуется — дефолт «видно всем» (`capability: null ⇒ всегда видим`). Идентичность переезжает в аккаунт-поповер внизу сайдбара (Профиль/Мои настройки=скоро, Уведомления, Тема, Сменить организацию, Выйти); плавающая «Выйти» и `ThemeToggle` из топбара удаляются. Справочники (критичность, SoD, каталог ролей, повседневные операции) выносятся из суб-вкладок «Права» в пункт «Справочники» зоны АДМИНИСТРИРОВАНИЕ; в «Доступе» остаётся операционный просмотр грантов + журнал. Все существующие маршруты (`path`) сохраняются байт-в-байт — IA меняет только группировку, ярлыки и подвал, не роутинг.**

Решение **пропорционально**: это перекладка данных в `nav-config.js` + один новый presentational-компонент `AccountMenu` + удаление двух фрагментов из `shell.jsx`. Никакого роутера, никакого permission-движка (capability — задел-поле, не код).

### 2.1 Почему 4 зоны, а не 2 пространства

Две оси «авторинг/работа» не масштабируются: «наблюдаю» и «администрирую» — самостоятельные режимы с разной аудиторией и частотой. Четыре зоны отражают **что я сейчас делаю**:

| Зона | Ментальная модель | Аудитория (audience) | Частота |
|---|---|---|---|
| **РАБОТА** | делаю свои задачи, веду процессы | `end-user` | daily |
| **КОНСТРУКТОР** | собираю решение из примитивов | `builder` | weekly |
| **НАБЛЮДАЕМОСТЬ** | смотрю, как система работает | `manager` | weekly |
| **АДМИНИСТРИРОВАНИЕ** | настраиваю исполнителей/доступ/справочники/интеграции | `admin` | rare |

`audience` — это **семантический ярлык зоны/пункта** (не право). T-0539 повесит на него + на `capability` фактическую фильтрацию; сейчас всё видно всем.

## 3. Новая модель nav-config

### 3.1 Типы (JSDoc, как сегодня — zero-dep, plain JS)

```js
/**
 * @typedef {'live' | 'demo' | 'soon'} NavStatus
 *   статус-классификация (без изменений из T-0355).
 *
 * @typedef {'work' | 'constructor' | 'observability' | 'admin'} NavZoneId
 *   четыре операционные зоны (заменяют двухзначный NavSpace 'authoring'|'work').
 *
 * @typedef {'end-user' | 'builder' | 'manager' | 'admin'} NavAudience
 *   семантический ярлык: «для кого этот пункт». Дефолт наследуется от зоны.
 *
 * @typedef {'daily' | 'weekly' | 'rare'} NavFrequency
 *   как часто пункт нужен; влияет на порядок/будущую коллапс-логику. Информативно.
 *
 * @typedef {Object} NavItem
 * @property {string}        id          стабильный id (== screen-id, основа маршрута)
 * @property {string}        label       человеко-понятный ярлык (ru)
 * @property {string}        icon        kit Lucide icon name
 * @property {NavZoneId}     zone        зона, которой принадлежит пункт
 * @property {NavAudience}   audience    для кого (дефолт = zone.audience)
 * @property {string|null}   capability  ЗАДЕЛ под T-0539: capability-ключ, гейтящий
 *                                       видимость. `null` ⇒ видно всем (дефолт СЕЙЧАС).
 *                                       Словарь ключей берётся из модели грантов
 *                                       (resource_type×operation, T-0018) — фиксируется в T-0539.
 * @property {NavFrequency}  frequency   частота использования (информативно)
 * @property {number}        order       порядок внутри зоны (возрастающий)
 * @property {string=}       path        переопределение маршрута (инвариант §6)
 * @property {boolean=}      screen      есть реальный экран/маршрут
 * @property {boolean=}      hidden      скрыт из nav полностью (маршрут жив)
 * @property {NavStatus}     status      live | demo | soon
 *
 * @typedef {Object} NavZone
 * @property {NavZoneId}     id          'work' | 'constructor' | 'observability' | 'admin'
 * @property {string}        label       'Работа' | 'Конструктор' | 'Наблюдаемость' | 'Администрирование'
 * @property {NavAudience}   audience    дефолтная аудитория зоны
 * @property {number}        order       порядок зон в сайдбаре (1..4)
 * @property {NavItem[]}     items       пункты зоны (в порядке item.order)
 */
```

### 3.2 Структура `NAV`

`NAV` становится массивом из **4 `NavZone`** + одиночного home-пункта «Обзор» НАД зонами (как сегодня `home: true`). «Обзор» — точка входа, не принадлежит ни одной зоне (рендерится без заголовка-ярлыка). Внутри зоны — подгруппы только там, где их ≥2 (правило §«заголовок без выбора = шум» сохраняется): в АДМИНИСТРИРОВАНИИ пункты «Исполнители», «Доступ», «Справочники», «Интеграции и LLM» — это **пункты-аккордеоны/группы**, каждый со своими листьями.

Зоны рендерятся в порядке `order`: **1 РАБОТА · 2 КОНСТРУКТОР · 3 НАБЛЮДАЕМОСТЬ · 4 АДМИНИСТРИРОВАНИЕ**. Между зонами — тот же визуальный разделитель-класс `chs-nav__space-divider`, но теперь он ставится перед КАЖДОЙ зоной (кроме первой), а не один раз. Заголовок зоны рендерится как `chs-nav__grouplabel` (uppercased CSS, без новых токенов).

> **Замечание о подзонах Администрирования.** «Исполнители» и «Интеграции и LLM» содержат по 2+ листа → это группы с заголовком. «Доступ» и «Справочники» — тоже группы (см. маппинг §3.4 и вынос §5). Реализатор волен отрисовать их либо как вложенные подгруппы внутри зоны АДМИНИСТРИРОВАНИЕ, либо как отдельные `chs-nav__group` блоки, помеченные `zone:'admin'`. Контракт: все они имеют `zone:'admin'` и идут после разделителя 4-й зоны. Рекомендуемая форма — **плоские группы с `zone`**, чтобы не плодить уровень вложенности в рендере (минимальная правка `shell.jsx`).

## 4. Меню пользователя (аккаунт-поповер)

### 4.1 Что строим

Подвал сайдбара (`shell.jsx` §756–765) превращается из статичного блока «глиф + имя + плавающая Выйти» в **кнопку-триггер аккаунт-поповера**. Клик/Enter/Space по строке идентичности открывает поповер (kit-овер popover/Menu; если в ките нет — kit Modal `size:sm`, как у CommandPalette — НЕ ручной overlay, см. находку аудита #3/#5).

**Состав меню (сверху вниз):**

| Пункт | Действие | Статус |
|---|---|---|
| Профиль | (заголовок-карточка: имя + роль + орг) → страница профиля | **скоро** (disabled + видимая причина, не native `title`) |
| Мои настройки | пользовательские преференсы | **скоро** (disabled + видимая причина) |
| Уведомления | `navigate('/notifications')` | live (тот же маршрут, что и пункт зоны Наблюдаемость) |
| Тема | inline-переключатель Светлая/Тёмная (переносится сюда из топбара) | live |
| Сменить организацию | открывает выбор тенанта (мульти-тенант, T-0537-смежно); если 1 орг — disabled c причиной | live / honest-disabled |
| — разделитель — | | |
| Выйти | `handleLogout()` (существующий) | live |

### 4.2 Что удаляем

- **Плавающая «Выйти»** — `shell.jsx` §762 `<button … chs-nav__logout-btn>`. Логаут переезжает внутрь поповера (последний пункт). Класс `chs-nav__logout-btn` удаляется/перецеливается.
- **`ThemeToggle` из топбара** — `shell.jsx` §354 (`<ThemeToggle theme=… setTheme=… />` внутри `chs-topbar__right`). Сам компонент `ThemeToggle` можно переиспользовать ВНУТРИ поповера (пункт «Тема»), либо заменить на компактный сегмент — реализатор выбирает; контракт: тема-переключатель НЕ остаётся в топбаре. Проп `theme/setTheme`, который `Topbar` сейчас прокидывает только ради `ThemeToggle`, после выноса в `Topbar` не нужен.

### 4.3 Доступность (G-инварианты аудита)

- Триггер поповера — **настоящий `<button>`** (`aria-haspopup="menu"`, `aria-expanded`), не кликабельный `<div>` (находка #5 — fake-ARIA/нет клавиатуры).
- Внутри — фокус-трап, Esc-закрытие (через kit Modal/Menu — не ручной).
- «скоро»-пункты: `aria-disabled` + **видимая** пояснительная строка (не native `title` — находка #9).
- Контраст текста меню в обеих темах ≥ AA (FF-UX-CONTRAST, §7).

## 5. Вынос справочников

### 5.1 Сегодня (`RIGHTS_TABS`, `shell.jsx` §55–62)

Экран «Права» имеет 6 суб-вкладок, смешивающих **операционный просмотр** грантов и **справочные конструкты**:

| RIGHTS_TAB id | Ярлык | path | Жанр | → Куда |
|---|---|---|---|---|
| `overview` | Обзор ролей | `/rights` | операц. просмотр грантов роли (read-first, `screen-rights.jsx`) | **остаётся в «Доступ»** |
| `trail` | Журнал | `/rights/trail` | операц. журнал выдач (grant-trail, live) | **остаётся в «Доступ»** |
| `intents` | Повседневные операции | `/rights/intents` | СПРАВОЧНИК интентов (каталог повседневных операций) | → **Справочники** |
| `editor` | Редактор роли | `/rights/editor` | СПРАВОЧНИК: каталог/редактор ролей (demo) | → **Справочники** |
| `criticality` | Критичность | `/rights/criticality` | СПРАВОЧНИК: уровни критичности | → **Справочники** |
| `sod` | SoD | `/rights/sod` | СПРАВОЧНИК: матрица разделения обязанностей | → **Справочники** |

### 5.2 После выноса

- **«Доступ»** (пункт `rights`, зона АДМИНИСТРИРОВАНИЕ / подгруппа «Доступ»): операционный просмотр — **Обзор ролей** (`/rights`) + **Журнал** (`/rights/trail`). Это «кто что может» (read-first просмотр грантов, по доктрине T-0018: гранты — единственная авторитетная модель, просмотр read-only). Суб-вкладки экрана сокращаются до этих двух.
- **«Справочники»** (пункт `reference`, подгруппа «Справочники»): **Критичность** (`/rights/criticality`), **SoD** (`/rights/sod`), **Каталог ролей** (`/rights/editor`), **Повседневные операции** (`/rights/intents`). Это «настраиваю справочные конструкты, из которых считаются гранты». Критичность/SoD/каталог ролей — вычислительные входы модели грантов (T-0018 §9: `role_criticality`/dual-control считаются ИЗ грантов; справочники — их параметры), логично жить вместе как справочный жанр.

### 5.3 Реализация выноса (минимальная)

Маршруты `/rights/*` **НЕ меняются** (инвариант §6). Меняется только **группировка суб-вкладок** и **точка входа в nav**:

1. `RIGHTS_TABS` расщепляется концептуально на `ACCESS_TABS` = `[overview, trail]` и `REFERENCE_TABS` = `[criticality, sod, editor, intents]`. Реализатор может (а) держать один `RIGHTS_TABS` с полем `genre: 'access'|'reference'` и фильтровать суб-таб-бар по текущему пункту nav, либо (б) завести два массива. Контракт: на странице «Доступ» видны только access-вкладки, на «Справочниках» — только reference-вкладки.
2. Пункт `reference` в nav открывает справочники (по умолчанию `path:/rights/criticality` — первый справочник, либо страница-хаб; маршруты-листья `/rights/sod|editor|intents` доступны через суб-таб-бар).
3. Ярлык вкладки `editor` в справочниках читается как **«Каталог ролей»** (человеко-понятнее, чем «Редактор роли»), `status:demo` сохранён.

## 6. Инвариант: маршруты НЕ меняются (path-override)

**Жёсткий инвариант.** IA T-0538 меняет ТОЛЬКО группировку, ярлыки, подвал и суб-таб-разбиение. Множество существующих маршрутов (`<Route>` в `shell.jsx` §772–818 + `RIGHTS_TABS.path` + `item.path`-override) остаётся **байт-в-байт** тем же:

- Каждый `NavItem.id` по-прежнему резолвится в маршрут `item.path || '/' + item.id` (механика `NavItem`/`paletteDestinations` неизменна).
- `modeler` сохраняет `path:/processes/new/edit`; новый `reference` получает `path:/rights/criticality` (существующий маршрут).
- Ни один `<Route path=…>` не добавляется и не удаляется этой задачей. (Если реализатор захочет страницу-хаб `/reference` — это ОТДЕЛЬНЫЙ опциональный маршрут, не ломающий существующие; по умолчанию НЕ требуется.)
- FF-PATHS (§7) доказывает: каждый `path`, на который ссылается nav, резолвится в существующий маршрут (нет битых ссылок); и обратно — палитра не потеряла назначений.

## 7. Fitness-функции (CI-gating)

Каждая — исполнимое правило для `npm run ci` / e2e-journey. `ci_check` указывает на `ci/checks/ux/*.sh` (статические гейты, как существующие g2/g5/g6) или `e2e/journeys/*.ux.journey.ts` (живой journey против собранного `web/dist`, по конвенции `e2e/journeys/README.md`).

| FF | Правило (assert) | ci_check | gating |
|---|---|---|---|
| **FF-UX-DEAD** (G1) | Нет мёртвых `enabled` пунктов nav/меню: каждый кликабельный (`screen && status!=='soon'`) пункт nav и каждый enabled-пункт аккаунт-поповера ведёт на существующий маршрут/действие; «скоро» помечены `aria-disabled` + видимой причиной | `ci/checks/ux/ux-g1-no-dead-nav.sh` | static-now |
| **FF-UX-CONTRAST** (G3/G4) | Текст и иконки нав-сайдбара, заголовков зон и аккаунт-поповера дают контраст ≥ WCAG AA в **обеих** темах (light/dark); никаких hex-fallback в var() для нав-поверхностей | `e2e/journeys/nav-ia.ux.journey.ts` (axe/contrast-проба обеих тем) | static-now (journey) |
| **FF-UX-JARGON** (G5) | Ни один видимый ярлык зоны/пункта/подгруппы/меню не содержит дев-жаргона (en-enum, slug, UUID, HTTP-код, `space:'authoring'`, `control-plane`) | `ci/checks/ux/ux-g5-jargon-denylist.sh` (расширяется на nav-ярлыки) | static-now |
| **FF-NAV-PATHS** | Каждый `path` (явный `item.path` ИЛИ выведенный `'/'+id`), на который ссылается nav/палитра, резолвится в существующий `<Route>` в `shell.jsx`; и каждый сегодняшний маршрут по-прежнему достижим (нет осиротевших/битых ссылок) | `ci/checks/ux/nav-paths-resolve.sh` | static-now |
| **FF-NAV-MAP** | Множество nav `item.id` (включая hidden) В НОВОЙ модели == множеству сегодняшних id (полнота переноса: ничего не потеряно/не задвоено сверх сознательного быстрого-доступа `notifications`) | `ci/checks/ux/nav-paths-resolve.sh` (та же проверка, секция MAP) | static-now |
| **FF-NAV-NOSYS** | В зоне **РАБОТА** НЕТ системных/админских пунктов: ни одного пункта с `zone:'work'`, чей id ∈ {org, agents, rights, reference, llm-connections, llm-config, assistant-prompt, audit, spend}. Системные пункты обязаны нести `zone ∈ {admin, observability}` | `ci/checks/ux/nav-zone-purity.sh` | static-now |

> Минимум по контракту-хэндоффу выполнен: ≥1 `FF-UX-*` (три: DEAD/CONTRAST/JARGON) + FF «каждый существующий path резолвится» (FF-NAV-PATHS) + FF «системные пункты НЕ в зоне РАБОТА» (FF-NAV-NOSYS). Новые `*.sh` — additive в `ci/checks/ux/`; новый journey — additive в `e2e/journeys/` (zero runner-change по README).

## 9. Non-goals (НЕ строится в T-0538)

1. **Фактический capability-фильтр nav** — T-0539. Здесь только поля-задел + дефолт «видно всем».
2. **Динамические «Разделы» (Финансы/HR/Продажи)** в зоне РАБОТА — E16/T-0349.
3. **Страницы «Профиль»/«Мои настройки»** — заглушки «скоро»; реальные экраны позже.
4. **Реальный мульти-тенант-свитчер логики** — UI-пункт «Сменить организацию» + honest-disabled при 1 орг; серверная часть — T-0537-смежно.
5. **ToastProvider / kit-свип** — T-0528 / T-0531 (только координация, §8).
6. **Изменение любых маршрутов/`<Route>`/API** — запрещено инвариантом §6.
