# ADR T-0236 — Restore dev green: additive FF-25-3 allow-set extension for T-0233 runtime custody

- Status: accepted
- Date: 2026-06-15
- Owner-task: T-0236
- Touches frozen: **false** (FF-25-6 frozen files byte-unchanged)

## Context

T-0233 (the first live agent — legal-precheck motor) merged into `dev` with
`npm run fitness` RED (a D-056 integration-honest-gate escape during run s19:
the full gate was not honestly run to completion before merge). The red is
`secret-handle-isolation.sh` check **FF-25-3**: three T-0233 files reference
`llm_secret_handle` but are not in the FF-25-3 `ALLOWED_FILES` array (which was
authored for the T-0025/T-0042 hire-path).

Every reference in the three files is a legitimate **custody site**, not a leak:
- `run-precheck.ts`: column reference in a type field, a null-check
  (`llm_configured`), and a `SELECT` — used to decide dormancy and custody the
  handle into the injected `LlmPort`. Never a raw value, log, or error.
- `openai-llm-port.ts`: a header **comment** only. Actual custody is via the
  opaque `SecretResolverPort` / `validateSecretHandleShape` / `redactHandle`.
- `run-precheck.test.ts`: `vault://...` handle-**reference** fixtures (opaque
  references, not secret values).

A second constraint surfaced during verification: `secret-handle-isolation.sh`
is owned by T-0025 (header line 2) and is therefore protected by the
`frozen-checks-immutable.sh` meta-gate (FF-FCI1). A foreign task editing it
trips FF-FCI1 unless sanctioned via the FF-FCI12 channel
(`ci/checks/data/frozen-sanctions.jsonl`).

## Decision

1. **Extend FF-25-3 `ALLOWED_FILES`** additively with exactly the two runtime
   custody files (`run-precheck.ts`, `openai-llm-port.ts`). The test sibling is
   auto-allowed by the existing `*.test.ts` stem rule. Update the ADR §13.3
   amendment comment block to document the T-0233 runtime-custody rationale.

2. **Append one mechanism-class sanction line** to `frozen-sanctions.jsonl` for
   `{task:T-0236, file:ci/checks/secret-handle-isolation.sh}`. This is the
   **D-060 additive auto-sanction class**, identical in shape to T-0233's
   already-ratified unpark of `agent-instruction-runtime-dormant.sh`: additive
   allow-set widening, no new authority, frozen files untouched, same
   legal-precheck runtime. The meta-gate prints `SANCTION`/`AUDIT` lines on the
   bypass (never silent); abuse is visible in the pre-merge diff (accepted R-2
   residual-risk class).

## Alternatives considered (rejected)

- **Remove the handle references from the T-0233 runtime** — rejected: breaks
  T-0233's custody design (the motor MUST read the handle reference to decide
  dormancy and custody it to the injected port; the adapter comment documents
  the RL-3 custody contract). Would re-open a working feature to satisfy a check
  that was simply not extended.
- **Leave dev red** — rejected: the whole point is restoring the integration-
  honest gate so the `promote-to-dev` honesty contract (D-056) holds again.
- **Founder-gate the sanction** — not required: D-060 carves out the additive +
  narrow + frozen-untouched + self-test-verifiable class as the *mechanism*
  (auto-sanction) path; founder gating is reserved for destructive /
  authority-widening thaws. The T-0233 review explicitly ratified this exact
  class for the legal-precheck runtime.

## Consequences

- `npm run fitness` returns to GREEN to completion; dev honest-gate restored.
- The FF-25 dormancy boundary remains intact — only two additional **custody**
  sites are allow-listed; FF-25-1/2/4/5/6/8 are untouched and still pass.
- Provenance note (from T-0233 review R-1, carried forward): `is_sanctioned()`
  matches only `{task,file}`, not `sanctioned_by`/`decision` class. A follow-up
  hardening to assert sanction-class vs thaw-class is a separate task; this ADR
  does not change the meta-gate.
