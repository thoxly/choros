# Choros — Триггеры, точки входа, исходы и связи (ADR · E16)

> Как машинерия (доктрина владения данными + швы S0–S5) соединяется с интерфейсом:
> чем триггерится процесс, где пользователь его «запускает», как шаг ветвится
> кнопками, как связанные приложения показываются на карточке, и какие справочники
> системные. Переосмысление текущей UI-модели (3 кнопки, два несвязанных мира).

## 1. Решение в одной строке

**Пользователь действует на ОБЪЕКТЕ, а не «запускает процесс»: процесс — машинерия за
кадром бизнес-действия. У инициатора три точки входа (создать/подать объект · действие
на записи · задача в инбоксе), и generic-кнопка «запустить процесс» растворяется в них.
Триггер живёт на привязке процесс↔приложение (`process_app_binding` повышается из
витрины в рантайм-конфиг: тип-триггера + стартовая форма + маппинг). Для транзакционных
сущностей создание = запуск (форма создания и есть стартовая). Приложение —
универсальный примитив: без привязанного процесса оно = справочник. Шаг ветвится
ИСХОДАМИ (семантика на схеме, оформление в панели, пресеты+агент), исход умеет звать
подпроцесс. Карточка композирует родные поля + read-only проекции связей в
изолированных группах; перф держит ПОЛИТИКА резолюции (1-хоп live / агрегат
материализуется по event-log / hop-cap), а не лимит на число связей.**

---

## 2. Три точки входа инициатора (generic «запустить процесс» уходит)

1. **Создать / подать объект** («Создать счёт») — для транзакционных сущностей это и есть
   запуск (см. §3). Контекст: внутри приложения или глобальный лаунчер «Создать…».
2. **Действие на записи** («Отправить договор на пересогласование») — для мастер-сущностей
   с долгой жизнью и многими процессами; кнопка на карточке.
3. **Задача в инбоксе** — процесс сам пришёл к исполнителю; «запускать» нечего.

Generic-кнопка «Запустить процесс» (сейчас захардкожена на `telLinear`) — **убрать из
рантайма**; максимум остаётся как админ/отладочный лаунчер.

## 3. Триггер-типы на привязке (process_app_binding: витрина → рантайм)

`process_app_binding` (075) сегодня — display-only. Повышаем до **рантайм-конфига
триггера**, несущего: `тип-триггера` + `стартовая-форма` (= форма создания из
`record_schema`, S4) + `маппинг полей`.

| Тип триггера | Когда стартует | Где у пользователя | Пример |
|---|---|---|---|
| **on_create** | запись создана (или поле/статус → «к согласованию») | «Создать <X>» — создать = запустить | счёт, заявка, отпуск |
| **record_action** | пользователь жмёт действие на существующей записи | кнопка на карточке | пересогласование договора |
| **launcher** | выбор бизнес-действия из «Создать…» | глобальный лаунчер (динамич., не хардкод) | разовая заявка |
| **auto** | событие/таймер/условие | пользователь не видит (агент/внедренец) | регулярная сверка |

**create = start** (для on_create): `POST /api/records` на реестре с триггером on_create
дёргает старт процесса в ОДНОЙ транзакции через шов S1; бизнес-ключ связывает запись и
инстанс (резолвер instance→record, S1a). Черновик-вариант: триггер на переходе статуса
`draft → submitted` (кнопка «Отправить» = старт) — даёт контроль без отдельной кнопки
«запустить».

## 4. Транзакционные vs мастер; приложение-без-процесса = справочник

- **Транзакционная сущность** (счёт, заявка, отпуск): рождается ради обработки, 1 запись ≈
  1 прогон → создать = запустить (форма создания = стартовая). Авто.
- **Мастер-сущность** (контрагент, договор, сотрудник, товар): долгоживущая, разные
  процессы за жизнь → запись создаётся сама, процессы = действия на карточке (record_action).
- **Приложение — универсальный примитив.** «Справочник» = приложение БЕЗ привязанного
  процесса (CRUD-only). «Транзакционное» = приложение с триггером on_create. Один субстрат,
  разная конфигурация. Привязка процесса — опциональна; отдельный «тип сущности» не нужен.

## 5. Исходы шага (кнопки) — семантика на схеме, оформление в панели

Трёхслойное разделение (даёт routing, держит схему чистой):
1. **Семантический исход** — на задаче, рулит маршрутом; на холсте = **именованные ветки**
   (`Согласовать / Отклонить / На доработку`), НЕ сырые условия.
2. **Оформление кнопки** (текст, цвет, «требует комментарий», confirm) — в **панели свойств,
   вне холста**.
3. **Маршрут** (исход → ветка) — единственное, что нужно схеме; компактно.

**Пресеты (убивают ад настройки; покрывают ~90% + свои):**

| Пресет | Исходы |
|---|---|
| **Готово** | 1: `Готово` → дальше (дефолт ~50% шагов) |
| **Решение** | 2: `Согласовать` / `Отклонить` |
| **Решение с доработкой** | 3: `Согласовать` / `Отклонить` / `На доработку` → назад |
| **Свои исходы** | N названных пользователем (хвост) |

Агент выбирает пресет из смысла шага; внедренец задаёт свои.

**Цель исхода** может быть: `→ дальше` / `→ конец` / `→ назад` / **`→ запустить ПОДпроцесс
(синхронно, ждём)`** / **`→ запустить процесс (асинхронно, не ждём)`**. На холсте подпроцесс
= одна коробка с drill-in (родительская схема на одном уровне абстракции). **Сущность —
нить, что сшивает композированные процессы** (подпроцесс работает на той же записи через
S1a + бизнес-ключ).

**Не смешивать:** исход-кнопки = ветку выбирает ЧЕЛОВЕК; DMN-шлюз = ветку решают ДАННЫЕ
(сумма>5млн → юрист). Два механизма, схема не перегружается.

## 6. Карточка: связи + политика резолюции

- Карточка композирует **родные поля + read-only проекции связанных приложений** (через
  `cross_app_ref` 068) в **помеченных изолированных секциях** («Из договора», «Из CRM»).
  Родное редактируется; связанное — read-through (правка на исходной записи). ACL на каждом
  хопе → редактированная проекция при нехватке прав (§6 extensibility).
- **Настраиваемо вручную И агентом**: какие связанные поля и в какой группе — выбирает
  внедренец или предлагает агент (знает обе схемы).
- **Перф держит ПОЛИТИКА резолюции, не лимит связей** (связи = дешёвые метаданные):
  - **Список** (100 строк): родные поля + денормализованный кэш-ключ (snapshot), БЕЗ
    резолюции → быстро всегда.
  - **Карточка**: 1-хоп резолвится **live** при открытии (lazy, на раскрытие секции).
  - **Агрегаты / rollup**: **материализуются** (кэш), refresh через **event-log/outbox
    (S3)** при изменении источника → не считаются на каждый чит.
  - **Глубже hop-cap (2–3)**: не live → отдельный отчёт.
- Рычаг **ясности** (а не перфа): курировать 3–5 релевантных полей на связь в свёрнутой
  секции — режет когнитивную и перф-нагрузку.

## 7. Системные справочники (узкий core-бэкбон)

Core-справочник = (а) универсален для всех тенантов, (б) критичен для
целостности/апгрейда/интеграции, (в) читается самой машинерией. Иначе — шаблон-приложение.

| Core (extend-not-replace, часто проекция внешнего) | Почему core |
|---|---|
| Оргструктура (подразделения/должности) | бэкбон акторов; питает гранты/резолюцию (S0/S2) |
| Пользователи / Сотрудники | проекция Keycloak; идентичность = актор |
| Роли | модель полномочий (PDP) |
| Контрагенты | хаб B2B, ссылается всё; часто sync 1С |
| Валюты | универсально, крошечно, стабильно |
| Производственный календарь | нужен машинерии для SLA «через 2 рабочих дня» |
| *(опц.)* Единицы измерения | универсально для товаров |

**НЕ core, а шаблоны** (тенант владеет): номенклатура/товары, прайсы, категории, статусы,
источники лидов.

## 8. IA: пространство авторинга ≠ пространство работы

- Сейчас nav режет «Конструктор» (приложения) отдельно от «Работа» (процессы) — разрывает
  объект и работу над ним. **Раздел = бизнес-функция/домен** (Финансы, HR, Продажи), внутри —
  приложения + их действия + относящиеся задачи.
- **Отделить пространство АВТОРИНГА** (конструктор/модельер/AI-консоль — для внедренца и
  агента) от **пространства РАБОТЫ** (функциональные домены — для конечного пользователя).
- «Раздел» — лёгкий навигационный конструкт группировки приложений по функции (создаёт
  агент/внедренец), а не тяжёлая сущность-с-записями.

## Открытые вопросы (точки решения фаундера)

- **Дефолт транзакционных:** «черновик → Отправить» (рекоменд., безопаснее) vs «создал →
  сразу пошло». (confidence: medium)
- **Глобальный лаунчер «Создать…»:** оставить вторым входом (рекоменд.) или только контекст. (medium)
- **hop-cap:** 2 или 3 хопа live по умолчанию. (medium)
- **Набор пресетов исходов:** Готово / Решение / Решение+доработка / Свои — достаточно? (high)
- **core-справочники:** фиксируем список §7 (контрагенты/валюты/календарь core) или урезаем. (medium)
