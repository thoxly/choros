# ADR · T-0627 — Draft-tier publish step: делаем заметным, не разливаем видимость

**Phase:** DESIGN → BUILD · **Status:** ready · **Date:** 2026-07-05
**Task:** T-0627 [UX/публикация, столп 4]
**Origin:** капстоун T-0584 (LIVE_PROOF, 2026-07-04) вскрыл, что рядовой сотрудник, работающий
в draft-приложении вместе с коллегами («команда ведёт сделки на общей доске»), видит только
свои записи — записи коллег отдают честный 404. Sandbox-gate (T-0558, T-0623) корректен по
дизайну: это и есть контракт «черновик = песочница автора». Проблема НЕ в контракте, а в том,
что путь «опубликовать → стало общей доской» невидим и не объяснён.

**Не переоткрывать (frozen):**
- `src/core/sandbox-gate.ts` — `decideDraftVisibility`, `sandboxReadPredicate` (T-0557/T-0558/T-0623).
- `src/db/sandbox-gate-dao.ts` — `resolveActorPrivilege` (T-0557).
- Любая query в `src/http/records.ts` / `src/http/applications.ts`, использующая эти примитивы.
- Контракт 404 для скрытой/несуществующей записи — сервер НЕ должен и после этой задачи не
  различает «запись существует, но скрыта» от «записи нет» (иначе это была бы утечка факта
  существования чужих данных через границу гейта).

---

## 1. Проблема (по факту капстоуна T-0584 / T-0623)

Draft-приложение — песочница автора: рядовой сотрудник видит и создаёт свои записи, но
запись коллеги (тоже созданная в том же draft-приложении) резолвится в 404. Это ожидаемо
(fail-closed: непривилегированный актор видит только `published` + свои собственные строки),
но с точки зрения пользователя выглядит как баг: «я создал запись, коллега её не видит» /
«коллега создал запись, я её не вижу», без единого слова объяснения — только голый 404.

Единственный выход из песочницы — публикация приложения владельцем/админом:
`POST /api/applications/:id/publish-solution` (уже реализовано, T-0563,
`apps-publish-dialog.jsx` + `apps-publish-api.js`). Но:

- кнопка «Опубликовать решение» спрятана в выпадающем «…»-меню на экране списка приложений
  (`screen-apps.jsx`, `buildAppMenuItems`) — НЕ видна с экрана записей, где реально
  проживается проблема;
- нет объяснения в момент столкновения с «только свои записи» / 404 чужой записи;
- нет онбординг-подсказки при создании приложения, что публикация нужна для командной работы.

## 2. Что НЕ меняем (граница задачи)

Явно фиксирую периметр, который остаётся нетронутым:

1. `decideDraftVisibility` / `sandboxReadPredicate` — те же правила, тот же SQL-фрагмент.
2. `resolveActorPrivilege` — тот же источник истины (owner/admin OR `authoring_draft`).
3. 404-контракт для `GET /api/records/:id` — сервер по-прежнему не различает «скрыто» от
   «не существует» в ответе. Это осознанное решение T-0558 (не давать непривилегированному
   актору узнать, что чужая запись СУЩЕСТВУЕТ, просто ему недоступна) — разглашать даже
   «запись есть, но не видна» само по себе было бы утечкой.
4. Никакой новой ручки чтения, которая считала бы/перечисляла скрытые записи для
   непривилегированного актора (это тоже была бы утечка через агрегат).

Всё, что делает эта задача, построено ТОЛЬКО из контекста, который браузер уже легитимно
имеет:

- `GET /api/applications/:id` — тенант-скоуп, БЕЗ tier-фильтра (см. `src/http/applications.ts`
  строки ~628-648): любой член тенанта уже может прочитать `tier` приложения (это видно даже
  в списке `/apps` всем). Использование этого поля для текста баннера/честного EmptyState не
  открывает НИКАКОЙ новой поверхности.
- `GET /api/me/nav-capabilities` (T-0539) — уже резолвится один раз при загрузке шелла и
  кешируется в `web/src/app-shell/active-tenant.js` (`getNavCapabilities()`): даёт
  `isGenesisOwner` + `capabilities[]` (включая `authoring_draft`). Это ЗЕРКАЛО клиентской
  копии того же решения, что принимает `resolveActorPrivilege` на сервере — используется
  ИСКЛЮЧИТЕЛЬНО для того, чтобы решить, какой текст показать и показывать ли кнопку
  «Опубликовать» (само действие публикации по-прежнему проверяется сервером независимо).

## 3. Решение

### 3.1 Баннер на экране записей приложения (`screen-app-records.jsx`)

Когда загруженное `app.tier === 'draft'`, сразу под шапкой экрана рендерится постоянный
(без dismiss) баннер `role="status"`, токен-стиль (зеркалит существующий warning-баннер
`screen-forms.jsx`):

- **owner/admin/authoring_draft-держатель** (`canPublish === true`, из кешированных
  NavCapabilities): «Приложение в черновике: пока видны только ваши записи. Опубликуйте, чтобы
  команда работала на общей доске.» + кнопка **«Опубликовать»**, открывающая ТОТ ЖЕ
  `PublishSolutionDialog`, что уже используется в `screen-apps.jsx` (импортирован, не
  продублирован).
- **рядовой сотрудник** (`canPublish === false`): та же констатация факта, БЕЗ кнопки (G3 —
  никогда не показываем мёртвую/чужую кнопку): «Приложение в черновике: пока видны только ваши
  записи. Когда владелец опубликует приложение, команда увидит общую доску.»

Баннер существует, пока `app.tier !== 'published'`; исчезает без перезагрузки страницы, как
только `app` перегружается с `tier==='published'` (существующий `loadApp`/`handlePublished`
уже переиспользуется — публикация из самого баннера триггерит тот же `onDone`, что и публикация
из «…»-меню).

### 3.2 Честный текст вместо голого 404 (`screen-record-detail.jsx`)

При 404 от `GET /api/records/:id` экран ДОПОЛНИТЕЛЬНО (best-effort, не блокируя) тянет
`GET /api/applications/:appId` (appId уже есть в URL-параметрах маршрута
`/apps/:appId/records/:id`). Если приложение резолвится и `tier === 'draft'`, вместо голого
«Запись не найдена» показываем честную, НЕ утверждающую факт существования формулировку:

> «Запись не найдена. Приложение ещё в черновике — если это запись коллеги, она станет видна
> после публикации приложения владельцем.»

Формулировка НАМЕРЕННО двусмысленна относительно факта существования («если это запись
коллеги») — она одинаково истинна что в случае «запись существует, но скрыта», что в случае
«записи вообще нет». Это не расширяет утечку: сервер по-прежнему возвращает один и тот же 404
в обоих случаях; клиент лишь добавляет контекст о приложении, который и так был публично
читаем.

Если запрос приложения падает / приложение уже `published` — экран деградирует БАЙТ-В-БАЙТ к
прежнему тексту («Запись не найдена или у вас нет к ней доступа.») — нулевая регрессия, когда
доп. контекст недоступен.

### 3.3 Онбординг при создании приложения (`screen-apps.jsx`, `CreateAppModal`)

Одно дополнительное предложение под существующей строкой «Создаётся в статусе «черновик»»:
черновик — личная песочница автора (видны только его записи), пока приложение не опубликовано
для команды.

## 4. Почему это не разливает видимость

- Ни `tier` приложения, ни NavCapabilities не являются НОВОЙ информацией: `tier` уже виден в
  таблице `/apps` (колонка «Статус», `TIER_CHIP`) любому члену тенанта; NavCapabilities уже
  резолвятся и используются для нав-сайдбара (T-0539) каждому залогиненному актору.
- Ни один из новых фетчей не расширяет ЧТО МОЖНО ПРОЧИТАТЬ — оба запроса (`GET
  /api/applications/:id`, кешированный `GET /api/me/nav-capabilities`) уже были легальны для
  того же самого актора ДО этой задачи; здесь их результат просто дополнительно ОТОБРАЖАЕТСЯ
  в двух местах, где раньше не отображался.
- Сама видимость записей (кто что читает/пишет) продолжает решаться ИСКЛЮЧИТЕЛЬНО
  `sandboxReadPredicate`/`decideDraftVisibility` на сервере — фронтенд не получил ни одного
  бита новых прав, только более честные слова вокруг уже существующих прав.

## 5. Альтернативы, отклонённые сознательно

- **Показывать в списке записей «N записей скрыто (черновик)».** Отклонено (см. spec
  out_of_scope): такой счётчик требует привилегированного COUNT, которого сервер сознательно
  не даёт непривилегированному актору — сама цифра «N» уже была бы утечкой факта существования
  и количества чужих данных.
- **Различать в 404 «скрыто» от «не существует».** Отклонено — это ровно то различение,
  которое T-0558 сознательно НЕ делает (иначе актор мог бы перебором id узнавать, какие id
  вообще существуют в приложении).
- **Автопубликация при создании второй записи другим автором.** Не рассматривалось — прямо
  противоречило бы ТЗ («не ломай sandbox-gate»); это была бы не UX-фикс, а снятие гейта.
