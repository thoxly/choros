## 1. FREE-TEXT ЭХО (главный инвариант аудита) — ДЕРЖИТСЯ

Прочитал `summaryForMoved` (audit-read-dao.ts:209-221) построчно:
- `moved = shape.movedKey in p` — оператор `in` возвращает **boolean по факту
  наличия ключа**; ЗНАЧЕНИЕ (`to_parent_id`/`to_department_id`/`to_position_id`)
  никогда не читается.
- `renamed = p["renamed"] === true` — **строгое** сравнение с `true`. Даже
  отравленный `renamed: "<script>"` даёт `false` (не эхоится, только сравнивается).
- Видимый текст = `${shape.subject} ${verb}`, где `subject` ∈ {"Отдел",
  "Должность","Сотрудник"} и `verb` ∈ `MOVE_VERBS` — **всё захардкожено**.
- `from_name`/`to_name`/`from_title`/`to_title` **не читаются ни в одной ветке**
  (moved/renamed/both/neither).

Проекция на провод `toAuditItem` (:291) = `{id, ts, actor, action, summary,
target}`. `payload`/`scope` в вывод НЕ попадают. Значит переименование отдела в
`<script>` или в имя с PII **не всплывает** ни в summary, ни в чипе.
Тест это доказывает ЖИВЬЁМ: audit-log.test.ts:487-514 — `renamed`-строка с
`from_name = REASON_SENTINEL` ("…SSN 123-45-6789") и `to_name = "Новое Имя"` →
summary = "Сотрудник переименован", и `r.raw` НЕ содержит ни того, ни другого.
`safeTargetFromPayload` (:248) читает только allow-list id-ключей — ни один из
org-move-ключей туда не входит, поэтому target для `.moved` падает на `subject`.

## 3. anti-UUID: MonoId-деградация department/position — ЧЕСТНАЯ, не регресс

`safeTarget` для `.moved` падает на `subject` (id узла) → screen-audit.jsx:63
рендерит `<MonoId chip>{ev.target}</MonoId>`. Сравнил с `record.create`:
- `record.create`/`grant.create` target = `record_id`/`grant_id` (UUID из
  allow-list), `targetDisplay = null` → тот же `<MonoId chip>` (regression-тест
  audit-log.test.ts:625, `grant.target === "g-77"` как MonoId).
- **Итог: department.moved/position.moved MonoId — БАЙТ-В-БАЙТ та же глубина, что
  у record.create.** Это честная деградация, а не machine-leak: до фикса эти три
  типа показывали сырой `type`-токен как ВСЮ строку (строго хуже).
- Гейт `anti-uuid-actor-render`: `MonoId` в списке санкционированных обёрток,
  `ev.target` не в списке flagged-полей → нарушения нет. Прогнал main + self-test
  → **PASS/PASS**. `anti-case-lock` main+self → **PASS/PASS**.
- Резолвер имени узла (department/position → NAME) отсутствует (batch — только по
  employee). Это законный **follow-up**, а не блокер (см. finding R-1).

## 4. employee.moved target-резолв — честен на краях

`audit.ts:589-609`: для `employee.moved` `item.target` (empId из `subject`)
добавляется в тот же `batchResolveActors` (та же таблица `employee`, одна
round-trip). `resolveActorDisplay` (actor-resolver.ts:209-223):
- **деактивированный** сотрудник: SELECT берёт `deactivated_at` без фильтра →
  резолвится с `deactivated:true` → ActorChip с маркером (консистентно T-0698/0648).
- **удалённый/нерезолвимый**: honest fallback `{id, name:id, resolved:false}` —
  не "undefined", не падение. Тот же контракт, что у actor-колонки при неудаче.
- **кросс-тенант**: `batchResolveActors` — `WHERE tenant_id=$1` + RLS
  (`SET LOCAL choros.tenant_id`, actor-resolver.ts:123). Чужой target-id не
  матчится → fallback, имя чужого тенанта НЕ утекает. (Плюс subject пишется в
  той же тенант-транзакции — target всегда свой тенант.)

## 5. Матрица summary — честна во всех ветках

moved / renamed / both / neither (пустой payload) — каждая даёт осмысленный
русский через `MOVE_VERBS`, «undefined» невозможно. Пустой payload покрыт тестом
явно (audit-log.test.ts:599 → "Сотрудник изменён", target null). Комбинации
покрыты: employee moved-only/renamed-only/both, department moved-only, position
both. Проверка `renamed === true` защищает от неверного типа.
