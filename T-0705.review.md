## 3. Регресс-тест НЕ тавтологичен (mutation-verified мной)

Сам провёл мутацию: временная копия теста со **свапнутым** порядком регистрации (`registerRightsRoutes` ПЕРЕД resources) → тест `GET /api/rights/resources -> 200` упал **RED** (`expected 404 to be 200`). Копия удалена, дерево чистое. Тест гоняет РЕАЛЬНЫЙ `Router` + реальные хендлеры через живой `http.Server` (stub-pool, без БД) и чувствителен к порядку — не вакуум.

**Non-blocking (F1)**: тест регистрирует два модуля вручную в правильном порядке, а НЕ импортирует `buildRouter` из server.ts. Значит он локирует КОНТРАКТ (resources-до-rights), но не поймал бы автоматически будущий ре-ордеринг самого server.ts. Это ровно та же ограниченность, что у сиблинга CR-9, который он зеркалит — принятая конвенция, не блокер.

## 4. 401 — «артефакт» в основном согласен, но латентная гонка существует (не закрываю слепо)

**Согласен**, что 401 скорее token-timing артефакт: `shell.jsx:1015` `authReady` гейтит первый рендер (и все `useEffect`-фетчи экранов) до завершения KC-бутстрапа/refresh, поэтому 401 на валидной сессии в устойчивом состоянии маловероятен, а живой repro строителя (owner-логин, 0 non-2xx кроме 404) подтверждает чистый happy-path.

**НО механизм гонки структурно есть (F2, non-blocking)**: `authHeaders()` (dev-auth.js:89) в keycloak-режиме возвращает `{}` (БЕЗ Authorization), когда `getToken()` временно null (refresh в полёте). Три админ-экрана (`screen-rights.jsx`, `ra-grant-trail.jsx` = /rights/trail) фетчат **голым** `fetch(url, { headers: authHeaders() })`, а НЕ через T-0608 `fetchWithAuthRetry` self-heal. Транзиентное безтокенное окно или mid-session-истечение → 401 без самолечения. Это не доказанное «нечего чинить» — латентная гонка, follow-up: перевести три экрана на `fetchWithAuthRetry`.

## 6. Внескоуповая находка createHumanUser (actor_type) — РЕАЛЬНЫЙ P1 (высокая правдоподобность)

Оценка по коду — **НЕ ложная тревога**:
- KC **25.0.6** подтверждён (docker-compose.yml:52). В KC25 декларативный user-profile — GA, `unmanagedAttributePolicy` по умолчанию **DISABLED**.
- `createHumanUser` (admin-port.ts:398) ставит `attributes.actor_type=["human"]` через admin REST `POST /users`.
- `config/keycloak/realm-choros.json` **НЕ содержит секции `userProfile`** → `scripts/kc-dev-setup.sh` шаг 5 (строки 233-266, ЯВНО спроектированный «actor_type attribute declared with options validation» через `PUT /users/profile`) попадает в ветку **`[SKIP] no userProfile section`**.
- Итог: `actor_type` остаётся необъявленным/unmanaged → KC25 **молча дропает** его на admin-API create → у UI-созданного юзера в токене логина НЕТ claim `actor_type` → `verifyClaims` (FF-3) отвергает → **401 на всё**.
- Асимметрия «seeded OK / UI-created 401»: fixture-юзеры realm-import пишут атрибуты напрямую (обходя валидацию профиля) — ровно то, что наблюдал строитель. Подтверждается памятью T-0638 («realm-reimport стирает actor_type → 401»).

**Caveat**: не воспроизведено живьём; точное поведение KC (тихий дроп vs 400-reject) зависит от версии/политики — если KC вернёт 400, `createHumanUser` смаппит это в вводящий-в-заблуждение `EMAIL_INVALID`. В любом случае — дефект для UI-созданных аккаунтов. **Уверенность: ВЫСОКАЯ, что это реальный P1** (комментарий самого setup-скрипта доказывает: команда знает, что actor_type НАДО объявлять для KC25 — а realm JSON этого не несёт = дыра). НЕ чинил (вне скоупа).
