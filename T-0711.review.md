## 2. NULL application_id ветка — структурно невозможна, фолбэк fail-closed

Концерн «легаси до 075 с NULL app» СНЯТ: `process_app_binding` СОЗДАНА миграцией
075 c `application_id uuid NOT NULL` (подтверждено на живом PG:
`is_nullable=NO`). Таблицы до 075 не было — NULL-строк не бывает. Ветка
`$3::uuid IS NULL OR …` работает только как no-op-фильтр при отсутствии пина;
даже в гипотетике NULL-строки резолвер падает в `null` (`!isUuid(appRow.application_id)`
→ fail-closed 409), не крашится и не подменяет. Поведение по сценариям:
пин задан → NULL-строка `application_id = $3` даёт NULL → исключена (не находится);
пин не задан → NULL-строка попала бы в ORDER BY, но шаг-2 `application_id = $2`
с NULL → 0 строк → null. Итог: **ветка защитная, не нагруженная; всегда fail-closed.**

## 3. Детерминизм фолбэка — честный

`created_at` = bigint (millis). Две привязки в одной мс (сиды пишут 0, batch-upsert)
→ `created_at` равны → tie-break `id ASC` (uuid, часть PK) даёт ПОЛНЫЙ порядок:
детерминизм между запросами гарантирован. Какая из двух равных выигрывает —
произвольно-но-стабильно (id случаен, не семантичен). Приемлемо как legacy-фолбэк:
реальный фикс — пин (человеческий путь ВСЕГДА пинит, tie-break тогда не важен).
Документировано в ADR §2. db-тест AC-2 прогнал сам: вставка B первой физически
(created_at=200), A второй (created_at=100) → фолбэк устойчиво выбирает A, 5 повторов.
**7/7 на живом PG.**

## 4. Подмена / кросс-тенант — закрыто

db-тест AC-3 (прогнал): валидный-но-несуществующий UUID → `null` (не подмена
другой привязкой). Кросс-тенант — тот же предикат `WHERE tenant_id=$1 AND
application_id=$3`: чужая app-строка живёт под другим `tenant_id`, при $1=свой
тенант даёт 0 строк → null → 409. Плюс FORCE RLS + `SET LOCAL choros.tenant_id`
(резолвер бежит внутри withTenantClient). Утечки нет.

## 5. UUID-guard на HTTP — оба роута

`binding.ts` (rawApplicationId → `assertUuidShape` → 400) и `forms-document-ops.ts`
(идентично). db-тест AC-5c: малформенный → 400 VALIDATION до всякой резолюции
(не 500, не тихий фолбэк). Dual-casing (`applicationId`/`application_id`) как у
`processKey`/`process_key`.

## 6. Агентский шов — паритет с оговоркой (non-blocking follow-up)

document-ops теперь МОЖЕТ принять пин, но не обязан. Человек (FormDesigner)
шлёт `selectedAppId` автоматически; агент — опционально. Асимметрия ДОПУСТИМА
сейчас (у агентов нет app-пикера; при отсутствии пина — детерминированный
фолбэк-старейшая, не случайность), но на 2-привязочном процессе агент без пина
может валидировать против «не той» (старейшей) схемы. Кандидат follow-up:
агент-драйверы/ассистент, работающие с мульти-привязочным процессом, должны
резолвить+передавать `application_id`. Строитель уже осознанно пометил
floor1-editor `/edits` и FormBuilder как «без пикера → фолбэк» (handoff
`not_threaded_by_design`) — для них новый фолбэк детерминированнее прежнего
planner-arbitrary (строгое улучшение).
