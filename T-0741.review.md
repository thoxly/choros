## 1. Split-алгоритм (`splitDisplayName`, `src/keycloak/admin-port.ts:754-762`)

```ts
export function splitDisplayName(displayName: string): { firstName: string; lastName: string } {
  const normalized = displayName.trim().replace(/\s+/g, " ");
  if (normalized.length === 0) return { firstName: "", lastName: "" };
  const spaceIdx = normalized.indexOf(" ");
  if (spaceIdx === -1) return { firstName: normalized, lastName: normalized };
  return { firstName: normalized.slice(0, spaceIdx), lastName: normalized.slice(spaceIdx + 1) };
}
```

Прогнал `AP-8a` (24 юнит-теста файла admin-port.test.ts включают эти кейсы) — все зелёные:
- Пусто/пробелы-only → `{"", ""}` (не должно быть достижимо из продуктового пути — `validateCreateBody` уже требует непустой `display_name` до этой точки — проверил `src/http/user-mgmt.ts:294-297`, подтверждено).
- Один токен (`"Мадонна"`) → дублируется в оба поля. Подтверждено ЖИВЬЁМ (§2 анти-кейс) — KC принимает, ROPC-токен выдаётся.
- Два токена (`"Иван Петров"`) → firstName/lastName корректно.
- 3+ токена (`"Иван Петрович Петров"`) → firstName=первый, lastName=остаток rejoined (`"Петрович Петров"`) — задокументированное, принятое ограничение (patronymic внутрь lastName), не влияет на продукт, т.к. KC firstName/lastName нигде обратно в UI не читаются (проверил: `grep firstName|lastName web/src` — ноль хитов вне тестов).
- Кириллица/латиница/умляут/апостроф/дефис — pass-through без транслитерации, подтверждено юнитами И живой KC-пробой (см. ниже).
- Лишние/множественные пробелы — нормализуются в один пробел до сплита.

Split НЕ ломается ни на одном валидном ФИО-инпуте.

## 2. VERIFY_PROFILE — закрыт ЖИВЬЁМ, воспроизвёл независимо (не доверяя доке)

Не полагался на `docs/live-proof/T-0741-firstname-lastname.live-proof.md` — написал свой скрипт против того же `t-0633-keycloak-1` (:8180), registrar `choros-registrar`:

```
RED  (payload БЕЗ firstName/lastName, точная старая форма):
  POST /admin/realms/choros/users -> 201
```

## 5. displayName опционален / back-compat

`KcHumanUserSpec.displayName?: string` — опционально. В `makeHttpKeycloakUserPort`: `if (spec.displayName !== undefined && spec.displayName.trim().length > 0)` — при отсутствии/пустой строке `userBody` НЕ получает ключи `firstName`/`lastName` вовсе (не пустые строки — отсутствующие ключи), т.е. байт-идентичный payload прежнему поведению. Подтверждено юнитом AP-8b (`"firstName" in body === false`). Единственный незатронутый вызыватель (`register.ts`) не сломан.

## 7. Находки (non-blocking)

### NF-1 (axis 3, робастность) — новая KC-ошибка мисатрибутируется владельцу

**Локация:** `src/keycloak/admin-port.ts:521-525` (уже существующий блок `if (createResp.status === 400) { ... code = "EMAIL_INVALID" ... }`, НЕ изменён этим дифом) + `src/http/user-mgmt.ts:441-443` (мапит `EMAIL_INVALID` → `"email must be a valid email address"`).

До T-0741 этот generic-фолбэк был практически недостижим в обычном потоке (firstName/lastName никогда не слались → KC не могла вернуть `person-name-invalid-character` на них). T-0741 делает его новодостижимым: `display_name`, содержащий символы вроде `<`, `&`, `#`, `(`, `"`, после сплита попадает в `firstName`/`lastName`, где реальный KC 25 (`validations.person-name-prohibited-characters`, подтвердил в `config/keycloak/realm-choros.json`) отклоняет create с `400 error-person-name-invalid-character`. Этот 400 проваливается в тот же generic-фолбэк, что и настоящий невалидный email → владелец видит **«email must be a valid email address»** — неверное поле, реальная проблема (в `display_name`) не названа.

Живой репро (т-0633-keycloak-1, свои прогоны, не из докстрок задачи):
```
lastName='Bot #1'      -> 400 error-person-name-invalid-character
lastName='Menu (Test)' -> 400 error-person-name-invalid-character
lastName='A&B'         -> 400 error-person-name-invalid-character
lastName='Guest"1'     -> 400 error-person-name-invalid-character
```
Обычные ФИО — НЕ задеты (проверил живьём, все 201+токен):
```
"O'Brien", "Petrov-Vodkin", "Müller", "Смирнов-Дашевский", "Иван Петров",
"Оператор №3", "Info@Sales", "Иванов, Иван", "Sales Team"
```

Не blocking, потому что: (а) это активация ПРЕДСУЩЕСТВУЮЩЕГО generic-фолбэка (не новый баг в split-логике, которая сама корректна — см. §1); (б) отказ чистый — `createHumanUser` кидает ДО insert в `employee`, осиротевших записей нет (KC-first поток); (в) обычные человеческие имена (кириллица/латиница/дефис/апостроф/умляут/№/@/запятая) не задеты — проверено широким набором живых проб; (г)核 акцептанс-критерий задачи (закрытие VERIFY_PROFILE-разрыва для нормальных имён) доказан железно.

**Рекомендация:** отдельный follow-up — либо смапить `error-person-name-invalid-character` в собственный код с честным сообщением, называющим `display_name`/поле «Отображаемое имя» (не email), либо провалидировать `display_name` на допустимые символы до вызова KC (аналогично `EMAIL_RE` для email) и вернуть точную `VALIDATION`-ошибку раньше.
