# T-0657 — Audit: slug-resolver determinism (`slug = $ LIMIT 1` without ORDER BY)

Status: SPEC + AUDIT
Stems from: T-0611 follow-up (ADR-T0611-slug-resolve-disambiguation.md) — the
review that fixed `resolveIdBySlug` for `registry_def` cross-app slug collision
flagged that the SAME `slug = $ ... LIMIT 1` pattern likely recurs in other
resolvers (employee / tenant / role / …) across ~10 files, where the query area
may not be covered by a UNIQUE constraint → "first row wins" nondeterminism.

## Task framing (what "nondeterministic" means here)

A slug-lookup that **picks one row** (`LIMIT 1`, or `rows[0]`) is
**nondeterministic** iff the `WHERE` predicate does NOT constrain the search
area to a UNIQUE key of the table. If the predicate columns are a superset of
some `UNIQUE(...)` on the table, the query can match **at most one** row → the
missing `ORDER BY` is harmless (there is nothing to order). Only when two or
more rows can legitimately share the searched slug in the searched area is the
`LIMIT 1` an arbitrary pick.

Three lookup shapes are IMMUNE regardless of UNIQUE coverage:
- **boolean `EXISTS`** — returns true/false, never a row identity, so a
  collision changes nothing observable;
- **PK / id lookup** — `WHERE ... id = $` is unique by definition;
- **full-list SELECT** — no `LIMIT 1`, returns all rows (may be `ORDER BY`ed
  for display); the caller does not depend on a single arbitrary row.

## Conclusion — no undetected nondeterministic resolver

Every row-picking slug lookup in non-test `src/` is already deterministic:

1. **The overwhelming majority** search by a predicate that is a superset of the
   table's UNIQUE key (`employee`/`role`/`department`/`application`/`doc_page`
   → `tenant_id + slug`; `registry_def` → `tenant_id + application_id + slug`;
   `tenant` → global `slug`). At most one row can match → `LIMIT 1` is
   deterministic without `ORDER BY`.
2. **The one `registry_def`-by-slug-without-`application_id` resolver** —
   `resolveIdBySlug` (assistant.ts) — is exactly the site T-0611 already fixed
   with `SlugResolveResult` (`id | not_found | ambiguous`). Every OTHER
   `registry_def` slug query in the codebase already carries `application_id`
   in its WHERE (verified: 6 sites, all with full key).
3. **The two BYPASSRLS cross-tenant resolvers** whose area is genuinely NOT
   UNIQUE-covered (`resolveActorTenant` org.ts:323, `resolveAgentSlugFromAuth`
   org.ts:623) were BOTH already given deterministic `ORDER BY … LIMIT 1`
   tie-breakers in prior tasks (dev-pollution handling; T-0426 belt-and-braces
   over the `UNIQUE(kc_client_id)` index).
4. **The one no-tenant-scope employee lookup** (`humanEmployeeSlugExistsOnClient`)
   is a boolean `EXISTS` (T-0633) — cross-tenant by design, no row identity to
   be arbitrary about.

The T-0611-hypothesised "~10 nondeterministic slug resolvers" **do not exist**.
The pattern that made `registry_def` unsafe (search area narrower than the
UNIQUE key) is unique to that one table+call-site, and it is already fixed.

## Plan

- **Resolvers to fix: none.** Fixing a UNIQUE-covered lookup by adding an
  `ORDER BY` would be pure noise (T-0657 explicitly warns against rewriting the
  ~10 paths "ради красоты"). The two area-uncovered resolvers are already
  ordered; touching them risks regressing their deliberate tie-break semantics.
- **This spec is the deliverable** — the evidence table is the proof that every
  resolver is deterministic, so the audit closes with an audit-only commit and
  a regression-guard test rather than code changes.
- **Regression guard (test):** a unit test that pins the invariant the audit
  established — the SQL of the two representative area-uncovered resolvers
  (`resolveActorTenant`, `resolveAgentSlugFromAuth`) contains a deterministic
  `ORDER BY … LIMIT 1`, so a future edit that drops the tie-break (re-opening
  the nondeterminism) fails a cheap static assertion. This is the durable
  anti-recurrence seam for the class the audit certified.

## Non-goals

- No behavioral change to any resolver (signatures, results, error text all
  unchanged).
- No new `ORDER BY` on UNIQUE-covered lookups (would be dead code).
- No migration.
