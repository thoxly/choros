# T-0673 — Person-поле: resolve-ячейка вместо сырого слага

Родитель: эпик T-0647 E-UX-HUMAN. Продолжение анти-UUID слоя T-0648
(batch actor-resolver + ActorChip + гейт `ci/checks/ux/anti-uuid-actor-render.sh`).

## Дефект

`web/src/screens/records-form.js` `formatCellValue()` — person-тип возвращает
value КАК ЕСТЬ (сырой employee-slug, напр. `e-larina`), в отличие от
`relation`/`file`, у которых есть sentinel (`RELATION_CELL_ASYNC` /
`FILE_CELL_ASYNC`) → caller рендерит async-ячейку, резолвящую имя.
Person-ячейка в списке записей (`screen-app-records.jsx`) и в деталке
(`screen-record-detail.jsx`) показывает голый слаг вместо человеко-имени.

## Механизм (реюз, не второй резолвер)

T-0648 batch actor-resolver на бэке (`src/db/actor-resolver.ts
batchResolveActors`) читает `choros.employee` ОДНИМ запросом и подключается
per-endpoint (audit.ts/inbox.ts/grant-trail.ts вкладывают `actorDisplay` в
СВОЙ ответ) — нет общего клиентского `/api/actors/batch`.

Для записей эквивалентный батч уже существует и используется этим же
экраном: `fetchEmployees()` (`web/src/forms/field-renderer.jsx`) — ОДИН
`GET /api/org` (через `fetchWithAuthRetry` + `devHeaders()`, авторизованный,
с авторетраем на transient 401) отдаёт ВЕСЬ орг-список за один запрос вне
зависимости от числа person-полей/строк на странице. Тот же источник данных
(`choros.employee`), что и `batchResolveActors`, та же slug/id-схема값.
`screen-record-detail.jsx` уже резолвит `record.created_by` этим путём
(T-0608) — переиспользуем тот же паттерн для person-полей записи, а
отображение — через `ActorChip` (тот же T-0648 примитив, что в
аудите/инбоксе/grant-trail), не отдельный компонент рендера имени.

## Acceptance criteria

1. `formatCellValue(value, 'person')` для непустого значения возвращает НОВЫЙ
   sentinel `PERSON_CELL_ASYNC` (симметрично `RELATION_CELL_ASYNC`/
   `FILE_CELL_ASYNC`), а не сырое значение. Пустое/null/undefined → `—`
   (без изменений).
2. Список записей (`screen-app-records.jsx`, autogen-таблица): person-ячейка
   рендерится через `ActorChip` с резолвнутым именем сотрудника. Резолюция —
   ОДИН `GET /api/org` на весь экран/страницу (не на ячейку, не N+1) —
   переиспользует существующий `fetchEmployees()`.
3. Деталка записи (`screen-record-detail.jsx`): та же ячейка/резолюция —
   переиспользует уже загруженный `authorNames`-эквивалент (единая карта
   employee id/slug → {name,...}), не отдельный fetch.
4. Честный fallback: если id не резолвится (уволенный/удалённый сотрудник,
   рассинхрон) — показываем СЫРОЙ СЛАГ (не пустоту, не «—», не выдуманное
   имя) — как ActorChip уже делает для `resolved:false`.
5. Деактивированный сотрудник — ActorChip показывает пометку
   «деактивирован» (переиспользуем `employee.deactivated_at`, уже отдаётся
   `GET /api/org`? — если `/api/org` не отдаёт `deactivated_at`, деградируем
   честно: без пометки, но имя всё равно резолвится; не блокирующий критерий).
6. Кейс-контент (конкретные слаги/имена вроде «e-larina») — ТОЛЬКО в тестах,
   не в `src/`/`web/src/` продуктовом коде.
7. Гейты зелёные: `tsc --noEmit`, `npm run build`, `vitest run` (web),
   `ci/checks/ux/anti-uuid-actor-render.sh`, `ci/checks/anti-case-lock.sh`.

## Не в скоупе

- Kanban-карточки (`kanban-board.jsx`): `formatCellValue` может вернуть
  `PERSON_CELL_ASYNC` (symbol) — существующий код там уже дегрейдит любой
  non-string результат в `—` (см. `typeof rendered === 'string' ? rendered :
  '—'`), это ЧЕСТНАЯ деградация (не regression, не «—» вместо имени в
  местах, где задача требует резолва). Полноценный async-резолв в канбане —
  отдельная задача, если понадобится.
- Общий клиентский batch-endpoint `/api/actors` — не создаём; персон-резолв
  использует существующий `/api/org` (уже батч, уже auth-safe).
