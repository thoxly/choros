## 1. Новый роут гейтнут, держателей не палит — подтверждено чтением + живым PG

`GET /api/rights/intents/substitution-coverage` (`rights-intents.ts` новая функция
`registerSubstitutionCoverage`) обёрнут `withAuth` (аутентификация обязательна, keycloak-режим
требует Bearer JWT — тот же паттерн, что все соседние роуты файла). `extractActor` + `resolveTenant`
резолвят актора/тенант ИЗ токена/дев-хедера, не из query-параметров запроса — клиент не может
подставить чужой tenant_id. Запрос к `role_assignment` идёт внутри `withTenantTx(pool, tenantId, …)`
с `SET LOCAL choros.tenant_id` (тот же RLS-паттерн, что везде в кодовой базе) — чужой роль/тенант
структурно не читается (роль другого тенанта просто не матчит `WHERE tenant_id = $1`, holderSet
пуст → `provides_coverage: false, holder_count: 0`, не 403/leak, но и не чужие данные).

Ответ строго минимален: `{ role_id, substitute_employee_id, provides_coverage: boolean, holder_count: number }`
— **ID держателей НЕ возвращаются**, только агрегат. Прочитал реализацию и подтвердил живым PG-тестом
(`ci/checks/db/rights-intents.db.test.ts`, T-0745 describe-блок, 5/5 своих кейсов зелёные, гонял сам):
держатель → `true`, не-держатель → `false`, malformed UUID/missing params → 400, и explicit-кейс —
**обычный не-админ актор** (`e-t0745-nonholder-*`, без admin-authority) успешно читает эндпоинт (200) —
это осознанный минимальный гейт (нет `loadAdminContext`/`isGenesisOwner`), самосогласованный с тем, что
`registerSelfAbsence`-ЗАПИСЬ уже не несёт admin-гейта на своё окно (self-service паритет: рядовой
сотрудник, заполняющий «Я в отпуске», должен видеть предупреждение о себе же, не только админ).

Единственный оракул, который этот роут даёт рядовому сотруднику — булев "держит ли сотрудник X роль Y"
внутри СВОЕГО тенанта (без списка держателей). Это не новая категория утечки: тот же факт уже был
косвенно извлекаем ДО T-0745 через существующий WRITE (`self-absence`/`substitute` уже возвращают
`tier: "tier1"|"tier2"` в ответе, из которого наблюдательный сотрудник мог вывести то же самое ценой
реальной побочной записи). Новый read даёт тот же сигнал БЕЗ побочного эффекта — не хуже, чем было,
не блокирует. Не blocking, см. non-blocking #1 ниже для дальнейшего ужесточения при желании.

`http-route-auth-coverage.sh` (FF-0328-1/2/3) прогнал сам — PASS, новый роут в перечне
withAuth-обёрнутых файлов.

## 2. Предупреждение честно отражает реальность — подтверждено чтением T-0744 механики

`substituteCoverageWarning` — чистая функция, реюзит булев сигнал `providesCoverage` сервера
(не переизобретает предикат на клиенте). Серверная сторона (`registerSubstitutionCoverage`) буквально
импортирует и вызывает `substituteProvidesCoverage` из `src/core/substitution.ts` (T-0744, файл НЕ
тронут этим дифом) — `substituteProvidesCoverage({ ttlGrantId: null, substituteEmployeeId }, holderSet)`,
т.е. сводится к `holderSet.has(substituteEmployeeId)`. HolderSet строится ТЕМ ЖЕ предикатом
(`confirmed_by IS NOT NULL`, in-window), что уже дважды используется в этом файле для tier-определения
в `registerSubstitute`/`registerSelfAbsence` — минус исключение absent/substitute (осознанно: здесь
вопрос «держит ли САМ замещающий», а не «есть ли третий держатель» — задокументировано в коде и
`T-0745.spec.md §2`). Один источник правды, не второе определение.

Текст баннера («задача уйдёт... владельцу тенанта, роль будет считаться незаполненной») сверил с
РЕАЛЬНОЙ T-0744-механикой в `inbox.ts`: `role_unfilled`-fallback (`resolveExecutorFallbackBatch` →
`makeTenantOwnerFallbackPort` → `findTenantOwnerSlug`) **реально назначает исполнителем владельца
тенанта** (не просто «даёт право заявить» — комментарий в самом `inbox.ts:919` формулирует то же:
«an unfilled role routes to the tenant owner»), а claim/approve-гейт (`isOwnerOrphanClaimEligible`,
T-0744) ограничивает ЭТО право только genesis-owner при реально пустом эффективном пуле — текст не
обещает ничего, чего система не делает. Термин «владельцу тенанта» совпадает с уже устоявшимся в
продукте (`screen-org.jsx`, `screen-users.jsx`).

Текст также не паникует и не обещает автоэскалации — regression-тест
`'never claims the stand-in loses ability to act at all'` в `ra-intents.test.jsx` это фиксирует, и
формулировка честно ограничена случаем опустевшего пула (не «сразу», не «немедленно»). Консистентен
с T-0720/T-0731 дисциплиной (никакого «Tier-N» в видимом тексте, только человеческие термины).

## Non-blocking

1. **[axis 1, `src/http/rights-intents.ts` registerSubstitutionCoverage]** Роут — булев оракул
   «держит ли конкретный сотрудник конкретную роль» без admin-гейта, вызываемый сколько угодно раз
   на любую пару role_id/substitute_employee_id внутри своего тенанта. Не новая категория утечки
   (см. §1 — тот же факт уже извлекаем через существующий WRITE ценой побочного эффекта), и не
   блокирует эту задачу — но если это станет реальным беспокойством, кандидат на будущее ужесточение:
   ограничить `role_id` ролями, которые актор реально видит в своём orgDirectory/self-scope
   (аналог `GET /api/rights/tenant-state`'s self-scope фильтра), а не любой ролью тенанта.
2. **[axis 5, docs/tasks/T-0745.spec.md / commit-сообщение]** Комментарий в коде
   (`rights-intents.ts` header нового блока) и текст коммита ссылаются на «rights-intents.ts:744,1231»
   для существующего `force_tier2` — актуальные номера строк после вставки нового роута сдвинулись
   (747/1314). Косметика, не функциональный дефект.
3. **[axis 6, ra-intents.test.jsx]** Весь файл (не только T-0745-часть) состоит из
   source-string/"source-presence" тестов, не настоящих `@testing-library/react` render-тестов

   T-0745-регрессия). Реальный JSX runtime (проп-тайпо, некорректный map) этими тестами не ловится;
   единственная живая проверка — ручной браузерный прогон по `live_proof_plan` хендоффа, который,
   честно, НЕ выполнен (стенд был офлайн на момент сдачи — сам хендофф это прямо помечает как

   доступном окне на стенде — не blocking для этого вердикта (числа гейтов, которые МОЖНО было
