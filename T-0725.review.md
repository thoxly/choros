## 1. СКОУП-ТРАКТОВКА (главное) — ЧЕСТНАЯ, паритет РЕАЛЕН на уровне шва

Строитель трактовал item (1) «схема тула агента экспонирует applicationId» как
контракт РОУТА (JSDoc), а не новый `ToolDeclaration`. Проверено адверсарно:

- **LLM-тула document-ops НЕ существует.** `assistant-configurator.ts` содержит
  ровно 9 тулов (`CONFIGURATOR_TOOLS`: propose_plan, create_application,
  relate_application, author_binding, edit_jsonschema, emit_form, author_dmn,
  generate_process, request_promote) — ни один не зовёт document-ops. Грепы по
  `document-ops`/`documentOps`/`document_ops` в `assistant-configurator.ts` — 0.
- **Кто вообще зовёт роут?** Греп `forms/document-ops` по `src/` + `web/`: НЕТ ни
  одного вызывающего, кроме регистрации роута в `server.ts`. Человеческий канвас
  (`FormDesigner.jsx`) шлёт `/api/forms/binding`, НЕ document-ops. Значит
  document-ops — чистый машинный HTTP-шов для внешнего агента/MCP/API-интегратора.
  Для ЭТОГО потребителя «схема тула» и ЕСТЬ документированный контракт роута.
- **Инвентить `ToolDeclaration` было бы АРХИТЕКТУРНОЙ ОШИБКОЙ, не факторизацией:**
  ADR-T0656 §4.4 отложил регистрацию document-ops как тула с ДРУГОЙ auth-моделью
  (DRAFT-only с человеческим promote vs прямой патч ОПУБЛИКОВАННОГО
  form_binding.layout под `process_designer`/owner). Смешать их в одном туле =
  рассинхрон контракта. Строитель корректно НЕ стал этого делать.

**Реальный паритет ИЛИ отложен ключевой кусок?** — Паритет РЕАЛЕН для фактического
шва: до фикса агент через document-ops тихо получал старейшую схему; после —
обязан пин или получает честный 422. Асимметрия «человек всегда попадает в свою
схему (пикер структурно шлёт пин), агент может тихо промазать» закрыта на уровне
шва. Отложен НЕ ключевой кусок этой находки, а БУДУЩИЙ LLM-тул-обёртка (которой
нет и которая — отдельная неготовая design-задача). Это честный
PARTIAL-с-обоснованием, а по сути — COMPLETE для реального шва. **НЕ уклонение.**

→ Follow-up (nit N1): когда/если document-ops станет `ToolDeclaration`, схема
того тула должна экспонировать `applicationId` (как T-0700 для author_binding) и
поднимать 422 как ASK-петлю ассистента.

## 2. ДЕТЕКТОР — ТОЧЕН

- Детектор = `listProcessAppBindingCandidates(...).length > 1` И пин отсутствует.
- **Ложных срабатываний на single НЕТ.** Миграция 075:
  `CONSTRAINT process_app_binding_natural_key UNIQUE (tenant_id, process_key,
  application_id)` — ровно одна строка на пару (процесс, приложение). `form_key`
  НЕ в натуральном ключе → «один app + много форм» НЕ даёт лишних строк. Значит
  `count>1` ⟺ строго 2+ РАЗНЫХ приложения. Живьём: AC-d SINGLE без пина → 200.
- **count=1 → no-op**, дальше `classifyLayoutSave(...,null)` → T-0711 фолбэк на
  единственную строку (доказано AC-d live).
- **count=0 → no-op**, существующий fail-closed путь (`resolveLiveRecordSchema`
  → null → 409 WRONG_FLOOR), НЕ 422 — гейт не дублирует. Доказано unit «ZERO
  bindings → 409».
- **Гонка** (привязка добавлена между пре-флайт-COUNT и resolve внутри той же tx,
  READ COMMITTED — по снимку на statement): узкое окно, где 2-я привязка
  закоммичена посреди запроса, всё ещё уйдёт в тихий фолбэк. Доброкачественно
  (одновременное добавление привязки к сохранению формы нереалистично), приемлемо.
  Nit N2, не блокер.

## 3. 422-ОШИБКА — не течёт, читаема

- Пре-флайт стоит ПОСЛЕ `checkRole` (auth) и ВНУТРИ `withTenantTx` — список
  кандидатов виден только аутентифицированному process_designer/owner.
- **Кросс-тенант утечки НЕТ**: `process_app_binding` FORCE RLS + политика
  `tenant_id = current_setting('choros.tenant_id')`; запрос ещё и явно фильтрует
  `WHERE pab.tenant_id = $1`; JOIN `choros.application` тоже tenant-scoped
  (`a.tenant_id = pab.tenant_id`). Двойная защита.
- `applicationId` в message — внутритенантный id, нужен агенту для ретрая (не
  секрет). Имя = `display_name ?? slug ?? id` — человекочитаемо, UUID лишь фолбэк.
